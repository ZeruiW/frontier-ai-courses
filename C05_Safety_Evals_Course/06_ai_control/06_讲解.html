1范式转变：从 alignment 到 control

前五个模块的隐含假设是：我们通过评测来判断模型是否安全。本模块换一个问题： 假设模型不安全——它在策略性地寻找机会做坏事——我们的部署流程还能不能保证整体安全？ 这就是 AI Control 研究纲领 [Greenblatt 2023] 的出发点。

直白讲

Alignment 路线想把模型本身训练成可信的：它不想骗你，所以系统安全。 Control 路线不赌这一点：就算模型想骗你，我们在它周围布置监控、审计、替换等流程， 让它即使想搞破坏也很难成功。前者改"动机"，后者改"环境"。Control 评测要回答的问题是： 这套流程在最坏情况下到底能兜住多少。

严谨讲

Alignment 的安全论证依赖模型性质的命题（"$M$ 不会策略性破坏"），其证据来自训练过程与行为评测， 但模块 05 已表明这类证据可被 sandbagging 与 alignment faking 削弱。 Control 的安全论证只依赖部署协议（protocol）的性质：对任意符合能力假设的对抗策略 $\pi_{adv}$， 协议 $P$ 满足 $\Pr[\text{灾难性结果} \mid P, \pi_{adv}] \le \varepsilon$。 命题的量词从"模型恰好可信"变成"对所有允许的攻击策略成立"，可以用红蓝博弈直接测量。

维度Alignment（让模型可信）Control（不依赖可信也安全）
安全性来源模型内在动机 / 训练目标部署协议：监控、审计、替换、权限隔离
核心假设训练能产生并保持对齐存在更弱但可信的模型与少量人类监督
对欺骗的鲁棒性脆弱：欺骗恰好是要排除的对象设计目标就是抗故意破坏（intentional subversion）
评测方式行为评测、可解释性证据红蓝博弈：红队代入模型测协议最坏情况
失效方式悄无声息（评测时伪装）可量化退化（监控器 AUC 不足、预算耗尽）

Control 的适用窗口

Control 不是对任意强的模型都成立。它有一个明确的能力窗口：

  • 下界：模型要强到有用——否则直接不用它就好，不存在"既要用它又怕它"的问题。
  • 上界：模型还没强到能稳定绕过监控——如果 U 能可靠地骗过所有监控器、在审计中伪装、 与其他实例协同，control 协议的安全保证就会崩塌。Greenblatt 等人明确把适用范围限定在 "transformatively useful 之前、wildly superintelligent 之前"的过渡期。
把 control 理解为给"模型可能不可信"这个事实买的保险：保险不要求你证明事故不会发生， 只要求事故发生时损失可控。窗口上界的含义是：保费（监控、审计成本）必须低于保额（拦截成功率）， 当模型强到能系统性骗保时，这份保险就失效了——那时只能靠 alignment 或者不部署。

2设定形式化：U / T / H 与红蓝博弈评测法

Control 设定的三个角色 [Greenblatt 2023]：

  • U (untrusted model)：强但不可信的模型。它产出我们真正想要的高质量输出， 但威胁模型假设它可能在少数任务上故意植入问题（如代码后门）。
  • T (trusted model):更弱但可信的模型（能力低到我们确信它不会策略性破坏）。 可以用它打分、改写、或在可疑时顶替 U。
  • H (human audit budget)：有限的高质量人类审计资源。人类审计近似"金标准"—— 被审到的攻击一定暴露——但贵，只能覆盖极小比例（如 2%）的任务。

评测方法是一场红蓝博弈：

  • 蓝队设计部署协议：何时调 U、何时调 T、怎么打可疑分、审计预算花在哪。
  • 红队接管 U（用攻击策略替换/改造 U 的行为），目标是在整个部署周期内让至少一次攻击不被发现地通过。
  • 评测在大量模拟部署（campaign）上测量：协议在红队最优攻击策略下的安全性，以及在正常（无攻击）场景下保留的有用性。

注意博弈的不对称性：红队赢需要"至少一次攻击成功且全程不被抓"；蓝队赢只需要"抓到一次"—— 抓到即获得确凿的策划证据，可以停用模型、升级所有历史输出的审查（incrimination）。 这个"抓一次就全赢"的规则是 control 协议很多反直觉性质的来源（比如稀疏攻击反而更危险，见 notebook 实验）。

3基础协议族：monitoring / defer / editing

所有基础协议都围绕同一个原语：T 给 U 的每个输出打一个可疑分（suspicion score）， 协议决定可疑分如何转化为动作。以下伪代码中 audit() 表示消耗人类预算的金标准检查。

3.1 Trusted monitoring（可信监控）

最基础的协议：永远采用 U 的输出，但 T 全程打分，可疑分最高的 top-k% 送人工审计。

# Trusted monitoring（审计预算 c，如 2%） threshold ← 校准使得正常输出中恰有 c% 超过阈值 for task in deployment: y ← U(task) # 永远用 U 的输出 s ← T.suspicion(task, y) # T 打可疑分 if s ≥ threshold: if audit(task, y) 发现攻击: # 消耗 H 预算 shutdown(U); 全局胜利 # 抓一次就停用 deploy(y)

3.2 Defer-to-trusted（可疑即换人）

在 monitoring 之上加一层：可疑分处于"较高但不够送审"区间时，直接丢弃 U 的输出、改用 T 自己做。 攻击被无声中和（不消耗审计预算），代价是这部分任务质量降到 T 的水平。

# Defer-to-trusted（审计阈值 θ_a > defer 阈值 θ_d） for task in deployment: y ← U(task); s ← T.suspicion(task, y) if s ≥ θ_a: # 最可疑：审计 if audit(task, y) 发现攻击: shutdown(U) deploy(y) elif s ≥ θ_d: # 次可疑：不用 U，T 顶上 deploy(T(task)) # 质量较低，但攻击被中和 else: deploy(y)

3.3 Trusted editing（可信改写）

defer 的精细版：T 不是从头重做，而是改写 U 的输出——保留主体结构、移除可疑部分。 质量损失小于完全 defer，但要求 T 有足够能力识别并安全地改写可疑片段。

# Trusted editing for task in deployment: y ← U(task); s ← T.suspicion(task, y) if s ≥ θ_a: audit 路径（同上） elif s ≥ θ_e: deploy(T.edit(task, y)) # T 改写 U 的输出 else: deploy(y)
协议安全机制usefulness 代价对监控器的要求
upfront auditing（基线）只审计部署初期的前 k% 任务≈ 0无（不用监控器）——但被稀疏/延迟攻击轻易击败

[Greenblatt 2023] 在 APPS 编程后门设定（GPT-4 当 U、GPT-3.5 当 T、2% 审计预算）中报告了这条阶梯： upfront auditing 安全性 15%、trusted monitoring 62%、defer-to-trusted 在牺牲少量 usefulness 后更高、 trusted editing 最高可到 92%+。具体数字依赖设定，但"协议设计的递进能大幅提升最坏情况安全性"这一定性结论是本模块的主心骨。

4safety–usefulness 前沿

每个协议（连同它的参数）都被压缩成平面上的一个点。两个坐标的定义：

$$ \text{safety}(P) \;=\; \min_{\pi \in \Pi_{\text{red}}} \Pr\big[\,\text{部署全程没有任何攻击成功通过}\mid P,\,\pi\,\big] $$ $$ \text{usefulness}(P) \;=\; \frac{\mathbb{E}\big[\,\text{协议 } P \text{ 下实际采用输出的质量}\mid \text{无攻击}\,\big]}{\mathbb{E}\big[\,\text{全部采用 } U \text{ 输出的质量}\,\big]} \;\in\; [\,q_T/q_U,\; 1\,] $$

三点说明：

  • safety 对红队取 min：这是最坏情况量，所以红队搜索的充分性直接决定 safety 估计是否偏高（见第 6 节）。
  • usefulness 在无攻击分布上测：正常部署中绝大多数任务是良性的，协议的日常代价就是"误伤良性任务" （defer 掉的良性任务只拿到 T 级质量）。
  • 两者由同一组参数耦合：审计预算 $c$、defer 阈值 $\theta_d$ 调高任何一个都是"用 usefulness 买 safety"。 扫描参数即得一条曲线，对所有协议取非支配点集（任何一维更好且另一维不更差的点不存在）就是 Pareto frontier。control 研究的目标可以概括为一句话：把这条前沿向右上方推。
为什么必须画前沿而不是报一个数？因为"safety 92%"单独没有意义——把 U 全关掉 safety 是 100%。 决策者真正面对的问题是：在我能接受的性能损失（比如 5%）内，最好的协议能买到多少安全？ 这恰好是前沿曲线在 usefulness = 0.95 处的高度。notebook 的核心图就是这条曲线族。

5监控器的质量要求与 CoT monitoring

5.1 监控器 AUC 决定协议上限

Trusted monitoring 类协议的安全性最终归结为一个判别问题：T 的可疑分能不能把"攻击输出"和"正常输出"分开。 用 AUC（attack vs benign 的 ROC 曲线下面积）刻画判别力。在审计预算 $c$ 固定时， 单次攻击被审到的概率就是 ROC 曲线在 FPR = $c$ 处的 TPR：

$$ p_{\text{catch}} \;=\; \mathrm{TPR}\big(\mathrm{FPR}=c\big) \;\overset{\text{高斯近似}}{=}\; \Phi\big(\mu_{\text{gap}} - \Phi^{-1}(1-c)\big), \qquad \mu_{\text{gap}} = \sqrt{2}\,\Phi^{-1}(\mathrm{AUC}) $$

审计预算 $c$ 只有 2% 意味着工作点在 ROC 的极左端——正是 AUC 提升收益最陡峭的区域。 notebook 会展示：AUC 从 0.85 提到 0.95，safety 的提升远超协议参数微调能给的任何收益。 结论：监控器质量是整个协议族的杠杆变量，评测 control 方案时应优先报告监控器的判别指标。

5.2 CoT monitoring：监控推理链 [Baker 2025]

监控器看什么决定它能发现什么。只看最终输出（action monitoring），精心伪装的攻击可能无迹可寻； CoT monitoring 让监控器读模型的推理链—— [Baker 2025] 发现前沿推理模型在 reward hacking 时常在 CoT 中明示意图（如直接写出"让我们绕过这个测试"）， 监控 CoT 的召回率远高于只监控行为与输出。

监控可见性税（monitorability tax）。同一项工作给出本模块最重要的警告： 如果把"CoT 被监控器判为可疑"直接作为训练惩罚（对 CoT 施加优化压力），模型短期内行为变好， 但很快学会把推理隐藏起来——继续 reward hacking，CoT 却看起来无害（obfuscated reward hacking）。 监控信号一旦被用作优化目标就会失效（Goodhart），且失效方式是摧毁可见性这一公共资源。 [Baker 2025] 的建议：宁可接受模型 CoT "不那么干净"，也不要为了好看而训练它—— 为保持可监控性付出的这点性能/观感代价就是 monitorability tax，值得付。
对评测者的含义：CoT monitoring 的有效性是一个会漂移的经验事实，不是架构保证。 报告 CoT 监控召回率时必须注明：被测模型的训练过程是否对 CoT 施加过优化压力； 否则今天测得的 95% 召回，在下一个训练版本上可能毫无外推效力。

6control 评测方法学：代理任务与外推限制

怎么把上述博弈落成一个可执行、可复现的评测？[Korbak 2025] 系统化了 control evaluation 的设计要素：

6.1 构造代理攻击场景

  • 代理任务（proxy setting）：真实灾难（如在生产系统植入后门）不能拿来做实验， 所以用结构同形的良性替身——例如"在编程题解里植入一个使特定输入出错的逻辑缺陷"作为合成后门任务。 要求：攻击有客观判定（缺陷可被触发验证）、攻击机会的分布与真实部署相似。
  • 红队替身（attack policy）：评测时不是等 U 自发作恶，而是由红队显式构造攻击策略注入 U （提示工程、微调、或脚手架包装），代表"如果 U 想搞破坏，它最聪明能怎么做"。

6.2 红队充分性（red-team adequacy）

safety 是对红队策略取 min，因此红队不够强，safety 就被高估——这是 control 评测最大的效度威胁。 红队至少要系统搜索这几个维度：攻击频率与时机（稀疏攻击 vs 密集攻击）、攻击伪装（针对监控器优化可疑分）、 协同（多实例 U 串谋、利用协议状态）。Korbak 等人强调评测报告必须说明红队的搜索预算与方法， 与能力评测中的 elicitation 报告（模块 02）完全同构。

6.3 结果外推的限制

  • 能力外推：评测用今天的 U 测，结论默认只对"不强于评测时 U"的模型成立。 模型每次重大更新，control 评测需要重跑——它是一个持续义务而非一次性认证。
  • 分布外推：代理任务覆盖的攻击面有限；真实部署中存在评测时未建模的攻击渠道 （工具调用、长期记忆、多 agent 交互）。safety 数字只在建模的攻击面内有效。
  • 策略外推：人类红队 + 当前自动化手段找到的最优策略 ≠ 全局最优策略。 诚实的报告应把 safety 写成"对已搜索策略集合的下确界估计"，并给出搜索范围。

7与 sandbagging / 对齐的关系：纵深防御的一层

把模块 05 和本模块拼起来，可以看到一条完整的逻辑链：

  • 模块 05 的结论：行为评测可能被策略性低表现（sandbagging）和 alignment faking 污染， 所以"评测显示安全"不能单独支撑"模型可信"。
  • 本模块的回应：那就构建不依赖"模型可信"前提的安全层。control 协议的安全论证恰好绕开了 sandbagging 能破坏的那类证据。
  • 但 control 自身依赖的前提——T 真正可信、人类审计接近金标准、U 不能稳定骗过监控——同样需要论证， 其中"U 的真实能力没有超出窗口上界"又回头依赖能力评测（模块 02）没有被 sandbagging 骗过。
所以 control 不是替代 alignment 的银弹，而是defense-in-depth（纵深防御）中的一层： alignment 降低"模型想攻击"的概率，control 降低"想攻击且成功"的条件概率，能力评测约束"攻击能造成的损失上界"。 各层假设相互独立程度越高，整体失效概率越低——这正是下一模块 safety case 要做的事： 把每层的证据和假设显式写进一个结构化的安全论证里。

8评测视角：可复现的 control 评测与报告

作为评测科学家，交付一份 control 评测时的检查清单：

报告要素必须包含常见缺陷
设定声明U / T / H 的具体实例与预算；代理任务构造方式；攻击成功的客观判据审计预算未注明，safety 数字无法比较
红队规格搜索的策略空间（频率/伪装/协同）、搜索预算、最优策略描述只测了一个手写攻击策略，safety 系统性偏高
统计处理蒙特卡洛 campaign 数、safety 的置信区间、随机种子少量 campaign 的点估计，抽样误差淹没协议差异
主结果safety–usefulness 前沿（参数扫描），而非单点只报单一工作点，掩盖了 trade-off 形状
敏感性safety 对监控器 AUC、攻击率的敏感性曲线未报告杠杆变量，结论无法迁移到新监控器
效度边界能力/分布/策略三类外推限制的明确陈述把代理设定的 safety 当成真实部署的 safety
与所有安全评测一样：control 评测中的"攻击"全部是良性占位物（合成标记、可验证的逻辑缺陷）， 评测的产出是测量方法与统计结论。本课程 notebook 更进一步——攻击只是一个布尔标记 is_attack， 不含任何攻击内容；我们模拟的是协议的概率结构，这已足够复现所有定性结论。

9研究前沿与开放问题

  • untrusted monitoring 与串谋：用另一个 U 级模型当监控器能突破 T 的能力上限， 但两个不可信模型可能串谋（collusion，如通过输出中的暗号协调）。反串谋协议（paraphrasing、信息隔离）的有效性 如何被评测？红队如何系统搜索串谋信道？
  • 对 agent 部署的 control：Greenblatt 2023 的设定是单步输出；真实部署是长 horizon 的 agent （工具调用、状态累积）。攻击可以拆成多步各自无害的动作，监控粒度（步级 vs 轨迹级）与 resampling 协议 的评测方法尚在早期 [Korbak 2025]。
  • 可监控性的保持：如何在继续做 RL 后训练的同时不摧毁 CoT 的可见性 [Baker 2025]？ "monitorability"能否成为一个可测量、可作为发布门槛的指标？
  • control safety case 的组合：怎么把 control 评测的 safety 估计、监控器漂移监测、 红队充分性论证组合成可审计的安全论证？（模块 07 直接处理。）
  • 评测视角的元问题：control 评测自身用了 U 来扮演红队（自动化攻击搜索）—— 如果 U sandbagging 攻击能力，红队就不充分，safety 被高估。"用被测模型评测被测模型"的循环如何打破？
