1为什么 mAP 不足以衡量 TSR：五个盲区

这一节是本模块的地基，也是 JD 里「Build and maintain evaluation pipelines」那条职责的真正含义——评测流水线的价值不在于「把 mAP 算出来」，而在于算出一组能让团队做对决策的数字。而 mAP 单独拿出来，会系统性地让团队做错决策。要说清这一点，得逐条拆。

盲区①：平均把关键类稀释掉了

mAP 是按类别取算术平均。一个 60 类的 TSR 系统里，「停车让行」和「景点指示」的权重完全相同——各占 1/60。假设某次改动让「停车让行」的 AP 从 0.85 掉到 0.65（掉了 20 个点，这是一次严重的安全回退），整体 mAP 只掉 20/60 = 0.33 个点。

0.33 个点在检测任务里落在种子噪声范围内（C61 模块 01 会讲：同配置不同种子的 mAP 波动典型是 ±0.2–0.5）。也就是说：一次会导致漏检停车让行标志的模型回退，在 mAP 上看起来和「什么都没发生」完全一样，甚至可能被当成正常波动而放行上车。这不是假设，这是用 mAP 做发布门禁的系统必然会遇到的事故模式。

盲区②：与距离/尺寸无关

mAP 对所有目标一视同仁。但 TSR 的全部工程价值集中在远距离：40 米内的大牌子谁都能检出，真正决定用户体验的是「能不能在 80 米外就稳定报出来」（模块 04 算过：100 km/h 降到 60 km/h 需要 165 米的余量）。而按数量算，数据集里 40 米内的大目标往往占多数——它们主导了 mAP，却几乎不携带任何区分度。

盲区③：完全没有时序

mAP 是逐帧独立计算再汇总的。一个每秒闪 15 次的系统和一个稳定输出的系统，只要每帧的框和分数一样，mAP 一模一样。 但前者会让仪表盘上的限速数字疯狂跳变、让下游限速控制反复触发与撤销——这是用户第一眼就会抱怨的缺陷，而它在 mAP 上完全隐形。模块 04 花了整整一节讲迟滞，而 mAP 对迟滞的收益一分钱都不给。

盲区④：precision 是相对量，不反映误检的绝对数量

这一条最反直觉，值得用数字说透。两个系统的 precision 都是 0.95：

系统 A系统 B
每帧平均检出数1.020.0
precision0.950.95
每帧误检数0.051.0
每分钟误检数（30 FPS）901800
工程结论勉强可用完全不可上车

precision 的分母是系统自己的输出量，所以它衡量的是「输出的纯度」，而不是「用户被打扰的频率」。TSR 场景下每帧真值目标数常常是 0（大部分路段没有标志），此时 precision 的分母全是误检，指标行为极不稳定。

盲区⑤：与下游动作脱节

直白说

mAP 的核心是 IoU 阈值。但对下游而言，把一块限速牌的框画得准 0.05 个 IoU，没有任何价值——下游要的是「限速值是多少」和「它管哪段路」。反过来，把「限速 60」认成「限速 80」，无论框画得多准，都是一次可能导致超速的严重错误。mAP 对定位误差高度敏感、对语义错误的代价差异完全盲目——它只知道「分类错了」，不知道「错成 80 比错成 40 危险得多」。

严谨说

更精确地说：mAP 隐含的损失函数是 0/1 损失 + IoU 门限，而 TSR 的真实损失函数是一个asymmetric cost matrix（非对称代价矩阵），且这个矩阵的元素跨越好几个数量级。用一个损失函数训练/选型，再用另一个损失函数决定安全，中间的鸿沟就是所有「离线指标很好、路测很差」的根源之一。COCO mAP@[.5:.95] 甚至把这个问题放大了：它把一半的权重压在 IoU 0.75–0.95 这一段对 TSR 毫无意义的精细定位上。

本节结论不是「mAP 没用」。mAP 是一个很好的「模型能力的单一标量摘要」，适合做研究迭代的快速信号；它不是一个「系统是否可以上车」的判据。 把这两件事分开，就是安全导向评测体系的全部出发点。 面试里被问到「你怎么评价一个 TSR 系统」，如果第一句就是 mAP，基本被判定为只做过刷榜；如果能说出「mAP 做迭代信号、分桶 + 代价敏感 + FP/km + 时序稳定性做发布判据」，这一题就满分了。

2分桶评测：把平均值拆开

盲区①②的直接解药是分桶（stratified evaluation）：不要报一个数，报一张表。TSR 需要的分桶维度是固定的几条，每条都对应一类真实失效模式（模块 03 的四象限）：

分桶维度典型分档为什么必须分对应的失效模式
像素尺寸<16 / 16–32 / 32–64 / ≥64 px工程价值全在小桶，而小桶样本量最少远距离漏检
物理距离>80 / 50–80 / 30–50 / <30 m决策余量直接由距离决定上报太晚
光照白天 / 黄昏 / 夜间 / 隧道出入口ISP 与曝光在这几档行为完全不同逆光、眩光、隧道口过曝
天气晴 / 阴 / 雨 / 雾 / 雪对比度与散射改变目标外观低对比度漏检
遮挡度0 / 1–30% / 30–60% / >60%遮挡是最常见的召回损失来源树叶、车辆、杆件遮挡
类别组禁令 / 警告 / 指示 / 指路 / 辅助安全代价按组差好几个数量级关键类被平均掩盖

直白说

分桶最直接的收益是让「整体 +0.3」这种没有信息量的结论变成可行动的判断。同一个 +0.3，可能是「夜间 +3.0、白天 −0.5」（增强起效了，但白天有轻微副作用，可以接受），也可能是「大目标 +1.0、小目标 −1.5」（模型学会了偷懒，这是必须回滚的）。不分桶你永远分不清这两种情况。

严谨说

但分桶有一个必须正视的统计代价：桶越细，每桶的样本量越少，指标方差越大。AP 是一个比例型统计量，其标准误大致按 1/√n 收缩；一个只有 30 个正样本的桶，AP 的 95% 置信区间宽度可能超过 ±0.15——此时「小桶掉了 0.1」根本不是一个可靠的信号。实践中的两条硬规则：① 每个桶至少 50 个正样本（关键类放宽到 30，但必须同时报置信区间）；② 所有分桶指标都必须带 bootstrap 置信区间，否则团队会在噪声上做决策。

还有一个更隐蔽的陷阱：边缘分布掩盖交互效应。你可能看到「夜间 AP 0.72（还行）」「远距离 AP 0.70（还行）」，但「夜间 ∧ 远距离」这个交叉桶的 AP 只有 0.31——而这恰恰是最危险的场景。一维分桶天然看不到这个。解法是对「安全上最要命的 3–5 个组合」显式建立交叉桶（夜间×远距、雨天×小目标、逆光×禁令类），而不是把所有维度做笛卡尔积（那会让每个桶都没样本）。选哪几个交叉桶，本身就是领域知识的体现。

按实例平均 vs 按桶平均：一个会翻转结论的选择

分桶之后还要决定怎么汇总，而这个选择能直接翻转模型排名。设三个尺寸桶的样本数是 100 / 300 / 600：

小桶 (100)中桶 (300)大桶 (600)micro（按实例）macro（按桶）
模型 A0.800.900.920.9020.873
模型 B0.500.950.960.9110.803
结论A 好 0.30B 好B 好B 赢A 赢
micro 平均（按实例加权）会被样本量最大的桶主导，而数据集里样本量最大的桶通常是「最容易的那一档」——因为近处的大目标又多又好标。于是 micro 平均系统性地奖励「在容易的地方做得更好」的模型。macro 平均（每桶等权）则强行给稀有而关键的桶同等发言权。TSR 的正确默认是 macro，并且对安全关键桶再加权。 面试里能主动指出「micro/macro 的选择会翻转排名」，说明你真的分析过评测代码而不只是读过输出。

3代价不对称：把安全后果写进指标里

盲区①⑤的根本解药，是承认不同的错误代价差好几个数量级，而且不对称。TSR 的代价结构有三层，逐层都不对称：

  1. 类别之间不对称：漏检「停车让行」可能导致闯路口；漏检「景点指示」几乎零后果。二者相差 100 倍以上。
  2. 错误方向不对称：把「限速 60」认成「限速 80」会导致超速；把「80」认成「60」只是保守。同一对类别，两个方向的代价可以差 5–10 倍——这是最常被忽略的一层。
  3. 漏检与误检不对称，且方向随类别翻转：对「停车让行」，漏检远比误检危险；对「限速 30」（出现在高速上），误检导致的急减速反而更危险。不存在一个全局的「recall 优先」或「precision 优先」。

把它形式化：定义代价矩阵 C[c_true][c_pred]（含 c_pred = ∅ 表示漏检、c_true = ∅ 表示误检），系统的risk score（风险分）就是混淆计数与代价矩阵的内积，再除以里程做归一化：

\[\mathcal{R}=\frac{1}{L_{km}}\sum_{c,c'} N_{c\to c'}\; C[c][c'] \qquad(\text{单位：代价 / km})\]

直白说

这个数的用法很直接：它替代 mAP 成为「单一主指标」。它天然把关键类的权重提上来、把无关类的权重压下去，并且量纲有物理意义（每公里承担多少风险），可以跨版本、跨车型比较。而且它对上一节的 micro/macro 之争免疫——代价加权本身就是一种更有依据的加权方式。

严谨说

但必须防住一个真实的失败模式：代价数值不能拍脑袋，否则它就变成了「用一个更不透明的数掩盖分歧」。工业界的正规做法是从下游后果反推，借用功能安全的方法论：HARA（Hazard Analysis and Risk Assessment）按「暴露频率 × 可控性 × 严重度」给每个危害场景定级，FMEA 则从失效模式出发排优先级。代价矩阵应该是这些分析的产物，有文档、有评审、有版本号——而不是某个工程师在配置文件里改的一个常数。

错误典型代价（相对值）理由
漏检「停车让行 / 让行」100可能导致不减速通过冲突点
漏检「禁止驶入 / 单行道」80可能进入逆行车道
限速类低值错成高值（60→80）15直接导致超速
漏检限速牌8维持原速，通常有其他信息源兜底
限速类高值错成低值（80→60）2保守，主要是体验问题
误检一块不存在的限速牌12可能导致无故减速，后车追尾风险
漏检 / 错分指路、景点类0.5几乎无安全后果
用 mAP 选模型会选出「平均好但关键类差」的模型，这不是理论担忧。notebook 里会构造一个真实存在的场景：模型 A 的 mAP 比模型 B 高 0.003（在噪声内），但 A 的风险分是 B 的 1.7 倍——因为 A 在「停车让行」上掉了 25 个点，而这个类只占 60 类里的一个。如果发布门禁只看 mAP，A 会被放行。 这就是「评测流水线」这条职责真正要防的事故。

4工程化的率指标：FP per km 与 per-sign recall

盲区④的解药是换分母。这一节讲两个替换，它们都极其简单，但会立刻改变团队的讨论方式。

替换一：precision → FP per km / per hour

指标分母能不能被刷能不能跨系统比对应用户体验吗
precision系统自己的检出数能——提高阈值就涨不能（分母不同）不对应
FP / 帧标注帧数不能勉强（依赖数据集构成）不直接
FP / km行驶里程（物理量）不能能直接对应
FP / hour行驶时长不能能（但受车速影响）直接对应
MTBF（误报间隔里程）—不能能最直观：「平均多少公里一次」

直白说

「能不能被刷」这一栏是关键。precision 的分母是系统的输出量，所以只要少输出就能把它拉高——把阈值从 0.5 提到 0.9，precision 从 0.90 涨到 0.98，看起来是进步，实际上是把召回砍掉了一半。任何以 precision 为主要目标的优化，都会退化成「提高阈值」。 而 FP/km 的分母是里程，是一个和系统行为完全无关的外生物理量，提高阈值会让 FP/km 下降、同时让 recall 下降——两个数一起动，取舍就暴露出来了，没法自欺欺人。

严谨说

量级感也很重要，这是能在面试里立刻显出手感的地方：FP/km = 0.1 意味着每 10 km 一次误报。一次 30 km 的通勤会触发 3 次无故减速或错误限速显示——用户会在一周内关掉这个功能。量产 TSR 的目标通常是 FP per 100 km < 1，关键类（会触发实际控制动作的）还要再严一到两个数量级。把这个数字记住，比记住任何 mAP 数字都有用。

替换二：per-frame recall → per-sign recall

这是 TSR 特有的、也是最容易被忽略的一个替换。考虑一块牌子在视野里存在 90 帧，系统在其中 12 帧检出：

帧序号 0 ......... 40 ......... 60 ......... 78 ... 90 真值 ████████████████████████████████████████████ (90 帧都有) 检出 ▓▓ ▓▓▓▓ ▓▓ ▓▓▓▓ (12 帧) ↑ 首次检出 @ 52 m per-frame recall = 12 / 90 = 13.3% ← 看起来像个失败的系统 per-sign recall = 1 / 1 = 100% ← 用户视角：这块牌子被识别了 首次检出距离 = 52 m ← 真正决定体验的量 稳定检出距离 = 38 m ← 从这里起 95% 的帧都能检出 **三个数描述的是同一段数据，但导向完全不同的工程结论。**

直白说

per-frame recall 严重低估了一个有时序融合的系统的真实能力——模块 04 讲过，只要有几帧检出并且被正确关联累积，系统就能稳定上报。所以只报 per-frame recall 的评测，会让你去优化一个根本不重要的量（每一帧都要检出），而放过真正重要的量（第一次可靠检出发生在多远）。

严谨说

但反过来也要警惕：per-sign recall 会掩盖「检出得太晚」。一块牌子在 15 米处才第一次检出，per-sign recall 仍然是 100%，可那时候已经来不及减速了。所以 per-sign recall 必须和「首次检出距离的分布」一起报，单独看没有意义。正确的一组是：per-sign recall（有没有）+ 首次检出距离 p50/p90（多远）+ 稳定检出距离（从哪起可信）。 这三个数一起，才完整描述了 TSR 的召回能力。

把这一节浓缩成一条可迁移的判据：一个指标是否值得进发布门禁，先问它的分母是什么。分母是系统自己的输出（precision、平均检出置信度），它就可以被优化行为污染；分母是外生的物理量（里程、时长、物理标志个数），它才是诚实的。 这条判据在推荐系统、语音唤醒、异常检测里同样成立——唤醒词检测的行业标准指标就是「误唤醒次数 / 24 小时」，理由完全一样。

5时序稳定性指标：mAP 完全看不见的那一半

盲区③的解药。模块 04 花了整节讲迟滞、状态机、证据累积，而这些工作在 mAP 上一分收益都体现不出来。要让它们可被度量、可被优化、可进门禁，必须显式定义一组时序指标。以下五个是量产 TSR 的最小集合。

指标定义为什么它重要典型目标
首次检出距离轨迹第一次被上报时的距离（不是第一次检出）决定下游有多少决策余量p50 ≥ 70 m，p90 ≥ 45 m
稳定检出距离最远的 d，使得从 d 起 ≥95% 的帧都在上报「偶尔闪一下」不等于「可用」≥ 50 m
闪烁次数单条轨迹生命周期内上报状态的翻转次数直接对应用户看到的跳变每标志 ≤ 1
误报持续时长一次误报从上报到撤销的时间，报 p50 / p950.1 s 与 3 s 的误报是两种事故p95 ≤ 0.5 s
ID switch / 类别跳变率同一物理标志被换 ID 或换类别的次数跳变会让下游反复重置约束≤ 0.02 次 / 标志

直白说

「首次上报距离」而不是「首次检出距离」这个措辞是刻意的。检出是检测器的事，上报是整个系统的事——模块 04 的 n_init、τ_on、迟滞都作用在两者之间。只测检出距离，等于把时序模块的全部工作排除在评测之外；只有测上报距离，模块 04 的参数才有了目标函数。这也是为什么这两个模块必须连起来读。

严谨说

「误报持续时长」则是迟滞的反面账单。模块 04 里我们用 τ_off < τ_on 换来了闪烁次数的数量级下降，代价正是误报撤销变慢。如果评测里只有「闪烁次数」而没有「误报持续时长」，团队会一路把 τ_off 调到极低——闪烁指标一片绿，而路上的误报会赖着三秒钟不走。 凡是存在此消彼长的一对机制，评测里必须同时有度量两端的指标，否则优化一定会滑向一边。 这条规律远超 TSR，是设计任何指标体系时的通则。

计算这些指标有一个前提常被忽略：你需要「物理标志级」的真值关联，而不只是逐帧框标注。也就是说，标注时必须把同一块牌子在连续帧里的框用同一个 instance ID 串起来（类似 MOT 的标注格式）。如果标注规范里没有这一条，上面五个指标一个都算不出来——而等你发现的时候，数据已经标完了。「评测指标决定标注规范」，这个因果方向必须在项目启动时就想清楚。

一个把时序稳定性讲给非算法同事听的好比喻性说法（不跨域，就用本领域的话）：mAP 衡量的是「系统在每一个瞬间是否正确」，时序指标衡量的是「系统作为一个持续运行的服务是否可依赖」。 前者是照片，后者是录像。而用户和下游模块消费的永远是录像。

6场景化回归集与发布门禁

有了指标，下一步是把它们组织成一个能拦住回退的门禁。核心思想：把模块 03 的每一个失效模式，都变成一个小而专的回归集。

regression_suite/ ├── core/ 通用能力，样本量大，看趋势 │ ├── all_daylight/ 3000 帧 —— 主指标（风险分）在这里算 │ └── all_night/ 1200 帧 ├── failure_modes/ **每个失效模式一个集合，名字就是模式名** │ ├── small_far_60_100m/ 300 帧 门禁：小目标桶 recall 不许跌 │ ├── occlusion_by_vehicle/ 240 帧 门禁：遮挡桶 recall 不许跌 │ ├── backlight_tunnel_exit/ 180 帧 门禁：观察项（样本少） │ ├── billboard_fp/ 400 帧 门禁：**FP/km 硬上限** │ ├── rain_night/ 200 帧 │ ├── variable_e_sign/ 150 帧 门禁：切换响应延迟 ≤ N 帧 │ └── gantry_multi_sign/ 160 帧 门禁：ID switch ≤ 阈值 ├── critical_class/ **安全关键类专项，样本量小但门禁最硬** │ ├── stop_yield/ 220 帧 门禁：recall **绝对不许跌**（硬门禁） │ └── no_entry/ 140 帧 └── temporal/ 必须带 instance ID 的连续片段 ├── approach_sequences/ 80 段 首报距离 / 稳定距离 / 闪烁 └── fp_episodes/ 60 段 误报持续时长 p95 设计原则：**每个集合都要能回答一个具体问题**，而不是「再多标点数据」。 如果一个集合掉点了你说不出该改什么，这个集合就没设计好。

门禁规则要分三档，混在一起会让门禁要么形同虚设、要么天天误报：

档位适用对象规则违反后果
硬门禁（blocking）安全关键类 recall、FP/km 上限、p99 延迟不许跌，容差 = 0（或极小）直接阻断发布，必须修复
软门禁（warning）整体风险分、各分桶 AP跌幅 > 容差 且统计显著 → 需要书面说明与审批阻断，但可由负责人签字覆盖
观察项（tracking）样本量 < 50 的小集合、新加入的场景只记录趋势，不阻断无，但连续 3 次劣化会自动升级为软门禁

直白说

容差必须来自种子方差，而不是拍脑袋。C61 模块 01 会讲：同配置换个随机种子，检测 mAP 的波动典型在 ±0.2–0.5。所以把软门禁的容差设成「跌 0.1 就拦」，结果是门禁天天误报，团队三周内就会学会绕过它——这是门禁系统最常见的死法。正确做法：先跑 3–5 个种子测出该指标的自然波动，把容差设在 2σ 附近，并要求跌幅同时通过显著性检验。

严谨说

而显著性检验用在几十个切片上时，必须做多重比较校正。20 个切片各做一次 α=0.05 的检验，即使模型完全没变，也期望有 1 个切片报「显著劣化」（1−0.95²⁰ = 64% 的概率至少出现一个假警报）。Bonferroni 校正（阈值除以切片数）过于保守，会让真实回退也检不出来；Benjamini–Hochberg（BH-FDR）控制的是「被判为显著的结论中假阳性的比例」，是这个场景的正确工具——notebook 里会完整实现它。

门禁设计里有一条必须写进流程的反直觉规则：门禁必须可以被人为覆盖（override），但每次覆盖都要留下记录、理由和责任人。 一个不能被覆盖的门禁，在遇到「已知原因、可接受的临时劣化」时会阻塞整个团队，于是团队会去修改门禁本身、或者干脆绕开流水线发布——两种结果都比允许覆盖糟糕得多。 而覆盖记录本身就是最有价值的技术债台账：如果同一条门禁被覆盖了三次，那它要么阈值定错了，要么你们有一个一直没修的真问题。

7离线指标与路测体验为什么会背离

这是评测工程师最常被问到、也最难回答的问题：「离线 recall 0.92、FP 很低，为什么车上跑起来一堆误报？」 原因有七条，按实际发生频率排序。

#原因机理怎么验证 / 怎么修
1分母不匹配（最常见、最被忽略）评测集里 80% 的帧含标志，真实道路只有 5%。误检主要发生在无标志的背景帧上，而这类帧在评测集里被严重欠采样按真实里程的帧构成重新加权；或直接用连续路测片段做评测
2帧级 vs 事件级离线数 FP 帧数，用户感受的是 FP 事件数（一次误报 = 连续若干帧）把 FP 帧合并成事件再统计；同时报两者
3时序被忽略离线逐帧算，路上是连续输出；闪烁在离线完全隐形用模块 04 / 本模块第 5 节的时序指标
4工作点不同离线扫整条 PR 曲线取 AP，车上是一个固定阈值永远同时报「固定工作点下的 recall/FP」
5预处理/后处理不一致训练用 PIL、车上用 OpenCV/ISP；resize、BGR/RGB、letterbox 差异逐层对拍（C60 模块 01/04 的方法论）
6采集域漂移评测集是一年前那批相机采的，车上是新 ISP / 新镜头按采集批次分桶评测；新硬件必须新采集
7标注口径 ≠ 用户口径标注把 120 m 外糊成一团的牌子也标了，但用户根本不需要那么远就报把评测的有效距离范围与产品需求对齐

第 1 条值得算一遍账，因为它的量级往往超出所有人的直觉。设背景帧的每帧误检率 q_bg = 0.004、含标志帧 q_sign = 0.001：

\[\text{FP/km}=\frac{f\cdot t}{L}\Big[\pi_{bg}\,q_{bg}+(1-\pi_{bg})\,q_{sign}\Big],\qquad \pi_{bg}=\text{背景帧占比}\]

直白说

评测集里 π_bg = 0.20，真实道路上 π_bg = 0.95。于是评测集报出的「每帧平均 FP 数」是 0.2×0.004 + 0.8×0.001 = 0.0016，而真实道路上是 0.95×0.004 + 0.05×0.001 = 0.00385——相差 2.4 倍。如果你天真地拿离线的 0.0016 去外推一小时路测（60 km、108000 帧），会得到 2.9 FP/km，而实际是 6.9 FP/km。这个 2.4 倍的低估，足以让一个「离线看起来达标」的版本在路测第一天就被否掉。

严谨说

而这个偏差是结构性的、必然发生的，因为标注是按「有目标的片段」组织的——标注供应商没有动力去标一万帧空旷的高速路。所以评测集天然会过采样含标志帧。两条修法：① 显式保留一批「连续里程片段」（哪怕大部分帧没有标志），专门用来测 FP/km，这是唯一诚实的做法；② 如果只能用现有集合，就按真实 π_bg 对两类帧重新加权再汇总。面试里能主动讲出「分母不匹配」这一条，基本可以断定你真的做过评测流水线而不只是跑过 cocoeval。

把这七条压成一句可操作的原则：离线评测集与线上分布的每一处差异，都会在指标上产生一个可估算的偏差；工程师的职责不是消灭差异（做不到），而是知道每一处差异会往哪个方向、偏多少。一个能说出「我们的离线 FP 率大约低估 2–3 倍，因为背景帧欠采样」的团队，和一个只会说「路测和离线对不上」的团队，能力差距是数量级的。

8记分卡与评测流水线：把这条职责做成工程

最后把前七节收成一件可交付的东西：一张记分卡 + 一条流水线。这正是 JD 里「Build and maintain evaluation pipelines」的完整答案形态。

记分卡：一个主指标 + 若干护栏

多目标优化在工程组织里是不可执行的——当有五个同等重要的目标时，任何改动都能找到一个变好的目标，于是所有改动都能被论证为「进步」。唯一的解法是把目标结构化成「一个主 + 若干约束」：

层级指标角色规则
主指标代价加权风险分（/100 km）唯一的优化目标，用于排序模型越低越好；发布看它的相对变化
护栏FP per 100 km（整体 & 关键类）硬约束超过上限 → 直接阻断
护栏安全关键类 per-sign recall硬约束不许跌
护栏端到端 p99 延迟、显存峰值硬约束（来自 C53/C60）超预算 → 阻断
护栏闪烁次数、误报持续时长 p95硬约束超过上限 → 阻断
诊断分桶 AP、混淆矩阵、TIDE 分解不进门禁，用于解释主指标为什么变化必须随每次评测自动产出

直白说

把「诊断指标」和「门禁指标」分开是这张表最重要的设计。门禁指标要少、要稳、要能被无歧义地判定；诊断指标要多、要细、要能定位原因。 把诊断指标塞进门禁，会让门禁充满噪声并被团队绕过；把门禁指标做得太粗，则拦不住真回退。

严谨说

还有一条容易被忽略的工程纪律：评测代码本身必须有单元测试。指标算错是极其常见的事故——IoU 的 +1 边界、类别 ID 的 0/1 偏移、按类别聚合时把空类算成 0 而不是跳过、AP 的插值方式写错……而这类 bug 的可怕之处在于它不会报错，只会让所有决策基于错误的数字。标准做法：用「完美预测」（应得 1.0）、「全空预测」（应得 0.0）、「手算过的小例子」（应得某个精确值）三组合成输入做单元测试——notebook 里的每个指标实现都会配这样的断言。

流水线：让「跑过评测」这件事变成不可跳过的

[数据版本 v] ──┐ [模型 commit c] ─┼──▶ ① 推理（固定 seed / 关 TTA / 固定后处理参数 / 记录环境） [配置 hash h] ──┘ │ ▼ ② 指标计算（评测代码有单测；产出 raw predictions 归档） │ ▼ ③ 切片报告（分桶 × 类别 × 时序，全部带 bootstrap CI） │ ▼ ④ 与 baseline 对比（配对检验 + BH-FDR 多重比较校正） │ ▼ ⑤ 门禁判定（硬 / 软 / 观察三档） ├─ 通过 ──▶ 打包 + 归档 scorecard.json ──▶ 可发布 └─ 不通过 ─▶ 阻断（可 override，但记录理由 + 责任人） 不变量：**「存在一份 scorecard.json」本身就编码了「这个版本通过了评测」这个事实。** 没有 scorecard 的产物一律不允许进入发布流程 —— 用产物的存在性编码验证已通过， 比依赖人记得跑评测可靠得多。
面试里被问「你怎么理解 build and maintain evaluation pipelines」，一个满分的回答骨架是三段：①「评测的目的不是产出数字，是产出正确的决策」——所以先讲主指标/护栏/诊断的分层，以及为什么 mAP 只能做诊断不能做门禁；②「评测本身是要被测试的软件」——讲评测代码的单元测试、数据版本、可复现性、raw prediction 归档；③「评测要贴着线上分布」——讲分母不匹配、连续里程片段、离线-路测偏差的量化。 能把这三段讲完的候选人，实际比能背出 DETR 结构的候选人稀少得多。

9研究前沿与开放问题

评测这个方向的论文远少于模型方向，但正因为如此，它的开放问题密度更高。

  • mAP 的替代与补充：TIDE 把 AP 的损失分解成 Cls/Loc/Both/Dupe/Bkg/Miss 六类，并算出「修好每一类能涨多少 AP」——这是决定下一步做什么的最强工具（C61 模块 02 会完整实现）。LRP error（Localisation-Recall-Precision）把定位误差、漏检、误检合成一个可解释的单一误差量，且不依赖 AP 的插值技巧。Optimal Correction Cost 则从「修正到完美需要多少操作」的角度定义指标——这个视角和本模块的代价加权风险分是同源的。
  • 安全导向的评测框架：ISO 21448 (SOTIF) 关注「功能本身没故障、但因为性能局限导致的危害」，其核心是把场景空间划分成「已知安全 / 已知不安全 / 未知不安全」三象限，并要求把第三象限持续缩小——这与 C58 的数据闭环是同一件事的两种表述。RSS（Responsibility-Sensitive Safety）则试图给出可形式化验证的安全约束。开放问题：感知的性能指标如何严格地映射到系统级安全指标，目前还没有被广泛接受的方法。
  • 不确定性的严格保证：conformal prediction 能在很弱的假设下给出有覆盖率保证的预测集合（例如「以 95% 概率，真实类别在这个候选集里」）。把它用到检测上（框的置信区域、类别集合）是活跃方向，但如何在时序累积后仍保持覆盖保证，仍是开放的——而这恰好是模块 04 贝叶斯累积最需要的理论支撑。
  • 长尾评测的统计功效：稀有类的测试样本可能只有几十个，AP 的置信区间宽到无法做决策。「要检出 0.02 的 AP 变化需要多少样本」这类功效分析（power analysis）在检测评测里几乎没人做，但它决定了你的门禁到底有没有意义。C61 模块 01 会补上这一课。
  • 仿真与重建闭环评测：CARLA 类仿真器的域差太大；而基于 NeRF / 3D Gaussian Splatting 的真实场景重建 + 反事实重放（改变天气、光照、增删标志）是近两年的热点——它有望解决「安全关键场景无法在真实道路上重复采集」这个根本困难。开放问题是重建的保真度是否足以支撑安全结论。
  • 时序稳定性指标没有共识：MOT 领域有 MOTA/IDF1/HOTA，但它们是为「跟踪质量」设计的，不直接对应「输出稳定性」。各家量产团队各用一套（本模块给的五个指标是一个常见组合），学术界尚无统一定义。这是一个真实存在、且明显有价值的空白。
  • 离线-在线 gap 的可预测性：能否从离线数据的分布统计，提前预测某个模型在真实里程上的 FP/km？这本质上是一个分布外泛化的估计问题（unsupervised accuracy estimation 方向），目前的方法在检测任务上都还不够可靠。
