1从模糊到可验收：七步框架里最容易被低估的一步

XPENG 这类面试给出的 system design 题面，几乎从不会是「设计一个满足以下 12 条规格的系统」——更常见的是一句故意留白的话：「你会怎么提升 TSR 的识别效果？」或者更极端的「设计一套交通标志识别系统。」这类问题没有边界：没说是哪一类标志、没说当前的问题出在哪、没说要多快出结果。

这不是面试官偷懒——故意留白本身就是考点。面试官想看到的是：拿到一个没有边界的问题时，你的第一反应是「立刻给方案」还是「先划边界」。C63-00 §4 的失败模式①「直接跳到模型」，本质上就是没有做本节要讲的这件事。

「需求澄清」在七步框架里排第一，但它的分量常常被低估——很多候选人把它当成寒暄，问一两句「大概是什么场景」就急着往下讲方案。本模块要讲清楚：需求澄清不是走过场，它的产出是一份「可验收规格」——一份写下来之后，你和面试官都能判断「这个方案到底算不算做到了」的具体描述。

模糊需求（面试官原话）可验收规格（你澄清后应该拿到的东西）
「提升 TSR 识别效果」「在保持误报率不超过当前水平的前提下，把 30 米外限速牌的召回率从 82% 提升到 90% 以上，验收方式是分距离分桶评测（见 C55-05），上线前离线回归门禁不低于门槛」
「设计一套交通标志识别系统」「面向 L2 辅助驾驶，覆盖国标 GB 5768 全部大类，检出距离 ≥60m，端到端延迟预算 ≤20ms，第一版不处理电子可变限速牌，漏检安全关键类的代价是漏检普通指路牌的 10 倍以上」

直白说

换个说法：面试官抛给你的是一个「未完成的句子」，你的任务不是把它补完成一个具体架构，而是先把这个句子本身补完整——谁在用、什么场景、怎么算好、怎么算差、差了代价多大、有什么限制、以及同样重要的——明确声明这一版不管什么。这七件事没搞清楚之前，任何架构图都只是在猜。

严谨说

这也是本课与 C65-04（模糊问题与需求澄清）的分工所在：C65-04 讲的是通用的「把开放题收敛成有边界的题」的方法论，适用于任何面试场景；本模块讲的是这套方法论在 ML system design 面试里的专属落地——包括为什么指标要分三层、为什么代价不对称决定了工作点、为什么「不做什么」要在这一步就明确说出来。两者互相引用，C65-04 不重复讲三层指标映射，本课也不重复讲通用的收敛技巧。

下面 §2 给出一份可以直接套用的提问清单；§3–§4 展开这份清单里分量最重的一项——「什么算成功」——因为它不是一句话，而是一整套需要相互印证的三层指标；§5–§8 依次讲代价不对称、预算写下来、范围裁剪与非功能需求。

2澄清问题清单：七个必问维度

下面这张表是把「需求澄清」拆成七个可以逐一发问的维度。不要把它当成审问清单一次性甩给面试官——真实对话里你会在讲方案的过程中穿插着问，但七个维度都要在设计完成前被回答过，缺一个都是隐患。

维度问题模板为什么必须问TSR 场景的一个可能答案
① 用户是谁 who「最终使用者/下游消费方是谁？是终端乘客、还是内部系统？」决定输出形态与评测标准——给人看和给下游算法消费是完全不同的接口下游是规控模块与 VLA 感知接口（见 C59-03），不是人眼直接看
② 什么场景 scenario「在什么条件下运行？白天/夜晚？城市/高速？哪个地区的标志体系？」场景直接决定数据分布、延迟预算与失效模式的权重（见 C55-03）覆盖国标 GB 5768，城市与高速都要，且要考虑逆光与夜间（见 C55-03）
③ 什么算成功 success「用什么指标衡量？达到多少算达标？」没有成功定义，后面所有取舍都无法判断对错——见 §3 三层指标映射见 §3，这里不能只回答一句「mAP 要高」
④ 什么算失败 failure「错误具体长什么样？漏检、误检、错分、定位不准，还是响应太慢？」不同失败形态需要完全不同的应对策略（呼应 C55-03 的四象限框架）「漏检『停车让行』」和「把广告牌误检成限速牌」是两种性质完全不同的失败
⑤ 失败的代价 cost「漏检一次和误检一次，代价量级差多少？」决定工作点怎么选——见 §5 代价不对称漏检安全关键标志的代价，通常是漏检普通指路标志的一个数量级以上
⑥ 有什么约束 constraints「延迟预算、算力、数据规模、标注预算、团队规模、上线时间线？」决定建模与部署的可行集，而不是「理论最优集」车端 SoC 算力有限、延迟预算要留给后续融合与决策（见 C60）
⑦ 什么不做 non-goals「第一版明确不做什么？」范围裁剪本身是加分项——见 §7第一版不处理电子可变限速牌、不做跨相机融合

直白说

这七个维度不是任意顺序都行——「什么算失败」必须先问，「失败的代价」才有意义：如果你不先枚举清楚错误会以什么形态出现（漏检？错分？延迟超标？），代价矩阵根本无从谈起。同理，「有什么约束」问在「什么算成功」之后更合理——先确定目标，再确定在什么条件下追这个目标，这样约束才不会变成「先射箭再画靶」的借口。

严谨说

严谨地说，这七个维度分别对应一份规格文档里必须有答案的七个字段：stakeholder、context、success_metric、failure_taxonomy、cost_matrix、constraints、explicit_non_goals。notebook 里的问题清单生成器会把这七个字段的默认问题模板打出来，并检查一次设计演练的记录里是否每个字段都留下过至少一句话的答案——这就是「可验收规格」的可操作定义。

问约束不是浪费时间，是加分项——但要问得具体。「有什么限制吗」这种笼统的问法，面试官往往只会回一句「你觉得呢」，因为它没有给出具体的选项。更好的问法是给出候选项：「延迟预算大概是几十毫秒还是几毫秒？这决定了我要不要考虑级联架构」——具体的问题本身就在展示你已经知道这个约束会如何影响后面的设计。

3三层指标映射：业务指标 → 模型指标 → 系统指标

「什么算成功」这个问题的完整答案，从来不是一个数字。真正专业的回答是一套三层结构——业务真正关心的结果、模型在数据集上的统计表现、系统在部署环境里的实际行为——三层各自独立存在，缺了任何一层都会让「成功」这个词变得空洞。

┌───────────────────┐ ┌───────────────────┐ ┌───────────────────┐ │ 业务指标 │ │ 模型指标 │ │ 系统指标 │ │ business metric │◀────▶│ model metric │◀────▶│ system metric │ │ │ 映射 │ │ 映射 │ │ │ 安全事件率 │ 且 │ mAP / 逐类召回率 │ 且 │ 端到端 FP/km │ │ 用户投诉率 │ 经常 │ 逐类精确率 │ 经常 │ P99 延迟 │ │ 接管次数 (呼应 C59) │ 背离 │ 校准误差 ECE │ 背离 │ 误报持续时长(见C55-05)│ └───────────────────┘ └───────────────────┘ └───────────────────┘ ▲ ▲ ▲ │ │ │ 产品/安全/法务关心 算法工程师关心 SRE/系统工程师关心 关键提醒：箭头不是"公式换算"，是"需要人为验证一致性的假设"—— 模型指标涨了，不代表业务指标一定跟着涨（见 §4）
层级定义谁通常关心TSR 场景的具体形态
业务指标
business metric		直接影响业务结果、通常以人或滚动周期为观测单位的指标产品负责人、安全团队、法务/合规因漏检导致的安全事件率、因误报导致的急刹次数、用户投诉率
模型指标
model metric		模型在给定评测数据集上的统计表现，静态、可复现算法工程师mAP、逐类召回率/精确率、校准误差 ECE
系统指标
system metric		整个系统在真实部署环境下的实际表现，包含级联与工程因素SRE、系统集成工程师端到端 FP/km（见 C55-05）、P99 延迟、首次检出距离、误报持续时长
三层不是同一件事的三种叫法，是三种不同的度量对象。模型指标衡量的是「这个函数在这批数据上表现如何」——它是静态的；系统指标衡量的是「这套流水线在真实世界的时间轴上表现如何」——它是动态的，还叠加了跟踪、融合、级联带来的额外误差（见 C63-00 §5 的链式相乘）；业务指标衡量的是「这一切最终有没有改善真实世界的结果」——它甚至可能被非模型因素（比如司机本身的注意力）稀释。能一次说清楚这三层，是「成功指标」这一格能拿到高分的关键。

直白说

面试里怎么用？被问「这个系统怎么算成功」时，不要只回答一个模型指标——按三层说一遍：「业务上我们想降低因交通标志漏检导致的接管次数；这会体现在模型指标上，我们要求安全关键类别的召回率不低于 X；但光看模型指标不够，系统上线后我们还要看端到端的 FP/km 和 P99 延迟有没有落在预算内。」——这一句话同时拿到了「成功指标」维度的满分。

严谨说

更严谨地说，三层指标之间理想情况下应该存在一个单调的因果链：模型指标的改善 → 系统指标的改善 → 业务指标的改善。但这条因果链在实践中经常断裂——断裂的具体原因是下一节要展开的内容，也是很多候选人只会说「指标好了」却说不出「好了会不会真的反映在业务上」的地方。

4指标为什么会背离：五个根因与一个数值例子

三层指标之间的因果链断裂，不是偶然，是五类结构性原因造成的——把这五类原因背下来，比背「三层指标」这个名词本身更有面试价值，因为它能回答追问「你怎么知道模型指标涨了，业务指标就会跟着涨」。

背离原因具体表现怎么发现怎么应对
① 评测集分布与真实分布不一致
selection bias		评测集里稀有但高代价的类别被低估（呼应 C58-01 长尾），模型指标看起来很好，实际业务里这些类别更常见对比评测集与线上流量的类别先验分布分层重采样、按真实先验重新加权评测（见下方数值例子）
② 指标定义的隐含假设不同模型指标按「图像」计数，业务/系统指标按「事件」计数——同一目标被多帧重复检测，在系统层会被去重（见 C55-04 时序融合），模型指标不体现这个去重追问「这个指标的分母/分子到底数的是什么单位」在报告指标时显式写清楚统计单位（每图像 / 每目标 / 每公里）
③ 时间尺度不同模型评测是某个时间点的离线快照；业务指标是长期滚动的，会被之后的数据漂移侵蚀对比模型上线时与上线 3 个月后的系统指标趋势定期重新评测 + 监控数据漂移（呼应 C58-05 闭环验证）
④ 阈值/工作点不同模型报告用的是默认阈值（比如 0.5）算出来的指标，但系统实际跑在另一个工作点（见 §5）核对报告指标时用的阈值和线上配置的阈值是否一致报告指标时必须连同工作点一起给出，不能只给一个脱离阈值的数字
⑤ 复合误差
compounding error		系统是多级级联的（检测→跟踪→融合），模型指标只衡量单级，系统指标是各级复合后的结果见 C63-00 §5 的链式相乘公式 $R=\prod r_i$报告系统指标时用端到端的复合结果，而不是单级指标

一个可以在 notebook 里复现的数值例子

假设某 TSR 模型对六类标志的逐类召回率（模型指标）是固定的：限速牌 97%、停车让行 95%、让行标志 93%、临时施工牌 65%、电子可变限速牌 55%、其他指路牌 90%。评测集里这六类的占比大致均衡（分别为 40%/25%/15%/5%/2%/13%），按此算出的加权平均召回率是 92.55%——这是你在评测报告里会看到的数字。

但真实路测流量的类别占比不同：电子可变限速牌在真实道路上更常见（占比从评测集的 2% 升到 5%），临时施工牌略少见一些。用真实占比重新加权，加权召回率是 92.71%——甚至比评测集上的数字还略高，看起来一切正常。但如果按「业务代价」而不是「召回率」加权——临时施工牌与电子可变限速牌漏检的安全代价分别是普通标志的 8 倍与 10 倍——加权后的业务代价从 0.278 涨到 0.349，相对上升了 25.5%。

模型指标几乎没变（92.55% → 92.71%，甚至还涨了 0.16 个百分点），业务代价却涨了 25.5%。如果你只报告「加权召回率」，会给出一个「系统变得更好了」的错误结论——因为召回率的加权方式（按样本数量）恰好抵消了低召回类别，而业务代价的加权方式（按数量 × 代价）放大了这些类别。这正是「模型指标」与「业务指标」背离的一个真实机制，而不是抽象说法。

直白说

这个例子的教训不是「电子可变限速牌的模型不好，赶紧去优化它」——那是下一步的工程决策。这里的教训是：只报告一个整体指标（无论是召回率还是 mAP）永远不足以回答「业务变好了没有」这个问题，必须同时看「按真实分布重新加权」和「按代价重新加权」这两个动作分别得出的结论是否一致。

严谨说

更一般地，这是一致性检查（consistency check）的核心思路：拿同一份逐类表现数据，分别用「评测集分布」「真实分布」「代价加权」三种权重算一遍汇总指标，如果三者的相对变化方向不一致，就说明存在 §4 五个根因里的某一个，需要在设计里显式指出，而不是等上线三个月后被业务方追问「为什么模型指标很好，用户还在投诉」。

5代价不对称与工作点选择

有了 §2 的「失败的代价」这个答案，下一步是把它变成一个可以计算的代价矩阵，再用它去选一个具体的工作点（决策阈值）——这一步经常被跳过，候选人讲完模型就直接跳到部署，却没有回答「阈值到底设多少」这个所有真实系统都必须回答的问题。

预测 \ 真实真实为正（有标志）真实为负（无标志/其他类）
预测为正TP：正确检出，代价≈0FP：误检，代价 = $c_{FP}$（比如广告牌被误识别成限速牌，引发不必要减速）
预测为负FN：漏检，代价 = $c_{FN}$（比如漏检『停车让行』，安全风险极高）TN：正确忽略，代价≈0
\[\mathbb{E}[\text{cost}](t) \;=\; c_{FP}\cdot \#\{FP \mid \text{threshold}=t\} \;+\; c_{FN}\cdot \#\{FN \mid \text{threshold}=t\}\]

阈值 $t$ 越低，模型越倾向于「宁可信其有」——FN 变少、FP 变多；阈值越高则相反。最优工作点就是让上面这个期望代价最小的 $t$，而它完全由 $c_{FP}/c_{FN}$ 这个比值决定。notebook 里会用一组合成分数做网格搜索，验证一个关键结论：当 $c_{FN}$ 相对 $c_{FP}$ 越大（漏检代价远高于误检代价），最优阈值越低——这正是「漏检安全关键标志代价高」这句话翻译成工程语言后的样子。

面试里的标准表述：「因为漏检『停车让行』的代价远高于误检一个广告牌，我们不会用一个全局统一的置信度阈值——安全关键类别应该用更低的阈值（宁可多报警，也不能漏掉），非安全关键类别可以用更高的阈值来控制误报率。这是cost-sensitive threshold selection（代价敏感的工作点选择），具体的评测方法见 C55-05。」——能说出「不同类别用不同阈值」这一句，是这个知识点里最容易被面试官追问、也最容易拿满分的一句话。

直白说

很多人以为「选阈值」只是模型训练完之后调一个超参数的小事，其实它是需求澄清阶段就该定下来的产出——因为代价矩阵本身来自业务方（哪个错误更致命是产品/安全团队的判断，不是算法工程师能凭空决定的）。如果你在建模阶段才第一次讨论「阈值怎么设」，说明代价这件事在澄清阶段就没问清楚。

严谨说

严谨地说，工作点选择还要考虑约束条件而不是纯粹的期望代价最小化——比如「FP 率不能超过每小时 N 次」这类硬性 SLA（见 §6），此时问题变成「在满足 FP 约束的前提下最大化召回率」，是一个带约束的优化，而不是无约束的期望代价最小化。面试里能区分这两种表述，会显得对生产系统的理解更深一层。

6SLA、延迟、吞吐、成本、功耗：为什么要在开场就写下来

七步框架的第⑥步「服务与部署」会深入讲容量估算与延迟分解（见 C63-04）；但本节要强调的是一个更早的动作：在需求澄清阶段，就把这些数字当成「设计的输入」写下来，而不是留到设计快结束时才顺带提一句。

直白说

怎么在面试里用？拿到题目后，紧跟在 §2 的「有什么约束」问题之后，主动把关键数字复述一遍并写在白板角落：「确认一下：端到端延迟预算 20ms、这一版不追求多相机融合、硬件是现有车规 SoC」——这样后面每一次给出方案时，都可以直接对照这几个数字自我检查，而不是讲完了被面试官反问「这样延迟会不会超」。

严谨说

这也是为什么本课建议把预算写在白板最显眼的位置，而不是记在脑子里——45 分钟里认知负荷很高，一份写下来的预算表能让你在后续任何一步都能快速回头核对，这本身就是「取舍显式」这个评分维度的直接体现。

7范围裁剪：先明确说「不做什么」是加分项

很多候选人下意识地回避说「不做什么」，担心显得能力不够、格局不够大。这个直觉是错的。一个试图在 45 分钟里设计出「完美系统」（覆盖所有场景、所有边缘情况）的候选人，几乎必然会在某个环节被时间追着走，最终什么都讲得很浅——这正是七步框架时间预算表（C63-00 §3）反复强调的风险。

「不做什么」的例子（TSR 场景）为什么第一版明确排除什么条件下会被重新纳入
电子可变限速牌（LED 显示）识别逻辑与静态标志完全不同（需要处理刷新率、亮度变化），属于独立子问题静态标志召回达标、且产品明确要求覆盖电子牌场景时
跨相机融合（广角+长焦）增加大量工程复杂度（标定、时间同步），且单相机方案可能已经满足首版指标单相机在远距离检出上遇到瓶颈、且有多相机硬件预算时
与高精地图联动做先验融合依赖地图团队的接口与更新频率，是另一个团队的产出地图接口稳定、且有专门的项目排期时
罕见区域性标志（如某些国家特有形状）训练数据几乎没有，强行覆盖会拉低整体精度且浪费标注预算明确要拓展到该地区市场时，作为独立里程碑
「不做什么」必须具体，不能是「我们先做一个简单版本」这种空话。面试官想听到的是「明确排除 X，因为 Y，如果 Z 条件满足会重新评估」——这既展示了你理解问题的全貌（知道 X 存在），又展示了你会做取舍（决定现在不做 X），还展示了你不是拍脑袋排除的（给出了重新纳入的条件）。三句话缺一个，这一格就只能拿到及格分。

直白说

范围裁剪和 §2 的「什么不做」问题是同一件事的两个时刻——§2 是在澄清阶段问出来，本节是在讲方案时主动声明。两者缺一不可：如果面试官没有主动问，你也应该在讲方案的开场主动说一句「为了在时间内讲完核心设计，我先明确这一版不做 X 和 Y」。

严谨说

从工程角度看，范围裁剪的本质是把一个无穷维的设计空间投影到一个可以在预算（时间/算力/团队）内完成的子空间。拒绝显式做这件事，不会让问题变简单，只会让复杂度被隐藏起来，最终在某个你没预料到的环节（通常是评测或部署）以更贵的方式重新出现。

8非功能需求：可解释、合规、隐私、可回滚

除了「模型准不准」这个功能性需求，一套完整的可验收规格还要覆盖四类非功能需求——它们通常不会被面试官主动提起，主动提到它们本身就是加分项，因为这是区分「做过研究」和「做过真正上线的产品」的一条分界线。

维度问题TSR 场景的具体体现
可解释性
interpretability		系统做出判断后，能不能说清楚「为什么」？为什么这一帧减速了——需要能追溯到具体检出的标志与置信度（呼应 C59-04 的可解释输出）
合规
compliance		是否满足所在地区的法规要求？不同国家的标志法规体系不同（GB 5768 / Vienna 公约 / MUTCD，见 C55-01），跨区域部署需要额外的合规校验
隐私
privacy		采集与存储的数据是否涉及个人信息？车辆采集的画面可能包含行人面部与车牌，需要脱敏处理才能用于训练与回传（呼应 C58-04 的数据挖掘基础设施）
可回滚
rollback		新版本出问题时，能不能快速退回上一个版本？模型/配置必须有版本管理，回滚不应该需要重新走一遍完整发布流程（呼应 C63-00 §5 与 C63-05 案例演练）

直白说

这四项容易被误认为是「上线后才需要考虑的事」，但它们本该在需求澄清阶段就被提出——因为隐私合规可能直接约束你能用什么数据（比如某些数据不能出境、必须先脱敏才能标注），而这会反过来影响 §2 的「有什么约束」和后续 C63-02 的数据系统设计。

严谨说

严谨地说，非功能需求和功能性需求的关键区别是：功能性需求可以用一个具体指标验收（召回率是否达到 90%），非功能需求往往需要用一套流程或清单来验收（是否有脱敏流程、是否有版本回滚开关、是否有可解释的日志）。面试里能提到这一点，说明你理解「验收」这个词本身在两类需求下的含义是不同的。

不用四项全部展开——挑和场景最相关的一到两项讲透，比每项都说一句空话更值钱。对 TSR 这个场景，可解释性与可回滚通常是关联度最高的两项（安全相关系统的判断必须可追溯，出问题必须能快速兜底）；隐私合规在数据采集与标注阶段更相关（呼应 C58），如果面试聚焦在感知系统设计本身，可以一句话带过再收尾，把时间留给核心设计。

9研究前沿与开放问题

最后放一组更长期的问题——它们超出一次 45 分钟面试的范围，但会影响你怎么看待「需求澄清」这件事本身。

  • 三层指标的一致性检查还没有标准化的工具链。业界普遍认可「模型指标不等于业务指标」这个结论，但把它变成一套可以自动运行的一致性检查（而不是每次上线前靠人工讨论）仍是各家自建、缺乏公开标准的领域。本模块 notebook 里的一致性检查函数只是一个最简版本，真实系统需要更细的分桶与统计功效分析（见 C61-01）。
  • 代价矩阵本身的不确定性常被忽略。§5 假设 $c_{FP}$、$c_{FN}$ 是已知常数，但现实中「漏检一次的代价」本身很难精确量化（安全事件的期望代价涉及概率乘以后果，且后果分布是重尾的），用点估计的代价矩阵做工作点选择，本质上是对一个不确定量做了一次简化——这个简化在什么条件下会失效，是一个仍在被讨论的问题。
  • 「不做什么」的边界会随着系统演进而移动，但很少有团队系统性地复盘「我们当初排除的东西，现在该不该重新纳入」。范围裁剪的决策记录（为什么排除、什么条件下重新评估）很少被当作一等公民的工程产物来维护，这和 C58-05 的数据版本与血缘管理面临的是同一类「决策可追溯性」问题。
  • 非功能需求的验收正在从「人工清单」向「自动化门禁」演进（比如把隐私脱敏、可回滚开关做成 CI 流水线里的强制检查项，呼应 C37 的 MLOps 生命周期），但可解释性这一项的自动化验收目前仍然主要依赖人工评审，还没有被广泛接受的自动化标准。
