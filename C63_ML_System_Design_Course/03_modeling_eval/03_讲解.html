1建模与评测在七步框架里的位置：为什么顺序颠倒是常见扣分项

模块 00 给出的七步框架是「① 澄清与范围 ② 成功指标 ③ 数据 ④ 建模 ⑤ 评测 ⑥ 服务与部署 ⑦ 迭代与风险」。本模块讲第 ④ 步和第 ⑤ 步——但真正要讲透的不是「有哪些模型」「有哪些评测方法」，而是为什么这两步经常被候选人在无意中颠倒或跳过，以及面试官是怎么当场发现这件事的。

一个极其常见的开场是这样的：面试官刚讲完场景，候选人立刻说「这个我会用一个 Transformer-based 的检测器，配合多尺度特征融合……」——模型架构被第一个说出口，而数据长什么样、拿什么当基准、怎么判断这个模型真的比现有方案好，一个字都还没提。这不是知识不够，是顺序错了。

七步框架里，第④⑤步内部还有一个更细的强制顺序： ④ 建模 ⑤ 评测 ┌───────────────┐ ┌───────────────┐ │ ④a baseline │──必须先做完──▶ │ ⑤a 离线评测 │ │ 最简可行方案 │ │ 方案先定义 │ └───────────────┘ └───────────────┘ │ │ ▼ ▼ ┌───────────────┐ ┌───────────────┐ │ ④b 约束驱动 │──有了baseline──▶│ ⑤b 用同一套 │ │ 选型/迭代 │ 才有对照物 │ 评测方案裁决 │ └───────────────┘ └───────────────┘ 常见的错误顺序：④b（直接谈新颖架构）→ 从未做 ④a → ⑤ 评测无从谈起（没有对照物） 正确顺序： ④a（先定 baseline）→ ⑤a（先定评测方案）→ ④b/⑤b 交替迭代

直白说

直白地说：如果你都不知道「什么都不做」或「用最简单的办法」能拿多少分，你怎么向别人证明你那个更复杂的模型「真的更好」？没有基准和没有评测方案，复杂模型的收益就是一句无法被验证的断言。

严谨说

更严谨地说，这是一个可证伪性（falsifiability）问题：一个不能被拒绝的主张不是工程判断，是信仰。建模（④）和评测（⑤）互为前提——建模需要评测方案才能判断迭代方向对不对，评测方案需要至少一个基准模型的产出才有东西可评。面试官正是通过「候选人有没有主动建立这个互为前提的闭环」来判断此人是否具备可独立负责一个建模任务的成熟度。

「我会用 X 模型」不是一个好的开场白，除非紧跟着一句「不过我会先做 Y 当基准，用 Z 这套评测方案来判断 X 是否真的比 Y 好」。前半句展示的是知识储备，后半句才展示的是工程判断——而后半句恰恰是大多数候选人会跳过的部分。

2baseline 优先原则：为什么跳过它是最常见的扣分项

先给最简单、最快能跑起来的方案，再谈复杂模型——这条原则听起来是常识，但在真实面试记录里，它是被违反得最频繁的一条，原因很朴素：候选人担心「说个简单方案会不会显得不够厉害」。结果恰恰相反：跳过 baseline 直接谈新颖架构，是系统设计面试里最容易被扣分的一步，因为它暴露的不是「不懂新技术」，而是「不知道怎么用最小成本验证一个方向值不值得投入」。

baseline 阶梯：每一级台阶回答「多的复杂度换来多少价值」

阶梯形态TSR 场景的具体样子建设成本回答的问题
第 0 级：规则/启发式无需训练，纯先验规则按颜色阈值+形状模板粗筛候选区域，不做任何学习数小时到 1 天「问题的下限在哪？规则能覆盖多少？」
第 1 级：简单模型经典 ML 或极小型网络小型单阶段检测器，单尺度、无数据增强、默认超参1–3 天「不需要任何精心设计，模型化能带来多少提升？」
第 2 级：现成预训练方案开源预训练模型直接微调用公开预训练的检测 backbone 在自有数据上微调（呼应模块 02 的冷启动策略）3–7 天「别人已经解决的部分，我要不要重新发明？」
第 3 级：定制方案针对约束定制架构/训练策略针对小目标与延迟约束定制的检测器（见 C53/C57）数周起「这一级的额外投入，是不是问题真正需要的？」
价值 ▲ │ ╭────── 第3级：定制方案 │ ╭─────────╯ (投入最大，边际收益通常最小) │ ╭─────────╯ 第2级：预训练微调 │ ╭─────────╯ 第1级：简单模型 │──────╯ 第0级：规则/启发式 └──────────────────────────────────────────────▶ 投入 面试里最常见的错误：只讲第3级的位置在哪，从不提前面三级台阶实际值多少分 —— 这样面试官无法判断你是否知道"这一步投入是否值得"，只能假设你不知道

直白说

把 baseline 类比到编程题的「先给暴力解」（见 C62-00）：暴力解不追求最优，追求先有一个正确的对照物，让后面的优化有据可依。建模里的 baseline 扮演完全相同的角色——它未必要多准，但必须先存在，而且必须便宜到能在几天内跑出来。

严谨说

从决策论角度看，这仍然是一个期望值问题：直接投入第 3 级方案，如果最终效果不如第 1 级（这在真实项目里并不罕见——很多「显而易见该有用」的复杂设计，实测收益是负的），那么前面投入的时间全部沉没，还要再花时间退回来做第 1 级。先做 baseline 的期望时间成本几乎总是更低，因为它同时提供了「正确性下限」和「后续所有比较的参照系」——省下来的不是 baseline 本身的时间，是「发现复杂方案不划算」之后不需要走的弯路。

面试当场最容易失分的一句话：被问「这个方案预期能到多少精度」时回答「应该会不错，毕竟用了最新的架构」。这句话里没有任何可以被验证的内容。正确的回答结构是：「baseline（比如规则筛选+简单分类器）大概能到 X，我预期新方案能在哪些切片上超过它、超过多少、为什么——如果实测没有超过，我会认为这个复杂度投入是不划算的。」面试官在这句话里同时打分「工程判断」和「诚实度」两栏。

3模型选型：由约束驱动而非由新颖度驱动

有了 baseline 之后，下一步是「往哪个方向迭代」——这里最常见的失分模式是把选型问题答成一场架构知识竞赛：候选人流利地罗列 DETR、RT-DETR、Swin……却从未提到延迟预算是多少、有多少标注数据、团队能不能维护它。约束驱动的选型，是先划出可行集，再在可行集里选最优；新颖度驱动的选型，是先选「最好」的，再假装约束会自己解决。

约束维度具体问题违反后果
延迟预算推理耗时能否落在给定的毫秒预算内（含预处理/后处理，不能只看模型本身）模型再准，装不进帧预算就是不可用（呼应 C53-00 的 33ms 账本）
算力/显存预算训练与推理各自的显存、车端算力上限训练不起来，或者能训但车端跑不动，需要重新量化/裁剪（呼应 C60）
数据量候选架构对数据量的敏感度——数据饥渴型架构在小数据集上可能不如简单模型（呼应 C54-05 的 DETR 收敛难题）选了数据饥渴的架构却没有对应量级的标注预算，训练不收敛或过拟合
可维护性/团队能力团队是否有能力调试、部署、监控这个架构；出问题时能否定位选了团队没人真正懂的架构，出故障时排查成本远高于收益
可解释性/安全合规任务是否要求模型决策可解释、是否有监管要求端到端黑盒方案在强安全审查场景下可能无法通过合规审查

直白说

直白地说：选型的第一步不是「哪个模型最强」，是「先把明显不可行的选项划掉」——延迟超预算的划掉、显存装不下的划掉、需要比你有的多十倍数据的划掉。剩下的才是「值得比较」的候选集，这时候再谈准确率、再谈论文里的新颖点才有意义。

严谨说

这正是帕累托前沿选型方法的前置步骤（完整方法见 C53-05，本节不重复）：先用硬约束做可行性过滤（feasibility filter），得到一个可行集；再在可行集内部比较延迟-精度权衡，找出「没有被其他候选支配」的那些点。面试里被追问「为什么不用 X」时，最有说服力的回答永远是「X 在可行性过滤这一步就被排除了，原因是……」，而不是「X 没有 Y 新」。

新颖度陷阱的两个典型例子：① 选一个需要 500 epoch 才收敛的 DETR 变体，却没有检查团队的数据量和算力预算是否撑得住这个训练成本（可变形注意力等改进本质是在缓解这个问题，见 C54-04，但仍需要正确评估）；② 为了追求论文排行榜上的 0.5 个点提升，选择一个需要额外部署自定义算子的架构，而团队的部署链路（见 C60-02）根本不支持自定义 TensorRT plugin——这类选择在系统设计面试里会被追问到「你考虑过部署可行性吗」，答不出来就是选型逻辑本身有洞。

4特征与表示的设计

选定了模型方向之后，还要回答「模型吃什么」——这一节容易被讲成一份特征清单，但面试里真正有价值的是判断一个特征该不该用的标准，而不是特征本身有多少种。判断标准只有三条：有没有信号、推理时能不能拿到、值不值得为它付出额外的服务依赖。

判据具体问题违反的典型后果
有信号这个特征和目标之间是否存在稳定的统计关联，而不是训练集里偶然的巧合模型学到虚假相关，遇到分布外样本立刻失效
推理时可得（无训练-服务偏差）训练时用到的信息，在线上推理的那一刻是否真的能拿到训练-服务偏差（training-serving skew）：离线评测很漂亮，上线却不行，是最隐蔽的一类 bug
服务成本可接受计算这个特征是否会挤占延迟预算，是否引入新的外部依赖（如需要调用地图服务）特征本身很有用，但计算它比模型推理还慢，整体延迟预算被拖垮
训练-服务偏差最经典的一类错误：用「整段视频的全局统计量」（比如这段视频里某类标志出现的总次数）做特征——训练时能拿到，因为训练样本是离线整理好的完整片段；但在线推理时，车辆只能看到「到当前时刻为止」的信息，看不到未来帧。这类特征在离线评测里表现优异，一旦上线立刻失效，而且往往需要很久才能定位到根因——因为它不像坐标系错位那样能被立刻测出来。

放到 TSR 场景里，值得纳入的上下文特征通常包括：自车速度与朝向（判断标志是否即将进入有效视野）、车道信息（标志关联到哪条车道，呼应 C59-03 的感知接口设计）、高精地图先验（该位置历史上是否有已知标志）——这几类都满足「推理时可得」，因为它们来自车辆自身的实时状态，而不是需要提前看到未来才能计算的统计量。

直白说

「多加一个特征」听起来是免费的，实际上每加一个特征就多一条服务依赖：这个特征从哪个上游系统拿、它挂了模型该怎么办、它的延迟是否稳定。

严谨说

工程上应该把每个候选特征放进一张「特征清单」，为每个特征标注：来源系统、更新频率、推理时的可得性证明（不是假设，是证明——比如指出它只依赖 $t$ 时刻之前的信息）、以及去掉它之后模型效果下降多少（用于判断这条依赖是否值得维护）。这张清单本身就是可以在白板上画出来的产出物。

5离线评测设计：切片、回归门禁与显著性

有了候选模型，下一步是「怎么判断它比 baseline 好」。这里的核心原则是：一个全局指标永远不够，评测方案必须显式设计成「切片 + 门禁 + 显著性」三件套——切片定义决定你能不能看见局部退化，门禁规则决定「不掉点」这件事是不是真的被检查了，显著性决定你看到的提升是不是噪声。这三件事的技术细节（如何计算显著性、如何做多重比较校正）已经在 C58-05 与 C61-01 讲透，本节讲的是面试里怎么把它们组织成一个完整的评测设计。

切片维度TSR 场景举例为什么全局指标看不见它
距离/尺寸分桶60m 外的小目标 vs 10m 内的大目标小目标数量占比可能只有 10%，全局 mAP 被大目标平均掉
天气/光照夜间、逆光、雨雾场景如果这些场景在评测集里占比本来就低，局部退化对全局分数几乎没有影响
类别限速禁令 vs 罕见的临时施工标志高频类别主导全局平均，罕见类别的严重退化会被稀释到看不见
安全等级「停车让行」类 vs 一般指路类（呼应模块 01 的代价不对称）全局指标不区分错误的安全后果是否相同
\[\text{Gate}_{\text{slice}}:\quad m_{\text{new}} \;\ge\; m_{\text{base}} - \tau, \qquad \tau = k \cdot \hat{\sigma}_{\text{seed}}\]

回归门禁的容差 $\tau$ 不应该拍脑袋定一个数字（比如「不能掉超过 1 个点」），而应该由种子方差撑起来：先测出同一配置换随机种子的指标波动 $\hat{\sigma}_{\text{seed}}$（检测任务典型量级见 C61-01），再取 $k$ 倍（常见取 $k=2$–$3$，对应约 95%–99.7% 的置信区间）作为容差。容差小于种子方差，意味着门禁会被噪声频繁误触发；容差远大于种子方差，意味着真实退化会被放过——这条公式本身就是「显著性」这个抽象词在评测设计里的具体落地形式。

切片数量一多，「所有切片都不掉点」这句话本身就会被噪声拖累出假阳性回归。如果评测集分了 30 个切片，即便新模型和 baseline 没有任何真实差异，单纯因为随机波动，也会有若干个切片「看起来」退化超过容差——这正是多重比较问题（multiple comparisons）。工程上通常用 Bonferroni 或更宽松的 FDR 校正来调整每个切片的判定阈值，具体计算方法见 C61-01，面试里只要能说出「切片一多必须做多重比较校正，否则会被自己的评测设计坑」，就已经展示了比大多数候选人更深一层的理解。

直白说

怎么在白板上讲清楚离线评测设计？先画一张「切片 × 指标」的表格骨架，再在每个格子旁边标上门禁阈值，最后说明「新模型要跑几个随机种子、用什么检验判断提升是否显著」——三句话覆盖切片、门禁、显著性。

严谨说

更完整的表述会加上：显著性检验要用配对而非非配对形式（同一批测试样本上比较两个模型，而不是把两次独立训练的结果当成两组独立样本），因为配对检验能消除「测试样本本身难度不同」带来的方差，这一点在检测任务里尤其重要，因为不同图像的难度差异极大。

6在线评测：A/B、影子模式与灰度发布

离线评测通过，不代表可以直接全量上线——在线评测的作用是用递增的风险敞口验证「离线看到的提升，在真实流量上是否成立」。三种常见形态按风险从低到高排列：影子模式、灰度发布、A/B 测试。

风险敞口递增 ──────────────────────────────────────────────▶ ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ 影子模式 │──▶│ 灰度/金丝雀 │──▶│ A/B 测试 │──▶│ 全量发布 │ │ shadow mode │ │ canary │ │ │ │ │ │ 新模型跑但 │ │ 小比例真实 │ │ 显著性验证 │ │ │ │ 不影响决策 │ │ 流量，观察 │ │ 后放量的 │ │ │ │（只记录不生效）│ │ 是否有硬故障 │ │ 正式对照实验 │ │ │ └─────────────┘ └─────────────┘ └─────────────┘ └─────────────┘ 几乎零风险 风险可控 需要统计功效 需要长期监控 能测延迟/ 能测崩溃率/ 才能测"体验层面 （呼应第7节的 吞吐/一致性 明显异常 是否真的更好" 离线-在线背离）
形态回答的问题统计要求典型持续时间
影子模式新模型能不能稳定跑、延迟是否达标、和现网结果差多少只需要描述性统计（均值/分布对比），不需要假设检验数天到数周
灰度/金丝雀小流量下有没有明显故障（崩溃、极端错误、安全事件）阈值监控为主，样本量通常不足以做严谨的显著性检验数天
A/B 测试新模型是否在业务指标上有统计显著的提升需要提前算样本量与功效，避免「看着实验跑没多久就下结论」数周（取决于所需样本量与流量规模）
\[n \;\approx\; \frac{2\,(z_{\alpha/2} + z_{\beta})^2 \, p(1-p)}{\delta^2}\]

这是两比例 A/B 测试最常用的样本量估算式（每组所需样本量）：$p$ 是基准指标（比如当前误报率），$\delta$ 是希望能检测到的最小有意义差异（minimum detectable effect），$z_{\alpha/2}$、$z_{\beta}$ 分别由显著性水平 $\alpha$（常取 0.05，$z\approx1.96$）和统计功效 $1-\beta$（常取 0.8，$z\approx0.84$）决定。面试里的关键不是背这个公式，是知道『$\delta$ 定得越小，需要的样本量越大』这个反比关系——如果业务方要求检测出 0.1% 的微小差异，需要的流量可能是检测 5% 差异所需流量的上千倍，这个换算能力比记住公式本身更重要。

直白说

怎么决定选影子模式还是直接 A/B？看这次改动的下行风险：如果新模型可能在某些场景下彻底失效（比如从未在真实路测跑过的新架构），先影子模式测稳定性，再灰度测极端故障，最后才是 A/B 测业务提升。如果只是一次成熟迭代的小幅调参，可以直接小流量 A/B，跳过冗长的影子阶段。

严谨说

这是一个分阶段风险敞口（staged rollout）的设计问题：每一阶段用更小的统计严谨性换取更低的风险敞口，或者反过来，用更大的风险敞口换取更快拿到统计显著的结论。面试里能主动提出「这次改动的风险量级决定了要不要跳过某个阶段」，比死板地背「先影子再灰度再 A/B」这个固定顺序更显判断力。

7离线-在线背离：成因与对策

这是模块里最容易被深挖的一节——「离线 mAP 0.82，但路测感觉像 0.6」是感知系统里流传最广的一句抱怨（技术层面的逐层定位方法见 C60-00，本节讲的是评测设计阶段该怎么预见并降低这种背离，而不是出了问题之后怎么二分排查）。背离几乎从不是单一原因，而是几种成因叠加。

成因机制诊断信号对策
分布偏移离线评测集是历史某个时间窗口的快照，真实流量的场景分布已经变化（新路段、新季节、新车型占比）评测集各切片占比与最近上线流量的场景统计对不上定期用最新流量重新采样评测集切片占比（呼应模块 02 的分层抽样与代表性检验）
反馈环偏差线上模型的过去决策，影响了后续被记录/被标注的数据，评测集本身已经被模型自己的历史行为污染评测集里「模型曾经自信预测过」的样本被过度代表，模型对自己熟悉的分布看起来更好评测集优先来自主动采集/众包等不受当前模型决策影响的独立通道（呼应模块 02 的来源画像）
指标代理失配优化的是模型指标（如 mAP），但业务真正关心的是下游结果（如「驾驶员是否需要接管」），两者只是弱相关代理模型指标持续上升，但业务侧满意度/接管率没有对应改善尽早建立模型指标到业务指标的映射并定期校验（呼应模块 01 的三层指标映射）
硬件/精度差异离线评测跑的是全精度模型，线上跑的是量化/剪枝后的版本，行为已经不完全一致离线用同一份 checkpoint 复测，线上用部署后的 engine 复测，两者有差距评测方案必须包含「用真实部署产物（量化后的 engine）复测」这一步，而不是只测训练用的 checkpoint（见 C60 模块 02-03）
选择性记录只有触发规则命中的片段才被回传标注，评测集里「模型很确信且错了」的那类样本被系统性欠采样触发规则和评测集构造用了同一套置信度阈值评测集构造要独立于线上触发规则，或者对触发采样做逆概率加权修正

对策的共同思路是「让离线评测集在统计意义上更像真实线上流量」，常用的具体手段是重要性加权（importance weighting）：给评测集里的每个样本一个权重，使加权后的切片占比与线上真实占比对齐，再计算加权指标。这和模块 02 里「用蒙特卡洛检验一份抽样代表不代表总体」是同一个思路的两个应用——一个用来检验抽样是否具代表性，一个用来在评测阶段主动修正代表性偏差。

最容易被忽视的一条：反馈环偏差是「自我实现的乐观」。如果评测集主要来自「模型自己曾经检测到并被记录下来」的样本，那么模型在这份评测集上天然会显得更好——因为它在筛选自己更擅长的那部分现实。面试里能主动提出「评测集的来源是否受当前模型决策影响」这个问题，是这一节里最容易让面试官眼前一亮的点，因为它比「量化掉点」这类更常见的答案更少被提到。

直白说

怎么在白板上讲清楚背离的成因？先问自己一句「离线评测集是怎么来的」——如果答案里出现「从线上触发/线上日志采样」，就要立刻检查反馈环偏差和选择性记录这两条；如果评测集是很久以前建的，就要检查分布偏移。

严谨说

系统设计层面的根本对策是把「评测集的代表性」当成一个需要持续维护的资产，而不是一次性建好就不变——定期用最新流量重新校验切片占比、定期检查触发规则是否引入了新的选择性偏差，这本身就应该写进模块 08（服务与迭代）的监控清单里。

8迭代节奏与实验管理

最后一块拼图是「怎么持续做下去」。系统设计面试里偶尔会被追问「你打算多快迭代一次、怎么保证多个人同时在改动不会互相踩」——这一节给出可以直接照搬的组织原则。

一次迭代的完整生命周期（呼应 C58-05 的闭环流水线，本节只讲节奏与治理）： 提出改动 ──▶ 离线基线对比 ──▶ 回归门禁 ──▶ 影子/灰度 ──▶ A/B ──▶ 全量 ──▶ 监控 │ │(第5节) │(第5节) │(第6节) │(第6节) │ │ ▼ ▼ │ │ 必须与baseline 未过门禁 ─▶ 打回④(建模)重新迭代 │ │ 用同一套评测方案 │ └───────────────────── 下一轮迭代的输入 ◀───────────────────────────────────┘ （呼应第7节：监控发现的背离，反过来修正评测集代表性）
治理原则具体做法违反后果
单变量原则每个实验相对上一个基线只改一个维度（架构、数据、超参三选一），详细方法见 C61-01多个改动叠加时不知道收益归因于哪个改动
实验并发上限同时进行中的实验数量要匹配评测/标注/上线容量，而不是想开多少开多少实验堆积，评测和上线成为瓶颈，迭代反而变慢
实验记录最小字段代码 commit、数据版本（呼应模块 02 的数据血缘）、配置、随机种子、完整切片指标，缺一不可事后无法复现，也无法归因，实验白做
迭代节奏和数据闭环对齐模型迭代速度不应快于「触发→挖掘→标注」闭环的产出速度（见 C58-05）迭代很快但每次用的都是同一批旧数据，边际收益迅速归零

直白说

怎么把「迭代节奏」讲成一个系统设计答案？先说清楚一次迭代要过哪些门禁（离线对比→回归门禁→分阶段上线），再说清楚多个实验之间怎么协调（单变量、有并发上限、有统一的记录格式），最后点出迭代速度的真实瓶颈通常不是训练算力，而是数据闭环的产出速度和评测容量。

严谨说

这是一个节奏对齐问题：建模迭代、数据闭环、评测容量是三个不同速度的齿轮，系统设计的成熟度体现在知道哪个齿轮是当前的瓶颈——多数团队早期以为瓶颈在算力，跑了几轮迭代后才发现真正的瓶颈是「评测切片够不够细」或者「新数据进来的速度够不够快」。面试里能提前说出这一点，等于提前回答了面试官接下来大概率会问的追问。

一句话总结本模块四节的因果链：baseline 给出对照物 → 约束驱动的选型给出可行且可维护的候选 → 切片+门禁+显著性的离线评测给出可信的初筛 → 分阶段的在线评测给出真实世界的验证 → 持续监控离线-在线背离，把发现反哺回评测集设计——这是一个闭环，不是一条直线。

9研究前沿与开放问题

建模与评测的方法论在工业界演进很快，但很多问题仍然没有定论。以下几个方向，在面试里被主动提起时通常会被视为「想得比较深」的信号。

  • 离线代理指标与真实业务价值之间的鸿沟，仍然缺少通用的度量方法。「模型指标到业务指标的映射」目前主要靠具体场景的定制建模（比如用因果推断估计「感知提升多少能换来接管率下降多少」），还没有跨任务通用的框架。这意味着「指标代理失配」这一类离线-在线背离，短期内仍然只能靠人工经验去发现，而不是靠自动化工具。
  • 反馈环偏差的系统性修正方法仍在发展中。因果推断与离策略评估（off-policy evaluation）提供了理论工具来修正「评测集被模型自身历史决策污染」的问题，但在高维感知任务（而非简单的推荐排序场景）上的实用化程度还有限。这是一个值得持续关注、但目前工程上仍主要靠「评测集来源独立于线上决策」这类结构性设计来规避而非修正的领域。
  • 大模型时代的 baseline 定义正在改变。当一个开源预训练大模型稍加提示或微调就能给出不错的结果时，「baseline」和「定制方案」之间的成本差距被大幅压缩，这会重新排列本模块「baseline 阶梯」里各级台阶的性价比——但「先建立可对照的基准再谈提升」这条原则本身不会过时，变化的只是每一级台阶的具体建设成本。
  • 持续评测（continuous evaluation）与自动化回归门禁的边界还在摸索。随着迭代速度加快，人工审阅每一次切片指标变化的方式难以为继，自动化的门禁规则需要在「误报率」和「漏报真实退化」之间找平衡——这本质上是模块 02 提到的「代价不对称」问题在评测治理层面的重现。

★ 必读：Sculley et al., Hidden Technical Debt in Machine Learning Systems（NeurIPS 2015）——「反馈环」「训练-服务偏差」等概念的经典出处，本模块多处引用其框架。★ Breck et al., The ML Test Score（IEEE Big Data 2017）——把「模型是否可以上线」量化成一份可勾选的测试清单，是离线评测设计一节的方法论源头之一。★ Kohavi, Tang & Xu, Trustworthy Online Controlled Experiments（2020）——A/B 测试的系统性参考书，样本量、功效、常见陷阱的完整处理见其中，本模块只取了最小可用子集。
