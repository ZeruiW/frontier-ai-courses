1六个案例怎么用：通用答题脚手架

这是全课的落点。前面四个模块给了你七步框架、需求澄清的问题清单、数据设计的方法论、建模评测的原则、服务容量的心算工具——本模块把它们缝合成六段完整的 45 分钟演练，每段都按「题面 → 澄清问题 → 七步展开 → 关键取舍 → 追问预案 → 评分要点」的固定结构写。

六个案例不是六个要背下来的剧本。面试官几乎不会原样出这六道题——他真正想看的，是你能不能把「同一套骨架」套到一道没见过的题面上。正确的使用方式是：先把①（本岗位主案例）练到能脱稿讲出完整脚本，再挑一两个练到「看到题面能立刻认出是哪种模式」，不要试图六个都背熟——背答案会在面试官稍微改一下题面时立刻露馅，理解骨架才能应对变体。

开场 90 秒说什么

面试官抛出一句模糊的题面（「设计一个 XXX 系统」）之后，你有大约 90 秒把自己的姿态定下来。这 90 秒不解决任何技术问题，它解决的是「面试官愿不愿意跟你一起把这道题做细」的问题。

时间段要说什么为什么
0–20 秒复述题面，用自己的话说一遍你理解的问题范围确认双方对题面的理解一致，防止 20 分钟后发现理解错了
20–60 秒抛出 2–3 个最关键的澄清问题（不是全部问题，先问能决定方向的那几个）展示你知道「先问什么」比「问了多少个」更重要
60–90 秒宣布路线图：「我打算按范围→指标→数据→建模→评测→部署→风险这七步展开，先从范围和指标开始」让面试官知道接下来 45 分钟的结构，减少他打断确认进度的次数

白板画什么

┌───────────────────────────────┬────────────────────────────────────┐ │ 左上：范围与指标 │ 右上：架构图（数据流实线 + 控制流虚线）│ │ · 用户是谁 / 不做什么 │ · 在线/近线/离线三层（见本课模块04） │ │ · 业务→模型→系统 三层指标映射 │ · 系统边界（车端/云端，谁负责谁） │ ├───────────────────────────────┼────────────────────────────────────┤ │ 左下：数据与评测 │ 右下：容量数字与风险清单 │ │ · 数据来源 / 标注 / 泄漏防范 │ · QPS/显存/延迟预算的量级心算 │ │ · 离线评测切片 + 在线 A/B │ · 降级方案 + 监控 + 迭代风险 │ └───────────────────────────────┴────────────────────────────────────┘ 底部留一条窄带：写「45 分钟七步时间条」，边讲边划掉已完成的格子

四象限 + 一条时间带是一个可以套用到任何案例的骨架。关键不是画得多美观，是让面试官从任何一个象限都能看出你现在在讲七步框架的哪一步。

45 分钟的时间条（七步通用版）

0 5 10 20 30 38 43 45 ├────────┼─────────┼──────────────┼──────────────────────┼────────┼─────┼───┤ │①范围 │②指标 │ ③数据 │ ④建模 │⑤评测 │⑥部署│⑦风险│ │ 5min │ 5min │ 10min │ 10min │ 8min │5min │2min │ └────────┴─────────┴──────────────┴──────────────────────┴────────┴─────┴───┘ 与 C62/C65 的编码题时间条不同：这里没有「写代码」这一步， 取而代之的是「④建模」——它对应的不是敲代码，而是画出模型选型的推理链

最后 5 分钟怎么收尾

  • 结论先行地复盘取舍：「如果只能选一个方案，我会选……因为在给定约束下它的性价比最高；放弃的是……，代价是……」——这是 C65-03「说清放弃了什么」原则的直接应用。
  • 主动列风险与下一步：「如果给我更多时间，我会重点验证……」——比等面试官问「还有什么没考虑到」更主动。
  • 反问环节别浪费：问一个和这道题强相关的真实问题，例如「这个系统现在实际的延迟瓶颈在哪一层？」——既是真实好奇，也可能拿到有用信息去调整前面的判断。

直白说

为什么要死记一套脚手架，而不是「随机应变」？因为 45 分钟的高压环境下，随机应变的候选人最常见的失败模式是「越讲越细，最后卡在某个技术细节里出不来」。脚手架的价值就是给你一个「万一想不出更好的话该怎么办」的默认动作——先把七步的骨架过一遍，永远比在第③步就陷进去强。

严谨说

更严谨地说，脚手架提供的是可预测的产出节奏：面试官在评分时最怕遇到「不知道候选人卡在哪一步、还要不要给提示」的不确定性。一份清晰宣布的路线图（「我打算先……再……最后……」）把这种不确定性降到最低，这与 C63 模块 00「四种常见失败模式」里「不谈风险」「直接跳到模型」是同一个问题的两面。

最常见的翻车方式：把 90% 的时间花在④建模上。建模确实是最容易讲、最有「技术含量」的部分，但评分卡上它只是七分之一。如果 30 分钟过去了还在讲模型架构细节，⑤⑥⑦三步会被压缩到几乎没有——而这三步恰恰是最能体现「工程成熟度」的部分。看到时间条走到 20 分钟，无论建模讲没讲完，都要主动往下一步走。

2案例① TSR 感知系统（本岗位主案例）

这是唯一一个你必须练到能脱稿讲出完整脚本的案例。它的特殊之处不在于技术难度，而在于——这里只引用 C55/C57/C58/C60 的结论，不重述任何技术细节。真正的考点是「你能不能把四门课的内容组织成一次连贯的系统级论证」，而不是「你记不记得 NWD 的公式」。

题面（面试官原话，故意含糊）：「设计一个交通标志识别（TSR）感知系统，用于量产自动驾驶车辆。」

澄清问题

  • 输出消费者是谁？规控模块（需要结构化约束）还是 HMI 提示（需要人类可读）还是两者都要？
  • 覆盖场景？高速为主还是含城区复杂路口？国内标准（GB 5768）还是需要跨区域泛化？
  • 成功标准是什么？多远距离检出算合格？可接受的 FP/km 是多少（见 C55-05）？
  • 硬约束？车端算力/相机路数/端到端延迟预算是多少？
  • 明确不做什么：是否包含交通信号灯识别（那是独立感知任务，不在本题范围）？

七步展开（每步只引用结论，不重述机制）

步骤这一步说什么
① 范围先锁定输出对象与「标志」的定义边界（分类体系差异见 C55-01），明说信号灯/车道线不在本题范围
② 指标业务→模型→系统三层映射；工作点由代价不对称决定（漏检「停车让行」代价远高于漏检指路牌，见 C55-05）
③ 数据两级 vs 端到端的类别解耦取舍（见 C55-02）；长尾处理谱系（见 C58-01）；难例挖掘与触发器（见 C58-02/03）
④ 建模baseline 优先；小目标是核心难点（IoU 对位移的敏感性与 NWD 度量，见 C57-01/03）；多帧时序融合与状态机（见 C55-04）
⑤ 评测mAP 不足以评价 TSR——按距离/尺寸/光照分桶、代价敏感指标、FP/km（见 C55-05）
⑥ 部署容量估算与延迟预算分解（见本课模块 04）；训练-部署一致性与量化（见 C60）；降级方案（模型/特征降级/兜底规则）
⑦ 风险数据闭环持续迭代（见 C58-05）；失效模式全景与优先级排序（见 C55-03）
\[R_{\text{system}} \;\approx\; R_{\text{det}} \times \text{Acc}_{\text{cls}} \qquad \text{（两级方案的级联召回是乘法关系，见 C55-02，此处只引用结论）}\]

直白说

关键取舍：两级方案（类别无关检测 → 高分辨率分类）在面试里怎么讲？「两级更容易独立迭代、分类器可以用更高分辨率单独优化，代价是级联误差和额外延迟；端到端更快但新增类别要重训整个检测器。在算力紧张、类别会持续新增的量产场景，两级通常是更稳的默认选择——但这是个可以被具体约束推翻的默认值，不是教条。」

严谨说

更严谨地说，这个取舍的量化依据是级联召回公式 $R_{system} \approx R_{det} \times Acc_{cls}$——它揭示了两级方案的误差不是简单相加而是相乘，所以两级的检测器必须把召回做得非常高（哪怕多一些误检也无妨，因为分类器会二次过滤），这直接决定了检测器该往「高召回」而不是「高精确率」调工作点。完整推导与更多细节见 C55-02，本案例不重复。

追问回答要点对应评分维度
「如果只能改一个环节，你会先改哪个？」先用误差分解（TIDE 式，见 C61-02）定位收益最大的一类错误，而不是凭直觉猜归因能力
「长尾类别数据不够，你会怎么做？」引用 C58-01 的方法谱系（重采样/重加权/logit adjustment/解耦训练）+ copy-paste（见 C56-03）知识广度 + 引用而非重述
「怎么保证离线指标和路测体验一致？」评测-部署一致性方法论见 C60，加上分桶评测（见 C55-05）系统思维
本案例最容易的翻车方式：只讲模型架构，不讲数据闭环和降级方案。面试官会认为你没有量产系统的手感——一个只会选 backbone 的候选人和一个懂得「数据飞轮才是护城河」（见 C58 全课的核心主张）的候选人，在这道题上的评分差距会非常大。

3案例② 车道线与可行驶区域

题面：「设计一个车道线检测与可行驶区域分割系统。」

澄清问题

  • 输出形式是什么？离散关键点、参数化曲线（如三次多项式）、还是像素级分割 mask？
  • 「车道线」和「可行驶区域」是同一个任务还是两个任务？（这是本题最容易被面试官设的陷阱）
  • 主要场景是结构化的高速公路，还是含大量无车道线/施工遮挡的城区道路？
  • 下游轨迹规划模块期望的输入格式是什么？这决定了输出表示怎么选。

七步展开

步骤这一步说什么
① 范围先分清车道线（几何/拓扑）与可行驶区域（语义分割）是两个不同任务，含糊地当一个任务设计会被立刻扣分
② 指标车道线看关键点/曲线的横向偏移误差（直接影响控制平顺性，不只是 IoU）；可行驶区域看 mIoU；两者都要看帧间抖动
③ 数据车道线标注是曲线标注，一致性挑战与 TSR 的框标注不同；长尾场景（无标线土路、临时施工线）
④ 建模车道线常用行/列锚点分类或参数化曲线回归；可行驶区域是标准语义分割；两者可共享 backbone 做多任务学习
⑤ 评测横向偏移误差的分布（不能只报平均值）；按曲率/遮挡程度/天气分桶
⑥ 部署输出频率要匹配控制回路（通常要求高于其他感知任务，30Hz+）；BEV 转换的标定误差是隐蔽的系统性误差源
⑦ 风险标定漂移不容易被发现（不像模型精度那样直接可测）；恶劣天气下车道线失效率高，需要专门的降级策略

直白说

关键取舍：参数化曲线回归 vs 逐点分割再拟合曲线？「曲线回归输出更平滑、直接可控，但表达力受限于多项式阶数，遇到复杂弯道或分叉路口容易欠拟合；分割更灵活但需要额外的后处理拟合曲线，引入延迟和二次误差。选择依据是下游控制器需要什么样的输入格式，而不是哪个模型更新潮。」

严谨说

更严谨地说，这个取舍还牵涉一个容易被忽视的误差源：相机内外参标定误差会通过 BEV 转换非线性放大——近处误差小，远处同样的像素误差在物理空间里被放大数倍。因此无论选哪种表示，评测都必须按距离分桶，且要有独立的「标定健康度」监控指标，而不是只监控模型输出本身。

追问回答要点对应评分维度
「标定误差怎么被发现？」监控输出的跨帧一致性/抖动幅度作为标定健康度的代理指标，而不是等到精度下降才发现监控意识
「车道线消失时怎么办（施工/褪色）？」降级到「用历史轨迹外推 + 保守减速」的兜底策略，呼应 C59-04 的安全兜底层设计降级方案（呼应本课模块04）
把车道线和可行驶区域当同一个任务设计，是这道题最常见的失分点。两者的标注方式、评测指标、下游消费方式都不同——面试官很可能就是在等你主动区分这两者，如果你在①范围阶段就说清楚，这一步单独就能拿到「结构化思维」的加分。

4案例③ 以图搜图 / 相似场景检索

题面：「设计一个系统，给定一张图片，从图库中检索出最相似的图片（或场景）。」

澄清问题

  • 「相似」怎么定义？像素级近重复、语义级场景相似，还是「同一场景不同时间」？——三种定义对应完全不同的技术路线。
  • 图库规模量级（万级/亿级）决定索引方案。
  • 是在线实时检索还是离线批量去重？延迟要求差几个数量级。
  • 是否需要可解释性（用户/工程师需要知道「为什么这两张相似」）？

七步展开

步骤这一步说什么
① 范围先定「相似」的粒度——像素近重复用感知哈希，语义相似用深度嵌入，两者是不同工具（呼应 C58-04 的近重复检测与嵌入检索）
② 指标Recall@K / Precision@K + 检索延迟；如果是去重场景则用近重复检出率
③ 数据训练嵌入模型需要相似对/三元组，可用「同一轨迹连续帧视为正对」做弱监督，省去大量人工标注
④ 建模双塔式嵌入结构（呼应 C47-03 双塔召回的范式），度量学习损失（triplet/contrastive）——本质与检索是同一套范式
⑤ 评测离线 held-out 查询集上的 Recall@K；在线看点击率或人工判定相关性
⑥ 部署ANN 索引（如 HNSW/IVF）的召回-延迟权衡（呼应 C58-04 的向量库工程）；索引更新频率与冷启动
⑦ 风险嵌入空间会漂移——模型更新后旧向量与新向量不可直接比较，需要全量重建索引的版本管理

直白说

关键取舍：暴力全量比对 vs 近似最近邻（ANN）索引？「暴力比对召回 100% 但延迟随图库规模线性增长，图库过百万就不可用；ANN 索引用可控的召回损失换来对数级或常数级的查询延迟，损失多少召回、换多少延迟是这里唯一需要量化说清楚的取舍。」

严谨说

更严谨地说，ANN 索引的召回-延迟曲线本身就是一条帕累托前沿（呼应 C65-03 的帕累托前沿判断法），工程上通常先定延迟 SLA 再在这条前沿上找可行区间，而不是先追求最高召回再看延迟够不够——这是一个「先约束再优化」而不是「先优化再检查约束」的典型例子。

追问回答要点对应评分维度
「索引更新期间怎么保证查询一致性？」双索引切换（旧索引继续服务，新索引构建完成后原子切换）工程成熟度
「怎么评估嵌入模型学得好不好？」离线 Recall@K + 人工抽查最近邻是否语义合理 + 在线信号三者结合，不能只看一个评测设计

这道题本质上和「用嵌入检索挖长尾难例」（见 C58-04）是同一个工具的不同应用场景——面试官只是换了个包装，真正考的是你能不能认出「这其实是我熟悉的那个模式」，而不是从零发明一套新方案。

5案例④ 内容审核 / 异常检测（不平衡与代价不对称）

题面：「设计一个系统检测平台上的违规内容（或异常交易）。」

澄清问题

  • 违规的定义是否稳定？规则是否会频繁变化（对抗性环境的信号）？
  • 漏检一条违规内容 vs 误伤一条正常内容，哪个代价更高？——这个答案决定后面所有工作点选择
  • 是否有人工复核环节？机器只是初筛还是要独立做出最终判定？
  • 违规样本的实际占比大概是多少（0.1%？1%？）？——决定不平衡处理的紧迫程度

七步展开

步骤这一步说什么
① 范围这是不平衡 + 代价不对称的典型题——第一步必须问清代价矩阵，它决定后面所有设计
② 指标不平衡下 accuracy 会撒谎，必须用 PR-AUC 而非 ROC-AUC；工作点按代价矩阵求解（呼应本课模块01的代价敏感工作点选择）
③ 数据极端长尾（违规样本可能 <0.1%），处理谱系同 C58-01；标注一致性差（违规判定本身带主观性，需要多标注者一致性检验）
④ 建模baseline 优先用规则 + 简单分类器；机器初筛 + 人工复核的分层策略（级联误差传播的思想与 C55-02 一致，但代价结构不同）
⑤ 评测代价敏感指标；A/B 要留意新奇效应与长尾类别的统计功效不足问题
⑥ 部署审核通常可以近线/离线（除非强实时场景要求在线阻断）；人工复核队列的容量估算（呼应本课模块04的 QPS→人力换算）
⑦ 风险对抗性规避——违规者会主动学习并调整策略绕开检测，这是与 TSR 完全不同的独有风险
\[\text{期望代价} = P(\text{FN}) \cdot \text{Cost}_{\text{FN}} + P(\text{FP}) \cdot \text{Cost}_{\text{FP}} \qquad \text{（工作点选择即在此式上最小化期望代价，而非最大化准确率）}\]

直白说

关键取舍：机器初筛 + 人工复核，这条分层策略要怎么讲？「机器负责召回尽量高（不漏掉可疑内容），人工负责精确率（避免误伤申诉成本），阈值设置在「宁可让人工多看几条，也不要机器直接误伤用户」这一侧——这是由 Cost_FP（误伤用户的信任成本）通常高于人工复核成本决定的。」

严谨说

更严谨地说，这与 TSR 两级方案的级联思想是同构的（都是「机器负责召回、后一级负责精确率」），但代价结构完全不同：TSR 的第二级代价是延迟，这里第二级代价是人力成本——同一个架构模式，换一个领域代价结构就完全变了，这正是本模块存在的意义：练的是模式识别能力，不是记具体数字。

追问回答要点对应评分维度
「误报率能接受多少？」用代价矩阵反推工作点，不能拍一个固定阈值——「多少」是算出来的不是猜的代价意识
「违规者会不会学习并规避检测？」提到对抗性数据漂移，需要持续监控特征分布漂移 + 快速迭代规则的能力识别领域特有风险
用 accuracy 作为唯一指标是这道题最致命的错误。在 1000:1 不平衡下，「全部预测为正常」就能拿到 99.9% 准确率，但这个系统毫无用处——如果候选人主动提到这一点并解释为什么要用 PR-AUC，这是本案例里权重最高的加分点之一。

6案例⑤ 推荐排序

题面：「设计一个推荐系统的排序模块（给定候选集合，返回排序后的列表）。」

澄清问题

  • 具体场景是信息流排序、搜索结果重排，还是相关推荐？
  • 优化目标是点击率、停留时长，还是要在相关性和多样性之间做多目标权衡？
  • 冷启动用户/物品怎么处理？是否有可用的先验特征？
  • 这道题聚焦哪一段——是完整的召回到重排全链路，还是只做「排序」这一段？（要主动向面试官确认并收窄）

七步展开

步骤这一步说什么
① 范围先声明这题聚焦「精排」这一段（呼应 C47 召回→粗排→精排→重排的完整漏斗），排除召回策略细节
② 指标业务（留存/时长）→模型（nDCG/AUC/校准误差）→系统（延迟）三层映射；离线 AUC 涨在线不涨是这个领域的经典背离
③ 数据用户行为日志作为标签；position bias（位置偏差）和曝光偏差是这个领域特有的数据陷阱
④ 建模baseline 优先用简单 LR/GBDT 特征工程，再上 learning-to-rank（呼应 C47-04）；多目标用多任务学习或加权融合
⑤ 评测离线 nDCG@K/AUC；position bias 会导致离线指标虚高，必须用在线 A/B 校验
⑥ 部署精排通常在几十毫秒延迟预算内对几百候选打分，模型量级要和候选数量做权衡（轻量特征 vs 深模型）
⑦ 风险反馈循环——推荐系统会强化自己的偏差（推荐什么就更容易被点击什么），导致训练数据分布被模型自己污染
\[\text{nDCG@K} = \frac{\text{DCG@K}}{\text{IDCG@K}}, \qquad \text{DCG@K} = \sum_{i=1}^{K}\frac{2^{rel_i}-1}{\log_2(i+1)}\]

直白说

关键取舍：离线 AUC 涨了一点，要不要直接上线？「不能只看涨了多少，要看这个涨幅是否超过种子方差的噪声区间（呼应本课模块01/C61-01 的显著性检验），并且要意识到离线指标本身可能因 position bias 而系统性虚高，最终判断要靠 A/B 的真实业务指标。」

严谨说

更严谨地说，position bias 的成因是：训练数据里排在前面的物品天然获得更多曝光和点击，模型学到的「相关性」里混入了「曾经被排得靠前」这个混杂因素（呼应 C65-02 混杂因素与相关不等于因果）。工业界常用倾向得分（propensity score）或随机化探索流量来去偏，但这已超出本题范围，点到为止即可。

追问回答要点对应评分维度
「离线 AUC 涨了 0.02，要不要上线？」先做显著性/功效判断（呼应模块01/C61-01），量级判断而非直接下结论统计严谨性
「怎么处理 position bias？」提到倾向得分/随机化探索的思路，点到为止（不是本课重点，不必深入）知识广度但不越界

这题呼应 C47 的完整漏斗，但 system design 面试通常只考「精排」这一段——先在①范围阶段划清边界，是这道题的第一个、也是最容易被忽视的加分动作。

7案例⑥ 数据闭环平台

题面：「设计一个数据闭环平台，用于持续发现和修复模型的失效场景。」

澄清问题

  • 服务对象是单一模型（如 TSR）还是通用平台（服务多个感知任务）？——决定架构的通用性要求
  • 触发来源是什么？线上信号、用户反馈，还是离线评测发现的回归？
  • 标注预算规模量级是多少？
  • 谁来决定新模型能不能发布——全自动门禁还是需要人工确认？

七步展开（本案例本质是把 C58 全课打包成一个「系统」的题面，只引用结论）

步骤这一步说什么
① 范围先确认服务对象是单模型还是通用平台——这决定接口设计的通用性要求，是本题最重要的一次澄清
② 指标闭环效率指标——从发现问题到修复上线的周期时间（见 C58-05），不能只看「加了多少数据」
③ 数据触发→挖掘→验证三环节缺一不可（见 C58 全课结论，此处只引用不重述机制）；标注预算按类别缺口×难度×成本分配
④ 建模这一步在这题里不是训练新模型，而是「如何决定该不该训练」——边际收益曲线是核心工具（见 C58-05）
⑤ 评测分场景切片评测 + 回归门禁（见 C58-05），多重比较校正避免「测得越多越容易碰到假阳性」
⑥ 部署平台本身是离线/近线系统，不需要严苛在线延迟，但要考虑百万级样本的存储/索引/去重吞吐（呼应 C58-04）
⑦ 风险数据版本与血缘追踪缺失，会导致出问题时无法回溯是哪批数据/哪次训练造成的——这是平台化的核心工程价值所在
┌──────────┐ ┌──────────┐ ┌──────────┐ │ 触发 │ ───▶ │ 挖掘 │ ───▶ │ 验证 │ ───▶ 发布/回滚门禁 │ Trigger │ │ Mining │ │Validation│ └──────────┘ └──────────┘ └──────────┘ 带宽是硬约束 预算是硬约束 种子噪声是硬约束 （只引用 C58 的三环节划分，具体机制见 C58-02/03/04/05，本题不重复）

直白说

关键取舍：给平台设计「通用性」（服务多个感知任务）vs 只为单一模型（如 TSR）做定制化优化？「通用平台的接口和抽象层要投入更多前期设计成本，但能摊薄到未来所有模型上；单模型定制能更快见效，但每加一个新模型都要重新做一遍。选择依据是团队未来要服务几个模型——如果确定长期只有 TSR 一个消费者，过度设计通用平台是浪费。」

严谨说

更严谨地说，这个取舍是投资回报的时间尺度问题：通用平台的收益在时间轴上后置且随模型数线性增长，定制方案的收益前置但不可迁移。工程上常见的折中是先做单模型定制方案跑通闭环，在第二个模型接入时才抽象出通用接口——这也是「延迟不可逆决策」（呼应 C65-03）原则的具体应用：架构通用化是相对难以撤销的投入，值得等到有第二个真实需求时再做。

追问回答要点对应评分维度
「标注预算只够做一件事，你会先做哪个环节？」用边际收益曲线排序（见 C58-05），量化回答而非凭直觉决策的量化能力
「怎么防止把噪声标签当难例挖掘出来？」引用 C58-02 难例与噪声区分方法（多模型一致性/损失轨迹），点到为止知识边界意识
这道题最容易的失分方式：把「数据闭环平台」讲成「把数据增强和难例挖掘的技术清单念一遍」。面试官要的是「平台」两个字所要求的接口设计、责任边界与门禁规则——这是一道系统设计题，不是一道「你知道多少种难例挖掘技术」的知识问答题（那是 C64/C65 的考法）。

8六个案例的共性：怎么用有限时间准备

如果把六个案例并排对比，会发现它们表面上领域各不相同，但骨架完全一样——这正是本模块设计的初衷：训练「认出模式」的能力，而不是「记住六份答案」的能力。

案例核心难点指标陷阱部署特征呼应课程
① TSR 感知系统小目标 + 长尾类别 + 代价不对称mAP 掩盖关键类，需分桶+代价敏感指标车端在线，硬延迟预算C55/C57/C58/C60
② 车道线/可行驶区域两个任务被误当一个；标定误差非线性放大只看 IoU 忽略横向偏移分布输出频率需匹配控制回路（高频）（本课首创案例，无直接前课）
③ 图搜图/场景检索「相似」定义不清；索引召回-延迟权衡只看 Recall@K 忽略嵌入漂移在线检索 vs 离线去重延迟差数量级C47-03 / C58-04
④ 内容审核/异常检测极端不平衡 + 对抗性环境accuracy 在不平衡下完全失效多为近线/离线，人工复核队列容量C58-01（不平衡谱系）
⑤ 推荐排序position bias + 反馈循环离线 AUC 涨≠在线涨几十毫秒对几百候选打分C47（完整漏斗）
⑥ 数据闭环平台把技术清单讲成「平台」需要接口/门禁思维只看加了多少数据，不看周期时间/回归离线/近线为主，吞吐而非延迟敏感C58 全课

直白说

为什么六个案例「长得像」？因为它们共享同一套可迁移骨架：七步框架（范围→指标→数据→建模→评测→部署→风险）、三层指标映射（业务→模型→系统）、代价不对称的工作点选择、以及服务容量的数量级心算。领域知识（TSR 的小目标、推荐的 position bias、审核的对抗性）只是换了「皮肤」，骨架不变。

严谨说

更严谨地说，这是系统设计能力的可迁移性假设：如果一个人真正掌握了骨架，他应该能在没见过的第七个案例上，用同样的步骤在 45 分钟内产出一份结构完整的方案——这也是本模块判断你是否「学到了」而不是「背到了」的标准：拿一个全新的题面（比如「设计一个语音唤醒误唤醒检测系统」），看自己能不能不看任何参考、独立走完七步。

时间有限时的准备优先级：① 先把 TSR 案例的七步脚本练到能脱稿讲出来（这是唯一保底必考的）；② 再挑 1–2 个「和你过往项目背景最接近」的案例作为第二重点，深入到能被追问三层也不慌的程度；③ 其余案例只需要做到「看到题面能立刻认出属于哪种模式，并知道去哪门课找细节」——不要平均分配时间在六个案例上，那是准备算法面试时「题型平均分配」同一个错误的系统设计版本（见 C62-00）。

9研究前沿与开放问题

system design 面试这套评估方式已经相当成熟，但下面几个问题仍然开放，值得知道它们的存在。

  • ML system design 面试的预测效度缺少公开研究。和 C62-00 提到的 coding 面试类似，「45 分钟能不能讲清一个系统设计」与「这个人实际带项目的能力」之间的相关性，各家都没有公开验证过，评分卡的设计更多依赖行业共识而非实证数据。
  • LLM 正在改变「系统设计」的考察重心。当模型能在几秒内生成一份看起来完整的架构方案时，面试的重心正从「能不能画出架构」转向「能不能在压力追问下暴露方案的隐藏假设与失效边界」——本模块「追问预案」的比重会在未来的面试形态里持续上升。
  • 「平台化」能力目前没有标准化评分维度。案例⑥（数据闭环平台）里「接口设计 vs 定制化速度」的取舍，在工业界有大量实践但少有公开的量化决策框架，这是 ML infra 领域一个尚未被教材充分覆盖的空白。
  • 案例库本身的可迁移性缺少度量。「练六个案例能不能应对第七个没见过的案例」这个核心假设，目前主要靠经验判断，还没有类似「学习曲线」那样可量化的验证方法——notebook 里的自评分器是一个初步尝试，但它衡量的是「覆盖了哪些步骤」而不是「理解的迁移程度」，这是两回事。

★ 必读：Chip Huyen, Designing Machine Learning Systems（O'Reilly, 2022）——本课整套七步框架与「不确定性是一等公民」的核心主张均对照此书，但本课按 XPENG TSR 岗位的题型分布做了重排，并把服务容量心算与六个案例显式化。★ Martin Kleppmann, Designing Data-Intensive Applications——传统后端 system design 的方法论根基，本课模块 04 的延迟/容量心算直接继承其思路。配套材料：各大厂公开的 ML System Design Interview 题库合辑（非官方，但可作为额外练习素材来源）。
