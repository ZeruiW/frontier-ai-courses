1为什么「服务与部署」是 system design 面试的第六步而不是可选项

很多候选人把 system design 面试等同于「选一个模型架构」，讲完 backbone、损失函数、评测指标就觉得大功告成。但面试官在评分卡上单独留了一整栏给服务与部署——因为这是把一个能跑的模型变成能被别人依赖的系统的最后一公里，也是唯一一段能被数量级心算当场验证真假的内容。

这一步要回答的问题很具体：这套方案需要多少台机器？多少显存？多少延迟？花多少钱？扛不住流量峰值怎么办？模型突然变差怎么发现？出了事怎么在 5 分钟内回滚？每一个问题都有一个数量级答案，而面试官最想看到的，正是你能不能当场心算出这个数量级，而不是含糊地说「上 K8s 自动扩缩容就行」。

这一步的隐藏考点是「你是否知道自己的方案值多少钱、跑多快」。一个说得出「TSR 检测模型约 8M 参数，fp16 推理显存占用几十 MB，单张 T4 在 batch=1 下大约 8–15ms，一路车规相机 30FPS 只需一张卡的零头算力」的候选人，比一个只会说「用 TensorRT 加速一下」的候选人，可信度高一个数量级——因为前者展示的是可验证的工程判断，后者只是关键词堆砌。

本节要拆掉的三个误解

误解为什么错正确的心态
「服务架构就是画个框图」框图人人会画，面试官要的是每条边上的延迟/流量数字每画一条箭头，就要能说出这条边大概几毫秒、每秒几次调用
「容量按经验留够余量就行」「留够余量」不是数字，面试官会追问「够是多少」——答不出就露馅永远用心算公式推导一个具体数字，再说「所以我留 X 倍余量」
「降级方案是锦上添花」车规系统里，没有降级方案的设计等于没有设计——模型总会挂，问题只是挂了怎么办降级方案要跟主链路一起画，不是面试最后补一句

直白说

换个说法：如果说模块 01–03 是在回答「我们要造一个什么」，那模块 04 是在回答「造出来的这个东西，物理上跑得动吗、扛得住吗、坏了怎么办」。这三个问题分别对应容量估算、扩缩容、降级与监控——本模块就按这个顺序展开。

严谨说

更严谨地说，服务与部署要交付的是一份可验证的资源-延迟-成本三元组：给定 QPS 目标与延迟 SLA，反推需要多少实例、多少显存、多少预算；并且这份估算要能在两条独立路径上互相校验（例如「按 FLOPs 算」和「按实测吞吐外推」应该给出同一数量级的答案——见模块 05 的通用脚手架）。这正是本课与 C65-01（Fermi 估算）的分工：C65-01 教你怎么心算，本模块教你ML 服务场景下具体估算什么。

「面试官没问延迟/成本我就不用讲」是常见误区。七步框架里这一步默认要主动讲，因为它是区分「纸上谈兵」和「能上线」的分水岭。如果时间紧张，至少要主动说出一张锚点数字表里的两三个数字（本模块第 3 节），哪怕来不及展开推导，也比完全不提要强得多。

2架构图怎么画：数据流、控制流与在线/近线/离线三层

白板上的架构图，评分标准不是「画得像不像论文插图」，而是能不能让面试官一眼看出「数据从哪来、经过谁处理、谁能改变这个流程的走向」。这需要同时画出两种线，很多候选人只画了一种就以为完事了。

线的种类画的是什么TSR 场景的例子遗漏的后果
数据流（实线）数据从产生到被消费的路径：原始信号 → 特征 → 预测 → 下游动作相机帧 → 预处理 → 检测模型 → 后处理 → 跟踪 → 规控只画数据流会让人以为系统没有反馈与控制
控制流（虚线）谁在监控谁、谁能触发降级/回滚、配置从哪里下发监控服务发现延迟超标 → 触发模型降级 → 通知运维 → 人工确认回滚遗漏控制流，面试官会追问「模型挂了谁去处理」，答不上来直接露馅

画完两种线之后，要标出系统边界：哪部分在车端、哪部分在云端；哪部分是我们负责的、哪部分是第三方/上游团队负责的。边界不标清楚，评测和排障责任就说不清楚。

在线 / 近线 / 离线三层：分工原则与延迟量级

几乎所有工业 ML 系统都能拆成这三层，划分依据只有一个：这份计算能不能等。

层延迟量级谁在用它TSR 系统里对应什么为什么不能放到别的层
在线（online）个位数到几十毫秒请求路径上，结果直接影响当前这一帧的动作单帧检测推理、跟踪关联、置信度合成规控要在这一帧做决策，等不了；放慢就是漏检的另一种形式
近线（nearline）秒级到分钟级不阻塞当前决策，但要在「不太久」之后生效多帧置信度累积的滑窗统计、场景标签打点、触发器判定要不要回传这段片段太慢会错过时间窗口（比如已经过了那个路口才判断要不要回传）；但没必要挤占在线预算
离线（offline）小时级到天级批处理，允许攒一批再算夜间批量重标注难例、模型再训练、大规模回归评测、报表在线资源紧张、时效性要求低，硬塞进在线只会拖慢关键路径
在线（车端，个位数~几十 ms） 相机帧 ──▶ 预处理 ──▶ 检测/分类 ──▶ 跟踪与状态机 ──▶ 输出给规控 │ │ │ 采样/触发（低置信、分歧、规则命中）│ 监控埋点 ▼ ▼ 近线（车端缓存 / 边缘节点，秒~分钟级） 实时指标流 置信度滑窗累积、片段打包、场景标签初筛 ───▶ 回传队列（带宽受限） │ ▼ 离线（云端，小时~天级） 数据落库 → 难例挖掘/标注（C58）→ 训练 → 离线评测/回归门禁 → 灰度发布
三层划分的本质是「把等不了的和等得起的分开，不要用离线的思维设计在线，也不要用在线的成本设计离线」。面试里常见的错误是把「多帧投票」直接算进在线延迟预算——其实滑窗累积可以放近线异步进行，只要状态机设计得当（见 C55-04），在线只需要读最新的累积结果，不需要每帧都重算整个窗口。

直白说

画图时的顺序建议：先画在线主链路（这是评分权重最高的部分），再补近线的旁路，最后补离线的回路。很多人一上来就画整个数据闭环（近线+离线），结果时间耗在无关紧要的细节上，反而没时间讲清楚在线路径的延迟预算——本末倒置。

严谨说

更严谨地说，三层的边界不是绝对的，而是由 SLA 决定的相对划分：同一个「置信度更新」计算，在需要每帧输出的系统里是在线的一部分，在只需要每秒输出一次的系统里可以挪到近线。画架构图时，先确认 SLA 数字，再决定某个模块该放哪一层，而不是凭直觉分类。

3可背的锚点数字表：容量估算的地基

数量级心算最怕的不是不会算，而是手里没有可靠的锚点数字——公式对了，代入一个错两个数量级的常数，结论照样错。下面这几张表是本模块乃至整个 system design 面试唯一需要背下来的内容，其余都可以现场推导。

\[\text{显存(GB)} \approx \underbrace{\frac{P \times \text{bytes/param}}{10^9}}_{\text{权重}} + \underbrace{k_{\text{opt}} \cdot \frac{P \times \text{bytes/param}}{10^9}}_{\text{优化器状态（仅训练）}} + \underbrace{\text{激活} \times \text{batch}}_{\text{与输入分辨率/序列长强相关}}\]

背这些表的目的不是精确，是「量级不错」。面试里没人要求你说出「T4 是 65.13 TFLOPS」，但如果你说成「A100 的算力和车端 SoC 差不多」，那是错一个数量级的判断，会被认为完全没有工程手感。记忆的颗粒度应该是「个位数 T / 几十 T / 几百 T / 几千 GB/s」这种数量级标签，而不是精确小数点。

4容量估算的数量级心算：QPS → 实例数、参数量 → 显存、FLOPs → 算力、成本/千次推理

有了锚点数字，容量估算就是四条可以当场心算的公式。面试里要按顺序推导，每一步都口算出中间结果，而不是直接甩出最终答案——过程比答案值钱。

① QPS → 实例数

\[\text{实例数} = \left\lceil \frac{\text{QPS} \times \text{单请求延迟(s)}}{\text{单实例并发度}} \times (1+\text{余量}) \right\rceil\]

其中单实例并发度本身也要拆：GPU 推理常见的做法是动态批处理（dynamic batching），单卡在延迟预算内能吃下的并发请求数 ≈ 延迟预算 ÷ 单请求延迟 × 批处理效率折扣（通常 0.5–0.8）。举例：TSR 云端复检服务 QPS=200，单请求（batch=1）延迟 10ms，SLA 要求 p99 < 50ms，单卡在 50ms 内可接受批处理后约等效于 3–4 个并发 → 需要实例数 ≈ 200×0.01/3.5×1.3 ≈ 0.74 → 至少 2 台（含余量与高可用最低两台）。

② 参数量 → 显存

推理场景的心算三步：①权重（参数量×2 字节 fp16）②KV cache / 激活（随 batch 与序列长/分辨率线性或更高增长）③框架与 CUDA context 固定开销（几百 MB 到 1–2GB）。举例：一个 8M 参数的 TSR 检测器，权重仅 16MB，即使算上激活与框架开销，单卡显存占用通常在几百 MB 量级——这也是为什么车端 SoC 的十几 GB 显存对纯检测模型绰绰有余，真正吃显存的是同时跑的多个感知任务叠加。

③ FLOPs → 算力（需要多少张卡）

\[\text{所需算力(TFLOPS)} = \frac{\text{单次推理 FLOPs} \times \text{QPS}}{\text{硬件利用率} \times 10^{12}}\]

举例：单帧检测推理 4 GFLOPs（TSR 轻量检测器量级），QPS=1000（多路相机汇总到云端做复检），利用率按保守的 0.3 算：所需算力 ≈ 4×10⁹×1000 / (0.3×10¹²) ≈ 13.3 TFLOPS——不到一张 T4 峰值算力（65 TFLOPS）的四分之一，说明瓶颈很可能不在算力而在延迟/调度开销，这个「瓶颈定位」的结论本身就是加分点。

④ 成本 / 千次推理

\[\text{成本/千次} = \frac{\text{单卡每小时成本}}{\text{该卡每小时可处理的请求数}} \times 1000\]

举例：一张云端推理卡每小时成本按几元到十几元量级估（视厂商与是否包年），若单卡每秒能处理 100 次推理（考虑批处理），每小时约 36 万次，则每千次成本 ≈ 单卡时价 ÷ 360 ——量级通常在分钱到一角钱/千次这个区间。这个数字的价值在于横向比较：如果某个方案算出每千次成本是别的方案的 10 倍，即使精度更高，也要在设计里主动提出「这是否值得」。

估算目标核心公式（口诀）最容易出错的常数
实例数QPS × 延迟 ÷ 并发度 × 余量忘记乘余量系数（通常 1.3–2×，覆盖峰值与容错）
显存参数量 × 2字节 + 激活 + 固定开销只算权重、漏算激活——大分辨率/大 batch 时激活占大头
算力FLOPs × QPS ÷ (利用率 × 峰值)用峰值算力代入而不打利用率折扣（0.2–0.5）
成本单卡时价 ÷ 单卡吞吐用「理论最大吞吐」而非「SLA 约束下的实际吞吐」
数量级心算最容易在「单位换算」上翻车：GB 与 Gb 混淆（差 8 倍）、毫秒与秒混淆（差 1000 倍）、TFLOPS 与 GFLOPS 混淆（差 1000 倍）。面试里报错一个单位比算错一个系数更致命，因为它暴露「口算习惯不严谨」。推荐做法：每算一步都显式写出单位，并在心里过一遍「这个数字大概是多少个 0」。

直白说

怎么在白板上呈现这套心算？先说公式骨架，再逐项代入锚点数字，最后给一个带「大约」的结论并主动说校验方法：「QPS 200，单请求 10ms，按并发 3.5 折算，大概需要一台多一点，我会配 2 台留余量。我可以用另一条路径校验一下：按算力账算出来所需 TFLOPS 远小于单卡峰值，说明瓶颈应该在延迟而不是吞吐，两条路径结论一致。」

严谨说

这套心算的理论基础是利特尔法则（Little's Law）：系统内平均请求数 = 到达率 × 平均停留时间，即 $L=\lambda W$。实例数估算本质就是在给定 $\lambda$（QPS）与 $W$（延迟 SLA）时反推需要多大的服务能力 $L$，再除以单实例能提供的服务能力。这是一条比死记硬背公式更可靠的推导起点——忘记具体公式时，回到 $L=\lambda W$ 总能重新推出来。

5延迟预算分解与关键路径

延迟预算分解要回答的问题是：SLA 给的总延迟，怎么分给每一个子系统，谁是瓶颈。这一步的方法论只有一句话：先画出关键路径（critical path），只有关键路径上的延迟才计入端到端延迟——并行发生的分支不叠加。

SLA：端到端 P99 < 100 ms（相机曝光到规控收到结构化输出） ┌───────────┬───────────┬────────────┬───────────┬────────────┬──────────┐ │ 预处理 │ H2D 拷贝 │ 模型推理 │ 后处理NMS │ 跟踪关联 │ 序列化 │ │ 4 ms │ 2 ms │ 12 ms │ 3 ms │ 2 ms │ 1 ms │ └───────────┴───────────┴────────────┴───────────┴────────────┴──────────┘ 合计 24 ms（关键路径，串行）—— 剩余 76 ms 预算去哪了？ │ ┌─────────────────────────┴─────────────────────────┐ │ 并行分支：多帧置信度累积在近线异步进行，不占关键路径 │ │ 另一并行分支：日志与监控埋点异步写，不阻塞主链路 │ └─────────────────────────────────────────────────┘ → 关键路径 24ms << SLA 100ms，说明这条链路有充分余量应对： ① 多相机竞争算力时的排队延迟 ② 偶发的 GC/调度抖动 ③ 后续新增子任务

这张图揭示一个常被忽略的事实：SLA 留的余量，本质上是给「不在关键路径上但会偶发挤占资源」的东西留的——多任务抢占、GC 停顿、温度降频（见 C60-05）、以及未来新增功能。面试里主动提到「留出的余量准备应对什么」比只报一个总数更有说服力。

子系统典型延迟量级决定它的因素优化手段
预处理（resize/归一化/letterbox）1–5 ms分辨率、是否 GPU 侧处理GPU 侧预处理、算子融合，见 C60-01
H2D/D2H 拷贝0.5–3 ms数据量、是否零拷贝/统一内存锁页内存、异步流、零拷贝，见 C60-05
模型推理3–20 ms参数量、精度（fp16/int8）、batch量化（见 C60-03）、结构裁剪、decoder 层数可调（见 C53-04）
后处理（NMS/解码）1–5 ms候选框数量、是否 GPU 侧 NMSclass-agnostic NMS、EfficientNMS plugin（见 C60-04）
跨进程/网络传输（若跨服务）1–10 ms（同机房）；几十~上百 ms（跨地域）是否同机部署、序列化格式同机部署、二进制序列化替代 JSON
关键路径识别的心法：先问「如果这个子系统突然变成 0 延迟，端到端延迟会不会跟着变」。如果答案是否（因为它和别的东西并行发生，被别的分支盖过），它就不在关键路径上，优化它对端到端延迟没有帮助——这是很多人做了「假优化」的根源：优化了一个不在关键路径上的模块，端到端延迟纹丝不动，还以为是测量出了问题。

直白说

延迟预算分解在白板上要先给总数、再拆分、最后指出瓶颈在哪，顺序不能反：「总预算 100ms，我先拆到子系统：预处理 4、拷贝 2、推理 12、后处理 3、跟踪 2，关键路径合计 24ms。推理占了关键路径的一半，如果以后要加功能，优化重点应该先看推理这一块。」

严谨说

更严谨地说，端到端延迟的尾延迟（p99）不等于各阶段 p99 之和——如果各阶段延迟近似独立，端到端 p99 通常比逐阶段 p99 简单相加更极端（多个阶段同时抖动的概率虽低但影响叠加）。工程上通常用各阶段 p50 之和 + 单独测量端到端 p99 做校验，而不是天真地把逐阶段 p99 相加，这也是 C60-05 里「测延迟的正确姿势」一节的结论在系统设计层面的应用。

6批处理与缓存、扩缩容与降级方案

扛住流量峰值、扛住模型偶发失效，靠的是三件事：批处理与缓存（提升吞吐）、扩缩容（应对负载变化）、降级（应对失效而不是假装它不会发生）。三者缺一，方案在面试官眼里就是「没考虑生产环境」。

批处理与缓存

技术解决什么问题TSR 场景怎么用代价
动态批处理（dynamic batching）GPU 利用率低（batch=1 时算力吃不满）多路相机的检测请求在几毫秒窗口内攒批一起推理增加排队延迟，窗口设置需要在吞吐与延迟间取舍
结果缓存重复计算（同一场景短时间内被重复请求）同一标志连续帧的分类结果可复用，无需每帧重跑分类器（见 C55-02 两级方案）缓存失效策略要设计好，否则会用旧结果掩盖真实变化
特征复用多任务共享 backbone 特征，避免重复前向检测/分割/深度估计共享同一 backbone 输出耦合多个任务的发布节奏，一个任务改动可能影响全部

扩缩容

云端服务用基于 QPS/延迟指标的自动扩缩容（当 p99 延迟或队列长度超阈值时加实例），车端没有「扩容」这个选项——车端只有一块固定的 SoC，扩缩容变成了「算力预算内的任务调度」：TSR 只是众多感知任务之一，高优先级任务（避障）挤占算力时，TSR 必须能在更少算力下继续工作，这直接引出降级方案。

降级方案：模型降级、特征降级、兜底规则

降级层级具体做法触发条件代价与恢复
模型降级切换到更小/更快的模型（如 decoder 6 层→3 层，见 C53-04；或退回上一个稳定版本）延迟超阈值、显存不足、新模型上线后指标异常精度下降但仍有输出，优于无输出；需要提前验证降级模型的最低可接受精度
特征降级跳过非必要的增强计算（如关闭多帧融合，只用单帧结果；关闭高分辨率精检分支）算力被高优先级任务抢占、近线服务延迟稳定性/召回下降，但延迟可控；需要有滞后感知（用户/下游应知道当前是降级状态）
兜底规则模型完全不可用时，用简单规则输出保守结果（如「未识别到限速牌时不解除上一个已知限速约束」）模型服务崩溃、推理超时、置信度长期为 0规则通常保守但绝不能是「什么都不做」——见 C59-04 的安全兜底层
没有降级方案的系统设计，在车规场景里是不及格的，无论模型精度多高。面试官会假设「模型一定会挂」，然后问「挂了怎么办」——如果答案是「不会挂」，这个回答本身就是危险信号。正确的姿势是主动画出降级路径，并说明每一级降级对应的精度/延迟代价。
正常路径: 相机 → 检测(全精度) → 跟踪 → 多帧融合 → 高置信输出 │ 延迟超标/显存不足 ▼ 模型降级: 相机 → 检测(轻量版) → 跟踪 → 多帧融合 → 输出(精度略降，仍标注"降级中") │ 轻量版仍不可用/推理服务崩溃 ▼ 特征降级: 相机 → 检测(轻量版) → 跟踪(跳过多帧融合，单帧直出) │ 检测服务完全不可用 ▼ 兜底规则: 维持上一个已知安全状态（如已生效的限速约束不擅自解除），并触发告警

直白说

降级方案在白板上怎么讲？先说触发条件，再说降级动作，最后说恢复条件：「如果延迟连续 3 帧超过 SLA，我会自动切到轻量检测模型；如果轻量模型也失败，跳过多帧融合直接用单帧结果；如果检测服务整体挂了，跟踪与规控维持上一个已知状态而不是清空，同时打告警。延迟恢复正常 10 秒后，逐级恢复到全精度路径。」

严谨说

更严谨地说，降级方案的设计要满足单调保守性：每一级降级的输出集合应该是上一级的一个安全子集，而不是引入新的不确定行为。这与 C65-03「不可逆 vs 可逆决策」的原则一致——降级动作本身应该是可逆的（能自动恢复），但降级期间的每一个决策不能是不可逆的危险动作。

7监控与回滚：数据漂移、指标漂移、延迟分布

部署上线不是终点，监控是让「系统正在变差」这件事从「路测时才发现」变成「几分钟内被自动发现」的机制。面试里这一节常被压缩成一句「上监控」，但完整的监控体系要覆盖三类完全不同的漂移。

监控对象度量什么为什么会漂移典型告警设计
数据漂移输入分布是否变化（如夜间占比突增、新地区标志样式变化）季节/地域/传感器更新导致输入分布偏离训练分布对关键输入特征（亮度均值、目标尺寸分布）设分位数告警，超出训练分布的 P1/P99 区间即报警
指标漂移线上代理指标是否变化（置信度均值、检出率、FP/km，见 C55-05）模型退化、上游预处理悄悄改动、新版本模型引入回归对每个关键类别设独立的滑窗均值告警，避免被大类平均掩盖小类退化
延迟分布p50/p99 是否漂移、是否出现静默回退（见 C60-05）硬件降频、负载升高、TensorRT 引擎与硬件/驱动不匹配对 p99 设硬阈值告警；额外监控「分区数」以发现静默回退
\[\text{误报率控制}: \quad \Pr(\text{告警} \mid \text{系统正常}) \le \alpha, \qquad \text{通常取 } \alpha \in [0.001, 0.01]\ \text{（每千/每百次检查允许一次误报）}\]

阈值设定的核心矛盾：阈值太紧 → 告警疲劳（误报率高，值班人员开始无视告警）；阈值太松 → 漏报（真实退化没被发现，直到用户投诉或事故发生）。工程上常用训练/验证集上的历史分位数 + 滑窗平滑 + 连续 N 次超阈值才触发三件套来控制误报率，而不是对单次观测值设死阈值。

回滚：不是「删掉新版本」，是「验证过的降级路径」

  • 回滚必须在部署前就验证过，而不是出事时现推演——把回滚当成降级方案的一种（模型降级到上一个稳定版本）。
  • 回滚要有明确的触发条件与责任人：谁能决定回滚、需要多少证据、回滚决定要不要人工确认——全自动回滚适合有把握的场景（如延迟超标），涉及精度/安全判断的回滚通常要保留人工确认环节。
  • 灰度发布本身就是回滚成本最低的部署方式：先在 1% 流量/影子模式验证（见 C58-03），出问题时只影响很小范围，比全量发布后再回滚代价低得多——这也是为什么模块 03 强调 A/B 与影子模式。
「监控了平均值」是最常见的监控盲区。平均值会掩盖尾部退化——一个占比 2% 的稀有标志类召回从 90% 掉到 40%，在整体 mAP 上可能只掉 0.5 个点，但对下游安全动作是致命的。关键类别必须有独立的监控线，不能只看聚合指标——这与 C55-05「为什么 mAP 不足以衡量 TSR」是同一个论证在监控层面的应用。

直白说

白板上讲监控，建议按「三类漂移 + 告警阈值设计 + 回滚触发条件」的顺序过一遍，最后加一句「关键类别单独监控，不能只看聚合指标」——这一句往往是加分句，因为大部分候选人只会说「上 Grafana 看指标」。

严谨说

更严谨地说，监控系统本身也要满足可观测性的三个支柱（metrics/logs/traces）： 指标（metrics）负责「有没有问题」的快速判断，日志（logs）负责「具体哪一条请求出的问题」，追踪（traces）负责「问题出在链路的哪一段」——延迟预算分解（第 5 节）里的每一段都应该有独立的 trace span，否则出问题时只能定位到「端到端变慢了」而无法定位到具体子系统。

8车端与云端的分工：为什么不能什么都放车上，也不能什么都放云上

TSR 这类车规感知系统的服务架构，本质上是一个车端-云端的分工问题，而不是纯粹的云端服务设计。分工的判据只有一条：这个计算需不需要在没有网络的情况下也能正确工作。

维度车端云端分工原则
延迟要求个位数到几十毫秒（硬实时）可以容忍百毫秒到秒级凡是直接影响当前帧决策的，必须在车端
算力预算固定、共享给多个感知任务（见第 6 节）近乎弹性（可加机器）算力密集但不紧急的任务（大模型复检、离线训练）放云端
网络可用性不可假设网络时刻在线假设网络可用任何「网络断了会导致安全问题」的功能都不能依赖云端
模型规模受限于车端 SoC 显存与算力，通常是小模型/蒸馏后的模型可以跑大模型（VLA 云端大模型，见 C59-01）云端大模型的知识蒸馏到车端小模型，而不是车端直接跑大模型
数据回传受带宽限制，只能回传触发片段（见 C58-03）接收车队回传数据，驱动数据闭环（见 C58-05）车端做「筛选」，云端做「深加工」
一句话记住车云分工：车端负责「这一帧必须现在决定的事」，云端负责「攒起来一起做更好」。TSR 检测本身必须在车端；但「这个新标志样式我们要不要专门训一版模型」这种决策，完全可以云端慢慢做。混淆两者的后果是要么车端算力扛不住，要么因为等云端而错过决策时机。

直白说

在系统设计面试里，一旦画出「车端-云端」两个框，就要主动说明网络断开时车端能不能独立工作到「安全」的程度——这一句话直接回应了车规系统对「优雅降级」的最高要求：不是「效果好」，而是「网络断了也不会做出危险决策」。

严谨说

更严谨地说，车云协同架构本质上是一种分层容错设计：车端是保证安全下限的「快系统」，云端是提升体验上限的「慢系统」（呼应 C59-04 的快慢双系统）。评估这类架构时，要分别验证「快系统单独工作时是否仍安全」与「慢系统失效时快系统是否能优雅接管」两条独立性质，而不是把两层耦合在一起测试。

9研究前沿与开放问题

服务与容量估算这套心算方法论已经相当成熟，但下面几个方向仍在快速变化，值得知道它们的存在。

  • 推理服务的成本模型正在被 MoE 与推测解码（speculative decoding）重写。传统「参数量 → 显存 → 成本」的线性心算对稀疏激活模型不再直接适用——MoE 模型的显存占用接近总参数量，但推理算力只对应激活参数量，两者要分开估算。这对 VLA 云端大模型的成本估算（见 C59-05）影响尤其大。
  • 车端多任务算力调度缺少公开的量化方法论。已知「车端算力常被多任务分摊」是共识，但如何在系统设计阶段就为「TSR 之外还有 N 个感知任务」做出可验证的算力预留，目前更多是各家的内部工程经验，缺少公开的调度模型与 benchmark。
  • 降级方案的形式化验证仍是空白。「降级动作是安全子集」目前主要靠工程规范与人工评审保证，还没有成熟的自动化工具能验证一条降级路径在所有触发场景下都不会引入新的危险行为——这与形式化方法（formal verification）在自动驾驶软件栈的应用是同一个更大的开放问题的一角。
  • 「监控什么」正在从人工设计指标转向自动发现异常模式。传统监控依赖工程师预先想好告警规则，而基于无监督异常检测的监控（自动发现「以前没见过的输入分布」而不需要预先定义规则）正在成为长尾场景漏检的补充手段，但误报率控制仍是主要瓶颈。
