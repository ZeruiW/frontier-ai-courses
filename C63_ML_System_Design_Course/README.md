# ML 系统设计面试

这门课补的是一块**看起来存在、实际几乎是空白**的缺口。

HR 给出的一面形式白纸黑字写着：

> First Round Interview Format (including but not limited to):
> Technical Knowledge Assessment, **Problem-Solving**, and Practical (Coding) Exercise
> "it'll include coding, **system design**, ML knowledge, etc."

而在 C00–C62 这 63 门课里，检测、TSR、部署、VLA 的领域深度覆盖得很密，
但用关键词把全库扫一遍会看到：**只有 C07 模块 07 的一节**提到过
「ML/eval system design 框架」——**没有七步方法论，没有时间预算表，
没有案例库，甚至没有讲清楚"这类面试到底在评什么"**。

## 核心主张

这门课只讲一件事，但要讲透：

> **system design 面试评的不是你画的框图有多复杂，
> 而是「需求澄清 + 取舍显式 + 能自我批判」这三件事。**

三个维度分别对应：

1. **需求澄清**——你有没有先把一道没有边界的题，收敛成一道可验收的题；
2. **取舍显式**——你的每一个技术选择，能不能说出「为什么选它、放弃了什么」；
3. **自我批判**——你敢不敢在结尾主动说出「这个方案的弱点是什么、我会怎么验证它」。

大多数候选人败在这三件事上，而不是败在"不懂某个模型"。
这门课把三件事拆成可训练的动作：**七步框架** + **45 分钟时间预算** + **六个完整案例演练**。

## 七步框架速记

这是贯穿全课的骨架，00 模块给出检查器，01–04 模块逐步展开，05 模块拿六个案例练习完整走一遍。

| 步骤 | 一句话 | 常见追问 | 建议用时（45 分钟里） |
|---|---|---|---|
| ① 澄清与范围 | 把模糊需求变成可验收规格：用户/场景/成功/失败/代价/约束/不做什么 | "如果我们不做这个假设呢" | 5–7 分钟 |
| ② 成功指标 | 三层指标映射（业务→模型→系统）+ 工作点选择 | "这个指标涨了，业务方真的会满意吗" | 3–5 分钟 |
| ③ 数据 | 来源、标注、划分与泄漏防范、长尾、冷启动 | "训练集哪来、够不够、会不会泄漏" | 5–7 分钟 |
| ④ 建模 | baseline 优先、约束驱动选型，不是新颖度驱动 | "为什么不直接上最新论文的模型" | 8–10 分钟 |
| ⑤ 评测 | 离线（切片/门禁/显著性）+ 在线（A/B/影子/灰度） | "+0.3 算提升吗，怎么证明" | 5–7 分钟 |
| ⑥ 服务与部署 | 架构分层、延迟预算分解、容量估算、降级方案 | "P99 延迟怎么保证" | 8–10 分钟 |
| ⑦ 迭代与风险 | 监控、回滚、失效模式、下一步怎么改进 | "如果上线后指标掉了怎么办" | 3–5 分钟 |

**四种最常见的失败模式**（任意一种出现都会被明显扣分）：

1. **直接跳到模型架构**——跳过①②，面试官会怀疑你是不是背了一个通用模板；
2. **不问约束**——不问延迟/算力/成本，方案听起来完整但**不可部署**；
3. **不谈评测**——只讲怎么训练，不讲怎么证明训好了；
4. **不谈失败与回滚**——听起来"这个系统永远不会错"，这是最大的危险信号。

## 学习路径（按你还剩多少时间选）

### 路径 A · 还有一周（约 8–12 小时）

完整走一遍 `00 → 01 → 02 → 03 → 04 → 05`，每天一个模块，
先读 HTML 讲解（30–40 分钟），再跑 notebook 并**动手把每个求解器/估算器跑一遍、改改参数看结果怎么变**
（40–60 分钟）。最后 1–2 天专门做 05 的六个案例，**严格计时 45 分钟，出声讲，讲完自己按评分要点打分**。

判断走完了没有的标准很简单：**给你一道全新的模糊需求，你能不能在 90 秒内说出一个可验证的范围假设。**

### 路径 B · 还有三天（约 5–6 小时）

`00 → 01 → 04 的锚点数字表 → 05`，跳过 02/03 的完整讲解，只看它们的要点小结与 notebook 里的关键结论。

理由：01（需求澄清）和 05（案例演练）是**最直接影响当场表现**的两块，
而 02/03 的具体方法（标注成本模型、切片评测设计）在案例库里已经被引用和复习了一遍，
**边际收益不如把时间投在"能不能顺畅地过一遍完整案例"上**。

- **Day 1**：00 全部 + 01 全部（七步框架与需求澄清清单要能脱稿复述）。
- **Day 2**：04 的容量估算锚点数字表（背下来）+ 05 的 TSR 案例（本岗位主案例，逐字过一遍脚本）。
- **Day 3**：05 剩余五个案例，每个限时 20 分钟简化演练（正常是 45 分钟，压缩练反应速度）。

### 路径 C · 只剩一晚（约 2.5 小时）

**不要试图学新内容，只做两件事：**

1. **读 00 + 记住七步框架与四种失败模式**（30 分钟）——这一步不增加你会的知识，
   但能保证你不会当场漏掉某个环节，性价比最高。
2. **过一遍 05 的 TSR 案例脚本**（60 分钟）——这是本岗位面试最可能出现的题，
   逐字看一遍"澄清问题 → 七步展开 → 关键取舍 → 追问预案"，然后合上脚本自己复述一遍。

剩下时间：把 04 的容量估算锚点数字表（QPS→实例数、参数量→显存、FLOPs→算力）扫一遍，
这是"听起来有工程手感"最廉价的加分点。

**明确不要做的事**：不要在最后一晚试图理解 02 的标注成本模型推导细节。
遇到数据设计问题时，诚实地说出"这里有几个方案，我按成本从低到高排一下优先级"，
这个回答本身已经体现了取舍显式化，比记不住的公式更值钱。
