1为什么今天还要懂 TensorFlow

先诚实地承认现状：研究生态已经彻底 PyTorch 化。新论文的官方实现、HuggingFace 的主线、绝大多数教程——都是 PyTorch。那为什么还要花一个模块讲 TensorFlow？

理由具体情形需要到什么程度
生产栈存量巨大很多企业的推理服务是 TF Serving、数据管线是 tf.data、移动端是 TFLite能读懂、能改、能对接
复现旧工作2016–2020 年的大量论文（含 BERT、T5 的原始实现）是 TF能读代码、能把权重搬出来（模块 02）
JD 明确要求「TensorFlow, PyTorch, or JAX」几乎是标配写法能说清三者的语义差别
理解「静态图」这个范式torch.compile、JAX 的 jit、ONNX 导出、TensorRT 全都基于同一套「追踪成图再优化」的思想这是最重要的理由

直白说

最后一条值得展开：PyTorch 2.x 之后，「静态图」的概念反而变得更重要了。torch.compile 做的事情——追踪、构图、优化、缓存、遇到不支持的东西就 graph break——与 tf.function 在概念上是同一件事。理解 TF 的追踪语义，能让你立刻明白 torch.compile 为什么会重编译、为什么某些 Python 代码会让它退化。

严谨说

换句话说：这个模块表面上讲 TensorFlow，实际上讲的是「Python 代码怎么变成一张计算图」这个跨框架的通用问题。同一套语义在 TF（tf.function）、JAX（jit）、PyTorch（torch.compile）、以及 ONNX 导出（torch.onnx.export 的 tracing 模式）里反复出现，而它的坑也一模一样：追踪时 Python 只跑一次、控制流会被固化、副作用只发生在追踪期、形状变化会触发重追踪。

所以学这个模块的正确心态是：不是「学一个过时的框架」，而是「学一个所有现代框架都在用的范式」——而 TensorFlow 恰好是这个范式最早、也最彻底的实现，所以它的语义暴露得最清楚。用 TF 理解追踪，再回头看 torch.compile，会觉得后者只是把同样的东西藏得更深了一些。

2静态图 vs 动态图：一个概念上的分界

动态图（eager / define-by-run）—— PyTorch 默认、TF2 默认 Python 逐行执行，每个算子立刻算出结果 y = x @ w # ← 这一行执行时，矩阵乘真的发生了 if y.sum() > 0: # ← 真的读了 y 的值来做分支 z = relu(y) ✅ 好调试（可以 print、可以打断点、可以用 Python 的一切） ❌ 无法整图优化（算子融合、常量折叠、内存复用都做不了）；无法脱离 Python 部署 静态图（graph / define-and-run）—— TF1 默认、tf.function / jit / compile Python 只是**构图脚本**，跑一遍产出一张图；之后执行的是图，不是 Python @tf.function def f(x): y = x @ w # ← 这一行执行时，只是往图里**加了一个节点** if tf.reduce_sum(y) > 0: # ← 变成图里的一个 tf.cond 节点 z = tf.nn.relu(y) return z ✅ 可整图优化、可序列化、可脱离 Python 部署（TF Serving / TFLite / ONNX） ❌ 调试困难（print 只在追踪时执行一次）；Python 控制流会被**固化**
维度动态图静态图
Python 代码的角色就是计算本身构图脚本（只跑一次或极少次）
print(x) 的行为每次调用都打印当前值只在追踪时打印一次，之后完全不执行
Python 的 if每次按实际值分支按追踪时的值固化成一条分支
跨算子优化❌✅ 融合、常量折叠、布局优化、内存复用
部署需要 Python可脱离 Python
形状变化无所谓可能触发重追踪（每种形状一张图）

直白说

两栏里最容易咬人的是 print 与 if 这两行。「Python 代码只在追踪时跑一次」这个事实，会让一大批看起来正常的代码产生诡异行为：调试用的 print 只出现一次然后消失；用 Python 变量做的计数器永远停在追踪时的值；if len(x) > 5 这样的条件被永久固化成追踪那次的结果。而它们都不报错。

严谨说

解决办法是区分「构图时的量」与「运行时的量」。构图时的量（Python int、list、shape 的静态部分）在追踪时就确定；运行时的量（tensor 的值）只有执行图时才知道。凡是要依赖运行时的量做的事，都必须用框架提供的图算子表达——TF 里是 tf.cond/tf.while_loop/tf.print，JAX 里是 lax.cond/lax.scan，PyTorch 编译时是让它 graph break 或用 torch.cond。这条区分是所有静态图框架的第一性原理。

TF 有一层额外的复杂度叫 AutoGraph：它会自动把一部分 Python 控制流改写成图算子（if → tf.cond、for → tf.while_loop），但只在条件依赖于 tensor 时才改写。这个「有时改写、有时不改写」的行为是 TF 最难懂的地方之一——同样一段 if，条件是 Python bool 就固化、是 tensor 就变成图节点。写 tf.function 时，最好显式地知道每个条件到底是哪一种，而不是依赖 AutoGraph 猜对。

3重追踪：性能问题的头号来源

tf.function 会为每一种输入「签名」缓存一张图。签名 = (输入的 dtype, 形状, 以及所有 Python 参数的值)。签名变了就重新追踪一次。

\[\text{cache key} = \big(\text{dtype}_1, \text{shape}_1, \dots, \text{dtype}_n, \text{shape}_n,\; \text{python\_args}\big)\]
什么会触发重追踪为什么怎么避免
输入形状变化每种形状一张图input_signature 里把可变维标成 None；或把 batch/seq padding 到固定桶
dtype 变化同上统一 dtype，别混 fp32/fp16 调用
传 Python 标量而非 tensorf(x, 3) 与 f(x, 4) 是两个不同签名把它包成 tf.constant(3)，或用 input_signature 声明
传 Python 对象（list/dict/自定义类）按值/按 id 参与 key尽量只传 tensor
每次调用都新建 tf.function缓存跟着函数对象走，对象没了缓存也没了别在循环/方法内部定义 @tf.function

直白说

最后一行是个非常隐蔽的性能杀手：在类的方法里或循环里创建 tf.function，每次都会得到一个新的函数对象，缓存永远命中不了——于是每一步训练都在重新追踪。症状是「训练极慢但 GPU 利用率很低」，而代码看起来完全正常。TF 会在重追踪超过若干次后打一个警告，但那条警告很容易被淹没在日志里。

严谨说

重追踪的代价有多大？追踪一次的成本大致相当于跑几十到几百次前向（要执行 Python、构图、做图优化）。所以如果每一步都重追踪，你的吞吐会掉一到两个数量级。这与 torch.compile 的重编译完全同构——后者的重编译更贵（要跑 Inductor 生成 kernel），所以 PyTorch 提供了 dynamic=True 与 torch._dynamo.config.cache_size_limit 来控制。两个框架的调优手段不同，但要诊断的现象是同一个：「你的图被重建了多少次」。

调试静态图的三个技巧

  • 先关掉编译再调试：tf.config.run_functions_eagerly(True) / torch._dynamo.disable() / jax.disable_jit()。先确认逻辑对，再打开编译确认语义没被追踪改变——把两类问题分开，比在编译模式下硬调快得多。
  • 用图内的打印算子：tf.print（不是 Python 的 print）、jax.debug.print。它们是图的一部分，每次执行都会打印，所以能看到运行时的真实值。
  • 数副作用的执行次数：上面那个计数器技巧。它同时诊断两件事——执行次数 > 1 说明有重追踪；执行次数 = 调用次数说明编译完全没生效。

这三招合起来能覆盖静态图调试的绝大多数场景，而且它们的顺序是有讲究的：先用第一招把「逻辑错」与「追踪语义错」分开——如果关掉编译后结果就对了，问题一定在追踪语义（控制流被固化、形状被写死、副作用消失）；如果关掉编译还是错，那就是普通的逻辑 bug，跟静态图无关。这个二分能省掉大量在错误方向上的排查。

诊断重追踪有一个通用技巧，跨框架都能用：在被编译的函数里放一个纯 Python 的副作用（如 print 或计数器自增），然后数它执行了几次。执行次数 = 追踪次数。如果它在训练循环里每步都打印，你就抓到了重追踪。这个技巧同时也演示了「Python 代码只在追踪时执行」这个语义——notebook 会把它实现出来。

4Keras 的三种 API：什么时候用哪个

API长什么样能表达什么不能表达什么
Sequentialkeras.Sequential([Dense(64), Dense(10)])单输入单输出的线性堆叠分支、多输入输出、残差
Functionalx = Input(...); y = Dense(64)(x); Model(x, y)任意 DAG（多输入输出、残差、共享层）依赖运行时值的控制流、递归
Subclassingclass M(keras.Model): def call(self, x): ...任意 Python 逻辑（最像 PyTorch）—（但失去了静态图检查与自动可视化）

直白说

三者的关系值得说清：Functional API 构建的是一个「可被检查的数据结构」——它在定义时就知道整张图的拓扑与形状，所以能做 model.summary()、能画图、能自动检查形状不匹配、能被完整序列化成 .keras/SavedModel。Subclassing 则是纯 Python，框架看不到内部结构，所以 summary() 要先跑一遍才知道形状，序列化也需要额外的 get_config()。

严谨说

这与 PyTorch 的差别是范式级的：PyTorch 只有 subclassing 这一种（nn.Module.forward 是纯 Python），它放弃了「模型是可检查的数据结构」这个性质，换取了完全的灵活性。所以 PyTorch 要导出图必须靠追踪（torch.jit.trace/torch.onnx.export/dynamo），而 Keras Functional 模型天然就是图。模块 03 讲导出时你会看到这个差别的直接后果：Keras Functional 导出几乎无痛，PyTorch 导出要处理一堆追踪的坑。

三个「不报错但数值错」的默认值差异

这张表的最后三行是迁移事故的最高发区，而且它们的共同特点是「代码不报错、形状也对、但数值错」。Conv2D 的权重布局（(out,in,kH,kW) vs (kH,kW,in,out)）不转置就直接 reshape，会得到一个形状正确但完全乱掉的卷积核。LayerNorm 的 eps 相差 100 倍，在激活值很小时会造成可观的数值差异。BatchNorm 的 momentum 语义相反——PyTorch 的 0.1 对应 TF 的 0.9，直接照抄数字会让滑动统计量的更新速度差 9 倍。模块 02 会把这些做成一张可执行的映射表。

5顺带说清 JAX：第三种范式

JD 里的三个框架，JAX 是最不一样的一个。用一段话把它的定位说清楚，你就能在面试里准确回答「三者的区别」。

PyTorchTensorFlowJAX
核心抽象有状态的 nn.Module有状态的 Layer + 图纯函数 + 显式参数
参数在哪藏在模块里藏在层里作为参数显式传入（pytree）
随机数全局 RNG全局 RNG显式传 key（可复现性极强）
图从哪来compile/tracetf.functionjit
变换——grad/vmap/pmap/jit 可自由组合
最大优势生态与灵活生产栈与部署可组合的函数变换 + XLA 编译

直白说

JAX 的核心主张是「把模型写成纯函数」：y = f(params, x)，参数显式传入、没有隐藏状态、随机数靠显式 key。代价是写起来更啰嗦（要自己管 params 树），收益是所有变换都能自由组合——jit(grad(vmap(f))) 是合法且常用的写法，而这在有状态的框架里很难做到。

严谨说

对本课的意义在于：JAX 把「静态图追踪」的语义暴露得最彻底。它的 tracer 对象在追踪时代替真实数组，任何试图对 tracer 做 Python 层面判断（if x > 0、int(x)）的代码都会立刻报错（ConcretizationTypeError），而不是像 TF 那样静默固化。这个「宁可报错也不静默」的设计，反而让 JAX 的追踪语义最容易学对。如果你想真正理解追踪，从 JAX 学最快；如果要面对生产存量，从 TF 学最有用。

一个能在面试里用的总结：三个框架的差别不在「能做什么」（都能训 Transformer），而在「状态放在哪里」与「图从哪里来」。PyTorch：状态在对象里、图靠事后追踪；TensorFlow：状态在层里、图靠 tf.function 装饰；JAX：没有隐藏状态、图靠 jit 且变换可组合。把这三句话说清楚，比列举 API 差异有说服力得多。

6算一笔账：追踪的成本与收益

静态图不是免费的。它的取舍可以量化成一个简单的盈亏平衡问题。

\[\text{总时间}_{\text{图}} = n_{\text{trace}} \cdot C_{\text{trace}} + N \cdot t_{\text{graph}}, \qquad \text{总时间}_{\text{eager}} = N \cdot t_{\text{eager}}\]
\[\text{值得编译} \iff N > \frac{n_{\text{trace}} \cdot C_{\text{trace}}}{t_{\text{eager}} - t_{\text{graph}}}\]
场景追踪次数单次追踪成本加速比盈亏平衡的调用次数
形状固定的训练循环1≈ 200 × 单步1.3×≈ 870 步（很快回本）
形状固定的推理服务1≈ 200 × 单步1.5×≈ 600 次
形状每次都变= 调用次数≈ 200 × 单步1.3×永远不回本
形状分 8 个桶8≈ 200 × 单步1.3×≈ 7000 次

第三行是关键：如果每次调用的形状都不同，追踪次数等于调用次数，编译永远是纯亏损——而且比 eager 还慢（多了追踪开销）。这就是「变长输入 + 静态图」的根本矛盾。三条标准解法：

  • 形状分桶：把序列长度 padding 到 {128, 256, 512, …} 这样的几个桶，把追踪次数从 N 降到桶数。代价是 padding 浪费（C50 模块 02 算过）。
  • 动态维度：TF 的 input_signature 里把可变维标成 None、PyTorch 的 dynamic=True、ONNX 的动态轴（模块 03）。代价是失去部分基于静态形状的优化。
  • 只编译热点：把形状稳定的部分（如单层 Transformer block）编译，形状多变的部分留在 eager。这是最实用的折中。

把本模块浓缩成一句可迁移的智慧：「Python 代码只在追踪时执行一次」这一句话，能解释静态图框架里 80% 的诡异行为——print 只出现一次、计数器不动、控制流被固化、形状一变就变慢。而且它跨框架成立：tf.function、jax.jit、torch.compile、torch.onnx.export 全都如此。学会问「这一行是在构图还是在计算」，你就掌握了这一整类框架。

7生态动态与开放问题

  • 范式的收敛：PyTorch 2.x 引入编译、TF2 引入 eager、JAX 一直是「纯函数 + jit」。三者在语义上正在互相靠拢，但工程细节（缓存策略、graph break 的处理、动态形状的支持程度）差异仍大。「一份代码跑三个后端」（如 Keras 3 的多后端）是当前的尝试，成熟度仍在演进。
  • 动态形状的编译：这是所有编译器共同的难题。符号形状（symbolic shapes）、形状特化与去特化的策略、以及「多大的形状变化才值得重编译」都缺乏好的自动决策，目前主要靠人工配置分桶。
  • graph break 的可诊断性：torch.compile 遇到不支持的 Python 会静默地打断图（回退 eager），性能损失巨大但不报错。TORCH_LOGS=graph_breaks 之类的工具在改善，但「为什么这里断了、怎么改」仍需要相当的经验。
  • 训练与推理图的一致性：训练用的图与导出的推理图常常不同（dropout、BN 的行为、控制流分支）。「保证导出的图与训练时数值一致」缺乏自动化的验证工具——这正是模块 02/03 要你手写对拍的原因。
  • Keras 3 的多后端路线：同一份 Keras 代码跑在 TF/JAX/PyTorch 后端上。它对「跨框架迁移」是个有意思的答案（不迁移，换后端就行），但对已有的原生代码没有帮助，且抽象泄漏在所难免。

必读：TensorFlow 官方指南的 Better performance with tf.function（重追踪的准确规则与诊断方法，本模块第三节的一手来源）、Introduction to graphs and tf.function、The Keras functional API；JAX 文档的 How to think in JAX 与 JAX — The Sharp Bits（后者把追踪的坑列得最清楚，强烈推荐即使你不用 JAX 也读一遍）；PyTorch 的 torch.compile 与 TorchDynamo 文档（对照阅读会发现语义高度同构）。原理侧：C38（autograd 与编译）、C36（kernel 与融合）。完整清单见 references.md。
