1集大成：把零件组装成 agent

到这里，我们已经造好了一个编码 agent 的全部零件：文件工具（手，模块 01）、Shell 工具（脚，模块 02）、代码搜索（眼，模块 03）、Edit-Test-Fix 循环（小脑，模块 04）。本模块是集大成——把这些零件组装成一个完整的、能端到端解决任务的编码 agent，让它在一个玩具仓库里真的修好一个 bug、跑绿测试，并用 SWE-bench 式的视角评判它是否成功。

组装一个 agent，需要三样新东西，本模块逐一攻克：① 工具注册表（tool registry）——把所有工具登记成一张「名字→实现+参数说明」的表，让 agent 能按名字查找、调用、捕获错误；② agent 主循环——模块 00 那个骨架的完整版：LLM 发起工具调用 → 分发执行 → 把结果回填 → 再问 LLM，直到任务完成；③ 系统提示与评测——给 agent 定下行为纪律（先看再改、改完跑测试、别改测试作弊），并用「补丁是否让测试通过」客观地评判它。

这正是 Claude Code、SWE-agent、aider 这些真实编码 agent 的内核结构。它们当然比我们的玩具复杂得多——更多工具、更精巧的提示、更强的上下文管理、与真实大模型对接——但骨架是同一个：一组工具、一张注册表、一个循环、一套纪律、一个客观的成功判据。本模块结束时，你会拥有一个不到两百行、不依赖任何框架、却真能修 bug的完整编码 agent，并彻底理解它每一个齿轮如何咬合。

一句话抓住本模块：把手/眼/脚/小脑组装成一个完整 agent = 工具注册表（按名字分发）+ agent 主循环（LLM 发起 tool_use→执行→回填 tool_result→再问）+ 系统提示（行为纪律）+ SWE-bench 式评测（补丁让测试通过 = 成功）。零件齐了，组装才是 agent。

2工具注册表：能力登记成表

工具注册表：把能力登记成一张表

前几个模块写了一堆工具函数（read_file、edit_file、run_shell、code_search……）。要让 agent 能自主地用它们，得先把它们组织成一张注册表：每个工具登记三样——名字（LLM 用它指名调用）、实现函数（实际执行的代码）、参数模式 schema（告诉 LLM 这工具要什么参数）。

class ToolRegistry:
    def __init__(self, work):
        self.work = work
        self.tools = {}        # name -> {'fn': callable, 'schema': dict}
    def register(self, name, fn, schema):
        self.tools[name] = {'fn': fn, 'schema': schema}
    def call(self, name, args):
        '''按名字分发执行，捕获异常转成对 LLM 友好的错误字符串。'''
        if name not in self.tools:
            return f'错误：未知工具 {name}。可用：{list(self.tools)}'
        try:
            return self.tools[name]['fn'](self.work, **args)
        except Exception as e:
            return f'工具 {name} 执行出错：{type(e).__name__}: {e}'   # 不让异常崩掉循环
    def schemas(self):
        return [t['schema'] for t in self.tools.values()]   # 喂给 LLM 的工具清单

注册表有两个关键设计。其一，分发时捕获一切异常：工具执行可能抛错（文件不存在、编辑匹配不上、命令超时），绝不能让一个工具的异常崩掉整个 agent 循环。要把异常转成一条对 LLM 友好的错误字符串回填——这样 LLM 看到「编辑失败：匹配了 3 处」，能自己纠正重试，循环继续。其二，注册表能吐出所有工具的 schema 清单，这正是要传给 LLM 的「你有哪些工具可用」——它据此知道能调什么、怎么填参数。

直白说

工具注册表就像给 agent 一个「工具箱清单 + 说明书」：每件工具有名字、有功能说明、有「怎么用」（要哪些参数）。agent（LLM）看着这份清单决定「这一步该用哪件工具、怎么填参数」，然后注册表负责把它的请求翻译成实际的函数调用。

严谨说

形式上，注册表是一个从工具名到 (实现, 接口契约)的映射，外加一个分发器（dispatch）。它实现了LLM 的符号化请求（「调用 edit_file，参数 {...}」）与宿主的实际执行之间的解耦——LLM 只需知道名字和 schema，无需知道实现；宿主可自由替换实现而不影响 LLM。这与 RPC、插件系统、以及 MCP（模型上下文协议）是同构的设计——MCP 正是把这套「工具注册 + 分发」标准化成跨 agent 的协议。

注册表里那行捕获一切异常、转成友好错误看似不起眼，却是 agent鲁棒性的命门。没有它，LLM 一个填错参数的工具调用就会让整个 agent 崩溃退出；有了它，错误变成 LLM 能看见、能学习、能纠正的反馈——agent 从「脆弱」变「有韧性」。这再次呼应全课主线：把错误做成对 LLM 友好的反馈，agent 才能自我纠正。

3agent 主循环：tool_use→执行→tool_result

Agent 主循环：tool_use → 执行 → tool_result

有了注册表，就能写agent 主循环——模块 00 那个骨架的完整版。它的节奏是：把任务和工具清单发给 LLM，LLM 要么请求调用工具（继续），要么给出最终答复（结束）；若请求工具，就分发执行、把结果回填进对话，再发给 LLM；如此往复，直到 LLM 说完成、或到达步数上限。

def run_agent(llm, registry, task, max_steps=15):
    messages = [{'role': 'user', 'content': task}]      # 对话历史
    for step in range(max_steps):
        action = llm.step(messages, registry.schemas())  # 问 LLM（真 Claude 或 Mock）
        if action['type'] == 'final':                    # LLM 给最终答复 → 结束
            return {'done': True, 'steps': step, 'answer': action['text']}
        # 否则 action 是一次工具调用
        name, args, tid = action['name'], action['args'], action.get('id')
        result = registry.call(name, args)               # 分发执行（已捕获异常）
        # 回填：记录 LLM 的工具请求 + 工具结果（贴合 Anthropic tool_use/tool_result 格式）
        messages.append({'role': 'assistant', 'content': [
            {'type': 'tool_use', 'id': tid, 'name': name, 'input': args}]})
        messages.append({'role': 'user', 'content': [
            {'type': 'tool_result', 'tool_use_id': tid, 'content': str(result)}]})
    return {'done': False, 'steps': max_steps, 'answer': '(到达步数上限)'}

注意消息回填的格式刻意贴合 Anthropic Messages API：LLM 的工具请求记为一个含 tool_use 块的 assistant 消息，工具结果记为一个含 tool_result 块（带 tool_use_id 与对应请求配对）的 user 消息。这样做的好处是：把 MockLLM 换成真实 Claude 时，这个循环几乎不用改——因为它累积的 messages 本就是真实 API 要的格式。这是模块 00「面向接口编程、真假 LLM 无缝切换」纪律的兑现。

直白说

主循环就是 agent 的「工作节奏」：接到任务，反复地「想下一步干什么 → 干（调工具）→ 看结果 → 再想」，直到觉得任务完成。它和人解决问题的过程一模一样，只是把「想」交给了 LLM、把「干」交给了工具。

严谨说

形式上，主循环驱动一个交替的对话：assistant 轮（LLM 思考 + 可能的 tool_use）与 user 轮（tool_result 观察）交替累积。stop_reason 是这台状态机的转移信号——tool_use 则继续、end_turn 则终止。整个循环是模块 00「观察-决策-行动」回路的完整实现，工具注册表是其「行动空间」，messages 历史是其「状态」。这就是一个 agent 的全部——没有更多魔法。

主循环里 max_steps 同样是不能省的安全阀（同模块 04 的步数上限）：LLM 可能陷入反复调工具却不收敛的状态，硬上限保证它最终会停。另外，长循环会让 messages 越积越长、逼近上下文窗口——生产 agent 要做历史压缩（总结早期步骤）、工具输出截断（模块 02 已做）、prompt caching（缓存不变的系统提示与工具定义）来对抗。本课玩具规模不必，但你要知道这些是真实 agent 绕不开的工程。

4系统提示：行为纪律

系统提示：给 agent 定下行为纪律

光有工具和循环还不够——agent 还需要知道该怎么用这些工具、遵守什么纪律。这由系统提示（system prompt）交代：它放在对话最前，为整个会话设定 agent 的角色与规则。一个编码 agent 的系统提示通常包含：

  • 角色：「你是一个编码助手，任务是修复代码库里的 bug，让测试通过。」
  • 工作流纪律：「先用搜索/读文件理解代码，再用精确编辑修改，改完务必跑测试验证。」——把模块 01–04 的最佳实践写成规矩。
  • 安全/正确性红线：「只修复实现，绝不通过修改测试来让它通过」（防 reward hacking，模块 04 强调过）、「不执行危险命令」。
  • 工具用法提示：「编辑用的旧字符串必须在文件中唯一」「一次只改一处、改完即验」等——降低 LLM 用错工具的概率。

系统提示的本质，是把你（工程师）关于「一个好的编码 agent 该怎么行事」的领域知识与纪律，用自然语言注入给 LLM。它和工具的 description 一脉相承——都是写给 LLM 的提示词，引导它把强大的能力用在对的地方、用对的方式。一个写得好的系统提示能显著提升 agent 的成功率与安全性；写得差（含糊、自相矛盾、漏掉关键纪律）则让 agent 行为飘忽、甚至危险。

SYSTEM_PROMPT = """你是一个编码 agent，任务是修复给定代码库里的 bug，让测试通过。
工作流：
1. 先用 code_search / read_file 理解相关代码，再动手改。
2. 用 edit_file 做精确修改（old 字符串须在文件中唯一）。
3. 每次修改后用 run_tests 跑测试验证。
纪律：
- 只修复【实现代码】，绝不通过修改测试用例来让测试通过。
- 测试全部通过后，简要说明你做了什么改动，然后结束。
"""

系统提示是 agent 的「岗前培训手册」：同样的工具、同样的模型，一份好手册能让 agent 像资深工程师那样先理解再动手、改完必验、守住底线；一份差手册则让它横冲直撞。尤其那条「不准改测试来通过」——它是把人类的诚信标准注入 agent 的关键一句，少了它，agent 可能学会「作弊式通过」这种危险捷径。提示词工程不是玄学，而是把工程纪律显式地讲给模型听。

5端到端：真的修好一个 bug

端到端：让 agent 真的修好一个 bug

把注册表、主循环、系统提示拼起来，agent 就能端到端解决任务了。走一遍完整流程（这正是 notebook 里 MockLLM 真跑的过程）——任务是「test_calc 失败了，修复它」：

  1. 感知：agent 调 run_tests → 看到红、test_add 失败；调 read_file('calc.py') → 看到 return a - b；
  2. 决策：LLM 判断 bug 在减号，应改为加号；
  3. 行动：调 edit_file('calc.py', 'return a - b', 'return a + b') → 唯一匹配，改成功；
  4. 验证：再调 run_tests → 绿、test_add passed；
  5. 收尾：LLM 给最终答复「已修复 add 的符号错误，测试通过」→ 循环结束。

这一连串里，每个工具调用都在玩具仓库里真实执行：真的跑 pytest、真的读文件、真的改文件、真的再跑 pytest 看它由红变绿。唯一被「固定」的是 LLM 每一步的决策（由 MockLLM 按合理脚本给出）。所以当 notebook 打印「✅ agent 修复成功，测试通过」，那是整个 agent 系统真的把 bug 修好了，不是演戏。这就是模块 00 立下的「MockLLM 端到端、真实但隔离」纪律的最终兑现。

退一步看这个 agent 的全貌：它把模块 01–04 的所有积累收束成了一个连贯的系统——搜索（眼）帮它定位、文件工具（手）帮它读改、shell（脚）帮它验证、循环（小脑）让它迭代、注册表+主循环把这一切串成自主行为、系统提示给它行为准则。这不到两百行的代码，就是一个麻雀虽小、五脏俱全的编码 agent。理解了它，你就理解了 Claude Code 这类产品的骨架——剩下的差别是规模与打磨，不是本质。

现实参照：这个 perceive→decide→act→observe 的端到端流程，正是 SWE-agent 轨迹里 agent 解一道真实 GitHub issue 的过程；Claude Code 修 bug 时也跑同样的循环。把本模块的 agent 理解透，你就掌握了把零件组装成自主 agent 的完整方法。清单见 references.md。

6SWE-bench 式评测

SWE-bench 式评测：补丁让测试通过 = 成功

造出 agent 后，怎么客观地评判它行不行？编码任务有一个得天独厚的优势——成功是可自动判定的：agent 生成的补丁，要么让测试通过，要么没有。这就是 SWE-bench 评测的核心思想。

SWE-bench 的构造很巧妙：从真实 GitHub 仓库取一批「issue + 修复该 issue 的 PR」，把仓库回退到 PR 之前的状态（带着 bug），让 agent 读 issue、生成补丁；然后用那个 PR 自带的测试来判定——补丁让这些测试通过了，就算解决。关键在于：评测靠的是测试是否通过（客观、自动），而非把 agent 的补丁与人类的「标准补丁」逐字比对（那样会冤枉掉「写法不同但同样正确」的解）。

评测概念含义本课玩具版的对应
SWE-bench真实 issue + PR 测试判定的基准玩具仓库 + 它的测试
resolved / 解决补丁让相关测试全部通过run_tests 返回绿
pass@k允许尝试 k 次，有一次过即算解决agent 一次 rollout 是否修绿
PASS_TO_PASS本应一直通过的测试（防回归）修复后跑全套、原有用例仍绿
FAIL_TO_PASSissue 对应、原本失败应被修绿的测试目标失败用例由红转绿

把这套思想搬到我们的玩具 agent，评测就极简而严格：给 agent 一个带 bug、测试为红的仓库，让它跑一轮；结束后跑一次测试——绿则 resolved=True，红则失败。更严谨些，还可检查它没有篡改测试文件（防作弊）、并跑全套测试（防它修好目标却弄坏别的，即 PASS_TO_PASS 回归）。一个客观、不可被轻易操纵的成功判据，是评测 agent（乃至训练 agent）的基石。

评测最大的陷阱是奖励信号被污染。如果 agent 能看到判定用的测试、又被允许改它，它可能「修改测试让自己通过」——评测显示成功，实则作弊（reward hacking，模块 04 讲过）。SWE-bench 的防范是用 agent 改完后才施加的、它没见过的测试来判定。本课玩具版至少要做到：评测时校验测试文件未被改动。评测的可信度，等于成功判据不可被操纵的程度——这是 agent 评测科学的核心命题。

7接上真实 Claude（Messages API）

接上真实 Claude：Messages API 与 tool use

最后一步，把 MockLLM 换成真实 Claude。由于我们全程面向接口编程，这一步只需实现一个同接口的 <code>ClaudeLLM.step()</code>——它内部调 Anthropic Messages API、按 tool_use/tool_result 协议工作，主循环与注册表一个字都不用改。

真实适配的要点：① 把注册表的 schema 清单传给 tools= 参数；② 调 client.messages.create(model='claude-sonnet-4-6', system=SYSTEM_PROMPT, tools=..., messages=...)；③ 看返回的 stop_reason——是 tool_use 就从 content 里取出工具调用（名字、入参、id）返回给主循环执行；是 end_turn 就把文本作为最终答复返回。前面主循环回填的 messages 格式本就贴合它，于是无缝衔接。

class ClaudeLLM:
    def __init__(self, client, model='claude-sonnet-4-6', system=''):
        self.client = client; self.model = model; self.system = system
    def step(self, messages, tool_schemas):
        resp = self.client.messages.create(
            model=self.model, max_tokens=2048, system=self.system,
            tools=tool_schemas, messages=messages)
        if resp.stop_reason == 'tool_use':
            for block in resp.content:
                if block.type == 'tool_use':
                    return {'type': 'tool', 'name': block.name,
                            'args': block.input, 'id': block.id}
        text = ''.join(b.text for b in resp.content if b.type == 'text')
        return {'type': 'final', 'text': text}

def get_llm(mock_script=None, model='claude-sonnet-4-6', system=''):
    '''有 key+包 → 真 Claude；否则 → MockLLM。同一 step() 接口。'''
    if os.environ.get('ANTHROPIC_API_KEY'):
        try:
            import anthropic
            return ClaudeLLM(anthropic.Anthropic(), model=model, system=system)
        except ImportError:
            pass
    return MockLLM(mock_script)            # 无 key 回退：教学/测试默认走这里

这就是本课无 key 回退契约的最终形态：get_llm() 检测环境，有 key 且装了 anthropic 就给真 Claude，否则给 MockLLM——两者暴露同一个 step(messages, tool_schemas) 接口，所以你的整个 agent（注册表、主循环、系统提示、评测）既能在无 key 的课堂上用 MockLLM 端到端跑通，又能在有 key 时一行不改地切到真实 Claude 去解真实仓库。这正是「面向接口而非实现」的威力——它让本课的玩具 agent 与真实 agent 之间，只隔着一个工厂函数的选择。

真实适配的权威依据：Anthropic《Tool use (function calling) with Claude》（tools 定义、tool_use/tool_result 往返、stop_reason 驱动循环）与《Messages API》文档。本节代码即按这两份文档写的骨架；接上真实 key 后，它就是一个能跑的真实编码 agent。清单见 references.md。

8研究前沿与开放问题

研究前沿与开放问题

  • 规划与子任务分解：玩具 agent 是「反应式」的（看一步走一步）。真实复杂任务需要 agent 先规划（拆成子任务、排顺序、必要时回溯）。如何让 agent 在反应与规划间取得平衡、何时该停下来重新规划，是 agentic 系统的核心前沿。
  • 多 agent 协作：把一个大任务分给多个专门化 agent（一个读代码、一个写补丁、一个审查），或用一个 agent 调度其他 agent。协作的通信协议、责任划分、避免内耗，是活跃方向。
  • 长程任务与记忆：跨越很多步、超出上下文窗口的任务，需要 agent 有外部记忆（笔记、检索）、会总结压缩历史。如何让 agent 在长任务里不「失忆」、不偏离目标，仍是开放难题。
  • 可靠性、安全与对齐：能自主改代码、跑命令的 agent 一旦出错或被诱导，破坏力很大。权限最小化、人在回路、prompt injection 防御、不可操纵的评测——把 agent 做得既强大又可信，是贯穿能力与对齐的终极课题。

必读：Anthropic《Building effective agents》（agent 设计哲学：用最小脚手架、何时该用 agent）、SWE-agent（ACI 与完整 agent 架构）、SWE-bench（客观评测）、Anthropic《Tool use》/《Messages API》（真实对接）、ReAct（推理-行动范式）。这些合起来就是把本课玩具 agent 推向真实世界的完整地图。清单见 references.md。
