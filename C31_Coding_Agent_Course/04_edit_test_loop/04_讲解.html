1Edit-Test-Fix：agent 的小脑

前三个模块给了 agent 手（文件）、脚（shell）、眼（搜索）——但它们都是单次、被动的工具：你叫它读，它读一次；你叫它改，它改一处。真正让一堆工具活起来、变成一个能自主解决问题的 agent 的，是把它们组织成一个会自我纠错的循环。这就是本模块的主角——Edit-Test-Fix 循环，agent 的小脑。

人类工程师修 bug 从不指望一次写对：改一处 → 跑测试 → 看哪挂了 → 再改 → 再跑，直到绿。这个快速迭代、用反馈逼近正确的循环，是软件工程的本能。编码 agent 的强大，恰恰来自把这个循环自动化：让 LLM 来做「改」与「看」，让程序来做「跑测试」与「判断收没收敛」，两者咬合成一个能转起来的轮子。有了它，agent 不再是「赌一次写对」，而是「迭代到对」——这是质的飞跃。

把循环拆开，有四个关键环节，本模块逐一攻克：跑测试（用模块 02 的 shell 跑 pytest，拿到结果）、解析失败（从 pytest 那一大坨文本输出里，抽出「哪些用例失败、失败在哪个文件哪一行、什么错」的结构化信号）、定位与修复（把失败信号喂给 LLM，让它决定改哪、怎么改）、收敛判定与防死循环（什么时候算成功停下、什么时候该认输别空转）。其中解析失败是技术核心——它把「人看的报告」翻译成「机器能决策的信号」。

一句话抓住本模块：agent 不靠一次写对，靠快速迭代逼近对。Edit-Test-Fix 循环 = 改→测→解析失败→定位→再改，直到测试绿或到步数上限。把 pytest 的文本输出解析成结构化失败信号，是让这个循环转起来的技术核心。改与验合起来，才有了「自我纠错」。

2循环骨架：改→测→修

循环的骨架：改 → 测 → 修，直到绿

先看整个循环长什么样。它本质上是一个带退出条件的迭代：每一轮，agent 改一次代码、跑一次测试；测试绿了就成功退出，没绿就把失败信息喂给 LLM 让它再改；改了若干轮还不绿，就到达步数上限、认输退出。

┌──────────────────────────────────────────┐ 任务 ───▶ │ 跑测试 (pytest) │ │ │ │ │ 全绿? ──是──▶ ✅ 成功，退出 │ │ │否 │ │ ▼ │ │ 解析失败 (哪些用例/哪个文件:行/什么错) │ │ │ │ │ ▼ │ │ 喂给 LLM → 它决定改哪、怎么改 → 应用编辑 │ │ │ │ │ 到步数上限? ──是──▶ ❌ 放弃，报告 │ └─────┴────否────────────────────────────────┘ └──────── 回到「跑测试」
def edit_test_fix(llm, work, max_iters=5):
    for i in range(max_iters):
        passed, output = run_tests(work)          # 模块 02 的 shell 跑 pytest
        if passed:
            return {'success': True, 'iters': i}    # 收敛：测试全绿
        failures = parse_pytest(output)            # 解析失败信号（本模块核心）
        action = llm.fix(failures, work)           # LLM 据失败决定怎么改
        apply_edit(work, action)                   # 用模块 01 的 edit 应用
    return {'success': False, 'iters': max_iters}   # 到上限仍未绿，放弃

直白说

这个循环就是把「工程师修 bug 的工作日常」写成了代码：跑测试看红绿、红了就看报错、改一改、再跑。区别只是把「看报错决定怎么改」交给了 LLM、把「跑测试和判断红绿」交给了程序。两者配合，agent 就能像人一样迭代调试。

严谨说

形式上，这是一个在「代码状态空间」里的反馈控制循环：测试结果是误差信号，LLM 的编辑是控制动作，目标是把误差（失败用例数）驱到零。它和模块 00 的 agent 主循环同构，只是专门化了——动作限定为编辑、观察限定为测试结果、终止条件是测试通过。这种「有客观、可自动判定的反馈信号」的结构，正是编码任务特别适合 agent 的根本原因。

注意循环里两个非 LLM的环节——run_tests 和 parse_pytest——是确定性的纯程序逻辑，也是本模块要你亲手写的重点。LLM 负责的 llm.fix 在教学里由 MockLLM 扮演（按脚本给出正确的编辑），于是整个循环能在临时仓库里真跑 pytest、真改文件、看着测试由红变绿——固定 LLM 决策，专注验证循环与解析逻辑是否正确。这正是模块 00 立下的纪律。

3解析 pytest：文本→结构化信号

解析 pytest 输出：从文本到结构化信号

循环的技术核心，是把 pytest 吐出的人看的文本翻译成机器能决策的信号。pytest 失败时的输出大致长这样：

$ pytest -q
F.                                              [100%]
=================== FAILURES ===================
_________________ test_add ____________________
    def test_add():
>       assert add(2, 3) == 5
E       assert 1 == 5
E        +  where 1 = add(2, 3)
calc.py:2: AssertionError
=========== short test summary info ===========
FAILED test_calc.py::test_add - assert 1 == 5
1 failed, 1 passed in 0.03s

agent 要从这坨文本里抽出三样最有用的东西：① 总览（1 failed, 1 passed——还剩几个挂的，用来判断收敛与进展）；② 失败用例列表（FAILED test_calc.py::test_add - ...——哪些用例红了、各自报什么错）；③ 失败位置（calc.py:2: AssertionError——出错在哪个文件哪一行，这是定位修复的关键）。pytest 贴心地提供了 short test summary info 段（每个失败一行 FAILED ...），用正则抓它最省事；位置则从 traceback 里形如 文件:行号: 的行抓。

import re
def parse_pytest(output):
    # 总览：'1 failed, 2 passed'
    m = re.search(r'(\d+) failed', output)
    n_failed = int(m.group(1)) if m else 0
    # 失败用例：summary 段的 'FAILED <nodeid> - <msg>'
    failed = re.findall(r'^FAILED (\S+)(?:\s+-\s+(.*))?$', output, re.M)
    # 失败位置：traceback 里的 'path:line: ErrorType'
    locs = re.findall(r'^(\S+\.py):(\d+): (\w+)', output, re.M)
    return {'n_failed': n_failed,
            'failed_tests': [{'nodeid': t, 'message': msg} for t, msg in failed],
            'locations': [{'file': f, 'line': int(ln), 'error': e} for f, ln, e in locs]}

直白说

解析就像把一份啰嗦的故障报告，提炼成一张「问题清单」：几个问题没解决、分别是什么、各在哪。工程师扫一眼报告就能抓住这些，但 agent 需要你用正则把它们明确地抽出来，它才能据此行动。

严谨说

形式上，这是把半结构化文本解析成结构化记录。pytest 的输出有稳定的格式约定（summary 行、traceback 的 file:line: 格式），使正则解析可行。但要清醒：解析是脆弱的——pytest 版本、插件、配置都可能改变输出格式。健壮做法是优先解析最稳定的部分（summary 段、返回码），并对解析失败有兜底（至少能从返回码知道「失败了」）。生产里也有用 pytest 的机器可读输出（如 JSON report 插件）来彻底绕开文本解析的。

为什么解析质量如此关键？因为它决定了 LLM下一步能看到什么。给它一个精确的「calc.py:2 处 AssertionError，期望 5 得到 1」，它几乎能直接定位修复；给它原始的 200 行 traceback，它要自己大海捞针、还可能被无关栈帧带偏。好的解析 = 把信号从噪音里拎出来，直接递到 LLM 手上——这又回到了贯穿全课的 ACI 原则：工具的输出是为 LLM 设计的。

4失败定位：下一步改哪

失败定位：下一步该改哪

解析出失败信号后，下一个问题是定位：在所有可能的改动里，最该改哪个文件、哪一行？这是循环里「承上启下」的一步——承接解析的输出，启动 LLM 的修复。定位做得准，LLM 一改就中；定位偏了，LLM 在错误的地方打转，循环空转却不收敛。

最直接的定位信号，就是 traceback 里的失败位置——calc.py:2: AssertionError 直接告诉你「第 2 行的断言挂了」。但要注意一个常见陷阱：traceback 里最后一个 file:line 往往是断言所在的测试文件（test_calc.py），而真正要改的是被测代码（calc.py）。所以定位时要懂得区分：测试文件里的位置是「症状」（断言在哪失败），被测源码里的位置才常是「病灶」（逻辑哪里错）。一个聪明的定位会优先指向非测试的源文件。

定位信号来自可靠性用途
traceback 的 file:linepytest 输出高（直接给坐标）首选：直接定位出错行
失败用例名 test_xxxsummary 段高知道哪个功能坏了，反查它测的代码
断言信息 expected/gottraceback中理解错在哪（逻辑/边界/类型）
改动与失败的时间相关性循环历史中刚改完就挂 → 很可能是这次改坏的
代码搜索（模块 03）符号/调用关系中失败用例调了哪些函数 → 候选病灶

把这些信号综合起来喂给 LLM，效果最好：「test_add 失败，断言 add(2,3)==5 实得 1，traceback 指向 calc.py:2」——这样一段浓缩的、多信号交叉印证的描述，远胜于甩给 LLM 一坨原始输出。这一步本质是在做信息的浓缩与聚焦：从「全部输出」收敛到「最可能的病灶 + 足够的诊断」，让 LLM 的注意力落在对的地方。

定位的精髓是区分症状与病灶。测试失败（症状）总是显现在 assert 那一行（测试文件里），但根因（病灶）往往在被测的实现代码里。一个只会盯着症状改的 agent，可能去改测试让它「通过」（这是作弊、是危险的反模式！）；一个懂得追溯病灶的 agent，会去改真正错误的实现。让 agent 改源码、而非改测试来「通过」，是 edit-test-fix 循环必须守住的底线——这一点在模块 05 的 agent 提示词里会再强调。

5收敛判定与防死循环

收敛判定与防死循环

循环必须知道两件事：什么时候成功（收敛，停下庆祝），什么时候失败（认输，别再空转）。前者简单：测试全绿——返回码为 0、或解析出的 n_failed == 0。后者才是难点，因为 agent 可能永远改不对，你不能让它无限循环下去。

最基本的防护是步数上限（iteration budget）：循环最多跑 N 轮，到了还没绿就放弃并如实报告「未能在 N 步内修复」。这是必备的安全阀——没有它，一个改不动的 bug 会让 agent 无限烧钱、无限耗时。N 怎么选是权衡：太小则放弃太早（本来再两轮就能修好）、太大则在死路上耗太久，实践中常取个位数到一二十，并可按任务难度调。

更精细的防护是检测振荡（oscillation）与无进展。两种典型病态：① agent 在两个错误状态间来回打转（改 A 坏 B、改 B 又坏 A，反复横跳）；② 每轮改动后失败数毫无减少（改了等于没改，甚至越改越多）。检测前者可记录每轮的「代码状态指纹」（如文件内容哈希），发现重复就判定陷入循环、提前终止；检测后者可追踪 n_failed 的变化趋势，若连续若干轮不下降就叫停。

def edit_test_fix(llm, work, max_iters=8):
    seen_states = set()                            # 状态指纹，检测振荡
    last_failed = None
    stagnant = 0
    for i in range(max_iters):
        passed, output = run_tests(work)
        if passed:
            return {'success': True, 'iters': i, 'reason': '测试全绿'}
        info = parse_pytest(output)
        # 无进展检测：失败数连续不降
        if last_failed is not None and info['n_failed'] >= last_failed:
            stagnant += 1
        else:
            stagnant = 0
        if stagnant >= 3:
            return {'success': False, 'iters': i, 'reason': '连续 3 轮无进展，放弃'}
        last_failed = info['n_failed']
        # 振荡检测：代码状态指纹重复
        fingerprint = snapshot(work)
        if fingerprint in seen_states:
            return {'success': False, 'iters': i, 'reason': '检测到状态振荡，放弃'}
        seen_states.add(fingerprint)
        apply_edit(work, llm.fix(info, work))
    return {'success': False, 'iters': max_iters, 'reason': '到达步数上限'}

直白说

这些防护就像给一个埋头修车的人定几条规矩：修了八次还没好就先停下来求助（步数上限）；如果发现自己在反复拆同一个零件又装回去（振荡），说明思路错了、该换法子；如果修了半天故障一点没少（无进展），也该停下重新诊断。盲目硬干只会浪费时间。

严谨说

形式上，这是给一个可能不收敛的迭代过程加终止保证。步数上限给了最坏情况的硬上界；振荡检测利用「状态重复 ⇒ 确定性地陷入循环」来提前止损；无进展检测用「误差不降 ⇒ 当前策略无效」来叫停。三者叠加，把「可能永远跑下去」变成「最多 N 步、且能更早识别死路」。这是任何含迭代的 agent 都必须处理的可靠性问题——能力之外，agent 还得知道何时停。

无防护的 agent 循环是生产事故的常见来源：一个 agent 在改不动的 bug 上无限循环，几小时烧掉巨额 API 费用、占满资源，且毫无产出。步数上限是最低限度的、绝不能省的保护；振荡与无进展检测则让 agent 更早地优雅放弃（并如实报告「我没修好，原因是 X」），而非假装还在努力。一个会说「我搞不定」的 agent，比一个无限空转的 agent 有用得多——诚实的失败是可处理的，无声的空转是灾难。

6跑起来：一个完整修复回合

把循环跑起来：一个完整的修复回合

把跑测试、解析、定位、修复、收敛防护拼起来，就是一个能自主修 bug 的循环。走一遍完整流程（这正是 notebook 里 MockLLM 真跑的过程）：

  1. 第 1 轮：跑 pytest → 红（1 failed）→ 解析出「test_add 失败，calc.py:2 处 add(2,3) 得 1 期望 5」；
  2. 定位：信号指向 calc.py:2 的实现（非测试文件）→ 喂给 LLM；
  3. 修复：LLM 决定把 return a - b 改成 return a + b（用模块 01 的唯一匹配编辑应用）；
  4. 第 2 轮：再跑 pytest → 绿（2 passed）→ 收敛，成功退出，报告「2 轮修复」。

这个循环把前三个模块的工具编排了起来：搜索（眼）帮 LLM 定位、文件工具（手）应用编辑、shell（脚）跑测试拿反馈。可以说，模块 01–03 造的是零件，本模块造的是把零件转起来的引擎。引擎一转，agent 就从「一组孤立的能力」变成了「一个能自主迭代解决问题的系统」。这是从工具到 agent 的关键一跃。

还要强调循环里那条人/程序与 LLM 的分工线：确定性的、可验证的部分（跑测试、解析、收敛判定、防死循环）由你写的程序掌控；开放的、需要理解与创造的部分（看懂错误、想出怎么改）交给 LLM。这种分工不是偶然——它把系统的可靠性（程序保证循环不失控、测试客观判定）与 LLM 的灵活性（应对千变万化的 bug）各自发挥到位。理解这条线划在哪，你就理解了 agent 工程的精髓：哪些事该信确定性代码，哪些事该信模型。

现实参照：这正是 SWE-bench 上 agent 解题的核心循环——生成补丁、跑测试、据结果迭代。SWE-agent 的轨迹里能清楚看到这种 edit-test-fix 节奏。Claude Code、aider 修 bug 时也都在跑这个循环。把本模块理解透，你就理解了编码 agent「自我纠错」的引擎。清单见 references.md。

7测试质量与回归（reward hacking）

超越单个循环：测试本身的质量与回归

循环的奖励信号是「测试通过」，但这带来一个深刻的问题：测试本身可信吗？如果测试覆盖不全，agent 可能写出「通过了测试、却没真正修好（甚至引入新 bug）」的补丁——测试是绿的，问题还在。这是以测试为奖励的根本局限：你只能验证测试覆盖到的行为。EvalPlus 等研究正是指出「测试覆盖不足会高估正确性」。

一个直接的工程纪律是：修完要跑整个测试集，而非只跑目标用例。因为一个修复可能引入回归（regression）——修好了 A、却弄坏了原本正常的 B。只跑「刚才失败的那个用例」会漏掉这种连带破坏；跑全套才能确认「修好了目标，且没碰坏别的」。这也是为什么 SWE-bench 的判定要跑该 issue 相关的一整组测试（含本应一直通过的 PASS_TO_PASS 用例），确保补丁不引入回归。

更进一步，成熟的 agent 会把循环的反馈源扩展到测试之外：跑 linter（抓风格/低级错误）、类型检查（mypy，抓类型不匹配）、甚至让 agent自己补测试来提高覆盖。每多一种客观、可自动判定的反馈信号，循环就多一只「眼睛」，agent 的改动就多一层保障。本课聚焦最干净的信号（pytest 通过），但你要知道：循环的反馈质量，上限就是 agent 修复质量的上限。喂给循环的信号越全面、越可信，agent 修得越靠谱。

一个必须警惕的反模式：agent 为了让测试变绿，去改测试（放宽断言、删掉失败用例）而非改实现。这在技术上「通过」了，实质是作弊、是危险的。防范靠几道闸：提示词明令「只改实现、不改测试来通过」、把测试文件设为只读、或评测时用 agent看不到的隐藏测试（SWE-bench 正是如此——agent 改完后用它没见过的测试判定）。奖励信号一旦能被 agent 操纵，就失去了意义——这是 agent 评测与训练里 reward hacking 的一个具体而重要的实例。

8研究前沿与开放问题

研究前沿与开放问题

  • 超越「测试通过」的奖励：测试覆盖不全时，如何更可信地判定「真的修好了」？结合静态分析、形式化验证、LLM 评审、隐藏测试，是让奖励信号更难被操纵、更贴近真实正确性的方向。
  • 更聪明的失败定位：当 traceback 不直接指向病灶（如错误在数据流上游、或异步/并发 bug）时，如何定位？把 spectrum-based fault localization、delta debugging、调用图分析接进 agent，是前沿。
  • 循环的样本效率与规划：怎么让 agent 用更少轮数收敛？先规划（理解 bug 全貌再动手）vs 贪心迭代（改了再看）的取舍、何时该退一步重新审视，是 agent「调试智慧」的活跃研究。
  • reward hacking 与对齐：agent 改测试作弊、或找到测试的漏洞「蒙混过关」，是 reward hacking 的具体形态。如何设计不可被操纵的反馈、如何检测作弊，连接到更广的 AI 对齐问题。
