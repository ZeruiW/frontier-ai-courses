1这门课讲什么

欢迎来到 构建编码 Agent（你的 Claude Code）。这门课只追求一件事：让你从「会用 Claude Code」变成「会造一个」。

绝大多数人和编码 agent 的关系，止于在编辑器里按下「让 AI 改这个 bug」然后等结果。这门课要把那个黑盒打开：当你给 agent 一句「测试 test_add 挂了，修一下」，它内部到底怎么找到对的文件、怎么决定改哪一行、怎么验证自己真的修好了？答案出人意料地朴素——一个编码 agent，本质上就是一个 LLM、一组工具、和一个把它们串起来的循环。没有魔法。

把这句话拆开，就是本课的全部内容：LLM 负责思考（它本身我们不造，按需接 Claude 或用 MockLLM 替身）；工具 是 agent 伸向真实世界的手脚眼睛——读写文件、跑 shell、搜代码、跑测试，这些我们从零用纯标准库写；循环 把两者缝合：把任务和工具清单发给 LLM，LLM 要么直接回答、要么说「帮我调用某工具」，我们执行后把结果回填，再问 LLM，如此往复，直到任务完成。这个循环就是 agent 的心脏，模块 05 你会亲手把它写出来。

学完你应当能回答这类问题（也是 agent / 应用工程岗的高频面试题）：编码 agent 的主循环长什么样？为什么现代 agent 用「唯一字符串替换」而不是行号来编辑代码？给 agent 跑 shell 必须防哪几件事？怎么把 pytest 的报错变成 agent 下一步的依据？SWE-bench 是怎么客观判定一个 agent 修对了没？——并且能用纯标准库把这些工具和那个循环从零写出来、在临时仓库里真的把 bug 修绿。

一句方法论上的话先说在前面：本课的价值不在「我们没接真实大模型也能学」这个妥协，而在它逼你只关注真正难的部分——工具的接口设计与那个循环的控制流。提示词的微调、模型的选择，这些重要但易变、且高度依赖具体模型；而「一个工具该怎么把结果讲给 LLM 听」「循环何时该停、出错怎么办、怎么防死循环」这些结构性问题，才是把一个能跑的 agent 和一个一碰就崩的 demo 区分开的东西，且不随模型换代而过时。把它练扎实，换任何模型、任何框架都立刻能上手。

2agent = LLM + 工具 + 循环

一个编码 agent 是什么：LLM + 工具 + 循环

先看最小的骨架。一个聊天机器人是「输入→LLM→输出」，一来一回就结束。一个 agent 多了一个回路：LLM 的输出可以是「我要调用工具 X」，程序执行 X、把结果接回去，让 LLM 基于新观察继续。正是这个回路让它能改变世界并根据反馈自我纠正。

┌─────────────────────────────────────────────┐ │ │ 任务 ──▶ │ 对话历史 ──▶ LLM ──▶ 它想干什么？ │ │ ▲ │ │ │ │ ┌─────┴─────┐ │ 把结果 │ │ 最终答复 调用工具 │ 回填 ────┘ │ │ │ │ │ └───────────┘ 执行工具(读/写/shell/测试) │ (循环继续) 在真实工作区里跑 │ └─────────────────────────────────────────────┘ ▲ 到达最终答复 / 步数上限 → 退出

用伪代码写出来，整个 agent 短得惊人——这就是模块 05 你要填满的骨架：

messages = [user(task)]                 # 对话历史
for step in range(MAX_STEPS):            # 步数上限：防无限打转
    reply = llm(messages, tools)         # 问 LLM（真 Claude 或 MockLLM）
    if reply.wants_tool:                 # 它要调用工具？
        result = run_tool(reply.tool, reply.args)   # 执行（可能改文件/跑测试）
        messages.append(tool_call(reply))           # 记下它的请求
        messages.append(tool_result(result))        # 回填观察结果
    else:                                # 它给了最终答复
        return reply.text                # 退出循环

直白说

把它想成你带一个聪明但手脚被绑住的实习生：他脑子很好（LLM），但看不见你的代码库、动不了你的文件、跑不了你的测试。你的工作（写工具 + 写循环）就是给他装上手、眼、脚，并定下规矩：先看再改、改完跑测试、出错了再来一轮。

严谨说

形式上：agent 是在一个观察-决策-行动的回路里运行的策略。LLM 是策略函数 π(history)→action；工具是把 action 作用到环境、并返回观察的转移函数；循环驱动这个马尔可夫式的交互直到终止。编码任务的妙处在于它的奖励是客观的——测试通过与否，无需人来打分，这也是它适合 agent、也适合自动评测的根本原因。

本课只造工具和循环这两层，不训练也不实现 LLM 本身——那是另一类课的内容。LLM 在本课里是一个可替换的部件：教学与测试时用确定性的 MockLLM，想看真实效果时换成 Claude（下一节的回退契约）。这种解耦正是工程上的正确姿势：把「会变的、贵的、不确定的」部分（模型）与「你能完全掌控的」部分（脚手架）分开。

3方法论一：MockLLM 端到端跑通

方法论一：用 MockLLM 把循环端到端跑通

造 agent 有个先天的麻烦：它的「大脑」是一个又贵、又慢、又不确定的远程模型。如果每改一行代码都要真调一次 API，开发会慢得无法忍受，测试也无法复现（同样输入，模型每次回答还可能不一样）。所以本课的第一条纪律是：用一个确定性的 MockLLM 替身来驱动整个循环。

MockLLM 不思考，它只是按预设脚本依次返回动作：第 1 步「调用 read_file 看看 bug」、第 2 步「调用 edit 改这一行」、第 3 步「调用 run_tests 验证」、第 4 步「测试绿了，结束」。它把一个真实模型会做出的合理决策序列固定下来，于是——你的工具、你的循环、你的解析逻辑，全都能在无网络、无 API key、零成本、完全可复现的条件下端到端跑通并 assert 验证。

直白说

MockLLM 就像拍电影时的替身演员：危险又昂贵的镜头（真实模型）先用替身把走位、灯光、机位（你的工具和循环）全部调试好，确认整套流程跑得通，最后才让主角（真 Claude）上场。替身让你能反复重拍而不烧钱。

严谨说

严格地说，MockLLM 把 agent 系统里唯一的非确定性来源（模型采样）替换成了一个确定性的桩，从而让 agent 的其余部分变成一个可单元测试的纯函数式管道。这正是测试一切含外部依赖系统的标准手法（dependency injection + mock）。它验证的不是「模型聪不聪明」，而是「假如模型做出了正确决策，我的脚手架能不能正确地执行出结果」——而后者恰恰是本课要教的。

关键认知：MockLLM 跑通 ≠ 假装跑通。循环、工具、文件改动、pytest 真的在临时目录里跑、测试真的由红变绿——这一切都是真实发生的，只有「该调用哪个工具」这个决策是预设的。所以当你的 notebook 打印「✅ 测试通过」，那是工具链真的把玩具仓库的 bug 修好了，不是台词。把模型决策固定下来，恰恰让你能确信脚手架本身是对的。

4方法论二：临时目录里真跑

方法论二：在临时目录里真跑文件、shell、pytest

第二条纪律关乎安全与真实的平衡。本课的 agent 要读写文件、跑 shell、跑测试——这些都是有副作用、甚至危险的操作。我们既想让它真的执行（这样才学得到东西、assert 才有意义），又不能让它碰你机器上的真实文件。解法是：把所有操作关进一个临时目录沙箱。

Python 标准库的 tempfile.mkdtemp() 给我们一个全新的、隔离的目录；我们在里面真的用 open() 写文件、用 subprocess.run() 跑命令、用 pytest 跑测试。工作区里的一切都是真的，但它与系统隔离、用完即可 shutil.rmtree() 删除，不留痕迹。这给了我们两全：操作是真实的（不是模拟的），风险是隔离的（不会误伤）。

import tempfile, shutil, os, subprocess

work = tempfile.mkdtemp(prefix='agent_ws_')   # 全新隔离工作区
try:
    # 在 work 里【真的】建一个玩具仓库
    open(os.path.join(work, 'calc.py'), 'w').write('def add(a,b):\n    return a - b\n')  # 故意的 bug
    open(os.path.join(work, 'test_calc.py'), 'w').write('from calc import add\n'
                                                        'def test_add():\n    assert add(2,3)==5\n')
    # 在 work 里【真的】跑 pytest
    r = subprocess.run(['python','-m','pytest','-q'], cwd=work,
                       capture_output=True, text=True, timeout=60)
    print(r.returncode, '→ 非 0：bug 让测试失败了')   # agent 接下来要修它
finally:
    shutil.rmtree(work)                       # 用完即焚，不留痕迹

这段代码是全课的物理基础：模块 01 在这样的工作区里读写和编辑文件，模块 02 在里面跑 shell，模块 03 在里面搜代码，模块 04 在里面跑 pytest 并解析结果，模块 05 让完整 agent 在里面端到端修 bug。每个 notebook 都会建一个这样的工作区、做完真实操作、assert 验证、再清理。真实但隔离，是本课所有「能跑」承诺的来源。

安全永远是 agent 工程的一等公民。一个能跑 shell、能写文件的 agent，如果不加约束，理论上能 rm -rf /、能读走你的密钥、能写坏系统文件。本课从第一个工具起就把安全做进去：文件工具校验路径不越界（模块 01）、shell 工具设超时 + 截断输出 + 拦截危险命令（模块 02）、一切都在临时目录沙箱里（全课）。把这些当成工具的一部分，而不是事后补丁。

5方法论三：无 key 回退真实 Claude

方法论三：无 key 自动回退真实 Claude

MockLLM 保证你能学、能测；但你一定也想看看接上真实模型是什么样。本课的第三条纪律是：每个 notebook 都附一段对接真实 Claude 的适配代码，但没有 API key 时自动回退到 MockLLM，绝不阻断。

做法很简单：写一个统一的 get_llm() 工厂，它检测环境里有没有 ANTHROPIC_API_KEY、装没装 anthropic 包——两者都有就返回一个调用 Anthropic Messages API 的真实客户端（用 client.messages.create(model=..., tools=...)，按 tool_use / tool_result 协议多轮往返）；否则就返回 MockLLM。关键是两者暴露同一个接口，于是你的 agent 主循环一个字都不用改，就能在「真 Claude」与「替身」之间无缝切换。

def get_llm(script=None, model='claude-sonnet-4-6'):
    """有 key+包 → 真 Claude；否则 → MockLLM。两者同一接口。"""
    import os
    if os.environ.get('ANTHROPIC_API_KEY'):
        try:
            import anthropic                      # 真实路径
            return ClaudeLLM(anthropic.Anthropic(), model)
        except ImportError:
            pass
    return MockLLM(script)                        # 回退：教学/测试默认走这里

直白说

这就像给软件留一个「离线模式」：联网时用云端的强大功能，断网时用本地的够用功能，用户体验不中断。本课的「离线模式」就是 MockLLM——它让课程在任何机器上、不花一分钱、不配任何密钥都能完整跑完。

严谨说

工程上这是对依赖倒置的运用：agent 主循环依赖的是一个抽象的 LLM 接口（给消息和工具、拿回「要调工具」或「最终答复」），而非某个具体厂商的 SDK。真实 Claude 和 MockLLM 都是这个接口的实现。这样写出的 agent 既可测（注入 Mock）、又可换（今天 Claude、明天换别家只改工厂），是面向接口而非面向实现的典范。
