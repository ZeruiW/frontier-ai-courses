1tokenizer 是文本与模型的接口

tokenizer（分词器）是文本与模型之间的接口：模型只认识整数 id，tokenizer 负责把原始字符串切成一串离散 token、再映射成 id。这个看似机械的预处理，其实是一个被严重低估的设计决策——它决定了每段文本占多长的序列、未登录词怎么办、数字和代码怎么表示、不同语言公不公平。选错 tokenizer，等于在每一步训练和推理上都交一笔隐形税。

为什么不直接按字符（或字节）切？因为序列会太长。一篇文章按字符切是几千个 token，模型的注意力是 $O(n^2)$，序列长一倍、算力翻四倍。那为什么不按整词切？因为词表会爆炸（英语就有数十万词，还有无穷的拼写变体、专名、数字），且永远有OOV（未登录词）没法表示。子词分词（subword tokenization）是这两个极端的中点：常见词整体成一个 token、罕见词拆成有意义的子词片段。

直白说

打个比方：tokenizer 是给文本「打包装箱」。箱子太小（按字符）→ 要很多箱子（序列长、运费高）；箱子型号太多（按整词）→ 仓库装不下（词表爆炸）且遇到没见过的东西没箱子装（OOV）。子词分词是一套精心设计的标准箱型：常用东西有专属箱子，罕见东西用通用小箱拼装。

严谨说

形式化：tokenizer 是一个函数 $T: \Sigma^* \to V^*$，把字符串映射到词表 $V$ 上的 token 序列。好的 $T$ 要同时优化几个互相牵制的目标：压缩率（序列尽量短）、覆盖率（不出 OOV）、词表大小（embedding 参数量）、语义合理性（切分对齐语言单位）。这几个目标构成一个权衡空间，没有免费的最优解。

tokenizer 是训练前就冻结、之后几乎改不了的决策——它定下后，所有数据都按它编码、embedding 表按它的词表建，中途换 tokenizer 等于推倒重训。所以它必须一次选对。这也是为什么前沿实验室会在 tokenizer 上反复实验：它是少数「一锤子买卖」的预训练超参之一。

一个常被忽视的事实：tokenizer 的影响会乘进每一步。压缩率差 10%，意味着同样的语料多花 10% 的 token——训练时多 10% 的算力、推理时每次请求多 10% 的延迟与成本、context 窗口少装 10% 的内容。在一个要训几个月、服务几年的模型上，这 10% 的复利是巨大的。所以 tokenizer 不是「预处理小事」，而是贯穿模型整个生命周期的成本系数。

2BPE：反复合并最高频对

BPE：从字符反复合并最高频对

BPE（Byte-Pair Encoding，字节对编码）是 GPT 系列用的分词法，由 Sennrich 2016 引入 NLP（源自 Gage 1994 的压缩算法）。它的训练算法朴素到优美：从字符开始，反复找出语料里出现频率最高的相邻 token 对，把它合并成一个新 token，记录这条合并规则，直到词表达到目标大小。

初始(按字符): l o w </w> l o w e r </w> n e w e s t </w> w i d e s t </w> 语料词频: low×5 lower×2 newest×6 widest×3 统计相邻对频率 -> 最高频是 (e,s)=9 [newest 6 + widest 3] 合并 #1: (e,s)→es ... n e w es t w i d es t 统计 -> 最高频 (es,t)=9 合并 #2: (es,t)→est ... n e w est w i d est 统计 -> 最高频 (l,o)=7 [low 5 + lower 2] 合并 #3: (l,o)→lo ... lo w lo w e r ... 继续到词表大小达标 产出: 有序合并表 [(e,s),(es,t),(l,o),...] ← 编码时按这个顺序贪心合并

注意两个关键点。其一，合并表是有序的：编码新文本时，必须按训练时的合并顺序依次尝试合并，顺序乱了结果就错。其二，BPE 是确定且贪心的——每步只看当前最高频对，不回头优化全局，所以训练飞快（这是它流行的原因之一）。

byte-level BPE：彻底消灭 OOV

现代做法是 byte-level BPE（GPT-2 起）：不在 Unicode 字符上、而在 UTF-8 字节（只有 256 个基元）上做 BPE。好处是任何文本——任何语言、emoji、乱码、二进制——都能无损编码，永远不会出现 unknown token。代价是非 ASCII 文本（如中文，一个字 3 字节）起步时 token 更碎，靠合并再拼回来。

直白说

byte-level 的精神是：退到最底层的通用基元（字节），就再也没有「没见过」的东西。任何文件本质都是字节流，256 个字节值能拼出一切。BPE 再在这之上学出高频组合，把常见模式压短。

严谨说

这也解释了一个常见现象：英文 token 看起来像词或词根（因为 ASCII 字符直接是字节），但中文/日文的 token 常是「字节碎片」拼的——因为模型先看到 3 个 UTF-8 字节，再靠学到的 merge 把它们组合。这正是下一节 fertility 对非英语不公平的根源。

BPE 的贪心不保证最优切分：因为只按频率合并、不考虑语言学边界，会切出一些反直觉的 token（把常见但无意义的字符组合合并）。更糟的是数字：早期 BPE 把 “100” “200” “1000” 各自合成不同 token，模型很难学会算术（它看不到数字的位值结构）。对策是数字按单个数位切（每个 0-9 一个 token），让模型看到 “1”“0”“0” 的结构——LLaMA、GPT-4 等都这么做。这是 tokenizer 设计直接影响下游能力（算术、代码）的典型例子。

3Unigram 与 WordPiece

Unigram 与 WordPiece：另外两条路线

BPE 是「自底向上合并」，但它不是唯一选择。两个重要的对手是 Unigram LM tokenizer（Kudo 2018）和 WordPiece（BERT 用）。理解三者的差异，是 tokenizer 设计的核心知识。

维度BPEWordPieceUnigram LM
方向自底向上：从字符合并自底向上：从字符合并自顶向下：从大词表剪枝
合并/保留准则频率最高的相邻对似然增益最大的对 $\frac{f(xy)}{f(x)f(y)}$剪掉对语料似然损害最小的 token
训练算法贪心计数合并贪心（似然准则）EM 迭代 + 剪枝
分词（编码）按合并表贪心最长前缀匹配最大似然切分（可采样多种）
代表模型GPT 系、LLaMA、RoBERTaBERT、DistilBERTT5、ALBERT、多语模型

Unigram：从大到小的概率剪枝

Unigram 反着来：先建一个过大的候选词表（所有高频子串），给每个 token 一个概率 $p(t)$，假设一句话的概率是其切分中各 token 概率之积（unigram 假设）。用 EM 估计这些概率，然后反复剪掉「删了它对语料总似然损害最小」的一批 token，直到词表降到目标大小。

\[\text{切分 } \mathbf{s}=(t_1,\dots,t_k) \text{ 的概率} = \prod_{i=1}^{k} p(t_i), \quad \text{编码取 } \arg\max_{\mathbf{s}} \prod_i p(t_i)\]

直白说

BPE 像「攒积木」：从最小块开始，把常一起出现的粘成大块。Unigram 像「砍预算」：先列出所有可能的词条，再把性价比最低的一个个砍掉，留下最值钱的一批。

严谨说

Unigram 的两个独特优势：① 编码时它取全局最大似然切分（用 Viterbi），比 BPE 的贪心更可能切出合理边界；② 它能对同一文本采样多种切分（subword regularization），训练时当数据增强，提升鲁棒性。代价是训练比 BPE 慢（要跑 EM）。

WordPiece 介于两者之间：合并方向同 BPE，但准则不是纯频率，而是看合并后能多大提升语料的语言模型似然（近似 $\frac{f(xy)}{f(x)f(y)}$，即这对字符「绑在一起」比「各自独立」更有信息量）。实践中 BPE 与 Unigram 是当前主流，WordPiece 主要存在于 BERT 系。SentencePiece（Kudo & Richardson）这个库把 BPE 与 Unigram 都实现了，且语言无关（把空格也当普通符号 ▁ 处理），是多语模型的事实标准。

Sennrich 2016（BPE 引入 NLP）、Kudo 2018（Unigram + subword regularization）、Kudo & Richardson 2018（SentencePiece）是分词三件套必读；想理解 WordPiece 看 Wu 2016（GNMT）。完整清单见 references.md。

4核心权衡：词表 ↔ 序列长度 ↔ fertility

核心权衡：词表大小 ↔ 序列长度 ↔ fertility

tokenizer 设计的中心问题是选多大的词表。这不是孤立的数字，而是一个三角权衡的支点。先定义两个关键指标：

  • fertility（繁殖率）：平均每个词被切成多少个 token。fertility=1 表示每词一个 token（理想），>1 表示词被切碎。
  • compression ratio（压缩率）：原始字节数 ÷ token 数，即平均每个 token 顶多少字节。越高越好（同样 context 装更多文本）。

词表越大，常见词越能整体成 token → fertility 越低、序列越短、压缩率越高。听起来词表越大越好？不——代价在三处：

词表增大的影响好处 / 坏处说明
fertility ↓ / 压缩率 ↑✅ 好处序列变短，训练/推理的注意力计算省（$O(n^2)$）
embedding 参数量 ↑❌ 坏处embedding + 输出层 $= 2 \times V \times d$，词表 256k 时这部分能占小模型参数的一大块
每个 token 见的次数 ↓❌ 坏处固定语料下词表越大，每个 token 的训练样本越稀疏，罕见 token 学不好
softmax 计算 ↑❌ 坏处输出层在 $V$ 上做 softmax，$V$ 大则每步更贵

直白说

词表大小像「字典厚度」：字典越厚，每个概念越可能有专属词条（表达精炼、句子短）；但字典太厚，很多词条你一辈子用不了几次（学不熟），而且随身带着它（embedding 参数）很重。要的是覆盖常用、又不臃肿的那个厚度。

严谨说

数学上看总成本：序列长度 $\propto 1/\text{压缩率}$（影响算力），embedding 参数 $\propto V$（影响模型大小与稀疏性）。压缩率随 $V$ 增长但边际递减（高频词早被收进去了，再加的都是低频长尾），而 embedding 成本随 $V$ 线性增长。两条曲线一升一降，存在一个甜点区——现代 LLM 多落在 $V \in [32\text{k}, 256\text{k}]$，且近年随模型变大、context 变长而上移（大模型摊得起 embedding，且更看重短序列）。

notebook 会让你在真实英文文本上从零训 BPE，画出压缩率随词表大小的边际递减曲线，并算 fertility——亲眼看到「加词表的收益越来越小」这条决定甜点区的曲线。

5难处理的：数字、代码、多语

难处理的东西：数字、代码、多语

通用 tokenizer 在三类内容上会栽跟头，每一类都直接影响某项下游能力：

数字：位值结构被打碎

如果 “127” 是一个 token、“128” 是另一个完全无关的 token，模型就看不到「它们只差 1」。这让算术、计数变得极难。解法是把数字按单个数位切（“1”“2”“7”），让模型看到位值结构。LLaMA、GPT-4、PaLM 都对数字做特殊处理。这是 tokenizer 设计直接决定模型能不能学会算术的硬例子。

代码：空白与缩进是语义

代码里连续的空格/制表符（缩进）是语法。朴素 tokenizer 把 4 个空格切成 4 个 token，浪费且割裂缩进。代码友好的 tokenizer 会把常见的缩进模式（如 “ ” 四空格、“ ” 八空格）合成单 token。Code Llama、StarCoder 等都优化了对空白与常见代码模式的处理，显著提升代码压缩率与能力。

多语：fertility 的不公平

这是 tokenizer 最严重的公平性问题。一个主要在英文上训的 BPE，对英文 fertility≈1.3，但对中文、阿拉伯文、印地语等可能 fertility 高达 2-4：同样语义的一句话，非英语要花几倍的 token。后果是双重的：① 这些语言的用户付几倍的 token 费、context 装得少（Petrov 2023）；② 训练时这些语言信号更稀疏，学得更差（Rust 2021）。

同一句「我爱机器学习」级别的语义，不同 tokenizer 的 token 数(示意): 英文 tokenizer 处理英文: ████ 4 tokens 英文 tokenizer 处理中文: ██████████████ 14 tokens ← 3-4x fertility 惩罚 多语 tokenizer 处理中文: ██████ 6 tokens ← 专门分配词表后改善 代价: 多语 tokenizer 要更大词表，英文上略有损失(权衡)

tokenizer 的语言不公平是结构性、且会传导到成本与能力的：API 按 token 计费时，小语种用户为同样的内容付几倍钱；context 窗口按 token 算时，小语种能放进的实际内容少几倍；训练时小语种 token 稀疏，能力天然落后。多语模型（BLOOM、mT5）必须在词表里给各语言留足配额，但这又挤占英文、增大词表——这是个没有完美解的权衡（C12 负责任 AI 关切）。

6编码与解码：合并表怎么用

编码与解码：合并表怎么用

训练产出合并表后，编码（encode）新文本的算法是：先把文本拆成最小单元（字节/字符），然后按合并表的顺序反复扫描、把能合并的相邻对合并，直到没有可合并的为止。

# BPE 编码伪代码
def encode(text, merges):        # merges 是有序列表 [(a,b), ...]
    tokens = list(text)          # 起步：拆成字符/字节
    for (a, b) in merges:        # 严格按训练时的合并顺序
        tokens = merge_all_occurrences(tokens, a, b)
    return tokens
# 关键：merges 的顺序 == 训练时学到的顺序，不能乱

一个微妙但重要的点：编码必须按训练合并顺序，因为后面的合并依赖前面的结果（“es” 要先合出来，“est” 才能合）。解码（decode）则简单——token 序列直接拼回字符串（byte-level 的话把字节拼起来再 UTF-8 解码）。好的 tokenizer 应当是无损可逆的：encode 再 decode 要还原原文（包括空格），这正是 SentencePiece 用 ▁ 显式标记空格的原因。

直白说

编码像「按菜谱步骤做菜」：菜谱（合并表）的步骤有先后，跳步或乱序就做坏了。每一步「把这两样合到一起」，严格照训练时学的顺序来。

严谨说

效率上，朴素 encode 对每条 merge 扫一遍文本是 $O(|\text{merges}| \times n)$，慢。真实实现（HuggingFace tokenizers、tiktoken）用优先队列 / 字典树等数据结构把它优化到接近线性，这样推理时分词不成为瓶颈。本课 notebook 实现朴素版（看清逻辑），并验证 encode→decode 可逆。

还有一个决定性细节：BPE 通常先按空格/标点把文本切成「词」（pre-tokenization），再在每个词内部做 BPE，不允许跨词合并。这避免了把 “the cat” 合成一个 token 这种荒唐结果，也让空格的归属明确（GPT 系把前导空格并进词首 token，用 Ġ 标记）。pre-tokenization 的规则（怎么切词、空格怎么算、数字怎么处理）本身就是 tokenizer 设计的一部分，且直接影响数字/代码的表现——这就是为什么「数字按位切」其实是在 pre-tokenization 阶段强制把数字串拆开。

一句话记住编码：先按词切开、每个词拆到最碎，再按学过的顺序一步步粘回去。训练学的是「该粘哪些、按什么顺序粘」；编码就是机械地执行这套粘合规则。理解了这点，BPE 就没有黑魔法了。

7评估一个 tokenizer 的好坏

评估一个 tokenizer 的好坏

怎么判断 tokenizer A 比 B 好？不能只看一个数。一套实用的评估维度：

指标怎么算越好的方向
压缩率 / fertility字节÷token / token÷词压缩率高、fertility 低（在目标语料上）
词表利用率训练后实际用到的 token 占比高（没有大量死 token 浪费 embedding）
跨语言公平各语言 fertility 的方差小（不系统性歧视某语言）
数字/代码处理算术、代码任务的下游表现数字按位切、代码空白合并
无损可逆encode∘decode == 原文必须成立（含空格、特殊字符）
下游 loss/能力用它训小模型测验证 loss最终裁判，但贵

一个反直觉但重要的点：压缩率高不总是好。更激进的合并能压更短，但可能把语义边界压没了（把 “unhappiness” 合成一个 token，模型就看不到 “un-” 的否定结构）。压缩率是代理指标，最终标准永远是下游能力——但下游评估贵，所以实践中先用压缩率/fertility 快速筛选，再用小模型验证候选。

直白说

别只盯着「压得多短」。一个把所有东西都压成一个 token 的极端 tokenizer 压缩率无穷大，但模型啥也学不到。要的是既短、又保留语言结构、又对各语言公平的平衡。

严谨说

这呼应了机器学习里反复出现的教训：代理指标（压缩率）≠ 真实目标（下游能力）。优化代理到极致常会偏离真实目标（Goodhart 定律）。tokenizer 评估的正确姿势是多指标 + 最终下游验证，而非单点最大化压缩率。

notebook 第 5 节会让你实现 fertility、压缩率、词表覆盖率三个评估函数，在英文文本上对比不同词表大小的 tokenizer，亲手得出「甜点区」。

8研究前沿与开放问题

研究前沿与开放问题

  • tokenizer-free / byte 级模型：能不能彻底不要 tokenizer，直接在字节上建模？MEGABYTE、ByT5、以及 2024 的 BLT（Byte Latent Transformer）等尝试用层次化结构处理长字节序列。诱惑是消灭一切 tokenizer 的偏见与不公平，挑战是字节序列太长、算力吃不消——这是活跃前沿。
  • 数字与算术的表示：按位切只是权宜。怎么让模型真正理解数值（位值、大小、运算）仍未解决；有工作尝试专门的数字编码、或反转数字顺序（让模型从低位开始算，更符合进位逻辑）。
  • 多语公平的根本解：在固定词表预算下，怎么分配给各语言才公平？按使用人口？按数据量？按 fertility 均衡？这是个有价值取向的优化问题，没有技术上的唯一答案（Petrov 2023、BLOOM 的 ROOTS 实践）。
  • tokenizer 与模型联合优化：tokenizer 现在是训练前冻结的，但它显然影响最终能力。能不能让它可学习、或随训练自适应？这会打破「一锤子买卖」的限制，但工程上极难（换 token 就要重建 embedding）。
  • 压缩率与能力的真实关系：更高压缩率到底帮多少？最近有研究发现压缩率与下游能力相关但不单调——存在「压得太狠反伤能力」的拐点。把这条关系刻画清楚，能让 tokenizer 选择从经验走向定量。

延伸阅读：Rust 2021（tokenizer 对多语的影响）、Petrov 2023（语言间不公平）、ByT5 / MEGABYTE / BLT（tokenizer-free 方向）。想动手就用 SentencePiece / HuggingFace tokenizers 在你自己的语料上训一个，对比 fertility。完整清单见 references.md。
