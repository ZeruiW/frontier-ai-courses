1从工具到系统：最后一块拼图

前四个模块给了你四件工具：差分隐私（给隐私一个可累加的预算）、DP-SGD（把 DP 装进训练）、联邦学习（数据不出域）、机器遗忘（事后撤回）。但工具不等于系统。一个真实的隐私系统不是「用了 DP」或「跑了联邦」，而是把这些工具组装成一条端到端的管线，并能过审计、被监管认可、向用户交代。本模块就是这最后一块拼图：从原理到生产——隐私预算怎么分配与核算、合规怎么落地、端侧怎么部署、审计与文档怎么做。

先确立一个贯穿本模块的认知，它在前面每个模块都出现过、这里要正面回答：「用了某个隐私技术」≠「整个系统是隐私的」。模块 02 讲过「跑了 DP-SGD 不等于流程私有」（超参搜索、数据预处理都要核算）；模块 03 讲过「联邦不等于零泄露」（聚合结果仍可能反推）；模块 04 讲过「遗忘删不掉已扩散的副本」。这些缺口在单个模块里是脚注，在系统层面却是必须正面管理的——可信部署的核心工作，就是把各工具的保证正确地拼起来、把它们的缺口用别的工具或流程补上、并把整个系统的隐私性质算清楚、记录下来、接受审计。

这个「拼起来」有三个层次的工作，对应本模块的主线：① 技术组合（DP+联邦+遗忘如何正交叠加、隐私预算如何在多个任务间分配与核算）；② 合规落地（把 GDPR 的抽象义务——同意、最小化、被遗忘权、可携权——翻译成可执行的检查与机制）；③ 审计与文档（用经验攻击验证声称的隐私、用模型卡 / 合规清单让系统可问责）。学完这一模块，你就完成了从「会写隐私机制」到「会交付隐私系统」的最后一跃。

一句话定位本模块：前四模块教你造零件，本模块教你组装整机并通过质检。核心心智模型是把隐私当作一个需要全生命周期管理的属性——不是训练时加个 DP 就一劳永逸，而是从数据收集（同意、最小化）、训练（DP/联邦）、部署（端侧、预算核算）、到运营（遗忘请求、审计、文档）的每个环节都要守住、并能证明守住了。本模块 notebook 会把一条端到端隐私管线（预算分配 + 组合核算 + 合规检查 + 审计报告）从零跑通。

2技术组合：DP+联邦+遗忘叠加

技术组合：DP + 联邦 + 遗忘如何叠加

可信部署的第一步是把四个工具正交地拼起来。回顾每个工具防什么、留什么缺口，就能看出怎么组合互补：

工具防什么缺口（需别的工具补）在管线里的位置
联邦学习原始数据集中（数据不出域）上传的更新/聚合结果仍可能泄露数据层：决定数据流向
安全聚合服务器看到单个客户端更新聚合的「和」仍可能反推个体传输层：保护单个更新
DP / DP-SGD从输出/模型反推个体有效用代价；不防数据被偷训练层：限制信息泄露
机器遗忘用户撤回后影响仍在删不掉已扩散的副本运营层：响应删除请求

它们正交是因为各防一个独立环节，所以能层层叠加而不冲突：典型的生产隐私栈是联邦学习（数据不出域）+ 安全聚合（服务器只见总和）+ client-level DP（总和也不泄露个体）+ 客户端采样（顺带隐私放大），再配上机器遗忘处理运营期的删除请求。每一层补上前一层的缺口：联邦不防反推→DP 补；DP 不防看单个更新→安全聚合补；都不管事后撤回→遗忘补。Google 的 Gboard、跨机构医疗联邦正是这种组合拳。

但叠加不是免费的，要管理它们的相互作用。两个最重要的：① 隐私放大的复用——联邦的客户端采样恰好就是 DP 的子采样，二者共享同一个 q，所以隐私放大只能算一次、不能重复计；② 效用代价的叠加——DP 噪声 + 非 IID 漂移 + 通信压缩误差会累积伤害效用，调参时要通盘考虑。理解「每个工具防什么、缺口在哪、叠加时如何相互作用」，是设计隐私栈的核心能力——不是把技术堆上去，而是让它们的保证拼成完整覆盖、让它们的代价不至于压垮系统。

匹配威胁

一个系统级的常见错误：以为隐私技术可以「叠加得越多越安全」。实际上每个工具都有效用代价和工程复杂度，盲目堆叠会让系统既慢又难维护，还可能因为配置错误反而留下漏洞（比如安全聚合实现有 bug、DP 的 ε 算错、遗忘没验证）。正确的姿势是先明确威胁模型（防谁、防到什么程度），再选最小够用的工具组合——cross-silo（几家可信医院）和 cross-device（亿级不可信手机）需要的栈完全不同。匹配威胁，而非堆砌技术。

3隐私预算管理：分配与核算

隐私预算管理：把 ε 当有限资源分配

模块 01 把 ε 当成「可消费的预算」，但那还是单次机制的视角。在一个长期运行的系统里，隐私预算管理升级成一个真正的财务规划问题：你有一个总预算（比如整个产品对每个用户的总 ε=4），它要分配给多个任务、多次发布、多轮训练、甚至多年的运营——而且一旦花完就不该再碰这份数据。

预算管理的核心动作有三个。分配（allocation）：把总预算切给各个用途——训练用多少、发布统计用多少、留多少给未来。核算（accounting）：每次消费后用组合定理（模块 01）/ RDP 会计（模块 02）累加已花的 ε，实时知道余额。叫停（enforcement）：余额不足时拒绝新的查询/训练，而不是偷偷超支。这三件事缺一不可——只分配不核算会超支，只核算不叫停等于没管。

直白说

把它想成给一个项目分预算：总共 100 万（总 ε），市场部花一笔、研发花一笔、留一笔应急（未来的查询）。每花一笔记一次账（组合定理累加），花超了就不批新的开销。隐私预算管理就是这套财务纪律，只不过货币是 ε、账本是隐私会计器。

严谨说

严谨说，预算分配要用对组合定理：同一份数据上的多个任务是串行组合（ε 相加 / RDP 累加）；不相交数据子集上的任务是并行组合（取 max，不耗额外预算）。聪明的分配会尽量用并行省预算（把不同任务作用在不同数据子集上）、用更紧的会计（RDP 而非朴素组合）榨出更多可用 ε。预算管理的优劣直接决定系统在固定隐私强度下能做多少事。

一个真实的、教科书级的例子是美国 2020 年人口普查：它有一个全局隐私预算，要分配给从国家到街区的各级、各类统计发布。分配方案（哪个统计花多少 ε）经过激烈的技术 + 政策辩论——因为这直接决定了哪些数据更准、哪些更糊。这说明预算分配不是纯技术决策：它是「在固定隐私总量下，把准确性这个稀缺资源分给谁」的价值判断。工程师的责任是把每种分配方案对应的「谁多准、谁多糊」如实算出来，供决策者权衡——这正是本模块 notebook 要实现的预算分配 + 组合核算。

预算管理还有一个时间维度的难题：DP 保护的是「一份固定数据上的一次性分析」，但真实系统是持续运行、数据持续流入的。同一个用户的数据如果反复进入多次训练/发布，他的隐私损失会持续累加——所以要决策预算的「时间粒度」：是按每次发布、每个用户的终身、还是滚动时间窗（如每月重置）来管预算？每种选择对应不同的隐私语义和工程复杂度。还有更微妙的：新数据加入能不能「换来」新预算？已删除数据的预算能不能回收？这些「动态 DP」问题在学术上仍未完全解决，工程上通常保守处理（按用户终身或固定窗口，宁可少花）。这正是为什么预算管理是 DP从单次机制走向生产系统最难的一跃。

预算管理的一句话纪律：总 ε 是花一次少一次的硬约束，必须分配、核算、叫停三管齐下。最危险的反模式是「预算无限」的错觉——以为每次单独看都是私密的（小 ε），就可以无限次查询/训练。组合定理无情地告诉你：足够多次的小 ε 查询会把隐私漏光。没有预算管理的 DP 系统，就像没有账本的公司，迟早破产（隐私耗尽）而不自知。本课 notebook 会把这个「账本」实现成一个 PrivacyBudget 类，分配-核算-叫停一应俱全。

4合规：义务翻译成机制

合规：把法规义务翻译成可执行机制

隐私技术的外部驱动力是法规：GDPR（欧盟）、CCPA（加州）等规定了一系列义务。可信部署的关键工作之一，是把这些抽象的法律义务翻译成具体、可执行、可检查的技术机制。这种翻译是「法规是 why、技术是 how」的具体落地：

法规义务意思对应的技术/流程机制本课哪个模块
知情同意 consent用数据前要获得明确同意同意管理系统 + 数据访问门控（无同意不入训练集）流程
数据最小化 minimization只收必要的最少数据联邦学习（数据不集中）+ 不存原始查询模块 03
被遗忘权 RTBF用户可要求删除其数据删原始数据 + 机器遗忘 + 失效快照模块 04
量化隐私保证能说清保护到什么程度DP 的 (ε,δ) + 隐私会计 + 审计模块 01/02
可问责 accountability能证明合规、可被审计模型卡 / 数据说明书 + 合规清单 + 审计报告本模块

最值得展开的是被遗忘权，因为它是合规与技术结合得最深、也最容易做表面功夫的地方。一个真正的删除请求响应，远不止「从数据库删掉那行」——它是一条链路：① 删原始数据 → ② 机器遗忘（删模型里的影响，模块 04）→ ③ 失效已分发的模型快照 / 缓存 → ④ 通知下游（用了这数据的衍生模型）→ ⑤ 验证遗忘有效（成员推断）→ ⑥ 记录这次删除（审计留痕）。缺任何一环，「被遗忘权」就名不副实。很多系统只做了第①步就声称合规——这正是模块 04 强调「遗忘必须验证、遗忘是架构的函数」的现实意义。

还有一项常被工程忽视、却是 GDPR/CCPA 明确要求的义务——数据可携权（data portability）与访问权（right of access）：用户有权拿到「你存了我哪些数据、用它做了什么」并导出。这在 ML 系统里很棘手：一条数据进了模型权重后，「你用我的数据做了什么」很难说清（它和千万条数据纠缠在一起）。务实的做法是维护数据血缘（data lineage / provenance）——记录每条数据进了哪些数据集、训练了哪些模型、影响了哪些发布。血缘不仅服务可携/访问权，还是被遗忘权的前提（要删一个人，先得知道他的数据流到了哪里）和审计的基础。所以「记录数据去了哪」是贯穿多项合规义务的基础设施，值得在系统设计早期就建好。

把合规做成可执行的检查而非一纸承诺，是工程的关键。本模块 notebook 会把合规清单实现成一组检查函数——「这条数据有同意吗？」「隐私预算还没超吗？」「遗忘通道可用吗？」「文档齐全吗？」——每条返回通过/不通过，组成一个上线前必须全绿的 gate。这把合规从「法务读文档拍脑袋」变成「CI 里自动跑的检查」，是「合规即代码（compliance as code）」的方向，也让合规可复现、可审计、不靠人记。

一个要分清的边界：本课教你把合规义务翻译成技术机制，但不替代法律意见。法规的具体适用（哪些数据算个人数据、什么构成有效同意、跨境传输规则）高度依赖司法辖区与案情，是法务/合规专家的领域。工程师的责任是提供能满足义务的技术能力（DP 的 ε、可用的遗忘通道、齐全的文档）并把系统的隐私性质如实算清，让法务能基于真实情况判断合规——而不是用技术黑话掩盖问题，或假装某个技术「自动合规」。技术与法务是协作，不是替代。

5端侧部署：架构层的隐私

端侧部署：隐私的另一种架构选择

除了给数据加噪、让数据不集中，还有一种更彻底的隐私架构：端侧部署（on-device）——把模型推理（有时连训练）直接放在用户设备上跑，敏感数据（你的照片、消息、健康数据）根本不离开设备。这是「数据最小化」的极致：不是少传，而是不传。

端侧部署与本课其他技术的关系是互补的架构选择：联邦学习是「训练时数据不出域」，端侧推理是「推理时数据不出域」，二者常一起用（端侧联邦训练 + 端侧推理，如 Gboard）。它的隐私优势很直接——没有数据上传就没有传输泄露、没有服务器拖库风险、用户对自己的数据有物理控制。代价则是工程约束：设备的算力、内存、电量、存储都有限，大模型放不进手机，所以端侧往往要配合模型压缩（量化、蒸馏、剪枝，见 C27/C36 GPU 课）把模型缩小。

端侧也不是隐私的银弹，有它自己的缺口和权衡：① 模型本身要分发到设备，模型权重可能被逆向（提取训练数据、知识产权风险）；② 端侧难以集中审计（模型在千万台设备上各跑各的，怎么验证它们都合规？）；③ 更新困难（修一个隐私 bug 要推送到所有设备）；④ 个性化数据留在端上又带来本地存储的安全问题。所以端侧部署是把一部分风险从服务器转移到设备，而非消除风险——要和威胁模型匹配着用。

端侧还和一个可信硬件的方向交汇，值得一提：当某些计算必须在服务器做（如聚合、个性化推荐）、又不想让服务器看到明文数据时，可信执行环境（TEE，如 Intel SGX、ARM TrustZone）提供一个「飞地（enclave）」——数据在里面解密计算、外部（包括云服务商自己）都看不到，还能用远程证明（attestation）向用户证明「我确实在飞地里、按约定的代码处理了你的数据」。它和本课的密码学手段（安全聚合、同态加密）是互补的信任根：密码学靠数学保证、TEE 靠硬件保证，各有性能与威胁模型上的取舍（TEE 快但要信任芯片厂商、有侧信道风险；密码学慢但信任假设更少）。可信部署的工具箱里，硬件与密码学常常并用。

端侧 vs 云端的隐私权衡一句话：端侧用「数据不上传」换「模型要下发 + 难审计 + 难更新」。它最适合数据极敏感、模型够小、不需频繁更新的场景（输入法预测、照片分类、健康监测）。把它放进可信部署的工具箱：它是和 DP/联邦并列的一种架构层隐私手段，回答的是「数据在哪里被处理」这个最根本的问题——能不上传就不上传，是最朴素也最强的隐私。

6审计：声称 vs 实际的隐私

审计：声称的隐私 vs 实际的隐私

可信部署的最后一道关，也是最容易被跳过的一道，是审计：用经验手段验证系统实际提供的隐私，是否名副其实于它声称的隐私。这至关重要，因为隐私的 bug 是沉默的（模块 00 讲过）——ε 算错了、安全聚合实现有漏洞、遗忘没删干净，系统照常工作，不会报错，只会悄悄不安全。审计就是主动去戳这些沉默的漏洞。

审计的核心方法是用攻击来验证防御（呼应 C12 测量、C44 攻击）。两个主力工具：

  • 成员推断审计：用最强的成员推断攻击（如 LiRA，Carlini 2022）去攻击你的系统，看实际的攻击成功率。若你声称 ε=2 但攻击成功率高得像没有保护，说明实现有 bug 或 ε 算错。这给出一个经验 ε（empirical ε，Nasr 2021），与证明的 ε 对账。
  • 金丝雀注入（canary）：故意往训练集里塞一些独特的、可识别的样本（如随机字符串），训练后检测模型是否记住/泄露了它们。金丝雀被泄露的程度，直接经验性地度量了系统的记忆与隐私——这是审计 DP 与遗忘最实用的探针。

审计揭示的一个深刻现象是「证明的 ε」与「经验的 ε」常有差距：经验攻击反推的隐私损失，往往远小于证明的 ε。这有两种解读，都有价值：要么说明你的证明很松（可以放心调小噪声、提高效用——省下的都是利润）；要么说明攻击还不够强（真实风险被低估，要警惕）。无论哪种，审计都把「纸面保证」和「现实风险」连了起来——不审计的隐私声明，本质上是没被检验的假设。

实现 ≠ 有效

审计能发现的最严重问题，往往是实现 bug 而非理论缺陷：DP 的噪声加错了地方、采样不是真随机（破坏了放大假设）、安全聚合的掩码没正确相消、遗忘只改了表面参数、或者最常见的——超出 DP-SGD 范围的数据访问没被算进 ε（超参搜索、看验证集）。这些 bug 让声称的 ε 完全失真，而代码照常运行、测试照常通过。所以「实现了隐私机制」和「隐私机制真的有效」之间，隔着一道必须用攻击来跨越的鸿沟——审计不是可选项，是隐私系统的验收测试。

7文档与问责：让隐私可检验

文档与问责：让隐私可被检验

可信的最后一块是可问责（accountability）：系统的隐私性质必须被记录下来、能被第三方检验。再好的隐私技术，如果没人说得清「这个模型用了多大 ε 的 DP、是不是联邦训练的、遗忘通道怎么用、训练数据从哪来」，就无法被信任、无法被监管、无法被问责。文档是把隐私从「团队内部口口相传」变成「可审计的事实」的载体。

标准化的文档载体有两个：模型卡（model card）记录模型的用途、训练数据、隐私处理（ε、是否 FL、是否遗忘）、已知风险；数据说明书（datasheet）记录数据集的来源、同意状况、敏感字段、处理方式。它们是 AI 系统的「营养成分表」——让使用者、审计者、监管者一眼看清隐私性质，无需读代码。

把文档、检查、审计串起来，就构成一个完整的可信部署生命周期，这也是本模块 notebook 要走通的端到端流程：

数据收集 ──> 训练 ──────> 部署 ──────> 运营 │ │ │ │ 同意+ DP/联邦+ 端侧/云+ 遗忘请求+ 最小化 预算核算 预算余额 持续审计 │ │ │ │ └───────────┴──── 模型卡/数据说明书 ───┴──── 合规清单 gate (全程记录隐私性质，上线前必须全绿)

这条生命周期把全课串成一个闭环：模块 01/02 的 DP 在「训练」处、模块 03 的联邦在「数据收集/训练」处、模块 04 的遗忘在「运营」处，而本模块的预算核算、合规清单、审计、文档贯穿全程、把它们粘合成一个可交付、可问责、可持续的系统。至此你应当明白：可信 ML 不是某个算法，而是一种把隐私当作全生命周期工程来管理的能力——这正是这门课从第一个模块就在铺垫的主线。

延伸：Abowd 2018（人口普查 DP 的规模化预算管理）、Ponomareva 2023（DP 实操与报告规范）、Mitchell 2019（Model Cards）、Gebru 2021（Datasheets）、Nasr 2021（经验隐私审计）。清单见 references.md。

8研究前沿与开放问题

研究前沿与开放问题

  • ε 的语义与沟通：把 ε 翻译成决策者/用户能懂的风险语言（如「攻击成功率上界」）仍是社会-技术难题。预算分配的「公平性」（不同群体/用途分多少 ε）也缺乏共识框架。
  • 证明 ε 与经验 ε 的弥合：用越来越强的攻击（LiRA 及后续）逼近真实隐私下界，让证明更紧、噪声更省。把审计标准化为隐私系统的「验收测试」是工程方向。
  • 合规即代码：把法规义务系统性地编译成可执行检查与可验证证明，让合规可复现、可自动化。隐私的形式化验证（证明一个系统满足某隐私规约）刚起步。
  • 可信组合的理论：DP+FL+SecAgg+遗忘叠加时的隐私-效用-成本联合分析、相互作用（如放大复用、误差叠加）的统一刻画，远未成熟。
  • 可问责的技术化：如何让用户/监管可验证地确认隐私承诺被兑现（密码学承诺、可信硬件、可审计日志），把信任从「相信厂商」变成「能够检验」，是隐私治理的核心缺口。
  • 基础模型时代的隐私部署：LLM 的端到端隐私（DP 微调 + 端侧推理 + 遗忘 + 抗抽取）、隐私与能力/对齐的权衡，是把本课推向前沿模型的综合挑战（与 C44 攻击、C23 对齐交汇）。

必读：Abowd 2018（规模化 DP 部署）、Ponomareva 2023（DP 实操规范）、Nasr 2021（隐私审计）、Kairouz 2021（FL 部署全景）。完整清单见 references.md。
