1动机：线上没有标签，怎么知道模型变坏了

模型上线了，门禁也过了，离线 acc 0.92。三个月后，客服开始抱怨「最近推荐越来越不准」。你打开监控面板——发现根本没有监控面板。于是你想算算线上准确率，却发现一个残酷的事实：线上没有标签。用户不会告诉你他点的那个推荐到底「对不对」；贷款是否违约要等几个月才知道；医疗诊断的真值可能永远拿不到。你想监控性能，却没有性能的真值可监控。

这是上线后监控的核心困境，也是本模块要破解的：在标签延迟（甚至永远缺失）的现实下，怎么知道模型是不是在变差？答案是drift detection（漂移检测）——不直接量性能，而是监控数据分布的变化，把它当作性能下滑的早期预警信号。如果线上输入的分布已经明显偏离了训练时的分布，模型八成开始不灵了，哪怕你还没拿到一个标签。

退一步看，这正是 ML 系统与传统软件最刺眼的差异，也是 Sculley 论文反复强调的「监控缺位是最贵的技术债」之所指。传统服务的监控盯的是它有没有在跑（QPS、延迟、错误率、CPU）——这些 ML 系统当然也要。但 ML 系统会以一种传统监控完全看不见的方式坏掉：服务 200 OK、延迟正常、零异常，模型却在持续输出越来越差的预测。传统监控回答「系统活着吗」，ML 监控还得回答「模型还清醒吗」——而后者没有现成的报错可依赖，只能靠我们主动去测分布、测性能。这一整套「主动质量监控」，就是本模块的主题。

直白说

打个比方：你管理一座水库（模型），但下游用水（性能真值）的反馈要几个月才回来。与其干等，不如装一排上游传感器盯住入库水质（输入分布）——水质一旦异常，你立刻知道「下游迟早出事」，提前应对。漂移检测就是这排传感器：它不直接测「模型准不准」，而是测「喂给模型的数据还像不像它见过的」。水质变了不代表水一定有毒（模型可能还扛得住），但它是一个廉价、实时、可提前几个月的预警，远胜于干等下游中毒的化验报告。

严谨说

形式上，模型训练时见的是分布 P_train(x, y)，上线后真实数据来自 P_live(x, y)。两者偏离有几种：数据漂移 / 协变量偏移（P(x) 变、P(y|x) 不变）、概念漂移（P(y|x) 本身变了）、标签偏移（P(y) 变）。我们能无标签地直接观测的只有 P(x) 的变化（数据漂移），所以它成了监控的主力信号。本模块从零实现两个最常用的数据漂移度量：PSI 与 KS 检验。

一个必须刻在脑子里的区分：数据漂移检测是性能下滑的「必要预警」，不是「充分证据」。数据漂移了，模型可能还撑得住（它对这种变化鲁棒）；数据没漂移，模型也可能因概念漂移（P(y|x) 变）而悄悄变差——而概念漂移无标签时几乎测不到。所以漂移监控是早期、廉价、无标签的预警，最终仍需真值回流来确认性能（接模块 05）。把漂移报警当成「该去看一眼了」，而非「模型一定坏了」或「没报警就一定没事」——这个心态上的分寸，是用好任何监控信号的前提。

2PSI：分箱比占比的稳定性指数

2.1 PSI：群体稳定性指数

PSI（Population Stability Index）是工业界（尤其风控、信贷）最常用的漂移度量，二十多年来在评分卡监控里久经考验。思路朴素到一句话：把一个变量分箱，比较「参考期」与「当前期」每个箱里的样本占比，占比差得越多，分布漂移越大。它本质是在问一个很自然的问题——现在来的这批数据，落在各个区间的比例，还和当初训练时一样吗？

\[\mathrm{PSI} = \sum_{i=1}^{B} (p_i - q_i)\,\ln\frac{p_i}{q_i}\]

其中 p_i 是当前期落入第 i 个箱的占比，q_i 是参考期的占比，B 是箱数。这个式子其实是对称化的 KL 散度：两个分布完全一致时每项为 0、PSI=0；差异越大每项越大。理解了这一点，你就不会把 PSI 当成一个凭空发明的工业指标，而会看出它和信息论里衡量分布差异的经典量是同源的。它的妙处是给出一个单一可比的数，配上一组久经考验的经验阈值：

PSI 值解读行动
< 0.1分布基本稳定无需动作
0.1 – 0.25中等漂移警惕，加密监控、排查原因
> 0.25显著漂移告警，考虑重训（接模块 05）

实现 PSI 有两个魔鬼细节。其一，分箱要在参考期上定一次、之后固定：若每期都按当期数据重新分箱，箱边界跟着漂，就量不出漂移了（你在用移动的尺子量移动的东西）。其二，空箱要做平滑：某个箱在某一期占比为 0 时，ln(p/q) 会出现 ln(0) 或除零而炸成无穷。标准做法是给每个箱加一个极小的 ε（如 1e-6）兜底。这两个坑不处理，PSI 要么测不准、要么直接报 inf——本模块 notebook 会把这两个坑都演示给你看，让你亲眼见证「不固定分箱」与「不平滑」分别怎么把 PSI 弄坏。

用一组真实数字把 PSI 算到底，你就再也不会觉得那个 0.1/0.25 阈值是凭空来的。设某特征分 3 个箱，参考期占比 q 与当前期占比 p 如下：

箱 q(参考) p(当前) p-q ln(p/q) (p-q)·ln(p/q) 低 0.50 0.30 -0.20 -0.511 0.1022 中 0.30 0.30 0.00 0.000 0.0000 高 0.20 0.40 +0.20 +0.693 0.1386 PSI 求和 = 0.241 ≈ 0.24

逐项算清楚：低箱占比从 50% 掉到 30%、高箱从 20% 升到 40%——质量明显从低端搬到了高端。代入 (p−q)·ln(p/q) 逐箱求和得 PSI≈0.24，正好压在「中等漂移」与「显著漂移」的 0.25 边界上，提示你「这个特征该警惕、再涨一点就得告警」。注意「中箱」占比没变，贡献恰为 0——这印证了式子的性质：分布没动的部分不贡献 PSI，动得越多贡献越大。手算一遍这个例子，PSI 就从一个神秘的工业指标，变成了你能在脑子里估出量级的透明工具。

为什么 PSI 在风控等领域成了事实标准？因为它把一个统计问题压成了一个可运营的数字：一个标量、一组所有人都认的阈值（0.1 / 0.25）、对样本量不过分敏感。对比下一节的 KS 检验——KS 更严谨（带 p 值），但在几十万样本上会把肉眼无差的两分布都判「显著」，反而不好运营。PSI 的 0.1/0.25 是经验法则（rule of thumb），不是定理，但正是这种「糙而稳、好沟通」的特性让它能贴在监控面板上、写进运维手册、被非统计背景的同事理解和执行。这提醒我们：生产监控的指标，可解释性和可运营性常常比理论纯粹性更重要。

PSI 是逐变量的：它一次只看一个特征。真实系统有成百上千个特征，于是冒出多重检验问题——同时盯几百个特征，纯靠运气也会有一批「漂移」。假设每个特征 5% 的误报率，盯 200 个特征，期望就有 10 个「漂移」纯属偶然。不做校正（Bonferroni / Benjamini–Hochberg）就把每个超阈的特征都告警，面板会被噪声淹没（alert fatigue，告警疲劳），真正的漂移反而被淹没。监控的艺术一半是统计，一半是别让告警变成狼来了——这条多重检验的教训与模块 03 门禁里「反复刷测试集」的陷阱，其实是同一个统计幽灵。

3KS 检验：免分箱的 ECDF 距离

3.1 KS 检验：不用分箱的分布比较

PSI 要分箱，箱数与边界是主观选择。KS statistic（Kolmogorov–Smirnov 两样本检验）提供一个无需分箱的连续变量漂移度量。它的核心对象是 ECDF（经验累积分布函数）：

\[\hat F(x) = \frac{1}{n}\sum_{j=1}^{n}\mathbb{1}[x_j \le x], \qquad D = \sup_x \big| \hat F_{\text{ref}}(x) - \hat F_{\text{cur}}(x) \big|\]

KS 统计量 D 就是两条 ECDF 曲线之间的最大纵向距离。两分布完全相同时两条曲线重合、D=0；差异越大、曲线分得越开、D 越大。计算上有个漂亮的捷径：把两组样本合并排序，在每个数据点处算两条 ECDF 的差，取绝对值最大者——O(n log n)，无需任何分箱参数。这个「最大纵向距离」的几何直觉很重要：它对分布的任何形状变化都敏感（位置、尺度、形状），而不只是均值——这是它比「只比均值」之类的朴素检测强的地方，也是练习 2 会让你从零用 ECDF 复刻 D 来吃透的点。

KS 还自带一个显著性检验：在「两样本同分布」的零假设下，D 的分布是已知的（Kolmogorov 分布），于是能算出 p 值。近似临界值 D > c(α)·sqrt((n+m)/(nm))（c(0.05)≈1.36）。这把「漂移了吗」从「PSI 超不超 0.25 这个经验阈值」升级成「在统计意义上两分布是否同源」——更严谨，但对大样本过于敏感（几十万样本时，肉眼无差的两分布都会被判显著）。这又回到模块 03 的那条教训：「统计显著」不等于「实际重要」。在生产里，常要同时看 KS 的 p 值（是否同源）和 PSI 的幅度（漂移多大值得管），而非只盯一个 p 值——否则大样本下你会被无穷无尽的「显著但无关紧要」的漂移淹没。

本模块 notebook 会把我们从零写的 KS 与 scipy.stats.ks_2samp 做对拍，逐位一致——这既验证了实现的正确性，也呼应了 GPU 课那条方法论：写一个机制，就和一个可信参考对拍。能从零写出 KS 并与权威库对上，意味着你真正理解了它在算什么（两条 ECDF 的最大间距），而不是把它当成一个黑盒函数。这种「能从零复刻 + 能与参考对拍」的理解深度，正是本课区别于「API 巡游」式教学的地方。

维度PSIKS 检验

PSI 和 KS 谁更好？没有绝对答案，它们是互补的。实践常做法：用 PSI 当日常监控的「红绿灯」（一个数、有公认阈值、对大样本不过敏），再用 KS 当需要统计严谨性时的复核（给 p 值）。本模块两个都从零实现，让你理解它们各自在量什么、何时会骗你——这比记住「该调哪个库的哪个函数」重要得多。

4滑动窗口：当前分布怎么估

漂移检测要比较「参考期 vs 当前期」，那「当前期」是多长？这就是sliding window（滑动窗口）的问题：只用最近一段时间的数据来估当前分布。窗口大小是个根本性的权衡：

窗口太短 (如最近 100 条) 窗口太长 (如最近 30 天) + 反应快：突变能立刻察觉 + 估计稳：噪声小、不易误报 - 噪声大：正常抖动也常误报 - 反应慢：渐变漂移要拖很久才发现 - 稀释：突变被大量旧数据淹没 ←——— 灵敏 / 噪声大 稳定 / 迟钝 ———→ 没有免费午餐：快与稳不可兼得，按「漂移多快、误报多贵」选

窗口的选择取决于你预期的漂移速度与误报的代价。突变型漂移（如某上游数据源格式骤变）要短窗口快速捕捉；渐变型漂移（如用户偏好缓慢迁移）适合长窗口稳健估计。更聪明的做法是自适应窗口（如 ADWIN，见 references）：用统计检验自动决定该回看多远——分布稳就放长、一变就缩短。本模块先把固定滑窗做扎实，它是一切的基础，练习 3 会让你实现一个自适应窗口的雏形。

漂移本身也有类型，不同类型对窗口提出不同要求（Gama 2014 综述的分类）：突变（sudden）——分布瞬间跳变（换了数据源）；渐变（gradual/incremental）——慢慢迁移（季节、习惯）；周期（recurring）——周期性回来（节假日、工作日/周末）；重现（reoccurring）——旧分布隔段时间又出现。识别类型很重要：周期性「漂移」可能根本不该告警（它每周都这样），把它误当异常会制造大量误报。成熟的监控会把已知的周期性纳入基线（比如按星期几分别建参考分布），只对非预期的偏离告警。这是把「统计漂移」翻译成「值得管的漂移」的关键一步。

除了「硬截断」的滑动窗口，还有一类更平滑的做法值得知道：指数加权（EWMA）——给近期数据大权重、远期数据指数衰减，用一个衰减系数 α 取代「窗口长度」这个硬边界，既不会像短窗那样被单点尖峰带飞，又比长窗反应快。它和滑窗是同一个「如何估当前分布」问题的两种参数化：滑窗问「回看多少条」，EWMA 问「过去的权重衰减多快」。生产里检测渐变漂移时 EWMA 往往更顺手（没有窗口边界处的突跳）；检测突变时短滑窗或 CUSUM（累积和，专测均值突跳）更灵。理解「窗口长度 ↔ 衰减系数 ↔ 灵敏度/稳定性」这组等价旋钮，比记住某一个具体算法更重要——它们都在那条「快与稳不可兼得」的权衡线上取点。

5告警：从「漂移分」到「该不该叫人」

有了 PSI/KS 和滑窗，最后一步是告警逻辑：什么时候真的把人叫起来？这一步常被当成「加个 if 判断」而草草了事，但它其实是监控系统成败的关键——一个统计再漂亮的检测器，配上糟糕的告警策略，整个系统也会沦为没人看的噪声源。直接「PSI 一超 0.25 就告警」太天真，会被噪声反复触发。实战的告警要更稳：

  • 持续性要求：要求漂移连续若干个窗口超阈才告警（一次性尖峰多半是噪声或数据管道抖动），类似监控里的「持续 5 分钟 CPU>90% 才报警」。
  • 分级告警：PSI ∈ [0.1, 0.25] 记为「警惕」（加密监控、不叫人），> 0.25 才「告警」（叫人 + 触发重训评估）——对应模块开头那张 PSI 阈值表。
  • 抑制与去重：同一漂移已告警后，在它消除前不要每个窗口重复刷告警（告警风暴会让人直接静音整个系统，反而漏掉真问题）。
  • 把告警接上行动（runbook）：告警不是终点，而该触发一个明确的动作——排查数据管道、人工复核、或进入模块 05 的重训触发评估。每条告警最好都附一份「收到后该怎么做」的处置手册（runbook），否则半夜被叫醒的人只会一脸茫然。一个没人响应、不接任何行动的告警，等于没有。

监控系统最大的失败模式不是「漏报」，而是告警疲劳（alert fatigue）：误报太多 → 大家学会无视告警 → 真出事时那条关键告警也被无视。一个叫狼来了的监控系统比没有监控更危险——它给了你「一切尽在掌控」的错觉。所以告警设计的第一原则是宁可少而准，不可多而吵：每一条告警都应当值得一个人停下手头的事去看。

6三层监控栈：数据/预测/性能

把监控放回全局：它是生命周期闭环里从「上线」绕回「重训」的那条反馈边。模型部署后（模块 03），监控（本模块）持续盯住输入分布与（延迟到达的）性能；一旦漂移/性能跌破阈值，就触发模块 05 的重训。一个完整的监控栈分三层：

监控层盯什么标签需求时效
数据漂移输入特征分布 P(x)（PSI/KS）不需要标签实时，最早预警
预测漂移模型输出分布 P(ŷ)、置信度分布不需要标签实时，次早预警
性能监控真实指标 acc/AUC/业务 KPI需要真值滞后（标签延迟后）

为什么要分这三层、而不是只盯性能？因为它们覆盖了不同的失败模式 × 不同的时效。只盯性能监控，你会发现得太晚（标签延迟）；只盯数据漂移，你会漏掉「数据没变但概念变了」的情况，也会被「数据变了但模型扛得住」的情况误报。三层叠起来才形成纵深防御：数据漂移在最前线拉响第一声警报（无标签、实时），预测漂移补一道（看模型自己的反应），性能监控在后方做最终裁决（有了真值）。这种多信号、分层、时效互补的监控架构，是从「玩具脚本」走向「能托住生产的系统」的标志。

注意这三层的时效递减、可信递增：数据漂移最早但只是间接信号，性能监控最晚但是金标准。成熟系统三层并用——用数据/预测漂移做早期预警（无标签、实时），等真值回流后用性能监控做最终确认（这正是模块 05 反馈闭环要解决的标签回收）。中间的预测漂移（模型输出分布变了吗、置信度整体下降了吗）是常被忽视的便宜信号：它无需输入侧分箱，直接看模型自己的反应，往往比逐特征 PSI 更早、更聚合地反映「模型懵了」。

本模块的真实数据胶囊会把这套逻辑完整演一遍：一个信贷风控模型，上线后申请人的收入/负债比分布逐月漂移（数据漂移，PSI/KS 可见），同时收入与违约的真实关系也在减弱（概念漂移）。你会看到一个关键现象——PSI 在 AUC 真正掉下来之前就升高了：无标签的漂移信号给了你提前量，而 AUC（需要真值）只是事后确认了模型确实变差。这恰好印证了为什么我们要费力去监控分布，而不是干等性能数字：等性能数字出来，可能已经损失了几个月的线上效果。

7闭合反馈环：让生命周期真正转起来

最后把监控放进整个生命周期的语境收个尾：监控是让闭环真正闭合的那条边。模块 01–03 把模型安全地送上线，但如果上线后没人盯，模型就在无人察觉中慢慢腐烂——这正是 Sculley 论文称监控缺位为「最贵的债」的原因：它不是一次性的坑，而是持续渗血的伤口。有了本模块的漂移检测，模型劣化第一次有了可观测、可量化、可告警的抓手；而这个抓手的下游，就是模块 05——告警触发重训，重训产出新模型，新模型回到模块 01 被追踪、模块 02 被版本、模块 03 过门禁、再上线被本模块监控。环就此闭合，生命周期才真正转了起来。可以说，监控是把前四个模块从「一次性的上线流程」升级为「能长期自我维持的系统」的那块拼图——没有它，再漂亮的上线也只是把一个注定会腐烂的东西推出了门。

这条「上线后持续盯住、劣化即预警、预警驱动重训」的逻辑，是 MLOps 区别于传统「训练-部署」二段式思维的精髓所在。把它内化，你看任何生产 ML 系统都会下意识地问：它的体温计在哪？没有标签时它靠什么知道自己病了？——这个问题的答案，往往直接暴露一个团队 MLOps 的成熟度。

8研究前沿与开放问题

  • 无标签的性能估计：能否在没有真值时直接估计线上准确率，而不只是测漂移？NannyML 的 CBPE/DLE 等方法用模型的置信度结构 + 漂移做性能估计，是「标签延迟」难题最前沿的攻法（见 references）。
  • 高维与多变量漂移：逐特征 PSI 会漏掉「单看每个特征都正常、但特征间的联合关系变了」的漂移。用降维（PCA）+ 两样本检验、或域分类器（domain classifier）检多变量漂移是活跃方向（Rabanser 2019）。
  • 区分数据漂移 vs 概念漂移：报警说「漂移了」，但到底是 P(x) 变（模型可能还行）还是 P(y|x) 变（模型真坏了）？无标签时两者难以区分，而它们要的应对完全不同。这是漂移研究的核心难题（Gama 2014 综述）。
  • 漂移的「值不值得管」：检测到漂移 ≠ 该重训。重训有成本、有风险（模块 05 的灾难性遗忘）。如何把「漂移幅度」翻译成「预期性能损失」再翻译成「重训的投入产出比」，让监控直接驱动理性决策，仍缺成熟框架。
  • 对抗性环境下的监控：在欺诈、垃圾内容、滥用检测里，分布漂移不是自然发生的，而是对手刻意制造的——攻击者会主动把行为移出你的检测器看得见的范围。在「对手会适应你的监控」的前提下设计鲁棒的漂移检测，是安全相关 ML 监控的特有难题，与传统的「自然漂移」假设根本不同。
