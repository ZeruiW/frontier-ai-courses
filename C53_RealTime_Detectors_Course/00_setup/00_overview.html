1「实时」到底有多硬：三个不能谈判的约束

这门课讲实时目标检测器——YOLO 家族、RTMDet、RT-DETR。它们和 Faster R-CNN、Mask R-CNN 那一支的区别不在「精度」，而在它们是被一个外部给定的延迟预算逼出来的。理解这一点，后面每一代的设计选择才有解释。

「实时」不是一个形容词，它是三个可量化、且同时成立的约束。缺任何一个，这门课里的绝大多数设计都会失去动机。

约束具体是什么违反了会怎样谁给定的
① 延迟预算端到端 p99 必须小于分给你的那几毫秒——注意是 p99 不是均值，也不是 FPS帧被丢弃、下游拿到过期的感知结果、控制回路失稳外部硬性给定：相机帧率 × 感知任务排期
② 显存与带宽车端 SoC 的显存要被十几个任务瓜分；带宽常常比算力更早成为瓶颈engine 构建失败、被迫降分辨率、多任务互相抢占硬件平台选型（几年前就定死了）
③ 精度在那个延迟预算下能达到的最高精度，而不是不限时间能达到的精度漏检 / 误检直接变成安全事件产品与安全团队

直白说

三者的关系不是「三个目标做权衡」，而是「两个是硬约束、一个是优化目标」。延迟预算与显存是外部给你的，你不能通过「模型再准一点」去和它们谈判；精度才是你唯一能争取的东西。所以实时检测器的整个研究史，可以概括成一句话：在给定的毫秒数里，把 AP 往上抬。

严谨说

这也解释了为什么实时检测领域的论文长得和通用检测不一样：通用检测比的是「在 COCO 上的 AP」，实时检测比的是一条曲线——延迟为横轴、AP 为纵轴的帕累托前沿。一个模型「更好」的严格定义是：它把这条前沿往左上方推了。单点比 AP、或者单点比 FPS，都是没有意义的（第 4 节会把这件事讲透，而它是本课最容易在面试里加分的一个点）。

学完这门课你应当能当场回答：标签分配为什么比换 backbone 更能涨点？结构重参数化凭什么「训练时多分支、推理时单分支」还数值等价？YOLOv10 的一致双分配到底怎么去掉 NMS 的、和 DETR 的一对一匹配是不是一回事？RT-DETR 为什么敢说自己比 YOLO 快——它省掉的到底是哪一部分时间？给你一个 33 ms 的帧周期和一块被十几个任务瓜分的 SoC，你怎么为交通标志检测选型并给出论证？

233 毫秒的账：交通标志检测到底分到多少

先把「实时」这个词换成数字。车端前视相机常见 30 FPS，于是有一个不可协商的帧周期：

\[T_{\text{frame}} = \frac{1000}{30} \approx 33.3\ \text{ms}\]

但这 33.3 ms 不是给检测器的。它要先被一串固定开销切掉，剩下的才是「全部感知任务」的时间窗，然后这个时间窗还要被十几个感知任务瓜分。交通标志检测（TSR, Traffic Sign Recognition）在这里面只是一个中等优先级的任务。

一帧 33.3 ms 的真实去向（量产前视感知的典型量级） |<--------------------------- 33.3 ms 帧周期 --------------------------->| | 曝光+ISP+MIPI | 全部感知任务 | 融合/跟踪/规控/执行 | 裕度 | | 8.0 ms | 16.3 ms | 7.0 ms | 2.0 | | | v v +----- 感知的 16.3 ms 再被瓜分 -----+ | BEV 障碍物 45% 7.35 ms | | 车道线/可行驶区域 20% 3.27 ms | | **交通标志 TSR** 15% 2.45 ms | <-- 本课的主角 | 红绿灯 10% 1.63 ms | | 其他（静态障碍/占位） 10% 1.63 ms | +-------------------------------------+ TSR 的端到端预算 = 2.45 ms 再把这 2.45 ms 拆开（这一层才是你能动的）： 预处理 resize+letterbox+归一化 ......... 0.35 ms 14% H2D 拷贝 ............................... 0.15 ms 6% 网络前向 backbone+neck+head ............ 1.45 ms 60% <-- 换模型只能动这一段 NMS .................................... 0.30 ms 12% <-- 唯一随场景波动的一项 解码/坐标还原/阈值 ..................... 0.12 ms 5% D2H 拷贝 ............................... 0.05 ms 2% --------------------------------------------------- 合计 2.42 ms，余量 0.03 ms
这张账单告诉你什么推论
网络前向只占 60%论文里 FPS 那一栏通常只测这 60%。「换个快一倍的 backbone」对端到端最多带来 30% 的收益
预处理 + 后处理占 39%它们在 CPU 上、常常没被优化、且是训练-部署不一致的头号来源（见 C60）
NMS 是唯一「不确定」的一项耗时随候选框数近似 O(n²) 增长。空旷高速 40 个候选 vs 雨夜误检爆炸 900 个候选，端到端延迟能差 40%——这是 RT-DETR 存在的直接理由（模块 04）
余量只有 0.03 ms任何「顺手加一个后处理」的想法都要先算账。「反正只多 0.5 ms」在这里等于超预算 20 倍余量
预算是硬约束，不是建议值

notebook 第 4 节会给你一个反直觉的结果：本课要讲的所有公开模型，没有一个能塞进 2.45 ms——最快的 YOLOv5-S 在 T4 上也要 4.5 ms。这不是账算错了，而是真实的量产约束长这样。它逼出了三条工程路线：① 用 tiny/nano 档 + INT8 + 更小输入分辨率把延迟压下去（代价是小目标掉点，见 C57）；② 把 TSR 降频到 10–15 Hz 跑（代价是首次检出距离变远、时序稳定性变差，见 C55 模块 04）；③ 只在 ROI（消失点附近的图像上半部）上跑（代价是漏掉侧向标志）。面试里被问「你怎么把这个模型放进车里」，说得出这三条并说得出各自的代价，就已经区分度很高了。

3三条主线：这门课其实只讲三件事

YOLO 从 v1 到 v10、加上 RTMDet 与 RT-DETR，表面上是十几个模型、上百个改动。但真正影响精度与延迟的机制只有三条，其余都是围绕它们的工程包装。把这三条抓住，你就能在面试里对任何一个新模型做出判断，而不是背名字。

主线它回答的问题关键节点本课在哪讲
① 标签分配
label assignment		训练时，哪些位置该被当成正样本？这个问题的答案决定了梯度往哪流IoU 阈值 → ATSS → OTA/SimOTA → TaskAligned → dynamic soft label模块 02（全模块）；模块 01 的 YOLOX / v8 / v10
② 无 NMS
NMS-free		能不能让模型直接吐出不重复的框？NMS 是延迟不确定性的唯一来源一对多 + NMS → DETR 的一对一匹配 → YOLOv10 一致双分配模块 01（v10）、04（RT-DETR）；C54 全课
③ 结构重参数化
re-parameterization		能不能训练时用复杂结构、推理时折叠成简单结构？免费的精度Conv+BN 融合 → RepVGG 多分支 → YOLOv6/v7 的 RepBlock模块 01（含 numpy 数值等价证明）

直白说

为什么是这三条？因为它们分别对应了检测器的三个可独立优化的层面：① 训练信号（分配）、② 输出形式（去重）、③ 计算形式（重参数化）。三者互不干扰，可以自由组合——这正是 YOLOv6/v7/v8/v10 能一代一代叠加的原因。反过来，一个「新模型」如果在这三条之外只改了 backbone 的连接方式，它的收益通常在 ±0.5 AP 的噪声里。

严谨说

更有价值的是它们的共同结构：三条主线都是「训练期与推理期解耦」。分配只在训练期存在（推理时没有 GT，也就没有分配）；一对一 vs 一对多的区别也只在训练期（推理时只是要不要跑 NMS）；重参数化更是字面意义上的训练一个结构、推理另一个结构。「凡是只在训练期付出代价的改动，都是免费的午餐」——这是实时检测领域最重要的一条心法，也是它区别于「加模块涨点」式研究的根本处。

把这条心法反过来用，就得到一个很好用的判据：看到一个新的检测器改进，先问「它的代价是落在训练期还是推理期」。落在训练期（更复杂的分配、更多的辅助头、更强的增强、更长的训练）→ 值得试，因为推理零成本。落在推理期（多一个注意力模块、多一个尺度、TTA）→ 必须先算延迟账，因为你只有 2.45 ms。这个判断你在面试现场就能做，不需要跑实验。

4怎么读延迟-精度曲线：同延迟比 AP，而不是同 AP 比延迟

实时检测的所有论文都会画一张图：横轴延迟、纵轴 AP、一堆点连成几条曲线。这张图有一种正确读法和两种常见的错误读法，而分辨它们是这个领域的入门门槛。

先给出严格定义。模型 A 支配（dominate）模型 B，当且仅当：

\[A \succ B \iff t_A \le t_B \ \wedge\ \mathrm{AP}_A \ge \mathrm{AP}_B \ \wedge\ (t_A < t_B \ \vee\ \mathrm{AP}_A > \mathrm{AP}_B)\]

不被任何模型支配的那些点，构成帕累托前沿（Pareto front）。被支配的模型可以直接从候选名单里划掉——存在一个又快又准的替代品，没有任何理由选它。notebook 第 4 节会让你在一组真实量级的数据上把这件事算出来：11 个模型里有 5 个是被支配的。

读法长什么样为什么对 / 错
✅ 同延迟比 AP「我有 10 ms 预算，这个预算内 AP 最高的是谁？」延迟预算是外部硬约束、AP 是可争取量。这个问法直接对应真实的选型决策
❌ 跨延迟点比 AP「我们比 YOLOv8-M 高 4.1 AP」（却慢了 65%）把两个不在同一预算档的模型放一起比。论文最常见的话术，也是面试里最容易被追问穿的一句
❌ 同 AP 比延迟「达到 53 AP 我们只要 9.3 ms」在研究语境下可以，在工程语境下是倒过来的：没有人会先定一个 AP 目标再去找延迟。AP 目标本身就是延迟预算的函数

直白说

为什么「同 AP 比延迟」在工程上是错的？因为AP 不是一个需求，延迟才是。产品不会说「我要 53 AP」，产品会说「感知在 33 ms 帧周期里，TSR 只能占 2.45 ms」。于是唯一有意义的问题是：在 2.45 ms 里我能拿到多少 AP。把这个问句反过来，你就会做出「为了达到某个 AP 而超支延迟」的决定——而延迟超支在车端是硬故障，AP 低一点只是性能差一点。

严谨说

还有一个更隐蔽的错误：比较不在同一条测量协议下的点。不同论文的 FPS 可能包含或不包含 NMS、包含或不包含预处理、batch size 是 1 还是 32、精度是 FP32/FP16/INT8、卡是 V100/T4/A100/3090。这些差异合起来能造成 3–5 倍的差距，远大于模型之间的真实差距。所以任何跨论文的曲线对比都只能用来「粗分档」，不能用来做最终选型——选型必须自己在目标硬件上、用统一协议重测（模块 05 会给出完整的重测流程与容易踩的坑）。

notebook 里那张模型表刻意用了各论文自报的量级数字，于是会得到一个「RT-DETR 系几乎占满前沿、RTMDet 全被支配」的结论。你应该对这个结论保持怀疑，而不是记住它——因为 RT-DETR 论文的对比表就是在自己的测量协议下做的（例如 YOLO 那一侧是否用了官方最优的 TensorRT 导出、NMS 用什么实现与阈值）。这正是「论文的 FPS 不可信」的活标本。本课教你的不是「哪个模型最好」，而是怎么自己把这张表算出来。

一个必须提前说清的边界：本课不讲「怎么训一个更准的检测器」这件事的全部。数据（C55/C56/C58）通常比模型更能决定 TSR 的最终指标——在一个 badcase 驱动的项目里，把 RTMDet-S 换成 RT-DETR-R18 可能涨 2 AP，而把夜间数据补齐可能涨 8 AP。本课教的是「模型这一侧能榨出多少」，以及更重要的：怎么用可验证的方式说清它到底榨出了多少。

6环境、方法论与这门课的用法

本课全程 纯 numpy + 标准库、CPU 可跑、不联网。不需要 PyTorch、mmdetection、TensorRT 或任何数据集下载。所有 notebook 在 CPU 上实跑验证，assert 零失败。

pip install -r requirements.txt      # numpy / matplotlib / jupyterlab / ipykernel
jupyter lab                          # 打开 00_setup/00_environment_check.ipynb
真实世界里你需要本课怎么处理
GPU + TensorRT 实测延迟用参数化的延迟模型（含 NMS 的目标数依赖项）+ 各论文自报数字的量级表；真实测量协议写在模块 05 的胶囊里
COCO / TT100K 数据集用按针孔相机模型合成的交通标志尺寸分布（px = f·S/Z），物理上可解释、可复现
mmdetection / ultralytics把关键机制从零用 numpy 实现：Conv+BN 融合、RepVGG 合并、k-means anchor、ATSS/SimOTA、软标签代价矩阵
PyTorch 训练循环只在需要「证明数值等价」的地方复现前向；本课不训练模型，本课解剖模型

三条贯穿全课的纪律：

  • 凡是说「更好」，必须说清是在哪个延迟点上更好。孤立的 AP 数字在这门课里没有意义。每次比较都要能写成「在 X ms 预算下，从 A 换到 B，AP 从 p 变到 q」。
  • 凡是改动，必须归因到训练期还是推理期。这决定了它的代价结构，也决定了要不要试。第 3 节的心法要贯穿每一个模块。
  • 凡是数值等价的声明，必须用 assert 证明。「重参数化后精度不变」不是一句话，是 np.allclose(y_multi_branch, y_fused)——模块 01 的 notebook 会让你亲手写出这个 assert。

这门课的用法建议：模块 01–02 顺着读（它们是后面所有内容的语言），03–04 可以按需求跳读，05 建议在选型前重读一遍。如果你现在就要为一个具体项目选模型，可以先读 00 + 05，把账算出来，再回头读 01–04 理解每个候选到底做了什么。全课的 notebook 彼此独立，不依赖前一个的变量。

7研究前沿与开放问题

实时检测在 2023 年之后进入了一个有意思的阶段：纯 CNN 的 YOLO 系与端到端的 DETR 系在同一条帕累托前沿上正面相遇了，而且各自都在吸收对方的东西。以下是目前仍然开放的问题。

  • 无 NMS 的收益到底有多大，仍然没有公认答案。 YOLOv10 与 RT-DETR 都主张「去掉 NMS」，但去掉 NMS 换来的是延迟的确定性（方差变小）而不必然是延迟的均值更低。在候选框不多的场景（高速上的 TSR），NMS 本来就只占 12%。「无 NMS 值不值」是一个和场景强相关的问题，不存在通用答案。
  • 一对一匹配的训练效率问题没有被真正解决。 一对一提供的监督信号密度远低于一对多，这是 DETR 系收敛慢的根因之一。目前的主流做法（YOLOv10 的双分配、Co-DETR/Group-DETR 的辅助一对多分支）本质都是「训练时借一对多的密集监督、推理时只用一对一」——这更像是绕过问题而不是解决问题。
  • 结构重参数化与量化的冲突。 多分支合并后的等效卷积，其权重分布往往比原生单分支训练出来的更「长尾」，导致 INT8 量化掉点更严重。「重参数化友好的量化」或「量化感知的重参数化」目前还没有干净的解法——这是 C60 模块 03 会重新遇到的问题。
  • 标签分配的理论仍然缺失。 从 IoU 阈值到 ATSS 到 SimOTA 到 TaskAligned，每一步都被实验证明有效，但「什么是最优的分配」至今没有一个可优化的形式化目标。OTA 的最优传输视角是最接近的一次尝试，但它的代价函数仍然是手工设计的。
  • 评测协议的碎片化。 「同一模型在不同论文里 FPS 差 3 倍」是这个领域的常态。缺少一个像 MLPerf 那样被普遍接受的实时检测端到端 benchmark（含预处理、含 NMS、报 p99、指定硬件与精度），使得跨论文比较基本失效——这是本课模块 05 花整整一个模块讲测量的原因。
  • 面向车端多任务共享算力的联合优化。 现实中 TSR 不是独占 SoC，而是和 BEV、车道线、红绿灯抢时间片。「多个感知任务共享 backbone / 联合排期 / 动态分配算力」在工业界已经是标配，在学术界几乎没有对应的 benchmark——这也是学术实时检测与量产实时检测最大的一条鸿沟。

必读（按本课顺序）：You Only Look Once(Redmon 2016) 与 YOLO9000(2017) —— 读它们是为了理解「网格回归」的原始动机与 anchor 被引入的确切原因；YOLOX: Exceeding YOLO Series in 2021 —— 解耦头 / anchor-free / SimOTA 三件套的消融表是整个领域最有信息量的一张表；RepVGG: Making VGG-style ConvNets Great Again(2021) —— 结构重参数化的原始论文，公式极简，务必自己推一遍；RTMDet: An Empirical Study of Designing Real-Time Object Detectors(2022) —— 大核与共享头，工程细节写得最实在；DETRs Beat YOLOs on Real-time Object Detection(RT-DETR, 2023) —— 注意读它的 NMS 敏感性分析那一节；YOLOv10: Real-Time End-to-End Object Detection(2024) —— 一致双分配。相邻课程：C18（检测基础）、C54（DETR 家族）、C57（小目标）、C60（车端部署）。完整清单见 references.md。
