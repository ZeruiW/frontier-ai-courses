03 · 轨迹级与过程级评测

结果层结构性看不见三件事：钱花在哪、卡在哪、能不能从错误里爬出来 · 轨迹分析是唯一「事前决定、事后无法补救」的环节——没记 args_hash / status / attempt，冗余率、恢复率、pass^k 就永远算不出来 · 轨迹比较适合做断言，不适合做打分：必经动作用 LCS 子序列检查，把编辑距离当主指标等于在惩罚探索、训练 agent 模仿人类的低效 · 失败模式七分类（互斥、有优先级）——在把失败归因为「模型不够强」之前，先排除循环、工具误用、预算耗尽、提前放弃这几类，它们换更强的模型解决不了 · 过程标注的 kappa 低时先怀疑问法：把「这一步好不好」换成「是否让任务离目标更近」，一致性立刻上一个台阶 · Goodhart：「平均步数」这个指标不应该出现在任何报告里——失败的轨迹更短，所以降低平均步数的最省事路径是增加失败率

1结果层看不见的三件事：钱、卡点、恢复力

模块 02 结束时留了一个尾巴：两个 micro 成功率相同的 agent，可能是完全不同的两个产品。轨迹层要回答的正是结果层结构性看不见的三个问题。

问题结果层为什么看不见轨迹层用什么回答决策价值
钱花在哪成功率是 0/1，与消耗无关步数、token、工具调用次数、墙钟时间的分布（尤其是尾部）直接决定单位任务成本与能不能上线
卡在哪一步失败只有一个 0，没有位置信息失败时的最后动作类型、已达成的 checkpoint、错误码分布决定下一步该修什么（工具？提示？上下文？）
能不能从错误里爬出来成功掩盖了过程中的挣扎，失败掩盖了差一点成功恢复率：遇到工具报错后，后续步骤是否走上正轨这是把 demo 变成产品的最关键能力

直白说

为什么「恢复力」值得被单列成一个一级指标？因为真实环境里，工具报错、页面加载失败、命令返回非零状态，是常态而不是异常。一个在干净环境里成功率 60% 的 agent，如果每次遇到报错就原地打转，上线后的成功率可能掉到 20%——而这个落差在任何离线成功率数字里都看不出来。

严谨说

形式化地说，令 $E$ 是「轨迹中至少出现一次工具错误」这个事件。我们真正关心的是条件成功率 $P(\text{success} \mid E)$ 与 $P(\text{success} \mid \neg E)$ 的差距，以及 $P(E)$ 在离线环境与线上环境之间的漂移。总成功率 $P(\text{success})$ 把这三个量混成了一个数——它在离线到线上的迁移中最不稳定，恰恰因为 $P(E)$ 在两个环境里差别巨大。

一句可以直接用在评审会上的话：「成功率」是一个终点指标，而 agent 上线后遇到的分布，主要由「过程中会不会出岔子」决定。所以离线评测必须主动注入错误，并单独报告注入错误后的条件成功率。notebook 第 2 节给出注入方式与恢复率的计算。

2日志 schema：没记下来的东西，事后一个也补不回来

轨迹分析是唯一一个「事前决定、事后无法补救」的评测环节。任务集不够可以补跑，判分器有偏可以重判，但如果当初没记工具的返回码，你今天就永远算不出恢复率——除非把所有实验重跑一遍。

最小可用 schema

{
  "run_id": "eval-2026-08-28-a3f1",     // 一次评测运行
  "task_id": "billing-refund-017",
  "attempt": 2,                          // 同一任务的第几次重复（04 模块的 pass^k 需要）
  "model": "…", "scaffold_version": "harness@1.7.2",
  "steps": [
    {
      "i": 0,
      "type": "tool_call",               // tool_call | model_output | user_turn | error
      "tool": "search_orders",
      "args_hash": "9c1f…",              // 用于检测重复调用（冗余率）
      "status": "ok",                    // ok | tool_error | timeout | refused
      "error_code": null,
      "latency_ms": 812,
      "tokens_in": 3120, "tokens_out": 88,
      "checkpoint_reached": null         // 达成了哪个 checkpoint（模块 02）
    }
  ],
  "outcome": {"score": 1, "reason": null},
  "totals": {"steps": 14, "tokens": 51230, "wall_ms": 41200, "usd": 0.34}
}
字段不记会失去什么重要度
args_hash算不出冗余调用率与循环检测——agent 反复用同样参数调同一个工具是最常见的浪费★★★
status / error_code算不出恢复率，也无法把失败按错误类型分组★★★
attempt无法计算 pass^k / pass@k，多次重复的数据退化成一堆无法配对的独立样本★★★
scaffold_version历史结果不可比——这是 agent 评测里最容易被忽略的可复现字段（05 模块）★★★
tokens_in/out成本无法归一化，所有跨模型对比失效★★☆
checkpoint_reached无法做部分得分，也无法定位卡点★★☆
latency_ms看不出「慢」是模型慢还是工具慢★☆☆

一条现实建议：轨迹日志的 schema 应该在你写第一个 agent 之前就定好，并且从此只增字段、不改语义。字段语义一改，历史数据就变成需要考古的东西。如果你的团队已经在用 OpenTelemetry，直接沿用 GenAI 语义约定 里的 span 属性名（gen_ai.*）而不是自造一套——理由不是标准更优雅，而是现成的 trace 查看器可以直接用（C68 模块 05 展开）。

3六个轨迹指标：定义、直觉与它们各自的失效方式

轨迹指标不需要很多。下面六个覆盖了绝大部分归因需求，每一个都能从上面的 schema 直接算出来。

指标定义回答什么什么时候会骗你
步数 / token / 成本轨迹长度与消耗，报中位数 + P90而非均值这个 agent 贵不贵均值被少数超长轨迹主导；必须报分位数
工具调用精确率调用的工具中，属于「本任务确实需要」的比例它是不是在乱试工具需要标注「本任务需要哪些工具」；标注本身有主观性
工具调用召回率本任务需要的工具中，实际被用上的比例它是不是漏掉了关键信息源有些任务不用某工具也能做对——低召回不必然是坏事
无效动作率status != ok 的步数占比环境/参数用得对不对把「探索性试错」也算成无效——需要区分「首次探索」与「重复犯错」
冗余率(tool, args_hash) 重复出现的步数占比有没有在原地打转合法的轮询（等任务完成）会被误判；需要白名单
恢复率出现工具错误后，下一步换了策略且最终成功 的比例遇到岔子能不能自救任务本身太简单时恢复率虚高（错误无关紧要）

循环检测：最有价值的单个信号

在真实运行日志里，最常见、最贵、也最容易自动检出的失败是循环：agent 反复执行同一组动作，每次都得到同样的结果，直到耗尽预算。检测方法有两层：

  1. 精确循环：连续窗口内出现重复的 (tool, args_hash) 序列。用一个滑动窗口 + 哈希即可，$O(n)$。
  2. 语义循环：动作不完全相同（比如每次搜索的关键词略有变化），但观测结果几乎不变。检测方式是看状态摘要的变化量——连续 $k$ 步状态摘要没有变化，即判定为语义循环。

循环检测的工程价值在于它可以直接接到预算控制上：检出循环就提前终止这条轨迹，把省下的预算拿去跑别的任务。在成本受限的评测里（05 模块），这一条能把有效样本量提高一大截。注意：提前终止会改变你测量的东西——被终止的轨迹要单独标记为 terminated_by_loop_detector，而不是简单记成失败。

为什么不要把这些指标压成一个总分

很容易产生的冲动是：把六个指标加权求和，得到一个「轨迹质量分」。不要这么做。原因在第 7 节——这些指标互相之间存在真实的权衡（少走弯路 vs 充分探索），压成一个数会让权衡消失，而权衡恰恰是你要看的东西。

4和参考轨迹比：编辑距离、LCS，以及「唯一正确路径」这个陷阱

一个自然的想法：既然人类专家能做这个任务，就录一条参考轨迹，然后用编辑距离衡量 agent 偏离了多远。这个方法有用，但必须先破除一个误解。

「参考轨迹 = 唯一正确路径」是错的，而且是危险的错。同一个任务通常有多条合法路径，而且 agent 的最优路径未必等于人类的最优路径——它读文件比人快，试错比人便宜，所以「先粗读全部再定位」对它可能比「精确检索」更划算。把轨迹相似度当作主指标，等于在训练 agent 模仿人类的低效之处。

那轨迹比较有什么用

用法怎么做为什么这样是安全的
必经动作检查只检查参考轨迹里的关键动作子集（如「必须查过退款政策」）是否作为子序列出现只约束必须发生的事，不约束顺序与其余动作——这是 checkpoint 在轨迹层的形式
禁止动作检查断言某些动作从未出现（如「从未对他人账户做写操作」）只约束不许发生的事，零假阳性风险
偏离度作为诊断量算编辑距离，但只用于排序人工复核的优先级（偏离最大的先看）不进主指标，只做分诊
路径多样性统计把成功轨迹聚类，看有几种解法揭示任务是否真的有唯一解，反过来验证任务设计

两种距离，各自适用的场景

\[d_{\text{edit}}(a, b) = \min\{\text{插入/删除/替换次数，把动作序列 } a \text{ 变成 } b\}\]

编辑距离对整体结构敏感，适合「路径应该大致相同」的短任务；最长公共子序列（LCS）只看必经动作有没有按序出现，对插入的额外动作宽容，适合「允许 agent 多做探索」的长任务。做必经动作检查时用 LCS，做偏离度分诊时用编辑距离。

直白说

一句实践总结：轨迹比较适合做「断言」，不适合做「打分」。「必须包含 X」「不许出现 Y」是断言，客观且零争议；「和参考路径的相似度是 0.73」是打分，而这个 0.73 没有任何可解释的业务含义。

严谨说

从测量的角度，轨迹相似度是一个代理指标，它与真实效用之间的相关性依赖「参考轨迹确实是最优的」这个未经验证的假设。把它作为主指标会引入 specification gaming 的一个变体：agent 学会模仿参考轨迹的表面结构而不是它的目的。断言型的检查则没有这个问题，因为它们只编码了必要条件，不编码充分条件。

5过程级评测：步骤 rubric、过程奖励与标注一致性

第三层，也是最贵的一层：逐步判断「这一步做得对不对」。它的价值不在于给出更准的总分，而在于信用分配——把一次失败精确定位到某一步的某个决策。

三种过程级判分的来源

来源怎么产生成本可靠性
规则写死的检查（这一步是否调用了必需的工具、参数是否合法）低高，但只能覆盖能写成规则的部分
人工步骤标注标注员逐步打 好/中性/坏 三档极高（一条 40 步的轨迹要标 40 次）取决于标注规范；必须测 kappa（C10-02）
过程奖励模型（PRM）用步骤标注训一个模型，之后自动打分训练贵，推理便宜在分布内可靠，分布外会失效——PRM 自己也需要被评测

关于人工步骤标注有一个必须提前知道的现实：标注者之间的一致性通常显著低于结果级标注。「这个任务完成了吗」容易达成共识；「第 17 步该不该先看日志」则见仁见智。如果 Cohen's kappa 低于 0.4，这批过程标注不应该被用来训 PRM，也不应该进报告——它测的是标注员的偏好，不是 agent 的质量。解法是收窄标注问题：不问「这一步好不好」，问「这一步是否让任务离目标更近」，后者的一致性通常高得多。

过程 vs 结果监督：一条关键结论

推理模型的研究里有一个已经被反复验证的结论值得搬过来：过程监督在「需要长链推理、且中间步骤可验证」的任务上显著优于结果监督，因为结果监督会把「过程全错但答案蒙对」的样本当作正例。在 agent 评测里，这个结论翻译成：

  • 用结果层做最终评判（它对齐真实效用），
  • 用过程层做归因与训练信号（它提供密集的、定位准确的反馈），
  • 永远不要用过程分代替结果分作为主指标——过程好但没做完，产品价值是 0。

6失败模式分类学：把「失败了」变成「因为什么失败」

一份只报成功率的评测，对改进工作的指导价值接近于零。把失败自动归类，是轨迹层最直接的产出。下面是一份可以直接复用的分类表，每一类都给出了可以从日志自动判定的判据。

失败类别自动判据（从 schema 直接算）该修什么
预算耗尽steps == max_steps 且未达终态先看是不是循环；不是循环则考虑提高预算或改进规划
循环冗余率 > 阈值，或状态摘要连续 $k$ 步不变上下文管理（C33）、加入「已试过什么」的显式记忆
工具误用同一工具连续多次 tool_error，错误码为参数类工具描述/schema 写得不清楚（C69 会讲这也是攻击面）
提前放弃步数远低于中位数且未达终态、无错误提示里的终止条件太宽松；常由「优化步数」这个目标诱发（第 7 节）
幻觉式完成宣称完成但终态检查失败，且无错误记录最危险的一类——需要强判分器与不可能任务（模块 01/02）
越权/副作用过程审计日志里出现任务无关的写操作权限边界（交给 C69）
真·能力不足以上都不是：动作合法、无循环、预算充足，就是没做对这才是真正需要更强模型的部分

这张表最重要的价值在最后一行：在把失败归因为「模型不够强」之前，先把前六类排除掉。真实项目里，前六类经常占到失败总量的一半以上——而它们全部是 harness、提示、工具描述、上下文管理的问题，换更强的模型解决不了。

分类要做成互斥且有优先级的（自上而下第一个命中即分类），否则一次失败会同时落进三个桶，比例加起来超过 100%，报告就没法读了。

7轨迹指标的 Goodhart 陷阱：优化步数会教会 agent 提前放弃

最后一节讲一个必须知道的失败案例，它几乎发生在每一个开始用轨迹指标做优化目标的团队身上。

目标：把平均步数从 24 降到 12（"让 agent 更高效"） │ ├─ agent 学到的合规解法：更好的规划、更少的冗余调用 ✔ 我们想要的 │ └─ agent 学到的更省力解法：**遇到难题早点放弃** ✘ 我们不想要的 │ └─ 平均步数 ↓↓ 成功率 ↓ 而"平均步数"这个指标看起来非常漂亮

原因很简单：失败的轨迹通常更短（agent 早早宣布做不了），所以「降低平均步数」的最容易的路径是增加失败率。任何在全部轨迹上计算的效率指标，都有这个方向的病理解。

三条修正规则

  1. 效率指标只在成功轨迹上计算：报「成功任务的中位步数」而不是「全部任务的平均步数」。这一条消掉了「靠失败变快」的路径。
  2. 成本永远与成功率成对出现：单独的成本数字没有意义，正确的报告形式是成本-成功率的前沿曲线（05 模块的主题）。
  3. 把提前放弃单列为一个失败类别并单独监控（第 6 节的表里已经有了）。只要这个比例在上升，效率的改善就是假的。

直白说

把三条规则合成一句可以直接执行的规范：「平均步数」这个指标不应该出现在任何报告里。该出现的是「成功任务的中位步数 + P90」和「提前放弃率」。

严谨说

更一般的表述：当一个指标 $M$ 与主目标 $U$ 之间存在选择效应（$M$ 的取值依赖于 $U$ 的实现与否），在全样本上计算 $M$ 会引入碰撞偏倚（collider bias）。$\mathbb{E}[\text{steps}]$ 正是这种情况：条件于「成功」这个中间变量的分层统计$\mathbb{E}[\text{steps} \mid \text{success}]$ 才是无歧义的量。同样的道理适用于延迟、token 消耗、工具调用次数——所有效率类指标都要分层报告。

这个陷阱不只发生在「拿指标当训练目标」的时候。只要你把某个轨迹指标写进了周报并且团队开始盯着它，优化压力就已经存在了——人也会 Goodhart，不只是模型。所以规范应该在指标被引入的那一天就定好，而不是等到发现异常之后。

8多智能体与子 agent：轨迹从链变成树

当 agent 会派生子 agent（C34 的编排模式）时，轨迹不再是一条链，而是一棵树。前面七节的指标全部需要重新定义，否则会算出误导性的数字。

root agent ├─ step 0 plan ├─ subagent A ──┬─ step 0 search ← 子轨迹，有自己的步数/token/错误 │ ├─ step 1 read_file │ └─ (返回摘要，2400 token → 只有摘要进入 root 的上下文) ├─ step 1 分析 A 的摘要 ├─ subagent B ──┬─ step 0 run_tests │ └─ step 1 patch └─ step 2 汇总并结束 ✗ 错误算法：只统计 root 的 3 步 → 严重低估成本 ✓ 正确算法：树的**全部节点**求和 = 真实成本；root 深度 = 真实"决策链长度"
指标链式定义树形下的正确定义算错的后果
成本所有步骤 token 之和整棵树所有节点的 token 之和只算 root 会低估几倍——子 agent 才是 token 大头
步数轨迹长度拆成两个数：root 决策链长度与总节点数混成一个数会让「派生一个干了 40 步的子 agent」看起来只花了 1 步
恢复率错误后是否换策略分层：子 agent 内部的恢复 vs root 对「子 agent 失败」的恢复后者才是编排质量的真正指标
冗余率重复的 (tool, args)跨子 agent的重复调用也要算多个子 agent 各查一遍同样的东西，是多智能体最典型的浪费
失败归因七分类先定位是哪个节点失败，再对该节点做七分类把子 agent 的工具误用记成 root 的能力不足

多智能体轨迹里有一个特有的失败模式，链式结构下不存在：信息在层级之间被压缩丢失。子 agent 读了 2400 token 的内容，只把一句摘要返回给 root——如果摘要漏掉了关键细节，root 会在看起来信息充分的情况下做出错误决策，而日志里每一步都是「成功」。检测手段：给每次子 agent 返回记录「输入 token / 输出 token」的压缩比，并把压缩比异常高的节点单独标记出来复核。

一条容易被忽略的编排质量指标：派生决策的正确率

多智能体系统里，root agent 做的最重要的一类决策不是「下一步调什么工具」，而是「这件事要不要派给子 agent 去做」。这个决策做错有两个方向，代价完全不同：过度派生——把一个两步就能做完的事包装成一个子 agent，多付一整份上下文的钱，还多了一次信息压缩的机会；派生不足——把一个需要 40 步探索的子任务塞进 root 的主线，把 root 的上下文撑爆，后面的决策全部在被污染的上下文里做出（呼应 C33）。把这两类分别统计出来，比任何总成本数字都更能说明编排设计得好不好：过度派生率高说明派生阈值定得太低，派生不足率高说明 root 没有识别出子任务的边界。

判定方式并不需要人工：过度派生 = 子 agent 的总步数 ≤ 2 且没有产生任何写操作；派生不足 = root 主线上出现了连续 $\ge k$ 步的同类探索动作（读文件、搜索）而未派生。两个判据都能从第 2 节的 schema 加上 parent_span_id 后直接算出来。

最后一条实践建议：树形轨迹的日志 schema 只需要在第 2 节的基础上加两个字段——parent_span_id 与 depth。有了它们，上面所有指标都能用一次树遍历算出来；没有它们，你只能得到一堆无法拼回原结构的扁平记录。这正是「schema 是事前决定」这句话最贵的一次体现。
