1为什么 agent 评测不是「多轮版的静态基准」

静态基准（MMLU、GSM8K、HumanEval）的评测循环短到可以画在一行里：prompt → 一次生成 → 比对答案 → 得分。把同一套工具搬到 agent 上会立刻失效，原因不是「步数变多了」这么简单——是评测对象的数学结构变了：从「一次采样的正确率」变成了「一条在有状态环境里展开的轨迹的成败」。

维度静态基准agentic 基准带来的评测后果
交互结构单轮，模型输出即终点多步，且每一步的输入依赖上一步的输出误差会沿轨迹放大：第 3 步的一个小偏差可能让后面 20 步全部作废
环境无状态，题目是纯文本有状态：文件系统、数据库、浏览器 DOM、容器同一个 prompt 跑两次可能得到不同结果，环境本身成了方差源
判分字符串/选项匹配，确定性执行结果、最终状态、rubric、LLM judge 混用判分器自己会犯错，必须先评测判分器（见 02 模块与 C67）
成本每题一次前向，成本近似常数每题几千到几十万 token，且方差极大不报成本的成功率数字是不可比的（见 05 模块）
scaffold 依赖几乎无——prompt 模板影响有限harness/scaffold 的影响常常大于模型本身的差异「模型 A 比模型 B 强」这句话在 agent 评测里必须附上 harness 版本才成立
失败模式答错了就是答错了超时、死循环、工具报错未恢复、越权、提前放弃只报一个成功率会把这些完全不同的失败混成一个数字

直白说

直白地说：静态基准像一道选择题——给题目、收答案、对答案，三步结束。agentic 基准像一场开卷实操考试——给你一台电脑和一个任务，你可以自己查资料、自己改文件、自己跑测试，考官最后看的是你把这台电脑折腾成了什么样。问题在于：同一个人做两次，桌面状态、网络快慢、工具报不报错都不一样，所以「他做对了」这句话本身就带着不小的随机性。

严谨说

更严谨地说，静态基准评测的是条件分布 $P(y \mid x)$ 上的一个期望；agentic 基准评测的是部分可观测马尔可夫决策过程（POMDP）里策略 $\pi_\theta$ 的期望回报 $\mathbb{E}_{\tau \sim \pi_\theta, \mathcal{E}}[R(\tau)]$，其中期望同时对策略的采样随机性和环境 $\mathcal{E}$ 的随机性取。这意味着：(a) 方差有两个独立来源，(b) 环境版本变化等价于换了一个被评测的分布，历史分数不可直接比较，(c) 回报 $R$ 本身是设计出来的，判分函数的设计误差直接进入被测量的量。

一个具体到可以直接引用的例子：SWE-bench 的原始版本里有相当比例的任务本身不可解——issue 描述里缺少复现所必需的信息，或者对应的隐藏测试用例检查了 issue 里根本没提到的行为。这直接催生了 SWE-bench Verified（由人工标注员逐条筛出可解子集）。这件事的教训不是「SWE-bench 不好」，而是：agentic 基准的任务集本身就是一个需要被评测的对象，在静态基准里几乎不会出现这种问题。

2三层评测对象：结果 / 轨迹 / 过程

整门课的组织骨架是一句话：一个 agent 可以在三个不同的层面上被评测，三层各自回答不同的问题，任何只做一层的评测报告都是残缺的。

┌──────────────────────────────────────────────────────────┐ │ 第三层 · 过程 process 「每一步做得对不对？」 │ │ 步骤级 rubric / 过程奖励 / 关键动作检查点 │ │ → 03 模块。粒度最细，标注最贵，最能定位失败根因 │ ├──────────────────────────────────────────────────────────┤ │ 第二层 · 轨迹 trajectory 「它是怎么做到（或没做到）的？」│ │ 工具调用序列 / 冗余步数 / 无效动作率 / 错误恢复率 │ │ → 03 模块。能解释「为什么两个同样 40% 的 agent 完全不同」 │ ├──────────────────────────────────────────────────────────┤ │ 第一层 · 结果 outcome 「任务到底完成了没有？」 │ │ 测试通过 / 最终状态匹配 / rubric checkpoint 达成率 │ │ → 02 模块。最便宜、最客观，但信息量最低 │ └──────────────────────────────────────────────────────────┘ 成本 ↑ 可解释性 ↑ 主观性 ↑ 往上走
层典型指标判分成本能回答的问题不能回答的问题
结果 outcomeresolve rate / pass@1 / 最终状态匹配率低（可自动化）这个 agent 能不能完成这类任务它是靠什么完成的、失败时卡在哪
轨迹 trajectory平均步数、无效动作率、恢复率、工具调用精确率中（需要日志 schema + 分析脚本）两个成功率相同的 agent 差在哪、成本从哪来某一步的决策在专家看来是否合理
过程 process步骤级 rubric 得分、关键检查点命中率高（需要人工或强 judge 逐步标注）失败根因、局部能力缺口（如「不会读报错」）在真实分布上的整体成功率

直白说

为什么三层缺一不可？举个具体场景：两个 agent 在同一批任务上都拿到 40% 的成功率。第一个平均花 8 步、很少走弯路，失败时是「真的不会」；第二个平均花 47 步、反复试错撞对答案，成本是前者的六倍，而且一旦任务稍难就彻底崩掉。只看结果层，这两个 agent 完全一样；加上轨迹层，它们是两种完全不同的产品。

严谨说

从测量的角度：结果层给出的是一个伯努利变量的期望估计，信息量上界是 1 bit/任务；轨迹层把同一次 rollout 的其余观测量（动作序列长度、动作类型分布、失败-恢复事件）也纳入统计，在任务数固定的前提下显著提高了单位样本的信息量——这正是「任务集很贵，所以要从每条轨迹里榨出更多信息」这一工程现实的直接推论。过程层则进一步把信用分配（credit assignment）做到步骤粒度，代价是引入了标注者主观性，因此它自己也需要一致性检验（呼应 C10 的标注科学）。

记住这条分工：结果层用来做决策（发不发布、选哪个模型），轨迹层用来做归因（钱花在哪、为什么慢），过程层用来做改进（下一步该修什么）。把三者混在一张表里报告，往往意味着三个问题一个都没答清楚。

3一次 agent 评测的七个决策点

本课把「做一次 agent 评测」拆成七个必须显式做出的决策。这七个点也正好是 01–05 模块的路线图——每一个决策做错，后面所有数字都会失去意义。

  1. 任务集从哪来：用公开基准还是自建任务集？公开基准要面对污染与任务质量问题，自建要面对样本量与代表性问题。→ 01 模块
  2. 判分函数怎么定义：执行测试、最终状态匹配、rubric checkpoint 还是 LLM judge？判分器的假阳性率是多少？→ 02 模块
  3. 部分得分给不给：全有全无（binary）还是分档？部分得分会改变模型排序吗？→ 02 模块
  4. 轨迹指标记哪些：日志 schema 决定了事后能算什么。没记的东西事后补不回来。→ 03 模块
  5. 跑几次、跑几个 seed：pass@k 还是 pass^k？两个 agent 差 3 个点算不算真的差？→ 04 模块
  6. 成本怎么归一化：给 A 无限预算、给 B 有限预算的对比是无意义的。→ 05 模块
  7. harness 怎么固定与报告：scaffold 版本、工具集、超时、重试策略、容器镜像。→ 05 模块

这七点里最容易被跳过、后果最严重的是第 7 条。同一个模型换一套 scaffold，SWE-bench 分数可以差出十几个百分点——这个幅度远大于多数模型版本之间的真实差距。所以「模型 A 在 SWE-bench 上得 X 分」这句话如果不附带 harness 描述，严格来说是无法被复现、也无法被比较的。

5环境、依赖与本课的运行约定

本课全程 CPU、断网可跑、不需要任何 API key。这一点需要解释，因为「agent 评测」听起来天然需要真实模型和真实环境。本课的处理方式是把两件事分开：

  • 评测的数学与工程（判分函数、部分得分、轨迹指标、pass^k、自举置信区间、成本-成功率前沿、harness 方差分解）——这些全部是确定性的计算，用 numpy 加一个模拟 agent 就能完整复现，而且比真实实验更适合学习：你可以人为控制真值，验证你的估计量是不是无偏的。
  • 真实基准的接入——每个模块末尾的「🧪 真实工程胶囊」给出可以原样复制到有网环境里跑的代码（SWE-bench 的加载与提交格式、inspect-ai 的 task 定义、容器化 harness 的启动脚本），但不作为课内练习的前置依赖。

依赖只有 numpy 与 matplotlib（可选，只用于画前沿曲线），其余全是标准库。所有练习都有 assert 判分，跑通即通过。

pip install numpy matplotlib jupyterlab ipykernel
jupyter lab      # 或直接在 Colab 里点每个 notebook 顶部的徽章

本课的模拟 agent 全部使用固定 seed 的 numpy.random.Generator，所有 assert 的期望值都是在这些 seed 下算出来的。如果你改了 seed 又发现自测不过，那是预期行为——但请顺手想一下：一个换个 seed 就变的结论，本身就说明样本量不够，这正是 04 模块的主题。
