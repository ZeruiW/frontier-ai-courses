1一个 agent 分数的方差从哪来：四个来源与它们的层级

模块 00 说过 agentic 评测有两个随机源。现在把它拆细——实际有四个，而且它们处在不同的层级，这决定了压方差的手段完全不同。

┌─ ① 任务间方差 σ²_between ────────────────────────────────────┐ │ 不同任务的难度不同。这是**最大**的方差来源，常占一半以上。 │ │ 压制手段：**配对设计**（同一批任务比较两个 agent） │ ├─ ② 任务内方差 σ²_within ─────────────────────────────────────┤ │ 同一任务重复跑，结果时对时错。来自采样温度 + 环境随机性。 │ │ 压制手段：**每个任务多跑几次**（k 次重复） │ ├─ ③ 用户/环境模拟器方差 ──────────────────────────────────────┤ │ 模拟用户是另一个 LLM；页面加载时序、外部 API 抖动。 │ │ 压制手段：钉死模拟器模型与温度；录制回放 │ └─ ④ harness / 基础设施方差 ───────────────────────────────────┘ 超时阈值、并发度、重试策略、容器调度。**换个并发度分数就变**。 压制手段：钉死配置并写进报告（05 模块）

四者中，只有 ① 和 ② 能用统计手段处理，③ 和 ④ 必须靠工程手段消除——它们不是随机误差，是没被控制住的自变量。

\[\operatorname{Var}(\bar{X}) = \frac{\sigma^2_{\text{between}}}{N} + \frac{\sigma^2_{\text{within}}}{N k}\]

其中 $N$ 是任务数、$k$ 是每个任务的重复次数。这个式子有一个非常实用的推论：

加重复次数 $k$ 的收益有天花板，加任务数 $N$ 的收益没有。把 $k$ 从 1 加到无穷，方差最多降到 $\sigma^2_{\text{between}}/N$——换算成标准差，最多只能压到 $k=1$ 时的 $\sqrt{\rho}$ 倍（$\rho$ 是组内相关系数，见第 4 节）。agent 评测的 $\rho$ 常在 0.4–0.8，也就是说把重复次数加到无穷，标准差最多只降三到四成。反过来，$N$ 翻倍两项一起减半。所以「先扩任务集，再加重复」几乎总是对的——除非你的目标是 pass^k 这种本身就定义在重复上的指标。

直白说

但是——这里有个真实的成本约束把上面这条建议部分推翻了：agentic 任务的边际成本极高。加一道任务要写环境、写判分器、做人工审核；加一次重复只要多花一次 API 调用。所以现实里的最优解通常是「任务数被预算卡死在 $N$，然后在剩下的钱里选 $k$」。notebook 第 3 节会把这个取舍算成一道最优化题。

严谨说

形式化：在预算约束 $N c_{\text{task}} + N k c_{\text{run}} \le B$ 下最小化 $\frac{\sigma^2_b}{N} + \frac{\sigma^2_w}{Nk}$，可以解出最优重复次数 $k^{*} = \sqrt{\dfrac{\sigma^2_w}{\sigma^2_b} \cdot \dfrac{c_{\text{task}}}{c_{\text{run}}}}$。这是经典的整群抽样最优分配公式：任务越贵（$c_{\text{task}}$ 大）、任务内噪声越大（$\sigma^2_w$ 大），就越该在每个任务上多跑几次。它同时解释了为什么 SWE-bench 类基准（任务极贵）值得多跑几个 epoch，而合成任务集（任务几乎免费）应该直接扩任务数。

2pass@k 与 pass^k：两个指标，两种产品

这是本模块最需要被记住的一节。两个符号只差一个位置，含义完全相反。

指标问的问题公式（$n$ 次采样中成功 $c$ 次的无偏估计）适用场景
pass@k试 $k$ 次，至少成功一次的概率$1 - \dfrac{\binom{n-c}{k}}{\binom{n}{k}}$结果有人复核或有验证器：代码补全、候选生成、best-of-n
pass^k试 $k$ 次，全部成功的概率$\dfrac{\binom{c}{k}}{\binom{n}{k}}$结果直接执行、没人复核：自动退款、自动改配置、自动发邮件

为什么必须用无偏估计器而不是「跑 $k$ 次数一数」？因为后者只用了一次实验的信息，方差极大。无偏估计器的思路是：跑 $n \gg k$ 次，然后计算「从这 $n$ 次里随机抽 $k$ 次会发生什么」的期望，这等价于对 $\binom{n}{k}$ 种抽法求平均，方差大幅降低。

单任务成功率 p = 0.7 时： k: 1 2 3 5 8 pass@k 0.700 0.910 0.973 0.998 1.000 ← 随 k 单调**上升**，很快饱和到 1 pass^k 0.700 0.490 0.343 0.168 0.058 ← 随 k 单调**下降**，指数衰减 同一个 agent，报 pass@8 是"接近完美"，报 pass^8 是"基本不可用"。 两个数字都没撒谎——它们回答的是两个不同的产品问题。
用错指标是 agent 评测里最常见、也最有实际后果的错误。一个客服 agent 的 pass@8 有 99%，听起来可以上线；但它每次处理一个真实工单只有一次机会，没人会帮它挑八个候选里最好的那个——真正决定产品体验的是 pass^1（即单次成功率）和它在重复运行下的稳定性。判断标准只有一条：结果被执行之前，有没有人（或验证器）能挑一挑？有 → pass@k；没有 → pass^k。

pass^k 的另一层含义：它在测「一致性」而不只是「能力」

如果一个 agent 的行为完全确定（同一输入永远同一输出），那么 $\text{pass}^k = \text{pass}^1$ 对所有 $k$ 成立——曲线是水平的。pass^k 随 $k$ 下降得越快，说明这个 agent 的行为越不稳定。所以 $\text{pass}^1 - \text{pass}^k$ 这个差值本身就是一个有用的不一致性指标，它把「能力」和「可靠性」分开了：能力决定曲线的起点，可靠性决定曲线的斜率。

3配对设计：把最大的方差源直接消掉

回到第 1 节的结论：任务间方差占大头。配对设计的全部思想就是不去估计它。

直白说

独立设计问的是「A 的平均分是多少？B 的平均分是多少？两者差多少？」——这里面「任务有难有易」的波动被算了两遍。配对设计问的是「在同一道题上，A 和 B 谁赢？」——题目难度对两者是同一个数，做差的时候直接消掉了。

严谨说

形式化：设任务 $i$ 上 A 与 B 的得分为 $X_i, Y_i$，差值 $D_i = X_i - Y_i$。则 $\operatorname{Var}(D_i) = \operatorname{Var}(X_i) + \operatorname{Var}(Y_i) - 2\operatorname{Cov}(X_i, Y_i)$。由于两个 agent 在同一批任务上的得分高度正相关（难题对谁都难），$\operatorname{Cov}$ 项很大，$\operatorname{Var}(D_i)$ 远小于 $\operatorname{Var}(X_i) + \operatorname{Var}(Y_i)$。在二值结果的情形下，这直接退化为 McNemar 检验：只有「一个对一个错」的不一致对携带信息，一致对（都对/都错）对差值的检验完全无贡献。

\[\chi^2_{\text{McNemar}} = \frac{(|b - c| - 1)^2}{b + c}, \quad b, c \text{ 是两类不一致对的计数}\]
设计需要的任务数（区分 3 个点）前提条件什么时候不能用
独立设计每组约 4000+无—
配对设计约 1500–2000（不一致率 20% 时）两个 agent 必须跑同一批任务、同一套 harness任务集在两次运行之间变过；harness 版本变过
配对 + 多次重复更少（用任务内均值代替 0/1，进一步降方差）同上 + 记录了 attempt 字段预算不允许

配对设计有一个必须遵守的纪律：两个 agent 的运行必须在同一次评测运行里完成，或者至少共享完全相同的环境快照。如果你今天跑 A、下周跑 B，中间容器镜像更新过、外部 API 改过、任务集补过题，那么这就不是配对设计——你以为消掉了任务难度，实际上引入了一个更大的时间混杂因素。

4置信区间：把 $Nk$ 次 rollout 当独立样本是错的

一个极其常见的错误：跑了 500 道任务 × 每题 5 次 = 2500 条轨迹，然后按 $n = 2500$ 算置信区间。这会把区间宽度低估到只有真实值的一半左右。

原因是同一任务的 5 次重复不独立——它们共享同一个任务难度。统计学上这叫整群结构（clustered data），有效样本量不是 $Nk$，而是

\[n_{\text{eff}} = \frac{Nk}{1 + (k-1)\rho}\]

其中 $\rho$ 是组内相关系数（intra-cluster correlation）。在 agent 评测里 $\rho$ 通常很高（0.4–0.8），因为任务难度主导一切。取 $\rho = 0.7$、$k = 5$：$n_{\text{eff}} = 2500 / (1 + 4 \times 0.7) = 658$——不到名义样本量的三成。

正确做法：按任务重采样的聚类自举

# 错误：把每条轨迹当独立样本
boot = rng.choice(all_2500_rollouts, size=2500)          # ✗ 区间会窄一半

# 正确：重采样「任务」，每个被抽中的任务连同它的全部 k 次重复一起进来
task_ids = rng.choice(unique_tasks, size=N, replace=True) # ✓
boot = concat(rollouts_of(t) for t in task_ids)

记忆口诀：自举要重采样「最外层的独立单位」。在 agent 评测里，独立单位是任务，不是 rollout，也不是步骤。同理，如果你的任务集里同一个仓库贡献了 30 道题，严格来说独立单位是仓库而不是任务——这会让区间进一步变宽。要不要做到这一层，取决于你的结论是想推广到「这些任务」还是「这类仓库」。

notebook 第 4 节会用模拟验证这件事：构造一个已知真值的场景，分别用朴素自举和聚类自举算 95% 区间，统计覆盖率（真值落在区间内的比例）。朴素自举的覆盖率会显著低于 95%——这是评测报告里「误差棒画得太窄」的直接来源。

5功效分析：要跑多少才够，以及预算该怎么切

把前四节合起来，就能回答那个每次都会被问到的问题：「我要跑多少才够？」

三个必须先回答的前置问题

  1. 你要检测多大的差异？（最小实际重要差异 MDE）「任何差异都想检测」等价于「需要无穷样本」。先想清楚：差 1 个点会改变你的决策吗？如果不会，就别把它设成 MDE。
  2. 你能接受多大的误报率（Type I）与漏报率（Type II）？注意这里的 $\alpha$ 是显著性水平，与模块 02 里判分器的假阳率 $\alpha$ 是两个不同的量。研究场景常用 $\alpha = 0.05, \text{power} = 0.8$；但 CI 门禁场景（C68-04）应该用完全不同的取值——误报会让整个团队开始忽略告警，所以 $\alpha$ 要设得很低。
  3. 你的预算是多少？如果算出来需要 4000 道任务而你只有 500 道，正确的反应不是「凑合跑」，而是改变结论的形式：从「A 比 B 强」改成「在 500 道任务上没有观察到显著差异，检测下限是 8 个点」。

第 3 条值得特别强调，因为它是这门课里最容易被跳过、也最影响诚信的一步。「没有观察到显著差异」和「两者相同」不是一回事。一份负责任的报告必须给出检测下限：「本次评测能以 80% 的功效检出 ≥8 个百分点的差异；实测差异 3 个点，不显著」——这句话既诚实又有信息量，而「A 和 B 差不多」这句话两样都不是。

场景$\sigma^2_w / \sigma^2_b$任务边际成本推荐 $k$理由

6排行榜上的胜者诅咒：为什么第一名的分数总是虚高

最后一个统计陷阱，它解释了一个反复出现的现象：榜单第一名的成绩，在独立复现时往往会掉几个点。这不需要任何人作弊就会发生。

直白说

机制很简单：如果 20 个模型的真实能力都差不多，那么榜首那个只是运气最好的那个——它的观测分数 = 真实能力 + 一个恰好为正的噪声。换一批任务重跑，噪声重新掷骰子，它就掉下来了。「取最大值」这个操作本身就是有偏的。

严谨说

形式化：设 $\hat{\theta}_i = \theta_i + \varepsilon_i$，$\varepsilon_i \sim \mathcal{N}(0, \sigma^2)$。则 $\mathbb{E}[\max_i \hat{\theta}_i] > \max_i \theta_i$，且当所有 $\theta_i$ 相等时，偏差的量级是 $\mathcal{O}(\sigma \sqrt{2 \ln m})$（$m$ 为参赛者数量），其中 $\sigma\sqrt{2\ln m}$ 是一个上界，$m$ 不大时实际值明显更小。$m = 20$、$\sigma = 2$ 个点时 $\mathbb{E}[\max_i \varepsilon_i] \approx 1.87\sigma$，榜首的期望虚高约 3.7 个点（上界给出 4.9）——这个量级完全足以解释「排行榜前几名挤在几个点内」的现象，也解释了为什么复现时会系统性地掉分。

缓解手段怎么做代价
报置信区间而不是点估计榜单每一行都带误差棒；重叠的名次视为并列榜单不再有唯一的第一名（这是好事）
留出集榜单用公开集排名，最终结论用从未被优化过的留出集复核需要额外维护一套任务
收缩估计把各模型的分数向总体均值收缩（James–Stein / 经验贝叶斯）单个模型的分数不再是「它自己的成绩」
多重比较校正比较 $m$ 个模型时对 $\alpha$ 做 Bonferroni/BH 校正更保守，可能漏掉真实差异

对读榜单的人，一条极其实用的经验法则：看排名前，先看误差棒宽度和任务数。500 道任务的基准，95% 区间大约是 ±4 个点——这意味着榜单上相差 4 个点以内的名次，本质上是并列。把它们读成「A 优于 B」是过度解读。

7报告规范：一行不误导人的结果长什么样

把本模块的全部内容压缩成一个可以照抄的模板：

resolve_rate (pass^1, micro):  34.2%  [30.1%, 38.4%]   N=500 tasks × k=5 attempts
  ├─ 置信区间方法:              按任务聚类自举, 2000 次重采样
  ├─ 有效样本量 n_eff:          658  (ρ=0.70, 名义 2500)
  ├─ pass@5:                    58.1%     ← 有验证器/人复核时才看这个
  ├─ pass^5:                    12.7%     ← 直接执行、无复核时看这个
  └─ 最小可检测差异 (MDE):      8.1 个百分点 (α=0.05, power=0.8, 配对设计)

vs baseline (配对):             +3.1 个百分点  [-1.2, +7.5]   McNemar p = 0.14
  └─ 结论: 未观察到显著差异；本次评测的检测下限是 8.1 个点，
           实测差异 3.1 点落在检测能力之下——**不能得出「A 更强」的结论**。
  • 指标名要写全：pass^1 而不是「成功率」，micro 而不是「平均」——模块 02 已经证明了这些词各自对应不同的数字。
  • $N$ 和 $k$ 必须分开写：写成「2500 次运行」是在误导读者，因为它们不是 2500 个独立样本。
  • MDE 必须出现：没有 MDE 的「不显著」是没有信息量的。
  • 置信区间的计算方法必须写明：朴素自举和聚类自举给出的区间可以差一倍。

最后一条容易被忽略的提醒：本模块所有的统计工具，都建立在「判分器是准确的」这个前提上。如果判分器有 5% 的假阳率（模块 02），那么再漂亮的置信区间也只是「对一个有偏的量的精确估计」。顺序永远是：先量 bias，再压 var，最后写区间。

8序贯评测：跑到一半能不能停

agentic 评测很贵，所以一个很自然的想法是：边跑边看，差距明显了就提前停。这个想法是对的，但朴素地执行会让误报率暴涨——它是评测里最常见的统计错误之一。

为什么「边跑边看」会作弊

如果你每跑 50 道题就看一次 $p$ 值，一旦 $p < 0.05$ 就停下来宣布显著，那么即使两个 agent 完全相同，你也迟早会碰到一次 $p < 0.05$。检查 10 次的话，实际误报率会从 5% 涨到 20% 以上——这叫窥视问题（peeking / optional stopping）。

这个错误在 agent 评测里特别容易犯，因为评测是逐任务流式产出结果的，人天然会在跑的过程中盯着看。「跑到 300 题的时候看起来 A 明显更好，我们就停了」——这句话描述的是一次无效的实验。

三种正确做法

方法怎么做适用场景代价
固定样本量事先按 MDE 算出 $N$，跑完再看最简单、最不容易出错，默认选它不能提前停，跑满才有结论
alpha spending把总的 $\alpha=0.05$ 按检查次数分配（如 O'Brien–Fleming 边界：早期极严、后期放宽）评测很贵、希望有机会早停需要事先声明检查时点与边界
始终有效的推断用序贯置信序列（anytime-valid CI），它在任何时刻都成立持续监控型评测（C68 的线上门禁）区间比固定样本量的宽（这是随时可看的代价）

三者的共同点是：「什么时候可以停」这件事必须在开始之前就定好，而不是看着数据决定。这一条纪律，和模块 05 的「harness 要事先钉死」是同一种性质的要求——都是在防止一个自由度被事后利用。

直白说

反过来说，有一种「提前停」是完全合法的，而且应该多用：停掉那些明显没救的单条轨迹（模块 03 的循环检测）。这不是统计上的提前停止——它不改变任务的判定结果，只是省下了本来也要浪费的预算，然后把这些预算投到别的任务上。省下的钱直接变成更大的 $N$，这是纯赚。

严谨说

区别在于停止规则作用的层级：序贯检验的停止规则作用在推断层面（决定何时下结论），因此会影响第一类错误率；循环检测的停止规则作用在单个样本的生成过程上，只要它与该样本的最终标签独立（检出循环的轨迹本来就会失败），就不引入偏倚。但这个「独立」必须被验证——如果你的循环检测器偶尔会误杀本来能成功的轨迹，它就变成了一个有偏的截断，此时被终止的轨迹必须单独统计而不能简单记成失败。
