2代码仓库类：SWE-bench 家族的三个数字

SWE-bench 是目前影响力最大的 agentic 基准，也是最值得逐层拆开看的一个——因为它把「一个好的 agentic 基准应该长什么样」和「一个 agentic 基准会踩哪些坑」同时演示了一遍。

任务是怎么构造出来的

  1. 从 12 个流行的 Python 开源仓库里，抓取已合并的 PR；
  2. 只保留「解决了某个 issue」且「修改了测试文件」的 PR——后者是关键：有测试改动，才有自动判分的可能；
  3. 把 PR 拆成两半：issue 文本（给 agent 看）与 补丁 + 测试（用来判分，对 agent 隐藏）；
  4. 把仓库回滚到 PR 的父提交，记录下 FAIL_TO_PASS（打上补丁前失败、之后通过的测试）与 PASS_TO_PASS（前后都必须通过的测试）。

于是判分函数变成了一段完全确定性的代码：把 agent 产出的 patch 打进容器，跑这两组测试，全绿才算 1 分。原始版本有 2294 条任务实例。

直白说

为什么 PASS_TO_PASS 这么重要？因为没有它的话，「把整个文件删掉再重写一个只让目标测试通过的版本」也能拿分。PASS_TO_PASS 是防回归的那道闸门——它对应模块 00 里「修一个好位置会引入回归」的那个设计。任何自建的代码类任务集，如果只检查目标行为、不检查既有行为，判分器就是有洞的。

严谨说

从测量的角度，$\text{FAIL\_TO\_PASS}$ 度量的是功能达成，$\text{PASS\_TO\_PASS}$ 度量的是副作用约束。只有前者的判分函数在数学上是一个不完全的规格（under-specified specification），它允许存在大量「通过判分但语义错误」的解——这正是 reward hacking 的入口（C67 模块 05 会从奖励模型的角度重讲这件事）。

三个数字：2294 / 500 / 300

版本规模怎么来的该在什么时候用
SWE-bench（full）2294自动化流水线产出，未经人工逐条审核研究覆盖面时用；报告主分数时已基本被 Verified 取代
SWE-bench Verified500由专业开发者逐条审核，剔除「issue 描述不足以复现」「测试检查了 issue 没提到的行为」等不可解或误判任务报告主分数的默认选择
SWE-bench Lite300按自动化规则筛出的轻量子集，跑得快、成本低开发迭代期的快速回归（呼应 C68 的 CI 门禁）
Verified 的存在本身就是本模块最重要的一课。它说明：一个被广泛引用、被写进无数技术报告的基准，在发布近一年后，被发现有相当比例的任务根本无法被正确完成——不是模型不行，是题目有问题。推论很直接：你自建的任务集，如果没有经过「人类专家能不能做出来」这一关，默认就应该假设它含有可观比例的坏题。

家族的其余成员

  • SWE-bench Multimodal：换成 JavaScript 仓库、且 issue 里带截图/录屏，考察「看得懂界面问题」的能力——判分方式不变，仍然是跑测试。
  • SWE-bench Multilingual：把语言从 Python 扩展到多种语言，用来检验「在 Python 上的成绩有多少来自对 Python 生态的记忆」。
  • 持续更新型变体（如 SWE-bench-Live 一类的做法）：只收录模型训练截止之后新产生的 PR，定期滚动。这是对付污染的结构性解法，代价是每次滚动后分数不可与历史直接比较。
  • Terminal-Bench 一类：把环境从「仓库」放宽到「一台终端」，任务包含环境配置、数据处理、系统运维，判分同样靠测试脚本。
  • SWE-Lancer 一类：用真实自由职业任务与端到端测试判分，并附带「这个任务在市场上值多少钱」的价格标签——把成功率折算成经济价值，是 05 模块成本视角的一个极端版本。

3工具+对话类：τ-bench 与「终态匹配」判分

SWE-bench 的判分靠跑测试，那么客服型 agent（帮用户改机票、退货、查订单）怎么判分？τ-bench 给出的答案是：不看它说了什么，看它把数据库改成了什么样。

┌─────────────┐ 自然语言 ┌──────────────┐ 工具调用 ┌────────────┐ │ 用户模拟器 │ ◄──────────► │ 被测 agent │ ◄─────────► │ 领域数据库 │ │ (也是 LLM) │ │ │ (get/update)│ 订单/航班… │ └─────────────┘ └──────────────┘ └────────────┘ │ │ │ │ 用户目标(隐藏) │ 领域策略文档(可见) │ 终态 ▼ ▼ ▼ ┌────────────────────────────────────────────────────────────────────┐ │ 判分 = (数据库终态 == 标注的目标终态) AND (必答信息都对用户说了) │ └────────────────────────────────────────────────────────────────────┘
设计选择怎么做的为什么这么做副作用
用户是模拟的用一个 LLM 扮演用户，只知道自己的目标，不知道系统内部规则真实客服场景里信息是挤牙膏式给出的，一次性把需求说全不真实模拟器的随机性直接进入评测方差；模拟器换模型 = 换了基准
判分看终态对比数据库最终状态与人工标注的目标状态绕开了「同一件事有很多种说法」的自然语言判分难题只对有写操作的任务有效；纯咨询类任务需要额外的信息检查项
有领域策略文档给 agent 一份「什么情况下才允许退款」之类的规则文档考察规则遵循而不只是任务完成策略文档写得越细，越考「长文本里找规则」而非 agent 能力
强调多次运行同一任务重复 $k$ 次，报告 pass^k（k 次全对的比例）客服 agent 的商业价值取决于可靠性而非峰值能力评测成本乘 $k$；04 模块专门讲这个指标
pass^k 是 τ-bench 留给整个领域的最重要遗产。pass@k 问的是「试 $k$ 次至少成一次的概率」，适合可以人工挑选结果的场景（比如代码补全）；pass^k 问的是「连续 $k$ 次都成功的概率」，适合没人复核就直接执行的场景（比如自动退款）。把一个客服 agent 的 pass@8 拿去汇报，等于在汇报一个和产品价值无关的数字。

τ²-bench 一类的后续工作把设定进一步推向双向控制：用户不再只是提供信息，而是也能操作环境（比如「你去重启一下路由器」），agent 必须指挥用户完成部分动作。这带来了新的判分维度：指令的可执行性——说得对但用户听不懂照做不了，同样是失败。

4图形界面与网页类：程序化 validator 与环境漂移

WebArena 与 OSWorld 代表了另一条路线：不构造判分测试，而是给每一个任务手写一个校验函数。

基准环境规模判分方式关键设计
WebArena自建可复现的网站集群：购物、论坛、GitLab、CMS、地图，全部本地部署812 个任务每个任务一个程序化 validator：查数据库行、查 URL、查页面文本，或检查「不可能达成」时是否正确放弃自托管是全部关键——真实网站会变，本地快照才能复现
VisualWebArena同上但任务需要视觉理解（按图找商品、看图填表）910 个任务同上 + 图像相关的检查考察 VLM 的界面理解（呼应 C00）
OSWorld真实操作系统（Ubuntu/Windows）+ 真实应用（LibreOffice、GIMP、VS Code、浏览器）369 个任务每个任务一段执行式校验脚本：读文件内容、跑命令、查配置跨应用任务是难点：在 A 里查到的东西要填进 B
Mind2Web离线录制的真实网页轨迹2350 个任务元素级匹配：选对了 DOM 元素、动作类型对不对离线 = 完全可复现，但无法评测「走错了能不能回来」
WebVoyager 一类真实在线网站几百个任务用 VLM 看截图做 judge最真实，也最不可复现——同一个任务两周后跑，网站已经改版

直白说

离线、自托管、在线，三种取舍其实是同一个跷跷板：越真实越不可复现，越可复现越不真实。离线轨迹（Mind2Web）可以精确复现，但 agent 一旦偏离录好的路径就没法继续评了；自托管快照（WebArena）保住了交互性，代价是网站是「冻在某一天的样子」；在线真实网站最有说服力，但你今天的 45% 和三个月后的 45% 根本不是同一个实验。

严谨说

形式化地说，设 $\mathcal{E}_t$ 是 $t$ 时刻的环境。可复现性要求 $\mathcal{E}_{t_1} = \mathcal{E}_{t_2}$；生态效度（ecological validity）要求 $\mathcal{E}$ 与部署环境 $\mathcal{E}^{*}$ 同分布。在线基准满足后者而违反前者，离线基准反之。工程上的通行解法是「双轨」：自托管快照做回归门禁（要可复现），在线小样本做生态校验（要真实），两条线的数字分开报告、从不混算——这正是 C68 模块 05 里离线-在线双回路的雏形。

「不可能任务」是 WebArena 的一个被严重低估的设计。任务集里混入了一部分在该网站上根本无法完成的请求，正确行为是识别并明确放弃。没有这类任务的基准，会系统性奖励「编造一个看起来完成了的答复」的行为——而这恰恰是 agent 在真实产品里最危险的失败模式。自建任务集时，请务必留出 5%–15% 的不可能任务。

5开放网络与科研类：唯一答案与人类基线

最后两类基准解决的是同一个难题：当任务的产出不是「代码」也不是「数据库状态」，怎么客观判分？

GAIA：把开放问题设计成唯一短答案

GAIA 的做法是从判分倒推题目设计：只出那些答案唯一、简短、可以精确匹配的问题（一个数字、一个名字、一个短语），但通往这个答案的路径需要多步搜索、读文件、看图、算数。题目分三个难度级别（大致对应需要的步数与工具数），共几百道，并且发布时带着一个刺眼的对比：人类能做对九成以上，而当时最强的带插件模型只有一成多。

GAIA 的方法论可以直接拿去自建任务集：先问「我怎么自动判对错」，再据此设计题目形态，而不是先出一堆开放题再发愁怎么判分。「答案唯一且简短」是一条极强的约束，它换来的是判分器几乎零成本、零主观性。

BrowseComp 一类：难找但易验证

沿着 GAIA 的思路再推一步：刻意构造「答案极难找到、但一旦找到极易验证」的问题（把多个稀有约束叠加，使得答案在网上只有一处能拼出来）。这类基准的价值在于它专门测长程搜索的耐心，而不是知识量——模型记不住这些答案，只能真的去搜。

MLE-bench / RE-Bench 一类：用人类基线定分数

设计问题解法代价
机器学习任务没有「对/错」，只有分数高低拿真实竞赛的排行榜当标尺，把 agent 的成绩折算成奖牌等级（铜/银/金）需要竞赛级别的完整数据与评测集
不同任务的分数尺度完全不同统一转成「相对人类分布的百分位」再聚合百分位对分布尾部不敏感，接近上限时会失去区分度
单个任务要跑很久（数小时到数十 GPU 小时）限定墙钟时间预算，并把时间预算作为一个自变量报告评测成本极高，通常只能跑很少的 seed（04 模块的统计困境在这里最尖锐）

这一类基准还引出了一个正在成为主流的报告维度：「时间跨度」（time horizon）——不问「成功率多少」，而问「这个 agent 能以 50% 成功率完成的任务，人类专家要花多久」。它的好处是把不同难度的任务统一到一根有物理意义的轴上，坏处是需要为每个任务标注可靠的人类耗时。

6所有 agentic 基准的四种共同病灶

不管环境是什么，agentic 基准都会得同样四种病。识别它们，是读懂任何一份 agent 评测报告的前提。

病灶机制症状缓解手段
① 污染任务来自公开仓库/网页，早已进入训练语料；更隐蔽的是解法泄漏——issue 的评论区里就写着正确补丁小模型在某些任务上异常地好；模型能凭空说出仓库里的私有函数名时间截断（只用训练截止后的数据）· 持续滚动的 live 版本 · n-gram/嵌入重合检测 · 检查「不给 issue 只给文件名能不能做对」
② 任务不可解或判分过弱描述信息不足以复现；隐藏测试检查了描述里没提的行为；或者反过来，测试太弱，随手改改就能过人类专家做不到 100%；不同的正确解法拿到不同分数人工逐条审核（Verified 的做法）· 用多个强模型的解法做交叉验证 · 检查测试覆盖率
③ 环境漂移依赖版本、页面结构、外部 API 随时间变化同一份代码几个月后跑出不同分数；旧论文的数字复现不出来容器镜像 digest 钉死 · 网络录制回放 · 定期重跑历史基线做「环境健康检查」
④ 饱和与 harness 过拟合分数逼近上限后区分度消失；或者大家都在调 scaffold 而不是模型榜单前几名挤在 1–2 个点内；换个 harness 排名就翻转报告 harness 全量配置 · 引入更难的子集 · 用 pass^k 等更严格的指标拉开差距

关于污染有一个特别值得警惕的细节：代码类基准的「解法泄漏」不只发生在训练语料里，也可能发生在任务本身内部——如果 issue 的正文或评论里已经贴出了修复补丁，那么这道题测的是「读理解」而不是「解决问题」。自建任务集时，把 issue 的评论区、后续 commit message、PR 描述全部剥离，是一条必须写进流水线的清洗规则。

直白说

怎么快速判断一份 agent 评测报告值不值得信？看它有没有回答这四个问题：① 任务是什么时候产生的，模型训练截止是什么时候？② 任务集有没有人审过？③ 环境版本钉死了吗？④ harness 是什么、跑了几次？四个都没答的报告，读一下当参考即可，不要拿来做决策。

严谨说

这四个问题分别对应四类效度威胁：construct validity（污染让基准不再测量它声称测量的能力）、internal validity（坏题让分数与能力脱钩）、reliability（环境漂移让测量不可重复）、external validity（harness 过拟合让结论无法迁移到别的实现）。C10 用心理测量学的语言系统讲过这四类效度，本课只是把它们翻译到 agent 场景。

7什么时候必须自建任务集，以及怎么建

公开基准的价值是横向可比，但它几乎必然与你的真实场景有分布差距。以下三种情况必须自建：

  • 你的工具集是私有的——公开基准里没有你们的内部 API，agent 在上面的表现说明不了任何事；
  • 你要做回归门禁——你需要的是「上周能做对的今天还能不能做对」，公开基准的粒度太粗、跑得太慢（C68 模块 04）；
  • 公开基准已经饱和——所有候选模型都在 90% 以上，分数不再包含决策信息。

自建任务集的六条规则

  1. 先写判分函数，再写任务：判不了分的任务不要收。这条规则能挡掉八成的坏题。
  2. 每个任务都要有防回归检查项（对应 PASS_TO_PASS）：只查目标行为的判分器一定会被 hack。
  3. 混入不可能任务（5%–15%）：不这么做就是在奖励编造。
  4. 难度要有梯度：全是难题 = 全零，没有区分度；全是简单题 = 全满分，同样没有区分度。目标是让整体成功率落在 30%–70% 区间——这是信息量最大的位置（notebook 里会算给你看）。
  5. 任务要标注元数据：需要几个工具、预期几步、涉及哪个子系统、人类耗时。没有元数据就没法做切片分析，一个总分掩盖所有细节。
  6. 先让人做一遍：人类专家做不到 90% 以上的任务，八成是题有问题而不是难。

关于第 4 条的量化直觉：一道题如果所有被测 agent 都通过（或都失败），它对区分这些 agent 的贡献是 0 bit——它仍然可以用来验证「没有退化」，但对「A 和 B 谁更强」这个问题一无所知。把任务集的成功率推向 50% 附近，等价于把每道题的信息量推向最大（$H(p)$ 在 $p=0.5$ 取最大）。这是 C10 的 IRT 视角在 agent 任务集设计上的直接应用。

最后一条实践建议：任务集要版本化，并且永远不要「就地修改」。发现坏题时，正确做法是发布 v2 并同时保留 v1，而不是悄悄把 v1 里的题改掉——否则所有历史分数一夜之间失去意义。版本化的具体做法见 C68 模块 01。
