1不带成本的成功率是不可比的

先说结论：「agent A 在 SWE-bench Verified 上得 48%」这句话，在没有成本信息时是一个无法使用的数字。原因很直接——任何 agent 的成功率都可以通过多花钱提高。

花钱的方式怎么提高成功率成本增幅是否算「模型更强」
提高重试/采样次数跑 $n$ 次取最好的（需要验证器）线性 $\times n$❌ 这是 best-of-n，不是模型能力
放宽步数上限从 30 步放到 200 步近似线性❌ 换个预算数字就能复制
更长的上下文 / 更多检索把整个仓库塞进上下文token 成本可能涨十倍❌ 这是 scaffold 的选择
更强的 scaffold加反思、加子 agent、加验证步骤视实现而定，常 2–5 倍❌ 这是 harness 能力，不是模型能力
模型本身更强同样预算下做对更多不变✅ 只有这一行才是

所以「谁更强」这个问题在不固定预算的情况下没有定义。正确的提法只有两种：①「给定相同预算，谁的成功率更高」；②「达到相同成功率，谁的成本更低」。这两种提法都要求你把成本作为一等公民记录下来——而这正是绝大多数公开 agent 评测报告缺失的那一栏。

直白说

换个说法：报告一个不带成本的 agent 分数，等价于报告一辆车的最高时速却不说油耗。两辆车都能跑到 200 公里，一辆烧 8 升一辆烧 30 升——「都能跑到 200」这句话本身是真的，但用它做采购决策是荒谬的。

严谨说

形式化地说，agent 的能力不是一个标量，而是一条成本-效用曲线 $s(b)$：给定预算 $b$（token、时间、调用次数），可达到的期望成功率。报告单点 $s(b_0)$ 只在 $b_0$ 被明确写出时才有意义；比较两个 agent 等价于比较两条曲线，而两条曲线可以相交——低预算下 A 更好、高预算下 B 更好，是完全正常的情况。这也解释了为什么「哪个模型最强」这个问题在产品语境下经常没有答案，而「在我们的预算下哪个更合适」永远有答案。

2成本模型：四种成本与归一化

要把成本记进报告，先要定义什么叫成本。agent 评测里有四种，它们的单位不同、可比性也不同。

成本类型单位怎么测陷阱
token 成本美元 / 任务$\sum(\text{in} \times p_{\text{in}} + \text{out} \times p_{\text{out}})$缓存命中会让实际账单远低于名义 token；跨模型比较时价格会变，应同时记 token 数与当时的单价
墙钟时间秒 / 任务端到端计时受并发度、限流、外部服务抖动影响极大；不同并发下测出的时间不可比
工具/环境成本调用次数、容器分钟计数 + 计时容易被忽略；跑测试套件的 CPU 时间在代码类任务里可能超过 token 成本
人力成本人分钟 / 任务人工复核、人工判分的耗时在半自动评测里是真正的瓶颈；它决定了评测能跑多大规模

归一化：三种做法，各自的适用面

  1. 固定预算：给所有 agent 同样的 token/步数上限，比成功率。最简单、最公平，推荐作为默认做法。缺点是预算选得不好会让某些 agent 的曲线被截断在拐点之前。
  2. 成本归一成功率：报「每美元买到多少次成功」。适合成本敏感的产品决策，但它隐含假设成功的边际价值恒定——对「必须做完否则一分不值」的任务不成立。
  3. 报整条曲线：在多个预算档位各跑一遍，画成本-成功率前沿。信息最完整、成本最高，适合模型选型这种一次性决策。

一个非常容易踩的坑：用「平均 token 数」做成本归一化，会重蹈模块 03 的 Goodhart 覆辙——失败的轨迹往往更短更便宜，所以「降低平均成本」的最省事路径依然是「早点放弃」。正确做法是报「每次成功的平均成本」（总成本 ÷ 成功次数），它天然把失败的开销摊到了成功头上。

3成本-成功率前沿：怎么读，怎么用

把每个配置（模型 × scaffold × 预算）画成 (成本, 成功率) 平面上的一个点，取帕累托前沿——不存在另一个点同时更便宜且更准的那些配置。

成功率 │ ● D (贵且强) 60%│ ● C │ ● B 40%│ ● A ○ E (被 C 支配：更贵且更差) │ ○ F (被 A 支配) 20%│ └──────────────────────────────────────────────► 每任务成本 $0.05 $0.2 $1.0 $4.0 $18 前沿 = {A, B, C, D}。E 和 F 被支配 —— 它们在任何预算下都不该被选。 选哪个取决于你的预算线落在哪里，而不是"谁的分数最高"。
读法问题答案在图上哪里
预算给定我每任务最多花 $1，选谁在 $x = 1$ 处作垂线，取前沿上左侧最高的点（B 或 C）
目标给定我要 55% 成功率，最便宜多少在 $y = 0.55$ 处作水平线，取前沿上最左的交点
边际成本从 C 提到 D 值不值看两点间的斜率：多花的钱除以多得的成功率
被支配点E 为什么永远不该选存在 C 同时更便宜更准——这类点在真实评测里非常常见，通常是 scaffold 没调好

best-of-n 的特殊地位

best-of-n（跑 $n$ 次取最好）是成本-成功率曲线上最容易被误用的一段。它的成功率就是模块 04 的 pass@n，成本近似线性增长。三条必须记住的性质：

  • 它需要一个验证器。没有验证器就没法「取最好的」，此时 $n$ 次采样的实际价值接近 $n = 1$——这是 best-of-n 最常见的误用。
  • 边际收益急剧递减：pass@n 随 $n$ 增长很快饱和；从 1 到 2 通常涨十几个点，从 8 到 16 可能只涨一两个点，而成本翻倍。
  • 验证器本身有假阳率：$n$ 越大，「被验证器错判为成功的失败解」被选中的概率越高。这是模块 02 的 $\alpha$ 在 best-of-n 场景下的放大效应——$n$ 大到一定程度，best-of-n 会开始系统性地挑出 hack 解。

第三条值得记牢：best-of-n 是一个对判分器质量极其敏感的操作。判分器完美时它单调有益；判分器有 5% 假阳率时，$n = 32$ 的 best-of-n 有很大概率选中一个假阳解。notebook 第 3 节会把这个概率算出来——它同时也是 C67 模块 05 里 reward hacking 的评测侧同构现象。

4harness / scaffold：影响常常大于模型本身的差异

这是整门课里最反直觉、也最重要的工程事实：在 agentic 基准上，同一个模型换一套 scaffold，分数的变化幅度经常超过两代模型之间的差距。

scaffold 包含什么

组成部分具体选择对分数的影响机制
工具集给不给 grep？文件编辑是全文替换还是行级 patch？工具的表达力直接决定了 agent 需要多少步；行级编辑工具能显著降低格式错误
提示与角色系统提示、few-shot、是否要求先规划影响探索策略与放弃倾向
循环结构单 agent / 反思循环 / planner-executor / 多子 agent结构越复杂，成本越高，收益不一定单调
预算与终止最大步数、最大 token、超时、重试次数最容易被忽略、影响最大的一组
上下文管理压缩策略、记忆、检索（C33）长任务上决定成败
错误处理工具报错怎么回传给模型、要不要自动重试直接决定模块 03 的恢复率

由此得到一条必须遵守的报告纪律：任何 agent 基准分数，如果没有附带 scaffold 的完整描述，都不构成一个可比较、可复现的结果。「模型 A 得 48%，模型 B 得 42%」这句话，如果 A 用的是精心调过的自研 scaffold、B 用的是官方最简 baseline，那么这个 6 个点的差距可能完全来自 scaffold。

怎么做一次公平的模型对比

  1. 固定 scaffold，只换模型——这是唯一能支持「模型 A 比 B 强」这个结论的设计；
  2. 但要意识到它的局限：一个为 A 调优过的 scaffold 在 B 上可能水土不服。更公平（也更贵）的做法是各自用各自的最佳 scaffold，然后明确声明「这比较的是「模型+scaffold」这个组合，不是模型本身」；
  3. 报告 scaffold 消融：至少给出「最简 baseline scaffold」下的分数作为参照，让读者能把 scaffold 贡献和模型贡献分开。

直白说

为什么这件事在静态基准时代不存在？因为静态基准的 scaffold 只是一个 prompt 模板，变化空间很小。agent 的 scaffold 是一整个程序——它决定了模型能看到什么、能做什么、什么时候停。说得直白些：agent 基准测的从来不是模型，而是「模型 + 你写的那个程序」的组合。

严谨说

从测量的角度，scaffold 是一个未被控制的调节变量（moderator）。当调节变量的效应量与主效应量同阶时，不报告它就使得整个实验缺乏内部效度。正确的实验设计是把 scaffold 作为一个显式因子纳入：至少做 2×2（两个模型 × 两个 scaffold），从而能估计交互项。notebook 第 4 节会把这个 2×2 设计跑一遍，展示交互项如何翻转结论。

5可复现性清单：十个必须钉死的东西

「可复现」在 agent 评测里的含义是：另一个人拿到你的报告，能在正负一个误差棒内重现你的数字。下面这十项缺一项就做不到。

#要钉死的东西怎么钉不钉会怎样
1容器镜像记 sha256: digest，不是 tagtag 会被覆盖，几个月后同一个 tag 是不同的镜像
2任务集版本数据集哈希 + 版本号，且只增不改（模块 01）悄悄修过的题会让历史分数全部失效
3scaffold 版本git commit + 配置文件哈希第 4 节的全部理由
4模型标识完整模型 ID + 快照日期（若可用）「最新版」是一个会移动的目标
5采样参数temperature / top_p / seed（若支持）温度不同，方差与均值都不同
6预算参数max_steps / max_tokens / 超时 / 重试次数这是最影响分数、也最常被漏写的一组
7并发度worker 数并发会改变超时行为——高并发下容器变慢，超时任务变多
8网络策略断网 / 白名单 / 录制回放联网的评测在两个时间点跑就是两个实验
9判分器版本判分代码的 commit + 金标准集的 α/β（模块 02）判分器也会被修 bug
10重复次数与聚合方式$N$、$k$、micro/macro、CI 方法（模块 04）同一批数据能算出好几个不同的数字

把十项压成一个指纹

实践上的做法是把这十项序列化后取哈希，得到一个 run fingerprint，写进每一条结果记录。两次运行的指纹相同，分数却差很多——这本身就是一个需要调查的告警（说明还有没被记录的变量在动）；指纹不同的两次运行，则从一开始就不该被直接比较。

指纹机制的额外好处是它让「不可比较」这件事变成机器可判定的。在 C68 的 CI 门禁里，这一条直接变成一个断言：assert current.fingerprint == baseline.fingerprint，不相等就不允许做回归对比，而不是让人去肉眼核对配置。

网络：录制回放（record/replay）

对必须联网的评测，唯一可行的可复现方案是录制回放：第一次运行时把所有 HTTP 请求与响应录下来，之后的运行从录制里回放。代价是录制会过期（页面改版后录制内容与真实世界脱节），所以正确的用法是双轨：录制回放用于回归门禁（要可复现），定期的真实联网小样本用于校验录制是否已经失真（呼应模块 01 的离线-在线取舍）。

6评测卡：一份完整报告的最小集合

把模块 02、04、05 的报告规范合并，得到一张评测卡（eval card）。它的作用和模型卡类似：让读者在不重跑实验的情况下判断这个数字能不能用。

评测卡里最容易被砍掉、但绝对不能砍的三行是：① scorer 的 α/β（没有它，所有数字都可能是系统性偏的）；② MDE（没有它，「不显著」没有信息量）；③ fingerprint（没有它，这份报告不可复现）。这三行的共同点是：它们都在限制你能从数字里得出的结论，所以在追求好看的压力下最先被删掉。

7从评测到决策：上线门槛该怎么定

最后一步，也是整门课的落点：这些数字怎么变成「能不能上线」这个二值决策。

把指标翻译成期望效用

\[\mathbb{E}[U] = p_{\text{success}} \cdot V_{\text{success}} - p_{\text{fail}} \cdot C_{\text{fail}} - C_{\text{run}}\]

其中 $V_{\text{success}}$ 是一次成功的业务价值、$C_{\text{fail}}$ 是一次失败的代价（包括人工返工、用户流失、可能的赔付）、$C_{\text{run}}$ 是运行成本。上线门槛就是 $\mathbb{E}[U] > \mathbb{E}[U_{\text{现状}}]$。

场景$C_{\text{fail}}$ 的量级需要的成功率门槛该用的指标
草稿建议（人来定稿）很低——人会改低（40% 就有价值）pass@k 或 pass^1
自动执行、可撤销中等——出错要回滚中（80%+）pass^k，$k$ 取一次会话的操作数
自动执行、不可撤销（转账、发邮件）极高很高，且必须有人工确认点pass^k + 越权/副作用率（模块 03）
安全相关灾难性无论多高都要加保护层以上全部 + C69 的攻击面评测

有一个必须显式说破的推论：当 $C_{\text{fail}}$ 很高时，提高成功率的边际价值会低于「加一个人工确认点」的价值。换句话说，把 41% 提到 47% 可能远不如「在不可逆操作前停下来问一句」有用。评测报告如果只报成功率，会让整个团队一直往「提分」的方向使劲，而错过这个在产品上更划算的选项。

三个必须报给决策者的数字

  1. 给定预算下的成功率与其置信区间——它决定 $p_{\text{success}}$；
  2. 失败的构成（模块 03 的七分类）——它决定 $C_{\text{fail}}$，因为「没做完」和「做错了还删了东西」的代价差几个数量级；
  3. 每次成功的成本——它决定 $C_{\text{run}}$，也决定这件事在规模化后还成不成立。

到这里，本课的闭环就完成了：模块 01 选/建任务集，02 定义并验证判分器，03 从轨迹里挖归因信息，04 给出可信的不确定度，05 把成本与可复现性钉死并翻译成决策。下一步：判分器如果是一个 LLM 呢？那整套「先验证测量仪器」的逻辑要怎么做？——那是 C67。

8评测本身的成本控制：用更少的钱得到同样的结论

最后一个实用主题：前面所有内容都在教你把评测做严谨，而严谨通常意味着更贵。这一节反过来——在不牺牲结论质量的前提下，把评测成本降下来。

手段怎么做省多少代价 / 前提
剔除零信息任务所有候选 agent 都过或都不过的任务，对区分它们贡献 0 bit（模块 01）常能省 30%–50% 的运行量只对「比较」有效；做回归门禁时这些任务仍然有用（它们检测退化）
分层抽样按难度/子系统分层，从每层抽样而不是全跑线性节省需要任务元数据；小层要有保底名额
循环与预算早停检出循环即终止（模块 03）省掉长尾轨迹的大部分开销终止规则必须与最终标签独立（04 模块第 8 节）
缓存同一 (prompt, 模型, 参数) 的结果复用重跑时可省 90%+会掩盖非确定性——测方差时必须关掉缓存
两阶段筛选先用便宜的小任务集粗筛掉明显不行的配置，再用全量任务集精测存活者候选多时省得最多粗筛的排序必须与精测相关；相关性要先验证过
配对设计同一批任务同时跑两个 agent（模块 04）样本量省一半以上两者必须共享完全相同的环境快照

第四条的缓存值得单独警告：缓存会让你的评测看起来非常稳定，而这种稳定是假的。开着缓存重跑两次得到完全一样的分数，说明的不是「结果可复现」，而是「你根本没有重跑」。规则：估计方差、算置信区间、跑 pass^k 时必须关闭缓存；只有在做确定性回归对比（配置没变、只想确认没退化）时才开。

最贵的那一项通常不是算力

一个反直觉但普遍的事实：成熟评测体系里最贵的成本项往往是人力——写任务、写判分器、做人工审核、复核 L3 样本（模块 02 第 8 节）。算力可以线性扩容，人力不行。所以真正的成本优化重点是：

  1. 让判分器可复用：把判分逻辑做成不变量库而不是每个任务一段一次性脚本（模块 02 第 3 节）；
  2. 让任务可生成：能参数化生成的任务（同一模板换参数）边际成本接近零，但要小心它们的难度分布过于集中，通常需要与人工任务混合使用；
  3. 让人工只做机器做不了的事：人不该去判「测试过没过」，只该去判「这条判分器都拿不准的样本到底算不算成功」——这正是三级流水线的设计目的。

把这三条做到位，评测的边际成本会从「每次都要投入人力」变成「一次投入、长期复用」，而这正是 C68 那门课要展开的主题：把评测从一次性的实验变成一套基础设施。
