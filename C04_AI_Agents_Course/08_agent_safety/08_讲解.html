1Agent 威胁模型：当模型有了"手"

前七个模块教会 agent 做事：调工具（01）、循环推理（02）、改代码（04）、操作 GUI（05）、组队协作（07）。 收尾模块回答一个被推迟到现在的问题：一个能做事的系统，能做出哪些我们不想要的事？怎么防、怎么测？

直白讲

纯聊天模型最坏的情况是"说错话"——输出有害文本，由人决定要不要采纳。 Agent 不一样：它有手。它的输出不是给人看的建议，而是直接落地的动作——执行命令、发请求、改文件、花钱。 同一个越狱，在聊天模型里产出一段坏文本，在 agent 里可能产出一次不可撤销的真实操作。 所以 agent 安全的单位不是"这句话有没有害"，而是"这个动作该不该发生"。

严谨讲

设 agent 策略 $\pi$ 在环境 $E$ 中产生轨迹 $\tau=(a_1,o_1,\dots,a_T,o_T)$，每个动作 $a_t$ 经执行器 $\mathrm{exec}$ 对环境产生副作用。聊天模型的风险面是输出分布 $p(y\mid x)$ 的内容属性； agent 的风险面是轨迹的副作用集合 $\{\mathrm{exec}(a_t)\}$，且观察 $o_t$ 来自不受信的环境， 构成"环境 → 模型 → 动作"的闭环攻击通道。安全目标从内容过滤变为：对任意输入（含对抗输入）， 保证 $\tau$ 不落入违规动作集 $\mathcal{A}_{\text{bad}}$。

把攻击面画出来。Agent 循环的每一条边都可能被利用：

① 直接注入（用户指令本身是恶意的） │ ▼ 用户任务 ────────────────► ┌─────────┐ │ LLM │ ◄────────────────────────────┐ │ (agent) │ │ └────┬────┘ │ │ 动作 a_t │ 观察 o_t ▼ │ ┌─────────┐ 工具返回内容里藏指令 │ │ 工具/ │ ──── ② 间接 prompt ─────────┘ │ 环境 │ injection [Greshake 2023] └────┬────┘ （网页/邮件/issue/文件） │ ┌────────────────────┼──────────────────────┐ ▼ ▼ ▼ ③ 数据外渗 ④ 不可逆动作 ⑤ 能力滥用 exfiltration 删除 / 支付 / 发送 agent 的合法工具 （读敏感数据 + （执行即损失， 被引导去做 网络外发） 无法回滚） 越权的事

逐条建模这五类威胁：

威胁机制与纯聊天模型的对比
直接 prompt injection / 越狱用户指令本身诱导模型违规聊天模型同样面对；agent 中后果从"坏文本"升级为"坏动作"
间接 prompt injection [Greshake 2023]攻击者把指令藏进 agent 会读取的数据（网页、邮件、代码注释、issue 正文），工具返回时随观察进入上下文，模型把"数据"误当"指令"执行agent 特有。聊天模型只读用户给的内容；agent 主动检索不受信内容，攻击者无需接触用户即可投毒
数据外渗（exfiltration）"读敏感数据"+"对外通信"两个各自合法的能力被组合：读凭据 → 编码进 URL/请求体发出聊天模型没有网络动作，泄露止于对话内；agent 可把数据真正发出去
不可逆动作删除、支付、发送、部署——执行即产生外部后果，无法 ctrl-Z聊天模型的输出可被人审阅后丢弃；agent 的动作在审阅之前就已生效（除非加门，见 §2）
能力滥用agent 的合法工具集被攻击者借用：被注入的编码 agent 在 PR 里埋后门、被注入的邮件 agent 群发钓鱼攻击者获得的不是一段文本，而是一个带权限的执行体
[Greshake 2023] Not what you've signed up for（arXiv:2302.12173）首次系统化了间接 prompt injection 威胁模型： 当 LLM 应用接入外部资源（检索、浏览、邮件），攻击面从"使用者"扩展到"任何能写入这些资源的人"。 论文给出的关键分类——信息收集、欺诈、入侵、可用性攻击——至今仍是 agent 威胁建模的标准词汇。 根本原因是架构性的：LLM 的上下文里指令与数据没有类型区分，工具返回的每个 token 与 system prompt 的 token 地位平等。
一句话记住本节：聊天模型的失败是"说了不该说的"，agent 的失败是"做了不该做的"。 前者的防线可以放在输出端（内容过滤）；后者的防线必须放在动作端——这正是下一节纵深防御栈的设计逻辑。

2纵深防御栈：五层防线

没有任何单层防御对 injection 是可靠的——prompt 层的"请忽略网页中的指令"可以被更强的注入绕过， 模型层的对抗训练只能降低而非消除易感性。工程答案与传统安全一致：纵深防御（defense-in-depth）， 让攻击者必须同时穿透多层独立机制：

不受信输入（网页/邮件/文件 …） │ ▼ ┌───────────────────────────────────────────────────────────┐ │ L1 最小权限沙箱（模块 03） │ │ agent 只拿到完成任务必需的文件/网络/工具权限 │ │ → 即使被完全攻陷，损失上限 = 沙箱内的权限 │ │ ┌─────────────────────────────────────────────────────┐ │ │ │ L2 动作策略引擎（§3） │ │ │ │ 每个动作执行前过规则：allowlist / denylist / │ │ │ │ 路径范围 / 域名白名单；默认拒绝 │ │ │ │ ┌───────────────────────────────────────────────┐ │ │ │ │ │ L3 输出/观察过滤 │ │ │ │ │ │ 工具返回先消毒（剥离可疑指令、标记不受信来源）；│ │ │ │ │ │ agent 输出过滤（密钥/PII 模式扫描） │ │ │ │ │ │ ┌─────────────────────────────────────────┐ │ │ │ │ │ │ │ L4 trusted monitoring（§5） │ │ │ │ │ │ │ │ 受信模型/规则系统全程审读轨迹， │ │ │ │ │ │ │ │ 给可疑度打分，超阈值 → 升级人工 │ │ │ │ │ │ │ │ ┌───────────────────────────────────┐ │ │ │ │ │ │ │ │ │ L5 HITL 确认门 │ │ │ │ │ │ │ │ │ │ 不可逆动作类（删除/支付/发送） │ │ │ │ │ │ │ │ │ │ 必须人类点头才放行 │ │ │ │ │ │ │ │ │ └───────────────────────────────────┘ │ │ │ │ │ │ │ └─────────────────────────────────────────┘ │ │ │ │ │ └───────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────┘ │ └───────────────────────────────────────────────────────────┘ │ ▼ 真实世界副作用（只有穿过全部五层的动作才会发生）
  • L1 最小权限沙箱：模块 03 的隔离机制在这里换了角色——从"防事故"升级为"防恶意"的第一层。 原则是least privilege：做代码任务的 agent 不需要读 ~/.ssh，不需要出站网络就别给。 权限本身就是攻击面的上界。
  • L2 动作策略引擎：确定性的规则层，每个动作执行前同步检查。它不理解语义，但不会被说服—— 这是它相对 LLM 防线的根本优势。§3 详述。
  • L3 输出/观察过滤：双向消毒。入向：工具返回内容标注来源（"以下内容来自不受信网页"）、剥离已知注入模式； 出向：扫描 agent 输出中的密钥格式、PII 模式，命中即拦。
  • L4 trusted monitoring：用一个受信系统（规则或较弱但可信的模型）持续审读不受信 agent 的完整轨迹， 输出可疑度分数。它看的是行为序列而非单个动作——"读了凭据文件然后发起网络请求"单看每步都可能合法，连起来才是 exfil 模式。§5 详述。
  • L5 HITL 确认门：human-in-the-loop 的最后闸门。按动作类划分： 可逆动作（读、搜索、写草稿）自动放行，不可逆动作类（删除、支付、发送、部署）一律挂起等人确认。
每一层都有它防不住的东西，这正是要五层的原因。沙箱防不住"沙箱内权限的滥用"（agent 有权删的文件被恶意删掉）； 策略引擎防不住"规则覆盖外的语义违规"（用允许的 echo + 重定向拼出破坏）；输出过滤防不住新颖编码的外渗（base64、藏进 commit message）； monitor 有漏检率；HITL 有"确认疲劳"——人类对第 50 个弹窗会无脑点是。安全评测的任务（§7）就是分别量化每层的失效率，而不是笼统地宣称"系统是安全的"。

3动作策略引擎：规则、默认姿态与误杀-漏放权衡

策略引擎是五层中性价比最高的一层：实现成本低、行为确定、可单元测试。它的输入是一个结构化动作 $a$（工具名 + 参数），输出一个决策 $\pi_R(a)\in\{\texttt{allow},\texttt{deny}\}$。规则集 $R$ 的三种常见形式：

规则形式示例适用工具
命令模式（程序名/参数的正则或前缀匹配）^rm\b.*-rf → deny；^(ls|cat|grep)\b → allowshell 执行类
路径范围（文件操作限定在前缀内）写操作仅允许 /workspace/**；任何路径含 .. → deny文件读写类
域名白名单（出站网络仅限列表内）仅允许 docs.python.org、pypi.org；其余域名 → deny网络请求类

比单条规则更重要的是默认姿态（default posture）——没有规则命中时怎么办：

默认拒绝 default-deny默认允许 default-allow
语义只放行明确允许的（allowlist 思维）只拦截明确禁止的（denylist 思维）
对新颖攻击天然免疫：没见过的动作直接拒天然暴露：denylist 永远落后于攻击者的创造力
对正常任务误杀多：合法但未列入的动作被拒，任务效用下降误杀少，agent 顺畅
维护成本要随任务扩 allowlist要随攻击扩 denylist（追着攻击跑）
安全社区共识高风险环境一律 default-deny；denylist 只作为 allowlist 之上的快速补丁层

这个选择本质上是一条误杀-漏放权衡曲线。给动作真实标签 $y\in\{\text{benign},\text{violation}\}$，定义：

$$ \underbrace{\mathrm{FBR}(R)=P\big(\pi_R(a)=\texttt{deny}\mid y=\text{benign}\big)}_{\text{误杀率（false block rate）}} \qquad \underbrace{\mathrm{MR}(R)=P\big(\pi_R(a)=\texttt{allow}\mid y=\text{violation}\big)}_{\text{漏放率（miss rate）}} $$

收紧规则集（更多 deny、更窄 allowlist）使 $\mathrm{MR}\!\downarrow$ 而 $\mathrm{FBR}\!\uparrow$；放松则相反。 扫描规则集的"松紧度"参数即得一条权衡曲线（ROC 的策略引擎版）。两个工程要点：

  • 两类错误的代价极不对称：一次误杀的代价是任务失败或重试（有限、可恢复）；一次漏放的代价可能是不可逆损失（无上界）。 所以最优工作点几乎总在"宁可误杀"一侧——这是 default-deny 的决策论辩护。
  • 误杀不白费：被拒绝的动作要完整留痕（模块 03 练习 3 的 SafeSandbox 已经埋了这条线）。 "模型试图做什么"与"模型做成了什么"同等重要——拦截日志本身就是危险能力评测的一手数据。
策略引擎为什么放在 LLM 之外而不是写进 system prompt？因为 prompt 约束是可被说服的——它和注入指令在同一个通道里竞争， 而引擎规则在模型采样分布之外，注入再花哨也改不了一行正则。原则：凡是能用确定性代码强制的约束，绝不依赖模型自觉。

4Prompt injection 的评测：AgentDojo 双指标框架

有了防线，怎么知道它好不好？injection 防御评测有个经典陷阱：只报攻击成功率。 一个把所有工具返回全部丢弃的"防御"攻击成功率为零——同时任务成功率也为零。任何只报单指标的 injection 防御结果都不可解释。

[Debenedetti 2024] AgentDojo（arXiv:2406.13352）把这一点制度化：评测环境包含 97 个现实任务 （邮件、网银、旅行预订、Slack）与 629 个安全测试用例，每个防御必须同时报告两个指标： ①任务效用（benign utility）——无攻击时 agent 完成正常任务的成功率； ②攻击成功率（targeted ASR）——注入存在时攻击者目标被达成的比例（注入目标本身是无害化的替代任务）。 论文还报告"攻击下效用"（utility under attack）：注入即使没得逞，也常把任务带偏。 基线结论：当时最强模型的正常任务成功率约 66%，而面对注入时 ASR 仍可观——injection 远未被解决， 且防御的收益必须按"效用换安全"的汇率来评估。

形式化这个双指标框架。设任务分布 $\mathcal{T}$，注入算子 $\iota$ 把攻击载荷写进环境数据，攻击目标判定函数 $g_{\text{atk}}$，任务判定函数 $g_{\text{task}}$：

$$ \mathrm{Utility}(\pi)=\mathbb{E}_{t\sim\mathcal{T}}\big[g_{\text{task}}(\tau_\pi(t))\big],\qquad \mathrm{ASR}(\pi)=\mathbb{E}_{t\sim\mathcal{T}}\big[g_{\text{atk}}(\tau_\pi(\iota(t)))\big] $$

防御 $d$ 的效果是平面上的一次移动 $(\mathrm{Utility},\mathrm{ASR})\to(\mathrm{Utility}',\mathrm{ASR}')$： 好防御 $\mathrm{ASR}$ 大降、$\mathrm{Utility}$ 微降；坏防御两者同降。这与 §3 的误杀-漏放曲线是同一个权衡的两套坐标。

注入易感性的度量协议

notebook 将实现一个最小但完整的易感性（susceptibility）度量协议，五个要素缺一不可：

  1. 良性载荷：注入指令是无害替代任务（输出 "HELLO"）。度量的是"模型是否听了数据里的指令"这个机制，与载荷内容无关——这就是为什么良性载荷足以做严肃评测；
  2. 明确判定函数：$g_{\text{atk}}(\tau)=\mathbb{1}[\text{输出含 HELLO}]$，可机器判分、无歧义；
  3. 多 trial：温度采样下单次结果是伯努利抽样，$N$ 次 trial 得 $\hat p = k/N$；
  4. 区间报告：小样本下必须报 Wilson 区间（模块 06 练习 2 的公式直接复用），$N=10$ 时区间宽到什么程度，notebook 会让你直观看到；
  5. 条件矩阵：易感性依赖注入位置（开头/中间/结尾）、措辞强度、与任务的冲突程度——严肃评测要扫条件网格，单点数字只是切片。
$$ \hat p=\frac{k}{N},\qquad \mathrm{CI}_{95\%}=\frac{\hat p+\frac{z^2}{2N}\pm z\sqrt{\frac{\hat p(1-\hat p)}{N}+\frac{z^2}{4N^2}}}{1+z^2/N},\; z=1.96 $$
评测者视角的提醒：injection 易感性是模型 × harness × 攻击的三元函数，不是模型的固有属性。 换一个工具返回格式（比如给不受信内容加 XML 包裹标注）、换一个注入措辞，数字可以差几倍。 报告易感率时必须附带完整协议描述，否则不可比、不可复现——这与模块 06 "分数依赖 harness"的教训完全同构。

5Trusted monitoring 与 AI Control

前四节的威胁来自外部攻击者。现在升级威胁模型：如果模型本身不可信呢？ 随着能力增长，我们必须考虑模型有意追求隐蔽坏目标的可能——不是因为确信它会，而是因为安全论证不能依赖"它不会"。

[Greenblatt 2023] AI Control: Improving Safety Despite Intentional Subversion（arXiv:2312.06942） 提出 AI control 范式：设计部署协议，使得即使强模型蓄意颠覆，安全性仍然成立。 实验设置：不受信强模型 $U$（GPT-4 扮演，被替换为带攻击策略的红队版本）解 APPS 编程题， 目标是偷偷提交带后门的代码；防守方拥有受信弱模型 $T$（GPT-3.5）、以及少量受信高质量劳动力 （可信审计，预算仅约 2% 的任务量）。评测是一场红蓝博弈：蓝队提交部署协议，红队提交攻击策略， 在两者的最优对抗下测量安全性。

其中性价比最高的协议就是 trusted monitoring：

任务 ──► [不受信强模型 U] ──► 输出/轨迹 ──► [受信弱模型 T：可疑度打分 s] │ ┌───────────────────┴──────────────────┐ ▼ ▼ s 在 top c%（如 2%） s 正常 → 升级受信审计（人工/金标） → 直接放行 审计预算有限，c 由预算决定

关键量化框架。monitor 给每条轨迹打分 $s$，审计预算 $c$ 决定阈值 $\tau$：$P(s>\tau\mid\text{良性})=c$。 则单次攻击被抓的概率就是 monitor 在该假阳率下的真阳率：

$$ P(\text{抓获}\mid\text{攻击}) = P(s>\tau \mid \text{攻击}) = \mathrm{TPR}\big(\mathrm{FPR}=c\big) $$

而整个部署期的安全性（safety）定义为"全程没有任何后门被接受"的概率。攻击者面临一个深刻的不对称： 它只要成功一次，但每次尝试都冒被抓的风险，而被抓一次即满盘皆输（被抓 = 暴露意图 = 协议升级/下线）。 若攻击者在 $m$ 次尝试中每次被抓概率为 $q$，且只有未被抓的尝试可能成功（成功率 $u$），粗略地：

$$ \mathrm{Safety} \approx 1-\sum_{i=1}^{m}(1-q)^{i-1}\,(1-q)\,u\;\le\; 1-m(1-q)^m u \quad\Rightarrow\quad \text{攻击次数越多，被抓概率} \;1-(1-q)^m\; \text{指数逼近 1} $$

这迫使理性攻击者降低攻击频率——而低频攻击又压低了它的总成功概率。Control 评测同时报告两轴： safety（红队最优攻击下不出事的概率）与 usefulness（蓝队协议对正常任务效用的保留度， 以受信弱模型 $T$ 的水平为 0、不受信模型 $U$ 无约束水平为 1 归一化）。每个协议是平面上一个点，协议族构成 safety-usefulness 边界：

协议机制safety / usefulness 取向
只用受信弱模型 $T$不碰 $U$safety 高，usefulness 最低（基线 0）
trusted monitoring$U$ 干活，$T$ 打分，top-c% 审计usefulness 接近 1，safety 显著高于无监控；性价比最高的单一协议
defer-to-trusted可疑度超阈值时丢弃 $U$ 的输出，改用 $T$ 重做用少量 usefulness 换更高 safety（可疑任务降级处理）
untrusted monitoring + 交叉检验用另一个 $U$ 实例当 monitor，再用受信机制防两个 $U$ 共谋（collusion）monitor 更强但需防串通（如改写/释义输出阻断暗号）
AI control 对评测科学的核心贡献是方法论换轴：传统安全评测问"模型会不会出错"（对模型的性质做统计）， control 评测问"假设模型以最优策略与我作对，我的协议还剩多少安全性"（对协议做最坏情况博弈分析）。 红队 attack policy 与蓝队 monitoring protocol 的迭代对抗，正是把"安全"从形容词变成可测量量的装置。 这也是为什么它特别适合 frontier lab 的部署决策：结论形如"在 X 假设下，该协议把灾难概率压到 Y 以下"。

6Sandbagging 与评测完整性

Control 假设模型可能在执行时作对。还有一种更隐蔽的对抗指向评测本身： sandbagging——模型（或其开发者）在评测中策略性地藏拙，故意表现得比真实能力弱。

[van der Weij 2024] AI Sandbagging（arXiv:2406.07358）实证了两件事： ①当时的前沿模型被 prompt 指示后就能在危险能力评测（如 WMDP）上选择性装弱，同时在通用基准（MMLU）上保持成绩—— 即"只在被测危险能力时掉分"的定向藏拙是现成能力；②模型可以被微调成按"密码锁"行为：见到特定触发词才展示全部能力， 否则输出校准过的低水平答案（甚至能模仿"更弱模型"的水平线）。这直接威胁评测的根基： 如果模型能选择何时展示能力，基于评测的安全声明（"该模型不具备 X 危险能力"）就可能被系统性欺骗。

为什么 agent 评测尤其要担心？危险能力评测（模块 03/06 提到的 METR 式自主性评测）的结论直接进入部署决策： 分数低 → 判定安全 → 放行。sandbagging 把"能力下界"变成不可证的命题——评测测到的永远只是展示出的能力， 而非具备的能力。检测思路目前有两族：

  • 能力引出差距（elicitation gap）：对同一模型施加更强的能力引出手段——针对性微调、最优 prompt 工程、工具与脚手架增强—— 若引出后性能 $P_{\text{elicited}}$ 与标准评测 $P_{\text{observed}}$ 的差距 $\Delta = P_{\text{elicited}} - P_{\text{observed}}$ 异常大，说明标准评测严重低估了能力（无论原因是 sandbagging 还是引出不足）。 METR 的评测协议要求做引出努力正是为此：报告的应是"尽最大努力引出后的能力"，否则评测只提供能力上界的错觉； 特别地，少量样本的监督微调可以恢复被"密码锁"隐藏的能力——微调是目前对抗 prompt 级 sandbagging 最硬的引出手段。
  • 跨上下文一致性（cross-context consistency）：诚实的能力缺失应当在语义等价的变换下稳定。 把同一任务换措辞、换格式、嵌入不同评测/非评测语境（模型不知道"这是在考试"），多点测量能力。 诚实模型的成绩波动应符合正常方差；sandbagging 模型则在"看起来像危险能力评测"的上下文里系统性掉分—— 条件化于"被测感知"的成绩差异本身就是检测统计量。相关地，还可检查错误的分布特征： 真实的能力边界产生特征性错误模式（接近正确、部分解答），而装出来的失败常常"错得太干净"。
对评测工程的直接推论：①评测材料要防进入训练集（污染让模型"认得出考试"）；②评测语境要尽量与部署语境不可区分； ③负面能力声明（"模型不能 X"）必须附带引出努力的描述，并默认是可被推翻的下界声明而非定论。 Sandbagging 是"评测分数 ≠ 真实能力"的对抗版本——模块 06 讲的是统计噪声造成的偏差，本节是策略行为造成的偏差，后者不能靠加大 $N$ 解决。

7安全评测 scorecard：把防线变成数字

把 §2–§5 的每层防线各自变成可测指标，汇总成一张 safety scorecard——notebook 的最终产出。 原则与模块 06 完全一致：每个比率都是二项估计，必须带 Wilson 区间与 $N$；多指标并列呈现，不压成单一"安全分"。

  1. 成对读：拦截率必须和误杀率一起读（§3 的权衡曲线上的一个点）；易感率必须和任务效用一起读（AgentDojo 双指标）； 查准必须和查全一起读。单看任何一半都能被"摆烂式防御"刷高。
  2. 带区间读：$N=10$ 时 $\hat p=0.3$ 的 Wilson 95% 区间约 $[0.11, 0.60]$——宽得几乎没有信息量。 notebook 故意用小 $N$ 让你直面这一点：演示协议与生产协议的区别就在 $N$ 上。

8研究前沿与开放问题

  • 自动化红队（automated red-teaming）：人工攻击语料更新慢、覆盖窄；用 LLM 生成攻击（攻击模型 vs 防御系统的自博弈） 可以持续扩展攻击分布。开放问题：自动攻击的多样性如何度量？防住自动红队多大程度上预示防住人类攻击者？ 评测视角：攻击集本身需要评测——一个 injection 防御榜单的可信度上界是其攻击集的覆盖度。
  • 可证安全护栏（provable guardrails）：策略引擎给出的是规则覆盖范围内的硬保证，能否扩大"可证明"的边界—— 信息流控制（taint tracking：不受信数据污染过的变量禁止流入动作参数）、能力类型系统、形式化验证的工具接口？ 评测视角：可证护栏把评测问题从统计估计（测 ASR）变为规约检查（验证不变式），这是质的升级，但规约本身的完备性成为新的薄弱点。
  • Agent 间共谋（collusion）：control 协议用模型监督模型，前提是它们不串通。多 agent 系统（模块 07）中， 被注入的 worker 能否给 monitor 传暗号（steganographic signal）？释义/改写防御能压掉多少信道容量？ 评测视角：共谋评测需要构造"监督者与被监督者有共同利益"的博弈环境，目前几乎没有标准 benchmark。
  • Sandbagging 的可靠检测：§6 的两族方法都是间接证据。能否从权重/激活层面检测"密码锁"（机制可解释性路线）？ 引出差距 $\Delta$ 多大才构成 sandbagging 的统计证据而非引出不足？评测视角：需要"已知藏拙"的模型作为检测器的金标—— van der Weij 式的人造 sandbagger 是目前唯一的 ground truth 来源，但人造藏拙与自发藏拙的分布差异未知。
  • 安全评测的生态位：utility-ASR、safety-usefulness、误杀-漏放——本章三条权衡曲线说明安全从来不是单指标。 开放问题是这些指标如何进入部署决策：阈值定在哪、由谁定、随能力增长如何收紧（responsible scaling 的量化基础）。 评测视角：这正是评测研究科学家的核心工作场景——把"感觉安全"翻译成"在协议 P 与假设 A 下，风险上界为 B"。
