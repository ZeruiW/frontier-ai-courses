1LLM 为什么需要工具：参数化知识的三条边界

一个纯语言模型只做一件事：在给定上下文下预测下一个 token。它的全部"知识"都冻结在权重里 （parametric knowledge）。这带来三条无法靠堆参数解决的硬边界：

  • 时效边界：训练数据有截止日期（knowledge cutoff）。"今天 arXiv 上有什么新论文"在权重里根本不存在， 任何回答都只能是幻觉。
  • 计算边界：Transformer 用注意力做模式匹配，不是图灵机意义上的精确计算器。 多位数乘法、长链算术、日期推算的错误率随位数显著上升——模型在"背"算术，而不是在"算"算术。
  • 行动边界：模型的输出是文本。不接外设的情况下，它读不了你的文件、查不了数据库、发不了请求—— 它能描述动作，但不能执行动作。

直白讲

工具调用就是给模型一部"可以打出去的电话"：模型自己知道答不了的时候， 不再硬编一个答案，而是按约定格式喊一声"帮我查一下 X / 算一下 Y"，外部程序执行后把结果递回来， 模型再基于真实结果继续作答。模型负责决策（调不调、调哪个、传什么参数）， 程序负责执行。

严谨讲

设模型为条件分布 $p_\theta(y_t \mid y_{<t}, x)$。工具调用把生成过程改写为带外部查询的解码： 解码途中模型可发射一个结构化调用 $c=(f, a)$（工具名 $f$、参数 $a$），运行时执行 $r=f(a)$ 并把 $r$ 注入上下文， 后续 token 条件于 $p_\theta(y_t \mid y_{<t}, x, c, r)$。模型的权重没有变， 变的是上下文中出现了训练分布之外、但真实可靠的证据。这是后续所有 agent 行为的原子操作。

Toolformer [Schick 2023] 是"让 LM 自学用工具"的里程碑：不靠人工标注，让模型自己在语料中插入候选 API 调用 （计算器、QA、翻译、日历、检索），执行后用一个自监督过滤准则决定保留哪些调用——只保留"调用结果真的让后文更好预测"的样本：
$$ L_i^{+} \;=\; L_i\big(\text{call}\,\rightarrow\,\text{result}\big), \qquad L_i^{-} \;=\; \min\!\big(L_i(\varnothing),\; L_i(\text{call only})\big) $$ $$ \text{保留该调用} \iff L_i^{-} - L_i^{+} \;\ge\; \tau $$
其中 $L_i$ 是位置 $i$ 之后 token 的加权交叉熵损失。在过滤后的语料上微调，模型就学会了"何时该调、调什么"。 这个准则本身就是一种工具有用性的可度量定义——评测视角下非常值得借鉴。
本课程把 agent 拆成层层递进的积木：本模块 = 单次工具调用；模块 02 把它套进"推理-行动"循环（ReAct）； 模块 03 给循环加上沙箱与 harness；模块 06 回头系统性地度量这一切。把单次调用的机制吃透，后面每一层都是在它之上加控制流。

2function calling 机制解剖：四阶段时序

所有厂商的 function calling 实现，剥掉字段名差异后都是同一个协议，分四个阶段：

  1. 声明（schema 注入）：开发者在请求中提供工具列表，每个工具 = name + description + 参数的 JSON Schema。这些 schema 会被序列化进模型的上下文（对模型来说工具列表就是 prompt 的一部分）。
  2. 决策（结构化输出）：模型不再只输出自然语言，而是可以输出一个结构化调用块——工具名 + 符合 schema 的参数对象， 并以特殊的停止原因（tool_calls / tool_use）结束本轮生成。
  3. 执行（运行时）：模型从不执行任何代码。你的程序解析调用块、校验参数、真正运行函数，拿到结果（或错误）。
  4. 回填（结果注入）：把结果以约定格式（OpenAI 的 role:"tool" 消息 / Anthropic 的 tool_result 块）追加进对话历史，再次请求模型。模型基于真实结果继续——要么给出最终答案，要么发起下一次调用。
开发者/运行时 模型 (LLM API) ──────────────── ────────────── ① 请求: messages=[user 问题] tools=[{name, description, JSON Schema}] ──────► 读到工具清单 + 问题 │ 判断: 需要外部能力 ② 响应: stop_reason=tool_use ◄──────┤ 输出结构化调用块 { name: "calculator", │ {"expression": "127*893"} input: {...}, id: "toolu_x" } │ │ ③ 运行时执行: （模型此刻什么都不做， 校验参数 → calculator(...) 等待下一次请求） → result = "113411" │ ④ 请求: 原历史 + assistant(调用块) + tool_result(id=toolu_x, content="113411") ──────► 看到真实结果 │ 信息已足够 响应: stop_reason=end_turn ◄──────┘ 生成最终自然语言答案 "127 × 893 = 113,411" （若仍需要工具 → 回到 ②，循环直至 end_turn 或 max_turns）
两个最常见的初学者误解：①以为"API 帮我执行了函数"——没有，除少数服务端工具（如 code execution、web search）外， 自定义工具永远由你的代码执行，模型只产生"调用意图"；②忘记把assistant 的调用块原样放回历史再附上结果—— 调用块里的 id 是结果与调用配对的唯一凭据，丢了它 API 会直接报错。这也是为什么说 function calling 是一个 协议而不只是一个参数。

3原生 tool API 对比：OpenAI 与 Anthropic

两家的原生接口语义同构、字段不同。对照看一遍请求/响应结构，以后读任何 agent 框架的源码都不会迷路。

OpenAI：tools / tool_calls / role:"tool"

# 请求
resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "巴黎现在天气如何？"}],
    tools=[{
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的当前天气",
            "parameters": {                      # JSON Schema
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"],
            },
        },
    }],
)

# 响应（模型决定调用工具时）
msg = resp.choices[0].message
# resp.choices[0].finish_reason == "tool_calls"
# msg.tool_calls == [ToolCall(id="call_abc",
#     function=Function(name="get_weather",
#                       arguments='{"city": "Paris"}'))]   # ← JSON 字符串!
args = json.loads(msg.tool_calls[0].function.arguments)

# 回填：assistant 消息（含 tool_calls）+ role="tool" 消息
messages += [
    msg,   # 含 tool_calls 的 assistant 消息必须原样放回
    {"role": "tool", "tool_call_id": "call_abc", "content": "15°C，小雨"},
]

Anthropic：tools / tool_use 块 / tool_result 块

# 请求
resp = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=1024,
    messages=[{"role": "user", "content": "巴黎现在天气如何？"}],
    tools=[{
        "name": "get_weather",
        "description": "查询指定城市的当前天气",
        "input_schema": {                        # 注意: input_schema 而非 parameters
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"],
        },
    }],
)

# 响应：resp.stop_reason == "tool_use"
# resp.content == [TextBlock("我来查一下..."),
#                  ToolUseBlock(type="tool_use", id="toolu_abc",
#                               name="get_weather",
#                               input={"city": "Paris"})]   # ← 已解析的对象!

# 回填：assistant 内容原样放回 + user 消息携带 tool_result 块
messages += [
    {"role": "assistant", "content": resp.content},
    {"role": "user", "content": [{
        "type": "tool_result",
        "tool_use_id": "toolu_abc",
        "content": "15°C，小雨",          # 出错时可加 "is_error": True
    }]},
]

并行调用（parallel tool calls）：两家的模型都可能在一轮响应里发出多个调用—— OpenAI 的 tool_calls 是列表，Anthropic 的 content 可含多个 tool_use 块。 协议要求：每个调用 id 都必须有一个对应的结果，并且在同一条回填消息里一起返回，缺一个就报错。 运行时可以并发执行这些调用（互不依赖时显著降延迟），也可以关掉该行为 （OpenAI parallel_tool_calls=False；Anthropic 在 tool_choice 中设 disable_parallel_tool_use: true）——评测时常需要关掉以获得确定性的单步轨迹。

4prompted tool calling：没有原生支持时怎么办

原生 function calling 依赖两件事：模型经过专门的调用格式微调，且 API 层做了结构化解析（甚至约束解码）。 当你用的是没有这层支持的开源小模型、或在做不依赖特定 API 的评测 harness 时，就退化为 prompted tool calling：用 system prompt 约定输出格式，自己解析。

SYSTEM = """你可以使用以下工具：
{tools_json}

需要调用工具时，只输出一个 JSON（用 ```json 围栏包裹）：
```json
{"tool": "<工具名>", "args": {<参数>}}
```
拿到工具结果后，若信息已足够，直接输出最终答案（不要再输出 JSON）。"""

然后对模型的原始输出做鲁棒提取：剥掉 markdown 围栏、跳过前后的自然语言"废话"、 做花括号配对截取候选 JSON、json.loads 失败再尝试宽松解析。配套 notebook 会从零实现这条解析链。

格式保证专门微调 + API 解析；strict 模式下约束解码保证合法 JSON仅靠指令遵循，格式正确率与模型能力强相关，小模型可能只有 70–95%
典型失败参数语义错误（格式几乎不错）围栏不闭合 / 夹带解说文字 / 单引号伪 JSON / 幻觉工具名 / 直接拒绝输出 JSON
解析成本SDK 给出结构化对象需要自写 robust extractor + 重试逻辑
可移植性绑定厂商字段任何能续写文本的模型都能用
评测含义测的是"决策 + 参数"能力额外混入"格式遵循"能力，需把两者分开归因
ToolLLM [Qin 2023] 证明了开源模型可以通过微调追上这条差距：作者从 RapidAPI 收集了 16,464 个真实 REST API，用 ChatGPT 自动构造多工具指令数据（ToolBench），并提出 DFSDT （基于深度优先搜索的决策树，允许回溯换 API）替代单链 CoT；微调出的 ToolLLaMA 在其自动评测器 ToolEval 上接近 ChatGPT 的工具使用水平。 对评测者的启示有二：①工具使用能力是可注入的（数据工程问题，不是涌现魔法）； ②大规模 API 评测必须配自动评估器 + API 检索器，人工逐条核对不可扩展。
为什么本课程的 notebook 默认走 prompted 路线（Qwen2.5-1.5B-Instruct）？因为它把原生 API 帮你藏起来的所有失败模式暴露出来了—— 你会亲手遇到格式漂移、解析失败、幻觉工具，并亲手写校验与修复循环。理解了底层，再用原生 API 就只是换字段名。

5schema 设计即接口设计

模型"看到"的工具只有 schema——名字、描述、参数定义。schema 写得多好，调用正确率的上限就有多高， 这与给人类工程师设计 API 是同一门学问，只是用户换成了一个靠文本理解接口的模型。三条经验规律：

  • description 决定"何时调用"。只写"查天气"不如写清触发条件："当用户询问当前或未来天气时调用； 不要用于历史气候统计"。对工具调用偏保守的新一代模型，把触发条件写进 description 能直接提升应调未调（recall）。
  • 参数命名与类型决定"怎么调用"。q 不如 search_query； 自由字符串不如 enum。能用枚举约束的（单位、模式、语言代码），一律枚举—— 模型不可能拼错一个枚举值的字段语义，但完全可能把自由字符串写成同义词。
  • required 划定责任边界。必填项太多 → 模型被迫编造参数（幻觉）； 必填项太少 → 工具内部默认值悄悄接管语义，失败难以归因。原则：模型必须从用户话语里得到的信息才设 required，其余给默认值。

评测视角的归因陷阱：一个 agent 在某工具上失败率高，先别下结论"模型弱"。 用同一模型 + 重写过的 schema 跑 A/B，经常能看到正确率移动 10–30 个百分点—— 这说明你度量的其实是 模型 × 接口 的联合系统。SWE-agent [Yang 2024]（模块 04）把这个思想推到极致： 专门为 LM 设计的 Agent-Computer Interface 本身就是性能的一等公民。 报告 agent 评测结果时，工具 schema 必须作为实验配置的一部分被固定和公开。

6错误处理：回喂与修复循环

工具调用的三类典型故障，对应三道防线。共同原则：错误不终止循环，而是作为信息回喂（feed back）给模型， 给它一次自我修复的机会——LLM 对高质量错误信息的修复率出奇地高，对含糊错误信息则几乎为零。

故障类发生点防线与回喂内容
① 参数校验失败执行前对照 schema 检查必填项/类型/枚举（notebook 练习 2 实现 validate_args）。 回喂："ERROR: 参数 from_unit 取值 'kilometer' 不在枚举 ['m','km','mile'] 中" ——指名道姓、给出合法选项。
② 工具执行异常执行中try/except 捕获，绝不让异常炸掉 agent 循环。 回喂：异常类型 + 可操作的修复提示（"除数为零，请检查表达式"），而非整页 traceback。
③ 幻觉工具解析后调用名不在注册表（registry）中。 回喂："ERROR: 工具 'web_search' 不存在。可用工具: ['calculator', 'unit_convert', ...]" ——把可用清单再报一遍。

修复循环的形状（注意与第 2 节的主循环是同一个循环，错误只是另一种 tool_result）：

调用 → 校验失败/执行异常/工具不存在
     → 构造结构化错误信息，作为该调用 id 的结果回喂
       （OpenAI: role="tool" 的 content 写错误文本；
        Anthropic: tool_result 加 "is_error": true）
     → 模型读到错误 → 修正参数 / 换工具 / 改为直接回答
     → 直到成功或触发 max_turns 保险丝
必须设 max_turns。模型可能陷入"调用失败 → 原样重试 → 再失败"的死循环， 每一圈都在烧 token 和时间。生产与评测 harness 都要有回合上限 + 预算上限双保险（模块 03 的 harness 会正式化这件事； 成本-准确率联合报告见 [Kapoor 2024]）。另外注意安全面：错误信息会进入模型上下文， 若工具输出来自不可信外部源，这条回喂通道就是 prompt injection 的入口——模块 08 展开。

7工具调用的可靠性度量

把"这个模型工具用得好不好"变成可测量的问题，至少要拆成三层指标，逐层归因：

  • 调用格式正确率（format correctness）：输出能否被解析为合法调用（JSON 可解析、字段齐全、工具名存在）。 纯语法层，prompted 路线的第一道坎。
  • 参数正确率（argument correctness）：解析成功的调用中，工具名与参数是否语义正确。 可用精确匹配、schema 校验通过率，或更稳健的执行等价（执行后结果一致）来判。
  • 多步任务成功率（end-to-end success）：整条轨迹最终是否完成任务——这是模块 06 的主战场。

三层指标的统计处理。单层指标是伯努利试验：$N$ 次独立采样中 $k$ 次成功，

$$ \hat{p} = \frac{k}{N}, \qquad \mathrm{SE}(\hat{p}) = \sqrt{\frac{\hat{p}(1-\hat{p})}{N}} $$

$N=10$ 时标准误最大可达 $0.16$——所以 notebook 里"跑 10 次"的小实验只能看趋势，报告论文级结论需要 $N$ 上百并给置信区间。 更要命的是多步复利效应：若每步成功率为 $p$ 且近似独立，长度 $T$ 的任务成功率为

$$ P(\text{task}) \approx p^{T} \qquad\Rightarrow\qquad 0.99^{50} \approx 0.605,\quad 0.95^{50} \approx 0.077 $$

单步 95% 听起来很高，50 步任务就只剩 8%。这就是为什么 agent 评测对单步工具可靠性如此敏感， 也是为什么"把任务长度作为自变量"成为 METR 时间跨度方法 [Kwa 2025] 的核心设计。 另一个为模块 06 埋线的指标是 τ-bench [Yao 2024] 提出的 pass^k： 同一任务独立跑 $k$ 次全部成功的概率（$\text{pass}^k = \mathbb{E}_{\text{task}}\big[\binom{c}{k}/\binom{n}{k}\big]$， $n$ 次试验 $c$ 次成功）——它度量的是可靠性而非"碰运气的最好成绩"，与 pass@k 恰好是对偶的两个方向。

做评测时的实操清单：①固定温度与随机种子策略并写进报告；②格式错误与语义错误分开计数（否则你不知道该修 parser 还是换模型）； ③同一指标在原生 / prompted 两条路线上不可直接比较——它们度量的能力组合不同（见第 4 节表格）。

8研究前沿与开放问题

  • 工具学习的训练范式之争：自监督插入（Toolformer [Schick 2023]）、大规模 SFT（ToolLLM [Qin 2023]）、 还是 RL 直接以任务成功为奖励？RL 路线正在成为前沿实验室主流，但奖励黑客（reward hacking）会以"看起来调了工具"的形式出现—— 评测上需要执行级验证而非格式级验证。
  • API 海量化与工具检索：当可用工具从 3 个变成 16,000 个 [Qin 2023]，schema 无法全部塞进上下文。 工具检索（tool retrieval / tool search）把"选工具"变成一个检索问题——评测时检索器的召回率成为系统瓶颈的新候选， 归因又多了一层。
  • MCP 标准化趋势：Model Context Protocol（Anthropic 2024 年开源，2025 年起被各家客户端与框架广泛采纳） 把"工具提供方"与"agent 框架"解耦成客户端-服务器协议：工具一次封装、处处可用。 对评测的影响是双向的——生态统一让跨模型横评更公平；但第三方 MCP server 也引入了新的供应链与注入攻击面（模块 08）。
  • schema 的自动优化：既然 schema 质量显著影响正确率（第 5 节），能否让模型自动改写工具描述并以调用正确率为目标迭代？ 初步工作显示可行，但存在对特定模型过拟合的风险——"为 GPT 调优的 schema"未必利好 Claude，横评时要警惕。
  • 开放问题：格式能力与决策能力的解耦度量。约束解码可以把格式正确率推到 100%， 但它是否会损伤决策质量（模型被迫在不该调用时也输出合法调用）？目前缺少系统性研究，是一个适合 evaluation 研究者切入的空白。
