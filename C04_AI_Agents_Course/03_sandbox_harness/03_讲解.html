1为什么 agent 必须进沙箱

模块 02 里你写的 ReAct agent 还只能调用我们手工注册的安全工具。但真正有用的 agent ——编码 agent、计算机操作 agent ——必须能执行任意代码。这一步跨出去，性质就变了：

能执行代码的 agent = 能搞坏环境的 agent。它可以删文件、占满磁盘、发起网络请求、修改自己的评测脚本。这不需要假设任何"恶意"——模型只要在解一个任务时犯傻（比如把清理命令的路径写错），宿主机就遭殃。因此沙箱（sandbox）不是可选的工程优化，而是 agent 评测的前提条件。

容易被忽略的是：沙箱的动机有两个，安全只是其一，另一半是科学性。评测对环境提出了三条硬要求：

  • 隔离（isolation）：agent 的副作用不能逃出边界——既保护宿主机，也保护评测本身（agent 不能读到评分脚本或参考答案）。
  • 可重置（resettable）：第 $i$ 次 run 不能看到第 $i-1$ 次 run 留下的文件、进程、缓存。否则各次 run 不再独立，pass@k、方差估计全部失真。
  • 可复现（reproducible）：今天跑和三个月后跑，环境逐字节一致（固定镜像、固定依赖版本），分数才可比、回归才可查。

直白讲

沙箱就是一个"随便弄坏、坏了就扔"的隔离工作区：agent 在里面想干嘛干嘛，干完我们把它整个删掉、按同一份模板重建一个全新的。这样每次实验的起点一模一样，agent 闯了祸也波及不到外面。

严谨讲

沙箱定义了一个状态空间受限的环境 $E$、一条副作用不可穿越的隔离边界，以及一个重置算子 $\mathrm{reset}:E\to E_0$，保证每个 episode 都从同一初始状态 $E_0$ 出发。这使得多次 run 的结果可视为对同一分布的独立采样，统计量（成功率、方差、置信区间）才有定义。

不重置环境是 agent 评测最常见的低级灾难之一：上一次 run 留下的中间产物让下一次 run "莫名其妙地成功"（状态泄漏），或者残留进程占着端口让后续全部失败。更隐蔽的是评测信息泄漏——如果评分函数、参考答案或其他任务的解放在 agent 可读的路径里，能力分数会被系统性高估。设计沙箱时要把"agent 会主动翻文件系统"当作默认假设。

承载这一切的程序叫 harness（评测脚手架）：它负责搭环境、把任务指令交给 agent、转发工具调用、记录所有事件、计时计费、调用评分函数、回收环境。本章的 notebook 会带你从零写一个最小但五脏俱全的 harness。

2隔离层级阶梯：subprocess → container → VM → air-gapped

隔离不是有或无，而是一道阶梯。每上一级，防御面更宽、成本更高。选哪级取决于威胁模型：你评的是温顺的小模型写排序算法，还是 frontier 模型的自主复制能力？

网络是单独一根轴，与上述阶梯正交：一个 Docker 容器若放行了外网，模型可以下载工具、查题解，甚至把数据发出去——隔离级别再高也被这条通道击穿。所以 METR Task Standard 把网络权限做成任务的显式声明（见下一节），评测报告也必须注明任务是否允许联网，否则分数不可比。

3METR Task Standard 解剖：任务即标准包

有了沙箱，下一个问题是："一个任务"到底是什么？如果每个研究者都用自己的脚本、自己的目录约定、自己的评分写法，任务就无法交换、无法复跑、无法审计。METR 给出的答案是 Task Standard [METR 2024]：把任务定义成一个自包含的标准包——

一个 Task Standard 任务包 ┌────────────────────────────────────────────────────────┐ │ 环境镜像 (Dockerfile / 基础镜像) │ │ └── 依赖、数据、初始文件 —— 可复现的 E₀ │ │ TaskFamily (Python 类) │ │ ├── get_tasks() # 一族任务的参数化变体 │ │ ├── get_instructions(t) # 给 agent 的自然语言指令 │ │ ├── start(t) # 启动时布置环境(写入文件等) │ │ ├── score(t, submission) # 评分函数 → [0,1] 或 None │ │ └── get_permissions(t) # 资源/权限声明(如 full_internet)│ └────────────────────────────────────────────────────────┘ ▲ 任务作者只写这个包 ▼ 平台(Vivaria)负责其余 搭环境 · 注入指令 · 转发 agent 行动 · 记录轨迹 · 计分 · 回收

四个组成部分各司其职：

  • 镜像：环境的可复现载体。固定到镜像 digest，三个月后重跑就是逐字节同一个环境。
  • instructions：agent 看到的任务说明。注意它是任务包的一部分而不是评测者临场写的 prompt——指令措辞会显著影响成绩，必须版本化。
  • 评分函数：score(t, submission) 在环境内部检查产物（跑测试、对比输出），返回 $[0,1]$ 分数；返回 None 表示需要人工评分。评分逻辑与任务同包，杜绝"换个评分脚本分数就变"。
  • 资源声明：需要 GPU 吗？允许联网吗？需要哪些环境变量（如 API key）？显式声明使平台能统一执行最小权限原则。

为什么标准化任务格式对评测机构至关重要？因为评测机构的核心资产是"任务 × 模型 × 时间"的矩阵：同一批任务要跑在不断更新的模型上，纵向比较能力增长 [Kwa 2025]。如果任务格式不标准——

  • 每接入一个新 agent/模型都要为每个任务做适配，$O(\text{任务}\times\text{agent})$ 的工程量爆炸；标准化后是 $O(\text{任务}+\text{agent})$；
  • 外部贡献的任务无法质检（QA 一个任务 = 检查它符合 Task Standard 接口并在参考解上得满分）；
  • 历史分数不可信（无法证明今天的环境与当年一致）。
METR Task Standard / Vivaria [METR 2024]：Task Standard 定义任务包格式；Vivaria 是配套的开源运行平台——启动任务环境、接入 agent、记录完整轨迹、支持人类基线实验与人工接管。UK AISI Inspect [UK AISI 2024] 是另一套主流开源框架：任务 = dataset + solver + scorer，内置 Docker 沙箱与统一的评测日志（eval log）格式及查看器。两者是当前 agent 评测基础设施的两个参考实现，notebook 里我们手写的迷你 harness 正是它们的同构缩影。

4轨迹即证据：事件模型与完整性要求

agent 评测的原始产出不是一个分数，而是一条轨迹（trajectory）：episode 中发生的全部事件的有序记录。分数只是轨迹的一个汇总统计量。把轨迹当成证据（evidence）来设计——它要经得起事后审计：为什么这个 run 算成功？模型真的自己解出来的，还是评分函数有漏洞、还是环境泄漏了答案？

工程上，轨迹最常用的形态是追加写的 JSONL 事件流：每行一个事件，写完即落盘（崩溃也只丢最后一行）。最小事件模型四种类型：

事件类型必记字段用途
llm_call模型 id、完整输入 messages、采样参数（temperature/seed/max_tokens）、完整输出、token 用量、时延重放的素材；审计模型"看到了什么、说了什么"
tool_call工具名、完整参数、发起它的 step、时延还原 agent 的行动序列；安全审查（它试图执行什么命令？）
observation工具返回（stdout/stderr/退出码）、是否截断、是否超时还原 agent 的信息输入；调试环境问题
score评分器版本、分数、判分依据、最终答案结果本体；支持事后用新评分器重算

外加 episode 级元数据（任务 id、镜像 digest、harness 版本、开始/结束时间戳）。完整性要求：进出模型的每一个 token 都可审计。这不是洁癖，而是三类下游需求决定的：

  • 归因调试：失败是模型不会、解析器写炸、还是环境坏了？没有完整轨迹只能猜（模块 06 详述失败归因）。
  • 重放与重评分：第 5 节的录制-重放、以及"评分函数修了个 bug，历史 run 全部重算"都要求轨迹无损。
  • 安全审查：评 frontier 模型危险能力时，轨迹是向外界证明"评测确实这样发生过"的唯一凭据。
"给模型截断" ≠ "给日志截断"。工具输出太长时，harness 通常截断后再喂给模型（防上下文爆炸）——但日志里应同时记录原始输出（或其哈希+存档引用）和实际喂给模型的截断版。只存截断版，重放时无法验证截断逻辑本身没改变行为；只存原始版，你不知道模型实际看到了什么。notebook 练习 1 就是实现这个截断器。

代价是隐私与体积：完整轨迹可能含密钥（环境变量被 env 打出来）、用户数据、专有代码；长时程任务一条轨迹可达 GB 级。常见权衡手段：写入前对已知 secrets 做脱敏（redaction）、大对象内容寻址存储（轨迹里只存哈希）、对 observation 分层存储（热存截断版、冷存原始版）——但 llm_call 的输入输出永远全量保留，那是证据链的主干。

5确定性与重放：录制-重放测试法

harness 本身是软件，也会有 bug。怎么测一个依赖 LLM 的系统？每次跑真模型既贵又不稳定。答案是重放（replay）：用日志里录好的 LLM 输出替代真实调用，重新执行整条循环。

直白讲

录一次真实 run，把模型每一步说的话存下来。之后测试时不再调真模型，而是用一个"复读机"按顺序吐出录好的回复。如果 harness 没变，重跑的每一步观察、最终答案都应该和录的那次一字不差；改了解析器之后重放结果变了，就说明你的改动影响了行为——这就是免费的回归测试。

严谨讲

设轨迹 $\tau=(a_1,o_1,a_2,o_2,\dots,a_T)$，其中 $a_t$ 为模型输出、$o_t$ 为环境观察。若环境转移 $o_t=f(\text{state}_{t-1},a_t)$ 是确定的，则注入录制的 $\{a_t\}$ 序列必复现 $\{o_t\}$ 与终态。重放校验即检查 $\forall t:\ o_t^{\text{replay}}=o_t^{\text{log}}$；首个失配位置 $t^\*$ 精确定位非确定性或行为变更的引入点。

重放成立的前提是除 LLM 外一切皆确定。现实中非确定性来源很多，要逐一识别和控制：

非确定性来源表现控制手段
LLM 采样temperature>0 时每次输出不同；即使 T=0，浮点归约顺序/批处理差异也不保证逐位一致评测时记录采样参数与 seed；测试 harness 时直接用重放替身，绕开真实推理
时间戳 / 随机数agent 脚本里 time.time()、random() 产生不同输出固定 seed、冻结时钟（注入假时间源），或在比对时排除易变字段
并发并行工具调用完成顺序不定，观察交错顺序变化评测中序列化工具调用，或记录并在重放时强制原顺序
外部 API / 网络搜索结果、网页内容随时间漂移录制-重放外部响应（VCR 式 mock）、镜像静态站点、或干脆断网
环境本身依赖版本漂移、文件遍历顺序镜像固定 digest；代码中显式 sorted()
重放还有第二个妙用：把"贵的"和"便宜的"分开迭代。轨迹录一次（贵，调真模型），此后解析器重构、日志格式迁移、评分函数修复都在重放上验证（免费、毫秒级）。Inspect 的 eval log、Vivaria 的 run 记录都支持这种工作流 [UK AISI 2024; METR 2024]。notebook 里你会亲手实现 ReplayLLM 并用 assert 验证重放一致性。

6超时、重试与部分失败：评测口径要先定

长时程 agent run 里，"失败"不是一个点而是一个谱：模型答错、单步卡死、整个任务超时、API 限流、harness 崩溃、评分器抛异常……每一种怎么计分，必须在跑评测之前定好，否则数字出来后怎么算都像在挑对自己有利的口径。

两级超时

  • 步级超时（per-step）：单次工具调用的上限（如 60s）。超时后 kill 该调用，把"超时"作为 observation 还给 agent——agent 还有机会换策略。这是环境反馈的一部分。
  • 任务级超时（per-task）：整个 episode 的墙钟/token 预算（如 8 小时或 200 万 token）。打满即终止 episode。这是评测口径的一部分——METR 的 time-horizon 方法学里，预算本身就是自变量 [Kwa 2025]。

重试会污染统计口径

关键区分：基础设施重试（HTTP 500、限流退避——重试后输入完全相同）可以做且应该做，它修复的是测量仪器；episode 级重试（失败了重跑一次任务取最好结果）则直接改变了被测量的量。设单次尝试成功率为 $p$，允许 $k$ 次独立尝试取最好：

$$ P(\text{至少一次成功}) \;=\; 1-(1-p)^k \;\;\xrightarrow{\;p=0.3,\,k=5\;}\;\; 0.83 $$

把 0.83 当作"成功率"报告，等于偷偷把指标从 pass@1 换成了 pass@5。正式的口径用无偏估计量写清楚：对某任务做 $n$ 次采样、$c$ 次成功，则

$$ \widehat{\text{pass@}k} \;=\; 1-\frac{\binom{n-c}{k}}{\binom{n}{k}} \qquad\text{vs}\qquad \widehat{\text{pass}^{\wedge}k} \;=\; \frac{\binom{c}{k}}{\binom{n}{k}} $$

pass@k（$k$ 次中至少一次成功）衡量能力上限，随 $k$ 单调上升；pass^k（$k$ 次全部成功，τ-bench 提出）衡量可靠性，随 $k$ 单调下降 [Yao 2024]。同一组 run，两个口径讲两个故事——报告里必须写明 $n$、$k$、采样温度与重试政策。

部分失败的计分政策

失败类型例子建议处理
agent 失败答案错误、放弃、超预算计 0 分——这是被测能力的一部分
环境/基础设施错误容器起不来、API 持续 5xx标 error 并剔除后重跑，不计 0——否则系统性低估
harness bug解析器把合法动作判为非法修复后整批重跑；轨迹是发现它的唯一手段
评分器异常score() 抛异常标 error 人工复核；绝不能静默当 0 分
最危险的模式是把基础设施错误静默计为 0 分：模型 A 评测那周 API 不稳定，模型 B 那周一切正常——榜单上 A 输了，实际上输的是运维。轨迹里必须区分 failed（agent 没做到）与 error（我们没测成），并在报告中给出 error 率。Kapoor et al. 对 agent 评测的标准化缺失有系统批评 [Kapoor 2024]。

7资源计量：token、成本与墙钟时间

两个 agent 都得 80 分，一个花 \$0.4、6 分钟，另一个花 \$40、4 小时——"同分"显然不是同等能力。准确率必须与成本联合报告 [Kapoor 2024]，而联合报告的前提是 harness 在轨迹里逐事件计量资源：

  • token：每次 llm_call 记录 input/output token 数（API 会返回 usage；本地模型用 tokenizer 数）。注意 agent 循环里上下文滚雪球，input token 通常远大于 output。
  • 金钱成本：按价目表折算。设第 $i$ 次调用输入 $n_i^{\text{in}}$、输出 $n_i^{\text{out}}$ 个 token，单价 $p_{\text{in}},p_{\text{out}}$（每 token）：
$$ C \;=\; \sum_{i=1}^{N}\Big( n_i^{\text{in}}\,p_{\text{in}} + n_i^{\text{out}}\,p_{\text{out}} \Big) \;+\; C_{\text{compute}}(\text{沙箱机时}) $$
  • 墙钟时间：episode 总时长，并拆分为模型时间（等 LLM 返回）与工具时间（等命令执行）。两者的比例直接告诉你优化方向，也是与人类基线对比的基础——METR 的 time horizon 把"人类完成该任务所需时间"作为任务难度的标尺 [Kwa 2025]。

实现上零额外成本：第 4 节的事件模型里每个事件本来就带 duration_s 和 usage 字段，成本汇总只是对 JSONL 的一次聚合扫描（notebook 练习 2 实现 cost_summary）。这些数字在模块 06 会变成正式的评测维度：成本-准确率帕累托前沿、预算约束下的能力曲线。现在不记，将来没法补。

把计量做进 harness 而不是事后估算，还有一个理由：预算执行。任务级 token 预算、成本上限都需要 harness 实时累加才能在越界时终止 episode——这本身就是第 6 节"任务级超时"的资源版。

8研究前沿与开放问题

  • 沙箱逃逸面的系统化：容器逃逸、通过放行的网络通道外渗、利用评分函数本身的漏洞"作弊得分"——agent 评测的攻击面还没有像 web 安全那样的成熟分类法。评测视角：危险能力评测的可信度上限就是其沙箱的强度；报告里应披露隔离级别与网络策略。间接注入类攻击（环境内容反向操纵 agent）见模块 08 [Greshake 2023]。
  • 长时程任务的状态快照：8 小时的 run 跑挂了只能从头再来？VM/容器快照（checkpoint/restore）允许从中途恢复、甚至从同一中间状态分叉出多条延续来估计条件成功率。但快照与"可复现"存在张力：恢复点的内存状态难以逐位验证。Vivaria 的人工接管功能是这个方向的工程雏形 [METR 2024]。
  • 推理不确定性 vs 重放：T=0 也不保证逐位一致（批处理、浮点归约顺序），跨硬件更难。开放问题：评测报告应该要求什么粒度的"可复现"——逐位、逐事件、还是仅统计意义上的？
  • 轨迹格式的跨机构标准：Inspect eval log、Vivaria run 格式、各 lab 内部格式互不兼容，导致第三方无法复核。一个被广泛采纳的"轨迹交换格式"会像 ONNX 之于模型一样改变评测生态——目前 Inspect 的 log 格式是最接近事实标准的候选 [UK AISI 2024]。
  • 感知到被评测的模型：若模型能从环境特征识别出"这是沙箱/评测"，可能系统性改变行为（如 sandbagging，刻意藏拙 [van der Weij 2024]）。沙箱做得越"标准"，越容易被识别——逼真性与标准化的矛盾尚无好解。
