1索引会腐烂：三种腐烂，三种修法

前面四个模块的产物都是一次性的决策：解析器选定了、分块参数解出来了、查询流水线上线了。而索引是有状态的——它从建成的那一刻起就开始与现实脱节。

腐烂类型什么变了症状修法能不能局部修
内容腐烂源文档改了 / 删了答出旧政策；答出已删除内容增量索引（第 2 节）能——按 doc_id 定位
结构腐烂分块参数 / 解析器换了同一份内容以两种粒度共存，top-k 被自己造的近重复占满全量重建 + 原子切换（第 5 节）不能——新旧块混在一个索引里就是错的
模型腐烂embedding 模型升级相似度失去意义（第 4 节量这件事）全量重建 + 原子切换绝对不能——两个向量空间之间的距离没有含义

直白说

最后一列是这一节的重点。内容腐烂可以一份份修，而结构腐烂与模型腐烂必须整体换。把它们当成同一类问题处理（「那就慢慢迁移吧，先写新格式，旧的以后再说」）会产生一个既不是旧的也不是新的索引，而这个中间状态的行为是无法解释的——违反了 C68 模块 00 的第一条性质（差异可解释）。

严谨说

为什么模型腐烂「绝对不能」局部修？因为向量空间之间没有对齐关系。两个不同模型（甚至同一模型的两个版本）产生的向量，其内积不是相似度，而是一个没有含义的数。而它是一个「看起来很正常」的数——在 $[-1, 1]$ 之间，有分布，能排序。所以混用不会报错，只会安静地给出错误的排序，这是本模块最危险的一个失败。第 4 节把失真量出来。

有一个部署惯例会直接触发模型腐烂：把 embedding 模型名写成 latest 或不写版本。服务方更新模型后，新写入的向量与索引里的旧向量属于不同空间，而系统一切正常、没有任何报错。模型 ID 与版本必须钉死，并且写进索引的元数据里——这与 C69 模块 02「钉内容哈希而不是版本号」是同一类纪律。

2增量索引：三种语义，其中删除最容易做错

模块 01 已经给出了摄取契约。这一节把它扩展到持续运行的场景。

增量索引的三种操作 ┌──────────┬─────────────────────────┬──────────────────────────┐ │ 操作 │ 正确实现 │ 常见错误 │ ├──────────┼─────────────────────────┼──────────────────────────┤ │ 新增 │ upsert，主键 (doc,v,i) │ append → 重复摄取变两份 │ │ 更新 │ **先删该 doc 全部旧块** │ 只写新块 → 新旧块共存 │ │ │ 再写新块 │ （旧块永远不会被访问到 │ │ │ │ ……除非它比新块更像查询） │ │ 删除 │ 删块 + 写 tombstone │ 只从源库删 → 索引里还在 │ │ │ + **断言删除数 == 预期** │ 不断言 → 「删了 0 条」不报错 │ └──────────┴─────────────────────────┴──────────────────────────┘

直白说

「更新时只写新块」这个错误值得展开，因为它的症状很迷惑：大部分查询表现正常（新块通常更像查询，排在前面），但偶尔会返回旧内容——而「偶尔」取决于查询措辞与旧块的相似度。这类间歇性错误极难定位，因为它不可复现。

严谨说

删除则有一个额外的可验证性要求：删除操作必须返回删掉了几条，调用方必须断言这个数。「执行了删除但删掉 0 条」是一个必须能被发现的失败——它的成因通常是过滤条件写错（doc_id 大小写、路径归一化差异），而没有断言时它看起来是一次成功的删除。这在合规语境下是实质性的：用户被告知数据已删除，而它还在被检索。

删除的三层

  1. 索引里的向量与块——必须删。这是唯一决定「还能不能被检索到」的一层。
  2. 派生资产：摘要、三元组、实体倒排、缓存（第 7 节）。它们不删的话，内容会从另一条路回来。
  3. 日志与评测集——这一层通常不能简单删（会破坏历史可比性），正确做法是标记而不是物理删除，并在聚合时排除（与 C68 模块 01 的「坏题三条处理路径」同构）。

3新鲜度：过期答案率是可以算的

「索引多久重建一次」通常是拍出来的。它可以从两个可测的量算出来：滞后时间与变更率。

\[P(\text{某文档已过期}) = 1 - (1-p)^{L} \approx pL \quad (pL \ll 1)\]

直白说

$p$ 是单篇文档单位时间的变更概率（可以从源库的修改时间统计出来），$L$ 是索引滞后的时间（单位与 $p$ 一致）。$p = 1\%/\text{天}$、$L = 7$ 天时，约 6.8% 的文档在索引里是旧的。

严谨说

但真正要报的不是这个数，而是它对答案的影响：$$P(\text{答案过期}) = \sum_d \pi(d) \cdot \left(1 - (1-p_d)^{L}\right)$$其中 $\pi(d)$ 是文档 $d$ 被查中的概率。关键洞察：$\pi$ 与 $p$ 通常正相关——热门文档也是改得最频繁的文档（政策、价格、排班）。所以按「文档均匀」估出来的过期率会系统性偏低。notebook 第 3 节把两种估法的差距量出来。

变更率 p滞后 L过期文档比例该怎么办
1%/天7 天6.8%可接受（多数内部文档库）
1%/天30 天26%太高——缩短到周级
5%/天7 天30%太高——需要事件驱动增量
5%/天1 天5%可接受
20%/天1 天20%批量重建救不了——必须近实时增量

这张表给出的工程结论很直接：先测 $p$，再定重建周期，而不是反过来。而 $p$ 几乎总是能从源库的 updated_at 免费算出来——它是本模块成本最低、收益最高的一次测量。

两种更新策略

  • 批量重建：定时全量或增量扫描。简单、可预测；滞后等于周期的一半（平均）到一个周期（最坏）。
  • 事件驱动：源库变更触发单篇重索引。滞后可以做到分钟级，但需要一个可靠的变更流，而且必须有一条定时的对账任务——事件会丢，而丢了的那一篇会永久过期。对账做法：比对源库与索引里的 (doc_id, content_sha) 集合。

4换 embedding 模型：不可混用的全量迁移

这是本模块最重要的一节，因为它的错误做法不会报错。

❌ 渐进迁移（错） 新写入的块用新模型，旧块保持旧模型，同一个索引 → 查询用哪个模型编码？ 用新模型 → 与旧块的内积没有含义 用旧模型 → 与新块的内积没有含义 → 无论怎么选，**一半的索引在给出无意义的分数** → 而这些分数长得很正常：在 [-1,1] 之间，有分布，能排序 ✅ 双索引 + 原子切换（对） 1. 建影子索引（新模型），与主索引并存 2. 一致性校验：同一批查询在两个索引上的结果对比 3. 原子切换：改一个指针（别名 / 配置项 / DNS） 4. 保留旧索引 N 天，随时可回滚

直白说

为什么内积「没有含义」而不只是「不太准」？因为两个模型的向量空间的基是无关的。模型 A 的第 17 维编码的东西与模型 B 的第 17 维毫无关系，所以逐维相乘再求和这个操作，在数学上是一个随机投影的内积——它的期望是 0，方差取决于维度。

严谨说

notebook 第 4 节用两个「模型」（不同的哈希盐）把这件事量出来：同一段文本在两个空间里的向量，内积接近 0；而「一段文本与它自己的改写」在同一个空间里内积很高。于是混用索引时，跨空间的那一半块的分数会系统性地偏低——它们不是排在后面，而是几乎永远排在后面，等于那部分索引对检索不可见（而存储与账单照付）。

一致性校验该比什么

影子索引建好后不能直接切。但也不能要求「结果完全一致」——那等于要求新模型没有任何改进。正确的校验是三条：

  1. 覆盖率：两个索引的块数、doc 数、向量数必须完全相等。这是确定性检查，不相等就是漏了内容，直接阻断。
  2. 离线指标不降：在同一套评测集上跑 recall / fact-recall，按 C68 模块 04 的方法从方差推阈值，不要拍一个百分比。
  3. 结果重叠率作为观测量而不是门禁：报 top-k 的 Jaccard，但不设阈值——它低可能意味着新模型更好，也可能意味着更差，这个数本身不能判定方向。它的用途是：如果重叠率是 1.0，说明你其实没换成新模型（配置没生效）。

第 3 条的最后一句是一个真实的、便宜的自检：迁移后如果结果一点没变，先怀疑配置没生效，而不是高兴「新模型很稳」。

5双写与原子切换：中途状态必须不可达

切换的正确性只有一个要求：任何一个请求看到的，要么是完整的旧索引，要么是完整的新索引，不存在第三种状态。

时间线 t0 主索引=A(旧模型) 影子=B(新模型，空) t1 主索引=A 影子=B ← 全量回填中 t2 主索引=A 影子=B ← 回填完成，跑一致性校验 t3 主索引=B 旧=A ← **原子切换：改一个指针** t4 主索引=B 旧=A ← 观察期（保留 N 天） t5 主索引=B ← 删除 A 回填期间的新增/更新怎么办？ **双写**：写 A 也写 B。B 用新模型编码。 漏了双写的后果：切换后 B 缺了回填期间的所有变更， 而这个缺口**不会报错**——只是有些内容检索不到。

直白说

「原子」在实现上通常就是一个指针：向量库的 collection alias、配置中心的一个键、或者一个 ACTIVE_INDEX 环境变量。关键是它必须是单一来源，且读取方每次请求都重新读它——进程启动时读一次并缓存的实现，会让切换后旧进程继续用旧索引，于是同一时刻不同实例返回不同结果。

严谨说

回滚同样重要：切换后要保留旧索引 N 天，$N$ 至少覆盖「一个完整的业务周期 + 发现问题需要的时间」。而回滚必须是同一个指针的反向操作——如果回滚需要重建索引，那就等于没有回滚。notebook 第 5 节把切换与回滚都实现了，并演示中途状态（混版本）下的错误行为。

切换清单（六项，缺一项都可能出事）

  • 回填期间双写，且双写失败要报警而不是静默丢弃
  • 回填完成后覆盖率完全相等（确定性检查）
  • 离线指标不降（统计检查，阈值从方差推）
  • 切换是改一个指针，读取方每次请求重新读
  • 旧索引保留 N 天，回滚是同一指针的反向操作
  • 切换前后各跑一次监控基线（第 8 节的四项），否则切换后指标变差时你分不清是新模型的问题还是切换的问题

6多租户：两种隔离，选错了是安全问题

模块 03 说过「过滤必须前置」。这一节讨论更基本的一层：要不要给每个租户单独的索引。

方案隔离强度成本什么时候用
元数据过滤（共享索引）取决于每一次调用都带对了过滤条件低（一个索引）租户多、每个租户数据少；且过滤是不可绕过的默认值
独立索引 / 独立 collection结构性隔离——错误的租户根本连不到那个索引高（N 个索引的元数据与内存开销）租户少而大；或合规要求物理隔离
混合：大租户独立、小租户共享分档中最常见的落地形态；但要注意「小租户升级成大租户」时的迁移

直白说

选择的判据不是成本，而是「一次漏写的距离」：共享索引 + 可选的过滤参数 → 一行漏写就是一次跨租户泄漏；共享索引 + 必填的过滤参数 → 漏写会报错；独立索引 → 连错索引才可能出问题，而那是一个更显眼的错误。这是一个纵深防御的排序，而不是三个等价选项。

严谨说

无论选哪个，有两条必须做：① 租户维度的监控要分租户看——「某个租户的零结果率突然 100%」在总体指标里完全看不见；② 删除与新鲜度也是按租户的——一个租户要求删除数据时，你需要能枚举「属于这个租户的全部块」，而这依赖模块 01 把 tenant 写进了每个块的元数据。

一个具体的、常见的泄漏路径：缓存。查询侧缓存（模块 03 第 7 节）的键如果不含 tenant，那么租户 A 的结果会被租户 B 的相同查询命中。缓存键必须含租户标识——这一条与检索侧的过滤同等重要，而它更容易被忘。

7派生资产会静默过期

索引里不只有块的向量。凡是从文档「算出来」的东西，都必须跟着文档版本失效。

派生资产来自哪个模块不失效的后果
父块 / 摘要索引模块 02 第 6 节答案引用了新版本的子块，而喂给模型的父块是旧的
三元组 / 实体倒排模块 04 第 5 节图里还有一条已经不存在的关系；而图检索答出来的东西「不在任何块里」，所以无法通过引用核查发现
查询侧缓存模块 03 第 7 节文档更新了但缓存里是旧结果
同义词表 / 别名表模块 03 第 3 节指向了已删除的文档用词
离线评测集的 gold chunk id本课全程评测集悄悄失效——gold 块被重新分块后 id 变了，于是所有题的 recall 都是 0，而这看起来像一次严重的效果退化

直白说

统一的做法只有一条：每个派生资产都带上它依赖的 (doc_id, version) 或content_sha，并在读取时校验。不匹配就当缓存未命中（重新计算）或报警，而不是照用。

严谨说

最后一行值得单独说，因为它会造成一次假的效果事故：换了分块方案后，评测集里记录的 gold_chunk_id 全部失效，recall 掉到 0，看起来像新分块方案彻底失败。正确做法是评测集记录「答案文本 + doc_id」而不是 chunk_id——本课全程用「答案字符串是否在召回的块里」判定，正是为了避免这个问题。这与 C68 模块 01「不要用内容哈希当 ID」是同一类教训：不要把标注绑在会变的东西上。

8检索层的监控四项 + 门禁

C68 模块 05 讲了线上监控的一般框架（PSI/KS、漂移、闭环）。这一节只给检索层特有的四个指标，它们都不需要真值。

指标怎么算它能抓到什么分租户看吗
零结果率候选集为空或 top-1 分数低于阈值的请求占比过滤条件写错（模块 03 第 5 节）、索引被清空、租户配置错必须
top-1 分数分布分位数（P10/P50/P90）embedding 模型被换掉了 / 混用了两个空间（左尾变重，中位数可能不动）、索引损坏建议
引用率生成的答案里带引用的比例 / 引用被点击的比例召回质量下降（模型找不到可引用的依据）建议
新鲜度滞后$\max_d (\text{now} - \text{indexed\_at}_d)$ 与 P99增量任务挂了、事件流丢消息（第 3 节的对账）必须

直白说

四个指标里「top-1 分数分布」最容易被忽略，但它是模型腐烂的唯一线上信号。混用了两个 embedding 空间时，跨空间那部分块的分数会被压到接近 0，于是分布的左尾变重——而中位数可能一点不动——而其它三个指标都可能完全正常。

严谨说

门禁按 C68 模块 04 的分级：确定性项阻断（新旧索引的块数不等、任一租户的零结果率 100%、新鲜度滞后超过 SLA），统计项报警（分数分布的 PSI、引用率的变化）。把统计项设成阻断是「门禁被关掉」这一结局的起点。

9索引的容量与成本：三个乘数

索引运维的最后一件事是账。向量索引的成本有三个乘数，而它们都容易被低估。

\[\text{cost} \approx N_{\text{doc}} \times \frac{L_{\text{doc}}}{s-o} \times \big(d \cdot b + m_{\text{meta}}\big) \times (1 + r_{\text{shadow}})\]
乘数它是什么容易被低估的原因
$\frac{L_{\text{doc}}}{s-o}$（每文档的块数）由分块参数决定重叠是分母里的减项：$s=400, o=62$ 时块数是无重叠的 1.18 倍，而 $s=100,o=59$ 时是 2.44 倍（模块 02 第 3 节）
$d \cdot b$（每向量的字节数）维度 × 每维字节换一个「更好的」嵌入模型经常同时把维度从 768 提到 1024–3072，而这是一个 1.3–4 倍的存储与内存乘数，还会同时抬高检索延迟
$1 + r_{ ext{shadow}}$（影子索引期间）迁移期间两份索引并存迁移期间容量翻倍，而「保留旧索引 N 天」意味着这个翻倍要持续 N 天（第 5 节）

直白说

第二行值得展开，因为它是一个常见的、被低估的决策。「升级到更强的嵌入模型」在账面上不只是一次重建：维度变大 → 向量存储与内存按比例增长 → 检索延迟增长 → 如果用了量化（C11 模块 02 的 PQ），量化参数也要重调。所以这个决策该先在离线集上量出「fact-recall 提升多少」，再和这一串成本一起看。

严谨说

还有一项不在公式里的成本：元数据的基数。本课要求每个块带 doc_id / version / chunk_index / start / end / section_path / tenant / effective_date / element_type——这些字段的存储通常与向量本身同量级，而且它们上面的索引（用于前置过滤）还要额外开销。但它们不是可以省的：模块 01 第 5 节已经说过，缺任一个都会让某个运维操作变得不可能。正确的做法不是砍字段，而是把它们放在合适的存储里——过滤要用的进向量库的 metadata，只用于展示的放外部表按需取。

一个能立刻用上的估算：先算「每文档块数 × 向量字节数」，再乘 2（影子期）。如果这个数已经超出预算，那么在选嵌入模型之前，先回去看模块 02 的成本倍数——把重叠从「块长的 20%」改成「最长答案 −1」通常能省掉一大截。
