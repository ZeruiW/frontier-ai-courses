1查询侧的四个动作，顺序不能换

模块 01 和 02 决定了索引里有什么，而它们都是摄取时的决策——改一次要重建索引。查询是整条流水线里唯一可以在运行时、按请求、零成本回滚的东西。这让它成为迭代最快的一层。

查询进来之后的四个动作（顺序不能换） 用户查询 │ ├─① 路由 route ────► 这个查询该不该检索？该查哪个索引？ │ 不该检索的直接放行，**不要注入噪声** ├─② 改写 rewrite ──► 补上下文（多轮）、消解指代、对齐文档用词 │ ├─③ 扩展 expand ───► 一个查询变多个（同义、子问题、HyDE），并行检索后融合 │ └─④ 过滤 filter ───► 元数据硬约束（租户、时效、章节、语言） **必须在检索之前，不能在 top-k 之后** │ ▼ 检索（C11 的地盘）

直白说

为什么顺序不能换？因为每一步的输入是上一步的输出，而且它们的失败方式不同。路由放在最前，因为「不该检索」的查询根本不需要后面三步；过滤放在最后但必须作用于检索之前——它是一个作用在候选集上的硬约束，放到 top-k 之后就变成了「把已经算好的结果扔掉」，这是本模块第 5 节要量的一个具体错误。

严谨说

更准确地说，四个动作作用在不同的对象上：① 作用在请求上（要不要走这条路）；② 作用在查询文本上（$q \to q'$）；③ 作用在查询集合上（$q \to \{q_1, \dots, q_m\}$，然后需要一个融合算子把 $m$ 个排序合并成一个）；④ 作用在候选集上（$C \to C \cap F$）。③ 与 ④ 的交换律不成立——先融合再过滤和先过滤再融合会给出不同的 top-k，而正确的是后者（每一路都在同一个受约束的候选集上排序）。

有一条实用的判据可以决定「该不该在查询侧加东西」：如果这个改动可以只对 1% 的流量开启并在十分钟内关掉，它就属于查询侧；否则它属于摄取侧。这也说明了为什么查询侧值得优先投入：它的实验成本最低。

2路由：第一个问题是「该不该检索」

大多数 RAG 系统对所有查询都检索。这是一个默认值，不是一个决定，而它有真实的代价。

查询类型例子检索的结果该怎么做
闲聊 / 元问题「你好」「你能做什么」召回一堆无关制度条款直接放行，不检索
可自答的常识 / 计算「3000 除以 12 是多少」召回含数字的无关块，反而可能把模型带偏不检索
需要外部知识「餐饮报销上限多少」正常工作检索
多轮追问「那差旅呢」召回失败——「那差旅呢」几乎没有可匹配的信号先改写成独立查询（第 3 节），再检索
跨库「上季度的销售数据」在文档库里找不到路由到结构化数据源

直白说

「不该检索却检索了」的伤害不是零。无关上下文会挤占预算，而且它带进来的具体数字与条款会成为干扰项。notebook 第 1 节用一个「从上下文里取第一个数字」的规则型回答器把这件事量出来——它是模型「被上下文带偏」这个真实行为的一个诚实的、可控的替身。

严谨说

路由本身是一个分类问题，而它的两类错误代价不对称：漏检索（该查没查）的代价是答不上来；误检索（不该查却查了）的代价是注入噪声。前者通常更严重，所以路由器应当偏向检索——只在高置信度下才跳过。实现上最稳的一档是规则 + 兜底：明确的闲聊/计算模式走规则跳过，其余全部检索；不要一上来就用一个 LLM 分类器，它的误检索率你没有数据去估计。

3改写：三种做法与它们各自的边界

改写解决的是模块 00 里那个「词汇鸿沟」失败：用户的问法和文档的写法不共享词。

做法怎么做成本边界
同义词/别名表维护一张「用户词 → 文档词」的映射，字符串替换近零，可缓存只能覆盖你想到的词；但它对高频词的收益极高，而且是唯一可以被审计和回滚到具体一行的做法
LLM 改写让模型把查询改成「文档里会怎么写」，或消解多轮指代一次额外调用，必须缓存会改变语义——「不含增值税」被改成「增值税」是真实发生的事故；所以改写结果要与原查询并行检索后融合，而不是替换
HyDE（假设性文档嵌入）让模型先编一个答案，用这个假答案去检索一次额外调用把查询从「问句空间」搬到「答案空间」，对问答风格不匹配的语料收益最大；但它会放大模型的知识偏见——编出来的假答案含错误实体时会检索到错误的地方

直白说

HyDE 的机制值得单独说清楚，因为它常被误解成「让模型猜答案」。它真正做的是换一个嵌入的输入：问句和陈述句在向量空间里的分布本来就不同（问句有疑问词、没有具体数值），而文档全是陈述句。用一个（可能错的）陈述句去检索，比用一个正确的问句更接近目标分布。

严谨说

notebook 第 3 节量了这件事：原查询与目标文档的相似度只有 0.05，而一个「粗糙的、内容并不正确」的伪答案就把它拉到 0.48。这正是 HyDE 的关键性质：伪答案不需要正确，只需要在正确的文体与词汇分布里。推论：HyDE 的伪答案不该用高温度采样多个，也不该追求事实正确——它只需要像一段文档。

改写的两条硬纪律：① 永远保留原查询作为并行的一路（改写坏掉时还有兜底）；② 改写器是 harness 的一部分，它的版本必须进指纹（C68 模块 02）——换了改写 prompt 而指纹不变，两次评测就不可比而看起来可比。

4多查询融合：为什么它降的是方差

一个改写有可能变好，也有可能变坏。多查询融合的价值不是「更好」，而是「更稳」——这个区别决定了怎么评估它。

直白说

机制：$m$ 个改写各自检索，得到 $m$ 个排序，用 RRF 把它们合成一个。某一路改写偏了，它在融合里只占 $1/m$ 的权重；而所有路都同意的文档会被推到最前。所以融合把「单次改写的运气」平均掉了。

严谨说

RRF 的定义（C11 模块 03，此处只引用）：$\text{RRF}(d) = \sum_{i=1}^{m} \frac{1}{k_0 + \text{rank}_i(d)}$，$k_0$ 常取 60。它只用排名不用分数，所以不同改写之间的分数尺度不需要对齐——这正是它在多查询场景里比「分数加权平均」更实用的原因。notebook 第 4 节量的是跨改写的召回率标准差：单路的方差明显大于融合后的方差。

单路 vs 融合（示意） 改写 A → recall 0.9 ┐ 改写 B → recall 0.5 ├─ RRF ─► recall 0.8，**但方差远小于单路** 改写 C → recall 0.8 ┘ 单路: 均值 0.73，标准差 0.17 ← 你不知道线上会抽到哪一路 融合: 0.80，标准差 ~0.03 ← 稳定 注意: 融合后的均值**不一定**高于最好的那一路（0.9）。 融合买的是「不会掉到 0.5」，不是「一定拿到 0.9」。

这解释了一个常见的失望：「我加了多查询融合，最好情况下的效果反而降了」——这是预期行为。如果你有办法可靠地挑出最好的那一路，就不需要融合；而正因为挑不出来，融合才有价值。

成本：$m$ 路检索的延迟可以并行掉，但嵌入调用与向量库查询的次数是 $m$ 倍。实践中 $m = 3$（原查询 + 一个同义改写 + 一个 HyDE）是一个常见的甜点，而且这三路的失败模式互不相同——这比三个同类型改写更有价值。

5过滤：必须在检索之前

元数据过滤看起来是个实现细节，但「在检索之前过滤」和「在 top-k 之后过滤」是两个不同的算法，结果差别巨大。

后置过滤（错） 前置过滤（对） 全库检索 top-10 候选集 = 全库 ∩ 过滤条件 │ │ ▼ ▼ 在这 10 条里筛过滤条件 在受约束的候选集里检索 top-10 │ │ ▼ ▼ **可能只剩 0-2 条** 稳定拿到 10 条 为什么: 如果满足过滤条件的文档只占全库 5%， 那么全库 top-10 里期望只有 0.5 条满足条件。

直白说

这个错误在小规模测试时常常不暴露，因为测试库里满足条件的文档占比很高。上线后租户变多、时间窗变窄，占比一掉，top-k 就被清空了。症状是「有些用户什么都搜不到」，而检索层没有任何报错。

严谨说

定量地说：设满足过滤条件的文档占比 $\phi$，且相关性与是否满足条件独立，则后置过滤后剩下的条数近似 $\text{Binomial}(k, \phi)$，期望 $k\phi$，而 $P(\text{一条都不剩}) = (1-\phi)^k$。$k = 10, \phi = 0.05$ 时这个概率是 0.60——六成的请求会返回空。notebook 第 5 节把这条曲线量出来。

两个必须报警的事件

  • 过滤后候选集为空或过小——这通常意味着过滤条件写错了（模块 01 第 4 节：过滤是硬约束，没有中间状态）。报警而不是静默返回空。
  • 过滤条件里出现了非预期的字段值——比如租户 ID 是 None。这类值在「过滤」语义下会静默匹配到全部或全不匹配，而前者是一次跨租户泄漏（模块 05）。

多租户场景下这一条是安全边界，不是性能优化：租户过滤必须在检索之前，且必须是不可绕过的默认值——由调用方「记得传 tenant」的设计，等于把一次泄漏的距离缩短到一行漏写的代码。

6向量检索对否定与数值约束几乎失明

这一节是一个能力边界，而认清它比试图修它更重要。

「包含增值税的发票」与「不包含增值税的发票」在向量空间里几乎是同一个点。notebook 第 6 节量出来的相似度是 0.94——一个「不」字改变了全部语义，却几乎不改变向量。

直白说

原因不难理解：嵌入是词的聚合，而否定词是一个短词，它对聚合结果的贡献很小。本课的玩具嵌入把这个问题放大了，但真实的句嵌入模型在否定上确实也弱——这是一个被反复报告的已知局限，不是实现问题。

严谨说

同样失明的还有数值与时间的比较：「超过 5000 元的合同」与「不超过 5000 元的合同」、「2024 年之后生效」与「2024 年之前生效」。向量空间没有序关系。结论很直接：否定、数值区间、时间窗、集合成员——这四类约束必须走结构化过滤，不能指望嵌入。

约束类型向量检索正确做法
否定（「不含 X」）几乎失明（cos ≈ 0.94）把否定项抽出来，作为排除过滤器
数值区间（「超过 5000」）无序关系抽成 where amount > 5000
时间窗（「今年的」）无序关系抽成 effective_date 范围（模块 01 的元数据）
集合成员（「只看 A 部门」）只能靠词共现，不可靠抽成 where dept in (...)

所以查询侧的第一步其实是一次「结构抽取」：把查询里的硬约束抽出来变成过滤器，剩下的语义部分交给向量检索。这也是为什么模块 01 的元数据必须抽全——抽不到的字段，这里就没有可用的过滤器。

7查询侧的成本与缓存键

改写与 HyDE 都要额外调用模型。查询侧的缓存命中率通常很高（用户的问法高度重复），所以缓存是这一层最划算的一件事。

查询侧缓存的键（漏一项就会读到旧结果） key = sha256( 原始查询, ← 显然 路由决策版本, ← 路由规则改了，结论可能变 改写器标识 + prompt 哈希, ← **最常被漏的一项** 同义词表版本, 模型 ID + 温度, ← 温度 > 0 时改写结果不确定 扩展路数 m, ) 注意: 温度 > 0 的改写**不该缓存单次结果**， 要么固定温度为 0，要么缓存「一组」改写并整组复用。

直白说

这与 C68 模块 02 的缓存键是同一条纪律，只是对象从「评测配置」换成了「查询处理配置」。失败症状也一样：改了 prompt 而分数一点不变，然后被误读成「这个改动没有效果」。

严谨说

还有一个查询侧特有的成本项：扩展 $m$ 路会让向量库的 QPS 变成 $m$ 倍。这在延迟上可以并行掉，但在容量上不能——$m = 3$ 意味着向量库要按三倍流量做容量规划。所以 $m$ 是一个必须写进容量文档的参数，不只是一个效果旋钮。

8查询侧的评测：不能用文档原句当查询

这是本模块最容易被忽略、后果最严重的一条。

直白说

构造评测集最省事的做法是：从文档里挑一句话，把它改成一个问题，作为查询。这样构造出来的查询与目标文档共享大量词，于是词汇鸿沟这个失败在你的评测集上根本不存在——而它在真实流量里是最常见的失败之一。

严谨说

后果是系统性的：你会测出一个虚高的 recall，并且会得出「查询改写没有收益」这个错误结论（因为在你的评测集上确实没有）。这是一个典型的评测集与目标分布不匹配——与 C68 模块 05 的「离线-在线不匹配」是同一类问题，只不过这里的不匹配是构造方式带来的，一开始就在里面。

三条构造纪律

  1. 查询必须来自真实用户，或至少是「不看文档的人」写的。看着文档写问题的人会不自觉地用文档的词。
  2. 每个问题准备 2–3 个改述（paraphrase），并分别报分。改述之间的分数差就是这个系统对表述的敏感度——它是查询侧改动最该关注的指标，比平均 recall 有信息量得多。
  3. 专门留一个「跨词汇」子集：问法与文档用词刻意不重叠。查询侧的所有改动都应该在这个子集上看收益；在整体集上看会被大量「本来就能答对」的样本冲淡。

一个便宜的自检：算一下你的评测查询与目标块的词重叠率。如果它显著高于真实流量的重叠率，你的评测集偏乐观了，而偏乐观的方向恰好掩盖了查询侧的价值。notebook 第 8 节把这个自检实现成一个函数。

9多轮对话：查询侧最大的单项收益

前面八节都假设查询是独立的。而真实系统里大部分查询是多轮里的追问，而它们在检索上几乎是不可用的。

用户: 餐饮报销上限是多少？ 系统: 200 元。 用户: 那差旅呢？ ← 这个查询单独拿去检索，几乎没有可匹配的信号 「那」「呢」是停用词，只剩「差旅」两个字 ❌ 直接检索 「那差旅呢」 → 相似度极低，可能召回任何含「差旅」的块，也可能什么都召不回 ✅ 先改写成独立查询 history: [Q: 餐饮报销上限是多少 / A: 200 元] → 「差旅报销的上限是多少」 → 正常检索

直白说

指代消解是查询改写里收益最大的一项，而且它的收益与「同义词映射」是叠加的（两者解决不同的问题）。它也是唯一一个「不做就完全不工作」的改写——同义词缺失只是效果差一点，而指代不消解是直接失败。

严谨说

三个实现要点：① 只用最近 2–3 轮——历史越长，改写器越容易把早前的话题带进来；② 改写后必须过第 3 节的安全检查（否定词、数字、长度），不过就退回「原查询 + 上一轮的问题」这个更笨但更安全的拼接；③ 缓存键要含历史的哈希——同一句「那差旅呢」在不同历史下应当改写成不同的查询，而这正是第 7 节缓存键最容易漏的一项。

一个便宜的判别器

不是所有追问都需要改写。判据：查询里的实词（去掉停用词后）少于两个，或者含明显的指代词（那、这、它、上面、刚才），就走改写。其余直接检索。这条规则的价值是把改写调用量压到一小部分请求上——而改写是查询侧唯一需要额外模型调用的动作。

10查询侧的上线顺序

查询侧有五六个可以加的东西。顺序很重要，因为它们的收益/成本比差一个量级。

顺序动作成本为什么排在这个位置
1多轮指代消解一次调用（只对追问）不做就完全不工作；而且它的收益不依赖其它任何一项
2元数据过滤前置 + 空候选报警近零它修的是正确性问题（含跨租户泄漏），不是效果问题
3同义词/别名表近零，可缓存可审计、可回滚到具体一行；对高频词收益极高
4路由（只加 skip 规则）近零先只加规则并统计命中率，确认漏检索为 0 之后再考虑更复杂的
5HyDE 或多查询融合m 倍调用与 QPS放在最后，因为它们最贵，而且收益要在「跨词汇子集」上才看得出来
—LLM 路由分类器一次调用/请求通常不值得：它的误检索率你没有数据去估计，而规则路由已经拿到了大部分收益

这个顺序背后是一条通用判据：先做「不做就不工作」的，再做「近零成本」的，最后做「按倍数花钱」的。而每一步都要在第 8 节的「跨词汇子集」上单独看收益——在整体集上看会被大量「本来就能答对」的样本冲淡。

11查询侧的五个失败模式与它们的信号

查询侧的失败几乎都不会报错。这一节给每一个配一个可观测的信号。

失败用户看到的可观测信号在哪一节
改写把语义改了答案与问题无关，但读起来自信改写前后的否定词/数字/长度差异（这是确定性检查，零误报）第 2 节
过滤条件写错「什么都搜不到」过滤后候选集大小；分租户看零结果率第 5 节
路由误判问常识却答出制度条款skip 与 retrieve 两条路径的分流比例；它突然变化通常意味着有人改了规则第 1 节
缓存读到旧结果「我改了 prompt 但一点变化都没有」缓存命中率——改了改写器之后命中率没掉，就说明键里漏了它第 7 节
评测集偏乐观线上效果远差于离线评测查询与目标块的词重叠率 vs 线上流量的重叠率第 8 节

直白说

第四行那个信号值得单独记住，因为它把一个难以察觉的 bug 变成了一次简单的对照：改了改写器之后，缓存命中率必须掉下来。没掉 → 键里漏了改写器标识 → 你读到的全是旧结果。这比「检查代码写对了没有」可靠得多。

严谨说

第五行是本模块最难修的一个，因为它在你的指标里表现为「一切正常」。唯一的办法是拿线上真实查询做对照：抽样 200 条线上查询，算它们与被召回块的词重叠率分布，与评测集的同一个分布比。两个分布差很远就说明评测集不代表线上——而这与 C68 模块 05 的「离线-在线不匹配」是同一类问题，只不过这里的不匹配是构造方式带进来的，一开始就在里面。

12查询侧的边界：什么不属于这一层

查询侧很容易变成一个什么都往里塞的地方。这一节划清它的边界。

动作属不属于查询侧为什么
改写、扩展、路由、结构抽取属于它们只改变「送进检索的东西」，不改变索引，可以按请求生效、十分钟内回滚
重排（cross-encoder / ColBERT）不属于它作用在召回结果上，属于检索层（C11 模块 03）；本课不重复
上下文预算分配、截断、压缩不属于它作用在组装阶段，属于 C33；本课到「拿到 top-k」为止
答案生成的 prompt 设计不属于它在检索之后；把它和检索问题混在一起会让归因失效
同义词表的维护流程属于，但它是数据不是代码它应当有版本、有 owner、进缓存键（第 7 节）；把它硬编码在代码里是一个常见的退化

第四行是一个真实的归因陷阱：「效果不好」时同时改检索和改生成 prompt，然后效果变好了——你不知道是哪个起了作用。而下一次其中一个失效时，你也不知道该动哪个。这与 C68 模块 00 的可归因性是同一条：一次只动一层，并且每层都有自己的指标。

本课在这条链上的位置：模块 01/02 决定索引里有什么，模块 03（本模块）决定送进检索的查询长什么样，C11 决定怎么在索引里找，模块 04 决定要不要再查一轮，C33 决定召回的东西怎么装进窗口，模块 05 决定这一切在一年后还成不成立。每一格都有自己的指标与门禁——这是本课全部八节的组织原则。
