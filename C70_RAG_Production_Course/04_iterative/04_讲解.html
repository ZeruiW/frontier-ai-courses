1多跳问题的单轮 recall 天然是 0

前面三个模块都假设答案在某一个块里。这一节处理它不成立的情况，而这类问题的单轮检索不是「效果差」，是数学上不可能。

问题：差旅报销的审批人邮箱是什么？ 块 A: 「差旅报销由财务部的王敏负责审批。」 ← 查询能碰到（有「差旅报销」） 块 B: 「王敏的联系邮箱是 wangmin@acme.com。」 ← 查询碰不到（没有「王敏」） 单轮检索: 查询词 = {差旅, 报销, 审批人, 邮箱} 块 B 的词 = {王敏, 联系, 邮箱} 共享词 = {邮箱} → 相似度极低，排不进 top-k **注意这不是「排序不够好」**： 查询里根本没有「王敏」这个信息——它要等块 A 被读到之后才存在。

直白说

所以多跳问题的结构是：第二跳的查询是第一跳结果的函数。$q_2 = f(q_1, \text{docs}_1)$，而单轮检索只能算 $\text{retrieve}(q_1)$。把 top-k 从 5 加到 50、把 embedding 换成最强的那个——都不改变这一点。

严谨说

定量地说：设问题需要的证据集合是 $E = \{e_1, e_2\}$，$e_2$ 与 $q_1$ 的相似度低于第 $k$ 名。则单轮的事实级 recall$= |E \cap \text{retrieved}| / |E| \le 1/2$，而端到端可答需要它等于 1。这也说明多跳题的 recall 必须按「事实集合是否被完整覆盖」算，而不是按「召回了几条相关文档」算——后者会给出 0.5 这个看起来还行的数，而真实的可答率是 0。第 8 节会把这个定义写清楚。

一个诊断技巧：如果某类问题无论怎么调检索都上不去，先检查它是不是多跳的。把答案需要的事实一条条列出来，看有没有哪一条的「可检索线索」只存在于另一条里。有 → 这是迭代问题，不是检索问题。

2迭代检索的循环：四个必须显式写出来的部件

迭代检索的骨架很短，但它的四个部件里有三个经常被省掉，而省掉任何一个都会让它在生产上失控。

while True: ① docs = retrieve(q_current) ← 检索（C11 + 本课 03） ② if sufficient(question, evidence): ← **停止准则**（第 3 节） break ③ q_current = next_query(question, evidence) ← 后续查询生成 ④ if hops >= MAX_HOPS or cost >= BUDGET: ← **硬上界**（不可省） break hops += 1 常被省掉的三个: ② 没有 sufficient() → 只能跑固定轮数，要么不够要么浪费 ④ 没有硬上界 → **成本没有上界**，这是最危险的一个 去重 → 每一跳都可能召回同一批文档，浪费预算（第 6 节）
部件最简实现省掉的后果
停止准则 sufficient问题里的必需槽位是否都被证据覆盖固定轮数：简单题浪费 2–3 倍成本，难题仍然答不上来
后续查询 next_query从已有证据里抽出新实体，拼上原问题的谓词查询漂移（第 4 节）
硬上界 MAX_HOPS / BUDGET两个整数成本没有上界；一次 pathological 查询能烧掉整天的预算
去重见过的 chunk_id 集合每一跳召回同一批文档，上下文被重复内容占满

第三行值得强调：没有硬上界的迭代检索是一个开放的成本漏洞。它不需要恶意输入——一个措辞含糊的问题就足以让 sufficient() 永远返回 False。MAX_HOPS 必须是代码里的常量，而不是配置里的可选项。

3三种停止准则：成本与效果的三个点

停止准则决定了迭代的全部成本特性。三种做法，成本上界都一样，但期望成本差很多。

准则怎么判断期望轮数问题
固定轮数跑 $H$ 轮就停恒为 $H$简单题浪费、难题不够；但它是唯一完全可预测的一个
覆盖度问题的必需槽位是否都在证据里找到了随题目难度自适应需要一个能抽槽位的解析器；槽位抽错会导致提前停或停不下来
边际收益这一跳有没有带来新信息（新块 / 新实体）接近覆盖度，但不需要理解问题容易被近重复骗——召回一批新的但内容重复的块会被判成「有新信息」

直白说

实践中最稳的组合是「覆盖度 + 边际收益 + 硬上界」三条同时用：覆盖度满足就停（正常路径）；覆盖度不满足但边际收益为 0 就停（说明再查也查不到，这条防的是「答案根本不在库里」）；硬上界兜底。

严谨说

成本的形式化：设每跳成本 $c$（嵌入 + 检索 + 一次判断），则最坏成本恒为 $H_{\max} \cdot c$（由硬上界保证），而期望成本是 $c \cdot \mathbb{E}[H]$。三种准则的区别只在 $\mathbb{E}[H]$——这也是为什么「加停止准则」是一次纯粹的成本优化，它不改变最坏情况，只改变账单。notebook 第 3 节把三种准则的 $\mathbb{E}[H]$ 与可答率一起量出来。

一条容易被忽略的纪律：停止准则的判断不能看「答案对不对」——线上没有真值。它只能看结构性的信号：槽位覆盖、新信息量、检索分数分布。这与 C68 模块 02 的「重试只能看异常类型，不能看判分结果」是同一条纪律。

4查询漂移：迭代最常见的失效方式

后续查询是从上一跳的证据里生成的。如果生成规则不锚定原问题，查询会一跳一跳地走远。

问题: 差旅报销的审批人邮箱是什么 ❌ 不锚定（用上一跳文档里的显著词当新查询） hop1: 差旅报销的审批人邮箱是什么 → 「差旅报销由财务部的王敏负责审批」 hop2: 财务部 负责 审批 → 「财务部的报销审批时限为三个工作日」 hop3: 报销 审批 时限 → 「审批时限为三个工作日」 → 越走越远，**再也回不到「邮箱」这个目标** ✅ 锚定（新实体 + 原问题的目标谓词） hop1: 差旅报销的审批人邮箱是什么 → 「…财务部的王敏负责审批」 hop2: 王敏 邮箱 → 「王敏的联系邮箱是 wangmin@acme.com」 → 命中

直白说

漂移是可以量出来的：算每一跳的查询与原问题的相似度。不锚定时它单调下降；锚定时它保持在一个水平上。notebook 第 4 节把两条曲线画在一起。这个量应当作为线上指标监控——它掉下去通常意味着后续查询生成的 prompt 出了问题。

严谨说

锚定的最小实现只有一句话：$q_{i+1} = (\text{新实体}) \oplus (\text{原问题的目标谓词})$。新实体来自上一跳的证据，目标谓词来自原问题且永不改变。更强的做法是把原问题原样拼进每一跳的查询里（代价是查询变长、相似度被稀释——模块 02 第 7 节的稀释效应在这里以另一种形式出现）。

一个便宜的护栏：要求每一跳的查询与原问题的相似度不低于第一跳的某个比例（比如 0.5 倍），否则丢弃这一跳的查询并停止。它拦不住所有漂移，但能拦住「走到完全不相关的话题上」这种严重情况。

5图检索：只用图的结构，不训练任何模型

有一类问题连迭代也做不好：「A 和 B 之间有什么关系」「谁同时负责 X 和 Y」。它们需要的不是「找到某一段文字」，而是「在实体之间走几步」。

从块里抽出三元组，得到一张图 块: 「差旅报销由财务部的王敏负责审批。」 → (差旅报销, 审批人, 王敏) (王敏, 部门, 财务部) 块: 「王敏的联系邮箱是 wangmin@acme.com。」 → (王敏, 邮箱, wangmin@acme.com) 块: 「合同审批由法务部的李强负责。」 → (合同审批, 审批人, 李强) (李强, 部门, 法务部) 差旅报销 ──审批人──► 王敏 ──邮箱──► wangmin@acme.com │ 部门 ▼ 财务部 ◄──部门── 张伟 ◄──审批人── 采购申请 问「差旅报销和采购申请的审批人有什么共同点」： flat 检索：两个块各自能召回，但「共同点」这个信息**在任何块里都不存在** 图检索 ：从两个实体各走两步，取交集 → {财务部} ← 答案是图算出来的
问题类型flat 检索迭代检索图检索
单跳事实（「差旅上限多少」）最好（最便宜）浪费浪费
多跳事实（「审批人邮箱」）不可能最好可以（如果三元组抽全了）
关系/聚合（「共同点」「一共几个」）不可能很难（需要很多跳）最好——答案是图算出来的，不在任何块里
全局摘要（「这批文档讲了什么」）不可能不可能社区检测 + 分层摘要（GraphRAG 的主要贡献）

直白说

图检索的成本几乎全在摄取侧：抽三元组要跑一遍模型（或规则），而且文档更新时要增量维护图。查询侧反而很便宜——邻域扩展是几次索引查找。所以图检索的决策点是「值不值得在摄取时多花这一遍」，而不是「查询时快不快」。

严谨说

它的两个真实风险：① 三元组抽取的召回率决定了上限——抽不到的关系在图里不存在，而这个上限在查询侧完全看不到（表现为「答不上来」，与检索失败无法区分）；② 图会腐烂——文档更新后旧三元组必须删掉，而「删一条边」比「删一个块」难得多，因为一条边可能有多个来源块支持（模块 05 会讨论这个 provenance 问题）。

一个实用的中间档：不建完整的知识图谱，只抽实体 → 块的倒排表。这已经能支持「同时提到 X 和 Y 的块」「提到 X 的所有块」这类查询，而成本只是一次实体识别。notebook 第 5 节实现的就是这一档。

6迭代的成本模型：三个乘数

迭代检索的成本很容易失控，因为它的三个乘数都不显眼。

\[\text{cost} \le H_{\max} \times m \times (c_{\text{embed}} + c_{\text{search}}) + H_{\max} \times c_{\text{judge}} + c_{\text{gen}}\]
  • $H_{\max}$：最大跳数。$H = 3$ 已经是三倍成本。
  • $m$：每跳的查询扩展路数（模块 03 第 4 节）。这一项最容易被忘——迭代 3 跳 × 融合 3 路 = 9 次检索，而两个改动是分别上线的，没人把它们乘起来算过。
  • $c_{\text{judge}}$：每跳的停止判断。如果它是一次 LLM 调用，那么它可能比检索本身贵。所以停止判断应当优先用结构性信号（槽位、新块数），不要默认用模型。

直白说

还有一项不在公式里但同样真实的成本：上下文预算。每一跳都往证据里加块，$H$ 跳之后上下文可能是单轮的 $H$ 倍（如果不去重，还会更多）。而上下文长度直接影响生成成本与延迟。

严谨说

把它写进 C66 模块 05 的口径：迭代检索要报的是 $/success 而不是 $/query。迭代的价值恰恰是把一部分「本来必然失败」的查询变成成功，所以按 $/query 看它一定更贵，按 $/success 看才可能划算。notebook 第 6 节把两个口径都算出来，它们给出的结论可以是相反的。

一个直接可用的部署策略：只对「单轮判定为证据不足」的查询开启迭代。这让 $\mathbb{E}[H]$ 接近 1（大多数查询单轮就够），而多跳查询仍然能被答对——本质上是把迭代当成一条兜底路径而不是默认路径。

最后一行是本模块最重要的一条工程忠告。迭代检索能掩盖分块问题、解析问题、查询问题——它会让指标变好，同时让成本变高、延迟变长、系统变复杂。上线迭代之前，先确认前面三个模块的检查都是绿的。顺序仍然是模块 00 说的那个：parse → chunk → query → 才是 iterate。

必须记录的四个字段

每次迭代检索都要记录：hops（实际跳数）、new_chunks_per_hop（每跳的新块数）、drift（每跳查询与原问题的相似度）、stop_reason（sufficient / no_gain / max_hops / budget）。stop_reason 的分布是最有信息量的一个——max_hops 占比高说明上界在兜底而不是准则在工作，这通常意味着 sufficient() 太严或者答案不在库里。

8多跳题的 recall 必须按事实集合算

这一节修正一个会系统性误导人的指标定义。

直白说

常规 recall 的分母是「标注为相关的文档数」，而多跳题的标注通常只标了第一跳能找到的那一条（因为标注者也是搜出来的）。于是单轮检索在这类题上能拿到不低的 recall，而端到端可答率是 0。

严谨说

正确的定义：把每道题的答案拆成必需事实集合 $E$，recall 定义为「$E$ 被完整覆盖的题目比例」——$$\text{fact-recall} = \frac{|\{\text{题} : E \subseteq \text{retrieved}\}|}{|\text{题数}|}$$注意它是一个全或无的量。覆盖了 $E$ 的一半，端到端就是 0，所以指标也应当是 0。

指标单轮在多跳题上的值端到端可答率会不会误导
文档级 recall@5（只标第一跳）高（~1.0）0会——这是最常见的误导来源
文档级 recall@5（标全两跳）0.50会（0.5 看起来还行）
fact-recall（全或无）00不会

推论：评测集必须为多跳题标出完整的事实集合，而这件事只能在造题时做——事后从日志里补是不可能的，因为你不知道当时需要哪些事实。

还有一个更朴素的检查值得放进 CI：把评测集按「需要几个事实」分层报分。单事实题与多事实题的分数混在一起报，会让多跳能力的改动完全看不见——多跳题通常只占评测集的 10–20%，而它们的分数变化会被另外 80% 冲淡。

9什么时候不该用迭代

迭代检索是本课最贵、最复杂、最容易被滥用的一层。这一节给出四个「先别上」的判据。

  1. 模块 02 的 intact 还没达标——答案本来在一个块里，只是被切断了。此时迭代能让指标变好，但成本是修分块的几倍（第 7 节量过），而且它把一个已解决的问题变成了一个持续的成本。
  2. 多跳题在评测集里占比很低而且没被单独标注——你无法证明迭代有收益（第 8 节：混在一起报会把 +1.00 冲淡成 +0.43）。先造多跳评测集并标出完整事实集合，再谈上线。
  3. 还没有 MAX_HOPS 与单查询预算——没有硬上界的迭代是一个开放的成本漏洞，而它不需要恶意输入，一个措辞含糊的问题就够（第 2 节）。
  4. 停止判断只能用 LLM——第 6 节量过：用 LLM 判断时迭代连 $/success 都比单轮更贵。先找到一个结构性的充分性信号（槽位覆盖、新实体、检索分数分布），找不到就说明这类问题的「够不够」还没被定义清楚。

直白说

反过来，什么时候该上：评测集里有一个明确的多跳子集、它的 fact-recall 是 0、而这个子集对业务重要。这三条同时成立时，迭代是唯一的解——因为单轮 recall 在这类题上不是「差一点」，是结构上的 0（第 1 节）。

严谨说

还有一个中间选项常被忽略：把多跳问题在摄取侧解掉。如果「审批人 → 邮箱」这类关联在语料里是稳定的，那么在摄取时把它们物化成一个块（或一条三元组），多跳问题就变成了单跳问题。代价是摄取侧的复杂度与派生资产的维护（模块 05 第 7 节），收益是查询时零额外成本。这个权衡与第 5 节图检索的决策点是同一个：钱花在摄取侧还是查询侧。

10与生成交错：为什么本课把它们分开讲

IRCoT / Self-RAG / FLARE 这条线的做法是把检索与生成交错：生成一步 → 用生成的内容触发检索 → 继续生成。本课刻意把它们分开，理由值得说明。

本课的形态（检索循环独立） 交错形态（IRCoT 式） retrieve → judge → next_query generate 一句 ▲ │ │ └────────────────────┘ ├─► 用这句话当查询去检索 然后一次性 generate │ └─► 把结果拼进上下文，继续 generate ✓ 每一跳的查询是可检查的 ✓ 查询更自然（就是模型的思路） ✓ 停止准则是结构性的 ✗ 停止准则耦合在生成里，难以单独测试 ✓ 可以完全不调用大模型来测试 ✗ 每一步都要真实模型，无法离线复现

直白说

分开讲的理由是可测试性：本课全部的实验（并列组、锚定、停止准则、漂移、成本）都能在没有真实模型的条件下跑出来并断言。交错形态把「查询生成」这一步塞进了生成过程，于是它的行为与模型强耦合，无法离线复现——而不可复现的东西没法在 CI 里守住。

严谨说

工程上的建议是分阶段：先把独立的检索循环做对（本课的四个部件 + 监控四字段），确认它在多跳子集上把 fact-recall 从 0 提到可用；之后如果还需要更自然的查询，再把它交错进生成。反过来（一上来就做交错）的问题是：当效果不好时，你分不清是检索循环的问题还是生成的问题——而这正是 C68 模块 00 的第二条性质（可归因性）要避免的情形。

一句话：交错形态更强，独立形态更可测。而在一个还没有多跳评测集、还没有 MAX_HOPS、还没有 stop_reason 看板的系统里，可测比强更值钱。

11上线迭代检索的七项清单

把本模块压成一张可勾选的清单。前四项是前置条件，后三项是上线动作。

  1. 模块 01/02/03 的门禁全绿——尤其是模块 02 的 intact（第 7 节：迭代会掩盖分块问题）。
  2. 评测集里有一个明确的多跳子集，标出了完整的事实集合，并按「需要几个事实」分层报分（第 8 节）。
  3. MAX_HOPS 由单查询预算反解，写成代码常量（练习 2）。
  4. 停止判断用结构性信号——找不到这样的信号说明「够不够」还没被定义清楚（第 3/6 节）。
  5. 迭代只对「单轮证据不足」的查询开启（第 6 节：覆盖度准则的自然结果）。
  6. 记录四个字段并上看板：hops 的 P50/P99、new_per_hop、drift、stop_reason 分布（第 7 节）。
  7. 报 $/success 而不是 $/query，并把它与单轮基线并排放（第 6 节：它不是一个自动偏向迭代的口径）。

清单里最容易被跳过的是第 2 项。没有多跳子集时，迭代的收益在整体指标上只有几个点，而成本是可见的三倍——于是它看起来像一个不划算的改动，然后被砍掉。而实际上它在那个子集上把 0 变成了 1。
