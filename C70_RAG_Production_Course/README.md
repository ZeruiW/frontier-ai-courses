## 这门课为什么存在

在真实系统里，「RAG 答不上来」这件事绝大多数时候和检索算法没有关系。

```
┌──────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
│ 文档摄取  │──►│  分块  │──►│  索引  │──►│  检索  │──►│  组装  │──►答
│  与解析   │   │        │   │        │   │        │   │  上下文 │
└──────────┘   └────────┘   └────────┘   └────────┘   └────────┘
     ▲              ▲            ▲            ▲
   本课 01        本课 02      本课 05      C11 全课
   本课 03（查询侧）· 本课 04（迭代检索）
```

**C11 覆盖的是「检索」这一格里的算法与它的评测。本课覆盖它左边的三格和右边的一格。**

因为检索算法只能在「已经进了索引的东西」里找——如果答案在解析时被丢掉了、在分块时被切断了、
在索引里已经过期了，那么把 HNSW 换成暴力 kNN、把 top-5 改成 top-20、加一个 cross-encoder 重排，
**一个都救不回来**。而这类失败的共同特征是：**检索指标看起来正常，端到端答案却是错的**。

## 方法论：为什么用玩具嵌入而不接真实模型

三条理由：

1. **本课要测的量都不需要真实模型**——「答案完整落在单块内的比例」「近重复占满 top-k 的程度」
   「索引滞后导致的过期答案率」「新旧 embedding 混用后的相似度失真」，
   这些全都是流水线的结构性质，与用哪个嵌入模型无关。
2. **只有在知道真值的条件下，才能验证一个改动是把结果推近了还是推远了。**
   真实模型会把「分块改好了」和「模型今天心情好」混在一起。
3. **玩具替身让失败可以被精确注入**——OCR 错误率设成 3%、索引滞后设成 6 小时、答案跨块设成必然发生。
   真实系统里这些故障是偶发的，而偶发的故障没法用来教学。

每个模块末尾的 **🧪 真实工程胶囊** 给出可原样复制的落地代码
（`unstructured`/`pypdf` 的解析入口、`RecursiveCharacterTextSplitter` 的分隔符优先级、
父子块的存储布局、查询改写的 prompt 与缓存键、实体倒排的两张表、影子索引的双写与 alias 切换）——
**但课程本身不依赖它们。**

一个诚实的说明：本课的玩具嵌入在**否定**与**同义词泛化**上比真实模型更弱。
课程在用到这一点的地方（模块 03 第 6 节）明确说明了这件事——
它放大了一个真实存在的局限，而不是发明了一个不存在的问题。
