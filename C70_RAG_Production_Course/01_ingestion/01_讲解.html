1解析的目标不是「拿到文字」

几乎所有 RAG 项目的第一行代码都是text = extract_text(pdf)。这一行同时决定了这个系统的上限，因为它决定了语料里存在什么、不存在什么。

直白说

解析必须同时拿到三样东西，而不是一样：文字（说了什么）、结构（谁属于谁）、来源（这段字在哪一页哪一节）。只拿文字的代价是：结构与来源在下游无法恢复。不是「难恢复」——是信息已经不在了。

严谨说

把它写成一个映射：一份文档 $D$ 的解析结果应当是一个三元组序列$\{(t_i, s_i, p_i)\}$，其中 $t_i$ 是文本片段、$s_i$ 是它的结构角色（标题 / 正文 / 表格单元 / 列表项 / 脚注）、$p_i$ 是它的位置（页、区间、章节路径）。常见的 extract_text 返回的是 $\text{concat}(t_i)$——一个把 $s_i$ 与 $p_i$ 全部投影掉的映射。投影是不可逆的，这就是「无法恢复」的准确含义。

丢掉的东西下游哪一步会因此失败能不能事后补回来
表格的行列对应「A 行 B 列的值是多少」——块被召回、数字也在，但答案不可恢复不能。拍平后 1580 与「上海/2023」的关联已经消失
标题层级分块（模块 02）无法按章节切；检索无法按章节过滤部分可以（靠字号/编号启发式），但不可靠
阅读顺序实体与属性错配——这类错误的答案读起来完全通顺不能，除非重新解析
位置（页/区间）引用核查、删除、更新、权限过滤（模块 05 全靠它）不能
列表的层级「第二类的第三条」被拉平成同级，条件被错误地并列部分可以（靠缩进），PDF 里缩进常常已经没了

这张表最重要的一列是第三列。解析是整条流水线里唯一一个「做错了就无法在下游补救」的环节——分块参数可以改、查询可以改写、索引可以重建，但解析时丢掉的信息只能靠重新解析拿回来。所以它值得被当成一次性的、需要认真做的工程决策，而不是一行 extract_text。

2结构损失的实验：四种解析，同一份表格

把上一节的第一行做成一个可复现的实验。一份四行三列的营收表，四种解析方式。其中第二种的结论和多数人预期的不一样，值得先看：

原始表格 ┌────────┬────────┬────────┐ │ 地区 │ 年份 │ 营收 │ ├────────┼────────┼────────┤ │ 北京 │ 2023 │ 1240 │ │ 北京 │ 2024 │ 1310 │ │ 上海 │ 2023 │ 1580 │ ← 问：上海 2023 年营收多少？ │ 上海 │ 2024 │ 1620 │ └────────┴────────┴────────┘ ① 保结构（行 → 句） "上海 在 2023 年的营收是 1580 万元。" ✅ 可答 ② 行主序拍平（按行连起来） "地区 年份 营收 北京 2023 1240 … 上海 2023 1580 …" ⚠️ 行对应扛住了 ↑ 单元格与行名恰好相邻；但「营收」只在开头出现一次 → **列名丢了** ③ 列主序拍平（按列读——PDF 里按 x 坐标优先排序的真实结果） "地区 北京 北京 上海 上海 年份 2023 2024 … 营收 1240 … 1580 …" ❌ 不可答 ↑ 每个字都在，检索照样召回，但 1580 与「上海+2023」隔了几十个 token ④ 行主序拍平 + 按字符数硬切 块1: "… 北京 2024 1310 上海 2023 " 块2: "1580 上海 2024 1620" ← 「上海 2023」与「1580」被切开 ❌ 不可答 ↑ 几百行的大表上，这件事必然发生在某些行上

notebook 第 1 节会把四种都量一遍，结论有三条：

  1. 只有行转句（①）在所有条件下都可恢复。
  2. 行主序拍平（②）在小表上扛住了「哪一行」——单元格与它的行名恰好相邻；但它丢了「哪一列」——「营收」只在开头出现一次，离 1580 几十个 token。所以「拍平必然丢结构」是一个错的说法；丢失发生在两个具体条件下：列主序读取（③），以及行与行名被块边界切开（④）。而这两个条件在真实文档上都很常见——PDF 按 x 坐标优先排序就会得到 ③，几百行的大表必然遇到 ④。
  3. 不可恢复的那些块，检索指标依然正常。相似度 > 0.3、1580 这个数字确实在召回的块里——precision@1 是满分，端到端是错的。

第 2 条的工程含义不是「拍平有时可以」，而是相反：不要把「表格能不能扛住」当成一个概率事件去赌。行转句对 ③ 和 ④ 都免疫，而它的实现只有五行。

直白说

为什么会这样？因为相似度衡量的是词的重叠，而不是关系的保留。拍平后的块包含「上海」「2023」「1580」这三个词，查询也包含前两个——重叠很高。但「哪个数字属于哪一对」这个信息不在词袋里。

严谨说

更一般地：设关系 $R = \{(\text{行}, \text{列}, \text{值})\}$。保结构的解析产生的文本 $T_1$ 满足 $R$ 可从 $T_1$ 唯一恢复；拍平的文本 $T_2$ 只保留了 $\pi(R)$——三个投影的并集，而 $|\{R' : \pi(R') = \pi(R)\}|$ 在 $m$ 行 $n$ 列时是组合级的。检索指标是 $T$ 与 $q$ 的函数，与 $R$ 是否可恢复无关——这就是「指标正常但答案错」的形式化来源。

落地做法：表格必须走单独的路径

  • 行转句（最简单、最有效）：每一行渲染成一句自然语言，把列名带上。四行表变成四个可独立检索的句子。
  • 保留原表 + 摘要句：块的正文是行转句，但 metadata 里挂着这张表的 markdown 原文，供需要时整表喂给模型。
  • 大表要分块：几百行的表整块喂进去等于把上下文烧掉；行转句之后天然就是可检索单元。
  • 永远记录 element_type='table'——下游要知道这个块的来源是表格才能正确使用它（也才能在评测时单独看表格类问题的准确率）。

3阅读顺序：最隐蔽的一种结构损失

PDF 里没有「段落」这个概念，只有一堆带坐标的文本块。把它们拼成文本需要一个顺序，而选错顺序不会报错。

一个双栏版面（左右两栏，各三段） x=50 x=320 y=100 ┌──────────┐ ┌──────────┐ │ 左栏 段1 │ │ 右栏 段1 │ y=200 ├──────────┤ ├──────────┤ │ 左栏 段2 │ │ 右栏 段2 │ y=300 ├──────────┤ ├──────────┤ │ 左栏 段3 │ │ 右栏 段3 │ └──────────┘ └──────────┘ ❌ 按 y 排序（"从上到下"）： 左1 右1 左2 右2 左3 右3 ← 两栏交错，语义被打断 ✅ 先按 x 分栏、栏内按 y 排序： 左1 左2 左3 右1 右2 右3 ← 正确 注意：**按 y 排序在单栏文档上是对的**， 所以这个 bug 在测试文档上常常不出现。

交错的后果比「读起来别扭」严重得多。如果左栏讲的是 A 产品的参数、右栏讲 B 产品的参数，交错之后每一段的上下文里都同时有 A 和 B——分块之后一个块里会出现「A 的名字 + B 的参数」，而这个块读起来完全通顺。

这是本课最推荐加进 CI 的一项检查：解析后随机抽 5 页，人工确认阅读顺序。它便宜、一次性，而它防住的错误在任何自动指标里都看不见。notebook 第 2 节给出一个自动版本：在已知实体-属性配对的合成版面上，量出错配率。

分栏的判定

直白说

实用的启发式：看 x 坐标的直方图有没有明显的双峰。有 → 双栏，按峰分组；没有 → 单栏，直接按 y 排。再加两条：页眉页脚按 y 的极值剔除；跨栏的大标题（宽度接近页宽）单独处理。

严谨说

更稳的做法是XY-cut：递归地在投影直方图的最大空白处切分——先找垂直投影的最大间隙（切栏），再在每栏内找水平投影的间隙（切段），递归直到块足够小。它的好处是同时给出了阅读顺序和一棵版面树，而版面树正好是模块 02 结构感知分块需要的输入。代价是它对表格与图文混排会过切，需要配合 element 类型做例外。

4OCR 噪声：从字符错误率到「答不出来」

扫描件与图片 PDF 必须走 OCR，而 OCR 一定有错。关键问题是：字符级错误率 $\varepsilon$ 传导到检索上会放大多少倍？

\[P(\text{一个长度 } L \text{ 的词被破坏}) = 1 - (1-\varepsilon)^{L}\]

直白说

直觉：错误率是按字符算的，但检索是按词匹配的，所以长词更容易被毁掉。$\varepsilon = 3\%$ 时，两字词被毁的概率是 5.9%，八字词是 21.6%。而专有名词、型号、法条编号恰恰都是长串——OCR 噪声优先毁掉的正是最有检索价值的那些词。

严谨说

这个式子还解释了两类检索的不同斜率。词法检索（BM25）依赖精确词匹配，所以一个词被破坏就等于这个词的信号完全丢失，查询里 $m$ 个关键词全部存活的概率是 $(1-\varepsilon)^{\sum L_i}$——随查询长度指数衰减。语义检索用子词/字符 n-gram，一个字符错误只毁掉包含它的那几个 n-gram，降级是渐进的而不是断崖的。notebook 第 3 节把两条曲线画在一起。

OCR 错误率 ε2 字词被毁8 字词被毁含 3 个关键词的精确匹配存活率
0.5%1.0%3.9%≈ 91%
1%2.0%7.7%≈ 83%
3%5.9%21.6%≈ 57%
5%9.8%33.7%≈ 40%

最后一列按查询含 3 个词、平均词长 6 计算。它给出的结论很直接：ε 到 3% 时，纯词法检索已经不能作为唯一召回路径了——必须配一路语义检索（这正是 C11 模块 01 混合检索的一个非常实际的动机）。

摄取侧能做什么

  1. 记录 OCR 置信度并把低置信页标出来——大多数 OCR 引擎给每个词一个置信度。把页级平均置信度写进 metadata，低于阈值的页进人工复核队列。
  2. 对关键实体做词典纠错：产品名、人名、法条号是封闭集合，用编辑距离对齐到词典。这一步的收益远大于对全文做纠错。
  3. 不要在摄取时「顺便」用 LLM 清洗全文——它会安静地改写内容（C69 的视角：这等于让不可信内容经过一个会重写它的环节），而你会失去与原文的对齐，引用核查就没了。
  4. 把 ε 当成一个需要被监控的量：抽样人工标注 200 个词，算字符错误率，写进摄取报告。它变差通常意味着上游换了扫描设备。

5元数据：摄取时几乎免费，之后无法补

元数据是本课后面三个模块的燃料。它在摄取时抽取几乎不要钱，而事后补几乎不可能（因为原文已经不在手上了）。

元数据怎么来下游用途缺了会怎样
doc_id / version摄取时分配（永不复用）幂等、更新、删除（模块 05）删不掉、更不了
source_uri / 页码 / 字符区间解析器给的位置引用核查、给用户跳转答案无法被验证，用户不信
section_path（章节路径）标题层级栈结构感知分块（02）、按章节过滤（03）分块只能按字符数硬切
effective_date / updated_at文档内容或文件属性时效过滤、新鲜度监控（05）旧政策与新政策同时被召回
tenant / acl（权限标签）来源系统多租户隔离（05）跨租户泄漏——这是安全事故
element_type解析器（Title/Table/List/Text）表格特殊处理（02）、按类型评测表格与正文被同样对待
lang语言检测分块的字符/词切分、embedding 选择中英混排的块被按错误的粒度切

有一个判据可以决定「这个元数据要不要抽」：它会不会出现在某个查询的过滤条件里，或者出现在某个运维操作的 WHERE 子句里？会 → 抽。「删除这个用户的所有文档」「只看 2024 年之后生效的版本」「只看这个租户的」——这些都是 WHERE 子句。

元数据过滤是双刃的

过滤能把候选池缩小、把 precision 拉高。但它同时是一个 recall 风险：过滤条件写错，答案会被直接排除在候选之外，而检索层完全不会察觉。

直白说

notebook 第 4 节量了这件事：加上正确的章节过滤，precision@3 明显上升；而把过滤条件写窄一格（少包含一个章节），recall 直接掉到 0——不是掉一点，是完全召不回。过滤是硬约束，它的失败模式是断崖式的。

严谨说

形式化：无过滤时候选集是 $C$，过滤后是 $C \cap F$。则 $\text{recall} = 0$ 当且仅当所有相关块都不在 $F$ 里。与相似度不同，$F$ 里没有「排名靠后」这个中间状态。工程上的对策是双路召回：一路带过滤、一路不带，再合并（C11 的 RRF）；并把「过滤后候选数为 0」当成一个必须报警的事件。

6去重：RAG 里它有一个特有的后果

去重算法本身在 C43 讲过（MinHash / SimHash）。这一节只讲它在 RAG 里的一个特有后果，这个后果不是「浪费存储」，而是「浪费上下文预算」。

语料里有 4 份近重复文档（同一份合同的四个版本） 查询 → top-5 召回： ┌─────────────────────────────────────────┐ │ 1. 合同v3 第2段 ← 内容 A │ │ 2. 合同v1 第2段 ← 内容 A（几乎同一句） │ │ 3. 合同v4 第2段 ← 内容 A │ │ 4. 合同v2 第2段 ← 内容 A │ │ 5. 附件说明 第1段 ← 内容 B │ └─────────────────────────────────────────┘ 有效独立信息量 = 2 条，而不是 5 条。 **你花了 5 个块的上下文预算，买到了 2 个块的信息。**

直白说

为什么近重复必然占满 top-k？因为相似度是内容的函数——内容几乎一样的块，得分也几乎一样，所以它们会作为一个整体一起进 top-k 或一起不进。k 越大，这个问题越严重，而不是越轻。

严谨说

定义有效独立文档数$\text{eff}@k = |\{\text{去重后的内容簇}\} \cap \text{top-}k|$。如果语料里某个内容有 $r$ 份近重复，那么在它们都排在前面的情况下 $\text{eff}@k \approx k - r + 1$。把 $\text{eff}@k / k$ 当成一个监控指标——它掉下来通常意味着上游灌进了一批重复文档。C11 的 MMR 可以在检索时缓解，但摄取时去重更便宜也更彻底。

三层去重，各管一件事

层次手段抓什么注意
文档级精确content_sha 相同同一份文件被灌了两遍最便宜，一定要做
文档级近重复MinHash / SimHash（C43）同一份文档的多个版本、格式转换副本不要直接删——保留最新版并用 supersedes 链接
块级近重复块的 shingle 指纹页眉页脚、免责声明、模板文字这些块与任何查询都有一点相关，是噪声的主要来源

块级去重有一个容易踩的坑：不要跨文档合并块。两份不同合同里的同一句条款看起来是重复的，但用户问「合同 X 里有没有这条」时，答案必须来自合同 X。正确做法是保留两份块、在检索时按 doc_id 做多样性约束（每个 doc 最多进 n 个块）。

7摄取契约：让摄取可重放、可回滚、可删除

摄取是一个写操作，而写操作需要契约。本课的契约是四条，全部可以用几行代码实现（notebook 第 6 节）。

  1. doc_id 一次分配、永不改变、永不复用。它必须来自来源系统的稳定标识（文件路径 + 来源系统 ID），不能是内容哈希——用内容哈希当 ID，改一个错别字这份文档的历史就断了（与 C68 模块 01 的稳定 ID 是同一条）。
  2. 版本单调递增，content_sha 用来检测变化。摄取时先算 sha：与当前版本相同就整份跳过（这是幂等性），不同就 version+1 并替换该 doc 的全部块。
  3. 块的主键是 (doc_id, version, chunk_index)。写入用 upsert 而不是 append。「同一份文档摄取两次索引里出现两份块」这个 bug 的唯一根因就是用了 append。
  4. 删除必须传播到索引，并且是可验证的。删除操作要返回「删掉了几个块」，调用方要断言这个数与预期一致——「删了但一个块都没删掉」是一个必须能被发现的失败。
一次摄取的完整状态机 新文档 ─────────────► [v1 已索引] │ 内容变了 │ 内容没变 ┌───────────────────┴──────────────┐ ▼ ▼ [删 v1 全部块] [整份跳过] [写 v2 全部块] n_written = 0 [v2 已索引] （幂等） │ │ 源库删除 ▼ [删该 doc 全部块] ──► 断言 n_deleted == 该 doc 的块数 [写一条 tombstone] ← 防止「被重新灌回来」

最后一行的 tombstone 值得解释：如果只是删了块，而上游的全量同步任务下一轮又把这份文档送进来，它会被当成新文档重新索引。删除记录（doc_id + 删除时间 + 原因）让摄取器能拒绝它，也让「为什么这份文档不在索引里」有答案。

8摄取质量门禁：六项可机器判定的检查

这一节把整个模块变成一段能放进 CI 的代码。六项检查，每一项都对应前面某一节的失败。

#检查阈值怎么定抓的是哪一节的问题
1零文本页比例> 5% 报警扫描件走错了路径（没走 OCR）
2表格块的比例与行转句覆盖率有表格但行转句为 0 → 阻断第 2 节：表格被拍平
3元数据完整率doc_id/version/source_uri/section_path 缺任一 → 阻断第 5 节：元数据事后补不回来
4OCR 平均置信度 / 抽样字符错误率低于基线 2σ 报警第 4 节：上游换了扫描设备
5块级近重复比例> 20% 报警；eff@10 / 10 < 0.6 报警第 6 节：近重复占满 top-k
6幂等性自检同一批重放一次，n_written == 0，否则阻断第 7 节：摄取契约

注意第 6 项的形式：它不是「检查代码写对了没有」，而是「把同一批数据再摄取一遍，断言什么都没发生」。这是幂等性唯一可靠的验证方式，也是 C68 模块 00 的 run ∘ run = run 在摄取侧的对应物。

门禁的两条使用纪律，与 C68 模块 04 一致：确定性的检查（2/3/6）直接阻断，因为它们的误报率是零；统计性的检查（1/4/5）只报警，阈值从历史基线的方差推。把统计检查设成阻断是「门禁被关掉」这一结局最常见的起点。

9摄取流水线的执行顺序：六步，顺序不能换

这一节把前八节合成一条可执行的流水线。六个步骤的顺序是有约束的——换一个位置就会有信息永久丢失。

① 解析（拿文字 + element 类型 + 坐标 + 页码） │ ← 唯一能拿到坐标的时刻。之后坐标就没了。 ② 阅读顺序修正（分栏 / 剔页眉页脚 / 跨栏标题） │ ← 必须在 ① 之后（要坐标）、在 ③ 之前（表格分流要按修正后的顺序找上下文） ③ 表格分流（行转句 + 保留 markdown 原文） │ ← 必须在拼接成纯文本**之前**。拼完就分不出哪段是表格了。 ④ 元数据抽取（section_path / effective_date / tenant / lang） │ ← 标题层级栈只在遍历 element 时存在 ⑤ 去重（文档级精确 → 文档级近重复 → 块级） │ ← 必须在 ⑥ 之前：写进去再删比不写贵，而且中间状态会被检索到 ⑥ 幂等写入（先删该 doc 旧版本，再 upsert；tombstone 检查）

直白说

最容易被换错位置的是 ③ 和 ⑤。③ 放到「拼成纯文本之后」是最常见的错误——一旦拼接完成，表格与正文就不可区分了，而表格需要完全不同的处理路径（第 2 节）。⑤ 放到 ⑥ 之后（「先写进去，之后再跑一个去重任务」）会让近重复块在两次任务之间被检索到，而这段时间的行为无法解释。

严谨说

还有一条不在图里的约束：① 到 ⑥ 必须是同一个事务边界内的一次操作，或者至少是可重放的。如果流水线在 ④ 之后崩溃，重跑必须从 ① 开始，而不是从 ⑤ 继续——因为中间产物里没有坐标了。实现上最简单的保证是：中间产物全部在内存里，只有 ⑥ 写外部存储。这也意味着单篇文档的处理不应该跨进程拆分。

一个检验流水线设计的问题：「如果我想给已经索引过的文档补一个元数据字段，需要重新解析吗？」需要 → 说明这个字段只能在解析时拿到，那它就必须在第一遍就抽出来（第 5 节的判据）。
