1「提升 TSR 效果」这类没有边界的问题在考什么

面试官抛出一句「我们想提升 TSR 的效果，你会怎么做？」，然后不再补充任何信息——这不是他偷懒，也不是题目没写全。模糊本身就是考题的一部分。在真实工作里，需求就是这样到达工程师手上的：产品经理说「用户反馈标志识别不够好」，领导说「这个季度把感知效果提上去」。没有人会把一个需求拆好边界再交给你，拆边界这件事本身就是这份工作的一部分。

所以面试官真正想看的，不是你能不能想出一个技术方案，而是：

「拿到一个没有边界的问题时，这个人是先制造边界再开始干活，还是假装它已经有边界然后一头扎进去，或者被边界不清吓住、原地打转？」——这三种反应对应了完全不同的工程成熟度，而且它们在 45 分钟内就能被区分出来。

反应类型候选人的行为面试官看到了什么典型得分
过早收敛没问任何问题，直接假设「提升效果=提升 mAP」，开始讲模型架构他会把没写清楚的线上需求直接做错，而且做错了自己都不知道低——正确性和沟通都受影响
过度澄清连续问 15 个问题，把面试官问得不耐烦，10 分钟过去还没进入分析他在真实项目里会把「需求评审」开成马拉松，团队会绕开他低——时间管理与决断力扣分
结构化收敛问 4–6 个覆盖不同维度的问题，然后主动提出一个假设并请确认，边界清楚后开始分析他能把模糊状态转化成可执行状态，而且过程可复现、可信任高——这是本模块要练的目标行为

直白说

换个说法：这道题从来不是在考「你懂不懂 TSR」。它在考的是你如何把一句话的需求，变成一份别人可以照着干活的规格。这件事在公司里有个名字，叫scoping（范围界定），是初级工程师和资深工程师之间最大的行为差异之一——初级工程师等着被告知做什么，资深工程师自己把「做什么」定义出来，然后拿去和上游对齐。

严谨说

更严谨地说：一个没有边界的问题在数学上等价于一个欠约束的优化问题——目标函数不唯一、约束集不完整，此时任何「立刻求解」的尝试都是在一个错误的问题上做优化。正确的第一步不是解题，而是把问题变成良定义（well-posed）的形式：补齐目标、约束与评价标准，才能谈得上求解。这正是本模块要给的方法论。

在 XPENG TSR 的语境下，这类问题会以更具体但同样模糊的方式出现：「近期路测发现标志识别体验不够好，你来负责改进」——这句话里没有说是哪类标志、哪种场景、要改进什么指标、预算是多少。本模块接下来的每一节，都会用这句话作为贯穿始终的例子。

不要把「模糊」误判为「面试官没准备好」。已经出现在正式 JD 里的岗位职责原文是 Problem-Solving，而不是 Algorithm Knowledge——这意味着面试官很可能是故意不把问题说完整的，故意程度因人而异，但你的应对策略应该对此保持一致：永远先假设它是故意的。

2澄清问题清单模板：六个维度，覆盖需求空间的正交轴

与其临场现想问什么，不如背下一个六维度清单。这六个维度是从「一个需求规格必须包含什么」反推出来的——少了任何一个，你后面的方案都会在某个方向上站不住脚。

维度要问的问题模板为什么它是独立的一维落到「提升 TSR 效果」上的具体问法
目标 Goal「效果」具体指哪个指标？提升多少算达标？不同指标（召回/精确率/稳定性）对应完全不同的技术路线「您说的‘效果’具体是指检出的召回率、误检率，还是多帧输出的稳定性（比如闪烁）？」
用户 User这个改进最终服务于谁、在什么场景下被使用？同一个模型对「城市道路」和「高速」的用户价值完全不同「这次是聚焦城市道路场景，还是包含高速和乡村路？」
约束 Constraint延迟、算力、开发周期、能不能重训整个模型？约束决定了可行方案集合，不问约束会提出不可能实现的方案「上线窗口是多久？可以重训检测器，还是只能在后处理层面改？」
现状 Baseline现在的水平是多少？已知的短板在哪？不知道起点，就无法判断「提升」是否已经发生、发生了多少「现在这一项的基线大概是多少？有没有已知的具体失效场景？」
成功标准 Success metric怎么验收？谁来判断「做完了」？没有验收标准的项目永远做不完，也没法总结汇报「怎么算这次改进成功？是看某个离线指标涨了，还是要过路测门禁？」
不做什么 Non-goals这次明确排除在外的是什么？范围裁剪是防止方案膨胀的唯一手段，也是本模块反复强调的加分项「有没有什么是这次明确不管的，比如新增标志类别，或者换传感器？」
┌─────────────────────────────────────────┐ │ 澄清清单 · 六维度自检表 │ │ ──────────────────────────────────── │ │ [ ] 目标 Goal —— 提升哪个指标？ │ │ [ ] 用户 User —— 谁在用、什么场景？│ │ [ ] 约束 Constraint —— 延迟/算力/周期？│ │ [ ] 现状 Baseline —— 起点在哪？ │ │ [ ] 成功标准 Success —— 怎么算过关？ │ │ [ ] 不做什么 Non-goals —— 明确排除什么？ │ │ ──────────────────────────────────── │ │ 六格全打勾才算「问完」， │ │ 打勾数 ≠ 提问数量——问十遍「目标」 │ │ 仍然只算打勾一格。 │ └─────────────────────────────────────────┘

直白说

很多人以为「问得多」就是「问得好」，于是把六个问题在心里默念一遍，逐字照搬地问出来。这是错的——面试官记的不是你问了几个问题，而是你的问题覆盖了几个不同的维度。连续问三个都属于「目标」维度的变体（「具体是哪个指标？」「这个指标现在多少？」「这个指标为什么重要？」——注意第二个其实是「现状」维度），看起来问得很勤快，实际打勾数只有一到两格。

严谨说

严谨地说，这六个维度构成需求规格空间的一组近似正交基：目标和成功标准虽然相关（有目标才谈得上成功与否），但前者定义方向、后者定义阈值，仍然是两个独立可被单独问漏的信息；约束和不做什么也容易被混为一谈，但前者是「外部强加的限制」，后者是「你主动做的范围裁剪」——这个区分在面试里非常值钱：主动提出「不做什么」是加分项，被动接受约束只是及格线。

常见坑：把「问了很多问题」等同于「问得系统」。自检方法很简单——问完之后在心里对着六维度清单逐格打勾，如果某一格始终是空的，说明你的澄清是有偏的，通常偏向你自己更熟悉、更愿意谈的那个维度（技术出身的人常常反复确认「约束」和「现状」，却从不问「不做什么」）。

3把开放题收敛成有边界的题：假设 + 声明 + 请确认

问完清单不代表问题就有边界了——面试官很可能对一半的问题回答「你觉得呢，你来定」。这才是这道题真正的分水岭：面试官把决策权交还给你的那一刻，考的是你能不能替他把问题收边，而不是继续把球踢回去。

开放题："提升 TSR 效果" │ ▼ ① 问清楚最模糊的那个词（"效果"到底指什么指标？） 仍然开放："提升 TSR 的召回率" │ ▼ ② 补上场景与约束（哪种场景？多远检出？延迟预算？） 半收敛："在城市道路场景下，把 80m 以内限速标志的召回率提上去" │ ▼ ③ 声明一个具体假设，并请面试官确认 已收敛 + 待确认："我先按『限速标志 · 80m 检出距离 · 不新增误检』 这个假设往下展开；如果您觉得该聚焦别的标志类别 或者别的场景，我们随时可以切换。" │ ▼ ④ 面试官点头 / 提出修正 —— 你已经把「猜题」的责任转移成了「共识」

第③步里那句确认话术，是整个模块里唯一需要逐字背下来的句子，因为它同时做了三件事：

这句话做了什么具体体现如果不这么说会怎样
显式声明假设「我先按……这个假设」——把隐含决定摊在明处面试官不知道你在假设什么，只会觉得你「自己在讲自己的」
保留退出通道「如果……我们随时可以切换」——承认这只是一个起点，不是唯一答案显得武断，好像你觉得自己的猜测一定对
把决定权还给面试官，但不等他回答说完就继续往下讲，不停下来等一个「同意」——除非他主动打断如果每说一个假设都停下来等确认，等于把主动权又交还回去，退化成「过度澄清」

直白说

直白地说：这句话的作用是「我先选一条路走给你看，走错了你随时可以喊停」。这比「您觉得应该聚焦哪个场景？」高明得多——后者是在提问，前者是在提议，提议的默认状态是「成立，除非被反对」，提问的默认状态是「不成立，直到被回答」。面试的时间是稀缺资源，默认状态为「成立」能让你立刻往前走。

严谨说

这也是satisficing（满意即可，而非最优）决策的一个具体应用：在信息不完整、时间有限的条件下，理性的策略不是穷尽所有备选方案再选最优，而是选一个足够合理的假设，边执行边根据反馈修正。这与 C65-03（权衡与决策）里「可逆决策要快」的结论是同一件事——选择「按 A 假设往下走」这个决定本身几乎是零成本可逆的（面试官一句话就能让你切到 B），所以没有理由在它上面犹豫。

三个收敛案例：从「一句话」到「一个可执行的题面」

原始开放题收敛后的题面用的假设
「提升 TSR 效果」「在城市道路场景，把限速标志在 80m 内的召回率提升，且不新增误检」假设「效果」=召回，场景=城市道路，约束=误检不能涨
「模型上线后用户反馈不好」「先确认是不是特定场景（夜间/逆光）的召回下降，用分场景切片评测定位」假设「不好」可以通过分桶评测被观测到，而非纯主观
「给这个检测器做优化」「先假设‘优化’指延迟而非精度，因为上一句提到了‘车上跑起来卡’」从上下文的只言片语（‘卡’）里抓取线索，而不是死等对方讲清楚
反面案例：来回确认到面试结束。「您是说召回还是精确率？」「那城市道路还是高速？」「那需要多快？」——如果每问一句都停下来等答案，且对方总是回「你定」，你会在澄清阶段耗光大半场时间。正确的应对是在第 2–3 轮追问后就主动收口，自己拍一个假设往前走——第 6 节会给出「何时该停」的量化判据。

4开放题往往不止一个方向：用「影响 × 成本 × 不确定性」排序

收敛出一个题面之后，通常会发现候选的改进方向不止一个——继续拿 TSR 举例，「提升召回」可能有五六条路可走：加数据、换模型、调分配策略、做时序融合、修标注……面试官这时候常追问一句：「如果只能先做一件事，你会先做哪个？」这是本节要解决的问题：把「我觉得应该先做 A」变成一个可以摆到桌面上讨论的排序。

排序依据三个独立的量——这三个词就是要点里说的影响 × 成本 × 不确定性：

维度含义怎么估TSR 例子里的体现
影响 Impact如果做成了，目标指标能提升多少1–10 打分，或直接给区间估计（呼应 C65-01 的估算法）「加时序投票」对稳定性影响大，对召回本身影响有限
成本 Cost需要多少人天/算力/日历时间按「重训模型」>「调超参」>「后处理规则」的经验梯度排「换检测器架构」成本远高于「加一层多帧投票逻辑」
不确定性 Uncertainty做了之后，效果符合预期的把握有多大取其补集confidence（置信度）参与计算更直观「重新标注噪声标签」的收益比「上新模型架构」更确定
\[\text{Score} \;=\; \frac{\text{Impact} \times \text{Confidence}}{\text{Cost}}, \qquad \text{Confidence} = 1 - \text{Uncertainty}\]

这个打分公式不是本模块发明的，它是产品管理里常用的 RICE 打分法（Reach × Impact × Confidence ÷ Effort）去掉「触达范围」维度后的简化版——面试场景下候选方案通常影响的是同一批用户，Reach 项可以省略。

候选方向Impact(1-10)Confidence(0-1)Cost(人天)Score排名
加多帧时序投票降低闪烁70.831.87① 第一优先
难例挖掘：易混淆标志对(限速60/80)60.741.05② 第二优先
扩充远处小目标训练数据90.570.64③ 值得做但不急
重新标注一批噪声标签40.650.48④ 收益有限
换用更强检测器架构60.490.27⑤ 明确暂缓

直白说

把这张表念给面试官听，比直接说「我觉得先做 A」有说服力得多：「时序投票的分数最高，因为它成本低（3 人天）、把握大（0.8），虽然对召回本身影响不是最大的；扩数据的 Impact 最高，但成本和不确定性都大，我会排在后面而不是排除。」这句话同时展示了排序方法和「我知道自己在权衡什么」——两者都是加分项。

严谨说

需要主动说明这个模型的局限：这三个数字都是你在面试现场的估计，精确到小数点后两位没有意义，真正有价值的是相对顺序与排序对估计误差的敏感度——如果把「时序投票」的 Impact 从 7 改到 5，Score 变成 1.33，排序仍然不变，说明结论是稳健的；但如果「难例挖掘」和「扩数据」的分数很接近，就要老实说「这两个我打分打得很接近，实际会先做一个小实验来决定」——这比装出虚假的确定性更专业。

面试官通常不关心你的数字精不精确，只关心你有没有一个可复现的计算过程。把「拍脑袋排序」换成「三个维度打分再排序」，即使分数本身是估的，别人也可以顺着你的逻辑挑战某一格分数——而拍脑袋排序是没法被挑战的，没法被挑战的结论在面试里反而更危险，因为它显得不可推敲。

5读面试官的信号：他在引导、在压力测试、还是只是好奇

澄清与收敛的节奏，很大程度上取决于面试官此刻在扮演哪种角色——同样一句追问，背后的意图可能截然不同，而误判角色会导致完全错误的应对。

信号类型典型表现背后的意图正确的应对
引导 Guiding在你卡住时抛出一个具体的小问题（「你觉得延迟会是瓶颈吗？」）他在给你一个台阶，希望你顺着走下去顺着接住，明确说「对，这提醒了我……」再继续，不要绕开
压力测试 Stress test对你已经给出的方案连续追问「为什么不是 B？」「如果……呢？」他在测试你的方案有多结实，而不是在暗示你答错了不要立刻推翻自己。先守住原假设，说明它成立的条件，除非对方给出让你信服的反例
好奇 Curiosity语气放松，问的是「那这个在实际场景里怎么用？」这类延伸问题他单纯觉得有意思，或者想看看你的知识广度可以适度展开，甚至反过来问他们团队的真实做法，这是建立好感的机会

直白说

分辨这三者最实用的方法不是听内容，是听语气和时机：压力测试通常发生在你刚给出一个略显草率的结论之后、语速比平时快、连续追问不给你太多喘息；引导通常发生在你明显卡住超过 10 秒之后、语气比平时更轻；好奇通常发生在一个阶段性结论已经站稳之后、语气放松、带有「顺便问一下」的味道。

严谨说

更可操作的经验法则是：把压力测试当作对「你的论证」的测试，而不是对「你的答案」的测试。面试官反复追问「为什么不是 B」，最常见的期望回应不是「那我们换成 B 吧」，而是「A 在 X 条件下优于 B，因为……；但如果条件变成 Y，我同意 B 会更好」——展示你知道自己论证的适用边界，比展示你愿意随时改主意更值钱。频繁被一问就倒的候选人，传递的信号是「他自己也不确定这个结论」。

最容易犯的误判：把压力测试当成「我说错了」。于是立刻放弃刚才的假设，转向面试官暗示的方向——即使那个方向站不住脚。这种「一压就倒」的反应，在真实工作里对应的是「一被上级质疑就改方案，不管质疑是否成立」，是资深工程师形象的反面。正确姿态是先用一句话确认自己没理解错他的追问，再决定是坚持、修正、还是承认对方是对的。

6何时该问、何时该假设并往前推：卡在澄清阶段不动也是扣分项

前面几节都在讲「怎么问」，这一节讲一件同样重要、却常被忽略的事：什么时候应该停止问，直接假设并往前推进。这不是一个软性的建议——长时间停留在澄清阶段本身就是一个扣分项，它和「过早收敛」是同一枚硬币的两面，都会被面试官记下来。

遇到一处不确定，要不要问？ │ ┌──────────────────┴──────────────────┐ │ │ 猜错的代价高吗？ 澄清阶段已经用掉的时间 （方向性错误 / 安全相关 / 后续推倒重来） 是否已经超过预算的 20%？ │ │ 是 → 问一句，成本很低 是 → 停止提问， │ 声明假设并往前推进 否 → 算期望代价： │ E[错] = P(猜错) × 猜错的代价 否 → 回到左边继续判断 │ E[错] 明显大于「问一句打断节奏」的代价 → 问 E[错] 与问一句的代价相当或更小 → 假设并往前推进
\[\mathbb{E}[\text{Cost}_{\text{wrong}}] \;=\; P(\text{assumption 错}) \times \text{Cost}_{\text{if wrong}}, \qquad \text{ask} \iff \mathbb{E}[\text{Cost}_{\text{wrong}}] > \text{Cost}_{\text{ask}}\]

这个判据落到具体场景里非常好用：

场景猜错代价判断该怎么做
「效果」到底指哪个指标极高——整个方案的方向都可能错E[错] 远大于问一句的成本必须问，这是第 2 节清单里的「目标」维度
示例图片是不是要脱敏处理低——这是实现细节，写代码时顺手改一行E[错] 很小直接假设「要脱敏」并说出来，不必占用宝贵的澄清时间

纠结「城市道路」的确切定义要不要再确认一次低，且已经问过一次类似的问题重复澄清同一维度，边际收益趋近于 0不要再问，直接用你已有的理解往前走

直白说

很多候选人对「多问几句更保险」这件事有一种执念，但保险感是虚假的——面试官的耐心和面试的总时长都是硬约束，每多问一句不那么关键的问题，都是在拿后面「展示分析能力」的时间去换一个低价值的确定性。对照第 4 节的打分法：问问题这个动作本身也有 Impact/Cost/Confidence——在代价很低的细节上，不问带来的「不确定性」远比多占用的时间划算。

严谨说

这与诊断类问题（C65-02）的信息增益逻辑是一致的：expected value of information（信息的期望价值）如果小于获取这条信息的成本，理性的选择就是不获取、直接用先验行动。唯一的区别是这里的「代价」还包含一个隐藏项——面试官对你时间管理能力的观感，它不出现在数学公式里，却真实地影响最终评分。

「卡在澄清阶段不动」是本节要根除的行为，它比「假设猜错」更致命。假设猜错了，你还有机会说「我发现这个假设不成立，让我调整」——这本身是加分项（见 C65-00 的沟通铁律）。而卡在澄清阶段，面试官看到的是你没有能力在信息不全的情况下做出任何决定，这是一个更根本性的负面信号，因为几乎所有真实工作场景信息都是不全的。

7完整演练：从「提升 TSR 效果」到一份可执行方案

把前六节串起来，走一遍完整流程。面试官原话：「我们想提升 TSR 的效果，你会怎么做？」

  1. ① 复述：「我理解一下：目标是让 TSR 系统的表现变好，但‘效果’具体指什么、在什么场景下、有什么约束还不清楚，我想先确认几件事。」
  2. ② 六维度提问（覆盖检查）：依次问目标（哪个指标）、用户/场景（城市道路还是高速）、约束（能不能重训、延迟预算）、现状（现在大概什么水平）、成功标准（怎么算达标）、不做什么（这次不管什么）。假设面试官对「目标」「场景」给了明确回答（召回、城市道路），对其余几项说「你自己定」。
  3. ③ 收敛并声明假设：「现在的信息是：召回、城市道路。我再补一个假设——既然没提到重训整个模型的预算，我先假设这次改动不涉及重训检测器，聚焦在数据、分配策略和后处理这几层。我先按这个假设往下展开，如果预算其实更宽松，我们随时切换。」
  4. ④ 列出候选方向并用 Impact×Confidence÷Cost 排序：给出第 4 节那张表，念出排序结果和理由。
  5. ⑤ 给出分阶段计划：「第一步做时序投票，一周内可以看到效果且风险低；第二步做难例挖掘处理易混淆标志对；数据扩充和换架构作为后续选项，先不动。」
  6. ⑥ 主动收尾：「这是我基于‘城市道路 + 不重训检测器’这个假设给出的排序。如果这次其实更看重高速场景，我会把优先级往‘远距离小目标’那条线调整——这个我们可以再讨论。」
阶段反面写法（低分）正面写法（高分）
复述直接说「行，那我先看看数据有没有问题」先复述目标本身还不明确，再进入提问
提问只问「现在准确率多少」，问完就开始讲方案覆盖六个维度中的四个以上，且互相不重复
收敛面试官说「你定」之后继续追问「那到底是哪个」主动拍板一个假设，并声明可以随时切换
排序「我觉得应该先做时序投票」，不给理由给出 Impact/Confidence/Cost 三项与排序逻辑
收尾讲完排序就停下等下一个问题主动指出假设的边界，反问式确认是否需要调整

直白说

这套流程走下来大概只需要 3–4 分钟，比大多数候选人预想的要快得多。它快的原因不是省略了哪一步，而是每一步都有明确的产出和明确的「往下走」的触发条件——六维度问完就收敛，收敛完就排序，排序完就给计划，全程没有一处「等对方给答案」的停顿。

严谨说

从整个课程体系看，这个流程正是 C65-00 四步框架（clarify → decompose → hypothesize & verify → converge & tradeoff）在「需求本身模糊」这一特定场景下的展开：本节的①②对应「澄清」，③对应把「分解」和「假设」提前到需求层面，④⑤对应「假设与验证」中的方案侧展开，⑥对应「收敛与权衡」。掌握了这一节，你等于把四步框架在最难的起点——一句话都说不清楚的需求——上完整地走了一遍。

如果只能记住一句话：澄清的目的不是把问题问到毫无歧义，而是问到「你敢为这个假设负责」为止。毫无歧义在真实工作里几乎不存在，敢负责的假设+可撤销的声明，才是可执行的起点。

8研究前沿与开放问题

需求澄清这件事看似是纯粹的软技能，但背后其实有一条持续演进的研究脉络，而且随着 AI 系统本身开始承担「提问」这个角色，它正在变得更重要，而不是更次要。

  • 「好的澄清问题」本身可以被建模和排序。对话系统与问答领域一直在研究「该问哪个澄清问题收益最大」，其核心思想与本模块第 4 节的打分法同构——都是在信息不完整时，对「问哪一句话」本身做期望价值估计。这提示我们：澄清能力不是纯粹的沟通技巧，而是一种可以被形式化、被训练的推理能力。
  • 需求工程（requirements engineering）里的「模糊性」被证明是系统性的，不是个别项目的意外。经典结论是：用户几乎从不会在第一次描述里给出完整、无歧义的需求，这不是因为用户偷懒，而是因为tacit knowledge（默会知识）——很多约束和期望，当事人自己都是隐式持有、说不出来的，只有被具体问题「戳」到才会浮现。这解释了为什么本模块的清单要覆盖六个维度而不是一个开放式的「还有什么要补充的吗」——后者几乎总是得到「没有了」这个（错误的）回答。
  • 大语言模型 agent 让「何时主动澄清、何时直接假设执行」变成一个正在被研究的决策问题。过度澄清的 agent 会让用户觉得啰嗦、打断心流；从不澄清的 agent 会在错误的假设下越走越远。目前工业界的经验做法与本模块第 6 节的判据高度一致——按「猜错代价」分级，低风险操作直接执行并事后可撤销，高风险操作才停下来确认。这套人类面试沟通的经验法则，正在被重新发现为 AI 系统设计的基本原则。
  • 「假设并前进」的最优停止点缺少统一理论。本模块给出的判据（澄清时间超过预算的某个比例即强制停止）是一条经验法则，而非从第一性原理推导的最优解——真正的最优停止点应当依赖具体任务的代价结构，这在面试的高压力、低样本环境下几乎不可能精确求解，只能退而求其次，用一条足够好、足够稳健的经验阈值。

★ 必读：Rob Fitzpatrick, The Mom Test——全书就是一套「如何通过提问获得真实需求而不是被礼貌敷衍」的方法论，与本模块「六维度清单」的设计动机直接对应。★ Marty Cagan, Inspired: How to Create Tech Products Customers Love 第II部分「发现」章节——讲清楚了「目标 / 约束 / 成功标准」为什么必须在动手之前拍板。★ Rao & Daumé III, Learning to Ask Good Questions: Ranking Clarification Questions using Neural Expected Value of Perfect Information（ACL 2018）——把「该问哪个澄清问题」形式化为期望信息价值最大化，是本模块第 4/6 节打分法的学术对应物。
