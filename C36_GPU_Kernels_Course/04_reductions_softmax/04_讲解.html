1规约问题：天生串行的累加

到目前为止我们处理的算子（向量加、矩阵乘的逐元素累加）都有一个共同点：输出彼此独立。每个线程算自己那一格，互不打扰，天然并行。但深度学习里到处是另一类运算——reduction（规约）：把一组数聚合成一个标量。求和、求最大、求范数、求方差，softmax 的分母、LayerNorm 的均值、loss 的累加，全是规约。

规约的麻烦在于它天生是串行的。最朴素的写法 acc = 0; for x in arr: acc += x 有一条贯穿始终的依赖链：第 i 步必须等第 i-1 步算完。n 个元素就是 n 步、O(n) 的深度（depth，即关键路径长度）。在一台有几千个核心的 GPU 上，让一条线程串行地加 n 个数，等于让 99.9% 的硬件围观一个线程干活——这是对并行机器最大的浪费。

直白说

串行求和像一个人点钞：一张一张数，数到第一万张才知道总数。GPU 想要的是分组并行点钞：一千个人同时数，再把各组的小计汇总。问题是「汇总」本身又是个规约……这就是本模块要解开的递归。

严谨说

形式上，规约把二元算子 ⊕ 折叠到序列上：x₀ ⊕ x₁ ⊕ ... ⊕ x_{n-1}。朴素折叠的计算深度是 O(n)。我们想要的是把深度压到 O(log n)，同时保持总工作量（work，运算总次数）仍是 O(n)——即 work-efficient 的并行规约。

为什么不能像逐元素算子那样，让每个线程算一个输出就完事？因为规约的输出只有一个，而我们有几千个线程。要么让一个线程包揽全部（浪费并行），要么让多个线程协作产出这一个结果——而协作就意味着线程之间要交换中间值、要同步。规约因此是第一个真正逼我们用上 shared memory 和 __syncthreads()（模块 02 的工具）来组织线程间协作的算子。前几个模块各管一摊，这里第一次把它们拧在一起。

一句话抓住本模块：规约的并行化 = 用结合律把一条 O(n) 的依赖链，重排成一棵 O(log n) 深的树。这棵树后面会长成 softmax，再长成 FlashAttention 的核心递推。先把树看懂。

2树形规约：用结合律换 O(log n) 深度

把串行链改成并行，关键是利用结合律：(a⊕b)⊕c = a⊕(b⊕c)。既然加法可以任意结合，我们就两两配对地加，每一轮把待合并的元素数砍掉一半。这就是 tree reduction（树形规约）。

n=8 的树形规约（每轮一半线程把另一半加过来 + 一次同步）： 轮 0: x0 x1 x2 x3 x4 x5 x6 x7 (8 个活跃) \ / \ / \ / \ / 轮 1: x0+x4 x1+x5 x2+x6 x3+x7 · · · · (4 个活跃, 4 个空闲) \ / \ / 轮 2: (..)+(..) (..)+(..) · · · · · · (2 个活跃) \ / 轮 3: 总 和 · · · · · (1 个活跃) log2(8)=3 轮搞定（而非 8 步）。每轮之间要 __syncthreads()。

GPU 上的标准写法用步长（stride）减半的模式：第一轮步长 n/2，线程 t 把 buf[t] 和 buf[t+stride] 相加；然后步长减半、同步、再来一轮，直到步长为 1。活跃的线程数也随之减半。注意每轮之后必须 __syncthreads()——否则下一轮可能读到上一轮还没写完的中间结果（这是 GPU 上最经典的竞态 bug）。

深度从 O(n) 降到 O(log n)：n=1024 时，串行要 1024 步，树形只要 10 步。总工作量仍是 n-1 次加法（每个非叶节点一次），所以是 work-efficient 的——我们用 log 的深度换来了海量并行，没有浪费额外的算力。

步长减半还顺手躲过了bank 冲突（模块 02）。减半模式下第一轮是 buf[t] += buf[t+stride]，两个地址相距 stride（≥32 时整除 32），落在同一组 bank 上但属于不同线程的不同访问，硬件可并行；而相邻配对模式 buf[2t] += buf[2t+1] 让活跃线程访问偶数地址 0,2,4,…，相邻活跃线程隔 2 个字、bank = (2t) mod 32 只覆盖偶数 bank，造成 2-way 冲突。所以「先加远的」一举两得：既无 warp 发散，又无 bank 冲突——这是 NVIDIA 规约优化讲义里从朴素到极致七版优化中最早、收益最大的一步。

树形规约里步长减半（先加远的）通常优于步长加倍（先加相邻的）。原因是减半模式下，活跃线程是连续的前一半 t < stride，它们恰好落在连续的 warp 里——不活跃的 warp 整组退出、毫无warp divergence；而相邻配对模式（t % (2*stride) == 0）会让每个 warp 内一半线程活、一半死，处处发散。同样的 O(log n)，访存与发散行为却天差地别，这正是 NVIDIA 那篇规约优化讲义的核心教训。

3浮点结合律：为什么结果会有微小差异

这里埋着一个数值上的细节，初学者常被它吓到：树形规约和串行规约得到的结果可能不完全相等。原因是——浮点加法并不严格满足结合律。

数学上 (a+b)+c = a+(b+c)，但在有限精度的浮点世界里，每次加法都要把结果舍入回最近的可表示数。不同的加法顺序 = 不同的中间舍入 = 略微不同的最终值。一个经典例子：

\[(\,10^{16} + 1\,) - 10^{16} \;=\; 0 \quad\text{而}\quad 10^{16} + (\,1 - 10^{16}\,) \;=\; 1\]

前者里 10^16 + 1 因为精度不够，1 被舍入吞掉了。所以并行规约的结果依赖于归约树的形状，跨硬件、跨 block 尺寸都可能有最后几位的差异。

直白说

别慌——这不是 bug，是浮点的天性。差异通常在 1e-6 量级（单精度），对训练和推理毫无影响。你只需知道：要求两种规约 逐位相等 是不现实的，对拍时用 np.allclose 给个合理的容差就对了。

严谨说

有意思的是，树形规约往往比串行规约更精确。串行累加里，acc 越加越大，后面的小数被它的舍入误差淹没（误差随 n 线性累积）；树形规约让相近量级的数先相加，舍入误差只随 log n 增长。这也是高质量数值库偏爱成对（pairwise）求和的原因。

一个真实世界的坑：因为并行规约结果依赖线程调度与 block 尺寸，同一份代码两次运行可能给出最后几位不同的 loss（尤其用了原子加 atomicAdd 时，累加顺序完全不确定）。这会破坏逐位复现。需要可复现时，要么用确定性规约算法，要么接受 atol 容差——切勿用 == 比较浮点规约的结果。

4warp shuffle 规约：绕过 shared 与同步

树形规约的每一轮都要 __syncthreads() 同步整个 block，还要把中间值在 shared memory 里读写一遍。对于一个 warp 内部（32 个锁步线程）的规约，有更快的办法：warp shuffle——让线程直接交换寄存器，完全绕过 shared memory 和同步。

指令 __shfl_down_sync(mask, val, offset) 让 lane t 直接读到 lane t+offset 的寄存器 val。于是 warp 内规约就是 5 步的折半：offset = 16, 8, 4, 2, 1，每步把自己和下方 offset 处的值相加：

warp 内 32-lane 规约（shuffle-down，5 步，无 shared、无 barrier）： offset=16: v[t] += shfl_down(v, 16) # lane 0..15 拿到 16..31 offset= 8: v[t] += shfl_down(v, 8) offset= 4: v[t] += shfl_down(v, 4) offset= 2: v[t] += shfl_down(v, 2) offset= 1: v[t] += shfl_down(v, 1) → lane 0 现在持有 32 个数的总和。 log2(32)=5 步。

为什么更快？因为 warp 是锁步执行的，shuffle 在硬件上是 lane 之间的直连，不需要 barrier（warp 内天然同步），也不碰 shared memory（省掉一次往返延迟，还不占 shared 容量、不引发 bank conflict）。这是 warp 级原语相对 shared-memory 规约的纯收益：

维度shared-memory 规约warp-shuffle 规约
作用范围整个 block单个 warp（32 lane）
同步开销每轮 __syncthreads()无（warp 锁步天然同步）
内存往返每轮读写 shared零（lane 间寄存器直连）
bank conflict可能（需 padding 规避）不涉及（不碰 shared）
典型用法warp 间汇总少量结果warp 内规约 32 个值

完整的 block 规约因此是两级的：① 每个 warp 用 shuffle 把自己 32 个值规约成 1 个；② 把每个 warp 的结果写进一小块 shared（只有 block_size/32 个数）；③ 让第一个 warp 再 shuffle 规约这些 warp 结果。两级下来，整个 block 的规约只用了一次 shared 往返加两轮 shuffle，比纯树形规约的 log(block_size) 次同步快得多。

这里值得停下来体会一个反复出现的设计模式：把一个大规约分层成「廉价的局部规约 + 少量的全局规约」。warp shuffle 解决局部（32 个数），shared 解决跨 warp（几个数），如果再大到跨 block，就得借助 global memory 加原子操作、或干脆分两个内核。每往上一层，通信就贵一个数量级，所以好的内核总是把尽可能多的规约压在尽可能低的层级完成。后面的分块矩阵乘、FlashAttention 的块内归一化，骨子里都是这个「分层规约」思想的变体。

记住这个分层套路——warp 内用 shuffle，warp 间用 shared——它在 GPU 编程里无处不在：规约、softmax、甚至 FlashAttention 的块内归一化都按这个两级结构组织。warp 是「免费同步」的最大单位，能在 warp 内解决的就别惊动整个 block。

5数值稳定 softmax 与它的三遍代价

有了规约这把锤子，来看第一个真实的融合目标：softmax。它是注意力的心脏，定义为

\[\mathrm{softmax}(x)_i = \frac{e^{x_i}}{\sum_{j} e^{x_j}}\]

直接照搬公式（exp(x) / exp(x).sum()）有个致命问题：exp 会溢出。注意力的 logits 经常到几十甚至上百，exp(1000) 在 float32 里是 inf，于是分子分母全是 inf，结果是 nan，整个前向直接报废。

解法是减去每行最大值再取 exp。设 m = max_j x_j：

\[\mathrm{softmax}(x)_i = \frac{e^{x_i - m}}{\sum_{j} e^{x_j - m}}\]

为什么这样不改变结果？因为分子分母同时乘了 <code>e^{-m}</code>（一个公共常数），约掉后值完全不变。但数值行为天差地别：现在最大的指数是 e^{0}=1，其余都 ≤ 1，永不溢出。这就是numerically stable softmax，是所有正确实现的标配（模块 00 的对拍热身已经见过它）。

但请数一数它需要几遍扫描整行：第一遍求 max（一次规约），第二遍求 sum of exp(x-m)（又一次规约），第三遍才能算出每个 exp(x_i-m)/sum 写回。三遍 pass——每一遍都要把整行从 HBM 读一次（对长行而言，整行可能放不进寄存器/shared）。注意力受访存限制，这三遍 HBM 往返正是 softmax 的主要开销，也正是下一节要消灭的东西。

这三遍代价正是融合 softmax 内核要消灭的目标：把求 max、求和、归一化三遍扫描合并进一个内核，整行只从 HBM 读一次、中间的 exp 结果留在寄存器/shared 而非落回显存。在访存受限的注意力里，省下的这两趟 HBM 往返就是纯加速——这也是 torch.compile 自动生成 Triton 内核时最爱做的融合之一。下一节的 online softmax 更进一步，把三遍直接压成一遍。

减最大值只是数值稳定技巧，不改变数学含义；别和 softmax 的 temperature（除以 T 改变分布锐度）混淆。前者是必须的工程正确性，后者是改变语义的超参。两者都作用在 exp 之前，但目的完全不同。

6online softmax：一遍流式归一化

能不能一遍就算完 softmax？看似不行——你得先看完整行才知道 max，才知道 sum。但 Milakov & Gimelshein（2018）给出了一个漂亮的递推：一边流式扫描，一边同时维护 max 和归一化和，每当遇到一个更大的值，就用一个校正因子把已经累加的和「回缩」到新基准。这就是 online softmax。

维护两个运行量：运行最大值 m 和运行归一化和 l = Σ e^{xⱼ - m}（注意 l 是相对于当前 m 的）。每来一个新值 xᵢ：

\[m_{\text{new}} = \max(m,\, x_i), \qquad l \leftarrow \underbrace{l \cdot e^{\,m - m_{\text{new}}}}_{\text{校正旧和}} \;+\; \underbrace{e^{\,x_i - m_{\text{new}}}}_{\text{加入新项}}\]

核心是那个校正因子 e^{m - m_new}。当新值比旧 max 大时，max 抬高了，之前所有项的「减去的基准」都变了，于是把旧的和 l 乘以 e^{old_max - new_max} ∈ (0,1]，就等价于把每一个旧项都重新按新基准 e^{xⱼ - new_max} 算了一遍——一次乘法搞定，不必回头重算。

直白说

打个比方：你在班里实时记录「相对最高分的总和」。突然来了个更高分的同学，于是所有人相对最高分的差都变小了。你不用把每个人重算一遍，只要把之前的总和统一乘一个缩小因子（e^{老最高-新最高}），再把新同学加进来。

严谨说

可以严格证明这个一遍递推与三遍 softmax 数学完全等价（归纳法：每步后 (m, l) 恰好等于「目前见过的所有元素」的真 max 与真归一化和）。扫完整行后，softmax(xᵢ) = e^{xᵢ - m_final} / l_final。

跑一遍数字：流式处理 [1, 3, 2]

用 x = [1, 3, 2] 手算一遍，确认递推真的对。初始 m=-∞, l=0：

  1. 来 x=1：m_new=max(-∞,1)=1；l = 0·e^{-∞-1} + e^{1-1} = 0 + 1 = 1。状态 (m,l)=(1, 1)。
  2. 来 x=3：m_new=max(1,3)=3；校正因子 e^{1-3}=e^{-2}≈0.135；l = 0.135·1 + e^{3-3} = 0.135 + 1 = 1.135。状态 (3, 1.135)。
  3. 来 x=2：m_new=max(3,2)=3（没刷新）；校正因子 e^{3-3}=1；l = 1·1.135 + e^{2-3} = 1.135 + 0.368 = 1.503。状态 (3, 1.503)。

验算：直接算 Σe^{xⱼ-3} = e^{-2}+e^{0}+e^{-1} = 0.135+1+0.368 = 1.503，与流式结果逐位吻合。注意第 2 步那个关键动作：max 从 1 跳到 3，于是把已累加的 l=1 乘上 e^{-2} 回缩到新基准——这正是「不回头重算、一次乘法对齐」的全部魔法。本模块 notebook 会把这套手算变成 np.allclose 对拍，确认任意输入下流式 = 三遍。

online softmax 把 softmax 从「先看完全局、再算」变成「边走边修正」。它本身只是把 3 遍压成更少遍的小技巧，但它解锁的能力是致命的：既然不需要先看完整行，就可以把行切成块、一块一块地喂——这正是 FlashAttention 能对 K/V 分块的唯一前提。下一节就把它推广到块。

7分块 online softmax：合并块状态

把上一节的「每来一个元素就更新」升级成「每来一块就更新」。一行被切成若干块，每块先各自算出自己的局部状态 (m_block, l_block)，然后用同一条校正因子规则把两个块的状态合并：

\[m = \max(m_1, m_2), \qquad l = l_1\, e^{\,m_1 - m} + l_2\, e^{\,m_2 - m}\]

这里 (m₁,l₁) 是「目前累积块」的状态，(m₂,l₂) 是「新到的块」的状态。合并时把两边各自相对全局新 max 缩放再相加。逐块合并完所有块，得到的最终 (m,l) 与一次性看完整行的结果逐位无关于分块方式——块大小怎么选，答案都一样。

整行 softmax = 把每块的 (m,l) 状态用结合律合并（与块大小无关）： 块A [x0..x3] → (mA,lA) ┐ ├─ merge → (m,l) ┐ 块B [x4..x7] → (mB,lB) ┘ ├─ merge → 最终 (m,l) 块C [x8..x11]→ (mC,lC) ───────────────────┘ 每个 merge 用校正因子把两边对齐到新 max 再相加。

注意这个 merge 运算是可结合的（associative），所以它不仅能串行地一块块累积，还能像第 2 节那样组织成规约树并行合并——这就是为什么在线 softmax 既能流式（FlashAttention 的串行 KV 循环），又能并行（树形归并）。结合律再次贯穿始终。

这条「分块 + 状态合并」的递推，就是 FlashAttention 注意力内核的数学骨架——下一模块只需再给状态加一个输出累加器 O（同样用校正因子缩放），就能在永不物化 n×n 分数矩阵的前提下算出精确注意力。在线 softmax 是 FlashAttention 的「发动机」。原始论文见 Milakov & Gimelshein 2018，应用见 Dao 2022（清单见 ../references.md）。

8研究前沿与开放问题

规约与 softmax 看似基础，却是大量前沿内核工作的发源地：

  • 融合 softmax 内核：把三遍（或在线一遍）softmax 写成单个内核，整行只读一次 HBM、中间的 exp 结果留在寄存器/shared 而非落回显存。这是访存受限算子的标准优化，也是 torch.compile 自动生成 Triton 内核时最常做的融合之一。
  • 在线 softmax = FlashAttention 的钥匙：没有它，注意力就必须先物化整个 n×n 分数矩阵才能 softmax（显存 O(n²)）。在线递推让分数可以分块算、用完即弃，是长上下文（32k、128k+）可行的根本算法前提。
  • 反向传播的数值稳定：softmax 的梯度涉及 p ⊙ (g - (p·g)) 的形式，FlashAttention 反向不保存概率矩阵，而是用前向存下的 LogSumExp（m + log l，每行一个标量）重算。如何在重算中维持数值稳定、避免灾难性抵消，是活跃的工程细节。
  • 结合扫描（associative scan）视角：在线 softmax 的状态合并是一个 monoid（含单位元 (-∞, 0)、满足结合律），因此可用parallel scan 在 O(log n) 深度并行。这把 softmax、规约、前缀和、甚至线性注意力/SSM 统一在同一代数框架下，是近年序列建模的重要视角。
  • 更低精度与在线归一化：FP8/BF16 下 exp 的动态范围更紧张，在线维护 max 帮助把指数压回安全区间；FlashAttention-3 在 Hopper 上结合 FP8 与在线 softmax 的稳定性处理，是这条线的最新前沿。

必读：Milakov & Gimelshein 2018《Online normalizer calculation for softmax》（在线 softmax 原始论文）、NVIDIA《Optimizing Parallel Reduction in CUDA》（规约从朴素到极致的七版优化）、Blelloch 1990（并行扫描的代数基础）、以及 Dao 2022《FlashAttention》（在线 softmax 的杀手级应用）。完整清单见 ../references.md。
