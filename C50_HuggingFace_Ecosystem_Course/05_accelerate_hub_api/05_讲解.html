1Accelerate：四行改造与它藏起来的东西

accelerate 的定位是：让同一份训练代码在单卡 / 多卡 / 多机 / TPU / 混合精度下都能跑，而你只改四行。Trainer 内部就是用它。

from accelerate import Accelerator

accelerator = Accelerator(gradient_accumulation_steps=4)      # ① 建
model, optimizer, dataloader, scheduler = accelerator.prepare( # ② prepare 四件套
    model, optimizer, dataloader, scheduler)

for batch in dataloader:
    with accelerator.accumulate(model):                        # ③ 累积上下文
        loss = model(**batch).loss
        accelerator.backward(loss)                             # ④ 替代 loss.backward()
        optimizer.step(); scheduler.step(); optimizer.zero_grad()

# 保存时要先解包
accelerator.wait_for_everyone()
unwrapped = accelerator.unwrap_model(model)
accelerator.save_model(unwrapped, "out")
这一行它替你做了什么
Accelerator()读环境（accelerate config / 环境变量）决定后端：单卡 / DDP / FSDP / DeepSpeed / TPU；初始化进程组
prepare(model).to(device)；多卡时包 DDP/FSDP；混合精度时挂 autocast
prepare(dataloader)换掉 sampler 做分布式切分（每个 rank 只拿 1/N）；把 batch 自动搬到设备
prepare(optimizer)包一层以配合梯度缩放（fp16 的 GradScaler）与梯度累积
accelerator.backward(loss)fp16 时先 scale 再 backward；累积期间跳过梯度同步（省通信）
accumulate(model)自动管理「什么时候该同步梯度」——累积中间步用 no_sync() 避免无用的 all-reduce

直白说

最容易被忽略、也最重要的是 prepare(dataloader) 换掉了 sampler。这意味着你的 batch_size 是每个进程的——8 卡时实际有效 batch 是 8 倍。这与 TrainingArguments 的 per_device_train_batch_size 是同一件事（模块 03 的乘法关系）。写裸 accelerate 代码时忘了这一点，就会「换台机器超参全变」。

严谨说

第二个隐藏行为是累积期间的梯度同步优化。DDP 默认在每次 backward 后就 all-reduce 梯度，但梯度累积时中间几步的同步是纯浪费（最终只用累加值）。accelerator.accumulate() 会在非同步步用 model.no_sync() 跳过通信——在 grad_accum=8 时能省掉 7/8 的梯度通信量。这是个不小的加速，而且完全对用户透明。自己写 DDP 循环忘了这个是常见的性能损失来源（C39 有完整的通信量分析）。

四类日常操作的正确写法

  • 打印/日志只在主进程：accelerator.print(...)（或 if accelerator.is_main_process:）。否则 8 卡会打 8 遍。
  • 保存前解包：accelerator.unwrap_model(model)。直接保存 DDP 包装后的模型会得到带 module. 前缀的键名——加载时全部 missing_keys（模块 01 那个坑）。
  • 收集指标：accelerator.gather_for_metrics(preds)。它比裸 gather 多做一件事——去掉分布式采样为了整除而重复的样本，否则最后几条会被重复计入。
  • 同步点：accelerator.wait_for_everyone()。在保存、评估、写文件前后需要，否则 rank 0 还没写完别的 rank 就去读。
gather_for_metrics vs gather 是个具体且容易出错的区别。分布式采样器为了让每个 rank 拿到相同数量的样本，会在数据集末尾重复少量样本（padding the dataset）。裸 gather 会把这些重复样本也收上来，导致评估指标有微小偏差（数据集小、卡多时偏差更明显）。gather_for_metrics 知道原始长度并裁掉重复部分。症状是「多卡评估结果与单卡略有不同」——很容易被误认为是随机性。

2Hub 与 safetensors：分发、版本与安全

模型要给别人用（或给自己的推理服务用），就要经过 Hub 或某个等价的存储。这里有三件需要讲清的事。

① revision：可变标签 vs commit sha

# ❌ 不可复现：main 分支随时会变
model = AutoModel.from_pretrained("org/model")

# ✅ 可复现：钉死 commit
model = AutoModel.from_pretrained("org/model",
                                  revision="a1b2c3d4e5f6...")   # 或 tag "v1.2"

# 记录到实验日志里（C37/C40）
from huggingface_hub import HfApi
sha = HfApi().model_info("org/model").sha
print(f"loaded revision={sha}")

Hub 的缓存按 commit sha 分目录（snapshots/<sha>/），所以钉死 revision 既保证可复现，也保证缓存命中稳定。用 main 的项目在上游更新权重后会静默换模型——这是「昨天还好今天变差」的一个真实来源。

② safetensors：为什么它比 pickle 重要

pytorch_model.bin（pickle）model.safetensors
格式Python pickle 字节流header JSON + 连续张量字节
加载时执行代码会（__reduce__ 可运行任意命令）不会（纯数据解析）
零拷贝 / mmap❌ 需要反序列化到内存✅ 可直接内存映射
部分加载❌ 要读整个文件✅ 按 tensor 名单独读
加载速度（大模型）慢快 2–5 倍
pickle 是可执行的

从不可信来源加载 .bin 等于运行陌生人的脚本。pickle 的反序列化会调用对象的 __reduce__，构造一个恶意 pickle 让它执行 os.system(...) 是教科书级的攻击。safetensors 从格式上消除了这个可能。同样的道理适用于 trust_remote_code=True——它会执行 repo 里的 modeling_*.py。两者都只对可信来源使用。生产上应该：只从组织内部 registry 或已审计的 repo 加载、强制 use_safetensors=True、并对权重文件做哈希校验。这与 C48 模块 01 的镜像供应链安全是同一类问题。

③ 上传：模型卡片不是可选项

push_to_hub 很简单，但一个只有权重没有说明的 repo 三个月后连你自己都用不了。模型卡片至少要写清六件事：

  • 基座与 revision：从哪个 checkpoint 的哪个 commit 微调而来。
  • 数据：训练数据是什么、多少条、怎么构造的、有什么已知偏差。
  • 超参：有效 batch、lr、epoch、LoRA 配置（直接贴 TrainingArguments）。
  • 评测：在什么集合上、什么指标、多少个种子、与什么基线比。
  • 输入格式：必须写清 chat template 或 prompt 格式——这是使用者最需要、最常缺失的信息。
  • 限制与许可：不适用的场景、基座模型的许可传递性。

关于许可有一条实操提醒：微调模型的许可通常受基座许可约束。Llama 系有自己的社区许可（含使用量与命名条款），Gemma、Qwen 等各有条款。「我只是训了个 adapter」不改变这一点——adapter 离开基座无法工作，所以基座的条款照样适用。商用前务必读一遍基座的许可，这不是形式主义（C12/C45 有关于合规的系统讨论）。

3调远端模型：重试、限流、幂等

JD 里的「OpenAI APIs」不只是「会写 client.chat.completions.create」。把一个 API 调用做成生产可用的东西，需要四层防护——这与 C48 模块 02 讲的服务端护栏是同一套原理的客户端镜像。

层解决什么关键点
① 重试与退避瞬时故障（429、5xx、网络抖动）指数退避 + 抖动；只重试可重试的错误；尊重 Retry-After
② 客户端限流不把自己的配额打爆、不给服务端加压令牌桶，RPM 与 TPM 双限（模块与 C48 一致）
③ 幂等重试不产生重复副作用/重复扣费Idempotency-Key（或自建缓存）
④ 超时与预算不让一个请求挂死整个流程分层超时；总预算（token/金额）上限与熔断

重试：哪些能重试、退避怎么算

\[\text{delay}_k = \min\left(\text{cap},\; \text{base} \cdot 2^{k}\right) \times U(0.5, 1.5)\]
状态码含义能重试吗怎么做
429限流✅优先用响应里的 Retry-After，没有才用退避
500 / 502 / 503 / 504服务端错误✅指数退避
408 / 连接超时超时✅（若幂等）退避 + 幂等键
400请求本身有问题❌重试一万次也一样错——要报出来
401 / 403认证/权限❌配置问题
404模型不存在❌配置问题
context_length_exceeded上下文超限❌（但可降级）截断输入或换更大上下文的模型后重新请求
抖动（jitter）不是可选的。如果一批客户端同时遇到 429、又都用相同的确定性退避，它们会同步地在同一时刻重试，形成周期性的洪峰——这叫「惊群」（thundering herd），会让服务端更难恢复。加一个 U(0.5, 1.5) 的随机因子就能把重试打散。这是分布式系统里最便宜、最常被忽略的一行代码。

流式：客户端侧要处理的三件事

  • 增量拼接：每个 chunk 的 delta.content 可能为 None（第一个 chunk 通常只有 role），累加时要跳过。
  • usage 不在流里：默认流式响应不带 usage，要计费/统计得开 stream_options={"include_usage": True}（最后一个 chunk 带 usage）。不开的话你无法回答「这次调用花了多少 token」。
  • 断连要取消：客户端放弃后要真正关闭连接（用 with 或显式 close()），否则服务端还在为你生成——这既浪费你的配额也浪费服务端算力（C48 模块 02 的第三个 SSE 坑的另一侧）。

tool calling 与结构化输出

两个常被混淆的能力：

  • tool / function calling：模型输出「我要调用哪个函数、参数是什么」，你去执行并把结果回传，模型继续。它是一个多轮协议——注意要把 tool_calls 的助手消息与对应的 tool 角色结果消息都追加回 messages，否则下一轮模型会困惑。
  • 结构化输出 / JSON schema：约束模型的输出必须符合一个 schema。它不是 tool calling——没有函数要执行，只是保证格式。用 response_format={"type":"json_schema", ...}。比「在 prompt 里请求 JSON 然后自己解析」可靠得多，但仍要处理「schema 合法而语义错误」的情况。

一条关于成本的实操建议：把 token 计数与花费做成可观测的。每次调用记录 model / prompt_tokens / completion_tokens / 业务标签，聚合成「每个功能每天花多少钱」。没有这个数据，你无法回答「哪个功能在烧钱」，也就无法优化。这与 C48 模块 05 的成本归因是同一件事，只是在客户端侧做。加上「缓存命中的 prompt 便宜很多」这一点（prompt caching），把系统提示固定在前缀能显著省钱——这是最便宜的一个优化。

4把调用做成可观测的：日志、指标与降级

四层防护解决的是「单次调用怎么活下来」。但一个真实系统还需要回答三个运营问题：现在健康吗、刚才为什么慢、这个月钱花在哪。这三个问题的答案全部来自「你在调用现场记了什么」。

记什么字段用来回答什么
身份model（服务端回显的实际模型）、request_id、业务标签「哪个功能、用的哪个模型」——成本归因与故障定位的第一层
用量prompt_tokens / completion_tokens / cached_tokens「花了多少钱」；缓存命中率
时延TTFT、总时长、排队/重试耗时单独记「慢在哪」——是服务端慢还是自己在退避等待
结果finish_reason、状态码、重试次数length 比例上升 = 输出被截断，是质量与容量的双重预警（C48 模块 02）

直白说

其中「重试耗时要单独记」是最容易漏、也最容易造成误判的一条。假设你观测到 P95 端到端延迟是 8 秒，很自然会去优化 prompt 或换更快的模型——但如果其中 6 秒是你自己在退避等待（因为撞了限流），那么真正的问题是并发控制，而不是模型速度。把「服务端耗时」与「客户端等待耗时」分成两个指标，能立刻区分这两种完全不同的问题。

严谨说

finish_reason 的监控价值同样被低估。它只有几个取值（stop / length / tool_calls / content_filter），但 length 的比例是个极好的领先指标：它上升意味着输出被 max_tokens 截断——可能是用户在问更复杂的问题、可能是 prompt 变了、也可能是模型开始啰嗦。无论哪种，都意味着「用户看到的答案是不完整的」，而这在错误率与延迟指标上完全看不出来。

降级：当上游不可用时

重试解决瞬时故障，但如果上游持续不可用（配额耗尽、区域故障、模型下线），无限重试只会让你的服务一起挂掉。这时需要降级链：

  • 换模型：主模型不可用 → 退到更小/更便宜/另一家的模型。前提是你的 prompt 不依赖某个模型的特殊行为（这也是「别过度依赖单一模型的怪癖」的实际理由）。
  • 降质量：把 max_tokens 调小、关掉思考链、跳过重排——换取在配额内完成。
  • 用缓存/兜底答案：语义相近的历史回答、或一个诚实的「暂时不可用」。
  • 熔断（circuit breaker）：连续失败 N 次后直接快速失败一段时间，不再发请求。这既保护上游、也让你的服务快速返回而不是全体挂在超时上（C48 模块 02 的背压在客户端的镜像）。

降级链有一个必须显式决定的问题：降级后的结果要不要标记？如果用小模型的回答与主模型的回答混在一起、事后无法区分，那么你的离线评测会被污染（「上周质量下降」其实是那天降级了 20% 的流量）。把降级层级作为一个字段记进日志与返回值，这一个字段能省掉未来无数次归因困惑。

把这一节浓缩成一句可执行的建议：写一个统一的 call_llm() 封装，把重试、限流、幂等、超时、日志、降级全部放进去，然后禁止业务代码直接调 SDK。这样所有防护与观测都是默认开启的，而不是靠每个调用点自觉。这是本课模块 05 最实际的产出——notebook 里的客户端骨架就是它的雏形。

把本模块浓缩成一句话：模型训练完只是一半，「把它安全地送出去」和「可靠地调用别人的模型」是另一半，而这一半的技术含量全在「失败处理」上——保存时要解包、加载时要钉 revision、格式要用 safetensors、调用要重试退避限流幂等、上下文要算预算。这些都不难，但少任何一个，系统就会在某个你没预料到的时刻出问题。

6生态动态与开放问题

  • 分布式配置的表达层：FSDP/DeepSpeed 的参数散落在 accelerate config、TrainingArguments、JSON 配置与环境变量里，同一个概念（如 ZeRO 阶段、参数分片粒度）在不同层有不同名字。这是当前最真实的工程摩擦，社区在推动收敛但尚未完成。
  • 模型供应链安全：safetensors 解决了格式层的代码执行，但 trust_remote_code、自定义 tokenizer、以及权重本身的后门（数据投毒、权重篡改）仍是开放问题。模型签名与 SBOM（软件物料清单）式的溯源正在探索，尚无普遍实践（C44 有攻防视角的讨论）。
  • API 协议的边角语义：OpenAI 兼容已是事实标准，但 logprobs 的定义、流式增量的 tool_calls 拼装方式、结构化输出的约束表达、seed 是否被尊重，各家实现不一致。跨供应商切换时这些边角会咬人。
  • prompt 缓存的定价与语义：各家的前缀缓存策略（命中条件、TTL、折扣比例）不同且会变，让「怎么组织 prompt 最省钱」成了一个随时间移动的目标。缓存命中还会影响延迟分布，使容量规划更复杂。
  • 可复现性的现实边界：即使钉死 revision 与随机种子，服务端模型更新、批处理下的浮点归约顺序、以及 kernel 版本变化都会让输出改变。「LLM 应用的可复现」目前只能是「统计上可复现 + 输入输出留档」，这与 C40 的实验纪律有持续的张力。
