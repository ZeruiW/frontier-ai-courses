1fast tokenizer：offsets 与 word_ids 才是它的价值

很多人以为 use_fast=True 的价值只是「快」（Rust 实现，比 Python 版快 10–100 倍）。速度确实是它的名字来源，但对正确性而言，更重要的是它返回的两组对齐信息。

返回值是什么解决什么问题
input_idstoken id 序列喂给模型
attention_mask1=真实 token，0=padding让模型忽略 pad（漏传就会去注意 pad）
offset_mapping每个 token 在原始字符串中的 (start, end) 字符区间把模型的 token 级预测映射回原文字符位置——span 抽取、NER 高亮、实体链接全靠它
word_ids()每个 token 属于第几个「词」（特殊 token 为 None）把词级标注对齐到子词级——token 分类的必需品（C49 模块 03 那个坑）
token_type_ids句 A / 句 B 标记句对任务
overflowing_tokens超长时被切出去的部分滑窗处理长文档（配 return_overflowing_tokens=True）
text = "Washington is nice" 0123456789... tokens: [CLS] Wash ##ing ##ton is nice [SEP] input_ids: 101 6242 2075 2669 2003 3835 102 offsets: (0,0) (0,4) (4,7) (7,10) (11,13)(14,18) (0,0) └──── 三个子词的 offset 拼起来 = 原文 [0,10) = "Washington" word_ids(): None 0 0 0 1 2 None └──── 三个子词都属于**词 0** 用途 ①（NER）：词级标注 ["B-LOC","O","O"] -> 只给每个词的**第一个**子词打标签， 其余填 -100 -> [-100, B-LOC, -100, -100, O, O, -100] 用途 ②（QA）：模型预测 span = token 3..5 -> 用 offsets 换算成原文字符 [7,18) -> 直接从原始字符串切出答案，**不用 detokenize**（避免空格/大小写失真）

直白说

为什么不能靠 decode() 把答案还原？因为分词不是无损可逆的。decode(encode(text)) 常常与 text 不同——空格被规范化、大小写被 lowercase 模型改掉、某些 Unicode 被归一化。抽取式 QA 的答案必须逐字符来自原文（这是它相对生成式的核心优势，C49 模块 03 说过），所以只能靠 offset_mapping 从原始字符串切。用 decode 拼答案是个常见错误，症状是「答案基本对但标点/空格有细微差异」，然后 EM 分数莫名偏低。

严谨说

word_ids() 的作用同理不可替代。你有词级标注 [('Washington','B-LOC'), ('is','O'), ('nice','O')]，模型输出是子词级的。要计损失就必须知道「哪些子词属于哪个词」。手工做这个对齐（按空格切、再逐个匹配子词）在有标点、有连字符、有多语言的真实数据上极易出错。word_ids() 是唯一可靠的来源，而它只有 fast tokenizer 才有——slow tokenizer 调用它会直接抛异常。

两个具体的 gotcha：①offset_mapping 需要显式开启（return_offsets_mapping=True），而且它只对 fast tokenizer 可用。②特殊 token 的 offset 是 (0,0)，不是 None——如果你用 offset[0] == 0 判断「是不是序列开头」，会把 [CLS] 和真正的第一个 token 混起来。正确做法是用 sequence_ids()（区分特殊 token / 句 A / 句 B）或 word_ids() 里的 None 来识别特殊 token。

2padding / truncation：四种组合与算力浪费

这两个参数看起来平淡，但组合起来直接决定你浪费多少算力。

padding行为每 batch 的序列长度算力浪费
False（默认）不 padding各不相同（不能直接组 batch）—
True / 'longest'补到本 batch最长随 batch 变化最省（动态 padding）
'max_length'补到 max_length（或模型上限）固定可能浪费巨大
'do_not_pad'同 False——

直白说

为什么 padding='max_length' 可能浪费巨大？因为注意力是 O(L²)。假设你的数据平均长度 60、最长 500，设 max_length=512 全补齐：每条都按 512 算，而实际有效计算只占 (60/512)² ≈ 1.4%。改成动态 padding（补到本 batch 最长），如果 batch 内长度接近，浪费就很小。

严谨说

更进一步的优化是按长度分组（length grouping）：把长度接近的样本放进同一个 batch，让每个 batch 的最长值尽量接近其平均值。Trainer 里就是 group_by_length=True（配 length_column_name）。它的代价是破坏了随机性（同 batch 的样本长度相关），对某些任务可能有轻微影响，但对大多数任务是纯赚。notebook 会把三种策略的 padding 浪费率算出来对比，你会看到几倍的差距。

truncation 的三种策略

  • truncation=True（='longest_first'）：句对时优先截长的那句，逐 token 交替截直到达标。默认，通常是对的。
  • 'only_second'：只截第二句。QA 任务用这个——问题不能截，上下文可以。这是个具体且重要的选择。
  • 'only_first'：只截第一句。少见。
截断是静默的

截断是静默的——超长输入被砍掉一半，不会有任何警告，训练照常进行，你只会看到「效果不如预期」。这是数据侧最隐蔽的 bug 之一。防护做法：预处理时统计长度分布与截断率，并把「截断率 > X%」当作告警。notebook 会实现这个统计。另外 return_overflowing_tokens=True 可以把溢出部分作为额外样本返回（滑窗），这是长文档 QA 的标准做法，但要注意它会改变样本数量——Dataset.map 里用它必须配 remove_columns，否则新旧列长度不一致会报错。

3datasets：Arrow、map 与指纹缓存

datasets 的三个核心设计决定了它的全部行为特征。

设计是什么带来什么
Arrow 后端数据存成列式的 Arrow 文件，内存映射访问可以用几百 MB 内存处理几百 GB 数据集；多进程共享零拷贝
指纹缓存对 (数据集状态, 函数字节码, 参数) 做哈希，命中则直接读缓存文件重跑脚本时 map 秒完成；但也带来「改了函数却没生效」的困惑
惰性/流式IterableDataset 边下边用，不落盘TB 级数据集无需下载完；但不支持随机索引与 len()

map 的四个关键参数

ds = ds.map(
    tokenize_fn,
    batched=True,            # ① 一次传一批（dict of lists）而不是一条 -> 快 10-100 倍
    batch_size=1000,         # ② 每批多少条
    num_proc=8,              # ③ 多进程；⚠️ 与 batched 一起用时注意函数必须可 pickle
    remove_columns=ds.column_names,   # ④ 删掉原始列
)

直白说

batched=True 是最重要的一个。它让你的函数一次收到一批数据（{'text': [...1000 条...]}），于是可以调用 fast tokenizer 的批量接口——Rust 侧并行处理，比逐条调用快一到两个数量级。代价是函数签名变了：batched=False 时 example['text'] 是字符串，batched=True 时是字符串列表。这个签名切换是新手最常犯的错。

严谨说

remove_columns 什么时候必需？当你的函数改变了样本数量（如 return_overflowing_tokens 产生更多行）或者新列与旧列长度不一致时。datasets 会把返回的新列与保留的旧列拼在一起，长度不一致就报错 Column lengths mismatch。规则：只要你的 map 可能改变行数，就必须 remove_columns=ds.column_names。另外它还能显著省磁盘——不删原始 text 列，缓存文件会大好几倍。

指纹缓存：省时间也制造困惑

map 会算一个指纹：数据集当前状态的哈希 + 你的函数的字节码/闭包哈希 + 所有参数。指纹相同就直接读缓存文件，不重新计算。这让「改一行代码重跑脚本」从几分钟变成几秒。

但它也带来两类困惑：

  • 改了函数却没生效：极少见但会发生——如果你的函数依赖外部可变状态（全局变量、文件内容、随机数），指纹没变但行为变了。解法：把依赖显式作为参数传入（fn_kwargs=），或 load_from_cache_file=False 强制重算。
  • 缓存文件堆积：每次不同的 map 都生成一个缓存文件，一个大数据集反复处理会吃掉几十 GB 磁盘。解法：用 keep_in_memory=True（小数据集）或定期清理 ~/.cache/huggingface/datasets。

关于指纹缓存有一条实用经验：调试预处理函数时先在小切片上跑（ds.select(range(100))），确认正确后再跑全量。这样既快，又避免生成一堆无用的大缓存文件。而且能让你在几秒内迭代，而不是每次等几分钟——这个习惯对数据预处理的开发效率影响很大。

4streaming：什么时候用、代价是什么

load_dataset(..., streaming=True) 返回 IterableDataset：边下边用，不落盘。对 TB 级数据集（C43 的场景）是唯一可行方案。

能力Dataset（内存映射）IterableDataset（流式）
随机索引 ds[42]✅❌ 只能顺序迭代
len(ds)✅❌（有些数据集有元信息，多数没有）
shuffle()✅ 全局精确打乱🔶 缓冲区近似打乱（buffer_size）
map()✅ 提前算好并缓存✅ 但是惰性的（迭代时才算）
磁盘占用需要完整下载几乎为零
多 epoch✅🔶 需要重新迭代（配 set_epoch 换 shuffle 种子）

直白说

缓冲区打乱是流式的核心妥协，值得理解清楚。它维护一个大小 N 的缓冲区：先填满，然后每次随机吐一个、再补一个进来。N 越大越接近全局打乱，但内存占用也越大。如果数据集在磁盘上是按某种顺序排列的（比如按来源、按时间），而 buffer_size 远小于一个「块」的大小，那么同一个 batch 里的样本会高度相关——这会显著伤害训练。

严谨说

解决办法是两级打乱：①先打乱 shard 顺序（datasets 的流式 shuffle 会同时做这个），②再在缓冲区内打乱。这样即使 buffer_size 只有一万，样本也来自随机的不同 shard，相关性大幅降低。C43 模块 02 有对这个近似质量的完整量化——那门课让你算出「缓冲要多大才够」，本课只讲参数在哪。

流式的一个实操坑：它与 num_proc / DataLoader(num_workers=N) 的交互。多 worker 各自迭代同一个流会导致重复数据，除非数据集支持按 shard 切分给不同 worker（datasets 会尽力处理，但对 shard 数少于 worker 数的情况会警告并降级）。规则：流式训练时确保 shard 数 ≥ worker 数 × 进程数，否则要么重复要么有 worker 空转。

5DataCollator：动态 padding 与标签构造

map 之后每条样本还是变长的（如果你用了动态 padding）。把它们组成一个矩形张量、并构造 labels，是 collator 的职责。它在 DataLoader 里每个 batch 被调用一次。

Collator做什么用在哪
DataCollatorWithPadding补齐到本 batch 最长 + 生成 attention_mask分类任务（labels 已是标量）
DataCollatorForTokenClassification同上 + 把 labels 也补齐（用 -100）NER / 序列标注
DataCollatorForLanguageModeling现场做 MLM 掩码（mlm_probability=0.15，就是 C49 模块 01 的 80/10/10）MLM 预训练
DataCollatorForLanguageModeling(mlm=False)CLM：labels = input_ids.clone()，pad 位置置 -100CLM 预训练 / SFT
DataCollatorForSeq2Seq补齐 input 与 labels + 生成 decoder_input_ids翻译 / 摘要

直白说

「动态掩码」就是在这里发生的。C49 模块 02 讲的 RoBERTa 相对 BERT 的一大改进——每个 epoch 重新采样掩码位置——在 HF 生态里是默认行为，因为 collator 在每个 batch 被调用时都会重新掩一次。你不需要做任何事就得到了动态掩码。反过来，如果你想要静态掩码（复现 BERT 原始设置），得在 map 阶段就掩好并禁用 collator 的掩码。

严谨说

collator 里最容易出错的是 -100 的处理。PyTorch 的 CrossEntropyLoss(ignore_index=-100) 是全生态的约定：labels 里为 -100 的位置不计损失。padding 位置、未被掩的位置、SFT 里的 prompt 部分——都要填 -100。漏填的后果是模型在学「预测 pad token」或「背诵 prompt」，loss 看起来正常（甚至更低，因为 pad 很容易预测）但效果差。这是 SFT 里最经典的一个 bug，模块 04 会再遇到它。

一个能救命的调试习惯：训练开始前，取一个 batch 打印出来看。检查四件事——input_ids 解码回文本是否通顺、attention_mask 的 0 是否只在该在的位置、labels 里 -100 的比例是否符合预期、以及 labels 与 input_ids 的对齐关系是否正确。这四个检查能在三十秒内发现 80% 的数据侧 bug，而不用等训练跑完看效果。notebook 会把这个检查封装成一个函数。

6算一笔账：padding 浪费与截断率

\[\text{padding 浪费率} = 1 - \frac{\sum_i L_i}{B \cdot \max_i L_i} \quad(\text{按 token}), \qquad 1 - \frac{\sum_i L_i^2}{B\cdot(\max_i L_i)^2}\quad(\text{按注意力})\]

两个公式的区别很重要：线性部分（FFN、embedding）按第一个算，注意力按第二个算。因为注意力是平方的，长度不齐时它的浪费被放大。

策略batch 内长度token 浪费注意力浪费
padding='max_length'（512）[60, 80, 55, 500] → 全补 512≈ 66%≈ 75%
padding=True（动态）[60, 80, 55, 500] → 补到 500≈ 65%≈ 74%
padding=True + 按长度分组[55, 60, 80, …] 与 [500, …] 分开≈ 10%≈ 20%

读这张表：动态 padding 在长度差异大的 batch 里帮助有限，真正的杠杆是「按长度分组」。这也解释了为什么 group_by_length=True 在长度分布长尾的数据上能带来 2–4 倍的吞吐提升。

第二笔账是截断率，它是数据质量的隐形杀手：

\[\text{截断率} = \frac{|\{i : L_i > L_{max}\}|}{N}, \qquad \text{信息损失率} = \frac{\sum_i \max(0, L_i - L_{max})}{\sum_i L_i}\]

这两个数要分开看：截断率高但信息损失率低（很多样本只超出一点）通常可以接受；截断率低但信息损失率高（少数极长样本被砍掉大半）意味着你在丢弃某个特定子群体的数据——这可能是系统性偏差，比随机丢失更危险。

把本模块浓缩成一句话：数据层的坑几乎全是「形状与对齐」的坑——padding 补在哪边、labels 里哪些位置填 -100、子词怎么对齐到词、offset 怎么映射回原文字符。它们全都不报错，只让效果变差。所以本模块最该带走的是那个「打印一个 batch 检查四件事」的习惯，以及「统计截断率并告警」的纪律。

7生态动态与开放问题

  • 序列打包（packing）：把多条短样本拼进一个定长序列以消除 padding 浪费，用 attention mask 或 position_ids 防止跨样本注意（cross-contamination）。trl 的 SFTTrainer(packing=True) 与 FlashAttention 的变长接口都支持，但「打包是否损害效果」在不同任务上结论不一，尤其对短样本任务。
  • tokenizer 的多语言公平性：同样一句话，不同语言的 token 数差异可达数倍（中文、泰语、部分非洲语言尤其吃亏）。这直接转化为相同信息量下更高的 API 费用与更小的有效上下文。如何在有限词表下做到跨语言公平，是活跃的研究与工程问题。
  • 字节级与无分词模型：完全去掉 tokenizer（ByT5、MegaByte、以及近年的动态分块方案），从根上消除词表偏差与 OOV。代价是序列变长数倍，需要架构层面的补偿。目前尚未在通用场景胜出，但在多语言与代码上有吸引力。
  • 数据集格式的收敛：Arrow/Parquet 正在成为事实标准，但流式训练下的确定性打乱、断点续训的精确恢复（跑到第几个样本）、以及多 worker 的无重复切分，各家实现仍有差异。Mosaic StreamingDataset 与 datasets 的流式在这些语义上不完全一致。
  • 预处理的可复现性：指纹缓存让重跑变快，但也让「预处理版本」变成一个隐式状态。把 tokenizer 版本、预处理函数、参数一起写进数据集卡片与实验记录，是 C40/C37 强调但生态尚未强制的实践。
