1三件套：config / model / tokenizer

transformers 的全部设计围绕一个三元组。理解这个三元组的职责边界，库就不再是黑箱。

组件是什么存成什么文件谁决定它
config纯数据：层数、维度、头数、词表大小、激活函数、特殊 token id……config.json模型作者；model_type 字段是 Auto* 分发的依据
model计算图 + 权重model.safetensors（或旧的 pytorch_model.bin）由 config 完全确定结构；权重从文件加载
tokenizer文本 ↔ token id 的双向映射 + 特殊 token 规则tokenizer.json / vocab.txt / tokenizer_config.json与模型强绑定——换 tokenizer 等于换语言
tokenizer 与 model 必须同源

三件套里最容易犯的错、后果也最严重的一个：tokenizer 与 model 不匹配。用 bert-base-uncased 的 tokenizer 去喂 roberta-base 的模型，代码完全不会报错——两者词表大小相近，id 都在合法范围内，前向能跑、loss 能降。但每个 id 在两个词表里对应完全不同的词，模型看到的是彻底的乱码。症状是「训练正常但效果差得莫名其妙」，且极难排查。铁律：tokenizer 与 model 必须从同一个 checkpoint 名字加载，把这个名字写成一个变量，绝不手写两遍。

三件套的另一个重要性质是config 完全决定结构。这意味着你可以：

from transformers import AutoConfig, AutoModel

cfg = AutoConfig.from_pretrained("bert-base-uncased")
cfg.num_hidden_layers = 4          # 只要 4 层
model = AutoModel.from_config(cfg)  # 得到一个 4 层的随机初始化 BERT

# 或者：加载预训练权重但改掉分类头的类别数
from transformers import AutoModelForSequenceClassification
m = AutoModelForSequenceClassification.from_pretrained(
        "bert-base-uncased",
        num_labels=5,                       # 覆盖 config
        ignore_mismatched_sizes=True)       # 头的形状不匹配 -> 重新随机初始化头

ignore_mismatched_sizes=True 这个参数值得记住：它允许「主干加载预训练权重、头随机初始化」，这正是微调的标准情形。不加它，加载一个 num_labels 不同的分类模型会直接报错。

2from_pretrained 的六步：这一行到底做了什么

AutoModelForSequenceClassification.from_pretrained("bert-base-uncased", num_labels=3) ① 解析来源 是本地目录？是 Hub repo id？带 revision（分支/tag/commit）吗？ -> 决定去 HF_HOME 缓存里找，还是走网络下载 ② 下载/命中缓存 config.json → 解析出 model_type="bert" 缓存路径 ~/.cache/huggingface/hub/models--bert-base-uncased/snapshots/<sha>/ ⚠️ 缓存按 **commit sha** 分目录，所以 revision 变了会重新下载 ③ 分发到具体类 MODEL_FOR_SEQUENCE_CLASSIFICATION_MAPPING["bert"] -> BertForSequenceClassification ④ 按 config 构建结构（此时权重是随机的） kwargs 里的 num_labels=3 覆盖 config 中的值 ⑤ 加载权重文件并做 **键名匹配** model.safetensors 里的 state_dict 与模型的 named_parameters() 对齐 ├─ missing_keys : 模型要但文件里没有 → **随机初始化**（分类头就在这里） ├─ unexpected_keys : 文件里有但模型不要 → 丢弃（如预训练的 MLM 头） └─ mismatched_keys : 名字对但形状不对 → 报错，除非 ignore_mismatched_sizes=True ⑥ 后处理 tie_weights（嵌入与输出层共享）/ dtype 转换 / device_map 放置 / eval() 模式

直白说

第 ⑤ 步是整个加载过程里唯一会静默出问题的地方，必须学会读它的输出。transformers 会打印一段警告，告诉你哪些键 missing、哪些 unexpected。微调时看到「分类头被随机初始化」的警告是正常且期望的；但如果看到大量主干权重 missing（比如所有 encoder.layer.*），说明键名对不上——通常是模型类选错了或 checkpoint 结构不同，这时模型基本等于随机初始化。

严谨说

怎么显式检查而不依赖读日志？用 output_loading_info=True：model, info = AutoModel.from_pretrained(..., output_loading_info=True)，info 是一个含 missing_keys / unexpected_keys / mismatched_keys / error_msgs 的字典。把它写进你的加载函数里做断言——比如「missing_keys 里只允许出现 classifier」。这一个 assert 能挡住一整类难查的 bug。

关于安全的一条硬规矩：优先用 safetensors，避免 .bin。PyTorch 的 .bin 是 pickle 格式，加载时会执行任意代码——从不可信来源加载 .bin 等于运行陌生人的脚本。safetensors 是纯数据格式（header JSON + 张量字节），零拷贝、可 mmap、不执行代码。现代 transformers 默认优先选 safetensors；若必须加载 .bin，至少确认来源可信。另外 trust_remote_code=True 同理——它会执行 repo 里的 Python 代码，只对可信 repo 使用。

3dtype 与设备放置：三个最常混的参数

参数作用常见值坑
torch_dtype权重的数值精度torch.float16 / bfloat16 / "auto""auto" 读 config 里的 torch_dtype；不指定则一律 fp32（显存 ×2）
device_map把层分配到哪些设备"auto" / "cuda:0" / 字典"auto" 需要 accelerate；会做跨 GPU/CPU/磁盘的自动切分
low_cpu_mem_usage边加载边放置，不先在 CPU 建整个模型True加载 70B 时几乎必需；否则先吃 140GB 内存
attn_implementation选注意力 kernel"sdpa" / "flash_attention_2" / "eager"FA2 需要额外安装且只支持部分 dtype/架构

直白说

fp16 vs bf16 是最该搞清的一对。两者都是 16 位，但指数位/尾数位分配不同：fp16 有 10 位尾数、5 位指数（精度高、动态范围小），bf16 有 7 位尾数、8 位指数（精度低、动态范围与 fp32 相同）。训练时 bf16 明显更稳（不需要 loss scaling，不容易溢出为 inf）；推理时两者差别不大，但要看硬件支持（bf16 需要 Ampere 及以上）。如果你在 fp16 训练里遇到 loss 变 nan，第一反应应该是换 bf16。

严谨说

device_map="auto" 的行为值得知道细节：它按层顺序贪心地填满第一个设备、再填下一个，超出所有 GPU 就放 CPU（offload），再超出就放磁盘。这让你能在小卡上跑大模型，但跨设备的层间传输会让推理慢好几倍。所以它是「跑得起来」的手段，不是「跑得快」的手段。真要快就得靠张量并行（C39）或换更小的模型/量化（C27）。

显存的粗算公式值得背下来：推理显存 ≈ 参数量 × 每参数字节数 × 1.2（那 20% 是激活与碎片）。7B 模型 fp16 = 7e9 × 2 × 1.2 ≈ 17 GB；int4 量化 ≈ 4.2 GB。训练显存 ≈ 参数 × (2 权重 + 2 梯度 + 8 优化器状态) = 参数 × 12 字节（Adam fp32 状态），7B 训练要 84 GB——这就是为什么全量微调 7B 需要多卡，而 LoRA 只需一张卡（模块 04）。notebook 会把这个公式实现成工具。

4任务头：AutoModelFor* 家族

同一个主干可以接不同的头，transformers 用 AutoModelFor<Task> 系列表达这件事。选错头是新手最常见的错误之一。

类输出对应 C49 的范式labels 的形状
AutoModel隐状态 (B, L, H)，无头—（自己接头）不接受 labels
AutoModelForSequenceClassification(B, C)序列分类（模块 03①）(B,) 类别 id，或 (B,C) 多标签
AutoModelForTokenClassification(B, L, K)token 分类（模块 03②）(B, L)，忽略位置填 -100
AutoModelForQuestionAnswering两个 (B, L)span 抽取（模块 03③）start_positions + end_positions
AutoModelForMaskedLM(B, L, V)MLM（C49 模块 01）(B, L)，未掩位置填 -100
AutoModelForCausalLM(B, L, V)CLM / 生成(B, L)，内部自动右移
AutoModelForSeq2SeqLM(B, L_tgt, V)encoder-decoder（C49 模块 04）(B, L_tgt)，内部生成 decoder_input_ids
labels 的右移到底谁做

AutoModelForCausalLM 的 labels 会被内部自动右移——你传 labels = input_ids，库内部会做 logits[..., :-1, :] 对 labels[..., 1:]。如果你自己先右移一遍再传进去，就等于移了两位，模型学的是「预测下下个 token」。这个错误的症状是：loss 能降但生成完全不通顺。反过来，AutoModelForSeq2SeqLM 的 labels 不需要你右移（库会据它生成 decoder_input_ids），但如果你手动传了 decoder_input_ids，库就不再帮你移。这两个不对称是最容易踩的实现坑之一，notebook 会用 assert 把它钉死。

5generate()：参数全解与最常见的误用

model.generate() 是一个参数极多的方法，但它们分成几个正交的组：

组参数作用
长度max_new_tokens / min_new_tokens用 max_new_tokens 而不是 max_length——后者包含 prompt，会随输入变化
解码策略do_sample / num_beamsdo_sample=False, num_beams=1 是贪心；num_beams>1 是 beam search；do_sample=True 是采样
采样形状temperature / top_k / top_p / min_p只在 do_sample=True 时生效——这是最高频的误用
重复控制repetition_penalty / no_repeat_ngram_size缓解退化（C49 模块 04）
停止eos_token_id / stop_strings多个 eos 可传列表；stop_strings 需要传 tokenizer
beam 相关length_penalty / early_stopping只在 num_beams>1 时有意义
输出return_dict_in_generate / output_scores要 logprob 或注意力时必须开
头号误用：设了 temperature=0.7 但没设 do_sample=True。此时 temperature 被完全忽略，你得到的是贪心解码——但代码不报错，你会以为「temperature 没什么用」。新版本 transformers 会给警告，旧版本静默忽略。反过来，temperature=0 在 generate 里是非法的（除零），要确定性输出应该用 do_sample=False。这与 OpenAI API 的 temperature=0 语义不同（那里是服务端把它翻译成贪心），是自建服务与 API 之间的一个常见混淆点。

三个还需要知道的细节

  • batch 生成必须左 padding。decoder-only 模型生成时从序列末尾续写，如果用右 padding，pad token 会夹在 prompt 和生成之间。所以批量生成前要 tokenizer.padding_side = 'left'。这个坑的症状是「单条生成正常、批量生成变差」——极其常见。
  • attention_mask 必须传。padding 位置若不 mask，模型会去注意 pad token。tokenizer(...) 返回的字典里已经有它了，直接 **inputs 展开传进去就行——手写参数时容易漏。
  • Llama 系没有 pad token。它们的 tokenizer 里 pad_token 是 None，批量处理会报错。标准做法是 tokenizer.pad_token = tokenizer.eos_token。但注意：如果同时把 eos 当 pad 又要在 labels 里忽略 pad，就必须小心不要把真正的 eos 也忽略掉（模块 03 会处理这个）。
# 一段可直接用的批量生成骨架
tok.padding_side = "left"                       # ① decoder-only 批量生成必须左 padding
if tok.pad_token is None:
    tok.pad_token = tok.eos_token               # ② Llama 系没有 pad token

inputs = tok(prompts, return_tensors="pt", padding=True, truncation=True,
             max_length=1024).to(model.device)  # ③ attention_mask 在返回的字典里

out = model.generate(
    **inputs,                                   # ④ 一定要展开传，别只传 input_ids
    max_new_tokens=256,                         # ⑤ 不用 max_length
    do_sample=True, temperature=0.7, top_p=0.9, # ⑥ 采样参数只在 do_sample=True 时生效
    repetition_penalty=1.05,
    pad_token_id=tok.pad_token_id,
)
# ⑦ 只解码新生成的部分（切掉 prompt）
gen = out[:, inputs["input_ids"].shape[1]:]
texts = tok.batch_decode(gen, skip_special_tokens=True)

6算一笔账：显存与上下文预算

把本模块的参数变成两个必须会算的数字。

\[\text{推理显存} \approx N_{params} \times b_{dtype} \times 1.2 + \underbrace{2 \cdot n_{layers} \cdot n_{kv} \cdot d_{head} \cdot L \cdot b_{dtype}}_{\text{KV 缓存}}\]
模型dtype权重KV(L=4096, B=1)合计（约）
Llama-3-8Bfp1616.0 GB0.5 GB（GQA 8 组）≈ 20 GB
Llama-3-8Bint44.5 GB0.5 GB≈ 6 GB
Llama-3-70Bfp16140 GB1.3 GB≈ 170 GB（多卡）
Llama-3-70Bint435 GB1.3 GB≈ 44 GB（单 A100 80G 可跑）

训练侧的账更重要，因为它决定你能不能在手上的卡上训：

\[\text{训练显存} \approx N_{params}\times\underbrace{2}_{\text{fp16权重}} + N_{params}\times\underbrace{2}_{\text{梯度}} + N_{trainable}\times\underbrace{8}_{\text{Adam fp32 状态}} + \text{激活}\]

注意第三项用的是 N_trainable 而不是 N_params——这正是 LoRA 省显存的根本原因：全量微调 7B 的优化器状态是 56 GB，LoRA（可训练参数 0.1%）只有 56 MB。模块 04 会把这个对比算完整。

第二个必须会算的是上下文预算。它经常被忽略，直到线上出现「长输入被静默截断」的 bug：

\[L_{prompt}^{max} = \underbrace{L_{model}}_{\text{模型上限}} - \underbrace{n_{special}}_{\text{特殊token}} - \underbrace{L_{gen}}_{\text{生成预留}}\]

把本模块浓缩成一句话：transformers 的复杂度几乎全在「加载」与「生成」这两个动作的参数上，而它们的坑几乎全是「静默失败」——不报错、能跑、结果错。tokenizer 不匹配不报错、权重没加载上只给个警告、temperature 不生效只是被忽略、右 padding 批量生成只是变差一点。所以本模块最该带走的不是参数表，而是一套显式检查的习惯：加载后断言 missing_keys、生成前断言 padding_side、始终从同一个变量取 checkpoint 名字。

7生态动态与开放问题

  • 加载与量化的融合：from_pretrained 正在吸收越来越多的量化后端（bitsandbytes、GPTQ、AWQ、FP8、torchao），通过 quantization_config 统一接口。但不同后端支持的架构、dtype、是否可训练差异很大，「哪个量化在我的场景可用」目前只能靠试。
  • generate 的可组合性：解码策略从少数几种膨胀到几十种（对比解码、投机解码、DoLa、约束解码、结构化输出）。LogitsProcessor 与 StoppingCriteria 提供了扩展点，但组合多个策略时的交互（谁先谁后、是否互斥）缺乏统一规范。
  • 结构化输出与约束解码：让模型必须输出合法 JSON/正则/语法，做法有 grammar-constrained decoding、outlines/xgrammar 类库、以及服务端的 JSON mode。哪种在质量-速度上最优、约束是否会损害推理能力，仍在讨论。
  • 模型代码的分发方式：trust_remote_code 让新架构无需等库更新即可发布，但它是个真实的安全面。社区正在探索更安全的中间形态（声明式 config、受限执行环境），尚无定论。
  • 版本兼容与可复现：transformers 迭代极快，默认行为（如 generate 的默认参数、tokenizer 的特殊 token 处理）会变。钉死版本 + 记录 revision commit sha 是目前唯一可靠的复现手段（C40 有系统讨论）。

必读：transformers 文档的 Auto Classes、Models（from_pretrained 的完整参数）、Generation Strategies 与 GenerationConfig 四篇；safetensors 的格式规范（理解为什么它比 pickle 安全）；PyTorch 的 Automatic Mixed Precision 文档（fp16 vs bf16 的数值细节）。源码上建议读 modeling_utils.py 的 _load_pretrained_model（第 ⑤ 步的键名匹配全在那里）与 generation/utils.py 的 _sample。完整清单见 references.md。
