1LoRA：四个参数，每个都有明确含义

LoRA 的原理一句话：冻结原权重 W，只训练一个低秩增量 ΔW = BA（A: r×d_in，B: d_out×r，r ≪ min(d_in,d_out)）。原理在 C02 讲过，本模块只讲参数怎么配、为什么。

\[h = Wx + \frac{\alpha}{r}\,BAx, \qquad A \sim \mathcal{N}(0,\sigma^2),\; B = 0\]
参数含义常用值怎么想
r低秩的秩8 / 16 / 32 / 64容量旋钮。任务与预训练分布越远、数据越多，越需要大 r。8 够用于风格/格式适配；领域知识注入常要 32+
lora_alpha缩放的分子；实际缩放是 α/r通常取 2r 或 r它的作用是「让改 r 时不必重调 lr」。固定 α/r 比值，换 r 时有效步长不变
target_modules给哪些线性层加 LoRA["q_proj","v_proj"]（默认）或全部 q,k,v,o,gate,up,down覆盖面比 r 更重要——原论文发现同等参数预算下，「小 r + 覆盖更多模块」优于「大 r + 只覆盖 q,v」
lora_dropout作用在 LoRA 分支输入上的 dropout0.0 – 0.1小数据集上有用；大数据集通常设 0

直白说

B 初始化为 0 是个关键设计：这让训练开始时 ΔW = BA = 0，模型输出与原模型逐字节相同。这意味着 LoRA 微调是从「原模型」这个点连续地出发的，不会有初始的性能跳崖。如果 A 和 B 都随机初始化，训练一开始模型就被随机扰动破坏，需要先花很多步「修回来」。这个细节在 notebook 里会用数值验证。

严谨说

α/r 的设计动机值得说清，因为它常被误解为「另一个学习率」。原论文的意图是：当你把 r 从 8 调到 64 时，BA 的输出尺度会随 r 变化（更多的秩累加），如果不缩放，有效学习率就变了、要重新调 lr。用 α/r 缩放后，固定 α/r 比值扫 r 就不用重调 lr。所以实践中你应该固定比值（如 α=2r）而不是固定 α——固定 α=16 然后把 r 从 8 调到 64，实际上把缩放从 2.0 降到了 0.25。

target_modules 的名字是模型特定的，这是最常见的报错来源。Llama 系是 q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj；BERT 系是 query,key,value,dense；GPT-2 是 c_attn,c_proj（而且 c_attn 是把 QKV 融在一起的一个大矩阵）。填错名字的症状是 ValueError: Target modules not found，或者更糟——只匹配到一部分层而不报错。可靠做法：print([n for n,_ in model.named_modules()]) 先看一眼，或者用 target_modules="all-linear" 让 peft 自动找。

2peft 的四个动作：包装、训练、保存、合并

from peft import LoraConfig, get_peft_model, PeftModel, TaskType

# ① 包装：冻结原权重、注入 LoRA 分支
cfg = LoraConfig(
    r=16, lora_alpha=32,                 # α/r = 2
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    lora_dropout=0.05,
    bias="none",                          # 通常不训 bias
    task_type=TaskType.CAUSAL_LM,         # ⚠️ 必须与任务匹配，否则头不对
)
model = get_peft_model(base_model, cfg)
model.print_trainable_parameters()
# -> trainable params: 40,370,176 || all params: 8,070,000,000 || trainable%: 0.50

# ② 训练：和普通 Trainer 完全一样（模块 03）
trainer = Trainer(model=model, args=args, ...); trainer.train()

# ③ 保存：只存 adapter（几十 MB，不是几十 GB）
model.save_pretrained("out/adapter")     # adapter_model.safetensors + adapter_config.json

# ④ 加载 / 合并
m = PeftModel.from_pretrained(base_model, "out/adapter")   # 可继续训练或推理
merged = m.merge_and_unload()             # W <- W + (α/r)BA，得到普通模型
merged.save_pretrained("out/merged")      # 完整权重，可直接给 vLLM 用
动作产出大小能继续训练吗
save_pretrained（adapter）adapter_model.safetensors几十 MB✅ 用 PeftModel.from_pretrained 加载后可以
merge_and_unload()普通 nn.Module（权重已融合）与基座相同（几十 GB）❌ LoRA 分支已消失，只能当普通模型全量训
多 adapter 共存多个 adapter 目录每个几十 MB✅ set_adapter(name) 切换；可同时加载

直白说

merge_and_unload() 的取舍：合并后推理零额外开销（不用算 LoRA 分支，也不影响 kernel 融合），且能直接喂给 vLLM/TensorRT 这类只认标准权重的引擎。代价是失去了「多 adapter 动态切换」的能力，而且合并是不可逆的（除非你留着原基座和 adapter）。规则：训练与实验期不合并（保留灵活性），最终上线时合并（换取推理效率）。

严谨说

多 adapter 共存是 LoRA 一个被低估的能力：一个基座 + N 个几十 MB 的 adapter，可以服务 N 个不同任务/客户。显存里只有一份基座权重，切换 adapter 几乎零成本。这在多租户场景下的成本优势是巨大的（对比 N 份完整模型）。生产上 vLLM 等引擎已支持 multi-LoRA 服务（同一 batch 里不同请求用不同 adapter）。这也是「不合并」的一个强理由。

task_type 填错 = 分类头被冻在随机状态

task_type 填错是个静默陷阱。TaskType.CAUSAL_LM 与 SEQ_CLS 的区别在于：后者会把分类头（score/classifier）也标记为可训练（因为它是新初始化的，必须训）。如果你做分类却填了 CAUSAL_LM，分类头会被冻结在随机初始化状态——训练能跑、loss 会降一点（LoRA 在适应那个随机头），但效果永远上不去。症状：准确率卡在一个远低于预期的水平且怎么调超参都不动。

3QLoRA：四个组件，缺一个就不是 QLoRA

QLoRA 让 65B 模型在单张 48GB 卡上微调。它不是一个技巧，而是四个组件的组合：

组件做什么省了什么参数
4-bit NF4 量化把冻结的基座权重量化到 4 bit（NormalFloat4，针对正态分布优化的量化格点）权重显存 ÷4（16 GB → 4.5 GB）load_in_4bit=True, bnb_4bit_quant_type="nf4"
双重量化把量化用的 scale 常数本身再量化一次额外省约 0.4 bit/参数bnb_4bit_use_double_quant=True
分页优化器优化器状态在显存不足时分页到 CPU避免峰值 OOMoptim="paged_adamw_8bit"
LoRA 在量化权重上基座 4-bit 冻结，LoRA 分支用 bf16 训练梯度与优化器状态只按 LoRA 参数算bnb_4bit_compute_dtype=torch.bfloat16
 
from transformers import BitsAndBytesConfig
from peft import prepare_model_for_kbit_training, LoraConfig, get_peft_model

bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16,   # 计算时反量化到 bf16
)
base = AutoModelForCausalLM.from_pretrained(CKPT, quantization_config=bnb,
                                           device_map="auto")
base = prepare_model_for_kbit_training(base)   # ⚠️ 别忘：转 LayerNorm 到 fp32、
                                                #    开 gradient checkpointing、
                                                #    让 embedding 输出 requires_grad
model = get_peft_model(base, LoraConfig(r=64, lora_alpha=16, ...))
prepare_model_for_kbit_training 常被漏掉，而它做的三件事都是必需的：①把 LayerNorm 转成 fp32（量化模型里 LN 用低精度会不稳）；②开启 gradient checkpointing；③给 embedding 的输出挂一个 hook 让梯度能流过（量化层不可导，梯度必须绕过它到 LoRA 分支）。漏掉它的症状是「loss 不降」或「梯度为 None」。另外 QLoRA 论文用的是 r=64 且覆盖所有线性层——比常规 LoRA 激进得多，因为 4-bit 基座本身有量化误差，需要更大的 LoRA 容量来补偿。

最后一条必须知道的边界：QLoRA 训练慢。每次前向都要把 4-bit 权重反量化到 bf16，这个开销让训练速度约为 bf16 LoRA 的 60–70%。所以 QLoRA 是「显存不够时的解法」，不是「更快的解法」。如果你的卡放得下 bf16 LoRA，就别用 QLoRA。

4TRL 的 SFTTrainer：数据格式与 prompt 掩码

trl 把后训练算法包成了几个 Trainer。SFTTrainer 是最常用的，它的核心工作是把「对话」变成「带正确 labels 的 token 序列」。

三种数据格式

# 格式 ① conversational（推荐）—— SFTTrainer 会自动套 chat template
{"messages": [{"role": "system",    "content": "You are helpful."},
              {"role": "user",      "content": "什么是 LoRA？"},
              {"role": "assistant", "content": "LoRA 是……"}]}

# 格式 ② prompt-completion
{"prompt": "什么是 LoRA？", "completion": "LoRA 是……"}

# 格式 ③ 纯文本（自己拼好，SFTTrainer 直接用）
{"text": "<|user|>什么是 LoRA？<|assistant|>LoRA 是……<|end|>"}

直白说

格式 ① 的好处是让 tokenizer 的 chat template 决定拼接方式。每个指令模型都有自己的对话格式（Llama-3 的 <|start_header_id|>、ChatML 的 <|im_start|>、Mistral 的 [INST]），格式必须与该模型预训练/指令微调时一致，否则模型看到的是陌生的分隔符。用 tokenizer.apply_chat_template()（或让 SFTTrainer 自动做）是唯一可靠的做法——手写拼接几乎一定会在某个特殊 token 上出错。

严谨说

最关键的语义是 prompt 掩码：SFT 只应对 assistant 的回答 计损失，system/user 部分要填 -100（模块 02 讲过）。SFTTrainer 通过 DataCollatorForCompletionOnlyLM（配 response_template）或对 conversational 格式的自动处理来做这件事。如果不掩，模型会同时学习「生成用户提问」——loss 看起来更低（用户提问也是可预测的文本），但模型在推理时可能自己接着编用户的下一句话。这是 SFT 最经典的 bug。

SFTConfig 参数作用注意
max_length序列长度上限超出被截断——注意回答被截断比 prompt 被截断更糟
packing把多条短样本拼进一个定长序列消除 padding 浪费（模块 02），但需要正确的跨样本掩码；短样本任务上可能有害
completion_only_loss / DataCollatorForCompletionOnlyLM只对回答计损失必须开；response_template 要与 chat template 完全一致
dataset_text_field纯文本格式时指定字段名与 conversational 格式互斥
neftune_noise_alpha在 embedding 上加噪声做正则小数据集上有时有效，非必需
packing=True 的取舍值得单独想清楚。它把 padding 浪费降到接近 0（吞吐可能翻倍），但引入两个问题：①跨样本的注意力污染（需要 position_ids 或变长 attention 正确隔离，否则一条样本会「看到」另一条）；②短样本被拼在一起后，每条样本的相对权重变了——原来每条样本贡献一个梯度，现在长样本贡献更多 token 因此权重更大。对指令数据（长度差异大）这个偏移是真实的。规则：数据量大且长度接近时开 packing；数据少或长度差异大时别开。

5DPOTrainer：成对数据与 beta

DPO 的算法原理在 C02/C23 讲过（用偏好对直接优化策略，不需要显式奖励模型）。本模块讲数据格式与三个关键参数。

# DPO 的数据格式：每条是一个「偏好对」
{"prompt":   [{"role": "user", "content": "什么是 LoRA？"}],
 "chosen":   [{"role": "assistant", "content": "LoRA 是一种低秩适配方法……"}],
 "rejected": [{"role": "assistant", "content": "我不知道。"}]}

from trl import DPOConfig, DPOTrainer
trainer = DPOTrainer(
    model=policy,                    # 要训练的策略（通常是 SFT 后的模型）
    ref_model=None,                  # None -> 自动用 policy 的初始副本；
                                     #        用 LoRA 时可以直接禁用 adapter 当参考
    args=DPOConfig(beta=0.1,         # KL 约束强度：**最重要的参数**
                   loss_type="sigmoid",   # sigmoid(标准DPO)/ipo/hinge/kto_pair
                   max_length=1024,
                   max_prompt_length=512),
    train_dataset=pref_ds,
    processing_class=tok,
)
\[\mathcal{L}_{DPO} = -\log\sigma\!\left(\beta\left[\log\frac{\pi(y_w|x)}{\pi_{ref}(y_w|x)} - \log\frac{\pi(y_l|x)}{\pi_{ref}(y_l|x)}\right]\right)\]
参数含义调大会怎样调小会怎样
beta隐式 KL 约束的强度更保守，贴近参考模型，学得慢更激进，可能偏离太远导致退化（重复、乱码、能力下降）
ref_model参考策略—用 LoRA 时可以省掉一份模型：禁用 adapter 即得参考
loss_type损失变体ipo 对长度偏差更鲁棒；hinge 更硬—

直白说

ref_model=None + LoRA 是个漂亮的组合。DPO 需要同时算策略与参考的 logprob，通常意味着显存里要放两份模型。但用 LoRA 时，「参考模型」= 「禁用 LoRA 分支的同一个模型」——因为 LoRA 的 B 初始化为 0，禁用它就精确回到 SFT 后的模型。trl 会自动利用这一点，显存直接省一半。这是 LoRA 与 DPO 的一个非平凡协同。

严谨说

beta 的实践区间是 0.01–0.5，常用 0.1。它的作用类似 PPO 里的 KL 系数：太小则策略跑得太远，出现「reward hacking」式的退化（输出变长、变重复、通用能力下降）；太大则几乎学不动。调 beta 时必须同时监控「非目标能力」——DPO 很容易在提升偏好胜率的同时损害通用能力（C23 有系统讨论）。另外要警惕长度偏差：偏好数据里若 chosen 系统性更长，DPO 会学到「更长 = 更好」，这是文献中反复出现的问题，loss_type="ipo" 或显式长度归一化是缓解手段。

DPO 之前必须先 SFT。DPO 假设策略已经在目标分布上有合理的概率质量——直接在基座模型上跑 DPO，效果通常很差且不稳定。标准流程是 基座 → SFT → DPO（C02 的完整链路）。另一个常见错误是把 SFT 数据直接当 DPO 数据（把 SFT 答案当 chosen、随机答案当 rejected）——这样的 rejected 太容易区分，学不到细粒度偏好，这与 C49 反复出现的「负例设计决定学到什么」是同一条原理。

6算一笔账：LoRA 到底省了多少

\[N_{LoRA} = \sum_{\text{目标层}} r\,(d_{in} + d_{out}), \qquad \text{占比} = \frac{N_{LoRA}}{N_{total}}\]
配置可训练参数占比优化器状态checkpoint训练显存（7B）
全量微调7.0 B100%56 GB≈ 84 GB≈ 84 GB
LoRA r=8, 仅 q,v≈ 4.2 M0.06%34 MB≈ 8 MB≈ 18 GB
LoRA r=16, 全部线性层≈ 40 M0.57%320 MB≈ 80 MB≈ 20 GB
QLoRA r=64, 全部线性层≈ 160 M2.3%1.3 GB≈ 320 MB≈ 8 GB

三个观察：

  • 省显存的主力是「优化器状态按可训练参数算」（模块 01 的公式），不是权重本身。全量微调的 56 GB 优化器状态直接变成几百 MB。
  • checkpoint 从几十 GB 变成几十 MB，这改变了实验方式——你可以毫无压力地保存二十个实验的 adapter，而全量微调时连三个 checkpoint 都要考虑磁盘。
  • QLoRA 的显存最低但训练最慢（反量化开销，约为 bf16 LoRA 的 60–70% 速度）。它是「放不下时的解法」，不是「更快的解法」。

还有一个常被忽略的账：推理开销。未合并的 LoRA 每层多两次小矩阵乘（x→A→B），FLOPs 增加约 2r/d（r=16, d=4096 时约 0.8%），但因为是两个小 kernel，实际延迟增加可能到 10–20%（kernel 启动开销与显存往返占主导）。合并后开销归零——这就是上线前该合并的理由。

把本模块浓缩成一句话：LoRA 的价值不只是「省显存」，而是把「微调」从一件重工程变成一件轻工程——几十 MB 的产物、可以同时保留几十个版本、一个基座服务多个任务、切换成本接近零。这个「轻」带来的实验速度提升，可能比省下的显存更有价值。

7生态动态与开放问题

  • LoRA 变体的丛林：DoRA（分解幅度与方向）、rsLoRA（改缩放为 α/√r）、LoRA+（给 A、B 不同学习率）、VeRA（共享随机基）、PiSSA（用 SVD 主成分初始化）——各自报告了改进，但缺乏统一的、控制了算力预算的对比。「该用哪个变体」目前主要靠试。
  • r 与任务的关系：普遍经验是「风格适配小 r、知识注入大 r」，但缺乏可操作的先验判据。LoRA 到底能学到多少「新知识」（而非只是重新组合已有能力）是个尚未澄清的问题，也直接关系到「什么时候必须全量微调」。
  • 多 adapter 的服务与组合：同 batch 混合不同 adapter（S-LoRA、vLLM 的 multi-LoRA）已工程化，但多个 adapter 的语义组合（同时应用两个 adapter、或按权重混合）效果不可预测，缺乏理论。
  • DPO 家族的爆炸：IPO、KTO、ORPO、SimPO、CPO……各自修正 DPO 的某个缺陷（长度偏差、需要成对数据、需要 SFT 阶段）。在什么数据条件下哪个更优缺乏系统结论，且很多对比没有控制超参搜索预算（C40 会说这是典型的可复现性问题）。
  • 偏好数据的长度偏差：几乎所有偏好数据集里 chosen 都系统性更长，导致对齐后的模型输出越来越长。显式长度归一化、长度控制的解码、以及在数据侧平衡长度，都是缓解手段，但没有干净的解法。

必读：Hu et al. 2021 LoRA（重点读 §7.2 关于 r 与 target modules 的消融——「覆盖更多模块优于更大 r」这个结论出自那里）、Dettmers et al. 2023 QLoRA（四个组件与 NF4 的推导）、Rafailov et al. 2023 DPO（推导必读，理解 beta 的来源）、Meng et al. 2024 SimPO 与 Azar et al. 2024 IPO（长度偏差的两种修正）。文档侧：peft 的 LoRA 与 Quantization、trl 的 SFTTrainer 与 DPOTrainer。原理侧：C02（后训练全链路）、C23（对齐前沿）、C27（量化）。完整清单见 references.md。
