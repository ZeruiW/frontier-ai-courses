1Trainer 内部到底跑了什么

Trainer 常被当成黑箱，但它其实就是一个写得很仔细的训练循环。把它的骨架看清，你才知道出问题时该往哪儿看、以及什么时候该弃用它自己写。

trainer.train() 的骨架（省略了分布式与日志细节） ① 准备 DataLoader(train_dataset, collate_fn=data_collator, batch_size=per_device_train_batch_size, sampler=按 group_by_length / seed 构造) optimizer = AdamW(参数分两组：weight_decay 组 与 no_decay 组) scheduler = get_scheduler(lr_scheduler_type, warmup_steps, total_steps) ⚠️ total_steps = ceil(len(loader) / grad_accum) * num_train_epochs （max_steps 若 >0 则覆盖它） ② for epoch in range(epochs): for step, batch in enumerate(loader): ③ loss = model(**batch).loss # 模型内部算 loss ④ loss = loss / grad_accum # ← 关键：先除再回传 ⑤ loss.backward() # 累积梯度 if (step + 1) % grad_accum == 0: ⑥ clip_grad_norm_(params, max_grad_norm) # 默认 1.0 ⑦ optimizer.step(); scheduler.step(); optimizer.zero_grad() ⑧ global_step += 1 # ← **优化步**，不是 batch 数 ⑨ 到点则：log / evaluate / save_checkpoint ⑩ 结束：load_best_model_at_end 则回载最佳 checkpoint

直白说

看清第 ⑧ 步就解开了一个常见困惑：logging_steps / eval_steps / save_steps 数的是优化步（global_step），不是 batch 数。grad_accum=8 时，跑了 800 个 batch 才是 100 个 global_step。这就是为什么「我设了 logging_steps=10 但半天不打日志」——因为你的 grad_accum 很大。

严谨说

第 ④ 步也值得注意：loss 在 backward 之前被除以 grad_accum。这是为了让累积 N 个 micro-batch 的梯度等价于一个 N 倍大 batch 的梯度（因为 loss 默认是 batch 内均值）。如果你自己写循环忘了这一步，有效学习率会被放大 N 倍——症状是「梯度累积一开就发散」。反过来，如果你的 loss 是 reduction='sum'，就不该除。这个细节在自定义 compute_loss 时特别容易搞错。

什么时候该弃用 Trainer 自己写循环？判据是：当你需要在一个训练步内做「非标准」的事情时——比如多个模型交替更新（GAN、RLHF 的 actor-critic）、需要在 backward 之间插入自定义操作、或者每步的数据依赖上一步的输出（on-policy 采样）。反过来，只要你的训练是「取一个 batch、算一个 loss、更新一次」，Trainer 就够用，而且它处理好的边角（断点续训、分布式、日志、混合精度）你自己写要花很久才能同样可靠。

2有效 batch：三个数相乘才是你关心的那个量

\[B_{eff} = \texttt{per\_device\_train\_batch\_size} \times \texttt{gradient\_accumulation\_steps} \times n_{devices}\]

这是 TrainingArguments 里最常被搞混的一组参数。三个数的组合决定了：优化器看到的实际 batch、显存占用、以及吞吐。

组合有效 batch显存吞吐何时选
bs=32, accum=1, dev=132高最高显存够时的首选
bs=8, accum=4, dev=132低略低显存不够时的标准换法
bs=1, accum=32, dev=132最低低（GPU 利用率差）极端显存受限
bs=8, accum=1, dev=432每卡低最高（并行）有多卡时

四行的有效 batch 完全相同（都是 32），数学上等价（对 Transformer 而言——用 BatchNorm 的模型不等价，但 Transformer 用 LayerNorm，无此问题）。选哪一行只看显存与吞吐。

但有三个真实的不等价之处要知道：①dropout 的随机性——micro-batch 拆分改变了 dropout mask 的分布，理论上有微小差异（实践中可忽略）。②eval_accumulation_steps 与评估显存——评估时默认把所有预测攒在 GPU 上再算指标，大数据集会 OOM；设了它才会分批搬到 CPU。③日志里的 loss 是 micro-batch 的均值，不是有效 batch 的——所以梯度累积下日志 loss 的方差会更大，看起来更抖，但这不代表训练不稳。

学习率与有效 batch 的关系

有效 batch 变了，学习率通常要跟着变。两条经验规则：

  • 线性缩放：lr ∝ B_eff。来自 SGD 的理论（Goyal et al. 2017 的 ImageNet in 1 Hour），在大 batch 训练时用得多。
  • 平方根缩放：lr ∝ √B_eff。对 Adam 类自适应优化器更常见，因为 Adam 已经对梯度做了归一化。微调场景通常用这条，或者干脆不调（微调的 batch 范围变化不大）。

实践建议：微调时先固定 lr=2e-5 这类常用值，只在有效 batch 变化超过 4 倍时才按 √ 规则调。把学习率与 batch 一起扫是个昂贵且常常不必要的做法（C40 有关于实验设计的系统讨论）。

配置错误三连

三个高频配置错误：①load_best_model_at_end=True 但 eval_strategy="no"——没有评估就没有「最佳」，会报错或静默不生效。②metric_for_best_model="loss" 但忘了 greater_is_better=False——库会去选 loss 最大 的 checkpoint，也就是最差的那个。（注：对以 loss 结尾的指标名，新版本会自动推断方向，但显式写出来永远更安全。）③save_total_limit 太小配上 load_best_model_at_end——最佳 checkpoint 可能已被删掉；库会尽力保留它，但设成 1 仍可能出问题，建议至少 2。

学习率调度：三个参数的交互

TrainingArguments(
    learning_rate=2e-5,
    lr_scheduler_type="cosine",   # linear / cosine / constant_with_warmup / ...
    warmup_ratio=0.06,            # 占总步数的比例（与 warmup_steps 二选一）
    # warmup_steps=500,           # 绝对步数；**同时设两个时 warmup_steps 优先**
    num_train_epochs=3,
    # max_steps=-1,               # >0 时覆盖 num_train_epochs
)

要注意 总步数的计算：total = ceil(len(dataloader) / grad_accum) × epochs。调度器按总步数规划衰减曲线，所以如果你中途改了 grad_accum 或数据量，衰减曲线就变了——这是「同样的超参换个机器结果不一样」的一个隐蔽来源（不同卡数 → 不同 len(dataloader) → 不同总步数）。

4compute_metrics 与 Callback：两个扩展点

compute_metrics 的签名与陷阱

def compute_metrics(eval_pred):
    logits, labels = eval_pred            # 都是 numpy array（已从 GPU 搬回）
    preds = logits.argmax(-1)
    # ⚠️ token 分类要先过滤 -100
    mask = labels != -100
    return {"accuracy": (preds[mask] == labels[mask]).mean()}

trainer = Trainer(..., compute_metrics=compute_metrics)
陷阱症状解法
忘了过滤 -100指标异常低（把 padding 也算进去了）mask = labels != -100
模型返回 tuple 而非单个 logitslogits 是个 tuple，argmax 报错用 preprocess_logits_for_metrics 提前收缩，或在函数里解包
评估时 OOM评估阶段崩溃（训练正常）eval_accumulation_steps=N 分批搬到 CPU
生成式任务用 argmax指标毫无意义（BLEU/ROUGE 需要生成的文本）Seq2SeqTrainer + predict_with_generate=True

Callback：在训练循环的钩子上挂东西

TrainerCallback 提供了十几个钩子（on_train_begin、on_step_end、on_evaluate、on_save…）。它能读状态、能改控制流，但不能改梯度或权重——那些要靠子类化 Trainer 覆盖 compute_loss / training_step。

  • 典型用途：早停（EarlyStoppingCallback）、自定义日志、按条件调整超参、在评估后跑一段自定义分析、把指标推到外部系统。
  • 控制流：通过修改 control.should_training_stop / should_evaluate / should_save 来干预。
  • 边界：想改 loss 的计算方式 → 覆盖 compute_loss；想改优化器 → 覆盖 create_optimizer；想在 backward 前后插东西 → 覆盖 training_step。Callback 不是万能的扩展点，搞清边界能省很多时间。

关于 EarlyStoppingCallback 有一个必须知道的依赖：它需要 load_best_model_at_end=True 才有意义，否则你停在了「连续 N 次没进步」的那个点，而不是最好的那个点。三个参数要配套出现：eval_strategy="steps"（或 epoch）、load_best_model_at_end=True、metric_for_best_model。缺一个，早停就变成了「提前结束在一个较差的点」。

5checkpoint 与断点续训：存了什么、恢复了什么

checkpoint-500/ ├── model.safetensors 模型权重（fp16 时约 N×2 字节） ├── optimizer.pt **优化器状态**（Adam 的 m 与 v，约 N×8 字节）← 最大的一块 ├── scheduler.pt 调度器状态（当前 step） ├── rng_state.pth 随机数状态（Python/numpy/torch/CUDA） ├── trainer_state.json global_step / epoch / 日志历史 / best_metric ├── training_args.bin 当次训练的全部参数 └── (可选) scaler.pt fp16 的 GradScaler 状态 ⚠️ 所以一个 checkpoint 约是权重大小的 **3-5 倍**。7B 模型 fp16 全量训练的 单个 checkpoint 约 14(权重) + 56(优化器) = 70 GB。save_total_limit 不设会撑爆磁盘。 resume_from_checkpoint 恢复的是**全部**上述状态 -> 训练可以逐 step 复现； 只加载 model.safetensors（from_pretrained）则**丢掉优化器动量与调度器进度** -> 「继续训练」实际上是「用一个新的优化器重新开始」，曲线会有明显跳变。

直白说

这个区别在实践中很重要。「我想在别人的 checkpoint 上继续训练」有两种完全不同的含义：如果你要接着他的训练进度往下跑，必须有完整的 checkpoint 目录（含 optimizer.pt）；如果你只是要在他的权重上做一次新的微调，那 from_pretrained 就够了，而且你应该用新的优化器（旧动量对新任务是噪声）。

严谨说

还有一个容易忽略的点：恢复训练要求数据顺序也能恢复。Trainer 通过保存 rng_state 与 global_step 来跳过已消费的 batch，但这依赖 Dataset 支持索引与确定性采样。流式数据集（IterableDataset）的精确恢复要复杂得多——需要数据集本身支持「从第 N 个样本继续」，这在 datasets 的流式实现里支持有限（Mosaic StreamingDataset 在这方面做得更完善，C43 有讨论）。

一条实用的磁盘纪律：save_total_limit=2 + save_steps 设得别太密。见过太多次「训练跑了两天，磁盘满了，最后一个 checkpoint 写坏了」。另外如果你只需要最终权重（不需要续训），可以在训练后手动删掉各 checkpoint 里的 optimizer.pt——能省掉 2/3 的空间。

6十个高频坑（附症状）

#坑症状解法
1logging_steps 数的是优化步不是 batch「设了 10 但半天不打日志」除以 grad_accum 来理解
2自定义 compute_loss 忘了除 grad_accum梯度累积一开就发散loss / self.args.gradient_accumulation_steps（或用 return_outputs 约定）
3remove_unused_columns=True（默认）吃掉了你的自定义列自定义 collator 收不到某个字段设 remove_unused_columns=False
4labels 列名不叫 labelsloss 是 None，训练不动重命名列，或在模型 forward 里接受你的名字
5评估阶段 OOM（训练正常）跑到第一次 eval 就崩eval_accumulation_steps + per_device_eval_batch_size ↓
6fp16 下 loss nan训练几百步后变 nan换 bf16；或降 lr、加 warmup
7load_best_model_at_end 没配套 eval_strategy报错或不生效三个参数配套出现
8gradient_checkpointing 与 use_cache 冲突警告 + 变慢或报错model.config.use_cache=False
9多卡下 per_device 被误当成总 batch有效 batch 是预期的 N 倍记住要乘卡数
10Trainer 会把模型移到 GPU，但你的自定义模块没跟着device mismatch 报错所有子模块都注册为 nn.Module 的属性

这十个坑里有个共同规律：它们大多来自「参数之间的隐式依赖」——logging_steps 依赖 grad_accum、load_best_model_at_end 依赖 eval_strategy、gradient_checkpointing 依赖 use_cache。所以本模块最实用的产出是一个「配置校验函数」：把这些依赖写成断言，在 Trainer 构造之前跑一遍。notebook 会让你实现它。

7算一笔账：训练时长与 checkpoint 磁盘

\[\text{总优化步} = \left\lceil \frac{N_{samples}}{B_{eff}} \right\rceil \times E, \qquad T \approx \text{总优化步} \times \frac{B_{eff}}{\text{吞吐(样本/秒)}}\]
配置NB_effepochs总优化步checkpoint 数（save_steps=500）
小数据微调5,000323≈ 4710（跑不到 500 步！）
中等微调50,000323≈ 4,6899
大规模 SFT500,0001282≈ 7,81315

第一行揭示了一个很常见的困惑：save_steps=500 但训练只有 471 步 → 一个 checkpoint 都不会存（除非 save_strategy="epoch"）。同理 eval_steps=500 会导致「从头到尾没有评估」，进而让 load_best_model_at_end 失效。小数据集上应该用 save_strategy="epoch" 而不是 steps。

磁盘账：

\[\text{单 checkpoint} \approx N_{params}\times b_{w} + N_{trainable}\times(b_{w} + 8), \qquad \text{总磁盘} = \text{单个} \times \texttt{save\_total\_limit}\]
模型训练方式单 checkpointsave_total_limit=3
BERT-base (110M)全量 fp16≈ 1.3 GB≈ 4 GB
Llama-8B全量 bf16≈ 96 GB≈ 288 GB
Llama-8BLoRA (r=16)≈ 0.2 GB≈ 0.6 GB

这张表解释了 LoRA 在工程上的另一个巨大好处（除了显存）：checkpoint 从 96 GB 变成 0.2 GB。这让「保存二十个不同实验的 checkpoint」从不可能变成毫无压力，直接改变了实验迭代的方式。模块 04 会详细讲。

把本模块浓缩成一句话：Trainer 的复杂度不在任何单个参数，而在参数之间的乘法关系与隐式依赖。乘法关系（有效 batch = 三个数相乘、总步数 = 样本数 ÷ 有效 batch × epochs）决定了训练的实际规模；隐式依赖（logging 依赖 accum、best model 依赖 eval）决定了配置对不对。写一个配置校验函数把这些关系显式化，是本模块最值钱的产出。

8生态动态与开放问题

  • Trainer 与更底层框架的分层：Trainer 之下是 accelerate（模块 05），旁边有 lightning、composer、以及各家自研循环。抽象边界仍在移动——比如 FSDP/DeepSpeed 的配置到底该在哪一层表达，目前分散在 TrainingArguments、accelerate config 与 JSON 配置文件里，是实际的痛点。
  • 优化器的显存创新：8-bit Adam、Adafactor、Lion、以及 GaLore / LoMo 这类「低秩梯度投影」方法都在压缩优化器状态。哪些在什么规模下无损，缺乏系统对比；optim= 的选项还在增加。
  • 确定性与可复现的代价：full_determinism=True 会关掉一批快速 kernel、显著变慢。在多卡+混合精度下做到逐 bit 复现基本不现实（浮点归约顺序不定）。「可复现」在实践中只能是「统计上可复现」，这与 C40 强调的实验纪律有张力，尚无好答案。
  • 流式数据的精确恢复：断点续训要能「从第 N 个样本继续」，这对内存映射数据集容易、对流式数据集很难。规范尚未统一，各家实现语义不同。
  • 训练过程的可观测性：现在的日志主要是 loss 与 lr，但真正有诊断价值的是梯度范数分布、各层更新幅度、激活统计、以及 token 级的 loss 分布。这些需要自己写 Callback 采集，缺少开箱方案（C37 的实验追踪与此互补）。
