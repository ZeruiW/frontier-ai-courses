# 术语词典 · Glossary（Eval 基础设施与线上监控）

> 按主题分组。每条给出：**英文 / 中文 / 一句话定义 / 为什么重要 / ⚠️ 常见误解**。
> 组织原则是本课的四层架构 + 线上：**spec → runner → store → gate → online**。
> 与相邻课程的分工见 [README](README.md)：评测方法本身在 C66/C67，
> 模型生命周期在 C37，数据管道在 C43。**本课只管「怎么把评测跑一千次而不失真」。**

## 一 · 总体框架 · Framework

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| eval infrastructure | 评测基础设施 | 让同一套评测能被可靠、重复、便宜地执行的那一层工程。 | 它保证的不是「跑得快」，而是**「这个数字变了」这件事有唯一的解释**。 | 以为它是「把脚本整理一下」。**它的核心是三个可验证的性质**（确定性/可归因/幂等），不是代码整洁度。 |
| determinism (in eval) | 确定性 | 不是「两次跑出同样的数字」，而是**随机性被收拢到少数几个显式来源**，且这些来源可控或可测。 | LLM 评测天然带随机性，追求逐位相同不现实；可实现的目标是「差异可解释」。 | 以为 `temperature=0` 就等于确定性。**任务顺序、并发调度、外部环境、judge 都是随机源**，而且并发那一项会真实地改变分数。 |
| attributability | 可归因性 | 任何两次运行的差异，都能被归因到某个显式记录的配置项。 | 它把「为什么这次不一样」从考古变成查询。 | 以为需要人工维护一份「要记录哪些字段」的清单。**spec 是纯数据时，指纹就是它的哈希**，加字段自动生效。 |
| idempotence | 幂等性 | `run(spec, store) ∘ run(spec, store) = run(spec, store)`。 | 一次实现同时解决三件事：中断续跑、部分重跑、意外重复执行。 | 以为需要复杂的状态机。**实现只有一句话：主键 `(run_id, task_id, attempt)`，写入前先查在不在。** |
| four-layer architecture | 四层架构 | spec（声明）/ runner（执行）/ store（结果）/ report（报告）。 | 几乎所有成熟评测系统都会收敛到这个结构。 | 把 ① 和 ② 合并（「配置直接写在脚本里」）。**这是所有后续问题的根源**——配置写在代码里就无法被哈希、比较、diff。 |
| anti-pattern (silent) | 静默反模式 | 六个不会报错、但会让数字失去意义的做法。 | **它们危险正因为不报错**——代码照跑，数字照出，只是不再意味着你以为的东西。 | 以为「没报错就是对的」。本课六条里有四条会让分数系统性偏高，而且都不抛异常。 |

## 二 · Spec 与版本化 · Spec & Versioning

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| spec as data | spec 即数据 | 评测配置是可序列化、可哈希、可 diff 的纯数据，不含执行逻辑。 | **投入产出比最高的结构决策**：换来可哈希（指纹）、可 diff（差异定位）、可生成（参数扫描）。 | 以为「配置文件」就等于 spec-as-data。关键是**所有会改变被测量分布的因素都在里面**——包括 prompt 模板的哈希。 |
| run fingerprint | 运行指纹 | 规范化后的 spec 的哈希。 | 它让「这两次能不能比」变成一行 `assert` 而不是一次回忆。 | 对**原始** spec 取哈希。**必须在规范化之后算**（迁移 + 填默认值 + 归一等价写法），否则「写了默认值」和「没写」会算出不同指纹。 |
| stable task ID | 稳定样本 ID | 分配一次、永不改变、永不复用的样本标识。 | 内容被修正时，历史结果仍然对得上。 | 用内容哈希当 ID。**改一个错别字，这条样本的历史结果就永远对不上了**；内容哈希应当单独存一列用来*检测*变化。 |
| content_sha | 内容哈希 | 样本内容字段的哈希，与 ID 分离。 | 它让版本 diff 能精确区分「内容改了」与「只是标签改了」——两者对历史可比性的影响完全不同。 | 以为它可以替代 ID。它的职责是**检测**，不是**标识**。 |
| dataset versioning | 数据集版本化 | `(id, version, sha)` 三元组唯一确定一份任务集；已发布版本只读。 | **修改与删除都改变了聚合分母**，主版本号的作用是让这件事在文件名里就能看见。 | 「就改一道坏题，只是一道」。后果是所有引用过 v1 的历史报告都指向一个不存在的东西。 |
| intersection recompute | 交集重算 | 跨版本比较时，只在两边共有**且内容未变**的样本上重算双方。 | **这是跨版本比较唯一正确的做法**——直接比较把「分母变化」和「模型提升」混在了一起。 | 只取 ID 交集就够了。**还要排除 `content_sha` 变过的样本**——ID 相同但内容变了，它已经不是同一道题。 |
| rate-based sampling | 按比例抽样 | `hash(task_id) % N < rate*N`，每条样本独立判定是否入选。 | **只要抽样数量 N 固定，任务集增长时抽中的那批就必然会变**；按比例选则已有样本的入选与否永不改变。 | 以为「固定 seed 的随机抽样」就稳定了。固定 N 时它数学上不可能稳定——这不是实现问题。 |
| schema migration | schema 迁移 | 把旧格式的 spec 升到当前版本的纯函数，必须幂等。 | 字段一定会变；迁移器让它变得不痛。 | 改字段的语义（比如 `timeout` 从毫秒改成秒）。**旧 spec 依然能解析，但含义变了，而且不会报错**——正确做法是加新字段并废弃旧的。 |
| datasheet | 数据集说明 | 记录来源、时间、标注规范、已知坏题、判分器 α/β、**预期分数区间**。 | 回答那些「半年后有人会问、而当时的人已离职」的问题。 | 觉得它是文档洁癖。**「预期分数区间」是一条极便宜的健康检查**——预期 30–50% 的任务集跑出 95%，几乎肯定是流水线坏了。 |

## 三 · Runner · Execution

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| cache key | 缓存键 | `hash(输入内容 + 完整执行指纹)`。 | 缓存能省 90%+ 的重跑成本，但**键设计错了会安静地返回旧结果**。 | 手写一份「要包含哪些字段」的列表。**必然会漏**——新加配置项时没有任何机制提醒你更新它；应当直接用 `exec_fp`。 |
| stale cache read | 陈旧缓存命中 | 改了 prompt 但缓存键没变，于是读到旧结果。 | 症状是「我明明改了 prompt，分数却一点没变」，**而它会被误读成「这个改动没有效果」**。 | 以为这类 bug 会被测试发现。它不抛异常、不报警，唯一的症状是一个看起来合理的结论。 |
| runner failure taxonomy | 失败六分类 | 瞬时错误 / 限流 / 超时 / 拒答 / 格式错误 / 判分器崩溃。 | 只有 `scorer_error` 可以从分母排除，其余全部计入。 | 把超时当纯基础设施问题重试到成功。**超时是混合信号**——一部分来自服务器慢，一部分是真实的能力信号，掩盖后者会系统性高估。 |
| retry selection bias | 重试的选择偏倚 | 重试条件与「结果好坏」相关时引入的单向选择效应。 | **「重试到成功为止」把 55% 的真实能力抬到了 78%**，而且不会报错。 | 以为「只有故意作弊才会发生」。**很多时候是无意的**——比如「解析失败就重试」，而难题更容易解析失败。 |
| jitter | 抖动 | 退避时长乘一个随机因子。 | 没有它，一批同时被限流的请求会在同一时刻重试，形成**惊群**，把上游再打垮一次。 | 以为它是可选的优化。模拟里 200 个请求无抖动时全部挤在同一时刻。 |
| token bucket | 令牌桶 | 按速率补充令牌、允许突发的限流器。 | 上游的限额通常是**按速率**而不是按并发数，两者管的不是一件事。 | 以为固定并发数就够了。**只有并发上限没有限流器会在请求快速返回时超速；只有限流器没有并发上限会在请求变慢时堆积。** |
| circuit breaker | 熔断器 | closed → open → **half_open** 三态。 | half_open 让熔断能**自动恢复**——而评测经常在夜间/CI 里无人值守地跑。 | 以为「失败就停」就是熔断。没有 half_open 的话，熔断之后需要人工重启。 |
| dry run estimate | 预检 | 先跑 5–10 条，外推总成本并要求确认。 | **把「事故」变成「预估」**，能抓住绝大多数配置写错导致的成本爆炸。 | 觉得多此一举。它便宜到几乎没有理由不做，而 `max_tokens` 写多一个零这种事很常见。 |

## 四 · 结果存储与分析 · Store & Analysis

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| wide fact table | 宽事实表 | 一条 rollout 一行，所有维度作为列或可 join 的外键。 | **你现在想不到的问题，半年后一定会被问到**；存了明细它是一句查询，只存聚合它是一次重跑。 | 以为存储成本很高。评测结果通常是百万行、几十 GB——对任何数据库都是小数据。 |
| post-hoc aggregation | 后置聚合 | 聚合是明细表上的视图，不是表本身。 | 同一批结果能算出 micro / macro / pass^k / 加权四个都对但含义不同的数字。 | 把聚合写死在 runner 里。**换口径就要重跑，而重跑的成本会让人倾向于「就用现在这个数」**，即使它不是回答当前问题的正确口径。 |
| denominator discipline | 分母纪律 | 每个聚合数字都要带 n、排除数、排除理由。 | 「分数 0.412」和「分数 0.412（n=498，排除 14 条判分器崩溃）」是两个可信度完全不同的陈述。 | 觉得是形式主义。**这是本课能提供的最便宜的可信度提升**。 |
| nan on empty | 空输入返回 nan | 分母为 0 时返回 `nan` 而不是 0。 | 返回 0 会让「没有数据」和「全错」在下游变得无法区分。 | 以为返回 0 更安全。**这两种情况在告警逻辑里应当触发完全不同的动作。** |
| Simpson's paradox | 辛普森悖论 | 每个分层里 A 都更好，合并后 B 更好。 | **在评测里真实发生**，且成因通常不是有人故意，而是两次运行的任务集不完全相同（超时被跳过的题不一样）。 | 以为它只是统计课上的趣题。**只要两边任务构成不同，总分就不可直接比较**——必须交集重算。 |
| direct standardization | 直接标准化 | 用同一套分层权重重算双方。 | 它是 Simpson 悖论的标准解法，在评测里就是「按共同任务集重算」或「按线上分布重加权」。 | 以为只有跨版本才需要。**同一数据集版本内部也会发生**——只要两次运行的完成情况不同。 |
| run diff (fixed/regressed/churn) | 逐题差异 | 从错变对 / 从对变错 / 翻转总数 / 净变化。 | 「涨了 3 点」不可行动；「修好 42 道、退化 30 道，其中 9 道在 billing」可行动。 | 只看 net。**churn 要和噪声基线比**——噪声下本来就会自发翻转几十道题，churn 不超过它就没有信息。 |
| integrity checks | 完整性校验 | 指纹唯一 / 覆盖完整 / 无重复 / 状态合法 / 数据集一致。 | 五条都对应一类真实事故；**「覆盖完整」必须比对预期行数**，否则被吞掉的异常发现不了。 | 放在一个「记得跑一下」的脚本里。**必须放进加载函数**——放在加载函数里它就不可能被忘记。 |

## 五 · CI 门禁 · Gating

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| gate trust erosion | 门禁信任消耗 | 误报持续消耗团队对门禁的信任，直到它被降级或关掉。 | **门禁最可能的死法不是漏报，是被关掉**；漏报的代价有限（下一道防线还在），误报的代价是复利的。 | 以为「宁可错报不可漏报」。模拟显示 α=5% 的门禁 20/20 都在三周内被关掉。 |
| false alarm budget | 误报预算 | 把「每月至多 m 次误报」换算成单次误报率 α。 | **这是设定阈值时唯一有意义的口径**——「单次 5%」听起来很小，换算成每天 20 次运行就是每天一次。 | 沿用统计学默认的 α=0.05。**它在论文里合理（一篇论文一次检验），在 CI 里是灾难性的（一天二十次）。** |
| threshold from variance | 阈值三步法 | 测噪声 → 定误报预算 → `z(α)·σ·√2`。 | 阈值有了依据，而不是拍脑袋。 | 噪声大就把阈值放宽。**阈值大到十几个点时，正确动作是去降噪**——一个只能检出 12 个点退化的门禁形同虚设。 |
| deterministic gate | 确定性门禁 | 完整性 / 指纹可比 / 绝对分数区间 / 安全断言。 | **这四类不涉及统计推断，误报率天然为零**，是门禁里最可信、最该优先建设的部分。 | 一上来就去调统计阈值。**顺序反了**——零误报的确定性检查应当先建。 |
| absolute score bound | 绝对分数区间 | 分数掉出 datasheet 声明的预期区间就阻断。 | 能抓住判分器坏了、答案泄漏、任务集被换这类流水线事故。 | 只在分数下降时告警。**分数异常升高同样是事故信号**——「只在下降时告警」会漏掉整整一类问题。 |
| paired gating | 配对门禁 | 在同一批任务上比较，让任务难度这个方差源被消掉。 | **零成本把噪声砍到不到一半**。 | 以为「都跑同一个基准」就算配对。**必须跑同一批任务**——基线 500 条、当前 487 条（13 条超时被跳过）就不是配对，而且被跳过的通常是最难的。 |
| regression-only gate | 只看退化的门禁 | 退化题数超过噪声上限就阻断，不看净变化。 | **符合 CI 的语义**：门禁的职责是防止把东西弄坏，不是确认变好了。 | 觉得净变化为正就该放行。「修好 50 道、弄坏 30 道」里，那 30 道可能包含核心路径。 |
| n-strike rule | 连续 N 次才阻断 | 单次异常只警告，连续两次才阻断。 | **误报率从 α 降到约 α²（前提是两次运行的噪声独立；持续性噪声会让实际值高得多），检出率只掉 9 个点**——因为真实退化会持续存在而误报是随机的。 | 以为会大幅漏报。真实退化第二次跑它还在，所以 power² 依然很高。 |
| two-tier gating | 两级门禁 | smoke（每次提交，确定性检查）+ full（合并前，统计门禁）。 | smoke 的 σ 大约 3–5 个点，按误报预算算阈值要放到 ±12 个点以上——**而那么大的退化根本不需要统计检验**。 | 给 smoke 也配统计门禁。**smoke 的正确定位是确定性检查 + 抓灾难性变化**，这是算出来的结论。 |

## 六 · 线上监控 · Online

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| offline-online gap | 离线-在线落差 | 离线指标涨了而线上没变化。 | 它有**两层不匹配**：分布（$D_{off}\ne D_{on}$）与口径（$s \ne u$），**两层的修法完全不同**。 | 直接归因为「提升太小」。**最常见的其实是分布不匹配**，而正确的诊断顺序是先查覆盖率，再谈效应量。 |
| PSI / KS | 群体稳定性指数 / KS 统计量 | 分布漂移的两个标准度量。 | 无标签、实时、覆盖全量流量，是最便宜的一层监控。 | 以为 PSI 高就是变差了。**它能告诉你「变了」，不能告诉你「变差了」**——漂移告警的正确动作是触发一次带标签的抽样评测。 |
| unlabeled signal | 无标签信号 | 自一致性 / 行为分布 / 重问率 / 拒答率 / 下游任务成功。 | 线上绝大多数请求没有标签，但**没有标签不等于没有信号**。 | 以为必须有标注才能监控。三个零成本信号覆盖三个失败方向：模型不稳定、行为漂移、用户没被满足。 |
| reask rate | 重问率 | 用户收到回答后立刻换种说法再问一遍的比例。 | **不需要任何标注、实时可得、与真实满意度强相关**。 | 拿它做绝对判断（「12% 说明质量不好」）。它混杂了 UI 与用户习惯，**只适合同期同流量的相对比较**。 |
| guardrail | 护栏 | 响应返回用户前的实时检查，分 L0 规则 / L1 小模型 / L2 LLM 三层。 | 分层的意义不只是省成本，更是**把零误伤的确定性检查与有误伤的模型判断分开**。 | 让 L2 直接拒答。**L2 的误伤落在真实用户身上**，通常只该降级或标记；而且误伤率过高时 guardrail 会被降级成「只记录」然后被忘掉（与 CI 门禁同构）。 |
| head vs tail sampling | 头部 / 尾部采样 | 请求开始时决定记不记 vs 按结果决定记不记。 | 尾部采样信息量高得多，但**引入强选择偏倚**——直接算平均会严重低估质量。 | 混在一起统计。**必须记 `sample_kind` 与 `sample_p`**，否则两类数据再也分不开；尾部数据要做逆概率加权（IPW）。 |
| feedback loop | 闭环 | 线上问题 → 去标识化 → 人工确认 → 写成可判分任务 → 进任务集新版本。 | 让同一个问题**永远不会再悄悄回来**——这就是回归测试的意义。 | 把线上 case 直接贴成一道题。**通常判不了分**；而且 guardrail 触发 ≠ 模型错了，不确认就入库等于把误伤固化成标准答案。 |
| recurrence rate | 复发率 | 已经进了任务集的问题，在线上再次出现的比例。 | **闭环有没有真的起作用的唯一硬指标**。 | 只看回灌延迟。延迟再短，如果问题照样复发，说明那道题写得不对（判分器没抓住真正的失败模式）。 |
| production share cap | 线上回灌占比上限 | `from_production` 任务在任务集中的占比上限（如 30%）。 | 线上问题按定义是模型的弱项，占比过高会让**任务集漂成一个「疑难杂症集」**，不再代表真实流量。 | 以为回灌越多越好。需要同时从线上做**均匀随机**采样来补充「正常」任务。 |
