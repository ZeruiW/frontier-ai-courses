1缓存：本课最贵的一个 bug 就藏在这里

先讲缓存，因为它是 runner 里收益最大、也最容易出错的一块。收益很直接：重跑时省 90% 以上的调用成本。而错误的形态是模块 00 反模式清单里的第四条——它不会报错。

❌ 缓存键 = hash(输入文本) ┌──────────────────────────────────────────────────────────┐ │ 第一次跑: prompt_v1 + 输入 X → 调用模型 → 存进缓存 │ │ 改了 prompt 的一句措辞 │ │ 第二次跑: prompt_v2 + 输入 X → **缓存命中** → 返回旧结果 │ │ │ │ 症状: 「我明明改了 prompt，分数却一点没变」 │ │ 误读: 「这个改动没有效果」 ← 实际上它根本没被执行 │ └──────────────────────────────────────────────────────────┘ ✓ 缓存键 = hash(输入内容) + 完整配置指纹 prompt 变了 → 指纹变了 → 缓存不命中 → 真的重新调用
\[\text{cache\_key} = H\big(\underbrace{\text{input}}_{\text{内容}} \;\|\; \underbrace{\text{fp}(\text{spec}_{\text{exec}})}_{\text{配置}}\big)\]
必须进缓存键的东西为什么漏了会怎样
输入内容显然所有样本共用一个结果
模型 ID 与快照换模型就是换实验拿 A 的结果当 B 的
采样参数（temperature/top_p/seed/max_tokens）改了会改变输出分布温度扫描全部读到同一个结果
prompt / 模板的哈希最常被漏的一个改了 prompt 分数不动，被误读成「改动无效」
工具集与 schema（agent 场景）工具变了行为就变了同上
缓存格式版本存储结构变更时要整体失效新代码读到无法解析的旧记录

有一条纪律可以一劳永逸地避免这类 bug：缓存键直接用模块 01 的 exec_fp（执行指纹），而不是手写一个「要包含哪些字段」的列表。手写列表必然会漏——因为新加一个配置项时，没有任何机制提醒你去更新那个列表。而 exec_fp 是整个执行配置的哈希，加了字段它自动就变了。

什么时候不该缓存

  • 估计方差、算置信区间、跑 pass^k 时必须关缓存——开着缓存重跑两次得到同样的分数，说明的不是「结果可复现」，而是「你根本没有重跑」（这条与 C66 模块 05 第 8 节完全一致）；
  • 非确定性判分器（LLM judge）的缓存要更谨慎：它可以缓存，但缓存键里必须包含 judge 的完整指纹，且做 swap 探针时两次调用的键必须不同（否则第二次直接命中第一次的结果，探针失效）；
  • 调试期——加一个 --no-cache 开关，并让它显式打印「缓存已禁用」，避免自己被自己骗。

2失败分类：静默跳过是最常见的数据污染

模块 00 讲过「失败样本必须计入分母」。这一节讲得更细：失败不是一类，而是至少五类，它们该被区别对待。

失败类型典型来源该不该重试该不该计入分母该怎么记
瞬时基础设施错误网络抖动、502、连接重置该重试成功后按成功计记重试次数
限流（429）并发太高该（退避后）同上单独统计，用于调并发
超时模型慢、任务难看情况计入，且算失败超时是一种能力信号，不是纯粹的基础设施问题
模型拒答 / 内容过滤安全策略触发不该计入，且单独统计拒答率是一个独立指标（C67-05）
输出格式错误没按 schema 返回可以重试 1 次计入解析失败率必须报告（C67-01）
判分器崩溃validator 有 bug不该（先修 bug）标记为 scorer_error，从主指标里排除但要显式报告这是唯一可以排除的一类

直白说

为什么超时要算失败而不是算基础设施错误？因为超时是混合的：一部分来自基础设施（服务器慢），一部分来自任务本身（这道题模型想太久）。而后者是真实的能力信号——一个总是超时的 agent，在产品里就是不可用的。把超时算成「基础设施错误并重试到成功」，等于系统性地掩盖了这个信号。

严谨说

更精确的处理是把超时按原因拆开：如果同一批任务在低并发下不超时、高并发下超时，那是基础设施；如果在任何并发下都超时，那是任务/模型。C66 模块 05 的「并发敏感性检查」正是用来做这个区分的——分数对并发不敏感，才说明超时阈值有足够余量、超时反映的是真实能力。

最后一行的 scorer_error 是唯一可以从主指标排除的失败类型，但它必须被显式报告，而且它的比例应该趋近于零。如果 5% 的样本因为判分器崩溃被排除，那么这份报告的可信度就取决于「崩溃是不是随机发生的」——而它通常不是（判分器更容易在奇怪的输出上崩溃，而奇怪的输出更可能是失败的）。

3重试：退避、抖动，以及它悄悄引入的偏倚

重试是必需的，但它有两个层面的问题：工程层面（怎么退避才不打垮上游）和统计层面（重试会不会污染结果）。后者更少被讨论，但更重要。

工程层面：指数退避 + 抖动

\[\text{delay}_k = \min\big(\text{base} \cdot 2^{k},\ \text{cap}\big) \cdot U(0.5,\ 1.5)\]

抖动（jitter）那一项不是可选的。没有抖动时，一批同时被限流的请求会在同一时刻同时重试，形成惊群（thundering herd），把上游再打垮一次。乘一个 $U(0.5, 1.5)$ 的随机因子，就能把重试时刻摊开。

统计层面：重试引入的选择偏倚

这是本模块最重要的一条：重试的触发条件必须与「结果好坏」无关。如果你对失败的样本重试、对成功的样本不重试，就引入了一个只朝一个方向的选择效应——「重试到成功为止」是评测里最隐蔽的一种作弊，而且很多时候是无意的。C66 模块 02 第 8 节的三级复核流水线里已经出现过同一条纪律。
重试触发条件有没有偏倚为什么
HTTP 5xx / 连接错误没有与模型输出的内容无关
429 限流没有同上
输出解析失败有轻微偏倚难题更容易输出不合规格式（C67-01）；可以重试，但要记录并报告重试率
判分为 0严重偏倚这就是「重试到成功为止」——绝对禁止
输出「看起来不对」严重偏倚同上，只是更隐蔽

一条可执行的规则：重试的判断函数只能看异常类型与 HTTP 状态码，不能看模型输出的内容，更不能看判分结果。在代码结构上，这意味着重试逻辑必须在判分之前完成——拿到判分结果之后就不许再重试了。

4并发与限流：为什么并发是 harness 的一部分

C66 模块 05 的复现清单第 7 条说「并发度必须写进报告」。这一节讲清楚为什么。

并发度 ↑ │ ├─ 吞吐 ↑ （想要的） ├─ 单请求延迟 ↑ （上游排队） ├─ 超时率 ↑ ← **分数会变** ├─ 429 率 ↑ ← 重试变多，成本变高 └─ 容器/CPU 争抢 ↑ ← 代码类任务里测试跑得更慢，更容易超时 结论：**并发度是一个会影响分数的自变量**，不是一个纯粹的性能旋钮。

并发敏感性检查：一个必做的健康检查

做法很简单：在 1 / 4 / 8 / 16 四个并发度上各跑一遍 smoke 子集，看分数是否稳定。

现象说明该做什么
分数对并发不敏感超时阈值有足够余量✅ 正常，记录并发度即可
高并发下分数下降超时阈值设得太紧，高并发下大量任务撞上超时放宽超时或降低并发；不要接受这个分数
高并发下 429 率暴涨超过了上游配额上限流器（下一节）
低并发下也不稳定不是并发的问题回去查随机源（模块 00 第 3 节）

限流：令牌桶

直接用固定并发数是不够的，因为上游的限额通常是按速率（每分钟多少请求 / 多少 token）而不是按并发数。标准做法是令牌桶：

桶容量 = burst（允许的突发量）
补充速率 = rate（每秒补多少个令牌）

请求前: 取 1 个令牌；没有就等到有为止
        （token 计费的场景：按预估 token 数取多个令牌）

好处: 平时允许突发，长期严格遵守平均速率——正好匹配多数 API 的限额语义

限流器和并发上限要同时存在，它们管的不是一件事：并发上限管的是「同时有多少请求在飞」（保护内存与连接数），限流器管的是「单位时间发出多少请求」（遵守上游配额）。只有并发上限没有限流器，会在请求快速返回时超速；只有限流器没有并发上限，会在请求变慢时堆积。

5预算控制：熔断、上限、以及「先跑一小批」

评测可以很贵。一个没有预算保护的 runner，有可能在你去吃午饭的时候花掉一个月的额度——而这类事故通常不是因为写错了循环，而是因为某个环节开始疯狂重试。

保护机制触发条件动作为什么需要
硬性总预算累计成本 > 上限立即停止并保存已有结果最后一道防线
单任务上限单条任务成本 > 上限终止该任务，标记 budget_exceeded防止一条失控的轨迹吃掉全部预算（呼应 C66-03 的循环检测）
错误率熔断最近 N 次调用的失败率 > 阈值暂停并告警上游挂了的时候不要继续烧钱重试
预检（dry run）正式跑之前跑 5–10 条，外推总成本并要求确认最有效的一个：把「事故」变成「预估」

第四条值得强调，因为它便宜到几乎没有理由不做：先跑 10 条，用实测的单条成本 × 总任务数，打印出「本次运行预计花费 X」，然后再继续。这一步能抓住绝大多数「配置写错导致成本爆炸」的情况——比如不小心把 max_tokens 写成了 100000，或者 attempts 写成了 50。

熔断器的三个状态

熔断器（circuit breaker）不是简单的「失败就停」，它有三个状态，这个设计是为了能自动恢复：

  • closed（正常）：请求正常通过，统计失败率；
  • open（熔断）：失败率超阈值，直接拒绝所有请求，不再打上游；
  • half-open（试探）：熔断一段时间后，放一个请求过去试试；成功就回到 closed，失败就回到 open 并延长等待。

关键在 half-open 这个状态——没有它，熔断之后需要人工介入才能恢复；而评测经常在无人值守时跑（夜间、CI），自动恢复的价值远大于它的实现成本。

6断点续跑：三个层次

模块 00 已经实现了最基本的续跑（主键去重）。这一节讲它的三个层次，以及为什么第三层经常被忽略。

层次能续什么实现什么时候不够用
① 任务级已完成的任务不重跑主键 (run_id, task_id, attempt) 去重单条任务本身很贵时（agent 跑 40 步）
② 调用级同一任务内已完成的模型调用不重发缓存（第 1 节）调用之间有状态时（agent 的环境已经变了）
③ 状态级agent 的中间状态（环境快照、上下文）检查点 + 环境快照环境不可序列化时

第三层有一个必须知道的陷阱：从检查点恢复的运行，与从头跑到底的运行，未必是同一个实验。如果 agent 的行为依赖于「已经花了多少预算」「上下文里有什么」，那么恢复点的状态就成了一个隐藏变量。实践建议：状态级续跑只用于「省钱地重跑失败任务」，不要用于产出正式报告的运行——正式运行应当从头跑完，并在 spec 里记录 resumed: false。

run_id 的设计

续跑的一切都建立在 run_id 上，所以它的设计值得单独说：

  • run_id 应当由 spec 指纹 + 时间戳组成，例如 f2a91b7c-20260829-1430。前半段让你一眼看出「这次跑的是什么配置」，后半段保证唯一。
  • 复用 run_id 必须是显式的：加 --resume <run_id> 参数，而不是默认复用。模块 00 练习 3 的「跳过数 > 0」就是检测意外复用的信号；
  • 续跑时必须校验指纹：如果 --resume 的那个 run_id 对应的指纹与当前 spec 不同，直接报错退出——否则你会得到一个「一半用旧配置、一半用新配置」的运行，而且完全看不出来。

7Runner 本身的可观测性：五个必报的数

最后一节：runner 自己也需要被监控。下面五个数应当在每次运行结束时打印，并落到结果里——它们不是「性能指标」，而是「这份结果可不可信」的判据。

RUN SUMMARY · run_id=f2a91b7c-20260829-1430
  完成:            512 / 512 tasks × 3 attempts = 1536 rows
  失败分解:        ok 1489 | timeout 22 | refusal 11 | parse_error 9 | scorer_error 5
  ────────────────────────────────────────────────────────────────
  ① 缓存命中率:     0.0%      ← 首次运行应为 0；非 0 说明 run_id 被复用了
  ② 重试率:         3.2%      （其中 429 占 2.1%，5xx 占 1.1%）
  ③ 并发实际值:     8         （配置 8，未被限流器压低）
  ④ 限流等待占比:   11.4%     ← 超过 30% 说明并发设得比配额高，纯粹在浪费墙钟时间
  ⑤ 成本:           $12.47    （预检估计 $11.80，偏差 +5.7%）
  ────────────────────────────────────────────────────────────────
  scorer_error 0.33%          ← 必须趋近于零；超过 1% 就该去修判分器
指标健康范围异常时说明什么
缓存命中率首次 0%，重跑 > 90%首次运行非 0 → run_id 被意外复用；重跑很低 → 缓存键里混进了不该有的东西（比如时间戳）
重试率< 5%高 → 上游不稳或并发过高；同时要看重试是否只发生在失败样本上（第 3 节的偏倚）
限流等待占比< 30%高 → 并发设得比配额高，加并发只会增加等待，不会提高吞吐
成本 vs 预检估计偏差 < 20%偏差大 → 预检样本不代表整体（通常是难题更贵）
scorer_error 率趋近 0> 1% → 判分器有 bug，这份结果的可信度存疑

这五个数里最容易被忽略、也最有诊断价值的是「首次运行的缓存命中率非 0」。它几乎总是意味着有人复用了 run_id——而复用 run_id 会让新配置的结果与旧配置的结果混在同一个 run 里，这是一个「指纹校验都抓不到」的污染（因为写入时用的是当前指纹，混进去的旧行用的是旧指纹，而聚合时如果没检查「一个 run 内指纹唯一」就发现不了）。所以模块 00 里那条 assert len(fingerprints) == 1 是必须的。

8成本归因：钱到底花在哪

模块 02 第 5 节讲了怎么不超支，这一节讲怎么知道钱花在哪——因为「总共花了 12 美元」这个数字不足以做任何优化决策。

切分维度回答什么问题典型发现
按任务哪些题最贵长尾极端：5% 的任务吃掉 40% 的预算（通常是循环或超长轨迹）
按失败类型钱有多少花在了失败上失败样本的成本占比经常超过一半——因为失败往往伴随重试与超长轨迹
按重试重试消耗了多少重试率 5% 但成本占比 15%（重试的都是难题，本身就更贵）
按缓存命中缓存省了多少用来验证缓存是不是真的在工作

第二行的发现最有行动价值：如果一半的预算花在了最终失败的样本上，那么「提前放弃明显没救的任务」就是一个立竿见影的优化（C66 模块 03 的循环检测 + 本模块第 5 节的单任务预算）。而这个判断只有在成本按失败类型切分之后才能做出——看总成本永远看不出来。

实现上这不需要新字段：模块 02 已经在每行结果里记了 cost_usd 与 status，切分只是一句 GROUP BY（模块 03）。这是「存最细粒度事实」这条设计的又一次兑现。

9Agent 场景的额外复杂度：轨迹、环境、嵌套调用

前七节讲的 runner 假定「一个任务 = 一次模型调用」。agent 场景下这个假定不成立，而它带来的复杂度值得单独说清楚。

维度单次调用场景agent 场景runner 要多做什么
调用次数1 次几十到几百次预算控制要下沉到单任务粒度（第 5 节）

失败一次调用失败第 17 步失败——前 16 步的成本已经花掉了记录失败发生在第几步；决定是重跑整条还是从检查点续
环境无状态容器/数据库/浏览器，必须在任务之间重置环境生命周期管理；重置失败也是一类失败
超时单次调用超时两级：单步超时 + 整条轨迹超时两个都要配，且都要进 spec

第四行是 agent 评测里最常见的一类静默污染：环境没有在任务之间被正确重置。上一个任务往数据库里写的数据还在，下一个任务读到了它——结果可能变好（信息泄漏）也可能变坏（状态冲突），而且完全不报错。防御方式是在每个任务开始前做一次「环境指纹」校验：对初始状态取哈希，与预期值比对，不一致就判为 env_error 并跳过——这与本课反复出现的「确定性检查优先」是同一条思路。

agent 场景的缓存：只能缓存确定性前缀

由于状态依赖，agent 的调用无法逐个独立缓存。可行的两种做法：

  • 整条轨迹缓存：键 = (task_id, exec_fp)，值 = 完整轨迹。命中率低（任何配置变化都失效），但语义绝对正确；
  • 确定性前缀缓存：如果 agent 的前 $k$ 步在给定配置下是确定的（temperature=0 且环境已重置），可以缓存这个前缀。但必须把「环境初始状态的哈希」也放进键里——否则环境变了而缓存命中，会得到一条在错误环境上产生的轨迹。

嵌套调用的成本归因

agent 场景还有一个成本侧的细节：一次任务的成本要归因到哪一步。如果只记总成本，你会知道「这个任务花了 0.8 美元」，但不知道其中 0.6 美元花在了一个反复重试的工具调用上。

解法是让每一步的成本都单独落库，并在聚合时提供两个视角：按任务（这道题贵不贵）与按步骤类型（钱花在规划、工具调用、还是最后的总结上）。后者是优化成本时唯一有用的视角——而它需要的字段在 C66 模块 03 的轨迹 schema 里已经有了，这里只是把它接进 runner 的成本统计。

单任务预算：与 C66-03 的循环检测接在一起

模块 02 第 5 节讲的预算控制，在 agent 场景下有一个额外的抓手：C66 模块 03 的循环检测。检出循环就提前终止这条轨迹，省下的预算拿去跑别的任务。但被终止的轨迹必须单独标记为 terminated_by_loop_detector，而不是简单记成失败——因为「被我们主动掐掉的」和「模型自己做不出来的」是两个不同的量，混在一起会让失败分类失去意义（第 2 节）。
