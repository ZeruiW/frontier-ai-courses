1一条 rollout 一行：宽事实表与后置聚合

结果层的核心设计只有一句话：存最细粒度的事实，把聚合留到查询时做。听起来平淡，但它决定了这套系统能不能回答半年后才被问出来的问题。

❌ 存聚合结果 ✓ 存最细粒度事实 ┌──────────────────────────┐ ┌────────────────────────────────┐ │ run_id | score | n │ │ run_id | task_id | attempt |… │ │ r-001 | 0.412 | 512 │ │ r-001 | t001 | 0 |… │ │ r-002 | 0.447 | 498 │ │ r-001 | t001 | 1 |… │ └──────────────────────────┘ │ r-001 | t002 | 0 |… │ └────────────────────────────────┘ 能回答: "总分是多少" 能回答: 总分 / macro / 按难度切片 / 不能回答: 按难度切片？pass^k？ pass^k / 与上次逐题 diff / 只用强判分 哪些题变了？只用强判分任务？ 任务重算 / 任何**当时没想到**的问题 ——**而且不用重跑**

直白说

为什么这条如此重要？因为你现在想不到的问题，半年后一定会被问到。「这个提升在难题上也成立吗」「是不是只在某个子系统上涨的」「如果只算判分器强的那些任务呢」——这些问题在存了明细的系统里是一句查询，在只存了聚合的系统里是一次重跑（几百美元 + 几小时）。

严谨说

从数据建模的角度，这是事实表的标准形态：每行是一个不可再分的观测事件（一次 rollout 的结果），所有能想到的维度（任务属性、配置、时间）都作为列或外键存在。聚合是这张表上的视图，而不是表本身。存储成本换来的是分析的自由度——而评测结果的存储量通常很小（几十万行、几百 MB），这个交换几乎总是划算的。

最小 schema：11 个字段

-- 主键三元组（模块 00）
run_id        TEXT     -- 一次运行
task_id       TEXT     -- 稳定样本 ID（模块 01）
attempt       INTEGER  -- 第几次重复（pass^k 需要）

-- 可归因性
fingerprint   TEXT     -- 执行配置指纹（模块 01/02）
dataset_ver   TEXT     -- 任务集版本（跨版本比较需要）
scorer_ver    TEXT     -- 判分器版本

-- 结果
status        TEXT     -- ok | timeout | refusal | parse_error | scorer_error
score         REAL     -- NULL when status != 'ok'
output        TEXT     -- 原始输出（失败样本尤其要留，否则永远查不出原因）

-- 成本与诊断
cost_usd      REAL
latency_ms    INTEGER

PRIMARY KEY (run_id, task_id, attempt)
output 这一列经常被以「太占空间」为由砍掉。不要砍——至少对失败样本不要砍。「为什么这道题失败了」这个问题，没有原始输出就只能重跑；而重跑时的随机性可能让那次失败不再复现。如果确实需要省空间，正确做法是对成功样本做压缩或抽样保留，对失败样本全量保留——因为你要看的永远是失败的那些。

2聚合逻辑必须与结果分离

上一节说「聚合留到查询时做」。这一节说清楚为什么这不只是灵活性问题，更是正确性问题。

同一批结果，可以算出好几个都「对」但含义不同的数字（C66 模块 02 已经展示过 micro/macro）。如果聚合逻辑被写死在 runner 里，那么换一个口径就要重跑——而重跑的成本会让人倾向于「就用现在这个数」，即使它不是回答当前问题的正确口径。

口径定义回答什么问题什么时候是错的
micro所有 rollout 一视同仁求平均「在这个任务分布上表现如何」任务数不均衡时，大子集主导总分
macro（按任务）先按 task_id 求平均，再对任务求平均「典型任务上表现如何」各任务重复次数不同时，等权可能不是你要的
macro（按子集）先按子系统/难度求平均，再等权「各类任务都还行吗」小子集的噪声被放大到与大子集同权
pass^k每个任务 k 次全对的比例「可靠性如何」（C66-04）结果有人复核时（那时该看 pass@k）
加权按线上流量占比加权「对用户的实际影响」权重来源没写进报告时

一条实践规范：把聚合写成一组独立的、可组合的函数，并让报告同时输出至少两个口径。如果 micro 与 macro 给出相反的排序，这件事本身就是报告里最重要的发现（C66 模块 02 第 7 节已经说过一次，这里是它的工程落实）。而这一切的前提，是明细还在。

聚合函数的三条约束

  1. 纯函数：输入是明细行，输出是数字。不读文件、不发请求、不依赖全局状态。这样它可以被单元测试，而聚合逻辑的 bug 是最难被发现的一类；
  2. 显式声明分母：每个聚合函数都要能报出它用了多少行、排除了多少行、为什么排除。「分数 0.412」和「分数 0.412（n=498，排除 14 条判分器崩溃）」是两个可信度完全不同的陈述；
  3. 对空输入有定义：分母为 0 时返回 nan 而不是 0——返回 0 会让「没有数据」和「全错」在下游变得无法区分。

3切片分析：Simpson 悖论会在评测里真实发生

有了明细，切片就是一句 GROUP BY。但切片会暴露一个在评测里真实发生、且经常被误读的现象。

模型 A 模型 B easy (400 题) 95% (380) 98% (98) ← B 每一片都更好 hard (100 题) 40% (40) 45% (45) ← ────────────────────────────────────────── 总计 84% 58% ← 但 A 的总分更高 原因: 两个模型跑的**任务构成比例不同** A: 400 easy + 100 hard B: 100 easy + 100 hard 这不是矛盾，是 Simpson 悖论——总分被"跑了哪些题"这个混杂变量污染了。

直白说

在评测里这个现象最常见的成因不是有人故意，而是两次运行的任务集不完全相同：有些任务超时被排除了、有些是新加的、有些在一次运行里失败被跳过了。只要两边的任务构成不同，总分就不可直接比较——这和模块 01 的「跨版本比较要做交集重算」是同一件事，只是这里发生在同一个数据集版本内部。

严谨说

形式化地说，总分是各层分数按各层样本占比加权的结果：$\bar{s} = \sum_g w_g \bar{s}_g$，其中 $w_g = n_g / n$。当两次运行的 $\{w_g\}$ 不同时，$\bar{s}_A - \bar{s}_B$ 里混着「各层分数差」与「权重差」两部分，而后者与模型能力无关。解法是标准化权重：用同一套 $\{w_g\}$（通常取两边的交集或目标分布）重算两边——这在流行病学里叫直接标准化，在评测里就是「按共同任务集重算」。

所以报告里有一条硬规范：比较两次运行时，必须先检查它们的任务集是否一致；不一致就在交集上重算。这条检查应当是自动的——notebook 第 3 节会把它写成一个函数，而模块 04 会把它变成 CI 里的一行断言。

哪些切片维度值得预留

  • 任务属性：难度、子系统、来源、创建时间（污染检验用）、判分器强度（C66-02）；
  • 执行属性：attempt 序号（看首次 vs 重试）、并发度、是否命中缓存；
  • 结果属性：失败类型（模块 02 的五分类）、延迟分桶、成本分桶；
  • 时间：run 的时间戳——用来画趋势图，也用来定位「什么时候开始变的」。

这些维度不需要在存储时预聚合，只需要保证它们能被 join 到——任务属性来自数据集（模块 01 的 tags），执行属性来自 spec，结果属性来自明细行本身。

4两次运行的 diff：从「分数变了」到「哪些题变了」

「分数从 41.2% 涨到 44.7%」——这句话几乎不包含可行动的信息。有信息的是：哪些题从错变对了，哪些题从对变错了。

\[\Delta = \underbrace{|\{i: s_i^{A}=0,\ s_i^{B}=1\}|}_{\text{fixed}} - \underbrace{|\{i: s_i^{A}=1,\ s_i^{B}=0\}|}_{\text{regressed}}\]
量含义为什么比总分有用
fixed从错变对的题数直接对应「这个改动修好了什么」
regressed从对变错的题数最重要的一个——净提升为正也可能伴随大量退化
churn$\text{fixed} + \text{regressed}$衡量「改动有多大」；churn 高而净变化小 = 只是噪声在翻转
net$\text{fixed} - \text{regressed}$这才是总分变化的来源
churn 是一个被严重低估的量。如果 fixed=30、regressed=25，净提升只有 5 题，但有 55 道题的结果翻转了——这说明模型的行为在这些题上本来就不稳定，那 5 题的「提升」很可能只是这次采样的运气。正确的判读是：先看 churn 与净变化的比例。churn 远大于净变化时，应该增加重复次数而不是宣布提升（呼应 C66 模块 04 的方差分析）。

配对分析：这里可以直接用 McNemar

逐题 diff 天然是一个配对设计（同一批任务、两个配置），所以 C66 模块 04 的 McNemar 检验可以原样用上：只有 fixed 与 regressed 这两类不一致对携带信息，$\chi^2 = (|f - r| - 1)^2 / (f + r)$。这让「这次提升是不是显著」变成一个可以自动计算的判断，而不需要人去感觉「3.5 个点好像挺多的」。

5结果的完整性校验：五条应当自动跑的检查

存储层还有一个容易被忽略的职责：在把结果交给分析之前，先检查它自己是不是完整的。下面五条检查很便宜，但每一条都对应一类真实发生过的事故。

检查断言不通过说明什么
指纹唯一一个 run 内 fingerprint 只有一个值run_id 被复用，新旧配置的结果混在一起（模块 02 第 7 节）
覆盖完整行数 == 任务数 × attempts有任务被静默跳过了——通常是异常被吞了
无重复主键三元组唯一幂等写入被绕过了
状态合法status 只取枚举内的值；status='ok' ⟺ score 非空runner 里有分支忘了赋值
数据集一致所有行的 dataset_ver 相同跑到一半数据集被换了

第二条「覆盖完整」有一个容易被绕过的情况值得单说：如果 runner 在任务级别 catch 了所有异常并 continue，那么失败的任务连一行都不会写入——行数少了，而分数看起来正常甚至更高（因为最难的那些任务恰恰最容易抛异常）。所以这条检查必须比对「预期行数」而不是「已有行数的内部一致性」，而预期行数只能从 spec 里算出来（任务数 × attempts）。

这五条应当作为加载函数的一部分，而不是一个「记得跑一下」的脚本——放在加载函数里，它就不可能被忘记；放在脚本里，它半年后一定会被忘记。

6存储规模与保留策略

最后一个工程问题：这些明细会不会撑爆存储。答案通常是不会，但值得算一笔账，因为这笔账会影响你要不要保留 output 列。

\[\text{行数} = N_{\text{tasks}} \times k_{\text{attempts}} \times N_{\text{runs}}\]
场景单次行数一年的运行次数总行数含 output 的体量
CI smoke60 × 1每天 20 次 × 250 天 = 500030 万约 1–3 GB
每日全量500 × 336555 万约 5–15 GB
模型选型500 × 5每月几十次约 100 万约 10–30 GB
合计量级——百万行几十 GB

百万行、几十 GB——对任何数据库都是小数据。所以默认策略应当是全部保留，而不是一上来就设计复杂的归档流程。

如果确实需要缩减

  1. 先压缩 output，不要先删它——文本压缩率通常有 5–10 倍；
  2. 按状态差异化保留：失败样本的 output 全留，成功样本的可以只留哈希或抽样留；
  3. 冷热分层：三个月以上的运行归档到对象存储，但保留每个 run 的聚合摘要在热库里（趋势图需要它）；
  4. 永远不要删的：主键、fingerprint、status、score。这四列加起来每行不到 100 字节，百万行也只有几十 MB——删它们省不了多少空间，却会让历史彻底不可用。

关于保留策略有一条经验：决定「删什么」时，想的不是「现在需要什么」，而是「半年后有人会问什么」。而半年后被问得最多的问题是「这道题当时为什么错了」——答这个问题需要的恰恰是失败样本的原始输出。

7报告的形状：从明细到一份可以贴出去的东西

把 C66/C67 的报告规范与本课的存储层接起来，得到一份完整报告的生成路径：

明细行 (store)
  │
  ├─ 完整性校验（第 5 节）───────────► 不通过就停，不要出报告
  │
  ├─ 主指标 ────► micro + macro + 分母与排除说明
  ├─ 不确定度 ──► 按任务聚类自举（C66-04）
  ├─ 切片 ──────► 按难度/子系统/判分器强度（第 3 节）
  ├─ 与基线 diff ► fixed / regressed / churn / McNemar（第 4 节）
  ├─ 成本 ──────► $/success 而不是 $/task（C66-05）
  └─ 运行健康 ──► 五个数（模块 02 第 7 节）
  │
  └──► EVAL CARD（C66-05 的模板 + 本课的运行健康块）
  • 完整性校验是一个门，不是一个提示——不通过就不该产出报告；
  • 每一个数字旁边都要带分母，这是本课能提供的最便宜的可信度提升；
  • 与基线的 diff 优先于绝对分数——因为读者真正要决策的是「这个改动能不能合」；
  • 运行健康块必须在报告里，而不是只在日志里。「缓存命中率 30%（首次运行）」这种异常，只有出现在报告顶部才会被看见。

最后一句总结本模块：存储层的价值不在于存得快，而在于它决定了你未来能问出什么问题。存了明细，半年后的新问题是一句查询；只存了聚合，同一个问题是一次几百美元的重跑——而在那种成本下，大多数问题最终不会被问。

8结果表的 schema 演化：加字段容易，改语义要命

结果表会活很多年，字段一定会变。这一节的规则与模块 01 的 spec 演化同构，但有一个结果表特有的约束。

变更安全吗怎么做
加一列（可空）✅ 安全历史行为 NULL；聚合函数要能处理 NULL
加一个 status 枚举值⚠️ 要小心必须同时更新「哪些计入分母」的策略表，否则新状态会被默认计入或默认排除
改一列的语义🚫 危险历史行照样能读，但含义变了——必须加新列而不是改旧列
删一列🚫 危险历史分析脚本会静默地少一个维度

第二行是结果表特有的坑：新增一个 status 值时，所有历史聚合都会被影响。比如加了 env_error（环境重置失败，见模块 02 第 8 节）——如果聚合函数用的是「除了 scorer_error 都计入」，那么这个新状态会被当成失败计入分母，历史数据与新数据的口径就不一致了。所以策略表（哪些计入分母）必须与 status 枚举一起版本化，并且聚合结果要记录它用的是哪个版本的策略。

一条便宜的防御：聚合函数遇到未知的 status 值时抛异常，而不是默默归类。这把「新状态被静默错误分类」从一个数据问题变成了一个立刻可见的报错——而这正是本课反复主张的：让不会报错的问题变得会报错。

9趋势与基线：一条时间序列比两个点有用得多

前七节都在讲「两次运行的比较」。这一节讲时间维度——因为很多问题只有在时间序列上才看得见。

三类只有趋势才能回答的问题

问题两点比较能答吗趋势能答什么
「什么时候开始变的」✗定位到具体的某一天/某个 commit
「这是波动还是趋势」✗看方差带与斜率——单次下降 2 个点可能是噪声，连续五次下降不是
「基线该更新了吗」✗基线与当前的距离持续拉大 = 基线过期了

直白说

第三个问题在实践中最容易被忽略。CI 门禁需要一个基线，而基线用久了会过期——模型改进了很多次之后，拿三个月前的基线做比较，「相对基线没有退化」这句话已经没有信息量了。正确做法是滚动基线：每次成功合并后更新基线，让门禁始终比较的是「相对上一个已知良好状态」。

严谨说

但滚动基线有一个必须警惕的副作用：渐进式退化（creeping regression）。如果每次都只退化 0.3 个点（远低于门禁阈值），滚动基线会把每一次都判为通过，而二十次之后总共退化了 6 个点。防御方式是同时维护两个基线：滚动基线（比上一次，抓突发退化）与锚定基线（比一个季度前的固定版本，抓渐进退化）。两个都要在门禁里检查，阈值可以不同——锚定基线的阈值应当更宽但绝不能没有。

渐进式退化是所有「只比上一次」的门禁的共同盲区，而它在真实项目里非常常见——因为每一次单独看都是合理的取舍（「这次为了修 bug 稍微牺牲一点分数」）。锚定基线的作用就是让这些取舍的累积效应可见。

基线更新的一个反直觉细节

滚动基线还有一个容易做错的地方：基线应当在「合并后」更新，而不是在「门禁通过后」更新。两者的差别在于：门禁通过的 PR 可能最终没有被合并（作者放弃了、被别的 PR 取代了）。如果基线跟着「通过的门禁」走，它就会指向一个从未进入主干的状态——而后续所有 PR 都在和这个不存在的状态比较。

实现上这意味着基线更新必须由「合并事件」触发，而不是由「CI 成功」触发。这个细节不做对的症状是：主干上的分数与基线记录的分数长期对不上，而且很难查——因为每一次单独看都是正常的。

趋势图上该画什么

  • 主指标 + 置信带——没有置信带的趋势图会让人过度解读每一个小波动；
  • 标注事件：模型版本变更、任务集版本变更、judge prompt 变更。指标跳变时第一件事是看有没有事件对齐——通常有；
  • 分子集的趋势：核心能力集与回归集的趋势应当分开画，它们的正常形态完全不同（前者缓慢上升，后者应当贴着 100%）；
  • 运行健康的趋势（模块 02 的五个数）——成本或重试率的缓慢上升，往往比分数变化更早地预告问题。
