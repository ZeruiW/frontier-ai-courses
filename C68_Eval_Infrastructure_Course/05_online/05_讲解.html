05 · 线上监控与漂移

「离线涨了线上没涨」有两层不匹配——分布（$D_{off} \ne D_{on}$）与口径（$s \ne u$），两层的修法完全不同，混在一起谈会做错方向；最常见的是分布，最容易被误诊成「提升太小」，正确的诊断顺序是：先查覆盖率，再谈效应量 · PSI/KS 能告诉你「输入输出变了」，不能告诉你「变差了」——模拟里「模型变啰嗦」让 KS 强烈报警而真实质量几乎没变；所以漂移告警的正确动作是触发一次带标签的抽样评测，而不是直接回滚 · 三个无标签信号覆盖三个失败方向：自一致性（模型不稳定）· 行为分布（长度/格式密度/拒答率，正是 C67-05 的 hack 形态）· 重问率（用户没被满足）——三者全自动、零标注成本 · guardrail 分层的意义不只是省成本：L0 确定性可放心拦截，L2 的误伤落在真实用户身上，通常只该降级不该拒答 · 尾部采样的数据不能直接算平均，必须记 sample_kind 与 sample_p · 闭环里 复发率是唯一的硬指标，而 from_production 必须设占比上限，否则任务集会漂成一个「疑难杂症集」

1离线指标与线上表现：为什么它们经常对不上

这门课到这里为止讲的都是离线评测：固定的任务集、可控的环境、可复现的结果。这一节讲那个所有人迟早会撞上的问题：离线涨了三个点，线上一点感觉都没有。

原因机制怎么诊断怎么修
分布偏移离线任务集是人挑的，真实流量的分布完全不同把线上请求聚类，看离线任务集覆盖了哪些簇从线上采样回灌任务集（第 6 节）
指标口径不同离线测「答案对不对」，线上看「用户满不满意」在同一批样本上同时算两个指标，看相关系数对齐口径，或明确声明离线是代理指标
饱和离线任务集上大家都 90%+，提升发生在离线覆盖不到的尾部看离线分数的分布是否压在上界换更难的任务集（C66-01 的信息量分析）
提升太小3 个点的离线提升，在线上被其他因素的方差淹没算线上的 MDE（C66-04）接受它检测不出来，或改用配对/影子设计
非模型因素主导线上体验主要由延迟、UI、检索质量决定分解线上指标的方差来源先修那个主导因素

直白说

这五个原因里，最常见的是第一个，最容易被误诊成第四个。「可能是提升太小了」听起来很合理，于是团队去做更大的改动；而真实原因往往是离线任务集根本不覆盖线上的主要场景——改动再大也白搭，因为它优化的是一个不重要的分布。区分方法很直接：先看覆盖率，再谈效应量。

严谨说

形式化地说，离线指标估计的是 $\mathbb{E}_{x \sim D_{\text{offline}}}[s(x)]$，而你关心的是 $\mathbb{E}_{x \sim D_{\text{online}}}[u(x)]$。两者之间隔着两层不匹配：$D_{\text{offline}} \ne D_{\text{online}}$（分布）与 $s \ne u$（指标口径）。「离线涨了线上没涨」这件事，必须先确定是哪一层出的问题——第一层用覆盖率诊断（第 2 节），第二层用同批样本上的相关系数诊断。两层的修法完全不同，混在一起谈会导致做错方向。

一条实用的诊断顺序：① 覆盖率（离线任务集覆盖了多少线上流量的分布）→ ② 口径相关性（在同一批样本上，离线指标与线上指标的相关系数）→ ③ 效应量与 MDE。按这个顺序查，通常在第一步就能找到答案；而很多团队直接从第三步开始，于是永远在讨论「是不是要做更大的改动」。

2分布漂移：PSI、KS，以及它们各自的盲区

线上监控的第一层是无标签监控——不需要知道答案对不对，只看输入和输出的分布有没有变。它便宜、实时、覆盖全量流量。

两个标准工具

\[\text{PSI} = \sum_{b} (p_b - q_b)\ln\frac{p_b}{q_b}, \qquad \text{KS} = \sup_x |F_p(x) - F_q(x)|\]
指标适用判读盲区
PSI（群体稳定性指数）分箱后的分布对比，类别型与数值型都行< 0.1 稳定 · 0.1–0.25 需关注 · > 0.25 显著漂移对分箱方式敏感；零频次桶要做平滑
KS 统计量连续变量的分布对比配合样本量算 p 值只看最大偏离点，对分布形状的局部变化不敏感
类别频次的卡方离散类别（意图、语言、来源）同上类别很多时功效低
嵌入空间的分布距离语义漂移MMD / 分类器双样本检验计算贵；结果不可解释

无标签漂移监控有一个结构性的局限，必须提前说清楚：它能告诉你「输入变了」，但不能告诉你「变得更差了」。输入分布漂移了，模型可能表现更好、更差、或者没变化——PSI 高只是一个「该去看看」的信号，不是一个「出问题了」的结论。所以漂移告警的正确动作是「触发一次带标签的抽样评测」，而不是直接回滚。

该监控哪些分布

  • 输入侧：请求长度、语言、意图类别、来源渠道、是否带附件/图片；
  • 输出侧：响应长度、格式元素密度、拒答率、置信度分布——这四个正是 C67 模块 05 里 reward hacking 的四种形态，在线上它们同样是「模型行为漂移」的最早信号；
  • 系统侧：延迟分位数、错误率、重试率、工具调用次数（agent 场景）、成本；
  • 判分器侧：如果线上有 LLM judge 在跑，它自己的分布也要监控（C67-03 的哨兵集）。

输出侧的四个指标值得单独强调：它们不需要任何标签，却能抓住模型行为的实质性变化。「平均响应长度一周内涨了 40%」这个信号，比任何离线指标都更早地告诉你「有什么东西变了」。

3Guardrail：线上的实时护栏

漂移监控是事后的（发现了才去查）。Guardrail 是实时的：在响应返回给用户之前做一次检查。

用户请求 ──► 模型 ──► ┌─────────────────────────────┐ ──► 用户 │ GUARDRAIL │ │ L0 规则 (微秒级, 零成本) │ │ L1 小模型 (毫秒级, 极便宜) │ │ L2 LLM (百毫秒, 贵) │ └─────────────────────────────┘ │ 触发 ▼ 降级 / 重生成 / 转人工 / 拒答
层检查什么延迟误伤率触发后的动作
L0 规则格式合法性、必填字段、长度上限、禁用词、PII 正则< 1ms极低（确定性）重生成或用兜底模板
L1 小模型安全分类、意图偏离、语言不匹配10–50ms低但非零降级到保守回答
L2 LLM judge事实一致性、是否回答了问题、语气100–800ms取决于 judge 质量（C67）转人工或重生成

Guardrail 有一个与 CI 门禁完全同构的失败模式（模块 04 第 1 节）：误伤率过高时，它会被降级成「只记录不拦截」，然后被忘掉。而线上 guardrail 的误伤代价比 CI 误报更直接——它伤的是真实用户的体验。所以分层的意义不只是省成本，更是把「零误伤的确定性检查」和「有误伤的模型判断」分开：L0 可以放心拦截，L2 通常只该降级或标记，不该直接拒答。

Guardrail 的三个必报指标

  1. 触发率（按层分开）——突然升高说明模型或流量变了；
  2. 误伤率——需要人工抽查被拦截的样本。这个数不测就等于不知道 guardrail 在做什么；
  3. 漏放率——从用户投诉、事后审计里反推。最难测，但也最重要。

最后一条实践建议：guardrail 的每一次触发都要落一条结构化日志（哪一层、哪条规则、原始输出、最终动作）。这些日志是回灌离线任务集最好的原料（第 6 节）——被 guardrail 拦下来的样本，正是模型最容易出问题的地方。

4抽样：全量记录不现实，随机抽样浪费预算

线上流量可能是每天几百万条，而人工标注预算可能是每天几百条。怎么抽这几百条，决定了你能发现什么。

策略怎么抽适合发现什么代价
均匀随机固定比例随机抽估计整体质量（唯一无偏的）难样本太少，发现不了具体问题
分层按意图/渠道/长度分层，每层保底各细分场景的质量需要分层维度
不确定性驱动抽 judge 置信度低、swap 不一致的（C67-03）判分器的薄弱区 + 模型的边界结果有偏，不能直接外推
异常驱动抽 guardrail 触发的、超时的、用户负反馈的真实问题极度有偏

推荐的组合与 C67 模块 03 的元评测集设计完全同构：「均匀随机的主集」+「不确定性驱动的加强集」+「异常驱动的问题集」，三者分开统计、绝不混算。主集回答「整体质量是多少」（无偏），加强集回答「难的地方怎么样」，问题集提供「该修什么」的线索。把它们混成一个数字，三个问题一个都答不了。

追踪采样率与统计的关系

如果你对 trace 做了采样（比如只记录 1% 的完整轨迹），那么基于 trace 的任何统计都要做逆概率加权——而且要注意采样本身可能是有偏的：

  • 头部采样（在请求开始时决定记不记）——无偏，但会漏掉罕见的错误；
  • 尾部采样（请求结束后按结果决定记不记，比如「出错的全记」）——信息量高得多，但引入了强选择偏倚。用尾部采样的数据估计整体错误率会严重高估；
  • 实践组合：头部固定比例（用于无偏统计）+ 尾部全量记录异常（用于诊断），并在数据里用一个字段标明这条 trace 是怎么被采到的——没有这个字段，两类数据混在一起就再也分不开了。

5无标签监控：没有金标准时能看什么

线上绝大多数请求是没有标签的——没人告诉你这个回答对不对。但没有标签不等于没有信号。

信号怎么得到能预警什么可信度
自一致性同一请求采样两次，比较两个回答模型在这类输入上不稳定★★★（C67-03 的 swap 一致性同构）
拒答/兜底率直接统计模型开始回避（或安全策略变了）★★★
输出行为分布长度、格式密度、置信表述行为漂移（C67-05 的 hack 形态）★★★
用户行为代理重问率、复制率、点踩率、会话轮数用户满意度的代理★★☆（受 UI 影响大）
下游任务成功用户是否完成了目标动作最接近真实效用★★★（但归因难）
工具调用成功率（agent）直接统计工具误用、环境变化★★★

直白说

这里面最有价值、也最容易被忽略的是「重问率」：用户在收到回答后立刻换一种说法再问一遍，几乎必然意味着上一个回答没解决问题。它不需要任何标注，实时可得，而且与真实满意度高度相关。

严谨说

从测量的角度，这类信号是行为代理指标：它们与真实效用相关，但混杂了 UI、用户习惯、流量构成等因素。因此它们适合做相对比较（新版本 vs 旧版本，同期同流量）而不适合做绝对判断（「重问率 12% 说明质量不好」）。这与 C67 模块 03 里「样本级 vs 系统级」的结论同构：带噪声的信号在配对比较里依然有用，在绝对判断里不可靠。

一个便宜且强推荐的组合：「自一致性抽样」+「行为分布监控」+「重问率」。三者都不需要标注、都能全自动跑、成本近乎为零，而且覆盖了三个不同的失败方向——模型不稳定、行为漂移、用户没被满足。（这与 C67 模块 05 第 6 节推荐的「可验证任务正确率 + 行为分布监控」是同一个思路。）

6闭环：把线上信号送回离线任务集

这是本课的落点，也是把「评测基础设施」与「模型改进」连起来的那一环。

┌──────────────────────────────────────────────────────────────┐ │ │ │ 线上流量 ──► guardrail 触发 / 负反馈 / 低置信 / 高重问 │ │ │ │ │ ▼ │ │ ① 采样与去标识化（PII） │ │ ▼ │ │ ② 人工确认「这确实是个问题」 │ │ ▼ │ │ ③ 写成可判分的任务（C66-01 的六条规则） │ │ ▼ │ │ ④ 进入任务集的**新版本**（C68-01：只增不改） │ │ ▼ │ │ 离线评测 ──► CI 门禁 ──► 发布 ──────────────────────────────┘ │ │ └──── 从此这个问题**永远不会再悄悄回来**（这就是回归测试的意义） ┘

四个必须做对的细节

  1. 去标识化必须在采样时做，不是在入库后做——一旦真实用户数据进了任务集仓库，清理成本就高得多；而且任务集通常会被更多人访问。
  2. 人工确认这一步不能省：guardrail 触发不等于模型错了（可能是 guardrail 误伤）。不确认就入库，等于把 guardrail 的误伤固化成了「标准答案」。
  3. 写成可判分的任务：这是 C66 模块 01 的六条规则（先写判分函数再写任务、要有防回归检查项、难度要有梯度……）。「把线上 case 直接贴成一道题」通常判不了分。
  4. 进新版本而不是改旧版本（模块 01）——而且要标注来源为 from_production，因为这批任务的分布与人工构造的任务不同，分析时需要能分开。

闭环有一个必须防的退化模式：任务集逐渐被「线上出过问题的 case」填满。这些 case 按定义是模型的弱项，所以任务集会变得越来越难、分数越来越低，而且它不再代表真实流量的分布。缓解：给 from_production 的任务设一个占比上限（比如 30%），并且同时从线上做均匀随机采样来补充「正常」的任务——否则任务集会漂成一个「疑难杂症集」。

闭环的健康指标

  • 回灌延迟：从线上发现问题到它进入任务集的时间。超过一个月，闭环基本等于不存在；
  • 复发率：已经进了任务集的问题，有没有在线上再次出现。这是闭环有没有真的起作用的唯一硬指标；
  • 任务集的来源构成：人工构造 vs 线上回灌的比例，以及后者是否超了上限。

7全课收尾：五层之间的信息流

把本课五个模块串起来，是一条从「声明」到「反馈」的完整回路：

① SPEC 评什么、怎么判、版本与指纹 ─┐ │ │ ② RUNNER 并发/重试/缓存/预算，幂等可续 │ 离线 │ │ ③ STORE 一条 rollout 一行，只追加 │ │ │ ④ CI GATE 确定性检查 + 配对统计门禁 ─┘ │ ▼ 发布 ⑤ ONLINE 漂移 / guardrail / 无标签信号 │ └──────────► 回灌 ──► ① 的新版本任务集
模块它保证的性质缺了它会怎样
01 SPEC可归因（差异指向配置项）两次运行的差异说不清楚
02 RUNNER执行不污染结果缓存读到旧结果、重试抬高分数——都不报错
03 STORE未来能问出新问题换个口径就要重跑，于是大多数问题不会被问
04 CI GATE退化进不了主干退化上线；或门禁误报太多被关掉
05 ONLINE离线看不见的问题被抓住离线一直涨，线上一直没感觉

直白说

回头看，这五层解决的其实是同一个问题的五个面：怎么让「这个数字变了」这件事变得可解释。可归因（01）、不被执行污染（02）、可重新切片（03）、可被自动判断（04）、可被真实世界校验（05）——五层都在服务同一个目标。

严谨说

而这个目标本身来自 C66 与 C67 的那条主线：先验证测量仪器，再相信读数。C66 教你怎么量一个 agent，C67 教你怎么验证判分器，本课教你怎么让这套测量能被可靠地、重复地、便宜地执行。三者合起来，才构成一个可以支撑决策的评测体系——而缺了本课这一环，前两课的方法只能被执行一次，然后在第二次执行时因为某个没被记录的配置项而失去可比性。

如果这门课只带走一句话：基础设施的价值不在于跑得快，而在于它让「结果变了」这件事有唯一的解释。而所有的工程决策——spec 是纯数据、缓存键含指纹、主键三元组、聚合后置、阈值从方差推、线上信号回灌——都是在服务这一条。

下一门课 C69 · Agent 安全与提示注入：本课模块 03 的 guardrail 是质量护栏，而当输入里有人主动想让 agent 做坏事时，需要的是另一套东西——攻击面在哪、怎么量它、怎么防。

8影子运行：零风险地拿到真实分布上的配对样本

C66 模块 05 第 7 节提到过影子运行。这一节把它放在监控的语境里重讲，因为它填补了离线评测与线上 A/B 之间的一个空档。

真实请求 ──┬──► 现网模型 ──► 返回给用户 │ └──► 候选模型 ──► **不返回**，只落库 │ ▼ 两个输出在同一个真实请求上配对 ──► 判分器比较
方式用户暴露样本分布配对需要金标准吗
离线评测0%人挑的，通常有偏是（同一批任务）是
影子运行0%真实流量是（同一个请求）否（比较两个输出即可）
金丝雀 / A-B1–100%真实流量否（不同用户）否（看线上指标）

直白说

影子运行填的空档很具体：它同时具备「真实分布」与「配对」两个性质，而离线评测只有配对、A/B 只有真实分布。配对意味着方差极低（同一个请求，两个版本），真实分布意味着它测的是用户实际会问的东西——这两条加起来，让影子运行成为检测「离线覆盖不到的退化」最灵敏的手段。

严谨说

代价有两个，都要提前想清楚：① 双倍推理成本（可以靠采样比例控制，1–5% 通常就够）；② 需要一个能比较两个输出的判分器——而这正好是 C67 的内容，包括它的全部偏差问题。特别要注意的是位置偏差：比较现网输出与候选输出时，必须做 swap 双跑（C67-02），否则「候选更好」这个结论可能只是因为它被放在了第二位。

影子运行还有一个必须处理的工程细节：副作用。如果候选模型是一个 agent，它可能会真的去调用工具、写数据库——影子运行必须跑在只读或沙箱化的工具集上，否则「零用户暴露」这个前提就不成立了。这与 C69 的沙箱与权限边界是同一套机制。

9监控本身的成本与优先级

本课列了十几种监控信号。全部都上是不现实的，这一节给出按性价比排序的建设顺序。

优先级建什么成本覆盖什么失败为什么是这个顺序
P0错误率 / 延迟 / 成本的基础监控极低（通常已有）系统挂了不建这个，后面所有信号都不可信
P0输出行为分布（长度、格式密度、拒答率）极低（纯统计，无标注无调用）模型行为漂移零成本，且是最早的预警信号
P1重问率 / 用户行为代理低（需要会话拼接）用户没被满足与真实满意度强相关，且无需标注
P1L0 确定性 guardrail低格式错误、越界输出零误伤，可放心拦截
P2输入分布漂移（PSI/KS）低流量构成变化它只说「变了」，需要配合抽样才有结论
P2自一致性抽样中（双倍推理，但只抽 1%）模型不稳定抽样比例可以很低
P3每周人工抽样标注高（人力）真实质量唯一的金标准，但要等前面几层把范围缩小
P3L2 LLM guardrail高（每请求一次额外调用）语义问题误伤落在用户身上，要先把 α/β 量出来（C67）

这张表最重要的是第二行：输出行为分布监控是零成本的——它不需要标注、不需要额外调用、不需要金标准，只是对已有日志做几个统计。而它覆盖的正是 C67 模块 05 里那四种 reward hacking 形态（长度膨胀、格式套路化、自信化、拒答漂移）。如果你只能建一样东西，建这个。

从监控到诊断：三层漏斗

上面那张表还隐含了一个结构：这些信号构成一个漏斗，每一层的作用是把「需要人看」的范围缩小一个数量级。

全量流量 (10^6/天) │ P0: 行为分布 + 错误率 ← 零成本，全量覆盖 ▼ 异常时段/切片 (10^4) │ P1: 重问率 + guardrail ← 低成本，定位到具体场景 ▼ 可疑样本 (10^2) │ P2: 自一致性 + PSI 驱动抽样 ▼ 人工标注 (10^1-10^2/周) ← 唯一的金标准，也是唯一贵的一层

建设顺序应当自上而下：先建全量的零成本层，让它把范围缩小，再让昂贵的人力只处理最后那一小撮。反过来做（一上来就大规模人工标注）的问题不是「太贵」，而是「抽样是随机的，因此大概率抽不到真正出问题的地方」——这与第 4 节抽样策略的讨论是同一件事。

一个容易被忽略的成本：监控自己的可靠性

监控系统本身也会坏，而且它坏了的时候不会告警（因为告警就是它的职责）。三条便宜的防御：

  • 心跳指标：监控管道每分钟写一个计数器。「指标停止上报」应当触发告警，而不是被当成「一切正常」；
  • 合成流量：定期发几条已知答案的请求走完整链路，它同时验证了服务与监控两条链路；
  • 告警的告警：如果某个指标连续 N 天没有任何波动，那通常不是「非常稳定」，而是「数据源断了」。

直白说

最后一条值得单独说：「指标异常地平稳」是一个被严重低估的故障信号。真实指标总是有噪声的；一条完全水平的曲线，十有八九是采集断了、或者读到了缓存、或者除数被写死了。

严谨说

这与模块 02 的「首次运行缓存命中率非 0」是同一类诊断：都是在检查「一个本该变化的量为什么没有变化」。这类检查的共同特点是：它们抓的不是「值超出了范围」，而是「值的行为不对」——而后者往往对应着更根本的故障（数据没进来、代码路径没被执行），却几乎不会被常规的阈值告警覆盖。
