1Spec 必须是纯数据：三条后果

模块 00 说过「spec 是纯数据」是投入产出比最高的结构决策。这一节讲清楚它换来了什么。

性质因为 spec 是数据，所以…如果 spec 是代码，就要…
可哈希指纹 = sha256(json)，自动、完整、零维护人工维护一份「要记录哪些字段」的清单，且必然会漏
可 diff两次运行的差异是一个结构化的 diff，能精确到字段读两份脚本的 git diff，靠人判断哪些改动会影响结果
可生成 / 可扫描「跑 5 个模型 × 3 个温度」是 15 个 spec 的笛卡尔积写循环，而循环里的配置又回到了代码里

怎么划界：什么进 spec，什么留在代码里

直白说

一条实用的判据：「改这个东西，会不会让结果变得不可与之前比较？」会 → 进 spec；不会 → 留在代码里。模型 ID、温度、prompt 模板、判分器版本、任务集版本、步数上限、超时——全部会；日志格式、进度条样式、重试的退避曲线——通常不会（注意「重试次数」会，因为它影响错误率）。

严谨说

更严格的说法：spec 应当包含所有会改变被测量分布的因素。形式化地，设一次运行产生的结果分布是 $P(\text{result} \mid \text{spec}, \text{code}, \text{env})$。基础设施的目标是让 $\text{code}$ 与 $\text{env}$ 对这个分布的影响可忽略——$\text{env}$ 靠容器 digest 与录制回放固定（C66-05），$\text{code}$ 靠「把影响分布的东西全搬进 spec」。剩下的、确实会影响分布但又无法进 spec 的部分（比如并发导致的超时行为），就是模块 00 里「指纹相同却结果不同」那类告警要抓的东西。

一个反复出现的边界情况：prompt 模板该进 spec 还是留在代码里？答案是它的哈希必须进 spec。模板本身可以放在文件里（便于编辑与 review），但 spec 里要存它的哈希——否则改了一句措辞，指纹不变，两次运行看起来可比但实际不可比。这与 C67 模块 01 第 8 节的「judge prompt 是 harness 的一部分」是同一条。

2样本 ID：为什么不能用内容哈希

这是评测数据集特有的一个问题，在普通的数据工程里不常见，但在评测里它直接决定了历史结果还能不能用。

用内容哈希当 ID（❌） 用稳定 ID（✓） ┌────────────────────────┐ ┌────────────────────────┐ │ id = sha(问题文本) │ │ id = "billing-017" │ │ │ │ （分配一次，永不改变） │ │ 修正一个错别字 │ │ 修正一个错别字 │ │ → 文本变了 │ │ → 文本变了 │ │ → **ID 变了** │ │ → ID **不变** │ │ → 历史结果全部对不上 │ │ → 历史结果照样对得上 │ └────────────────────────┘ └────────────────────────┘ 内容哈希单独存一列 content_sha， 用来**检测**内容变化，而不是当 ID。

稳定 ID 的四条规则

  1. ID 分配一次，永不改变——哪怕内容被修正、被重写。
  2. ID 永不复用——删掉的样本，它的 ID 也退休，不能给新样本。复用 ID 会让历史结果指向一个完全不同的样本，这是最难查的一类污染。
  3. ID 里不编码可变信息——不要用 hard_billing_017 这种，因为「难度」和「所属子集」都会变；那些应该是元数据字段，不是 ID 的一部分。
  4. 同时存 content_sha——它不当 ID，但它是「这条样本的内容变过没有」的唯一可靠信号。

第 4 条带来一个很有用的能力：当你比较两个数据集版本时，可以精确地把变化分成四类——新增（ID 只在新版有）、删除（只在旧版有）、内容修改（ID 同但 content_sha 不同）、以及元数据修改（两个都同，但难度/标签变了）。这四类对「历史结果还能不能用」的影响完全不同——notebook 第 3 节会把这个 diff 器写出来。

3数据集版本：只增不改，以及三种变更的语义

模块 00 的反模式清单里有一条「就地修改任务集」。这一节讲替代方案。

\[\text{dataset} = (\text{id},\ \text{version},\ \text{sha}) \quad\text{三元组唯一确定一份任务集}\]

三种变更，三种版本语义

变更类型版本怎么走历史结果还能用吗典型场景
新增样本v1 → v1.1（次版本）能：旧样本的结果原样有效，只需补跑新增的扩充任务集
修改样本内容v1 → v2（主版本）该样本的历史结果作废，其余仍有效修正坏题、补充缺失信息
删除样本v1 → v2（主版本）该样本的历史结果保留但不再进入聚合剔除不可解的题（SWE-bench Verified 的做法）

直白说

为什么修改和删除都要走主版本？因为它们都改变了聚合分母。「v1 上 42%」和「v2 上 45%」这两个数字，如果 v2 剔除了 20 道最难的题，那么这 3 个点的提升可能完全来自分母的变化。主版本号的作用就是让这件事在文件名里就能看见，而不是藏在某次 commit 里。

严谨说

更精确地说，评测结果是一个定义在特定任务集上的量：$\hat{p}_{v} = \frac{1}{|D_v|}\sum_{i \in D_v} s_i$。当 $D_v \ne D_{v'}$ 时，$\hat{p}_v$ 与 $\hat{p}_{v'}$ 估计的是两个不同的总体参数，直接比较是无意义的。唯一可比的做法是在交集 $D_v \cap D_{v'}$ 上重算两边——这正是 notebook 第 4 节要实现的「交集重算」。

发现坏题时最诱人、也最错误的做法是「就把那道题改一下，反正只是一道」。后果是：所有引用过 v1 的历史报告，从此都指向一个不存在的东西——文件名说 v1，内容已经不是 v1 了。正确做法是发 v2，并且把 v1 保留为只读。存储成本几乎为零（任务集通常只有几 MB），换来的是历史的完整性。

坏题的三条处理路径

  • 剔除并发新版——最干净，SWE-bench Verified 走的就是这条；代价是分母变了，需要在交集上重算历史。
  • 保留但标记 excluded_from_main——样本还在，只是不进主指标。好处是历史分母不变，可以直接比较；坏处是需要在聚合逻辑里处理这个标记。
  • 修正内容并发主版本——适用于「题本身是好的，只是描述不全」。

推荐第二条作为默认：它对历史可比性的破坏最小，而且「为什么剔除」这个信息被保留在数据集里而不是某个 commit message 里。

4子集与切片：一份数据集，多种跑法

真实系统里，同一份任务集需要被以不同规模跑：CI 门禁要快（几十条），选型要全（几百条），而分析要能按维度切片。这些需求不应该靠拷贝出多份数据集来满足。

机制怎么做关键性质
元数据标签每条样本带 tags（难度、子系统、来源、创建时间）切片是查询，不是拷贝
命名子集spec 里声明 subset: "smoke"，由标签定义子集定义本身也要版本化
确定性抽样sample_n=50, sample_seed=0，用 ID 排序后取同 seed 必然抽到同一批——这是可复现的前提
分层抽样按标签分层，每层保底 N 条小类不会被抽没（呼应 C66-01 的信息量分析）

确定性抽样有一个比想象中更深的坑，值得把话说透：只要你固定抽样数量 N，任务集增长时，抽中的那批就必然会变。这不是实现问题——「从 46 条里抽 15 条」和「从 246 条里抽 15 条」本来就是两个不同的均匀样本，原有样本被挤出去是数学上必然的。唯一真正稳定的做法是按比例选而不是按数量选：include = int(hash(task_id), 16) % 1000 < rate * 1000。这样已有样本的入选与否永远不变，新增样本只是按同样的比例被纳入。notebook 第 5 节会把三种做法的稳定性对比出来。

固定数量 vs 固定比例：该选哪个

需求该用理由
CI smoke 子集固定比例 + 分层保底membership 稳定，分数波动才能被归因到模型而不是「换了一批题」
「我只有 20 分钟预算」固定数量接受 membership 会变，但要在报告里注明抽样是变化的
调试单条样本显式列 ID不抽样

smoke / full 两档是最常见的配置

smoke 子集（30–80 条，覆盖各类型各一点，跑几分钟）用于 CI 每次提交；full 集（全量，跑几小时）用于合并前或每日定时。smoke 的设计目标不是「准确估计分数」，而是「抓住明显的退化」——所以它的抽样应当偏向覆盖度而不是代表性：每个子系统、每种难度都要有，哪怕各只有两三条。

5Schema 演化：只增字段、给默认值、写迁移器

spec 的字段一定会变——加新参数、拆旧字段、改语义。这一节讲怎么让它变得不痛。

  1. 只增字段，不改语义。把 timeout 从「秒」改成「毫秒」是最坏的一类变更——旧 spec 依然能解析，但含义变了，而且不会报错。需要改语义时，加一个新字段并废弃旧的。
  2. 新字段必须有默认值，且默认值要让旧 spec 的行为保持不变。例如新增 retries 时默认设为 0（而不是 2），否则所有历史 spec 的语义都被悄悄改了。
  3. spec 自带 schema_version，并写一个 migrate(spec) 函数把旧版本升到当前版本。迁移必须是纯函数且幂等：migrate(migrate(x)) == migrate(x)。
  4. 指纹在迁移后计算——否则同一个语义的 spec，旧格式和新格式会算出不同的指纹，历史结果又对不上了。

第 4 条是个容易忽略但很关键的细节。指纹应该是「规范化之后的 spec」的哈希，而不是「用户写的那份 spec」的哈希。规范化包括：迁移到当前 schema、填上所有默认值、把等价的写法归一（比如 1 与 1.0）。这样「显式写了默认值」和「没写」会算出同一个指纹——这正是你想要的语义。

向后兼容的一个反例

# ❌ 危险的变更：新字段的默认值改变了旧 spec 的行为
# v1 的 spec 没有 retries 字段，当时的行为等价于 retries=0
{"budget": {"timeout_s": 30}}

# v2 加了 retries，默认值设成 2
DEFAULTS = {"retries": 2}          # ← 所有历史 spec 的错误率都被悄悄改了

# ✓ 正确：默认值保持旧行为，需要重试的显式写出来
DEFAULTS = {"retries": 0}

6数据集也要有一张卡：来源、构造、已知缺陷

最后一节讲一个经常被跳过、但半年后必然后悔没做的东西：给任务集配一份说明（datasheet）。

它要回答的问题很具体——都是「半年后有人会问、而当时的人已经离职」的那些：

问题为什么会被问到不记的后果
样本从哪来评估污染风险（C66-01）无法判断分数是不是被污染撑起来的
创建/采集时间做时间截断检验污染检测最有力的手段直接用不了
谁标注的、标注规范是什么怀疑标签质量时要追溯只能重新标一遍
已知坏题清单「这道题为什么被剔除」同一道坏题被反复发现、反复讨论
不可能任务的比例解读「放弃率」这个指标把正确的放弃误判成失败（C66-01）
判分器与它的 α/β校正观测值（C66-02）所有数字都可能是系统性偏的
预期的合理分数区间判断「跑出 95%」是好消息还是 bug最容易被忽略、也最实用的一条

最后一行值得展开：给每个任务集写一句「合理的分数应该落在哪个区间」，是一条极其便宜的健康检查。如果一个预期 30–50% 的任务集突然跑出 95%，那几乎肯定是流水线出了问题（判分器坏了、答案泄漏进 prompt 了、或者任务集被换成了 smoke 子集），而不是模型突然变强了。这条检查在 CI 里就是一行断言（04 模块）。

datasheet 应当和数据集放在一起并一起版本化——放在 wiki 里的说明，三个月后必然与数据集脱节。

  subsets/
    smoke.json             # {"name":"smoke","filter":{"tags":["core"]},"sample_n":60,"seed":0}

spec/
  demo-qa.json             # 引用 dataset id+version+sha，不内联任务内容
  • frozen: true 是一条硬约束：已发布的版本目录设为只读，CI 里加一条检查——已冻结版本的 sha 与 MANIFEST 不一致就直接失败。
  • CHANGELOG 要逐条记理由，尤其是剔除的那些。「为什么剔除这道题」是最容易丢失、也最容易被重复讨论的信息。
  • spec 不内联任务内容，只引用 (id, version, sha)。内联会让 spec 变得巨大且无法 diff。
  • 子集定义是独立文件且要版本化——改了 smoke 的定义，等于换了一个任务集。

最后强调一遍本模块的核心纪律，因为它是所有后续模块的地基：任务集只增不改；改了就发新版本；已发布的版本永远只读。违反这一条的代价不是「不够规范」，而是「所有历史数字失去意义」——而这件事发生时不会有任何报错。

8谁来写任务：三种来源与各自的偏倚

补一个模块 01 之前没说的问题：这些任务是谁写的，以及这件事怎么影响结果。

来源怎么产生系统性偏倚该怎么标注
人工构造工程师/领域专家按经验写偏向「已知的失败模式」——写题的人写的是他想到的问题source: manual
线上回灌从真实流量的问题样本转化（模块 05）偏向模型的弱项，占比过高会让任务集漂成疑难杂症集source: from_production，且设占比上限
公开基准直接引入污染风险最高（C66-01）；分类体系可能与你的产品定义不一致source: public + 原始基准的版本
合成生成用模型批量造题偏向生成模型自己擅长的形态；难度分布过于集中source: synthetic + 生成配置的哈希
source 这个字段的价值在于它让上面这些偏倚变得可分析。「这次提升主要来自 from_production 的那批题」和「主要来自 manual 的那批」，是两个完全不同的结论——前者说明修好了真实问题，后者可能只是拟合了写题人的偏好。而没有这个字段，这两种情况在数据里长得一模一样。

合成任务还有一个特有的要求：生成配置必须被记录并版本化（用什么模型、什么 prompt、什么参数生成的）。否则你无法回答「这批合成题为什么和上批不一样」——而这正是本课模块 00「可归因性」在数据侧的同一条要求。

9多数据集与组合评测：一次运行跑多个任务集

真实系统里很少只有一个任务集。典型的配置是「核心能力集 + 安全集 + 回归集 + 线上回灌集」四个一起跑。这带来两个模块 01 之前没处理的问题：怎么聚合、怎么版本化。

问题一：跨数据集怎么聚合

方式怎么算适合陷阱
不聚合每个数据集单独报一个数推荐默认读者需要自己综合，但这是诚实的
等权平均各数据集分数取平均各集重要性相当时小数据集的噪声被放大到与大数据集同权
按样本量加权等价于把所有样本合并求 micro各集来自同一分布时大数据集主导总分（C66-02 的 micro 陷阱）
按业务重要性加权人为指定权重对外报告一个数时权重来源必须写进报告，否则不可复现
「不聚合」应当是默认选择，理由和 C66 模块 02 的 micro/macro 讨论一致：把安全集的 98% 和核心能力集的 43% 平均成 70.5%，这个数字既不能用来判断能力，也不能用来判断安全。如果一定要一个总分（比如给管理层看），那么权重必须显式写出来，并且要做敏感性分析——权重扰动 ±20% 会不会翻转结论（呼应 C67-01 的 rubric 权重）。

问题二：组合的版本化

每个数据集有自己的版本，那么「这次跑的是哪个组合」也需要一个版本：

  • suite 的指纹 = 各数据集三元组 + 聚合方式的哈希——换掉任何一个子集的版本，suite 版本就要走；
  • 子集之间的样本 ID 必须全局唯一：如果 core-tasks 和 regression 里都有 t001，结果表的主键就会冲突。实践做法是给 ID 加数据集前缀（core:t001）；
  • 回归集是一个特殊的子集——它由线上回灌构成（模块 05），只增不删，而且它的分数应当接近 100%（因为都是已经修过的问题）。回归集的分数下降是一个比总分下降严重得多的信号。

一个实践细节：数据集之间会有重叠

组合评测里一个容易被忽略的问题：同一道题可能同时出现在两个数据集里——线上回灌的问题被加进了回归集，而它恰好也被人工加进了核心能力集。如果两边用了不同的 task_id，这道题会被算两遍；如果用了同一个 ID，结果表的主键就会冲突。

正确处理：在 suite 层面做一次去重检查，并显式声明「同一道题归属哪个集」。推荐的归属规则是「最严格的那个集优先」——同时出现在核心集与回归集时归回归集，因为回归集的门禁更严（下一段），归到那边不会漏掉问题。

最后一条值得展开：回归集的语义与其他集完全不同。核心能力集问「能做到多少」，回归集问「有没有把修好的又弄坏」。前者的分数是 40% 也很正常，后者掉到 95% 就该拉警报——所以它们的门禁阈值也应当完全不同（模块 04）。把它们平均成一个数，等于同时毁掉两个信号。
