1从「一次性脚本」到「基础设施」：分界线在哪

C66 与 C67 回答的是「评什么、怎么算才对」。这门课回答下一个问题：当这套评测要被跑几百次、被十个人跑、被跑一年，它需要长成什么样。

先划清一条线：并不是所有评测都需要基础设施。一次性的探索实验，用一个脚本跑完就删掉，是完全正确的做法。值得投入基础设施的判据只有一个——这套评测会不会被重复跑。

场景会被跑几次一次性脚本够不够真正的成本在哪
探索一个新想法1–3 次够写基础设施的时间超过它节省的时间
模型选型10–30 次（几个候选 × 几个配置）勉强手工记录配置、事后拼不回「那次是怎么跑的」
CI 回归门禁每次提交完全不够误报会让团队关掉门禁；漏报会让退化上线
线上质量监控持续完全不够离线指标与线上表现脱节而没人发现
长期能力追踪每周/每月，持续一年以上完全不够半年后没人说得清历史数字是怎么来的

直白说

一个判断标准比「跑几次」更准：「如果这次结果和上次不一样，你能在十分钟内说清楚为什么吗？」答不上来，就说明你需要基础设施——不是为了跑得更快，而是为了让「结果变了」这件事变得可解释。C66 模块 05 的 harness 指纹已经埋下了这个种子，本课把它长成完整的系统。

严谨说

更形式化地说，评测基础设施要保证三个性质：① 确定性（同样的输入与配置产生同样的输出，或至少产生同分布的输出）；② 可归因性（任何两次运行的差异，都能被归因到某个显式记录的配置项）；③ 幂等性（重跑不会破坏已有结果，中断后能续跑）。这三条是本课全部工程决策的来源——缓存设计、结果存储的主键、CI 门禁的阈值，都是在服务这三条。

反过来说一句同样重要的话：不要在探索期就上基础设施。评测的定义在早期变化极快（任务集在改、判分器在改、指标口径在改），过早固化的 schema 会把这些变化变成迁移成本。正确的时机是：当你第三次手工重复同一件事的时候。

2四层架构：spec / runner / store / report

几乎所有成熟的评测系统都会收敛到同一个四层结构。把它画出来，本课后面五个模块就是这四层各自的展开。

┌──────────────────────────────────────────────────────────────┐ │ ④ REPORT 报告层 │ │ 切片、对比、置信区间、评测卡、趋势图 │ │ → 03 模块（分析）· 04 模块（CI 门禁）· 05 模块（线上看板） │ ├──────────────────────────────────────────────────────────────┤ │ ③ STORE 结果层 │ │ 每条结果一行；主键 = (run_id, task_id, attempt) │ │ 幂等写入、可续跑、可回溯 │ │ → 03 模块 │ ├──────────────────────────────────────────────────────────────┤ │ ② RUNNER 执行层 │ │ 并发、限流、重试、超时、缓存、断点续跑、预算熔断 │ │ → 02 模块 │ ├──────────────────────────────────────────────────────────────┤ │ ① SPEC 声明层 │ │ 任务集是什么 · 怎么跑 · 怎么判分 · 版本与哈希 │ │ **纯数据，不含执行逻辑** │ │ → 01 模块 │ └──────────────────────────────────────────────────────────────┘
层职责关键约束做错的后果
① SPEC声明「评什么、怎么判」纯数据、可序列化、可哈希；不含执行逻辑配置散落在代码里 → 无法比较两次运行的差异
② RUNNER把 spec 变成结果幂等、可中断续跑；所有失败可分类跑一半崩了要全部重来；成本失控
③ STORE存结果只追加、主键唯一；结果不可变重跑覆盖了历史；无法回答「上周是多少」
④ REPORT把结果变成结论与 C66/C67 的统计规范一致报告出错误的数字（本课不重复讲，直接复用前两课）

四层里最容易被合并的是 ① 和 ②——「反正都是我写的代码，配置直接写在脚本里就好了」。这是所有后续问题的根源：配置写在代码里，就无法被哈希、无法被比较、无法回答「这两次运行到底差在哪」。把 spec 抽成纯数据，是本课投入产出比最高的一个结构决策——它直接让 C66 模块 05 的运行指纹变成可能。

3三个性质：确定性、可归因性、幂等性

第 1 节的 DUAL 里提到了三个性质。它们不是抽象的工程美学，而是每一条都能翻译成具体的代码约束。

确定性：不是「结果一样」，而是「差异可解释」

LLM 评测天然带随机性（采样温度、环境抖动、judge 的不稳定），所以「两次跑出同样的数字」通常做不到。可实现的目标是：把随机性收拢到少数几个显式的来源，并让这些来源可控（seed）或可测（重复运行的方差）。

随机源能不能消除怎么处理
模型采样能（temperature=0）或部分能（固定 seed，若 API 支持）报告里必须写明温度与 seed
任务顺序 / 并发调度能结果按 task_id 排序后再聚合，不依赖完成顺序
外部环境（网络、容器、时钟）部分能录制回放；容器 digest；把时间相关的输入固定
judge / 用户模拟器部分能固定模型与温度；swap 双跑（C67-02）

可归因性：任何差异都能指向一个配置项

这条的实现就是 C66 模块 05 的运行指纹，本课把它从「一个应该做的事」变成「架构上必然做到的事」——因为 spec 是纯数据，指纹就是它的哈希，不需要人去维护一份清单。

幂等性：重跑不破坏，中断能续

\[\text{run}(\text{spec}, \text{store}) \circ \text{run}(\text{spec}, \text{store}) = \text{run}(\text{spec}, \text{store})\]

实现方式很简单，但必须一开始就做对：每条结果的主键是 (run_id, task_id, attempt)，写入前先查在不在，在就跳过。这一条同时解决了三个问题——中断续跑、部分重跑、以及「不小心跑了两次」。

幂等性带来一个不那么明显但很重要的好处：它让「增量扩样本」变成一个安全操作。任务集从 300 条加到 500 条时，你只需要用同一个 run_id 再跑一遍——已完成的 300 条会被跳过，只跑新增的 200 条。没有幂等性的话，这个操作要么重跑全部（浪费），要么手工挑出新增的（容易错）。

5环境、依赖与本课的运行约定

本课全程 CPU、断网可跑、不需要任何 API key，而且比前两课更彻底——因为基础设施的正确性本来就不该依赖真实模型。

  • 被评的「模型」是一个可控的假函数：给定输入返回确定或带受控随机性的输出，并且可以人为注入失败（超时、限流、格式错误）。这比真实 API 更适合验证 runner 的正确性——你可以精确控制第几次调用会失败。
  • 存储是本地 JSONL / SQLite（标准库自带），所有幂等性、并发、续跑的逻辑都能在上面完整验证。
  • 真实接入（inspect-ai 的 task 定义、OpenTelemetry 埋点、CI 配置、Prometheus 告警规则）放在每个模块末尾的「🧪 真实工程胶囊」里。

6六个反模式：它们都不会报错

最后用一份反模式清单收尾。它们的共同点是不会抛异常——代码照跑，数字照出，只是那些数字不再意味着你以为的东西。

反模式表面上实际后果本课哪里解决
配置写在代码里省事无法比较两次运行的差异；无法生成指纹01：spec 是纯数据
就地修改任务集「就改一道坏题」所有历史分数一夜之间失去意义01：只增不改，发新版本
用行号或哈希内容当样本 ID不用另外维护 ID改一个错别字，样本 ID 就变了，历史结果对不上01：稳定 ID
缓存里不含配置指纹缓存命中率高改了 prompt 却读到旧结果——最隐蔽的一个02：缓存键设计
失败样本直接跳过报告看起来干净分母变小，成功率虚高（与 C67-01 的解析失败同构）02：失败必须分类并计入
CI 门禁阈值拍脑袋定「掉 2% 就报警」噪声不断误报 → 团队关掉门禁 → 门禁形同虚设04：用重复运行的方差定阈值

第四条值得单独强调，因为它是本课里最贵、最难查的一个 bug：缓存键里如果不包含 judge prompt / 模型 ID / 采样参数的指纹，那么你改了 prompt 之后再跑，会安静地读到旧结果。症状是「我明明改了 prompt，分数却一点没变」，而很多人会把它误读成「这个改动没有效果」。规则：缓存键 = 输入内容哈希 + 完整配置指纹，缺一不可。

这六条会在后面五个模块里被逐一解决。notebook 的最后一节给出一个自检器：把你现有的评测流程按这六条打分。

7谁来维护：基础设施的所有权与腐化

最后一节讲一个技术之外、但决定成败的问题：这套东西归谁管。评测基础设施有一个特殊的组织属性——它服务所有人，因此很容易不属于任何人。

所有权模式怎么运作典型腐化方式适合什么阶段
无主谁需要谁改配置漂移：每个人加自己的分支逻辑，半年后没人说得清默认行为是什么只在最早期可接受
兼职维护某个人「顺便」维护知识单点：那个人休假时没人能改；他离职时系统冻结小团队的现实选择
平台化有专门的人/小组，其他人通过 spec 使用脱节：平台团队不知道使用者的真实需求，加的功能没人用评测成为多团队共享设施之后
共享代码 + 明确 owner任何人可提 PR，但有明确的 review 责任人较慢，但腐化最少多数团队的推荐形态

直白说

腐化的具体形态几乎总是同一个：有人为了赶一次实验，在 runner 里加了一个「临时」的 if 分支，然后它永远留在了那里。三个月后，没人知道这个分支在什么条件下触发，也没人敢删——而它可能正在悄悄改变某些运行的行为。

严谨说

从架构的角度，防腐化的机制其实已经内置在本课的设计里了：如果所有会影响结果的配置都必须进 spec，那么「在代码里加一个临时分支」这件事在结构上就是被禁止的——因为那个分支的行为不会进入指纹，而 CI 里那条「同指纹的两次运行结果不该差太多」的检查会把它暴露出来（模块 00 第 4 节的告警）。换句话说，「spec 是纯数据」这条设计不只是为了可比性，也是一条组织层面的防腐化约束。

三条低成本的维护纪律

  • 任何新增的配置项必须有默认值，且默认值保持旧行为（模块 01）——这让「加功能」不会破坏别人的历史数据；
  • runner 里不允许出现 if os.environ.get(...)——环境变量是配置的暗门，它绕过了 spec，因此绕过了指纹；
  • 每季度跑一次「反模式自检」（本模块 notebook 第 6 节），把腐化变成一个可以被看见的分数，而不是一种感觉。

一条判断基础设施是否健在的简单测试：随便找一个三个月前的运行结果，问「我能不能今天原样复现它」。如果答案需要「问一下当时跑的人」，那么这套基础设施已经在腐化了——而这个测试只需要五分钟，值得每季度做一次。
