1云的抽象：三件套与它们的计价单位

前四个模块都在讲「怎么做」。这一模块讲「在谁的机器上做、花多少钱」——这是把技术方案变成可执行方案的最后一步，也是研究工程师最容易被卡住的一步（方案很漂亮，但一算钱发现做不了）。

剥掉所有产品名词，云只有三样东西，而且每样的计价单位都不同——这个差异是所有成本优化的起点：

抽象是什么计价单位关键陷阱
计算虚拟机 / 容器 / 函数时间（秒·实例）闲着也全额计费；GPU 实例的最小计费粒度可能是分钟甚至小时
存储对象存储 / 块存储 / 文件系统容量 × 时间 + 请求次数小文件的请求费可能超过存储费；块存储必须挂在实例上才计费但删了实例它还在
网络出网 / 跨区 / 跨可用区字节（几乎只对出方向收费）最容易失控的一项；跨可用区流量在很多云上也收费

直白说

记住这条不对称：进云免费、出云收费；同区便宜、跨区贵、出公网最贵。这一条就能解释云架构里大量看似奇怪的设计——为什么模型权重要放在和 GPU 同一个区域、为什么要做节点本地缓存（模块 01）、为什么日志不该无脑全量传到另一个区。

严谨说

严格地说，成本模型是 C = Σ_i (unit_price_i × quantity_i)，优化就是压 quantity 或换更便宜的 unit_price。压 quantity 的手段是前四个模块的全部内容（更小的镜像、更高的装箱率、更准的扩缩）；换单价的手段是本模块的内容（spot、预留、区域选择、实例类型）。两条路径要一起走，但顺序上先压 quantity——因为便宜单价 × 巨大用量，仍然是巨大账单。

一个几乎所有团队都踩过的坑：出网流量费的隐形。GPU 账单是显眼的、被反复盯着的；数据传输费散落在账单各处（S3 GET、跨 AZ、NAT 网关、负载均衡器处理字节数），单条都不大，加起来可能占总账单的 15–30%。模块 01 算过的「20 副本拉 140 GB 权重 = $252 一次」就是典型。第一次做云成本分析时，务必按「服务」和「费用类型」两个维度都切一遍，你大概率会在网络那一栏发现惊喜。

2对象存储：模型权重的家

LLM 部署里，对象存储（S3 / GCS / OSS）承担一个特定角色：模型权重的唯一真相源。它的几个性质直接决定了你的部署方案。

性质含义对 LLM 部署的影响
扁平命名空间没有真正的「目录」，只有 key 前缀权重按 models/<name>/<sha256>/ 组织，用内容哈希做版本（模块 01）
读后写一致性现代对象存储对新对象是强一致的（S3 自 2020 起）上传完立刻能读到，不用再写「等一会儿」的重试逻辑
不可变更新对象是整体替换，没有原地追加/修改「换模型」= 写一个新 key，而不是覆盖旧 key。这天然给你回滚能力
单连接带宽有限单个 GET 通常几百 MB/s 封顶拉 140 GB 必须分片并发下载（aws s3 cp 默认就做，自己写要注意）
请求计费每次 GET/LIST 都收费safetensors 分片成几百个小文件时，请求费和延迟都会显现

有两个具体决策值得记住：

  • 权重必须和 GPU 在同一区域（region）。跨区拉取不仅慢（延迟 + 带宽），还产生每 GB 的传输费。「同一个 bucket 服务全球集群」是个诱人但昂贵的错误——正确做法是每个区域一份副本，用跨区复制（CRR）同步。
  • 用内容哈希而不是可变标签做 key。models/llama3-8b/latest/ 这种 key 会让你无法回答「三天前那个副本加载的是什么」。用 models/llama3-8b/sha256-abc…/，再用一个小的 manifest 文件记录「当前 latest 指向哪个哈希」——这样 latest 的变更本身是可追踪、可回滚的。

把对象存储想成一个巨大的、按字节收租的、只能整存整取的 KV 存储。它不是文件系统——没有 rename（是 copy+delete，140 GB 的 rename 会真的复制 140 GB）、没有 append、没有 POSIX 语义、LIST 是分页且昂贵的。所有把它当文件系统用的方案（比如 s3fs 挂载后让 torch 直接从上面 load）都会在规模上暴露问题。正确用法是显式的「下载到本地 → 从本地加载」。

3实例选择与 spot 经济学

这一节是本模块最有直接经济价值的部分：什么时候该用 spot（抢占式）实例。

云厂商把闲置容量以 60–90% 的折扣卖出，代价是可能被随时收回（通常给 30 秒到 2 分钟的通知）。问题是：这笔账什么时候划算？

期望成本模型

设按需价 p_od、spot 价 p_spot、单位时间中断概率 h（hazard rate）、一次中断的恢复成本 c_int（重启 + 重新加载 + 丢失的进行中工作）。每小时的期望成本：

\[\mathbb{E}[C_{spot}] = p_{spot} + h \cdot c_{int}, \qquad \text{spot 划算} \iff p_{spot} + h\cdot c_{int} < p_{od}\]

由此得出盈亏平衡的中断率：

\[h^* = \frac{p_{od} - p_{spot}}{c_{int}}\]
工作负载c_int（一次中断损失）适合 spot？为什么
离线批量推理（可断点续跑）低：只丢一个分片的进度✅ 非常适合中断成本几乎为零，折扣是净赚
预训练（有 checkpoint）中：丢失上次 checkpoint 后的进度 + 重启全部 rank🔶 视 checkpoint 频率而定C39 的容错工程决定了 c_int；同步训练里一个 rank 挂 = 全体重来
在线推理（面向用户）高：用户请求失败 + 容量缺口 + 冷启动 3 分钟❌ 不适合单独用SLO 与错误预算的代价远超省下的钱
在线推理（spot + 按需混合底座）低：按需底座保底，spot 只做弹性部分✅ 标准做法把「必须有」和「多多益善」分开定价

直白说

最后一行是工业界的标准答案，值得展开：把容量分成「基线」和「弹性」两层。基线（覆盖 P50 流量）用按需或预留实例，保证 SLO 的下界；弹性（P50 以上的部分）用 spot，被收回了只是容量少一点、退化到基线，不至于服务不可用。这个组合能拿到 spot 大部分的折扣，同时把风险控制在「性能降级」而不是「服务中断」。

严谨说

工程上还要配三件事：①处理中断通知——监听云的抢占事件（AWS 的 ITN、GCP 的 preemption notice），收到后立刻走模块 01 的优雅停机流程（摘流量、排空）。这两分钟足够放完在途请求。②多样化实例池——不要把所有 spot 押在同一个实例类型/可用区上，容量池相关性会让它们同时被收回。③容量上限与回退——spot 拿不到时能自动回退到按需，而不是无限重试。

除了 spot，还有两种降价手段值得一提，它们的取舍很不一样：

  • 预留实例 / Savings Plan：承诺 1–3 年用量，换 30–60% 折扣。适合确定长期存在的基线容量。风险是锁定——GPU 迭代很快，锁 3 年 A100 可能在第二年就不划算了。对 GPU 通常建议 1 年而非 3 年。
  • Committed use / 阶梯定价：按承诺的消费额度打折，比预留实例灵活（不绑定具体机型）。对快速演进的 GPU 栈更友好。
spot 中断是相关的，不是独立的

一个必须提前想到的相关性风险：spot 的中断不是独立事件。当整个区域的容量紧张时（比如某个大客户突然扩容、或者某个新模型发布引发全行业抢卡），你的所有 spot 实例可能在几分钟内被同时收回。如果你的弹性层全是 spot 且占了 70% 容量，这一刻就是一次全面的容量崩塌。设计时要问「如果全部 spot 同时消失，我还剩多少容量、够不够撑住 P50 流量」——这个问题的答案决定了基线层该配多大。

4作业调度：K8s Job vs Slurm vs Ray 三种世界观

在线服务用 K8s Deployment（模块 03）。但研究工程师大量的工作是离线作业：跑评测、批量推理、微调、超参搜索。这类工作有完全不同的调度需求，也发展出了三套不同的系统。

Kubernetes JobSlurmRay
出身云原生 / 微服务HPC / 超算中心分布式 Python / ML
核心抽象Pod + 容器作业（job）+ 分区（partition）+ 节点task / actor + 对象存储
资源申请声明式 YAML，requests/limitssbatch --gres=gpu:8 --nodes=4@ray.remote(num_gpus=1) 装饰器
排队与公平需插件（Volcano/Kueue）内置且成熟：优先级、QoS、fairshare、backfill内置基础调度，公平性较弱
gang scheduling需插件原生（分布式训练的默认预期）placement group
交互性弱（面向长期运行的服务）srun 可交互强：Python 里直接起分布式任务
适合在线服务、CI、云原生批处理大规模训练集群、学术/企业超算Python 生态的分布式实验、RL、超参搜索

直白说

三者不是竞争关系，很多组织同时用：K8s 跑在线服务，Slurm 跑训练，Ray 跑实验和数据处理。选哪个主要看你的机器归谁管——如果你在一个有共享 GPU 集群的组织里，那大概率是 Slurm（这是超算界几十年的标准）；如果你在一个云原生团队，那就是 K8s + Kueue/Volcano；如果你在做 RL 或大规模超参搜索，Ray 的编程模型会让你快很多。

严谨说

关键的技术差异在调度粒度与排队语义。K8s 的调度器是为「长期运行的服务」设计的：Pod 一旦调度就假定长期存在，没有内置的排队公平性和 backfill。Slurm 是为「有明确开始和结束的作业」设计的：它天然理解「这个作业要 4 节点跑 6 小时」，因此能做backfill（在等待大作业攒够资源的空隙里插入短小作业，显著提高利用率）和 fairshare（按历史用量调整优先级）。把长作业塞进 K8s 而不加调度插件，通常会得到很差的集群利用率。

Slurm 的最小心智模型

作为研究工程师，Slurm 是你最可能天天用、却从没系统学过的东西。它的核心只有几个概念：

#!/bin/bash
#SBATCH --job-name=sft-llama8b
#SBATCH --partition=gpu-h100        # 分区 = 一组机器 + 一套策略（时长上限、优先级）
#SBATCH --nodes=4                   # 要 4 台机器
#SBATCH --ntasks-per-node=8         # 每台起 8 个任务（对应 8 张卡）
#SBATCH --gres=gpu:8                # 通用资源：每节点 8 张 GPU
#SBATCH --cpus-per-task=12
#SBATCH --time=12:00:00             # 时限；**越短越容易被 backfill 提前调度**
#SBATCH --output=logs/%x-%j.out     # %x=job name, %j=job id
#SBATCH --requeue                   # 被抢占后自动重排队（配合 checkpoint）

srun python train.py --config configs/sft.yaml

# 常用命令
#   sbatch  train.sh        提交
#   squeue -u $USER         看自己的队列（ST 列：PD=排队 R=运行 CG=收尾）
#   scancel <jobid>         取消
#   sinfo -p gpu-h100       看分区里有多少空闲节点
#   sacct -j <jobid>        看历史作业的资源使用与退出码
#   scontrol show job <id>  看排队原因（Reason 字段：Priority / Resources / QOSMaxJobs…）

关于 Slurm 有一条极其实用、但很少有人明说的经验：--time 填得越准（越短），你排队等得越少。因为 backfill 调度器会在「等大作业攒资源」的空隙里，插入那些「声明时长足够短、能在空隙内跑完」的作业。你填 --time=48:00:00 图保险，结果永远排在队尾；填 --time=3:00:00（真实需要 2.5 小时），可能立刻就跑上了。代价是超时会被强杀，所以要配合 checkpoint 与 --requeue。

5多区域、容灾与数据合规

单区域部署有两类风险：可用性（区域级故障，虽罕见但发生过）和延迟（跨洲用户的网络往返就有几百毫秒）。多区域是解法，但它的成本远不止「乘以 N」。

维度单区域多区域增量成本来源
GPU 容量按峰值配每个区域都要有基线容量无法跨区共享池 → 总容量必须超过全局峰值
权重存储一份每区一份 + 跨区复制存储 × N + 复制流量
运维复杂度一套N 套配置、N 套发布流水线人力（最贵的一项）
流量路由简单GeoDNS / Anycast / 全局负载均衡额外组件与调试难度

务实的建议是分阶段：先做单区域多可用区（multi-AZ，模块 03 的拓扑分布），这能挡住绝大多数硬件与机房级故障，成本增量很小；只有当你的用户真的跨洲、或者 SLO 真的要求抗区域级故障时，才上多区域。「万一某个区挂了」在大多数业务上并不值那笔钱。

数据合规：一个绕不开的约束

对 LLM 服务，数据出境是个真实的法律约束而不只是技术选择。用户的对话内容可能包含个人信息，很多司法辖区（欧盟 GDPR、中国的数据出境规定、各行业的本地化要求）限制它被传输到境外。这会强制你的架构：

  • 推理必须在数据所在地完成——意味着每个受管辖区域都要有完整的部署，不能「统一送回总部的大集群」。
  • 日志与遥测也受约束——请求内容不能进集中式日志系统。常见做法是「本地存原文、只把脱敏后的指标外发」。
  • 模型权重的流向通常不受限（它不含用户数据），所以权重可以从一个地方分发到各区域。这是多区域部署里唯一简单的部分。

一个容易被忽略的合规细节：用户对话默认不该进训练数据。很多团队会顺手把线上流量存下来「以后做微调用」，这在多数司法辖区需要明确的用户同意，而且一旦混进训练集就很难剥离（模型已经记住了）。数据留存策略应该在服务上线之前就定下来，而不是事后补救。这条和 C12（负责任 AI）、C45（隐私与可信 ML）直接相关。

6单位经济：$ / 1M token 的完整分解

最后把前五个模块的所有决策，汇聚成研究工程师最该会算的一个数字：每百万 token 的成本。它是和产品、财务、老板沟通的唯一共同语言。

\[\text{\$/1M tok} = \frac{p_{node} }{ \underbrace{T_{peak}}_{\text{峰值吞吐}} \times \underbrace{u}_{\text{平均利用率}} \times \underbrace{\eta}_{\text{装箱率}} \times 3600 / 10^6 }\]
因子由谁决定典型值提升它的手段
p_node 单价云选型、spot/预留$32/h（8×H100 按需）spot（−70%）、预留（−40%）、换区域
T_peak 峰值吞吐C24/C27 推理引擎与量化4000 tok/scontinuous batching、FP8/INT4、投机解码
u 平均利用率模块 04 自动扩缩 + 流量曲线0.35–0.65自动扩缩、混部离线任务填谷
η 装箱率模块 03 调度策略0.5–0.85装箱调度、减少反亲和约束、统一实例规格

这个分解的价值在于它告诉你优化该往哪儿使劲。很多团队的直觉是「买更快的卡」或「优化 kernel」（提高 T_peak），但如果你的 u 是 0.3、η 是 0.5，那么把这两项提上去的收益，远大于把吞吐再榨 20%——而且便宜得多。

同一套硬件，四个因子的复合效应： 最差配置: $32 / (4000 × 0.25 × 0.50 × 3600/1e6) = $17.8 / 1M tok 典型配置: $32 / (4000 × 0.45 × 0.70 × 3600/1e6) = $7.05 / 1M tok 优化配置: $32 / (5500 × 0.65 × 0.85 × 3600/1e6) = $2.93 / 1M tok 优化+spot: $10 / (5500 × 0.65 × 0.85 × 3600/1e6) = $0.92 / 1M tok 最差 → 最优 = 19 倍。**没有一项来自「换更好的 GPU」。**

直白说

这张对比表是本课的最终论点：部署工程的复合收益，和模型优化的收益是同一量级甚至更大的，但它几乎不需要研究突破，只需要把每个环节做对。镜像小一点（模块 01）、容量算准一点（模块 02）、装箱好一点（模块 03）、扩缩稳一点（模块 04）、单价选对一点（模块 05）——每项 20–40%，乘起来就是一个数量级。

严谨说

但要诚实地标注这个模型的边界：T_peak 依赖具体模型、序列长度分布与引擎版本，必须靠压测标定；u 依赖真实流量曲线，不同业务差异巨大；spot 的 $10/h 是乐观值且不保证可得。把这个公式当成「分解归因的框架」而不是「报价单」——它的用途是回答「我该优化哪一项」，而不是「我明年要花多少钱」。后者需要用你自己的实测数字重算一遍。

把整门课浓缩成一句话：LLM 部署不是「把模型放上线」这一个动作，而是一条由镜像、契约、编排、发布、成本五个环节组成的链路；每个环节的决策都会以乘法的方式影响最终的可靠性与单位成本。这就是为什么「模型很好但上不了线」和「上线了但烧钱烧不起」是两个如此普遍的故事——它们卡的不是任何单点的难题，而是这条链路上若干个「看起来无所谓」的默认选项。

7研究前沿与开放问题

  • 异构与碎片化的算力市场：H100/H200/B200/MI300/TPU/自研 NPU 并存，加上 neocloud（CoreWeave、Lambda 等）与去中心化算力市场，「同一个模型该跑在哪种卡上最便宜」变成了一个持续的优化问题。跨厂商的性能-价格自动选型工具仍很原始。
  • 训练与推理的混部：推理集群在流量低谷有大量闲置 GPU，训练/评测作业正好可以填谷。但两者的 SLO 差异巨大（推理要低延迟、训练要长时间独占），抢占策略、显存隔离、checkpoint 频率的协同设计还没有成熟方案。这是当前最大的一块「地上的钱」。
  • 碳感知调度：不同区域、不同时段的电网碳强度差几倍。把作业调度到低碳时段/区域（carbon-aware scheduling）在延迟不敏感的批处理上完全可行，但与成本、容量的多目标权衡缺乏公认框架。
  • 成本归因的粒度：多租户共享 GPU 集群里，「这个业务方该分摊多少 GPU 成本」在技术上很难算准（共享 KV 缓存、批处理让请求间成本互相纠缠）。公平的多租户计量与计费模型仍是开放问题。
  • Slurm 与 K8s 的融合：研究组织普遍同时拥有两套集群，资源无法共享。Kueue、Volcano、Slinky（Slurm on K8s）、Ray on Slurm 等都在尝试打通，但排队语义、gang scheduling、公平性模型的差异让融合并不平凡。

必读：AWS/GCP 的 spot 实例最佳实践文档（中断处理与多样化池的官方指南）、Slurm 官方 Quick Start 与 Backfill Scheduling 文档（比任何二手教程都清楚）、Ray 的 Architecture Whitepaper、FinOps Foundation 的成本分摊框架、Patterson et al. 2021 Carbon Emissions and Large Neural Network Training（算力的碳账）。工程对标：SkyPilot（跨云选型与 spot 容错的开源实现，非常值得读源码）。完整清单见 references.md。
