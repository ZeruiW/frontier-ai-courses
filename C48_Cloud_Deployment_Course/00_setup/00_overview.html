1这门课讲什么

欢迎来到 LLM 生产部署与云原生。这门课只追求一件事：把一个「在我机器上能跑」的模型，变成一个「在别人流量下活着」的服务。

如果你读过 C24（高效推理服务），你已经知道推理引擎内部的机制——PagedAttention 怎么管 KV 缓存、continuous batching 怎么把 GPU 喂满、投机解码怎么省步数。那门课回答的是「单个引擎怎么跑得快」。如果你读过 C37（MLOps），你知道了实验追踪、数据版本、评测门禁、漂移监控——「模型的生命周期怎么管」。本课接在这两者中间那个被跳过的缺口上问：这个跑得快的引擎，怎么被打包、被调度、被发布、被扩缩、被计费，才能承载真实流量而不半夜把你叫醒？

这个缺口非常具体。你有一个 vLLM 进程，它在你的开发机上 8000 端口跑得好好的。现在要回答：它的依赖怎么固化（Docker）？它对外长什么样（serving API）？它在一百台机器上怎么被拉起来、挂了谁重启它（Kubernetes）？新版本怎么上线而不是一刀切（canary）？流量涨十倍怎么办（autoscaling）？这一切一个月烧多少钱（cost model）？——这五个问题，就是本课的五个模块。

直白说

换个说法：C24 教你造发动机，本课教你把发动机装进车、上牌、加油、开上路、还得算清油钱。发动机再好，没有底盘、油路和仪表盘，它就只是台在实验室里轰鸣的机器。工业界绝大多数「模型很好但上不了线」的故事，卡的都不是模型，是这层。

严谨说

严格地说，本课覆盖的是 serving stack 中推理引擎之上、业务逻辑之下的那一层：容器运行时（OCI image + runtime contract）、服务契约（HTTP/gRPC + 流式协议）、编排与调度（K8s control plane、scheduler、autoscaler）、渐进交付（progressive delivery）与成本工程（capacity planning、spot economics）。这一层的知识不随模型架构更迭而过期。

学完你应当能回答这类问题（也是 LLM 平台/推理基础设施岗的高频面试题）：为什么模型权重通常不打进镜像？readiness 探针配错了会怎样，为什么 LLM 服务特别容易踩这个坑？一个 8×H100 的节点上应该跑几个副本，装箱率怎么算？金丝雀放 5% 流量、跑多久才有统计效力？HPA 按 GPU 利用率扩缩为什么会震荡，该按什么指标？spot 实例便宜 70%，什么情况下反而更贵？——并且能在纯 Python 里把镜像层缓存、请求路由、装箱调度、滚动更新、HPA 控制律、成本模型都从零模拟一遍、用 assert 验证。

一句方法论的话先说在前面：本课的价值不在「我们没有 K8s 集群也能学」这个妥协，而在它逼你只关注真正难的部分——控制平面的逻辑、容量与风险的数学。具体用哪家云、哪个 Ingress 控制器、YAML 里哪个字段叫什么，这些是会变的、可查文档的；而「声明式控制循环为什么收敛」「滚动更新期间容量为什么会塌」「金丝雀要多少样本才能判断」「spot 中断率多高时期望成本反超按需」是不随工具过时的硬功夫。

2世界观：三笔账与「生产的不对称性」

贯穿全课的世界观可以浓缩成一句话：生产环境里，决定成败的不是「能不能做到」，而是「SLO 守不守得住、容量够不够、钱烧不烧得起」。所以本课给每个机制都配三笔账：

这笔账回答什么怎么算本课例子
SLO 账 reliability用户感知的可用性与延迟达标吗可用率、P50/P95/P99 延迟、错误预算消耗速率滚动更新期间 P99 会不会破线
容量账 capacity这些副本扛得住多少 QPS排队论：到达率 λ、服务率 μ、并发 c、利用率 ρ8 副本在 ρ=0.8 时的 P95 排队时延
成本账 cost每百万 token 花多少钱实例单价 × 时长 ÷ 有效 token 吞吐spot vs 按需的期望成本交叉点
生产的不对称性

最反直觉、也最重要的一条：生产系统的失效是不对称的。做对一百次没人注意，做错一次全网皆知。这条不对称性决定了本课所有设计决策的方向——宁可牺牲一点效率，也要把爆炸半径切小。金丝雀发布比全量发布慢、成本高，但它把「新版本有 bug」的损失从 100% 流量切到 5%；多副本比单副本贵，但它把「一台机器挂了」的损失从「服务全挂」切到「容量少 1/N」。你在本课学的几乎每一个机制，本质都是在用确定的成本，买不确定的风险的下界。

这条不对称性还有个推论，是新手最容易违背的：可观测性不是上线后的补充，而是上线的前置条件。一个没有指标、没有探针、没有结构化日志的服务，出问题时你唯一的手段是重启和猜。本课在模块 02（服务契约里就要暴露健康与指标）和模块 03（探针如何驱动流量摘除）里会反复回到这一点。

把这三笔账养成习惯，是做任何生产部署的第一步且最容易被跳过的一步。新手最常犯的错是先把服务跑起来、压测一把、看着 QPS 数字满意地上线——结果撞上滚动更新时的容量塌陷、撞上 readiness 配错导致的流量打到未加载完的 Pod、撞上月底账单里 70% 是闲置 GPU。先算账、再动手：SLO 定不下来就别谈优化，容量算不清就别谈扩缩，成本模型没有就别谈选型。

4方法论：用纯 Python 模拟控制平面

本环境没有 Kubernetes 集群、没有 GPU、不联网。这看起来是个巨大的妥协，但对本课而言恰恰是个好约束——因为云原生这一层的困难，几乎全部是「逻辑与数学」的困难，而不是「跑得动」的困难。

直白说

K8s 的调度器本质上就是个装箱算法；Deployment 控制器本质上就是个「比较期望和现实、发出差量动作」的循环；HPA 本质上是个带死区的比例控制器；金丝雀判据本质上是个假设检验。这些东西你都可以用几十行 Python 写出来、用 assert 验证它的性质——而且写出来之后，你对真实 K8s 的理解会比读一百页文档更深。

严谨说

形式化地说，我们把控制平面建模为一个离散时间系统：状态 s_t（Pod 集合、副本数、就绪标记）、期望 d（spec）、控制器 f，演化为 s_{t+1} = f(s_t, d, 外部事件)。「收敛」= 在无外部扰动下 s_t → d；「震荡」= 存在极限环。本课的 notebook 就是把 f 写出来、跑这个迭代、并对 收敛性、单调性、爆炸半径 下 assert。

具体到每个模块，我们的三条纪律是：

  • 对拍（differential testing）：每个「聪明」的实现都要和一个朴素参考对齐。best-fit 调度器要和暴力枚举的最优装箱对比装箱率；SSE 编码器要和解码器 round-trip 一致；限流器要和「按定义逐秒统计」的参考一致。
  • 算账（accounting）：每个机制都要产出一个数字。镜像层缓存命中率 → 构建时间；副本数与 ρ → P95 排队时延；spot 中断率 → 期望小时成本。数字对了，直觉才靠得住。
  • 下界思维（blast radius）：每个设计都要回答「最坏情况下有多少用户受影响、多久恢复」。这是本课独有的第三条纪律，也是生产工程与实验工程最本质的区别。

一个提醒：模拟不等于真实，但模拟能让你在真实环境里问对问题。你在 notebook 里让 HPA 震荡起来之后，第一次看真实集群的扩缩曲线就会立刻认出「这是采样周期和冷却期没配好」；你算过装箱率之后，看到节点 GPU 利用率 62% 就会立刻想到碎片而不是「模型不够快」。这就是本课想给你的东西。

5环境与运行

本课全程 纯标准库 + numpy、CPU 可跑，不需要 Docker、不需要 Kubernetes、不需要云账号、不需要联网。所有 notebook 在 CPU 上实跑验证、assert 0 失败。

# 建议在课程统一环境里跑
pip install -r requirements.txt      # numpy / pandas / jupyterlab / ipykernel
jupyter lab                          # 打开 00_setup/00_environment_check.ipynb

讲解里出现的 Dockerfile、deployment.yaml、sbatch 脚本等真实配置片段仅作对照展示，不参与运行——但它们全部是可以原样贴进真实环境使用的正确写法，建议你在有条件时逐个试一遍。每个模块末尾的「🔧 旁注」会明确指出：你在 numpy 里验证过的逻辑，对应真实系统里的哪个组件、哪个参数。

你需要本课怎么处理
Docker 引擎用 Dockerfile 解析器 + 层缓存模拟器复现构建语义；真实 Dockerfile 作对照
Kubernetes 集群用 Python 写 reconcile 循环、探针状态机、调度器；真实 YAML 作对照
GPU / 多节点用资源向量与装箱模型表示；所有账目以公开的 H100/A100 规格与云价目为准
云账号用参数化成本模型；单价可在 notebook 顶部改成你自己的报价
压测流量用泊松到达过程生成合成流量，配合 M/M/c 解析解对拍

最后一句关于心态的话：这门课里没有任何一个概念是「高深」的。容器是分层文件系统加命名空间，K8s 是一堆控制循环，金丝雀是个假设检验，HPA 是个比例控制器。它们之所以让人望而生畏，是因为工具的表面复杂度（YAML、CRD、云控制台）遮住了底下极其简单的核心。本课的全部目的，就是把那些表面剥掉，让你直接摸到核心——摸到之后你会发现，剩下的都是查文档的事。
