1调试的第一性原理：把「不 work」变成可证伪的假设

模块 02 的决策树在第一步就把你送到这里：mAP ≈ 0，或者 PR 曲线的左端就崩了。这一节先讲方法，后面八节是具体的病历。

三条铁律

  1. 先证伪最便宜的假设。「查一次类别映射」10 分钟，「训一次模型」10 小时。任何时候都应该先做那个 10 分钟的检查——即使你「觉得」不太可能是它。「觉得不可能」正是这类 bug 能存活三个月的原因。
  2. 每个假设都要能被一个具体的观察证伪。「我觉得是学习率问题」不是假设，「如果是学习率过大，那么第 1 个 iteration 的梯度范数应该 > 100，且权重更新后 loss 会上升」才是假设。写不出「如果……那么应该观察到……」的句子，说明你还没想清楚。
  3. 二分定位，而不是逐个尝试。训练链路是 数据 → 增强 → 编码 → 前向 → 损失 → 反传 → 更新 → 评测 八段。八段里定位一段，二分只要 3 次；逐个试平均要 4 次，最坏 8 次。更重要的是二分给了你「已排除」的确定性，而逐个试只给你「试过了没用」的焦虑。
训练链路的八段与「二分定位」的切点 ①原始数据 → ②增强 → ③标签编码 → ④前向 → ⑤损失 → ⑥反传 → ⑦优化器 → ⑧评测 │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ └─ 反解：把预测 │ │ │ │ │ │ │ 喂成 GT，mAP │ │ │ │ │ │ │ 必须 = 1.0 │ │ │ │ │ │ └─ 冻结全部权重， │ │ │ │ │ │ loss 必须完全不变 │ │ │ │ │ └─ 数值梯度对拍解析梯度 │ │ │ │ └─ 把 GT 当成完美预测喂进 loss， │ │ │ │ loss 必须 ≈ 0 │ │ │ └─ **单 batch 过拟合**：loss 必须 → 0 │ │ └─ 把编码后的目标**解码回框**，与原 GT 逐元素对拍 │ └─ 关掉全部增强，看指标是否恢复 └─ 直接可视化 dataloader 吐出来的张量 + 框，画在图上肉眼看 **每一段都有一个「必须成立的等式」**——这就是可证伪性的具体形态。

直白说

为什么「反解检查」这么有效？因为它把一个开放问题（模型为什么不好）变成了一个封闭问题（这个变换是不是可逆的）。标签编码 → 解码 → 与原 GT 对拍，如果对不上，bug 就一定在编码里，不可能在别处；如果对得上，编码这一段就被彻底排除了，你再也不用回头怀疑它。调试的进展不是「试了很多东西」，而是「排除了很多可能」。

严谨说

更严格地说，这是把系统的每一段都包上一个不变量（invariant）：编码段的不变量是 $\text{decode}(\text{encode}(b)) \approx b$；损失段的不变量是 $\mathcal{L}(\text{GT}, \text{GT}) \approx 0$；反传段的不变量是解析梯度与数值梯度在 $10^{-5}$ 量级一致；评测段的不变量是「把 GT 当预测送进去 mAP = 1.0」。这些不变量应当写成单元测试常驻仓库，而不是每次出事再手写一遍。在 TSR 这种「数据格式多、供应商多、坐标系多」的项目里，这套断言的价值会随着团队规模超线性增长——因为大多数管线 bug 是在别人改了上游之后引入的，而单元测试是唯一会替你盯着上游的东西。

把本节压成一句话：不要问「是什么坏了」，要问「哪一段可以被彻底排除」。每一次成功的调试，都是把搜索空间对半砍掉若干次的结果。

列清单 vs 给流程

面试里这一节是「资深度探针」。被问「模型不收敛你怎么查」时，列举一堆可能原因（学习率、初始化、数据……）只能拿及格分——因为那是背下来的清单，不是流程。拿高分的回答是给出顺序与判据：「我会先跑单 batch 过拟合，因为它一步就能把『数据+模型+损失+优化器』整体判定为可用或不可用；如果过拟合不了，说明是前四段；如果能过拟合但真实训练不降，说明是数据规模/增强/学习率调度的问题。」面试官要听的是你能把搜索空间切开，而不是你知道很多可能性。

2症状一：loss 变成 NaN

NaN 的特点是会传染：一旦某个张量里出现一个 NaN，它会在下一次前向-反传中污染所有与之相连的权重，两三个 iteration 之内整个网络就全是 NaN 了。所以「什么时候出现的」比「现在哪里有」重要得多——你必须抓第一现场。

四条通路

通路机制典型触发条件10 分钟内的判据
① 数值溢出学习率过大 → 权重爆炸 → 激活爆炸 → exp/softmax/log 溢出lr 比正常大 10–100×；warmup 没生效；混合精度下 fp16 的最大值只有 65504看 grad norm 曲线：NaN 之前一定有一段指数上升。若 grad norm 正常则不是这条
② $\log 0$ / 除零$-\log p$ 在 $p$ 被 saturate 成 0 或 1 时；IoU 的分母为 0；标准差为 0 的归一化自己手写的 BCE/focal 没加 $\epsilon$；标注里存在 $x_1 = x_2$ 的退化框NaN 在第一个 iteration 就出现，且与 lr 无关 → 几乎必然是这条
③ 坏标注$\log(w/w_a)$ 在 $w \le 0$ 时；坐标为 inf/nan；类别 id 越界导致索引到未初始化内存标注 json 里有负宽高、超界坐标、空框；数据增强裁剪后产生零面积框固定 seed 后 NaN 出现在同一个 iteration → 一定是某个特定样本
④ 反传中的除零$\sqrt{x}$ 在 $x=0$ 处梯度为 $\infty$；$\lVert v\rVert$ 归一化时 $v = 0$；GIoU 的闭包面积为 0前向不报错、反传才 NaN；常见于自写的 IoU-family 损失前向的所有中间张量都正常，只有 .grad 里有 NaN

为什么手写 BCE 一定要用 log-sum-exp 稳定版

这是最常见的 ② 号病例，值得写清楚。朴素实现是：

\[\mathcal{L} \;=\; -y\log\sigma(z) \;-\; (1-y)\log\bigl(1-\sigma(z)\bigr), \qquad \sigma(z) = \frac{1}{1+e^{-z}}\]

当 $e^{-z}$ 相对 1 小于机器精度时，$1+e^{-z}$ 被舍入成 $1$，于是 $\sigma(z)$ 被精确地舍入成 1.0——float32 的临界点约 $z = 17$，float64 约 $z = 37$（notebook 会把这两个断点逐点打出来）。此时 $\log(1-\sigma(z)) = \log 0 = -\infty$；如果这个样本的标签恰好是 $y=0$，loss 就是 $+\infty$，反传立刻产出 NaN。注意这不是「数值不准」，是「结果完全错误」——而且它只在某些样本上触发，所以看平均 loss 是发现不了的。稳定形式是：

\[\mathcal{L} \;=\; \max(z,0) \;-\; z\,y \;+\; \log\bigl(1 + e^{-|z|}\bigr)\]

这个式子对任意 $z$ 都不会溢出（$e^{-|z|} \le 1$），且与朴素式在数学上完全等价。notebook 里会把两者在 $z$ 从 10 到 100 的范围内逐点对比，看着朴素版在 $z = 37$ 附近断掉。

直白说

定位 NaN 的标准姿势是「前向逐层挂哨兵」：在每一层输出后记录 (有无 NaN, min, max)，找到第一个出现 NaN 的位置。PyTorch 里可以用 torch.autograd.set_detect_anomaly(True)（会慢很多，只在复现时开）或者给每个模块挂 forward hook。关键是不要在 NaN 已经扩散之后才去看——那时候到处都是 NaN，信息量为零。

严谨说

工程上更彻底的做法是把哨兵做成常驻的、低成本的：每 $N$ 个 iteration 记录一次全局 grad norm、各层激活的 max(|x|)、以及 loss 的各个分项（cls / box / obj 分开记）。这样 NaN 出现时你不需要复现——历史曲线里已经写着答案。特别地，把 loss 的各分项分开记录能一眼区分通路 ①③：只有 box 分项炸而 cls 正常，几乎必然是坏标注（$\log(w/w_a)$ 那条）；所有分项同时炸，才是学习率导致的整体发散。这个「分项记录」的成本接近 0，但省下的排查时间以小时计。

坏标注不是小概率事件

TSR 项目里 ③ 号通路格外高发，因为交通标志的标注常常来自多个供应商、多个年份、多种工具。真实见过的坏数据：宽或高为 0 的框（标注员点了一下就保存）、坐标是归一化值但字段名写着 pixel、被遮挡标志的框被标成负坐标、以及一张图里同一块牌子被标了两次且其中一次类别不同。防御手段只有一个：在 Dataset 的 __getitem__ 里加断言——assert (w > 1) and (h > 1) and 0 <= x1 < x2 <= W，并且在断言里打印文件名，否则你只知道「有坏数据」，不知道是哪张。

NaN 的第一个问题永远是「它是第几个 iteration 出现的」。第 0–1 个 iteration 出现 ⇒ 数据或损失的实现问题；训练几百步后才出现 ⇒ 学习率/发散；固定 seed 后总在同一步出现 ⇒ 某个特定样本。这一个问题就能砍掉三分之二的可能性。

「数据没打乱」为什么会让 loss 躺平

如果一个 batch 里全是同一类（比如连续 64 帧同一段路的限速 60），那么这个 batch 的最优解就是「无论看到什么都输出限速 60」。下一个 batch 全是指路牌，最优解又变成「都输出指路牌」。于是模型在两个互相矛盾的解之间来回跳，梯度互相抵消，平均下来什么也没学到。TSR 的数据天然是按行车序列采集的，相邻帧极度相关——这使得「忘记打乱」在 TSR 项目里的后果比在 ImageNet 上严重得多。

直白说

「冻错了层」有一个非常隐蔽的变体：你设了 requires_grad=False，但 optimizer 是在设之前构造的。此时参数确实不产生梯度，但如果 optimizer 带 weight decay，它仍然会每步把这些权重乘以 $(1-\lambda\eta)$ 往零缩——结果是「冻结」的 backbone 被慢慢地衰减成零。症状是训练前几百步正常，然后指标开始不可逆地下滑。

严谨说

反过来的坑同样常见：BatchNorm 的统计量不受 requires_grad 控制。把 backbone 「冻住」但忘了 model.eval() 或忘了把 BN 换成 FrozenBatchNorm，BN 的 running_mean/var 会继续被新数据更新，于是「冻结的 backbone」的输出分布在训练中一直在变。这在 TSR 的微调场景里很致命：你在 COCO 预训练权重上微调，本意是保住通用特征，结果 BN 统计被几千张全是路面和天空的图带偏，通用特征反而被破坏得比不冻还厉害。检查方法很简单：训练前后把 backbone 某个 BN 层的 running_mean 打出来对比，变了就说明没真冻住。

lr range test 有一个容易忽略的前提：它必须在「已经确认数据管线正确」之后做。如果标签是错的，任何学习率下 loss 都降不下去，你会得出「所有 lr 都不行」的结论，然后浪费一天在调 lr 上。这就是为什么第 7 节的「单 batch 过拟合」应该排在 lr range test 之前——它能一次性判定「数据+模型+损失」这一整块是否可用。

4症状三：mAP 恒为 0（三大元凶占绝大多数）

这是检测任务独有的、最经典的症状：loss 在正常下降、可视化的框看起来也在目标附近，但评测出来 mAP 就是 0.00x。工业界的经验分布是：类别 ID 偏移、坐标格式弄反、评测集与训练集类别表不一致——这三个加起来占了绝大多数。它们的共同点是：都不会报错，都不会让 loss 异常，只在最终指标上表现为「一切归零」。

为什么类别表不一致这么隐蔽

因为它经常是由「正确的代码」产生的。典型场景：训练侧用 sorted(os.listdir(ann_dir)) 得到类别顺序，评测侧用 json.load() 里 categories 数组的原始顺序。两边都没错，但顺序不同。更隐蔽的是：某个类在训练集里出现过、在评测集里一个样本都没有，于是评测侧的类别表少了一项，后面所有 index 全部左移一位。

直白说

为什么「类别 ID 偏移」会让 mAP 精确地掉到 0 而不是掉一半？因为 AP 是逐类算的。偏移一位之后，类 $c$ 的预测全部落进类 $c{+}1$ 的评测里；而类 $c{+}1$ 的 GT 与类 $c$ 的目标在图像上完全不重叠，所以 IoU 全是 0，每一类的 AP 都是 0，平均下来还是 0。这也解释了一个反直觉的现象：偏移 1 位和偏移 5 位的后果完全一样，都是 0。所以「mAP 是 0 而不是 0.3」本身就是强烈的信号——模型能力问题不会让指标精确归零，只有映射问题会。

严谨说

坐标格式的情况稍有不同，值得单独想清楚。把 cxcywh 直接当 xyxy 用会得到 $(c_x, c_y, w, h)$ 这样一个「框」：当 $w < c_x$ 或 $h < c_y$ 时它的宽高为负，面积按 clip(x2-x1,0) 算出来是 0，于是 IoU 恒为 0，mAP 精确为 0；而当目标靠近图像左上角时 $w > c_x$，会得到一个「从中心点延伸到 $(w,h)$」的怪框，IoU 是个很小的正数。所以「坐标格式弄反」的指纹不只是 IoU 低，更关键的是「IoU 恰好等于 0 的比例接近 100%」——而模型定位不准时这个比例几乎是 0（框再歪也总有些许重叠，IoU 是连续分布）。notebook 里会把「正常 / cxcywh 当 xyxy / xywh 当 xyxy / yxyx 当 xyxy」四种情况的指纹并排打出来，一眼就能分辨。

背清单 vs 给判据

这是 TSR / 检测岗位的高频面试题：「mAP 一直是 0，你怎么查？」

不合格的回答：「我会检查数据、检查代码、打印一下看看。」

拿分的回答：「我会按三个 3 分钟的检查走。第一，把预测类别整体 ±1 重算 mAP——如果突然正常就是类别 ID 偏移，COCO 的 category_id 从 1 开始是最常见的来源。第二，把预测框按 cxcywh→xyxy 转换后重算 IoU 分布——如果平均 IoU 从 0.03 跳到 0.85 就是坐标格式。而且格式错的指纹很特别：IoU 分布是『大量精确的 0 + 少量小正值』的双峰，不是模型定位不准的单峰。第三，diff 训练与评测两侧类别表的顺序——如果混淆矩阵是个置换矩阵，就是这个。这三条覆盖绝大多数情况，都不用重训；三条都过了我才会去怀疑模型。」

加分句：「而且 mAP 恰好是 0 而不是 0.3 本身就是线索——模型能力问题不会让指标精确归零。」

5数据管线 bug 的特征指纹

上一节的三大元凶都是「让 mAP 归零」的重症。还有一类更麻烦：指标掉了但没归零——模型照样能跑，指标从 0.72 掉到 0.58，你会以为是「这次训练没调好」，于是开始调超参，然后在一个有 bug 的管线上做三个月的架构消融。

对抗这类 bug 的唯一有效手段是「指纹」：每种 bug 都有一组它独有的可观测特征。认识指纹，你就能从症状直接反推病因，而不是逐个试。

为什么「通道顺序」的指纹是类别相关的

这是本节最有价值的一条，也是 TSR 特有的洞察。交通标志的颜色是语义：红色 = 禁令、蓝色 = 指示、黄色 = 警告、绿色 = 高速指路。R 与 B 互换会把红色变成蓝色、蓝色变成红色——一个禁令标志在模型眼里变成了指示标志。而白底黑字的指路牌 R≈G≈B，交换前后几乎不变。

BGR/RGB 弄反的类别指纹（notebook 会实测这张表） 类别组 颜色特征 交换 R/B 后 准确率变化 ───────────────────────────────────────────────────────────────────── 红色禁令（限速/禁止） R 高 B 低 -> R 低 B 高 变蓝 ▼▼▼ 崩到接近 0 蓝色指示（直行/环岛） B 高 R 低 -> B 低 R 高 变红 ▼▼▼ 崩到接近 0 黄色警告（注意行人） R 高 G 高 B 低 -> R 低 G 高 B 高 变青 ▼▼ 大幅下降 白底黑字（指路牌） R≈G≈B -> R≈G≈B 几乎不变 ▬ 基本不掉 ───────────────────────────────────────────────────────────────────── **这个「掉点的类别选择性」就是指纹。** 对照：如果是 mean/std 归一化写错，所有类别会**均匀**掉点， 因为它不改变通道之间的相对关系，只是整体平移/缩放。 => 看到「颜色类崩、中性色类不掉」就直接去查通道顺序，不要调超参。

直白说

指纹思维的价值在于它把调试从「顺序搜索」变成「哈希查表」。没有指纹时，你面对 6 种可能的 bug 要平均试 3.5 次，每次可能要重训或重跑评测；有指纹时，你看一眼「掉点的类别选择性」就能定位。而且指纹是可以自动化的——把这几条检查写成一个脚本，每次评测完自动跑一遍，它会主动告诉你「疑似通道顺序问题」。

严谨说

更深一层：好的指纹必须是「充分区分」的，而不只是「相关」的。「mAP 掉了」和通道顺序相关，但它和另外五种 bug 也相关，所以它不是指纹。「颜色语义类崩而中性色类不掉」只和通道顺序相关，所以它是指纹。设计指纹的方法是问：这个 bug 的机制会在哪个维度上产生不对称的影响？通道顺序 → 颜色维度不对称；resize 不一致 → 尺寸维度不对称；类别表错位 → 类别维度上呈置换结构；坐标格式 → IoU 分布形态不对称。「找不对称」是构造指纹的通用方法，也是本节最可迁移的东西。

组合 bug 会污染指纹

一个真实的、极难查的组合 bug：训练用 PIL 读图（RGB）+ cv2.resize（默认 INTER_LINEAR），推理用 cv2.imread（BGR）+ PIL 的 resize（默认 BICUBIC）。两个 bug 叠加时，指纹会互相干扰——通道错导致颜色类崩、插值错导致小目标崩，你看到的是「颜色类的小目标崩得特别厉害」，很容易被误判成「小目标问题」而去加 P2 层。所以指纹检查必须是「逐项独立」的：一次只改一个变量重测，而不是看着最终指标猜。这正好呼应模块 01 的单变量原则。

6症状四：训练正常但验证极差；过拟合与欠拟合的区分

「训练 loss 一路下降到 0.05，验证 mAP 只有 0.11」——这个症状有两个完全不同的病因，而把它们搞混是初级工程师最典型的失误：一个需要更多数据/更强正则，另一个需要修 bug。

真·过拟合验证管线不一致（伪过拟合）
训练指标很好很好
验证指标差，但不至于崩（比如 0.72 → 0.55）崩到接近随机（0.72 → 0.11）
关键判据把训练集当验证集跑评测流程 → 指标仍然很好把训练集当验证集跑评测流程 → 指标同样崩
曲线形态验证 loss 先降后升，有明确拐点验证 loss 从第一个 epoch 就是坏的，没有拐点
随数据量加数据会改善加数据完全无效
常见根因数据太少、模型太大、增强太弱、训太久验证侧的 resize/归一化/通道/letterbox 与训练侧不同；
评测时忘了 model.eval()（BN 用了 batch 统计）；
验证集类别表不一致（见第 4 节）

那个关键判据值得单独强调：把训练集喂进验证的那条代码路径去评测。如果指标同样崩，那就与「泛化」毫无关系——数据模型都是同一批，唯一的变量就是那条代码路径。这是一个能在 20 分钟内做完、并且结论是二值的实验，收益极高。

直白说

检测任务的欠拟合有一个很有辨识度的表现：回归分支退化到「输出训练集框的平均值」。表现为所有预测框尺寸差不多、位置都靠近图像中心。因为在没学到有效特征时，最小化 L1/GIoU 损失的最优常数解就是训练集框分布的中位数。看到「所有框长得一样」，先别怀疑标签分配，先怀疑模型压根没在学。

严谨说

TSR 场景里还有一类介于两者之间的情况值得警惕：虚假过拟合——模型不是记住了训练样本，而是记住了训练集里的一个捷径特征。例如某个采集批次的图像都有相同的相机 ISP 风格，模型学会了「这种色调下出现的圆形物体就是限速牌」；换到另一个批次（另一台车、另一个国家），这个捷径失效，指标崩塌。它的判据是：验证集按「采集批次」分桶后，同批次内的验证指标好、跨批次的差。这不是加数据能解决的（加同批次的数据没用），也不是正则化能解决的——唯一的解法是让训练数据在那个捷径维度上具有多样性（多车型、多时段、多地域），或者用增强主动破坏那个捷径（色彩抖动、ISP 模拟）。这直接连到 C56 的增强设计与 C58 的数据闭环。

别把管线问题说成泛化问题

最容易在面试里丢分的一句话：「验证集上差就是过拟合」。面试官会立刻追问「你怎么排除是验证管线的问题」。准备好那个判据：「我会先把训练集喂进验证的代码路径跑一遍——如果指标同样崩，那和泛化没关系，是管线；如果指标依然很好，才是真的泛化问题。这个实验 20 分钟能做完，结论是二值的。」

7万能诊断法：先把一个 batch 过拟合

如果这门课你只能记住一个技巧，就记这个。拿 8–32 个样本，关掉所有增强、关掉正则、关掉 dropout、关掉学习率衰减，反复在这一个 batch 上训练几百到几千步。训练 loss 必须掉到接近 0，mAP 必须接近 1.0。

它为什么这么强

因为它一次性判定了「数据 → 增强 → 编码 → 前向 → 损失 → 反传 → 优化器」这一整块是否可用，而且把「泛化」这个最难的变量彻底移出了方程。

\[\text{一个足够容量的模型在 } n \text{ 个样本上，最优训练损失应当} \to 0 \quad (n \ll \text{参数量})\]

这句话是无条件成立的——它不依赖数据质量、不依赖任务难度、不依赖超参调得好不好。所以如果做不到，就一定有 bug，而不是「这个任务比较难」。这个「无条件」是它作为判据的全部价值所在。

单 batch 过拟合的结果 -> 结论 loss -> ~0，mAP -> ~1.0 ==> 数据/编码/前向/损失/反传/优化器 **全部可用** 问题一定在：数据规模、增强、学习率调度、正则、验证管线 （搜索空间瞬间砍掉一半以上） loss 完全水平（一动不动） ==> 梯度没有流到权重 查：requires_grad / optimizer.param_groups / 是否忘了 loss.backward() / 是否 detach 了 / lr 是否为 0 / 是否有 torch.no_grad() 包住了 loss 下降但停在某个正数（例如二分类停在 0.693 = ln 2） ==> 模型只能输出常数 查：特征全被 ReLU 杀死（死亡神经元）/ 输入全零 / 归一化把方差归零了 / 只有 bias 可训练 loss 下降到 0 但 mAP 仍然是 0 ==> **训练侧对、评测侧错** —— 直接跳到第 4 节的三大元凶 （这是最有价值的一种结果：它把 bug 精确锁在评测代码里） loss 剧烈震荡 / 变 NaN ==> 学习率过大或数值实现有问题（第 2 节）
检查项为什么必须关掉忘了关的后果
数据增强随机增强让「同一个 batch」每步都不同，等于换了任务loss 降不到 0，你会误判为有 bug
Dropout / DropPath注入随机性，同上loss 在某个正数附近抖动
Weight decay把权重往零拉，与「记住这几个样本」相冲突loss 停在一个非零平台

shuffle只有一个 batch，无所谓，但要确保每步用的是同一批数据实际上在遍历数据集，等于普通训练

直白说

还有一个进阶用法：用「能过拟合多少个样本」来估计模型容量与实现质量。先过拟合 1 个样本，再 8 个、64 个、512 个。如果 8 个能过拟合而 64 个不能，说明有一个与 batch 大小相关的 bug（比如损失里错误地对 batch 维度求了 max 而不是 mean，或者标签分配在多目标时出错）。这个「阶梯式过拟合」能定位到很多单样本测不出来的问题。

严谨说

在检测任务里还要额外注意一点：「过拟合一个 batch」在有标签分配（label assignment）的检测器里不是平凡的。如果分配策略有 bug——比如所有 anchor 都被判成负样本、或者正样本阈值设得过高——那么无论训多久，分类分支都只会学到「全是背景」，loss 会降到「全预测背景」对应的值然后不动。所以检测的单 batch 过拟合必须同时打印「每步分到的正样本数」：如果正样本数是 0 或者远小于 GT 数，问题就在分配，而不在网络。这一条在 TSR 上尤其重要，因为小目标（8–20 px）在 IoU 阈值 0.5 的静态分配下天然极难匹配到正样本（C57 模块 03 展开），「正样本数 = 0」在 TSR 项目里是常态而不是异常。

单 batch 过拟合是检测调试里唯一的「无条件必须成立」的实验。它成立时你排除了半个系统；它不成立时你知道 bug 一定在前半段。没有任何其他实验有这么高的信息量/成本比。

常见的自欺欺人：「我的 loss 降到 0.02 了，应该没问题」。在检测里 loss 是多项之和（cls + box + obj/dfl），某一项塌成 0 而另一项没动，总和看起来也会很小。必须分项打印，并且必须同时看 mAP——mAP 在单 batch 上应该达到 0.95 以上，达不到就说明「loss 低」和「预测对」之间断了链，那个断点通常就在后处理或评测里。

8分布式不一致与复现失败的排查顺序

单卡跑通之后，多卡上出现「指标比单卡低 2 个点」「每次跑结果都不一样」「某张卡 hang 住」——这类问题的特点是：它们几乎从不报错，只是让结果慢慢变得不可信。

问题机制症状检查/修法
BN 不同步每张卡用自己的 mini-batch 算 BN 统计。8 卡 × batch 2 = 每张卡只有 2 个样本的统计量多卡指标低于单卡；per-GPU batch 越小差距越大换 SyncBatchNorm；或增大 per-GPU batch；或换 GN/LN。per-GPU batch ≥ 16 时通常不必同步
随机种子相同所有 rank 用同一个 seed → 数据增强在所有卡上完全一样等效 batch 的多样性只有名义值的 $1/N$；训练比预期慢、指标偏低seed = base_seed + rank；DataLoader worker 还要再叠一层 worker_id
数据分片重叠sampler 配置错误导致同一样本被多张卡拿到；或 drop_last=False 时补齐样本重复一个 epoch 的实际样本数 ≠ 数据集大小；指标虚高（重复样本相当于变相过采样）打印 len(sampler) * world_size 与数据集大小对比；评测时用 去重后的 结果
忘了 set_epochDistributedSampler 的打乱种子固定 → 每个 epoch 的划分完全相同每个 epoch 每张卡看到的都是同一批数据；loss 曲线呈现强周期性每个 epoch 开头调 sampler.set_epoch(epoch)——这是最常忘的一行
梯度累积与 loss 缩放累积 $k$ 步时 loss 没除以 $k$，等效学习率变成 $k$ 倍换了累积步数之后训练发散或指标变化很大确认 loss 归一化口径；换累积步数时等效 lr 要跟着变
评测只在 rank 0 做各 rank 的结果没有 gather 完全，或 gather 时顺序不定多卡评测结果与单卡不一致，且每次略有不同评测结果按样本 id 排序后再算指标；指标计算只在一个 rank 上做

复现失败的排查顺序

「同一份代码、同一份配置，昨天 0.72、今天 0.68」——按下面的顺序查，每一步都比下一步便宜：

  1. 先确认这不是种子方差。检测任务同配置不同种子的 mAP 波动典型是 ±0.2–0.5 个点（模块 01）。0.72 vs 0.68 完全可能就是噪声。先跑 3–5 个种子看分布，再决定要不要查。这一步排除掉的「bug」占了所有「复现失败」报告的一大半。
  2. 代码版本。git status 是否干净？有没有未提交的本地修改？依赖库版本有没有变（pip freeze diff）？「我只改了个打印」是经典的最后遗言。
  3. 数据版本。数据集有没有被人补标/修标？标注文件的 md5 对得上吗？在 TSR 项目里数据是持续回流的，「同一个数据集」这个说法本身就需要版本号才有意义。
  4. 随机性来源。seed 设了几处（python / numpy / 框架 / cudnn / DataLoader worker）？cudnn.benchmark=True 会让算法选择依赖硬件状态；某些 GPU 算子本身非确定性（atomicAdd 的浮点加法不满足结合律）。完全确定性通常要付 10–30% 的速度代价，所以多数团队选择「不追求逐位复现，只追求指标分布可复现」。
  5. 环境。驱动 / CUDA / 框架版本 / 硬件型号。换卡会改变 kernel 选择，也会改变浮点累加顺序。
  6. 最后才是「代码里有 bug」。

直白说

第 1 步值得再强调一次：大多数「复现失败」根本不是失败，是没有理解方差。一个只跑了单种子的实验，它的 mAP 是一个随机变量的一次抽样，而你在拿两次抽样比大小。「昨天 0.72 今天 0.68」这句话在统计上是没有信息的，除非你知道 $\sigma$。

严谨说

反过来，真正需要「逐位复现」的场景也是存在的，而且在车企里很重要：安全相关的模型证据链。当一个模型要进入量产、要过功能安全评审时，「这份权重是由这份代码 + 这份数据 + 这个环境产生的」必须是可验证的，否则出了事故无法归因。此时可复现性不再是调试便利，而是合规要求。工程上的做法是分层：日常迭代允许非确定性（换速度），发布候选版本必须在确定性模式下重跑一遍并归档（固定 seed、cudnn.deterministic=True、固定镜像、固定数据快照）。这套东西在 C37 的 MLOps 课里叫「实验记录的最小必要字段」，在这里叫「出事之后你还能不能说清楚」。

所有 worker 生成同样的增强

DataLoader worker 的种子是一个经典事故，值得单独记住：多个 worker 进程会各自继承主进程的 numpy 随机状态，如果不显式给每个 worker 设不同的种子，所有 worker 会生成完全相同的随机增强。症状是：增强的有效多样性只有名义值的 $1/N_{\text{workers}}$，指标莫名其妙比预期低，而且怎么调增强参数都没用。修法是给 DataLoader 传 worker_init_fn，用 base_seed + rank * n_workers + worker_id 初始化。这个 bug 在 C56 模块 04 有完整的实验复现。

9研究前沿与开放问题

调试看起来是最「工程」的一节，但它背后有一批还没被解决好的问题。

  • 训练故障的自动诊断。目前 grad norm、激活分布、loss 分项这些信号都要人看。能否用一组规则或一个小模型，从训练日志里自动判定「这是学习率过大 / 这是标签分配失效 / 这是数据管线错」？工业界已有雏形（如自动 NaN 归因、自动 lr 推荐），但覆盖率与误报率都还很差，而这恰恰是「训练一次要几千 GPU 小时」的场景下最值钱的能力。
  • 标签噪声与「难例」的可分离性。模块 02 提到 10–20% 的 badcase 是标注错。置信学习、损失轨迹（一个样本的 loss 随训练的演化形态）、多模型一致性都能部分识别，但在检测任务上（框与类别两个维度、还有漏标）仍无成熟方法。漏标（missing annotation）尤其难：模型检出了一个真实存在但没被标注的目标，训练时它被当成难负样本，等于主动教模型「不要检出这类目标」——这是长尾类别持续变差的隐藏机制。
  • 确定性与性能的取舍。GPU 上的浮点归约天然非确定，完全确定性要付显著的速度代价。能否设计出「统计可复现」的训练——不要求逐位相同，但保证指标分布的可复现性有理论界？这对需要通过安全评审的车载模型是实际需求，目前只能靠「多跑几次取分布」这种经验做法。
  • 训练-部署一致性的形式化验证。现在的做法是逐层对拍 + 容差判定，但容差该设多少、逐层对齐能否推出端到端对齐、量化误差如何在层间传播——这些都没有可用的理论。C60 模块 01/04 给了工程做法，但「证明两条管线等价」仍然是开放问题。
  • 分布式训练的可观测性。多卡训练里「哪张卡拖慢了」「哪次通信超时了」「BN 统计在各卡上差多少」目前都缺乏低开销的标准工具。随着模型与集群规模增长，这类「系统层的误差」正在变成精度损失的重要来源，而它们在单卡上完全不可见。
  • 把调试知识沉淀成可执行资产。本模块的每条诊断都可以写成一个自动检查器（notebook 里做了几个）。更进一步的问题是：如何让这些检查器随着代码演化而不腐化？「不变量测试」（decode∘encode = id、$\mathcal{L}(\text{GT},\text{GT})=0$、GT-as-prediction 的 mAP = 1）应当像单元测试一样常驻 CI，但业界这么做的团队仍是少数——这是一个「知道该做但没做」的巨大缺口。

★ 必读：Andrej Karpathy, A Recipe for Training Neural Networks（2019 博文）——「先和数据融为一体 / 搭端到端骨架并接上 dumb baseline / 过拟合 / 正则化 / 调参 / 榨干」这套顺序，以及「neural net training fails silently」这个论断，是本模块全部方法论的源头。建议逐段精读并对照自己的流程。

★ Bolya et al., TIDE（ECCV 2020）——与模块 02 配套；当你需要判断「是模型能力问题还是管线问题」时，TIDE 的分解形态本身就是一个强指纹。

★ Northcutt, Jiang & Chuang, Confident Learning: Estimating Uncertainty in Dataset Labels（JAIR 2021）——标注噪声的系统性识别；把它的思路迁移到检测（框 + 类别 + 漏标）是很好的自研课题。
