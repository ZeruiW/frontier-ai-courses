1从「会跑通」到「能负责」：中间隔着什么

前面八门课（C53–C60）教的是零件：实时检测器怎么设计、集合预测怎么匹配、小目标为什么难、增强怎么做、长尾怎么挖、车端怎么部署。这门课教的是把零件装成一个你敢签字的系统——以及在面试里把这件事讲清楚。

先把「会跑通」和「能负责」的差距摊开。它不是知识量的差距，是你被问到什么问题时答不上来的差距：

能力层级典型表现被问到什么会卡住在面试里的信号
会跑通能改 config、能启动训练、能跑出一个 mAP 数字、能导出 ONNX「这个 mAP 是在什么评测集、什么 score 阈值、什么 IoU 口径下算的？」答案里全是工具名（mmdet / ultralytics / TensorRT），没有数字
能改进知道加 Mosaic、换标签分配、加 P2 能涨点，也真的涨了「涨了 0.4，你怎么知道这不是种子噪声？」能说方法，说不出验证；对代价（延迟/显存/训练时长）没有账
能负责任何改动都能预估影响、能在指标动了之后定位到原因、交付物可复现可回滚——（这一层的问题是「你怎么设计整个闭环」，而这正是他想听的）回答自带数字、代价、验证方式、失败时的退路

这三层之间的跳跃，靠的是三个可训练的能力。它们贯穿本课全部六个模块：

直白说

这三个能力有一个共同的底色：把「感觉」换成「数」。「我觉得这个改动应该有用」→「这类改动在这个尺寸桶上的经验量级是 +1.5~4 点，延迟代价 25~60%」；「不知道为什么掉点了」→「掉点只发生在夜间桶，其他桶在噪声范围内，所以是数据分布问题不是模型容量问题」；「我这边是好的」→「run_id 3f2a1c，commit d41d8c，数据版本 v7，种子 0，manifest 在这里」。

严谨说

更精确地说，这三个能力对应工程系统的三个属性：可预测性（predictability，改动前能给出影响的先验区间）、可观测性（observability，指标变化能被分解到可定位的维度）、可复现性（reproducibility，任意历史状态可以被重建）。这三者缺任何一个，团队的迭代速度都会从「线性推进」退化成「随机游走」——因为无法预测就只能全试、无法观测就只能猜、无法复现就无法回退，于是每次迭代都在重新支付上一次的成本。

一句话概括本课的立场：检测工程的难点从来不是「模型不够好」，而是「你不知道模型为什么是现在这样，也不知道下一步该做什么」。C53–C60 给你候选动作，C61 教你在候选动作里选、验、交付。

2能力一 · 指标意识：任何改动都能说出对哪个指标有多大影响

指标意识不是「知道 mAP 是什么」，而是一个具体到可以被检验的能力：给你一个改动，你能在不跑实验的情况下说出四件事——影响哪个指标、多大量级、什么方向、什么代价。

先说「哪个指标」：整体 mAP 是最不敏感的那一个

绝大多数 TSR 改动的效果，在整体 mAP 上都是被稀释的。假设你的数据里小目标（<32²）占 40%、稀有类占 3%，那么：

改动它真正影响的指标在整体 mAP 上看到的为什么被稀释
加 P2 层 / 提高输入分辨率mAP_small +1.5~4.0+0.6~1.6只有 40% 的样本受益
稀有类 copy-paste尾部类 AP +3~15+0.2~1.0稀有类只占类别权重的一小块
INT8 校准集缺夜间样本夜间桶 −5~−15−0.5~−1.5夜间帧只占评测集 10%
水平翻转增强（含方向性标志）左转/右转类 AP −5~−20−0.2~−1.0方向类只有几个类别
「涨了多少」的正确答法是「涨在哪」

面试高频翻车点。被问「你这个改动带来多少提升」时，只答「整体 mAP 涨了 0.8」会被立刻追问「涨在哪？」——如果你答不上来，面试官得到的信息是你没有分桶评测，而分桶评测是 TSR 岗位的基本功。正确答法：「整体 +0.8，但这个数字没有意义——真正的效果在小目标桶（<16px）上是 +3.2，其他桶在噪声范围内（±0.2）。因为这个改动只影响高分辨率特征层，所以这个分布正是我预期的。」面试官想听的是：你的预期和你的观测是否对得上——对得上说明你理解机制，对不上而你注意到了，说明你会归因。

再说「什么代价」：每个改动都要记一笔双边账

把一个改动的价值写成收益与代价的比值，是选型的最小工具。设 baseline 延迟为 $T_0$：

\[\text{ROI} \;=\; \frac{\Delta \text{AP}_{\text{关键桶}}}{\Delta T / T_0}\,, \qquad \text{而「必做项」的判据是} \;\; \Delta T \le 0 \;\wedge\; \Delta \text{AP} > 0\]

这个式子的作用不是算出一个精确的分数，而是强迫你把代价写下来。notebook 里会让你对一张 14 项的改动表逐条算 ROI，你会发现结论非常反直觉：Mosaic、close-mosaic、换标签分配、延长训练——这几项的延迟代价是严格的 0，却常常被排在「加分辨率」之后。

直白说

为什么「零延迟代价」的改动会被排后面？因为它们不酷。加分辨率、换更大 backbone、上 Transformer——这些改动有故事可讲；而「把 epoch 从 12 拉到 36」「把 MaxIoU 分配换成 TaskAligned」听起来像杂活。但在量产系统里，延迟预算是硬约束，而训练时长不是——车端 33 ms 的一帧里 TSR 可能只分到 4–6 ms，多花 3 天训练却不占这 6 ms 的改动，价值上限比任何架构改动都高。

严谨说

严谨地说，这是一个约束优化问题而不是无约束优化：目标是在 $T \le T_{\text{budget}}$、$M \le M_{\text{budget}}$（显存）、$P \le P_{\text{budget}}$（功耗）的可行域内最大化关键桶的 AP。零延迟改动不消耗任何约束资源，因此它们在可行域内的任何一点都是严格改进——用经济学的话说，它们是帕累托改进而不是权衡。面试里主动把改动分成「免费的」和「要花预算的」两类，是一个很强的成熟度信号，因为它说明你把延迟当成了预算而不是指标。

指标意识的一个必要成分是知道自己不确定。经验量级应该报成区间而不是点估计：说「+1.5 到 +4.0，取决于小目标占比」比说「+2.7」可信得多。报点估计的人，要么真的做过一模一样的实验，要么在编——而面试官会用追问区分这两种情况（「为什么是 2.7 不是 2.2？」）。

3能力二 · 归因：看到指标变化，能定位到原因

归因是三个能力里最难教、也最值钱的一个。它的核心不是「知道所有可能的原因」（那只是背清单），而是知道下一步该做哪个检查。

坏做法：按可能性从高到低逐个试

常见的排查方式是「先看看是不是学习率的问题，不是的话看看是不是数据的问题，还不是的话……」。这在候选原因有 6 个、每个检查要 20 分钟时，期望耗时约 2 小时。更糟的是它是串行的，且每次失败不提供任何信息。

好做法：挑「能把候选集劈成两半」的检查

把候选原因看成一个概率分布 $p_1,\dots,p_k$。一个二值检查把候选集分成「检查通过 → 排除掉 S」和「检查失败 → 排除掉补集」两支。这个检查的信息增益（information gain）恰好等于被它分到一边的那部分概率质量 $m$ 的二元熵：

\[\mathrm{IG} \;=\; H(p_1,\dots,p_k) - \bigl[\,m\,H(P\mid S) + (1-m)\,H(P\mid \bar S)\,\bigr] \;=\; H_b(m) \;=\; -m\log_2 m - (1-m)\log_2(1-m)\]

这个等式非常有用，因为它把「哪个检查最有价值」这个模糊问题变成了一个可以口算的问题：找那个把概率质量切得最接近 50/50 的检查。notebook 里会把它实现出来，并在一个真实的症状（「mAP 恒为 0」）上跑一遍。

症状：mAP 恒为 0（loss 正常下降） 候选原因与先验（来自你团队的历史事故统计，不是拍脑袋） 类别 ID 偏移 0/1 ................ 0.35 ┐ 坐标格式弄反 xywh↔xyxy .......... 0.25 ├─ 数据/接口类，占 0.85 标注坐标未随 resize 缩放 ......... 0.10 │ 评测集与训练集类别表不一致 ....... 0.15 ┘ 学习率过大导致框全部发散 ......... 0.10 ┐─ 训练类，占 0.15 数据没打乱（每 batch 单类） ....... 0.05 ┘ 候选检查 切出的质量 m IG=H_b(m) A. **把 GT 当预测送进评测器**，看 mAP 是否 = 1.0 0.85 0.610 B. 打印前 20 个预测框的坐标范围（[0,1] 还是像素） 0.35 0.934 C. 检查 loss 曲线是否在 3 个 epoch 后仍在降 0.15 0.610 D. 统计一个 batch 里的类别数是否 > 1 0.05 0.286 E. **打印训练侧与评测侧的 class_id -> name 映射表** 0.50 1.000 ← 最优 ▶ 先做 E：一次检查消掉 1 bit（二值检查的理论上限），6 个候选 3 次内定位。 ▶ **注意 A 虽然直觉上"最全面"，信息增益反而只有 0.61**—— 因为它切出 0.85 的质量，几乎总是给同一个答案（"评测管线有问题"）， 做完之后你面对的还是原来那 4 个候选。

直白说

这里有个反直觉的结论值得记住：「最全面的检查」通常不是「最该先做的检查」。检查 A（把 GT 当预测喂进评测器）能一次性判定「评测管线是否正常」，覆盖 85% 的候选原因，听起来应该先做。但正因为它覆盖面太大，它的结果几乎总是「评测管线有问题」，于是做完之后你面对的还是原来那 4 个候选。而检查 E（打印两侧的类别映射表）只针对两个原因，却恰好把候选集切成 0.50 / 0.50，无论结果如何都真正砍掉一半。

严谨说

这与二分查找的直觉是同一个东西：二分之所以是 $O(\log n)$，不是因为每次比较很聪明，而是因为每次比较把搜索空间对半砍。归因也一样——检查的价值由它的判别性决定，而不由它的覆盖面决定。在实践中这意味着：面对一个指标异动，先花两分钟列出候选原因和它们的先验质量，再挑那个把质量切得最均匀的检查，通常比直接动手快一个数量级。面试里被问「线上某类标志漏检，你的排查流程是什么」时，如果你的回答是一个「先查 A 再查 B」的固定清单，那是背的；如果你的回答是「先看漏检是集中在某个场景桶还是全局均匀——这一个观察就能把候选原因砍掉一半」，那是会的。

归因的可迁移心法：不要问「原因是什么」，要问「哪个观察最能区分候选原因」。前者需要灵感，后者是一个可以系统执行的算法——而且它在训练调试（模块 03）、误差分析（模块 02）、部署一致性排查（C60）里是同一个算法。

4能力三 · 交付纪律：可复现、可回滚、可交接

前两个能力决定你能走多快，第三个能力决定你走过的路能不能被别人（包括三个月后的你自己）沿用。它是三者里唯一一个「不做也不会立刻出事」的能力——所以也是最容易被牺牲的那一个。

属性具体要求缺失时的典型事故验证方式
可复现任意历史 run 能被重建：代码 commit（含是否 dirty）、数据版本、完整配置、环境（Python/CUDA/驱动/库版本）、随机种子、完整指标「上个季度那个 0.82 的模型是怎么训的？」——没人知道，只能重训一遍，两周没了随机抽一个 30 天前的 run，从 manifest 重跑，看指标是否落在种子方差区间内
可回滚每个发布物有唯一 ID、可追溯到源 run、上一版本随时可切回；回滚不需要重新构建新版本上线后夜间误报暴涨，但旧 engine 已被覆盖，只能带病运行到重新构建完成定期做回滚演练：随机挑一个历史版本，计时看多久能切回去
可交接别人能在不问你的情况下：跑通训练、复现评测、理解为什么是这个配置、知道已知的坑你休假一周，团队的迭代停摆；或者新人花三周重新踩你踩过的坑让一个没碰过这个项目的同事按文档跑一遍，记录他卡住的每一个点

这三条里，可复现是地基——不可复现的东西谈不上回滚（回滚到一个你重建不出来的状态没有意义），也谈不上交接（交接一堆无法重现的数字等于没交接）。而可复现的最小实现只有一件事：每个 run 落一份 manifest。

run_manifest.json —— 最小必要字段（缺一项，可复现性就有一个洞） { "run_id": "2026-08-17_tsr_p2head_s0", ← 人可读 + 唯一 "code": { "commit": "d41d8cd98f00b204e9800998", ← **必须** "dirty": false, ← **必须**：true 意味着不可复现 "repo": "git@internal:perception/tsr" }, "data": { "train": "tsr_v7.2 (sha256:9f86d0…)", ← 数据也要版本 "val": "tsr_eval_v3 (frozen 2026-06-01)", "buckets": "size/light/weather/class" ← 分桶定义也是数据的一部分 }, "config_hash": "a3f5…", "config": { …完整展开，不要只存 diff… }, "env": { "python":"3.11.9", "numpy":"1.26.4", "torch":"2.4.1+cu121", "gpu":"A100-80G", "driver":"550.54" }, "seed": 0, ← **必须**：没有种子=没有对照 "metrics": { ← **全量**，不是只存 mAP "mAP": 0.8213, "mAP50": 0.9410, "by_size": {"<16px":0.412, "16-32":0.701, "32-64":0.868, ">64":0.912}, "by_light": {"day":0.851, "night":0.674, "backlit":0.612}, "by_class": { …全部类别… }, "fp_per_km": 0.83, "latency_p50_ms": 8.9, "latency_p99_ms": 9.2 }, "artifacts": { "ckpt":"s3://…/best.pth", "onnx":"…", "engine":"…" }, "wallclock_h": 11.4, "notes": "P2 层实验，对照 run 2026-08-17_tsr_base_s0" }

直白说

为什么 dirty: true 要当成红线？因为它意味着这次 run 用的代码在世界上任何地方都不存在——不在 git 里，不在别人机器上，只在你当时那个工作区。三天后你 checkout 到别的分支，这次实验就永久失去了复现可能。而实验结果一旦不可复现，它在后续所有对比里都是不可用的——你不知道它的 baseline 是什么状态。

严谨说

更微妙的是 metrics 必须存全量这一条。常见做法是只把 mAP 写进 tracking 系统，因为「其他的以后要看再算」。问题是「以后」通常意味着评测代码已经改过、评测集已经加过数据、分桶定义已经调整过——于是你拿不到当时那个分桶数字了，历史 run 之间的分桶对比永久失效。存储成本是几 KB，重建成本是重跑一次评测（如果还能重建的话）。这条规则可以推广：凡是「重新计算比存下来贵得多」的量，就在产生的那一刻存下来。

只讲成功的项目叙事 = 没负责过

交付纪律在面试里的考法比你想的直接。常见问法是「讲一个你负责的项目，从头到尾」——听起来是叙事题，实际上面试官在数三样东西：①你说的每个指标有没有对应的评测口径；②你说的每个改进有没有对应的验证方式；③你有没有提到任何一次回滚、失败或代价。只讲成功、只讲涨点、不讲代价的叙事，会被判定为「没有真正负责过」——因为真实的项目里一定有回滚、有掉点、有为了赶版本做的妥协。模块 04 会把这套叙事的结构完整拆开。

直白说

一个具体例子说明「落地层」是什么意思。C58 教了 repeat factor sampling、Focal Loss、copy-paste、主动学习触发——四个处理长尾的手段。但真实场景里你不会四个一起上：你要先知道「尾部类现在的 AP 是多少、漏检是因为召回不足还是错分、样本量是 30 张还是 300 张」，才知道该上哪一个。这个「先诊断再开方」的流程，C58 不教（它教药），C61 教（它教诊断）。

严谨说

反过来说，C61 的方法论如果没有前八门课支撑，会退化成正确但无用的废话。「要做分桶评测」——按什么分桶？（C55 的失效模式四象限 + C57 的尺寸分层给出维度）。「要做消融」——消融哪些组件？（C56 的增强算子 + C53 的分配策略给出候选）。「要归因」——候选原因有哪些？（C60 的三层鸿沟 + C58 的数据问题类型给出清单）。方法论的价值与它所依赖的领域知识密度成正比，这也是为什么本课的每一个模块都会大量回引前八门课的具体结论。

学习顺序上的一个建议：不要等 C53–C60 全部学完再来学 C61。更有效的方式是先把本模块和 m01（实验设计）过一遍，建立「任何结论都要问怎么验证的」这个反射，再去学前八门课——这样你读每一个「这个方法涨了 X 点」的结论时，会自动去找它的实验条件。本课的 m02（误差分析）和 m05（面试演练）则适合放到最后。

6面试评估的真实维度：面试官在打什么分

最后把视角切到面试。理解面试官的评分维度，比多背十篇论文有用——因为它决定了你同样的知识该怎么组织输出。

一个成熟的检测岗面试官，本质上在估计一个量：「把一个检测模块交给这个人独立负责，出事的概率有多大」。所有问题都是这个估计的探针。

评估维度面试官怎么探满分信号不及格信号
基础扎实度白板写 IoU / NMS / mAP；追问边界情况边界情况主动处理（无交集、包含、score 相同、空输入），并说明为什么这么处理能写主干但边界全错；或写不出来只能描述
机制理解 vs 名词记忆「DETR 为什么不需要 NMS」「RT-DETR 凭什么快」能把机制拆成独立的部件并各自解释（如「无 NMS 来自一对一分配，与 Transformer 无关，YOLOv10 也做到了」）复述论文摘要；说不出「不用它会怎样」
指标意识「这个改动涨了多少」「+0.3 算提升吗」报区间不报点估计；主动说分桶；主动说代价；知道 +0.3 可能是噪声并说得出为什么报一个精确数字但说不清评测口径
归因能力「线上某类标志漏检，怎么排查」「INT8 掉 3 个点怎么办」给出能砍掉一半候选的第一个检查，而不是一串固定清单背诵式的排查步骤，顺序与信息量无关
工程成熟度「你怎么保证这个对比是公平的」「讲一次失败的实验」主动提代价、回滚、妥协、没成功的尝试全是成功故事；从不提代价
领域适配「TSR 和通用检测有什么不同」「水平翻转有什么坑」能把通用知识翻译到 TSR 的物理约束上（像素尺寸、颜色语义、代价不对称）把 COCO 的经验直接搬过来

这六个维度里，指标意识与归因能力是区分度最高的两项——因为它们无法靠短期背诵获得，也最能反映真实的工程经历。这正是本课把 m01（实验设计与归因）和 m02（误差分析）放在最前面的原因。

直白说

有一个很实际的推论：如果你没有真实的车载项目经历，最有效的补偿不是编经历，而是把方法论讲到无懈可击。面试官分得清「做过」和「没做过」，但他更在意「你知不知道该怎么做」。一个诚实的回答——「我没有量产 TSR 的经历，但如果让我设计这个评测体系，我会这样做：……（然后给出分桶维度、门禁规则、代价不对称的处理）」——比一个编造的项目安全得多，也有效得多。

严谨说

反过来，把课程项目讲成生产项目是最容易被戳穿的策略。追问模式非常固定：「你的评测集有多少帧？」「误报率是每公里多少次？」「上线后回滚过吗？」——这些数字编不出来，因为它们之间有约束关系（帧数、目标数、FP/km、评测集构成必须自洽）。更安全也更强的做法是把课程项目如实讲，但把方法论讲满：「这是一个合成数据上的实验，规模是 XX，我知道它和量产的差距在 YY，如果拿到真实数据我会先做 ZZ。」这个回答同时展示了诚实、规模感和方法论——三个都是加分项。

把整门课的目标压成一句：让你在被追问三层之后，答案依然有内容。第一层（是什么）靠记忆，第二层（为什么）靠理解，第三层（你怎么知道 / 代价是什么 / 不用它会怎样）靠的就是本课教的三个能力。面试的胜负基本都在第三层分出来。

7研究前沿与开放问题

本课的主题——实验方法、归因、可复现——在学术界正处在一轮认真的反思中。以下几条既是开放问题，也是很好的面试谈资。

  • 机器学习的可复现性危机。大量被广泛引用的「改进」在受控重复实验下无法复现，或者提升完全落在种子方差内。Bouthillier 等人的工作系统地量化了 benchmark 里的方差来源（数据划分、初始化、数据顺序、超参搜索），结论相当刺耳：许多论文报告的差距小于它们自身的方差。这直接支撑了本课 m01 的核心主张。
  • 检测任务的显著性检验几乎是空白。NLP 有 Dodge 等人推动的「报告预算与期望最大值」规范，RL 有 Henderson 等人的多种子呼吁，而检测领域至今主流做法仍是单种子单次 COCO mAP。原因很现实：一次 COCO 训练要几十 GPU-小时，跑 10 个种子的成本无法接受。「在训练成本高到做不起重复实验时，如何得到可信结论」是一个真正的开放问题——目前的替代方案（分桶一致性、跨数据集一致性、机制解释）都只是弱证据。
  • Benchmark 过拟合与评测集老化。同一个测试集被社区反复使用多年后，报告的提升有多少来自对该测试集的隐性过拟合？Recht 等人在 ImageNet/CIFAR 上的重采样实验给出了量化答案（新测试集上准确率普遍下降，但排序基本保持）。对 TSR 而言这个问题更尖锐，因为评测集通常来自与训练集同一批采集，域内相关性远高于 ImageNet。
  • 消融的归因理论。加法式与减法式消融给出不同结论已是共识，Shapley 值提供了公理化的公平归因，但代价是 $2^k$ 次实验。如何在少量实验下估计交互作用（部分因子设计、代理模型、主动实验设计）在 ML 系统里应用得还很少——而这是统计学里成熟了几十年的工具。
  • 自动化实验管理与「智能体做实验」。随着 agent 能自动改配置、跑训练、读指标，「谁来保证单变量原则和统计严谨性」变成了一个系统设计问题：自动化会把「试到显著为止」这种坏实践的速度放大几个数量级。多重比较校正、预注册（pre-registration）这类原本属于临床试验的做法，正在被重新讨论。
  • 评测与下游价值的脱节。mAP 涨了，路测体验没变——这在自动驾驶里是常态（C55 m05 展开）。如何设计与下游安全收益对齐的离线指标，仍然没有公认答案；代价敏感指标、场景加权 mAP、违规率代理都各有缺陷。

★ 必读：Bouthillier et al., Accounting for Variance in Machine Learning Benchmarks（MLSys 2021）——把 benchmark 方差按来源分解并给出「该跑多少次」的实用建议，是本课 m01 的直接理论基础。★ Dodge et al., Show Your Work: Improved Reporting of Experimental Results（EMNLP 2019）——「报告调参预算与期望最大值曲线」这个规范的源头，解决的是「新方法调了 200 组、baseline 用默认值」的不公平。★ Henderson et al., Deep Reinforcement Learning that Matters（AAAI 2018）——多种子、方差、报告规范的经典警世之作，结论在检测领域同样成立。
