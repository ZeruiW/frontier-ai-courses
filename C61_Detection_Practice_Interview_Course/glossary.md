# 术语词典 · Glossary（检测工程实战与面试实务）

> 按主题分组。每条给出：**英文 / 中文 / 一句话定义 / 为什么重要 / 常见误解**。
> 这门课的术语和前八门不同——它们大多不是「模型的零件」，而是**你用来对自己的结论负责的工具**。
> 面试里被追问「你怎么知道这个提升是真的」「你怎么定位到这个原因的」时，答案就在这里面。
>
> 与相邻课程的分工见 [README](README.md)：统计学通论在 C40、实验跟踪与门禁的工程形态在 C37、
> 检测评测指标的定义在 C18/C55、部署侧排查在 C60。**本课聚焦「判断、归因、表达」这三件事。**

## 一 · 实验方法与统计 · Experiment Method & Statistics

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| seed variance | 种子方差 | 同一份代码、数据、超参，只改随机种子重跑，指标出现的波动。 | 检测任务上 mAP 典型波动 **±0.2–0.5**，这是判断「多大算提升」的地板线。**面试里主动提这一点能立刻显出水平。** | 以为固定种子就消除了方差。固定种子只是**冻结**了这次抽样，方差仍在——它衡量的是你的结论对随机性的依赖程度。 |
| sources of variance | 方差来源 | 权重初始化、数据顺序、增强采样、dropout、cuDNN 非确定性算子、多卡归约顺序。 | 定位方差来源决定了能不能降低它：数据顺序可控，cuDNN 非确定性只能关（代价是变慢）。 | 以为「设了 `torch.manual_seed` 就完全可复现」。DataLoader worker、cuDNN benchmark、AMP 都各有自己的随机源。 |
| controlled comparison | 受控对比 / 单变量原则 | 两次实验之间**只允许有一个差异**，其余全部对齐。 | 这是归因的前提。没有它，你不知道涨的 0.5 是新模块的功劳还是顺手多训了 20 epoch。 | 以为「我只改了一行代码」就是单变量。改增强会改变有效训练量、改分辨率会改变有效 batch，**耦合改动比你想的多**。 |
| the five "same" | 公平对比的五个同 | 同 epoch / 同增强 / 同分辨率 / 同调参预算 / 同评测集。 | 少任何一个，对比结论都不成立；论文里大量「提升」死在第四条上。 | 以为第四条（同调参预算）可以豁免。**给新方法调 50 组、给 baseline 调 3 组**，是学术界与工业界最普遍的不公平。 |
| ablation study | 消融实验 | 逐个去掉/加上组件，看指标变化，用来归因。 | 「你怎么知道是哪个改动起作用」的标准答案；YOLOX 的 Table 2 是范本。 | 以为消融就是「删了看掉多少」。**删除与添加会给出不同结论**（下两条），报的时候必须说清是哪种。 |
| additive ablation | 加法式消融 | 从 baseline 出发，每次只**加**一个组件（baseline + X）。 | 回答「这个组件单独能带来多少」，适合论证某个新点子的价值。 | 以为它等价于减法式。加法式会**低估**有协同效应的组件（X 只有在 Y 存在时才发挥作用）。 |
| subtractive ablation | 减法式消融 | 从完整系统出发，每次只**去掉**一个组件（full − X）。 | 回答「这个组件现在还有没有必要留着」，是工程上更该做的那种。 | 以为掉得少就说明组件没用。可能是**功能被其他组件冗余覆盖**了——两者一起去掉才会崩。 |
| interaction effect | 交互效应 | 两个改动一起用的收益 ≠ 各自单独收益之和。 | 解释了加法式与减法式为什么会矛盾，也解释了「A+B 都涨但一起用反而掉」这种常见现象。 | 以为收益可加。**强增强 + 长训练**是典型正交互，**强增强 + 小模型**是典型负交互（欠拟合）。 |
| paired test | 配对检验 | 让两个方法在**同一批种子/同一批样本**上比较，检验差值而非各自的均值。 | 配对消掉了共同的噪声源，**同样的种子数下功效比非配对高数倍**——这是最省算力的统计技巧。 | 以为要跑两组独立实验才严谨。恰恰相反，**能配对就一定要配对**；不配对是在白白扔掉信息。 |
| paired bootstrap | 配对自助法 | 对样本（图或类别）有放回重采样，每次重算两个方法的指标差，得到差值的分布。 | 对 mAP 这种**非均值型、非可加**的指标，解析式检验不适用，bootstrap 是最实用的替代。 | 以为对「模型」重采样。要重采样的是**评测样本**（逐图或逐类），不是模型输出本身。 |
| bootstrap confidence interval | 自助置信区间 | 用重采样分布的分位数（如 2.5%/97.5%）作为区间估计。 | **报区间比报点估计有说服力得多**：「+0.4 [−0.1, +0.9]」立刻说明了这个提升还不牢靠。 | 以为区间越窄越好。区间宽是事实，把它藏起来只是把风险推给下一个人。 |
| permutation test | 置换检验 | 随机交换两个方法的配对结果，看观测到的差值在零假设分布里排第几。 | 假设最少的检验，配对场景下几行代码就能写完，**面试里说得出它就是加分**。 | 以为它和 t 检验只是形式不同。置换检验**不假设正态**，小样本（3–5 个种子）下更可信。 |
| p-value | p 值 | 假设两法无差异时，观测到当前或更极端差异的概率。 | 是「这个提升可能是噪声吗」的量化回答，也是门禁规则的输入。 | 以为 p 小就说明提升大。**p 值同时被效应量和样本量驱动**；跑 50 个种子能让 +0.05 也显著，但它没有工程价值。 |
| effect size / Cohen's d | 效应量 | 差值相对于波动的标准化幅度，d = (μ₁−μ₂)/σ_pooled。 | 它回答的是「差多少」而不是「有没有差」，**工程决策要的是这个**。 | 以为显著就等于重要。**统计显著 + 效应量微小 = 不值得上线**，因为它换不回增加的复杂度与风险。 |
| statistical power | 统计功效 | 当真实差异存在时，你的实验能把它检出来的概率（常取 0.8）。 | 功效不足的实验，**不显著这个结果本身没有任何信息量**——你不能说「没提升」，只能说「没看出来」。 | 以为不显著就是没效果。这是最常见的误读；先算功效，再解释阴性结果。 |
| power analysis | 功效分析 | 由「想检出的最小效应 + 已知方差 + 目标功效」反推需要的样本量（这里是种子数）。 | 把「跑几个种子」从拍脑袋变成计算：**要以 80% 把握检出 +0.3、σ≈0.3 的配对差异，大概需要 8–10 个种子**。 | 以为它只在做实验前有用。**事后功效分析**同样重要：它告诉你为什么你的三种子实验什么都证明不了。 |
| MDE | 最小可检出效应 | 在给定种子数与方差下，你有 80% 把握能检出的最小提升。 | 反过来用最实际：**三个种子的 MDE 可能是 +0.6，那么你所有 +0.3 的结论都是空的**。 | 以为可以靠「多测几个评测集」代替多种子。评测集变了就换了问题，方差来源也不同。 |
| multiple comparisons | 多重比较 | 同时做多个检验时，至少一个偶然显著的概率急剧上升。 | 一次跑 12 组消融、每组 α=0.05，**至少一个假阳性的概率约 46%**——这就是「我试了很多都涨了」的真相。 | 以为「我只关心其中一个」就不用校正。只要你是**看完全部结果再挑的**，就必须校正。 |
| Bonferroni correction | 邦费罗尼校正 | 把阈值改成 α/m（m 为检验数）。 | 最简单、最保守，检验数少（<5）时够用。 | 以为它总是太保守所以不用。m 小的时候它和更精细的方法差别不大，**而它一行就能实现**。 |
| Benjamini–Hochberg (BH) | BH 校正 / FDR 控制 | 把 p 值升序排，找最大的 k 使 p₍k₎ ≤ (k/m)·q，前 k 个判为显著；控制的是**假发现率**。 | 消融实验的默认选择：既不像 Bonferroni 那样漏掉真信号，又能把「一堆假阳性」摁住。 | 以为它控制的是「至少一个假阳性」。不是——它控制的是**在你宣称显著的那些里面，假的占比**，这更贴合筛选场景。 |
| winner's curse | 赢家诅咒 | 在一堆噪声里挑出的「最好」结果，其真实水平系统性地低于观测值。 | 解释了为什么排行榜第一名换个测试集就掉下来，也解释了为什么你精挑细选的超参在新数据上不灵。 | 以为多试几组只是「多花点算力」。**试得越多，你选出的那个被高估得越厉害**——这是数学必然，不是运气。 |
| p-hacking / HARKing | p 值操纵 / 事后编假设 | 反复调整评测口径直到显著；或先看到结果再编一个「本来就想验证」的假设。 | 它们是「我的方法在 A 数据集的 B 子集上涨了 2 个点」这类结论的来源，**在面试里会被一眼识破**。 | 以为只有学术界才有。工业界的形态是「换个评测集/换个阈值/去掉两个坏 case 再报」，更隐蔽也更常见。 |
| tuning budget | 调参预算 | 分配给每个方法的超参搜索次数与算力。 | **不同预算下的对比无效**；报告里必须写清两边各搜了多少组。 | 以为「我用了默认参数所以公平」。默认参数是**为 baseline 调过的**，对新方法反而不公平。 |
| compute-matched comparison | 同算力对比 | 两个方法用相同的总训练算力（而非相同 epoch 数）比较。 | 当新方法每步更慢时，同 epoch 对比是在偷算力；**部署视角下同算力才是真问题**。 | 以为同 epoch 就是公平。DETR 系与 YOLO 系的对比里，这个差别能颠覆结论。 |
| reproducibility vs replicability | 可复现 vs 可重复 | 前者：同代码同数据同环境能得到同结果；后者：别人独立实现也能得到同结论。 | 门禁与回滚依赖前者；论文与技术方案的可信度依赖后者。 | 以为两者是一回事。**你的实验可复现，不代表结论成立**——它可能只是稳定地过拟合了这一个划分。 |
| experiment record schema | 实验记录字段 | 一次实验必须记下的最小集合：代码 commit、数据版本、完整配置、环境指纹、随机种子、全部指标（不只是主指标）。 | 缺任何一项，三个月后这次实验就等于没做过；**这也是面试里「你们怎么管理实验」的标准答案骨架**。 | 以为记了超参就够。**数据版本与环境指纹是最常被漏、也最常导致复现失败的两项**。 |
| adaptive overfitting | 评测集过拟合 | 反复在同一个 test set 上做决策，逐渐把它当成了训练集。 | 解释了「离线一路涨、上车不涨」的一大类情况；也是必须有 holdout 与定期换新评测集的理由。 | 以为不训练在上面就不算过拟合。**你每次看着它做选择，就泄漏了一点信息**，几十次之后就不干净了。 |

## 二 · 误差分析 · Error Analysis

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| error analysis | 误差分析 | 系统性地把「指标为什么是这个值」拆解成可命名、可计数、可排序的原因。 | **它是「下一步做什么」的唯一理性来源**；没有它，改进就是撞运气。面试里这一段最能区分层次。 | 以为误差分析就是「看几张 badcase」。看图是最后一步，**先分解、再抽样、最后才看图**。 |
| TIDE | TIDE 误差分解 | 把 mAP 的损失归到六个互斥类型：Cls / Loc / Both / Dupe / Bkg / Miss，并给出每类的修复收益。 | 检测误差分析的事实标准；**它把一个标量指标变成一张待办清单**。 | 以为它是又一个指标。它是**归因框架**——重点不是六个数字，而是「哪一类的修复收益最大」。 |
| Cls error | 分类错误 | 框定位对（IoU ≥ 阈值）但类别判错。 | 在 TSR 里通常指向**相似标志对**（限速 60/80、禁止驶入/禁止通行），对策是细粒度特征与两级架构。 | 以为分类错就该加分类损失权重。先看混淆矩阵——如果集中在少数几对，**改数据比改损失有效得多**。 |
| Loc error | 定位错误 | 类别对但 IoU 落在 [0.1, 阈值) 之间。 | 小目标场景下 Loc 常是最大项；它指向的是回归损失、分配策略与输入分辨率，而不是分类头。 | 以为 Loc 高就要换 IoU 损失。**在小目标上，Loc 高更可能是分配不公平导致正样本太少**（见 C57）。 |
| Both error | 双错 | 类别与定位同时不对。 | 通常量很小；如果占比异常，往往说明**存在系统性的坐标或类别映射 bug**。 | 以为它是 Cls 与 Loc 的简单叠加。它更像一个 bug 指示灯，**占比突然升高要先怀疑数据管线**。 |
| Dupe error | 重复检测 | 同一个 GT 被多个框命中，多余的那些算 FP。 | 直接指向 NMS 阈值、class-wise 与否、以及一对多分配的去重能力。 | 以为调低 NMS 阈值就能解决。调低会误删密集场景的真目标；**Dupe 高更常见的原因是分数排序与定位质量不对齐**（见 TaskAligned）。 |
| Bkg error | 背景误检 | 在没有目标的地方检出（与任何 GT 的 IoU < 0.1）。 | TSR 里的经典来源是**广告牌、车身贴纸、路牌反光、对向车道标志**；这类误检对下游是直接的错误动作。 | 以为提高分数阈值就能压掉。会连带压掉召回；**正确做法是定向挖掘难负样本**（见 C58）。 |
| Miss error | 漏检 | GT 完全没有被任何框命中（连低分框都没有）。 | 需要和「检出了但分数低于阈值」严格区分——**两者的修复方向完全相反**。 | 以为漏检就是「模型不认识」。先查是不是被 top-k 预筛选、score 阈值或 NMS 截掉了，那是后处理问题不是模型问题。 |
| fix impact / ΔAP | 修复收益 | 假设把某一类误差全部改对，mAP 能涨多少。 | **排优先级的唯一硬依据**：「Bkg 占了 1.2 个 AP，Loc 只占 0.3」直接决定这周做什么。 | 以为各类修复收益可以相加。**它们互相重叠**（修好 Bkg 会改变排序，从而影响别类），只能作相对排序用。 |
| oracle analysis | 上限分析 | 用真值替换掉系统的某一环，看指标上限能到多少。 | 级联系统（两级 TSR）必备：**先知道「分类器换成完美的能涨多少」，再决定投不投入**。 | 以为上限高就值得做。上限高只说明有空间，**还要看逼近这个上限的成本**。 |
| Hoiem-style FP taxonomy | Hoiem 式误检分类 | 把 FP 分为定位不准 / 相似类混淆 / 其他类 / 纯背景四类。 | TIDE 的思想源头（2012 年），**在只有检测结果没有工具链时，手工按这四类归档也很有效**。 | 以为它被 TIDE 取代了。TIDE 更自动化，但 Hoiem 的论文对「不同类别的误差构成差异极大」这一点讲得更透。 |
| per-class AP | 逐类 AP | 每个类别单独的 AP 值。 | mAP 是均值，**均值会把「一个关键类别崩了」完全抹平**；TSR 必须逐类看。 | 以为逐类 AP 低就是样本少。也可能是**该类的标注一致性差**，先抽检标注再下结论。 |
| confusion matrix (detection) | 检测版混淆矩阵 | 在匹配之后统计「GT 类别 × 预测类别」，并额外加上 background 行与列。 | 找出**最容易互错的类别对**；TSR 里这张表几乎总能指出 2–3 对该合并或该加数据的标志。 | 以为可以直接套分类的混淆矩阵。检测必须先做匹配，**且必须有 background 行列**来容纳漏检与误检。 |
| PR curve diagnosis | PR 曲线诊断 | 从曲线形状读出病因，而不只是算它下面的面积。 | 两个高频病症：**高召回段突然崩塌** = 有一批样本模型完全没学到（长尾/某个场景缺数据）；**低召回段就不高** = 最自信的预测都错，通常是数据 bug 或类别映射错。 | 以为只要看 AP 就够。**AP 相同的两条曲线可以对应完全不同的问题**，也对应完全不同的修复动作。 |
| recall ceiling | 召回天花板 | 把分数阈值降到 0 时能达到的最大召回。 | 它把问题一分为二：**天花板低 = 模型/数据问题；天花板高但工作点召回低 = 阈值与排序问题**。这个二分能省掉大量无效尝试。 | 以为召回不够就是要加数据。先看天花板——如果天花板 0.95 而工作点只有 0.7，加数据是浪费。 |
| operating point | 工作点 | 部署时实际使用的分数阈值（及其对应的 P/R）。 | 车端要的从来不是 AP，而是**「FP/km ≤ X 时的召回是多少」**；工作点的选择是产品决策不是算法决策。 | 以为评测阈值和部署阈值该一致。**评测要用 0.001 才能画出完整曲线，部署常用 0.25–0.4**，两者必须分开配置。 |
| threshold sweep | 阈值扫描 | 遍历分数阈值，记录每个阈值下的 P/R/FP 率。 | 是选工作点、也是做代价敏感决策的原始材料。 | 以为扫描一次就定了。**不同场景（夜间/雨天）的最优阈值不同**，成熟系统会做分场景阈值。 |
| FP per km / FPPI | 每公里误检数 / 每图误检数 | 绝对量纲的误检指标。 | precision 是比例，**目标少的时候比例会骗人**；产品与安全团队只认绝对量纲。 | 以为 precision 0.95 就够好。一小时 300 个误检和一小时 3 个误检的 precision 可以完全一样。 |
| stratified sampling (badcase) | badcase 分层抽样 | 按尺寸/场景/类别/误差类型分层，每层抽固定数量来看。 | **随便翻 50 张只会反复看到最常见的那类错误**，最贵的长尾一张都不会出现——这是 badcase 分析最常见的失败方式。 | 以为「随机抽样」就客观。随机抽样忠实反映的是**频率**，而你要找的是**风险**，两者分布完全不同。 |
| slice-based evaluation | 切片评测 | 按预先定义的维度（尺寸/距离/光照/天气/类别组）分桶算指标。 | **整体 +0.3 可能掩盖「雨天 +3、晴天 −1」**；切片是发现这种情况的唯一方式，也是回归门禁的基础。 | 以为切片越细越好。切片太细会让每桶样本数不足，**噪声超过信号**；每桶至少要有能撑起统计的样本量。 |
| Simpson's paradox | 辛普森悖论 | 整体上 A 优于 B，但在每个分组里都是 B 优于 A。 | 提醒你**整体指标可能与所有子群结论相反**；分布变化（如测试集里晴天占比变了）就足以造成它。 | 以为这是理论上的怪谈。在检测里它非常实际：**尺寸分布一变，整体 mAP 的排序就可能翻转**。 |
| label noise (as error source) | 标注噪声 | GT 本身就是错的或不一致的那部分。 | 误差分析必须留一个「标注错」的桶，否则你会花几周去拟合噪声；小目标上标注 ±2 px 就是 25% 的相对误差。 | 以为标注是金标准。**抽检 200 个 badcase 常能发现 10–20% 其实是标注问题**，这个比例本身就是重要结论。 |
| eval matching rule | 评测匹配规则 | 评测时预测与 GT 如何配对（按分数降序贪心、每个 GT 只能被匹配一次、IoU ≥ 阈值）。 | 匹配规则的细节直接决定 TP/FP 计数，**自己实现评测时这里最容易和官方对不上**。 | 以为可以用匈牙利匹配做评测。COCO 用的是**按分数贪心**，换成全局最优会得到系统性偏高的结果，与官方不可比。 |
| ignore region / crowd | 忽略区域 | 标注为「不确定/密集群体」的区域，命中它既不算 TP 也不算 FP。 | 处理不当会让 FP 被严重高估；TSR 里对应「太小/太模糊/背面」的标志。 | 以为忽略区域可以直接删掉。删掉之后模型在那里的检出会被算成 FP，**结论会明显偏差**。 |
| cost-sensitive error | 代价敏感误差 | 给不同类别、不同误差类型赋不同权重后的加权指标。 | 漏检「停车让行」与漏检「景点指示」的代价差几个数量级，**均等权重的 mAP 无法表达这一点**。 | 以为加权只是「调个系数」。权重来自安全分析与产品决策，**算法工程师应该去要这个权重，而不是自己拍**。 |
| decision tree (metric → root cause) | 指标到根因决策树 | 把「指标异常 → 可能原因 → 下一步检查」固化成可执行的分支流程。 | 让排查从「灵光一现」变成**可交接、可复用的流程**；也是模块 02/03 的最终产物。 | 以为经验丰富就不需要流程。流程的价值不在于替你思考，而在于**保证你不会跳过那个最蠢也最常见的可能**。 |

## 三 · 调试与诊断 · Debugging & Diagnosis

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| overfit one batch | 单 batch 过拟合 | 拿 2–8 张图反复训练，看 loss 能不能压到接近 0、能不能把这几张图检得完美。 | **万能的第一诊断**：过不去 = 代码或标签有 bug（搜索空间砍一半）；过得去 = 数据量/超参/泛化问题。半小时就能做完。 | 以为它只验证「模型能学」。它同时验证了**损失、分配、解码、评测**这整条链路是自洽的——这才是它真正的价值。 |
| sanity check | 冒烟检查 | 训练前的一组廉价断言：可视化一个 batch 的图与框、打印类别分布、检查坐标范围。 | 这一步能拦掉八成的数据管线 bug，成本是五分钟。 | 以为「代码跑起来了」就是通过了冒烟检查。**大部分致命 bug 都不报错**，必须靠可视化和断言。 |
| bisect debugging | 二分定位 | 在训练侧与部署侧之间逐层对拍，每次砍掉一半可疑区间。 | 把「不知道错在哪」变成 log₂(N) 次检查；**这是 C60 那套一致性排查的算法本质**。 | 以为要从头逐层看。二分的关键是**每一步都要有可比较的中间张量**，所以「能 dump 中间结果」比调试技巧更重要。 |
| class ID off-by-one | 类别 ID 偏移 | 训练用 0-based、评测用 1-based（或反过来）导致全体类别错位一位。 | **mAP 恒为 0 的头号原因**，且完全不报错；COCO 的 category_id 不连续更容易踩。 | 以为「类别数对上了就没问题」。类别数对、顺序错，指标一样归零；**要比对的是类别名到 ID 的完整映射表**。 |
| coordinate format | 坐标格式 | xyxy（左上右下）/ xywh（左上+宽高）/ cxcywh（中心+宽高）三种常见约定。 | 弄反不会报错，只会让框在图上呈现出**可识别的几何图案**（聚成一团或整体偏移），这是它的指纹。 | 以为只要框的数量对就没错。**一定要把框画到图上看一眼**，这是唯一可靠的验证方式。 |
| normalized vs pixel coords | 归一化 vs 像素坐标 | 坐标是 [0,1] 相对值还是绝对像素值。 | 混用会让所有框缩到左上角一个点（或撑满全图），是评测归零的第二大原因。 | 以为一眼能看出来。当图像正好是 1×1 归一化到某个尺度时，**数值范围可能看起来"合理"**，必须显式断言范围。 |
| channel order (BGR/RGB) | 通道顺序 | OpenCV 读图是 BGR，多数训练框架与预训练权重按 RGB。 | 弄反的指纹很特别：**框的位置基本还对，但分数普遍下降、红蓝相关的类别错得最厉害**——TSR 里红色禁令牌首当其冲。 | 以为弄反了模型就会彻底失效。恰恰相反，它「还能跑」，只是掉几个点到十几个点，因此极难被发现。 |
| normalization mismatch | 归一化不一致 | mean/std 的值、顺序（先除 255 还是先减均值）、或数据类型转换时机不同。 | 与通道顺序并列的隐蔽杀手，症状同样是「能跑但掉点」。 | 以为「都用了 ImageNet 的 mean/std」就一致。**有的实现是 0–255 尺度的 mean，有的是 0–1 尺度的**，差 255 倍。 |
| letterbox inverse transform | letterbox 逆变换 | 把检测框从 padding+缩放后的坐标系还原回原图坐标系。 | 写错是「框整体偏移一个固定量」最常见的原因，且**在方图上测试不出来**（padding 为 0）。 | 以为用非方形图测一次就够。要用**极端长宽比**（如 1920×640）测，才能暴露 padding 方向与取整的问题。 |
| NaN loss | 损失变 NaN | 训练途中 loss 变成 NaN 或 inf。 | 四条支路要按顺序查：**学习率过大 → 数值溢出（AMP / exp / log(0)）→ 坏标注（宽高为 0 或负）→ 除零（无正样本时的归一化分母）**。 | 以为一定是学习率。检测里**「某个 batch 恰好没有正样本」导致除零**是极高频且极隐蔽的一条。 |
| gradient health check | 梯度健康检查 | 定期统计各层梯度范数、NaN 计数、零梯度比例并打印。 | 让「训练不对劲」从主观感觉变成可观测量；**梯度范数逐层跨 3 个数量级**通常意味着初始化或归一化有问题。 | 以为只看 total_norm 就够。**逐层看才有诊断价值**，总范数正常可以掩盖某一层已经死了。 |
| exploding / vanishing gradient | 梯度爆炸 / 消失 | 梯度范数指数级增大或趋近 0。 | 前者对应 NaN 与 loss 突刺，后者对应 loss 平台期；两者的处方完全不同（裁剪/降 lr vs 改初始化/加残差/换激活）。 | 以为梯度裁剪能治消失。裁剪只管上界；**消失要靠结构与初始化解决**。 |
| dead ReLU | 死亡神经元 | 某些通道的输出恒为 0，梯度也恒为 0，永久失活。 | 大比例死亡意味着有效容量远小于纸面参数量；用激活直方图可以直接看到。 | 以为换 LeakyReLU/SiLU 就万事大吉。**大量死亡往往是学习率过大留下的伤疤**，换激活只是掩盖症状。 |
| gradient clipping | 梯度裁剪 | 把梯度范数限制在阈值以内。 | 训练稳定性的廉价保险，检测里常设 10–35。 | 以为裁剪越紧越稳。裁得太紧会让**大梯度信号被系统性削弱**，收敛变慢且最终指标偏低。 |
| lr warmup | 学习率预热 | 前若干 iteration 把学习率从很小线性升到目标值。 | 检测器训练早期分配极不稳定，warmup 是防止前 500 步炸掉的标准做法。 | 以为 warmup 只对大 batch 有用。**动态标签分配的检测器几乎都需要它**，因为早期预测是纯噪声。 |
| loss plateau | 损失不降 | loss 从一开始就几乎不动。 | 检查顺序：学习率是否为 0 或过小 → 标签映射是否全错 → 数据是否没打乱 → 是否冻结了不该冻的层 → 优化器是否真的拿到了参数。 | 以为是模型容量不够。**容量问题是最后才该怀疑的**，前四条覆盖了绝大多数实际情况。 |
| data leakage | 数据泄漏 | 训练集里包含了验证/测试集的信息（同一段视频的相邻帧是最常见形态）。 | 症状是**验证指标好得不真实、上线断崖式下跌**；自动驾驶数据按帧随机划分几乎必然泄漏。 | 以为按图像 ID 随机划分就干净。**必须按视频段/路段/时间划分**，相邻帧之间的相似度接近 1。 |
| train/val preprocessing mismatch | 训练验证预处理不一致 | 验证集用了不同的 resize、归一化或增强。 | 「训练正常但验证极差」的头号原因，也是数据泄漏的镜像问题。 | 以为验证集不做增强就等于一致。**确定性的 resize 与 letterbox 方式也必须一致**，否则同样掉点。 |
| shuffle / sampler | 打乱 / 采样器 | 每个 epoch 是否重新打乱、以及各种加权采样器的行为。 | 不打乱会让梯度带上强烈的顺序相关性；分布式下 sampler 忘了 `set_epoch` 则**每个 epoch 顺序完全相同**。 | 以为 `shuffle=True` 就够了。**DistributedSampler 需要每个 epoch 显式调用 set_epoch**，漏掉不会报错。 |
| DataLoader worker seed | worker 随机种子 | 每个 worker 进程都有独立的 RNG 状态。 | 不正确设置会让**所有 worker 生成完全相同的增强序列**，等价于把增强多样性砍掉 N 倍——这是真实发生过的事故。 | 以为主进程设了种子就传下去了。fork 之后各 worker 的 numpy RNG 状态**相同**，必须用 worker_init_fn 区分。 |
| SyncBN | 同步批归一化 | 多卡训练时跨卡统计 BN 的均值方差。 | 单卡 batch 很小时（检测常见 2–4），不同步会让 BN 统计量噪声极大，**掉点 1–2 mAP 且难以察觉**。 | 以为 SyncBN 总是更好。它有通信开销；**单卡 batch ≥ 16 时收益很小**，得权衡。 |
| BN running stats | BN running 统计量 | 推理时使用的滑动平均均值/方差。 | 训练/推理模式切错、或 fine-tune 时冻结方式不当，会造成「训练 loss 很低但一 eval 就崩」。 | 以为 `model.eval()` 只影响 dropout。它同时切换 BN 的行为，**这是新手最常踩的一个坑**。 |
| AMP overflow | 混合精度溢出 | FP16 下中间值超出表示范围变成 inf。 | 检测里的 exp（框解码）与大 IoU 面积计算是高危点；GradScaler 的反复 skip 是它的信号。 | 以为开了 GradScaler 就安全。**前向的 inf 它救不了**，只能把敏感算子强制回 FP32。 |
| EMA | 权重滑动平均 | 维护一份指数滑动平均的权重用于评测。 | 检测里 EMA 常带来 +0.3–1.0 mAP，**几乎免费**；但也是「评测和保存的权重不是同一份」这类混乱的来源。 | 以为 EMA 权重可以直接继续训练。它是评测用副本，**恢复训练要用原始权重**，弄混会导致复现失败。 |
| determinism flags | 确定性开关 | cudnn.deterministic / benchmark、确定性算子、环境变量等。 | 追查「同种子跑两遍结果不同」时必须先关掉非确定性；**代价是训练变慢 10–30%**。 | 以为确定性应该常开。日常训练不需要；**只在复现 bug 时开**，否则白白损失吞吐。 |
| shard overlap | 数据分片重叠 | 多卡训练时不同 rank 拿到了重复样本。 | 会让有效数据量小于预期、且各卡梯度相关性升高，症状是「多卡不如单卡」。 | 以为框架都处理好了。自定义 sampler 或 IterableDataset 时**极易写错**，要用样本 ID 计数验证。 |
| checkpoint completeness | 检查点完整性 | 除权重外还需保存优化器状态、scaler、EMA、epoch、随机数状态。 | 少任何一项，resume 出来的曲线都和不中断的不一样，**回滚与复现都会失败**。 | 以为存了 state_dict 就够。**优化器动量与随机数状态**是最常被漏掉的两项。 |
| bug fingerprint | bug 指纹 | 每类数据管线 bug 在指标与可视化上留下的可识别特征。 | 有指纹就能从症状反查原因：**类别偏移 → 逐类 AP 整体位移；通道顺序 → 分数普降但框位置对；坐标格式 → 框镜像或聚团**。 | 以为要靠经验积累。指纹是可以**主动构造实验做出来的**——模块 03 的 notebook 就是干这件事。 |

## 四 · 叙事与沟通 · Narrative & Communication

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| STAR | 情境-任务-行动-结果 | 行为面试的标准结构：Situation / Task / Action / Result。 | 它强制你把「我做了个检测项目」展开成有因果的故事；**检测版的关键在 Action 里要包含「试过什么没成功」**。 | 以为 STAR 是套话模板。它是**信息完整性检查表**：缺 S 听众不知道难在哪，缺 R 听众不知道值不值。 |
| baseline | 基线 | 你的改动所对照的那个参照系统。 | 没有基线的数字全是空的；**「基线是什么、它是不是被认真调过」是面试官最常问的第一个追问**。 | 以为基线越弱越好显得提升大。弱基线是**减分项**——有经验的面试官会立刻问「这个 baseline 你调了吗」。 |
| paired metrics | 成对指标 | 每报一个收益就同时报它的代价（延迟 / 显存 / 训练时长 / 复杂度 / 其他场景掉点）。 | **只讲涨的那一半，是初级与资深最明显的分界线**；主动说代价反而会赢得信任。 | 以为讲代价会削弱说服力。恰恰相反——**不讲代价的人会被反复追问直到讲不出来**，那时才是真的翻车。 |
| attribution | 归因 | 说明观测到的收益来自哪个具体改动、以及你怎么确认的。 | 面试里「这个提升是怎么验证的」几乎必问，答案需要用到模块 01 的全部内容。 | 以为「我做了 A 然后涨了」就是归因。**那是时间先后，不是因果**；必须有受控对比与显著性。 |
| counterfactual | 反事实 | 「如果不做 X，会怎样」的明确回答。 | 它是归因的表达形式，也是消融实验存在的意义。 | 以为反事实只能靠实验。**有时可以靠机制推理给出方向与量级**，但必须明说这是推理不是实测。 |
| negative result | 阴性结果 / 失败实验 | 试过但没效果、或效果为负的尝试。 | **主动讲失败实验是资深度最强的信号之一**：它证明你在做归因，也证明你说的成功不是幸存者偏差。 | 以为面试要「只讲成功」。只有成功的履历听起来像编的；**一个讲得清楚的失败，胜过三个模糊的成功**。 |
| quantified impact | 量化影响 | 用数字表达结果：从多少到多少、在什么口径下、代价多少。 | 「显著提升了小目标检测」是零信息；「APs 从 18.4 到 22.1（3 seed 均值，配对 bootstrap 95% CI [+2.9, +4.5]），延迟 +1.2 ms」是信息。 | 以为数字越多越好。**数字必须带口径**：没有测量条件的数字比没有数字更糟，因为它会被追问。 |
| business impact | 业务影响 | 技术指标最终对应的产品/安全/成本变化。 | 自动驾驶里的翻译是：漏检率下降 → 某类接管减少；FP/km 下降 → 误刹减少。**能做这层翻译的候选人很少**。 | 以为业务影响必须有线上数据。没有实测时可以**给出推导链与假设**，讲清楚假设同样有说服力。 |
| BLUF / 结论先行 | Bottom Line Up Front | 先给结论与量级，再展开过程。 | 面试与技术评审的注意力都在前 30 秒；**先讲背景再讲结论的人，常常没讲到结论就被打断了**。 | 以为按时间顺序讲最自然。自然但低效——**听众需要先知道去哪，才能判断你的每一步值不值得听**。 |
| pyramid principle | 金字塔原理 | 结论在顶，下面挂 3 条互斥且穷尽的支撑，每条再挂证据。 | 给你一个可复用的组织方式，尤其适合系统设计题这种需要覆盖面的回答。 | 以为它是写作技巧。它首先是**思考的检查表**：如果三条支撑互相重叠，说明你的拆解还没想清楚。 |
| design doc / ADR | 设计文档 / 决策记录 | 记录「面临什么选择、考虑了哪些方案、为什么选这个、什么条件下要重新评估」。 | 它是「交付纪律」的具体载体，也是**你在面试里描述工作方式时最有说服力的证据**。 | 以为写文档是拖慢进度。真正拖慢进度的是**三个月后没人记得当时为什么这么选**，于是把讨论重来一遍。 |
| model card | 模型卡 | 记录模型的用途、训练数据、评测结果（含分组指标）、已知局限与不适用场景。 | 把「我知道它在哪些场景会失效」写成制度；**安全相关系统里这是必需品而非加分项**。 | 以为模型卡是给外部看的合规文档。它最大的读者是**三个月后的你和接手的同事**。 |
| datasheet for datasets | 数据表 | 记录数据集的采集动机、采集方式、构成、清洗、标注流程与已知偏差。 | TSR 数据的区域偏差、天气偏差、采集车配置差异，全都必须写在这里，否则跨域失败无从解释。 | 以为「数据就是数据」。**数据集是一次采样决策的产物**，不记录这些决策，后续所有分析都缺少前提。 |
| reproducible handoff | 可交接 | 别人拿到你的仓库、配置与文档，能独立复现你的结论。 | 「交付纪律」的验收标准；也是团队里被信任的基础。 | 以为交接就是把代码给出去。**没有数据版本与环境指纹的代码是不可交接的**。 |
| ownership framing | 归属表述 | 明确区分「团队做的」和「我做的」。 | 面试官在评估**你**；含糊的「我们」会让你的贡献被整体折价。 | 以为强调个人会显得不 team player。正确做法是**先讲团队目标，再明确自己负责的那一块**，两者不冲突。 |
| probing question | 追问 | 面试官对你答案的深挖，通常连续三层。 | 追问才是真正的评估环节；**第一层答案人人会背，第二三层区分真假**。 | 以为答完一个问题就结束了。**没有追问往往意味着面试官已经不感兴趣**，这不是好消息。 |
| depth ladder | 三层追问阶梯 | 典型顺序：为什么不用 X → 这个提升你怎么验证的 → 给你 10 倍资源你会做什么。 | 三层分别测**知识广度 / 方法论 / 判断力**，可以逐层准备。 | 以为第三层是闲聊。它是**最能看出 seniority 的一层**，因为它考察你有没有系统性的路线图。 |
| calibrated confidence | 校准的自信 | 知道的说清楚，不知道的直接说不知道并给出你会怎么查。 | 「我不确定，但我会先做 A 排除掉 B」比硬猜有价值得多；**这本身就是归因能力的展示**。 | 以为承认不知道会掉分。硬编答案被追问穿帮才是真正的致命伤，**面试官几乎都能听出来**。 |
| elevator pitch | 电梯陈述 | 30 秒讲清一个项目：问题、你做了什么、结果、代价。 | 自我介绍与「讲一个你最有成就感的项目」都以它开场，决定了后面 10 分钟的走向。 | 以为要把所有细节塞进去。它的作用是**让对方选择往哪深挖**，细节是留给追问的弹药。 |
| ten-minute story | 十分钟深度故事 | 一个能撑满 10 分钟、经得起三层追问的完整项目叙事。 | 一场面试通常只够讲 2–3 个；**准备 3–4 个覆盖不同能力维度的故事，比准备 20 个浅故事有效**。 | 以为故事越多越好。故事多而浅会让每个都被问穿；**深度覆盖比数量覆盖重要**。 |

## 五 · 面试题型与应答 · Interview Question Types

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| whiteboard coding | 白板编码题 | 当场手写一段核心算法（检测岗几乎必考 IoU 与 NMS）。 | 考的不是背诵，是**边界情况的意识**：无交集、包含关系、零面积框、分数并列、空输入。 | 以为写出主逻辑就过了。**主逻辑人人会写，边界情况才是打分点**；主动说出你考虑到的边界比写完更重要。 |
| think aloud | 出声思考 | 边写边讲你的判断依据与取舍。 | 面试官评估的是**思考过程**；沉默着写完再解释，中间的信息全丢了。 | 以为出声会显得没想清楚。相反，**沉默是最大的风险**——写错了没人能及时把你拉回来。 |
| edge case | 边界情况 | 输入的极端或退化形态。 | 检测里的经典集合：IoU 的零并集、NMS 的空候选、mAP 的某类无 GT、匈牙利的矩形代价矩阵。 | 以为边界情况是「加几个 if」。它们往往揭示**你对定义理解得够不够准**（某类无 GT 时该跳过还是记 0？COCO 的答案是跳过）。 |
| complexity analysis | 复杂度分析 | 说清时间/空间复杂度以及实际瓶颈。 | NMS 的 O(n²)、匈牙利的 O(n³)、mAP 的排序 O(n log n) 都是标准追问点。 | 以为报个大 O 就够。**要能说出在实际规模下哪一项才是瓶颈**（TSR 一屏几十个目标时 NMS 根本不是瓶颈）。 |
| reference implementation | 参考实现 | 一份自己写过、测试过、能默写的标准版本。 | 白板题的准备方式不是「看懂」，是**默写到肌肉记忆**；模块 05 的 notebook 提供五道题的参考实现与单元测试。 | 以为看懂了就会写。**看懂到写对之间平均隔着 3 次调试**，不动手就等于没准备。 |
| rubric / 评分要点 | 评分表 | 面试官心里那张「答到哪几点算合格/优秀」的清单。 | 知道评分点，你就知道**该先说什么**；模块 05 为每道题都给出了这张表。 | 以为答得多就分高。**漏掉核心点而堆砌周边知识**是典型的低分模式。 |
| answer skeleton | 答案骨架 | 一道题的标准结构与必须命中的关键词。 | 让你在紧张时也不会漏掉核心；骨架 + 现场细节 = 稳定发挥。 | 以为背骨架会显得机械。骨架是**结构**不是台词，细节仍然来自你的理解。 |
| three-part answer | 三段式应答 | 先讲**判断依据**（我会先看什么）→ 再讲**方案**（所以我会做什么）→ 最后讲**验证**（我怎么确认它有效）。 | 这个顺序展示的是工程思维；**反过来（先给方案）会被认为是在背答案**。 | 以为面试官想要的是方案。他们想要的是**你怎么得出这个方案**——方案本身网上都有。 |
| system design question | 系统设计题 | 「设计一个 TSR 的数据-模型-评测-部署闭环」这类开放题。 | 考察面最广，也最能体现 seniority；**必须先澄清约束再开始设计**。 | 以为要讲得越全越好。**不问约束就开讲**是最大的失分点：算力多少、延迟预算多少、有没有标注预算，答案完全不同。 |
| trade-off question | 取舍题 | 「YOLO 和 DETR 你选哪个」这类没有唯一答案的题。 | 考的是你**能不能把偏好变成有条件的推理**：在什么条件下选哪个、判据是什么。 | 以为要坚定地选一个。坚定但无条件的答案是减分的；**「取决于 X，如果 X 则 A，否则 B」**才是想要的。 |
| trap question | 陷阱题 | 「我的方法把 mAP 提升了 0.3，你觉得怎么样」这类。 | 正确应对：**先反问评测协议（几个种子？同一评测集？同预算？）→ 再谈种子方差与显著性 → 最后才给结论**。 | 以为要直接下判断。直接说「不错」暴露没有指标意识，直接说「这是噪声」又太武断；**问清楚再答**才是满分。 |
| behavioral interview | 行为面试 | 用过去的具体经历评估协作、冲突处理、抗压与主动性。 | 大厂几乎必有；**用 STAR 结构 + 真实细节**，编的故事在追问第二层就会露馅。 | 以为技术岗行为面试是走过场。它常常是**最终定级的重要输入**，尤其在 senior 以上。 |
| take-home assignment | 带回家作业 | 给一个小数据集/任务，限时提交代码与报告。 | 评分权重常常在**报告与工程规范**上而非最终指标；这正好是本课 01/04 的内容。 | 以为要把指标刷到最高。**清晰的实验设计、诚实的消融、明确的局限说明**通常比多 0.5 个点更值钱。 |
| live debugging | 现场调试题 | 给一段有 bug 的训练/评测代码让你找问题。 | 直接对应模块 03；**先问症状再看代码**是正确姿势。 | 以为要逐行读代码。**先问「现象是什么」**能把搜索空间砍掉九成——这也是面试官想看到的。 |
| reverse question | 反问环节 | 面试尾声由你提问。 | **你问出口的三个问题，是面试官对你 seniority 的最后一次修正**：问评测体系、数据闭环、团队怎么定义"完成"，都比问加班好。 | 以为反问只是礼节。问「这个岗位的模型上线后由谁负责回归」这类问题，会立刻改变对方对你的印象。 |
| red flag | 减分项 | 会被记下来的负面信号。 | 常见清单：数字说不出口径、只讲收益不讲代价、把团队成果说成个人的、被追问两层就开始编、贬低前公司。 | 以为只有答错才减分。**态度类减分项的杀伤力远大于知识缺口**，因为知识可以补。 |
| calibration of claims | 说法的分寸 | 区分「我实现过」「我读过论文」「我知道这个概念」。 | 分寸感本身就是可信度；**说清楚边界的候选人，其他说法也更容易被采信**。 | 以为要把每件事都说成做过。**面试官会顺着追问到你的知识边界**，边界处的诚实决定整场的可信度。 |
| interview post-mortem | 面试复盘 | 面试后立刻写下被问到的题、卡住的点、当时的回答。 | 它把一次面试变成一份可复用的数据；**两三轮之后你会发现问题高度重复**。 | 以为凭记忆就行。24 小时后细节丢失一半以上，**当天写**是硬要求。 |
