1指标不是结论：mAP 只说「有多差」，不说「差在哪」

先摆一个具体处境。你刚训完一版 TSR 检测器，评测集上 mAP@0.5 = 0.721，上一版是 0.706。接下来你要做什么？加数据？换 backbone？提高输入分辨率？调 NMS 阈值？改标签分配？做 copy-paste？这些每一条都要花 3 天到 3 周，而 0.721 这个数字对「该做哪一条」没有提供任何信息。

这就是初级和资深检测工程师之间最大的一道分水岭。指标回答的是「我现在在哪」，误差分析回答的是「往哪走最省力」。一个只会看 mAP 的人，改进路径本质上是随机搜索；一个会做误差分解的人，每次改动之前就能给出「这条路的收益上界是 +X mAP」。

mAP 把六件完全不同的事压成了一个数

回忆 AP 的定义——按置信度排序、逐条判 TP/FP、累积算 P/R、取单调包络下的面积：

\[\text{AP} \;=\; \sum_{k}\bigl(r_k - r_{k-1}\bigr)\; p_{\text{interp}}(r_k), \qquad p_{\text{interp}}(r) \;=\; \max_{\tilde r \,\ge\, r} p(\tilde r)\]

这个式子里，「一个检测被判成 FP」这件事只有一个出口，但入口有五个：框对了类别错、类别对了框不准、两个都错、这个目标已经被另一个更高分的框认领了（重复）、图里那个位置根本没有目标（背景）。而 recall 没到 1 的原因也不止一个：有些 GT 被上面某类错误「半覆盖」了，有些 GT 是彻底没有任何检测靠近。mAP 把这六种失败混成一个标量，然后你从这个标量里是解不回去的。

直白说

举个立刻能感受到差别的例子：同样是 mAP@0.5 = 0.72，可能是 A：每个类都在 0.70–0.74，模型均匀地「差一点」；也可能是 B：限速牌类 0.95、指路牌 0.93、而「停车让行」只有 0.11。A 需要的是更强的模型或更多数据；B 需要的是查「停车让行」这一类的标注、样本量和是否被别的类吃掉——这是两个完全不同的项目。而这两种情况在 mAP 这个数字上是一模一样的。

严谨说

更严格地说，mAP 是一个聚合统计量（aggregate statistic），它对底层错误分布的可辨识性（identifiability）为零：给定一个 mAP 值，能产生它的 (TP, FP 分类, FN 分布) 组合有无穷多个。误差分析要做的事，就是把这个不可逆的聚合过程部分地反演回去——办法不是从数字反推，而是回到原始的检测-GT 匹配结果，按错误的成因重新分桶，再针对每一桶做「反事实」计算。第 3 节的修复收益（oracle ΔAP）正是这个反事实：如果这一类错误全部消失，mAP 会变成多少？

把本节压成一句话：误差分析的目的不是「知道自己错了」，而是「知道修哪一个最划算」。任何一次改进动作，都应该能回答「它对应哪一类错误、这类错误的收益上界是多少、修它的成本是多少」——这三个问题答不上来，那次改动就是赌博。

「先看 badcase」= 没有流程

面试高频开场题：「线上某类交通标志漏检了，你的排查流程是什么？」如果你的回答从「我会先看看 badcase」开始，面试官基本就给你定档了。正确的开场是：「先确认这是召回问题还是分类问题——因为『漏检』这个词在工程上至少有四种不同的病：真·无检出、检出但被判成别的类、检出但框不准被判 FP、检出但分数低于上线阈值。这四种的修法完全不同，而误差分解能在 10 分钟内区分它们。」面试官想听的是你有一套可复用的分解流程，而不是你很勤奋地看图。

2TIDE 式误差分解：把 FP/FN 拆成六类

TIDE（A General Toolbox for Identifying Object Detection Errors，Bolya et al., ECCV 2020）给出的六类划分，已经是检测误差分析事实上的标准词汇。它的价值不在分类本身，而在于这六类各自对应一条不同的、可执行的修复路径——分完类你就知道该动数据、动标签分配、动 NMS、还是动分辨率。

判定只需要两个阈值

TIDE 用两个 IoU 阈值：前景阈值 $t_f = 0.5$（判 TP 的那条线）和 背景阈值 $t_b = 0.1$（「离目标近到值得归因」的那条线）。对每一个被判为 FP 的检测，先算它与同类 GT 的最大 IoU（记 $u_{\text{same}}$）和与异类 GT 的最大 IoU（记 $u_{\text{other}}$），然后走下面这棵判定树：

一个被判 FP 的检测 d（类别 c，分数 s） │ ├─ u_same >= 0.5 ? ── 是 ──► 它本来能匹配上，但那个 GT 已被更高分的框认领 │ => 【Dupe】重复检测 修法：NMS / 一对一分配 │ 否 ├─ 0.1 <= u_same < 0.5 ? ─ 是 ─► 类别对了，框不够准 │ => 【Loc】定位误差 修法：回归损失 / 分配策略 / 分辨率 │ 否（同类 GT 都离得很远） ├─ u_other >= 0.5 ? ── 是 ──► 框框得很准，但类别判错了 │ => 【Cls】分类误差 修法：细粒度分类 / 两级架构 / 难例 │ 否 ├─ 0.1 <= u_other < 0.5 ? ─ 是 ─► 框也不准、类也不对 │ => 【Both】双错 修法：通常和 Loc 一起治 │ 否 └────────────────────────────► 周围什么都没有 => 【Bkg】背景误检 修法：难负样本挖掘 / 阈值 / 上下文 所有 GT 里，**没有任何检测以 IoU >= 0.1 靠近过**的那些 => 【Miss】漏检 修法：召回侧（分辨率/分配/采样/数据）

直白说

为什么一定要按顺序判、而不是「哪个像就归哪个」？因为这六类不是互斥的自然分类，是人为定义的归因规则。一个框可能同时和同类 GT 有 0.3 的 IoU、和异类 GT 有 0.6 的 IoU——它到底算 Loc 还是算 Cls？TIDE 的答案是「优先归给同类」，理由是「类别对了只是框歪」比「框对了类别错」更容易修，归因应当偏向更可行动的那一侧。你可以不同意这个优先级，但你必须知道它存在——换了顺序，同一个模型的分解结果会不一样。

严谨说

更本质地说，误差归因是一个反事实赋值（counterfactual attribution）问题，而反事实在多因共存时天然不唯一。TIDE 的处理方式是把「归因规则」显式写死成一棵判定树，用可复现性换取唯一性——只要所有人用同一棵树，跨模型、跨版本的分解结果就可比。这和统计里的 Type I/Type III sum of squares 之争是同一类问题：不存在「正确」的分解，只存在「说清楚了的」分解。因此在团队里做误差分析，第一件事是把 $t_f$、$t_b$ 和判定顺序写进评测配置并版本化，否则两个人算出来的 Cls 占比不同，谁也说服不了谁。

分解写错比不写更糟

三个几乎人人踩过的实现坑：

① Dupe 必须在匹配之后判。匹配是按分数降序贪心做的，「这个 GT 已被认领」这个状态依赖顺序；先分类再匹配会把大量 Dupe 错记成 Loc。

② $u_{\text{same}}$ 要对「所有同类 GT」算，不只对「未匹配的同类 GT」算，否则 Dupe 这一类会永远是 0。

③ Miss 的定义必须和 Cls/Loc 不重复计。一个被判成 Cls 错误的检测，其实已经「看见」了那个 GT；如果 Miss 里再把这个 GT 数一遍，你会同时高估 Cls 和 Miss，两边都想修，最后修了个寂寞。

3修复收益：算出「修好每一类能涨多少 mAP」

上一节只是数数。数数会骗人——而且骗得很凶。「背景误检有 4200 个、分类错只有 310 个」这句话听起来结论很明显：去治背景误检。但这个结论在多数情况下是错的。

oracle：一次反事实实验

TIDE 的核心工具叫 oracle（先知）：假装有一个神仙，帮你只修好某一类错误，其他一切不变，然后重新算一遍 mAP。差值就是这类错误的修复收益上界：

\[\Delta\text{AP}_i \;=\; \text{mAP}\bigl(\mathcal{O}_i(D),\; G\bigr) \;-\; \text{mAP}(D,\; G)\]

其中 $D$ 是检测结果集合，$G$ 是标注集合，$\mathcal{O}_i$ 是第 $i$ 类错误的 oracle 算子。六个 oracle 的定义都非常朴素：

oracle它做什么为什么这样定义
O_Loc把 Loc 错误的框吸附到它最接近的同类 GT 上（IoU 变成 1）模拟「回归分支变完美」，但不改变分数与排序
O_Cls把 Cls 错误的预测类别改成它框住的那个 GT 的类别模拟「分类分支变完美」，框保持原样
O_Both同时修类别与框Both 的定义就是两者皆错
O_Dupe删掉重复检测模拟「去重完美」
O_Bkg删掉背景误检模拟「不再无中生有」
O_Miss把彻底没被覆盖的 GT 从评测中移除模拟「这些目标本来就检得到」——注意是改 $G$ 不是改 $D$

为什么数量最多的错误往往最不值钱

答案藏在 AP 的定义里：AP 是按分数排序后累积算的，所以一个 FP 的杀伤力完全取决于它排在第几名。背景误检的分数通常很低（模型自己也不确信），它们排在 PR 曲线的最尾巴，那一段的 recall 增量本来就接近 0，删掉它们对面积的贡献微乎其微。而一个 Cls 错误是双重伤害：它在错的那个类里是一个高分 FP（狠狠压低那条 PR 曲线的头部），同时在对的那个类里造成一个 FN（recall 上不去）。

注意最后一行。ΔAP 只是收益上界，真正的决策变量是「收益 ÷ 成本」。Miss 的 +6.3% 可能需要「把输入分辨率从 640 提到 1280 + 加 P2 层 + 延迟涨 40%」才能兑现一半；Cls 的 +7.8% 可能只需要「把限速类的 crop 送进一个 64×64 的二级分类器」，代价是 0.3 ms。两者的性价比差一个数量级。

直白说

还有一个必须记住的性质：这些 ΔAP 不可以相加。修好 Cls 之后再修 Loc，得到的总收益一般小于 $\Delta\text{AP}_{\text{Cls}} + \Delta\text{AP}_{\text{Loc}}$。原因很直观——两类错误经常打在同一批 GT 上，第一个 oracle 已经把那部分 recall 救回来了，第二个 oracle 再救就没得救了。所以看到「六项加起来 20%，但把所有错误全修好只涨 28% 到 100%」不要慌，这不是 bug。

严谨说

从数学上看，AP 是匹配结果的非线性、非可加泛函：它经过了「排序 → 累积 → 单调包络 → 求面积」四步，其中排序和取 max 都是非线性的。因此 $\mathcal{O}_i$ 的效应不满足叠加原理，$\Delta\text{AP}$ 更接近博弈论里的边际贡献而非独立分量。如果你真的需要一组「可加」的归因值，正确的工具是对六个 oracle 求 Shapley 值（$2^6 = 64$ 次评测，完全跑得动）——但实践中几乎没人这么做，因为决策只需要排序，不需要精确的份额。知道 Cls 最值钱就够了，不必知道它「精确占 34.7%」。

跑过的人和背过的人，一句话就分得出

面试里这是一个极高分的加分点，也是一个极容易翻车的点。被问「你怎么决定下一步做什么」时，说「我会做误差分析」只是及格；说「我会跑 TIDE 分解，拿到六类错误的 ΔAP，然后按 ΔAP 除以我估的工程成本排序，先做性价比最高的那一项；而且我会特别小心『数量多但 ΔAP 小』的背景误检——它排在 PR 曲线尾部，删干净了 mAP 也只涨不到 1 个点」——这才是拿分的回答。

翻车点：把 ΔAP 说成「可以相加的贡献占比」。面试官只要追问一句「那六项加起来等于总差距吗」，就能看出你到底跑过没跑过。

4逐类 AP 与混淆矩阵：找出最容易互相错分的标志对

六类分解告诉你「错在什么机制」，逐类分析告诉你「错在什么对象」。两者正交，都要做。

mAP 的那个「平均」是最危险的一步

mAP 对类别取的是无权重算术平均：一个在数据集中只出现 40 次的「注意落石」和一个出现 12000 次的「限速 60」，在 mAP 里权重完全一样。这带来两个方向相反的陷阱：

  • 陷阱 A（长尾稀释）：你把主力类别从 0.93 提到 0.95，mAP 只涨 0.02/N；而某个尾部类从 0.05 掉到 0.00，mAP 掉 0.05/N——于是「主力变好、长尾变差」的改动在 mAP 上可能是负的，尽管产品体验是正的（或反过来）。
  • 陷阱 B（尾部噪声）：只有 40 个样本的类，它的 AP 方差极大。换个随机种子 AP 可能从 0.31 跳到 0.48。把这种波动当成「我的改动生效了」，是本课模块 01 讲的种子方差问题在类别维度上的变体。

所以逐类表必须三列一起看：类别 AP、该类的 GT 数量、该类 AP 的种子间标准差。只看第一列的人会不停地追逐噪声。

检测的混淆矩阵怎么算（和分类不一样）

分类任务的混淆矩阵是 $C \times C$，每个样本必进一格。检测不是——检测有「无中生有」和「视而不见」，所以矩阵必须是 $(C{+}1) \times (C{+}1)$，多出来的那一行一列就是 background：

直白说

混淆矩阵最容易被忽略、信息量却最大的地方是最后一行和最后一列。很多人把混淆矩阵画成 $C \times C$（因为工具默认这么画），于是「停车让行召回只有 28%」这个致命信息被完全隐藏了——在 $C \times C$ 的矩阵里，这一行的对角线值 23 看起来还行，因为你不知道分母是 81。而对 TSR 来说，「停车让行」漏检和「指路牌」漏检的安全后果差着好几个数量级。

严谨说

工程上还要区分「未检出」与「检出但被判 FP」这两种落进最后一列的情况。前者是召回问题（模型压根没在那个位置输出任何框），后者是定位/阈值问题（有框，但 IoU 没到 0.5，或者分数低于评测的最低分数线）。这两者的修法完全相反：召回问题要动分辨率、标签分配、数据；定位问题要动回归损失与 IoU 阈值口径。所以成熟的评测脚本会把最后一列再拆成两列：miss_no_box 与 miss_low_iou，这正好对应第 2 节里的 Miss 与 Loc。混淆矩阵与 TIDE 分解在这里合流。

混淆矩阵的构造有一个陷阱：你得先决定「拿哪些检测来填矩阵」。用全部检测（含分数 0.01 的）会让最后一行爆炸；用 score > 0.5 的会让矩阵依赖于阈值选择。推荐做法：用「与评测工作点一致的阈值」（见第 6 节）填矩阵，并把阈值写在图标题里。同一个模型在阈值 0.3 和 0.5 下的混淆矩阵可以讲出完全不同的故事——不写阈值的混淆矩阵是不可复现的。

直白说

PR 曲线的最左端（低 recall）对应的是模型最自信的那几十个预测。一个训练正常的检测器，它最自信的预测几乎不可能错——那些是最大、最清晰、最典型的目标。如果连这批都错了一半，说明错的不是「难度」，而是「规则」：模型在按一套规则输出，评测在按另一套规则判分。类别 ID 差 1、坐标是 xywh 被当成 xyxy、评测集的类别表和训练时的顺序不同——这三个占了绝大多数。

严谨说

反过来说，(B) 高召回段崩塌是「难度」问题而非「规则」问题：规则是对的（高分预测都对），只是有一批样本模型确实没学会。崩塌点的位置还能反推出这批样本的规模——如果 PR 在 $r = 0.72$ 处崩掉，说明大约 28% 的 GT 属于这个「学不到」的子集。接下来的动作是明确的：按各种维度（像素尺寸、类别、天气、遮挡度、图像区域）分桶重画 PR，找出哪个桶整段贴地。找到那个桶，你就把一个模糊的「模型不行」变成了一个具体的、可以定向挖数据或改架构的工程问题。

一条心法：PR 曲线的左端诊断「规则」，右端诊断「难度」，中段诊断「能力」。左端有病先别碰模型——去查管线；右端有病先别调参——去分桶。

画 PR 曲线时必须注明三件事，否则曲线不可比：① IoU 阈值（0.5 还是 0.5:0.95 的哪一档）、② 是逐类曲线还是所有类混在一起（后者在长尾数据上几乎无意义，会被头部类完全主导）、③ 是否用了单调包络（VOC 风格的包络会把锯齿抹平，掩盖掉小规模的崩塌）。诊断时建议看不包络的原始曲线——锯齿本身也是信息，密集的锯齿意味着高分区里 TP/FP 交替出现。

6score 阈值与工作点：车端要的是「特定 FP 率下的召回」

这一节讲的是一个几乎所有做过研究、没做过产品的人都会犯的错：用 mAP 选模型，然后随便挑个 0.25 的阈值上线。

mAP 是阈值无关的，产品是阈值有关的

AP 的定义里对分数只用了「排序」，没用「绝对值」——把所有分数开平方，AP 完全不变。这意味着 mAP 对「模型的分数标定得好不好」完全不敏感，而线上系统恰恰是靠分数的绝对值做取舍的。两个 mAP 相同的模型，在 score > 0.4 这个具体工作点上的召回可以差 15 个点。

车端的真实需求长这样：「在误报不超过每 10 公里 1 次的前提下，尽可能早、尽可能全地检出交通标志」。写成优化问题就是：

\[\tau^\star \;=\; \arg\max_{\tau}\; \text{Recall}(\tau) \quad \text{s.t.} \quad \frac{\text{FP}(\tau)}{N_{\text{frames}}} \;\le\; \beta\]

$\beta$ 是产品定的误报预算（FP per frame，或换算成 FP per km / FP per hour）。注意这里根本没有出现 precision。原因是 precision 是个比值，它会随场景里目标的多少而漂移：高速上一公里只有 2 块标志，即使误报率不变，precision 也会比市区低得多。而 FP/frame 是绝对量，它直接对应「司机每天被误报打扰几次」，是产品和安全团队真正能理解的语言。

必须逐类设阈值

TSR 的类别之间代价极度不对称：漏掉一个「停车让行」可能导致路口事故；误报一个「景点指示牌」只是让 HMI 上多闪一下。用同一个全局阈值服务这两类，等于是拿最不重要的类别的误报预算，去限制最重要的类别的召回。

直白说

为什么阈值不能靠拍脑袋、也不能靠「取 F1 最大点」？因为 F1 隐含地假设了 precision 和 recall等价重要，而 TSR 里这个假设对任何一个类别都不成立。正确做法是把产品的误报预算写成硬约束，在约束下最大化召回——这样阈值就成了一个可计算的量，而不是一个可争论的量。notebook 里会实现这个求解器：输入检测结果、GT、帧数、预算 $\beta$，输出每类的 $\tau^\star$ 与对应召回。

严谨说

还有一层更工程的考虑：阈值必须在「送进时序融合之前」还是「之后」定，是两个完全不同的问题。C55 模块 04 讲的多帧确认会显著改变工作点——单帧允许更低的阈值（更高召回、更多 FP），因为跨帧的一致性检验会把随机 FP 滤掉；而一个只出现一帧的误检根本活不到上报。所以「单帧阈值」应该按「多帧确认后的 FP 预算」反推，而不是按单帧的 FP 预算设。这也解释了一个常见的困惑：为什么离线评测里看起来误报很多的模型，上车之后体验反而更好——因为离线评测的是单帧，产品体验的是融合后的输出。如果你的评测流水线只评单帧，你就系统性地高估了误报、低估了召回收益，进而会把阈值定得过高。

mAP 过门禁 ≠ 产品不坏

一个真实且常见的事故模式：用 mAP 做版本门禁，用固定阈值上线。新版本 mAP 从 0.72 涨到 0.75，顺利过门禁；上车后误报暴增，因为新模型的分数分布整体右移了（比如换了 loss 或加了标签平滑），同样的 0.4 阈值现在放行了更多低质量框。mAP 涨了，产品坏了，而且离线指标完全看不出来。

解法只有一个：门禁指标必须是「工作点上的指标」——固定 FP/frame 预算下的召回，或固定召回下的 FP/frame。而且每次换模型都要重新求解阈值，不能沿用上一版的。

7badcase 可视化：为什么必须分层抽样

误差分解给你数字，混淆矩阵给你类别，PR 曲线给你形状——但最终你还是要用眼睛看图，因为只有看图才能发现「这些漏检的牌子后面都有一根路灯杆」这种数字里没有的模式。问题是：怎么选那 100 张要看的图。

「随便看看」看到的是分布的众数，不是问题的分布

如果你从 badcase 池里均匀随机抽 100 张，你会得到什么？——你会得到 100 张限速牌。因为限速牌占了数据的 60%，即使它的错误率最低，绝对错误数依然最多。于是你花两小时看完，结论是「限速牌有时候会漏」，而真正的问题（那个只有 40 个样本、AP 只有 0.05 的施工临时牌）你一张都没看到。

这是一个采样偏差问题，而不是勤奋程度问题。看 500 张也救不了——你只会看到 300 张限速牌。

分层维度：至少四个

分层维度典型分桶为什么这个维度必须分不分的后果

配额怎么分：不要用比例分配

按各层大小成比例分配（$n_h \propto N_h$）等于没分层——大层还是吃掉全部名额。按等额分配（每层一样多）又会给一个只有 3 个样本的层塞 20 个名额。实践中最好用的是 平方根配额（square-root allocation）：

\[n_h \;=\; \max\Bigl(n_{\min},\; \Bigl\lfloor n_{\text{total}} \cdot \frac{\sqrt{N_h}}{\sum_{h'} \sqrt{N_{h'}}} \Bigr\rfloor\Bigr), \qquad n_h \le N_h\]

平方根压缩了层间的规模差异：一个 10000 样本的层和一个 100 样本的层，比例分配下名额差 100 倍，平方根分配下只差 10 倍。再加上「每个非空层至少 $n_{\min}$ 个」的下限，就能保证尾部类和极小目标层一定会被你看到。notebook 里会用最大余数法实现它，保证配额之和精确等于 $n_{\text{total}}$。

直白说

分层抽样还有一个副产品好处：它让 badcase review 变成可复现的流程而不是个人手艺。同一份检测结果、同一个随机种子，任何人跑出来的 100 张图是同一批；上一版和这一版的对比可以做到「同一个层里，上版错 12 张、这版错 5 张」。不分层就没法做这种版本对比，因为两次抽到的根本不是同一批东西。

严谨说

更进一步，成熟团队会把这套抽样固化成回归可视化集：每个分层固定抽 N 张图像 ID（而不是每次重抽），每次训完新模型都在这同一批图上出对比图。这样人眼看到的差异就是模型的差异，而不是抽样的差异。代价是这批固定样本会逐渐被「过拟合」——团队会不自觉地针对这 100 张调优。缓解办法是分两份：一份固定的回归集（用于版本对比），一份每次重抽的探索集（用于发现新问题），后者的种子随版本变化。这和 C58 的数据闭环、模块 01 的实验纪律是同一套思路：任何用于决策的观察，都必须先说清它的采样规则。

10–20% 的 badcase 是标注错

一个具体的操作细节：看 badcase 时一定要同时看「模型输出」和「GT」，并且要能看到分数。至少有 10–20% 的所谓 badcase 其实是标注错误——牌子被标漏了、标错类了、框标歪了。如果你不看 GT 就断定「模型漏了」，你会去挖一堆数据来修一个根本不存在的问题。建议在 review 界面上直接放一个「这是标注问题」的按钮，把这类样本回流给标注团队——这条链路本身就是 C58 数据闭环的一部分，而且往往是投入产出比最高的一条。

8从指标到根因：一棵可执行的决策树

把前七节合成一个流程。这棵树的设计原则是「先排除便宜的可能性」——查一次类别映射花 10 分钟，训一次模型花 10 小时，所以任何时候都应该先做那个 10 分钟的检查。

直白说

这棵树最重要的性质是它把「便宜的检查」排在了「昂贵的实验」前面。Q1 和 Q2 加起来不超过 30 分钟，却能拦下最常见、也最浪费时间的一整类问题——很多人在这两个问题上耗掉的是「训了三天发现是类别 ID 差 1」。而 Q4 那个「换更大的 backbone」被放在最后，不是因为它没用，而是因为它掩盖问题的能力太强：一个有管线 bug 的系统换了更大的模型也会涨点，于是 bug 被永久地留在了代码里。

严谨说

从方法论上看，这是期望信息增益除以成本的贪心排序：每一步选「能排除最多可能性 ÷ 花费最少时间」的检查。这个原则可以推广到任何调试场景，也是模块 03 那整本手册的组织依据。另一个值得内化的原则是：每一步都要求「可证伪的证据」，而不是「看起来像」。「我觉得是小目标问题」不算证据；「按尺寸分桶后 <16 px 桶的 AP 是 0.04、其余桶都 > 0.7」才算证据。面试里描述排查过程时，每说一个假设就跟一句「我会用 X 来验证它，如果看到 Y 就说明成立」——这个习惯会让你的回答听起来完全不一样。

整棵树可以压成一句话：先证伪「管线错了」，再证伪「数据不够」，最后才承认「模型不行」。绝大多数人是反着做的——上来就换模型，然后在一个有 bug 的管线上做了三个月的架构消融。

9研究前沿与开放问题

误差分析看起来是「工程」，但它底下压着一批相当硬的开放问题。下面这些既是研究方向，也是面试里展示深度的材料。

  • 归因的唯一性。TIDE 用一棵固定的判定树换取可复现性，但归因本身是不唯一的（第 2 节）。有没有一种「分解结果不依赖判定顺序」的定义？Shapley 值是一条路（对 $2^6$ 个 oracle 子集求边际贡献），但计算量与可解释性的取舍尚无定论，而且 Shapley 的公理是否适合 AP 这种排序型泛函也没被认真论证过。
  • 误差分解与下游安全后果的脱节。ΔAP 度量的是「对 mAP 的贡献」，但 TSR 真正关心的是「对驾驶行为的影响」。一个把「限速 80」判成「限速 60」的 Cls 错误，和把「停车让行」漏掉的 Miss 错误，在 ΔAP 上可能一样大，在安全上差着几个数量级。把代价矩阵嵌进误差分解（cost-sensitive TIDE），是一个实用价值极高但公开工作很少的方向（C55 模块 05 给了代价敏感评测的雏形）。
  • 时序维度的误差分解完全缺失。现有工具全部是单帧的。而 TSR 是一个「接近过程」，真正的产品指标是首次检出距离、闪烁次数、误报持续时长。「把 TIDE 推广到 track 级」——把一条轨迹的失败归因到 ID 切换、过晚检出、中途丢失、类别跳变——目前没有标准工具。
  • 自动化的根因归纳。现在的流程是「分解 → 人看 badcase → 人总结模式」。能否用 VLM 自动给 badcase 打场景标签，再做关联规则挖掘，直接输出「漏检集中在『逆光 + 树影 + 小于 20 px』这个交集」？这正是 C58 模块 04 讲的 scenario tagging 与误差分析的交汇处，也是 JD 里 「automated data mining workflows」最有含金量的一层。
  • 标注噪声与模型错误的可分离性。10–20% 的 badcase 是标注问题（第 7 节）。置信学习（confident learning）、损失轨迹分析、多模型一致性都能部分识别，但在检测任务上（涉及框与类别两个维度）仍缺少成熟方法。在评测集上，一个未被识别的标注错误会同时污染分子和分母，使误差分解系统性偏移。
  • 评测集本身的代表性。所有误差分析的结论都以「评测集能代表线上分布」为前提。当评测集与实际路况分布偏移时，你会自信地修一个线上并不重要的问题。分布偏移的检测、评测集的持续更新与「评测集也要做版本管理」，是把误差分析真正落地的前提（C37 与 C58 模块 05）。

★ 必读：Bolya et al., TIDE: A General Toolbox for Identifying Object Detection Errors（ECCV 2020，arXiv:2008.08115）——重点读 §3 的六类定义与 oracle 设计、§4 对比不同检测器的分解结果（看 one-stage 与 two-stage 的错误构成差异，这是面试里很好的谈资）。配套代码 tidecv 只有几百行，建议通读。

★ Hoiem, Chodpathumwan & Dai, Diagnosing Error in Object Detectors（ECCV 2012）——TIDE 的思想源头，第一次系统提出「按错误类型分解检测器性能」；它对目标尺寸、长宽比、遮挡等属性的分层分析至今仍是模板。

★ Lin et al., Microsoft COCO（ECCV 2014）附带的 detection analysis toolkit——那套 PR 曲线叠加图（C75 / Loc / Sim / Oth / BG / FN 逐层放宽）是 TIDE 的直接前身，理解它有助于理解「为什么需要 oracle」。

延伸：Everingham et al., The PASCAL VOC Challenge（IJCV 2010，AP 定义与单调包络的来源）；Northcutt et al., Confident Learning（JAIR 2021，标注噪声识别）；Oksuz et al., Localization Recall Precision (LRP) Error（ECCV 2018，一个把定位质量显式写进指标的替代方案）。相邻课程：本课模块 01（种子方差与显著性）、模块 03（管线 bug 的诊断手册）、C55 模块 05（安全导向评测与分桶）、C57 模块 05（按尺寸分桶）、C58 模块 05（闭环验证）。完整清单见 references.md。
