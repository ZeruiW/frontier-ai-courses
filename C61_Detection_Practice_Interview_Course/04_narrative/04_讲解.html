1叙事不是包装：面试官在做一个带噪的能力估计

先把一个常见的抵触情绪拆掉。很多工程师认为「讲故事」是销售的事，「我做过就是做过，说得漂不漂亮不重要」。这个想法在逻辑上就是错的，因为面试官看不到你做过什么，他只能看到你说的话。他要在 45 分钟里，从几千个汉字的观测里，估计一个他无法直接观测的隐变量：这个人能不能独立负责一个检测模型从数据到上车的完整迭代。

把这件事写成贝叶斯形式，一切就清楚了：

\[\underbrace{P(\text{能胜任} \mid \text{你说的话})}_{\text{面试官最后打的分}} \;\propto\; \underbrace{P(\text{你说的话} \mid \text{能胜任})}_{\text{似然}} \;\times\; \underbrace{P(\text{能胜任})}_{\text{简历给的先验}}\]

先验由简历决定，进了面试间就基本冻结了。你唯一能动的是似然。而似然真正起作用的是似然比——同一句话，做过的人说得出来的概率，比没做过的人说得出来的概率高多少：

\[\Lambda(\text{陈述}) \;=\; \frac{P(\text{陈述} \mid \text{真做过})}{P(\text{陈述} \mid \text{只读过论文})}\]

于是「什么话有信息量」有了一个可操作的判据：凡是不做也说得出来的话，$\Lambda \approx 1$，说了等于没说。「我用 YOLO 做了交通标志检测，效果不错」——任何看过五分钟教程的人都说得出，$\Lambda = 1$。「小目标桶（<32px）的 AP 只有 0.31，占全部漏检的 71%，所以我先做的是分桶评测而不是换模型」——不做过这件事根本编不出这组数字，$\Lambda$ 很大。

同一个项目的三种讲法，收到的信号完全不同

你的讲法面试官收到的信号为什么
「我用 YOLOv8 训了一个交通标志检测模型，mAP 到了 0.82」跑通了一个教程没有 baseline、没有指标口径（0.82 是 mAP50 还是 mAP50-95？）、没有约束、没有代价。这段话不需要做任何工作就能说出来
「baseline 是 YOLOv8s@640，COCO 口径 mAP50-95 = 0.58。我先做了按像素尺寸分桶，发现 <32px 的桶只有 0.31，而它占了全部漏检的 71%」有指标意识、会分桶、知道先归因再动手「分桶」「占漏检的 71%」这类数字只有真的跑过误差分析才有。这是 $\Lambda \gg 1$ 的陈述
「我先试了加 P2 层，小目标桶 0.31→0.42，但延迟从 6.1 ms 涨到 9.4 ms、显存 +40%，中配 SoC 上放不下，所以放弃了；最后落地的是输入分辨率 640→960 + 稀有类 copy-paste，小目标桶 0.31→0.39，延迟 6.1→7.8 ms，在预算内」做过、算过账、上过线有失败的分支、有代价、有约束驱动的决策。这是资深工程师和「会调包的人」之间最清晰的分界线

直白说

所以「讲故事」的训练，本质不是训练口才，是训练你把工作过程中真实存在但你自己没记下来的信息重新捡回来。多数人讲不好项目，不是不会说，是当初做的时候就没记 baseline、没记代价、没记试过什么没成功。叙事准备的第一步不是背稿，是回去把数字翻出来。如果翻不出来——那正是你该在下一个项目里改的工程习惯（这正是模块 01 讲实验记录 schema 的原因）。

严谨说

更严格地说，面试是一个低采样率下的能力估计问题：45 分钟、3–5 个话题，样本量极小，而候选人分布的方差极大。面试官为了在小样本下降低估计方差，会依赖高信息量特征——那些「不做过就编不出来」的细节，因为它们的似然比大。这解释了一个反直觉的现象：讲一个失败的实验，往往比多讲一个成功的实验更能提高你的评分。因为「我试了 X，涨了 Y」是每个人都会说的模板；而「我试了 X，预期涨 Y，实测只涨 0.1 而且方差 0.3，我判断这是噪声，于是跑了 5 个种子做配对检验，确认无效，然后归因到 Z」——这段话的每一个环节都需要真实的工程行为支撑。

抽象词是编造的指纹

「叙事」不等于「编故事」，两者的区别在面试里 30 秒内就会暴露。编出来的项目经不起第二层追问：你说「加了 copy-paste 涨了 3 个点」，面试官问「你的实例库怎么建的？贴的位置怎么约束的？贴完标注怎么生成的？有没有出现贴到天上的标志？」——真做过的人张口就来，编的人会开始用抽象词（「就是做了一些筛选」「按经验设置的」）。抽象词是编造的指纹。本模块教的全部内容，前提都是「这件事你真做过」——包括课程项目、复现实验、开源数据集上的实验，这些都算，但不能凭空虚构。

本节压成一句话：面试官不是在评价你的项目，是在用你的项目当探针评价你。所以叙事的目标不是「让项目显得大」，而是「让你做的判断显得清晰」。一个小项目讲出完整的归因链，胜过一个大项目讲成工序流水账。

2STAR 的检测版：四个格子里到底该填什么

STAR（Situation / Task / Action / Result）是通用的行为面试模板，但直接套用到检测项目上会讲得很空。检测项目有它特有的必填字段——缺哪一个，面试官都会当场追问，而追问是有代价的：它意味着你的表达没有覆盖到他的判据。下面这版是把 STAR 按检测工程的实际信息结构重写的。

┌─ S · Situation ─────────────────────────────────────────────────────┐ │ 必填 ① 场景：什么任务、什么数据、什么部署环境 │ │ 必填 ② baseline 指标 + **评测口径**（哪个数据集、哪个 mAP 定义、 │ │ 哪个 score 阈值、含不含 NMS 的延迟） │ │ 必填 ③ 问题是怎么被发现的（线上 badcase？分桶评测？回归门禁？） │ │ ✗ 常见缺失：只说「我们要做交通标志检测」——这是任务不是场景 │ └─────────────────────────────────────────────────────────────────────┘ ┌─ T · Task ──────────────────────────────────────────────────────────┐ │ 必填 ① 目标：要把哪个指标从多少提到多少（要有数字，哪怕是估的） │ │ 必填 ② **约束**：延迟预算 / 显存 / 算力平台 / 标注预算 / 排期 │ │ 必填 ③ 不能动的东西（下游接口、旧场景不许掉点、工具链无 plugin） │ │ ✗ 常见缺失：没有约束 —— 没有约束的问题不是工程问题，是作业 │ └─────────────────────────────────────────────────────────────────────┘ ┌─ A · Action ────────────────────────────────────────────────────────┐ │ 必填 ① **做了什么**（具体到方法名 + 关键超参 + 数据量级） │ │ 必填 ② **为什么这么做**（归因链：从现象到假设到方案） │ │ 必填 ③ **试过什么没成功**（至少一条，含为什么失败） │ │ 必填 ④ 怎么保证结论可信（几个种子？消融怎么设计？切片怎么切？） │ │ ✗ 常见缺失：② 和 ③ ——「做了什么」是工序，「为什么」才是判断力 │ └─────────────────────────────────────────────────────────────────────┘ ┌─ R · Result ────────────────────────────────────────────────────────┐ │ 必填 ① baseline → 改动后（同口径，成对给数） │ │ 必填 ② **代价**（延迟 / 显存 / 训练成本 / 其他场景 / 工程复杂度） │ │ 必填 ③ 验证方式（分场景切片？回归门禁？多种子？线上灰度？） │ │ 必填 ④ 业务影响（如果有：接管率、误报投诉、召回窗口提前多少米） │ │ ✗ 常见缺失：② —— 只报涨幅的结果陈述一定会被追问代价 │ └─────────────────────────────────────────────────────────────────────┘

同一件事，弱版与强版的逐格对照

格子弱版（面试里最常听到的）强版（$\Lambda$ 大的说法）
S「我做了个交通标志检测项目。」「TT100K 上做 TSR 检测，目标是车端 SoC，单帧感知预算 12 ms。baseline 是 YOLOv8s@640，mAP50-95 = 0.58；但我们真正关心的口径不是 COCO mAP，而是按标志像素尺寸分桶的召回，因为下游要的是「在多远能看到限速牌」。」
T「目标是提升 mAP。」「目标：<32px 桶的 recall@FP=0.1/帧 从 0.44 提到 0.60。硬约束三条：端到端 p99 ≤ 12 ms、显存 ≤ 1.2 GB、工具链不允许自定义 plugin。软约束：其他尺寸桶不许掉超过 0.5 个点（回归门禁）。」
A「我加了数据增强，换了个更大的模型，调了下超参。」「归因先行：TIDE 分解显示 Miss 占 mAP 损失的 62%，且 89% 的 Miss 集中在 <32px。于是我把方向锁定在小目标召回，排除了「换更强 backbone」这条路（它主要改善 Cls 与 Loc，而我的损失不在那）。做了三件事：① 输入 640→960（最直接，先验证天花板）；② P2 层（试了，见失败一节）；③ 稀有类 + 小尺度 copy-paste，实例库 4100 个 crop，贴入尺度按透视约束采样。」
R「mAP 提升了 3 个点。」「<32px 桶 recall 0.44→0.61（+0.17），总 mAP50-95 0.58→0.615。代价：延迟 6.1→7.8 ms（+28%）、显存 +0.3 GB、训练时长 +40%；>64px 桶掉了 0.3（在门禁容差 0.5 内）。验证：3 个种子、配对 bootstrap，小目标桶的提升 p<0.01；分场景切片里夜间桶也涨了 0.09，说明不是只在晴天生效。」

直白说

为什么 A 里的「为什么这么做」比「做了什么」重要得多？因为「做了什么」是可以照抄的，「为什么」是不能照抄的。你说「我用了 copy-paste」，面试官学不到任何关于你的信息——这个方法所有人都知道。你说「TIDE 分解显示损失 62% 在 Miss，且 89% 集中在小目标桶，所以我排除了换 backbone 这条路」——这句话暴露的是你的决策函数，而面试官招的正是这个决策函数。

严谨说

从评估的角度看，STAR 的四格对应四个不同的能力维度，面试官的评分表通常也是这么分的：S 测的是「问题定义能力」（你能不能把一个模糊的业务需求翻译成可测量的指标与口径）；T 测的是「约束意识」（能不能在有限资源下做取舍，而不是无限追求指标）；A 测的是「归因与实验设计能力」（这是最难伪装、区分度最高的一格）；R 测的是「交付纪律与诚实度」（有没有代价、有没有验证、敢不敢说负面结果）。如果你的叙事里某一格是空的，对应的那个维度就会被打「未观察到」——而在多数评分体系里，未观察到与不合格的处理方式是一样的。

A 段应该占一半以上时间

时间分配的经验值：一个 10 分钟的深度故事，S 应该占 60–90 秒，T 占 60 秒，A 占 5–6 分钟，R 占 90–120 秒。多数人的实际分配是 S 三分钟、A 两分钟——因为背景好讲、判断难讲。练习时用秒表卡一次，你会发现自己的 A 段短得惊人。

3指标必须成对出现：只讲涨的会被追问到崩

这是本模块最应该刻在脑子里的一条规则：工程里没有免费的提升。任何一个指标的改善，都必然伴随另一个指标的退化——如果你说不出代价，只有两种可能：①你没测；②你测了但不敢说。两种在面试官眼里都是减分项，而且第一种更糟，因为它意味着这个改动根本没有被验证过能上车。

为什么这条规则这么有杀伤力？因为它可以被机械地检查。面试官听你讲完 R，心里默数「涨的说了，代价呢」，没有就追问。而追问代价是一个开放式陷阱：如果你当场现编一个代价，语气和数字的具体度立刻会露馅；如果你说「没什么代价」，那要么是你没测，要么是这个改动大到不可信。

检测项目里的标准配对表

你想报的收益必须同时给出的代价面试官会怎么追问
mAP / AP 提升延迟、显存、训练成本（GPU-天）「延迟涨了多少？在什么卡上、什么 batch、含不含 NMS 和预处理？」
recall 提升同工作点的 FP 率（FP/帧 或 FP/km）「你是在同一个 score 阈值下比的吗？还是滑到了 PR 曲线的另一个点？」
小目标桶提升大目标桶是否退化、总延迟「大目标掉了吗？加分辨率的话为什么大目标会掉？」（答案：正负样本比例与感受野匹配变了）
尾部类别（rare）提升头部类别是否退化、总体 mAP「重采样倍率多少？head 类掉了几个点？你怎么定容差的？」
新场景（夜间/雨天）提升旧场景是否掉点（灾难性遗忘）「新老数据的配比是多少？旧场景切片过回归门禁了吗？」
INT8 后延迟下降mAP 掉点、哪些层保了 FP16、engine 体积「掉了几个点？分尺寸桶看，小目标掉得更多吗？」（几乎总是更多）
无 NMS / 端到端训练收敛成本、query 数上限、算子兼容性「你的 num_queries 是多少？单帧最大目标数统计过吗？」
加了 P2 层小目标涨FLOPs 与显存按分辨率平方涨、训练时间「P2 的 token 数是 P3 的 4 倍，你的显存怎么放下的？」
加大输入分辨率延迟约按面积线性、预处理耗时、与训练分辨率的一致性「训练和推理分辨率一致吗？letterbox 的实现两边对齐了吗？」
强增强（Mosaic/copy-paste）提升训练轮数需求上升、小模型可能欠拟合、最后要 close-mosaic「训练多少 epoch？关 Mosaic 的时机怎么定的？短训练下比较增强公平吗？」
多帧融合让输出更稳首次检出延迟（响应变慢）「你的确认帧数是多少？换算成距离，是不是晚了十几米才报出来？」
切片推理（SAHI）召回大涨切片数 ≈ (W/s)²，延迟可能是 4–16 倍「车端能承受吗？」（诚实答案通常是不能，要退到两级级联）

直白说

有一个更省事的自检口诀：每报一个数，问自己「这个数变好的时候，系统里哪个数变差了」。如果想不出来，八成是你只看了一个总指标（比如 COCO mAP），而总指标本身就是若干指标的平均——平均值是代价的天然藏身处。总 mAP 涨 0.3 完全可以是「夜间涨 3、白天掉 1」的合成结果，而白天占了你数据的 80%，这个改动上线后大概率是负收益。

严谨说

更根本的原因是：多数「提升」实际上是沿着某条权衡曲线的移动，而不是曲线本身的上移。调低 score 阈值让 recall 涨了——这是在 PR 曲线上滑动，AP 一点没变；加大模型让 AP 涨了——这是在延迟-精度帕累托前沿上滑动，效率一点没变。真正把曲线整体推上去的改动是稀有的（更好的标签分配、更好的数据、更好的损失），而这类改动值得单独强调。面试里能明确区分「我这个改动是沿曲线移动还是推动曲线」，是很高级的信号——因为它说明你知道自己交付的到底是什么。

追问链：从收益到方差到数据正确性

一条真实的追问链，绝大多数人在第三层就崩了：

你：「我用 copy-paste 把稀有类的 AP 提升了 5 个点。」
→ ①「总 mAP 涨了多少？」（如果你只算了稀有类，这里就答不上）
→ ②「head 类掉了吗？」（copy-paste 改变了类别分布，head 通常会掉一点）
→ ③「你怎么确认这 5 个点不是种子噪声？稀有类样本本来就少，AP 的方差会很大。」（这一层是杀招：尾部类在验证集上可能只有 30 个实例，单个种子的 AP 波动轻松超过 5 个点）
→ ④「贴上去的目标标注是怎么生成的？有没有出现遮挡了原有目标但没更新标注的情况？」（这是 copy-paste 真实的工程坑）

能一路答到第四层，你就赢了这一题。准备方法见第 6 节的「三层追问自审」。

把这条规则用一句面试可以直接说的话表达：「这个改动我记的是一对数：小目标桶 +0.17，延迟 +1.7 ms。在 12 ms 的预算里这个交换是划算的；如果预算是 8 ms，我不会做这个改动。」——注意最后半句，它说明你的决策依赖约束，而不是无条件追求指标。

4如何讲失败的实验：这恰恰是资深度的信号

多数候选人本能地隐藏失败的实验，因为担心显得能力不足。这是一个严重的策略错误。原因在第 1 节已经埋好了：失败实验的似然比极高。「我试了 A 涨了 3 个点」是所有人都会说的模板；「我试了 A，预期涨 2–3 个点，实测涨 0.1，我判断这是噪声，跑了 5 个种子确认，然后归因到 B」——这段话的每一个环节都需要真实的工程行为，编不出来。

更实际的原因：一个只有成功的项目叙事，在面试官听来是不真实的。做过检测项目的人都知道，成功率大概是三成。你讲了五个改动全部成功，面试官的第一反应不是「这人真厉害」，而是「这人只讲了成功的那些，或者他根本没做多少实验」。

失败的四种类型学（每一种传达的信号不同）

类型定义怎么讲传达的信号
① 假设错了你以为瓶颈在 X，做完发现不在「我一开始以为夜间掉点是曝光问题，做了低光合成增强，夜间桶只涨 0.02。后来做混淆矩阵才发现，夜间的错误 70% 是把反光的路牌背面误检成正面，是 FP 不是 FN——方向从一开始就错了。」归因能力 + 会用数据推翻自己。这是最高价值的一类
② 实现有 bug方法本身对，你写错了「copy-paste 第一版完全没效果，查了两天发现贴入的框在做仿射增强时没有跟随变换，标注和图像对不上。我后来固化了一个规则：任何新增的数据管线算子，必须先跑一遍可视化 + 框面积分布对比才允许进训练。」调试能力 + 从事故里沉淀流程（后半句是关键，没有它就只是「我犯了个错」）
③ 有效但代价不可接受指标涨了，但上不了车「加 P2 层，小目标桶 0.31→0.42，效果最好的一个方案。但延迟 6.1→9.4 ms、显存 +40%，中配 SoC 放不下。我保留了这个实验作为『天花板参考』——它告诉我小目标还有 11 个点的空间，剩下的工作就是找便宜的方式去逼近它。」约束意识 + 把失败转化为信息。「天花板参考」这个用法非常加分
④ 有效但不可复现第一次涨了，再跑就没了「换了个学习率调度，第一次跑涨了 0.4。我按惯例又跑了 3 个种子，均值只有 +0.05、标准差 0.31——第一次那个 0.4 就是种子噪声。这件事之后我把『单种子结论一律不进决策』写进了组里的实验规范。」统计素养。这一条在检测岗位上极其值钱，见模块 01

讲失败的六段式模板

  1. 假设：我当时认为瓶颈是 ___，依据是 ___（必须有依据，「凭感觉」是减分的）
  2. 预期：如果假设成立，我预期 ___ 指标会涨 ___（事先写下预期，这是资深工程师的标志）
  3. 实测：实际是 ___（给数字，包括方差）
  4. 归因：差距的原因是 ___（这一段是全部价值所在）
  5. 可迁移结论：我从中学到 ___（不是「以后要小心」这种空话，是一条可执行的规则）
  6. 后续处理：所以我改做了 ___ / 我保留它作为天花板参考 / 我把它写进了排除清单

直白说

有一个反例要特别避开：「我试了很多方法，都不太行，最后用了 X」。这句话看起来很诚实，实际上是最差的讲法——因为它没有归因。面试官听到的是「这人在乱试」。失败之所以有价值，是因为它排除了一个假设；如果你说不出排除了什么，那这个失败就真的只是失败。把「试了很多都不行」改成「我排除了三个方向，分别是因为 ___、___、___」，同样的经历，评价完全不同。

严谨说

从信息论视角看更清楚：一个实验的价值等于它消除的不确定性。成功的实验消除的是「这个方案行不行」；失败的实验如果做了归因，消除的是「瓶颈在不在这里」——后者往往覆盖更大的假设空间。你说「加 P2 涨了 11 个点但放不下」，同时告诉了面试官三件事：小目标还有大空间（假设空间的上界）、分辨率/层级是有效的杠杆（方向正确）、你的约束是显存和延迟（问题的真实形状）。一个信息量这么大的实验，藏起来不讲是巨大的浪费。而没归因的失败消除的不确定性接近零，讲了反而是负分——这正是「试了很多都不行」被扣分的数学原因。

失败要「有归因」且「有配比」

讲失败的两个边界：①不要讲「因为我不会所以失败」类型的失败（例如「我不太懂 TensorRT 所以没转成功」）——这类失败不消除任何关于问题的不确定性，只暴露技能缺口。②不要在一个 10 分钟故事里讲超过 2 个失败，否则叙事重心偏移，听起来像这个项目没做成。标准配比：一个深度故事里 2–3 个成功动作 + 1–2 个有归因的失败。

5简历里的检测项目：每个数字都是一个钩子

简历的作用和面试不同：简历决定先验，面试决定似然。但简历还有第二个作用，常被忽略——它是面试官的提问菜单。面试官准备问题时，几乎只看简历。你写什么，就会被问什么。这意味着简历可以（也应该）被设计成「主动引导追问方向」的工具：把你准备最充分的话题写得显眼，把你不想被深挖的部分写得简略。

 主动性   技术深度           可验证性           工程成熟度    业务视角

中「mAP 提升 3 个点」「什么口径？baseline 是什么？代价呢？」——追问全是补基础信息的面试官不得不花时间挖，挖出来的信息也不由你控制

直白说

还有一个操作性建议：为简历上的每个项目准备三个版本的讲述——30 秒、3 分钟、10 分钟。30 秒版用于自我介绍和「简单说说你做过什么」；3 分钟版用于面试官快速筛选话题；10 分钟版是深度版，只有当面试官说「详细讲讲这个」时才展开。最常见的失误是被问「简单说说」时讲了 8 分钟，把面试官原本想问的三个话题挤掉两个。

严谨说

从面试官的视角看，简历还承担一个更隐蔽的功能：校准你的自我评估准确度。如果你在简历上把一个 demo 级项目描述成生产系统，面试官在第一层追问（「日均处理多少数据？」「有回滚机制吗？」）就会发现落差，然后把这个落差泛化到你所有的自述——后续你讲的每个数字他都会打折。反过来，如果你的简历措辞与实际深度精确匹配（甚至略微保守），面试官会给你的所有陈述加一个信任加成。这个加成在模糊题（系统设计）上的价值极大。所以准确度 > 夸张度，这不是道德建议，是策略建议。

简历的检验方法：把每一条 bullet 交给一个不认识你的检测工程师，让他基于这条 bullet 出三个追问。如果你有任何一个答不上，改简历或补功课，二选一。notebook 里实现了一个 bullet 打分器，按「动词/方法/数字/口径/代价/影响」六项打分，可以先机器筛一遍。

6面试官的追问模式：五种探针与三层自审

追问不是刁难，是面试官在做主动采样——他从你的陈述里挑一个点，往深处钻，看你在什么深度开始变模糊。「开始变模糊的深度」就是他对你能力的估计。所以准备追问的方法不是背答案，是提前把自己的每个 claim 往下钻三层，找到自己变模糊的那一层，然后把它补上。

五种探针，各自在测什么

探针典型问法在测什么答题骨架踩雷点
① 替代方案「为什么不用 X？」（X 常是 DETR / 更大模型 / 更多数据 / 蒸馏）你是选择了这个方案，还是只会这个方案「X 我评估过。它在 ___ 上确实更优，但我的约束是 ___，X 会导致 ___。如果约束变成 ___，我会换 X。」——必须给出「什么条件下我会改选 X」「X 不好」——把方案说死，暴露没有取舍视角
② 验证追问「这个提升你怎么验证的？」「+0.3 你确定不是噪声？」统计素养与实验纪律（检测岗位最高频的探针）「多种子（n=___）+ 配对检验；同时看分场景切片，确认不是某一个桶的偶然；关键类别单独看。检测任务单种子波动典型 ±0.2–0.5，所以 +0.3 我不会当成结论。」「跑了一次就涨了」——立刻被判为没有实验纪律
③ 资源扩展「如果给你 10 倍算力/数据，你会做什么？」你有没有路线判断，还是只会执行手边的任务「先说我不会做的：单纯堆模型和堆数据，因为我的 TIDE 分解显示瓶颈在 ___。我会做三件事，按优先级：①___（预期收益___，依据___）②___ ③___。而且我会先花其中 10% 去做 ___ 的验证，避免把 10 倍算力投进一个错的方向。」「训个更大的模型」——最没信息量的回答
④ 反事实「如果重来一次你会怎么做？」「你觉得这个方案最大的问题是什么？」自我批判能力与成熟度（这题答「没什么问题」直接减分）「三点：①我在 ___ 上花的时间太多，因为一开始没做归因就动手；②___ 这个方案我没做消融，现在说不清它到底贡献了多少；③___ 的代价我当时没量化，上线后才发现。」假谦虚（「我最大的问题是太追求完美」）
⑤ 失效模式「你这个方案什么情况下会失效？」「上线后如果掉点你怎么查？」你有没有把方案想到边界，以及有没有排查方法论「三类失效：①分布外（___）②工程侧（___，比如预处理不一致）③长尾（___）。排查顺序我会用二分：先确认离线复现得了吗 → 复现不了就是部署侧，逐层 dump 对拍 → 复现得了就是数据或模型，做分桶归因。」「应该不会失效」

三层追问自审：准备方法的核心

对你叙事里的每一个数字和每一个方法名，做下面这个机械的三层展开。这是本模块最实操的产出——notebook 里有覆盖度检查器。

claim：「copy-paste 让稀有类 AP +5」 ├─ 第 1 层 · 「这是怎么测的」（口径 / baseline / 工作点） │ · 哪个数据集的哪个划分？稀有类怎么定义（&lt; 多少实例）？ │ · AP 是 AP50 还是 AP50-95？在哪个 score 阈值？ │ · baseline 是同一份配置只关掉 copy-paste 吗（单变量）？ │ ├─ 第 2 层 · 「这个数可信吗」（方差 / 显著性 / 副作用） │ · 几个种子？稀有类实例数少 → AP 方差大 → 5 个点可能是噪声 │ · head 类掉了吗？总 mAP 涨了吗？延迟/训练时长的代价？ │ · 有没有可能是「验证集里恰好有几张相似图」导致的泄漏？ │ └─ 第 3 层 · 「机制上说得通吗」（为什么有效 / 何时无效） · 为什么 copy-paste 对稀有类有效？（正样本数直接上升， 且背景多样性增加，缓解「稀有类总在同一种背景下出现」的偏差） · 什么时候它会无效甚至有害？（贴入尺度不符合透视、 边界接缝成为捷径特征、遮挡了原有目标但标注没更新、 贴到不可能出现的位置 → 模型学到错误的位置先验） · 真实分布里这个类少，是不是本来就该少检？（工作点问题） ⚑ 你在哪一层开始变模糊，就是你要补的地方。 经验值：**多数候选人在第 2 层的「方差」上崩，在第 3 层的 「何时无效」上崩。这两个正好是最能区分资深度的地方。**

直白说

第 3 层还有一个实用变体，叫「反向解释」测试：假设实测结果是相反的（copy-paste 让稀有类掉了 3 个点），你能给出一个同样合理的机制解释吗？如果能——而且很容易——说明你的第 3 层解释其实是事后合理化，不是真正的机制理解。（在这个例子里确实能：贴入的合成样本与真实分布有域差，模型学到了「有接缝的地方是稀有类」这个捷径，测试时反而更差。）能主动说出这个反向解释，是极强的信号——它说明你知道自己的结论是被数据支持的，而不是被故事支持的。

严谨说

从准备成本的角度算一笔账：一个 10 分钟的深度故事大约包含 8–12 个可追问的 claim，每个 claim 做三层展开是 24–36 个子问题。这看起来很多，但其中约 60% 是共享的——「几个种子」「口径是什么」「代价是什么」会在几乎每个 claim 上重复出现。所以正确的准备顺序是：先把通用层（口径、方差、代价、验证方式）一次性准备好并形成肌肉记忆，再逐个 claim 补第 3 层的机制解释。四个故事全部准备完，真正需要单独准备的第 3 层问题大约 30–40 个，一个周末可以完成。notebook 里的覆盖度检查器就是用来跟踪这个进度的。

「我不知道」的三段式

被问到确实不知道的东西，标准处理方式（这是加分而不是减分的机会）：①明确承认边界——「这个我没有实操过」；②给出你知道的相邻知识——「但我知道它要解决的问题是 ___，思路上应该是 ___」；③给出你会怎么查——「如果要落地，我会先做 ___ 的最小验证」。三段齐全的「我不知道」，比一个含糊的假装知道得分高得多。面试官对「不知道」的容忍度远高于对「不知道但装作知道」——后者会让他怀疑你之前所有的陈述。

直白说

注意时间轴里最后一段「留钩子」。一个好的故事结尾不是「所以我们上线了」，而是主动抛出下一步。这有两个作用：①它证明你对这个问题的思考没有随项目结束而停止（路线判断力）；②它让你控制了下一个话题，而下一个话题是你准备过的。面试的主动权就是这样一点点拿到的。

严谨说

四个故事之间还有一层共享结构值得刻意设计：让它们尽可能落在同一个虚构（但一致）的项目背景上——同一个数据集、同一个车端预算、同一套评测口径。这样四个故事之间可以互相引用（「故事 C 里提到的预处理不一致，就是在故事 A 的 960 分辨率改动上线后暴露的——训练用的是 PIL resize，车端 C++ 用的是 OpenCV INTER_LINEAR」）。互相引用会让整套叙事的可信度大幅上升，因为编造的故事之间不会有这种自洽的因果关系。反过来，如果四个故事各自独立、背景互不相干，听起来会像四段拼贴的知识点。

四个故事的准备顺序建议：先做 A（小目标）——它最贴 TSR 岗位靶心，且素材最完整；再做 C（部署一致性）——它是 JD 加分项里区分度最高的，多数候选人完全讲不了；然后 B（数据闭环）——它对应 JD 的 What Success Looks Like；D（选型）放最后，因为它更偏知识型，即使没准备好也能靠 C53/C54 的内容临场组织。

公司功课（面试前必做，30 分钟）

  • 技术路线：XNGP 的演进、图灵 AI 芯片、以及小鹏公开宣传的「端到端大模型 + VLA」路线。搜一下最近半年的技术发布会与工程师公开分享——能引用一句对方最近讲过的技术观点，是极高性价比的准备。
  • 把 TSR 放进他们的架构里：TSR 不是孤立模块，它的输出要进融合/跟踪、要与高精地图比对、要喂给规控或 VLA。面试时主动说出「TSR 的输出是给谁用的、以什么形式给」，会立刻把你和「只会刷点的人」区分开。
  • 区域性问题：中国 GB 5768 与欧洲 Vienna 公约、美国 MUTCD 的体系差异（形状-颜色-语义的映射规则不同），以及小鹏出海带来的跨区域泛化问题——这是一个很好的主动话题。
  • 准备一个「如果我入职第一个月会做什么」的回答：①读现有评测口径与切片定义；②跑一遍 TIDE + 分桶归因，建立自己对瓶颈的判断；③挑一个最小闭环（一个失效模式）走完全流程，熟悉工具链；④然后才提方案。这个顺序本身就是能力的展示。

没有真实车载项目怎么办

直白说

诚实地说明边界，然后用方法论的完整性补上。可以这样说：「我没有量产车载项目的经验，我的实验是在 TT100K 和自建的合成/公开数据上做的，规模是 ___。但我把整套流程走完了：分桶评测、TIDE 归因、多种子验证、ONNX 导出与数值对拍、INT8 校准与逐层敏感度分析。我知道真实车端还会遇到 ISP 域差、多任务抢占、功耗降频这些我没碰过的问题，如果入职我会优先补这部分。」——注意最后一句：主动列出自己没碰过的具体问题，比笼统说「我会努力学习」有说服力一百倍，因为它证明你知道差距在哪。

严谨说

为什么这个策略有效？因为面试官对自我评估准确度的敏感度远高于对经验年限的敏感度。一个能精确说出「我会 A、B，不会 C、D，而且知道 C、D 具体难在哪」的候选人，比一个笼统宣称「我全都会」的候选人可预测性高得多，而可预测性是招聘决策里的核心资产（招错人的代价远大于招慢的代价）。反过来，最危险的答法是含糊带过——「车端部署我也做过一些」，然后被追问 trtexec 的具体用法时卡住。这时面试官损失的不只是这一题的分，他会回头重新给你之前所有的陈述打折。这是本模块第 1 节那个贝叶斯模型的直接推论：一次被抓到的夸大，会改变面试官对你全部陈述的似然估计。

红线：虚构 / 编数字 / 泄密

三条绝对红线：①不虚构项目（包括把课程实验说成公司项目、把团队工作说成个人负责）——被追问两层必露馅，且诚信问题是一票否决；②不报没测过的数字——「大概涨了三四个点吧」这种含糊表述，会让你所有精确的数字一起失去可信度；③不泄露前雇主的敏感数据——被问到具体数字时说「这个具体数不方便说，我可以讲相对提升和方法」，这个回答本身就是加分项，它展示了职业素养。

面试前 72 小时清单

  1. T−72h：用 notebook 的自检器过一遍四个故事，补齐所有「缺代价 / 缺验证 / 缺归因」的告警；把关键数字（IoU 0.39、205×、$r_c$ 公式、TIDE 六类）做成一页卡片。
  2. T−48h：对着秒表讲一遍故事 A 与故事 C（各 10 分钟），录音回听——重点听 A 段占了多少时间，以及你有没有说出「代价」这个词。
  3. T−24h：做三层追问自审的覆盖度检查（notebook 里有），把覆盖率打到 80% 以上；过一遍模块 05 的白板题，手写 IoU / NMS / mAP 各一遍。
  4. T−12h：公司功课（技术路线 + 最近发布）；准备 5 个反问问题（见模块 05 第 8 节）；确认设备/网络/白板工具。
  5. T−1h：只看那一页关键数字卡片。不要在这个时候学新东西——临时学的知识在压力下最容易说错，而说错比不知道更糟。

9研究前沿与开放问题

  • 结构化面试的效度到底有多高？工业组织心理学的元分析长期认为结构化行为面试（有固定问题库 + 评分锚点）的预测效度显著高于非结构化面试，但近年有研究对早期元分析的效应量提出了修正（数据质量、范围限制的校正方式有争议）。对候选人的实际含义是：面对结构化面试，STAR 这类模板的收益最大；面对非结构化面试（纯聊技术），叙事结构的收益体现在「不遗漏关键维度」上，而不是「迎合评分表」。
  • 「+0.3 算不算提升」这个问题背后的复现性危机。检测领域的公开榜单竞争长期存在「单种子最优结果」的报告习惯，导致大量声称的改进无法复现。近年越来越多的工作开始报告多种子均值与标准差，但仍非主流。这个现状恰恰是你的机会：在面试里主动提出「我会看多种子和分场景切片」，等于站在了方法论更严格的一侧。
  • LLM 辅助的面试准备与评估。候选人用 LLM 生成项目叙事、公司用 LLM 做初筛与转录评分，双方都在军备竞赛。可预见的后果是：面试官会越来越依赖「不可被生成的细节」——具体的失败、具体的数字、具体的工程坑，因为这些是 LLM 生成的叙事里最薄弱的部分。这反过来印证了本模块的核心主张。
  • 代价指标的标准化缺失。检测论文报告 AP 与 FPS 已成惯例，但显存峰值、p99 延迟、engine 构建时间、量化后掉点、训练 GPU-天等「工程代价指标」几乎从不报告。这使得学术结果与量产选型之间存在系统性的断层——也解释了为什么工业界的选型决策看起来常常「不追 SOTA」。
  • 失败实验的发表与共享。ML 领域缺少负结果的发表渠道（少数 workshop 例外），导致同一个无效方案被不同团队反复试错。组织内部的「排除清单」（哪些方案在什么条件下被验证无效）是极高价值但极少被系统化维护的资产——如果你在面试里提出要建这个东西，是很好的加分点。
  • 把叙事能力当作可训练技能来量化。本模块的自检器是一个粗糙的规则系统（检查字段完整性、指标配对、追问覆盖度）。更好的做法应该是基于真实面试转录做标注学习「哪些陈述特征预测了通过」，但这类数据几乎不可能公开获取，所以目前只能靠规则 + 个人经验。这是一个真实的开放问题。
