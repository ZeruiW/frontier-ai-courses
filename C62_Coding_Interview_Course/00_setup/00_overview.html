1一面的 coding 环节到底在考什么

HR 把一面写成三段：Technical Knowledge Assessment（技术知识）、Problem-Solving（问题求解）、Practical (Coding) Exercise（实操编码）。第三段就是本课的战场——它是整个面试里唯一一个「你写下的东西会被逐字审视」的环节。

先把最大的误解拆掉：ML/CV 岗的 coding 环节，题目难度的中位数是 LeetCode easy–medium，不是 hard。面试官手里通常只有 45 分钟，还要留时间寒暄、介绍题目、追问、答疑；他没有时间看你解一道需要灵光一闪的难题，也没有兴趣。他真正想回答的问题是：

「把一个我没提前告诉他的中等难度问题交给这个人，45 分钟后，他能不能交出一段我敢直接合进代码库的东西？」——注意这句话里三个词：我没提前告诉他（考的是过程不是记忆）、45 分钟（考的是时间管理）、敢合入（考的是正确性 + 可读性 + 你自己测过）。

于是这个环节的交付物其实有三件，而不是一件。绝大多数人只交了第一件：

交付物具体形态不交会怎样被忽略的程度
① 一段能跑的代码15–40 行，变量名可读，能处理边界直接不及格所有人都知道
② 一句诚实的复杂度陈述「时间 O(n)，空间 O(1)，因为每个元素最多被两个指针各扫一次」面试官会认为你不知道自己写了什么一半人会说错或含糊过去
③ 一套你自己造的测试正常用例 + 空 + 单元素 + 全相同 + 极值，当场跑一遍「写完不测」是最常见的扣分项大部分人根本不做

直白说

换个说法：这一环节考的不是「你会不会这道题」，而是「你在不会的时候是怎么工作的」。一个当场认出原题、三分钟默写出最优解、全程不说话的候选人，分数常常低于一个先给 O(n²) 暴力解、讲清楚它慢在哪、然后一步步优化到 O(n)、最后自己造了五个测试用例跑通的候选人。前者展示的是记忆，后者展示的是可复现的工作方式——公司雇的是后者。

严谨说

更严谨地说：面试官是在用一个 45 分钟的高噪声样本，去估计「此人日常产出代码的质量分布」。样本量只有 1，所以他必须依赖那些方差小、可迁移的信号：是否先澄清需求（对应线上是否会写错需求）、是否先给可行解再优化（对应是否会过早优化）、是否主动测试（对应是否会把 bug 推到 code review）、是否诚实报复杂度（对应是否会对自己代码的性能撒谎）。「解出题目」这个信号方差极大——换一道题结果可能完全相反——所以它在评分里的权重反而没有你以为的那么高。

本课在整个课程体系里补的是哪个洞

这门课补的是全库最大的一个缺口。C00–C61 这 62 门课覆盖了检测、TSR、部署、VLA 等领域深度，但用关键词检索全库可以确认：「链表」「双指针」零命中，「时间复杂度」只出现在 1 门课里，「哈希表」也只有 1 门。也就是说，在此之前，你为这场面试准备的所有内容，都无法帮你通过 Practical (Coding) Exercise 这一关。

2六步答题协议：把「灵光一闪」变成「可复现的流程」

整门课只有一个东西必须背下来，就是它。六步答题协议的价值不在于它能让你解出更多题，而在于它让你在解不出来的时候仍然能拿到分——因为每一步都是独立计分的可见产出。

六步各自解决什么问题、以及不做会被扣什么，逐条对照：

步骤解决什么问题跳过它的典型后果面试官心里记的那一笔
① 复述与澄清防止解错题；把隐含约束显式化写到一半才发现「原来数组是有序的」，或者「原来可能有负数」「他不问需求就动手」——这是线上事故的性格画像
② 举例走一遍让你和面试官对「正确」达成共识；小例子还常常直接暴露解法写完代码没法验证，只能靠读代码找 bug「他没有 ground truth 就开始写」
③ 先给暴力解拿到保底分；给优化提供一个对照物卡在想最优解上，20 分钟白板一片空白「他没有可行解就去追最优解」——最致命的一条
④ 说优化思路把「思考」变成可见的产出；给面试官提示你的机会闷头写一个自己也不确定的解法「我不知道他在想什么，也没法帮他」
⑤ 写代码交付物本体—变量名、边界、缩进层数都在这里被看到
⑥ 测试与复杂度证明你不是「写完就扔」面试官发现 bug 而不是你发现 bug「他的代码需要别人来兜底」

直白说

为什么第③步「先给暴力解」是整个协议里最反直觉、也最值钱的一步？因为大多数人的本能是「我不能让他觉得我只会写笨办法」，于是憋着不说，直接冲最优解。但面试官的计分板上，「有一个正确的可行解」和「有一个最优解」是两格，前一格先拿到手才安全。而且说出暴力解不会降低对你的评价——恰恰相反，它显示你能快速把问题归约到一个已知可解的形式，这正是工程师日常做的事。真正掉价的是「既没有暴力解也没有最优解」的 20 分钟沉默。

严谨说

从决策论看，这是一个期望值问题。设直接冲最优解的成功概率为 $p$，用时 $T_1$；先写暴力解要花 $t_0$ 分钟，但把「至少有可行解」的概率提到接近 1。在 45 分钟的硬约束下，直接冲最优解的失败分支（概率 $1-p$）的收益接近 0，而先给暴力解的失败分支仍能拿到「正确性 3/5 + 沟通 4/5」。只要 $p < 0.85$ 左右，先给暴力解的期望分就更高——而对一道你没见过的中等题，$p$ 通常远低于 0.85。更进一步：暴力解还提供了对拍基准（第 6 节与模块 01 会反复用到），让你能当场用随机测试验证最优解的正确性，这在评分表上又是一格。

开局三雷

面试当场最容易翻车的三种开局，按危害排序：

① 听完题目立刻开始写代码。这一个动作同时丢掉步骤 ①②③④ 的分。即使你最后写对了，评分表上「沟通」和「测试意识」两栏也已经是低分了。
② 沉默超过 30 秒。面试官无法区分「在深度思考」和「已经卡死」，只能按后者记。正确做法是把卡住这件事本身说出来：「我现在在想能不能用哈希把内层循环干掉，但我不确定重复元素怎么处理，让我先写个例子。」
③ 默默修改题目。想不出来就悄悄假设「输入一定有序」——面试官会当场记下「他改需求不打招呼」。要改就大声改：「如果我可以假设输入有序，这题就变成对撞指针 O(n)；我可以先做这个版本吗？」

345 分钟怎么分：时间预算表与超时补救

超时补救：三种情况，三个动作

症状触发时刻立即动作话术（照抄）
想不出最优解第 15 分钟放弃优化，直接写暴力解，写完再回头优化「我先把 O(n²) 的版本写出来保证正确，如果还有时间我们再优化。」
代码写到一半发现思路错了第 28 分钟不要删。说出你的判断和证据，问是否值得改「我发现这个写法在有重复元素时会漏，反例是 [1,1,2]。我想改成先排序再对撞，大约需要 5 分钟，可以吗？」
写完了但只剩 3 分钟第 42 分钟放弃跑全部用例，只口述边界 + 报复杂度「时间关系我口头过一遍边界：空数组走 while 直接退出返回 []；单元素时 left==right 循环不进入。时间 O(n)，空间 O(1)。」
面试官频繁打断提示任何时刻停下来接住提示，这是救命绳不是干扰「您是说可以用一个哈希表记住已经见过的？让我想 20 秒……对，那内层循环就没了。」

直白说

很多人以为超时补救是「加快速度」。不是。补救的本质是降级交付：主动把目标从「最优解 + 完整测试」降到「可行解 + 口述边界」，并且把这个降级决定说出来。说出来和不说出来是两个完全不同的分数：不说，面试官看到的是「他没写完」；说了，面试官看到的是「他在时间约束下做了合理的取舍并主动沟通」——后者恰好是工程师最值钱的能力之一。

严谨说

这条原则与 C63 的系统设计、C65 的权衡决策是同一条：在硬约束下，显式的降级路径比隐式的失败有价值得多。在车端感知系统里，这叫graceful degradation（优雅降级）——算力不足时主动把 decoder 从 6 层降到 3 层（见 C53-04），比直接丢帧强；在面试里，主动宣布「我现在改为交付暴力解 + 口述复杂度」，比默默写不完强。面试官对这类信号极其敏感，因为它直接预测了你在项目 deadline 前的行为。

别把缓冲的 2 分钟花在「再优化一点点」上。那 2 分钟的最佳用途是反问：「这道题在你们实际工作里对应什么场景？」——这既是真实的好奇，也让面试官在收尾时对你留下正面印象。如果他说「我们做 TSR 的时候，多帧投票的窗口维护其实就是个滑动窗口」，你就拿到了后续话题的钥匙。

4面试官的五维评分表：分到底是怎么给的

大公司的 coding 面试普遍使用五维打分 + 加权的评分卡（rubric），每维 1–5 分。各家权重略有不同，但维度几乎一致。下面这套权重是一个可用的近似，notebook 里会把它代码化并做敏感性分析。

维度权重1 分（不及格）3 分（及格）5 分（强通过）
正确性 correctness0.30跑不通 / 逻辑根本错最优解基本对，边界有小漏最优解正确，边界全覆盖
复杂度 complexity0.20说不出复杂度，或说错能报对时间复杂度时间 + 空间都对，能说清为什么是这个量级
代码质量 code quality0.15单字母变量满天飞，嵌套 4 层可读，函数职责单一命名自解释，边界处理内聚，不用注释也读得懂
沟通 communication0.20长时间沉默 / 答非所问被问才答边写边讲，主动暴露不确定性，接得住提示
测试意识 testing0.15写完就说「好了」跑一个正常用例主动列边界清单并逐个跑，能自己找出 bug

把两个典型候选人代进去算一下，结论会让很多人不舒服：

候选人正确性复杂度代码质量沟通测试加权总分
A：沉默的最优解
认出原题，5 分钟默写最优解，全程不说话，写完说「好了」		553113.30（不及格线通常在 3.5）
B：会说话的暴力解
没见过题，澄清 4 个问题，先给 O(n²)，讲清优化方向但没写完最优解，造了 5 个用例全跑通		434554.15（强通过）
沟通 + 测试意识合计占 35%，比正确性还多 5 个百分点。这不是「大厂搞形式主义」——这两栏度量的是你的产出需不需要别人兜底，而这恰恰是团队协作里成本最高的一项。把这个数字记住，它会改变你练题的方式：练「边写边讲 + 主动测试」的边际收益，高于多刷 50 道题。

直白说

怎么用这张表指导准备？算提分收益：每一维「提升 1 分」的加权收益 = 权重 × 还差几分。对上面的候选人 A，收益排序是 沟通 0.20×4 = 0.80 > 测试 0.15×4 = 0.60 > 代码质量 0.15×2 = 0.30 > 其余 0。也就是说，A 应该做的不是再刷 100 道题（正确性已经满分），而是找个人对着讲一遍。notebook 的练习 2 会把这个计算实现出来，你可以拿自己的模拟面试录像去打分。

严谨说

需要说明这套权重的局限：① 各家权重不同，有的公司把正确性提到 0.4，有的把「问题分解能力」单列一维；② 存在门槛效应——正确性拿 1 分通常直接一票否决，加权总分再高也没用，所以不能把它当成纯线性模型；③ 面试官之间的方差很大，同一份表现在不同面试官手里可能差 0.5 分。正确的用法是把它当作注意力分配的工具（告诉你练什么），而不是当作可以精确预测结果的模型。

「正确性 1 分」是一票否决项。加权模型在这里失效：如果你的代码在面试官脑子里跑出了错误结果，后面四栏拿满分也救不回来。这就是为什么第③步「先给暴力解」如此重要——它把正确性的下限从 1 抬到 3。

复杂度速查：从 n 的量级反推「你被允许用什么算法」

这是面试里一个免费的提示，而且大多数人不会用。当面试官说出「数组长度最多 $10^5$」时，他已经把答案的复杂度告诉你了。经验换算的依据是：一台现代机器每秒可做 $10^8$ 量级的基本操作（C/C++），而 Python 由于解释开销，实际能跑的量级是 $10^6$–$10^7$：

\[T(n) \;\approx\; c \cdot f(n) \;\le\; B, \qquad B_{\text{C/C++}} \approx 10^{8},\quad B_{\text{Python}} \approx 10^{7}\]
\[n \le 10 \Rightarrow O(n!) \;\;|\;\; n \le 22 \Rightarrow O(2^n) \;\;|\;\; n \le 500 \Rightarrow O(n^3) \;\;|\;\; n \le 3\times10^3 \Rightarrow O(n^2) \;\;|\;\; n \le 10^6 \Rightarrow O(n\log n) \;\;|\;\; n \ge 10^7 \Rightarrow O(n)\]

这条阶梯是按 $B\approx10^8$ 的通用口径给的（面试里大家默认的就是它，已留出安全余量）。用 Python 实测时要再打一个数量级的折扣——notebook 里两种预算的表都会打出来，唯一有分歧的格子恰好在 $n=10^6$：$C{+}{+}$ 下 $O(n\log n)$ 还能跑（$2\times10^7$ 次操作），Python 下就只剩 $O(n)$ 了。

直白说

怎么当场用？听到「$n \le 10^5$」，你就可以说：「$10^5$ 排除了 $O(n^2)$（那是 $10^{10}$ 次操作），所以目标是 $O(n\log n)$ 或 $O(n)$。$n\log n$ 通常意味着排序或二分，$O(n)$ 通常意味着双指针、滑动窗口或哈希。让我先看看哪个性质可以利用。」这一句话同时展示了复杂度意识、算法储备和推理过程——三个评分维度一次拿到。

严谨说

反过来，这个换算也告诉你什么时候不该优化。如果面试官说 $n \le 1000$，那 $O(n^2) = 10^6$ 完全可以接受，此时花 15 分钟去想 $O(n\log n)$ 是premature optimization（过早优化），而且写出来的代码更容易错。正确的做法是明说：「$n\le1000$ 时 $O(n^2)$ 是 $10^6$ 次操作，在预算内，所以我先写简单正确的版本；如果你想看 $O(n\log n)$ 我再展开。」——这句话在评分表上比硬写一个最优解更值钱，因为它显示你会算成本收益。

不要把 $O(\cdot)$ 里的常数当成不存在。面试里说「都是 $O(n)$ 所以一样快」会被追问。在 Python 里，一次 dict 查找的常数大约是一次列表下标访问的 3–5 倍，一次 np.ndarray 的向量化操作又比 Python 循环快 20–100 倍。这就是为什么手写 NMS 的 numpy 版和纯 Python 版都是 $O(NK)$，但实测差两个数量级（见 C53-04）。

6Python 面试子集：哪些内置大方用，哪些会被判「绕过考点」

Python 的标准库强大到可以把很多算法题变成一行。问题是：一行流解决的那道题，考点可能正好是那一行。判断规则其实非常简单，只有一条：

如果这个内置函数就是本题要考的那个数据结构或算法，那就不能直接用；如果它只是一个与考点无关的工具，那就大方用，而且用得越熟练越好。拿不准的时候，把选择权交给面试官：「我可以用 collections.Counter 吗？还是您希望我手写这个计数逻辑？」——问这一句，两种情况你都拿分。
内置 / 库什么时候大方用什么时候会被判「绕过考点」被拦下时怎么办
sorted / list.sort题目主体是别的（区间合并、Top-K 的对照解），排序只是预处理题目就是「实现快速排序 / 归并排序」手写归并（稳定、好写、O(n log n) 稳定不退化）
dict / set几乎总是可以用。两数之和、去重、计数都指望它题目是「实现一个哈希表 / 处理哈希冲突」用数组 + 链地址法手写 put/get
collections.Counter字符串统计、频次分析的辅助步骤题目是「统计词频并返回 Top-K」——Counter 会把整道题吃掉d = {}; d[c] = d.get(c, 0) + 1，两行而已
bisect需要在有序数组上定位但考点不是二分（如 LIS 的 O(n log n) 解法）题目就是「实现二分查找 / 找左边界」手写三套模板（模块 02），并用 bisect 对拍
heapqTop-K、合并 K 个有序表、Dijkstra题目是「实现一个堆 / siftup siftdown」手写数组表示的二叉堆
itertools生成测试用例、写暴力解做对拍用 permutations 硬解本该 DP 的题（复杂度也不对）回到 DP / 回溯
functools.lru_cache记忆化搜索的标准写法，大方用并说明几乎不会被拦，但要能说清它等价于手写 memo 字典手写 memo = {}
numpyML 岗的加分项：向量化 IoU、矩阵操作、采样验证题目明确要求「不用第三方库」，或考的是循环边界本身回到纯 Python，但可以先说「生产里我会向量化」
re 正则解析日志、提取字段这类真实工程题题目是「实现字符串匹配 / KMP」手写朴素匹配 + 说明 KMP 思路

三个必须熟练、且几乎不会被拦的写法

  • 切片与负索引：a[::-1]、a[i:j]、a[-1]。但要知道切片是 O(k) 拷贝——在循环里切片会把 O(n) 悄悄变成 O(n²)，这是 Python 面试里非常常见的隐藏复杂度陷阱。
  • 解包与多重赋值：left, right = right, left、for i, x in enumerate(a)。对撞指针的交换用它，代码短一半且不会写错临时变量。
  • dict.get / collections.defaultdict：避免 if k in d 的分支，让滑动窗口的计数逻辑压到两行。但 defaultdict 有个坑：读取不存在的 key 会创建它，在「窗口内还剩几种字符」这类判断里会导致计数错误——模块 01 会踩这个坑给你看。

直白说

还有一类问题是整数与浮点。Python 的 int 是任意精度，所以「整数溢出」这个在 C++/Java 面试里的经典考点，在 Python 里不存在——但你仍然要提到它：「在 Python 里 (lo+hi)//2 不会溢出，但如果是 C++ 我会写 lo + (hi-lo)/2。」这一句话展示的是跨语言的正确性意识，成本几乎为零。

严谨说

浮点则是真的会出事：IoU、置信度、坐标都是浮点，== 比较几乎总是错的。面试里写 assert iou == 0.5 会被当场指出；正确写法是 abs(iou - 0.5) < 1e-9 或 np.allclose。更隐蔽的是把浮点数当 dict 的 key（模块 02 会展开）：0.1 + 0.2 不等于 0.3，所以 d[0.1+0.2] 取不到 d[0.3]。在 TSR 的框去重里，如果你用「坐标元组」做 key 来判重，就会踩这个坑——正确做法是量化到整数像素再做 key。

不要在面试里写一行流。return max((a[j]-a[i] for i in range(n) for j in range(i+1,n)), default=0) 这种代码，在评分表上「代码质量」不会加分，而「沟通」会扣分——因为面试官需要花 10 秒解析它，而这 10 秒里他在想的是「他是不是在炫技」。面试代码的目标函数是「让一个陌生人在 3 秒内读懂」，不是「让行数最少」。15–40 行、有意义的变量名、必要时一行注释说明循环不变量——这才是满分形态。

7研究前沿与开放问题

最后放一组更长期的问题。它们不会出现在你的一面里，但会影响你怎么看待「刷题」这件事——以及三年后这个环节会变成什么样。

  • coding 面试的预测效度到底有多高？公开研究极少，各家的内部数据也不外流。已知的是它对「代码正确性」有中等相关，对「长期产出」相关很弱。这正是评分表把 35% 权重给沟通与测试的原因——那两栏被认为更能预测协作产出。但这个假设本身也缺乏公开验证。
  • LLM 让「能否解出题目」这个信号迅速贬值。当模型能秒解绝大多数 LeetCode medium，面试的重心必然从「解出来」移向「解释、调试、批判」。已经出现的新形态包括：给一段有 bug 的代码让你定位、给一个 LLM 生成的解法让你 review 并指出复杂度错误、以及要求你在受限环境下证明自己的解正确。本课的「暴力解与最优解对拍」正是对这个趋势的直接准备——它训练的是「验证」而不是「产出」。
  • ML 岗特有的题型正在分化。越来越多的团队用与业务同构的题替代通用算法题：手撕 IoU/NMS（见 C61-05）、实现蓄水池采样、写一个分层抽样器、实现一个滑动窗口的指标聚合器。这类题的好处是能同时考算法与领域理解，坏处是可比性差、容易出成「只有内部人才知道」的题。
  • 「允许查文档 / 允许用 AI」的面试怎么评分？一部分公司已经允许开着搜索引擎面试，评分重心转向提示词质量、对返回结果的批判、以及集成速度。目前还没有成熟的 rubric，各家在摸索。可以预期：验证能力（写测试、造反例、对拍）的权重会继续上升。
  • 算法复杂度的「实际常数」缺少可教材料。面试里人人会说 $O(n\log n)$，但很少有人能说清「Python 里 $10^6$ 次 dict 查找大概几毫秒」。这个知识在真实工程里（比如判断一个后处理能不能塞进 33 ms 的帧预算，见 C53-05）比渐近复杂度有用得多，但它高度依赖语言与硬件，因而没有被写进任何教材。notebook 里我们会自己测一组。

★ 必读：Gayle Laakmann McDowell, Cracking the Coding Interview（6th ed.）第 VII 章「Technical Questions」——本课六步协议的原型出自这里，但本课把它按 ML/CV 岗的题型分布做了重排，并把时间预算显式化。★ Steven Skiena, The Algorithm Design Manual（3rd ed.）第 1–2 章与「War Stories」——读它是为了建立「先想问题归约、再想数据结构」的顺序感，而不是为了刷题。★ Cormen et al., Introduction to Algorithms（CLRS，4th ed.）第 2–4 章——只读循环不变量（loop invariant）与主定理这两部分，它们是模块 01 与模块 02 的理论底座。

配套材料：Google 公开的 Technical Interview Guidelines（讲评分维度与「hire/no-hire」的判定方式）；Vitter, Random Sampling with a Reservoir（1985）——模块 05 的蓄水池采样出处，也是本岗位数据采样工作的理论源头。相邻课程：C61 模块 05（检测专项白板题：IoU/NMS/mAP/匈牙利/Focal，本课不重复）、C63（ML 系统设计）、C64（技术知识问答）、C65（结构化问题求解与沟通）。完整清单见 references.md。
