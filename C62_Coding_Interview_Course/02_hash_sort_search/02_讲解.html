1哈希表：均摊 O(1) 的代价，与 Python 的三个坑

哈希表是面试里出现频率最高的数据结构，也是最容易被误报复杂度的一个。「用个 dict 就是 O(1)」这句话在 90% 的面试题里是对的，但你必须知道它在什么条件下成立——面试官问「dict 的查找真的是 O(1) 吗」时，他要的就是那 10%。

哈希表 = 一个定长数组 + 一个把 key 映射到下标的哈希函数 + 一套冲突解决策略。三样东西各自贡献一种失效模式：

链地址法（教学模型；CPython 实际用开放寻址） 桶数组 (capacity = 8) 装载因子 α = n / capacity ┌───┬───┬───┬───┬───┬───┬───┬───┐ │ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │ └─┬─┴───┴─┬─┴───┴─┬─┴───┴───┴───┘ │ │ │ ▼ ▼ ▼ [k8] [k1] [k2] ← 理想：每桶 O(1) 个元素 │ ▼ [k16] ← 冲突：同一桶挂成链 │ ▼ [k24] ← 退化：若所有 key 都映射到同一桶，查找变成 O(n) 的链表扫描 两种"变慢"要分清： ① 一次 rehash（扩容重建）= O(n)，但均摊到 n 次插入是 O(1) ← 可接受 ② 哈希函数烂 / 被攻击 → 每次查找都是 O(n) ← 不可接受

均摊分析：为什么扩容不破坏 O(1)

CPython 的 dict 在装载因子超过 2/3 时把容量翻倍并重建全部条目。单次扩容是 $O(n)$，但从空表插到 $n$ 个元素，一共只会在容量为 $1,2,4,\dots$ 时各触发一次重建，总代价是等比级数：

\[\sum_{i=0}^{\lceil\log_2 n\rceil} 2^{i} \;<\; 2n \quad\Longrightarrow\quad \frac{\text{总重建代价}}{n\ \text{次插入}} \;=\; O(1)\ \text{（均摊）}\]

「均摊 O(1)」和「每次 O(1)」不是一回事。对延迟敏感的系统（比如车端每帧要跑的后处理），均摊 O(1) 意味着某一帧会突然多花几毫秒——这正是模块 00 里说的「延迟均值 vs 延迟分布」。工程上的对策是预分配：如果知道最多有 4000 个候选框，就一次性开好，别让它在关键路径上扩容。

Python 面试里真正会踩的三个坑

  1. hash(1) == hash(1.0) == hash(True)。所以 {1: 'x', 1.0: 'y', True: 'z'} 的长度是 1，值是 'z'。用「类别 id」做 key 时，如果一条路径传的是 int、另一条传的是 np.float32，它们会静默合并成同一个 key——这类 bug 不报错，只是统计数字对不上。
  2. 浮点数做 key。0.1 + 0.2 != 0.3，所以 d[0.1+0.2] 会 KeyError。更隐蔽的是 float('nan')：nan != nan，但 dict 查找有一条 identity 短路（先比 is 再比 ==），于是同一个 nan 对象能查到，另一个 nan 对象查不到。
  3. 可哈希性。list 不可哈希，tuple 可以，但含 list 的 tuple 又不可以（哈希是递归计算的）。自定义类如果重写了 __eq__ 而没重写 __hash__，Python 会把 __hash__ 设为 None，实例直接变成不可哈希——这是「我的对象放进 set 就报错」的标准答案。

直白说

面试里对内置函数的态度要分场合。如果考点不是哈希（比如题目是滑动窗口、二分、DP），直接用 collections.Counter、defaultdict、set 是加分的——它说明你熟悉标准库、代码短、不容易写错。如果考点就是哈希本身（「实现一个 LRU Cache」「设计一个支持 O(1) 随机删除的集合」），上来就 Counter 会被判「绕过考点」。安全做法：先问一句「我可以用 collections 吗？还是你希望我手写？」——这一问本身就是分数。

严谨说

更精确的判据是看题目要求的复杂度里，哈希是不是那个决定性的一步。「两数之和」的 $O(n)$ 解法唯一的技术内容就是「用哈希表把查找从 $O(n)$ 降到 $O(1)$」——此时用 dict 不是绕过考点，用 dict 就是考点。而「设计一个 insert/delete/getRandom 都 $O(1)$ 的结构」的考点是「哈希表存值到下标的映射 + 动态数组存值，删除时用『和末尾交换』避免空洞」——这里 dict 只是零件，不能替代设计。一句话：内置容器可以当零件，不能当答案。

浮点数不能当哈希 key

会导致线上事故的写法：用浮点数当 key 做分桶。评测代码里经常要按 IoU 或框面积分桶统计（呼应 C55-05 的分桶评测、C57-05 的按像素尺寸分桶），有人会写 buckets[round(iou, 2)] += 1。问题是 round(0.145, 2) 在 IEEE-754 下等于 0.14 而不是 0.15（因为 0.145 的二进制表示略小于 0.145），而 round(0.155, 2) 等于 0.16——舍入方向随数值不规则地翻转。同一份预测在两台机器上算出的 IoU 差 $10^{-16}$，就可能落进不同的桶，于是「训练机上的评测报告」和「CI 机上的评测报告」对不上。正确做法：桶边界用显式的有序数组 + bisect 定位，不要用浮点当 key。

2排序：自定义键、稳定性，以及 NMS 为什么需要它

Python 的 sorted / list.sort 用的是 Timsort（Tim Peters, 2002），一个「归并排序 + 自适应 run 检测」的混合算法。三条性质要能脱口而出：

性质含义为什么面试里重要
稳定比较相等的元素保持原相对顺序这是本节的主角——多关键字排序与输出确定性都靠它
自适应对已经部分有序的输入接近 $O(n)$；最坏 $O(n\log n)$「数据基本有序」是可以说出来的优化理由，比空谈复杂度有说服力
key 只调用 n 次先算好所有 key（decorate-sort-undecorate），再排序所以 key= 比 cmp_to_key 快得多；key 里做重活（比如算 IoU）只付 $n$ 次而不是 $n\log n$ 次

多关键字排序的两种写法，以及为什么第二种必须靠稳定性

# 写法 A：元组 key —— 首选，一次排序搞定
recs.sort(key=lambda r: (r.cls, -r.score))     # 类别升序、分数降序

# 问题：字符串没法「取负」。下面这句是错的
recs.sort(key=lambda r: (-r.score, -r.name))   # ✗ TypeError

# 写法 B：分次排序 —— 从次关键字排到主关键字，靠稳定性把结果叠起来
recs.sort(key=lambda r: r.name)                 # ② 次关键字：名字升序
recs.sort(key=lambda r: r.score, reverse=True)  # ① 主关键字：分数降序
# 稳定性保证：分数相同的记录，仍保持上一步排好的名字顺序

写法 B 的顺序是反的（先排次要的、后排主要的），这是稳定排序最经典的应用，也是面试里「稳定性有什么用」的标准答案之一。如果排序不稳定，写法 B 直接失效。

真正的重点：NMS 的确定性依赖排序稳定性

NMS（non-maximum suppression）的第一步是按分数降序排序，然后贪心地「保留最高分、抑制与它 IoU 超阈值的框」。问题来了：如果两个重叠的框分数完全相同，保留哪一个？

两个 IoU = 0.72 的框，分数都是 0.90 排序结果 [A, B] → 保留 A，抑制 B → 输出框在 (100,200,140,240) 排序结果 [B, A] → 保留 B，抑制 A → 输出框在 (103,204,143,244) ↑ 差了 3 像素，下游的距离估计就差了 "分数完全相同"有多罕见？一点也不罕见： · INT8 量化后，分类头的输出只有 256 个可能取值 → 大量并列 （见 C60） · 分数被 round 到 3 位小数后再排序 （常见的日志/导出代码） · 同一个目标的多个候选框，特征几乎一样 → 浮点结果逐位相同

而排序实现的 tie-break 行为在各处不一致：

实现是否稳定并列时的顺序风险
Python sorted / list.sort稳定保持输入顺序安全，但依赖「输入顺序本身是确定的」
np.argsort(x)（默认 quicksort）不稳定由 introsort 的划分决定，随数组长度和内容变化同一批框换个顺序输入，结果就变
np.argsort(x, kind='stable')稳定保持输入顺序推荐
torch.sort默认不保证；需 stable=TrueCUDA 上与 CPU 上可能不同训练端与部署端 tie-break 不一致
TensorRT TopK / EfficientNMS未文档化保证由 kernel 的归约顺序决定车端与离线复现不一致的经典来源（见 C60）

直白说

这类 bug 的表现极具迷惑性：一致性对拍时，1000 帧里有 3 帧出现「1 个框不一致」，位置差几个像素，分数完全相同。你会先去怀疑预处理、怀疑量化、怀疑算子精度——而真正的原因只是两个并列分数的排序顺序不同。修法只有一行：把排序键从 -score 换成一个保证唯一的元组。

严谨说

严谨的表述：NMS 的输出是排序结果的函数，而排序在存在并列键时是一个关系而不是一个函数——它把一个输入映射到一组合法输出。要让整条流水线成为确定性函数，必须给排序键补上一个total order（全序）：把键扩展成 (-score, class_id, x1, y1, box_index) 之类，使任意两个不同元素的键都不相等。这样一来，是否稳定就不再重要了——因为根本不会出现并列。这个技巧的通用形式叫「tiebreaker 消歧」，在任何「结果依赖排序顺序」的贪心算法里都适用（模块 04 的区间调度、模块 03 的并查集聚类都会再遇到）。

一条可迁移的心法：凡是贪心算法，输出就依赖于排序顺序；凡是依赖排序顺序，就必须保证排序键是全序的。面试里被问「你的代码是确定性的吗」，能主动指出这一点比写出正确解法更显水平。

3二分的三套模板与循环不变量

二分是「看起来会、写起来错」的头号题型。工程上的统计口径是：相当一部分工程师无法在不调试的情况下一次写对二分（Bentley 在《Programming Pearls》里做过课堂实验，Bloch 在 2006 年发现 JDK 里的二分查找有溢出 bug 且存在了九年）。面试里写错二分的代价特别高，因为它是「基础题」，写错等于基础不牢。

解决办法不是「多做题找感觉」，是把循环不变量写下来，然后让每一行代码都为不变量服务。

先把前提说清楚：二分的条件不是「有序」

很多人以为二分的前提是「数组有序」。更本质的前提是：存在一个把搜索空间切成两段的单调谓词 $\text{check}(x)$，使得它在前一段恒假、后一段恒真（或反过来）。数组有序只是让 a[mid] < t 这个谓词单调的一个充分条件。

\[\exists\, x^\ast \in [L, R]:\quad \text{check}(x)=\text{False}\ \ \forall x < x^\ast, \qquad \text{check}(x)=\text{True}\ \ \forall x \ge x^\ast\]

写二分之前，先把 check 写出来并确认它单调。做到这一步，第 5 节的「在答案上二分」就是同一套模板的直接应用。

模板 A · 找精确值（闭区间 $[lo, hi]$）

def bs_exact(a, t):
    """不变量 I_A：若 t 存在于 a 中，则它的下标一定在闭区间 [lo, hi] 内。
       循环条件 lo <= hi 正是「闭区间非空」。"""
    lo, hi = 0, len(a) - 1              # 初始区间 = 全数组，I_A 显然成立
    while lo <= hi:
        mid = lo + (hi - lo) // 2       # 写成这样而不是 (lo+hi)//2：防止大整数溢出（Python 无此问题，C++/Java 有）
        if a[mid] == t:
            return mid
        if a[mid] < t:
            lo = mid + 1                # a[mid] 及其左边全 < t，t 不可能在那里 → I_A 保持
        else:
            hi = mid - 1                # a[mid] 及其右边全 > t → I_A 保持
    return -1                           # 区间空 ⇒ 由 I_A，t 不存在

模板 B · 找左边界（半开区间 $[lo, hi)$）= bisect_left

def bs_left(a, t):
    """返回第一个 >= t 的下标（不存在则返回 len(a)）。
       不变量 I_B：a[0:lo] 全部 < t   且   a[hi:n] 全部 >= t
       循环结束时 lo == hi，于是「< t」和「>= t」的分界点就是 lo。"""
    lo, hi = 0, len(a)                  # a[0:0] 与 a[n:n] 都是空集，I_B 平凡成立
    while lo < hi:
        mid = lo + (hi - lo) // 2       # lo <= mid < hi（下取整保证 mid != hi）
        if a[mid] < t:
            lo = mid + 1                # a[0:mid+1] 全 < t（因为有序）→ I_B 保持
        else:
            hi = mid                    # a[mid:n] 全 >= t → I_B 保持；注意是 mid 不是 mid-1
    return lo

模板 C · 找右边界（半开区间 $[lo, hi)$）= bisect_right

def bs_right(a, t):
    """返回第一个 > t 的下标。
       不变量 I_C：a[0:lo] 全部 <= t   且   a[hi:n] 全部 > t
       与模板 B 只差一个符号：a[mid] < t  →  a[mid] <= t"""
    lo, hi = 0, len(a)
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if a[mid] <= t:
            lo = mid + 1
        else:
            hi = mid
    return lo
三套模板的区间语义（数组 a = [1, 3, 3, 3, 7]，t = 3） 下标: 0 1 2 3 4 5 值: 1 3 3 3 7 (末尾哨兵位) │ │ │ │ │ └─ bs_left = 1 │ │ 第一个 >= 3 │ │ └─ bs_right = 4 │ 第一个 > 3 └─ bs_exact 返回 1/2/3 中的某一个（不保证是哪个！） 由 B 和 C 派生出的一切（**只背 B 和 C，其余现推**）： 出现次数 = bs_right(a,t) - bs_left(a,t) = 4 - 1 = 3 最后一个 <= t = bs_right(a,t) - 1 = 3 最后一个 < t = bs_left(a,t) - 1 = 0 第一个 > t = bs_right(a,t) = 4 精确查找 = i = bs_left(a,t); a[i] == t ? i : -1 ⇒ 面试里不要背三套模板，背 bs_left 一套 + 上面这张换算表。

终止性：为什么这两套模板一定不死循环

记第 $k$ 轮的区间长度 $\ell_k = hi_k - lo_k$。模板 B/C 里 $mid = lo + \lfloor \ell_k/2 \rfloor$，于是：

\[\ell_{k+1} \;=\; \begin{cases} hi_k - (mid+1) \;=\; \lceil \ell_k/2\rceil - 1 & \text{（走 } lo=mid+1\text{）}\\[2pt] mid - lo_k \;=\; \lfloor \ell_k/2 \rfloor & \text{（走 } hi=mid\text{）}\end{cases} \qquad \Longrightarrow\qquad \ell_{k+1} < \ell_k \ \ (\forall\, \ell_k \ge 1)\]

两个分支都严格缩小区间，而 $\ell$ 是非负整数，所以循环至多执行 $\lceil \log_2 n\rceil$ 轮后 $\ell = 0$，退出。这就是「不会死循环」的完整证明——面试里说得出这句话，比说「我一般写 hi = mid」有份量得多。注意关键点：当 $\ell_k = 1$ 时 $mid = lo_k$，走 hi = mid 分支得到 $\ell_{k+1} = 0$——正因为用了下取整，这个分支才没有卡死。

直白说

记不住哪个模板对应哪种边界？给一个不用背的办法：写完循环体，用「区间只剩两个元素」的情形手推一遍。$lo, hi$ 相邻时 $mid$ 落在哪、两个分支各把区间变成什么——推 30 秒就能确定它会不会卡住。这个手推动作在面试里应该说出来：「我验一下 lo 和 hi 相邻的情况……」——这是测试意识的直接展示。

严谨说

更系统的方法是循环不变量三段式验证，这也是 Hoare 逻辑在实践中最常用的形式：①初始化——进入循环前不变量成立（空区间上平凡成立）；②保持——若进入某轮时成立，则该轮结束时仍成立（这一步逼你说清「为什么 lo = mid + 1 是安全的」）；③终止——退出条件 + 不变量 ⇒ 目标结论（lo == hi 且 a[:lo] < t <= a[hi:] ⇒ lo 就是左边界）。再加上一个严格递减的整数度量（这里是 $\ell$）就得到终止性。四件事写完，二分的正确性就是被证明的而不是被测试的。

mid = (lo + hi) // 2 在 Python 里永远安全（大整数），但在 C++/Java/CUDA kernel 里当 lo + hi 超过 INT_MAX 会溢出成负数——这就是 Bloch 2006 年在 JDK 里找到的那个 bug。面试写 Python 时用 lo + (hi - lo) // 2 并顺口提一句「这样写是为了在 C++ 里也不溢出」，是一个成本极低、辨识度很高的加分动作。

4死循环的四种成因：开闭区间不一致

二分的所有 bug 几乎都能归到同一个根因：区间的开闭约定和更新语句不匹配。「$hi$ 是最后一个候选下标」（闭）和「$hi$ 是第一个被排除的下标」（半开）是两套不能混用的约定，而它们的初始化、循环条件、更新语句各有一套配套写法，混搭必出事。

约定初始化循环条件排除 mid 的写法保留 mid 的写法
闭区间 $[lo, hi]$hi = n - 1lo <= hilo = mid+1 / hi = mid-1lo = mid / hi = mid（危险，需配上取整）
半开区间 $[lo, hi)$hi = nlo < hilo = mid+1hi = mid（安全）

直白说

考场上的自保流程只有三步，30 秒能做完：①写下你用的是闭区间还是半开区间，并把这句话说出来（「我用半开区间 [lo, hi)，hi 是第一个被排除的位置」）；②按上表抄配套写法；③用「区间只剩 1–2 个元素」手推一遍。第①步的价值不只是防错——它让面试官知道你脑子里有明确的约定，而不是在试。

严谨说

如果你已经陷进去了（跑不出来 / 结果偏 1），不要盲改 +1 -1——这是面试里最糟糕的画面，改一次跑一次，五分钟就没了。正确的补救是回到不变量：把「循环退出时 lo 应该满足什么」写在纸上（或注释里），再倒推每个分支是否维持了它。一个实用的兜底手段是加一个步数上界：for _ in range(len(a).bit_length() + 2) 替代 while，这样即使写错也只是结果错而不是挂死——在压力下把「死循环」降级成「答案错」，是能救命的工程习惯。

死循环 = 双重扣分

面试当场翻车的场景：二分死循环。共享屏幕的编辑器卡住、进程没响应、你开始慌——这几乎是 coding 环节最难看的失败模式，因为它同时暴露了「不会写二分」和「没有测试意识」两件事。预防成本极低：所有二分统一用半开区间 + bisect_left 模板，其余边界一律用第 3 节的换算表现推。如果真的卡住了，标准话术是：「我先加一个循环次数上界，把死循环变成可观察的错误，再看不变量哪里破了。」——面试官要的是这句话，不是你立刻改对。

5在答案上二分：最小化最大值 / 最大化最小值

这是中高频、且区分度最高的一类二分题。它的特征是：题面里出现「最小化最大的 X」「最大化最小的 X」「至少需要多少 Y」，而且直接求最优解很难，但给定一个候选答案去验证可行性却很容易。

识别信号（三个都满足就基本可以断定）：

  1. 答案是一个数，且取值范围有明确上下界（$L$ = 最松/一定可行，$R$ = 最紧/一定不可行，或反过来）。
  2. 存在一个单调的可行性谓词：若容量 $x$ 可行，则 $x+1$ 也一定可行（放宽约束不会让问题变难）。
  3. check(x) 好写——通常是一遍 $O(n)$ 的贪心扫描。

满足这三条，答案就是那个「谓词第一次为真的位置」，直接套模板 B：

\[x^\ast \;=\; \min\,\{\, x \in [L, R] \;:\; \text{check}(x) = \text{True} \,\} \qquad \text{总复杂度} \;=\; O\bigl(\,\text{cost}(\text{check}) \cdot \log (R-L)\,\bigr)\]

样板题：分割数组的最大值（LeetCode 410）

把非负数组 a 分成 m 个连续子数组，使得各子数组和的最大值最小。直接做是区间 DP，$O(n^2 m)$；在答案上二分只要 $O(n\log(\sum a))$。

def split_array(a, m):
    # check(cap): 每段和都不超过 cap 的前提下，贪心地尽量多塞，最少需要几段？
    # 单调性：cap 越大 → 需要的段数单调不增 → parts(cap) <= m 是单调谓词  ✔
    def parts(cap):
        cnt, cur = 1, 0
        for x in a:
            if cur + x <= cap:
                cur += x
            else:
                cnt += 1; cur = x       # 开新的一段（贪心：能塞就塞是最优的）
        return cnt

    lo, hi = max(a), sum(a)             # lo：一段都装不下单个元素就不可能可行；hi：全放一段一定可行
    while lo < hi:                      # 半开区间 [lo, hi]，不变量：答案 ∈ [lo, hi]
        mid = lo + (hi - lo) // 2
        if parts(mid) <= m:
            hi = mid                    # mid 可行 → 答案 <= mid，保留 mid
        else:
            lo = mid + 1                # mid 不可行 → 答案 > mid
    return lo

两个边界的选取是这类题最容易错的地方：$lo$ 必须取「显然不可行的下界」或「可行性刚好可能开始的位置」——这里 $\max(a)$ 是硬下界（任何一段至少要装得下最大的那个元素）；$hi$ 必须取「一定可行的上界」——全放一段即 $\sum a$。把边界的物理含义说出来，比写对代码更能证明你理解了。

CV / 感知工程里的同构问题（这才是本课的锚点）

  • 「给定 30 ms 的延迟预算，输入分辨率最大能开到多少？」 $\text{check}(r) = \text{latency}(r) \le 30$，分辨率越大延迟越大 ⇒ 谓词单调递减 ⇒ 二分找最后一个可行的 $r$。这就是 C53-05 的选型问题的一维版本。
  • 「要让召回率不低于 0.95，score 阈值最高能设到多少？」 $\text{check}(\tau) = \text{recall}(\tau) \ge 0.95$。$\tau$ 越大召回越低 ⇒ 单调 ⇒ 二分。这正是 C55-05 的工作点选择——而它在代码上就是一次答案空间二分。
  • 「切片推理时重叠率最小取多少能保证不漏检？」 $\text{check}(\rho) = $「任意目标至少完整落在一个切片内」，重叠越大越安全 ⇒ 单调 ⇒ 二分求下界（呼应 C57-04）。
  • 「标注预算固定，采样阈值取多少能覆盖长尾类的目标数量？」 $\text{check}(\theta)$ = 触发量 $\le$ 带宽预算（呼应 C58-03 的触发器阈值优化）。

直白说

为什么这类题在 ML/CV 岗特别常见？因为工程里大量的决策就长这个样子：一个连续的旋钮（阈值、分辨率、批大小、重叠率），一个单调的约束（延迟、召回、带宽、显存），要找旋钮的极限位置。你在工作里做的「二分调参」和面试里的 LC410，是同一个算法——面试里能主动把这层联系说出来，是把「刷题」变成「工程直觉」的最直接证据。

严谨说

两个必须警惕的失效条件。①单调性不成立：延迟对分辨率不是严格单调的（TensorRT 会在特定尺寸上选到更优的 kernel，出现「更大反而更快」的反常点），此时二分会收敛到一个局部错误的答案——正确做法是先扫一遍粗网格确认单调，再在单调段内二分。②浮点答案空间：不能用 while lo < hi（浮点相等几乎永不成立，会死循环），要用固定迭代次数——for _ in range(100): mid = (lo+hi)/2; ...，100 次把区间缩小 $2^{-100}$，远超 double 的精度，绝对够用且绝不死循环。

面试里必须主动验证单调性。直接写「这题二分答案」而不说明 check 为什么单调，是典型的「背题痕迹」。正确的一句话是：「我先确认单调性——如果容量 x 能装下，那 x+1 显然也能装下，所以 check 是单调的，可以二分。」说这一句大约花 8 秒，但它把「我做过这题」变成了「我知道为什么可以这么做」。

6Top-K 的三种解法与选择依据

「从 $n$ 个数里取最大的 $k$ 个」是 ML/CV 岗的超高频题型，因为它在真实系统里到处都是：NMS 前的候选框截断、难例挖掘的回传排序（C58-03）、检索的近邻返回（C58-04）、长尾类别的重采样。三种解法要能同时说出复杂度、空间、副作用和适用场景。

┌──────────────────────────────────────────────────┐ n 个数 │ ① 全排序 sorted(a)[-k:] │ O(n log n) 空间 O(n) ───────►│ ② 大小为 k 的最小堆 │ O(n log k) 空间 O(k) ← 流式可用 │ for x in a: heappushpop(h, x) │ │ ③ quickselect 随机主元三路划分，只递归一侧 │ O(n) 期望 空间 O(1) ← 破坏原数组 └──────────────────────────────────────────────────┘ ② 的关键性质：**只需要一次遍历，且内存只占 k**。 数据是一条流（车队每天几 TB 的回传候选）时，①③ 都要求全量落地，② 不用。 ③ 的关键性质：**期望 O(n)，最坏 O(n²)**。 最坏发生在「每次主元都选到极值」——有序输入 + 固定取首元素做主元 = 必然退化。 修法：随机主元（工程标配）或 median-of-medians（理论 O(n) 最坏，常数太大，实践不用）。

① 全排序$O(n\log n)$$O(n)$是否（sorted）$k$ 接近 $n$；需要有序输出；$n$ 不大时它实际最快（见下）

\[\frac{T_{\text{sort}}}{T_{\text{heap}}} \;=\; \frac{n\log_2 n}{n\log_2 k} \;=\; \frac{\log_2 n}{\log_2 k} \;=\; \frac{1}{\alpha} \quad\text{（记 } k = n^{\alpha}\text{）} \qquad\Longrightarrow\qquad k=\sqrt{n}\ \text{时堆只快 2 倍}\]

这个公式值得记住，因为它解释了一个反直觉的现实：堆的渐进优势远没有想象中大。$n = 10^6$、$k = 100$ 时，$\log_2 n / \log_2 k \approx 20/6.6 \approx 3$ 倍——而 Python 的 sorted 是 C 实现的 Timsort，常数比纯 Python 的堆循环小一到两个数量级。notebook 会实测给你看：在 Python 里，$n = 10^5$ 量级时 sorted(a)[-k:] 往往比手写 quickselect 还快。

直白说

所以面试里被问「用哪个」，最好的答案不是报一个方法名，而是先反问约束：「$k$ 和 $n$ 的量级是多少？数据能一次放进内存吗？需要有序输出吗？可以改原数组吗？」四个问题问完，选哪个是自明的——而且你已经展示了「按约束做决策」的思维方式，这正是模块 00 说的评分维度。

严谨说

更进一步，能主动区分渐进复杂度与实际耗时是一个很强的信号。标准说法：「渐进上 quickselect 是 $O(n)$ 最优，但在 CPython 里 sorted 走的是 C 层 Timsort，常数小两个数量级；如果 $n$ 只有 $10^5$，我会先写 sorted，只有在 profile 证明这里是瓶颈、或者数据规模到 $10^7$ 以上时才换 quickselect。」「先测量再优化」和「知道复杂度只是常数未知的上界」是两个独立的加分点，这句话同时拿到。反过来，如果你张口就说「必须用 quickselect 因为它是 O(n)」，成熟度会被打折。

回到检测：NMS 前的 top-K 截断

生产级检测后处理（TensorRT 的 EfficientNMS、MMDetection 的 nms_pre）几乎都会在 NMS 之前先做一次 top-1000 by score。这不是为了精度，是为了把最坏耗时钉死：NMS 的代价是 $O(NK)$，$N$ 是过阈候选数；不截断时 $N$ 随场景无上界，截断后 $N \le 1000$ 是常数（呼应 C53-04 的 WCET 讨论）。代价是：极端密集的场景（一整排限速牌 + 龙门架）可能有目标被截掉，所以评测里必须专门覆盖这类切片。

把三种解法压成一句：全排序买「有序」，堆买「小内存 + 流式」，quickselect 买「渐进最优」。你付的钱分别是 $\log n$ 因子、$\log k$ 因子、和最坏情况的保证。面试里说清「买了什么、付了什么」，比背三段代码有用。

去重和计数看起来是最简单的操作，但四种写法在是否保序、复杂度、额外空间上各不相同，面试里被追问「还有别的写法吗」时能一次说全四种，是很轻松的加分。

计数的确定性陷阱

Counter(a).most_common(k) 在频次并列时按插入顺序返回，不是按字典序。这意味着「同一份数据、不同的读取顺序 → 不同的 top-k 输出」——又是一个 tie-break 不确定性（和第 2 节的 NMS 是同一个病）。要确定性就必须显式给出全序键：

from collections import Counter

c = Counter(a)
# ✗ 并列时的顺序依赖插入序，不可复现
top = c.most_common(k)

# ✓ 显式全序：先按频次降序，再按元素本身升序
top = sorted(c.items(), key=lambda kv: (-kv[1], kv[0]))[:k]

# ✓ 桶排序版本：频次是 [0, n] 的整数 ⇒ 可以 O(n) 完成（不需要 O(n log n)）
buckets = [[] for _ in range(len(a) + 1)]
for val, cnt in c.items():
    buckets[cnt].append(val)
out = []
for cnt in range(len(a), 0, -1):
    for val in sorted(buckets[cnt]):          # 桶内排序保证确定性
        out.append(val)
        if len(out) == k:
            break

「前 K 个高频元素」的桶排序解法（$O(n)$）是这道高频题的加分答案：频次的取值范围被 $n$ 界住了，所以可以用计数排序思想直接把 $\log$ 因子消掉。面试里先给堆解法 $O(n\log k)$，再补一句「如果要严格 $O(n)$，可以用桶排序，因为频次上界是 n」——这是标准的「先给可行解、再给优化」节奏。

分桶：把连续值离散化成整数 key

按尺寸 / 距离 / IoU 分桶做切片评测（C55-05、C57-05）是感知工程里最常做的统计。第 1 节已经说过不能用浮点当 key，正确姿势是显式桶边界 + bisect：

import bisect

EDGES = [0, 16, 32, 64, 128, 256]     # 像素面积开方后的分桶边界（COCO 风格）
LABELS = ['<16', '16-32', '32-64', '64-128', '128-256', '>=256']

def bucket_of(v):
    # bisect_right 返回「第一个 > v 的边界下标」，减 1 就是 v 落在哪个区间
    # 不变量：EDGES[i] <= v < EDGES[i+1]  ⇔  返回 i
    i = bisect.bisect_right(EDGES, v) - 1
    return min(max(i, 0), len(LABELS) - 1)

# bucket_of(31.999999999) -> 1  ('16-32')；bucket_of(32.0) -> 2  ('32-64')
# 边界归属是**明确的**（左闭右开），不依赖浮点相等

颜色分类（荷兰国旗）三路划分中频加分三指针一次扫描；和 quickselect 的划分是同一段代码
H 指数排序 / 计数排序中频加分降序排后找最大的 $i$ 使 $c[i-1] \ge i$
寻找峰值 / 山脉数组的峰顶二分（谓词不是有序性）中频加分a[mid] < a[mid+1] 即峰在右——无序数组也能二分
第 K 小的数对距离答案二分 + 双指针计数低频加分二分距离阈值，双指针数对数
两个有序数组的中位数分割点二分低频加分在短数组上二分分割点，$O(\log \min(m,n))$
「寻找峰值」这道题是理解二分的试金石。数组完全无序，但「a[mid] < a[mid+1] ⇒ 右侧必有峰」这个谓词是单调可用的——它证明了第 3 节那句话：二分的前提是「存在可切分的单调判据」，而不是「数组有序」。面试里能拿这道题反过来解释二分的本质，说明你不是在背模板。

8面试标准答案骨架

这一节请当作可背诵材料。组织原则和模块 00 一致：先给判断，再给机制，最后给数字和代价。

Q1 · dict 的查找真的是 $O(1)$ 吗？

项内容
面试官想听你分得清期望 / 均摊 / 最坏三种复杂度口径，而不是背一个符号
30 秒骨架「期望 $O(1)$，最坏 $O(n)$。最坏发生在所有 key 冲突到同一个桶——现实里两种触发方式：自定义 __hash__ 写成常数，或者被构造的碰撞攻击（CPython 从 3.3 起默认开启哈希随机化 PYTHONHASHSEED 就是为了这个）。插入还有第三个口径：均摊 $O(1)$——装载因子超过 2/3 会翻倍扩容并重建，单次是 $O(n)$，但等比级数求和后均摊是 $O(1)$。对延迟敏感的系统这个区别是实的：均摊 $O(1)$ 意味着某一帧会突然多花几毫秒，所以关键路径上要预分配。」
加分点补一句「还有个容易忽略的：遍历 dict 是 $O(\text{capacity})$ 不是 $O(n)$，大量删除后表很稀疏，遍历仍要扫全表——CPython 删除只打墓碑不缩容」
踩雷点只说「$O(1)$」；或者说「最坏 $O(\log n)$」（那是 Java 8+ 的 HashMap 树化，Python 没有）

Q2 · 你怎么保证你的二分不会死循环？

项内容
面试官想听你有可陈述的方法，而不是「我一般都对」
30 秒骨架「三件事。①约定：我统一用半开区间 [lo, hi)，hi 是第一个被排除的位置，所以初始化 hi = n、循环条件 lo < hi、更新只用 lo = mid+1 或 hi = mid。②不变量：a[:lo] 全 $< t$、a[hi:] 全 $\ge t$，退出时 lo == hi 就是分界点。③终止性：下取整让 lo <= mid < hi，两个分支都严格缩小区间长度，而区间长度是非负整数，所以至多 $\lceil\log_2 n\rceil$ 轮必然退出。写完我会用『区间只剩 1–2 个元素』手推一遍。」
加分点「另外我只背 bisect_left 一套模板，右边界、计数、精确查找全部由它推——少一套模板就少一类 bug。」再顺口提 lo + (hi-lo)//2 防溢出（JDK 的经典 bug）
踩雷点答「多写几遍就熟了」；或者当场靠改 +1/-1 试出来

Q3 · Top-K 用哪种解法？

项内容
面试官想听你先问约束再选方法，并且知道渐进复杂度不等于实际耗时
30 秒骨架「先问四个问题：$k$ 与 $n$ 的量级、数据能否一次进内存、要不要有序输出、能不能改原数组。$k \ll n$ 且是流式 → 大小 $k$ 的最小堆，$O(n\log k)$、空间只要 $O(k)$；$n$ 极大且能全放内存、不要顺序 → quickselect，期望 $O(n)$，但要随机主元，否则有序输入会退化成 $O(n^2)$；$k$ 接近 $n$ 或需要有序 → 直接全排序。补一个实测事实：$\log_2 n/\log_2 k$ 在 $n=10^6,k=100$ 时只有 3 倍，而 CPython 的 sorted 是 C 层 Timsort，常数小两个数量级，所以 $n$ 在 $10^5$ 量级时全排序往往实际更快。」
加分点主动连到工程：「检测后处理里 NMS 前的 top-1000 截断就是这个——不是为了精度，是为了把 NMS 的最坏耗时钉死，代价是极密集场景可能截掉真目标。」
踩雷点张口就「必须 quickselect 因为 $O(n)$」；说不出 quickselect 的最坏情况与随机主元

Q4 · 排序的稳定性有什么用？

项内容
面试官想听你能给出两个层次的答案：语法层（多关键字）和系统层（确定性）
30 秒骨架「两个用途。①多关键字排序：主关键字要降序而次关键字是字符串时没法用元组取负，只能『先按次关键字排、再按主关键字排』，这一步完全依赖稳定性。②输出确定性——这个更重要：任何贪心算法的输出都依赖排序顺序，NMS 就是典型。两个 IoU 超阈值的框如果分数完全相同，先排到的那个会被保留、另一个被抑制，输出的框位置就不一样。而分数并列一点都不罕见：INT8 量化后分类头只有 256 个可能取值。更糟的是 np.argsort 默认不稳定、torch.sort 默认不保证、TensorRT 的 TopK 没有文档化保证——训练端和部署端的 tie-break 不一致，表现为『1000 帧里有 3 帧差一个框』，极难定位。」
加分点给出根治方案：「与其依赖稳定性，不如让排序键成为全序——用 (-score, class_id, x1, y1, index)，任意两个元素的键都不相等，就不存在并列，是否稳定也就无所谓了。」
踩雷点只答「保持相等元素的相对顺序」——这是定义不是用途

Q5 · 你怎么识别一道题该「在答案上二分」？

项内容
面试官想听你有可复用的识别信号，而不是「见过这题」
30 秒骨架「三个信号同时出现就基本可以断定：①题面是『最小化最大值』『最大化最小值』或『至少需要多少』；②直接求最优难，但给定候选答案验证可行性容易（通常一遍 $O(n)$ 贪心）；③可行性单调——放宽约束不会让问题变难。满足了就把答案空间当成有序数组，套 bisect_left 模板，复杂度是 $O(\text{check} \cdot \log(R-L))$。写之前我会先说清 $L$ 和 $R$ 的物理含义，比如 LC410 里 $L=\max(a)$ 是硬下界、$R=\sum a$ 是一定可行的上界。」
加分点「而且这个模式在工程里到处都是：给定延迟预算求最大分辨率、给定召回下限求最高 score 阈值、给定带宽预算求触发阈值——都是同一个算法。」把刷题模式映射到工程决策，是这道题最高分的答法。
踩雷点不验证单调性直接二分；浮点答案空间用 while lo < hi（会死循环，要用固定 100 次迭代）

五道题的共同结构：先分清口径（期望/均摊/最坏、渐进/实际），再给机制，最后给一个具体数字或一个工程后果。数字和后果是把「背过」和「用过」区分开的东西——把 2/3 装载因子、$\log_2 n/\log_2 k$、INT8 的 256 档、$\lceil\log_2 n\rceil$ 轮这几个记住即可。

9研究前沿与开放问题

  • 学习型索引（learned index）。 Kraska 等人 2018 年提出：既然 B 树本质是「把 key 映射到位置」的函数，那就用一个小模型直接拟合累积分布函数 CDF，预测位置后在局部做小范围二分。在只读、分布平滑的数据上比 B 树快数倍且省内存。开放问题：更新（插入会破坏已学的 CDF）、对抗分布下的最坏保证、以及如何给出可证明的误差界——这正是「机器学习替代经典数据结构」这条线的核心难点。
  • 最坏 $O(1)$ 的哈希。 Cuckoo hashing 用两个哈希函数保证查找最坏 $O(1)$（代价是插入可能失败并重建）；Robin Hood hashing 通过均衡探测距离压低方差。它们在数据库和 GPU 上被广泛使用，但在通用语言的默认 dict 里几乎没有——因为通用场景更在意平均性能与内存布局，这是「理论最优」和「工程默认」分道扬镳的典型案例。
  • GPU 上的排序与 select 是另一套算法学。 CPU 上的 quickselect 依赖分支和随机访问，在 GPU 上都是反模式；GPU 的 top-K 用的是 radix select（按位分桶，无数据依赖分支）或 bitonic 网络。这解释了为什么 TensorRT 的 EfficientNMS 不是「把 CPU NMS 搬到 GPU」而是重新设计的算法——以及为什么它的 tie-break 行为和 CPU 不一致（呼应第 2 节与 C60 的一致性对拍）。
  • 浮点归约的不确定性。 浮点加法不满足结合律，所以并行归约的分块方式一变，结果的最后几位就变；cuDNN 的算法自动选择（benchmark=True）会让同一份权重两次前向的分数差 $10^{-7}$。这个 $10^{-7}$ 本身无害，但它会让「并列分数」在两次运行中翻转顺序，从而让 NMS 输出不同的框——「确定性训练/推理」（deterministic mode）为此付出的性能代价是否值得，在量产系统里仍是有争议的工程决策。
  • 亚线性算法与 sketch。 当数据大到连一遍都扫不完时，Count-Min Sketch、HyperLogLog、蓄水池采样这类算法用固定内存给出有界误差的近似统计。大规模数据挖掘（C58-04）里统计「某个稀有类在几十 PB 回传里出现了多少次」用的就是这类工具；开放问题是如何给检测这种「结构化输出」设计合适的 sketch。
  • 近似最近邻（ANN）是高维版的 Top-K。 HNSW、IVF-PQ、ScaNN 把精确 top-K 的 $O(n)$ 换成亚线性，代价是召回不再是 100%。嵌入检索式的难例挖掘（C58-04）完全建立在这个取舍上——「召回 95% 的近邻但快 100 倍」在挖掘场景里是划算的，但在评测场景里就不一定；如何为不同下游任务选择 recall-latency 工作点，仍然主要靠经验。

★ 必读：Cormen et al., Introduction to Algorithms（CLRS）第 9 章（Medians and Order Statistics：quickselect 的期望线性证明与 median-of-medians）与第 11 章（Hash Tables：全域哈希与完美哈希的严格分析）——这两章是本模块所有复杂度陈述的出处，面试里要报「期望 / 均摊 / 最坏」的口径就必须读它。★ Tim Peters, listsort.txt（CPython 源码 Objects/listsort.txt）——Timsort 的设计说明，讲清了「自适应」与「稳定」是怎么同时做到的，一小时能读完，性价比极高。

延伸：Bentley & McIlroy, Engineering a Sort Function（1993）——工业级快排的主元选择与三路划分，quickselect 的工程细节都来自这里；Bloch, Extra, Extra – Read All About It: Nearly All Binary Searches and Mergesorts are Broken（2006，JDK 二分溢出 bug 的著名博文）；Kraska et al., The Case for Learned Index Structures（SIGMOD 2018）；Pagh & Rodler, Cuckoo Hashing（2004）；Cormode & Muthukrishnan, Count-Min Sketch（2005）；Malkov & Yashunin, HNSW（TPAMI 2020，ANN 检索的事实标准）。相邻课程：模块 01（双指针与滑动窗口）、模块 03（树与图，并查集的复杂度分析）、模块 04（DP 与贪心，区间调度）、C53-04（NMS 的 WCET 与 top-K 截断）、C58-04（嵌入检索与去重）、C60（训练-部署一致性与浮点确定性）。完整清单见 references.md。
