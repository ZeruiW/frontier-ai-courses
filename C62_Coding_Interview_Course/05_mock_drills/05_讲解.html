145 分钟怎么分：时间预算表与三档超时补救

先摆一个反直觉的事实：一面 coding 环节里，「代码没写完」的失败远少于「写完了但没人看得懂你在干什么」的失败。45 分钟的时间压力不是让你写得更快，而是逼你在每一分钟都产出可被评估的信号。所以时间预算的目标不是「留出足够时间写代码」，而是保证在任意时刻被打断，面试官都已经拿到了打分依据。

下面这张表是把模块 00 的六步答题协议落到分钟级的版本。它假设的是最常见的形式：45 分钟总时长，前 3–5 分钟寒暄与自我介绍已经结束，一道中等难度题，可能带一个追问。

阶段分钟必须产出的东西超时信号（超过就要主动跳）
① 复述 + 澄清0–3用自己的话把题重说一遍；问清 3 件事：输入规模、是否允许修改输入、异常输入怎么办问到第 4 个问题还没开始举例 → 你在拖延，直接进②
② 举例走一遍3–6手写一个 5–8 元素的小例子并把期望输出算出来；同时列边界清单（空 / 单元素 / 全相同 / 极值 / 重复）例子超过 10 个元素 → 太大了，白板上算不完，换小的
③ 暴力解 + 复杂度6–9口述（不写）一个一定正确的解法，给出 $O(\cdot)$，并说「这是我的正确性基线」开始写暴力解的代码 → 立刻停，暴力解只用来说
④ 最优思路 + 取得同意9–13说清优化的依据（哪个重复计算被消掉了），给新复杂度，然后问一句「我按这个写？」13 分钟还没拿到「可以」→ 直接说「我先写暴力解保证有可运行版本」
⑤ 写代码（边写边讲）13–3017 分钟写 15–40 行。先写函数签名和返回值，再写主循环，最后补边界30 分钟还没写完主循环 → 进入下面的超时补救
⑥ 自测30–38把②的例子逐行手跑并报中间状态；再跑一遍空 / 单元素；发现 bug 按第 4 节的流程修自测发现的 bug 超过 2 个 → 说出「我怀疑是 X」，别硬修第三个
⑦ 收尾38–45复述最终复杂度（时间 + 空间）；说 1 条可优化方向 + 1 条工程化考虑；反问一个问题—

三档超时补救：剩 10 / 5 / 2 分钟分别该做什么

补救的原则是换取部分分，而不是赌全分。面试官的评分表是分项的（见第 5 节），「思路清晰 + 代码 80% + 自己指出剩下 20% 怎么写」的得分，明显高于「代码 100% 但没测、复杂度说错」。

剩余时间唯一该做的事要说出口的原话绝对不要做
剩 10 分钟（写到一半）砍掉所有优化，退回到一定能写完的版本（暴力解或 O(n log n) 而非 O(n)）「时间不多了，我先把 O(n²) 的正确版本写完，写完再说怎么优化到 O(n)。」继续调你那个精妙的 O(n) 双指针边界
剩 5 分钟（主体写完、没测）停手，开始测。用②的例子手跑一遍，报中间状态「我现在用刚才那个例子走一遍，i=0 时 window 是 …」再加功能、再改变量名、再重构
剩 2 分钟（还有已知 bug）把 bug 说清楚：在哪、为什么、怎么改，然后报复杂度「这里当 k 大于数组长度时会越界，需要在入口加一个 k = min(k, len(a))；其余逻辑不受影响。」沉默地乱改；或者假装没问题

直白说

为什么「主动说出还没做的事」反而加分？因为面试官真正想知道的是「这个人明天上工，我能不能放心把一个模块交给他」。一个知道自己代码哪里没测、哪里有边界风险的人，比一个自信地交付未测代码的人可靠得多。在检测团队里，后者会把一个没处理空 detection 列表的后处理函数合进主干，然后在雨天场景（零检出）当场崩掉。

严谨说

从测量的角度说，45 分钟的面试是对候选人能力的一次极低样本量的估计，面试官必须在噪声极大的观测里做决策。因此他会优先采集方差小、可迁移的信号：澄清问题的质量、复杂度分析的准确性、对自己代码的怀疑程度——这些在 45 分钟里是稳定可观测的；而「能否一次写对」高度依赖是否刷到过这道题，是噪声。时间预算表的真正作用，是把你的产出主动对齐到低方差信号上。

写码窗口只做翻译

最贵的时间错误：把 13–30 分钟的写码窗口花在「一边想一边写」上。典型症状是写了 8 行、删掉 5 行、再写 6 行——面试官看到的是一片混乱，且无法判断你是否知道自己在干什么。写码窗口里应该只有翻译动作：把④已经说清的思路翻译成代码。如果写到一半发现思路不对，正确的动作是停下、说出「我发现我的思路在 X 情况下不成立」、回到④，而不是在代码里试。

2「说出来」的技巧：句式库、脱困话术、被提示怎么接

think aloud（边想边说）是这门课里性价比最高的一项技能：它不需要多刷题，却直接决定沟通维度的分数，而沟通往常是五维评分里权重第二高的一项（见第 5 节）。但绝大多数人第一次练的时候会失败，原因很具体——他们试图「说出自己正在想什么」，而人在紧张时的思维是碎片化的，说出来就是噪声。

正确的做法是反过来：不要直播思维，要播报状态。你只需要在固定的几个时刻，说固定的几句话。下面这张句式库把「该说什么」变成查表操作，练 3 遍就能形成肌肉记忆。

时刻句式模板它替你证明了什么
拿到题后「我复述一下：给我 __，要我返回 __，其中 __ 保证 __。对吗？」你在解正确的题（这是最贵的一分）
澄清时「输入规模大概是 10³ 还是 10⁷？这决定我是用 O(n²) 还是必须 O(n log n)。」你把规模和复杂度挂上了钩，而不是背模板
给暴力解「最直接的做法是双层循环，O(n²)。我先把它作为正确性基线，然后看能不能优化。」你有一个一定能交付的兜底方案
提出优化「我注意到内层循环重复算了同一个前缀和，把它换成哈希表可以降到 O(n)。」优化有依据，不是「我记得这题用哈希」
开始写「我先写签名和返回，然后主循环，最后补边界。」你有结构，不是想到哪写到哪
写循环时「这个 left 指针的不变量是：[left, right) 内没有重复字符。」不变量是资深候选人的标志词
写完一段「这一段处理主逻辑，空输入还没处理，我下面补。」你知道自己欠什么
自测时「我用 [3,1,4,1,5] 走一遍：i=0 时 …，i=1 时 …」测试意识——很多人整场没测一次
收尾「时间 O(n)、空间 O(k)，k 是不同字符数。如果要支持流式输入，我会把它改成 …」复杂度 + 一个延伸方向，占满最后 3 分钟

卡住时的三种脱困话术（按优先级）

卡住本身不扣分，卡住时沉默才扣分。三种话术对应三种不同的卡法，选错了会显得慌乱：

  1. 降维（不知道怎么下手）：「我先解一个更简单的版本——如果数组是有序的 / 如果 k=1 / 如果只有两个类别，那么 __。现在把这个约束放开，多出来的困难是 __。」这句话把「我不会」变成了「我在做归约」，而归约是真实的解题方法。
  2. 退回（思路走不通）：「我这条路要求 __ 成立，但反例 __ 说明它不成立，所以我放弃这个方向，退回到 O(n²) 的版本先写出来。」关键是给出反例——放弃有理由就不是放弃，是排除。
  3. 换视角（有思路但写不出来）：「我换个角度：这题问的是「最多能保留几个不重叠的区间」，等价于「按结束时间排序后的贪心」——我用后者写。」把问题换一个等价表述，是最常见的破局点。

被提示（hint）时怎么接

面试官给提示不代表你已经挂了——提示是流程的一部分，几乎所有面试都会给。真正决定分数的是你接提示的方式。标准动作是四步，10 秒内做完：

① 接住 「哦，你是说 __（把提示用自己的话复述一遍）」 ← 证明你真的听懂了 ② 归因 「对，我刚才漏了 __ 这个性质」 ← 说清它补上了你思路的哪一块 ③ 推进 「那么 __ 就可以用 __ 处理」 ← 立刻把提示转成下一步动作 ④ 继续写 （回到代码，不要道歉，不要复盘情绪） ← 「不好意思我太紧张了」是纯扣分 反模式：沉默 3 秒 → 「啊对对对」 → 直接照提示写但说不出为什么 面试官会记录成「需要引导才能推进，且不理解引导的内容」——这是明确的负面信号

直白说

还有一条硬规则：沉默不要超过 30 秒。如果你确实需要安静地想，就申请它——「我需要 30 秒安静想一下这个边界，可以吗？」几乎没有面试官会拒绝，而这一句话把「疑似卡死」变成了「有意识地思考」。想完必须主动报告，哪怕结论是「我还没想通」。

严谨说

为什么 30 秒是阈值？因为面试官在没有语音信号时唯一能观察的就是屏幕，而屏幕在你思考时是静止的——他无法区分「在推导」与「已经卡死」，于是保守地假设后者并开始考虑给提示。你每一次超过 30 秒的沉默，都在消耗他对你的先验。工程类比是很直接的：一个不打日志的长任务，运维只能假设它挂了并重启它。think aloud 就是给你的思考过程加日志，而日志的价值不在于详尽，在于心跳。

一句心法：面试官不是在读你的代码，是在读你的代码 + 你的解说构成的那个「系统」。解说缺失时，代码的分数会被自动打折——因为他没法确认那是你推出来的还是背下来的。

3七个翻车点：症状、代价与当场补救

下面七条来自对失败面试反馈的归纳。它们的共同点是：都不是算法能力问题，都可以在一次练习里改掉，而且都会被面试官明确写进评价。读的时候请对着自己上一次做题的录屏（强烈建议录屏）打勾。

翻车点面试官那边看到 / 记录的东西代价当场补救话术
① 一上来就写题目念完 10 秒内开始敲键盘；沟通维度全场无数据最贵。即使代码全对，评价也会是「像刷过这道题」「等一下，我先确认一下输入规模和边界，免得写错方向。」（任何时候都能补）
② 不问边界空输入 / 单元素 / 全相同从未被提及正确性维度直接扣分；面试官会用空输入当追问，你现场崩「我现在补一下边界：空数组返回 0，单元素返回它本身。」
③ 写完不测写完说「好了」然后看着面试官等评判第二贵。「测试意识」这一项拿 0 分，且暗示你在真实工作里也不测「我自己跑一遍：输入 [2,7,11,15]，target=9 …」
④ 复杂度说错把 sorted() 说成 O(n)、把哈希表最坏情况说成 O(1)、忘算递归栈空间技术深度维度重创。说错比不说更糟「我更正一下：这里排序是 O(n log n)，所以总复杂度由排序主导。」
⑤ 变量名混乱a, b, tmp, tmp2, res, res2, i, j, k, kk代码质量维度扣分；更糟的是你自己会 debug 不动改名成本很低：left/right、count_by_class、best_iou。写之前定名
⑥ 默默改需求题目说「返回下标」你返回了值；题目说「原地」你开了新数组致命。等于交付了一个不符合规格的模块「我确认一下：你要的是下标还是值？我上面写的是值，我改成下标。」
⑦ 沉默 > 30 秒屏幕静止、无语音、光标不动面试官开始准备提示，你的「独立性」评价下降「我需要 30 秒安静想一下这里的边界。」——把沉默显式申请出来

为什么「一上来就写」最贵：一条因果链

题目念完 → 立刻敲键盘 │ ├─ 没澄清规模 ─────→ 选了 O(n²)，30 分钟后被告知 n=10⁶ ─→ 全部重写，时间不够 │ ├─ 没澄清返回值 ───→ 写完才发现要下标不是值 ───────────→ 返工 5 分钟 │ ├─ 没举例 ─────────→ 对题意的理解偏了一点 ─────────────→ 代码「对」但答的是另一道题 │ └─ 没说思路 ───────→ 面试官全程不知道你在干什么 ───────→ 沟通 0 分； 且他无法在你写歪时把你拉回来 反过来：前 13 分钟的澄清 + 举例 + 暴力解，把上面四条风险一次性全消掉， 成本是 13 分钟，收益是「正确性 + 沟通」两个维度先拿到基础分。

特别提醒 ML/CV 岗的一个高发变体：把「工程直觉」当成需求改。题目要你实现一个按分数取 Top-K 的函数，你顺手把「分数相同时按框面积大的优先」加进去了——因为你在真实项目里就是这么做的。这在面试里是第 ⑥ 类错误：你引入了一个未经确认的规格。正确动作是问一句「分数相同时的顺序有要求吗？如果没有我就保持稳定排序」，这一问既避免了默改需求，又展示了你知道稳定性会影响确定性（见模块 02）。

七条里有五条（①②③⑥⑦）与算法能力完全无关，纯粹是流程纪律。这意味着一次认真的录屏复盘，通常能把你的面试通过率提高一档，而这个收益是刷 50 道题都换不来的。notebook 里有一个把这七条做成检查表的 cell，可以直接对着自己的录屏时间线跑。

4在别人注视下 debug：先说假设，再验证

面试里出 bug 是常态，出 bug 不扣分，慌乱地 debug 才扣分。而慌乱有三个非常一致的表现形式：① 盯着代码看 20 秒不说话；② 开始删代码（把可疑的行注释掉、把循环边界 ±1 试试）；③ 一次改三处然后重跑。这三种做法在真实工程里也是错的，面试官正是因为这一点才把它当成强信号。

假设—验证循环（把 debug 变成一个可解说的流程）

发现输出不对 │ ① 缩到最小失败用例 「我把输入从 8 个元素砍到 3 个，还是错，说明与规模无关」 │ ② 说出一个可证伪的假设 「我怀疑是 right 指针的边界：循环退出时 right 应该是 n，我猜它是 n-1」 │ ← 这一句是全场最值钱的一句话 ③ 用一次打印验证假设 print(f"exit: right={right} n={n}") ← 只加打印，不改逻辑 │ ④ 假设成立？ │ ├─ 是 → 只改这一处 → 重跑最小用例 → 再跑原用例 │ └─ 否 → 记下「已排除 right 边界」，回到 ②，换下一个假设 │ ⑤ 改完复述 「根因是 while 条件用了 < 而不是 <=，所以最后一个元素没被处理」 禁止：跳过 ② 直接改代码。那叫「试」，不叫 debug—— 而且一次改多处后，你无法归因是哪一处修好的（也可能引入了第二个 bug）。
症状最可能的根因（按概率）验证它的一行打印

直白说

为什么「先说假设」这么值钱？因为它是唯一能让面试官参与进来的 debug 方式。你说「我怀疑是 right 的边界」，他要么点头（你省 30 秒），要么说「你再看看初始化」（他给了你答案）。而你盯着代码沉默的时候，他什么都做不了，只能等你，并在心里记录「独立 debug 能力弱」。把 debug 说出来，等于把一个单人任务变成双人任务，而这在真实团队里正是你该做的事。

严谨说

从方法论上看，假设—验证循环是把 debug 从随机搜索变成二分搜索：每个被证伪的假设都会排除一部分状态空间，因此循环次数是对数级的；而「改一改试试」不排除任何东西，期望次数是线性甚至更差（还可能因为引入新 bug 而增加空间）。更严格地说，一个好的假设必须满足两个条件：可证伪（存在一次观测能否定它）与可定位（否定它之后，怀疑区间真的变小了）。「我觉得这里有问题」不满足第二条，「循环退出时 right 应该等于 n」两条都满足。这与模块 04 里「拿到错误答案先念状态定义、再手算 dp[1]/dp[2]」是同一套方法在 DP 上的特化。

永远不要清空屏幕

面试里最糟的 debug 动作：Ctrl+A 删掉重写。它一次性抹掉了你前面所有已被认可的进展（面试官已经在心里给那 20 行打过分了），并且宣告「我不知道错在哪」。哪怕你真的觉得重写更快，也要说出来：「这段的结构我想换成 __，我保留现在这版，在下面重写一个。」——保留旧版、新开一段，这既是面试策略，也是真实工程里的正确做法。

严谨说

需要提醒的是：真实的评分卡不会完全一致，权重在不同公司/不同岗位间会浮动（例如强调交付速度的团队会把正确性提到 40%），而且面试官之间存在评分者信度（inter-rater reliability）问题——同一场面试不同人打分可能差一档。这正是structured interview（结构化面试）被广泛采用的原因：固定题目、固定维度、固定锚点描述，可以把评分者方差压下来。对你的实际含义是：你无法控制面试官的宽严，但你可以控制「每个维度上都有可打分的证据」——证据缺失时，宽严差异的影响会被放大到决定成败。

把五维评分表压成一句话：让每一个维度上都留下证据。沟通的证据是解说，测试的证据是你跑过的用例，复杂度的证据是你说出的那句 $O(\cdot)$——都是几十秒的动作，但缺一项就少 15–20 分。

严谨说

更定量一点：设题型 $i$ 出现概率 $p_i$、你在其上的通过率 $q_i$，则一面 coding 通过率近似 $\sum_i p_i q_i$。把某题的 $q_i$ 从 0.5 提到 0.9 带来的增益是 $0.4 p_i$，所以提升应该完全按 $p_i$ 排序，而不是按题目「有意思」的程度。这也是为什么本清单坚持标注频率：没有频率标注的题单，会诱导你把时间花在低 $p_i$ 的漂亮题上。另一个推论：$q_i$ 已经接近 1 的题不要再刷了，边际收益是 0——很多人反复刷两数之和就是这个错误。

7采样三题为什么是 ML 岗的签名题：正确性可以被检验

蓄水池采样、加权采样、随机打乱这三道题值得单独一节，原因不是它们难，而是它们是少数「你可以在面试里当场证明自己写对了」的题——因为正确性是一个概率陈述，可以用统计检验验证。而在数据工程侧，它们三个就是流式抽样、长尾重采样、dataloader shuffle 的内核（见 C58）。

蓄水池采样：一行归纳法

问题：数据流长度 $n$ 未知，只能过一遍，内存只放 $k$ 个，要求最终每个元素被留下的概率都是 $k/n$。算法（Vitter 的 R 算法）：前 $k$ 个直接放进蓄水池；第 $i$ 个（$i\ge k$，0-based）以概率 $k/(i+1)$ 替换池中随机一个。

\[P(\text{第 } j \text{ 个元素在处理完前 } i+1 \text{ 个后仍在池中}) = \underbrace{\frac{k}{j+1}}_{\text{它进池}}\cdot\prod_{t=j+1}^{i}\underbrace{\left(1-\frac{k}{t+1}\cdot\frac{1}{k}\right)}_{\text{第 } t \text{ 个没把它踢掉}} = \frac{k}{j+1}\prod_{t=j+1}^{i}\frac{t}{t+1} = \frac{k}{i+1}\]

面试里要说出口的是中间那个连乘的裂项：第 $t$ 个元素踢掉某个特定位置的概率是 $\frac{k}{t+1}\cdot\frac{1}{k}=\frac{1}{t+1}$，所以「没被踢掉」是 $\frac{t}{t+1}$，连乘后分子分母逐项抵消，只剩首尾。能把这三句话说清楚，这题就满分了——代码只有 6 行。

加权采样：$u^{1/w}$ 这个技巧

加权版本要求 $P(\text{选中 } i)\propto w_i$。有两条路，面试里都该知道：

方法做法复杂度适用场景陷阱
累积和 + 二分算前缀和 $W$，抽 $u\sim U(0,W)$，二分找位置预处理 O(n)，每次抽 O(log n)有放回、权重固定、要抽很多次权重更新后前缀和要重算（用树状数组可 O(log n) 更新）
A-Res（Efraimidis–Spirakis）给每个元素配 key $u_i^{1/w_i}$（$u_i\sim U(0,1)$），取 key 最大的 $k$ 个一遍 O(n log k)流式、n 未知、无放回$k>1$ 时入选概率不正比于 $w_i$
\[k=1 \text{ 时 } P(i \text{ 胜出}) = \Pr\Bigl[u_i^{1/w_i} > \max_{j\ne i} u_j^{1/w_j}\Bigr] = \frac{w_i}{\sum_j w_j}\]

最后那个「$k>1$ 时不成比例」是一个真实的面试陷阱，也是工程里的真实坑。直觉上你会以为入选概率是 $k\,w_i/\sum w_j$，但这个数可能大于 1（权重极度倾斜时），显然不可能。真实成立的只有恒等式 $\sum_i \Pr[i\in S]=k$。notebook 里用 weights=[1,1,1,1,16], k=2 把这个偏差量化出来：朴素公式预测最重的那个入选概率是 1.6（不可能），实测约 0.97，而多出来的概率质量被均摊给了四个轻元素。

算出来的比例 ≠ 实测的比例

长尾重采样里的对应事故：你想让稀有类的采样概率正比于 $1/\sqrt{f_c}$，于是用 A-Res 一次抽 $k$ 个样本组成 batch，然后在报告里写「稀有类被过采样了 8 倍」。这个 8 倍是算出来的，不是实测的，而 $k>1$ 时它不成立。正确做法是直接统计一个 epoch 里各类的实际出现次数，或者改用有放回的累积和 + 二分（此时每次独立抽样确实严格正比于权重）。重采样比例算错的后果是长尾类被过度放大，训练出一个在稀有类上过拟合、在常见类上退化的模型（见 C58-03）。

Fisher–Yates：为什么「随便换到任意位置」必然有偏

正确版本第 $i$ 步从 $[i, n)$ 里随机取一个位置交换；常见的错误版本从 $[0, n)$ 里取。错误版本看起来「更随机」（每个位置都可能被换到），但它必然有偏，而且有一个不需要做实验就能给出的证明：

\[\text{错误洗牌共有 } n^n \text{ 条等概率执行路径，而排列有 } n! \text{ 个；若输出均匀，则 } n!\mid n^n.\]

但对任意 $n\ge 3$ 这都不成立：由 Bertrand 假设，存在素数 $p$ 满足 $n/2 < p \le n$；若 $n$ 是合数则 $p\nmid n$（因为 $2p>n$），若 $n$ 本身是素数则取 $p=2$（$2\nmid n$）。无论哪种情况，$n!$ 含有一个不整除 $n$ 的素因子，因此 $n!\nmid n^n$，于是至少有两个排列的概率不同——错误洗牌不可能均匀。$n=3$ 时 $27/6$ 不整除，实测就是：3 个排列各 $4/27\approx0.148$、另 3 个各 $5/27\approx0.185$，而均匀应是 $1/6\approx0.167$。notebook 用卡方检验在 27 万次重复上把这个偏差干净地抓出来。

直白说

为什么这个证明在面试里特别值钱？因为它不需要任何实验，只用一个整除性论证就否定了一个「看起来对」的算法。这类论证的通用形式是「计数不匹配」：算法的执行路径数如果不能被输出空间的大小整除，输出就不可能均匀。同一招还能用在「用 rand5 实现 rand7 为什么必须拒绝重采样」上——$5^m$ 永远不被 7 整除，所以任何有界步数的构造都不可能精确均匀。

严谨说

严格地说，「$n^n$ 条等概率路径」依赖于随机源是理想的均匀独立比特；实际实现里还有第二层偏差：用 rand() % n 从 $[0,2^{32})$ 映射到 $[0,n)$ 时，若 $n\nmid 2^{32}$ 会产生modulo bias——前 $2^{32}\bmod n$ 个值多一次机会。对 $n\sim10^6$ 量级的数据集索引，这个相对偏差约 $n/2^{32}\approx 2\times10^{-4}$，通常无害；但在密码学场景是致命的，标准做法是拒绝采样（丢弃落在最后一个不完整区间里的值）。numpy.random.Generator.integers 与 random.randrange 都已经做了这件事，而 C/C++ 里手写的 rand()%n 没有——这在部署侧（C60）是个真实差异点。

白板 / 纯文本形式的特殊策略

不能运行是白板形式的核心约束，它带来两个必须调整的动作：

  • 把「运行」换成「手跑状态表」。在代码右侧画一张两三列的小表（如 i | left | window），一行一行填。这既是你唯一的验证手段，也是测试意识的可见证据。
  • 版面先规划再写。写满了没地方补是白板上最常见的事故。把区域预先划成「题面 + 例子」「代码」「测试与复杂度」三块，代码区每行之间留一行空——面试中一定会需要插入一行边界处理。
  • 允许自己省略样板：import、type hints、docstring 都可以口头带过（「这里我省掉 import」），但不要省略函数签名与返回语句，那是规格。

共享屏幕形式则有一个专属机会：你可以事先准备一个对拍脚本模板。题目写完后，把随机用例生成 + 暴力解对拍跑起来（模块 01–04 一直在练这件事），10 秒钟就能提供一个别人拿不到的强信号。这也是本课所有 notebook 都坚持写对拍的原因之一。

共享屏幕的三个真实事故，都发生过：① 微信/Slack 弹窗把私人消息投给了面试官；② 编辑器字号 11 pt，面试官在笔记本上完全看不清，你被反复要求「往下滚一点」而浪费 3 分钟；③ 切窗口时露出了另一家公司的面试记录或某网站的题解页面——这一条会直接结束面试。面试前 10 分钟的检查清单：勿扰模式 → 字号 → 关闭所有无关窗口 → 桌面壁纸与书签栏 → 麦克风试音。

9研究前沿与开放问题

这一节不谈刷题技巧，谈两件与本模块直接相关但尚无定论的事：coding 面试到底测出了什么，以及采样算法在流式与加权场景下仍然开放的部分。

① 技术面试的效度：一个测量学问题

结构化面试（固定题目、固定维度、固定锚点）的效标关联效度在人事心理学的元分析里长期被报告为中等偏上，明显高于非结构化面试；但「白板 coding」这一特定形式的增量效度证据相当薄弱。Behroozi 等人用眼动与皮电测量发现，「有人注视下写代码」显著提高了认知负荷，并且这种压力对不同人群的影响不均匀——也就是说，白板测到的东西里混入了一个与工作绩效无关的成分。这类结果推动了两个方向的改动：给候选人私下编码时间（take-home 或 pair programming 的前 10 分钟静默），以及把评分锚点写得更细以压低评分者方差。

与之相关的另一个开放问题是contamination（题目污染）：公开题库被大规模刷过之后，「一次写对」这个信号的信息量在下降。近年的补偿手段是加一层未见过的变形（改约束、要求流式、要求原地、要求给出反例），以及把追问的权重提高——这正是本模块把「说清取舍」而不是「写得快」当成核心训练目标的原因。

② LLM 时代的面试形式：还没有共识

大模型可以在几秒内解掉绝大多数经典题，这让「无监督环境下的远程 coding 题」失去了区分度。目前业界在四种方案之间摇摆：回到线下白板；改成 AI 辅助允许但考「你怎么审阅与修正 AI 的输出」；换成基于候选人自己代码库的深度追问；以及引入监考与击键分析。四种都有明显缺陷（成本、公平性、隐私、可绕过），没有一种被证明有更高效度。对你的实际含义：「能说清为什么」的权重只会继续上升，因为它是最难被外部工具代劳的部分。

③ 采样算法里仍然开放的部分

  • 无放回加权采样的入选概率控制。A-Res 简单高效但 $k>1$ 时入选概率不正比于权重；要精确控制入选概率需要 $\pi$ps 类设计（Sampford、Tillé、Chao 的方法），代价是实现复杂或需要多遍数据。在长尾重采样里，这决定了你报告的「过采样倍数」是否真实（见 C58-03）。
  • 滑动窗口上的均匀采样。只对「最近 $W$ 个元素」均匀采样，不能重扫历史——Babcock 等人的 chain/priority sampling 给出了 $O(k)$ 空间的方案，但在窗口按时间而非按计数定义、且到达率剧烈波动时，方差控制仍是活跃问题。这正是车端日志采样的真实形态。
  • 分布式/并行下的可复现性。多 worker 的 dataloader 要同时满足「全局无放回」「跨 epoch 可复现」「worker 数变化后仍等价」——这三条不能同时廉价满足。目前的工程解是按 epoch 用主种子生成全局排列再切片，代价是排列必须能装进内存（见 C60 关于训练-部署一致性的讨论）。
  • 难例挖掘中的采样偏差。按 loss 采样会形成反馈回路：被采到的样本影响模型，模型又影响下一轮的 loss 排序。重要性采样的无偏修正（如按 $1/p_i$ 加权）在实践中方差极大，如何在偏差与方差间取点仍无标准答案（C58-04）。
