1后处理：训练-部署鸿沟的最后一公里

模块 01 处理预处理、模块 02–03 处理模型本身。到这一节，你的 ONNX 已经导出、engine 已经构建、INT8 已经校准到掉点 0.4 mAP。然后你把它接到车上，框整体往下偏了 420 像素。

直白说

后处理 bug 最气人的地方，是它不会让你的程序崩溃，也不会让 mAP 变成 0。它让 mAP 从 0.82 掉到 0.71，然后你会花两周去怀疑量化、怀疑校准集、怀疑车端相机的色彩空间——因为「掉 11 个点」看起来太像一个模型问题了。而真相可能只是逆变换里少减了一个 pad。

严谨说

更准确地说：后处理 bug 制造的是systematic error（系统误差）而非 random error（随机误差）。系统误差在 mAP 这类聚合指标上表现为一个平滑的下降，与「模型能力不足」在数值上不可区分；但在逐样本的对拍上，它表现为一个恒定的偏差项，一眼可辨。这就是为什么本模块的核心方法论是「逐阶段对拍」而不是「看指标」——把聚合指标换成逐元素比较，系统误差立刻从伪装中掉出来。这也是模块 00 那句「任何一致性问题都能在 30 分钟内定位到具体层」的兑现方式。

别把「排查一致性」答成「dump 每一层」

面试高频题：「训练和部署结果对不上，你怎么排查？」差答案是「逐层 dump 看哪层不一样」——这只覆盖了模型层，而模型层恰恰是最不容易出错的那一层（因为它有同一份 ONNX 作锚点）。满分答案的结构是：①先说三层划分（预处理 / 模型 / 后处理）与各自的典型故障率——业界经验里预处理与后处理合起来占绝大多数；②再说定位方法是「固定输入，逐阶段二分」，而不是「猜」；③然后主动举一两个具体分歧点（letterbox 逆变换的顺序、IoU 的 +1、sigmoid 在模型内外）；④最后说这套对拍工具应该在项目第一天就写好，而不是出事时才写。第④点是区分「修过 bug 的人」和「负责过交付的人」的分水岭。

本节的一句话：后处理是唯一一段「两份实现、零份约束」的代码。它的 bug 不会报错，只会让你误判成模型问题。

2NMS 的实现分歧：+1 约定、调用顺序与排序稳定性

先看一段几乎每个检测代码库里都出现过的代码——它来自 R-CNN / Fast R-CNN / Faster R-CNN 的 py_cpu_nms.py，被无数项目复制粘贴过：

# Faster R-CNN 时代的 NMS（Pascal VOC 口径）
areas = (x2 - x1 + 1) * (y2 - y1 + 1)          # ← 注意 +1
...
w = np.maximum(0.0, xx2 - xx1 + 1)             # ← 注意 +1
h = np.maximum(0.0, yy2 - yy1 + 1)
inter = w * h
ovr = inter / (areas[i] + areas[order[1:]] - inter)

# Detectron2 / COCO 时代
areas = (x2 - x1) * (y2 - y1)                  # ← 没有 +1
inter = max(0, xx2 - xx1) * max(0, yy2 - yy1)

这个 +1 从哪来

它不是笔误，是坐标语义的差别。Pascal VOC 的标注是「像素索引」：框 [0, 0, 7, 7] 表示从第 0 个像素到第 7 个像素，闭区间，一共 8 个像素，所以宽度是 $7-0+1=8$。COCO 的标注是「连续坐标」：框 [0, 0, 8, 8] 表示从坐标 0 到坐标 8 的半开区间，宽度就是 $8-0=8$。两种约定各自自洽，但把 VOC 的公式套到 COCO 的坐标上，每个框就凭空胖了一个像素。

\[\text{IoU}_{+1}(A,B) \;=\; \frac{(w_\cap+1)(h_\cap+1)}{(w_A+1)(h_A+1)+(w_B+1)(h_B+1)-(w_\cap+1)(h_\cap+1)} \;\ne\; \frac{w_\cap h_\cap}{w_A h_A + w_B h_B - w_\cap h_\cap} \;=\; \text{IoU}_{0}(A,B)\]

差多少：一个可以背下来的数字对

取两个边长 $s$、沿对角线错开 $d = s/4$ 像素的正方形框（相对位移固定为 25%，这正是同一目标上两个相邻候选框的典型关系）：

注意左边那一列：$\text{IoU}_0$ 在所有尺度上都恰好是 0.3913——它是尺度不变的（两个相似形的交并比只取决于相对位移 $d/s$）。而 $\text{IoU}_{+1}$ 不是：那个 $+1$ 是一个绝对像素量，它相对于 8 px 的框是 12.5% 的膨胀，相对于 64 px 的框只有 1.6%。

\[\Delta(s) \;=\; \text{IoU}_{+1}(s) - \text{IoU}_{0}(s) \;\sim\; \mathcal{O}\!\left(\tfrac{1}{s}\right) \qquad \text{（notebook 会用数值扫描验证这个 } 1/s \text{ 衰减）}\]

直白说

所以 +1 是一个只伤害小目标的 bug。你在 COCO 上跑，AP 差 0.1，觉得「无所谓」；换到 TSR 数据上，标志普遍只有 10–30 像素，同一个不一致就会让两侧的 NMS 在每一个密集场景上给出不同的保留集。而它在指标上的表现是「小目标桶掉点」——和「模型对小目标不行」长得一模一样。

严谨说

把它放到更一般的框架里：任何绝对像素量级的约定差异，其相对影响都与目标尺寸成反比。除了 +1，同类的还有：坐标 round 与 floor 的差别（±0.5 px）、letterbox padding 的奇偶取整（±0.5 px）、resize 时 align_corners 的半像素偏移（±0.5 px，见模块 01）。单个都是亚像素级，看起来可以忽略；但它们会叠加，而且全部只在小目标上放大。一个 12 px 的框累计偏 1.5 px，IoU 就掉到 $(10.5)^2/(2\cdot144-110.25)=0.62$；再叠一个 +1 约定的差异，抑制决策就可能翻转。这就是为什么本课坚持「逐元素对拍」而不是「肉眼看框画得对不对」——1.5 px 用眼睛看不出来。

一致性是「标注 / 训练+评测 / 部署」三方一致

不要试图「统一到有 +1」或「统一到没有 +1」然后就完事。正确的做法是：①确认你的标注用的是哪种坐标语义（VOC 风格的整数像素索引，还是 COCO 风格的连续坐标）；②让训练时的 IoU、评测时的 IoU、部署时 NMS 的 IoU 三者与标注语义一致。最常见的真实事故是只改了部署侧——于是部署和训练一致了，但和评测口径不一致，线下测出来的 AP 不再代表线上行为。一致性是三方的，不是两方的。

除了 +1，NMS 还有三处「顺序」分歧

IoU 的定义只是第一层。NMS 从来不是孤立调用的，它前后有一串筛选步骤——而这些步骤的顺序不写在任何接口签名里，却完全决定了输出。

「我只要 300 个框，那我 topK 就设 300」——这句话是本节最贵的一句话。把 EfficientNMS 的 topK 从默认的几千调到 300，engine 会小一点、快一点，评测集上 mAP 掉 0.2，看起来是个划算的交易。然后在城市路口，你的 TSR 会成片漏掉标志。正确的设置原则是：NMS 前的 topK 要按「单帧最大过阈候选数」留 2–3 倍余量（通常几千），NMS 后的 max_det 才按「单帧最大目标数」设（通常几百）。这两个参数解决的是完全不同的问题，名字像但不能互相替代。

② per-class 还是 global

top-k 是对所有类别的所有框取，还是每个类别各取 k 个？在 TSR 这种 100–300 类的任务上，差别是数量级的。global top-300 在一帧里如果有 200 个「限速 60」的高分候选，就会把其他所有类别挤到 100 个名额里；per-class top-10 则保证每个类别都有代表，但总数会涨到 $300\times 10=3000$。mmdetection 的「逐 FPN 层级 top-k」是第三种切法——它保证的是「小目标层不会被大目标层挤掉」，这对 TSR 比按类别切更有价值。

③ 排序的稳定性：一个只在 INT8 上出现的诡异分歧

直白说

分数相同的两个框，谁排前面？Python 的 np.argsort 默认用 quicksort（不稳定），C++ 的 std::sort 也不稳定，而且两者的「不稳定」方式不同。FP32/FP16 下这不是问题——浮点分数几乎不会精确相等。但 INT8 模型的输出经过反量化后，取值集合是离散的：一个 per-tensor 量化的分类头，输出只有约 256 个可能值。一帧里 1600 个过阈候选，分数的唯一值可能只有 30 几个，平均每个值挤着 50 个框。于是 NMS 的第一个「保留」是谁，取决于排序算法的实现细节——两侧输出的框集合会不一样，而且不可复现。

严谨说

严格地说，NMS 是一个order-dependent（依赖顺序）的贪心算法：保留集 $\mathcal{K}$ 由遍历顺序唯一决定，而遍历顺序在存在并列分数时是欠定的。修法有三档：①最省事——排序用稳定排序（np.argsort(kind='stable') / std::stable_sort），并保证两侧的输入框顺序也一致（这一条常被忘：稳定排序只保证「相等元素保持输入顺序」，如果输入顺序本身不同，稳定也救不了）；②更稳——把索引作为第二排序键，显式定义全序：key = (-score, flat_index)；③最稳——在 NMS 之前对分数做一次微小的确定性扰动打破并列（不推荐，会污染分数语义）。量产项目应该选 ②：它让 NMS 的输出成为输入的确定性函数，与语言、库、优化等级全部无关。这也是让端到端对拍能用 == 而不是「差不多」的前提。

把三个顺序问题压成一条检查：写下你这条管线里「筛选」发生的每一个位置，标注它是按什么排序、截断到多少、发生在 NMS 前还是后。两侧各写一份，对着看。这张表通常只有 5–6 行，但它能提前消灭本模块一半的坑。

batched NMS 的 offset trick：一次调用做完 class-wise

逐类循环调 NMS 在 GPU 上非常糟糕：80 个类就是 80 次 kernel launch，每次只处理几十个框，全是启动开销。标准技巧是给每个框的坐标加上 class_id × offset，把不同类别的框推到互不相交的坐标区间，然后做一次 class-agnostic NMS——数学上与 class-wise 严格等价（不同类的框永远不重叠，IoU 恒为 0），但只有一次调用。torchvision.ops.batched_nms 就是这么实现的。

\[\tilde{b}_i \;=\; b_i \;+\; c_i \cdot \Delta \cdot \mathbf{1}_4, \qquad \Delta \;>\; \max_i \bigl(\max(x_{2,i},\, y_{2,i})\bigr) \;\Longrightarrow\; \text{IoU}(\tilde{b}_i, \tilde{b}_j) = 0 \ \ \forall\, c_i \ne c_j\]
offset 越大越安全？恰恰相反

offset trick 有一个真实存在的数值悬崖：float32 的精度会在大坐标上崩掉。float32 的尾数是 24 位，在数值 $v$ 附近的最小间隔（ULP）约为 $v \cdot 2^{-23} \approx 1.2\times10^{-7} v$。取 $\Delta = 10^6$、类别 ID 到 1000 时，坐标量级是 $10^9$，此时 ULP ≈ 64 像素——一个 8 像素宽的框，$x_1$ 和 $x_2$ 会被舍入到同一个浮点数，宽度变成 0，面积变成 0，IoU 变成 NaN 或 0，NMS 完全失效但不报任何错。notebook 里会用 np.float32 把这个悬崖打出来给你看。正确做法：$\Delta$ 取「图像最大边 + 1」而不是一个拍脑袋的大数；或者干脆用 int32/float64 做坐标运算。另一个更稳的做法是把类别偏移加在整数网格上——先把坐标量化到 int32，加完 offset 再算 IoU。

TSR 场景：为什么这里必须做层次化

交通标志有一个别的检测任务少见的性质：细类之间在视觉上极度相似，但在语义上互斥。「限速 60」和「限速 80」的牌子形状一样、颜色一样、位置一样，只有中间的数字不同——而那个数字在 14 像素的牌子上只占 5×7 像素。模型在同一个位置同时输出「限速 60，0.52」和「限速 80，0.47」是完全正常的行为，不是 bug。

  • 用 class-wise：两个框都送给下游。下游拿到「这里既是限速 60 又是限速 80」，被迫自己做消歧——而下游（跟踪、地图匹配、规控）根本没有做这件事的信息。真实后果是：车会按哪个限速走？如果规控保守地取小值，那么每次「限速 80 误检成 60」都会造成无谓减速。
  • 用 class-agnostic：只留 0.52 那个。干净了，但代价是组合牌被误删——中国道路上「限速 40」下面挂「货车」辅助牌、或者「禁止左转 + 时段说明」上下叠放是常见配置，两块牌子的框在图像上高度重叠（IoU 可以到 0.4 以上），class-agnostic 会把辅助牌整个抹掉。而辅助牌恰恰承载着限定条件——把「7:00–20:00 限行」的辅助牌删掉，剩下的主牌语义就是错的。
  • 层次化：定义超类 {限速类}、{禁令类}、{辅助牌类}、{指路类}。同超类内 agnostic（限速 60 和限速 80 互相抑制，只留一个 + 把落选类别的分数一并上报给下游做消歧），跨超类 class-wise（主牌和辅助牌互不抑制）。这是唯一同时解决两个问题的模式。

直白说

选哪个模式，取决于你对「这两个框可不可能同时为真」的物理判断。同一块物理牌子不可能既是限速 60 又是限速 80——所以它们该互相抑制；一块主牌和它下面的辅助牌是两块物理牌子——所以它们不该互相抑制。NMS 的模式选择本质上是在编码「什么东西在物理世界里能共存」这个先验。

严谨说

工程上还要多做一件事：被抑制的框不该直接丢掉，应该把它的类别与分数作为「竞争假设」附在保留框上传给下游。理由是时序——单帧上「60 得 0.52 / 80 得 0.47」几乎是抛硬币，但连续 10 帧的累积证据可以把它分开（C55 模块 04 的多帧投票）。如果你在 NMS 里就把 0.47 那个丢了，下游永远拿不到这个信息，多帧融合就退化成「对单帧硬判决做投票」，而不是「对单帧似然做累积」——后者的收敛速度和抗噪能力都显著更好。换句话说：NMS 的输出接口不该是「框 + 一个类别」，而该是「框 + 一个超类内的类别分布」。这一点在把感知结果送进 VLA 时同样关键（C59 模块 03）。

4解码约定：激活函数、坐标格式与归一化

模型的输出张量是一堆没有类型信息的浮点数。「它们是什么」完全靠约定，而约定不在张量里。这一节把四类约定逐一列出，每类都给「弄错的症状」。

① sigmoid / softmax 在模型内还是模型外

把激活放进 ONNX 的好处是 C++ 端不用做、也不会做错；坏处是如果 Python 侧的后处理仍然按老习惯再做一次，你就得到了 $\sigma(\sigma(x))$。这个 bug 值得单独拿出来讲，因为它是本模块最阴险的一个：

\[\sigma(\sigma(x)) \in \bigl(\sigma(0),\ \sigma(1)\bigr) = (0.500,\ 0.731) \qquad \forall\, x \in \mathbb{R}\]
  • 所有分数都被压进 (0.5, 0.731)。你设的 score_thr = 0.3 于是一个框都筛不掉——8400 个候选全部过阈。
  • mAP 几乎不变。因为 $\sigma$ 是严格单调的，排序完全不受影响，而 AP 是纯粹基于排序的指标。所以离线评测报告是绿的。
  • 线上表现：候选数从 1600 涨到 8400 → NMS 耗时涨一个量级（$O(NK)$，见 C53 模块 04）→ 延迟 p99 爆表；同时误检率暴涨，因为所有背景框都过了阈值。
  • 诊断只要一行：打印全部分数的 min()。如果最小值大于 0.5，你就抓到它了。

反过来的错误同样常见：模型输出的是 logits（没有做 sigmoid），而 C++ 端直接拿去和 score_thr=0.3 比。logit 0.3 对应的概率是 $\sigma(0.3)=0.574$——阈值被无意中抬高了近一倍，症状是召回莫名其妙地掉，尤其是远处小目标（它们的置信度本来就低）。这两个错误的方向相反，但都不会报错。唯一可靠的防线是在对拍框架里把「模型原始输出」和「激活后分数」当成两个独立阶段分别比对（见第 8 节）。

② softmax 有背景类，sigmoid 没有

多类互斥头（softmax）通常有一个 background / no-object 类占据 index 0，前景类别从 1 开始；多标签头（sigmoid）每个通道就是一个前景类，从 0 开始。换头不改后处理 = 全部类别 ID 偏移 1——症状是 mAP 恒为 0 或极低，且预测类别的分布整体平移。这是「mAP 恒为 0」的三大成因之一（另两个见 C61 模块 03）。

③ 坐标格式：四种，没有一种自带标签

④ 归一化坐标 vs 像素坐标，以及「相对于谁」

这是四类里最容易出「安静失败」的一类。归一化坐标要回答一个额外的问题：相对于哪张图归一化？

  • 相对网络输入（含 padding 的 640×640）：DETR 系与多数导出脚本的默认。逆变换要先乘 640，再减 pad，再除 $r$。
  • 相对 letterbox 内的有效区域（640×360）：少数实现如此。逆变换只要乘原图尺寸。
  • 相对原图（1920×1080）：模型内部已经做完逆变换（有些导出脚本会把 $r$ 和 pad 作为常量折进图里）。这时 C++ 端再做一次逆变换就是灾难。

前两者之间只差一个 letterbox 比例——框会整体偏 10–20%，mAP 掉 5–10 点，看起来完完全全像「模型不行」。而「归一化当像素用」（框全挤在左上 1×1 像素里）和「像素当归一化用」（框被 clip 成全图一个大框）这两种是响亮失败，反而三秒就能发现。响亮的 bug 是好 bug；本模块真正要防的是安静的那些。

完整的坐标变换链

\[b_{\text{orig}} \;=\; \operatorname{clip}_{[0,W]\times[0,H]}\Bigl(\ \tfrac{1}{r}\bigl(\ \underbrace{T_{\text{fmt}}(b_{\text{net}})}_{\text{③ 格式转换}} \odot \underbrace{s}_{\text{④ 归一化尺度}} \;-\; \underbrace{p}_{\text{⑤ letterbox pad}}\ \bigr)\ \Bigr)\]

直白说

五个环节：格式（xyxy/cxcywh/…）、尺度（归一化还是像素）、pad、缩放比、clip 范围。任何一个环节两侧不一致，结果就错；而它们都不会报错。五个二值/多值选择组合起来是几十种可能的管线，其中只有一种是对的。

严谨说

工程上唯一可靠的做法是把这条变换链写成一个显式的、有单元测试的数据结构，而不是散落在代码里的几行算术。具体地：定义一个 CoordTransform 对象，字段是 $(r, p_x, p_y, W_{\text{net}}, H_{\text{net}}, W_{\text{orig}}, H_{\text{orig}}, \text{fmt}, \text{normalized})$，由预处理阶段生成并随帧传递，后处理阶段直接消费。关键在于「随帧传递」——它保证了逆变换用的参数一定是这一帧正变换时用的参数，而不是从配置文件里重新读一遍（配置文件读错、或者动态分辨率下参数变了没同步，都是真实事故）。再给它配一条不变量测试：inverse(forward(b)) ≈ b 对随机框成立到 $10^{-6}$。这条往返测试能在 CI 里挡住本节几乎所有的坑，代价是 20 行代码。

亚像素分歧：为什么 1 px 也要管

$1080 \times \tfrac13 = 360$ 是整数，很干净。但换一个分辨率，比如 $1920\times1084 \to 640$：$r = 1/3$，$rH = 361.33$，实现必须取整——round 得 361，floor 得 361，ceil 得 362。于是 $p_y = (640-361)/2 = 139.5$，而 padding 必须是整数像素：一侧 139、另一侧 140。逆变换该减 139 还是 139.5？两者差 0.5 px；而且实际的垂直缩放比是 $361/1084 = 0.33303$，不是名义的 $0.33333$。

\[\text{IoU}\bigl(b,\ b + (\delta,\delta)\bigr) \;=\; \frac{(s-\delta)^2}{2s^2 - (s-\delta)^2} \qquad\Longrightarrow\qquad \begin{cases} s=12,\ \delta=4: & \text{IoU} = \tfrac{64}{224} = \mathbf{0.286} \\[2pt] s=100,\ \delta=4: & \text{IoU} = \tfrac{9216}{10784} = \mathbf{0.855} \end{cases}\]
4 px 偏移：大牌 0.855，小牌 0.286

这两个数字是本模块最该背下来的一对。同样一个 4 像素的系统性偏移：在 100 px 的近处大牌上，IoU 还有 0.855，在任何评测口径下都算命中，你永远不会发现；在 12 px 的远处小牌上，IoU 只有 0.286，在 IoU=0.5 的口径下直接算完全漏检。于是你的报告上写着「小目标 AP 从 0.41 掉到 0.19，大目标 AP 不变」，而你会开始怀疑输入分辨率、怀疑 P2 层、怀疑 anchor 设置——因为这个指标形态和「模型对小目标不行」完全一样。TSR 是这个陷阱的完美受害者：它的目标常年在 10–30 px，而它的评测集里近处大牌又足够多，足以让总体 mAP 只掉几个点而不是崩掉。结论：凡是「只有小目标桶掉点」，第一个怀疑对象永远是坐标变换，而不是模型能力。

直白说

所以逆变换的正确性不能靠「画出来看着对」——4 像素在一张 1920 宽的图上是肉眼不可见的。唯一可靠的验证是往返测试：随机生成原图坐标的框，正变换到网络坐标，再逆变换回来，要求误差 < $10^{-6}$。这条测试 20 行，能挡住 E1–E4 全部四种错法。

严谨说

E5 需要单独一条测试，因为它不是数值错误而是语义错误：clip 的作用是「把框限制在真实图像范围内」。在网络坐标下 clip 到 $[0, 640]$，等价于允许框延伸到 padding 区域——而 padding 区域在原图上根本不存在。正确顺序是先逆变换回原图坐标，再 clip 到 $[0,W]\times[0,H]$。更彻底的做法是在 clip 之前先做一次「有效性过滤」：逆变换后宽或高 $\le 1$ 像素的框直接丢弃——因为一个被 clip 到只剩 1 px 宽的框，说明它原本几乎完全在图外，属于边缘伪检。在 TSR 里这条过滤特别有用：图像边缘常有半个标志（正在驶出视野），它们的框会被 clip 得很扁，而这类残缺目标的分类结果基本不可信，早点丢掉比送给下游做多帧融合更安全。

6后处理放 GPU 还是 CPU：拷贝量、plugin 与可调试性

后处理的物理位置有三种选择，它们的差别不在「快多少」，而在要搬多少字节过 PCIe/内存总线——这一项常常比计算本身贵得多。

先把账算清楚。一个 TSR 检测器，640×640 输入、三尺度 8400 个位置、200 个类别，raw 输出张量是 $8400 \times (4 + 200) = 1{,}713{,}600$ 个 float16，约 3.43 MB（float32 则是 6.85 MB）：

把阈值烧进 engine 是一个经常被低估的代价。检测器的工作点（score 阈值）不是一次定死的：上线后你会根据路测的 FP/km 反复微调，会为不同车型/不同区域配不同的值，会在雨天动态放宽。如果阈值在 plugin 里，每一次微调都要走「重建 engine → 重新验证 → 重新发版」的完整流程，而 engine 还和 GPU 型号 + 驱动 + TRT 版本绑定（模块 02），意味着每个硬件平台都要重建一遍。实践中常见的折中是：plugin 里把 score_threshold 设得很低（比如 0.01，只用来控计算量），真正的工作点阈值留在 plugin 之外的 C++ 里做二次过滤。这样既拿到了 GPU NMS 的延迟收益，又保住了阈值的可运行时调整。

直白说

所以三种方案不是「选一个」，而是同时保留两条路：一条 debug engine 输出 raw tensor（方案 A/B），一条 release engine 内含 plugin（方案 C）。发布前用对拍工具验证两条路在同一批图上输出一致；线上跑 release，出问题时切 debug 复现。两个 engine 从同一份 ONNX 构建，多花的只是几分钟构建时间。

严谨说

更严格的做法是把「后处理」定义成一份与实现无关的规格（spec）：明确写下激活函数、阈值顺序、topK 位置与语义、IoU 的边界约定、NMS 模式与超类划分、坐标格式与变换链、clip 与丢弃规则。然后三份实现（Python 参考 / C++ 手写 / TRT plugin 配置）都必须通过同一套 spec 测试用例。这套测试用例应该包含精心构造的边界样本：IoU 恰好等于阈值的一对框（测 > vs >=）、分数完全相同的一对框（测排序稳定性）、面积为 0 的退化框、坐标为负的框、超出图像边界的框、单帧候选数超过 topK 的密集帧。这些用例每一个都对应本模块讲过的一个坑，加起来不到 200 行，却是整条部署链路上投入产出比最高的代码。

7C++ 推理管线：内存、流、线程与相机对接

到这里语义都对齐了，剩下的是「怎么把它跑起来还跑得稳」。这一节讲 C++ 侧的结构——面试里问「你写过 C++ 推理管线吗」，考的不是你会不会写 cudaMemcpy，而是你知不知道哪些事在稳态运行期是禁止做的。

① 内存：稳态期不许分配

  • cudaMalloc 在稳态运行期是禁止的。它不只是慢——它会隐式同步整个 device，把你精心搭的异步流水线拦腰截断，制造几毫秒的延迟尖峰。所有 device buffer 必须在初始化阶段一次性分配好。
  • 动态 shape 下按 max profile 分配。模块 02 讲的 min/opt/max 三档，内存要按 max 那档算，运行时只改 setInputShape，不重新分配。
  • Host 侧必须用 pinned memory（cudaHostAlloc）。这一条最常被忽略：cudaMemcpyAsync 作用在 pageable memory 上时，实际行为是同步的——driver 必须先把数据搬到一个内部的 staging buffer。「我明明用了 Async 为什么还是阻塞」的标准答案就是这个。
  • 输出 buffer 双缓冲。第 $k$ 帧的结果还在被后处理消费时，第 $k+1$ 帧的推理已经在写输出了——单缓冲会数据竞争，而这种竞争在低负载时不会发作，只在延迟抖动大时偶发，是最难查的一类 bug。

② 流与同步：每帧只允许一个同步点

一条 CUDA stream 内部是严格顺序的，所以「预处理 kernel → enqueue → 后处理 kernel → D2H」放同一条 stream 就不需要任何显式同步，GPU 会自己保证顺序。整帧唯一需要 cudaStreamSynchronize 的地方，是 CPU 要读取最终结果的那一刻。

多余的同步：延迟没变，吞吐减半

中间插同步 = 流水线断流。最常见的写法错误是「为了调试方便」在每个阶段后面加一句 cudaDeviceSynchronize()，然后忘了删。症状是：单帧延迟没变多少（因为工作量没变），但吞吐掉一半——因为 CPU 与 GPU 完全串行了，CPU 提交下一帧的时间无法与 GPU 执行当前帧重叠。更隐蔽的同步点还有：cudaMemcpy（非 Async 版）、cudaMalloc/cudaFree、对 device memory 的 cudaMemset（非 Async）、以及 profiler 工具本身。排查方法：用 Nsight Systems 看时间线上 CPU 与 GPU 的重叠度；如果两条泳道是交替而不是重叠的，就有多余的同步。

③ 零拷贝：在车端 SoC 上不是「一定更好」

直白说

Jetson/Orin 这类 SoC 上 CPU 和 GPU 共享同一块物理 DRAM，理论上完全不需要 H2D 拷贝——用 cudaHostAllocMapped 或统一内存，GPU 直接读 CPU 写的那块内存就行。相机的 dmabuf 也可以直接映射给 CUDA，省掉「ISP 输出 → CPU buffer → GPU buffer」这两跳。省下的是每帧 1–4 MB 的搬运。

严谨说

但零拷贝有两个真实代价，忽略它们会得到反效果。①缓存一致性：mapped pinned memory 在 Orin 上通常是 uncached 或 write-combined 的，CPU 读它会非常慢（每次都要走 DRAM，没有 cache 命中）。如果你的 CPU 侧还要遍历这块内存做点什么，代价可能远超省下的拷贝。②访问带宽：GPU 访问 mapped host memory 的有效带宽低于访问 device memory，如果这块数据要被 kernel 反复读取（比如预处理 kernel 多次采样输入图），零拷贝反而更慢。正确的判据是「这块数据被读几次」：只读一次（比如从相机 buffer 读一遍做 letterbox）→ 零拷贝划算；要反复读 → 老老实实拷到 device memory。这也是为什么典型管线里「相机 → 预处理输入」用零拷贝，而「预处理输出 → 推理输入」用普通 device memory。

⑤ 与相机管线对接的四个细节

  • 时间戳必须是「曝光中点」而不是「帧到达时刻」。下游的时序融合、运动补偿、与 IMU/定位的对齐全都依赖这个时间戳。用到达时刻会引入一个随系统负载波动的偏差——而这个偏差直接变成标志位置的估计误差：车速 100 km/h 时，10 ms 的时间戳误差就是 0.28 m 的纵向位置误差。
  • 队列满时丢最老的帧，不能丢最新的。感知的价值随时间衰减，一帧 100 ms 前的图像对规控几乎无用。反直觉的是很多默认队列实现是「满了就阻塞」或「丢新的」。
  • 丢帧必须被计数并上报。静默丢帧会让下游的多帧融合逻辑（C55 模块 04）误以为目标消失了，触发错误的「lost」状态转移。正确做法是把 frame_id 传下去，让下游知道中间跳过了几帧。
  • 多相机要么硬件同步，要么在下游按时间戳重采样。前视长焦和前视广角如果差 15 ms，同一块标志在两路上的位置差可达十几像素，跨相机关联会失败。

C++ 管线的一句话心法：初始化时把所有能分配的都分配掉，稳态期只做「算」不做「管」。凡是运行期还在 malloc / 同步 / 创建对象的地方，都是未来延迟尖峰的来源。

8端到端对拍：从图像文件到最终框

前面八节列出了大约二十个可能的分歧点。你不需要记住它们——你需要一个能在 30 分钟内把任意一个揪出来的工具。这一节讲这个工具怎么设计。

核心原则：固定输入，逐阶段比对，二分定位

对拍不是「跑一遍看框对不对」，而是把管线切成有序的阶段，每个阶段 dump 一个张量，两侧逐元素比。第一个超出容差的阶段，就是 bug 所在。八个阶段用二分只要 3 步。

对拍必须让模型层完全相同

第 4 阶段的容差是整套工具里最需要动脑的一格。如果你的 Python 侧跑 PyTorch、C++ 侧跑 INT8 engine，那么第 4 阶段的差异里混进了量化误差——它本来就该有差异，你无法据此判断后面的分歧是谁造成的。正确做法是让 Python 侧也通过 TRT 的 Python API 加载同一个 engine 跑推理。这样第 4 阶段的两侧应当逐位相同（或只差非确定性 kernel 的 $10^{-6}$），模型层被彻底排除，剩下的差异必然来自预处理或后处理。这一步是把「三层鸿沟」压缩成「两层」的关键操作，也是很多团队的对拍工具用不起来的原因——他们比的是两个不同的模型。

工具的工程形态

  • C++ 侧编译一个 --dump-stage=N 的 debug 模式，把指定阶段的张量写成 .npy。不需要依赖任何库——npy 格式的写入器自己实现只要约 100 行（一个固定的魔数头 + shape/dtype 描述 + 裸数据）。
  • Python 侧一个脚本读进来逐阶段比，输出一张表：阶段名 / 是否通过 / 最大差异 / 失配元素占比 / 定位提示。
  • 把它接进 CI：每次改动后处理代码，用固定的 5–10 张回归图跑一遍对拍，全绿才允许合并。这是本模块所有内容里唯一能防止问题（而不是修复问题）的一条。
  • 回归图要精心选：一张稀疏帧、一张密集帧（候选数逼近 topK）、一张有并列分数的 INT8 帧、一张目标贴边缘的帧、一张极端长宽比的帧（触发 letterbox 的非对称 pad）。每一张都对应本模块的一个坑。

直白说

为什么是「逐阶段」而不是「最后比框」？因为最后比框只能告诉你「不一样」，不能告诉你「哪里不一样」。而后处理有二十个可能的分歧点，靠猜的期望代价是十次尝试；靠二分是三次。更重要的是：某些分歧在最终框上会互相抵消或被掩盖——比如 topK 截断掉了一批低分框，而这些框本来也会被 NMS 抑制，最终框完全相同；但换一帧密集图它就发作了。逐阶段对拍能抓到这种「潜伏的」不一致。

严谨说

这套方法的理论基础是把管线看成函数复合 $f = f_8 \circ \cdots \circ f_1$，两侧的差异 $\|f^{\text{py}}(x) - f^{\text{cpp}}(x)\|$ 是各级差异沿链条传播与放大的结果。逐阶段比对等价于对每个 $f_i$ 单独做等价性检验，把一个复合函数的调试问题分解成 8 个独立的单元测试。容差的设定要考虑传播：第 3 阶段 $10^{-5}$ 的相对误差，经过模型可能被放大到第 4 阶段的 $10^{-3}$（取决于网络的 Lipschitz 常数），再经过 NMS 这种不连续的算子可能变成第 7 阶段的「保留集完全不同」。所以第 6、7 阶段的容差必须是「离散的相等」而不是「数值接近」——候选数 N 差 1 个就是不通过，因为 NMS 之后它可能变成几十个框的差别。这个「在不连续算子处收紧容差」的原则，适用于任何含有排序、阈值、argmax 的管线。

本模块的终极结论：后处理一致性不是靠「小心」保证的，是靠「工具 + CI + spec 测试用例」保证的。一个新人写 C++ 后处理时会踩本模块的每一个坑——这不是他的问题，是流程的问题。对拍工具应该在项目第一天就存在，而不是第一次出事之后。

9研究前沿与开放问题

  • 端到端检测器把后处理一致性问题「结构性地」消掉了一大半。RT-DETR / YOLOv10 这类无 NMS 的模型，后处理只剩「top-k + 阈值 + 逆变换」，本模块第 2、3、4 节的坑（IoU 约定、topK 位置、class-wise 模式）全部消失。这是「无 NMS」被严重低估的部署价值——它省下的不只是几毫秒，还有一整类难以自动检测的一致性风险。C53 模块 04 从延迟角度讲了同一件事，两个角度加起来才是完整的论证。
  • 后处理算子的标准化仍然没做成。ONNX 从 opset 10 起有 NonMaxSuppression 算子，但它的语义（per-class、max_output_boxes_per_class 的计数方式、center_point_box 的坐标约定）与各框架、各推理后端的原生实现都对不齐；TRT 的 EfficientNMS 是自己一套；各家 NPU/DSP 的 NMS 加速器又是另一套。「同一个 ONNX 在两个后端上给出不同框」目前仍是常态，而不是 bug。
  • 差分测试（differential testing）与变形测试（metamorphic testing）应用到后处理。自动生成大量随机框-分数组合，喂给两份实现找分歧——这在编译器和数据库领域是成熟技术，在推理管线上还很少见。难点在于生成「有意义的」测试用例：完全随机的框很少触发边界条件，需要有导向地生成 IoU 恰在阈值附近、分数并列、面积退化的样本。这是一个门槛不高、工程价值很直接的方向。
  • 从单一 spec 生成多份实现（single source of truth）。用一份声明式的后处理描述（激活 / 阈值顺序 / NMS 模式 / 坐标约定）codegen 出 Python 参考实现、C++ 实现和 plugin 配置，让「两份实现不一致」在结构上不可能发生。已有零星尝试（如把后处理写进 ONNX 图、或用 MLIR 描述），但没有形成通用方案——主要障碍是不同后端的算子能力差异太大。
  • 数值可复现性与非确定性 kernel。TRT 的部分 kernel 使用 atomic 累加，浮点加法不满足结合律，同一输入两次运行可能差 $10^{-6}$。这个量级本身无害，但经过 NMS 这种不连续算子后可能被放大成「保留集不同」——尤其当分数并列时。「如何让整条推理管线逐位可复现」在功能安全场景（需要可重放、可取证）是个真问题，目前只能靠 --deterministic 类开关牺牲性能换取。
  • 可学习的去重。Learnable NMS、Relation Networks for Object Detection 等工作试图把去重变成网络的一部分而非手写规则。它们在精度上没有决定性优势，但在工程属性上很有吸引力：去重逻辑进了模型，也就进了 ONNX，也就自动一致了。这条路和端到端检测器殊途同归。
  • TSR 特有的开放问题：超类划分该由谁定义？层次化 NMS 需要一个超类体系（哪些细类互斥、哪些可共存），目前是人工维护的表。类别一多（几百类、还在增长）这张表就会腐化——新增一个「可变电子限速牌」类别时，有没有人记得把它加进限速超类？能否从数据里自动学出「哪些类别对在物理上不可能共存」（比如从标注中统计同位置共现频率），是一个小而实用的问题。
