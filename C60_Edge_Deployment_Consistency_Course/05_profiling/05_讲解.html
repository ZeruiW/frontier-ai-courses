1测延迟的七宗罪

一个数字比它背后的测量方法可信度更低。面试里报出「我们的模型 8 ms」而说不清测量口径，是减分的；能主动说出「batch=1、含预处理与拷贝、含后处理、FP16、Orin AGX MAXN 模式、warmup 500 次、报 p50 和 p99」，是加分的。这一节把七种最常见的测错方式列全。

CUDA event 与墙钟：两个都要报

直白说

CUDA event 计时测的是「GPU 上这段工作花了多久」，不含 CPU 提交开销、不含排队等待。墙钟计时（perf_counter 夹住「提交 + 同步」）测的是「用户从发出请求到拿到结果等了多久」。前者是你优化 kernel 时该看的，后者是产品该看的。两者的差就是「提交开销 + 排队 + 同步开销」，如果这个差很大（比如超过 GPU 时间的 20%），说明 CPU 侧成了瓶颈——常见原因是 kernel 太碎、启动开销占比过高。

严谨说

trtexec 就是这么设计输出的，四个数值必须分清：①GPU Compute Time——engine 在 GPU 上纯执行的时间；②Enqueue Time——CPU 把这一次推理提交进 stream 的时间，如果它接近甚至超过 GPU Compute Time，说明 CPU 提交跟不上 GPU 执行，需要 CUDA Graph 或减少层数；③Host Latency——含 H2D/D2H 的端到端；④Throughput——稳态吞吐，在多流/多 batch 下与延迟的倒数完全不是一回事。报「FPS」而不说是哪个口径，等于没报。

要多少个样本才能可靠地估出 p99

这是一个可以精确回答的统计问题。$n$ 个独立样本中，$p$ 分位数落在第 $\lceil pn \rceil$ 个次序统计量上，而「有多少个样本超过真实 $p$ 分位」服从二项分布 $\mathrm{Bin}(n, 1-p)$，秩的标准差是：

\[\sigma_{\text{rank}} = \sqrt{n\,p\,(1-p)} \qquad\Longrightarrow\qquad \text{95\% 置信区间对应的分位区间约为}\ \ p \pm \frac{1.96\sqrt{p(1-p)}}{\sqrt{n}}\]

1001 个0.99[97.0%, 101.0%]完全不可用——你的「p99」就是最大值
1 00010 个3.15[98.4%, 99.6%]勉强可用，是下限

「我跑了 100 次，p99 是 9.1 ms」——这句话在统计上是空的。100 个样本里只有 1 个超过 p99，你报的「p99」实际上就是这 100 次里的最大值，而最大值的方差极大（一次系统中断就能污染它）。更糟的是，如果你还是「同一张图跑 100 次」，那么数据依赖的那部分方差压根没进入样本。面试里被问「你们的 p99 是多少」，正确的回答要包含三件事：样本量、样本来源（真实帧序列还是重复单帧）、测量时长（是否覆盖热稳态）。只报一个数字，等于承认没做过。

把七宗罪压成一句检查：「我丢了 warmup 吗？我同步了吗？我用的是真实帧序列吗？我跑够 10000 次了吗？我报的是端到端还是纯推理？」五个问题全过，这个数字才配写进报告。

2为什么是 p99，不是均值

数据中心优化吞吐，车端优化尾延迟。这不是偏好差异，是任务性质的差异：网页慢 200 ms 用户皱个眉，感知帧晚 20 ms 到达，下游会按时间戳把它整帧丢弃——这一帧的算力白花了，而且这一帧本来可能正好包含那块新出现的限速牌。

超时率的算术：p99 达标 ≠ 安全

30 FPS 意味着每小时 $30 \times 3600 = 108{,}000$ 帧。把「超过延迟预算」的比例记作 $\epsilon$：

\[N_{\text{timeout/h}} \;=\; \epsilon \cdot f \cdot 3600, \qquad \bar{T}_{\text{between}} \;=\; \frac{1}{\epsilon f}\]

直白说

第二行是本节最该记住的一行。「我们的 p99 达标」听起来是个很好的结论，翻译成物理事件就是「每 3.3 秒丢一帧」。对一个 30 FPS 的感知链路，这意味着跟踪器每隔几秒就要处理一次「这一帧没有观测」；如果丢帧还不被上报（模块 04 讲过的静默丢帧），下游的生命周期状态机会误以为目标消失。

严谨说

更严重的是超时的相关性。上面那张表隐含假设「每帧是否超时相互独立」，但真实系统里超时几乎从不独立：热节流会让连续几万帧都变慢；一次内存碎片整理会连累几十帧；另一个感知任务的突发负载会压住 TSR 十几帧。所以除了 $\epsilon$，还必须报「最长连续超时段」——独立假设下 1% 超时率出现连续 5 帧超时的概率是 $10^{-10}$（几乎不可能），而热节流下连续 5000 帧超时是常态。两者的 p99 可以完全一样，但对系统的伤害差着数量级。notebook 里会把这两种分布并排放出来。

尾延迟从哪来：四个来源要分开治

  • 数据依赖：NMS 的耗时是 $O(NK)$，$N$ 与 $K$ 都随场景复杂度增长（C53 模块 04 实测 log-log 斜率约 1.7）。治法：给 NMS 输入设硬上限，或换无 NMS 架构，或把后处理搬到 GPU（模块 04）。
  • 系统抖动：Linux 非实时内核的调度延迟、页错误、中断、锁竞争、内存分配器。治法：关键线程绑核 + SCHED_FIFO + isolcpus；稳态期禁止分配（模块 04 的 C++ 检查单）。
  • 硬件：热节流与功耗墙（第 7 节）、DRAM refresh、其他任务抢占。治法：长时间测试 + 功耗模式声明 + 时间片预算。
  • 软件架构：多余的同步点、动态 shape 触发的 tactic 切换、队列排队。治法：Nsight Systems 看时间线（模块 04）。
TSR 场景的反相关是最讨厌的地方：延迟尖峰恰好出现在场景最复杂、最需要及时反应的时候。高速上视野里 2 块标志，候选框少、NMS 快；开进城市路口，龙门架 + 一排限速牌 + 店铺招牌 + 贴满贴纸的货车，候选框涨十倍、NMS 慢十倍——而这正是最容易出现「新标志突然出现、必须尽快识别」的场景。「平均够快」在这里没有任何安全意义。

直白说

整整 5.3 ms，比换一个更小的模型划算得多——而且完全不掉精度。如果你去优化模型，从 8.2 ms 压到 6.5 ms（掉 1.5 mAP）也只省 1.7 ms。新手一上来就想换 backbone，老手先量拷贝和预处理。

严谨说

两条最容易被忽略的收益值得单独拎出来。①H2D 传 uint8 而不是 float32，拷贝量直接降 4 倍——归一化本来就是逐元素操作，是访存受限的（见下一节），放在 GPU 上做几乎免费，而在 CPU 上做既慢又把数据撑大 4 倍。②D2H 只传最终框而不是 raw tensor，降 480 倍——8400×204 的 raw 输出有 3.43 MB，而 300 个框只有 7.2 KB。这两条加起来省的 0.44 ms 看着不多，但它们的真正价值是把 PCIe/内存总线让出来给别的任务——车端 SoC 上带宽是所有感知任务共享的稀缺资源，你少占 4 MB/帧，就是每秒少占 120 MB/s。

一条可迁移的心法：先画分解图，再决定优化什么。没有分解图的性能优化都是猜。而画分解图的成本是一天，猜错的成本是两周。

逐层之和与端到端不该相等

分解时要小心「逐层耗时之和 ≠ 端到端」。打开 per-layer profiling 会在每层后插同步点，破坏层间重叠、抑制某些融合，于是逐层之和通常比端到端大（10–30% 不等）。反过来，如果你测出「逐层之和明显小于端到端」，那差额就是 CPU 提交开销、排队、同步等待——这个差额本身是一个非常有价值的诊断量（对应 trtexec 的 Host Latency 减去 GPU Compute Time）。用 --separateProfileRun 把两件事分开测。

4Roofline：算子到底受什么限制

知道「时间花在哪个阶段」之后，下一层问题是「这个阶段为什么慢」。Roofline 模型用两个硬件常数和一个算子属性就能回答它。

\[I \;=\; \frac{\text{FLOPs}}{\text{Bytes}} \quad(\text{算术强度}), \qquad P_{\text{attainable}} \;=\; \min\bigl(P_{\text{peak}},\; I \times BW\bigr), \qquad I_{\text{ridge}} \;=\; \frac{P_{\text{peak}}}{BW}\]

取一块车端 SoC 的量级（GPU FP16 峰值约 42 TFLOPS、LPDDR5 带宽约 204.8 GB/s）：

\[I_{\text{ridge}} \;=\; \frac{42 \times 10^{12}}{204.8 \times 10^{9}} \;\approx\; \mathbf{205}\ \text{FLOP/Byte}\]

205 是一个高得吓人的脊点。它意味着：一个算子必须每读 1 个字节就做 205 次浮点运算，才配称为「计算受限」。绝大多数算子达不到。逐个算给你看（FP16，40×40 特征图，256 通道）：

直白说

5×5 depthwise 的 FLOPs 只有 3×3 稠密卷积的 1/92，但延迟只快 5.6 倍。换句话说，它的实际耗时是「按 FLOPs 推算」的 16.5 倍。原因很直白：depthwise 卷积每个输出通道只用自己那一个输入通道，数据复用率极低——搬进来的每个字节只被用了 25 次乘加（$k^2$），而稠密卷积用了 $256 \times 9 = 2304$ 次。

严谨说

这直接修正了一个常见的误读。C53 模块 03 讲 RTMDet 用 5×5 depthwise 大核时说「参数量代价极小」——那句话是对的，但它说的是参数量，不是延迟。$k$ 从 3 涨到 5，depthwise 的 FLOPs 涨 2.78 倍，但访存量几乎不变（权重只占 12.8 KB，可以忽略），于是延迟几乎不涨——从这个角度看大核确实是「便宜」的。但整个 depthwise 算子本身相对于它的 FLOPs 就是「贵」的：0.02 GFLOP 的算子花掉 8.1 μs，而 1.887 GFLOP 的稠密卷积才花 44.9 μs。结论是：FLOPs 不是延迟的好代理，尤其在轻量化架构上——MobileNet 系、ShuffleNet 系、以及所有大量使用 depthwise 的模型，其「FLOPs 很低」与「延迟很低」之间存在系统性的落差。选型时必须实测，不能查表。

融合省的从来不是计算，是「把中间结果写回显存再读回来」这一趟。这就是为什么模块 02 里「什么阻止了融合」值得追究——一个多余的 Reshape、一个被别处引用的中间张量、一个不支持的激活函数，都会把两个本可以融合的算子拆开，代价是一趟完整的往返访存。

有效算力接近峰值（$I > I_{\text{ridge}}$）计算受限降精度（FP16→INT8 直接翻倍）、减 FLOPs（剪枝/蒸馏/换结构）、用 Tensor Core 友好的通道数（32 的倍数）
有效带宽接近峰值（$I < I_{\text{ridge}}$）访存受限融合、降精度（也减字节！）、改 layout（NHWC / NC32HW32）、增大 batch 复用权重
两个都远低于峰值并行度不足增大 batch、多流并发、CUDA Graph 消除启动开销、检查是不是 tail effect（最后一个 wave 的 SM 没填满）
小模型上，启动开销可能是最大的一项

第三行最容易被忽略，而它在小模型上是常态。每个 kernel 的启动开销约 5–10 μs（含 CPU 侧提交与 GPU 侧调度）。一个融合后仍有 200 层的网络，光启动开销就是 1.0–2.0 ms——对一个 8 ms 的模型是 12–25%。症状是「GPU 利用率只有 40%，但换更大的模型延迟几乎不涨」。治法是 CUDA Graph：把整张图的 kernel 序列录制一次，之后每帧只提交一次 graph，把 $N$ 次启动摊成 1 次。代价是 shape 必须固定（动态 shape 要每档录一个 graph），且录制期间不能有 CPU 侧的条件分支——这正好和「稳态期不分配、不同步」的纪律吻合（模块 04）。

5静默回退：「转了 TRT 但没变快」

这是模块 02 埋下的伏笔，在这里给出可执行的检测方法。症状永远是同一句话：「我转了 TensorRT / 开了 FP16 / 做了 INT8，但延迟基本没变。」

严谨说

把这套检查自动化是本节的落点：解析 IEngineInspector 输出的 layer JSON（每层有 name / LayerType / Precision / TacticValue / 输入输出格式）与 --dumpProfile 的逐层耗时，合并成一张表，然后跑几条规则：①子图数 == 1；②FP32 层耗时占比 < 10%；③没有计算密集层（Conv/MatMul）落在 FP32；④没有出现 Reformat 层占用超过 5% 的耗时（reformat 是纯访存的格式转换，大量出现说明相邻层的 layout 偏好冲突）；⑤动态 shape 三档的延迟单调且无异常凸起。这五条规则跑一次不到一秒，却能挡住绝大多数「优化了但没优化」的发布。notebook 里会把这个检查器实现出来。

你的 ONNX 里没有的层，可能占掉 10% 的时间

Reformat 层是最容易被忽略的时间小偷。TensorRT 在两个 layout 偏好不同的层之间会自动插入 reformat（比如 NCHW ↔ NC32HW32，或 FP32 ↔ FP16 的转换）。这些层不在你的 ONNX 里，是构建器自己加的，所以你在模型结构里看不到它们。它们的算术强度是 0（纯搬运），却可能占掉 5–15% 的总耗时。治法：让通道数取 32 的倍数、让首尾层的精度与输入输出格式对齐（比如直接用 kHALF 的 NHWC 输入，避免入口处的一次 reformat）、避免在网络中间混用无法融合的精度。面试里能主动提 reformat，说明你真的读过 engine 的 layer 表而不只是跑过 trtexec。

6批处理、多流与车端多相机

批处理是数据中心提升吞吐的第一手段，在车端却基本用不上——除非你有多相机。这一节把账算清楚。

批处理的收益来自哪里

把一次推理的时间拆成两部分：与 batch 成正比的激活相关部分 $T_{\text{act}}$，和与 batch 无关的权重读取部分 $T_w$（权重只需读一次，供整个 batch 复用）：

\[T(b) \;=\; b\,T_{\text{act}} + T_w \qquad\Longrightarrow\qquad \frac{T(b)}{b} \;=\; T_{\text{act}} + \frac{T_w}{b} \;\xrightarrow[b\to\infty]{}\; T_{\text{act}}\]

所以吞吐的提升上限是 $\frac{T_{\text{act}}+T_w}{T_{\text{act}}}$，而且完全由权重读取的占比决定。取 $T_{\text{act}}=6.0$ ms、$T_w=2.2$ ms（即 batch=1 时 8.2 ms）：

batch总耗时每帧摊薄吞吐提升单相机下的端到端延迟多相机（硬件同步）
18.2 ms8.20 ms—8.2 ms8.2 ms
214.2 ms7.10 ms+15%33.3 + 14.2 = 47.5 ms（等 1 帧）14.2 ms
426.2 ms6.55 ms+25%100 + 26.2 = 126.2 ms（等 3 帧）26.2 ms（无等待）
850.2 ms6.28 ms+31%233 + 50.2 = 283 ms50.2 ms

直白说

第五列是车端否决批处理的理由：单相机做 batch=4，必须先等齐 4 帧，30 FPS 下就是白等 100 ms。为了把每帧摊薄从 8.2 压到 6.55 ms（省 1.65 ms），付出 100 ms 的等待——这笔账在任何延迟敏感系统里都不成立。吞吐提升 25% 是真的，延迟恶化 15 倍也是真的。

严谨说

但最后一列是车端唯一真正合理的批处理场景：多相机。前视长焦 + 前视广角 + 左右侧视，四路同一时刻曝光的图像天然构成一个 batch，不需要任何等待。串行跑是 $4\times8.2=32.8$ ms，batch 跑是 26.2 ms，省 20% 且延迟不增加。前提有两条，缺一不可：①四路必须硬件同步曝光（否则「等齐」又回来了，而且时间戳还不一致）；②四路必须用同一个模型与同一个输入分辨率——如果长焦用 640×640 而鱼眼用 960×640，或者长焦跑 TSR 模型而侧视跑另一个模型，就没法组 batch。在 TSR 里这一条经常不成立：远处小标志需要长焦的高分辨率，而侧视相机根本不需要跑 TSR。所以多相机 batching 的适用面比听起来窄得多，要具体看你的相机配置。

多流：填满 SM，但会推高单帧延迟

  • 多流的收益来自「一个 kernel 填不满 GPU」。小模型、小分辨率、小 batch 时，单个 kernel 可能只用掉 30% 的 SM，剩下的算力闲置。开 $N$ 条 stream 并发跑 $N$ 帧（或 $N$ 个任务），可以把利用率推上去。
  • 代价是单帧延迟上升：多个 kernel 竞争 SM、竞争 L2、竞争带宽。吞吐涨了，但每一帧都变慢了——这又是「吞吐 vs 延迟」的对立（模块 04 的线程模型表是同一个道理）。
  • stream priority 不是硬实时保证。CUDA 的 cudaStreamCreateWithPriority 只影响新 block 的调度倾向，已经在跑的 kernel 不会被抢占。一个长 kernel 可以把高优先级任务堵住几毫秒。车端要「TSR 优先」，靠的不是 stream priority，而是时间片预算与任务编排（下一节）。
  • MPS / MIG 在车端 SoC 上通常不可用，别按数据中心的经验做方案。
动态 batch 的隐藏成本：optimization profile。如果你想「有几路相机就用几路的 batch」，engine 必须建成动态 batch（min=1, opt=4, max=8）。代价有三：①构建时间显著变长（每档都要 tune）；②非 opt 档的 tactic 不是为它挑的，实测常有 10–30% 的额外损耗；③显存必须按 max 档预留。如果相机数量是固定的（量产车通常是），就用固定 batch 建 engine，别为了「灵活」白付这三笔钱。

7车端特有约束：功耗墙、降频、抢占

这一节的内容在数据中心几乎不存在，在车上是决定性的。桌面 GPU 有 300 W 的风冷预算和 25 °C 的机房；车端 SoC 有 30 W 的被动散热和夏天 60 °C 的舱内环境。

① 功耗模式：同一个 engine，延迟可以差两倍

车端 SoC 通常提供若干档功耗预算（例如 15 W / 30 W / 50 W / 无限制），由整车的电源与热设计决定。同一个 engine 在不同档下的延迟可以差 1.5–2 倍。因此：

不声明功耗模式的延迟数字是无效数字

任何一个延迟数字，不声明功耗模式就是无效的。论文里报「Orin 上 8 ms」而不说是哪档，等于没说；你自己的报告也一样。更常见的内部事故是：算法团队在开发板上用 MAXN 模式测出 8.2 ms，写进设计文档；集成到量产域控后实际是 30 W 档，跑出 13 ms，整个时序预算作废。纪律：benchmark 脚本第一行就打印当前功耗模式与时钟频率，并把它写进结果文件。

② 热节流：短 benchmark 全是骗人的

持续满负载下结温上升，超过阈值后 SoC 主动降频。一个简化的一阶热模型：

\[T(t) = T_{\text{amb}} + P R_{\text{th}}\bigl(1 - e^{-t/\tau}\bigr), \qquad \frac{f}{f_{\max}} = \operatorname{clip}\bigl(1 - k\,[T - T_{\text{thr}}]_+,\ \ \tfrac{f_{\min}}{f_{\max}},\ 1\bigr), \qquad T_{\text{lat}} \propto \frac{1}{f}\]

代入一组车规量级的参数（$T_{\text{amb}}=55$ °C 的夏季舱内、$P=40$ W、$R_{\text{th}}=1.1$ °C/W、$\tau=300$ s、节流阈值 85 °C、$k=0.02$/°C、最低频比 0.65）：

跑一分钟测出 p99 = 9.2 ms，跑 30 分钟是 12.7 ms。如果你的延迟预算是 12 ms，那么开发板上「余量 23%」的方案，在夏天开了半小时的车上已经超预算了（余量 −6%，17% 的帧超时）——而这半小时恰恰是长途驾驶最需要 TSR 稳定工作的时候。

严谨说

两个必须补充的严谨点。①这个一阶模型是简化的：真实系统里降频会同时降低功耗，$P$ 与 $f$ 耦合，达到的是一个自洽的热平衡点，实测曲线通常比模型更早收敛、更平缓。模型的价值不在预测精确值，而在告诉你「必须测长时间」这件事，以及给你一个外推的形状。②验收要报分段 p99 而不是整段 p99——把 30 分钟切成 1 分钟一段，每段各算 p99，看这条曲线是否收敛、收敛到哪。整段 p99 会把「前 5 分钟很快」和「后 25 分钟很慢」混在一起平均掉，恰好掩盖了你最想看的那个漂移。而且必须在目标环境温度下测：实验室 22 °C 空调房里测出的热稳态，和舱内 60 °C 是两个世界。

③ 多任务抢占：TSR 只是众多感知任务之一

一颗共享 SoC 上的感知任务（33 ms 一个周期，30 FPS） ┌──────────────────────────────────────────────────────────────┐ │ BEV 3D 检测 ████████████ 12.0 ms │ │ 占用栅格 █████████ 9.0 ms │ │ **TSR** ████████ 8.2 ms ← 我们 │ │ 车道线 ████ 4.0 ms │ │ 多目标跟踪(CPU) ██ 2.0 ms │ ├──────────────────────────────────────────────────────────────┤ │ 合计 35.2 ms > 33.3 ms 的周期预算 ← **超了** │ └──────────────────────────────────────────────────────────────┘ 降级策略（按优先级从低到高牺牲） · 车道线 降到 15 Hz（隔帧跑） 省 2.0 ms · 占用栅格 输入分辨率 ×0.8 省 2.6 ms · **TSR** decoder 6 层 → 3 层 省 0.9 ms（掉约 1 AP，C53 模块 04） · 兜底 丢帧（**最后手段**，且必须上报 frame_id）
  • GPU kernel 默认不可抢占（或抢占粒度很粗）。一个 3 ms 的长 kernel 会把所有其他任务堵住 3 ms，无论它们优先级多高。所以「给 TSR 设高优先级」并不能保证它准时。
  • 正确的做法是时间片预算（time-slice budgeting）：给每个任务分配固定的时间窗口，由一个编排层按周期调度；任务超出窗口就触发降级而不是抢占。降级路径必须提前设计好并测试过——这正是 C53 模块 04 里「RT-DETR 的 decoder 层数可调」在部署上的真实价值：它提供了一条精度可降级的路径，让系统在算力紧张时优雅退化，而不是直接丢帧。
  • DLA 卸载是车端特有的一张牌。Orin 这类 SoC 带独立的深度学习加速器，可以把部分任务放上去与 GPU 并行。但 DLA 支持的算子有限、精度只有 FP16/INT8、单位算力也低于 GPU，适合放对延迟不那么敏感、结构又规整的任务（比如后处理简单的分割网络），而不是延迟最紧的那个。
  • CPU 侧也要治：非实时 Linux 内核的调度抖动可以到几毫秒。关键线程绑核（sched_setaffinity）+ SCHED_FIFO + isolcpus 隔离出专用核，能把 CPU 侧的尾延迟压下一个量级。

车端延迟工程与数据中心的根本差别，一句话：数据中心问「平均每秒能处理多少」，车端问「最坏情况下这一帧会不会晚」。前者优化吞吐、可以排队；后者优化尾延迟、不能排队，而且要在功耗、温度、共享算力三重约束下证明它。

这张表看起来很长，但它的执行成本其实很低：第 1–6、8–11 项都可以脚本化，跑一遍不到一小时；第 7 项进夜间 CI；第 12 项是几条固定的故障注入用例。真正贵的是「没有这张表」——每次发布靠人回忆该查什么，漏掉的那一项就是下次事故。

严谨说

更进一步，这张表应该输出一份结构化的发布报告而不只是 pass/fail：每一项记录实测值、门限、余量百分比、以及本次相对上次的变化。余量百分比是最有价值的一列——它告诉你哪一项正在悄悄逼近门限。典型的场景是：连续三个版本 p99 从 9.1 → 9.6 → 10.2 ms，每次都「通过」（门限 12 ms），但趋势明摆着说下一次就要撞墙。门禁只能挡住已经越界的，趋势才能提前告诉你要撞墙了。这也是为什么第 13 项（可观测性）不是可选项——没有打点的系统，你连趋势都画不出来。

9研究前沿与开放问题

  • kernel 启动开销与图执行。CUDA Graph 把 $N$ 次 kernel 启动摊成一次提交，对小模型能省 10–25%；但它要求 shape 固定、无 CPU 分支。「如何在动态 shape 与控制流下仍然享受图执行」是活跃方向（条件节点、图更新 API、多档预录制），目前仍需要工程上做取舍。
  • 编译器路线与手写 kernel 的边界。TVM / TensorRT / Triton / MLIR 各自在自动搜索融合与 schedule；但在检测这类「主干规整、头部零碎」的模型上，自动编译器往往在头部与后处理上做不过手写。「哪些部分该交给编译器、哪些必须手写」目前没有普适答案，只能实测。
  • 实时 GPU 调度仍是开放问题。GPU 的抢占粒度粗、优先级不是硬保证，学术界的 kernel 切分（kernel slicing）、持久线程（persistent threads）、SM 分区等方案都在尝试给 GPU 任务提供可界定的 WCET。在车端多任务共享一颗 SoC 的场景下，这是「能不能证明不超时」的关键，也是功能安全论证最薄弱的一环。
  • 能耗感知的模型设计。当前几乎所有架构搜索的目标都是 FLOPs 或延迟，而车端真正的硬约束往往是能耗（它决定了热稳态，进而决定了持续延迟）。「以 J/frame 为目标的 NAS」还很少见，但它比以 FLOPs 为目标更贴近车端现实——本模块第 4 节已经说明了 FLOPs 与延迟的脱节，而延迟与能耗之间还有第二层脱节（访存的能耗远高于计算）。
  • Anytime inference / 可中断推理。让模型在任意时刻被打断时都能给出一个「当前最好的结果」，质量随允许的时间单调提升。DETR 系的逐层辅助头天然接近这个性质（C53 模块 04），但真正的 anytime 需要调度器与模型协同设计，目前在自动驾驶里还停留在「几档固定降级」的粗粒度形态。
  • Roofline 之外的性能模型。经典 roofline 忽略了 cache 层次、并行度不足、启动开销与 tail effect。ECM（Execution-Cache-Memory）模型、cache-aware roofline 等扩展更贴近真实，但都还没有成为深度学习部署的常规工具——实践中仍然是「先用 roofline 分类，再用 profiler 实测」。
  • 车规功能安全对延迟可预测性的要求正在收紧。ISO 26262 / ASIL 与 AUTOSAR Adaptive 对时序确定性有明确诉求，而「一个包含 GPU、共享内存、非实时内核的 AI 推理栈如何给出可论证的 WCET」目前业界还没有令人满意的答案。这也是为什么「无 NMS」「固定 query 数」「层数可裁」这类把数据依赖项消掉的架构性质，在车端的价值被系统性低估了。

★ 必读：Williams, Waterman & Patterson, Roofline: An Insightful Visual Performance Model for Multicore Architectures（CACM 2009）——本模块第 4 节的全部理论基础，篇幅不长，值得完整读一遍并自己画一张你目标硬件的 roofline 图。★ Dean & Barroso, The Tail at Scale（CACM 2013）——尾延迟这个概念在工程界的奠基文本，虽然写的是数据中心，但「为什么均值没有意义」「尾延迟从哪来」「怎么治」这三条对车端同样成立。

★ NVIDIA 官方文档三份，都要逐字读参数而不是看教程：TensorRT Developer Guide 的 Performance Best Practices 与 IEngineInspector 章节；trtexec 的完整参数表（尤其 --warmUp / --duration / --avgRuns / --dumpProfile / --separateProfileRun / --useCudaGraph）；Nsight Systems User Guide 的时间线判读部分（如何看 CPU 与 GPU 泳道的重叠）。配套：Jetson/Orin 平台的功耗模式与热管理指南——它是第 7 节所有数字的来源。
