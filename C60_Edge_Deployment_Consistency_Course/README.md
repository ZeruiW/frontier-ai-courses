# 车端部署与训练-部署一致性

> **一致性是可验证的工程属性，不是运气。**

这门课回答一个每个量产感知团队都遇到过、但很少被系统讲过的问题：

> 模型在服务器上评出来 mAP 0.82，导出、量化、装到车上跑起来，体感像 0.6。
> 这 0.22 到底去哪了？

绝大多数团队处理这个问题的方式是「再训一版试试」「把量化关掉看看」「换个 batch 再测」——
用一次昂贵的试错去换一个「行 / 不行」的比特。本课主张的方式完全不同：

**训练-部署鸿沟只可能来自三层：预处理 / 模型 / 后处理。**
每一层都有确定的输入、确定的输出、确定的对拍点和确定的容差。
所以定位它不是一次玄学调试，而是一次**二分查找**——只要你有对拍工具，
任何一致性问题都能在 30 分钟内落到具体的那一个算子上。

## 这门课直接对应的 JD 条目

本课是为下面这两条岗位要求写的：

- **职责**：*"Optimize models for production deployment, including ONNX / TensorRT / quantization /
  inference acceleration."* → 模块 02（ONNX → TensorRT、层融合、optimization profile、静默回退）
  与模块 03（INT8 校准、敏感层分析、混合精度、QAT 何时值得）。
- **加分项**：*"Experience debugging training-to-deployment consistency issues, including preprocessing
  mismatch, postprocessing mismatch, quantization accuracy drop, or runtime performance bottlenecks."*
  → 这一条几乎是本课的目录：模块 01 = preprocessing mismatch，模块 04 = postprocessing mismatch，
  模块 03 = quantization accuracy drop，模块 05 = runtime performance bottlenecks，
  模块 00 = 把这四类问题统一成一套定位方法论。

**面试时的表达方式很关键**：不要说「我做过 TensorRT 部署」，那句话所有人都会说。
要说「我遇到过 X 类不一致，症状是 Y，我用 Z 方法在多久内定位到了具体算子，修完涨了多少」。
本课的每个模块都在为这句话准备素材。

## 三条纪律（贯穿全课）

1. **先对拍，再优化。**
   在证明「两边数值一致」之前，任何性能数字与精度数字都不可信。
   一个 BGR/RGB 弄反的管线也能跑出很好看的 1.8 ms 延迟。

2. **容差要按机制设，不能拍脑袋。**
   FP32 逐层对拍容差 ~1e-5；FP16 放宽到 ~1e-2（相对）；INT8 的合理容差应该按
   **量化步长本身**（约 2/127 ≈ 0.016 的相对量级）来设。
   容差设太紧 → 天天假警报，最后没人看；设太松 → 真正的 bug 被放过。

3. **报延迟必须带条件。**
   batch 多大、含不含预处理、含不含 NMS、什么精度、什么卡、什么驱动、什么 TRT 版本、
   warmup 了多少次、报的是均值还是 p99——**八个维度里任何一个不同，数字就不可比**。
   这条纪律同时是一条面试加分项：主动说出测量条件的人，一听就是真跑过的。

三条纪律其实是同一件事：**把「感觉」替换成「可复现的数字 + 明确的判据」。**

## 学习路径

- **急着解决线上问题**（约 1.5 小时）：`00 → 01 → 04`。
  预处理和后处理占了真实不一致原因的绝大多数，而且它们的修复成本最低（不用重训）。
  读完你会有一套可以直接用的逐阶段对拍工具。
- **面向部署优化岗**（约 4 小时）：`00 → 02 → 03 → 05`。
  这是 JD 那条「ONNX / TensorRT / quantization / inference acceleration」的完整覆盖。
- **面向面试**（约 3 小时）：`00 → 03 → 05`，重点是模块 03 的**量化掉点排查决策树**
  与模块 05 的 **p99 / roofline / 验收清单**——这三样是部署类面试题的集中命中区。
- **完整路径**：`00 → 01 → 02 → 03 → 04 → 05`。
  后面的模块会反复引用前面的结论（例如模块 03 的校准集必须复用模块 01 的预处理，
  模块 05 的端到端延迟分解要用到模块 04 的后处理结构）。

每个 notebook 都能独立运行，纯 numpy、CPU、几秒到几十秒出结果，练习带 `assert` 判分。

## 与相邻课程的分工（说清不重复在哪）

这门课夹在好几门相关课程中间，边界必须划清楚，否则会写成一锅大杂烩：

| 课程 | 它讲什么 | 本课**不**重复什么 | 本课**接着**讲什么 |
|---|---|---|---|
| **C27 · 模型压缩与量化** | 量化**算法**本身：均匀/非均匀量化、QAT 的 STE、AWQ/GPTQ、稀疏与剪枝、蒸馏 | 不重讲量化的数学推导与训练方法 | 讲**部署侧的量化实务**：TensorRT 的三种校准器怎么选、校准集怎么构造、敏感层怎么找、掉点怎么排查。C27 教你量化是什么，本课教你为什么你的量化掉了 3 个点 |
| **C52 · 工业研究工程实务** | ONNX 的四要素（图 / opset / 动态轴 / 权重）、导出的通用坑、跨框架权重对齐 | 不重讲 ONNX 是什么、opset 怎么查、动态轴为什么要设 | 从 ONNX **之后**接手：ONNX → engine 这一段的编译行为（融合、autotuning、profile、plugin），以及检测任务特有的对齐问题 |
| **C24 · 推理引擎** | 推理引擎的**内部实现**：图优化器、内存池、算子调度、KV cache、批处理策略 | 不重讲引擎内部怎么实现的 | 讲**作为使用者**怎么让引擎给你正确且快的结果：怎么读分区日志、怎么用 profile、怎么判断它有没有骗你 |
| **C36 · GPU 内核编程** | kernel 怎么写、warp / shared memory / tensor core、访存合并 | 不重讲怎么写 kernel | 只用它的**结论**：roofline 与算术强度作为瓶颈判据；什么样的算子融合能省访存。写 plugin 时才需要回 C36 |
| **C53 · 实时检测器架构** | 延迟-精度权衡与**选型**：帕累托前沿、论文 FPS 为什么不可比、选哪个检测器 | 不重讲检测器架构与选型方法 | C53 给的是**选型层面**的延迟账（该选谁），本课给的是**落地层面**的实测与对齐（选好之后怎么真的做到）。两课的延迟拆解可以直接衔接 |
| **C61 · 检测工程实战与面试实务** | 实验设计、误差分析（TIDE）、调试手册、项目叙事、面试题库 | 不重讲实验方法论与面试话术 | 本课提供**部署方向的素材与答案骨架**；C61 把它们系统化成可背诵的题库与叙事模板。两课在「量化掉点排查」「训练-部署不一致排查」两题上交叉引用 |

另外：**C18** 讲检测基础（IoU / NMS / mAP），本课默认你知道 NMS 是什么，直接从「两边的 NMS 为什么不一样」开始；
**C57** 讲小目标检测，本课模块 01/03 会反复用到「小目标对插值与量化更敏感」这个结论，机理在 C57。

## 环境

见 `requirements.txt`。**纯 numpy + matplotlib，CPU 可跑，不需要 GPU，也不需要装
TensorRT / CUDA / OpenCV / torch。**

本课复现的是这些系统的**语义与账本**：

- 插值的采样公式（`align_corners` 两种映射、INTER_AREA 的区域平均）
- 融合的代数等价（Conv+BN 的权重折叠，可逐元素 `assert`）
- 量化的 scale 推导与三种校准器的目标函数（含完整的 Entropy-KL 实现）
- 坐标变换与逆变换的代数（letterbox 正变换 / 逆变换，以及三个经典错误版本）
- 延迟分布与 roofline（p50/p99、算术强度、H2D/D2H 的带宽账）

这些恰恰是可迁移的那部分——**TensorRT 的版本每年换，但「Conv+BN 为什么能合并」永远不变**。
每个模块末尾有一个 🧪 **真实工程胶囊**，把当天的结论翻译成可原样复制的
`trtexec` 命令、`IInt8Calibrator` 骨架、`polygraphy` 对拍命令与 C++ 片段。

## ⚠️ 关于本课里的数字

讲解中引用的延迟、掉点幅度、内存占比等数字来自公开文档、论文与常见工程经验，
**用于说明量级与相对关系，不是复现结果**。
换一块 SoC、换一个驱动版本、换一档功耗模式，绝对数字变化 30%–300% 都很正常。
模块 05 会专门讲清楚这些数字为什么不可比，以及一份可信的测量报告应该长什么样。
**在面试里引用具体数字时，一定要同时说出测量条件**——这本身就是加分项。
