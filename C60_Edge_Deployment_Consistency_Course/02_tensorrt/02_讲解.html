1链路全景：三次翻译，三类事故

从一个 nn.Module 到一个能在车上跑起来的 .plan 文件，中间要过三道关。每一道关都是一次「表达力换性能」的翻译，而每一次翻译有它专属的事故形态——把这三类事故分清楚，是本模块最实用的收获，也是排查时能不能在半小时内定位问题的分水岭。

直白说

一句话概括这条链路：ONNX 是「模型说了什么」，engine 是「这块芯片打算怎么做」。ONNX 里一个 Conv 节点在 engine 里可能变成半个层（被融进邻居）、可能变成三个层（被拆开加了两个格式转换）、也可能根本不存在（被常量折叠掉了）。所以拿 ONNX 的节点数去猜 engine 的性能，方向就是错的；你必须去看 engine 自己的层信息。

严谨说

更精确地说，TensorRT 的 builder 做的是一次目标相关的编译：输入是网络定义（INetworkDefinition）+ 构建配置（IBuilderConfig）+ 目标设备本身，输出是一个序列化的执行计划。它至少做四件事：①图级重写（常量折叠、死层消除、层融合、concat 消除）；②为每层枚举候选实现（tactic）并在真实设备上计时选最快的；③规划张量的内存复用（activation memory 是一块被反复覆写的池子，不是每层各占一块）；④插入必要的 reformat 层来对齐相邻层要求的数据布局与精度。其中②是「必须在目标硬件上构建」的根本原因，也是构建慢的根本原因。

分区式集成 = 把失败变成静默降级

能不能跳过 ONNX？可以，路径有 torch-tensorrt（PyTorch 直接编译）、TF-TRT、以及 ONNX Runtime 的 TensorRT ExecutionProvider。它们的共同特点是「分区式集成」：跑得动的子图交给 TRT，跑不动的留给原框架。开发期这很省事，但它把「事故 B」变成了默认行为——模型永远能跑，你永远不知道有多少留在了慢路径上。量产链路上，多数团队仍然走「显式导出 ONNX → 显式 build engine」，理由不是性能，是「不支持的算子必须让我在 CI 里当场看到，而不是在车上悄悄变慢」。

2builder config：那几个真正决定成败的开关

IBuilderConfig 上有几十个设置，但决定成败的就那么几个。这一节只讲这几个，并且讲清楚「设了会怎样」和「忘了设会怎样」——后者才是面试和线上真正要命的部分。

① workspace：它不是「engine 会用多少显存」

这是被误解最多的一项。config.set_memory_pool_limit(MemoryPoolType.WORKSPACE, N) 设的是「构建期允许某个 tactic 临时申请多少显存」，不是 engine 运行时的显存占用。很多高性能实现（需要大块中间缓冲的 implicit GEMM、Winograd 变换、某些 FFT 卷积）会申请可观的 workspace；你给的额度不够，这些 tactic 直接从候选集里被剔除，TRT 不报错，只是默默选一个慢的。

典型症状：同一个 ONNX、同一块卡，同事构建出来比你快 20%，唯一差别是他 workspace 给了 4 GB 你给了 64 MB。TensorRT 8.4 之后默认额度是设备总显存，所以新版本上这个坑变少了；但在显存紧张的车端 SoC 上，你常常需要主动调小它来避免构建期 OOM，这时候就得亲手做这个权衡。

② 精度标志：这是「许可证」，不是「命令」

config.set_flag(BuilderFlag.FP16) 的语义是「允许 TRT 在它认为划算的地方用 FP16」。TRT 仍然按实测耗时选 tactic——如果某层的 FP32 实现恰好更快（小层、或该层的 FP16 kernel 需要额外的 reformat），它就用 FP32。所以 「我开了 FP16 但一点没变快」是完全可能的，而且不会有任何警告。

直白说

把精度标志理解成「我授权你在这些数据类型里挑」，而不是「把模型转成 FP16」。同理，INT8 这个 flag 只是授权；没有 scale，TRT 根本不知道怎么把浮点映射到 8 位整数，所以它会把那些层留在 FP16/FP32。这就是为什么「我开了 INT8 但精度一点没掉」通常不是好消息——多半是根本没量化上（下一模块会展开）。

严谨说

从优化器的角度看，builder 在做一个受约束的组合优化：对每层 $\ell$ 选一个 tactic $t_\ell$（含实现算法、数据布局、精度），目标是最小化 $\sum_\ell \tau(t_\ell) + \sum_{(\ell,\ell')} \rho(t_\ell, t_{\ell'})$，其中 $\rho$ 是相邻层布局/精度不匹配时插入 reformat 的代价。精度标志改变的是可行域，不是目标函数。这解释了两个反直觉现象：①开了 FP16 反而某些层还是 FP32（因为 reformat 代价 $\rho$ 超过了该层的收益）；②手工把某层强制成 FP16 反而整体变慢（因为你在它前后各强加了一次 reformat）。

「开了 FP16 没变快」的四步排查

面试高频题：「你开了 FP16，延迟没变，怎么查？」标准答法有四步，缺一步就显得没做过：①先确认硬件与 TRT 版本支持（builder.platform_has_fast_fp16）；②用 --dumpLayerInfo --profilingVerbosity=detailed 导出层信息，统计还有多少层是 FP32——如果几乎全是 FP32，问题在构建配置；③如果层精度确实是 FP16，看 Reformat 层的数量与耗时占比——精度在层间反复切换会把收益吃光；④如果层精度对、reformat 也少，那瓶颈根本不在算力，去看 roofline：模型是 memory-bound 的话，FP16 只把权重读取量减半，激活读写量没变，收益天然有限。第④点是拉开差距的地方——很多人只会答前两步。

3动态 shape 与 optimization profile：min/opt/max 的性能账

TensorRT 的性能来自「为具体的 shape 挑具体的 kernel」。所以动态 shape 与性能天生是对立的——你每放宽一点输入的自由度，就要付出一点性能或一点显存。这一节讲清楚这笔账怎么算。

optimization profile 是什么

对每个动态维度，你要给三个数：min / opt / max。它们的作用各不相同，别混为一谈：

档位它决定什么设错的后果
min运行时允许的最小 shape（越界直接报错）设太大 → 小输入被拒；设太小 → 扩大了搜索范围，可能拖累 tactic 质量
optbuilder 在这个 shape 上计时并挑 tactic设错 = 你的高频 shape 上跑的是为别的 shape 挑的 kernel，实测可慢 10–30%
max允许的最大 shape；activation 显存按它预分配设太大 → 显存被无谓占住（车端 SoC 上很致命）；设太小 → 大输入直接报错
shape 分布（比如两级 TSR 里第二级分类器的 crop 数） 频次 │ ▄▄█▄▄ │ ▄███████▄ ▄ │ ▄███████████▄▄ ▄▄ ███ └────┴──┴───┴────┴──────────────────┴──┴────┴──► batch 2 4 8 12 48 56 64 方案 A · 单 profile [1, 8, 64] ├ opt=8 命中主峰 → 主峰上性能最好 ├ batch=56 时用的是为 8 挑的 tactic → 慢 15~30% └ 显存按 batch=64 预留 ← 主峰只用 8，浪费 8 倍 方案 B · 双 profile [1,8,16] + [17,56,64] ├ 两个峰各自命中 → 两边都快 ├ 构建时间 ×2，engine 变大 └ **每个 profile 需要独立的 execution context** → activation 显存 ×2 方案 C · 分桶（bucketing）：把 batch padding 到 {8, 16, 32, 64} ├ 每桶一个**静态 shape** engine → 每个都是最优 tactic ├ 显存 = max 桶（可只常驻常用桶，按需加载） └ 代价：padding 的算力浪费 + 多个 engine 的管理成本

三个方案的选择依据不是「哪个先进」，而是你的 shape 分布长什么样、显存有多紧、以及你能承受多少工程复杂度。用一个简单的代价模型就能算出来：

\[\mathbb{E}[T] \;=\; \sum_{s} p(s)\, t_0(s)\,\Bigl(1 + \alpha \bigl|\ln (s / s_{\text{opt}})\bigr|\Bigr), \qquad M \;=\; m_{\text{w}} + n_{\text{ctx}} \cdot m_{\text{act}}(s_{\max})\]

$t_0(s)$ 是该 shape 在专门为它构建的静态 engine 上的耗时，$\alpha$ 是「偏离 opt 的惩罚系数」（实测常在 0.05–0.25 之间，取决于层类型：GEMM 类对 tile 尺寸敏感，$\alpha$ 大；elementwise 类几乎无所谓）。notebook 里会用动态规划求出「给定 $k$ 个 profile，怎么切分 shape 区间使期望延迟最小」的最优解，并画出 $k$ 增加时的边际收益——你会看到典型情况下 $k=2$ 就吃掉了绝大部分收益，$k=4$ 以上基本白花构建时间。

直白说

最省事也最快的方案永远是静态 shape：把输入尺寸钉死，一个数都不许动。车端感知的主链路基本都这么做——相机分辨率是固定的，letterbox 之后也是固定的，没有任何理由让主检测器接受动态输入。动态 shape 真正不可避免的地方只有少数几处：多相机时激活的相机数会变（batch 维）、两级架构里第二级的 crop 数随场景变、以及需要多分辨率档位来做算力降级的场景。

严谨说

值得强调的是 execution context 与 profile 的绑定关系：一个 IExecutionContext 同一时刻只能绑定一个 optimization profile，切换 profile 要调 setOptimizationProfileAsync() 并等待同步——在延迟敏感的推理循环里频繁切 profile 是反模式。常见做法是为每个 profile 建一个常驻 context，但每个 context 都要有自己的 activation 显存（除非用 createExecutionContextWithoutDeviceMemory() 手动共享一块足够大的显存并自己保证不并发使用）。所以「多 profile」的真实代价是显存乘以 context 数，这在只有几 GB 可用显存的车规 SoC 上往往才是硬约束，而不是构建时间。

把这一节压成一句话：opt 决定你有多快，max 决定你占多少显存，min 只决定你会不会崩。三个数里最该被认真对待的是 opt，而它应该来自线上 shape 分布的实际统计，不是拍脑袋写的中位数。

4层融合：省的不是计算，是访存

层融合是 TensorRT 收益最大、也最容易被误解的一项优化。误解在于：很多人以为融合省的是 FLOPs。不是。Conv+BN+ReLU 融合之后，乘加次数一次都没少——省下的是把中间结果写回显存再读回来的那几趟，以及两次 kernel launch。

垂直融合的数值基础：Conv + BN 的等价变换

推理期的 BatchNorm 是一个逐通道的仿射变换（running stats 已冻结），而卷积也是线性的，所以两者可以合并成一个卷积。设第 $o$ 个输出通道的卷积核为 $W_o$、偏置 $b_o$，BN 参数为 $(\gamma_o, \beta_o, \mu_o, \sigma_o^2, \epsilon)$：

\[\mathrm{BN}\bigl(W_o * x + b_o\bigr) \;=\; \gamma_o\,\frac{(W_o * x + b_o) - \mu_o}{\sqrt{\sigma_o^2+\epsilon}} + \beta_o \;=\; \underbrace{\frac{\gamma_o}{\sqrt{\sigma_o^2+\epsilon}}W_o}_{\tilde W_o} * x \;+\; \underbrace{\frac{\gamma_o\,(b_o-\mu_o)}{\sqrt{\sigma_o^2+\epsilon}} + \beta_o}_{\tilde b_o}\]

这是严格恒等，不是近似（浮点舍入除外）。notebook 里会用 numpy 从零实现卷积与 BN，对随机输入验证融合前后 np.allclose 到 $10^{-10}$ 量级。这个证明值得亲手写一遍：C53 模块 01 讲的结构重参数化（RepVGG 多分支合并）用的是同一套代数，而下一模块讲 QAT 时的「BN folding 必须在插 fake-quant 之前做」也是同一件事。

结论非常尖锐：融合对「厚重的标准卷积」只值 9%，对「轻薄的 depthwise 卷积」值 67%。而现代实时检测器（RTMDet 的 CSPNeXt、YOLO 的轻量变体、MobileNet 系 backbone）里 depthwise 遍地都是——越是为「FLOPs 少」而设计的模型，越是 memory-bound，也就越依赖融合。这解释了一个常见困惑：「我换了个 FLOPs 只有一半的轻量 backbone，延迟怎么只降了 15%？」因为它本来就不受算力限制，你减的是它不缺的那个东西。

TensorRT 还做哪些图优化

类别做什么典型收益
常量折叠把只依赖常量的子图在构建期算掉（BN 参数、reshape 的 shape 张量）去掉一批运行时无用节点
垂直融合Conv+Bias+BN+激活 → 一个 CBR 层；ConvTranspose、FC 同理本节主角
水平融合同一输入的多个同类卷积（Inception 分支、多头投影）合并成一个大卷积后再切分kernel 数下降、GEMM 变大更高效
concat 消除让上游层直接写进 concat 输出的对应偏移，concat 本身消失省一整趟读写
shuffle / transpose 消除相邻的 reshape/transpose 相互抵消或被吸进邻居的布局要求去掉纯访存层
格式与精度重排（reformat）在布局/精度不匹配处插入转换层这是负收益，越少越好

一条可迁移的心法：融合的本质是把 memory-bound 的算子塞进 compute-bound 算子的 epilogue，让它们免费。凡是「算术强度低于 1」的算子（BN、激活、逐元素加、scale、cast），单独成 kernel 就是纯粹的带宽浪费。你自己写模型时也该按这个标准判断：新加的这个逐元素操作能不能被融进上一层？如果不能，它就要付一整趟 3 MB 的读写。

5什么阻止了融合：图优化的边界与写模型的纪律

融合是有前提的。前提被破坏时，TensorRT 不会报错、不会警告，只是安静地少融一次。结果就是「一个看起来毫无问题的改动，让延迟涨了 20%」。这一节把常见的阻断原因和它们的指纹列全。

最根本的一条：中间张量必须「用完即弃」

Conv 的输出要能被融进 BN，前提是这个中间张量除了 BN 没有别的用途。一旦它有第二个消费者，或者它被标记成网络输出，TensorRT 就必须把它实体化（materialize）到显存里——而一旦要写出去，融合就没意义了。

可以融合 被阻断（中间张量有两个消费者） ────────────── ──────────────────────────────── x x │ │ Conv Conv │ ← 只有 BN 用它 │ ← BN 用它，Add 也用它 BN ├──────────┐ │ BN │ ReLU │ │ │ ReLU │ y │ │ Add ◄──────┘ 融合成 1 个 CBR 层 Conv 的输出必须写回显存 中间张量 0 次落显存 → Conv+BN 融不了 → 多一趟 3.28 MB 读 + 3.28 MB 写 事故形态：为了 debug 把中间张量 mark 成 output builder network 里多写一行 network->markOutput(bn_out) → 该张量必须实体化 → 融合链断在这里 → **延迟涨 15~25%，没有任何报错，忘了删就上线了**
阻断原因指纹（怎么看出来）修法

直白说

怎么知道融合成没成？看层名。TensorRT 融合后的层名是把被融的层名拼起来的，形如 conv1 + conv1/bn + conv1/relu。所以只要 dump 一次 layer info，你就能一眼看出哪些层名是「一串」（融了）、哪些是「孤零零一个 BatchNormalization」（没融）。命令是 trtexec --loadEngine=m.plan --dumpLayerInfo --profilingVerbosity=detailed --exportLayerInfo=layers.json，然后写个十行的脚本统计层数、层名里的 + 个数、以及 Reformat 的占比。这个脚本应该进 CI，作为性能回归的门禁之一。

严谨说

更严谨地说，TensorRT 的融合是在其内部图上做模式匹配（pattern matching）+安全性检查：模式匹配决定「这几个层在结构上可以合并成哪个融合层」，安全性检查决定「合并之后语义是否仍然等价、以及中间结果是否真的不需要保留」。后者依赖的是 use-def 分析：只有当中间张量的 fan-out 恰好为 1 且它不在图的输出集合中，融合才被允许。这与传统编译器里的 operator fusion / loop fusion 是同一套理论，区别只在于 TensorRT 的融合模式是硬编码的（vendor 手写的 kernel 模板库），而 TVM/XLA 这类编译器会做更一般的调度搜索。硬编码的好处是命中时性能极强，坏处是没命中你完全没法干预——这正是「写模型时就要照着融合规则写」的原因。

数值全对 + 延迟涨 18% = 融合被阻断

真实事故形态，也是很好的面试故事素材：某次为了排查一个 badcase，工程师在导出脚本里多加了一个中间特征图作为输出，用完忘了删。ONNX 对拍通过（数值完全正确）、精度评测通过（数值完全正确）、只有延迟涨了 18%。因为没有人把「engine 层数」纳入回归门禁，这个改动一路走到了集成测试才被发现。教训：一致性检查只能抓「事故 A」，抓不到「事故 B」。你需要一条独立的、针对 engine 结构本身的门禁——层数、融合层占比、Reformat 层占比、FP32 层数、子图数。

6kernel auto-tuning：为什么构建要几十分钟

第一次跑 trtexec 的人几乎都会问同一个问题：「转换一个模型而已，为什么要等二十分钟？」答案是 TensorRT 根本不是在「转换」，它是在做实验。

builder 到底在忙什么

对图中的每一个层，TensorRT 会枚举一批候选实现——这些候选叫 tactic，来源包括自带 kernel 库、cuDNN、cuBLAS、以及针对特定 shape/精度的专用实现。同一个 3×3 卷积，候选可能包括：implicit GEMM 的若干种 tile 划分、explicit GEMM + im2col、Winograd 变换、以及不同的数据布局（NCHW / NHWC / NC/32HW32 等 vectorized 格式）。然后它把每个候选在目标 GPU 上真的跑几遍、计时、取最快的那个。

\[N_{\text{timing}} \;\approx\; \underbrace{L}_{\text{层数}} \times \underbrace{K}_{\text{每层候选 tactic 数}} \times \underbrace{R}_{\text{每个候选重复次数}} \times \underbrace{|\mathcal{P}|}_{\text{profile 数}}\]

一个 200 层的检测器，每层 10–100 个候选，每个候选重复 3–8 次，单 profile——就是几万次真实的 kernel 计时。INT8 还要更多（更多候选 + 校准本身的前向）。所以构建时间从「小模型 1 分钟」到「大模型 + 多 profile + INT8 半小时以上」都是正常的。

因素对构建时间的影响能不能省
层数 / 模型大小近似线性不能
optimization profile 数近似线性倍增能——少用 profile，优先静态 shape
INT8显著变慢（更多 tactic + 校准前向）校准结果可缓存复用
builderOptimizationLevel（0–5）级别越高搜得越广、越慢能——CI 用低级别快速验证，发布用高级别
timing cache命中后跳过计时能——二次构建可快 2–10×，CI 必用
构建机的空闲程度不影响时长，影响结果质量必须用独占机器
构建是有噪声的过程，engine 不是 ONNX 的确定性函数

一个反直觉但极其重要的事实：同一个 ONNX，在同一块卡上构建两次，得到的 engine 性能可能差 3–5%。因为 tactic 选择依赖的是实测计时，而计时会被机器上的其他负载、时钟频率波动、温度扰动。如果两个候选的真实耗时只差 2%，噪声完全可能让 builder 选错。这是 CI 里「性能测试 flaky」最常见的根因，而团队通常会误以为是测量环节的问题。

缓解手段：①构建用独占机器、锁频（nvidia-smi -lgc）；②增加计时重复次数（trtexec --avgTiming=8）；③用 timing cache 把「已经选定的 tactic」冻住——这不只是省时间，更是保证可复现：同一份 cache + 同一份 ONNX 应当产出行为一致的 engine。

直白说

把 timing cache 想成「实验记录本」：(层配置的哈希) → (最优 tactic, 实测耗时)。下次构建时，遇到同样配置的层就直接查表，不用重跑实验。所以它能把二次构建时间砍掉一大半。但记录本只在同一个实验室有效——换 GPU 型号、换 TRT 版本、甚至换 CUDA 版本，cache 就该失效（TensorRT 会做校验并忽略不匹配的条目，不会给你错误结果，只是白建一次）。

严谨说

从工程流程看，timing cache 把「构建」从不确定过程推向可复现过程，这对量产链路是刚需：功能安全要求「同一份输入产出同一份二进制」，而 auto-tuning 天然违背这一点。实践中的做法是：在一台锁频的构建机上生成 golden timing cache，把它作为构建产物之一纳入版本管理与签名，之后所有构建（包括 CI 和发布）都必须带上这份 cache。这样 engine 就成了 (ONNX, builder config, timing cache, TRT 版本, 设备型号) 的确定性函数，而不是「那天那台机器碰巧的结果」。另有 builderOptimizationLevel（TRT 8.6+）把「搜索广度」显式暴露成一个 0–5 的旋钮：级别 0 构建极快但性能可能差不少，级别 5 反之——这本质上是把「构建时间 vs 运行性能」的帕累托前沿交给你自己选点。

7engine 与硬件绑定：车端多平台的组合爆炸

上一节说清了 tactic 是在目标设备上实测选出来的，那么下面这条结论就是必然的：engine 是一个硬件相关的产物，不是一个可移植的模型文件。这条性质在单卡的服务器场景里只是个小麻烦，在车端却直接决定了整条发布流水线的形状。

engine 绑定了什么

绑定维度变了会怎样缓解手段与代价
GPU 架构（SM 版本）反序列化直接失败HardwareCompatibilityLevel::kAMPERE_PLUS：跨 Ampere+ 可移植，代价是只用架构通用 tactic，典型损失 5–15%
具体型号（SM 数、带宽、L2 大小）通常能加载，但 tactic 不再最优，性能悄悄下降为每个型号单独构建（这是默认做法）
TensorRT 版本反序列化失败（序列化格式与版本绑定）BuilderFlag::VERSION_COMPATIBLE：engine 内嵌 lean runtime，可跨版本加载；代价是体积变大、可能略慢
CUDA / cuDNN 版本多数情况兼容，边缘情况会失败冻结整条工具链版本
驱动版本有最低要求；低于要求则失败在车端镜像里固定驱动版本
构建时的 builder configengine 行为不同（精度、profile 范围）配置纳入版本管理并随 engine 一起签名

「反序列化直接失败」其实是好事——这是一个显式的错误，会在集成阶段就被抓到。真正危险的是「能加载但不是最优」那一类：模型跑得起来、精度也对，只是比应有的慢 20%，而没有人会因为「慢 20%」去怀疑 engine 用错了。

车端的组合爆炸

engine 矩阵 = 硬件平台 × 精度档 × 分辨率档 × 模型版本 × TRT 版本 硬件平台 Orin-N (低配) · Orin-X (中配) · 双 Orin (高配) · Thor (新平台) 精度档 FP16 · INT8 分辨率档 960x540(省电) · 1280x720(标准) · 1920x1080(远距) 模型版本 同时在路上的灰度版本可能有 2~3 个 TRT 版本 升级期会有新旧两版并存 4 × 2 × 3 = 24 个 engine / 每个模型版本 × 3 个在网模型版本 = 72 个 engine × 构建 12 分钟 = 14.4 机器小时（串行） ÷ 6 台并行构建机 = 2.4 小时 ← 每次改模型都要付这个 再 × TRT 一次小版本升级 = **全量重建 + 全量回归** 存储与分发：72 × ~80 MB ≈ 5.8 GB，OTA 只能下发匹配当前硬件的那一个 验证：**每一个 engine 都是独立的发布物，都要单独过精度与延迟门禁**

这张账最重要的一行是最后一行。「一份权重」不等于「一次验证」——engine 是硬件相关的，所以每一个 (平台, 精度, 分辨率) 组合都必须独立跑完整评测：融合结果可能不同、tactic 不同、INT8 的 scale 甚至可能因为校准在不同平台重跑而不同。这是很多团队在第一次上多硬件平台时严重低估的成本。

直白说

有没有办法只发 ONNX，让车在首次开机时自己构建？有团队这么做，但要非常小心。构建要十几分钟、要占用显存与算力、结果还带 3–5% 的随机性；如果构建恰好在用户第一次上车时发生，那就是十几分钟的「感知功能不可用」。现实做法通常是折中：出厂时预置一份 engine，OTA 下发时优先用云端构建好的匹配版本，只有在遇到未预见的硬件/驱动组合时才回退到车端构建，并且必须有明确的降级策略与用户提示。

严谨说

从发布工程的角度看，engine 的硬件绑定把模型交付从「分发一个文件」变成了「分发一个按 (硬件指纹, 软件版本) 索引的产物矩阵」。这需要三件基础设施：①硬件指纹采集（车端上报 SoC 型号、驱动、TRT 版本，服务端据此选包）；②产物血缘（每个 engine 必须能回溯到 ONNX 哈希、权重哈希、builder config、timing cache、构建机标识）；③回退路径（匹配不到时用哪个更保守的 engine，或退回到 FP16 版本）。值得注意的是，VERSION_COMPATIBLE 与 HardwareCompatibilityLevel 这两个选项本质上是在「用性能买维护性」——把 24 个 engine 压成 6 个，代价是每个都慢 5–15%。这个交换划不划算，取决于你的延迟预算还剩多少余量，以及你的发布团队有多大。

答完机制，还要答工程后果

面试题：「为什么不能把开发机上建好的 engine 直接拷到车上？」这题看着简单，但答得完整的人不多。骨架：①engine 是 builder 在目标设备上实测计时后产出的执行计划，tactic 选择依赖 SM 版本、SM 数量、显存带宽、L2 大小——这些换台机器就变了；②序列化格式与 TensorRT 版本绑定，跨版本反序列化会失败；③还绑驱动的最低版本；④即使 TRT 提供了 version-compatible 与 hardware-compatible 模式，它们是用「只选架构通用 tactic」换来的可移植性，典型要付 5–15% 的性能。加分点是主动补上工程后果：所以 engine 是 (硬件, 软件版本) 索引的产物矩阵，TRT 版本升级 = 全量重建 + 全量回归，这就是为什么量产上 TRT 版本升级频率极低。

8静默回退、plugin，与 trtexec 的常用姿势

本模块开头的「事故 B」——转了 TRT 但没变快——最常见的成因不是融合被阻断，而是静默回退（silent fallback）：一部分图根本没跑在 TensorRT 上。

静默回退的两种形态

  1. 算子级回退（分区）：你用的是 torch-tensorrt / TF-TRT / onnxruntime 的 TensorRT EP 这类分区式集成。它们把图切成「TRT 能跑的子图」和「交回原框架的子图」。模型能跑、数值也对，但每个子图边界都意味着一次同步、可能还有一次内存拷贝与布局转换。被切成 30 个子图的模型，比切成 1 个子图的慢一倍毫不稀奇。
  2. 精度级回退：你开了 FP16/INT8，但因为缺 scale、因为 reformat 代价太高、或因为该层没有对应精度的实现，TRT 把它留在了更高精度上。症状是「精度一点没掉」——听起来是好消息，实际是没量化上。

怎么看：三个必须进 CI 的数字

指标健康值怎么拿不健康说明什么
子图数= 1ORT-TRT EP 的日志 / ORT_TENSORRT_DUMP_SUBGRAPHS=1；torch-tensorrt 的 partitioning 报告有算子没被支持，正在走慢路径
非目标精度的层数接近 0（纯 FP16 目标下）trtexec --dumpLayerInfo --profilingVerbosity=detailed 里每层的 Precision精度标志没真正生效
Reformat 层占比< 5% 的耗时--dumpProfile --separateProfileRun 逐层耗时精度/布局在层间反复切换，收益被吃光
融合层占比多数层名里含 +层名统计脚本融合被阻断（第 5 节）

trtexec 常用姿势

# ① 构建（静态 shape，最简）
trtexec --onnx=det.onnx --saveEngine=det.plan --fp16 \
        --memPoolSize=workspace:2048 \
        --timingCacheFile=tc.cache --avgTiming=8 \
        --builderOptimizationLevel=3

# ② 构建（动态 shape：三档必须都给，且要给到每个动态输入）
trtexec --onnx=det.onnx --saveEngine=det.plan --fp16 \
        --minShapes=images:1x3x640x640 \
        --optShapes=images:1x3x640x640 \
        --maxShapes=images:4x3x640x640

# ③ 强制精度约束（做混合精度时用 obey，不满足就构建失败）
trtexec --onnx=det.onnx --saveEngine=det.plan --fp16 --int8 \
        --precisionConstraints=obey \
        --layerPrecisions=head_reg.*:fp16,backbone.stem.*:fp16

# ④ 逐层耗时剖析（找瓶颈层、找 Reformat）
trtexec --loadEngine=det.plan --shapes=images:1x3x640x640 \
        --warmUp=1000 --iterations=2000 --avgRuns=10 \
        --dumpProfile --separateProfileRun \
        --exportProfile=prof.json --exportLayerInfo=layers.json \
        --profilingVerbosity=detailed

# ⑤ 只测 GPU 计算、不含拷贝（注意：这个数字会比端到端好看很多）
trtexec --loadEngine=det.plan --noDataTransfers --useCudaGraph

# ⑥ 让 TRT 自己在 fp16/int8 里挑（快速摸上限用，不要直接拿去发布）
trtexec --onnx=det.onnx --best
别用 --noDataTransfers 的数字做预算

--noDataTransfers 是延迟数字被「美化」的头号来源。它测的是纯 GPU 计算，不含 H2D/D2H 拷贝。而在车端，输入是 1920×1080×3 的图，H2D 拷贝本身就可能占端到端的 10–30%。供应商与论文报的 FPS 常常就是这个口径，再加上 batch>1、不含预处理、不含 NMS。拿这个数字去做延迟预算，上车必然超时。本课模块 05 会给端到端测量的正确姿势。

plugin：什么时候不得不自己写

当某个算子既不在 ONNX opset 里、TRT 也不原生支持时，你有四条路，请严格按这个顺序尝试：

  1. 改模型——用等价的标准算子重写。代价最小，但要重训或至少重新验证数值等价。
  2. 用等价算子组合——比如把自定义插值拆成 Resize+Slice。代价：可能引入额外访存，且组合出来的图未必能融合。
  3. 用官方/开源 plugin——TensorRT OSS 仓库里有 EfficientNMS_TRT、MultiscaleDeformableAttnPlugin（RT-DETR / Deformable DETR 的救命稻草）、GroupNorm、InstanceNormalization 等。代价：要确认版本匹配、要自己编译进 runtime。
  4. 自己写——最后的选择。要实现前向 CUDA kernel、序列化/反序列化、动态 shape 支持（IPluginV2DynamicExt / 新版 IPluginV3）、多精度支持、以及 enqueue 的流语义。而且 plugin 是融合黑洞：它前后一定断开，所以一个写得很快的 plugin 也可能因为打断了融合链而净亏。

直白说

TSR 场景里这条决策链非常具体。如果你选了 RT-DETR（C53 模块 04），它的可变形注意力依赖 grid_sample——这在部分后端要 plugin。RT-DETRv2 把它换成离散采样正是为了绕开这一点。如果你选了 YOLO/RTMDet 系，主干全是标准卷积，唯一需要考虑的是要不要把 NMS 用 EfficientNMS_TRT 塞进 engine——塞进去可以省一次 D2H 拷贝和 CPU 后处理，但也把「NMS 的实现细节」冻进了 engine，以后想改 IoU 阈值语义就得重建。

严谨说

更一般地，plugin 的真实成本不在写它的那两天，在它的生命周期：①跨 TRT 版本的 API 迁移（IPluginV2Ext → IPluginV2DynamicExt → IPluginV3，每次大版本都可能要改）；②每个目标平台都要交叉编译并验证；③它是融合边界，会永久性地把图切成两半；④它是数值一致性的额外风险点（你自己写的 CUDA kernel 与 PyTorch 参考实现的浮点行为未必一致，需要单独对拍）；⑤功能安全审查时它是一段需要单独论证的自研代码。所以「能不写就不写」不是懒，是正确的工程判断——选模型架构时就应该把「需要几个自定义 plugin」当作一个选型指标。

9研究前沿与开放问题

TensorRT 代表的是「vendor 手写 kernel 库 + 实测搜索」这条路线。它的边界在哪、会被什么取代，是一个仍然在演进的问题。

  • 搜索式编译 vs 手写库。TVM/Ansor、XLA、Triton、torch.compile+Inductor 走的是「自动生成 kernel + 代价模型/实测搜索调度」，TensorRT 走的是「手写高度优化的模板库 + 在模板间选」。前者覆盖面广、能处理新算子，后者在覆盖到的算子上通常更快。开放问题：随着模型算子越来越多样（各种 attention 变体、状态空间模型），手写库的覆盖率还能撑多久？
  • 用学习到的代价模型替代实测计时。TVM 的 AutoTVM/Ansor 已经在做，TensorRT 的 builderOptimizationLevel 可以看成一个粗粒度的简化版。如果代价模型足够准，构建时间可以从几十分钟降到几十秒，而且构建结果变成确定性的——这对量产发布流水线的价值可能比性能本身还大。
  • 可移植性与性能的根本张力。hardware-compatible engine 要付 5–15% 的性能。这个损失是本质的（不同架构的最优 tactic 就是不同）还是可以靠更好的抽象消掉的？目前没有令人满意的答案，而车端多硬件平台恰恰最需要这个答案。
  • 融合的粒度正在上移。FlashAttention 类工作把整个 attention（含 softmax 与在线归一化）融成一个 kernel，这已经超出了「图级模式匹配」能表达的范围——它需要算法层面的重写（分块 + 在线 softmax），而不只是把相邻算子合并。开放问题：如何让编译器自动发现这类需要改变数值算法的融合？这可能需要 kernel 级 DSL 与形式化的重写规则。
  • engine 的数值等价性论证。怎么向功能安全审查证明「这个 engine 与训练时的模型行为一致」？FP16/INT8 下「等价」本身就没有明确定义。目前的实践是统计性的（大样本上的输出分布对比 + 指标不降），但形式化的边界证明（如给定输入范围下输出误差的上界）在检测模型上仍然做不到。
  • 构建即代码（build-as-code）与产物血缘。engine 是 (ONNX, config, timing cache, TRT 版本, 设备型号, 构建机状态) 的函数，其中最后一项还是随机的。如何把这个函数变成可复现、可审计、可签名的流水线，是部署工程里比调 tactic 更重要、却极少被论文讨论的问题。

★ 必读（工程文档优先于论文）：NVIDIA, TensorRT Developer Guide —— 重点读 “Working with Dynamic Shapes”（optimization profile 的完整语义）、“How TensorRT Works / Layer Fusion”（融合规则表，注意它随版本变化）、“Performance Best Practices”（workspace、timing cache、精度约束）。★ NVIDIA, trtexec 文档与 TensorRT OSS 仓库 —— plugin 的参考实现（EfficientNMS_TRT、MultiscaleDeformableAttnPlugin）是理解「plugin 到底要写什么」的最快途径。
