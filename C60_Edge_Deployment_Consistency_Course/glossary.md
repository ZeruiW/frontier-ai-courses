## 一 · 一致性方法论 · Consistency Methodology

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| train-deploy consistency | 训练-部署一致性 | 部署侧的预处理、模型计算与后处理，与训练/评测侧在**数值上**等价（在明确的容差内）。 | 它是「离线指标能不能代表车上表现」的前提。不一致时，你所有的离线实验结论都是在描述一个不存在的系统。 | 以为「跑通了、框看着对」就是一致。BGR/RGB 弄反、resize 插值不同、letterbox 逆变换写错——**三者都不报错、都能出框**，但每一个都能吃掉几个 mAP。 |
| three-layer gap | 三层鸿沟 | 训练-部署差异只可能来自三层：**预处理 / 模型 / 后处理**。 | 这是本课全部方法论的骨架：因为只有三层，所以定位是**二分查找**而不是玄学调试。 | 以为差异可能来自「说不清的地方」。数据从图像文件到最终框只经过这三段，**没有第四个地方能藏 bug**。 |
| golden reference | 黄金基准 | 一份被所有人认可为「正确」的实现，通常是训练时用的 Python 管线，或 onnxruntime 的 CPU 执行结果。 | 对拍必须有一个基准，否则「A 和 B 不一样」无法推进到「谁错了」。 | 以为 TensorRT 的输出就该等于 PyTorch。**基准要按层级选**：查导出问题用 onnxruntime CPU，查引擎问题才用 TRT，一步跨两层等于放弃定位能力。 |
| layer-wise numeric diff | 逐层对拍 | 喂同一份输入，按执行顺序比较两边每一层的输出，**在第一个失配处停下**。 | 后面所有层的差异都只是第一处失配的后果，继续比是浪费。它把「差 2 个 mAP」翻译成「第 7 层的 eps 不对」。 | 以为要比完所有层再综合判断。**第一处失配就是答案**，第二处开始已经被污染。 |
| bisection localization | 二分定位 | 把管线按阶段切开，先比中点的张量，再决定往前半段还是后半段找。 | log₂ 次比较就能定位到具体算子。一条 12 阶段的管线，**4 次 dump 就能收敛**。 | 以为必须逐阶段顺序查。顺序查是 O(n)，二分是 O(log n)；阶段越多差距越大。 |
| atol / rtol | 绝对 / 相对容差 | `abs(a-b) <= atol + rtol*abs(b)` 的两个参数。 | 判定「一致」必须给数字。没有容差的「结果差不多」不是工程结论。 | 以为一个容差走天下。**FP32 逐层 ~1e-5、FP16 ~1e-2（相对）、INT8 应按量化步长 2/127 ≈ 0.016 的量级设**——用 1e-5 去卡 INT8 只会天天报假警。 |
| symptom fingerprint | 症状指纹 | 每类不一致有其特征性的表现，可据此跳过大部分排查。 | **框整体偏移** → 坐标变换/逆变换；**分数整体偏低** → 归一化或通道顺序；**只有小目标掉** → 插值或量化；**偶发极端错框** → 动态 shape profile 或未初始化内存。 | 以为症状不可靠、必须从头查。指纹不给最终答案，但它能把候选从 20 个砍到 2 个。 |
| end-to-end diff | 端到端对拍 | 从同一个图像文件出发，两边各跑完整管线，比较最终框（含类别、分数、坐标）。 | 它是验收的**最后一道门**，也是唯一能捕捉「各层都对但拼起来错」的检查。 | 以为端到端对拍能替代逐层对拍。它只能告诉你「有问题」，**不能告诉你在哪**，两者是互补的。 |
| determinism | 确定性 | 同样的输入、同样的二进制，每次运行给出逐位相同的结果。 | 不确定的系统无法对拍、无法回归、无法定责。cuDNN 的算法选择、原子加、多线程归约都会破坏它。 | 以为 GPU 计算天然确定。**同一个 conv 在不同 batch size 下可能选到不同 kernel，结果差 1e-6**——这不是 bug，但会让严格对拍失败。 |
| environment fingerprint | 环境指纹 | 记录下能影响数值的一切版本：驱动、CUDA、cuDNN、TRT、ONNX opset、OpenCV、编译选项。 | 「在我这儿是好的」的唯一解药。engine 与硬件绑定意味着指纹的一个字段变了，产物就要重建。 | 以为 `requirements.txt` 够了。**GPU 栈的版本链在 pip 之外**（驱动、CUDA runtime、TRT 都是系统级），必须锁进镜像。 |
| regression gate | 回归门禁 | 发布前自动跑的一组硬性检查，任一不过就不许发。 | 把「记得检查」变成「不检查就发不出去」。本课模块 05 给出六项清单。 | 以为门禁就是「mAP 不掉」。**延迟 p99、显存峰值、长时间稳定性、多硬件一致性、回退方案**同样是硬门槛，只看 mAP 是最常见的漏。 |
| shadow mode | 影子模式 | 新模型在车上真实运行但不接管决策，只记录输出与旧模型对比。 | 唯一能在真实分布上验证一致性的方式——**离线数据集永远缺少你没想到的那些场景**。 | 以为影子模式只是「灰度发布」。它更重要的作用是**采集真实的输入分布**，用来构造下一轮的校准集与回归集。 |
| numerical vs statistical equivalence | 数值等价 vs 统计等价 | 前者要求逐元素接近，后者只要求指标（mAP、分数分布）接近。 | FP32 导出要求数值等价；INT8 只能要求统计等价（逐元素必然有差）。**判据必须跟着精度走**。 | 以为 INT8 也该逐元素对得上。INT8 的单元素误差可以很大，**要看的是最终框的 IoU 与分数排序是否稳定**。 |

## 二 · 预处理 · Preprocessing

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| preprocessing mismatch | 预处理不一致 | 部署侧的图像预处理与训练侧不同（尺寸、插值、通道、归一化、色彩空间任一不同）。 | **它是训练-部署掉点最常见的单一原因**，而且是最便宜的修复——不用重训，改几行代码。JD 里点名的第一条。 | 以为预处理「都差不多」。同一张 1920×1080 图缩到 640×640，cv2 与 PIL 的结果**逐像素最大差可达十几个灰阶**，足以让小目标的分数跨过阈值。 |
| bilinear interpolation | 双线性插值 | 输出像素由输入的 4 个最近邻按距离加权得到。 | 是 resize 的默认选择，也是所有分歧的发源地——**"双线性"只规定了加权方式，没规定坐标怎么映射**。 | 以为「双线性」是一个确定的算法。它至少有 3 种坐标映射约定 × 是否抗锯齿 × 边界处理方式的组合。 |
| `align_corners` | 角点对齐 | 决定输入输出网格如何对齐的布尔开关：`True` 时首尾像素中心严格对齐，`False` 时按像素**区域**中心对齐。 | 两者算的是**两个不同的坐标映射公式**，缩放比越大差异越明显。PyTorch 默认 `False`，某些旧实现默认 `True`。 | 以为它只影响边缘几个像素。它改的是整条映射线的斜率与截距，**每一个输出像素都会不同**；缩放 3 倍时中间像素也能差好几个灰阶。 |
| `coordinate_transformation_mode` | 坐标变换模式 | ONNX `Resize` 算子的属性：`half_pixel` / `pytorch_half_pixel` / `align_corners` / `asymmetric` / `tf_crop_and_resize`。 | **这是 ONNX 把上面那个分歧显式化的地方**。导出时选错，engine 端就会算出另一张图。 | 以为导出会自动选对。它取决于导出器版本与源框架，**必须导出后打开 ONNX 图确认属性值**，这是模块 02 的必查项。 |
| INTER_LINEAR | 线性插值（OpenCV） | 缩放时只取 4 个源像素加权。 | 放大时没问题；**缩小时是错的**——从 1920 缩到 640，每个输出像素代表 9 个源像素，只采 4 个意味着大部分像素从未被读到。 | 以为它是「安全的默认值」。它确实是 `cv2.resize` 的默认值，**而这正是坑所在**：默认值在下采样场景下会漏采样。 |
| INTER_AREA | 区域平均（OpenCV） | 缩小时对源区域内所有像素做面积加权平均。 | **缩小图像的正确选择**，等价于先低通再采样，不会漏掉信息。训练管线用 AREA、部署用 LINEAR 是经典事故。 | 以为 AREA 只是「更慢的 LINEAR」。它们在下采样时给出**结构性不同**的结果：细线条、远处小标志在 LINEAR 下可能整个消失。 |
| antialias | 抗锯齿 | 下采样前先按缩放比做低通滤波。 | `torchvision.transforms.Resize` 的 `antialias` 默认值在版本间**变过**（v2 起默认 True），是跨版本掉点的常见原因。 | 以为抗锯齿只影响观感。它改变的是送进网络的实际数值，**开与不开可以差 1 个 mAP 以上**。 |
| INTER_NEAREST | 最近邻 | 直接取最近的源像素，不做加权。 | 掩码/标签图必须用它（插值会造出不存在的类别 ID）。 | 以为「最近邻」也是唯一确定的。OpenCV 的 `INTER_NEAREST` 与 `INTER_NEAREST_EXACT` 的取整规则不同，**在半像素位置上会差一个像素**。 |
| letterbox | 保比缩放加边 | 按长边等比缩放到目标尺寸，短边用固定值 padding 补齐，保持宽高比不变。 | YOLO 系的标准预处理。不保比直接 resize 会让标志形状畸变，圆形禁令牌被压扁。 | 以为 letterbox 是一个标准算法。它有**至少四个自由参数**：pad 值（114 还是 0）、居中还是左上、缩放比要不要取整/限制不放大（`scaleup`）、pad 到 stride 倍数还是补满目标尺寸。四个都得两边一致。 |
| letterbox 逆变换 | inverse letterbox | 把网络输出的框从 letterbox 图坐标还原回原图坐标：先减 padding 偏移，**再**除以缩放比。 | **写错它是「框整体偏移」最常见的原因**，也是最难发现的——mAP 只是慢慢掉、不会崩，可视化上框「大致对但都偏一点」。 | 以为顺序无所谓。**先除比例再减 pad** 与 **先减 pad 再除比例** 给出完全不同的结果；只有后者对。另一个高频错误是左右 pad 不等（奇数差）时用了同一个偏移。 |
| padding value 114 | 填充值 114 | YOLO 系约定的灰色填充值（0–255 尺度下的 114，归一化后约 0.447）。 | 它进了卷积的感受野，会影响边缘目标的特征。**训练用 114、部署用 0 会让贴边的标志分数系统性偏低**。 | 以为填充区域「模型会忽略」。卷积不知道哪块是 padding，**边缘目标的感受野里就是有这些像素**。 |
| stride alignment | 步长对齐 | 输入尺寸必须是网络总下采样率（通常 32）的整数倍，否则特征图尺寸对不齐。 | 决定 letterbox 是「补满 640×640」还是「只补到 32 的倍数」（后者更快但改变了输入尺寸）。 | 以为随便补都行。补法不同 → 输入尺寸不同 → **TensorRT 的 optimization profile 可能不覆盖 → 触发重新选 kernel 甚至报错**。 |
| BGR vs RGB | 通道顺序 | OpenCV 读图是 **BGR**，PIL / torchvision / 多数训练框架是 **RGB**。 | **弄反不会报错、模型照样出框**，但等于给网络喂了一组它没见过的颜色。交通标志的红/蓝/黄是语义本身，反了之后红牌变蓝牌。 | 以为「模型会自己适应」。实测掉点常在 **10 个 mAP 以上**，且症状是「大部分框还在但分数普遍低、类别错得离谱」。这是面试里最值得主动举的例子。 |
| mean / std normalization | 均值方差归一化 | `x = (x/255 - mean) / std` 或 `x = (x - mean*255) / (std*255)`。 | 两种写法数学等价，但**如果一边除了 255 另一边没除**，输入就差 255 倍。 | 以为归一化参数一致就万无一失。还要确认：mean/std 是按 RGB 还是 BGR 顺序排的、是 0–1 尺度还是 0–255 尺度、有没有额外的 `/255`。 |
| uint8 to float timing | 类型转换时机 | 在 resize 之前还是之后把 uint8 转成 float。 | 先转 float 再 resize 与先 resize（uint8 内部累加、四舍五入）再转 float 的结果不同。 | 以为只是精度问题。OpenCV 在 uint8 上做插值时会**取整**，这个量化误差在小目标上是可见的。 |
| NHWC / NCHW | 张量布局 | 通道维在最后（NHWC，相机与 TensorRT plugin 常用）还是在第二维（NCHW，PyTorch 默认）。 | 转换要用 `transpose` 而不是 `reshape`——**`reshape` 不报错但内容全错**。 | 以为形状对了就是对了。`(1,3,640,640)` 可以由 `transpose` 得到也可以由 `reshape` 得到，**形状一样、内容完全不同**。 |
| ISP | 图像信号处理器 | 相机传感器 raw 数据到可用图像之间的硬件流水线：去马赛克、白平衡、降噪、色调映射、锐化。 | **训练数据往往是 JPEG 解码图，车上拿到的是 ISP 直出的 YUV/NV12** ——两者的噪声特性、锐度、色调曲线都不同，这是一条无法靠改代码消除的域差。 | 以为「都是图像，差不多」。ISP 的降噪会抹掉远处小标志的纹理，锐化会造出训练时没有的边缘；这类域差只能靠**用车端采集的数据训练/微调**来解决。 |
| YUV / NV12 | 色彩格式 | 车载相机与视频编解码的常用格式，亮度与色度分离且色度**降采样**（NV12 是 4:2:0）。 | NV12→RGB 的转换矩阵有多个标准（BT.601 / BT.709）与两种量程（full / limited range），**选错会整体偏色**。 | 以为 YUV→RGB 只有一个公式。BT.601 与 BT.709 的系数不同，limited range 还要先做 16–235 的映射，**四种组合两两之间都不一样**。 |
| JPEG decoder difference | 解码器差异 | libjpeg、libjpeg-turbo、PIL、OpenCV、GPU 硬解对同一个 JPEG 文件的解码结果可能相差 ±1–2 个灰阶。 | 严格对拍时会撞上它；也是「同一份数据两台机器算出不同 mAP」的少见但真实的原因。 | 以为 JPEG 解码是确定的。标准只规定了 IDCT 的精度范围，**不同实现的取整策略不同**。对拍时应从解码后的数组开始，而不是从文件开始。 |
| domain gap | 域差 | 训练分布与部署分布的系统性差异（光照、天气、相机、地区、ISP 调校）。 | 它与「一致性 bug」的区别是：**一致性 bug 可以修到零，域差只能缩小**。分清两者才不会把资源投错方向。 | 以为掉点都是域差、只能靠加数据。**先排除一致性 bug 再谈域差**——前者几小时能修，后者要几周的数据闭环（C58）。 |

## 三 · TensorRT 与编译 · TensorRT & Compilation

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| ONNX | 开放神经网络交换格式 | 事实上的模型交换格式。四要素：静态拓扑、**opset 版本**、符号形状（动态轴）、内联权重。 | 它是 PyTorch 与 TensorRT 之间的唯一桥梁，也是对拍的中间基准（onnxruntime CPU 结果 = 黄金参考）。 | 以为导出成功就等于导对了。**能加载 ≠ 语义一致**：控制流被固化、shape 被写死、Resize 的坐标模式选错，全都能"成功导出"。 |
| opset | 算子集版本 | 每个 ONNX 算子标注「自哪个 opset 起可用 / 语义变更」。 | 目标运行时支持的 opset 有上限；同一个 `Resize` 在 opset 10 与 13 下**属性集合都不同**。 | 以为 opset 越新越好。要**先查目标 TRT 版本支持到哪一档再导出**，导高了会触发算子回退甚至构建失败。C52 详讲。 |
| constant folding | 常量折叠 | 把只依赖常量的子图在导出期直接算成常量。 | `onnx-simplifier` / `polygraphy surgeon` 的主要作用；不折叠会留下一堆 `Shape`-`Gather`-`Concat` 小节点，**这些节点会阻断融合**。 | 以为它只是「让图好看点」。它经常是**融合失败的直接原因**，也是「导出后 TRT 层数异常多」的第一怀疑对象。 |
| builder / builder config | 构建器 / 构建配置 | TensorRT 把 ONNX 图编译成 engine 的过程与它的配置对象。 | 精度标志（FP16/INT8/BF16）、workspace 上限、optimization profile、timing cache 全在这里设，**每一项都会改变产物**。 | 以为构建是"格式转换"。它是**一次真实的编译 + 搜索**：会实测上百个候选 kernel，所以耗时几分钟到几十分钟。 |
| workspace size | 工作空间上限 | 允许各层临时使用的显存上限（新 API 里是 `MEMORY_POOL_LIMIT`）。 | 给少了，**某些高性能 kernel（如需要大 workspace 的 Winograd/隐式 GEMM）会直接不被考虑**，构建成功但速度慢。 | 以为它是「运行时占用」。它主要影响**构建期能选到哪些 tactic**；调大它常常是最便宜的一次提速。 |
| optimization profile | 优化配置档 | 动态 shape 下必须提供的 `min / opt / max` 三档尺寸。 | TensorRT 按 **opt** 那一档去选 kernel。**opt 定错，动态轴等于白设**：跑在 opt 附近很快，偏离就慢。 | 以为三档只是「合法范围」。min/max 决定能不能跑，**opt 决定跑多快**；多档差异大时应该建多个 profile 而不是把范围拉宽。 |
| explicit batch | 显式批次 | 新版 TensorRT 里 batch 维就是普通的第 0 维（可为动态）。 | 老的 implicit batch 模式已废弃；所有动态 shape 都靠 profile 表达。 | 以为 batch 维会被自动处理。**它和 H/W 一样需要写进 profile**，忘了就被固定成导出时的值。 |
| layer fusion | 层融合 | 引擎把多个算子合并成一个 kernel，主要分**纵向融合**（Conv+BN+激活）与**横向融合**（多个同源同参的分支）。 | 融合减少的是**中间张量的读写**，而不是 FLOPs——这也是为什么它对访存受限的检测网络收益极大。 | 以为融合总会发生。**中间插了 reshape/transpose、输出被多处消费、用了非标准激活、精度不一致**，任一条都会阻止融合。要看 verbose 构建日志里的层名（融合后的层名是拼起来的）。 |
| Conv+BN fusion | 卷积-批归一化融合 | 把 BN 的 γ/β/μ/σ 折进卷积权重：W' = γW/sqrt(σ²+ε)，b' = β - γμ/sqrt(σ²+ε)。 | **它是精确的代数恒等变换**，可以逐元素 `assert np.allclose` 验证；是所有推理引擎的第一个优化。 | 以为融合会掉精度。FP32 下它是恒等的；**掉精度只可能来自融合后数值范围变大导致的量化更难**（YOLOv6 论文专门讨论过这一点）。 |
| kernel autotuning / tactic selection | 内核自动调优 / 策略选择 | 对每一层实测多个候选实现（不同算法、不同 tile 大小、是否用 tensor core），选最快的。 | 这是**构建耗时几分钟到几十分钟的根本原因**，也是 engine 与硬件强绑定的根本原因。 | 以为构建慢是"编译慢"。它慢是因为在**真的跑 benchmark**；这也意味着构建机器的负载会影响选择结果。 |
| timing cache | 计时缓存 | 缓存 tactic 的实测耗时，跨构建复用。 | 能把重复构建从几十分钟压到几分钟，是 CI 里的必备优化。 | 以为可以跨硬件复用。**缓存与 GPU 型号绑定**，混用会选到次优 kernel（且不报错）。 |
| engine / plan | 引擎 / 序列化计划 | TensorRT 的编译产物，包含选定的 kernel、内存布局与权重。 | 它是真正被部署的东西。**engine 不是模型，是「模型 + 这台硬件的编译结果」**。 | 以为 engine 是跨平台的模型文件。它和 ONNX 完全不同——ONNX 可移植，engine 不可。 |
| hardware binding | 硬件绑定 | engine 与 **GPU 型号 × 驱动版本 × TensorRT 版本** 三元组绑定，换任一个都要重建。 | 车端往往有多个硬件档位（Orin 的不同 SKU、不同代平台），**N 个平台 × M 个模型 = N×M 条独立的构建-验证流水线**，这是真实的工程成本。 | 以为「换个同代显卡应该能用」。加载不匹配的 engine 会**直接失败或行为未定义**；新版本的 version/hardware compatibility 模式能放宽，但要付性能代价。 |
| DLA | 深度学习加速器 | NVIDIA Orin 等平台上独立于 GPU 的固定功能加速器。 | 车端的算力分配工具：把一部分网络放到 DLA，**给 GPU 腾出算力**给其他感知任务。 | 以为 DLA 是「免费的额外算力」。它**支持的层与精度都很有限**，不支持的层会回落到 GPU，跨设备切换本身有开销。 |
| plugin | 插件 / 自定义层 | 自己实现 TensorRT 不支持的算子（`IPluginV2DynamicExt` / `IPluginV3`）。 | 检测里最常见的两个 plugin 是 **EfficientNMS** 与 deformable attention 类算子。 | 以为写 plugin 是第一选择。**先试四条更便宜的路**：换等价算子、升级 opset/TRT、拆成支持的组合、把这段挪到 CPU 后处理。写 plugin 意味着你要自己负责它的多精度实现与所有平台的维护。 |
| silent fallback | 静默回退 | 不支持的算子被切成子图交给别的后端（CPU 或 CUDA），**不报错**。 | **症状是「转了 TRT 但没变快」**。ONNX Runtime 的 TRT EP 尤其容易发生，一张图可能被切成十几个子图。 | 以为不报错就说明全跑在 TRT 上。判据是**看分区数量与每个分区的后端**，以及层数是否远多于预期，而不是看端到端延迟。 |
| subgraph partitioning | 子图分区 | 把整图切成「这个后端能跑的」与「不能跑的」若干段。 | 分区越多越糟：每次跨后端切换都有**内存拷贝与同步**开销，可能比不优化还慢。 | 以为「大部分层进了 TRT 就行」。**一个卡在中间的不支持算子能把图切成两半**，收益直接减半。 |
| Q/DQ nodes | 量化/反量化节点 | 显式量化模式下，图里插入的 `QuantizeLinear` / `DequantizeLinear` 对。 | TensorRT 的**显式量化**路径（来自 QAT 或 PTQ 工具）比隐式量化更可控：量化位置由图决定，而不是由引擎猜。 | 以为 Q/DQ 越多越好。**Q/DQ 的摆放位置决定了哪些层能融合**，摆错会阻断融合导致更慢；要遵循「Q/DQ 传播」规则。 |
| strongly typed | 强类型模式 | 新版 TensorRT 里由图本身的类型决定每层精度，引擎不再自由选择。 | 让「哪层用 FP16」变成可复现、可审计的，而不是每次构建都可能不同。 | 以为设了 `FP16` 标志就是全网 FP16。默认它只是**允许**，引擎仍会为了速度或精度自行取舍；要强制必须用精度约束或强类型。 |
| `trtexec` | TRT 命令行工具 | 构建 engine、测延迟、导出逐层耗时的官方工具。 | **上手部署的第一个命令**：`--fp16 --int8 --shapes --dumpProfile --separateProfileRun --verbose` 几乎覆盖了本课模块 02/05 的全部操作。 | 以为 `trtexec` 报的延迟就是端到端延迟。它默认**不含预处理、不含后处理、可能不含 H2D/D2H**，而且用的是它自己造的随机输入。 |
| `polygraphy` | 对拍与调试工具 | 官方工具，可以一条命令同时跑 onnxruntime 与 TensorRT 并逐层比对。 | **它就是本课「逐层对拍」方法论的官方实现**：`polygraphy run model.onnx --trt --onnxrt --atol --rtol` 加上 `debug reduce` 能自动缩小到出问题的子图。 | 以为对拍要自己写脚本。自己写一遍有教学价值（notebook 里就会写），**但真实项目里直接用 polygraphy**。 |
| ONNX GraphSurgeon | 图手术工具 | 直接编辑 ONNX 图：删节点、改属性、插 plugin 节点。 | 插 EfficientNMS plugin、修 Resize 属性、去掉多余的 Cast，都靠它。 | 以为改图很危险所以不该做。**改图往往是最短路径**；危险的是改完不对拍。 |
| CUDA graph | CUDA 图 | 把一串 kernel 启动录制成一个图，一次提交。 | 小模型上 kernel launch 开销占比可达 10–20%，**CUDA graph 是把它拿回来的标准手段**。 | 以为它能加速计算。它只减少**启动开销**；对大 kernel 主导的网络几乎无效。 |

## 四 · 量化与校准 · Quantization & Calibration

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| INT8 quantization | 8 位整数量化 | 用 8 bit 整数表示原本 FP32 的权重与激活，配一个 scale（与可选的 zero-point）还原。 | 车端的默认精度：**显存与带宽降到 1/4，吞吐常有 2–3 倍提升**，且 tensor core 对 INT8 有专门通路。 | 以为 INT8 就是「精度低一点」。本质是**用 256 个格子去装原来的连续范围**——格子放在哪里（scale 怎么定）就是全部问题，这也是为什么校准比量化本身更重要。 |
| scale | 量化步长 | 浮点值与整数值之间的比例：`x ≈ scale * (q - zero_point)`。 | 它是量化的**唯一自由参数**（对称量化下），校准算法的全部工作就是给出它。 | 以为 scale 可以后期微调。它被写死进 engine（或 calibration cache），**改 scale 等于重建**。 |
| zero-point | 零点 | 浮点 0 对应的整数值。对称量化下固定为 0。 | 非对称量化靠它表达单侧分布（如 ReLU 后全为正）。 | 以为零点只是偏移量。它会引入**额外的交叉项**，让 INT8 GEMM 的实现更复杂（Jacob et al. 论文的核心推导之一）。 |
| symmetric vs asymmetric | 对称 vs 非对称 | 对称：范围是 `[-s*127, s*127]`，zero-point=0；非对称：范围任意 `[min, max]`，需要 zero-point。 | TensorRT 的激活与权重都用**对称量化**——因为对称量化的矩阵乘不产生交叉项，kernel 更快。 | 以为非对称一定更准。对 ReLU 后的单侧分布确实更省格子，**但硬件不支持时这份"更准"根本用不上**。 |
| per-tensor vs per-channel | 逐张量 vs 逐通道 | 整个张量共用一个 scale，还是每个输出通道一个 scale。 | **权重用 per-channel、激活用 per-tensor 是工业标准组合**：不同通道的权重范围可以差几十倍，共用 scale 会毁掉小范围的通道。 | 以为激活也该 per-channel。激活的 per-channel 在推理时**无法与矩阵乘融合**（每个元素的 scale 不同），所以硬件通常不支持。 |
| dynamic range | 动态范围 | 一个张量在校准集上观察到的数值范围。 | TensorRT 的隐式量化就是给每个张量设一个 dynamic range；校准 = 估计它。 | 以为要取真实的 min/max。**恰恰相反**——最优的范围通常比真实范围小（截断离群值换取更细的格子），这就是 Entropy/Percentile 存在的理由。 |
| calibration | 校准 | 用一小批无标注数据跑前向，统计激活分布，据此定 scale。 | PTQ 的核心步骤，**几百到上千张图、几分钟就能完成**，不需要标签、不需要训练。 | 以为校准是"轻微训练"。它**不改任何权重**，只统计激活；所以它便宜，也所以它的上限受限于校准集的代表性。 |
| calibration set | 校准集 | 用于校准的那批图像。 | **这是本课模块 03 最容易做错、也最少被讲到的一步**：它必须覆盖夜间、逆光、雨雪、隧道等长尾场景，且预处理必须与线上逐字节一致。 | **「用训练集的头 500 张」是经典错误**——它们很可能全是晴天白天同一段路，导致夜间场景的激活整段超出校准范围而被裁剪，夜间 mAP 断崖式下跌而白天看不出问题。 |
| calibration cache | 校准缓存 | 保存每个张量 scale 的文本文件，可跨构建复用。 | 让「换硬件重建 engine」不必重跑校准，也让 scale 可被 review 与 diff。 | 以为缓存可以跨模型版本用。**网络结构一改，张量名与分布都变了**，复用旧缓存会静默地用错 scale。 |
| MinMax calibration | 最大最小校准 | 直接取校准集上观察到的绝对最大值作为范围。 | 实现最简单，**在分布紧凑、无离群值时反而最准**（不丢任何信息）。 | 以为它"最保守所以最安全"。**它被单个离群值就毁掉**：一个 100 倍的异常激活会让其余 99.99% 的值全部挤进最低的两三个格子。 |
| Entropy / KL calibration | 熵校准 | TensorRT 默认（`IInt8EntropyCalibrator2`）：对激活直方图搜索一个截断阈值，使**量化前后分布的 KL 散度最小**。 | 它把问题形式化成「哪种截断丢的信息最少」，对有长尾的激活分布明显优于 MinMax。 | 以为它在最小化输出误差。**它最小化的是分布层面的信息损失**（Migacz 2017 的白皮书），这与最终 mAP 只是相关而非等价——所以仍需实测。 |
| KL divergence | KL 散度 | 衡量用分布 Q 近似分布 P 的信息损失：`sum P*log(P/Q)`。 | 熵校准的目标函数。实现里 P 是原始直方图（截断后把尾部质量并入最后一个 bin），Q 是量化再展开回来的分布。 | 以为 KL 是对称的。**KL(P‖Q) ≠ KL(Q‖P)**，方向搞反会得到完全不同的阈值；这是从零实现时最常见的 bug。 |
| percentile calibration | 分位数校准 | 取 99.9%（或 99.99%）分位数作为范围，直接截断上面的尾巴。 | **工程上最省事的折中**：一个超参、几行代码、效果通常接近熵校准。 | 以为分位数越高越安全。99.999% 已经接近 MinMax（重新引入离群值问题），**99.9 与 99.99 之间常有 0.5 mAP 的差别，值得实测两三个值**。 |
| outlier | 离群值 | 数值远大于同层其余激活的少数元素。 | 它是量化困难的**唯一根源**：没有离群值时 MinMax 就够用了。Transformer 的某些通道天然有极端离群值，这才有了 SmoothQuant。 | 以为离群值是"坏数据"应该丢掉。它们往往携带重要信息（强边缘、高对比目标），**量化的任务是权衡「保住它」与「保住其余 99.9%」**。 |
| saturation / clipping | 饱和 / 截断 | 超出量化范围的值被夹到端点。 | 截断是**有意为之**的信息取舍，不是错误。校准算法的输出本质上就是"截在哪"。 | 以为出现截断说明量化失败。零截断的量化（MinMax）常常更差。 |
| sensitivity analysis | 敏感层分析 | 逐层单独量化（其余保持高精度），测量该层对最终指标的影响，排序找出最敏感的层。 | **通常 5% 的层贡献 80% 的掉点**，把它们保 FP16 就能救回大部分精度而几乎不损失速度。 | 以为要做 N 次完整评测所以太贵。可以用**小验证集 + 输出层的余弦相似度/SQNR** 作为代理指标，成本降一两个数量级。 |
| SQNR | 信噪比（量化） | `10*log10(signal_power / quant_noise_power)`，逐层量化误差的标量度量。 | 敏感层分析的常用代理指标，比 mAP 便宜得多且与之高度相关。 | 以为 SQNR 高就一定 mAP 不掉。它是代理，**最终仍要用真实指标验收**，尤其是分类头这类对排序敏感的输出。 |
| mixed precision | 混合精度 | 大部分层 INT8、敏感层保 FP16/FP32。 | **PTQ 掉点的标准解药**，成本远低于 QAT。TensorRT 里通过层精度约束或 Q/DQ 摆放实现。 | 以为混合精度会大幅变慢。保 5–10% 的层通常只损失 5–15% 的速度，**但可能救回 1–2 个 mAP**。 |
| PTQ | 训练后量化 | 不重新训练，只用校准集定 scale。 | 几分钟到几十分钟出结果，**永远应该先试它**。 | 以为 PTQ 一定比 QAT 差。在检测任务上，PTQ + per-channel 权重 + 好的校准集 + 混合精度，掉点常常已在 0.5 mAP 以内。 |
| QAT | 量化感知训练 | 训练时插入伪量化节点（fake quant），让模型学会适应量化误差。 | **PTQ 掉点 > 1–2 mAP 且混合精度救不回来时才轮到它**；代价是一轮完整的训练与一整套流水线。 | 以为 QAT 是"更高级所以更好的做法"。它的成本是 PTQ 的几十倍，**先做 PTQ 的排查再决定**是唯一理性的顺序（这也是面试的标准答案骨架）。 |
| fake quantization / STE | 伪量化 / 直通估计 | 前向做量化-反量化、反向直接传梯度（因为 round 的梯度处处为 0）。 | QAT 的实现基础。算法细节在 **C27**，本课只需要它的接口与产物（带 Q/DQ 的 ONNX）。 | 以为 STE 是"数学上正确的梯度"。它是**有偏的近似**，这也是 PACT/LSQ 这些工作要改进的地方。 |
| PACT / LSQ | 可学习截断 / 可学习步长 | 把截断阈值（PACT）或量化步长（LSQ）本身作为可训练参数。 | 让"截在哪"由梯度决定而不是由校准启发式决定，是 QAT 精度的主要来源之一。 | 以为它们只对低比特（2–4 bit）有意义。INT8 下收益小但**在敏感层上仍可能是 0.3–0.5 mAP 的差别**。 |
| SmoothQuant | 平滑量化 | 把激活的离群值「转移」一部分到权重上（激活除以 s、权重乘以 s），让两者都更好量化。 | 处理**激活离群值极端**的场景（Transformer / DETR 类结构）的标准手段，且是数学等价的变换。 | 以为它是 LLM 专用。任何有 LayerNorm + 大离群通道的结构都适用，**RT-DETR 这类含 transformer encoder 的检测器量化时值得一试**。 |
| quantization accuracy drop | 量化掉点 | INT8 相对 FP32 的指标下降。 | JD 里点名的四类问题之一。**排查它有固定的决策树**：先验证 FP16 是否已掉（排除非量化因素）→ 检查校准集分布 → 换校准算法 → per-channel 权重 → 敏感层分析 + 混合精度 → 最后才 QAT。 | 以为掉点就该直接上 QAT。**大多数掉点的真实原因是校准集不具代表性**，换一份校准集比训一轮 QAT 便宜一千倍。 |
| detection-specific sensitivity | 检测任务的量化特性 | 分类头与回归头对量化的敏感度不同；小目标比大目标更敏感。 | 回归头输出的是连续坐标，量化误差直接变成**框的像素偏移**；对 8×8 像素的交通标志，2 px 偏移就让 IoU 从 1.0 掉到 0.39。 | 以为量化只影响分类分数。**小目标的框抖动才是 TSR 场景 INT8 掉点的主要来源**，所以评测必须按尺寸分桶看（C57）。 |

## 五 · 后处理与坐标 · Post-processing & Coordinates

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| postprocessing mismatch | 后处理不一致 | 部署侧的解码 + NMS + 坐标还原与训练/评测侧不同。 | 后处理是**两边各写一遍**的地方（Python 一份、C++ 一份），所以天然是不一致的重灾区。JD 点名的第二类问题。 | 以为后处理"逻辑很简单，不会错"。恰恰因为简单，它常被凭记忆重写而不是移植，**四个分歧点里踩中一个就够了**。 |
| decode / grid decode | 解码 | 把网络原始输出（相对偏移、分布、logit）还原成图像坐标下的框与分数。 | 它是 NMS 之前的一步，包含**网格中心偏移（+0.5 还是 +0）、stride 乘法、exp/sigmoid 的选择**，每一处都可能不一致。 | 以为解码公式各版本通用。YOLOv5 的 `(2σ(x)-0.5)` 与 v3 的 `σ(x)` 不同，**照着别的版本抄解码是经典事故**。 |
| DFL decode | 分布焦点损失解码 | 每条边输出一个离散分布，解码时做 softmax 后求期望。 | YOLOv8 / D-FINE 的回归表示。**部署侧漏掉这一步会让框全部塌到网格中心附近**。 | 以为它可以省略或近似成 argmax。argmax 会丢掉亚像素精度，**对小目标影响显著**。 |
| NMS | 非极大值抑制 | 按分数排序，保留最高分框并抑制与其 IoU 超阈值的框。 | 密集预测的必备后处理，也是端到端延迟里**唯一耗时随场景变化**的一段。 | 以为 NMS 是一个标准算法。它至少有四个自由选择：**class-wise 与否、top-k 预筛、score 阈值在前还是在后、IoU 的边界约定**。 |
| class-wise NMS | 分类别 NMS | 只在同类别的框之间做抑制。 | **TSR 必须用它**：限速 60 与限速 80 的牌子在路口叠放很常见，class-agnostic 会删掉其中一个，直接造成漏检。 | 以为两者差别很小。在类别高度相似且空间重叠的场景差别巨大；**这是本课能举出的最好的一个 TSR 特化例子**。 |
| class-agnostic NMS | 类别无关 NMS | 跨类别一起抑制。 | 在类别互斥且不可能重叠的场景更快、更干净（如人脸）。 | 以为它"更严格所以更安全"。它**会主动删掉正确预测**，在多类叠放场景是净损失。 |
| batched NMS | 批量 NMS | 给每个类别的框加一个巨大的类别偏移，把 class-wise 变成一次 class-agnostic 调用。 | 工程上把循环变成一次调用，是所有主流实现的做法。 | 以为偏移量随便取。**偏移必须大于图像最大边长**，否则不同类的框会意外互相抑制——这个 bug 只在大图上才会暴露。 |
| top-k pre-filter | top-k 预筛选 | NMS 前先按分数取前 k 个候选（常见 1000）。 | 把 NMS 的 O(n²) 上界钉死，是延迟可控的关键。 | 以为它无损。**k 设小了会截断密集场景的真实目标**；而且**两边 k 不同就是一个静默的不一致源**——同一张图，Python 端 k=1000、C++ 端 k=300，密集路口结果就不同。 |
| score threshold ordering | 阈值顺序 | 先按 score 过滤再 NMS，还是先 NMS 再过滤。 | 顺序不同，结果不同：先 NMS 时低分框可能抑制掉高分框的邻居。 | 以为顺序不影响结果。**它影响的是被抑制的集合**，在阈值附近的框上差异明显。 |
| IoU `+1` convention | 边界约定 | 老式实现算宽高用 `x2-x1+1`（把坐标当作离散像素索引），现代实现用 `x2-x1`。 | 两者对小框差别巨大：**8 像素的框，+1 约定让面积变成 9×9 = 81 而非 64，差 27%**，足以让 NMS 的抑制结果不同。 | 以为这是"历史遗留、无所谓"。Faster R-CNN 时代的代码、部分 C++ 实现、部分评测脚本仍在用 +1，**混用两边就是一个隐蔽的不一致源**。 |
| xyxy / xywh / cxcywh | 框格式 | 左上右下 / 左上加宽高 / 中心点加宽高。 | 三种格式在代码里长得一样（都是 4 个 float），**弄混不会报错**，只会让框全部错位。 | 以为可以靠数值范围判断。当框接近图像中心且尺寸中等时，三种格式的数值范围高度重叠，**只能靠约定和断言**。 |
| normalized vs pixel coordinates | 归一化 vs 像素坐标 | 坐标是 0–1 的比例，还是绝对像素值。 | 模型内部常用归一化（DETR 系尤其），部署侧要乘回原图尺寸。**乘错尺寸（乘了 letterbox 图而非原图）是框整体缩放错误的来源**。 | 以为看数值就知道。640×640 的图上，归一化坐标 0.8 和像素坐标 0.8 都"合法"，**前者是 512 px，后者贴着左边缘**。 |
| coordinate restoration | 坐标还原 | 把 letterbox 图上的框还原到原图：`(xy - pad) / ratio`，然后 clip 到图像边界。 | **顺序错、pad 用错、左右 pad 不等时用同一个偏移，是"框整体偏移"最常见的三个原因**。 | 以为偏移不大所以无所谓。1920×1080 缩到 640×640 时上下各 pad 140 px，**顺序写反会让框偏移一百多像素**——但 mAP 只是掉，不会归零，所以能一路带上车。 |
| clip to image | 边界裁剪 | 把还原后的框夹进 `[0, W] × [0, H]`。 | 缺了它，贴边目标的框会超出图像，下游（跟踪、距离估计）可能算出负数尺寸。 | 以为 clip 之后就安全了。**clip 会改变框的宽高比**，如果下游用宽高比做过滤，要在 clip 前算。 |
| sigmoid/softmax placement | 激活位置 | 分类分数的 sigmoid/softmax 放在模型内（导出进 ONNX）还是模型外（后处理里做）。 | **放在模型内**：后处理简单、两边不会算错；**放在模型外**：模型输出 logit，INT8 时动态范围更大更难量化。 | 以为只是代码组织问题。它直接决定 **INT8 输出层的量化难度**，也决定 EfficientNMS plugin 能否直接接上（plugin 期望的是已 sigmoid 的分数）。 |
| EfficientNMS plugin | 高效 NMS 插件 | TensorRT 官方 plugin，把整个 NMS 搬进 engine，在 GPU 上完成。 | 省掉一次 D2H（原本要把上万个候选框拷回 CPU），**在密集场景能省几毫秒**，且延迟更稳定。 | 以为接上就完事。它的输入布局、是否 class-wise、score 是否已激活、坐标格式**全都有硬性约定**，接错会静默给出空结果或错框——接完必须端到端对拍。 |
| memory ownership | 内存所有权 | C++ 管线里谁分配、谁释放、谁在什么时候可以读写某块缓冲区。 | 车端管线是多线程 + 异步的，**所有权不清晰就会读到还没写完的缓冲区**，症状是偶发的错框（最难复现的一类 bug）。 | 以为智能指针能解决一切。跨 CPU/GPU、跨 stream 的生命周期还需要**事件（event）同步**，`shared_ptr` 管不到 GPU 的执行时序。 |
| CUDA stream | 流 | GPU 上的一条异步执行队列，同一流内顺序执行、不同流可并发。 | 让 H2D 拷贝、推理、D2H 拷贝**流水线重叠**，是隐藏拷贝开销的标准手段。 | 以为异步就等于免费。异步只是**重叠**，总带宽占用没变；而且忘了同步就会读到未完成的结果。 |
| pinned memory | 锁页内存 | 不会被操作系统换出的主机内存，可被 GPU 直接 DMA。 | 用 pinned memory 的 H2D 带宽通常是 pageable 的 **2 倍以上**，且只有它支持真正的异步拷贝。 | 以为多分配点 pinned memory 没坏处。它是稀缺资源，**分配过多会拖慢整个系统**，且分配本身很慢——要预分配复用。 |
| zero-copy / unified memory | 零拷贝 / 统一内存 | 在 Orin 这类 **CPU 与 GPU 共享物理内存**的 SoC 上，让两者直接访问同一块内存，省掉拷贝。 | **车端 SoC 的关键优化**：H2D/D2H 在集成式内存架构上本来就是"从内存搬到内存"的无用功。 | 以为它在所有平台都有效。在独立显卡上零拷贝走 PCIe，**反而更慢**；这是典型的「优化必须跟着硬件架构走」的例子。 |
| double buffering | 双缓冲 | 用两套缓冲区交替，一套在被计算时另一套在被填充。 | 让相机取图与推理重叠，把端到端延迟从"取图 + 推理"降到 `max(取图, 推理)`。 | 以为双缓冲会增加延迟。它增加的是**内存占用**，降低的是延迟；但要注意它让"最新一帧"的语义变复杂。 |
| thread model | 线程模型 | 谁在哪个线程做什么：取图、预处理、推理、后处理、发布。 | 决定了延迟与吞吐的权衡。**单线程串行最简单也最慢，全流水线最快但最难保证一致性**。 | 以为多线程一定更快。跨线程传递 GPU 缓冲区需要同步，**同步开销可能超过并行收益**，小模型上尤其明显。 |

## 六 · 剖析与延迟 · Profiling & Latency

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| warmup | 预热 | 正式计时前先跑若干次，让 kernel 加载、缓存填充、时钟升频完成。 | **没有 warmup 的第一次调用可能比稳态慢 10–100 倍**（cuDNN 算法选择、上下文创建、JIT）。这是"测出来的延迟离谱"的头号原因。 | 以为跑 3 次就够。GPU 从低功耗态升到高频需要几十到几百毫秒，**至少 50–100 次或固定 warmup 时长**才进入稳态。 |
| synchronization | 同步 | 用 `cudaDeviceSynchronize` 或 CUDA event 确保 GPU 真的执行完了再停表。 | kernel 启动是**异步**的：不同步的话，你测的是"提交耗时"而不是"执行耗时"，能测出 0.05 ms 的"推理延迟"。 | 以为 Python 里 `time.time()` 前后夹一下就行。**必须显式同步**；更好的做法是用 CUDA event 打点，避免把 CPU 侧开销算进去。 |
| CUDA event timing | 事件计时 | 在 stream 里插入 event，用 `cudaEventElapsedTime` 测两点间的 GPU 时间。 | 比 wall clock 更准，且不会把 CPU 调度噪声算进去。 | 以为 event 时间就是端到端延迟。它只覆盖**该 stream 内**的工作，预处理（CPU）与跨流等待都不在里面。 |
| p50 / p99 latency | 中位 / 99 分位延迟 | 延迟分布的分位数。 | **车端安全关心的是尾延迟**：p99 超预算意味着每 100 帧丢一帧，而丢掉的那帧往往正是目标最多、最需要看清的那帧。 | 以为均值够用。含 NMS 的方案均值可能很好看，**p99 在密集场景会翻倍**；报均值等于隐藏了最危险的那部分。 |
| jitter | 抖动 | 延迟的波动幅度（p99 - p50 或标准差）。 | 下游的跟踪与融合模块假设固定周期，**抖动会直接变成时间戳误差与位置误差**。 | 以为只要平均帧率够就行。周期性抖动会让融合模块的运动补偿算错，**在高速场景下 10 ms 的抖动就是 0.3 米的位置误差**。 |
| end-to-end latency | 端到端延迟 | 相机出图 → 预处理 → H2D → 推理 → 后处理 → D2H → 下游可用，全程。 | **只报"推理"那一段是最常见的自欺**；预处理与拷贝加起来常占 30% 以上。 | 以为 `trtexec` 报的就是端到端。它默认不含预处理与后处理，**且用的是常驻显存的随机输入**。 |
| H2D / D2H | 主机到设备 / 设备到主机 | CPU 内存与 GPU 显存之间的拷贝。 | 1920×1080×3 的 uint8 图约 6 MB，**在 PCIe 上就是毫秒量级**；检测输出的上万个候选框拷回来也不便宜。 | 以为拷贝可以忽略。在车端 SoC 上它常占端到端的 **20–40%**，而且是最容易通过零拷贝拿回来的那部分。 |
| roofline model | 屋顶线模型 | 以**算术强度**（FLOPs / 访存字节）为横轴、可达性能为纵轴的性能上界模型。 | **把"该减 FLOPs 还是该减访存"变成一道可算的题**：算术强度低于拐点就是访存受限，此时减 FLOPs 毫无用处。 | 以为 roofline 只是画图工具。它给的是**上界与瓶颈判据**，实际性能低于上界还可能是别的原因（占用率、分支发散）——它排除方向，不给最终答案。 |
| arithmetic intensity | 算术强度 | 每读写一字节数据所做的浮点运算数。 | depthwise conv、逐元素算子、concat、reshape 的算术强度都极低，**它们是访存受限的，FLOPs 降一半延迟只降 10%**。 | 以为 FLOPs 就是延迟的代理。现代 GPU 上 FLOPs 与延迟的相关性可能低于 0.5，**必须实测**（C36 详讲机理，C53 从选型角度讲过）。 |
| compute-bound / memory-bound | 计算受限 / 访存受限 | 瓶颈在算术单元还是在内存带宽。 | 判定结果直接决定优化手段：计算受限 → 降精度、用 tensor core；访存受限 → 融合、改布局、减中间张量。 | 以为一个网络整体是一种。**不同层的瓶颈不同**：Conv 主体计算受限、neck 的 concat/upsample 访存受限，要逐层看。 |
| layer-wise profiling | 逐层剖析 | 拿到每一层的实际耗时（`trtexec --dumpProfile` 或 `IProfiler`）。 | 定位瓶颈的第一步。**常见发现是：一个不起眼的 reshape/transpose 占了 15% 的时间**。 | 以为逐层耗时之和等于总时间。融合之后层的边界已经变了，**profile 里的"层"是融合后的层**，与 ONNX 的节点不是一一对应。 |
| Nsight Systems / Compute | 系统级 / 内核级剖析器 | 前者看整条时间线（CPU、GPU、拷贝、流），后者看单个 kernel 的内部指标。 | **Systems 用来找"时间去哪了"（常常是等待和拷贝），Compute 用来找"这个 kernel 为什么慢"**。 | 以为直接上 Nsight Compute。绝大多数车端延迟问题在**时间线层面**就能看出来（同步点、串行化、拷贝没重叠），根本不需要 kernel 级指标。 |
| multi-stream | 多流 | 用多个 CUDA stream 并发执行不同任务。 | 车端多相机场景下，多流能提高 GPU 利用率。 | 以为多流一定降延迟。**多流提高的是吞吐**，单帧延迟可能因资源竞争而上升；车端要的是后者。 |
| batching | 批处理 | 把多路相机的图拼成一个 batch 一次推理。 | 提高吞吐、摊薄 kernel 启动开销。 | 以为 batch 越大越好。**batch 会引入等待**（要等齐所有相机的帧），这段等待时间直接计入端到端延迟；车端常见的是 batch=2~4 的折中。 |
| thermal / power throttling | 温度 / 功耗降频 | 持续高负载下，芯片因温度或功耗上限降低频率。 | **连续跑 30 分钟后的延迟比冷启动漂移 10–30% 很常见**——只测前 100 帧会得出乐观且错误的结论。 | 以为实验室测的数字能代表车上。车内环境温度更高、散热更差，**必须做长时间稳定性（soak）测试并报稳态延迟**。 |
| power mode | 功耗模式 | Jetson/Orin 上的 `nvpmodel` 档位与 `jetson_clocks` 锁频。 | **不锁频的测量结果不可复现**：同一份 engine 在不同档位下延迟能差 2 倍。 | 以为默认档位就是量产档位。量产往往用受限功耗档，**用 MAXN 测出来的数字发出去会被现场打脸**。 |
| preemption / time slicing | 抢占 / 时间片 | 多个进程共享一块 GPU 时的调度方式。 | **TSR 只是众多感知任务之一**（车道线、目标检测、可行驶区域、占用栅格都在抢同一块算力），单独测出来的延迟在整车上不成立。 | 以为"我的模型只要 8 ms 就够了"。整车联跑时排队等待可能让实际延迟翻倍，**必须做整系统联合测量**。 |
| cold start | 冷启动 | 从进程启动到第一帧可用的时间，含 engine 反序列化、显存分配、warmup。 | 车辆上电到感知可用的时间是产品指标；**大 engine 的反序列化可能要几百毫秒到几秒**。 | 以为只有推理延迟重要。冷启动慢会直接影响"上车就能用"的体验，也影响故障后的恢复时间。 |
| peak memory | 显存峰值 | 运行期间显存占用的最大值。 | 车端显存是硬约束且要和其他任务共享；**峰值超了就是崩溃，不是变慢**。 | 以为看稳态占用就行。峰值常出现在**动态 shape 的 max 档或密集场景的 NMS 中间缓冲**，要按最坏情况测。 |
| soak test | 长时稳定性测试 | 连续运行数小时，观察延迟漂移、显存增长、精度是否稳定。 | 抓降频、内存泄漏、缓冲区累积、时间戳漂移——**这些问题在 100 帧的测试里全都看不见**。 | 以为跑通就是稳定。显存泄漏每帧 1 KB，跑 10 小时就是 3.6 GB。 |
| acceptance checklist | 验收清单 | 发布前必须逐项通过的硬性检查。 | 本课模块 05 给出六项：**精度（分场景/分尺寸）、延迟 p99、显存峰值、长时间稳定性、多硬件一致性、回退方案**。 | 以为清单是形式主义。它的真实作用是**把"我觉得可以了"变成"这六项都有数字且都过了"**——同时也是一份能直接讲给面试官听的工程素养证明。 |
| rollback plan | 回退方案 | 新版本出问题时切回旧版本的机制与耗时。 | 车端 OTA 的回退比服务端难得多；**没有回退方案就不该发**。 | 以为回退就是"换个文件"。engine 与硬件绑定、配置与模型版本耦合、下游模块可能依赖新字段，**回退路径必须真的演练过**。 |
