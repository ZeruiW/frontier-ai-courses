1为什么 agent 安全是一个新问题，而不是旧问题的延伸

模型安全（C05）问的是「模型会不会说不该说的话」。对抗攻击（C44）问的是「输入扰动能不能改变模型的判断」。agent 安全问的是第三个问题：当模型能行动时，谁在实际控制这些行动。

聊天模型 Agent ┌────────────────────┐ ┌──────────────────────────────────┐ │ 输入: 用户的话 │ │ 输入: 用户的话 **+ 网页 + 文件 │ │ │ │ + 工具返回 + 其他 agent** │ │ 输出: 一段文字 │ │ 输出: **真实动作**（改文件/发请求 │ │ │ │ /转账/发邮件） │ │ │ │ │ │ 危害上限: 说错话 │ │ 危害上限: **它有权限做的任何事** │ └────────────────────┘ └──────────────────────────────────┘ 关键差别不是"更危险"，而是**输入里混进了不受信任的内容， 而模型无法在结构上区分"用户的指令"和"网页里的一句话"。**

直白说

把这个差别说得再具体一点：传统软件里，「数据」和「代码」是两种东西——SQL 注入之所以能被参数化查询彻底解决，是因为数据库能在结构上分开「这是查询语句」和「这是用户填的值」。而在 LLM 里，两者都是同一个 token 序列，模型没有任何机制去区分。这就是为什么 prompt injection 至今没有「参数化查询」那样的彻底解法。

严谨说

形式化地说，传统系统里存在一个解析边界：输入被解析成一棵语法树，用户数据只能占据叶子节点，无法变成控制节点。LLM 的「解析」是一个连续的注意力过程，不存在这样的结构性分隔——上下文里的任何 token 都可能影响后续生成。因此本课的全部防御思路都不是「消除注入」，而是限制注入成功后能造成的后果——这是一个从「阻止攻击」到「控制爆炸半径」的根本转变，也是理解后面五个模块的关键。

这条要说得非常清楚，因为它决定了你会不会把工程投入放对地方：不存在一个「能挡住 95% 提示注入」的过滤器，能让你安心地给 agent 高权限。剩下的 5% 在一个能自动执行的系统里就足够造成完整的危害，而且攻击者可以针对你的过滤器自适应地调整（05 模块）。正确的投入顺序是：先做权限边界（03 模块）与出站控制（04 模块），再做检测——而不是反过来。

2致命三要素：什么时候一个 agent 是危险的

并不是所有 agent 都有严重的安全问题。判断一个 agent 危不危险，有一个非常实用的三要素判据。

① 接触不受信任内容 （网页 / 邮件 / 用户上传文件 / 第三方工具返回） ╲ ╲ ② 能访问私密数据 ╳ ③ 能对外通信 （你的邮箱/代码库/ ╱ （发请求 / 发邮件 / 写公开位置 数据库/凭证） ╱ / 甚至只是渲染一张外链图片） ╱ **三个同时具备 = 数据外泄的完整链路已经就绪。** 只要缺任意一个，最严重的那类危害就不成立。
配置①不受信内容②私密数据③对外通信风险典型例子
只读摘要器✅❌❌低把网页总结给用户看，无其他权限
内部知识问答❌✅❌低只查内部文档，不接触外部内容
无数据的外呼✅❌✅中可被当成攻击跳板，但泄不了你的数据
邮件助理✅✅✅高读邮件（不受信）+ 有邮箱访问 + 能发邮件
编码 agent✅✅✅高读 issue/依赖（不受信）+ 有代码库与密钥 + 能推送/发请求

这个判据的实用价值在于它给出了明确的设计动作：与其纠结「怎么挡住注入」，不如先问「我能不能把这三个里的某一个去掉」。三者中最容易去掉、也最有效的通常是第三个（对外通信）——把出站限制在白名单内，数据外泄的链路就断了（04 模块）。而这不需要任何检测能力，是一个纯粹的架构决策。

需要补充一点：「对外通信」的定义比直觉宽得多。它不只是「调用 HTTP 接口」——渲染一张外链图片、生成一个可点击链接、写入一个会被别人读到的位置，都是对外通信。04 模块会把这些侧信道逐一拆开。

3信任等级：一个能写进代码的模型

要在工程上管住这件事，需要一个比「可信 / 不可信」更细的模型。本课用一个四级的信任等级，它的关键性质是可传播、可计算。

等级含义典型来源允许触发什么
L3 系统由你部署的、不可被外部影响的内容系统提示、工具 schema、策略文档任何操作
L2 用户来自已认证用户的直接输入用户在对话框里打的字该用户有权做的操作
L1 半可信来自内部系统但可能被间接影响内部数据库里由用户填的字段、内部 wiki读操作；写操作需确认
L0 不受信任何外部内容网页、邮件正文、上传文件、第三方 API 返回、其他 agent 的输出不允许触发任何操作，只能作为「被处理的数据」
\[\text{trust}(\text{输出}) = \min_{i \in \text{上下文}} \text{trust}(i)\]

直白说

这个式子是本课最重要的一条形式化规则，值得念一遍：一次模型调用的输出，信任等级等于它上下文里所有内容的最低等级。只要有一段 L0 的网页内容进了上下文，这次调用的输出就是 L0 的——哪怕系统提示写得再严格。而 L0 的输出不允许触发任何操作。

严谨说

这条规则等价于信息流控制里的no-read-up / no-write-down格结构（Bell–LaPadula 与 Biba 的混合形态）：完整性等级只能单调下降，不能凭空提升。「提升」只能通过一个显式的、被审计的降级/提权点发生——在 agent 系统里，这个点就是人类确认或一个不接触 L0 内容的独立验证器。notebook 第 2 节会把这条规则写成代码并验证它的传播行为。

这条规则最反直觉、也最容易被违反的推论：「让模型自己判断这段内容可不可信」是无效的——因为做这个判断的那次调用，它的上下文里就包含了那段不可信内容，所以它的判断本身也是 L0 的。不可信内容不能被用来判断它自己是否可信。这不是模型能力问题，是结构问题。

4攻击面地图：六个入口

把 agent 的输入侧展开，一共有六类不受信任的内容入口。本课后面五个模块基本就是沿着这张图展开的。

┌─────────────────────────── AGENT ────────────────────────────┐ │ │ │ ① 用户输入 直接注入（越狱、角色扮演） → C05 覆盖 │ │ ② 检索/浏览内容 **间接注入**（网页、文档、邮件）→ 01 模块 │ │ ③ 工具的返回值 被污染的 API 响应 → 01/02 │ │ ④ 工具的**描述** 工具 schema 投毒、工具影子 → 02 模块 │ │ ⑤ 其他 agent 的输出 多智能体间的注入传播 → 02 模块 │ │ ⑥ 记忆/历史 持久化注入（写进长期记忆） → 01 模块 │ │ │ └──────────────────────────────────────────────────────────────┘ │ │ ▼ ▼ 权限边界（03 模块） 出站通道（04 模块）
入口为什么容易被忽略本课哪里讲
② 检索/浏览内容最主流的入口，但很多系统把它当成「数据」而没有降级信任01 模块
③ 工具返回值开发者倾向于信任「自己调的 API」，但 API 返回的内容可能来自外部01 模块
④ 工具描述schema 与描述文本也进上下文——一个第三方工具的 description 字段就是一条注入通道02 模块
⑤ 其他 agent 的输出编排系统里子 agent 的返回被当成可信，但子 agent 可能读过网页02 模块
⑥ 记忆注入可以被持久化：这次读到的恶意内容被写进长期记忆，影响以后所有会话01 模块

第 ⑥ 项是危害持续时间最长的一类，值得单独警惕：如果 agent 有长期记忆，一次成功的注入可以变成永久的后门。攻击者只需要让 agent 读一次被污染的内容，而恶意指令被写进记忆之后，后续每一次会话都会加载它——而且此时上下文里已经看不到原始的攻击内容了，排查会非常困难。所以记忆的写入必须遵守第 3 节的信任规则：L0 内容不允许直接进入长期记忆。

6环境、依赖与本课的运行约定

本课全程 CPU、断网可跑、不需要任何 API key，而且有一条比前几课更重要的约定需要说明。

本课的 notebook 里不包含针对任何真实系统的可用攻击载荷。所有的「攻击」都是在一个本地的、完全模拟的 agent 上进行的：被攻击的 agent 是一个几十行的规则匹配器，「注入内容」是形如 [[INJECT:read_secret]] 的占位符标记。这样做不是为了回避，而是因为它更适合教学——你要学的是「信任等级怎么传播」「权限边界怎么设计」「攻击成功率怎么统计」这些结构性的东西，而这些东西用模拟器验证得更清楚、更可复现。真实的注入手法在讲解里以机制层面描述（足以让你设计防御），不给可直接复制的载荷。
  • 模拟 agent：一个可控的执行器，它会「服从」上下文里的指令标记——服从概率是一个可调的旋钮，让你能研究「防御把成功率从 40% 降到 8%」这类定量问题；
  • 可注入的内容源：模拟网页/邮件/工具返回，可以插入指令标记；
  • 权限系统与出站控制：真实实现（能力检查、白名单、审计日志），因为这些本来就不需要真实模型；
  • 真实工程胶囊：把防御机制落到真实系统的代码（工具权限声明、出站代理配置、审计埋点、AgentDojo 类基准的接入）。

7防御姿态：三条排序原则

最后给出本课的整体主张，它决定了后面五个模块的顺序。

  1. 架构 > 检测。去掉「致命三要素」里的一个，比训练一个更好的注入分类器有效得多，而且它的效果不依赖于攻击者的水平。先做权限与出站，再做检测。
  2. 假设注入会成功，设计爆炸半径。所有的防御目标不是「让注入失败」，而是「注入成功之后，攻击者能做的最坏的事是什么」。这个问题有确定的答案（= agent 的权限集），而且可以被系统性地缩小。
  3. 可逆操作与不可逆操作分开对待。读文件、查数据可以自动做；发邮件、转账、删除、推送代码必须有一个不接触 L0 内容的确认环节。这条与 C66 模块 05 的「失败代价高时，加人工确认点比提分更划算」是同一条结论，只是这里的「失败」是被攻击。

直白说

为什么把「架构」排在「检测」前面？因为两者的失败模式完全不同。检测失败是概率性的、且随攻击者水平变化——你今天挡住了 95%，明天有人换个写法就绕过了。而架构约束是确定性的：如果 agent 在结构上没有发邮件的能力，那么无论注入写得多巧妙，它都发不出邮件。

严谨说

用形式化的话说：检测提供的是概率性保证（$\Pr[\text{阻止}] = 1 - \text{绕过率}$，而绕过率对自适应攻击者没有下界），架构提供的是不变量（某类动作在系统中不可达，与攻击者能力无关）。安全工程的基本原则是：能用不变量保证的，就不要用概率保证。检测的正确定位是「减少噪声、提供告警信号」，而不是「作为主要防线」。

把这三条压成一句可以贴在墙上的话：不要问「怎么挡住提示注入」，要问「注入成功之后它能做什么，以及我怎么把那个集合缩小」。
