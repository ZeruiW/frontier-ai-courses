1安全评测与能力评测的四个结构性差别

C66 讲的是能力评测。安全评测复用它的全部统计工具，但有四个结构性差别，每一个都会改变方法。

维度能力评测安全评测后果
被测对象会不会对抗你不会（任务集是固定的）会——攻击者会针对你的防御调整静态基准的分数系统性高估防御效果
成功的定义完成任务攻击者达成目标（且通常有多条路径）判分需要枚举「所有算成功的终态」
关心分布的哪一端平均表现最坏情况——攻击者只需成功一次均值几乎没有意义，要看 ASR@k 与尾部
基率任务集里正例比例可控真实流量里攻击极罕见误伤的绝对量主导（模块 01 第 6 节）

直白说

第一行是全部差别的根源。能力评测里，「在这个任务集上得 42%」是一个关于模型的稳定事实；安全评测里，「在这个攻击集上防住了 95%」只是一个关于这批攻击的事实，而攻击集会因为你的防御而改变。

严谨说

形式化地说，能力评测估计的是 $\mathbb{E}_{x \sim D}[s(x)]$，其中 $D$ 固定；安全评测要估计的是 $\max_{a \in \mathcal{A}} \Pr[\text{success}(a)]$——一个对攻击空间取上确界的量。而任何固定的攻击集 $A_0 \subset \mathcal{A}$ 给出的都只是一个下界：$\max_{a \in A_0} \le \max_{a \in \mathcal{A}}$。所以静态基准报出的 ASR 是真实 ASR 的下界，而报出的防御成功率是真实防御成功率的上界——两个方向都是「让你看起来更安全」。

这条要说得非常直白，因为它是本模块的核心：「我们在 XX 注入基准上防住了 95%」这句话，在没有说明攻击者是否针对你的防御适配过时，所提供的保证接近于零。而这不是一个理论上的顾虑——对抗鲁棒性领域已经反复出现过「静态基准上很强、自适应攻击下几乎无效」的防御，而 agent 安全的评测方法学目前还远不如那个领域成熟。

2ASR 的三个口径：它们回答不同的问题

攻击成功率（attack success rate, ASR）是安全评测的主指标，但它至少有三个口径，混用会得出矛盾的结论。

\[\text{ASR}_{\text{per-attempt}} = \frac{\#\{\text{成功的尝试}\}}{\#\{\text{全部尝试}\}}, \quad \text{ASR@}k = \Pr[\text{k 次尝试中至少成功一次}], \quad \text{ASR}_{\text{per-target}} = \frac{\#\{\text{被攻破的目标}\}}{\#\{\text{全部目标}\}}\]
口径定义回答什么问题什么时候用它是错的
per-attempt成功尝试 / 全部尝试「单次攻击的成功概率」用来判断「系统安不安全」——因为攻击者可以多试
ASR@k$1-(1-p)^k$ 的无偏估计（k 次预算）「给攻击者 k 次机会，他能成功吗」不写明 k；不同 k 下的 ASR 完全不可比
per-target被攻破的目标 / 全部目标「有多少个场景/任务是可被攻破的」把「难攻破的目标」和「容易攻破的目标」混成一个数

三者的关系与 C66 模块 04 的 pass@k vs pass^k 完全同构，只是方向相反：能力评测里我们关心「至少成功一次」是好事，安全评测里「至少成功一次」是坏事。所以安全评测的默认口径应当是 ASR@k，而 k 取「一个真实攻击者能负担的尝试次数」——而这个数通常很大（自动化脚本可以试几千次）。

为什么 per-attempt 会严重误导

举一个具体的算术：单次 ASR 只有 1%，听起来防得很好。

  • 攻击者试 100 次：$1 - 0.99^{100} = 63\%$；
  • 试 500 次：$92\%$；
  • 试 1000 次：$99.996\%$。

而「试 1000 次」对一个自动化脚本是几分钟的事。所以报告 per-attempt ASR 时必须同时给出「攻击者需要试多少次才有 50% 概率成功」这个数——它比百分比直观得多，而且它直接对应攻击者的成本。

\[k_{50} = \frac{\ln 0.5}{\ln(1 - p)} \approx \frac{0.693}{p} \quad (\text{小 } p)\]

3自适应攻击：静态基准为什么系统性高估防御

第 1 节说过静态基准给出的是下界。这一节讲清楚差距有多大，以及为什么。

静态评测 自适应评测 ┌─────────────────────────┐ ┌──────────────────────────────┐ │ 固定的 200 条攻击载荷 │ │ 攻击者**知道你的防御**： │ │ （在防御上线**之前**收集）│ │ · 系统提示写了什么 │ │ │ │ · 检测器用什么模式 │ │ 跑一遍 → ASR = 4% │ │ · 白名单里有哪些域名 │ │ → "防住了 96%" │ │ 针对性构造 → ASR = 40%+ │ └─────────────────────────┘ └──────────────────────────────┘ ▲ ▲ 问题：这 200 条载荷是针对**没有防御的系统**设计的。 你的防御恰好挡住了它们，这几乎是必然的—— 因为你就是看着它们来设计防御的。

直白说

这里有一个很容易被忽略的循环：如果你用基准 $A_0$ 来指导防御设计，那么在 $A_0$ 上测出的效果就是训练集上的效果。它与「对新攻击的效果」的关系，和机器学习里训练误差与泛化误差的关系一样——而在安全场景里，「测试分布」是由一个主动优化的对手生成的，所以这个差距比普通的过拟合大得多。

严谨说

更精确地说，安全评测面对的是一个最小最大问题：$\min_{d \in \mathcal{D}} \max_{a \in \mathcal{A}} \Pr[\text{success}(a, d)]$。而静态基准把内层的 $\max$ 换成了在固定集合 $A_0$ 上的 $\max$，这是一个严格宽松的松弛。更糟的是：如果 $d$ 是在 $A_0$ 上选出来的，那么 $\max_{a \in A_0}$ 甚至不是 $\max_{a \in \mathcal{A}}$ 的一个无偏下界，而是一个被系统性压低的下界——这与 C66 模块 04 的胜者诅咒是同一个结构。

怎么做自适应评测：四条最低要求

  1. 攻击者必须知道防御的细节（白盒假设）——包括系统提示、检测器的模式、白名单内容。「攻击者不知道我们的 prompt」不是一个可依赖的假设（它会通过输出泄漏、通过内部人员泄漏、通过反复试探被推断出来）；
  2. 攻击者有一个明确的预算（尝试次数、时间、可控制的内容量），而结果按预算报告（ASR@k）；
  3. 攻击是分轮的：防御方改进 → 攻击方重新适配 → 再测。只有一轮的评测无法区分「防住了」与「这批攻击恰好被挡住了」；
  4. 留一部分攻击不用于防御设计（留出集）——这是把「训练误差」与「泛化误差」分开的最低手段，虽然它仍然不等于自适应攻击。

第三条在实践中最难做，因为它需要一个愿意持续投入的攻击方。一个务实的折中：把「攻击方」定义为一个明确的角色与流程，而不是一次性的活动——每次防御变更后，攻击方有固定的预算去尝试绕过，而绕过成功的样本进入回归集（第 6 节）。这样至少保证了「防御的每一次变更都被针对性测试过一轮」。

4防御的可组合性：单独有效 ≠ 组合有效

模块 01–04 给了很多防御。一个自然的假设是「多做几层更安全」。这个假设大体成立，但有三种它不成立的情形，而它们都很常见。

情形机制例子怎么发现
共享失效模式两层防御依赖同一个前提，前提被打破则同时失效注入检测器与输出剥离都基于「能正确解析文本」——而编码变体同时绕过两者检查每层依赖的前提，看有没有重叠
一层削弱另一层为了让 A 工作，放宽了 B为了让检测器能看到内容，把不受信内容解码后放进上下文——反而扩大了注入面变更影响面分析（模块 03 第 7 节）
组合产生新通道两个单独安全的能力，组合出一条新路径「读工作目录」+「写工作目录」+「工作目录被外部同步」= 外泄通道危险组合枚举（模块 02 第 5 节）

第三行的例子值得展开，因为它在真实系统里非常常见：agent 只有读写工作目录的权限（看起来完全安全），而工作目录恰好是一个被同步到云端的文件夹。于是「写文件」变成了一条出站通道，而它不在任何权限声明里。这类问题只能通过「枚举系统的可达性图」发现，而不是通过检查每个组件的安全性（模块 04 第 1 节的同一条结论）。

可组合性检验：一个可执行的做法

逐一关闭每一层防御，测量 ASR。这能得到两组信息：

  • 每层的边际贡献：关掉它，ASR 涨多少。边际贡献接近零的层，要么是冗余的，要么它依赖的前提已经被别的层保证了；
  • 共享失效模式：如果同时关掉 A 和 B 的 ASR 涨幅远大于各自单独关掉的涨幅之和，说明它们互补；如果远小于，说明它们依赖同一个前提（冗余）。
\[\text{互补性} = \text{ASR}(\overline{A}\overline{B}) - \text{ASR}(\overline{A}) - \text{ASR}(\overline{B}) + \text{ASR}(\text{全开})\]

这个量就是二阶交互项。它显著为正 = 两层互补（一起关掉才崩）；显著为负 = 两层冗余（关一个另一个就顶上了）。notebook 第 4 节会把这个矩阵算出来。

5判分：安全评测的「成功」比能力评测难定义得多

C66 模块 02 讲过判分器的重要性。在安全评测里这个问题更难，因为「攻击成功」通常有多条路径，而且部分成功也算成功。

四类判分方式

方式怎么判适用问题
目标状态断言「攻击者的邮箱收到了包含密钥的邮件」最可靠——可程序化验证需要为每个攻击目标写断言
动作序列匹配「agent 调用了 send_email 且收件人在攻击者域名下」可靠会漏掉「用别的通道达成同一目标」（模块 04 的十种通道）
信息泄漏检测在所有出站内容里搜索金丝雀值覆盖多通道需要预先埋金丝雀；编码变体要先解码（模块 04 第 5 节）
LLM judge让模型判断「这次交互是否被劫持」覆盖面最宽C67 的全部问题都适用，且 judge 自己可能被同一段内容注入

最后一行有一个安全评测特有的陷阱：如果用 LLM judge 来判断「这次注入成功了吗」，而 judge 的上下文里包含了那段注入内容，那么攻击者可以同时攻击 judge。这与模块 00 第 3 节的自检悖论是同一件事——判分器必须只看「动作与终态」，不看注入原文；或者用一个只接触结构化事实的判分器。

金丝雀值：覆盖多通道的最实用手段

在 agent 可访问的私密数据里埋入唯一的、高熵的标记值，然后在所有出站内容（HTTP、邮件、DNS 查询、渲染请求、写入的文件、甚至给用户看的输出）里搜索它。

  • 优点：一次埋设覆盖模块 04 的全部十种通道；而且它是确定性判分——命中就是泄漏了，没有歧义；
  • 必须做的一步：搜索前先解码（base64/hex/URL/零宽字符），否则编码后的金丝雀会被漏掉；
  • 要埋多个不同的金丝雀，对应不同的敏感度级别与不同的数据位置——这样你能知道「泄漏了什么」而不只是「泄漏了」；
  • 金丝雀本身不能太可疑——如果它长得像 CANARY_DO_NOT_LEAK_12345，一个稍微聪明的攻击就会避开它。它应当看起来像真实数据。

6红队：怎么组织，以及产出该长什么样

前五节讲测量。这一节讲攻击从哪来——因为自适应评测（第 3 节）需要一个持续的攻击方。

来源覆盖面成本适合发现什么
已知手法库窄（已公开的模式）极低回归——确保修过的问题不复发
自动化变异中（在已知手法上做编码/改写/组合变换）低检测器的绕过（编码变体、同义改写）
内部红队宽（懂你的系统）高架构层的漏洞——白名单里的可写目标、被同步的工作目录
外部红队 / 漏洞赏金最宽高你没想到的攻击面

四者的分工很清晰：已知手法库做回归（每次提交都跑），自动化变异做检测器的压力测试（每日），内部红队做架构评审（每次重大变更），外部红队做兜底（定期）。而其中最容易被跳过、也最有价值的是第三项——因为架构层的漏洞（模块 04 第 1 节那种「工作目录被同步」）只有懂系统的人才能发现，而自动化工具永远发现不了。

红队产出的结构化：让它能进回归集

红队最大的浪费是产出无法复用。一次红队活动发现了十几个问题，写成一份 PDF 报告，三个月后没人记得哪些修了、哪些复发了。

// 每一个红队发现都应当是一条可自动重跑的记录
{
  "id": "rt-2026-0142",
  "found_by": "internal-redteam", "found_at": "2026-08-15",
  "attack_class": "indirect_injection_via_tool_description",   // 归类，用于去重
  "target_capability": "send_email",                           // 攻击目标
  "entry_point": "tool_description",                           // 六个入口之一（模块 00）
  "budget_used": {"attempts": 12, "minutes": 40},               // 攻击成本
  "defenses_bypassed": ["sys_prompt_ignore", "injection_detector"],
  "defenses_that_held": ["egress_allowlist"],                   // ← 同样重要
  "repro": {"kind": "scripted", "path": "redteam/rt-0142.py"},  // **可自动重跑**
  "success_criterion": {"kind": "canary", "value_id": "canary-3"},
  "status": "fixed", "fixed_by": "PR-8821", "fix_kind": "architecture",
  "regression_added": true
}
  • defenses_that_held 与 defenses_bypassed 同样重要——它告诉你哪一层真正起了作用（第 4 节的边际贡献）；
  • fix_kind 要区分 architecture / detection / prompt——如果修复清一色是 detection，说明你在用概率保证承担不变量的职责（模块 00 第 7 节）；
  • budget_used 是攻击成本的直接度量——防御的目标之一就是把这个数推高；
  • repro 必须是可自动重跑的，否则它进不了回归集，而进不了回归集的发现必然会复发。
