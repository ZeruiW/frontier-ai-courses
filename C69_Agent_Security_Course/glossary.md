# 术语词典 · Glossary（Agent 安全与提示注入）

> 按主题分组。每条给出：**英文 / 中文 / 一句话定义 / 为什么重要 / ⚠️ 常见误解**。
> 组织原则是本课的主线：**威胁模型 → 注入 → 供应链 → 权限 → 外泄 → 评测**。
> 与相邻课程的分工见 [README](README.md)：越狱在 C05，对抗样本在 C44，
> 训练期隐私在 C45，评测统计规范在 C66。**本课只管「agent 会做什么」。**

## 一 · 威胁模型 · Threat Model

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| prompt injection | 提示注入 | 上下文里的不受信内容改变了模型的行为目标。 | 它与 SQL 注入的关键差别是**没有解析边界**：LLM 的上下文是扁平的 token 序列，「谁在说话」只是序列里的一些普通 token。 | 以为它是一个可以被过滤器解决的问题。**不存在一个「挡住 95%」的过滤器能让你安心给 agent 高权限**——剩下的 5% 在自动执行的系统里就足够造成完整危害。 |
| indirect prompt injection | 间接提示注入 | 注入来自 agent 读取的内容（网页/邮件/文件/工具返回），而不是用户输入。 | 它是 agent 场景的主要攻击面，而且**攻击者与用户是不同的人**——用户完全无辜。 | 把它与越狱混为一谈。越狱是用户想让模型说不该说的话（C05）；间接注入是第三方想让 agent 做不该做的事。 |
| lethal trifecta | 致命三要素 | 不受信内容 + 私密数据 + 对外通信，三者齐备则外泄链路完整。 | 它把「这个 agent 危不危险」变成一个三个布尔值的判断，并给出明确的设计动作。 | 以为要同时防三个。**去掉任意一个都能把风险从 HIGH 降下来**，而第三个（对外通信）通常最容易去掉。 |
| trust level | 信任等级 | L3 系统 / L2 用户 / L1 半可信 / L0 不受信。 | 它让「这段内容能不能触发动作」变成一个可计算的判断。 | 只分「可信/不可信」两档。四档的价值在于 L1 的存在——内部系统里由用户填的字段既不是 L2 也不该是 L0。 |
| trust propagation | 信任传播 | `trust(输出) = min(上下文)`，且只能单调下降。 | **全课最重要的形式化规则**，等价于信息流控制里「完整性等级只能单调下降」。 | 以为「换一次调用」或「总结一遍」能洗掉污染。**单调性证明了不能**——L0 一旦进上下文，所有派生内容都是 L0。 |
| self-check paradox | 自检悖论 | 「让模型判断这段内容可不可信」在结构上无效。 | 做这个判断的那次调用，上下文里就含有那段不可信内容，**所以判断本身也是 L0 的**。 | 以为这是模型能力问题（「更强的模型就能识别了」）。**它是结构问题**：不可信内容不能被用来判断它自己是否可信。 |
| elevation point | 提权点 | 唯一允许提升信任等级的地方：人类确认，或一个不接触 L0 内容的验证器。 | 把提权变成一个显式、可审计、可 grep 的操作。 | 在代码里随手赋值提升等级。**每一处手工提权都是一个需要 review 的漏洞候选**。 |
| invariant vs probabilistic guarantee | 不变量 vs 概率保证 | 前者是「某类动作不可达」，后者是「大概率不会发生」。 | **检测的绕过率对自适应攻击者没有下界**，而不变量与攻击者水平无关。 | 以为堆足够多层检测等于不变量。notebook 算过：靠堆检测层达到高保证需要很多层，每层都有误伤成本，而一个架构约束直接归零。 |

## 二 · 注入机制与缓解 · Injection & Mitigation

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| soft prior | 软先验 | 系统提示改变生成分布，但不改变可达状态空间。 | 它解释了为什么「忽略文档里的指令」有效但不够——它与攻击者的文本在竞争注意力，而不是管辖对方。 | 因为「没用」就不写。**它能把 ASR 降一个多量级**，在减少偶发事故上有实际价值；错的是把它当主要防线。 |
| invisible injection vector | 不可见注入向量 | HTML 注释、`display:none`、alt 文本、meta 描述、PDF 白字。 | **模型读到的文本与人看到的页面不是同一个东西**。 | 以为「让人先看一眼」是防御措施。notebook 里五条注入全藏在人看不见的位置。 |
| ingest boundary | 统一入口 | 所有外部内容必经的一个函数，**无条件**标成 L0。 | 信任降级集中在一处就不可能被漏掉。 | 留例外（「这个来源比较可信」）。**任何例外都会变成半年后的漏洞**。 |
| dual LLM pattern | 双 LLM 模式 | 隔离 LLM 接触 L0 但无权限，特权 LLM 有权限但只看结构化输出。 | 它把注入能传递的信息量限制在 $\log_2\|S\|$ 比特——**这是不变量而非概率保证**。 | 在 schema 里留一个自由文本字段（`summary: str`）。**容量瞬间变成无穷，整个模式失效**——而这个字段看起来无害且产品很想要。 |
| narrow interface | 窄接口 | 受严格 schema 约束（枚举/数值/布尔）的通信接口。 | 它是「agent 之间是不是真的有边界」的判据。 | 以为「子 agent」本身就是边界。**自由文本的 agent 间通信等价于把两个上下文合并**。 |
| persistent injection | 持久化注入 | 注入被写进长期记忆、缓存、配置或任务队列。 | 一次污染变成长期后门，而**排查时原始的攻击上下文已经不在了**。 | 只防「当次会话」。队列型最隐蔽：注入不必立刻造成危害，只需往队列里放一件事，消费时它看起来像系统自己产生的合法工作。 |
| detection asymmetry | 检测的不对称 | 基率极低（正常内容远多于攻击）+ 攻击者只需成功一次。 | 召回 99%/误伤 1%、且基率约 $10^{-4}$ 时（100 万条正常内容里 100 次攻击），误伤的绝对量是拦住的攻击的一百倍以上——这个倍数由基率决定，光看两个率算不出来。 | 以为提高召回就够了。**攻击者只需成功一次，你需要每次都挡住**——所以检测的定位是告警+降级，不是拒绝。 |
| intent-action consistency | 意图-动作一致性 | 比较「用户请求的意图」与「待执行的动作」。 | 误伤率极低，**而且它的输入里没有 L0 内容**——所以它的判断可以被信任。 | 与「判断内容像不像注入」混为一谈。后者落入自检悖论，前者不落入。 |

## 三 · 工具与供应链 · Tools & Supply Chain

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| tool description as prompt | 描述即 prompt | 工具的 `description` 与系统提示处于同一上下文、拥有同等结构地位。 | 一个第三方 server 的描述字段就是一条注入通道。 | 把 schema 当「接口定义」（编译期的东西）。**在 LLM 里它是运行时的 prompt**。 |
| nested description blind spot | 参数说明盲区 | 参数的 `description` 逐个进上下文，但几乎从不被逐个审阅。 | notebook 里那个投毒工具的**主描述完全正常**，注入全在参数说明里——只扫顶层会漏掉 100%。 | 审计时只看顶层那一段。必须**递归**覆盖所有嵌套的 description。 |
| tool shadowing | 工具影子 | 恶意工具通过同名覆盖、近似名、或描述劫持来替代合法工具。 | 平铺的注册表让「谁覆盖谁」由加载顺序决定。 | 以为它需要复杂手段。**在配置文件里把一个 server 往上挪一行**就是一次安全变更——而它看起来像格式整理。 |
| namespacing | 命名空间 | `server_id::tool_name` + 注册时冲突报错。 | 让同名覆盖在结构上不可能发生。 | 以为它解决了全部三种影子形态。**它解决不了描述劫持**（没有名称冲突），那只能靠描述审计 + 工具集最小化。 |
| tools lock | 工具清单锁 | 钉住工具清单的**内容哈希**（name + 全部 description + params + requires）。 | 工具是运行时从服务端拉取的，**服务端可以在不改版本号的情况下返回不同描述**。 | 以为钉死版本号就够了。软件包生态有 lockfile 与内容哈希，而工具生态没有——所以必须自己钉内容。 |
| rug pull | 抽地毯 | 一个已被审阅批准的依赖在之后变成恶意的。 | 在工具生态里它更快（无需发包，改服务端即可）。 | 以为「审过一次就安全」。校验必须发生在**每次启动**，不一致就拒绝启动（不是 warning）。 |
| permission aggregation | 权限聚合 | 编排层持有所有子 agent 权限的并集。 | 两个各自都不构成外泄链路的子 agent，**并集构成链路**。 | 以为编排层需要底层权限。**它只需要「调用子 agent」的权限**——这是最有效的一条设计变更。 |
| danger pair | 危险组合 | (能读私密的工具 × 能对外通信的工具) 的笛卡尔积。 | 危险不来自单个工具而来自组合，且它随 server 数**乘性**增长。 | 把「装很多 server」当便利性决策。**它是安全决策**：人工审阅能力是线性的，而组合数是乘性的。 |

## 四 · 权限与沙箱 · Permissions & Sandboxing

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| capability (four dimensions) | 能力四维 | 操作 / **范围** / 信任门槛 / 可逆性。 | 四条**合取** → 四个独立的收紧点，任一条不满足动作就不可达。 | 只做第一维（「有没有这个工具」）。**「范围」这一维最常被忽略也最有效**：把「读文件」收窄成「读工作目录」就把「读 `~/.ssh/`」变成不可达。 |
| scope check | 范围检查 | 限制能力作用于哪些对象（路径、域名、收件人）。 | 它是把「操作」变成「不可达」的最便宜手段。 | 用 `startswith` 做路径检查。**会被两类输入绕过**：`..` 穿越与同前缀目录（`/workspace_other`）——必须先规范化再比，且比较时要加分隔符。 |
| least privilege (computed) | 可计算的最小权限 | 任务每一步实际需要的能力的并集。 | 它把「最小权限」从口号变成一个可解的问题。 | 按角色授予。**角色是按人设计的，而 agent 的任务粒度比人细得多**——notebook 里按角色授予会过授几倍，并把 `read_home` 这个「读 `~/.ssh/`」的入口给出去。 |
| sandbox boundary | 沙箱的边界 | 沙箱隔离**代码执行的副作用**，不隔离被授权的 API 调用。 | 后者是「合法」调用，沙箱不会拦——**而 agent 的主要能力正来自它们**。 | 以为强沙箱能降低「拿着 token 去发邮件」的风险。所以权限边界通常比沙箱更重要。 |
| credentials outside sandbox | 凭证不进沙箱 | agent 调 API 时经过持有凭证的代理，沙箱内只有短期窄 scope 令牌。 | **能把「凭证泄漏」这类最严重的后果直接消除**。 | 觉得实现太麻烦。它是 OAuth token exchange 的标准思路，收益远大于成本。 |
| confirmation fatigue | 确认疲劳 | 确认频率上升 → 人不看内容直接点同意 → 确认从防线退化为一次点击。 | notebook 的模拟：每小时 1 次确认拦住 87%，每小时 60 次只拦住 8%。 | 以为「给所有操作都加确认」更安全。**更不安全**——目标是提高每次确认的**基率**而不是频率。 |
| TOCTOU | 检查时/使用时不一致 | 人确认的动作与实际执行的动作不是同一个。 | 参数重取、状态漂移、批量确认、确认复用四种形态都真实存在。 | 以为「弹了确认就安全」。修法是三条同时做：**frozen 的动作对象 + digest 校验 + 令牌一次性**。 |
| open-ended batch grant | 开放式批量授权 | 「不要再问我了」，而范围由后续动作自己解释。 | 攻击者只需让第一次操作看起来无害。 | 以为批量授权不可避免。**它必须绑定范围 + 会话 + 次数上限**：「本会话内向 `*@corp.test` 发邮件不再询问，最多 20 次」。 |
| provenance | 来源链 | 一个动作是被哪些内容（各自什么信任等级）触发的。 | **审计记录里唯一无法事后补上的字段**——其余都能从配置和代码重建。 | 以为记了「谁执行了什么」就够了。事故复盘时最需要的恰恰是「这个动作是被哪一段内容触发的」。 |

## 五 · 数据外泄 · Exfiltration

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| render side channel | 渲染侧信道 | agent 输出一个外链图片/iframe，客户端渲染时自动发起请求。 | **只需要「能输出文本」**——不需要网络权限、不需要任何工具。 | 以为「没给网络权限就泄不了」。这个通道完全不在 agent 的权限模型里，因为渲染发生在客户端。 |
| DNS side channel | DNS 侧信道 | 把数据编码进子域名，权威 DNS 服务器就收到了。 | 带宽约 100 字节/次，但**极难封堵**（沙箱默认放通 DNS，否则什么都跑不起来）。 | 以为 HTTP 层的白名单能防它。封它的唯一办法是**固定的内部解析器 + 只解析白名单域名**。 |
| chunked exfiltration | 分块外泄 | 把数据切成多次请求发出。 | 它让「单次带宽上限」失去意义：4KB 私钥用 100 字节/次也只需 41 次。 | 靠「限制单次请求大小」防外泄。**几乎没有防御价值**——有价值的是限制目标（白名单）与总量（预算）。 |
| egress allowlist | 出站白名单 | 只允许连接白名单内的目标。 | **本课唯一的网络层不变量**：它不判断内容只判断目标，攻击者换说法无效。 | 以为配好白名单就完事。**四类绕过**：重定向、DNS 侧信道、白名单内攻击者可控的接收端、SSRF。 |
| attacker-controllable endpoint | 可控接收端 | 白名单里的一个域名，攻击者能在其下控制一个接收数据的地方。 | 最隐蔽的一类绕过：把公开代码托管站加进白名单（因为要装依赖），而任何人都能在上面创建仓库。 | 只审「这个域名可信吗」。要审的是「**攻击者能否在这个域名下控制一个接收数据的地方**」。 |
| leakable volume | 可泄漏量 | $\le \min(R \cdot T \cdot B,\ V)$。 | **$V$（能读到的数据）是唯一有硬上界的项**——其余三项只能拖慢。 | 以为限速能减少泄漏总量。notebook 算过：常驻一个月后，降速的效果完全消失。 |
| rate limit (as detector aid) | 速率限制的真实作用 | 它把外泄从「一个大请求」推成「向同一目标的高频小请求」。 | **后者在正常流量里罕见得多**——所以速率限制与监控是配套的。 | 以为它是独立的防御。它本身不阻止外泄，它把攻击推入检测器的视野。 |
| decode-before-scan | 先解码再扫 | NFKC 规范化 → 剥零宽字符 → URL 解码 → base64/base32/hex 试解 → 再匹配。 | **DLP 能不能工作的前提**：不解码时，编码后的密钥全部漏掉。 | 以为是优化。notebook 里不解码时只有明文那一个被抓到。 |
| known-secret exact match | 已知秘密精确匹配 | 直接用你自己密钥的真实值做字符串匹配。 | **最容易做、效果最好、却最少被做**：不需要模式识别、不需要模型，误伤接近零、召回接近 100%。 | 觉得太简单所以没价值。它同时覆盖了「密钥被编码后外泄」（只要先解码）。 |

## 六 · 安全评测 · Security Evaluation

| 术语 (EN) | 中文 | 一句话定义 | 为什么重要 | ⚠️ 常见误解 |
|---|---|---|---|---|
| ASR (attack success rate) | 攻击成功率 | 至少三个口径：per-attempt / ASR@k / per-target。 | 混用会得出矛盾的结论。 | 用 per-attempt 判断「系统安不安全」。**攻击者可以多试**：单次 1% 时 $k_{50}=69$ 次，一个脚本几秒钟就试完。 |
| ASR@k | 预算内的攻击成功率 | k 次尝试至少成功一次的概率。 | **安全评测的默认主指标**，且 k 必须写明。 | 不写明 k。不同 k 下的 ASR 完全不可比。 |
| $k_{50}$ | 半数成功所需尝试数 | $\ln 0.5 / \ln(1-p)$。 | **最可沟通的那个数**：「攻击者花 $0.14、17 秒就能成功」比「ASR 是 1%」有意义得多。 | 以为百分比更专业。对非技术读者，成本比概率直观。 |
| adaptive attack | 自适应攻击 | 攻击者知道防御细节并针对性构造。 | 安全评测要估计的是**攻击空间上的上确界**，而固定攻击集只给出下界。 | 假设「攻击者不知道我们的 prompt」。它会通过输出泄漏、内部人员、反复试探被推断出来。 |
| static benchmark bias | 静态基准的偏倚 | 静态 ASR 是真实 ASR 的下界，静态防御率是真实防御率的上界。 | **两个方向都是「让你看起来更安全」**。 | 引用静态数字做决策。而如果防御是看着这个基准设计的，它甚至是一个被系统性压低的下界（胜者诅咒）。 |
| degradation multiple | 退化倍数 | 自适应 ASR / 静态 ASR。 | 它诊断「你的拦截有多少来自概率性的层」。 | 以为加架构层能降低这个比值。**退化倍数主要由非架构层决定**——架构层若对静态与自适应攻击的拦截比例相同，就等比例压低两者、降低绝对风险而不改变比值；但自适应攻击者会集中攻击残余通道，所以实际往往把比值推高。两个数要一起看。 |
| marginal contribution | 边际贡献 | 关掉某一层，ASR 涨多少。 | 它暴露「防御堆了很多层但都在同一层」。 | 看每层的「静态拦截率」。检测层的静态拦截率看起来更高，但边际贡献远小于架构层。 |
| second-order interaction | 二阶交互项 | $\text{ASR}(\bar A\bar B) - \text{ASR}(\bar A) - \text{ASR}(\bar B) + \text{ASR}(\text{全开})$。 | 正 = 互补，负 = 冗余。 | 只算交互项。**还要检查每层依赖的前提有没有重叠**——「注入检测器」与「输出剥离」在纸面上是两层，在失效模式上是一层。 |
| canary value | 金丝雀值 | 埋在私密数据里的唯一高熵标记，在所有出口搜索它。 | **一次埋设覆盖多种通道，且判分是确定性的**（命中就是泄漏）。 | 让它长得像 `CANARY_DO_NOT_LEAK_12345`。稍微聪明的攻击就会避开它——它应当看起来像真实数据。 |
| scorer must not see raw injection | 判分器不看注入原文 | 判分只依据「动作与终态」这些结构化事实。 | 否则攻击者可以同时攻击判分器（自检悖论的翻版）。 | 用 LLM judge 判断「这次注入成功了吗」并把原文喂给它。notebook 演示了它被同一段内容影响后把成功的攻击判成「未被攻击」。 |
| redteam finding (structured) | 结构化的红队发现 | 含 `attack_class` / `entry_point` / `defenses_bypassed` / `defenses_that_held` / `fix_kind` / 可自动重跑的 repro。 | `defenses_that_held` 与 `fix_kind` 分布是**最有价值的两个读数**。 | 把红队产出写成一份 PDF。**不可自动重跑的发现必然复发**；而 `fix_kind` 以 detection 为主说明方向有问题。 |
