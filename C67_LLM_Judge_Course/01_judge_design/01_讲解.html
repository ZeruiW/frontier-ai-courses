01 · Judge 设计

设计 judge 的第一步不是写 prompt，而是把问题往可判定的方向改写——一个「这个回复好不好」的 L0 问题，往往能拆成三四个 L2/L3 的可判定小问题 · pointwise 的头号病症是分数分布压缩：五档量表常常只有效用到一档半，而把量表从 5 档改成 100 档并不创造信息，它只是把同样的噪声铺得更开 · rubric 分解是全课性价比最高的工具：独立噪声按 $1/\sqrt{K}$ 衰减，4–6 项是甜点区；而「编造引用」这类问题必须用否决项归零，不能按权重扣分 · pairwise 的三个决策：允不允许平局、平局怎么进统计（推荐算半分）、以及必须成对调用（swap）——swap 一致率低于 80% 时胜率数字不可信 · 参考答案是双刃的：提升一致性，但会让 judge 奖励「像参考」而不是「同样正确」 · 解析失败与判断难度相关，悄悄丢弃会让一致率虚高

1先问「问什么」：判分问题的可判定性阶梯

设计 judge 的第一步不是写 prompt，而是把你想问的问题，往可判定的方向改写。同一个评测目标，可以被写成阶梯上的不同高度，而高度决定了这个 judge 能有多可靠。

可判定性 ↑（越上面越可靠、越便宜、越不需要 LLM） ┌──────────────────────────────────────────────────────────────┐ │ L4 程序可判定 "输出是不是合法 JSON / 有没有调用 tool X" │ → 不该用 LLM（C66） ├──────────────────────────────────────────────────────────────┤ │ L3 语义可判定 "有没有提到用户问的那个日期" │ → LLM 校验，一致率 >95% ├──────────────────────────────────────────────────────────────┤ │ L2 规则可裁决 "是否符合这条 rubric：给出了至少两个反例" │ → LLM rubric 项，一致率 85-95% ├──────────────────────────────────────────────────────────────┤ │ L1 有序比较 "A 和 B 哪个更好" │ → pairwise，一致率 70-85% ├──────────────────────────────────────────────────────────────┤ │ L0 绝对打分 "给这个回答打 1-5 分" │ → pointwise，最不可靠 └──────────────────────────────────────────────────────────────┘

直白说

这张梯子的实用价值在于：你手上那个「主观」的评测目标，往往可以被拆成一堆 L2/L3 的小问题，而不是被迫停在 L0。「这个客服回复好不好」这个 L0 问题，可以拆成：有没有回答用户实际问的问题（L3）、有没有引用正确的政策条款（L3）、有没有承诺公司做不到的事（L2）、语气是否得体（L1，只能停在这一层）。拆完之后，四项里有三项都爬到了梯子上层。

严谨说

形式化地说，这是把一个整体判断（holistic judgment）分解为一组分析性判断（analytic judgments）。分解的收益有两层：① 每个子判断的方差更小（问题更窄 → judge 的不确定性更低）；② 子判断可以被独立验证与独立监控（哪一项在退化，一眼看得出来）。代价是引入了聚合权重这个新的自由度——它必须做敏感性分析（notebook 第 3 节）。

一条可以立刻执行的检查：把你的 judge prompt 里那个问题读出来，问自己「两个认真的人类看同一份材料，会不会给出不同答案？」如果会，说明这个问题还停在 L0/L1，值得再往上拆一层。停在 L0 有时是不可避免的（审美、语气），但绝不应该是默认选择。

2pointwise 打分：分数分布压缩，以及三种缓解

pointwise（给单个回答打 1–5 分）是最常见也最容易出问题的用法。它的头号病症是分数分布压缩：让 judge 给一百个回答打分，你会发现七八十个都是 4 分。

压缩为什么发生

  • 没有锚点：judge 不知道「4 分」相对于什么。人类标注员在校准会上会看一批标好的例子，judge 通常什么都没看到。
  • 回避极端：模型倾向于避免 1 分和 5 分这种强判断（与 RLHF 训出的谨慎倾向一致）。
  • 量表本身太粗：五档要覆盖从「完全错误」到「无可挑剔」，中间的差异被压进同一档。

压缩的直接后果是判别力归零：如果 80% 的样本都是 4 分，那么这个 judge 在这 80% 之间提供的信息是 0 bit。量化方式就是分数分布的熵——或者更直观的有效档位数 $2^{H}$（$H$ 以 bit 为单位，与 notebook 里的实现一致）：五档量表如果有效档位数只有 1.6，说明你实际上在用一个「一档半」的量表。

缓解手段怎么做效果代价
rubric 分解拆成 4–6 个二元/三元的子项，再加权聚合（第 4 节）最有效：每个子项的分布都不压缩，聚合后连续化要设计 rubric、要定权重
few-shot 锚点给出每一档的 1–2 个标注样例有效，尤其是给出 1 分与 5 分的样例占上下文；锚点选得不好会引入新偏差
更细的量表 + 强制分布改成 0–100 分，或要求「不许连续给同一分」有效但脆弱：模型会集中在 70/80/85 这些整十整五上分数的语义变得更模糊
改用 pairwise直接换用法（第 3 节）彻底绕开该问题失去绝对分数，无法设阈值

有一个看起来很聪明、实际上要小心的做法：用 token 概率做加权平均分（如 G-Eval 的思路：取 1–5 这五个 token 的概率，算期望分）。它确实能把整数分变成连续分、缓解压缩；但它要求你能拿到 logprobs，而且把「模型对某个分数的不确定性」当成了「质量的中间态」——这两件事并不等价。作为缓解手段可以用，但不要把它当成校准过的概率（03 模块会讲怎么检验）。

3pairwise 比较：平局、置信度，以及「必须成对调用」

pairwise 把「打多少分」换成「谁更好」，绕开了绝对量表的全部问题，代价是引入了三个新的设计决策。

决策一：允不允许平局

口径做法适用陷阱
强制二选一不给平局选项样本量小、需要最大分辨力时把「确实分不出」的样本变成了纯噪声，并可能放大位置偏差（分不出时就选默认位置）
允许平局A / B / tie 三选一推荐默认平局比例过高（> 40%）时分辨力下降，需要检查是不是任务本身没有区分度
五档A 明显更好 / A 略好 / 平 / B 略好 / B 明显更好需要区分「差多少」时（如构造偏好数据）档位越多，一致性越低；「略好」这一档的一致率通常很差

决策二：平局怎么进统计

\[\text{win rate} = \frac{W + \tfrac{1}{2}T}{W + L + T} \quad\text{（推荐）}\qquad\text{vs}\qquad \frac{W}{W+L}\ \text{（丢弃平局）}\]

两种口径会给出不同的数字，而且在平局率高时差别很大。推荐左边这种（平局算半分）——它与 Elo 以及 Arena 类榜单拟合 Bradley–Terry 时的实际做法一致（把平局记成 $y=0.5$，见 04 模块）。严格来说 BT 本身没有平局项，处理平局的正统扩展是 Davidson 或 Rao–Kupper 模型；半分是一个好用的近似，但要在报告里写明。而且不会因为「平局多」而人为放大胜负差距。无论选哪种，都必须在报告里写明。

决策三：必须成对调用（swap）

这是本节最重要的一条工程纪律：任何 pairwise judge 调用都必须做两次，第二次交换 A/B 的位置。理由在 02 模块会量化：位置偏差普遍存在且幅度可观。两次结果不一致时，标准处理是记为平局（最保守）。而 swap 一致率本身是一个必须报告的指标——低于 80% 时，这个 judge 给出的胜率基本不可信。

成对调用把成本翻倍。这是值得付的——但它也意味着你在设计评测规模时要把这一倍算进去（呼应 C66 模块 05 的成本模型）。一个常见的折中：全量做单次调用，随机抽 10%–20% 做 swap 用于监控一致率；但请注意这只适合监控，不适合出结论——出结论的那一次评测应该全量 swap。

4rubric 设计：把主观质量拆成客观检查项

rubric 是这门课里性价比最高的一个工具。它把第 1 节的「往梯子上爬」变成了具体做法。

一个好 rubric 的五条标准

  1. 每一项都能独立判定：判定第 3 项时不需要看第 1 项的结论。互相依赖的项会让 judge 的错误在项之间传播。
  2. 每一项都是二元或三元的：「有 / 没有」「完全满足 / 部分满足 / 不满足」。不要在 rubric 项内部再放一个 1–5 分量表——那等于把压缩问题复制了 N 份。
  3. 项与项之间尽量正交：「准确性」和「是否有事实错误」是同一项的两种说法，放两遍等于给它加了双倍权重（而且是隐式的）。
  4. 覆盖失败模式而不是覆盖优点：从「这类回答通常怎么坏掉」倒推 rubric 项，比从「一个好回答应该有什么」正推更有效——后者容易写出一堆无法区分的空泛项。
  5. 包含一条否决项：某些问题（编造引用、承诺做不到的事、违反安全策略）应该直接把总分归零，而不是按权重扣分。

聚合：权重从哪来，以及怎么检验

rubric 分项之后必须聚合成一个数。权重是一个新引入的自由度，处理方式：

  • 先试等权：等权是一个诚实的默认值，而且经常已经够用；
  • 用人类偏好拟合权重：如果有一批人类的整体偏好标注，可以把「rubric 分项 → 人类偏好」拟合成一个线性模型，权重就是回归系数。这同时也检验了 rubric 的完备性——如果拟合得很差，说明你漏了某个维度；
  • 无论怎么定，都要做敏感性分析：权重扰动 ±20%，结论会不会翻转（呼应 C65 模块 03 与 C66 模块 02 的做法）。一扰动就翻的结论，真正的分歧点在权重上而不在数据上。

rubric 还有一个常被忽略的好处：它让 judge 的输出变得可解释、可申诉。「B 得 3.4 分、A 得 3.1 分」没法讨论；「B 在『引用了正确条款』这一项通过、A 没通过」可以被具体检查、被具体反驳。在需要跟业务方对齐评测口径的场景，这一点的价值往往超过分辨力本身。

5参考答案：有 vs 无，以及参考答案本身的质量

给 judge 一份参考答案（reference / gold answer），是提升一致性最直接的手段之一——但它有三个必须知道的边界。

设置judge 与人类的一致性适用场景风险
无参考最低开放式创作、无唯一解的任务judge 只能凭自己的先验判断，自偏好偏差最强
有参考答案显著提升有标准答案或范例的任务judge 会奖励「像参考答案」而不是「同样正确」
有参考 + 评分要点最高有明确得分点的任务（考试式）要点写得不全时，正确但不在要点里的答案被判错

中间那一行的风险值得展开：给了参考答案之后，judge 的判断会向「与参考答案的相似度」漂移，而相似度不等于正确性。一个用完全不同但同样正确的方法解题的回答，可能因为「和参考不像」被判低分。这与 C66 模块 03 里「把轨迹相似度当主指标等于惩罚探索」是完全同构的错误。缓解办法：在 prompt 里显式写「参考答案只是一种正确解法，其他正确解法应同等评分」，并在 rubric 里用「是否得出正确结论」替代「是否与参考一致」。

参考答案自己有多好

一个常被跳过的问题：你的参考答案是谁写的？如果它是某个模型生成后人工快速过了一遍的，那么它可能本身就带着那个模型的风格与错误，而 judge 会把这些一并当成标准。检验方式很简单：把参考答案本身送进 judge 打分，看它得多少分。如果参考答案自己只能得 3.5 分，那么用它当标准是有问题的。

6CoT 与结构化输出：顺序、schema 与解析失败

先理由后结论，还是先结论后理由

先理由后结论几乎总是更好，原因不是「让模型思考」这种笼统说法，而是一个具体的机制：先输出的 token 会成为后面 token 的条件。如果先写 "verdict": "A"，后面的 reasoning 就变成了对既有结论的辩护，而不是导向结论的推理——这在结构上就无法起到纠错作用。

// ✓ 推荐：理由在前，结论在后
{"reasoning": "…", "verdict": "A"}

// ✗ 不推荐：结论在前，理由变成事后辩护
{"verdict": "A", "reasoning": "…"}

// ⚠ 注意：JSON 对象的字段顺序在生成时是有意义的（模型按序生成），
//    即使解析后字段顺序无关紧要。

结构化输出的三个工程问题

问题表现处理
解析失败返回的不是合法 JSON（多了解释文字、截断、markdown 代码块包裹）① 用原生结构化输出/工具调用约束；② 兜底做一次宽松解析（剥离代码块、找第一个 {）；③ 重试，并记录重试率
枚举越界verdict 返回了 "A is better" 而不是 "A"schema 里用 enum 约束；解析时做归一化映射
截断reasoning 太长把 verdict 挤出了 max_tokens限制 reasoning 长度（「2–3 句」）并给足 max_tokens；这是「理由在前」的主要代价
解析失败率必须被记录并报告。原因不只是工程洁癖：解析失败往往不是随机的——遇到难判的样本时，judge 更可能输出一堆解释而不是干净的 JSON。如果你悄悄丢掉了这些样本，就引入了一个与判断难度相关的选择偏倚，剩下样本的一致率会虚高。正确做法是重试；重试仍失败的记为平局并计入分母。

7few-shot 锚点与量表校准

如果最终还是要用 pointwise，那么锚点是把分布拉开的最有效手段。但锚点的选择本身是一个需要小心的设计。

  1. 优先给两端：1 分和 5 分的样例比中间档更有价值——它们定义了量表的范围，而中间档会被内插出来。
  2. 锚点必须来自与被评样本相同的分布：用一批「精心挑选的漂亮回答」当 5 分锚点，会让所有真实回答都显得平庸，整体分数下移（严厉度偏差）。
  3. 锚点数量要少：每档 1–2 个。锚点占的上下文越多，被评内容在上下文里的相对权重越低；而且过多的锚点会让 judge 去做「最近邻匹配」而不是按标准判断。
  4. 锚点要版本化：换了锚点就等于换了量表，历史分数不可直接比较——这与 C66 模块 05 的 运行指纹是同一件事。

直白说

一个实用的自检：把锚点样例本身当作待评样本，送进 judge 跑一遍。如果 5 分锚点被打成 4 分，说明你的 prompt 与锚点之间存在矛盾，judge 并没有真的把锚点当作标准。这个自检便宜、快，而且经常能抓到问题。

严谨说

更一般地说，这是在检验量表的内部一致性：锚点定义了从质量到分数的映射 $g$，judge 的实际打分函数是 $\hat{g}$，自检就是在检查 $\hat{g}(\text{anchor}_k) = k$ 是否成立。不成立说明 prompt 中的文字描述（「5 分表示……」）与锚点样例给出的隐式定义不一致，而模型通常更信样例——所以修锚点比修文字描述更有效。

8judge prompt 的版本管理与回归

最后一节讲一件几乎所有团队都会在半年后后悔没做的事：judge prompt 的版本管理。

judge prompt 是评测系统里唯一一个「随时会被人顺手改一下」的组件——有人觉得措辞不好改一句，有人加了一条 rubric，有人调了锚点。而每一次改动，都意味着之前所有用这个 judge 跑出来的分数，与之后的分数不可比较。

要做的事怎么做不做的后果
prompt 哈希进结果把 judge prompt 模板（含锚点）的哈希写进每一条结果记录半年后没人说得清某个历史数字是哪版 prompt 跑的
金标准回归集留一批人类标注好的样本，每次改 prompt 都重跑，看一致率变化改动是「改好了」还是「改坏了」全靠感觉
双跑重叠期改版时新旧 judge 并行跑一段，量化两者的系统性差异指标曲线上出现一个无法解释的跳变
锚点与 rubric 单独版本化它们改动频率最高，单独管理便于定位无法回答「这次分数变化是模型变了还是量表变了」

最后强调一遍这条与 C66 模块 05 完全同构的纪律：judge prompt 是 harness 的一部分。「我们的模型这个月分数涨了 3 个点」——如果这个月里有人动过 judge prompt，这句话就是无意义的。把 prompt 哈希放进指纹，让「不可比较」变成机器可判定的一行 assert，而不是靠人回忆。

9多轮对话与长文档：judge 设计的两个特例

前八节默认被评的是「一个 prompt 对应一个回答」。真实系统里有两类常见情形需要额外的设计决策，值得单独说清楚。

多轮对话：评哪一轮

评法怎么做适用问题
只评最后一轮把前面的轮次当上下文，只判最后一个回复客服、问答类的单点质量监控看不出「前面几轮把对话带偏了」这类失败
逐轮评再聚合每一轮独立打分，取平均或最小值需要定位「第几轮开始崩」时轮次之间不独立——第 3 轮的差，可能完全是第 2 轮造成的
整段对话评一次把整个对话当一个整体判断评「这次会话有没有解决用户问题」长上下文里 judge 的注意力分布不均，结尾的内容权重更高
目标达成检查不评「好不好」，只查「用户的目标达成了没有」推荐：任务型对话需要为每个会话标注目标——但这正是 C66 终态判分的思路

多轮场景里最容易被忽略的一条：逐轮打分的平均值，会系统性地低估「前期埋雷、后期爆炸」这类失败——因为前面几轮单看都还不错。如果你关心的是「这次会话成功了吗」，就应该用目标达成检查（一个可判定的 L3 问题）而不是逐轮打分（一堆 L0 问题）。这又是第 1 节那把梯子的应用。

长文档：位置效应与分块

当被评内容很长（几千到几万 token）时，会出现两个 pointwise/pairwise 都要面对的问题：

  • 位置效应：长上下文中间部分的内容更容易被忽略。这意味着同样的错误，出现在文档中间比出现在开头或结尾更不容易被 judge 发现——这是一种与内容无关的系统偏差，可以用「把同一个错误插到不同位置」的探针测出来（模块 02 的范式）；
  • 整体判断被稀释：一份 8000 字的报告里有一个致命的事实错误，整体打分可能只掉 0.5 分。解法是 rubric 化 + 否决项——「有没有事实错误」作为一个独立的二元项，触发即否决，而不是混进整体印象里。

一个两类情形共用的原则：先问「失败长什么样」

多轮与长文档看起来是两个问题，但它们的正确解法来自同一句话：先列出这类内容典型的失败形态，再据此设计 judge，而不是先写一个「请评价这段内容的质量」的通用 prompt。

多轮对话的典型失败是「前期把用户的需求理解偏了，后面几轮都在解决错误的问题」；长文档的典型失败是「整体结构不错，但中间藏着一个致命的事实错误」。这两种失败，通用的「整体质量」prompt 都抓不到——前者需要「目标达成检查」，后者需要「事实错误」作为否决项。而一旦你列出了失败形态，rubric 项其实是被这份清单直接决定的（呼应第 4 节的第 4 条：覆盖失败模式而不是覆盖优点）。

分块评测是一个常见但需要小心的做法：把长文档切成块分别评再聚合。它能缓解位置效应，但引入了新问题——跨块的一致性问题（前后矛盾）在分块评测里完全看不见。实践中的折中是「分块评局部质量 + 整体评一致性」两条线分开跑，各自报告，不要合成一个数。
