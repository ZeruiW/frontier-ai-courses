1编排全景：从一份脚本到一片集群

前面四个模块教会了你分布式训练的「物理学」——集合通信怎么算、显存怎么分片、张量/流水怎么切、checkpoint 怎么存。但当你真的要在一个 256 卡的集群上把一份训练脚本拉起来、盯住、出了问题能修时，面对的是另一类问题：编排（orchestration）与调试（debugging）。这是分布式训练里最不性感、却最消耗工程师时间的一环——一个能跑通的并行策略，和一个能在真实集群上稳定跑两个月、断了能自愈、慢了能定位的训练系统，中间隔着的就是本模块。

先认清一个反直觉的事实：在大规模训练里，「让它跑起来」往往比「让它跑得对」更难。算法正确性你在单卡、双卡就能验证（这正是本课 notebook 一直在做的对拍）；但「512 个进程在 64 台机器上同时启动、各自绑定正确的 GPU、加入正确的通信组、在第 1 万步有一台机器网卡抖了一下而整个训练没有死锁」——这件事没有 assert 能在本地替你验证，它只在真实集群上、在凌晨三点报警时才暴露。

直白说

编排就是「把一个程序复制成 N 份、让它们认识彼此、各管一块硬件」的全部胶水：谁是 0 号、总共几个、连到哪个集合点、用哪块 GPU。调试则是当这台由几百个进程组成的机器卡住或算飞了时，怎么在没有单一现场的情况下定位元凶。

严谨说

形式上，一次分布式训练是 world_size 个进程，每个持有唯一 rank，通过一个 rendezvous（集合点） 互相发现、建立 process group（通信组）。编排是把 (rank, world_size, local_rank, MASTER_ADDR, MASTER_PORT) 这组环境变量正确地分发到每个进程；调试是在某个 collective 永久阻塞、或某个 rank 的张量和别人不一致时，重建出「谁在等谁」的全局图景。

一句话抓住本模块：同步训练是一台由几百个零件咬合而成的机器——任何一个零件慢一拍、缺一次、对不齐，整台机器要么变慢，要么卡死，要么悄悄算错。前四模块教你造零件，本模块教你装配、点火、和在它抽搐时找出哪颗螺丝松了。

2rank / world / local_rank 与启动器

启动一次分布式训练，本质是把同一个脚本在多台机器、多块 GPU 上各跑一份，并让它们就「我是谁、我们有几个、怎么找到彼此」达成一致。这套元信息靠几个约定俗成的环境变量传递：

变量含义举例（2 机 × 8 卡 = 16 进程）
WORLD_SIZE进程总数 = 参与训练的 GPU 总数16
RANK本进程的全局编号，0 .. world_size−1，全局唯一0 .. 15
LOCAL_RANK本进程在本机内的编号，决定绑哪块本地 GPU0 .. 7（每机）
MASTER_ADDRrank 0 所在机器的地址，作为 rendezvous 集合点10.0.0.1
MASTER_PORT集合点端口29500

这里最容易混淆、也最容易出 bug 的是 global rank 与 local rank 的区别。RANK 是你在整个世界里的身份（用于参与全局 collective）；而 LOCAL_RANK 是你在本台机器里的身份，唯一用途是 torch.cuda.set_device(local_rank)——把本进程钉死在某块物理 GPU 上。在 2 机 × 8 卡里，机器 B 上那个 LOCAL_RANK=0 的进程，其 RANK 是 8 而非 0。把这两者搞混（比如用 global rank 去 set_device）会让两个进程抢同一块卡、或越界访问不存在的卡，是新手第一天就会踩的坑。

分发这组变量、把进程拉起来的，是启动器（launcher）。最常见的两种：torchrun（PyTorch 自带，单机或配合调度器跨机）负责在每台机器上 fork 出 nproc_per_node 个进程并注入正确的 rank/local_rank；而在真正的 HPC/生产集群上，外层往往是 SLURM 这类作业调度器，先分配节点、再在每个节点上调起 torchrun 或直接调 python。无论哪种，它们干的事都一样：把上表那几个变量算对、塞进每个进程的环境里。

rendezvous 是启动阶段最脆弱的一环。所有进程必须能解析并连上 MASTER_ADDR:MASTER_PORT，否则会卡在「等其他 rank 加入」直到超时。典型故障：端口被占用、防火墙挡住、MASTER_ADDR 在多网卡机器上指向了不可达的网卡、或某台机器根本没起来导致 world 永远凑不齐。现代 torchrun 用 c10d rendezvous 后端（甚至 etcd）来做更健壮的成员发现与弹性重组——这正是模块 04 弹性训练的入口。

3通信组：rank 到 (dp,tp,pp) 的映射

光有「我是 rank 5」还不够。一旦你叠加了模块 02/03 的多维并行，rank 5 还需要知道：我在数据并行里和谁同组？张量并行里和谁同组？流水线里和谁同组？——因为不同的 collective 要在不同的子通信组（sub process group）上做。

做法是把 world_size 个 rank 看成一个三维网格 (dp, tp, pp)（数据并行 × 张量并行 × 流水并行），用一个固定的「展平公式」在线性 rank 与三维坐标间换算。约定一种行主序（最内层是 TP，其次 DP，最外层 PP）：

\[\text{rank} = pp \cdot (n_{dp} n_{tp}) + dp \cdot n_{tp} + tp\]

有了这个映射，每个 collective 就有了明确的「作用域」。一条朴素的规则贯穿所有并行：沿哪个维度做并行，就在那个维度的组里做 collective。数据并行的梯度 all-reduce 在固定 (tp, pp)、遍历 dp的那组 rank 上做；张量并行的激活 all-reduce 在固定 (dp, pp)、遍历 tp的那组 rank 上做；流水线的 send/recv 在相邻 pp的 rank 间做。Megatron-LM 正是这样为每种并行预先建好一批 torch.distributed.new_group(ranks=[...])，训练时各取所需。

沉默的错误

通信组建错是分布式训练最隐蔽的 bug 之一。如果 DP 组的成员算错（比如把本该同步的两个 rank 分到了不同组），训练不会报错——它照常 all-reduce，只是每个组各自平均了不完整的梯度，模型悄悄收敛到错误的地方。和模块 04 的 checkpoint 一致性一样：沉默的错误比崩溃可怕得多。建组逻辑必须用单元测试（如本模块 notebook 的往返 assert）和小规模对拍来验证。

4落后者：同步训练的木桶效应

现在进入同步训练的头号性能杀手：straggler（落后者）。同步数据并行的每一步都以一次梯度 all-reduce 结束，而 all-reduce 是一道屏障（barrier）——它必须等所有 rank 都到齐才能完成。于是这一步的耗时不是平均值，而是最大值：

\[t_{\text{step}} = \max_{r \in \text{ranks}} t_r \;\ge\; \frac{1}{N}\sum_r t_r = \bar{t}\]

这就是赤裸裸的木桶效应：512 块 GPU 里只要有一块因为某种原因慢了 20%，整个训练的每一步都慢 20%，另外 511 块卡在屏障前干等。更糟的是落后者不是固定的——这一步是 7 号卡热降频，下一步是 30 号卡的网卡重传，再下一步是某个 data loader 卡了一下。这种随机的、漂移的落后者让问题极难复现，也极难甩锅给某一块具体的硬件。

直白说

一桌人一起吃火锅，必须等最慢的那个人涮完才能一起下一轮。哪怕只有一个人慢吞吞，全桌的节奏都被他拖住，其他人只能干等。加的人越多，「总有一个人慢」的概率越大——这就是为什么卡越多、落后者问题越严重。

严谨说

落后者的来源大致三类：硬件（GPU 热降频、ECC 错误重试、某块卡是次品）、网络（某条链路拥塞或丢包重传、拓扑不对称）、软件/数据（不同 rank 拿到的样本长度不一导致计算量不均、某个 rank 的 data loader 卡顿、GC 停顿）。随 N 增大，「至少一个 rank 落后」的概率按 1−(1−p)^N 上升——这就是同步训练规模化的根本张力。

缓解手段没有银弹，但有套路：把数据切得更均衡（按 token 数而非样本数分桶，避免长短不一）；用更细的通信-计算重叠（见下节）让短暂的落后被算力吸收；对持续掉队的硬件做健康检查与剔除（这又回到模块 04 的弹性训练——把坏节点换掉）；以及在极端规模下转向异步或半同步训练（见第 8 节），从根上拆掉那道屏障。诊断的第一步永远是：把每个 rank 的单步耗时都记下来，看分布的尾巴有多长——这正是本模块 notebook worked 2 在做的事。

5扩展效率：强扩展、弱扩展与 Amdahl

加卡到底能不能等比例加速？这要分两种问法，对应两条完全不同的曲线。Strong scaling（强扩展）：问题规模固定，只是把卡加多，看墙钟时间能缩短多少倍——这是「我想把这次训练跑得更快」。Weak scaling（弱扩展）：每块卡的工作量固定，加卡的同时把总问题等比例放大，看每步耗时能不能保持不变——这是「我想训一个更大的模型/更大的 batch」。大模型预训练几乎全是弱扩展场景。

强扩展的天花板由 Amdahl 定律 锁死。设一个程序里可并行的比例是 p、串行（无法并行）的比例是 1−p，用 N 个处理器的加速比为：

\[S(N) = \frac{1}{(1-p) + \dfrac{p}{N}}, \qquad E(N) = \frac{S(N)}{N}\]

残酷之处在于那个串行部分 1−p：哪怕 N\to\infty，加速比也只能逼近 1/(1-p)。如果有 5% 不可并行（在分布式训练里，「不可并行」主要就是通信开销——它不产生有用的 FLOPs，纯属为了同步而付出的税），那么加速比上限是 20 倍——你哪怕堆一万块卡，也突破不了 20。这就是为什么单纯「加卡」边际收益递减，以及为什么减少通信占比（模块 01–03 的全部努力）等价于抬高那条天花板。

把上表读进肌肉记忆：可并行比例从 95% 提到 99%，512 卡下的加速比从 19× 跳到 84×——4 个百分点的通信优化，换来 4 倍的有效算力。这就是为什么前沿团队对通信开销锱铢必较：在大 N 下，省下的每一点通信，都在 Amdahl 曲线上被放大成巨大的吞吐差距。弱扩展之所以能撑起万卡训练，正是因为它让 p 随规模保持在高位，而非像强扩展那样被固定问题规模逼到效率塌方。

6MFU 与通信-计算重叠

理想的扩展效率是 100%，但你永远拿不到。把效率从纸面的 Amdahl 拉回现实，要引入一个生产环境的核心指标：MFU（Model FLOPs Utilization，模型算力利用率）——你的训练实际跑出的「有用 FLOPs / 秒」占硬件理论峰值的百分比。它一把尺子量穿了所有低效：通信、落后者、显存搬运、kernel 没打满、流水气泡，全反映在这一个数字里。

MFU 的算法很干净。一个 N 参数的稠密 Transformer，每个 token 的前向+反向大约消耗 6N FLOPs（前向 2N、反向 4N，这是模块 02 那本「成本账」的核心公式）。于是：

\[\text{MFU} = \frac{6\,N \cdot (\text{tokens/sec})}{\text{GPU 数} \times \text{单卡峰值 FLOP/s}}\]

现实中的 MFU 是个体检数字：精心调优的大规模预训练能到 50–60%（这已是优秀），随手跑个分布式训练拿到 20–30% 很常见，低于 15% 说明有明显的浪费在等你去抓。它最大的价值是把「快不快」从主观感受变成可对账的硬指标——你优化通信、修掉落后者、改善重叠之后，MFU 涨没涨，骗不了人。

把效率往上抬最有力的杠杆是通信-计算重叠（overlap）。朴素实现里，一步是「算完梯度 → 再 all-reduce → 再下一步」，通信时间纯粹叠加在计算之上。但梯度是反向一层层算出来的：靠后的层先算完梯度，完全可以一边继续反向传播更早的层、一边异步 all-reduce 已经算好的层的梯度。理想情况下，整步耗时从 compute + comm 压到 max(compute, comm)——只要通信能被计算盖住，它就近乎免费。

直白说

串行就像下班后再去排队取快递；重叠则是上班路上顺手取了。同样的两件事，重叠做完，省下的是「等」的那段时间。分布式训练的大量工程，就是想方设法把「通信的等待」藏进「计算的忙碌」里。

严谨说

PyTorch DDP 用梯度分桶（gradient bucketing）实现这一点：把参数分成若干 bucket，某个 bucket 的梯度一就绪就立刻发起异步 all-reduce，与仍在进行的反向计算重叠。FSDP（模块 02）则需要把 all-gather 参数的通信和上一层的计算重叠。重叠做得好不好，直接决定了你离 max(compute, comm) 这个下界有多近——本模块 notebook worked 5 会把这个收益量化出来。

7调试：死锁、NaN 与一致性

分布式训练的 bug 有一种独特的恐怖：没有单一的「现场」。单机程序崩了，你有一个栈、一个 core dump。而 512 个进程的训练「卡住了」，现场是 512 份各不相同的状态，而真正的元凶可能是其中某一个进程在某一行多调或漏调了一次 collective。学会在这种条件下调试，是高级分布式工程师的看家本领。

最常见、也最折磨人的故障是 hang / deadlock（挂起 / 死锁）。集合通信的铁律是：所有 rank 必须以完全一致的顺序、调用完全一致的 collective。一旦某个 rank 因为一个数据相关的 if 分支多走了一次 all-reduce，或某个 rank 提前抛异常退出而没参与本该参与的 all-reduce，剩下的 rank 就会在那道屏障前永远等下去，直到 NCCL 超时（默认常是 30 分钟）才报一个语焉不详的错。

工具箱里最该熟练的几样：NCCL_DEBUG=INFO（打印通信建链与拓扑，排查连接与带宽）；每 rank 独立日志（给每条日志带上 rank 前缀，hang 时一眼看出谁卡在哪一步——这是最朴素也最有效的手段）；flight recorder（PyTorch 的 NCCL 飞行记录仪，事后 dump 出每个 rank 最近的 collective 调用序列，直接定位是谁、在哪一步对不齐）；以及 py-spy dump（无侵入地抓出每个 python 进程当前的调用栈，看大家分别卡在哪一行）。

一条能救命的纪律：让随机性在该一致的地方一致、在该不同的地方不同。模型初始化、数据打乱的种子，在数据并行组内必须一致（否则各 rank 模型不同、梯度平均出垃圾）；而 dropout、数据采样的偏移，又往往需要按 rank 错开。把「哪些随机源该对齐、哪些该错开」想清楚并显式设种子，能消灭一大类「跑起来不报错、就是不收敛」的鬼故事。

8瓶颈定位与研究前沿

当确认训练「慢」之后，下一个问题永远是：慢在哪？——这决定了你该去优化什么。分布式训练的瓶颈无非三类，对应三种完全不同的处方，搞错方向的优化纯属浪费：

  • compute-bound（算力受限）：GPU 基本打满，时间花在真正的矩阵乘上。这是好状态——想更快只能换更强的卡、提升单卡 kernel 效率、或减少冗余计算。继续优化通信收益甚微。
  • communication-bound（通信受限）：算力在等数据，时间花在 all-reduce / all-gather / send-recv 上。处方是模块 01–03 的全部武器：更好的拓扑与算法、通信压缩、重叠、调整并行维度的切法减少跨节点通信。
  • straggler-bound（落后者受限）：平均利用率不低，但每步都被某个慢 rank 拖着。处方是均衡数据、健康检查剔除坏节点、弹性重组，而非优化通信或计算。

区分它们靠看 timeline / trace：把每个 rank 每一步的「计算段、通信段、空等段」画在一条时间轴上，瓶颈一目了然——通信段长是通信受限，某个 rank 总有一截空等是落后者受限，时间轴密密麻麻全是计算则是（令人欣慰的）算力受限。本模块 notebook 的最后一道练习，就是给你三组 (compute, comm, straggler_gap) 数字，让你写一个分类器判定瓶颈类型——把这套诊断思维固化成代码。

最后是这门课的研究前沿，全都指向一个共同的敌人——那道同步屏障，以及它在万卡尺度下的不可持续：

  • 异步 / 去中心化训练：彻底拆掉全局屏障。Gossip 式的去中心化 SGD（如 D-PSGD）、本地多步再同步的 Local SGD、以及面向广域网的 DiLoCo，用「少同步、容忍陈旧」换取对落后者和慢网络的鲁棒性。
  • 通信压缩：在 all-reduce 前把梯度量化（如 1-bit Adam、PowerSGD 低秩压缩）或稀疏化，直接砍掉通信量——以可控的精度损失换吞吐，在弱网络下尤其值。
  • 跨数据中心 / 弹性训练：当单个数据中心的电力和卡数见顶，训练开始跨地域。高延迟、易掉线的环境逼出了更强的弹性调度与容错（模块 04 的延伸）和对同步频率的重新设计。
  • 自动并行与编译：与其让工程师手调 (dp, tp, pp)，不如让编译器搜。Alpa、GSPMD、以及各类 auto-sharding 框架，把「怎么切才最优」变成一个可自动求解的问题——这是把本课的全部手艺自动化的方向。

延伸阅读（详见 ../references.md）：Narayanan 等的 Megatron-LM / 3D 并行（通信组与扩展效率的工程范本）；Stich 的 Local SGD、Lian 等的去中心化 SGD（异步训练理论）；Douillard 等的 DiLoCo（跨数据中心低通信训练）；Zheng 等的 Alpa（自动并行）；以及各厂大规模训练报告里的 MFU 与扩展效率实测。把本模块的纸面模型，去和这些真实万卡训练的数字对账。
