1为什么数据并行：复制模型、切分数据

上一模块我们把集合通信原语（all-reduce / reduce-scatter / all-gather）从零拆开了。现在用它们搭起分布式训练里最基础、也最先该上手的一种并行：数据并行（data parallelism, DP）。它的思想朴素得近乎天真——既然一块卡装得下模型、只是数据吃不完，那就多买几块卡，每块都放一份完整模型，把一个大 batch 切成几份各算各的，最后把梯度对齐。绝大多数分布式训练任务，从两卡到几千卡，骨架都是数据并行。

把它和单卡训练摆在一起看，差别只在一步。单卡每个 step 是：取一个 batch → 前向 → 反向得到梯度 → 优化器更新参数。数据并行把它复制到 world_size 个 rank 上，唯一的新增动作是反向之后、更新之前，插入一次梯度同步（all-reduce 求平均），让所有 rank 拿到完全一致的梯度、从而走出完全一致的下一步。

单卡: batch ──► forward ──► backward ──► [grad] ──► optimizer.step() 数据并行(W=4): rank0: shard0 ─► fwd ─► bwd ─► g0 ┐ rank1: shard1 ─► fwd ─► bwd ─► g1 ├─► all-reduce 求平均 ─► ḡ ─► step() (每 rank 同步) rank2: shard2 ─► fwd ─► bwd ─► g2 │ (唯一的新增动作) rank3: shard3 ─► fwd ─► bwd ─► g3 ┘

直白说

直白说：每块卡都是一个完整的「单卡训练」，只是各看 batch 的一部分；它们靠每步交换一次梯度来保持「步调一致」，于是 W 块卡看起来就像一块拥有 W 倍 batch、W 倍吞吐的超级卡。

严谨说

严谨说：DP 不改变优化的数学，只改变有效 batch 大小。W 个 rank、每 rank 本地 batch 为 b，等价于单卡 batch=Wb。理想情况下吞吐随 W 线性增长，但每步要为梯度同步付一次通信代价，这正是 DP 可扩展性的天花板所在。

数据并行解决的是「算力/吞吐」不够的问题，不解决「显存装不下模型」的问题——因为每块卡仍存一份完整模型。后者要靠本模块后半段的 ZeRO/FSDP（分片）或下一模块的张量/流水并行。先把这条分界线钉死：DP 复制模型、切分数据；ZeRO/TP/PP 切分模型本身。

还有一个常被混淆的点要先厘清：数据并行里的「切 batch」和单卡里的梯度累积（gradient accumulation）是两件互补的事。梯度累积是在一块卡上把一个大 batch 拆成若干 micro-batch 顺序前向反向、累加梯度后才更新一次，用时间换显存；数据并行是把 batch 拆到多块卡上并行算、用卡换时间。二者可以叠加：有效 batch = world_size × 每卡 micro-batch × 累积步数。理解这条乘式，是后面排查「为什么我加了卡 loss 曲线却变了」的基础——多半是有效 batch 变了而学习率没跟着调。

2DDP 与梯度 all-reduce

数据并行在 PyTorch 里的标准实现叫 DistributedDataParallel (DDP)。它的正确性基石是一条简单的等式：把各 rank 的梯度求平均，恰好等于在拼起来的大 batch 上算的梯度。只要损失对样本是求和或求平均的（几乎所有损失都是），这条等式就严格成立。

设损失是逐样本损失的平均，rank r 持有数据分片 D_r（各含 b 个样本）。rank r 本地算的梯度是它那 b 个样本梯度的平均；对 W 个 rank 的本地梯度再求平均，分母配平后正好是全部 Wb 个样本梯度的平均：

\[\bar g \;=\; \frac{1}{W}\sum_{r=0}^{W-1} g_r \;=\; \frac{1}{W}\sum_{r=0}^{W-1}\Big(\frac{1}{b}\sum_{i\in D_r}\nabla \ell_i\Big) \;=\; \frac{1}{Wb}\sum_{i=1}^{Wb}\nabla \ell_i \;=\; g_{\text{single batch}=Wb}\]

所以 DDP 的同步用的就是模块 01 的 all-reduce（求和后再除以 W，或直接用 all-reduce 的 average 变体）。每个 rank 在 all-reduce 之后持有完全相同的平均梯度，于是各自的 optimizer.step() 走出完全相同的参数——所有 rank 的模型副本逐位一致，这一点必须保证，否则副本会悄悄漂移。

直白说

一个新手常踩的坑：忘了除以 W，或在某些 rank 上漏算了某些参数的梯度（比如带控制流的模型某个分支没走到）。前者让学习率隐形放大 W 倍，后者让 all-reduce 在不同 rank 上对不齐、直接 hang 死或算错。

严谨说

工程上 DDP 不会等所有梯度都算完才发一次巨型 all-reduce，而是把参数分成若干 bucket，反向传播一边算梯度、一边对已就绪的 bucket 异步发起 all-reduce，让通信与反向计算重叠。这是 DDP 把通信开销藏进计算的关键，也是它比朴素「算完再同步」快得多的原因。

把通信与反向重叠这件事再讲透一点，因为它是 DDP 性能的命脉。反向传播是从最后一层往第一层逐层算梯度的，所以最后几层的梯度最先就绪。DDP 把参数倒序装进若干 bucket（默认每个约 25MB），某个 bucket 里的梯度一旦全部就绪，就立刻在后台 NCCL 流上发起这个 bucket 的 all-reduce，与此同时前面几层的反向计算还在 GPU 的计算流上继续。理想情况下，当第一层的梯度也算完时，后面 bucket 的通信早已完成大半——通信几乎被完全藏进反向计算里。

bucket 的大小是个真实的调参旋钮：桶太小，则发起的 all-reduce 次数多、每次都摊一遍固定的启动延迟（latency-bound），小消息打不满带宽；桶太大，则要等很久才凑满一个桶、重叠的机会变少，且第一个桶迟迟发不出去。桶大小本质是在「通信次数（延迟）」与「重叠程度」之间找平衡——这正是模块 01 里「带宽-延迟成本模型」在 DDP 上的直接应用。

DDP 要求每个 rank 在每一步参与完全相同的一组集合通信调用、顺序也一致。一旦某个 rank 因数据相关的控制流跳过了某次 all-reduce，其余 rank 会永远等它——这是分布式训练里最常见的 hang（卡死）。带动态控制流的模型要么用 find_unused_parameters=True，要么保证各 rank 计算图结构一致。一个隐蔽的同源 bug：用了梯度累积时，前 K−1 个 micro-step不该触发 all-reduce（否则白白同步 K 次），要用 model.no_sync() 上下文把它们的同步关掉，只在最后一步同步。

3显存账：16P 字节花在哪

要理解 ZeRO/FSDP 为什么存在，先得把一块卡上训练显存到底花在哪算清楚——这正是 C08「成本模型」那门课的核心，这里快速复述、并补上工程细节。以参数量 P 计，混合精度 + Adam 训练的常驻显存（不含激活）大致是：

项目 (EN)精度字节/参数说明
fp16/bf16 参数 (model weights)16-bit2P前向/反向实际用的低精度权重
fp16/bf16 梯度 (gradients)16-bit2P反向算出、待 all-reduce/更新
fp32 主参数 (master weights)32-bit4P优化器更新的高精度副本，避免精度损失
Adam 一阶动量 m32-bit4P优化器状态
Adam 二阶动量 v32-bit4P优化器状态

把它们加起来，就是那个著名的数字：

\[M_{\text{model+opt}} \;=\; \underbrace{2P}_{\text{fp16 参数}} + \underbrace{2P}_{\text{fp16 梯度}} + \underbrace{4P}_{\text{fp32 主参数}} + \underbrace{4P + 4P}_{\text{Adam }m,v} \;=\; 16P \ \text{字节}\]

也就是说，一个 7B（70 亿参数） 模型，光是参数+梯度+优化器状态就要 16 × 7e9 ≈ 112 GB——单张 80GB 的 A100/H100根本装不下，这还没算激活。这就是 ZeRO/FSDP 要解决的核心矛盾：这 16P 字节里，绝大部分（12P 的优化器状态+主参数）在 DDP 里被每块卡冗余地各存了一份。

冗余即浪费

数据并行最浪费的地方正在于此：W 块卡存了 W 份完全相同的优化器状态与主参数。两卡就浪费一半、八卡就浪费 7/8。ZeRO 的全部洞察就一句话：这些每步只被本 rank 用到一次的状态，没必要每块卡都存——切开、各存一片、要用时再临时凑齐。

把 16P 拆成两类很有用：「算的时候必须在手边」的是 fp16 参数（2P，前向反向每层都要）；「只在 step 时用一下」的是梯度+主参数+Adam 状态（14P）。ZeRO 正是顺着这条线，从「最不常用」的优化器状态开始，一层层往下切。

还有一笔账 16P 里没算、但常常才是 OOM 的真凶——激活（activations）。前向时每一层的输出都要缓存下来供反向用，这部分显存正比于 batch × seq_len × hidden × 层数，长序列、大 batch 下能轻松超过参数本身。它和 16P 的关键区别是：激活随 batch/序列增长，而 16P 只随模型大小固定。对付激活有两条独立的路：activation checkpointing（重计算，丢弃中间激活、反向时重新前向算一遍，用算力换显存，见模块 04）和把 batch 切小（梯度累积）。ZeRO/FSDP 切的是 16P 这部分，激活要靠 checkpointing 单独治——两者正交，大模型训练通常同时上。

4ZeRO-1：分片优化器状态

ZeRO（Zero Redundancy Optimizer，Rajbhandari 等 2020）把上面的 16P 分三个阶段逐步分片，每阶段消掉一类冗余。ZeRO Stage 1：分片优化器状态（Adam 的 m、v 以及 fp32 主参数，共 12P）。每个 rank 只负责其中 1/W 的参数对应的优化器状态。

它的一个训练步是这样跑的（注意通信原语正好是模块 01 学的那几个）：

  1. 前向 + 反向：每个 rank 用完整的 fp16 参数算出完整的 fp16 梯度（这步和 DDP 一样）；
  2. reduce-scatter 梯度：不做全量 all-reduce，而是让每个 rank 只收到自己负责那 1/W 分片的求和后梯度；
  3. 本地更新：每个 rank 用自己手里的 1/W 优化器状态，更新自己负责的那 1/W 主参数、再投影回 fp16；
  4. all-gather 参数：把各 rank 更新好的 fp16 参数分片拼回完整参数，供下一步前向使用。

显存账立竿见影：12P 的优化器状态被切成 12P/W，而 2P 参数 + 2P 梯度仍是全量。每 rank 常驻约：

\[M_{\text{ZeRO-1}} \;\approx\; 2P + 2P + \frac{12P}{W} \;=\; 4P + \frac{12P}{W}\]

直白说

直白说：ZeRO-1 把「最占地方又最少用」的优化器状态（12P）分给大家各管一段。W 越大，这 12P 摊得越薄；卡足够多时，每卡的优化器状态几乎可以忽略。

严谨说

严谨说：通信量上，ZeRO-1 把 DDP 的一次 all-reduce（= reduce-scatter + all-gather）拆成了反向后的 reduce-scatter 梯度 + 更新后的 all-gather 参数，每 rank 收发的总字节数与 DDP 的 all-reduce基本相同（约 2P）。所以 ZeRO-1 几乎是免费的显存节省——这也是它该被默认开启的原因。

5ZeRO-2：再分片梯度

ZeRO Stage 2：在 Stage 1 的基础上，再分片梯度。观察到一个浪费：在 ZeRO-1 里，每个 rank 算出并暂存了完整的 2P 梯度，但它最终只用得上自己负责那 1/W 片去更新参数——其余 (W-1)/W 的梯度在 reduce-scatter 后就被丢弃了。既然如此，何必为它们一直占着显存？

ZeRO-2 的做法是：反向传播一边算梯度，一边对已算完的梯度立即 reduce-scatter，每个 rank 只累积、保留自己负责那 1/W 分片的梯度，算完一片就把对应的完整梯度释放掉。于是梯度的常驻显存从 2P 降到 2P/W：

\[M_{\text{ZeRO-2}} \;\approx\; 2P + \frac{2P}{W} + \frac{12P}{W} \;=\; 2P + \frac{14P}{W}\]

注意此时仍有 2P 的 fp16 参数是全量的——因为前向反向每一层都要用完整参数算，这部分到 ZeRO-3 才会被切。ZeRO-2 在工程上很受欢迎：它把梯度+优化器状态（14P）全部摊薄，只留 2P 全量参数，显存收益大而实现相对 ZeRO-3 简单。

从 ZeRO-1 到 ZeRO-2，通信量依然没变：ZeRO-1 是「攒完整梯度→一次性 reduce-scatter」，ZeRO-2 是「每层梯度就绪就 reduce-scatter 它那一段」，搬的总字节数一样，只是把一次大通信拆成了许多次小通信、换来梯度显存从 2P 降到 2P/W。这又是一次和模块 01「同样的总量，不同的切法」的呼应：切法影响重叠与显存峰值，但不改变总通信量。代价是 ZeRO-2 的通信更碎（每层一次 reduce-scatter），对小模型可能因消息太小而打不满带宽——这也是为什么超大模型才更划算。

ZeRO-2 的「边反向边 reduce-scatter」必须和反向的计算图次序对齐：梯度是按层从后往前陆续算出的，通信要挂在每层梯度就绪的钩子（hook）上。若实现把通信和某层计算的依赖搞错，会读到尚未算完的梯度——这类 bug 不报错，只是悄悄让结果偏掉，必须靠和单卡对拍来抓（本模块 notebook 的纪律）。另一个易错点：开了梯度累积时，ZeRO-2/3 的梯度分片要在累积期间本地累加、只在最后一步参与跨 rank 通信，否则会重复同步。

6ZeRO-3 / FSDP：分片参数本身

ZeRO Stage 3（即 PyTorch 的 FSDP）：连 fp16 参数本身也分片。这是最彻底的一步，也是 FSDP（Fully Sharded Data Parallel，Zhao 等 2023）的核心。现在每个 rank 平时只持有 1/W 的参数；只有当某一层正要被用到时，才临时把这一层的参数 all-gather 齐全，用完立刻丢弃。

一个 FSDP 训练步因此变成一连串「凑齐—计算—丢弃」：

前向（逐 FSDP unit，例如逐层）: for layer in model: all-gather(layer.params) # 临时凑齐这一层的完整参数 (1/W → 全量) y = layer(x) # 用完整参数前向 free(layer.params) # 立刻丢弃，只留回自己那 1/W 分片 反向（逐 unit，对称）: all-gather(layer.params) # 再凑一次（或前向时保留/重算） grad = layer.backward(...) reduce-scatter(grad) # 每 rank 只留自己负责的 1/W 梯度分片 free(layer.params)

于是常驻显存里参数、梯度、优化器状态全部变成 1/W，峰值只额外多出当前正在计算的那一两层的全量参数（all-gather 的临时缓冲）：

\[M_{\text{ZeRO-3/FSDP}} \;\approx\; \frac{2P + 2P + 12P}{W} + \underbrace{M_{\text{layer}}}_{\text{峰值临时缓冲}} \;=\; \frac{16P}{W} + O(\text{一层参数})\]
阶段参数梯度优化器状态每 rank 常驻（不含激活）
DDP / ZeRO-02P2P12P16P
ZeRO-12P2P12P/W4P + 12P/W
ZeRO-22P2P/W12P/W2P + 14P/W
ZeRO-3 / FSDP2P/W2P/W12P/W16P/W + 一层

直白说

直白说：FSDP 把模型像拼图一样拆给每块卡各拿几块，谁也不留全图；算到哪一块就临时把那块拼出来，算完拆掉。代价是每用一层参数都要现场 all-gather 一次，通信变多；回报是显存几乎随卡数线性下降——这才让单卡装不下的大模型成为可能。

严谨说

严谨说：FSDP 把模型按 FSDP unit（一组要一起 all-gather 的参数，通常是一层或一个 transformer block）包装。为了不让通信暴露成串行等待，FSDP 会prefetch：在算第 i 层时就异步 all-gather 第 i+1 层的参数，把通信藏到计算背后——这又回到模块 01 的「通信-计算重叠」主题。

ZeRO-1/2/3 是一条平滑的权衡曲线，不是三选一的开关：从 ZeRO-1 到 ZeRO-3，显存越省、通信越多。直觉记法——ZeRO-1 切「最少用的」(优化器状态)、ZeRO-2 再切「中等用的」(梯度)、ZeRO-3 切「最常用的」(参数，故通信代价最大)。卡多显存松就用低 stage，模型大显存紧就用高 stage。

7权衡与选型：通信换显存

分片不是免费的——省下来的显存要用额外的通信去换。把账算清楚才能选对：DDP 每步只在反向后做一次 all-reduce（≈ 2P 的等效收发）；ZeRO-1/2 的通信量与 DDP 基本相同（all-reduce 被拆成 reduce-scatter+all-gather，总量不变）；ZeRO-3/FSDP 因为前向也要 all-gather 一遍参数，通信量约是 DDP 的 1.5×。

\[\text{每步等效通信量}:\quad \text{DDP}\approx 2P,\quad \text{ZeRO-1/2}\approx 2P,\quad \text{ZeRO-3}\approx 3P\ (\approx 1.5\times\text{DDP})\]

选型的经验法则（先按显存能不能装下来定，再按通信带宽微调）：

场景推荐理由
模型单卡装得下，只想加速DDP（或 + ZeRO-1）通信最少；ZeRO-1 几乎免费再省优化器状态
模型偏大、单卡勉强ZeRO-2梯度+优化器状态摊薄，参数仍全量、通信不增
模型单卡装不下ZeRO-3 / FSDP唯一能把参数也摊开的 DP 方案，代价是 1.5× 通信
超大模型、多节点FSDP + TP/PP（3D 并行）DP 解决不了的单层过大/层数过多，交给下一模块

一个重要的中间档是 HSDP（Hybrid Sharded Data Parallel）：节点内 FSDP 分片、节点间 DDP 复制。它利用了「节点内带宽（NVLink）远高于节点间带宽（InfiniBand）」的硬件现实——把昂贵的 all-gather 限制在高带宽的节点内，节点之间只做一次便宜的 all-reduce。这是大规模训练里 FSDP 落地的常见姿势。

不要被「ZeRO-3 显存最省」诱惑而无脑全开。当模型本就能装下时，ZeRO-3 的 1.5× 通信会白白拖慢训练；当节点间带宽很低时，全局 FSDP 的 all-gather 可能成为瓶颈，HSDP 往往更快。先用显存约束筛掉装不下的方案，再在能装下的方案里挑通信最省的——这是选型的正确次序。

8研究前沿与开放问题

数据并行与分片是分布式训练里最成熟的一块，但前沿仍在快速演进，主线是把「通信」这个新瓶颈继续往下压：

  • Offload 与 ZeRO-Infinity：把分片后的优化器状态、甚至参数进一步下放到 CPU 内存或 NVMe，用主机的大容量换 GPU 显存，让单机也能训超大模型（Rajbhandari 等 2021）。代价是 PCIe 带宽成为新瓶颈，需要精细的预取与重叠。
  • 通信压缩与低精度 all-reduce：梯度量化、稀疏化、误差反馈（error feedback）等，把每步同步的字节数直接砍掉，缓解带宽瓶颈；FSDP 也支持 bf16/fp8 通信。
  • FSDP2 与 per-parameter 分片：PyTorch 新一代 FSDP 用 DTensor 做更细粒度、更可组合的分片，改善与 TP/PP 的组合、降低显存碎片与峰值。
  • 与专家并行（Expert Parallel / MoE）组合：MoE 模型把不同 expert 放到不同 rank，引入 all-to-all 通信（模块 01 学过），与 FSDP/数据并行如何高效组合是当前热点。
  • 自动并行（auto-parallelism）：与其手调 DP/TP/PP/分片维度，不如让编译器（Alpa、GSPMD 等）在给定硬件拓扑下自动搜索最优并行方案——把本模块的选型表自动化。

奠基与必读：Rajbhandari 等 2020《ZeRO》（分片三阶段的原始论文）、Zhao 等 2023《PyTorch FSDP》（生产级实现与工程权衡）、Rajbhandari 等 2021《ZeRO-Infinity》（offload 到 CPU/NVMe）。完整清单与延伸见 references.md。
