1为什么需要模型并行：TP 与 PP 两条路

到目前为止（模块 02）我们假设了一个隐含前提：整个模型至少能塞进单卡——数据并行（DP）、ZeRO、FSDP 都是在「每张卡能放下模型，只是想用更多卡分摊 batch 与显存」的框架下做文章。但当模型大到连一层都放不进单卡时，这套假设彻底失效。一个 GPT-3 规模的 FFN 权重矩阵就是 12288 × 49152 的两块，单是这一层的参数加上它的激活与梯度，就可能撑爆一张 80GB 的卡。这时唯一的出路是把模型本身切开，分散到多张卡上——这就是model parallelism（模型并行）。

模型并行有两条正交的路，本模块各讲一条。第一条是tensor parallelism（张量并行，TP）：把单个算子内部的张量（权重矩阵）沿某个维度切开，让多张卡协作算完同一层。第二条是pipeline parallelism（流水并行，PP）：把模型的层序列切成若干段（stage），每段放一张卡，数据像在流水线上一样逐段流过。一句话区分：TP 是「把一层横向劈开给多卡」，PP 是「把多层纵向切段给多卡」。

直白说

打个比方：一份大文件要多人处理。TP 像「一页纸太大，几个人各撕一条同时誊写、最后拼起来」——大家干的是同一页；PP 像「装配流水线，第一个人做第一道工序传给第二个人」——每人负责不同工序。两者可以叠加：流水线上的每一道工序又可以由几个人合力完成。

严谨说

形式上：设模型有 L 层、每层参数 φ。DP 复制全部 Lφ 到每卡（显存不降）；TP 把每层的 φ 切成 φ/t 份（t=TP 度），显存随 t 下降但每层都要通信；PP 把 L 层切成 L/p 段（p=PP 度），每卡只存自己那几层，stage 间只在边界传激活。三者各切一个维度，可组合成 3D 并行。

记住选择的第一性原理：先用能放下模型的最省通信的方式，再加并行扩规模。TP 通信最密集（每层每次前/反向都通信），所以只在带宽极高的节点内（NVLink）用、度数通常 ≤ 8；PP 通信最稀疏（只在 stage 边界传激活），可跨节点；DP 通信居中（每步一次梯度 all-reduce）且可与反向重叠。这条「TP 在内、PP 居中、DP 在外」的排布会在第 7 节量化展开，是分布式工程师的核心手感。

本模块仍然用 numpy 在单进程内模拟多 rank：把 TP 的「按列/按行切权重」实现成对 numpy 数组沿轴切片、把跨卡求和实现成对 rank 列表求和（即模块 01 的 all-reduce）、把 PP 的「bubble」实现成对调度时隙的计数。每个并行实现都与单卡参考对拍到 1e-10，证明切分逻辑数值正确；真实的 Megatron-LM / PyTorch 代码作为对照展示。学完你会确信：这些听起来高深的并行策略，本质都是线性代数的分块 + 几次集合通信的组合。

2张量并行：列切分（免通信）

从一个 MLP 块说起：列切分（column parallel）

张量并行的精髓，在 Megatron-LM（Shoeybi 2019）对 Transformer 的 FFN 块的处理上展现得淋漓尽致。一个标准 FFN 块是两个线性层夹一个非线性：Z = GeLU(X·A)·B，其中 X 是 [s, h] 的输入（s=序列长×batch，h=hidden），A 是 [h, 4h] 升维，B 是 [4h, h] 降维。问题是：怎么把 A 和 B 切到 t 张卡上，且让通信尽可能少？

第一层的关键洞察是：把 A 沿列（输出维）切成 A = [A_1, A_2, …, A_t]，每块 [h, 4h/t]。那么 X·A = [X·A_1, X·A_2, …]——矩阵乘沿输出列的切分是完全独立的，rank i 只需自己的 A_i 和完整的 <code>X</code>，算出 Y_i = X·A_i（[s, 4h/t]）。更妙的是 GeLU 是逐元素的，GeLU(X·A) 的第 i 块就是 GeLU(Y_i)，所以非线性也能各算各的、无需任何通信：

\[X A = X\,[A_1 \mid A_2 \mid \cdots \mid A_t] = [X A_1 \mid X A_2 \mid \cdots \mid X A_t],\qquad \mathrm{GeLU}(XA) = [\,\mathrm{GeLU}(XA_1)\mid \cdots \mid \mathrm{GeLU}(XA_t)\,]\]

直白说

列切分之所以「免费」（前向不通信），是因为我们切的是输出维度：每张卡负责算出最终结果的不同几列，这些列之间互不依赖。再加上 GeLU 逐元素、不跨列混合，于是每张卡可以一路算到非线性之后都不用找别人要数据。

严谨说

严格地说：设 A=[A_1|A_2] 按列分块，则 XA=[XA_1|XA_2] 自动按列分块（矩阵乘的分块法则）。逐元素函数 f 满足 f([U|V])=[f(U)|f(V)]。故 GeLU(XA)=[GeLU(XA_1)|GeLU(XA_2)]，rank i 独立持有第 i 块 Y_i=GeLU(XA_i)，零通信。

列切分必须配一个完整的 <code>X</code>：每张卡都要有整份输入。这意味着输入 X 在进入这个 TP 块前，要么已经在每卡上复制（DP 维度天然如此），要么需要一次 all-gather。在 Megatron 的实现里，这对应前向的 f 算子是恒等（identity），把广播留给框架——记住「列切分的前向不通信，是因为输入已是完整的」这个前提。

3行切分 + all-reduce：一块只通信一次

行切分（row parallel）+ all-reduce：让一个块只通信一次

现在每张卡手上是 Y_i = GeLU(X·A_i)（[s, 4h/t]），第二层要算 Z = Y·B。如果把 B 也按列切，就得先把分散的 Y_i 拼回完整的 Y（一次 all-gather），不划算。Megatron 的神来之笔是：把 B 沿行（输入维）切成 B = [B_1; B_2; …; B_t]（竖着摞），每块 [4h/t, h]。这样 Y_i 的列数恰好对上 B_i 的行数，每张卡算一个部分和 Z_i = Y_i·B_i（[s, h]，已是输出的完整形状），而真正的结果是这些部分和之和：

\[Y B = [Y_1 \mid \cdots \mid Y_t]\begin{bmatrix}B_1\\ \vdots\\ B_t\end{bmatrix} = \sum_{i=1}^{t} Y_i B_i \;\xrightarrow{\;\text{all-reduce}\;}\; Z\ (\text{每卡一致})\]

这个求和正是模块 01 的 all-reduce！于是一个完整 FFN 块的通信账是：列切分（第一层，0 次）→ GeLU（0 次）→ 行切分（第二层，部分和）→ 1 次 all-reduce（把部分和加起来得到所有卡都一致的 Z）。整个 MLP 块前向只通信一次；反向传播对称地也只需一次 all-reduce（对输入梯度求和）。这种「列切→行切→一次 all-reduce」的配对，是 Megatron 把通信压到最低的核心设计。

为什么这样切最省？因为两次切分的方向是「互补」的：第一层切输出（结果天然分散在各卡），第二层切输入（恰好消费分散的结果），中间的分散状态一路保持、不需要拼回，只在最后把部分和汇总一次。如果两层切同一个方向，中间就得来回 gather/scatter，通信翻倍。让数据保持分片、推迟汇总到不得不汇总的那一刻——这是所有高效并行的通用智慧，和模块 02 的 ZeRO「推迟 all-gather」如出一辙。

自注意力（self-attention）的张量并行同理，只是切分维度更自然：把 Q/K/V 投影沿注意力头切分——每张卡负责一部分头的完整 Q_iK_i^T V_i 计算（头之间本就独立），输出投影 W_O 按行切，最后一次 all-reduce 汇总。所以一个 Transformer 层（attention + FFN）在 Megatron 下前向共 2 次 all-reduce（attention 一次、FFN 一次），反向 2 次。L 层就是 2L 次——这正是 TP 通信密集、必须放在 NVLink 内的原因。

直白说

注意力按头切几乎是「天造地设」：多头注意力本来就是若干个独立的注意力并排，把头分给不同卡，每张卡算自己那几个头，互不干扰，最后拼起来再投影。这也解释了为什么 TP 度通常取「能整除头数」的值（如 8 张卡分 64 个头，每卡 8 个头）。

严谨说

形式上：MHA(X)=Concat(head_1,…,head_n)W_O。把 n 个头分到 t 卡，rank i 算 head 子集并持有对应的 W_O 行块 W_{O,i}，得部分和 (Concat_i)W_{O,i}，all-reduce 求和即得 MHA(X)。结构与 FFN 的列切→行切完全一致。

4流水线并行：切层成 stage 与 bubble 问题

流水线并行：把层序列切成 stage

张量并行解决了「单层放不下」，但它通信太密（每层 2 次 all-reduce），TP 度做不大。当模型层数极多（如 96、128 层）、总参数远超单节点显存时，第二条路登场：pipeline parallelism。思路朴素得多——把模型的 L 层纵向切成 <code>p</code> 段（stage），stage 0 放第 0~L/p 层、stage 1 放下一段……每段放一张卡（或一组 TP 卡）。前向时，输入数据进 stage 0，算完把激活通过点对点（point-to-point）通信传给 stage 1，如此逐段流过；反向时梯度沿相反方向逐段回传。

PP 的通信代价极小：只在 stage 边界传一次激活（前向）和一次梯度（反向），且是点对点（send/recv），不是昂贵的集合通信。一个 [s, h] 的激活张量在边界传一次，相比 TP 每层 all-reduce 整个隐层，通信量小了好几个数量级。这就是为什么 PP 可以跨节点——边界带宽要求低，普通 InfiniBand 甚至以太网都扛得住。

朴素流水线（naive / GPipe 之前的 sequential）—— 同一时刻只有一个 stage 在干活： 时间 → t0 t1 t2 t3 t4 t5 t6 t7 stage0 [ F ] [ . ] [ . ] [ . ] [ . ] [ . ] [ B ] ... stage1 [ . ] [ F ] [ . ] [ . ] [ . ] [ B ] [ . ] stage2 [ . ] [ . ] [ F ] [ . ] [ B ] [ . ] [ . ] stage3 [ . ] [ . ] [ . ] [FB ] [ . ] [ . ] [ . ] F=前向 B=反向 .=空闲(idle)！ 4 个 stage，任一时刻 ≥3 个在发呆 —— 利用率仅 1/p
bubble 问题

朴素流水线有个致命病：bubble（流水线气泡）。因为 stage 之间有数据依赖（stage 1 必须等 stage 0 算完才能开始），在「填充」和「排空」流水线的阶段，大部分 stage 在空转。如果整个 batch 当成一个整体走流水线，利用率只有 <code>1/p</code>——切成 4 段反而每张卡只有 25% 的时间在干活，比单卡还慢！这显然不可接受，下一节的 micro-batch 就是为了治这个病。

这里要厘清一个常见误解：PP 切的是层，不是数据。所有 stage 处理的是同一份数据的不同阶段（像流水线工序），而不是像 DP 那样各处理不同的数据分片。所以 PP不减少单次前向的总计算量，它只是把模型摊到多卡以装下；真正的加速来自把 bubble 压下去之后、多个 stage 能并发处理不同 micro-batch。理解这一点，才能理解下一节为什么要把 batch 切碎。

5micro-batch 与 bubble 公式

micro-batch 与 bubble 公式

治 bubble 的办法是micro-batching：把一个 batch 切成 m 个micro-batch，让它们接连不断地灌进流水线。当 stage 0 算完第 1 个 micro-batch 传给 stage 1 后，它立刻开始算第 2 个，而不是干等。这样流水线一旦填满，所有 stage 就都在同时处理不同的 micro-batch——正是工厂流水线的精髓。这是 GPipe（Huang 2019）的核心贡献。

GPipe 风格（m=4 个 micro-batch 填充流水线，前向部分）： 时间 → t0 t1 t2 t3 t4 t5 t6 stage0 [F1] [F2] [F3] [F4] . . . stage1 . [F1] [F2] [F3] [F4] . . stage2 . . [F1] [F2] [F3] [F4] . stage3 . . . [F1] [F2] [F3] [F4] 填充期↑(bubble) ↑稳态:4 stage 全忙 ↑排空期(bubble) micro-batch 越多，中间「全忙」的稳态期越长，两头 bubble 占比越小

bubble 的占比可以精确算出来。设 p 个 stage、m 个 micro-batch，每个 micro-batch 在每个 stage 上耗时 1 个单位。填满流水线需要 p-1 步（填充），排空又需 p-1 步；而做完所有有用功需要 m + p - 1 步（最后一个 micro-batch 走完全程）。bubble 时间占比为：

\[\text{bubble fraction} = \frac{p-1}{m + p - 1}\]

这个公式是 PP 调优的命根子。代入数字：p=4, m=1（朴素）→ bubble 3/4=75%（利用率 25%，印证上一节）；p=4, m=8 → bubble 3/11≈27%；p=4, m=32 → bubble 3/35≈8.6%。micro-batch 越多，bubble 越小，但代价是激活显存随 m 增长（GPipe 要同时存 m 份激活等反向用）——这个权衡正是 1F1B 调度要破解的。

把 bubble 公式记成一句话：流水线越深（p 大）气泡越多，micro-batch 越多（m 大）气泡越被稀释。经验法则是让 m ≥ 4p（甚至 8p），把 bubble 压到 10% 出头。这也解释了为什么 PP 度不能太大——p 翻倍，要维持同样的 bubble 就得 m 也翻倍，激活显存跟着涨，迟早撑爆。所以 p 一般是个位数，靠 micro-batch 喂饱它。

61F1B 调度：压低激活显存峰值

1F1B 调度：把激活显存压下来

GPipe 把所有 micro-batch 的前向全做完、再统一做反向（F F F F … B B B B），这导致它必须同时保存 <code>m</code> 份激活（每个 micro-batch 的前向激活都要留着等它的反向用）。当 m 大时这是巨大的显存负担。1F1B（one-forward-one-backward，PipeDream/Megatron 采用）通过重排调度顺序解决了这个问题：流水线填满后，每个 stage交替地做一次前向、一次反向（F B F B …），让每个 micro-batch 的反向尽早执行、从而尽早释放它的激活。

1F1B（p=4）：填充后进入 F/B 交替稳态，激活峰值从 m 份降到约 p 份 stage0 F1 F2 F3 F4 B1 F5 B2 F6 B3 ... (做完 F 立刻穿插 B) stage1 F1 F2 F3 B1 F4 B2 F5 B3 ... stage2 F1 F2 B1 F3 B2 F4 B3 ... stage3 F1 B1 F2 B2 F3 B3 ... (最深 stage 最先开始 1F1B) 关键：B1 在 stage0 上很早就执行 → micro-batch 1 的激活早早释放

直白说

GPipe 像「把所有零件先全组装完，再统一质检」——半成品堆满仓库（激活显存爆）。1F1B 像「组装一个就质检一个」——仓库里始终只有少量半成品。两者的总工作量和 bubble 占比几乎一样，但 1F1B 的显存峰值低得多，所以能支持更深的流水线和更大的模型。

严谨说

严格地说：稳态下每个 stage 在任意时刻只需保存「已前向但未反向」的 micro-batch 激活。GPipe 这个数是 m（全部）；1F1B 是 ≈ p - rank（最多 p）。当 m ≫ p（为压 bubble 必须如此）时，显存节省达 m/p 倍。bubble 公式 (p-1)/(m+p-1) 两者相同。

更进一步的 interleaved 1F1B（Megatron 的「虚拟流水线」）把每张卡负责的层再切成几个不连续的小段（virtual stage），让一张卡在流水线里出现多次。这等效于增大了 p 而不增加物理卡数，把 bubble 公式里的填充开销进一步摊薄（bubble 降到约 (p-1)/(v·m+p-1)，v 是虚拟段数），代价是更多的点对点通信次数。前沿的 zero-bubble PP 甚至想把 bubble 干到接近 0，见第 8 节。

一个工程提醒：1F1B 的调度逻辑比 GPipe 复杂得多，要精确编排每个 stage 在每个时隙做哪个 micro-batch 的前向还是反向、何时 send/recv。这正是 Megatron-LM、DeepSpeed 这类框架的核心价值——把这套精密的流水线调度封装好，用户只需指定 pipeline_model_parallel_size 和 micro-batch 数。本模块 notebook 会用 numpy 把这套调度的时隙账（谁忙谁闲、bubble 多少、激活峰值多少）模拟出来，让你看清 1F1B 凭什么省显存。

73D 并行：DP × TP × PP 组合

3D 并行：DP × TP × PP 的组合

现实中的超大模型训练，从来不是单用一种并行，而是把三者组合成一个三维网格——这就是 3D parallelism（Narayanan 2021 在 Megatron-LM 上系统化）。每张卡同时属于三个维度：它是某个 TP 组的一员（和组内卡协作算每一层）、某条流水线的某个 stage、以及某个 DP 副本。总卡数 world_size = dp × tp × pp。比如 dp=8, tp=8, pp=12 就是 768 张卡的训练。

三个维度的排布不是随意的，而要顺着「通信频率 vs 互联带宽」匹配。核心原则见下表——这张表是分布式训练工程师反复用到的「摆放心法」：

维度通信模式频率放在哪典型度数
TP 张量并行all-reduce 整个隐层每层 2 次（极密）节点内 NVLink≤ 8（=单机卡数）
PP 流水并行点对点传激活每 stage 边界 1 次（稀疏）跨节点 InfiniBand数段~数十段
DP 数据并行梯度 all-reduce每 step 1 次（可重叠）最外层（跨节点）剩下的卡数

于是经典摆法是 「TP 在内、PP 居中、DP 在外」：先把 8 张卡用 NVLink 绑成一个 TP 组（吃掉最密的通信），再把若干节点用 PP 串成流水线（边界通信稀疏、容忍跨节点延迟），最后用 DP 复制整套来扩 batch（每步一次梯度同步、还能和反向重叠）。rank 到 (dp, pp, tp) 坐标的映射通常让 TP 维变化最快（相邻 rank 在同一节点内）：tp = rank % tp_size、pp = (rank // tp_size) % pp_size、dp = rank // (tp_size · pp_size)。这套坐标系是后面建通信组（process group）的基础，模块 05 会接着讲。

3D 并行的配置是个约束满足问题，错配会立刻 OOM 或慢成龟速。常见陷阱：(1) dp·tp·pp 必须恰好等于 world_size，不能多不能少；(2) tp_size 别超过单节点卡数（否则 TP 通信被迫走慢速跨节点链路，性能断崖）；(3) pp_size 要能整除层数、且留够 micro-batch 压 bubble；(4) global batch = dp × micro_batch × num_microbatch 要符合训练超参。本模块 notebook 的练习就是写一个合法的 rank ↔ (dp,pp,tp) 映射并验证往返一致。

有了 3D 还能再叠：序列/上下文并行切序列维（省激活，见下节）、专家并行（expert parallelism）切 MoE 的专家、ZeRO（模块 02）叠在 DP 维上分片优化器状态。现代框架（Megatron-Core、DeepSpeed、NeMo）把这些维度做成可自由组合的旋钮。但旋钮越多，搜索最优配置越难——这把我们带到本模块的最后一节：自动并行与前沿方向。

8研究前沿与开放问题

研究前沿与开放问题

  • 序列并行 / 上下文并行（sequence / context parallelism）：TP 没切到的 LayerNorm、Dropout、残差等逐元素算子的激活仍在每卡复制；序列并行（Korthikanti 2022）把它们沿序列维切开，进一步省激活显存。上下文并行（如 Ring Attention）则把超长序列的注意力沿序列维分块跨卡，是百万 token 上下文的关键。
  • zero-bubble pipeline（近零气泡流水线）：把反向再拆成「算输入梯度」与「算权重梯度」两部分，用权重梯度的计算去填 bubble，理论上能把 PP 的 bubble 压到接近 0（Qi 2023）。这是 PP 调度的最新前沿。
  • 自动并行（auto-parallelism）：3D+ 的配置空间巨大，手调既难又易错。Alpa（Zheng 2022）、GSPMD 等把「怎么切、怎么放」formulate 成优化问题，自动搜索最优并行策略。让编译器而非人来决定并行方案，是长期方向。
  • 专家并行与 MoE（expert parallelism）：MoE 模型把 FFN 换成多个专家 + 路由，专家并行把不同专家放不同卡，引入 all-to-all 通信（模块 01）。如何与 TP/PP/DP 协同、如何均衡专家负载，是当前大模型工程的热点。
  • 通信-计算重叠（overlap）：TP 的 all-reduce、PP 的 send/recv、DP 的梯度同步，能否被前后的计算「藏住」，直接决定扩展效率。算子级的重叠（如把 all-reduce 拆块与 matmul 流水）是榨干硬件的最后一公里，也接续模块 05 的扩展效率主题。

必读：Shoeybi 2019《Megatron-LM》（张量并行的奠基，列切/行切/一次 all-reduce 的来源）、Huang 2019《GPipe》（micro-batch 与 bubble）、Narayanan 2021《Efficient Large-Scale Language Model Training》（1F1B、interleaved、3D 并行的系统化）、Korthikanti 2022（序列并行）、Zheng 2022《Alpa》（自动并行）。完整清单与导读见 references.md。下一站模块 04 处理「这么多卡跑这么久，挂了怎么办」——checkpoint 与容错。
