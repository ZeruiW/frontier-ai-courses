1从零件到机器：为什么需要完整系统

前四个模块，我们把可扩展 agent 的四个核心零件各自从零造了一遍：模块 01 的 skill 加载器（按需加载的指令）、模块 02 的 slash 命令系统（用户显式触发的工作流）、模块 03 的 mini MCP（标准化的工具接口）、模块 04 的插件系统（把能力打包分发）。它们各自都能跑、都被 assert 验证过。但一个朴素的事实是：零件再漂亮，没装到一起就不是一台机器。本模块——也是全课的 capstone——要做的，就是把这四块严丝合缝地拼成一个完整的 skills 系统，再把它接到 agent 的决策循环上，让它端到端完成一个真实任务。

回到模块 00 立下的那条流水线：磁盘上的能力 → 发现 → 注册表 → 选择 → 注入/调用。前四个模块各自实现了这条线的某一段或某一类能力；本模块把它们统一成一条完整的、贯通的流水线，并补上最后、也最关键的一段——与 agent 循环集成：每一轮把命中的 skill 注入、把可用工具的 schema 提供给模型、执行模型选的工具、把结果回喂，直到任务完成。这是「拥有一堆能力」和「真的用这些能力做成一件事」之间的鸿沟。

本模块要让你建立的核心判断是：一个完整 skills 系统的价值，不在它收集了多少能力，而在它能否在面对一个具体任务时，恰当地『选择』出相关能力、并把它们『组合』起来执行。选择（selection）把「潜在能力」收敛成「本轮实际能力」；组合（composition）让多个能力协同完成一件单个能力做不到的事。这两个动作，是「完整系统」相对「单个零件」的全部增量价值——也是本模块代码的重心。

一句话抓住本模块：完整 skills 系统 = 把四个注册表（skill / command / tool）统一在一条『发现→选择→注入/调用』的流水线上，再接到 agent 循环里，让模型在一个任务中恰当地选择并组合能力。前四模块教你造零件，本模块教你把零件装成机器并发动它。难点不在任何单个零件，而在它们之间的接合：相关性怎么判、上下文怎么拼、工具怎么调、循环何时停、做得好不好怎么量。

注意渐进披露这条贯穿全课的原则在系统层再次出现：三个注册表常驻的都是「轻量目录」（skill 的描述、工具的名字+简介），完整内容（skill 正文、工具的详细 schema）一律命中后才加载。正是这条原则，让一个系统可以「拥有」成百上千个能力，却只为「本轮用到的」那几个付上下文成本——这是完整系统能 scale 的前提，也是模块 00 那条流水线一以贯之的设计。

可能有人会问：为什么是三个注册表，而不是把所有能力塞进一张大表？因为这三类能力的触发方式、生命周期、内容形态根本不同：skill 由模型按相关性自动触发、内容是给模型读的文本指令；命令由用户显式触发、内容是带占位符的 prompt 模板；工具由模型在循环中选中、内容是可执行函数 + schema。把它们分表管理，每张表才能用最合适的方式做发现、选择与注入——这与软件工程里「按职责分离关注点」是同一种判断。但三张表又共享同一条流水线骨架（发现→选择→注入/调用）与同一条原则（渐进披露），所以系统整体仍是统一的、可推理的，而非三个互不相干的子系统拼凑。理解这一点，你就抓住了「完整系统」既分而治之、又统于一道的设计精髓。

3选择：从潜在能力到本轮实际能力

选择：从『潜在能力』到『本轮实际能力』

系统启动后，三个注册表里躺着所有潜在能力。但面对一个具体任务，绝不能把它们全塞给模型——既贵，又会用无关的能力淹没真正相关的那几个。选择（selection）就是这一步收敛：给定任务，挑出相关的 skill、相关的工具、（若用户显式调用）要展开的命令。这是把「我会很多」变成「这次我用这几样」的关键动作。

最朴素的选择是关键词相关性：任务文本命中某个 skill 的 description 关键词，就选中它。真实系统则更进一步——让模型读一份「能力描述清单」自行判断哪些相关（本课用 MockLLM 模拟这个判断）。无论哪种，选择的产物都是一个相关能力的子集。

直白说

选择就像出门前按今天的安排收拾背包：去开会带电脑和笔记本，去爬山带水和外套——而不是把家里所有东西都背上。任务决定带什么；带得准，背包才轻、手才顺。

严谨说

形式上，选择是一个从「全部能力」到「相关子集」的映射 $\text{select}(\text{task}) \subseteq \text{registry}$。它的质量用召回（relevant 的有没有被选中）与精度（选中的是不是真 relevant）衡量。选择得好，下游的注入与调用才高效；选错了，要么漏了该用的能力、要么塞了一堆噪声。

选择的好坏直接可以量化，本课用两个经典指标。设某任务真正相关的能力集合为 $R$，系统选中的集合为 $S$：

\[\text{召回 recall} = \frac{|S \cap R|}{|R|}, \qquad \text{精度 precision} = \frac{|S \cap R|}{|S|}\]

召回低意味着「该用的能力没被选中」（任务可能因此失败）；精度低意味着「选了一堆无关能力」（浪费上下文、可能误导模型）。一个好的选择器要在两者间平衡——这与信息检索、推荐系统里的权衡完全同构。本模块 notebook 会在一个小任务集上用 assert 算出这两个指标，让「选择得好不好」从感觉变成数字。

4组合：让多个能力协同完成一件事

组合：让多个能力协同完成一件事

选出了相关能力，接着是组合（composition）：把它们协同起来完成任务。一个典型的组合是——一个 skill 提供「这类任务该怎么做」的指导（注入上下文），几个 工具 被模型依次调用来真正动手，可能还有一个 slash 命令 把整套流程一键发起。组合能力，是「完整系统」相对「孤立零件」的价值所在：单个工具只能做一件小事，组合起来才能完成一个有意义的任务。

以一个贯穿本模块 notebook 的例子说明：任务是「帮我把改动提交了」。完整系统的组合是：

  1. 选择：任务命中 git skill 的 description（『处理 git 提交、分支』）→ 选中 git skill；同时 tool_registry 里有 git_status / git_commit 两个工具。
  2. 注入：把 git skill 的正文（『写提交信息用祈使句、50 字内……』）注入上下文，并把两个 git 工具的 schema 提供给模型。
  3. 执行（组合）：模型据 skill 指导，先调 git_status 看改动、再调 git_commit 写一条规范的提交信息；系统执行每个工具、把结果回喂。
  4. 终止：模型确认提交完成，输出 final 文本。任务达成。

这条链里，skill 影响了模型怎么做（提交信息的风格）、工具让模型真的做成（执行提交）、循环把它们串成多步。这正是组合的精髓：不同种类的能力各司其职、协同推进，完成任何单一能力都完不成的任务。

组合里最常见的坑是选择与组合脱节：选中了 git skill 却没把它的正文注入上下文，或注入了 skill 却没把对应工具的 schema 提供给模型。结果模型「不知道该怎么做」或「没有手去做」，任务半途而废。正确的系统必须保证选中的每一类能力都被恰当地接入本轮上下文——skill 注入正文、工具提供 schema、命令展开模板，一个都不能漏。本模块的不变量检查会专门盯住这一点。

5与 agent 循环集成：让系统动起来

与 agent 循环集成：让系统动起来

有了选择与组合，最后一步是把整个 skills 系统接到 agent loop 上，让它真正动起来。这条循环就是模块 00 那张流水线的「注入/调用」段被反复执行：

def agent_run(task, system, llm, max_steps=6):
    # 1. 选择 + 注入：把命中 skill 正文 + 可用工具 schema 拼进上下文
    skills = system.select_skills(task)
    ctx = system.inject(skills) + '\n可用工具: ' + system.tool_specs_text()
    messages = [{'role': 'user', 'content': ctx + '\n任务: ' + task}]
    for step in range(max_steps):           # max_steps 守卫: 必须能停
        resp = llm(messages)                 # 模型决策(MockLLM/真实 Claude)
        if resp['type'] == 'final':          # 模型声明完成
            return resp['text'], messages
        result = system.dispatch(resp)       # 执行工具(组合的一步)
        messages.append({'role': 'assistant', 'content': resp})
        messages.append({'role': 'user', 'content': result})   # 结果回喂
    return None, messages                    # 超步数也要停, 不能死循环

这段循环把前面所有零件焊在了一起：select_skills 是选择、inject 与 tool_specs_text 是渐进披露的注入、dispatch 是模块 03 的工具分发、而 MockLLM（或换上真实 Claude）是那个读着 skill 指导、看着工具清单、决定下一步调什么的大脑。整门课到这里收口：你写的每一个零件，都在这条循环里各就各位地运转起来。

循环的纪律和模块 03 的工具调用一脉相承：必须能终止。终止条件有三：模型主动声明完成（输出 final）、达到 max_steps 上限、或任务被判定达成。漏掉 max_steps 守卫，一个状态不对的模型就能让循环空转到天荒地老——这是把一个能跑的 demo 变成一个可靠系统的分水岭。本模块的端到端测试会断言：循环在有限步内停下，且任务确实完成。

还要看清这条循环里信息是怎么单向流动又闭环的：第一轮，选择与注入把「该用哪些能力 + 这些能力怎么用」喂给模型；模型据此产出一个动作（tool_use）；系统执行动作、把观察（工具结果）回喂；模型基于新观察再决策……如此往复。每一轮模型的输入都比上一轮多了一条工具结果，于是它能看着前一步的结果决定下一步——这正是「组合多步」得以发生的机制。把这条循环和模块 00 的流水线图叠在一起看：流水线的「发现→选择→注入」是循环开始前的一次性准备，而「调用」这一段被循环反复执行，每次执行都把世界推进一步、把新状态带回模型。整门课讲的一切——按需加载的指令、标准化的工具、打包的插件——最终都是为了让这条循环里的每一步都有恰当的能力可用。

完整系统是各模块攻击面的总和

一个把整门课串起来的安全提醒：完整系统让外部内容（工具返回、MCP server 的结果、插件提供的能力）大量流入模型的决策上下文。其中任何一处不可信，都可能藏入恶意指令（间接提示注入），诱导 agent 做出非用户本意的动作；插件若不做命名空间隔离（模块 04），还可能用同名能力悄悄劫持调用。所以一个完整 skills 系统的安全，是前四模块安全考量的总和：skill 来源可信、工具返回当数据而非指令、插件隔离、高危工具加确认。能力越强、接入越多，这条防线越是用 agent 的前提而非可选项。

6评测：好不好用数字说话

评测：这个系统好不好，用数字说话

一个完整系统造好了，怎么知道它好不好？靠感觉不行，要靠evaluation。本课用一个小任务集 + assert，从四个维度量化它：

  • 召回 recall：每个任务真正相关的能力，有没有被选中？低召回 = 漏掉该用的能力 = 任务易失败。
  • 精度 precision：选中的能力，是不是真相关？低精度 = 塞了一堆噪声 = 浪费上下文、可能误导。
  • 任务完成率 task completion：端到端跑完，任务到底有没有达成？这是最终的、最重要的判据——前面都对、最后没做成也是白搭。
  • token 用量 token budget：完成任务用了多少上下文？渐进披露做得好，用量就低；做不好（如把所有 skill 正文全注入），用量就爆。

这四个维度构成一个朴素但完整的评测面板。它们之间常有张力：为提高召回可以多选能力，但精度和 token 用量会下降；为省 token 可以少注入，但召回可能掉。好的系统在这四个维度上取得平衡，而评测就是让这种平衡变得可见、可比较、可优化。本模块 notebook 会在一个确定性任务集上把这四个数算出来，并用 assert 钉住「系统达到了预期水平」。

直白说

评测就像给装好的机器做体检：转速够不够（召回）、有没有空转零件（精度）、活儿到底干完没（完成率）、费了多少电（token）。体检表上是数字，不是「感觉还行」——下次改了零件，一对比就知道是进步还是退步。

严谨说

形式上，评测是在一个标注好的任务集 $\{(\text{task}_i, R_i)\}$ 上，对每个任务跑系统、记录选中集 $S_i$、是否完成 $c_i$、token 用量 $t_i$，再聚合成平均召回、平均精度、完成率 $\frac{1}{n}\sum c_i$、平均 token。本课的任务集虽小且确定，但评测的方法与真实 agent 评测（如 τ-bench 式的任务-工具-用户交互评测）一脉相承。

把评测纳入系统，意味着你对「可扩展 agent」的理解从「能加能力」升级到了「能加能力、且知道加得好不好」。这正是工程成熟度的体现——也是本课希望你带走的、超越任何具体框架的判断力。

最后一句方法论的话作结：本课全程用 MockLLM + 对拍 + assert，把焦点钉在协议、控制流与正确性这些不随模型与厂商过时的硬功夫上。你验证过的每个零件，把 MockLLM(...) 换成 make_llm(model='claude-sonnet-4-6')（有 key 走真实 Claude、无 key 自动回退）就能接到真实模型；把内存 stdio 换成真实管道就能接到真实 MCP。结构对了，迁移就是换一行——这就是「亲手造一遍」最大的回报。

8研究前沿与开放问题

研究前沿与开放问题

  • 能力选择的规模化：当 skill / 工具 / 插件数以千计，关键词或一次性塞清单都不够。如何让模型按需检索能力（tool search、skill 检索）、动态加载，而非一次塞满上下文，是完整系统长大的必答题——渐进披露的下一个前沿。
  • 选择的智能与可解释：相关性判断从关键词走向语义检索、再走向让模型自己规划「这个任务需要哪些能力」。如何让选择既准又可解释（为什么选了这个 skill），是评测与调试的基础设施难题。
  • 组合的自动化：目前组合多由模型在循环里临时决定。能否让系统学会「这类任务的标准能力组合」（类似 workflow 模板），在自由组合与固定流程间取得平衡，是 agent 工程的活跃方向。
  • 跨能力的冲突与协调：多个插件提供功能相近的能力时，系统如何选择、如何避免冲突（命名空间只是第一步）、如何在它们之间路由，尚无定论。
  • 可靠性与评测：单步看着行的系统，在长任务、多能力组合下可能崩（pass@k 高但 pass^k 低）。如何构造可复现的任务集、可自动验证的完成判据、并量化可靠性，是把完整系统推向生产的关键（与本系列评测课相通）。
  • 安全与权限的统一治理：能力越多、接入越广，攻击面越大。如何在系统层统一治理——可信来源、最小权限、数据/指令分离、高危确认、监控——而非每个零件各自为政，是完整 skills 系统从「能用」到「敢放生产」的最后一公里。

必读：Anthropic Agent Skills 文档（skill 系统）、Claude Code slash commands / plugins 文档（命令与插件的组装）、MCP 规范（modelcontextprotocol.io，能力接入）、Tool search tool（能力的规模化选择）、以及渐进披露这一贯穿全课的原则。完整清单见 references.md。本模块是前四模块的综合，回看它们的前沿小节，会看到它们最终都汇入「如何让一个 agent 可靠地拥有、选择、组合大量能力」这一个问题。
