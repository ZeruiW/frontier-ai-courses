1保证输出合法的三条路

模块 01 把「解析失败」量化了。这一节给出三条修法，它们的成本与副作用完全不同。

路怎么做成本解析率能到 1.0 吗副作用
重试解析失败就重新采样期望 $1/p$ 次调用；$p$ 小时爆炸不能保证（可能一直失败）选择偏倚——被重试掉的样本不是随机的（第 5 节）
修复对不合法的输出做后处理（补括号、抽取、映射）近零不能保证可能改变语义——修得越激进越危险（第 6 节）
约束（受限解码）在每一步把不合法的 token 的 logit 设成 $-\infty$近零（一次掩码计算）能——不合法输出在生成时就不可能产生分布失真——本模块第 3 节会把它精确算出来

直白说

约束是唯一能把解析率保证到 1.0 的路，而且它同时消掉了重试的偏倚与修复的语义风险。所以在能用约束的地方，它应当是默认选择。但它不是免费的：它换来的是一个更微妙的问题——分布失真。

严谨说

三条路的关系不是「三选一」，而是有优先级的组合：能约束的字段用约束（枚举、数值、正则、JSON schema）；约束不了的部分（自由文本）用修复兜底；两者都失败时才重试，而且重试次数与结果必须被记录。这个顺序不能反：先重试再考虑约束，等于用钱买一个本可以免费拿到的性质。

一条判断能不能上约束的实用问题：「你的输出规范能写成一个正则或 JSON schema 吗？」能 → 直接约束；不能（比如「一段自然语言的解释」）→ 那部分只能修复兜底。而大多数结构化任务的输出大部分是可约束的——枚举标签、数值区间、字段名、括号配对。

2受限解码的机制：掩码 + 状态机

每一步的三件事 1. 模型给出 logits over vocab [v0, v1, …, v_{|V|-1}] 2. 语法状态机告诉你哪些 token 合法 mask ∈ {0, 1}^{|V|} 3. 把非法位置设成 -inf，再 softmax p_i ∝ exp(v_i) · mask_i 状态机从哪来： 正则 / CFG / JSON schema ──编译──► FSM（状态 × token → 状态 或 ⊥） 每一步：当前状态 + 候选 token → 有后继状态就合法 关键性质：**掩码是"这一步这个 token 能不能出现"， 而不是"选了它之后还能不能合法收尾"** —— 第 3 节的失真就来自这里。

直白说

掩码的构造有一个容易忽略的要求：合法的定义必须是「存在一条路径能走到接受状态」，而不是「这一步在语法里出现过」。前者需要在 FSM 上做一次可达性分析（哪些状态能到接受态），后者只看局部转移——用后者会产生「走到一半发现无路可走」的死局。

严谨说

工程上的实现要点：掩码要能被缓存。状态数通常远小于序列数，所以 (状态) → 允许的 token 集合 是一张可以预计算的表。这让约束的运行时开销接近零——这也是为什么第 1 节的表里它的成本写「近零」。而 tokenizer 会带来一个真实的复杂度：同一个字符串可能有多种 token 切分，所以 FSM 要建在 token 层而不是字符层（Outlines 这条线的主要工程贡献就在这里）。

3逐步掩码 ≠ 条件分布（本模块的核心）

这一节是本模块存在的理由。受限解码通常被理解成「从模型分布里只保留合法的部分」——而这个理解是错的。

\[P_{\text{mask}}(y) \neq P_{\text{model}}(y \mid y \in \mathcal{S})\]

直白说

为什么不等？因为逐步掩码在每一步只看「这一步哪些 token 合法」，它不知道「选了这个 token 之后，还有多少概率质量能合法收尾」。两个分支在这一步的概率相同，但一个分支之后大概率跑偏、另一个大概率能收好尾——真实的条件分布会偏向后者，而逐步掩码不会。

严谨说

notebook 第 3 节用一个可以全量枚举的玩具 LM 把两个分布精确算出来。结果：真实条件分布 {bug: 0.188, feature: 0.562, other: 0.250}，逐步掩码 {bug: 0.083, feature: 0.750, other: 0.167}，$\mathrm{KL} = 0.081$ nat，而 bug 被低估了 2.3 倍。机制在例子里是显式的：bug 被选中的概率低（0.05），但它之后「正确收尾」的概率高（0.90）；逐步掩码只看见前者。

为什么 bug 被低估 在 {"label":" 之后，模型给出： bug 0.05 feature 0.45 other 0.10 oops 0.40 逐步掩码：去掉 oops，归一化 → bug 0.083 feature 0.75 other 0.167 ↑ 到此为止，不再往后看 真实条件分布：还要乘上「之后能合法收尾」的概率 bug : 0.05 × 0.90 = 0.045 feature : 0.45 × 0.30 = 0.135 other : 0.10 × 0.60 = 0.060 归一化 → bug 0.188 feature 0.562 other 0.250 **bug 是一个"不常被想起、但一旦想起就写得对"的选项。** 逐步掩码看不见它的这个优点。

失真的唯一来源：分支之间的收尾能力差异

这一点值得单独立一小节，因为它与直觉相反。notebook 练习 2 会精确证明两件事：

  1. 如果所有分支的「下游收尾概率」相同，那么逐步掩码 恰好等于 条件分布——$\mathrm{KL} = 0$，无论被掩掉了多少质量。被掩掉 56% 还是 91%，KL 都精确地是 0。
  2. 失真随「分支之间收尾概率的差异」增长。把某个分支的收尾概率从 0.60 压到 0.15，KL 从 0.007 涨到 0.270（近 40 倍）。

所以「语法越紧失真越大」这个直觉是错的：紧不紧（掩掉多少）根本不影响失真；只有「不同分支之后有多容易合法收尾」才影响。这也给出了一个实用的判断：如果你的语法在所有分支之后的结构都一样（比如枚举一个标签然后固定收尾），那么失真为零，可以完全不管它。

这个失真什么时候重要

  • 分支之后的结构不同时才有失真——比如联合类型、可选字段、变长数组：选了 A 之后还要写很多东西、选了 B 之后马上就能收尾。
  • 只取 argmax（贪心/温度 0）时通常不重要——因为失真改变的是概率，而 argmax 常常不变。这也解释了为什么大多数生产系统没被它咬到：它们跑温度 0。
  • 需要采样多个候选、或需要用概率做后续判断时重要——best-of-n、自一致性投票、把 logprob 当置信度。这些场景下失真会系统性地偏向「容易开头但不容易收尾」的分支。

修正它需要在解码时做前瞻（估计每个分支的「可完成质量」），而那很贵——这是 grammar-aligned decoding 这条研究线在做的事。工程上的现实结论是：知道它存在、知道它在什么条件下重要，并在那些条件下不要把掩码后的概率当成条件概率来用。

4从 JSON schema 编译到掩码

实践里最常用的约束来源是 JSON schema。它的四类约束各自对应一种掩码。

schema 约束掩码怎么做注意
枚举 enum: [...]在值的位置只允许能前缀匹配某个枚举项的 token最有价值的一类——它直接把模块 01 的「取值域」变成硬保证
类型 type: integer只允许数字 token；小数点/负号按类型放行区间约束（minimum）无法完全用掩码表达——前几位数字合法但整体越界；只能生成后校验
必填字段 required状态机在字段未齐时不允许 }这一条把「缺字段」这类解析失败彻底消掉
字符串格式 pattern正则编译成 FSM复杂正则的 FSM 会很大；要缓存

直白说

第二行那个例外值得记住：区间约束不能完全用掩码表达。「生成一个 0 到 1 之间的数」时，掩码可以保证它是一个合法的小数，但不能保证它 ≤ 1（0.9 的前缀 0. 与 7.5 的前缀 7 在字符层都合法）。所以「不变量校验」这一步（模块 01 的 signature）不能被约束替代。

严谨说

还有一个纯工程的坑：schema 与解析器必须由同一个来源生成。手写 schema 给模型、手写解析器读结果，两者会漂移——而模块 01 练习 1 的第 3 项检查正是抓这个。正确做法是从一个类型定义（pydantic / dataclass）同时导出schema、掩码与解析器。

5重试的选择偏倚（定量）

模块 01 第 6 节定性地说明了它。这一节给出定量结果与成本。

\[\mathbb{E}[\text{calls}] = \frac{1}{p_{\text{parse}}}, \qquad \mathbb{E}[\text{correct} \mid \text{parse ok}] > \mathbb{E}[\text{correct}]\]

直白说

成本：期望调用次数是 $1/p$。$p = 0.9$ 时是 1.11 次（可以接受）；$p = 0.5$ 时是 2 次；$p = 0.2$ 时是 5 次。而「重试上限」把它变成一个截断分布：上限 $R$ 时仍有 $(1-p)^R$ 的比例最终失败。

严谨说

偏倚：解析成功与答对正相关（都受样本难度影响），所以在解析成功的子集上算准确率会高估。notebook 第 5 节把这个偏差量出来。而受限解码让 $p = 1$，于是成本回到 1 次、偏倚消失——这是「约束优于重试」最直接的论证：它同时便宜且无偏。

如果必须重试（约束不可用时）

  1. 重试的触发条件只能是「解析失败」——不能是「结果看起来不对」（那是在用真值调参，与 C68 模块 02 的重试纪律同构）。
  2. 报分的分母是全部样本，最终失败记为错。
  3. 重试次数的分布必须进报告——它是成本，也是「解析率其实不是 1.0」的证据。
  4. 重试要带温度扰动——温度 0 时重试会得到完全相同的输出，等于白花一次钱。而这又意味着重试引入了不确定性，于是配置的可复现性下降（C68 模块 02 的老问题）。

6修复：可行与有害的两种情形

修复动作可行吗为什么
去掉 markdown 代码块围栏可行纯语法层，不触碰内容；而且它对应模块 01 的「禁止项」槽位
去掉前后的解释文字，抽取 JSON 块可行同上；用「第一个 { 到匹配的 }」定位
补上缺失的右括号谨慎可能把一个被截断的输出补成一个「看起来完整」的错误结果——而截断通常意味着 max_tokens 不够，那是一个应当被发现的配置问题
把不在枚举里的值映射到最近的合法值有害它把「模型不知道答案」伪装成了「模型给了一个答案」；而下游无法区分这两者
用另一个模型把输出改写成合法格式有害（通常）引入第二个不确定环节，且错误传播变成乘法（模块 01 第 3 节）；能用约束的地方绝不该用这个

直白说

分界线很清楚：只做语法层的清洗，不做语义层的猜测。去围栏、抽 JSON 块是语法；把 BUG 映射成 bug 是灰色（大小写可以规范化）；把 maybe_bug 映射成 bug 是语义猜测。

严谨说

还有一条记录纪律：修复必须被记录，而且被修复过的样本要能被单独统计。因为「修复率」是一个健康指标——它上升通常意味着 prompt 的格式槽位或模型行为变了，而如果修复是静默的，这个信号就丢了。这与 C68 模块 02 的「失败分类必须报告比例」是同一条。

7选择树

输出规范能写成正则 / JSON schema 吗？ │ ├─ 能 ────► **用受限解码**（解析率保证 1.0） │ │ │ ├─ 需要采样多个候选 / 用 logprob 当置信度？ │ │ ├─ 是 → 注意第 3 节的分布失真，别把掩码后的概率当条件概率 │ │ └─ 否（温度 0 取 argmax）→ 失真通常不影响结果 │ │ │ └─ 有区间/跨字段不变量？→ 生成后仍要做 validate（掩码表达不了） │ └─ 不能（输出含自由文本） │ ├─ 把**可约束的部分**单独成字段并约束它 │ （比如 {"label": <枚举>, "reason": <自由文本>}） │ ├─ 自由文本部分用**语法层修复**兜底（去围栏、抽 JSON 块） │ └─ 仍然失败 → 重试（带温度扰动 + 上限 + 记录次数） └─ 报分的分母仍然是全部样本

这棵树的形状本身是结论：约束在最上层、修复在中层、重试在最下层，而「把可约束的部分拆成独立字段」是一个几乎总是值得做的重构——它把一次「全或无」的解析变成「结构化字段有保证 + 自由文本尽力而为」。

门禁（按 C68 模块 04 分级）

  • 确定性阻断：schema 与解析器不是同源生成的；启用了约束但 parse_rate < 1.0（说明掩码有 bug）；required 字段在 schema 里但掩码没实现
  • 统计阻断：修复率或重试率相对基线上升超过阈值
  • 报警：修复率 > 0 且在上升（它是格式槽位或模型行为变化的早期信号）

最后一条确定性检查值得单独说：「启用了约束但解析率不是 1.0」是一个逻辑矛盾——约束的定义就是不合法输出不可能产生。所以它出现时一定是实现有 bug（掩码漏了某条规则、或者约束根本没生效），而这是一个零误报的检查。

8tokenizer 带来的复杂度

前七节把掩码当成「token 集合」来处理。而把语法从字符层搬到 token 层，是这一层最真实的工程难点。

问题：同一个字符串有多种 token 切分 目标：输出 "feature" 可能的切分: [feature] | [feat][ure] | [f][eature] | [fe][at][ure] … 如果掩码只允许 [feature] 这一个 token， 那么当模型倾向于先出 [feat] 时，这条路被掩掉了 —— **而它本来能走到一个合法结果**。 于是掩码必须允许「任何能拼出某个合法后续的 token」， 也就是要在 token 层重建 FSM，而不是在字符层。

直白说

这不是理论问题，它有两个真实后果。① 掩码过严 → 把合法路径掩掉 → 模型被迫走一条概率更低的路，输出质量下降（而这看起来像「加了约束效果变差了」）；② 掩码过松 → 生成出无法回到合法状态的前缀 → 死局（练习 1 那个问题的另一种形态）。

严谨说

正确做法是预计算一张 (FSM 状态) → (允许的 token 集合) 的表，其中「允许」的定义是：这个 token 的字符串是某条合法路径的一个前缀片段。状态数远小于序列数，所以这张表可以在启动时算好并缓存——这也是为什么受限解码的运行时开销可以接近零。而这张表依赖具体的 tokenizer，所以换模型时要重算（模块 05 会把这一点归到「保留但需重测」那一档）。

一个实践建议：不要自己实现 token 层的语法编译。用 Outlines / xgrammar / GBNF 这类成熟实现——它们的主要价值恰恰在这个又琐碎又容易出错的地方。本课从零实现的是「掩码的语义」，不是它的高效实现。

9API 上的 structured output 与 tool-calling

拿不到 logits 时，还有一条路：服务方提供的 structured output / tool-calling —— 它们内部就是约束。

形式它给你什么要注意什么
JSON mode保证输出是合法 JSON只保证语法，不保证 schema——字段名、枚举值、类型仍然要自己 validate
schema-constrained output保证符合给定 JSON schema区间约束（minimum）通常不被保证（第 5 节的那个例外）；而 schema 的哪些关键字被支持要查文档
tool-calling保证参数符合工具的参数 schema它同时改变了模型的行为（模型知道自己在「调工具」），所以它与「输出 JSON」不是等价的两种写法——效果要分别测

直白说

三者的共同点：它们把「保证」从你这边移到了服务方那边。好处是省事；代价是你不知道它内部怎么实现的——包括本模块第 3 节那个分布失真是否被修正过。所以在采样多候选或用 logprob 当置信度的场景下，仍然要按「可能有失真」来对待。

严谨说

还有一条纯工程的纪律：无论用哪种形式，本地仍然要跑一次 validate。理由有三个：区间与跨字段不变量通常不被保证；服务方的实现可能在某些边缘情况下失效；而且这一步让你的解析率指标是自己测出来的，而不是相信来的。「启用了约束但解析率不是 1.0」这个矛盾（练习 4 的第一条检查）只有在你自己 validate 时才可能被发现。

10本模块的四条可执行结论

  1. 能约束的字段全部上约束。它是唯一能把解析率保证到 1.0 的路，同时消掉重试的成本（$1/p$）与偏倚。而它还是可迁移的——换模型时它原样保留（模块 05）。
  2. 把可约束的部分拆成独立字段。比如 {"label": <枚举>, "reason": <自由文本>}——这把一次「全或无」的解析变成「结构化字段有保证 + 自由文本尽力而为」，是一个几乎总是值得做的重构。
  3. 不变量校验不能被约束替代。区间约束（0 ≤ x ≤ 1）无法用逐步掩码表达，而跨字段的约束更不行。所以模块 01 的 signature.validate 这一步永远保留。
  4. 在三类场景下不要把掩码后的概率当条件概率：采样多个候选（best-of-n）、自一致性投票、把 logprob 当置信度。而判断有没有失真的判据很具体：看语法在不同分支之后的结构是否相同——相同则失真恰好为 0（练习 2），不同则要小心。

直白说

这四条里第 2 条最容易被忽略，而它的收益最直接。很多系统的输出是「一段带解释的自然语言，里面藏着一个结论」，于是解析永远是概率性的。把结论抽成一个枚举字段之后，那部分就变成了确定的——而解释部分即使解析失败，也不影响结论可用。

严谨说

第 4 条的判据值得再说一次，因为它把一个抽象结论变成了一次检查：如果你的 schema 是「一个枚举 + 固定的收尾」，那么所有分支之后的结构相同，失真恰好为 0，可以完全不管它。需要警惕的是联合类型、可选字段、变长数组——那里「选了 A 还要写很多、选了 B 马上收尾」，而这类 schema 恰恰是最常见的复杂输出形态。
