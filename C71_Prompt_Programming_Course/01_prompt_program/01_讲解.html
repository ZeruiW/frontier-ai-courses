1签名先于 prompt

模块 00 把一次调用拆成了四个部件。这一节再往前一步：先定义契约，再写 prompt。

Signature（契约） prompt（实现） inputs: {feedback: str} 「把用户反馈分类。 output: {label: Label, 标签只能是 bug / feature / … reason: str} 输出 JSON：{"label": …, "reason": …}」 Label: bug|feature|billing| account|other ↑ 这一段是**可替换的** parse: json → validate 而上面那个契约不是 关系：**一个签名可以有很多种 prompt 实现**（模块 03 的搜索空间就是它们）； 而换 prompt 不该改签名 —— 改签名意味着下游要改。

直白说

为什么这个顺序重要？因为签名是可以被机械检查的，而 prompt 不是。「输出必须是这五个标签之一」是一个断言；「这段指令写得清楚吗」不是。把契约独立出来之后，你得到了一个不依赖任何模型就能跑的测试——而这是这一层能进 CI 的前提。

严谨说

更实际的一点：签名决定了「解析失败」这件事是否可判定。没有取值域声明时，parse 只能返回模型说的那个字符串，而「模型自创了一个标签」与「模型答错了」无法区分。有取值域之后，前者变成 None，后者变成一个错标签——两个不同的失败，两套修法（模块 00 第 4 节量过：一个是 100% 解析失败，一个是准确率掉一半）。

签名的四个字段，每一个都有具体用途

字段内容谁用它
inputs输入字段名与类型渲染器；以及组合时的类型检查（第 3 节）
output输出字段名解析器；它必须与格式规范里的字段名一致——不一致是一个真实的 bug 源
domain（取值域）枚举、区间、正则或 schema解析器的合法性判定；以及模块 04 的解码约束
invariants（不变量）跨字段的约束，比如「reason 非空」「置信度在 [0,1]」它抓的是「格式对但内容荒谬」这一类，比如 confidence = 7.5

一个立刻可用的检查：把签名里的取值域和指令里出现的取值域做字符串比对。不一致 → 阻断。这一项是确定性的、零误报的，而它防住的是模块 00 第 4 节那个「解析失败率 100%」的故障。

2三个量必须一起报（这一节给出为什么）

模块 00 已经引入了三个量。这一节说明为什么它们不能互相替代——以及为什么只报端到端会让优化走向错误的方向。

\[\text{end-to-end} = \underbrace{P(\text{parse ok})}_{\text{契约层}} \times \underbrace{P(\text{correct} \mid \text{parse ok})}_{\text{能力层}}\]

直白说

这是一个乘法分解，而两个因子的改进手段完全不同。第一个因子靠指令、格式规范、解码约束提高（便宜、确定、可以做到 1.0）；第二个因子靠示例选择、更强的模型、微调提高（贵、不确定、有上界）。只报乘积时，你不知道该动哪一个。

严谨说

更糟的是：只报乘积会让某些「改进」看起来有效而实际有害。例子：把取值域放宽（允许模型输出任意字符串）会让解析率变成 1.0，于是端到端上升——但这只是把「解析失败」重新标记成了「答错」，而下游拿到的是一个不在枚举里的值，可能直接崩。三个量一起报时，这个「改进」会立刻暴露：解析率 1.0 而 acc-given-parsed 掉了。

情形parse_rateacc\|parsedend-to-end该做什么
契约没定清0.0–0.6可能很高低先修契约（指令写全取值域、规定格式）；不要碰示例
能力不够1.0低低示例选择（模块 02）→ 自动优化（模块 03）→ 才考虑换模型
部分解析失败0.6–0.95偏高（有偏）中最危险：被丢掉的样本不是随机的（第 5 节）
健康1.0高高看分层指标找残余问题

第三行的「偏高」是一个真实的估计偏差：解析失败的样本往往是模型「更不确定、更想多说话」的那些，而它们也更可能答错。所以在解析成功的子集上算准确率，系统性地高估了模型的能力。第 5 节会量出这个偏差，模块 04 会给出修法。

3组合：错误传播是乘法

把一个任务拆成两步（先粗分再细分）是一个很自然的想法。但它有一个不那么直观的代价。

单级 两级 feedback ──► [5 分类] ──► label feedback ──► [是不是技术问题?] ──┬─► [bug/feature] └─► [billing/account/other] 两级的端到端准确率 = P(第一级对) × P(第二级对 | 第一级对) 0.90 × 0.90 = 0.81 ← 两个「都挺好」的模块，合起来是 0.81 0.95 × 0.95 = 0.90 三级: 0.95³ = 0.857

直白说

错误传播是乘法，所以级数是一个成本。而人们拆分任务的直觉通常是「每一步更简单所以每一步更准」——这没错，但要赢下来，每一步的准确率提升必须补偿掉多乘一次的损失。notebook 第 3 节在同一个任务上把单级与两级都跑一遍，结果是单级更好——这在小标签集上很常见。

严谨说

什么时候两级会赢？三种情况：① 第一级近乎无误（比如靠规则而不是模型判定），于是乘法的损失接近 0；② 子任务的标签集差异很大，合成一级会让指令与示例互相干扰；③ 子任务需要不同的上下文（比如一支只需要产品文档、另一支只需要账务规则），合成一级会让每次调用都带上两倍的上下文。反过来说：如果三条都不成立，就不该拆。

组合时必须显式处理的三件事

  1. 类型检查：上一级的 output 必须能喂进下一级的 inputs。这是签名的直接用途，而它可以在不调用模型的情况下检查。
  2. 解析失败的传播：上一级解析失败时，下一级根本不该被调用。否则你会把 None 渲染进下一级的 prompt——而那通常表现为「模型答了一个莫名其妙的东西」，很难定位。
  3. 每一级的三个量都要分别记录。只记端到端时，「第一级解析失败率上升」这件事在指标上表现为「整体效果下降」，而你会去优化第二级。

一个具体的反模式：把「重试」当成一级。「解析失败就重试三次」看起来是提高鲁棒性，但它同时改变了你的样本分布——第 5 节会量出这个偏倚，而模块 04 会说明为什么约束优于重试。

4指令的五个槽位

指令看起来是一段自由文本，但它实际上有五个功能不同的槽位，而每个槽位缺失的症状不一样。

槽位内容缺失的症状严重程度
① 任务要做什么输出跑题；但通常示例能救回来中
② 取值域标签集 / 值域 / schema模型自创值 → 解析失败率 100%致命
③ 输出格式怎么输出、字段名部分解析失败（最麻烦的一种）高
④ 边界与兜底「都不符合时输出 other」「信息不足时输出 unknown」模型被迫在不合适的选项里挑一个，于是错误集中在边缘样本上高
⑤ 禁止项「不要解释」「不要输出 markdown 代码块」输出里裹了一层 ```json，解析器要么处理它要么失败中

直白说

第 4 个槽位最容易被忘，而它的症状最容易被误读。没有兜底选项时，模型必须在给定的类里挑一个，于是「其实不属于任何一类」的样本会被随机分配。在指标上这表现为「某几个类的精确率低」，而实际原因是缺一个 other。

严谨说

第 5 个槽位（禁止项）值得单独一提：它是唯一一个「不加也能工作，但加了能显著降低解析器复杂度」的槽位。每一条禁止项都对应解析器里的一段清洗代码——去代码块围栏、去前后解释、去 markdown 加粗。把它写进指令，等于把清洗成本从每次调用移到一次性的一句话上。但也不要指望它 100% 生效——解析器仍然要能处理没生效的情况。

notebook 第 2 节把五个槽位逐个删掉，量出每一个的边际贡献。结论是取值域与格式两项占了绝大部分，而它们恰好是最便宜、最确定的两项——这也解释了为什么「先修契约」是正确的顺序。

5输出格式三选：不是越结构化越好

格式例子解析鲁棒性成本什么时候用
裸值bug只要模型多说一个字就失败最低（几个 token）配上解码约束时最优（模块 04）；不配约束时最脆
JSON 单字段{"label": "bug"}较好；能容忍前后有解释（可以正则抽取）低默认选择
JSON 多字段（带理由）{"reason": "…", "label": "bug"}好；而且字段顺序会影响质量高（理由的 token 数远超标签）需要可解释性、或需要理由参与后续判断时

直白说

「带理由的 JSON」有一个容易被忽略的设计点：字段顺序。把 reason 放在 label 之前，模型在生成标签时已经写过理由；反过来则理由是对已给答案的事后合理化。这两者在质量上通常不同，而它是一个纯粹的格式设计选择。notebook 不模拟这个效应（它需要真实模型的自回归性质），但工程上必须知道「字段顺序是一个可调项」，并把它写进指纹。

严谨说

另一个反直觉的点：更结构化不一定更鲁棒。嵌套很深的 schema 会引入更多可能出错的地方（少一个括号、字段名拼错、类型不对），而解析失败是全或无的。所以 schema 的复杂度应当由下游真正需要的字段决定，而不是「顺便多要几个」。每多一个字段，就多一个解析失败的入口。

一条实用的规则：先用 JSON 单字段跑通并把解析率做到 1.0，再考虑加字段。而每加一个字段都要重新量解析率——它不会自动保持 1.0。

6重试的选择偏倚（初探）

解析失败时重试，是几乎所有系统的默认做法。它有效，但它会改变你测到的分布。

直白说

机制：「重试直到解析成功」会系统性地丢掉那些「模型倾向于不按格式回答」的样本。而这些样本通常是模型更不确定的那些，也就是更可能答错的那些。于是在「解析成功」的样本上算准确率，会高估真实能力。

严谨说

形式化：设样本的难度是 $d$，解析成功概率 $P(\text{parse} \mid d)$ 随 $d$ 递减，正确概率 $P(\text{correct} \mid d)$ 也随 $d$ 递减。则条件期望 $E[\text{correct} \mid \text{parse ok}] > E[\text{correct}]$——因为条件化在一个与正确性正相关的事件上。notebook 第 5 节把这个偏差量出来：只在解析成功的样本上报分，比真实端到端高出可观的一截。

三条纪律

  1. 重试的次数与最终是否成功必须被记录，而且报告里要写明「N 个样本经过重试」。这与 C68 模块 02 的「失败分类必须报告比例」是同一条。
  2. 报分的分母必须是全部样本，解析失败记为错。「在解析成功的样本上准确率 92%」这句话可以说，但不能单独说——它必须与解析率一起出现。
  3. 重试的触发条件只能是「解析失败」，不能是「结果看起来不对」。后者是在用真值调参——与 C68 模块 02 的「重试只能看异常类型，不能看判分结果」完全同构。

而根本的修法是模块 04 的解码约束：让不合法的输出在生成时就不可能产生，于是解析率恒为 1.0，重试与它带来的偏倚一起消失。

7变更即发布

prompt 是唯一一处「改一个字就直接改变生产行为、却通常不进 code review、不进 CI、不进版本记录」的地方。

一个最小可用的 prompt 版本化 prompts/ classify_feedback/ v3/ signature.json ← 契约（inputs/output/domain/invariants） instruction.txt ← 五个槽位 demos.jsonl ← **有序**，顺序是内容的一部分 format.json ← 输出格式规范 decoding.json ← 解码约束（模块 04） CHANGELOG.md ← 为什么改，量到的变化是多少 v4/ ... ACTIVE -> v3 ← 一个指针（与 C70 模块 05 的索引切换同构） 指纹 = sha256(signature + instruction + demos(有序) + format + decoding + model_id + temperature)

直白说

把 demos 存成文件而不是代码里的列表，是这套结构里最有价值的一步。它让「示例集合与顺序」变成可 diff、可 review、可回滚的数据，而不是散落在代码里的字符串。而模块 03 的自动优化产出的正是这个文件——于是「人手改」与「自动搜」产出同一种资产。

严谨说

回归门禁按 C68 模块 04 分级：确定性阻断（签名里的取值域与指令里的不一致；格式规范的字段名与解析器不一致；指纹变了但 CHANGELOG 没动），统计阻断（分层准确率相对基线下降超过按方差推出的阈值），报警（预测标签分布的 PSI —— 它抓的是顺序偏置与示例漂移）。把统计项设成阻断是「门禁被关掉」这一结局的起点。

最后一条确定性检查值得单独说：「指纹变了但 CHANGELOG 没动」是一个纯粹的算术检查，零误报，而它防住的是本模块最想防的那件事——一次没人知道发生过的 prompt 变更。

8五个反模式

反模式为什么有人这么做后果
只报端到端一个数「一个数好比较」格式问题与能力问题混在一起；放宽取值域这种有害改动看起来是改进（第 2 节）
示例硬编码在代码里「就几个例子」顺序不进版本、不进 diff、不进指纹；而顺序有真实影响（模块 00 第 6 节量过）
指令里不写取值域「示例里已经有了」解析失败率 100%——示例不能替代取值域声明（第 4 节）
为了「更结构化」加字段「以后可能有用」每多一个字段就多一个解析失败入口，而解析失败是全或无的（第 5 节）
拆成多级流水线「每一步更简单」错误传播是乘法；两个 0.9 合起来是 0.81（第 3 节）。拆分要满足三个条件之一，否则不该拆

这五条有一个共同点：它们都让「哪一层出了问题」变得不可判定。而本模块的全部内容就是把这件事变回可判定的——签名给出契约、三个量给出分层、组合显式化错误传播、版本化让每次变更留下痕迹。

9一个 prompt program 的最小工程清单

把前八节压成一张可勾选的清单。它的顺序就是投入的顺序。

  1. 写签名，不写 prompt——输入字段、输出字段、取值域、不变量。这一步不需要任何模型，而它产出的三个检查可以立刻进 CI。
  2. 把解析器与格式规范一起写，并让它们同源生成。手写 schema 给模型、手写解析器读结果，两者必然漂移。
  3. 指令按五个槽位写全，尤其是取值域（缺了就归零）与边界兜底（缺了会让错误集中在边缘样本上）。
  4. 三个量分别打点：解析率 / 给定解析的正确率 / 端到端。只报第三个时，第一个的问题会被误读成模型能力问题。
  5. 示例存成有序文件（不是代码里的列表），并进指纹。顺序是内容的一部分。
  6. 加一个 ACTIVE 指针与 CHANGELOG，并在 CI 里跑 audit。没有这一步，「改一个字」就是一次没人知道的发布。

直白说

这张清单里没有一项是「把 prompt 写得更好」。全部六项都是结构性的：契约、解析、打点、版本。这不是因为措辞不重要，而是因为在结构没建起来之前，你无法判断一次措辞改动是好是坏——而那正是模块 03 要处理的问题。

严谨说

一个常见的反对意见是「我们的场景简单，不需要这些」。判据很具体：如果你能回答「上一次改 prompt 是什么时候、改了什么、效果变化多少」这三个问题，那确实不需要。而如果三个都答不上来，那么这套结构的成本（大约几百行代码与一次目录重构）远低于「某天发现效果掉了但不知道是什么时候开始的」的代价。

10与 DSPy 的概念对应

本课从零实现这一层，但落地时大概率会用现成框架。这一节把概念对齐，方便两边互译。

本课的概念DSPy 里的对应说明
Signature（本模块第 1 节）dspy.SignatureDSPy 用类的 docstring 当指令、字段注解当取值域；本课把它们拆开是为了让「取值域是否在指令里出现」可以被单独检查

bundle 与指纹save() / load() 的 JSON框架不会替你算指纹或检查 CHANGELOG——这一层要自己加

两句话总结这张表：框架帮你做「渲染 + 优化」，不帮你做「契约检查 + 分层打点 + 版本运维」。而后三件事恰好是本课模块 01 的全部内容——所以用不用框架，这一层都得自己建。

11三条纪律的完整形式

模块 00 给出了三条贯穿全课的纪律。本模块把第一条与第三条补完了，这里写出它们的完整形式。

  1. 格式合规与任务正确必须分开计。完整形式：报三个量（解析率 / 给定解析的正确率 / 端到端），而且「解析成功的样本上准确率 X%」这句话不能单独出现——它必须与解析率一起出现，因为解析成功与答对正相关，条件化在它上面会高估（第 5 节）。
  2. 任何 prompt 改动都要在留出集上复核。这一条在模块 03 展开，但本模块已经给出了它的前提：没有分层指标时，「复核」只能看一个总分，而总分会掩盖某一层的塌陷。
  3. prompt 的每一个组成部分都要进指纹。完整形式：签名、指令、示例集合与顺序、格式规范、解码约束、模型 ID、温度；而 CHANGELOG 不进指纹——正因为它不进，「指纹变了但 CHANGELOG 没动」才成为一个可检查的矛盾。

三条纪律有一个共同的形状：它们都把一个「靠人记得」的要求，变成了一个机器可以判定的条件。而这正是「把 prompt 当程序」这句话的实际含义——不是让 prompt 看起来像代码，而是让它享有代码已有的那些保障：类型检查、测试、版本、评审。
