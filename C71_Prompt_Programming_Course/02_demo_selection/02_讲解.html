02 · few-shot 示例选择与顺序

示例有三个独立维度，收益量级差一个数量级：选择是阶跃（kNN 的 k=1 不输随机的 k=20）· 数量是缓坡 · 顺序是免费的三倍 · 同一批示例只改顺序：0.90 vs 0.30；而「最后一条放谁」这一个自由度就解释了顺序效应的六成 · 一个诚实的负面结果：流行的「打散标签」在本课模拟器上没有稳定收益——可迁移的是方法（顺序要搜、要在留出集上复核），不是规则 · kNN 与前缀缓存直接冲突（前缀从 1 种变成每请求一种），分桶 kNN 是那个折中 · 无内容探针一次调用测出标签先验；减先验校准把最差顺序从 50% 救到 70%——但它需要 logprobs，且隐含假设真实标签分布接近均匀 · kNN 让示例泄漏几乎必然发生（10/10 道题的示例里包含它自己）· 某类没有示例 → 该类准确率归零（这是正确性问题不是效果问题）· 「选中示例与输入的平均相似度」是这一层最好的无真值指标

1示例的三个维度，收益量级差一个数量级

「加几个例子」是最常见的 prompt 改动。但示例有三个独立的维度，而它们的收益量级完全不同。

维度问题本课量到的效应成本
选择选哪些？选对 1 条 ≈ 随机 20 条（0.90 vs 0.70）一次检索（可缓存）
数量放几个？随机选时收益缓慢上升；按相似度选时 k=1 就饱和了线性的 token 成本
顺序什么顺序？同一批示例，只改顺序：0.30 vs 0.90（三倍）零

直白说

第三行是本模块最值得记住的一个数。顺序是零成本的，而它的影响可以比「示例数量翻四倍」更大。而绝大多数系统里示例顺序是「代码里列表的书写顺序」，既没被测过也没进版本（模块 01 第 6 节把它做成了一个可 diff 的文件正是为了这个）。

严谨说

为什么会这样？在本课的模拟器里机制是明确的：近因偏置让靠后的示例被系统性偏好，所以「把最相似的示例放最后」与「放最前」是两个不同的算法。在真实模型上这个效应同样被反复报告（order sensitivity），只是方向与强度依模型而异——这恰恰意味着它必须被测，不能被假设。

一个立刻可做的实验：把你现有的示例列表反转一次，重跑评测。如果分数变了（它很可能会变），说明你的示例顺序是一个未被测量、未被版本化的超参数——而它是免费可调的。

2五种选择策略

策略怎么选优点代价 / 风险
随机从池子里随机取 k 条零成本，且对所有输入用同一批示例 → prompt 前缀稳定，缓存友好（C33）收益最低；而且方差大——换个种子分数就变
kNN（按输入相似度）取与当前输入最相似的 k 条收益最高（本课量到 k=1 即达 0.90）每个请求的示例都不同 → prompt 前缀不稳定，缓存全部失效；这是一个真实的成本权衡
覆盖（每类若干）保证每个标签至少 n 条防「某类完全没示例」——那会让该类准确率直接归零只保证覆盖，不保证相关
多样性（MMR 式）相似度 − λ×已选集合内的冗余避免 k 条示例几乎是同一句话λ 是一个要调的超参；在小池子上收益有限
难度（课程式）按难度排，简单在前难在后与顺序维度天然结合需要难度标注；而难度本身不好定义

直白说

kNN 与「缓存友好」是直接冲突的，而这个冲突常被忽略。固定示例 → prompt 前缀完全稳定 → 前缀缓存命中率接近 100%；kNN 示例 → 每个请求的前缀都不同 → 缓存全丢。在高 QPS、长 prompt 的场景下，这个成本可能超过 kNN 带来的收益。（前缀缓存的机制在 C33 模块 05。）

严谨说

有一个折中：分桶 kNN——先把输入粗分成少量桶（比如按意图或按 embedding 聚类到 8 个簇），每个桶预先算好一套固定示例。于是前缀只有 8 种，缓存仍然有效，而示例的相关性远好于全局随机。notebook 第 3 节实现了它，并量出它落在随机与 kNN 之间的什么位置。

「覆盖」这一条不是可选项：如果某个标签在示例里一次都没出现，那么它的准确率通常直接是 0（模块 00 练习 4 的 demos_coverage 诊断就是抓这个）。而这在真实系统里很容易发生——「从最近 20 条标注里取示例」的自然结果就是稀有类被完全漏掉。

3数量：成本线性，收益次线性

「多放几个例子」是最容易做的改动，也是收益/成本比最差的一个。

本课量到的曲线（10 道测试题） 准确率 0.9 │ ●───────●───────●───────● ← kNN 选择：k=1 就饱和 │ 0.7 │ ○ ← 随机选择：k=20 才到这里 │ ○ 0.5 │ ○ │ ○ ○ 0.2 │ ○────○ └──┬───┬───┬───┬───┬───┬──► k 1 2 3 5 8 12 20 token 成本 ∝ k（线性） → 「选对」是一次阶跃，「加量」是一条缓坡

直白说

这条图的工程含义很直接：先做选择，再考虑数量。而绝大多数团队的顺序是相反的——先把示例从 3 条加到 10 条（因为这最容易），然后发现效果提升不明显，于是得出「few-shot 没什么用」的结论。

严谨说

还有两个与数量相关的、容易被忽略的成本：① 上下文预算——示例占掉的 token 是从「能塞多少检索到的文档」里扣的（C33 的预算分配）；② 延迟——输入 token 数直接影响首 token 延迟。所以 k 不是一个只看效果的旋钮，它同时是一个容量参数。

怎么定 k

  1. 先把选择策略定下来（kNN 或分桶 kNN），因为它决定了曲线的形状。
  2. 扫 k 并找拐点——本课的 kNN 曲线在 k=1 就饱和，真实任务上通常在 4–16 之间。
  3. 把「拐点之后的 k」当成成本浪费直接砍掉。而如果拐点之后还在涨，说明选择策略还有改进空间——回到第 1 步而不是继续加 k。

4顺序：零成本的三倍差距

同一批 5 条示例，只改排列顺序。

kNN 选出 5 条，两种摆法 最相似的放**最前**： [最像的, 次像的, …, 最不像的] → 准确率 0.30 最相似的放**最后**： [最不像的, …, 次像的, 最像的] → 准确率 0.90 机制（本课模拟器里是显式的）： score_i = sim(x, x_i) + recency · (i / (n-1)) └── 靠后的示例得到正向加成 于是「最像的放最后」= 相似度与位置加成叠加，指向同一个示例 「最像的放最前」= 两者相互抵消，最终选中的可能是最不像的那条

直白说

这不是一个模拟器的人造效应：示例顺序对真实模型的影响被反复报告过，而且在某些任务上「换一个排列」造成的分数差距可以达到十几个点。本课模拟器只是把这个效应做成了可控、可解释的形式。方向依模型而异——所以工程上的结论不是「把最像的放最后」，而是「必须测，并且把测出来的顺序固定下来」。

严谨说

三种处理顺序的手段，成本递增：① 固定并版本化（零成本，必做）——把顺序当成配置的一部分，进指纹（模块 01 第 6 节）；② 搜一遍顺序（零成本）——顺序的自由度往往高度集中：本课量到「最后一条放谁」这一个选择就解释了顺序效应的六成；③ 多排列投票（k 倍成本）——跑多个排列取多数投票；它降的是方差（与 C70 模块 03 的多查询融合同构：降方差不保证提高均值）。

notebook 第 4 节还量了一件与流行做法相反的事：「打散标签」在本课的模拟器上没有稳定收益——因为这里的偏置来自「最后一条是谁」，而不是「末尾有一串同标签」。可迁移的是方法（顺序要搜、要在留出集上复核），不是规则。

5标签偏置：用无内容探针把它测出来

示例会给模型一个先验：某些标签更容易被输出，与输入内容无关。而这个先验可以被一个极便宜的实验测出来。

无内容探针（content-free probe） 把输入换成一个没有信息的占位符： "N/A" / "" / "[MASK]" 然后看模型输出什么。 输出的分布 = 这套 prompt 的**标签先验** 本课量到的： 示例里 other 放最后 → 探针输出 other 示例里 other 放最前 → 探针输出 billing 同一个示例集合，只改顺序，先验就变了。

直白说

探针的价值是它把「偏置」从一个模糊的担忧变成一个可测的量，而且它只需要一次调用。而它测出来的东西可以直接用来校准：把每个标签的分数减去探针给它的分数，再取 argmax（这就是 contextual calibration 的思路）。

严谨说

notebook 第 5 节把模拟器展开成一个标签分数向量再做校准——这一步不是实现细节，而是校准的前提：减先验作用在分数上，所以拿不到 logprobs 的 API 上这条路走不通。本课量到的效果是：它把偏置最严重的顺序配置从 50% 救到 70%，与最好的顺序配置持平；而在本来没有偏置的配置上不造成损害。还有一个隐含前提：减先验假设真实标签分布接近均匀——若真实分布本身严重倾斜（比如八成都是兜底类），该减到「真实分布」而不是「均匀」。拿不到 logprobs 时的替代是搜一遍顺序与多排列投票。

一条必须放进监控的指标：预测标签分布。它相对真实分布的偏移（PSI）会同时抓到顺序偏置、示例漂移、以及模型换版本——而这三件事在端到端准确率上都表现为「效果变差了」。（模块 01 第 6 节的门禁里已经放了这一项。）

6泄漏：示例来自评测集 = 一次不诚实的评测

这是本模块唯一一个「正确性」问题而不是「效果」问题。

直白说

如果示例池与评测集有交集，那么被选中当示例的那些测试样本，答案已经写在 prompt 里了。kNN 选择让这件事变得几乎必然发生——因为「与输入最相似的示例」在有交集时就是输入自己。

严谨说

notebook 第 6 节量出这个虚高。而修法是纯纪律性的：示例池与评测集必须来自不相交的样本 ID 集合，并且这件事要在 CI 里检查（一次集合求交，零成本）。这与 C03 模块 05 的污染检测是同一类问题，只不过这里的污染是自己在 prompt 里造出来的——所以它也更容易被彻底解决。

三条必须在 CI 里检查的

  • 示例池 ∩ 评测集 = ∅（按稳定 ID，不是按内容）
  • 示例池 ∩ 留出集 = ∅——模块 03 的自动优化会用留出集，而优化过程会「见过」示例池
  • 示例的答案字段不能出现在评测集的任何输入里——这条抓的是更隐蔽的泄漏（比如示例的理由文本被拼进了测试输入）

一个真实的、很容易发生的路径：「我们用线上日志做示例池，也用线上日志做评测集」。两者按时间切分不够——同一个用户的同一个问题可能出现在两边。必须按稳定 ID 去重后再切分。

7示例池的运维

示例池是一个会腐烂的资产，而它的腐烂方式与 C70 模块 05 的索引腐烂同构。

腐烂怎么发生症状检查
覆盖退化新样本按时间追加，稀有类被稀释某个标签的准确率突然归零每类示例数的最小值（确定性检查，可阻断）
标签漂移标注标准变了，池里新旧标准混存同类样本给出矛盾的信号，整体准确率缓慢下降抽样复核；池里样本要带标注时间与标注标准版本
分布漂移线上话题变了，池里还是旧话题kNN 选出来的示例与输入越来越不相似监控「选中示例与输入的平均相似度」——它掉下来就是漂移的直接信号
规模膨胀只加不删kNN 变慢；而效果不再提升按「被选中的频率」淘汰：从未被选中的示例可以删

直白说

第三行那个指标值得单独强调：「选中示例与输入的平均相似度」是这一层最有信息量的无真值指标。它不需要标注，而它同时反映了池子的覆盖度与线上分布的变化。它掉下来时，该做的是补池子，而不是改 prompt。

严谨说

还有一条与 C68 模块 05 同构的纪律：从线上回灌样本进示例池时，要限制回灌占比。因为回灌的样本是「当前系统答对/答错的那些」，它们的分布已经被当前系统塑造过了——全部用回灌样本会让池子越来越像系统自己的输出，形成闭环。与 C68 模块 05 的 from_production 占比上限是同一条。

8把示例选择做成一个可门禁的流程

示例卡（每次改示例池或选择策略时生成） pool_id: demos-2026w35 pool_size: 842 min_per_label: 31 ← 确定性检查 selector: bucket_knn(buckets=8, k=6) order_policy: interleave_labels + most_similar_last ← **必须写明** prompt_fp: 7c2a91be （示例集合与顺序都在里面） 泄漏检查: pool ∩ test = ∅ ✓ pool ∩ holdout = ∅ ✓ ← 阻断项 覆盖检查: 每类 ≥ 20 条 ✓ ← 阻断项 相似度: 选中示例与输入的平均相似度 0.61（基线 0.63） ← 报警项 效果: 分层准确率 每类都 ≥ 基线 − 2σ ✓ ← 阻断项 先验: 无内容探针 → other；预测分布 PSI 0.04 ✓ ← 报警项

分级仍然是 C68 模块 04 的那一条：确定性检查（泄漏、覆盖、指纹）阻断，统计检查（相似度、PSI）报警，效果回归按方差推阈值后阻断。

一个容易被忽略的确定性检查

order_policy 必须是一个显式声明的字符串，而不是「代码里的顺序」。检查方式：给定 pool 与 selector，用声明的 policy 重算一次示例序列，与实际发送的序列逐条比对。不一致 → 阻断。这一项抓的是「有人在代码里插了一条示例但没改配置」——而那正是本模块第 1 节说的「未被测量、未被版本化的超参数」的来源。

9示例从哪来：四个来源与它们的偏倚

前八节都假设有一个示例池。这一节讨论它从哪来——而每个来源都带一种特定的偏倚。

来源成本带进来的偏倚对策
人工标注高标注者的理解偏好；而标注指南的歧义会变成示例里的噪声标注一致性检查（C10 的 kappa 工具）
线上日志 + 人工复核中分布已经被当前系统塑造过——用户学会了「怎么问才能得到答案」限制回灌占比（C68 模块 05 的 from_production 上限）
bootstrap（当前系统做对的样本）低自我强化——只挑已经做对的（模块 03 第 3 节）配覆盖保底：每类至少一条，即使那一类当前一条都没做对
合成数据低它继承生成模型的偏好与盲区人工抽检；而且不要用被评测的同一个模型来生成

直白说

四个来源里最容易出问题的是第二个，因为它看起来最「贴近真实」。而线上日志里的问题分布已经是「当前系统能处理的那些」——用户遇到几次答不上来之后就不再那样问了。于是从日志里取示例会系统性地漏掉「系统本来就不擅长」的那类输入。

严谨说

一个便宜的对策：保留一个「困难样本」子池，专门放当前系统做错的输入，并强制它在示例池里占一个固定的最小比例。它与覆盖保底是同一类机制——用约束抵抗自我强化。而这与 C70 模块 04 的「迭代作为兜底路径」也是同一个思路：让系统的薄弱面被显式地保留在流程里，而不是被优化过程平均掉。

10示例选择与文档检索：像但不是一回事

「按相似度选示例」和「按相似度检索文档」在实现上几乎一样，但它们的目标函数不同，所以最优做法不同。

维度文档检索（C11 / C70）示例选择（本模块）
目标找到含答案的段落给模型一个「该怎么做这类题」的示范
「相关」的含义内容相关任务形态相关——示例的内容甚至可以与输入无关，只要它示范的是同一类推理
多样性的作用避免 top-k 被近重复占满覆盖标签空间（缺一类就归零）
k 的收益曲线随 k 缓升（更多候选）很小的 k 就饱和（第 2 节量到 k=1）
顺序影响的是「模型先看到什么」直接改变结果（三倍差距）
缓存索引侧缓存，与 prompt 无关前缀缓存——示例变了缓存就失效

直白说

最有实践价值的一行是第二行。文档检索里「不相关的段落」是纯噪声；而示例里「内容不相关但形态相同」的样本仍然有用——它示范的是输出格式、推理步骤的粒度、边界情况怎么处理。这解释了为什么「每类一条覆盖示例」即使与输入完全不相关也有价值。

严谨说

反过来也有一个陷阱：把示例选择完全等同于检索，会让人只优化「内容相似度」，而忽略覆盖度与顺序这两个更便宜的维度。本模块第 1/2 节的数字正是这件事的证据：覆盖（每类一条）就拿到了随机的两倍多，而它不需要任何相似度计算。

11拿到一个新任务时，这一层该按什么顺序做

本模块给出了很多可调的东西。这一节把它们排成一个顺序，依据是本课量到的效应量与成本。

顺序动作成本本课量到的效应
1覆盖保底：每类至少一条示例零缺一类 → 该类准确率归零（正确性问题）
2泄漏检查：池 ∩ 评测集 = ∅零（一次集合求交）泄漏会让所有后续测量失去意义
3搜一遍顺序，在留出集上复核零（只是重排）三倍差距；而「最后一条放谁」占六成
4换成 kNN 或分桶 kNN一次检索（可缓存）kNN 的 k=1 不输随机的 k=20
5扫 k 找拐点，砍掉拐点之后的 k零（省钱）kNN 曲线很小的 k 就饱和
6无内容探针 + 减先验校准（若有 logprobs）一次调用 + 实现把最差顺序从 50% 救到 70%
7示例池运维：监控平均相似度、淘汰未被选中的低漂移流量上平均相似度明显下降

直白说

前三步的总成本是零，而它们覆盖了本模块效应量最大的两项（覆盖度这个正确性问题、以及顺序这个三倍差距）。第 4 步开始才需要真正的实现工作。所以如果只能做一件事，做第 1 步；只能做三件，做前三步。

严谨说

一个常见的次序错误：直接从第 4 步开始（因为 kNN 听起来最像「正确做法」）。后果是：泄漏没查（于是 kNN 让每道题的示例包含它自己，分数虚高到无意义）、覆盖没保底（于是稀有类归零）、顺序没搜（于是白丢一个三倍的免费收益）。而这三件事都比 kNN 便宜。

12这一层的边界

示例是一个很容易被当成万能药的东西。这一节说清它解决不了什么。

问题示例能解决吗该去哪一层
输出格式不对部分——示例会示范格式，但不保证模块 04 的解码约束（它是保证而不是示范）
取值域没声明不能模块 01 的指令槽位；示例不能替代取值域声明
模型不知道某个领域事实不能检索（C11 / C70）——示例示范的是「怎么做」，不是「事实是什么」
需要多步推理有限C09（推理与测试时计算）；本课的模拟器没有推理能力，所以不讨论
上下文塞不下不能（示例本身就占预算）C33 的预算分配与压缩

直白说

第三行是最容易混淆的一条。「模型答错了，多给几个例子」这个反应在「格式/形态」类问题上有效，在「缺事实」类问题上完全无效——而两者在指标上都表现为「准确率低」。区分方式很直接：把答案所需的事实列出来，看它在不在 prompt 里。

严谨说

而第一行值得反过来读一遍：如果你正在用示例来「教模型输出正确的 JSON」，那么你在用一个概率性手段解决一个可以被保证的问题。模块 04 的解码约束能把解析率钉在 1.0，而示例只能让它「更常对」。把示例的预算省下来用在「示范任务形态」上，收益更高。

一句话记住这一层的定位

示例回答的是「这类题该怎么做」，不是「这道题的答案是什么」，也不是「输出必须长成什么样」。前者交给检索（C11 / C70），后者交给解码约束（模块 04）。而在「怎么做」这件事上，本模块量到的三个数值得记住：选对 1 条 ≈ 随机 20 条、顺序造成三倍差距、某类没示例则该类归零。三个数对应三个不同的动作——选择、排序、覆盖——而它们的总成本接近于零。
