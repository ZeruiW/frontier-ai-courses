1顺序：为什么几何在前、光度在后

前三个模块讲的是单个算子；这一模块讲的是把它们串成一条流水线。这不是把算子随便排一排的小事——顺序、概率、进程模型这三件事，每一件搞错都会让「你以为的增强」和「实际发生的增强」相差一个数量级，而且都不报错。

一条真实的检测增强流水线（YOLO 系的典型形态） 原始样本 (img, boxes, labels) │ ├─[A] 混合类（读多张图） Mosaic(p=1.0) → MixUp(p=0.1) │ ↑ 必须最先：它改变"什么是一个样本" ├─[B] 几何类（改坐标） RandomAffine → RandomPerspective → HFlip │ ↑ 全部合成一个 3×3 矩阵，**只重采样一次** ├─[C] 越界处理 裁剪到画布 → 面积/可见比阈值筛掉残框 │ ↑ 必须紧跟几何：此时坐标才是最终的 ├─[D] 光度类（不改坐标） HSV → 亮度/对比度 → 噪声 → 运动模糊 → JPEG │ ↑ 放在几何之后，否则高频扰动被重采样抹平 ├─[E] 尺寸归一 Letterbox / Resize（与推理端**逐行相同的代码**） └─[F] 张量化 HWC→CHW, uint8→float, mean/std 归一化 ↑ 这一段在 val/test/部署三处必须完全一致

这个顺序不是约定俗成，每一步都有可以量化的理由。

阶段是否改标注是否重采样像素放错位置的后果
A 混合类是（合并多图的框）是（缩放拼接）放在几何之后 → 每张子图各自做过几何，拼接后尺度分布失控
B 几何类是是拆开分多次做 → 多次插值，细节被反复抹平（下面有数值）
C 越界处理是（裁剪/丢弃）否放在几何之前 → 裁剪的是旧坐标，等于没裁
D 光度类否否放在几何之前 → 注入的噪声被后续插值平滑掉 50%–69%
E 尺寸归一是（等比缩放）是与推理端实现不同 → 训练-部署鸿沟（C60 的头号杀手）
F 张量化否否顺序错（先减均值再除 255）→ 数值全错但模型仍能训

直白说

「光度放在几何之后」的理由最容易被忽略，而它是可以精确算出来的：任何亚像素的几何变换都是一次低通滤波。双线性插值把一个像素写成相邻两点的凸组合，等价于一个 [1−f, f] 的卷积核。你先往图上加了 σ=0.1 的高斯噪声，再做一次 0.5 像素的平移，噪声方差就被乘上 0.5²+0.5²=0.5——实际的 σ 只剩 0.071。如果几何段是三个算子串着做，方差只剩 31%，σ 只剩 0.056。你在配置文件里写的强度和模型真正见到的强度，差了将近一倍。

严谨说

严格地说：设几何变换的重采样核为 h，对独立同分布的加性噪声，输出方差为 σ² · ‖h‖²₂。半像素双线性平移 h=[0.5,0.5]，‖h‖²₂=0.5；三次串联的等效核是它的三重卷积 [1,3,3,1]/8，‖h‖²₂=20/64=0.3125。这同时给出了第二条规则：几何算子应当先把所有变换合成一个仿射/透视矩阵，再做一次 warpAffine，而不是逐个算子各调一次。串联三次不仅慢三倍，还额外损失了 0.5−0.3125=37.5% 的高频能量——而高频正是小目标赖以被检出的信息。

「越界处理必须紧跟几何段」是另一个高频实现 bug。常见写法是在最后统一裁剪框，但此时若中间插入了 Mosaic 的二次拼接，坐标系已经换过了，裁剪就作用在错误的画布上。症状是训练集里凭空出现大量贴边的窄条框——它们是残缺目标，模型会学到「标志可以只有 2 像素宽」，直接污染小目标的尺度先验。规则：坐标系一变，立刻做一次合法性清洗。

把顺序规则压成一句可背的话：先决定「一个样本是什么」（混合），再决定「它长在哪」（几何 + 清洗），最后决定「它看起来怎样」（光度），末尾是与推理端字节对齐的归一化。越靠前的阶段影响越结构性、越不可逆；越靠后的阶段越是纯像素级的微调。

2概率相乘：你配置的强度和实际强度差一个数量级

流水线里每个算子都带一个触发概率 p。绝大多数人凭直觉理解它——「p=0.5 就是一半样本会被增强」——这句话对单个算子是对的，对整条流水线是灾难性的错。

\[P(\text{全部触发}) = \prod_{i=1}^{k} p_i, \qquad P(\text{一个都不触发}) = \prod_{i=1}^{k} (1-p_i), \qquad \mathbb{E}[\#\text{触发}] = \sum_{i=1}^{k} p_i\]

代入最常见的配置：5 个算子各 p=0.5。

量公式数值直觉预期
全部触发0.5⁵3.1%很多人以为是「一半」
一个都不触发0.5⁵3.1%——
平均触发个数5×0.52.5 个——
至少触发 3 个(10+5+1)/3250.0%——
至少触发 1 个1−0.5⁵96.9%看起来很安全，掩盖了强度分布

换成 8 个算子（真实流水线的常见规模）各 p=0.5：全部触发的概率是 0.5⁸ = 0.39%。你写在配置里的「最强增强组合」，在整个训练过程中只会出现在四百分之一的样本上——它几乎从未参与训练，而你却在 review 时按它来判断增强强度。

直白说

反过来算更有用：如果你希望「全套增强都上」的样本占 30%，5 个算子每个的 p 该设多少？答案是 0.30^(1/5) = 0.786——每个算子都要接近 0.8，而不是直觉的 0.5 或 0.6。这个反解在调参时极其实用：你先定「联合强度」这个业务上真正关心的量，再反推每个算子的 p，而不是逐个算子拍脑袋。

严谨说

另一个必须知道的实现陷阱是嵌套概率的折叠。Albumentations 的 OneOf([...], p=0.5) 语义是：以 0.5 的概率进入这个组，进入后按归一化权重从组内选一个。所以组内某算子的实际触发率是 0.5 × w_i/Σw，而不是它自己写的那个 p。三层嵌套（Compose 里套 OneOf 里套 Compose）之后，叶子算子的实际触发率常常低到 2%–3%。唯一可靠的做法是给流水线打点，把每个算子的实际触发率和联合分布统计出来，而不是读配置文件推理。

面试常问：你怎么判断一个增强算子有没有用

这个坑在消融实验里会直接导致错误结论。你加了一个新算子、设 p=0.3，跑完发现 mAP 只涨了 0.1，于是判定「这个增强没用」。但如果它嵌在一个 OneOf(p=0.5) 的三选一里，实际触发率是 0.5×1/3=16.7%，再乘上它只对 12% 的夜间样本有意义——真正受影响的样本占比 2%。+0.1 的整体 mAP 对应的是那 2% 样本上的巨大提升。这也是模块 05 要讲的「分场景验证」的动机之一。

落到 TSR 上：交通标志的关键失效场景（夜间、雨雾、逆光）在数据里本来就只占 10%–20%，针对它们的增强算子一旦再乘上一个 0.2 的触发概率，实际覆盖的样本就只剩 2%–4%。所以场景专用增强的 p 应当显著高于通用增强的 p，甚至应该按样本的场景标签做条件触发（只在夜间样本上加眩光、只在高速样本上加运动模糊），而不是全局均匀掷骰子。

3CPU 才是训练吞吐的真正瓶颈

检测训练的直觉是「GPU 在算」。真实情况常常相反：数据增强跑在 CPU 上，而检测增强（尤其是 Mosaic、copy-paste、透视变换）比分类增强重一个数量级。一旦 CPU 供不上，昂贵的 GPU 就在空转，而你从 loss 曲线上完全看不出来。

\[\text{throughput} = \min\!\left(\underbrace{\frac{W}{t_{\text{aug}}}}_{\text{CPU 侧}},\ \underbrace{\frac{B}{t_{\text{step}}}}_{\text{GPU 侧}}\right), \qquad \text{GPU 利用率} = \min\!\left(1,\ \frac{W \cdot t_{\text{step}}}{B \cdot t_{\text{aug}}}\right)\]

其中 W = worker 数，t_aug = 单样本增强耗时，B = batch size，t_step = 一步前反向的耗时。代入一组真实数字：t_aug=12 ms、B=32、t_step=60 ms。

W=7583533GPU（前反向）100%
W=8667533GPU（前反向）100%
W=8, 开 Mosaic（t_aug≈38 ms）208533CPU，严重39%
要喂饱 GPU 所需最少 worker———⌈533×0.012⌉=7；开 Mosaic 后 21

最后一行是这一节的重点：Mosaic 要读 4 张图、解码 4 次、拼接后再做一次几何变换，单样本成本大约是普通增强的 3 倍。于是「喂饱一张卡」需要的 CPU 核数从 7 跳到 21——在一台 8 卡机上就是 168 核，绝大多数机器给不出来。这就是为什么开了 Mosaic 之后训练明显变慢却查不出原因。

直白说

怎么确认是数据瓶颈而不是模型瓶颈？有一个五秒钟的判定法：把 DataLoader 换成一个返回固定张量的假数据源，再跑一遍。如果吞吐显著上升，瓶颈就在数据侧；如果几乎不变，瓶颈在 GPU 侧。这个「短路实验」比任何 profiler 都快，而且不会被采样误差和工具开销骗到。它和 C52 讲的「逐层二分定位」是同一个方法论：把整体慢分解成可以单独短路的环节。

严谨说

第二个必须区分的量是吞吐的均值瓶颈 vs 方差瓶颈。prefetch_factor 和队列只能削峰——它们把「某一批特别慢」的抖动吸收掉，让 GPU 不因为偶发慢批而空转。但队列无法提高长期平均吞吐：只要 W/t_aug < B/t_step，无论队列多深，稳态吞吐都等于 CPU 侧的供给速率。把 prefetch 从 2 调到 16 却没变快，说明你面对的是均值问题而不是方差问题——此时唯一的出路是降低 t_aug 或提高 W。

worker 数不是越多越好：① 每个 worker 是一个独立进程，要复制一份数据集索引与 Python 解释器，内存按 W 线性增长（大 annotations 字典能吃掉几 GB×W）；② 超过物理核数后线程争抢反而降低单 worker 吞吐；③ 与 OMP_NUM_THREADS 冲突——OpenCV/numpy 默认多线程，W 个 worker 各开 N 个线程会产生 W×N 的线程风暴。标准做法是 cv2.setNumThreads(0) + W ≈ 物理核数 − 2。

4吞吐优化的六个杠杆（按性价比排序）

确认是 CPU 瓶颈之后，有六个杠杆可用。它们的收益、代价和适用条件差别很大，按性价比排序而不是按流行度排序。

杠杆做什么典型收益代价 / 风险什么时候用
① 关掉库内多线程cv2.setNumThreads(0)、OMP_NUM_THREADS=11.3–2×几乎无永远先做这一条，五秒钟见效
② 合并几何算子多个仿射合成一个矩阵，只 warp 一次1.5–3×（几何段）要自己写矩阵合成几何算子 ≥3 个时必做，顺带提升画质
③ 换解码格式JPEG 预解码成 raw/npy/webdataset/LMDB2–4×磁盘占用涨 5–10×JPEG 解码常占 t_aug 的 40%–60%
④ 加 worker + 持久化num_workers↑、persistent_workers=True线性到核数上限内存 ×W；启动慢核数还有余量时
⑤ GPU 侧增强DALI / Kornia / torchvision.transforms.v2 放到 GPU3–10×抢 GPU 显存与算力；算子集受限；数值与 CPU 版不完全一致CPU 核数不够且增强以张量运算为主
⑥ 降低增强分辨率先 resize 到目标尺寸再做重算子1.5–2.5×小目标细节提前丢失TSR 场景慎用——见下方警告

直白说

杠杆 ③ 常常是最大的一块，却最少被想到。一张 1920×1080 的 JPEG 解码大约 6–10 ms，而整条增强流水线可能才 12 ms——意味着一半以上的 CPU 时间花在「把图片变成数组」而不是「增强」上。预解码成未压缩格式后，读取变成纯 IO，t_aug 直接腰斩。代价是磁盘：10 万张 1080p 图从 20 GB 涨到 300 GB。对车队数据这个代价通常可以接受，因为训练机本来就挂着大容量盘。

严谨说

杠杆 ⑤ 有一个必须提前知道的副作用：GPU 侧增强的数值与 CPU 侧不完全一致。插值实现、边界处理、浮点累加顺序都可能不同，导致「换了数据管线之后 mAP 变了 0.3」这类无法归因的现象。更麻烦的是它抢占 GPU 资源——增强占了 15% 的显存和算力后，你能开的 batch size 变小，反而可能整体更慢。正确做法是：先把 ①②③ 做完，确认 CPU 侧真的榨不出来了，再考虑 ⑤，并且切换前后必须做一次完整的对拍（这正是 C60 讲的训练-部署一致性方法论在训练侧的应用）。

省 CPU 省掉了小目标

杠杆 ⑥ 在 TSR 场景下是陷阱。「先把 1920×1080 缩到 640×640 再做增强」能省一大半 CPU，但 60 米外的限速牌在原图上只有 18 像素，缩放后只剩 6 像素——它在增强流水线的第一步就被抹掉了，后面所有的几何/光度增强都作用在一坨模糊上。症状是小目标 AP 莫名其妙掉 3–5 个点，而所有增强参数看起来都正常。规则：凡是会降低有效分辨率的优化，都必须按目标尺寸分桶验证，不能只看整体 mAP。

一个能省很多事的工程约定：把 t_aug 做成训练日志里的一等公民——每个 epoch 打印一次「单样本增强耗时的 p50/p99、各算子耗时占比、GPU 利用率」。这三个数一旦上了看板，「训练怎么变慢了」这个问题就从「玄学」变成了「看一眼日志」。它的成本是十几行代码，收益是整个团队不再靠猜。

5可复现性：DataLoader worker 的 RNG 陷阱

这一节讲的是一起真实事故，而且是那种「跑通了、指标也不算离谱、但你的增强多样性被静默砍掉了 3/4」的事故。它不会报错，不会 warning，只会让你的模型比应有的水平差几个点。

PyTorch DataLoader 的 worker 是 **fork** 出来的子进程 主进程 numpy 全局 RNG state = S0 │ random 模块 state = R0 │ ├── fork ──> worker 0 : numpy state = S0, random state = R0 ← 完全相同 ├── fork ──> worker 1 : numpy state = S0, random state = R0 ← 完全相同 ├── fork ──> worker 2 : numpy state = S0, random state = R0 ← 完全相同 └── fork ──> worker 3 : numpy state = S0, random state = R0 ← 完全相同 后果：4 个 worker 抽出的随机数序列**逐个相同**。 样本 0,4,8,... 由 worker0 处理，用 stream[0],stream[1],stream[2],... 样本 1,5,9,... 由 worker1 处理，用 **同一个** stream[0],stream[1],... => 样本 0/1/2/3 拿到**完全一样**的增强参数。 => 一个 epoch 里不同的增强参数只有 N/W 组，**多样性打了 1/W 的折扣**。 注意：PyTorch 会为 **torch 自己的 RNG** 做 base_seed+worker_id 的处理， 所以 torch.rand 是安全的；**numpy 与 python random 不在此列**。 而绝大多数检测增强库（Albumentations、imgaug、自写算子）用的正是 numpy。

这个 bug 有三个变体，症状与修法各不相同。

变体写法症状怎么检测修法
① 全 worker 同 seedworker 里直接用全局 np.random增强多样性 ÷ W，且完全静默统计一个 epoch 内不同增强参数的去重个数，应等于样本数worker_init_fn 里用 base_seed+worker_id 重新播种
② 只按 worker_id 播种seed(1234+worker_id)每个 epoch 重复同一串增强；训练 300 epoch 只见过 1 个 epoch 的增强多样性对比 epoch 0 与 epoch 1 的参数序列，应完全不同seed 里必须含 epoch（或用 torch.initial_seed()，它每 epoch 变）
③ 复现不了实验只固定 torch.manual_seed同样的命令跑两次结果不同跑两次对比 loss 曲线前 10 步固定 torch/numpy/random 三家 + generator= + 记录 num_workers
 
# ✅ 正确写法：seed 必须同时含 base_seed / epoch / worker_id
import numpy as np, random, torch

def worker_init_fn(worker_id):
    # torch.initial_seed() = base_seed + worker_id，且**每个 epoch 由 sampler 重新生成**
    seed = torch.initial_seed() % (2 ** 31)
    np.random.seed(seed)          # ← numpy 全局（兼容老代码）
    random.seed(seed)             # ← python random
    cv2.setNumThreads(0)          # ← 顺手把线程风暴关掉

# 更干净的做法：不用全局 RNG，每个 worker 持有自己的 Generator
class AugDataset(torch.utils.data.Dataset):
    def _rng(self):
        info = torch.utils.data.get_worker_info()
        wid = 0 if info is None else info.id
        ss = np.random.SeedSequence(entropy=self.base_seed,
                                    spawn_key=(self.epoch, wid))   # ← epoch 必须在里面
        return np.random.default_rng(ss)

loader = torch.utils.data.DataLoader(
    ds, batch_size=32, num_workers=8,
    worker_init_fn=worker_init_fn,
    generator=torch.Generator().manual_seed(1234),   # ← 控制 shuffle 的随机性
    persistent_workers=True, prefetch_factor=4,
)

直白说

把损害量化一下就知道为什么这值得单开一节：N=64 个样本、W=4 个 worker，变体 ① 下一个 epoch 里只有 16 组不同的增强参数。更糟的是，因为 seed 与 epoch 无关，这 16 组参数在全部 300 个 epoch 里一模一样——整个训练过程中模型只见过 16 种增强变体。而正确实现下是 64×300 = 19200 种。差了三个数量级，而 loss 曲线看起来完全正常。

严谨说

为什么它这么难被发现？因为增强的作用是统计性的：少了多样性不会让某个样本出错，只会让泛化差一点。你看到的是「mAP 比论文低 2 个点」，而这个差距会被归因到超参、数据量、backbone——几乎不会有人怀疑到 RNG。唯一可靠的防线是把「一个 epoch 内增强参数的去重个数」做成一条断言：它应该等于样本数，不等就直接抛异常。这是那种写一次、终身受益的十行代码。

评测有随机性 = 所有消融结论作废

还有一个更隐蔽的近亲：验证集 / 评测集的随机性。如果评测流水线里残留了任何随机算子（哪怕只是随机 letterbox 的填充位置），同一个 checkpoint 评两次会得到不同的 mAP。此时你在模块 05 要做的所有显著性检验都建立在流沙上——因为你无法区分「模型的差异」和「评测的噪声」。规则：评测路径必须是纯确定性的，并且用「同一权重评两次结果必须逐位相同」作为 CI 断言。

「可复现」不等于「固定了 seed」。同一个 seed 在不同的 num_workers 下会产生不同的增强序列（因为样本到 worker 的分配变了）；不同版本的 OpenCV/Pillow 的插值实现也会给出不同像素。所以实验记录里必须同时写下：seed、num_workers、增强配置哈希、以及关键库的版本号。这四项少任何一项，半年后都复现不出来。

6训练 / 验证 / 测试 / 部署：四条路径的增强一致性

增强只属于训练。这句话人人都会说，但真实代码里违反它的方式有很多种，而且每一种都会让离线指标失去意义。

路径允许的操作禁止的操作违反后的症状
train全部随机增强————
val只允许确定性变换：resize/letterbox/归一化任何随机性（含随机裁剪、随机 letterbox 填充位置）同一权重评两次结果不同 → 消融结论全部作废
test同 val，且必须与 val 共用同一份代码为了刷分单独调预处理test 高于 val 是数据泄漏或预处理不一致的指纹
deploy必须与 val 逐位一致换库（cv2↔PIL）、换插值、换 padding 值离线 mAP 0.82，车上像 0.6（C60 模块 01 的经典故事）

直白说

最常见的违规不是「验证集做了增强」这种低级错误，而是「训练和验证的确定性部分走了两条代码路径」。训练里 letterbox 用 114 填充、缩放比例向下取整到 32 的倍数；验证里图省事直接 cv2.resize(img,(640,640))——纵横比被拉伸了。模型在训练时从未见过被拉伸的标志，验证 mAP 于是无故低几个点，而你会以为是模型过拟合。规则：train/val/deploy 的确定性段必须是同一个函数，通过参数开关随机段，而不是三份实现。

严谨说

另一个高频错误是「验证集做了 TTA、线上没做」。TTA 能让离线 mAP 涨 1–2 个点，如果只在验证路径上打开，你得到的是一个系统性虚高的指标：所有基于它的选型、门禁、消融都偏了，而且偏的量随模型不同而不同（弱模型从 TTA 受益更多），导致模型间的排序都可能反转。原则：离线评测的配置必须是线上配置的一个精确镜像；任何线上不会做的事，评测路径也不许做。

落到 TSR 上，这条原则有一个额外的维度：车端相机的 ISP 输出才是真正的部署分布。训练数据如果是从压缩视频里抽的帧，它带着 H.264 的块效应；而车端拿到的是 ISP 直出的 YUV。这两者的高频特性差别很大，对 8–16 像素的小标志尤其致命。所以「增强要贴近部署分布」在这里意味着：训练侧要么补上 JPEG/视频压缩伪影的增强，要么把训练数据换成 ISP 直出——而验证集必须用后者，否则你测的是「模型在压缩视频上的表现」，与车上无关。

一条容易被忽略的推论：close-mosaic 这类「阶段性增强」让训练分布在中途发生跳变。关掉 Mosaic 的那一刻，训练分布突然向验证分布靠拢，验证 mAP 会出现一个明显的台阶。如果你在切换点附近做模型选择或早停，就会选到一个「刚好赶上台阶」的 checkpoint，而这个提升与你正在消融的那个变量毫无关系。规则：所有对比实验必须在完全相同的 epoch 数与相同的 close-mosaic 时点下进行。

7TTA 与 WBF：融合多个视角的正确方式

TTA（Test-Time Augmentation，测试时增强）是把同一张图用多种确定性变换各推一遍，再把结果融合。它是离线场景的免费午餐，也是车端几乎用不起的奢侈品。

① TTA 的构成与逆变换

典型配置：3 个尺度 × 2 种翻转 = 6 个分支。关键的实现细节是每个分支的框必须逆变换回原图坐标系：缩放分支要除以缩放比，翻转分支要做 x → W − x 并交换 x1/x2（忘记交换会得到 x1>x2 的非法框，NMS 里 IoU 全算成 0，症状是「TTA 之后反而掉点」）。

② 为什么融合不能用 NMS

直白说

NMS 的语义是「选一个、删掉其他」。这在单模型输出上是对的——重复框是冗余，删掉即可。但在 TTA 场景下，6 个分支给出的 6 个框是同一个目标的 6 次独立观测，每一次都带独立的定位噪声。此时删掉 5 个只留最高分的那个，等于扔掉了 5 份可以用来降噪的信息。正确的做法是平均——多次独立观测的加权平均，其方差是单次观测的 1/n。

严谨说

WBF（Weighted Boxes Fusion，加权框融合）正是这么做的：按分数降序遍历所有框，与已有簇的融合框 IoU 超过阈值就并入该簇，并用分数作权重重算融合坐标；否则新建一个簇。最后还有关键的一步——按支持该簇的分支数重标定分数：只被 1 个分支检出的框，其分数要乘上 1/T（T 为分支总数）。这一步是 WBF 相对 NMS 的第二个优势：它天然抑制了「只有某个尺度才看到」的偶发误检，而 NMS 对这类框无能为力（它没有重复框可以比较）。

\[b_{\text{fused}} = \frac{\sum_{i=1}^{n} s_i \cdot b_i}{\sum_{i=1}^{n} s_i}, \qquad s_{\text{fused}} = \left(\frac{1}{n}\sum_{i=1}^{n} s_i\right) \cdot \frac{\min(n, T)}{T}\]
融合方式坐标怎么定分数怎么定对 TTA 的适配性
NMS取最高分那一个最高分差：丢弃其余观测，定位方差不降
Soft-NMS取最高分那一个重叠者降权而非删除中：保住了召回，但坐标仍来自单个分支
NMW加权平均取最大值中：坐标对了，但单分支误检不被抑制
WBF分数加权平均均值 × min(n,T)/T好：定位降噪 + 单分支误检降分

③ 延迟账：为什么车端用不起

6 个分支意味着 6 次前向。按尺度的计算量正比于面积，[0.83, 1.0, 1.25] 三个尺度的相对代价是 0.69 + 1.00 + 1.56 = 3.25，再乘 2（翻转）= 6.5 倍单次推理。若单次推理 8 ms，TTA 就是 52 ms，加融合约 53.5 ms。

面试高频：TTA 上车吗

而 TSR 在车端的整体预算是这样的：30 FPS → 每帧 33 ms，这 33 ms 要装下多路相机的感知、融合、跟踪、规控——TSR 分到的通常只有 8–12 ms。53.5 ms 超出预算 5 倍以上。更致命的是 TTA 的延迟随目标数波动（融合是 O(n²) 的），破坏了 p99 延迟的确定性——而车端要的恰恰是确定性。结论：TTA 在量产感知里基本不可用。面试里被问「你会用 TTA 吗」，正确答案是「离线会，车端不会，因为……」并给出这笔账。

但 TTA 在离线仍有三个高价值用途，这才是它该出现的地方：① 打伪标签——半监督/自训练里用 TTA 提高教师模型的标注质量；② 难例挖掘的一致性信号——不同 TTA 分支给出的结果分歧越大，这张图越可能是难例（这正是 C58 讲的一致性触发器）；③ 评估精度上限——TTA 后的 mAP 可以视作「这个模型在这份数据上的能力天花板」，与单次推理的差距衡量了模型对视角/尺度的鲁棒性缺口。换句话说：TTA 涨得越多，说明你的增强训练做得越差。

8增强配置的版本管理：它是模型的一部分

增强配置不是「训练脚本的一个参数」，而是模型定义的一部分——同样的架构、同样的数据、不同的增强配置，产出的是两个能力完全不同的模型。它必须被当作代码一样版本化。

必须记录的字段为什么漏了会怎样
算子列表与顺序顺序影响数值（见第 1 节）复现时把光度放到几何前，噪声强度差一倍
每个算子的参数与 p强度的直接定义——
实测的联合触发分布配置里的 p 与实际触发率常常不同（嵌套 OneOf）消融结论错误归因
seed 策略 + num_workers两者共同决定实际的随机序列复现不出来（第 5 节）
库版本（cv2 / PIL / albumentations）插值与边界实现随版本变化换机器后 mAP 漂移 0.2–0.5，查不出原因
阶段性切换点（close-mosaic epoch）训练分布在此跳变对比实验的切换点不一致 → 结论不可比
配置哈希一个字符串就能判断两次实验是否可比只能靠人肉 diff YAML

直白说

配置哈希是这里最有杠杆的一条：把规范化后的增强配置（含库版本）序列化，取一个短哈希，写进 checkpoint 的元数据和每一行训练日志。此后「这两次实验的增强一样吗」就从一次考古变成了一次字符串比较。它同时解决了另一个问题——当有人在 review 里说「我只改了学习率」时，哈希会告诉你他顺手动过增强。这与 C52 讲的「给不可读的二进制产物附一份可读的来源说明」是同一个模式。

严谨说

更进一步：把「实测触发率」也纳入产物。训练开始时跑 2000 个样本过一遍流水线，统计每个算子的实际触发率与联合分布，写进日志。这一步把「配置」变成了「事实」：你不再需要在脑子里折叠嵌套概率，也能立刻发现「这个算子的实际触发率是 2%，难怪消融看不出差别」。成本是训练开始时多花 3 秒，收益是消除了整整一类的错误归因。

一个真实的组织性陷阱：增强配置常常被复制粘贴，然后各自演化。检测组从分类组抄了一份 HSV 参数，其中 hue_shift=±20° 对分类无害，但对 TSR 是灾难——红色禁令牌的色相偏 20° 就滑向橙/品红，语义被破坏（模块 02 已经量化过这一点）。规则：领域敏感的参数必须在配置里带注释说明约束来源，并写进 CI 断言（例如「hue 幅度不得超过 10°」），而不是指望下一个人记得。

把本模块浓缩成一句可迁移的心法：增强流水线是一个「你写的配置」与「模型实际见到的分布」之间存在系统性偏差的地方——顺序偏差、概率偏差、RNG 偏差、库实现偏差，四种都静默。因此工程上唯一可靠的姿态是：不推理，去测量。触发率要打点、多样性要断言、耗时要上看板、配置要哈希。这四件事加起来不到一百行代码，却消除了这个领域绝大多数的「查不出原因」。

9研究前沿与开放问题

增强流水线工程看起来很「工程」，但它连着几个仍然开放的研究问题。

  • 自动增强搜索：AutoAugment 用 RL 搜策略、成本极高（几千 GPU 小时）；Fast AutoAugment 用密度匹配把成本降两个数量级；RandAugment 把搜索空间压成两个超参（N 个算子、强度 M），几乎不损失精度——这个「简化反而更好」的结果本身是个重要教训；TrivialAugment 更进一步，连强度都随机采样。但检测任务上的自动搜索仍不成熟：搜索目标是 mAP（评估贵）、搜索空间要包含框变换的合法性约束、而且最优策略与数据集强相关。
  • 在线自适应增强：Population Based Augmentation、Adversarial AutoAugment 让增强强度随训练进程变化（早期弱、后期强），这与本课模块 05 要讲的「增强强度与训练时长的交互」是同一个现象的两面。开放问题是：能否用模型自身的不确定性来在线决定每个样本该被增强多强——即「样本级自适应增强」。
  • 数据管线的系统化：NVIDIA DALI、FFCV、WebDataset 把增强搬到 GPU 或做成流式格式。它们的共同难题是算子覆盖与数值一致性——GPU 实现与 CPU 实现的插值差异会造成不可归因的指标漂移。「跨后端的位级一致增强」目前没有标准方案。
  • 生成式增强：用扩散模型合成罕见场景（夜间的施工牌、雨雾中的限速牌）。收益诱人，但有两个硬问题：① 标注一致性——生成的图里目标框在哪、语义对不对，需要可控生成而非自由生成；② 分布真实性——生成数据的伪影会成为模型学到的捷径特征，在真实数据上反而掉点。这是当前 TSR 长尾问题最被寄予厚望也最不确定的方向。
  • 增强与半监督的统一：FixMatch / Unbiased Teacher 系列把「弱增强出伪标签、强增强做一致性约束」变成了半监督的核心机制。这意味着增强不再只是正则化，而成了监督信号的来源。开放问题是：强弱增强的「强度差」该多大——太小没有约束力，太大伪标签失效，目前仍靠手调。
  • TTA 的低成本化：能否用一次前向获得多视角的效果（如让网络内部显式建模尺度/翻转等变性），从而在车端也享受 TTA 的降噪收益？等变网络（equivariant CNN）与 test-time 自适应是两条正在探索的路径，目前都还没有达到「延迟可接受 + 收益可观」的组合。

必读：AutoAugment（Cubuk et al., 2019）与 RandAugment（Cubuk et al., 2020）——对照读，理解「搜索空间简化为何不损失精度」；Weighted Boxes Fusion（Solovyev et al., 2021）——WBF 的原始定义与 vs NMS/NMW 的对比实验，本模块 notebook 实现的就是它；Albumentations: Fast and Flexible Image Augmentations（Buslaev et al., 2020）——检测增强库的设计取舍与 OneOf 的概率语义；NVIDIA DALI 与 FFCV 的文档（数据管线瓶颈的系统性解法）；PyTorch 官方文档的 Randomness in multi-process data loading 一节（worker RNG 陷阱的一手说明）。相邻课程：C43（数据工程）、C58（难例挖掘与一致性触发）、C60（训练-部署一致性）。完整清单见 references.md。
