1光度增强在管什么：不动一个标注，却可能改掉标签

几何增强管的是「物体在图像里的位置与形状」，所以每做一次变换都必须同步改标注——模块 01 花了整整一节讲四角法与外接框。光度增强管的是另一件事：「同一个物体，在不同的光照、天气、传感器、编码条件下，长什么样」。它一个像素都不移动，框的四个数字原封不动。

正因为「不用改标注」，光度增强被广泛当成免费且安全的一类增强，默认配置抄一遍就上。这恰恰是交通标志识别里最危险的误解：标注文件没变，不等于标签语义没变。

几何增强光度增强

典型失效框膨胀、越界裁剪、小目标被丢弃语义被悄悄改掉、训练-部署分布错位
失效是否可见可见（画出来就知道框歪了）基本不可见（图看起来还挺正常）
TSR 特有禁区水平翻转（左转变右转、文字镜像）色相抖动（红=禁令、蓝=指示、黄=警告）
调过头的症状小目标召回崩、框系统性偏移混淆矩阵里出现「跨颜色族」的错分

直白说

光度增强的正当性只有一句话：你要教模型的是「这些变化不改变它是什么」。所以判断一个算子该不该用、幅度该多大，只需要问一个问题——真实世界里有什么东西会产生这个变化？变化能有多大？。相机自动曝光会让整幅图明暗浮动 ±1 EV，所以亮度抖动 ±30% 合理；但没有任何物理过程会把一块红牌变成黄牌，所以色相抖动 ±40° 不是增强，是label noise（标签噪声）。

严谨说

形式化地说：一个变换 T 是 label-preserving（保标签）的，当且仅当对任务的真实条件分布有 p(y | T(x)) = p(y | x)。光度增强的所有争议都在这一个等式上。对通用检测（COCO 里的「人/车/椅子」），颜色几乎不进入 p(y|x)，所以色相抖动无害甚至有益；对 TSR，颜色是分类边界本身的一部分，同一个变换直接把等式打破。这是「增强配方不可跨任务复制」最干净的一个反例——面试时能举出这个例子，比背十条增强列表更有说服力。

一个常见的错误推理是「加了强增强、验证集 mAP 没掉，所以是安全的」。验证集通常与训练集同分布、同标注体系，掉点会被平均掉：整体 mAP -0.1 可能对应「稀有黄色警告牌 AP -8」。光度增强的验证必须按颜色族与光照条件分桶看，这一点在模块 05 会展开。

与其记一张「常用增强清单」，不如把成像链路画出来——每个光度算子都应该能挂到链路上的某一环。挂不上去的算子，就是没有物理对应的算子，用它等于在制造训练-部署鸿沟。

直白说

把上表压成一句可操作的判据：先问「相机或环境里有什么会产生这个变化」，再问「它最大能有多大」。第一问筛掉没有物理对应的算子（channel shuffle 之流），第二问定幅度。幅度不该从别人的 config 里抄，而该从设备与场景里推——车载相机的自动曝光范围、白平衡算法的最大偏差、回传码率对应的 JPEG quality，这些都是可以问到具体数字的工程参数。

严谨说

有一个数学结构值得单独记：亮度、对比度、以及后面要讲的大气散射雾化，全都是逐通道仿射变换 I' = a·I + b。对这一族变换可以精确说清它对颜色做了什么：通道差被同乘 a，于是 (g-b)/Δ 这类比值完全不变 → 色相严格不变（前提是 b 三通道相同）；而 S = Δ/max 的分子乘 a、分母是 a·max + b，于是 b > 0 时饱和度必然下降。所以「雾会不会破坏颜色语义」有一个精确答案：雾主要杀饱和度，色相的偏移完全来自环境光 A 的非中性（天空偏蓝）——notebook 里会把这两个数都量出来。

记住这个分类比记算子列表有用得多：仿射类算子（亮度/对比度/雾）安全，非线性类（gamma）轻微移色，显式色相/通道操作危险。凡是你说不清它对色相做了什么的算子，就不要用在 TSR 上。

3交通标志的颜色就是语义：色相抖动的红线在哪

这一节是本模块的核心，也是 TSR 相比通用检测最特殊的一条约束。在 GB 5768（中国）、维也纳公约（欧洲）、MUTCD（美国）三套体系里，颜色都不是装饰，而是类别层级的一部分：红=禁令、黄（欧洲白底红边、中国黄底黑边）=警告、蓝=指示、绿=指路、棕=旅游区。模型看到一块红色圆牌，「这是禁令类」这个判断有一大半来自颜色——这是数据本身的统计事实，不是模型的偏见。

于是问题变得可以精确回答：色相偏移多少度，会让一块红色禁令牌落进另一个类别的颜色区间？

\[d_H(h_1,h_2)=\min\bigl(|h_1-h_2|,\;360^\circ-|h_1-h_2|\bigr),\qquad \hat{c}(h)=\arg\min_{c}\;d_H\bigl(h,\;h_c\bigr)\]

把每个类别的代表色算出色相 h_c，用最近色相作为一个「颜色族分类器」。某一类的安全余量，就是它到相邻类色相的一半（越过中点就翻类）。取本课用的一组代表色，结果是：

最小余量是 25.2°，出现在「红↔黄」这一对上——而这恰恰是 TSR 里后果最严重的一对：把「禁止驶入」认成「注意危险」，或者把「限速」认成「解除限速」，下游动作完全不同。现在把常用库的默认值放进同一把尺子：

* OpenCV 的 HSV 色相通道是 0–179（用 1 个单位表示 2°），所以 hue_shift_limit=20 等于 ±40°——这个单位换算是最常被漏掉的一步，很多人以为自己只抖了 20°。

直白说

为什么 YOLOv5 的默认值反而安全？因为它做的是乘性色相变换（H' = H · r，r ∈ [0.985, 1.015]），偏移量正比于色相值本身。而纯红在 OpenCV 里的色相值接近 0 或 179，乘性变换对色相值 0 附近的像素几乎没有影响——红色恰好是这个实现下最被保护的颜色。这纯属幸运，不是设计。换成 albumentations 的加性实现，同样的「20」就直接把红推进黄的地盘。

严谨说

更严谨地讲，判据不该只看色相中心，还要看类内色相分布的宽度。真实数据里「红」不是一个点：褪色的红、逆光下的红、夜间路灯下的红，色相能散布 ±15°。所以有效余量 = 半间隔 − 类内散布，25.2° 的一半余量里已经有相当一部分被真实变异吃掉了。正确做法是：从训练集里实际统计每个颜色族的色相直方图，取分位数算出真实的类间间隔，再据此定抖动上限——而不是用我们这里的四个代表色。notebook 的练习 1 会把这个流程实现出来。

主动说出来能加分的一段话

面试高频点，而且是主动提能加分的那一类。当面试官问「你会怎么给交通标志做数据增强」时，绝大多数候选人会背一遍 flip / scale / mosaic / HSV。能立刻区分出「跑过 baseline」和「想过这个任务」的，是下面这句话：

「交通标志有两个别的检测任务没有的增强禁区：一个是水平翻转（左转会变右转、文字会镜像），另一个是色相抖动——因为颜色本身就是类别语义的一部分。我算过，用常见的一组代表色，红色禁令牌只要色相正向偏移约 25 度就会落进黄色警告牌的色相区间，而 albumentations 的默认 hue_shift_limit=20 在 OpenCV 单位下等于 ±40 度，直接越界。所以我会把色相抖动限死在 ±12 度以内，而把幅度让给亮度、对比度和天气合成。」

这段话里有禁区、机理、具体数字、具体库的默认值、以及替代方案——五个要素齐全，追问也接得住。

反过来也要警惕过度保守。完全不做色相/饱和度抖动，模型会把「精确的那个红」当成必要条件，遇到褪色牌、夜间色偏、不同厂家的油漆批次就掉点。正确姿势不是「不抖」，而是「小幅抖 + 大幅抖饱和度与亮度」——饱和度和亮度的变化在真实世界里幅度大得多，而它们不跨越类别边界。

4传感器与编码链路上的退化：噪声、量化、压缩

光度增强里最容易被做成「假的」的一类，就是噪声。img + N(0, σ) 这一行代码在物理上是错的：真实的图像噪声不是加性高斯，而是「信号相关的泊松（光子散粒噪声）+ 信号无关的高斯（读出噪声）」，再经过数字增益放大。

\[\mathrm{SNR}=\frac{N}{\sqrt{N+\sigma_r^2}}\;\xrightarrow[\;N\gg\sigma_r^2\;]{}\;\sqrt{N},\qquad N \propto t_{exp}\cdot L\]

这个式子给出一个可以直接背的结论：在散粒噪声主导的区间，曝光量降到 1/16，信噪比只降到 1/4（√16 = 4）。换句话说，夜间画质差不是线性地差，而是按平方根变差——这解释了为什么「稍微暗一点」看起来还行，而「暗到某个点之后」画面突然崩掉：一旦 N 掉到与 σ_r² 同量级，读出噪声接管，SNR 开始线性下降。

直白说

JPEG 伪影对 TSR 的危害被严重低估。JPEG 的量化是在 8×8 的块上做的：一块 24×24 像素的限速牌，整个牌面只占 9 个块——牌上的「60」这两个数字所依赖的高频 DCT 系数，正是被量化表压得最狠的那一批。结果是：框还在、检测还检得出，但「限速 60 / 限速 80」这一对细粒度分类直接崩掉。这在两级架构（C55 模块 02）里表现为「检测召回正常、分类准确率异常低」，是一个非常有指纹特征的故障。

严谨说

更工程化的一点是训练数据与车端数据的编码链路不同。训练集通常是「相机 → JPEG 存盘 → 解码 → 训练」，车端是「相机 → ISP → 直接送模型」，中间没有 JPEG。于是模型在训练时见惯了块效应，上车后反而遇到了「太干净」的图——这是一种反向的域差，症状是离线指标好、路测更好或更差都可能，很难归因。正确做法是让训练与部署的编码链路对齐：要么训练时也用 ISP 直出的无损帧，要么在部署前把车端帧过一遍同样的编码。这与 C60 模块 01 讲的预处理一致性是同一个方法论。

顺序陷阱：resize(noise(img)) ≠ noise(resize(img))。缩小图像会对噪声做平均，把 σ 降低约 1/缩放比；所以「先在原分辨率加噪、再 letterbox 到 640」得到的噪声，比「先 letterbox、再加噪」弱得多。真实链路是先成像（带噪）再缩放，所以正确顺序是「先加噪再 resize」——但绝大多数增强流水线因为性能原因把 resize 放在最前面。这是一个「为了速度而牺牲物理正确性」的真实取舍，知道它存在比强行修正更重要。

5天气与光照合成：用物理模型，不要用滤镜

「加个雾」在图像处理里可以是一行 cv2.addWeighted，但那样合成出来的雾与距离无关——近处的车和 80 米外的标志被雾化了同样的程度。真实的雾不是这样，它有一个非常干净的物理模型，这也是本节要求手写实现的原因。

大气散射模型（Koschmieder）

\[I(x)=\underbrace{J(x)\,t(x)}_{\text{直接透射}}+\underbrace{A\,\bigl(1-t(x)\bigr)}_{\text{环境光}},\qquad t(x)=e^{-\beta\, d(x)},\qquad \beta=\frac{-\ln 0.05}{V}\approx\frac{3.0}{V}\]

其中 J 是无雾的真实场景辐射、A 是大气光（通常取天空的颜色）、d(x) 是每个像素的深度、β 是散射系数、V 是meteorological visibility（气象能见度，定义为对比度衰减到 5% 的距离）。关键点是 t 依赖深度——所以合成雾必须有一张深度图，哪怕是很粗糙的（地平线以下按行线性递减，就已经比全局叠加真实得多）。

直白说

合成天气最常见的坑不是模型写错，而是只合成了退化，没有合成相机对退化的反应。真实的雾天，车载相机的自动曝光会拉高增益（画面更亮更噪）、ISP 的对比度增强会试图「去雾」（把已经压缩的动态范围再拉开，放大噪声与量化台阶）、自动白平衡会被灰白的大气光带偏。只叠加一层 I = Jt + A(1-t)，得到的是「一台完全不做自动调节的相机拍的雾」——那台相机不存在。

严谨说

所以工程上更靠谱的顺序是：合成退化 → 模拟 ISP 的响应（自动曝光把均值拉回目标亮度、自动增益放大噪声、色调映射压对比度）→ 再量化到 8 bit。这样合成出来的图，其亮度直方图与真实雾天数据的直方图才对得上。验证方法也很朴素：拿一批真实雾天帧，与合成雾天帧比较亮度直方图、局部对比度分布、噪声功率谱三个统计量——三个都对得上，合成数据才值得进训练集。这比「看起来像雾」可靠得多。

合成数据进训练集之前必须回答一个问题：它会不会引入「合成指纹」。如果所有合成雾图的大气光 A 都是同一个常数、深度图都来自同一个线性假设，模型完全可能学到「见到这种特定的灰白渐变就是雾天场景」这个捷径，而不是学到「在低对比度下也要能找到标志」。症状是：合成雾上指标飞涨，真实雾上纹丝不动。对策是把 A、β、深度图的形态都随机化，并且始终保留一小份真实恶劣天气数据作为「不可被合成数据污染」的评测集。

6运动模糊与卷帘快门：车载相机独有的两种畸变

这两个退化在通用检测的增强库里几乎不出现，但在车上它们是天天发生的物理事实。而且它们都能被算清楚——不需要经验参数，只要相机内参和车速。

运动模糊：一个与焦距无关的比值

设相机焦距 f（像素）、标志物理尺寸 S、距离 Z、横向偏移 X（标志离相机光轴的横向距离，路侧牌典型 2–4 m）、自车速度 v、曝光时间 t_exp。标志在图像上的横坐标 u = fX/Z，对时间求导（dZ/dt = -v）得到像移速度 |du/dt| = fXv/Z²。于是：

\[L_{blur}=\frac{f X v}{Z^{2}}\,t_{exp},\qquad s_{px}=\frac{fS}{Z}\quad\Longrightarrow\quad \boxed{\;\frac{L_{blur}}{s_{px}}=\frac{X\,v\,t_{exp}}{S\,Z}\;}\]

模糊长度与目标像素尺寸的比值和焦距无关——换长焦镜头，模糊和目标一起放大，比值不变。这意味着「用长焦看远处标志」这个方案不会让运动模糊问题变好，这是一个很多人第一反应会想错的结论，也是面试里可以直接抛出的一个小推导。

（表中固定 X = 3 m、S = 0.6 m。）这张表把「为什么 TSR 夜间掉点特别多」拆成了一条可以完整讲出来的因果链——面试里被问到这个问题，下面这条链比「因为夜间光照差」有力得多：

  1. 光子少 → 要么拉长曝光，要么拉高增益，二选一（没有第三条路）；
  2. 拉长曝光 → 运动模糊按 t_exp 线性增长（上表最后两行）；
  3. 拉高增益 → SNR 按 √N 下降，噪声吃掉牌面的高频细节；
  4. 两条路都在削同一样东西：牌面上区分「限速 60」和「限速 80」的那点高频；
  5. 于是夜间的典型故障不是「检不出」，而是「检得出但认错」——混淆矩阵上是同族内的细粒度错分，不是跨族乱窜；
  6. 对应的解法也就明确了：低光合成 + 运动模糊必须成对进增强配方（只加噪不加模糊，等于只模拟了高增益那条路），评测必须按夜间/白天分桶，且要单独看细粒度分类准确率而不只看 mAP。

直白说

很多人第一次听到卷帘快门，想到的是手机拍螺旋桨那种夸张的弯曲。在 TSR 里这个直觉是错的：交通标志在图像上只占几十行，行与行的时间差是零点几毫秒，物体内部的畸变小于 1 个像素，完全淹没在标注误差里。所以「要不要给增强加卷帘畸变」的答案通常是「不需要」——把算力花在运动模糊和低光合成上收益大得多。

严谨说

但卷帘快门有一个真正会出事的地方：时序融合与运动补偿必须用「行时间戳」而不是「帧时间戳」。C55 模块 04 讲的多帧融合依赖「自车运动已知 + 标志静止 → 可以预测下一帧位置」，而这个预测用的是自车位姿在某个时刻的值。如果整帧用一个时间戳，30 m/s 下就引入了最多 0.6 m 的位姿误差；投影到 30 m 外的标志上，横向偏差可达数像素——对一个 20 px 的目标，这足以让 IoU 关联失败、跟踪断裂。症状是「跟踪 ID 频繁切换、迟滞状态机反复重置」，而根因在传感器时间模型上，不在跟踪算法里。这是一个非常典型的「在错误的层里 debug」的例子。

把这一节压成两句：运动模糊要算、要合成、要进配方；卷帘畸变不用合成，但一定要在时间戳上处理对。判断一个退化该不该做成增强，标准是「它是否改变了模型输入的像素分布」——卷帘畸变对小目标几乎不改变像素，所以它不是增强问题，是系统时间同步问题。

7域随机化与合成-真实的取舍

把上面这些合成手段串起来，就得到了domain randomization（域随机化）的朴素形式：与其猜测部署域长什么样，不如把训练域撑得足够宽，让部署域落在里面。这个思路在机器人仿真到实机迁移上非常成功，但直接搬到 TSR 上有明确的边界。

真实采集物理模型合成（本模块）渲染引擎 / 生成模型合成
单位成本高（采集车 + 标注）近乎为零中（要建场景/训模型）
长尾覆盖差（罕见天气可能几个月遇不到）好（参数直接扫）好
保真度满分中（缺 ISP 动态响应）中-高（但有生成指纹）
标注成本高零（原标注直接复用）零（渲染）/ 高风险（生成可能改变内容）
可控性无完全可控（β、A、t_exp 都是旋钮）部分可控
主要风险分布偏斜（只采到常见场景）合成指纹 → 学到捷径内容漂移 → 标注失效

直白说

域随机化的适用边界可以用一句话划清：它对「有物理模型的变化」有效，对「没有物理模型的变化」无效。曝光、噪声、雾、模糊都有干净的物理模型，随机化它们能真实地扩大覆盖；而「这个国家的标志底色偏暖」「这批标志的反光膜老化了」「这个路口的广告牌长得像禁令牌」这类变化没有模型可随机化——只能靠采集与挖掘（C58 整门课在讲这件事）。

严谨说

还有一个反直觉的边界：随机化过头会伤害精度。域随机化的代价是让模型学一个更宽的不变性，而模型容量与训练预算是固定的。把训练分布撑到「什么都可能」，模型在真实分布上就会欠拟合——这与模块 03 要讲的「小模型 + 强增强 = 欠拟合」是同一个现象的不同表述。正确的做法不是「尽量宽」，而是「宽到刚好覆盖部署分布的尾部」：先用真实数据估计部署分布的参数范围（能见度分布、曝光时间分布、车速分布），再让随机化范围略微超出这个范围，而不是无限撑开。这也让「增强幅度」从一个玄学超参变成了一个可以从数据估出来的量。

合成数据混入训练集时，配比是一个需要单独调的超参，而且它与「合成数据的保真度」强相关：保真度越低，能容忍的比例越小。一个稳妥的起点是「合成数据占该场景真实数据的 1–3 倍，且总占比不超过训练集的 15%」，然后用模块 05 的分场景消融验证。绝对不要把合成数据也放进验证集——那会让指标彻底失去意义。

8给 TSR 配一套光度增强：从失效模式反推

把前面所有结论收成一张可以直接抄进配置文件的表。注意每一行的「理由」列都指向一个具体的失效模式——这是本课程一贯的主张：增强配方应该从失效模式反推，而不是从别人的 config 抄。

配这套表时有三条纪律：

  1. 概率会相乘。上表列了 10 个算子，看起来「每张图都被大改」，实际上「同时触发亮度+色相+雾+模糊」的概率是 0.8×0.3×0.15×0.25 ≈ 0.9%。直觉严重高估了实际强度——模块 04 会做这个统计。所以不要因为「算子多」就把每个概率都调低，那会让强增强根本不发生。
  2. 顺序要遵循成像链路：几何 → 雾化（依赖深度，必须在几何之后、否则深度图对不上）→ 曝光/亮度/对比度 → 运动模糊 → 噪声 → 量化 → JPEG。把 JPEG 放在噪声之前，等于假设「先压缩后加噪」，物理上不成立。
  3. 验证集只做确定性变换（resize + normalize），一个随机算子都不能有。这是铁律，模块 04 会讲为什么它常被无意破坏。

整套配方的设计原则可以浓缩成一句：把幅度让给「颜色语义之外」的维度。亮度、对比度、饱和度、噪声、模糊、天气——这些在真实世界里的变异幅度大得多，而且都不跨越类别边界，放开手抖；色相是唯一一个必须捏死的旋钮。这一条能推广到所有「某个视觉属性直接编码类别」的任务——医学影像里的染色颜色、工业质检里的缺陷颜色、遥感里的地物光谱，都是同一个模式。

9研究前沿与开放问题

光度增强看起来是最「工程」的一块，但它有几个真正未解的问题，而且都直接卡在 TSR 这类安全相关任务上。

  • 增强策略的自动搜索，在检测上仍未收敛。AutoAugment / RandAugment / TrivialAugment 在分类上给出了「几乎不用调」的方案，但检测的搜索空间要同时考虑框变换与多目标交互，搜索代价高一个数量级；而且搜出来的策略往往包含对 TSR 有害的色彩算子（搜索目标是整体 mAP，看不见「红→黄」这种颜色族错分）。「带语义约束的增强搜索」——即把「色相不得跨越类间边界」写成硬约束再搜——目前几乎没有现成工作。
  • 合成天气与真实天气的差距仍然可测且显著。Foggy Cityscapes 这类基于深度的合成集把「有雾数据」从零变成了有，但在真实雾天上的迁移增益远低于同等数量的真实数据。核心缺口是 ISP 的动态响应没有被建模——自动曝光、自动白平衡、去雾算法都会对退化做出反应，而这些反应本身就是域差的一部分。「把 ISP 放进训练回路」（ISP-in-the-loop，甚至直接在 RAW 域训练）是一条正在被认真探索的路线，代价是数据管线要重做。
  • 扩散模型生成恶劣天气数据的标注一致性问题。用图生图把晴天帧改成雨夜帧，视觉保真度已经很高，但生成过程可能悄悄改变标志的颜色、形状甚至内容——把一块限速 60 改成限速 80，标注却没变。这类「内容漂移」比合成指纹危险得多，因为它直接制造错误标签；目前的对策（用检测器/分类器回检生成结果）本身又依赖被训练的模型，存在循环论证。
  • 「增强幅度应该多大」缺少理论。现状是网格搜索 + 经验值。有一条有希望的思路是把幅度与部署分布的参数分布直接对齐：从路测数据估出能见度、曝光时间、车速的真实分布，让增强参数按这个分布采样（而不是均匀采样）。这把「增强调参」变成了「分布估计」，可验证性强得多，但需要车队回传足够的元数据，属于 C58 数据闭环的范畴。
  • 测试时适应（test-time adaptation）与增强的关系。既然域差不可能被增强完全覆盖，另一条路是在部署时用无标签数据在线适应（TENT、BN 统计更新等）。对车端来说这非常诱人（隧道进出、天气突变都是渐变域移），但在线更新的模型难以验证、难以回滚，与量产系统「可复现、可追溯」的要求直接冲突——这是一个技术上有效、工程上暂时用不了的典型例子。
  • 颜色恒常性（color constancy）能否替代色相增强。与其教模型对色相不变，不如在预处理里做白平衡校正，把颜色归一化到标准光源下。理论上更优雅，实践中受限于校正算法本身的失败模式（大面积单色物体会让灰世界假设失效——而一块占据画面的蓝色指示牌正是这种情况）。「校正 vs 增强」的取舍在 TSR 上还没有定论。

必读：Sakaridis, Dai & Van Gool, Semantic Foggy Scene Understanding with Synthetic Data（IJCV 2018，基于深度的合成雾与它对真实雾的迁移分析，本模块雾化模型的工程参考）；He, Sun & Tang, Single Image Haze Removal Using Dark Channel Prior（CVPR 2009，大气散射模型在视觉里的经典化，反过来也是最好的合成参考）；Cubuk et al., AutoAugment（CVPR 2019）与 RandAugment（NeurIPS 2020）——注意它们的搜索目标里没有语义颜色约束；Zoph et al., Learning Data Augmentation Strategies for Object Detection（ECCV 2020，检测专用增强搜索）；Brooks et al., Unprocessing Images for Learned Raw Denoising（CVPR 2019，把 sRGB 反推回 RAW 再合成噪声，本模块低光噪声模型的正确做法）；Tobin et al., Domain Randomization（IROS 2017，域随机化的原始论述与它的边界）。相邻课程：C55 模块 03（失效模式全景）、C56 模块 04（流水线与顺序）、C56 模块 05（消融验证）、C60 模块 01（预处理一致性）。完整清单见 references.md。
