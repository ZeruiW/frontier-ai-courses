1正面回答这个问题

学到这里，一个诚实的问题必须被正面回答：2026 年了，做一个文本分类任务，我到底该用 BERT 微调还是直接调 LLM？

网上的答案通常是两个极端——「LLM 什么都能做，别折腾小模型了」或者「BERT 又快又准，别用大炮打蚊子」。两个都是坏答案，因为它们都没有给出判据。本模块要做的是把这个决策变成一个可以计算的问题。

先把三种方案摆出来，看它们各自在什么维度上占优：

方案精度（有标注数据时）推理成本冷启动（无标注数据）可控性
encoder 微调（BERT/DeBERTa）★★★★★ 通常最高★★★★★ 1 次前向、110M 参数★ 需要几百到几千条标注★★★★★ 输出空间受约束
LLM few-shot / zero-shot★★★ 中等，取决于任务★ 7B+ 参数、要生成★★★★★ 零标注即可用★★ 可能输出格式外的东西
LLM 微调（LoRA 等）★★★★★ 与 encoder 相当或略高★★ 仍是大模型★★ 需要标注（比 encoder 少些）★★★ 好一些
LLM 蒸馏到 encoder★★★★ 接近 encoder 微调★★★★★ 同 encoder★★★★ 用 LLM 造标注★★★★★ 同 encoder

直白说

最后一行是当今工业界最实用、也最被低估的答案：用 LLM 生成标注，用这些标注微调一个小 encoder，线上跑小的。它同时拿到了 LLM 的零标注启动能力和 encoder 的推理经济性。整个流程可以在几天内完成，成本是「几百美元的 LLM 调用 + 几小时的微调」，换来的是一个便宜三个数量级的线上服务。

严谨说

为什么便宜这么多？因为两件事叠乘：①参数量差 60 倍（110M vs 7B）；②前向次数差几十倍（encoder 1 次 vs LLM 生成 20 个 token 要 20 次 decode + 1 次 prefill）。60 × 20 = 1200 倍——这还没算 LLM 需要 GPU 而 encoder 可以跑 CPU。本模块的 notebook 会把这笔账精确算出来，你会看到从 $X/百万次调用 到 $X/1000 的差距。

但要公平：有三类情况 encoder 明确不适用。①输出是自由文本（改写、摘要、对话）——encoder 生成不了；②任务需要世界知识或复杂推理（「这段代码有什么安全隐患」）——小 encoder 没有这些能力；③需求变化极快、来不及标注和重训——LLM 改个 prompt 就上线了。选型的第一个问题不是「哪个更准」，而是「我的任务落在哪一类」。

2推理成本：把差距算成数字

这一节把「便宜」变成可验证的数字。任务：对一段 128 token 的文本做二分类。

\[\text{FLOPs} \approx 2 \times N_{params} \times N_{tokens\_processed}\]

这个经验公式（每个参数每个 token 约 2 次浮点运算，前向）足够做量级比较。关键在 N_tokens_processed——它对两种方案完全不同：

方案参数量处理的 token 数前向 FLOPs相对
BERT-base 分类110M128（一次编码）≈ 2.8×10¹⁰1×
DeBERTa-v3-base184M128≈ 4.7×10¹⁰1.7×
DistilBERT（6 层）66M128≈ 1.7×10¹⁰0.6×
Llama-8B zero-shot（输出 5 token）8B128 prefill + 5 decode≈ 2.1×10¹² + 生成≈ 75×
Llama-8B 输出 100 token（带解释）8B128 + 100≈ 3.6×10¹²≈ 130×

直白说

FLOPs 只是一半的故事，另一半是内存带宽。LLM 的 decode 阶段是 memory-bound 的——每生成一个 token 都要把全部权重从显存读一遍。8B 模型 fp16 是 16 GB，即使在 2 TB/s 带宽的卡上，理论上每步至少 8 ms。生成 100 个 token 就是 0.8 秒起。而 BERT-base 的一次前向在同一张卡上是毫秒级。

严谨说

还有一个更实际的维度：能不能跑在 CPU 上。BERT-base 在现代 CPU 上单条推理约 20–50 ms，完全可以在没有 GPU 的服务器上部署；量化后（INT8）可以到 10 ms 以内。8B LLM 在 CPU 上是几秒一个 token，实用性为零。「不需要 GPU」这件事本身就是巨大的成本与运维差异——这是 C48 模块 03/05 讨论的整个 GPU 调度与成本问题都可以跳过。

一个必须诚实标注的边界：上面的对比是「同样做二分类」的场景。如果任务本身需要 LLM 的能力（推理、世界知识、生成），这个对比就不成立——不是 encoder 便宜 100 倍，而是 encoder 做不了。成本比较只在「两者都能达到可接受精度」的前提下有意义。所以正确的顺序是：先确认 encoder 能不能达到精度要求（跑一个实验），能，再谈成本；不能，成本再低也没用。

3蒸馏：把 LLM 的能力搬进小模型

既然大模型准、小模型快，自然的想法是让小模型学大模型。这就是 knowledge distillation（知识蒸馏，Hinton et al. 2015）。

为什么软标签比硬标签好

蒸馏的核心不是「用大模型的预测当标签」，而是用大模型的完整概率分布当标签。区别很大：

一张图片/一段文本，教师模型的输出分布: 硬标签 (one-hot): [0, 1, 0, 0] ← 只告诉你「是猫」 软标签 (soft): [0.02, 0.85, 0.12, 0.01] 狗 猫 虎 汽车 ↑ 「有点像虎」——这条信息在硬标签里完全丢失！ 软标签携带的是**类间相似结构**（dark knowledge）： · 猫和虎相似，和汽车不相似 · 这个样本有多典型（0.85 vs 0.99） 一个 4 类问题，硬标签给 log2(4)=2 bit，软标签给的信息多得多。
\[\mathcal{L} = \alpha \underbrace{\text{CE}(y_{true}, p_{student})}_{\text{硬标签}} + (1-\alpha) \underbrace{T^2 \cdot \text{KL}\big(p^{T}_{teacher} \,\|\, p^{T}_{student}\big)}_{\text{软标签，温度 } T}\]
超参作用典型值注意
温度 Tsoftmax(logits/T)，T 越大分布越平滑、暴露越多类间结构2 – 5T=1 退化为普通概率；T→∞ 趋于均匀
T² 缩放补偿软标签梯度随 1/T² 衰减必须有忘了它，蒸馏项的梯度会随 T 增大而消失
α硬标签与软标签的权重0.1 – 0.5有真标签时保留一点硬标签通常更稳

直白说

T² 这个因子是最容易被漏掉的细节。软标签交叉熵对 student logits 的梯度里带一个 1/T，而 teacher 分布本身的平滑又贡献一个 1/T，合起来梯度按 1/T² 衰减。所以要乘 T² 把它补回来，否则 T=4 时蒸馏项的梯度只有硬标签项的 1/16，等于没做蒸馏。notebook 会把这个梯度尺度直接测出来。

严谨说

除了 logit 蒸馏，还有两类常用做法：①中间层蒸馏（让 student 的隐状态/注意力矩阵去拟合 teacher 的对应层，如 TinyBERT）——信号更密集但需要处理层数不匹配与维度对齐；②数据蒸馏（用 teacher 在无标注数据上打标签，然后当成普通监督数据训 student）——最简单、最工程友好，且可以跨架构（用 LLM 蒸馏到 encoder 就属于这类，因为二者的 logit 空间根本对不上）。

对「LLM → encoder」这个具体场景，只有数据蒸馏可行，因为两者的输出空间完全不同（LLM 输出的是 token 分布，encoder 输出的是类别分布）。但这反而简化了工程：你只需要让 LLM 输出标签（甚至可以让它输出置信度当作软标签），然后当成普通标注数据用。DistilBERT 那种同架构 logit 蒸馏是另一回事——它适用于「BERT → 小 BERT」，收益是 40% 更小、60% 更快、保留 97% 的 GLUE 性能。

4检索：双塔与交叉编码的成本-精度前沿

这是 encoder 今天最不可替代的战场。检索/语义搜索/RAG 的召回环节，几乎全部由 encoder 承担。原因就在模块 03 提过的那个二分：

任务: 从 100 万个文档里找出与查询最相关的 10 个 方案 A: cross-encoder（交叉编码） 对每个 (查询, 文档) 对拼在一起过模型 → 一个相关性分数 ┌──────────────────────────────────┐ │ [CLS] query [SEP] document [SEP] │──▶ BERT ──▶ score └──────────────────────────────────┘ 精度: ★★★★★（query 与 doc 的每个 token 都能互相注意） 成本: **100 万次前向 / 每个查询** ← 完全不可行 方案 B: bi-encoder（双塔） 两边分别编码成向量，用点积/余弦打分 query ──▶ BERT ──▶ q (768,) ┐ doc ──▶ BERT ──▶ d (768,) ┘──▶ score = q·d 精度: ★★★（两边没有交互） 成本: **文档向量离线预计算一次**；在线只编码 query（1 次）+ 向量检索（ANN，毫秒级） 方案 C: 两阶段（工业标准） ① bi-encoder 召回 top-100 （1 次前向 + ANN 检索） ② cross-encoder 精排 top-100 （100 次前向） 精度: ★★★★☆ 成本: 101 次前向 —— 可行！

直白说

两阶段架构不是妥协，而是在成本-精度前沿上的正确取点。它利用了一个关键的不对称：召回阶段只需要「不漏掉」（高 recall），不需要精确排序；精排阶段只需要处理很少的候选。把「贵而准」的模型用在已经缩小到 100 个的候选集上，成本就从 100 万次降到 100 次。

严谨说

定量地看：设召回 k 个候选，双塔的 recall@k 是 R(k)，交叉编码在候选集内的精度是 P。端到端质量约为 R(k) × P，成本约为 C_bi + k·C_cross。R(k) 随 k 快速饱和（k=10→100 提升明显，100→1000 提升很小），而成本随 k 线性增长。所以最优 k 落在 R(k) 曲线的拐点附近，通常是 50–200。notebook 会把这条前沿画出来并求最优 k。

句嵌入：为什么不能直接用 BERT 的 [CLS]

模块 01 和 03 都提过这一点，这里给出完整的原因与解法。直接拿预训练 BERT 的 [CLS]（或 mean pooling）做句向量，效果比 GloVe 词向量平均还差（Reimers & Gurevych 2019 的著名发现）。三个原因：

  • [CLS] 没有被训练过（去掉 NSP 后尤其如此）——模块 01 已论证。
  • 各向异性（anisotropy）：BERT 的表示集中在一个狭窄锥体里，任意两句的余弦相似度都在 0.7+，失去区分度。
  • 训练目标错配：MLM 优化的是「从上下文恢复词」，不是「相似句子的向量应该接近」。这两个目标并不天然一致。

解法是用对比学习专门训练句嵌入：SBERT 用有监督的 NLI 数据（蕴含对为正例、矛盾对为负例），SimCSE 用无监督的 dropout 作为数据增强（同一句过两次 dropout 得到正例对，batch 内其他句为负例）。核心损失是 InfoNCE：

\[\mathcal{L} = -\log \frac{\exp(\text{sim}(q, d^+)/\tau)}{\exp(\text{sim}(q, d^+)/\tau) + \sum_{d^-} \exp(\text{sim}(q, d^-)/\tau)}\]
负例设计再次决定一切

对比学习有个决定成败的因素：负例的质量与数量。用 batch 内随机句子当负例（in-batch negatives）最简单，但这些负例太容易区分（主题都不同），模型学不到细粒度。hard negatives（用当前模型检索出来的、排名靠前但实际不相关的文档）能大幅提升效果，DPR 与后续工作都强调这一点。这又回到了模块 01 的那条方法论：负例设计决定任务难度，也决定学到什么——NSP 的失败、SOP 的成功、对比学习的 hard negative，是同一条原理的三次体现。

5选型决策：一棵可执行的树

① 你的输出是什么？ ├─ 自由文本（改写/摘要/对话/代码） │ └─▶ 生成式。短输入长输出 → decoder-only LLM │ 长输入短输出 → enc-dec（T5/BART 系）或 LLM，算 KV 账（模块 04） │ └─ 标签 / 片段 / 向量 → 进入 ② ② 有多少标注数据？ ├─ 0 条，且需求可能天天变 │ └─▶ LLM zero/few-shot。**先上线，再看要不要优化** │ ├─ 0 条，但需求稳定、量大 │ └─▶ **LLM 造标注 → 蒸馏到 encoder** ← 最被低估的方案 │ └─ 几百条以上 → 进入 ③ ③ 推理量有多大？ ├─ 小（每天几千次） │ └─▶ 怎么方便怎么来。工程时间比算力贵。 │ └─ 大（每天百万次 / 需要低延迟 / 要跑 CPU） └─▶ **encoder 微调**（DeBERTa-v3 起步，不是 bert-base） ├─ 还要更快 → 蒸馏 + INT8 量化（C27） └─ 是检索任务 → 双塔召回 + 交叉编码精排两阶段

这棵树里有几个判断值得单独强调，因为它们与「直觉」相反：

常见直觉更准确的说法
「LLM 更强，所以精度更高」有足够标注数据时，微调过的 encoder 在封闭标签集任务上通常不输甚至更好。LLM 的优势是零样本与泛化，不是「在这个特定任务上更准」
「小模型是过渡方案，早晚被淘汰」单位经济的差距是 100–1000 倍，不会因模型进步而消失。只要还存在「高频、简单、封闭」的任务，小模型就有位置
「用 BERT 就够了」bert-base-uncased 是 2018 年的技术。同等成本下 DeBERTa-v3 或现代化 encoder 明显更好（模块 02）
「LLM 蒸馏很复杂」数据蒸馏就是「让 LLM 打标签，再当普通监督数据用」，几百行代码、几百美元、几天时间
「检索用 LLM embedding 更好」取决于任务与预算。专门训练的小嵌入模型在很多检索基准上不输大模型 embedding，而且便宜几十倍；但跨语言/长文档场景大模型 embedding 有优势

还有一个纯工程的考量常被忽略：可控性与可测试性。encoder 分类器的输出必然落在预定义的标签集里，你可以为它写单元测试、算精确的混淆矩阵、设置阈值、做校准（C10）。LLM 输出的是自由文本，即使要求它「只输出 A 或 B」，也存在小概率输出别的东西——你必须写解析与兜底逻辑。在需要严格 SLA 的生产环境里，「输出空间受约束」本身就是一个有价值的性质，它不体现在任何 benchmark 分数上。

6算一笔账：一个真实的选型决策

场景：内容审核，判断一段用户评论是否违规。每天 200 万次调用，延迟要求 P95 < 100 ms，已有 5000 条人工标注。

方案精度（假设）单次成本日成本P95 延迟结论
Llama-8B zero-shot0.86$0.00012$240~800 ms❌ 延迟超标
Llama-8B + LoRA 微调0.93$0.00012$240~800 ms❌ 延迟超标
DeBERTa-v3-base 微调0.94$0.0000018$3.6~35 ms✅ 推荐
DistilBERT 蒸馏 + INT80.92$0.0000004$0.8~12 ms✅ 极端成本敏感时

这张表里最刺眼的数字是 $240 vs $3.6——67 倍，一年是 8.6 万美元 vs 1300 美元。而精度差异是 0.93 vs 0.94（encoder 反而略高，因为有 5000 条领域内标注）。

但表格没说的部分同样重要，必须诚实列出：

  • 如果只有 0 条标注，LLM zero-shot 的 0.86 就是你能立刻拿到的；encoder 需要先标注或先蒸馏。「立刻可用」有真实的商业价值。
  • 如果违规类型每周都在变（新的规避手段），LLM 改 prompt 即可，encoder 要重新标注+重训。迭代速度可能比成本更重要。
  • 如果需要给出违规理由（给运营看的解释），encoder 给不了。这时可能需要「encoder 判断 + LLM 只对判为违规的少数样本生成解释」的混合方案——又是一个两阶段架构。

把整门课浓缩成一句话：三种 Transformer 形态不是「进化的三个阶段」，而是「注意力掩码的三种画法」，各自在不同的任务形状上占优；今天的正确做法不是选一个，而是把它们组合成两阶段/混合架构，让贵的模型只处理少量真正需要它的样本。双塔召回 + 交叉精排是这样，LLM 造标注 + encoder 上线是这样，encoder 判断 + LLM 解释也是这样。「用便宜的模型过滤，用贵的模型处理剩下的」是这个领域最通用、最被低估的架构模式。

7研究前沿与开放问题

  • encoder 与 decoder 的能力边界：随着 decoder-only 规模增长，双向表示的优势在很多基准上被抹平。在什么任务、什么规模下双向仍有不可替代的优势，缺乏系统的实证刻画。有工作发现在需要精细 token 级理解的任务（NER、抽取）上 encoder 仍占优，但边界不清晰。
  • LLM 作为标注器的可靠性：数据蒸馏的质量上限由 teacher 决定。LLM 标注的系统性偏差（位置偏好、长度偏好、对模糊样本的过度自信）会被 student 完整继承甚至放大。如何检测与校正这些偏差、以及需要多少人工标注来锚定，是活跃的实践问题（与 C03/C10 的 LLM-judge 研究同源）。
  • 嵌入模型的统一评估：MTEB 等基准推动了嵌入模型的发展，但也带来「刷榜」问题——针对基准优化的模型未必在真实检索中更好。检索质量与下游 RAG 效果之间的关系也不是单调的（更好的召回不一定带来更好的生成）。
  • 两阶段架构的联合优化：召回与精排通常分别训练，但它们的目标并不一致（召回要 recall，精排要 precision）。端到端联合训练、或让精排的信号回流指导召回（如 distillation from cross-encoder to bi-encoder）是有效但尚未标准化的方向。
  • encoder 的现代化与规模化：把现代组件装进 encoder 已被证明有效（模块 02），但 encoder 的缩放律、以及「大 encoder」（10B+）是否有价值，几乎无人系统研究。这可能是一个被规模化叙事掩盖的机会。
