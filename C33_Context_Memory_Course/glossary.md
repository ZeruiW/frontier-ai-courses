# 术语词典 · Glossary（上下文工程与记忆）

> 按主题分组，每条 2–3 句中文释义、英文术语保留。读 Anthropic 的 context engineering / prompt caching 文档、Messages API 规范、以及 RAG / 长上下文论文遇到生词回这里查。本课用纯 Python 标准库 + MockLLM 在 CPU 上模拟这些机制，但术语与真实 agent 系统、真实 Claude API 一一对应。

## 上下文工程总览 · Context Engineering Overview

| 术语 (EN) | 中文 | 释义 |
|-----------|------|------|
| context window | 上下文窗口 | 模型一次前向能看到的 token 上限（如 200K）。它是 agent 最稀缺的资源：一切要让模型「看到」的东西——系统提示、工具定义、对话历史、检索结果、记忆——都要挤进这一个窗口。本课的全部技术都是在经营这块有限空间。 |
| context engineering | 上下文工程 | 系统化地决定「在每一步把哪些信息、以什么形式放进上下文窗口」的工程学科。不是写一句好提示，而是管理一个随时间增长、可能溢出的信息预算：什么进、什么裁、什么压、什么写到外部再按需召回。 |
| token | 词元 | 模型处理文本的最小单位，介于字符与单词之间。token 数（而非字符数或字数）决定是否塞得下窗口、决定计费。英文约 1 token≈4 字符，中文常 1 字≈1–2 token；真实计数需用模型自带 tokenizer（本课用确定性近似）。 |
| tokenizer | 分词器 | 把文本切成 token 序列的算法（如 BPE）。同一段文本在不同模型的 tokenizer 下 token 数可能不同；真实计数要用目标模型的 tokenizer 或 `count_tokens` 接口，绝不能用别家（如 tiktoken 估 Claude 会偏差很大）。 |
| token budget | token 预算 | 给上下文各部分（系统/工具/历史/检索/记忆/留给输出的 `max_tokens`）分配的 token 配额。预算之和必须 ≤ 窗口。本课模块 01 从零实现「按预算分配并在超出时裁剪」的预算器。 |
| max_tokens | 最大输出 | 一次请求里模型最多能生成的 token 数。它和输入一起占用窗口：`输入 token + max_tokens ≤ 窗口`。给输出留太少会被截断（`stop_reason='max_tokens'`），留太多挤掉历史。 |
| MockLLM | 模拟模型 | 本课用的确定性「假模型」：用规则/查表代替神经网络，对给定输入返回可预测的输出（如摘要=拼接要点、embedding=词频向量）。它让整套上下文管线无需 API key 即可端到端跑通并被 assert 验证，把学习焦点钉在预算与控制流上。 |
| ground truth / oracle | 真值 / 参照 | 我们事先知道正确答案的对照物。本课每个机制都和一个朴素参照对拍：截断后 token 数 ≤ 预算、摘要后关键 id 仍在、检索 top-k 与暴力扫描一致、缓存命中数等于解析值——assert 通过即逻辑正确。 |

## Token 计数、预算与截断 · Counting, Budget & Truncation

| 术语 (EN) | 中文 | 释义 |
|-----------|------|------|
| token counting | token 计数 | 估算一段文本/一组消息占多少 token。真实系统用 `messages.count_tokens` 或模型 tokenizer；本课用一个确定性近似（按空白与字符规则）保证可重复、可断言，重点在「计数→预算→裁剪」这条控制流而非数字精确。 |
| budget allocation | 预算分配 | 把总预算切给各部分：系统提示与工具定义通常固定且必须保留，剩余额度分给历史/检索/记忆，并扣掉给输出预留的 `max_tokens`。分配策略直接决定「优先保住什么」。 |
| truncation | 截断 | 当内容超出预算时丢弃一部分以塞进窗口。关键是丢弃策略：丢哪些、保哪些。错误的截断会丢掉系统指令或正在引用的关键信息，让 agent「失忆」或「跑题」。 |
| head truncation | 头部截断 | 丢弃序列最前面的内容（最旧的）。对话里最旧的往往最不相关，所以「丢头保尾」是常见默认；但系统提示也在最前，必须先把它从可丢区域里排除。 |
| tail truncation | 尾部截断 | 丢弃序列最后面的内容（最新的）。一般不可取——最新消息通常最相关；但在某些「保留开头设定」的场景（如保住任务描述）下会用到。 |
| middle truncation / lost in the middle | 中间截断 / 中间迷失 | 丢弃序列中段、保留两端。其依据是 Liu 等 2023《Lost in the Middle》发现：模型对上下文两端（开头/结尾）的信息利用率显著高于中段。所以把最重要的信息放两端、必要时裁中段，是一种对齐模型注意力的截断策略。 |
| priority-based truncation | 优先级截断 | 给每条消息打优先级（系统>当前任务>近期>远期>可弃），超预算时从最低优先级开始丢，直到塞下。比单纯按位置截断更鲁棒，是本课模块 01 的核心练习。 |
| message retention / pinning | 消息保留 / 钉住 | 把某些消息标记为「永不丢弃」（系统提示、关键事实、用户的硬约束）。截断器必须先保住这些钉住项，再在剩余预算里裁其余。 |
| recency window / sliding window | 近期窗口 / 滑动窗口 | 只保留最近 N 条消息（或最近 N token）作为原文，更早的丢弃或交给摘要/记忆。是最简单的历史管理，但会硬性丢失早期信息——于是有了 compaction。 |
| reserved output tokens | 输出预留 | 在预算里专门留给模型生成的额度（即 `max_tokens`）。常见 bug 是把窗口塞满输入、没留输出空间，导致回答被腰斩。预算器必须先扣这部分。 |

## Compaction 与摘要 · Compaction & Summarization

| 术语 (EN) | 中文 | 释义 |
|-----------|------|------|
| compaction | 压缩 / 紧致化 | 当对话历史接近窗口上限时，把较早的消息用模型摘要成一小块「压缩记忆」，替换掉原文，从而腾出空间继续对话。与「直接丢弃」相比，它试图保住信息而非简单遗忘。Anthropic 在长会话里提供服务端 compaction。 |
| rolling summary / running summary | 滚动摘要 | 维护一份随对话不断更新的摘要：每次触发就把「上一份摘要 + 新一批旧消息」再摘要成新的一份。好处是摘要本身有界、不会无限增长；难点是多轮摘要可能逐渐丢细节（摘要漂移）。 |
| summarization trigger / threshold | 摘要触发阈值 | 决定何时启动压缩的条件：常按「历史 token 数超过窗口的某比例」（如 70%）触发，或按消息条数。阈值太高会来不及（先爆了），太低会过度压缩（频繁丢原文）。 |
| key information retention | 关键信息保留 | 压缩时必须保住的东西：用户的硬性约束、已确定的决策、待办、关键实体/ID。好的摘要 prompt 会显式要求「保留这些类别」；本课用「关键 id 集合在摘要后仍可被检出」作为可断言的保留判据。 |
| compression ratio | 压缩比 | 摘要后 token 数 / 摘要前 token 数。比值越小压得越狠、省空间越多，但丢信息风险越大。是衡量 compaction 强度的核心指标，本课模块 02 让你计算并验证它落在合理区间。 |
| recent-messages preservation | 近期原文保留 | compaction 通常只摘要「旧」消息，保留最近若干条的原文不动——因为近期上下文对下一步决策最关键，摘要它会损害连贯性。即「摘要远期、原样保留近期」。 |
| handoff / continuation | 交接 / 续接 | 把一个濒临爆窗的会话「交接」给一个新会话：用压缩摘要 + 关键状态作为新会话的起点。是超长任务跨多个上下文窗口推进的常见模式。 |
| summary drift | 摘要漂移 | 多轮滚动摘要中，信息在反复转述里逐渐失真或丢失的现象（类似「传话游戏」）。缓解办法：保留关键事实原文、对重要类别做结构化抽取而非自由摘要。 |
| context rot | 上下文腐化 | 随着窗口被无关或过时内容填满，模型表现下降的现象。compaction、截断、检索都是对抗 context rot 的手段：让窗口里尽量只剩当前相关的、新鲜的信息。 |

## 文件记忆与外部状态 · File Memory & External State

| 术语 (EN) | 中文 | 释义 |
|-----------|------|------|
| external memory | 外部记忆 | 存在上下文窗口之外（文件、数据库、KV 存储）的信息，agent 按需读写、按需召回少量进窗口。把「该长期记住但不必时刻在场」的东西移出窗口，是突破窗口上限的根本手段。 |
| file-based memory | 文件记忆 | 用文件系统当 agent 的长期记忆：把笔记/事实/进度写成文件，下次需要时读回。Claude 的 memory 工具与「写 MEMORY.md」实践即此类。本课模块 03 从零写一个读/写/更新/去重的文件记忆系统。 |
| memory write / read / update | 记忆写入/读取/更新 | 记忆系统的三个基本操作：写入新条目、按 key 或检索读出、就地更新已有条目（而非无脑追加）。更新而非追加是避免记忆无限膨胀、避免同一事实出现矛盾副本的关键。 |
| deduplication | 去重 | 写入前检查是否已有等价/高度相似的条目，若有则更新而非新增。没有去重的记忆会迅速被重复内容污染、召回质量下降、token 浪费。本课用 key 规范化 + 相似度阈值实现去重。 |
| structured memory | 结构化记忆 | 把记忆组织成有 schema 的条目（如 `{key, value, tags, updated_at}`）而非自由文本。结构化让更新、去重、按字段召回、过期清理都可程序化，远比一坨纯文本可维护。 |
| memory recall / retrieval | 记忆召回 | 在需要时从外部记忆里取回相关条目放进上下文。可按 key 精确取，也可用检索（模块 04）按相关性取。召回要受预算约束——只注入最相关的少量，而非全量回灌。 |
| memory block / MEMORY.md | 记忆块 | 一份持久的、人/agent 都可读写的文件，记录跨会话要记住的偏好、事实、约定。每次会话开始时注入或按需读取。是最朴素也最实用的 agent 记忆形态。 |
| memory tool | 记忆工具 | 模型可调用的、对记忆目录做 view/create/str_replace/insert/delete 的客户端工具（Claude 的 `memory_20250818`）。模型自己决定记什么、何时记、记到哪。本课的文件记忆系统是它的最小内核。 |
| eviction / expiry | 淘汰 / 过期 | 记忆容量有限时清理旧的/不再相关的条目（按时间、按使用频率、按相关性）。与缓存淘汰同理：没有淘汰策略的记忆终将膨胀失控。 |

## 检索入上下文 · Retrieval into Context

| 术语 (EN) | 中文 | 释义 |
|-----------|------|------|
| RAG (retrieval-augmented generation) | 检索增强生成 | Lewis 等 2020 提出：先从外部知识库检索相关片段，再把它们拼进提示让模型据此作答。让模型用上训练数据之外、最新或私有的知识，是「给模型外接一个图书馆」的范式。agent 的 RAG 即按需把外部知识检索进上下文。 |
| embedding | 嵌入 / 向量 | 把一段文本映射成一个稠密向量，使「语义相近的文本→向量也相近」。检索靠比较查询向量与文档向量的相似度。本课用 toy embedding（词频/词袋向量）演示机制，真实系统用学习到的 embedding 模型。 |
| cosine similarity | 余弦相似度 | 两个向量夹角的余弦，衡量方向是否一致（不看长度）：$\cos(a,b)=\frac{a\cdot b}{\lVert a\rVert\,\lVert b\rVert}\in[-1,1]$。是 embedding 检索最常用的相似度度量。本课模块 04 从零实现它。 |
| top-k retrieval | top-k 检索 | 对查询，按相似度排序所有候选、取最相近的 k 个。k 太小会漏掉相关内容，太大会注入噪声并撑爆预算。选 k 是相关性与预算之间的权衡。 |
| chunking | 切块 | 把长文档切成适合检索与注入的小片段（按段落、按固定 token 数、带重叠）。切得太大召回不精准且占预算，太小会割裂语义。是 RAG 流水线的前置步骤。 |
| injection budget | 注入预算 | 留给「检索结果」的 token 配额。检索可能返回很多片段，但只能注入预算内的若干；要在「召回足够相关」与「不挤占其他上下文」之间平衡。本课把注入预算作为 top-k 之上的硬约束。 |
| reranking | 重排 | 用更强（更慢）的打分器对初步检索的候选重新排序，把最相关的提到最前。常见两段式：先用便宜的向量检索召回 top-N，再用 reranker 精排出 top-k。能显著提升注入内容的相关性。 |
| relevance | 相关性 | 检索片段与查询的契合程度。检索系统的核心目标是高相关性——既要召回该召回的（recall），又要排在前面的确实相关（precision）。本课用可验证的小例子检验相关性排序正确。 |
| vector store / index | 向量库 / 索引 | 存储文档向量并支持高效相似度查询的数据结构（如 FAISS、近似最近邻 ANN）。本课用「线性扫描 + 排序」的朴素实现讲清原理；真实系统用 ANN 把检索从 O(N) 降到近似 O(log N)。 |
| query / passage | 查询 / 段落 | 检索的两端：查询是当前问题，段落是候选知识片段。两者都被映射到同一向量空间比较。有些 embedding 模型对查询和段落用不同编码（非对称检索）。 |

## Prompt 缓存与长会话经济学 · Prompt Caching & Long-Session Economics

| 术语 (EN) | 中文 | 释义 |
|-----------|------|------|
| prompt caching | 提示缓存 | 把请求里稳定不变的前缀（系统提示、工具定义、长文档、已发生的历史）在服务端缓存起来，后续请求命中即免去重新处理，省时省钱。Anthropic 用 `cache_control: {type:"ephemeral"}` 标记缓存断点。本课模块 05 从零模拟它。 |
| prefix match | 前缀匹配 | prompt 缓存的核心机制：缓存键由「渲染后 prompt 到某断点为止的精确字节」决定。任意一个字节的改变都会让该位置及之后的缓存全部失效。所以稳定内容必须放在前、易变内容放在后。 |
| cache breakpoint / cache_control | 缓存断点 | 在内容块上打的标记，告诉 API「缓存到这里为止的前缀」。Anthropic 的渲染顺序是 `tools → system → messages`，断点常打在最后一个稳定块上。每请求最多 4 个断点。 |
| cache hit / miss | 缓存命中 / 未命中 | 命中：前缀与已缓存的一致，按极低价（约 0.1×）读取；未命中：要重新处理并写入缓存（约 1.25× 写入价）。命中率是长会话成本的决定因素。本课用 `usage` 字段核对命中。 |
| cache write / read tokens | 缓存写入/读取 token | `cache_creation_input_tokens`（这次写进缓存的，约 1.25× 价）与 `cache_read_input_tokens`（这次从缓存读的，约 0.1× 价）。`input_tokens` 是未缓存、全价处理的部分。三者之和=完整 prompt 大小。 |
| TTL (time to live) | 存活时间 | 缓存条目的有效期：Anthropic 默认 5 分钟（写入约 1.25×），可选 1 小时（写入约 2×）。过期即失效，下次要重新写入。长会话若请求间隔超过 TTL，缓存会在间隙里失效。 |
| silent invalidator | 静默失效源 | 悄悄破坏前缀稳定性、让缓存永远 miss 的东西：系统提示里的 `now()` 时间戳、随机 UUID、未排序的 JSON、随用户变化的工具集。表现为命中数始终为 0。本课让你识别并修掉它们。 |
| cache-aware ordering | 缓存友好排序 | 按「稳定性」组织 prompt：最不变的（冻结的系统提示、确定顺序的工具）放最前、跨会话不变的放中间、每轮才变的（当前问题、时间戳）放最后。是让缓存生效的首要设计，比断点位置更重要。 |
| break-even | 盈亏平衡 | 缓存写入比读取贵，要请求够多次才回本。5 分钟 TTL 约 2 次请求即平衡（1.25×+0.1× < 2×），1 小时 TTL 约需 3 次。决定该不该缓存、用哪种 TTL。 |
| cost accounting | 成本账 | 把一次（或一段会话）的花费按未缓存输入、缓存写入、缓存读取、输出分别用各自单价加总。本课模块 05 让你为一个长会话算出「开缓存 vs 不开缓存」省了多少，理解上下文工程的经济动机。 |

## Agent 上下文与控制流 · Agent Context & Control Flow

| 术语 (EN) | 中文 | 释义 |
|-----------|------|------|
| messages / roles | 消息 / 角色 | Messages API 里对话由带角色的消息组成：`system`（指令/设定）、`user`（用户/工具结果）、`assistant`（模型输出）。上下文工程很大程度上就是在管理这串 messages：留哪些、压哪些、按什么顺序。 |
| system prompt | 系统提示 | 注入在最前、定义 agent 角色与约束的指令。它通常稳定且必须保留——既是截断时的钉住项，也是 prompt 缓存里最该放在前缀的内容。 |
| stateless API | 无状态接口 | Messages API 本身不记得上一轮——每次请求都要把完整历史重发。所以「历史怎么管理（截断/压缩/记忆/缓存）」完全落在调用方（scaffold）身上，这正是本课的主题。 |
| scaffold / harness | 脚手架 | 包裹模型的那层代码：组装上下文、管预算、做截断/压缩、读写记忆、做检索、管缓存。同一个模型配不同 scaffold，长会话表现可天差地别。本课很大程度上就是在教写上下文这一侧的 scaffold。 |
| context assembly | 上下文组装 | 每一步把「系统提示 + 工具 + 召回的记忆 + 检索结果 + 历史（或其摘要）+ 当前输入」按预算与顺序拼成一次请求的过程。是上下文工程所有零件的汇合点。 |
| effective context | 有效上下文 | 窗口里真正被模型用上的部分。窗口大不等于有效——塞满无关内容（context rot）会稀释注意力。目标是让有效上下文占比尽量高：少而精，而非多而杂。 |
