1为什么要把记忆移出窗口

前两个模块都在窗口之内腾挪：模块 01 在超预算时按优先级裁、模块 02 把旧历史压成摘要。但无论裁得多巧、压得多狠，你都在和一个固定大小的窗口硬碰硬——历史总会再涨、要记的事总会更多，迟早又顶到天花板。这一模块换一个根本思路：把信息搬到窗口外面去。

这就是 external memory（外部记忆）：把「该长期记住、但不必每一步都在场」的东西，写到上下文窗口之外的某个地方（文件、数据库、KV 存储），需要时再召回少量进窗口。窗口不再是信息的唯一容身处，而更像一块工作台：台面有限，但你可以把暂时用不到的东西放回身后的货架，用时再取一两样上来。一旦接受「窗口外还有地方放东西」，agent 能记住的总量就不再被窗口上限锁死——这是突破窗口上限的根本手段，也是本模块和前两章的分水岭。

理解这件事最好的类比来自 MemGPT（Packer 2023）：把 LLM 类比成一台操作系统。上下文窗口是 RAM（快、贵、小），外部存储是磁盘（慢、便宜、大）。操作系统从不把所有数据都塞进 RAM——它在 RAM 与磁盘之间换页，需要哪页就调哪页进来。agent 的记忆也该如此：窗口里只放当前这一步真正用得上的，其余的写到「磁盘」（文件记忆）上，按需「换入」。本模块就是从零写这套「磁盘」与「换页」的最小内核。

本模块的目标是从零写出一个文件记忆系统：把记忆组织成结构化条目、支持写入 / 读取 / 更新 / 去重、并能在需要时按需召回少量进上下文。我们用 in-memory（或临时文件）后端，把整条链路端到端跑通、用 assert 验证——你会看到，真实的 Claude memory 工具不过是把这套读写操作交给模型自己来调。

一句话抓住本模块：窗口是 RAM，文件记忆是磁盘；agent 不必把一切都记在『脑子』（窗口）里，而是写到『笔记本』（文件）上，用时翻一两页回来。本模块的全部工程，都是在让这本「笔记本」写得进、找得到、改得对、不重复——难点不在「调用模型」，而在记忆这一侧的结构、更新与去重。

2文件记忆：最朴素也最实用的长期记忆

文件记忆：最朴素也最实用的 agent 长期记忆

「外部记忆」可以很花哨（向量库、知识图谱），但最朴素、也最被广泛采用的形态就是文件记忆：用文件系统当 agent 的长期记忆，把笔记、事实、进度、用户偏好写成文件，下次需要时读回。Anthropic 的 memory tool（memory_20250818）正是这种思路——它给模型一个 /memories 目录和一组操作（view / create / str_replace / insert / delete），让模型自己决定记什么、何时记、记到哪个文件、何时改。

窗口内 (RAM, 每次请求都重新装) 窗口外 (disk, 跨请求持久) ┌────────────────────────────────┐ ┌──────────────────────────────┐ │ [系统提示] [本轮输入] [召回的1-2条] │ ◄──召回── │ memory 文件 / 条目库: │ │ ↑当前真正用得上的, 少而精 │ │ - user.偏好: 喜欢简洁回答 │ │ │ ──写入─► │ - project.约定: 用 pytest │ └────────────────────────────────┘ │ - fact.部署: 周五晚上线 │ ▲ 受窗口预算约束 │ ... (可远大于窗口, 不占预算) │ └──────────────────────────────┘

注意这张图和模块 02 compaction 的区别：compaction 把历史压缩后仍留在窗口里；文件记忆则把信息彻底移出窗口、只在需要时召回一两条。两者互补——compaction 管「这一长段对话怎么不爆」，文件记忆管「跨会话、跨任务该长期记住的东西放哪」。一个 agent 通常两者并用。

直白说

把文件记忆想成你工位旁的一本活页笔记本：脑子（窗口）一次只装得下几件事，但笔记本能记下成百上千条。需要某条时翻到那一页看一眼（召回），有新结论就记一笔（写入），发现写错了就划掉改正（更新）——而不是把整本笔记本都背进脑子。

严谨说

形式上，文件记忆是一个持久的键值/条目存储外加一组操作。它独立于上下文窗口存在（断了会话也还在），每次会话开始时可注入一份索引（如 MEMORY.md），或在对话中按需读取具体条目。写什么、读什么由 scaffold（或模型）决策，但「怎么存、怎么改、怎么不重复」是工程，这正是本模块要夯实的。

一个常见且实用的约定是 MEMORY.md：一份人和 agent 都可读写的 Markdown 文件，记录跨会话要记住的偏好、事实、约定，每次会话开始时整份注入或按需读取。它简单到几乎不需要任何基础设施，却能让 agent 跨会话不失忆——记住你上次说过「回答要简洁」「这个项目用 pytest」。本模块的结构化条目系统，就是 MEMORY.md 的可程序化升级版。

3写入/读取/更新：为什么更新比追加重要

写入 / 读取 / 更新：为什么「更新」比「追加」重要

记忆系统有三个基本操作：写入（记一条新的）、读取（按 key 或检索取回）、更新（就地改一条已有的）。前两个直觉好懂，第三个更新而非无脑追加，是新手最容易做错、却最关键的一点。

# 一个结构化记忆条目（key 唯一、value 可改、带元数据）
{
  'key': 'user.reply_style',          # 唯一标识，更新靠它定位
  'value': '用户偏好简洁、直接的回答',  # 真正要记住的内容
  'tags': ['preference', 'user'],     # 便于按类召回
  'updated_at': 12,                    # 逻辑时间戳, 便于淘汰/审计
}

设想用户先说「回答尽量简洁」，过会儿又改主意「其实我想要详细一点」。如果记忆只会追加，库里就同时躺着两条矛盾的条目：「偏好简洁」和「偏好详细」。下次召回时两条都被取出来塞进窗口，模型看到自相矛盾的指示，行为就乱了——这还只是两条；一个跑了几百轮的 agent 会追加出成千上万条、彼此矛盾的记忆。

别让记忆无脑追加

无脑追加是文件记忆的头号杀手。两个后果，都很隐蔽：① 膨胀——记忆无限增长，召回越来越慢、越来越贵、越来越多噪声；② 矛盾副本——同一件事的新旧版本同时存在，召回时一起进窗口，模型无所适从。正确做法是：写入前先看 key 是否已存在；存在就更新（覆盖 value、刷新时间戳），不存在才新增。「更新而非追加」一句话，但它是记忆能长期可用的命门。

所以一个正确的「写入」其实是 upsert（update-or-insert）：write(key, value) 应当先按 key 查，命中则原地更新、未命中才插入。读取则分两种：按 key 精确取（我知道要哪条，如 read('user.reply_style')）与按相关性检索取（我不知道 key、只知道大概要什么，交给模块 04 的检索）。本模块先把「按 key 的 upsert + 精确读」做扎实，下一模块再叠加「按相关性召回」。

把这套操作设计对，还顺带解决了一个工程问题：幂等。同一条「用户偏好简洁」写两次，结果应当和写一次一样（更新覆盖，而非变成两条）。幂等让记忆系统在重试、重放、并发写入下都不会悄悄出错——这与模块 05 缓存的幂等诉求一脉相承：可重复的操作，结果必须可重复。notebook 会用 assert 专门验证「写两次等于写一次」。

4去重：写入前先查是否已记过

去重：写入前先问『这条是不是已经记过了』

「更新而非追加」靠的是精确的 key 匹配。但现实里同一件事常以略不同的措辞出现：第一次记「用户喜欢简洁回答」，第二次记「用户偏好简短、直接的答复」——key 不同、意思几乎一样。光靠 key 匹配挡不住这种近似重复，于是需要 deduplication（去重）。

去重做两件事，层层把关：

  • key 规范化：写入前把 key 标准化（小写、去空格、统一分隔符），让 User.ReplyStyle 和 user.reply_style 落到同一个 key，先挡住「同义不同写」的 key。
  • 相似度阈值：对 value 计算与已有条目的相似度（本课用词频/集合相似度），超过阈值就判定为重复——更新那条已有的，而不是新增一条。

直白说

去重像图书馆收书时的查重：新到一本，先按书名规范化查目录（key 规范化）；书名对不上但内容八九不离十的，也不该再上一本新架位，而是更新馆藏记录（相似度阈值）。没有查重，书架很快被同一本书的不同版次塞满，读者（模型）反而更难找到对的那本。

严谨说

形式上，去重是写入路径上的一道前置检查：write(key, value) → 规范化 key → 查精确命中 → 再查近似命中（相似度 ≥ 阈值）→ 命中则更新、否则插入。阈值是个权衡旋钮：太高（如 0.99）几乎挡不住近似重复、库照样膨胀；太低（如 0.3）会把本不相同的条目误并成一条、丢信息。没有放之四海的阈值，要按数据调，本课让你亲手感受它的影响。

没有去重的代价，前一节已经说了一半（膨胀）；去重补上的是召回质量这另一半。想象库里有 50 条措辞各异、其实都在说「用户喜欢简洁」的条目——召回 top-5 时它们会霸占名额，把其他真正不同的记忆（「项目用 pytest」「周五上线」）挤出去。重复条目不只浪费 token，更会污染召回、稀释有效信息。去重让每条记忆都「只占一个名额」，召回回来的才是多样而非冗余的少量精华。

一个实现上的小心思：去重的相似度判断和模块 04 的检索相似度是同一套机制（都基于 embedding/向量的相似度）。这不是巧合——「判断两条记忆是不是同一件事」和「判断一条记忆与查询相不相关」本质都是度量文本的语义接近程度。本课用一个确定性的词频向量统一实现它，既服务去重、也为模块 04 的检索热身。

5结构化记忆 vs 一坨自由文本

结构化记忆 vs 一坨自由文本

到这里你可能会问：为什么非要把记忆做成 {key, value, tags, updated_at} 这样的结构化条目？直接维护一份大段的自由文本笔记不行吗？短期看行，长期看会出大问题——这一节专门讲为什么结构化。

差别的核心是：结构化让更新、去重、按字段召回、过期清理全部可程序化；自由文本则把这些都变成易错的字符串操作。对比一目了然：

维度一坨自由文本结构化条目 {key,value,tags,updated_at}
更新某条字符串查找替换，易误伤、易留旧副本按 key 定位、原地覆盖，精确且幂等
去重几乎做不到（无边界、无标识）key 规范化 + value 相似度，可程序化
按类召回全文一起回灌，无法只取相关类按 tags / key 前缀过滤，精确取一类
过期/淘汰无时间信息，无从下手按 updated_at 排序淘汰最旧
注入预算要么整份注入(撑爆)、要么瞎截逐条可数 token、按预算挑少量注入
审计/调试改了什么看不出条目 + 时间戳，可追溯每次变更

一句话：自由文本是给人读的，结构化条目是给程序管的。agent 的记忆既要能写进、更要能被可靠地维护（改、并、删、按需取），而维护的前提是有边界与标识——每条记忆是一个有 key 的独立单元，而不是一段没有缝的文本。这正是数据库用行/列而非一个大字符串存数据的同一个道理。

不过结构化也不是越细越好，这里有个务实的平衡。把记忆切得过碎（每个微小事实一条、字段拆十几个）会带来另一种维护负担：召回时要拼很多条才凑出完整语境、条目间的关系难以表达。实践中一个好用的折中是「Markdown 小节 + 要点行」：用 ## 小节 当 tag 分组、每行 - key: value 当一条结构化条目——既有 key/tag/可逐行更新的结构，又保留人类可读、可整段浏览的亲和性。这正是 MEMORY.md 在实践中如此流行的原因：它站在「纯自由文本」与「严格数据库」之间的甜点上。本模块 notebook 的胶囊会让你把一份这样的 MEMORY.md 解析成结构化条目库，亲手体会这个折中。

结构化的回报，在 agent 跑久了之后才完全显现：自由文本笔记会随时间退化成一团无法维护的浆糊（旧信息删不掉、矛盾改不净、相关的捞不出），而结构化条目库始终可增、可改、可查、可清。前期多花的一点结构，换来的是长期可维护——这与模块 02「结构化抽取关键类别比自由摘要更抗漂移」是同一种智慧。

6记忆召回：按需取少量、受预算约束

记忆召回：按需取少量，受预算约束

写得再好的记忆，用不上也是白搭。memory recall（记忆召回）就是在需要时把相关条目取回、放进上下文。召回有两条路：按 key 精确取（确定要哪条）和按相关性检索取（只知道大概，靠相似度排序取最相关的若干，即模块 04 的检索）。但无论哪条路，都要守住一条铁律。

召回的铁律：受预算约束，只注入最相关的少量，绝不全量回灌。一个常见的错误是「把整个记忆库都塞进窗口让模型自己挑」——这恰恰背叛了文件记忆的初衷（把东西移出窗口）。记忆库可以远大于窗口，正因为我们每次只召回一两条。召回必须像检索一样：排序、取 top-k、再受注入预算（模块 04）二次约束。把全部记忆回灌，等于没做文件记忆。

所以召回不是「读出全部」，而是排序 + 截取：先按相关性（或近期性、重要性）给条目打分排序，再从高到低取，直到达到条数上限 k 或注入 token 预算。这套「打分→排序→按预算截取」的骨架，你在模块 01（按优先级截断）见过、模块 04（top-k + 注入预算）还会再见——它是上下文工程反复出现的同一个母题：面对有限窗口，永远是「按某种重要性排序，再按预算取前面的」。

召回还有一种最朴素却极有效的形式，不该被向量检索的光环盖过：按 tag 或 key 前缀直接过滤。当 agent 明确知道「现在要的是这个项目的所有约定」时，一句 recall_by_tag('project') 比任何相似度计算都更准、更快、更可解释——它召回的就是确切属于那一类的全部条目，没有相似度的模糊地带。这正是结构化记忆带 tags 字段的回报之一。实践中的好策略往往是「结构过滤 + 相似度排序」两段式：先用 tag/key 把范围缩到相关的一类（精确、便宜），再在这类里用相似度排出最相关的少量（细排）。本模块 notebook 的练习就让你实现按 tag 召回，体会「不是所有召回都需要 embedding」。

打分该用什么信号？最朴素的是相关性（与当前查询的相似度）。更成熟的记忆系统（如 Generative Agents，Park 2023）会综合三种信号：相关性（与当下相不相关）、近期性（多久前的，越近越可能有用）、重要性（这条记忆本身有多重要）。三者加权打分，再取 top-k。本课先把最核心的「按相关性召回少量」做扎实，三信号加权留作延伸——但骨架完全一致：打分、排序、按预算取。

召回还有一个写入侧 vs 读取侧的工程取舍值得点明：相关性可以在写入时就算好（给每条记忆预存 embedding 向量、召回时直接比），也可以在召回时现算。预存省了召回的计算、但占存储且记忆更新时要重算向量；现算省存储、但召回变慢。对规模不大的文件记忆，现算足够；一旦条目上万，就该预存向量并上近似最近邻索引（模块 04）。这又是上下文工程里典型的「算力换存储 / 存储换延迟」权衡——和模块 01 的「近似计数 vs 精确计数」、模块 05 的「缓存写入 vs 重复处理」是同一类决策。

召回与去重在这里再次交汇：正因为写入时做了去重，召回 top-k 取回的才是k 条不同的记忆，而不是同一条记忆的 k 个措辞。去重保证召回名额不被冗余占据，召回保证只把少量精华送进窗口——两者一前一后，共同守住「窗口里少而精」这条上下文工程的总目标。

7淘汰与过期：满了得清

淘汰与过期：记忆也有容量，满了得清

文件记忆比窗口大得多，但也不是无限的——磁盘会满、检索会随条目数变慢、太多陈旧记忆会拉低召回质量。所以成熟的记忆系统都要有 eviction（淘汰）/ expiry（过期）策略：容量到上限时，清理掉最该清的那些。

「最该清的」按什么判定？常见三种信号，和召回打分恰好对偶——召回是「取最该留的」，淘汰是「清最该走的」：

  • 按时间（最旧）：清掉 updated_at 最早的，即「很久没更新过的」。最简单，这也是结构化条目带时间戳的回报之一。
  • 按使用频率（最少用）：清掉很少被召回命中的，即 LRU/LFU 式淘汰——和缓存淘汰是同一套思想。
  • 按相关性/重要性（最不重要）：清掉打分最低的。需要给条目维护一个重要性分。

直白说

淘汰像定期整理笔记本：页数有限，新的要记，就得撕掉最旧的、或最少翻的、或最没用的那几页。没有任何整理策略的笔记本，迟早厚到翻不动、也找不着东西——这正是没有淘汰的记忆库的下场。

严谨说

形式上，淘汰是写入路径的另一道后置检查：write 后若条目数超过容量上限，就按选定信号排序、删掉超出的部分。它和缓存淘汰（模块 05 会再遇到）共享同一套机制与权衡：淘汰太狠会丢掉还有用的、太松会让库膨胀。本课实现最直观的「按时间淘汰最旧」，让你看清「有界容量 + 淘汰策略」如何让记忆长期不失控。

过期（expiry）和淘汰（eviction）略有区别，值得分清：淘汰是「容量满了被动清」（库到上限才删），过期是「到点了主动失效」（如「这条临时笔记 24 小时后作废」）。有些记忆天生有时效——会话级的临时状态、一次性的任务上下文，过了就该自动消失，不该和「用户长期偏好」这种永久记忆混在一起占名额。给条目加一个可选的「有效期」字段，召回时跳过已过期的、淘汰时优先清它们，就能让短时记忆与长期记忆各得其所。这也呼应模块 05 缓存的 TTL：不是所有东西都该永久保留，给信息一个合理的寿命，系统才不会被陈旧内容拖垮。

把写入路径的三道关合起来看，一个生产级的记忆写入其实是：去重（这条记过吗？记过就更新）→ upsert（更新或插入）→ 淘汰（超容量了吗？超了清最旧）。三道关分别对抗冗余、矛盾、膨胀这三种让记忆退化的力量。少任何一道，记忆都会在 agent 跑久之后慢慢烂掉——而这正是文件记忆「看着简单、做好不易」的地方。

8研究前沿与开放问题

研究前沿与开放问题

  • 记什么、何时记（记忆的写入策略）：让模型自己决定记什么（如 Claude memory 工具）灵活但不可控——可能记太多噪声、也可能漏记关键。「该不该把这条写进长期记忆」是一个活跃的判断问题，介于提示工程与训练之间。
  • 分层记忆与换页（MemGPT 之后）：MemGPT 把窗口/外存做成 RAM/disk 分层并让模型『换页』。如何设计更细的层级（工作记忆 / 情景记忆 / 语义记忆）、何时换入换出、如何不在换页上浪费太多调用，仍在探索。
  • 记忆的检索与召回质量：召回回来的是不是真该召回的？Generative Agents 的「相关性+近期性+重要性」三信号是一种答案，但权重怎么定、重要性怎么估，没有定论。与模块 04 检索的前沿相通。
  • 矛盾消解与一致性：去重挡住近似重复，但语义矛盾（「周五上线」后来改成「下周一上线」）更难——如何检测并消解记忆里的矛盾、让 agent 始终用最新事实，是记忆可靠性的核心难题。
  • 记忆的遗忘与隐私：什么该主动遗忘（过期、被要求删除、含敏感信息）？记忆持久化带来隐私与合规问题（不该把密钥/PII 写进记忆）。淘汰策略与「被遗忘权」在 agent 记忆里交汇。
  • 记忆 × compaction × 检索的统一：本系列里 compaction（压历史）、文件记忆（存窗口外）、检索（按需拉回）其实是同一个「有限窗口 + 无限信息」问题的三个面。把它们统一成一套连贯的上下文管理，是 agent 基础设施的前沿方向。
