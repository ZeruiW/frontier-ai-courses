1收官：把四块零件拼成 agent

到了收官的一站。前四个模块各造了一块零件——循环（01）、工具系统（02）、LLM 适配器（03）、鲁棒层（04）。本模块把它们拼成一个完整、能用的 agent，让它真正地用工具多步完成一个研究式任务，并留好让它长大的扩展点。

这一站没有新概念——这是它最重要的特点，也是本课刻意的编排。如果前四模块你都跟下来了，本模块对你应当是一种『原来如此，全是已经懂的零件』的踏实感，而非「又要学新东西」的负担。把一个看似高深的「AI agent」还原成几个朴素零件的组装，让你确信「我已经会造它了」——这正是整门课要带你抵达的地方。

但「组装」本身也是一门学问，值得专门讲。零件齐了不等于系统就好——怎么把它们接在一起（清晰的接口、合理的职责边界）、怎么让整体可配置（换模型、换工具、调上限）、怎么让它可扩展（加新工具、加新能力而不重写）、怎么评测它确实完成了任务——这些是把零件变成「产品」的工程。本模块就讲这些，并最终让你跑通一个端到端的多步任务。

一句话抓住本模块：最小可用 agent = 循环(01) + 工具(02) 跑在适配器(03)上、外裹鲁棒层(04)，用清晰的接口拼起来、留好扩展点。重点从「造零件」转向「搭系统」：如何组装、如何配置、如何扩展、如何评测。学完这一站，你就拥有了一个自己从零造的、彻底理解的、能接真实 Claude 的 agent——而不再是某个框架黑箱的使用者。

2组装的解剖：零件如何咬合

把四块零件接起来：组装的解剖

先回顾每块零件提供了什么接口、它们如何咬合。理解这张「咬合图」，是组装的地基：

零件来自提供的接口在 agent 里的角色
LLM 适配器模块 03llm.complete(system, msgs, tools)大脑：被注入，可 mock 可真实
工具系统模块 02registry.export() / dispatch(call)手脚：声明给模型、执行模型的调用
agent 循环模块 01感知-决策-行动-观察 + 停止骨架：把大脑和手脚串成多步过程
鲁棒层模块 04重试/超时/循环检测/熔断/trace护甲：包裹循环、应对各类失败

这四块的咬合关系是有层次的，不是平铺的：循环是中心，它在「决策」阶段调用适配器、在「行动」阶段调用工具系统；而鲁棒层在最外层包裹整个循环（重试包住每次决策、熔断/循环检测监视每一步）。用一句话概括组装的拓扑：鲁棒层（外） → 循环（中） → {适配器, 工具系统}（被循环调用）。把这个拓扑想清楚，代码怎么组织就一目了然。

┌─────────── 鲁棒层 (04: 重试/超时/循环检测/熔断/trace) ───────────┐ │ │ │ ┌──────────── agent 循环 (01: 感知-决策-行动-观察) ─────────┐ │ │ │ │ │ │ │ ②决策 ──► llm.complete(...) ◄── 适配器 (03: mock/真实)│ │ │ │ ③行动 ──► dispatch(call) ◄── 工具系统 (02: 注册表) │ │ │ │ ④观察 ──► history.append(...) │ │ │ └──────────────────────────────────────────────────────────┘ │ └────────────────────────────────────────────────────────────────┘ ▲ 注入: llm, registry, 上限配置 (可插拔/可配置)

直白说

可以把组装想成搭一台电脑：CPU（循环）是核心，它通过插槽接上内存（适配器/大脑）和外设（工具系统/手脚）；机箱与电源保护（鲁棒层）裹在最外面。每个零件都有标准接口（插槽），所以你能换 CPU（换循环策略）、换内存（换模型）、加外设（加工具），而不必重做整机。组装的好坏，看的就是这些「插槽」设计得清不清晰。

严谨说

从设计看，好的组装体现两个原则：依赖注入（大脑、工具、上限都从外面传进 agent，而非内部写死——回顾模块 03）让 agent 可配置、可测试；单一职责（每块零件只管自己那摊事，接口之外互不知情）让系统可维护——改工具系统不影响循环，改鲁棒策略不影响适配器。这两条是把零件拼成『好系统』而非『一团乱麻』的关键。

本模块的 notebook 会让你把这四块亲手拼起来，组成一个 Agent 类：构造时注入 llm、registry、各种上限；run(task) 跑完整个多步过程、返回带状态与 trace 的结果。你会发现拼装代码出奇地短——因为重活前四模块都干完了，这里只是把接口对接好。这种「短」正是好分解的标志：当每块零件接口清晰，组装就该是平凡的。

3一个完整的最小 agent

一个完整的最小 agent

把组装落成代码。这是本课的集大成——一个完整、能用、能接真实 Claude 的最小 agent，前四模块的一切都在这里汇合：

class Agent:
    def __init__(self, llm, registry, system='You are a helpful agent.',
                 max_steps=15, max_cost=0.5, loop_threshold=3):
        self.llm = llm                    # 03: 注入的大脑(mock 或真实)
        self.registry = registry          # 02: 工具系统
        self.system = system
        self.max_steps = max_steps        # 04: 步数保险丝
        self.max_cost = max_cost          # 04: 预算保险丝
        self.loop_threshold = loop_threshold

    def run(self, task):
        history = [{'role':'user', 'content':task}]
        ct = CostTracker(self.max_cost)       # 04
        det = LoopDetector(threshold=self.loop_threshold)  # 04
        trace = []
        for step in range(self.max_steps):    # 01 循环 + 04 步数保险丝
            d = self.llm.complete(self.system, history, self.registry.export())  # 02+03
            ct.add(d['usage']); trace.append({'step':step, **_brief(d), 'cost':ct.total})
            if ct.over_budget():                              # 04 预算
                return _result('budget_exceeded', trace, ct)
            history.append(_assistant_msg(d))                 # 01 状态
            if d['stop_reason'] == 'end_turn':                # 01 正常停止
                return _result('done', trace, ct, answer=d['text'])
            for call in d['tool_calls']:
                if det.check(call):                          # 04 循环检测
                    return _result('loop_detected', trace, ct)
            results = [dispatch(self.registry, c) for c in d['tool_calls']]  # 02 分发+隔离
            history.append({'role':'user', 'content':results})  # 01 观察回灌
        return _result('max_steps', trace, ct)

逐行对照四个模块，你会看到它们各司其职、严丝合缝：__init__ 里注入 llm 与 registry（03、02）、配置上限（04）；for step in range(max_steps) 是循环骨架（01）+ 步数保险丝（04）；llm.complete(..., registry.export()) 一行同时用上适配器（03）和工具系统的 schema 导出（02）；预算熔断、循环检测来自 04；dispatch 的错误隔离来自 02；两处 history.append 的状态管理来自 01；每个 return 的明确状态来自 01/04 的终止状态机。整门课在这一个 run() 方法里收束。

如果你能读懂上面这段代码、并说清每一行属于哪个模块、为什么这么写——那么你已经掌握了 agent 的全部核心。这段代码就是 Claude Code、LangChain 这些框架最核心的那个 run 循环的骨架；它们比它复杂，但复杂在「更多工具、更精的上下文管理、更全的可观测」，而核心结构与此无异。你不再是那个『调框架 API 但不知道里面发生什么』的人了——你知道里面发生什么，因为你亲手写过它。这就是本课的终点，也是你作为 agent 工程师的起点。

4跑一个多步研究式任务

跑一个多步任务：端到端的研究式 agent

光有 agent 类还不够，得让它真的做点事。本模块的 notebook 会让它完成一个研究式多步任务——一个需要它自己决定『先做什么、再做什么』、串起多个工具才能解决的任务，比如：

任务: 「某圆的半径等于『agent』这个词的字母数, 求它的面积」

agent 的轨迹(它自主决定的多步):
  step 0  THOUGHT: 我得先知道 'agent' 有几个字母
          ACTION: count_letters(word='agent') -> 5
  step 1  THOUGHT: 半径是 5, 面积 = π·r²
          ACTION: calculator(expr='3.14159 * 5 * 5') -> 78.54
  step 2  FINAL: 该圆面积约为 78.54

这个任务的关键在于它不是一步能解决的——agent 必须先用一个工具拿到中间结果（字母数 5），再基于那个结果用另一个工具（半径 5 算面积）。这正是 agent 区别于单次问答的本质：多步、有依赖、自主编排。能跑通这个，就证明你的 agent 真的「转起来了」——循环在转、工具在被正确调用、中间结果在被正确回灌、最后正确收尾。

用 MockLLM 跑它时，我们能精确断言整条轨迹：第 0 步必调 count_letters、第 1 步必调 calculator 且参数用上了第 0 步的结果、第 2 步必收尾、最终答案含 78.54。这种逐步断言是 MockLLM 的独门价值（模块 00/03 反复强调）——它把「agent 端到端跑通了吗」从一个模糊的感觉，变成一组可证明的判据。换上真实 Claude，则是看它自主地走出类似的（但不保证逐字相同的）轨迹。

直白说

这个任务虽小，却五脏俱全：它要求 agent 感知任务、决策用哪个工具、行动执行、观察结果、再据结果决策下一步——把模块 01 的四阶段循环完整跑了两轮。麻雀虽小，它演示的正是任何复杂 agent（写代码、做研究、订机票）的同一套核心动作，只是工具更多、步数更长。

严谨说

从评测角度，这个任务示范了如何evaluation（评测）一个 agent：定义一个有客观正确答案的多步任务，跑 agent，检查（a）最终答案对不对、（b）轨迹合不合理（用了该用的工具、没绕远路）。这是 agent 评测的雏形。严肃的评测（AgentBench、τ-bench）会用大量这样的任务、测完成率与轨迹质量——但思路一致：给任务、跑 agent、验结果与过程。

本模块 notebook 会让你跑通这个研究式任务（MockLLM 端到端），再跑一个会出错并自我恢复的版本（中途调错工具、看到错误后改对），验证你拼装的 agent 不只在顺境能跑、逆境也扛得住——这正是前四模块所有努力的回报在一处的集中检验。

5可配置：一个 agent 多种用法

可配置：同一个 agent，多种用法

一个好的 agent 应当是可配置的——换个模型、换套工具、调个上限，都不该改 agent 本身的代码。这正是前面「依赖注入」的回报：所有变化点都通过构造参数注入，agent 的 run 逻辑保持稳定。

看看同一个 Agent 类能通过配置变出多少花样：

  • 换大脑：Agent(llm=make_llm(...)) ——测试用 MockLLM、上线用真实 Claude；甚至换不同模型（Opus 求强、Haiku 求快省）。agent 代码一字不改。
  • 换工具集：给不同任务注入不同的 registry——研究 agent 配搜索 + 计算器，编码 agent 配读写文件 + 执行，客服 agent 配查订单 + 发邮件。同一个循环，不同的「手脚」。
  • 调上限：高风险任务设小 max_cost 与 max_steps（严格止损）；可信的长任务放宽上限。同一个鲁棒逻辑，不同的「松紧」。
  • 换 system 提示：用 system 给 agent 不同的『人格』与规则（『你是严谨的研究助手』vs『你是简洁的代码助手』），不必改任何代码。

直白说

可配置让一个 agent 类变成一个产品族：同一套核心，配出研究助手、编码助手、客服助手……。这就像同一款车架配不同发动机、座椅、轮胎，变出家用版、越野版、赛道版——核心复用，差异在配置。

严谨说

从工程看，可配置 = 把「会变的」与「不变的」分开。不变的是 run() 的控制流（感知-决策-行动-观察的骨架、停止逻辑、容错结构）；会变的是注入的依赖与参数（哪个模型、哪些工具、什么上限、什么人格）。把变化点收敛到构造参数，核心逻辑就稳定、可复用、好测试——这是所有可复用组件的设计精髓。

一个值得强调的配置点是 agent vs workflow 的取舍（Anthropic《Building effective agents》的核心论断，回顾模块 00）：不是所有任务都该用『让模型自主决定步骤』的 agent。步骤固定、可预先编排的任务，用 workflow（代码写死步骤）更可控、更省、更可预测；只有任务开放、步骤难以预先确定时，才真正需要 agent 的自主性。你造的这个 agent 是一把好锤子，但别把所有问题都当钉子——先判断该用 agent 还是 workflow，再动手，这是成熟 agent 工程师与新手的分水岭。

6扩展点：让 agent 长大

扩展点：让 agent 长大

最小 agent 是最小的，但不是到顶的。一个好的最小实现，应当像一颗种子——核心完整，且预留了清晰的「长大」方向。本节梳理从这颗种子出发，agent 能往哪些方向生长，每个方向对应本课已埋下的伏笔：

扩展方向解决什么从哪长出来对应模块伏笔
更多/更强工具扩大能力边界往 registry 注册新工具模块 02
上下文管理支持长程任务(history 不撑爆)截断/压缩/外置记忆模块 01 状态管理
规划与反思更可靠地解复杂任务决策环加规划/Reflexion模块 01 决策
多 agent 协作分工解决大任务agent 调用 sub-agent整体组装
人在回路高风险动作的安全工具确认门控模块 02/04
更全的可观测生产级调试与监控结构化 trace + 分析模块 04 trace

这张表不是凭空罗列，而是本课每个模块都有意埋下的伏笔在此收束：模块 01 讲状态管理时点了「history 会撑爆上下文窗口、需要管理」→ 这里长出上下文管理；模块 01 讲决策时点了「朴素 ReAct 是贪心的、可加规划/反思」→ 长出规划与反思；模块 02 讲工具时点了「有副作用的工具需要确认门控」→ 长出人在回路；模块 04 讲可观测时建了 trace → 长出生产级监控。你造的种子已经预留好了所有这些生长点，因为本课从一开始就是按「能长大」来设计的。

直白说

把最小 agent 想成一栋打好地基、立好框架的毛坯房：水电管线（接口）都预埋好了，住人（核心功能）没问题；想加房间（新工具）、装修（上下文管理）、扩建（多 agent）都有接口可接，不必推倒重来。一个不好的最小实现则像违建——能将就住，但想改一点就得砸墙。本课造的是前者。

严谨说

从设计看，可扩展性来自正交分解：每个扩展方向都对应一个清晰的「接缝」——加工具是往 registry 加（不碰循环）、加上下文管理是在「感知」阶段插一层（不碰工具）、加规划是在「决策」前插一层（不碰行动）。正因为前四模块把这些关注点分得干净，每个扩展才能局部地加上去而不牵一发动全身。这是好分解的终极回报：系统能在不重写的前提下持续生长。

本模块 notebook 会让你亲手做一两个扩展（如给 agent 加一个新工具、加一段简单的上下文截断），亲身体会「在预留的接缝处加能力」是多么平滑——这是对你前四模块所建结构的最终验收：一个真正好的 agent harness，应当让『加新能力』变得容易。

7回望全课：你造了什么

回望全课：你造了什么

收官时回望整门课走过的路。你从「会用 agent 框架但不知里面发生什么」出发，一步步亲手造出了一个完整的 agent harness：

  1. 模块 00：认清 agent = 模型 + 循环 + 工具 + 上下文，立下「MockLLM 端到端 + 真实 Claude 适配」的方法论。
  2. 模块 01：把无状态的 LLM 用一个循环变成有状态的多步 agent——感知-决策-行动-观察、ReAct 解析、停止条件、状态管理、max-steps 守卫。
  3. 模块 02：给模型造「手脚」——工具注册表、JSON Schema、分发器、并行调用、错误隔离（坏调用变可反馈错误而非崩溃）。
  4. 模块 03：把「大脑」统一成一个可插拔接口——MockLLM 与真实 Claude 适配器一行互换、无 key 自动回退。
  5. 模块 04：把脆弱 demo 变成能跑的系统——重试、超时、循环检测、成本追踪与预算熔断、可观测 trace。
  6. 模块 05：把以上拼成一个完整、可配置、可扩展的最小 agent，端到端跑通多步任务。

更重要的是你获得的能力，而非代码。现在你能：读懂任何 agent 框架的源码（你知道它的循环、工具系统、适配器、鲁棒层各在哪、为什么这么设计）；在框架不够用时改动甚至替换它的某一部分；为框架覆盖不到的场景从零造一个专用 agent；以及——也许最重要的——在面对一个任务时，清醒地判断它该用 agent 还是 workflow、该配什么工具、设什么上限。

本课最深的一课，是祛魅：所谓「AI agent」，剥到底是一段你完全能掌控、能调试、能亲手造出来的程序。那行调模型的代码是「AI」，但围绕它的循环、工具、适配、护甲——把模型变成 agent 的一切——都是朴素、清晰、可控的工程。你不再被「agent」这个词唬住，因为你造过它。带着这份『我懂里面发生什么』的底气，无论是用框架、改框架、还是造新东西，你都站在了真正理解的地基上。

8研究前沿与开放问题

研究前沿与开放问题

  • 从单 agent 到多 agent 系统：复杂任务正越来越多地交给一组分工协作的 agent（一个协调者派活给若干专才 agent）。如何编排它们的通信、共享上下文、汇总结果、处理子 agent 失败，是当前最活跃的方向之一（Anthropic 的 multi-agent、managed agents）。
  • 长程自主与可靠性：让 agent 可靠地完成跑几十分钟、几百步的长任务（大型代码迁移、深度研究），需要更强的规划、上下文管理、自我纠错与中途可观测。「长程任务上的可靠性」是把 agent 从 demo 推向生产的核心瓶颈。
  • agent 安全与对齐：自主、有工具、能执行真实动作的 agent，一旦被对抗输入诱导或自身判断失误，可能造成真实危害。权限策略、人在回路确认、动作沙箱、行为审计——如何让强大的 agent 同时安全可控，是与能力并重的前沿。
  • 评测与可复现：agent 行为不确定、轨迹长、依赖外部环境，使「客观评测一个 agent 好不好」异常困难。如何构建可靠的 agent 基准、做回归测试、量化轨迹质量，是让 agent 工程从「手艺」走向「工程学科」的必经之路。

必读：Anthropic «Building effective agents»（agent 设计的总纲，收官重读一遍会有新体会）、ReAct（Yao 2022，循环的起点）。进阶：Reflexion、AgentBench/τ-bench（评测）、Anthropic 的 multi-agent 与 managed agents 文档。完整清单见 references.md。下一步建议：把你造的这个 agent 接上真实 Claude（设好 ANTHROPIC_API_KEY）、给它配几个真实工具（如真的网页搜索），跑一个你自己关心的任务——亲眼看到你亲手造的 harness 驱动真实模型工作，是这门课最好的句号。
