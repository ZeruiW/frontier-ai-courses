1为什么需要工具系统

模块 01 把循环做对了，但循环里有一行我们一笔带过：dispatch(tools, call)——执行模型想调的那个工具。这一行背后，是 agent 的「手脚」系统，本模块把它从零造出来。没有工具，LLM 只能说，不能做：它能告诉你「北京天气大概是晴」（凭训练记忆，可能过时或编造），但不能真的去查；能写出一段计算过程，但不能真的去算（还常算错）。工具系统就是把模型从「只会说」变成「能做」的那座桥。

先想清楚一个根本问题：一个只会输出文本的模型，怎么可能『调用』一个函数？答案是——它不能，至少不能直接调用。真正发生的是一场约定好的接力：模型输出一段结构化的文本，意思是「我想调用名为 search、参数为 {q:'北京天气'} 的工具」；你的 harness 解析这段文本，在一个注册表里按名字找到对应的真实 Python 函数，校验参数、调用它、拿到返回值，再把返回值说给模型听。模型自始至终只是在「说」，所有「做」都是 harness 替它做的。

所以「工具系统」要解决四个环环相扣的问题：(1) 注册——怎么把一个 Python 函数声明成「模型可用的工具」？(2) 声明——怎么用模型看得懂的方式告诉它「这个工具叫什么、做什么、参数怎么填」（JSON Schema）？(3) 分发——拿到模型的工具调用，怎么找到、校验、执行对应的函数？(4) 回灌与容错——怎么把结果（或错误）变成模型能继续推理的观察？本模块逐一攻破。

一句话抓住本模块：工具系统 = 一张『名字→(函数+说明书)』的注册表 + 一个『按调用找函数、校验、执行、包装结果』的分发器。模型靠「说明书」（schema）知道有哪些工具、怎么用；harness 靠「注册表」把模型的话落实成真实执行。全部难点在于：说明书写得让模型看得懂（schema 与 description），以及执行时坏调用不能崩掉整个 agent（错误隔离）。

2工具的解剖：名字+说明书+函数

工具的解剖：名字 + 说明书 + 函数

一个工具，无论在哪个框架里，都由三部分构成。理解这三部分各自给谁看、起什么作用，是设计工具系统的地基：

部分是什么给谁看作用
name 名字工具的唯一标识，如 get_weather模型 + harness模型用它指定要调谁；harness 用它在注册表里查函数
description 描述自然语言说明：做什么、何时用模型模型据此决定『要不要用、什么时候用』——常比模型本身更影响调用质量
input_schema 参数模式JSON Schema：参数的类型/必填/范围模型 + harness模型据此知道『怎么填参数』；harness 据此『校验参数合法性』
函数体 (implementation)真正执行的 Python 函数harness拿到合法参数后真正干活、返回结果

一个关键的认知：前三部分（name/description/schema）是给模型看的「契约」，最后一部分（函数体）是harness执行的「实现」。模型只看契约、永远碰不到实现——它不知道 get_weather 内部是调了某个 API 还是返回了固定值，它只知道「有这么个工具，这样调，会得到天气」。这种契约与实现分离正是工具系统的精髓：你能随意改 get_weather 的内部（换数据源、加缓存），只要契约不变，模型完全无感。

直白说

打个比方：工具的 name/description/schema 就像餐厅菜单上的「菜名 + 介绍 + 备注（忌口/份量选项）」，函数体则是后厨。顾客（模型）只看菜单点菜，从不进后厨；后厨怎么做、换没换厨师，顾客不关心，只要端上来的是菜单承诺的那道菜。菜单写得好不好（description 清不清楚），直接决定顾客点不点得对菜。

严谨说

形式上，一个工具是一个三元组的契约 (name, description, input_schema) 加一个可调用对象 fn。注册表是 name → (schema, fn) 的映射；「暴露给模型的工具列表」只含契约部分（schema），函数体绝不发给模型。这也是为什么模型再「聪明」也无法绕过你执行任意代码——它能调的，只有你注册过的那几个函数。

本模块的 notebook 会让你用一个 @tool 装饰器把这三部分一次性声明出来：写一个普通 Python 函数，加个装饰器，它就自动带上 name（函数名）、description（docstring）、并被登记进注册表。这正是 Claude SDK 的 @beta_tool、LangChain 的 @tool 在做的事——把「声明工具」这件事变得像写个带文档的普通函数一样自然。

3注册表：名字到函数的映射

注册表：名字到函数的映射

tool registry（工具注册表）是工具系统的心脏，本质朴素到极点——一个字典：name → (schema, function)。「注册一个工具」= 往这个字典里加一项；「分发一个调用」= 拿调用里的工具名去这个字典里查。所有 agent 框架的工具系统，剥到底都是这张表。

但围绕这张表，有几个设计决策值得想清楚：

  • 注册的接口：最朴素是 registry.register(name, schema, fn)；更优雅是装饰器 @registry.tool 自动从函数提取 name 与 docstring。后者让工具定义贴着函数本身，不易遗漏、不易写错。
  • schema 从哪来：可以手写 JSON Schema（最灵活、最啰嗦），也可以从函数的类型注解自动生成（最省事，但表达力有限）。工业框架两者都支持；本课先手写以看清结构，再演示从注解生成。
  • 暴露给模型的视图：注册表对内存着 (schema, fn)，但发给模型的只有 schema 列表（一个 export() 方法）。这是安全边界——函数体永不出网。
工具注册表 (registry) ┌─────────────────────────────────────────────────┐ │ 'get_weather' → (schema_w, fn_get_weather) │ │ 'calculator' → (schema_c, fn_calculator) │ │ 'search' → (schema_s, fn_search) │ └─────────────────────────────────────────────────┘ │ export() │ dispatch(call) ▼ 只发 schema 列表 ▼ 用 call['name'] 查 fn [给模型看的工具清单] 找到函数 → 校验 → 执行 → 包装结果 (绝不含函数体!)

直白说

注册表就像公司的通讯录：「名字 → 这个人 + 他的职责说明」。要找人办事（分发），按名字一查就找到；对外公布的（给模型的）只是「有哪些人、各管什么」（职责说明），而不是每个人的私人电话和家庭住址（函数实现）。

严谨说

从工程看，注册表把工具系统变成一个单一事实来源（single source of truth）：工具只在一处登记，「发给模型的清单」与「分发时查的函数」用的是同一张表，天然保证一致——模型看到的工具，就是 harness 能执行的工具，绝不会出现「模型以为有但其实没有」或「有但没告诉模型」的错位。

一个容易被忽视但重要的不变式：export() 给模型的工具名集合，必须恰好等于 dispatch 能找到的工具名集合。破坏它会导致两类 bug：告诉了模型某工具但分发时找不到（KeyError），或注册了某工具但忘了告诉模型（模型永远不会用它）。本模块 notebook 会把这个不变式写成一条 assert，守住它。

4JSON Schema：告诉模型怎么填参数

JSON Schema：怎么告诉模型「参数怎么填」

模型怎么知道 get_weather 需要一个叫 city 的字符串参数、而 calculator 需要一个表达式？靠 JSON Schema——一段用 JSON 描述「参数长什么样」的标准声明。它是模型与工具之间的参数契约。

# get_weather 工具的完整声明（Claude / OpenAI 通用的形态）
{
  "name": "get_weather",
  "description": "查询某城市的当前天气。当用户询问天气、气温、是否下雨时使用。",
  "input_schema": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "城市名，如 北京、上海"},
      "unit": {"type": "string", "enum": ["c", "f"], "description": "温标，默认摄氏"}
    },
    "required": ["city"]
  }
}

逐项看这段 schema 的作用：type:object 说「参数是一组键值对」；properties 列出每个参数的类型与说明；enum 限定取值（unit 只能是 c 或 f）；required 标出哪些必填（city 必填、unit 可省）。每个参数的 description 同样关键——它告诉模型「这个参数该填什么」（如 city 要填城市名而非邮编）。

schema 身兼两个角色，这是理解它的钥匙：对模型，它是「使用说明」——模型读它来决定怎么填参数；对harness，它是「校验规则」——执行前据它检查模型填的参数对不对（类型对吗？必填项齐吗？enum 越界吗？）。同一份 schema，既引导模型正确生成，又让 harness 在执行前拦截非法输入。

一个反复被验证的经验：description 写得好不好，常常比模型本身更影响工具调用质量。Anthropic 的建议是把 description 写得像给一个新同事的文档——讲清这工具做什么、什么时候该用（甚至什么时候不该用）、每个参数什么含义、边界条件。一个含糊的 description（如 "搜索"）会让模型乱用或不用；一个清楚的（如「当需要查训练数据之外的实时信息时使用网页搜索」）能让调用质量天差地别。这是 agent 工程里性价比最高的一处投入。

5分发：调用落实成执行

分发：把一次调用落实成一次执行

dispatch（分发）是工具系统的执行中枢，把模型的一个抽象调用 (name, input) 落实成一次真实执行。它是一条有固定步骤的流水线：

  1. 查找：用 call['name'] 在注册表里找对应函数。找不到 → 这是个幻觉工具（模型编了个不存在的名字），返回结构化错误。
  2. 校验：按 schema 检查 call['input']——必填项齐吗？类型对吗？enum 越界吗？不合法 → 返回结构化错误（让模型改），不执行。
  3. 执行：参数合法，调用函数。这一步可能抛异常（函数内部出错、外部 API 挂了）——必须捕获，不能让它冒泡崩掉 agent。
  4. 包装：把返回值（或捕获到的错误）包装成一个带 tool_use_id 的 observation/tool_result，回灌给模型。
def dispatch(registry, call):
    name, args = call['name'], call['input']
    # 1) 查找
    if name not in registry:
        return _err(call, f'无此工具 {name}，可用: {list(registry)}')   # 幻觉工具
    schema, fn = registry[name]
    # 2) 校验
    ok, why = validate(args, schema)
    if not ok:
        return _err(call, f'参数非法: {why}')                          # 不执行
    # 3) 执行（隔离异常）
    try:
        result = fn(**args)
    except Exception as e:
        return _err(call, f'工具执行出错: {type(e).__name__}: {e}')
    # 4) 包装
    return {'tool_use_id': call['id'], 'content': str(result), 'is_error': False}

注意这条流水线的每一步都有一个失败出口，且所有失败出口都通向同一种东西——一个带 is_error=True 的结构化结果，而非一个抛出的异常。这是工具系统健壮性的关键设计：无论是幻觉工具、非法参数、还是函数内部崩溃，对 agent 循环来说都只是『一个失败的观察』，模型看到它、知道哪儿错了、可以换个法子重试。循环本身一行容错都不用写。

直白说

把分发想成餐厅的传菜流程：服务员（dispatch）拿到点单，先看菜单上有没有这道菜（查找）、份量选项填没填对（校验），再交给后厨做（执行）。万一后厨把菜烧糊了（异常），服务员不会当场掀桌（崩溃），而是回来跟顾客说「这道菜出了点问题，您要不要换一个」（结构化错误）——顾客（模型）据此重新点。

严谨说

从契约角度，dispatch 保证了一个强不变式：它永远返回一个合法的 tool_result，从不抛异常。这把「容错」这件事收口在工具系统内部，让上层的 agent 循环可以假设「dispatch 一定给我一个结果」，从而保持简洁。模块 04 会在此基础上再叠重试、超时等更强的鲁棒手段。

这里有个微妙的设计选择：校验失败和执行出错，都返回 is_error 让模型重试，而不是直接终止 agent。为什么？因为模型常常能从错误里学到并改正——「参数 city 缺失」让它补上 city，「无此工具 foo，可用 [...]」让它改用正确的工具。把错误当成可反馈的信号而非终止信号，是让 agent 鲁棒的核心思路（贯穿模块 04）。当然，反复同样的错误就该靠循环检测止损了。

6并行工具调用

并行工具调用：一次调多个

有时模型在一轮里想同时调用多个互相独立的工具——比如「同时查北京和上海的天气」。现代模型（含 Claude）原生支持在一条助手消息里返回多个 tool_use 块，这叫 parallel tool calls（并行工具调用）。它能减少往返、提速。

处理并行调用有两条必须遵守的规则，错了 agent 就会出问题：

  • 可以并行执行，但要全部执行：这些调用彼此独立，你可以并发跑（线程池）以提速；但无论如何，模型给的每一个 tool_use 都必须有一个对应的 tool_result——少回一个，模型就会困惑「我那个调用怎么没结果」。
  • 所有结果放进同一条 user 消息回传：把这一轮所有的 tool_result 放进一条 user 消息里一起回传，而不要拆成多条消息。拆开回传会让模型误以为「并行调用没成功」，下次就不敢再并行了（这是 Anthropic 文档明确警示的坑）。
  • 靠 tool_use_id 对位：并行时多个结果回传，必须靠每个 tool_result 里的 tool_use_id 对回它来自哪个调用。绝不能按顺序硬对——顺序可能因并发执行而乱，对错位 = 把上海的天气安到北京头上。
模型一轮返回多个 tool_use: assistant: [tool_use(id=A, get_weather, 北京), tool_use(id=B, get_weather, 上海)] │ harness 可并发执行 A、B ▼ 全部结果放进【一条】user 消息回传，靠 id 对位: user: [tool_result(id=A, '北京 晴'), tool_result(id=B, '上海 雨')] ← 不要拆成两条消息!

一个隐蔽但常见的 bug：并行执行时用执行完成的顺序、而非 tool_use_id 来配对结果。并发下「上海」可能先返回、「北京」后返回，若按返回顺序硬塞，就会把结果对错位。永远用 tool_use_id 把结果对回它的调用——这和模块 01 强调的「状态要对」一脉相承：agent 的每一处对位（id、角色、顺序）错了，模型就会被你喂的错误信息带偏。

并行也带来一个正确性 vs 简单性的取舍。串行执行（一个个跑）最简单、最易调试，对大多数场景够用；并行执行更快，但要处理并发（线程安全、异常各自捕获、结果对位）。本课的最小 agent 默认串行（清晰为先），但 notebook 会让你把分发器扩展成支持并行的版本，并验证「无论串行还是并行，每个调用都拿到正确对位的结果」——理解这一点，你就懂了真实 agent 框架为什么要费力支持并行。

7接真实 Claude 的工具协议

接真实 Claude：工具系统如何对接 Messages API

本课的工具系统刻意设计得与 Claude Messages API 的工具协议同构，所以接真实模型几乎只是格式翻译。对照一下两边：

本课内部Claude Messages API说明
registry.export()tools=[{name, description, input_schema}]工具清单格式几乎一致
resp['tool_calls']content 里的 tool_use 块模型的工具调用意图
call['id']tool_use.id调用的唯一标识
dispatch 返回的 resulttool_result 块（放进 user 消息）回灌的观察
result['is_error']tool_result.is_error标记这次调用失败了
resp['stop_reason']stop_reason=="tool_use"模型想调工具的信号

具体流程：你把 registry.export() 作为 tools 传给 client.messages.create；模型若想调工具，返回的 content 里会有 tool_use 块、stop_reason=="tool_use"；你遍历这些块、用本课的 dispatch 执行，把每个结果包成 tool_result 块、全部放进一条 user 消息回传；再调一次 messages.create，模型据结果继续。这正是模块 01 的循环 + 本模块的工具系统，接到真实 API 上。

Anthropic SDK 还提供了一个 tool runner 帮你自动跑这整个循环：用 @beta_tool 装饰函数（自动从签名和 docstring 生成 schema）、client.beta.messages.tool_runner(...) 自动「调 API→执行工具→回灌→再调」直到完成。它等于官方版的 agent loop + 工具系统——本课先让你手写这两样（彻底理解），再让你看官方现成版（知道生产里怎么用、以及它替你做了什么）。

理解了这层同构，你就懂了本课的深层用意：我们用 MockLLM 验证的工具系统，和接真实 Claude 用的工具系统，是同一套代码。MockLLM 返回的 tool_calls 和真实 Claude 返回的 tool_use 块结构一致；本课的 dispatch 不在乎调用来自 mock 还是真模型。所以你在零成本的 MockLLM 上把工具系统打磨到正确，换上真实 Claude 时它立刻就能用——这就是『同构设计』的回报。

8研究前沿与开放问题

研究前沿与开放问题

  • 工具检索（tool search）：当工具有成百上千个时，把全部 schema 塞进上下文既贵又让模型选困难。前沿做法是让模型先检索出与当前任务相关的少数工具、只加载它们的 schema（Anthropic 的 tool search）。如何高效、准确地检索是活跃方向。
  • 程序化工具调用（programmatic tool calling）：与其一次调一个工具、把每个中间结果都塞回上下文，不如让模型写一段代码在沙箱里把多个工具像函数一样串起来调用，只把最终结果返回。能大幅减少 token 与往返，是工具调用的新范式。
  • 有副作用工具的安全：读类工具（搜索、计算）重试无害；但写类工具（发邮件、删数据、转账）一旦模型调错或被诱导，后果严重。如何对不可逆动作做确认门控、权限策略、幂等保证，是 agent 安全的核心前沿（Anthropic 的 permission policy、人在回路确认）。
  • schema 自动生成与校验严格性：从类型注解自动生成 schema 方便但表达力有限（难表达复杂约束）；strict 模式能保证模型输出严格符合 schema，但牺牲一点灵活。在「省事」「严格」「灵活」间取舍，仍在演化。

必读：Anthropic 的 tool use overview（工具协议权威）、Toolformer（Schick 2023，工具调用奠基）、Anthropic «Building effective agents»（工具设计原则）。进阶：tool search、programmatic tool calling 文档。完整清单见 references.md。
