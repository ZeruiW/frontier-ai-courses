1研究工程卫生：足够好就行

到这里你已经会设计受控实验、会用统计判断结果了。但研究不是跑一个实验就完事——真实的研究是跑成百上千个实验：不同超参、不同种子、不同数据、不同消融配置。这就带来一个新问题：怎么管理这一切，让它可复现、可追溯、可聚合？这就是研究工程卫生——介于「软件工程」与「做实验」之间的一套务实技能。

先说清楚本模块的立场。它不是要把你训练成软件工程师，也不要求你的研究代码达到生产级质量。Wilson et al. 的名篇标题说得好——good enough practices（足够好的实践）：研究代码的目标不是完美，而是守住可复现与可协作的底线。过度工程化（给探索性脚本写完整测试、设计复杂抽象）和毫无工程（所有参数硬编码、结果靠记忆、无法重跑）是两个极端，本模块教你找到中间那个务实的点。

直白说

研究工程卫生就像实验室的整洁：你不需要把实验室建成无尘车间，但试剂要贴标签、步骤要记录、仪器设置要可复现。否则三个月后你自己都不记得那瓶溶液是什么、那个 0.92 是怎么跑出来的。代码和实验也一样——不求华丽，但求半年后的你、以及别人，能照着重跑出来。

严谨说

核心矛盾是速度 vs 可复现。研究需要快速迭代（多写脚本、多试想法），但快速迭代天然制造混乱（散落的参数、未记录的运行、靠手动改代码切换配置）。好的研究工程，是用最小的纪律开销换取可复现性：把参数集中成 config、把运行自动记录、把随机源固定。这些纪律一旦成为习惯，几乎不拖慢迭代，却能在你需要回溯、复现、聚合时救命。

本模块教四件事，对应研究工程的四个支柱：config 管理（把实验参数显式化）、超参 sweep（系统地搜参，网格 vs 随机）、可复现（固定所有随机源、记录版本与环境）、结果聚合（把成百次运行汇总成可读的表）。每一件都直接回应「让实验可管理、可复现」这个目标。

2Config 管理：参数显式化

Config 管理：把参数从代码里揪出来

研究工程的第一块基石，是configuration management（配置管理）：把实验的所有可调项（超参、数据路径、种子、模型设置）从代码里揪出来，集中成一份显式、可序列化的 config（一个 dict / 一份 YAML/JSON）。

为什么这件看似琐碎的事如此重要？因为参数硬编码在代码里，会制造三个致命问题：

  • 无法复现：「那个 0.92 是用 lr=0.01 还是 0.001 跑的？」——如果参数散落在代码各处、还被改来改去，你根本回答不了。config 让每次运行的全部参数一目了然、可存档。
  • 无法 sweep：要扫描超参，你得能程序化地改参数。硬编码意味着每换一组参数就手动改代码（易错、无法自动化）；config 让你用循环生成一堆 config 跑批量。
  • 无法追溯：把 config 和结果一起存下来，你就能回答「这个结果对应哪组参数」。config 是连接「运行」与「参数」的契约。
❌ 参数硬编码在代码里 ✅ 参数集中成 config def train(): config = { lr = 0.01 # 散落各处 'lr': 0.01, batch = 32 # 改一个要 'batch': 32, ... # 翻遍代码 'seed': 0, seed = 0 # 跑完就忘 'model': 'resnet18', model = ... # 无法存档 } def train(config): 问题: 不可复现/不可sweep/不可追溯 ... # 一切从 config 读 # config 可存JSON、可循环生成、可追溯

一个好 config 系统的关键性质：可序列化（能存成 JSON/YAML 文件，跟着结果一起归档）、有默认值（不必每次指定所有参数）、可覆盖（命令行或脚本能改个别参数而不动其余）。还有一个常被忽视但极有用的性质——拼写校验：当你 make_config(learnig_rate=0.1) 写错参数名时，系统应当报错而非默默忽略。没有校验的 config，一个拼写错误会让你的「覆盖」悄无声息地失效（参数还是默认值），跑出一堆你以为改了、其实没改的实验——这是极难发现的 bug。不必上重型框架（Hydra、OmegaConf 等好用但非必需）——一个带默认值、能存读 JSON、能校验键名的 Python dict 就能起步。本模块 notebook 会让你从零写一个这样的轻量 config 系统。

一句话抓住 config 管理的精髓：每次实验，都应该能用一份 config 文件完全重建。理想状态是——你存下 config.json，半年后 train(load('config.json')) 就能跑出和当初一样的结果。做到这一点，你的实验就从「一次性的、靠记忆的」升级为「可存档的、可重放的」。这是可复现的前提，也是后面 sweep 与聚合的基础。

3超参 sweep：网格 vs 随机

超参 sweep：网格 vs 随机搜索

有了 config，就能做hyperparameter sweep（超参扫描）——系统地在多组超参上跑实验找最优。两种主力策略，背后是一个反直觉但重要的结论。

grid search（网格搜索）：对每个超参取若干候选值，枚举所有组合。直观、彻底，但有两个致命弱点：其一，组合数随超参个数指数爆炸（5 个超参各 5 个值 = 3125 次运行）；其二，它在不重要的维度上浪费大量预算——如果某个超参其实不影响结果，网格还是会在它的每个值上都跑一遍。

random search（随机搜索）：从每个超参的分布里随机采样组合，跑固定预算次数。Bergstra & Bengio 2012 的经典结论是：当只有少数超参真正重要时，随机搜索在相同预算下通常优于网格搜索。

为什么随机搜索常常更好（Bergstra & Bengio 2012 的核心图） 假设只有『重要超参』影响结果，『次要超参』几乎无影响。 花 9 次预算搜索： 网格搜索 (3×3): 随机搜索 (9 个随机点): 次要 → 次要 → 重 ┌─┬─┬─┐ 重 ┌────────┐ 要 │•│•│•│ 重要维度只试了 要 │ • • │ 重要维度试了 ↓ ├─┼─┼─┤ 3 个不同值! ↓ │• • •│ 9 个不同值! │•│•│•│ │ • • │ ├─┼─┼─┤ │ • • │ │•│•│•│ └────────┘ 网格在重要维度只覆盖3个值 随机在重要维度覆盖了9个值 -> 更可能找到好的

这张图是理解随机搜索优势的关键：网格搜索把 9 次预算浪费在「次要超参的 3 个值 × 重要超参的 3 个值」上，结果重要超参只试了 3 个不同值；而随机搜索的 9 个点，在重要超参维度上几乎试了 9 个不同值——同样的预算，在真正重要的维度上探索得更充分，因此更可能撞到好配置。推论：除非超参很少（2–3 个）且你确信每个都重要，否则随机搜索通常是更好的默认。更先进的还有贝叶斯优化、Hyperband 等，但随机搜索是性价比极高的起点。

还有一个公平性的维度常被忽视：当你给自己的新方法做了大量 sweep、却只给基线用默认超参时，「我的方法更好」很可能只是调参努力的不对等（一个模块 02 讲过的混杂）。诚实的 sweep 纪律要求：给基线和新方法同等的调参预算——你的方法 sweep 了 100 组，基线也该 sweep 100 组。很多论文的「提升」在给基线公平调参后大幅缩水甚至消失（Sculley 等反复指出）。sweep 不只是为自己找最优，更是公平对待对手的一部分。

sweep 的一个常见陷阱与模块 03 直接相关：在 sweep 里选出的「最优超参」自带乐观偏差。你试了 100 组超参、挑出验证集上最好的那组——但这个「最好」部分是运气（多重比较！），它在测试集上往往会回落。诚实的做法是：用验证集选超参，但用独立的测试集报告最终性能，且最好对选出的配置多跑几个种子确认它不是侥幸。把 sweep 的选择和最终评估分开，是避免「sweep 过拟合」的关键纪律。

4可复现：固定一切随机源

可复现：固定一切随机源

reproducibility（可复现）是研究工程的核心目标，也是最容易在细节上翻车的地方。「我固定了种子，为什么还是复现不出？」是一个极常见的困惑，答案是：随机源远不止一个种子。

一次机器学习运行里潜藏着多个独立的随机源，要可复现必须把它们全部固定：

随机源影响什么怎么固定
框架全局 RNG权重初始化、dropout、shufflenp.random.seed / 框架的 manual_seed
数据加载/打乱训练样本顺序给 DataLoader/采样器单独设种子
数据增强每个样本的随机变换增强管线的 RNG 也要设种子
多线程/多进程worker 的随机状态worker_init_fn 给每个 worker 设种子
GPU 非确定性算子并行归约的浮点累加顺序开 deterministic 模式（可能变慢）
哈希随机化字典/集合顺序（Python)PYTHONHASHSEED

更隐蔽的是non-determinism（非确定性）：即使固定了所有种子，某些操作（GPU 并行归约、多线程数据加载、原子操作）仍可能因执行顺序不定而给出略有差异的结果。这是因为浮点加法不满足结合律——$(a+b)+c \ne a+(b+c)$ 在浮点下可能不等，而并行归约的累加顺序每次都可能不同。要完全确定，需要显式开启框架的确定性模式（通常以性能为代价）。

但可复现不止于固定种子，还包括environment capture（环境固化）：记录并冻结软硬件环境——库版本（requirements.txt / lockfile）、CUDA 版本、甚至硬件型号。可复现性危机里大量案例死在「版本不对」：作者用 transformers 4.20 跑的结果，你用 4.40 复现不出，因为某个默认行为变了。还应记录代码版本（git commit hash），这样你能精确知道「这个结果是哪个版本的代码跑的」。

可复现的黄金标准，是每个结果都能追溯到「config + 代码版本 + 环境 + 种子」四元组。缺任何一个，复现就有风险：缺 config 不知道参数，缺代码版本不知道实现，缺环境不知道依赖，缺种子不知道随机状态。实践上不必每次都做到极致，但重要结论（要写进论文的）必须四件齐全。notebook 会让你写一个「可复现实验」：固定种子，连跑两次，断言两次结果逐位相同——这是可复现最直接的自检。

5实验日志与结果聚合

实验日志与结果聚合

当你跑了几百个实验，最后一个问题是：怎么把它们汇总成能下结论的东西？这需要两件事——experiment tracking（实验追踪，系统地记录每次运行）和results aggregation（结果聚合，把多次运行汇总成表/图）。

实验追踪的核心，是为每次运行记录一份结构化日志：它的 config（什么参数）、它的指标（什么结果）、它的元信息（代码版本、时间、种子）。有了这些，你才能回答「上周那个 0.92 是哪组参数跑出来的」「lr=0.01 和 0.001 哪个更好」这类问题。工具上 W&B、MLflow、TensorBoard 很方便，但起步阶段——一个把每次运行存成一行的 CSV / 一个 dict 列表就足够。重点不是工具多花哨，而是每次运行都留下可查的记录。

结果聚合是把这些记录按配置分组、算统计量的过程。这正是 pandas 的主场——groupby + agg 一行就能把「每个方法 × 每个超参的多个种子运行」聚合成「均值 ± 标准差 ± 运行次数」的可读表：

# 把长表(每行一次运行)聚合成每个配置的统计
summary = (df.groupby(['method', 'lr'])['accuracy']
             .agg(['mean', 'std', 'count'])
             .reset_index())
# 一眼看出: 哪个配置均值最高、方差多大、跑了几个种子

聚合时务必同时报告 count（运行次数）——这让读者（和你自己）知道每个数字背后有几个种子。一个基于 1 个种子的「均值」和基于 20 个种子的「均值」可信度天差地别（模块 03）。聚合的产物，应当直接喂给模块 05 的诚实图表：带误差棒的对比图，其误差棒就来自这里聚合出的 std 或 CI。研究工程的输出，是写作的输入——这就是闭环。

一个常见的反模式，是把聚合这一步留到最后、用手工完成：实验跑完，把几十个数字从日志里复制粘贴进 Excel/文档，手动算均值。这既慢又极易出错（粘错一个数、算错一个公式，结论就错了），而且不可复现（下次重跑还得手工再来一遍）。正确的做法是把聚合写成代码：从结构化日志（CSV/DataFrame）出发，用 groupby 一行算出所有统计量。这样不仅杜绝手工错误，还让「从原始运行到最终表格」整条链路可复现、可重放——改了实验重跑，表格自动更新。把分析也纳入可复现，是研究工程容易被忽视但回报很高的一环。

直白说

把实验结果当成数据来处理：每次运行是一行，参数和指标是列。一旦你这么想，pandas 的全套武器（筛选、分组、聚合、透视）都为你所用，「分析几百个实验」就和「分析一个数据集」一样自然。

严谨说

一个进阶但极有用的实践是把 config 摊平进结果表：让每次运行的记录既含指标、又含它的所有 config 项（lr、batch、seed 等作为列）。这样聚合时可以按任意config 维度分组、可以画「准确率 vs 学习率」的曲线、可以一眼看出哪个超参影响最大。config-as-columns 是把实验追踪和分析打通的关键技巧，notebook 会让你实现它。

6worked：config+sweep+可复现+聚合

worked 例：轻量 config + sweep + 可复现跑 + 聚合

本模块 notebook 的核心 worked 例，把研究工程的四件事串成一个完整的小型实验管线：定义 config → 生成 sweep → 可复现地跑每个 config → 聚合结果表。

我们用一个纯 numpy 的玩具「实验」（一个有已知最优超参的合成目标函数，模拟「训练并评测」），把整套工程流程走一遍——重点不在「训练」本身，而在围绕实验的工程卫生：

  1. config 系统：写一个带默认值、可覆盖、可序列化的轻量 config。
  2. sweep：用 config 系统生成一组网格 sweep 和一组随机 sweep，对比两者在固定预算下谁找到更好的超参。
  3. 可复现地跑：每个 config 固定种子运行，并断言「同一 config 跑两次结果逐位相同」（可复现自检）。
  4. 聚合：把所有运行存成 DataFrame，用 groupby 聚合成「每个配置的均值 ± 方差」，找出最优配置。

这个 worked 例的价值，是让你亲手搭一遍真实研究里天天用的管线。你会看到 config 如何让 sweep 变得自动化、固定种子如何让结果可复现（两次逐位相同）、pandas 如何把一堆运行秒变可读表。做完它，你就有了一个可以直接迁移到真实项目的研究工程骨架——把「玩具目标函数」换成「真实训练」，整套流程原样适用。

注意这条管线里四个模块的纪律是如何咬合在一起的：config（本模块）让每个实验可复现可追溯；sweep（本模块）系统地产生多个配置的运行；每个配置跑多个种子（模块 03 的统计要求）；聚合（本模块）把它们变成带方差的表（模块 03 的报告要求）；而这张表的方差列，正是模块 05 诚实图表的误差棒来源。换句话说，研究工程不是一堆孤立的技巧，而是把方法论各环节物理地连起来的传送带——没有它，受控实验、多种子统计、诚实图表都只是纸上的好主意；有了它，它们才能在一条能跑、能复现的流水线上真正落地。这正是本模块放在统计之后、写作之前的原因。

延伸阅读：Wilson et al.《Good Enough Practices in Scientific Computing》（务实的科研工程规范）、Bergstra & Bengio《Random Search for Hyper-Parameter Optimization》（随机 vs 网格）、Sandve et al.《Ten Simple Rules for Reproducible Research》（可复现十诫）。清单见 references.md。

7研究工程的最小纪律集

研究工程的最小纪律集

讲了这么多，把研究工程卫生浓缩成一个最小纪律集——做到这些，你的研究就跨过了「可复现、可协作」的底线，而开销很小：

  • 参数进 config：实验的所有可调项集中成一份可存档的 config，杜绝硬编码。
  • 固定随机源：每次运行固定种子（且记录种子）；重要结论开确定性模式核验。
  • 记录每次运行：config + 指标 + 代码版本(git hash) + 环境，至少存成一行 CSV。
  • 用版本控制：代码进 git，结果能追溯到 commit；不要用「final_v2_real_final.py」这种文件名管理版本。
  • 分离选择与评估：用验证集 sweep 选超参，用独立测试集报最终结果（避免 sweep 过拟合）。
  • 聚合而非堆砌：用 pandas 把多次运行聚合成带方差的表，而非把一堆数字粘进文档。

注意这套纪律的务实性：它不要求你写单元测试、不要求复杂架构、不要求重型工具。它只要求把最容易丢失、最难补救的东西（参数、种子、版本、运行记录）留存下来。这正是 Wilson 等「足够好的实践」的精神——用最小的纪律换取可复现性，而不是把研究代码工程化到完美（那是另一个极端的浪费）。

最后，研究工程卫生与本课其他模块环环相扣：它让模块 02 的受控实验可复现（否则别人重跑不出你的对照）、让模块 03 的多种子统计可执行（sweep 和聚合是多种子运行的载体）、为模块 05 的诚实图表提供数据（聚合出的方差就是误差棒）。一句话：研究工程是把方法论落地的工程基础设施——没有它，前面的纪律都停在纸面；有了它，它们才能真正跑起来、被验证、被传递。

8研究前沿与开放问题

研究前沿与开放问题

  • 大模型时代的可复现：当单次训练耗资百万、几乎无法重复时，传统的「多种子 + 完全可复现」难以为继。如何在这种约束下保证可信度（如报告训练曲线、用更便宜的代理实验），是尖锐的开放问题。
  • 实验管理工具的标准化：W&B、MLflow、Hydra、DVC 等各成生态，缺乏统一标准，迁移成本高。「实验该如何被记录、共享、复现」尚无社区公认的最佳实践栈。
  • 自动化超参优化的代价核算：贝叶斯优化、Hyperband、PBT 等比随机搜索更高效，但它们引入的「搜索过程本身的方差与过拟合」如何诚实报告，常被忽视。
  • 可复现的隐性成本：完全确定性模式常显著降低 GPU 性能；环境完全冻结又阻碍利用新硬件/新库。可复现与效率/可演进之间的权衡，没有普适答案。
  • 从「能复现」到「能扩展」：他人不仅要能重跑你的实验，还要能在其上轻松改一个变量重跑。如何设计「易于他人扩展」的实验代码（而非只是能复现的快照），是研究工程的更高目标。
  • 数据与代码的长期保存：论文发表五年后，依赖的数据集下线、库版本不可安装、容器镜像失效——「可复现」随时间衰减。如何让研究产物长期可复现（归档、容器化、依赖冻结）仍缺乏被普遍采纳的方案。

必读：Wilson et al.《Good Enough Practices in Scientific Computing》（工程卫生底线）、Bergstra & Bengio《Random Search for Hyper-Parameter Optimization》（sweep 策略）、Sculley et al.《Hidden Technical Debt in ML Systems》（研究工程的复杂度陷阱）。清单见 references.md。
