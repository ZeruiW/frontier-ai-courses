1为什么工具调用是 agent 的承重墙

一个 LLM 本身只会做一件事：给定一段文本，预测接下来的文本。它不能联网、不能读你的文件、不能跑代码、不能查数据库——它没有手。工具调用（function calling / tool use）就是给它装上手：约定一种格式，让模型在该用外部能力时，输出一个结构化的工具调用（工具名 + 参数），由我们的代码执行后把结果喂回去。

这件事看似简单，却是整个 agent 大厦的承重墙。模型要改变世界、要获取训练数据之外的新信息，唯一通道就是工具调用。搜索、代码执行、文件读写、数据库、浏览器、乃至下一模块 MCP 接进来的任意系统——在模型眼里都是「工具」。所以把这一次「模型说要调工具 → 我们执行 → 结果回喂」的往返做扎实、做鲁棒，是后面一切的地基。

这里有一个常被忽视的概念分层，先说清楚：模型永远不直接执行任何东西。它只是输出一段文本，这段文本恰好被格式化成「我想调 get_weather，参数是 city=北京」。真正去执行 get_weather 的，是我们写的代码（scaffold）；模型只是提出请求，执行与否、怎么执行、结果如何回传，全在我们掌控。理解这条边界至关重要：它意味着安全护栏、参数校验、权限控制都发生在模型之外（我们这一侧），模型再怎么「想」调危险工具，只要我们的分发器不放行，就调不成——这是模块 05 安全防线的根基，也是为什么本课把 scaffold 而非模型当主角。

本模块的目标是从零写出工具调用的完整 scaffold：工具如何定义（含参数的 JSON Schema）、模型的调用如何被解析、参数如何校验、如何分发到真实函数、如何处理并行调用、以及如何在出错时重试而非崩溃。我们用 MockLLM 当模型，把整条链路端到端跑通——你会看到，真实 Anthropic / OpenAI 的接口不过是给这套逻辑换了字段名。

一句话抓住本模块：工具调用 = 给 LLM 一份「菜单」（工具定义），它点菜（输出调用），你下厨（执行），再把菜端回去（结果回喂）。本模块的全部工程，都是在让这套点菜-下厨-上菜的流程不出错、能并发、出错能恢复。难点不在「调用模型」那一行 API，而在它两侧的解析、校验与分发。

2工具定义：带 schema 的菜单

工具定义：给模型一份带 schema 的菜单

一个工具定义包含三部分，缺一不可：名称（模型用它指代要调谁）、自然语言说明（模型靠它判断何时该调、参数什么意思）、以及参数的 JSON Schema（约束参数的类型、必填、取值）。三者里说明与 schema 的质量，直接决定模型调得对不对。

# 一个工具定义（贴近 Anthropic 形状；OpenAI 把 input_schema 叫 parameters）
{
  "name": "get_weather",
  "description": "查询某城市当前天气。当用户询问天气时调用。",
  "input_schema": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "城市名，如 北京"},
      "unit": {"type": "string", "enum": ["c", "f"], "description": "温标"}
    },
    "required": ["city"]
  }
}

这段 JSON Schema 是契约：它告诉模型「city 是必填字符串、unit 只能是 c 或 f」，也告诉我们的校验器「该挡住什么」。注意 required 与 enum ——前者保证必填字段不缺，后者把取值锁死在合法集合里。一个写得好的 schema，能从源头大幅减少模型给出非法参数的概率（配合 strict 结构化输出更甚）。

直白说

把工具定义想成给新来的实习生写的「报销单填写说明」：哪些栏必填、金额要填数字、币种只能选人民币或美元。说明写得越清楚、表单约束越严，实习生填错的概率越低，你事后核对的负担越小。

严谨说

形式上，工具定义是模型 prompt 的一部分（通常拼在 system 或专门的 tools 字段里）。模型据此决定 tool_choice：是不调（none）、自己看着办（auto）、必须调某个（any/tool）。本课的 MockLLM 用规则模拟这个决策，但解析、校验、分发这些下游环节与真实模型完全一致——这正是 scaffold 可迁移的原因。

一个容易被忽视的点：工具定义是写给模型看的，不是写给人看的。description 要从「模型在什么情形下、凭什么判断该调它、参数怎么填」的角度写，而不是堆术语。Anthropic / OpenAI 的最佳实践都强调：把「何时调用」写进 description，比只写「这个工具做什么」能显著提升调用准确率——这一点在 notebook 的真实 schema 胶囊里会有体感。

3一次工具调用的完整往返

一次工具调用的完整往返

有了菜单，看一次完整的「点菜-上菜」长什么样。以 Anthropic 形状为例，一次往返跨两条消息：

① 我们 -> 模型： [用户问题] + [工具定义清单] ② 模型 -> 我们： assistant 消息，content 里含一个 tool_use 块 { type:'tool_use', id:'tu_01', name:'get_weather', input:{city:'北京'} } ③ 我们执行 get_weather(city='北京') -> '晴 26°C' ④ 我们 -> 模型： user 消息，content 里含一个 tool_result 块 { type:'tool_result', tool_use_id:'tu_01', content:'晴 26°C' } ⑤ 模型 -> 我们： assistant 消息（文本）：『北京今天晴，26 度』 -> 结束

几个关键约定要记死：① 每个 tool_use 块有唯一 id；② 回传的 tool_result 必须用 tool_use_id 和它配对（多调用时靠它对号入座）；③ 工具执行失败时，tool_result 带 is_error: true 把错误作为内容回传给模型，让模型决定改参数重试还是换路——而不是在我们这边抛异常中断。

这条往返就是 ReAct 范式（Yao 2022）的最小单元：模型「想」（可能先输出一段思考）、「行动」（输出 tool_use）、看「观察」（tool_result）、再想……把它放进一个循环，就是一个能多步使用工具的 agent。本模块的 notebook 会把这个循环从零写出来，跑通「问 → 调工具 → 拿结果 → （可能再调）→ 回答」。

回头看模块 00 那张感知-动作循环图，这条往返恰好填满了它的一整圈：tool_use 是「动作」、tool_result 是「观察」、模型的下一次输出是基于新观察的再决策。一次往返是一圈，多次往返就是 agent 多步地与世界交互。所以掌握这一节，等于掌握了 agent 循环里信息如何在模型与环境之间流动的全部骨架——后面的 MCP（换一种方式接入工具）、computer use（换一种观察与动作）、agentic RL（用这些往返产生的轨迹训练模型），都没有跳出这个骨架，只是替换了其中某一段。

一个新手常踩的坑：把工具执行的异常直接抛出去中断整个 agent。正确做法是捕获异常、包成带 is_error 的 tool_result 回喂给模型。模型看到「city 参数无效」这样的错误信息，往往能自己改对再调一次。让错误成为模型的观察，而非程序的崩溃——这是 agent 鲁棒性的分水岭。

4参数校验：第一道防线

参数校验：scaffold 的第一道防线

模型给的参数不可全信：它可能漏填必填字段、给错类型（该是数字给了字符串）、给出枚举外的值、甚至调用一个根本不存在的工具（工具幻觉）。在把参数交给真实函数执行之前，必须用 schema 校验它们。校验不过，应当回一个清晰的错误让模型改，而不是让非法参数进到 os.remove(path) 里酿成事故。

一个最小但够用的 JSON Schema 校验器要查这几件事：

  • 工具存在：模型给的 name 在注册表里吗？不在 → 报「未知工具」（挡住工具幻觉）。
  • 必填齐全：required 里的字段都给了吗？缺 → 报「缺少字段 X」。
  • 类型正确：每个字段的值匹配它声明的 type 吗（string/integer/number/boolean/object/array）？
  • 枚举合法：声明了 enum 的字段，给的值在集合里吗？
  • 无多余字段（可选，严格模式）：给了 schema 里没声明的字段吗？

直白说

校验器就是门口的保安：检查证件（必填）、看证件类型对不对（type）、确认人在白名单上（enum/已知工具）。不合格的当场拦下并说清原因（「缺工牌」），而不是放进去再出事。

严谨说

形式上，校验是把模型输出的 input 对象与工具的 input_schema 逐字段比对。JSON Schema 本身远比这复杂（嵌套、anyOf、format……），但 agent 实践里80% 的价值来自这五项基础检查。本模块 notebook 从零实现它们；真实系统则常用现成的 schema 校验库或模型的 strict 模式从生成侧保证。

一个关于类型校验的小陷阱值得单独点出：在 Python 里 bool 是 int 的子类，isinstance(True, int) 为真。所以校验 integer / number 时若不先把 bool 排除，模型给的 True 会被误当成合法整数放行。这类「看似对、实则错」的边界，正是为什么校验器要从零亲手写一遍才有体感——notebook 的第 2 节会专门处理它。类似的暗礁还有：JSON 里没有整数/浮点之分（都是 number），所以 integer 校验在跨语言时要格外小心；以及空字符串、null 是否算「缺失」也需明确约定。

校验的产物不只是「过/不过」，更重要的是可读的错误信息。「city 字段缺失」「unit 必须是 c 或 f 之一，你给了 k」这种信息回喂给模型，命中率远高于一句笼统的「参数错误」。把校验器设计成「失败时返回精确诊断」，等于给了模型自我修正的钩子——这与人类看到清晰报错才改得快，是同一个道理。好的错误信息是 agent 自愈能力的一半。

5分发：路由到真实函数

分发：把调用路由到真实函数

校验通过后，要把「工具名 + 参数」路由到对应的 Python 函数执行——这叫分发（dispatch）。核心数据结构是一个工具注册表：把「工具名 → (可执行函数, schema)」存成一张表，模型给名字，我们查表执行。

# 工具注册表 + 分发（极简）
REGISTRY = {}                     # name -> {'fn':..., 'schema':...}
def register(name, fn, schema):
    REGISTRY[name] = {'fn': fn, 'schema': schema}

def dispatch(call):               # call = {'name':..., 'input':{...}}
    name = call['name']
    if name not in REGISTRY:
        return {'is_error': True, 'content': f'未知工具: {name}'}
    ok, err = validate(call['input'], REGISTRY[name]['schema'])
    if not ok:
        return {'is_error': True, 'content': err}
    try:
        result = REGISTRY[name]['fn'](**call['input'])
        return {'is_error': False, 'content': str(result)}
    except Exception as e:        # 执行期错误也包成 tool_result
        return {'is_error': True, 'content': f'{type(e).__name__}: {e}'}

注意分发器的纪律：无论是未知工具、校验失败、还是执行抛异常，它都不向上抛错，而是统一返回一个 tool_result（带 is_error 标记）。这把「错误」从「程序崩溃」降级为「模型的一次观察」，让上层的 agent 循环可以平滑地继续——模型据此重试或换路。这是把脆弱的 demo 变成鲁棒 agent 的关键转变。

注册表这个抽象还带来一个工程上的好处：解耦。工具的「定义」（给模型看的 schema）、「实现」（真正执行的函数）、「调度」（循环逻辑）被分到三处，互不纠缠。加一个新工具，只需写函数 + schema、register 一下，循环代码一行不改；换掉某个工具的实现（比如把假天气换成真 API），注册表外的一切照旧。这种「统一的调用形状 + 可插拔的工具」正是规模化的关键——当工具从 3 个涨到 300 个时，是注册表而非 if-else 链让系统不崩。下一模块的 MCP 把这个思想推到极致：连「工具从哪来」都标准化成一套协议。

注册表 + 分发器 = 把 LLM 的「自然语言意图」翻译成「确定性的函数执行」的那座桥。它有意把每个工具都收敛成同一个调用形状（名字 + 参数对象 → tool_result），于是无论 3 个工具还是 300 个，循环逻辑都不变——这也是 MCP（下一模块）能把工具规模化的前提。

6并行工具调用

并行工具调用

模型常在一次响应里同时请求多个互不依赖的工具调用——比如「同时查北京和上海的天气」。这叫 parallel tool calls，是省往返、降延迟的重要能力。处理它有两条铁律：

  1. 并发执行：多个无依赖的调用可以同时跑（本课用顺序执行模拟，逻辑相同；真实系统用线程/异步并发）。
  2. 结果合并回传：把本轮所有调用的 tool_result 放进同一条 user 消息里一次性回传。
并行结果必须合在一条消息

最容易出错、也最隐蔽的一点（Anthropic 文档明确警示）：绝不要把多个 tool_result 拆成多条消息分开回传。一次响应里的 N 个 tool_use，必须对应一条 user 消息里的 N 个 tool_result。拆开回传会悄悄训练模型以后少做并行调用——它「学到」并行的结果会被割裂，于是退回低效的串行。错误不报，但能力慢慢退化，极难排查。

分发器只要能接收一个调用列表、对每个调用复用单次分发逻辑、把结果按 tool_use_id 一一配对返回即可。配对靠 id：模型给的每个 tool_use 有唯一 id，回传的每个 tool_result 用 tool_use_id 指回去——这样即使结果乱序、即使有的成功有的失败，模型也能对号入座知道哪个结果对应哪个调用。

并行还带来一个错误处理的细节：部分失败。三个调用里一个失败两个成功，正确做法是把三个 tool_result 都回传（失败那个带 is_error），一个都不能少——漏掉失败那个，模型会以为它从没发生，逻辑就乱了。notebook 会专门验证「部分失败时结果数量与配对仍然正确」。

一个值得建立的判断：不是所有调用都该并行。并行的前提是「互不依赖」——同时查两座城市的天气可以并行，但「先查用户 id，再用这个 id 查订单」就有依赖、必须串行。现实里模型自己会判断哪些能并行、哪些要串行（并把有依赖的拆成多轮）。scaffold 这一侧的职责很纯粹：模型说要并行的（一次响应里的多个 tool_use），就忠实地并发执行并合并回传；至于该不该并行，是模型的决策、是提示工程与训练的范畴，不在本模块的工程边界内。

7错误处理与重试

错误处理与重试

真实工具会失败：网络抖动、服务 5xx、超时、限流。这类瞬时错误往往再试一次就好；而参数非法、未知工具这类确定性错误重试一万次也没用。区分这两类、对前者重试、对后者直接回错让模型改，是 agent 工程的基本功。

重试的标准做法是指数退避（exponential backoff）：第一次失败等 1 个单位、第二次等 2 个、第三次等 4 个……每次翻倍，再叠加一点随机抖动，避免大量 agent 在同一时刻一起重试把服务再次打垮（惊群）。

\[\text{wait}_k = \text{base}\times 2^{\,k}\times(1+\text{jitter}),\qquad k=0,1,2,\dots\]

直白说

打电话占线：第一次马上重拨、第二次等一会、第三次等更久——而不是疯狂连拨。对方真的不存在（号码错了）就别拨了，先去核对号码。区分『占线（可重试）』和『空号（别重试）』是关键。

严谨说

形式上要做两个判断：可重试性（错误属于瞬时类吗？通常按错误类型/HTTP 状态码判：5xx/超时可重试，4xx 参数类不可）与重试上限（试 N 次仍失败就放弃，把最终错误回喂给模型）。本课用一个确定性的「前 K 次失败、第 K+1 次成功」的假工具来验证重试逻辑——无需真网络，就能断言「恰好重试了几次」「最终成功」。

把重试放在哪一层也有讲究：放在分发器内部（对单个工具调用透明重试），还是放在agent 循环外部（让模型看到失败、自己决定重试）？两者并用最稳——瞬时基础设施错误在分发层透明吞掉（模型不必关心网络抖动），而任务层面的失败（工具说「找不到该用户」）则回喂给模型，由它在更高层决策。本模块 notebook 实现分发层的退避重试；模型层的「反思后重试」在模块 04 的 Reflexion 思路里再深入。

最后强调一个贯穿全模块的设计哲学：agent 工程的鲁棒性，几乎全部来自「正确地对待错误」。未知工具、参数非法、执行抛异常、瞬时故障——这些不是「异常情况」，而是 agent 运行中的常态。一个能用的 agent 与一个 demo 的区别，往往不在顺利路径写得多漂亮，而在每一类错误是否都有明确归属：哪些挡在执行外（校验失败）、哪些透明重试（瞬时）、哪些回喂给模型自愈（任务级失败）、哪些直接终止（重试用尽）。把这张「错误处置表」想清楚、用 assert 一条条验证它确实生效，就是本模块最该带走的工程素养。

8研究前沿与开放问题

研究前沿与开放问题

  • 从提示到训练（Toolformer 之后）：工具使用最初靠提示，Schick 2023 证明它可被训练进模型本身；如今前沿模型把工具调用作为原生能力训练。如何让模型在成百上千个工具里准确选择（而非塞满上下文），催生了 tool search、检索式工具加载等方向。
  • 结构化输出的可靠性：strict 模式 / 受约束解码能从生成侧保证参数合法，但与思维链、流式、复杂 schema 的兼容仍在演进。「既要模型自由推理、又要输出严格符合 schema」是活跃的工程前沿。
  • 动作空间的设计：固定 JSON 工具调用 vs 让模型直接写可执行代码当动作（CodeAct, Wang 2024）。代码动作表达力更强、能组合，但执行与安全更复杂——动作空间该多结构化，没有定论。
  • 并行与依赖：模型如何判断哪些调用可并行、哪些有依赖必须串行？让模型生成「调用计划图」（DAG）而非线性调用序列，是提升复杂任务效率的探索方向。
  • 工具调用的可观测与归因：当一个 agent 调了几十个工具后给出错误结果，是哪一步的工具用错了？把工具调用做成可追踪、可归因的，是评测与调试 agent 的基础设施难题（与模块 05 相通）。
  • 工具安全与权限：模型可能被诱导调用危险工具（删除、转账、外发），或被工具返回里的注入劫持。如何在分发层施加最小权限、对高危动作要求确认、把工具返回当数据而非指令——是把工具调用从「能用」推向「敢放生产」的关键，模块 05 专门展开。

必读：Anthropic tool use 文档（接口与并行/错误约定）、ReAct（Yao 2022，循环范式）、Toolformer（Schick 2023，工具能力可训练）、CodeAct（Wang 2024，代码动作）。清单见 references.md。
