1KV 墙：解码时的隐形显存杀手

我们到了最后一道墙，也是长上下文推理阶段最痛的一道——KV 墙。前四个模块解决了「位置不崩、注意力算得起、复杂度降下来」，但还有一个在自回归解码时才暴露的瓶颈：KV cache。

回忆解码：模型逐 token 生成，每生成一个新 token，都要对之前所有 token做注意力。为避免每步重算历史的 K、V，就把它们缓存起来——这就是 KV cache。问题是它随序列长度线性膨胀：

\[\text{KV cache 大小} = 2\,(K,V)\times L_\text{layers}\times H_\text{kv}\times d_\text{head}\times n \times \text{bytes}\]

直白说

KV cache 是长解码的「隐形显存杀手」。模型权重是固定的，但 KV cache 随你处理的上下文越长越大。一个 7B 模型在 128k 上下文下，KV cache 可能比模型权重本身还大好几倍——它，而不是模型，成了「能开多长上下文 / 多大批量」的真正限制。

严谨说

更糟的是，解码是访存受限的：每生成一个 token，都要把整个 KV cache 从显存读一遍。所以 KV cache 既吃显存容量（装不下），又吃显存带宽（读太慢）。长上下文解码慢、贵，根子大多在这里。这就是为什么 KV 压缩是长上下文服务的核心课题。

把 KV 墙和前面几道墙分清楚：内存墙（模块 02）是 prefill 时 n×n 的中间矩阵爆显存，FlashAttention 解决；KV 墙是 decode 时 O(n) 的缓存膨胀，本模块解决。二者都和长上下文有关，但一个在算注意力的瞬间、一个在保存历史的持续——FlashAttention 不省 KV cache，KV 压缩不省注意力计算，又是一对正交的杠杆。

把那条公式代进真实数字，68 GB 是怎么来的就一清二楚。7B 模型、L=32 层、H_kv=32 头、d_head=128、FP16（2 字节）、n=128k=131072：KV = 2 × 32 × 32 × 128 × 131072 × 2 字节。逐项乘：2(K和V) × 32 × 32 = 2048；× 128 = 262144；× 131072 ≈ 3.44×10¹⁰；× 2 字节 ≈ 6.87×10¹⁰ 字节 ≈ 68 GB。这个数随 n 严格线性——上下文减半到 64k，KV cache 就减半到 34 GB；翻倍到 256k，就涨到 136 GB。公式里每一个因子都是一条可调的省显存杠杆：减层数不现实，但减 H_kv（→ GQA/MQA）、减比特数（→ 量化）、减 n 的有效保留量（→ 淘汰/合并）正是本模块三条路各自攻击的项。

给一个直观的量级感受，理解 KV 墙为何如此扎手。一个 7B 模型权重 FP16 约 14 GB；而它在 128k 上下文下的 KV cache（32 层、32 个 KV 头、head_dim 128、FP16）约 68 GB——是模型本身的近五倍。也就是说，一旦上下文够长，决定「这张卡能不能跑、能跑多大批量」的不再是模型权重，而是 KV cache。这还只是单条序列；要并发服务多个长上下文请求，KV cache 的总量更是直接决定吞吐上限。长上下文服务的成本结构，很大程度上就是 KV cache 的成本结构——这是本模块所有压缩技术的现实动机。

2压缩 KV 的三条路

压缩 KV 的三条路：量化、淘汰、合并

压缩 KV cache 有三类正交手段，可单用也可叠加：

手段做什么省的维度代价
量化 quantization降低每个 K/V 数的存储精度（FP16→INT8/INT4）每元素的比特数量化误差（数值失真）
淘汰 eviction丢弃「不重要」token 的 KVtoken 数（序列维）误删将来要用的 token
合并 merging把相似/相邻 token 的 KV 合并成一个token 数（序列维）合并损失细节

注意它们省的是不同的维度：量化压「每个数多少比特」，淘汰/合并压「保留多少个 token」。所以量化和淘汰可以叠乘——先淘汰掉一半 token、再把剩下的量化到 4bit，压缩率相乘。

还有一类结构性压缩值得一提（详见 C20，本课不展开）：GQA / MQA——让多个 query 头共享同一组 K/V 头，直接把 H_kv 这一项缩小数倍。它是「设计模型时就压」（改架构），而本模块的量化/淘汰是「推理时再压」（不改模型）。两者也正交：一个 GQA 模型推理时照样可以再量化、再淘汰。

贯穿本模块的核心问题和模块 03 是同一个：哪些 token 重要、哪些可以不要？ 模块 03 问「哪些连接不算」（省算力），本模块问「哪些 token 的 KV 不存」（省显存）。attention sink（模块 03）已经给了第一个答案——开头几个 token 重要。本模块的 H2O 会给出更普适的答案：累积吸走注意力多的 token（heavy hitter）重要。理解了这条主线，淘汰类方法就都通了。

3KV 量化：用更少比特存 K、V

KV 量化：用更少比特存 K、V

最直接的压缩是量化：把 FP16（16 比特）的 K、V 存成 INT8（8 比特）甚至 INT4（4 比特），显存按比特数成比例下降。基本流程是仿射量化：

\[q = \text{round}\!\left(\frac{x - z}{s}\right),\qquad \hat x = s\cdot q + z,\qquad s = \frac{\max - \min}{2^{b}-1},\ z=\min\]

把一组数线性映射到 [0, 2^b−1] 的整数（s 是步长、z 是零点），存整数；用时再反量化回近似的浮点 x̂。比特数 b 越小越省，但量化误差越大。

手算一遍 INT4（b=4，量化级 2⁴−1=15）就懂了，也顺便看到离群值的破坏力。设一组 K 值 x=[0.1, 0.2, 0.15, 0.05]，分布很紧凑：

无离群值：min=0.05, max=0.20, s=(0.20-0.05)/15=0.01, z=0.05 x=0.1 → q=round((0.1-0.05)/0.01)=5 → x̂=0.05+5·0.01=0.10 (误差 0) x=0.2 → q=15 → x̂=0.20 (误差 0) → 4 个值几乎无损，因为它们铺满了 0..15 的量化格 加一个离群值 x=[0.1, 0.2, 0.15, 0.05, 5.0]： min=0.05, max=5.0, s=(5.0-0.05)/15=0.33, z=0.05 x=0.1 → q=round((0.1-0.05)/0.33)=round(0.15)=0 → x̂=0.05 (误差 0.05，50%!) x=0.2 → q=round(0.45)=0 → x̂=0.05 (误差 0.15，75%!) x=0.15 → q=round(0.30)=0 → x̂=0.05 → 4 个正常值全被挤进 q=0 这一格，彼此再也分不开

这就是离群值灾难的字面演示：一个 5.0 把量化范围从 0.15 撑大到 4.95（33 倍），步长 s 随之暴涨，于是所有正常值挤进同一个量化格、彼此无法区分，误差从 0 跳到 50–75%。分组量化的解法在这里一目了然：把这 5 个数切成两组（正常值一组、离群值单独一组）各自量化，离群值就只污染它自己那一格，正常值那组恢复近乎无损。这正是 notebook 里要复现的「全局量化 vs 分组量化」对比。

一个关键的实践智慧（KIVI 等）：K 和 V 要区别对待。经验发现 K 的不同通道（channel）数值分布差异大、对量化更敏感，宜按通道量化；V 则按 token量化更好。「为什么 K、V 不对称」不是玄学，而是它们在注意力里扮演的角色不同——K 进入 exp 的指数（误差被放大），V 只是被加权求和（误差较温和）。

直白说

量化的好处是通用、不挑任务：它不丢任何 token，只是让每个数糊一点。所以它在「不能误删信息」的场景下比淘汰更安全。代价是误差会通过注意力传播——尤其 K 的误差进了 softmax 的指数，可能被放大。

严谨说

量化误差怎么量？常用反量化后的重构误差（‖x − x̂‖）和下游影响（量化 KV 算出的注意力输出 vs FP16 的差距）。notebook 会让你实现 INT8/INT4 量化、测量这两种误差，并验证「比特越少误差越大」「按组量化比全局量化误差小」。

量化的一个陷阱是离群值（outlier）：若一组数里有个别极大值，它会把量化范围 [min,max] 撑得很宽，使大多数正常值挤在很少几个量化级里、精度暴跌。解法是分组量化（把数据切成小组各自量化，离群值只污染它那一组）。这与大模型权重量化里的离群值问题同源——是低比特量化的通用难点。

4KV 淘汰：H2O 与 heavy hitter

KV 淘汰：H2O 与 heavy hitter

量化压「比特」，淘汰压「token 数」。但淘汰危险得多——丢错了 token，将来要用时就彻底没了。所以淘汰的全部难点是：怎么判断一个 token 的 KV 将来还重不重要？

Zhang et al. 2023 的 H2O（Heavy-Hitter Oracle）给出了一个漂亮的答案，基于一个关键观察：注意力是高度集中的——少数 token（heavy hitters）累积吸走了绝大部分注意力权重（这正是 attention sink 现象的推广）。既然如此，只要保留这些 heavy hitters，就能在很小的缓存下维持性能。

H2O 的重要性打分简单有力：一个 token 的重要性 = 它到目前为止被所有后续 query 关注的累积注意力分数之和。

\[\text{importance}(j) = \sum_{i \ge j} P_{ij}\quad(\text{token } j \text{ 被后续所有 query 的注意力质量累积})\]

淘汰策略 = 保留两部分：① 重要性最高的若干 heavy hitters（长期重要的 token）+ ② 最近的一个滑动窗口（近期 token，无论重要性——因为它们还没机会积累分数，且局部信息要紧）。这个结构正是 StreamingLLM 的「sink + 滑窗」的数据驱动版——sink 换成了动态算出的 heavy hitter。

跟着一个最小例子走一遍淘汰决策。设已生成到第 5 个 token，缓存里有 token 0–4，但预算只够存 3 个。把每个 token 被后续 query 关注的累积分数列出来（含「最近窗口」标记，设窗口大小=1，即必保留最新的 token 4）：

token: 0 1 2 3 4(最新) 累积注意力: 0.9 0.1 0.15 0.2 —(刚生成,未积累) 角色: 候选 候选 候选 候选 ★最近窗口(强制保留) 预算=3，最近窗口占 1 个名额 → 剩 2 个名额给「候选」中分数最高的： 候选按分数排序: token0(0.9) > token3(0.2) > token2(0.15) > token1(0.1) 保留 token0、token3 (heavy hitters) + token4 (最近窗口) 淘汰 token1、token2 (窗口外的最低分) ✗

这一步把 H2O 的全部机制压缩成一次排序：最新 token 走「最近窗口」通道无条件保命，其余按累积注意力分数竞争剩下的名额，分数垫底的被踢出。注意 token 0 的 0.9 分——它很可能就是个 attention sink 或关键事实，被牢牢留下；而 token 1、2 没什么人关注，丢掉对后续影响很小。每解码一步，新 query 的注意力会给每个存活 token 的累积分数再加一笔，排序随之更新——所以这是一个在线、持续的淘汰过程，几乎不增加额外计算。

H2O 的 KV 保留（缓存预算固定时）： [heavy hitter][heavy hitter] ...(淘汰低分token)... [最近窗口] ↑累积注意力分数最高的 ↑最近的若干个 (长期重要，如关键事实) (近期上下文) 每步解码：算新 query 的注意力 → 更新各 token 累积分数 → 若超预算，淘汰窗口外分数最低的 token

H2O 的精妙在于把「重要性」变成了一个可在线累积的标量——每个 token 维护一个「累积被关注分数」，解码时顺便更新，超预算就踢掉窗口外的最低分。几乎零额外开销。另一个思路是 SnapKV：不在解码时动态淘汰，而是在 prefill 结束后，用 prompt 末尾一段「观察窗」的注意力预测哪些 prompt token 重要，一次性压缩。两者一个「解码时持续淘汰」、一个「prefill 后一次压缩」，都源自同一个「注意力集中」的观察。notebook 会实现 H2O 的累积打分与淘汰。

但淘汰类方法有一个无法回避的风险，必须诚实面对：淘汰是不可逆的——一旦一个 token 的 KV 被丢掉，它将来就再也回不来了。而「当前不重要」不等于「将来不重要」：一个 token 可能在被淘汰后，恰好成为某个后续 query 真正需要的那一个。这正是淘汰类方法在多跳、需要回看冷门细节的任务上可能翻车的根源（模块 6 的 RULER 会专门拷打这一点）。相比之下，量化是无损 token的（只是把每个数糊一点，不丢任何 token），所以在「不能误删信息」的场景下更安全。淘汰省得多但赌性大、量化省得少但稳妥——这是选择压缩策略时的核心权衡。

5评测：能输入很长 ≠ 真的看见

评测：能输入很长 ≠ 真的看见了

压缩（量化/淘汰）都是近似——它们必然损失信息。压多了，模型就「看不见」被压掉的内容了。所以本模块的下半场是评测：怎么检验「压缩后（或外推后、或稀疏后）模型还真的能用上长上下文里的信息」？这也是整门课的收口——前四模块让模型「能看长」，评测回答「是否真的看见了」。

最经典的探针是 NIAH（Needle In A Haystack，大海捞针，Kamradt 2023）：

  • 干草堆：一段很长的背景文本（如长文集）。
  • 针：一句与背景无关的、可检索的事实（如「旧金山最好的事是 2024 年 3 月 4 日在多洛雷斯公园吃三明治」）。
  • 任务：把针埋进干草堆的某个深度（位置），然后问模型那个事实，看它能否检索出来。
  • 扫描：在不同的上下文长度 × 针的深度组合下重复，画成一张热力图——直观暴露模型的「有效上下文」边界。

直白说

NIAH 的威力在于它把「有效上下文」可视化了。一个号称 128k 的模型，热力图可能显示它在 32k 之后、或在「中间深度」就开始捞不到针——这就是「能看长 ≠ 看得见」的铁证。它简单、可控、一眼看出问题，是长上下文模型的第一道体检。

严谨说

一个反复出现的现象是 lost in the middle（Liu et al. 2023）：模型对放在上下文开头和结尾的信息检索好，对放在中间的差，呈 U 形。所以 NIAH 必须扫描针的深度——只在结尾放针会得到虚高的好成绩。这也呼应模块 01：位置编码外推成功（PPL 不崩）只是必要条件，不保证中间位置真的可用。

NIAH 虽好，但太简单——它只考「单针、精确字符串检索」。一个模型可能 NIAH 满分，却在「需要综合多处信息」时失败。所以单靠 NIAH 会高估模型。这就引出了更难、更全面的基准 RULER（下一节）。评测长上下文的铁律是：既要扫位置（别只在结尾放针），也要加难度（别只考单针检索）。

6RULER：更难更全面的基准

RULER：更难、更全面的长上下文基准

RULER（Hsieh et al. 2024）是当前长上下文评测的标杆。它指出单一 NIAH 太容易，于是用合成的方式造了 13 类难度递增的任务，按长度分档，更能区分模型的真实长上下文能力：

  • 多针检索（multi-key NIAH）：埋多根针、问其中某一根，考干扰下的检索。
  • 变量追踪（variable tracking，多跳）：如「X1=12345; X2=X1; X3=X2……问 X3」，需要串联多处分散信息才能作答——远难于单针。
  • 聚合（aggregation）：如统计长文里某类词出现最多的若干个，需要通览并归纳全文，而非定位一处。
  • 长上下文问答：在长文里回答需要理解的问题，最接近真实使用。

RULER 的核心贡献是揭示了：许多模型「宣称的窗口」远大于「有效窗口」。一个号称 128k 的模型，可能在 RULER 的多跳任务上 32k 就开始崩。这把「上下文长度」从一个营销数字变成了一个可测量、可比较的能力。

直白说

为什么用合成任务？因为合成任务能精确控制难度与长度、能任意拉长而不受真实文档长度限制、且答案唯一可自动判分。这让我们能干净地测出「长度→能力」的衰减曲线，定位模型在哪个长度、哪类任务上开始失效。

严谨说

多跳（变量追踪）尤其能拷打压缩/稀疏/线性方法：它要求模型同时维持并组合多条分散的线索。KV 淘汰若把某条线索的 token 误删、稀疏若把它漏看、线性若把它压糊，多跳就会断链。所以多跳是检验「压缩/近似有没有伤到长程组合能力」的利器——notebook 会构造一个变量追踪任务来演示。

把评测和前四模块连起来，全课就闭环了：RoPE 外推（01）、FlashAttention（02）、稀疏（03）、线性（04）、KV 压缩（本模块）每一项都可能在 NIAH/RULER 上留下指纹。外推没做好→长位置检索崩；稀疏窗口太小→窗外的针捞不到；线性状态太小→多跳断链；KV 淘汰太狠→被删 token 的信息丢失。评测不是附加题，而是检验你所有长上下文技术到底有没有用、代价可不可接受的唯一裁判。这就是为什么本课把它和压缩放在同一个收口模块——学会造尺子，和学会造杠杆同样重要。

7把杠杆组合起来：真实系统

把杠杆组合起来：真实长上下文系统

学完五个模块，回头看一个真实的长上下文系统是怎么把这些杠杆叠起来的：

一个生产级长上下文模型 / 服务的典型配方： 位置墙 → YaRN/dynamic-NTK 扩窗 (模块 01) 内存墙 → FlashAttention-2/3 算 prefill 注意力 (模块 02) 算力墙 → (可选) 滑窗+sink / 块稀疏 降复杂度 (模块 03) → (可选) 混合架构插入线性/SSM 层 (模块 04) KV 墙 → GQA/MQA(架构) + KV 量化(KIVI) + 淘汰(H2O/SnapKV) (模块 05) + PagedAttention 管理碎片 (C24) 验真 → NIAH 扫深度 + RULER 多跳，确认有效上下文 (模块 05)

这张配方表是全课的总纲：没有银弹，只有针对每道墙的、可叠加的、各有代价的杠杆。工程上的决策永远是「先吃免费的（FlashAttention、GQA），再按需上付费的（稀疏/线性/KV 淘汰），每上一项都用评测确认收益 > 代价」。

再把全课的「精确 vs 近似」这条暗线收一收，它是判断每个杠杆该不该上的总开关。精确的杠杆（FlashAttention、GQA）几乎是免费午餐——不损质量、纯赚，应当默认全开；近似的杠杆（位置外推、稀疏、线性、KV 淘汰/量化）都在用「一点质量」换「一些资源」，是否划算高度依赖任务，必须用 NIAH/RULER 量化那「一点质量」到底是多少。这就是为什么本课把评测放在最后、和压缩同一模块：所有近似杠杆的命运，最终都由那张大海捞针热力图和那条 RULER 随长度衰减曲线裁决。脱离评测谈压缩率、谈稀疏度、谈线性化，都是空中楼阁。

实践建议：默认配置 = YaRN（若需扩窗）+ FlashAttention + GQA，这套精确、稳妥，是大多数场景的起点；显存吃紧再加 KV 量化（通用、低风险）；还不够再考虑 KV 淘汰或稀疏（有损，需评测）；超长 + 吞吐优先才考虑线性/SSM 或混合架构。每一步都遵循同一条纪律——用 NIAH/RULER 量化代价，别让「省了显存」偷偷变成「看不见信息」。

8研究前沿与开放问题

研究前沿与开放问题

  • 压缩的极限：KV 能压到多狠而不伤下游？1bit KV、极端淘汰、动态预算分配（不同层/头给不同预算）是活跃方向。压缩率与任务表现的帕累托前沿仍在被推进。
  • 重要性判定的准确性：H2O 用「累积注意力」判重要，但当前不重要的 token 可能将来变重要（淘汰是不可逆的）。更好的、考虑未来的重要性预测是开放难题。
  • 评测的真实性：合成基准（NIAH/RULER）可控但不真实，真实基准（LongBench/L-Eval）真实但难控。如何评测「真实长文档任务」上的长上下文能力，仍无完美答案；∞Bench 把战线推到百万级。
  • 有效上下文的本质：为什么会 lost-in-the-middle？是位置编码、注意力机制、还是训练数据分布所致？理解它才能从根上扩大有效上下文，而非只扩名义窗口。
  • 压缩 × 其它杠杆的相互作用：KV 量化叠加稀疏、叠加外推、叠加线性，误差如何累积、评测如何变化，是系统层面的开放问题。
