1英语好 ≠ 对所有语言公平

我们评测一个语言模型时，绝大多数基准——MMLU、GSM8K、HumanEval、HELM 的主力榜单——都是英语的。于是一个隐蔽的默认假设悄悄成立了：英语上的分数代表模型的能力。但全世界 80 亿人里，以英语为母语的不到 5 亿；模型服务的用户横跨数千种语言，而它们在训练语料中的占比极不均衡。英语好，绝不等于对所有语言都公平——这是本模块的出发点。

跨语言的不公平有两副面孔，本模块都要量化。第一副是能力差距：同一个问题，模型用斯瓦希里语回答的准确率、校准、安全性可能远逊于英语。第二副更隐蔽，却影响每一次调用——成本与上下文的差距：由于tokenizer对不同语言的切分效率天差地别，同样一句话在某些语言里要花数倍的 token，于是这些语言的用户付更多的钱、还更早撞上上下文长度上限。前者是性能问题，后者是基础设施层面的结构性歧视。

要谈论这件事，先要有一把刻画语言资源不均的尺子。Joshi 2020 把世界语言按可用语料与工具分成 0–5 共六档：5 类是英语这样的赢家（海量语料、成熟工具、被所有模型重点优化）；0 类是大量被遗弃的语言（几乎没有数字语料、没有基准、没人测）。绝大多数语言落在 0–2 类，却服务着相当大的人口。这把尺子告诉我们：评测里看到的语言差距，很大程度上是训练数据分布不均的镜像。

把这种不均放到全球尺度看尤其刺眼：训练语料、学术论文、评测基准三者高度集中在不到 20 种语言上，而世界上有 7000 多种在用语言。Blasi 2022 系统地把各项语言技术的效用与对应语言的使用人口对照，发现技术红利与人口规模严重脱节——服务上亿人的语言可能在主流系统里几乎得不到支持。这意味着，当我们说一个模型 “多语能力强” 时，必须追问：强在哪些语言、覆盖了多少真实用户、最弱的那门语言差到什么程度。本模块教的每一个指标，最终都服务于把这三个追问变成具体数字。

直白说

一句话：模型不是对所有语言一视同仁。它在英语这种高资源语言上被反复打磨，在低资源语言上却又差、又贵、又没人测。评测的任务，就是把这三件事——差多少、贵多少、测没测——分别变成可以写进报告的数字。

严谨说

形式上，跨语言评测要回答两类问题：(i) 跨语言迁移（cross-lingual transfer）——在高资源语言上学到的能力，迁移到低资源语言上保留了多少？(ii) 分配公平——把同一份服务（按 token 计费、固定上下文窗口）施加到不同语言上，各语言用户承担的成本/受限是否相等？前者用分语言的性能指标度量，后者用 fertility 及其下游换算度量。

记住本模块的中心隐喻：tokenizer 是一道收费站。所有进出模型的文本都要被切成 token，而收费标准（每句话切成几个 token）对不同语言极不公平。高资源语言（尤其英语）走 VIP 通道，低资源语言（尤其非拉丁文字、形态丰富的语言）被层层加价。本模块前半段量化这道收费站的不公（fertility、成本、上下文），后半段量化能力本身的差距（翻译质量、跨语一致性）。

2tokenizer fertility 是什么

从词到 token：fertility 的定义

模型不直接读字符，而是读 token——由 BPE / SentencePiece 等子词算法切出来的片段。一个 tokenizer 是在某个语料上学出来的：高频片段（常见英语词、词缀）会被合并成单个 token，低频片段则被拆成更碎的小块。于是同一段语义，在不同语言里被切成的 token 数可以差好几倍。度量这件事的标准指标是 fertility（分词膨胀率）：

\[\text{fertility} = \frac{\#\,\text{tokens}}{\#\,\text{words}} \qquad\text{(每个词平均被切成多少个 token)}\]

fertility 越接近 1，说明这门语言的词大多能被整词命中；fertility 越大，说明词被切得越碎。对英语，fertility 通常在 1.1–1.5；对形态丰富（morphologically rich）的语言如芬兰语、土耳其语，一个词承载大量词缀，常被切成 3–5 个 token；对非拉丁文字（如印地语、阿拉伯语、泰语）以及训练语料稀少的语言，fertility 还会更高。也常用每字符 token 数（tokens/char）做归一化对比，避免词边界定义本身的歧义——中文这种没有空格分词的语言，用 tokens/char 比 tokens/word 更可比。

同一句 “All human beings are born free…”（世界人权宣言第 1 条）经某 GPT tokenizer： English ▏token ▏token ▏token ▏… 13 tokens (fertility ≈ 1.1) Spanish ▏tok▏tok▏to▏ken▏… 19 tokens (fertility ≈ 1.6) Swahili ▏to▏ke▏n▏to▏ken▏… 22 tokens (fertility ≈ 2.2) Finnish ▏t▏ok▏e▏n▏…（词缀被切碎） 30 tokens (fertility ≈ 3.3) Hindi ▏字▏节▏级▏回▏退▏…（非拉丁，常退到字节） 38 tokens (fertility ≈ 4.8) 同样一句话，英语 13 token，印地语 38 token —— 近 3 倍。

为什么低资源/非拉丁语言 fertility 高？根源在 tokenizer 的训练数据分布：合并表（merge table）是在以英语为主的语料上学的，所以英语的常见组合被优先合并成大 token，而其他语言的字符组合没机会被合并，只能退回到更小的单元，极端情况下退到单字节（byte fallback）——一个印地语字符在 UTF-8 里占 3 个字节，若 tokenizer 没学到它，就会被切成 3 个 token。这不是语言本身的属性，而是谁的数据进了 tokenizer 训练集的属性。

这里有一个常被忽略却至关重要的判别：fertility 高低衡量的是 tokenizer 的偏向，不是语言的 “复杂度” 或 “信息量”。同样一句 “人人生而自由” 的语义，在中文里字符极少、在芬兰语里词缀繁多，但它们承载的信息是等价的；fertility 的差异完全来自tokenizer 见过谁的文本更多。把高 fertility 误读成 “这门语言本来就难/啰嗦”，会把一个可修复的工程偏向（换更均衡的 tokenizer 就能缓解）错当成语言的固有命运，从而推卸了系统设计者的责任。评测要做的，正是把这种偏向定量地摆到台面上，证明它是设计选择而非天意。

3分词税：fertility 变成钱

分词税：fertility 如何变成真金白银的不公

fertility 不只是个学术数字。商用模型按 token 计费，也按 token 限制上下文。于是 fertility 高的语言，用户为完全相同的语义付出更多的钱——这就是 Ahia 2023 命名的 token premium（分词税）。

算一笔账：假设 API 报价 $0.01 / 1K tokens。一段英语内容 1000 token，成本 $0.01。同样语义的印地语版本若 fertility 是英语的 3 倍，就是 3000 token，成本 $0.03——贵了两倍。对一个母语为印地语、按月调用模型的用户/企业，这是一笔实打实、持续发生的额外开支，且完全由他们的母语决定，与内容价值无关。Ahia 2023 在真实商用 tokenizer 上测得，某些语言的成本可达英语的 4–5 倍以上。

语言（示例）相对 fertility同义内容 token 数相对 API 成本谁在买单
English（5 类）1.0×1000$0.010（基准）—
Spanish（5 类）≈1.5×1500$0.015+50%
Swahili（2 类）≈2.0×2000$0.020+100%
Hindi（3 类）≈3.0×3000$0.030+200%
某 0 类语言≈4–5×4000–5000$0.040–0.050+300–400%

这是一种分配性危害（allocational harm），而且特别隐蔽：它不在任何一次回答的内容里，而藏在计费和上下文这层基础设施中。一个只看输出质量的评测会完全错过它。要把它揪出来，必须显式测量各语言的 fertility，并把它换算到成本与上下文维度——这正是本模块 notebook 前三节做的事。

更糟的是这种不公的受害者分布：fertility 最高的，恰恰是低资源语言；而低资源语言的使用者，往往又是经济上更脆弱的群体。于是分词税叠加在既有的不平等之上——技术放大了社会差距，而非抹平它。这就是为什么 Blasi 2022 主张：评测语言技术时，必须把效用分布与使用人口对照着看，而不只看一个全球平均分。

4上下文不公

上下文不公：同样的窗口，不同的容量

分词税的第二个面孔在能力维度，而非价格。模型的上下文窗口是按 token 定的（如 8K、128K token）。fertility 高的语言，同样的 token 预算只能塞进更少的实际内容。Petrov 2023 把这称为 context-length inequity（上下文不公）。

还是用 3 倍 fertility 举例：一个 8192 token 的窗口，英语用户能放约 8192 / 1.1 ≈ 7400 个词的内容；印地语用户（fertility ≈ 3.3）只能放约 8192 / 3.3 ≈ 2480 个词——不到英语的三分之一。这意味着同一个 RAG 系统、同一个长文档摘要任务、同一段对话历史，低资源语言用户能利用的信息量被硬生生砍掉一大块。能力上限被母语决定了。

\[\text{可用内容（词）} \approx \frac{\text{上下文窗口（token）}}{\text{fertility}}\]

直白说

同一个 “128K 上下文” 的卖点，对英语用户是 128K，对某些语言用户实际只有 40K。纸面规格一样，到手容量缩水。这不是模型选择忽略内容，而是 tokenizer 在入口就让低资源语言更占地方。

严谨说

严格说，上下文不公 = fertility 不均在固定 token 预算下的直接推论。它同时影响推理延迟（更多 token → 更慢）、成本（见上节）与可达任务复杂度（更短有效上下文）。三者都源于同一个 fertility，所以测准 fertility 是这一切的起点。

一个评测陷阱：在固定 token 预算下做跨语言长上下文评测，若不校正 fertility，你其实是在拿英语的 7400 词对比印地语的 2480 词——低资源语言分数低，可能根本不是模型能力差，而是它被给的信息就更少。公平的做法是按内容量（词/字符）而非 token 预算对齐，否则你测出的差距里混入了 fertility 的污染，结论不可靠。

5翻译质量：BLEU vs chrF

翻译质量：BLEU、chrF 与 FLORES-200

跨语言能力最直接的考场是机器翻译。但翻译质量怎么自动打分？两个主力指标：BLEU 与 chrF。BLEU 比较候选译文与参考译文的 词级 n-gram 重叠（配 brevity penalty 惩罚过短译文）；chrF 比较 字符级 n-gram 的 F 值（精确率与召回率的调和平均）。

对本模块的主题，关键区别是：BLEU 对形态丰富语言不公平。BLEU 在词级匹配，而形态丰富语言一个词有大量屈折变体（同一个词根可以有几十种词尾），候选译文用了意思对但词尾不同的形式，BLEU 就判为完全不匹配，分数被系统性压低。chrF 在字符级匹配，能捕捉到词根一致、仅词尾不同的部分得分，因此对这类语言更稳、更公平。这正是 FLORES-200 等多语基准更偏好 chrF 的原因。

指标匹配粒度对形态丰富语言优点陷阱
BLEU词级 n-gram有偏（偏低）历史标准、广泛可比词级匹配惩罚合理的屈折变体；跨语言可比性差
chrF字符级 n-gram F更稳更公平无需分词、跨语言更可比对纯语义错误（用词错但字符相近）不够敏感
人工评分 / COMET语义/学习式最公平但贵贴近人类判断成本高、COMET 需模型与训练数据

FLORES-200（Meta 的 No Language Left Behind 配套）是这个领域的事实标准：同一组句子被专业译成 200 种语言，于是跨语言性能首次变得可比——因为内容完全对齐，分数差异只反映语言难度与模型能力，不混入测试集差异。在 FLORES 出现之前，各语言的翻译评测集来源五花八门、难度参差，所谓 “某语言翻译更差” 常常分不清是模型差还是测试集难；对齐的平行评测集把这个混淆变量消掉了，这本身就是评测基础设施对公平的贡献。本模块 notebook 会从零实现 chrF（它只需字符 n-gram 统计，纯 numpy/pandas 即可），并在几对译文上打分，再演示最差组聚合：报告所有语言里 chrF 最低的那一组，而不是平均分。

还要提醒一个自动指标的根本局限：BLEU、chrF 都只是和参考译文比字面重叠，它们不懂语义。一个意思完全正确但用词新颖的译文会被判低分，一个抄了参考大半词却意思跑偏的译文可能得高分。这就是 COMET 等学习式指标（用模型预测人类评分）兴起的原因。但学习式指标本身又带来新的公平问题——它们的训练数据同样偏向高资源语言，于是连 “评测翻译的工具” 都可能对低资源语言不公。这是负责任评测里一个递归的警示：度量工具不是中立的，评测低资源语言时连指标的偏向都要纳入怀疑。

为什么从零实现 chrF？因为它把一个评测指标的价值取向暴露得淋漓尽致：选词级还是字符级，本身就是在决定哪种语言被公平对待。指标不是中立的测量工具，而是带着假设的镜头——换个镜头，谁是赢家就变了。这是负责任评测反复出现的教训。

6公平聚合：平均分的陷阱

公平聚合：平均分是怎么骗人的

假设你在 100 种语言上测了模型，现在要汇报一个数字。最自然的选择——把所有语言的分数平均——恰恰是最危险的。因为高资源语言不仅分数高，在加权方式里还常常占主导。这里有两种平均，差别是价值判断：

聚合方式定义谁主导护谁适用
micro average 微平均按样本等权（所有样本汇总算一个指标）大语言（样本多）整体用户体验关心总体命中率时
macro average 宏平均按组等权（每种语言一票，再平均）各语言平等小语言关心语言间公平时
worst-group 最差组取所有组里最差的那个指标被抛弃的语言最弱势者关心下限/不漏掉任何群体

一个具体的数字陷阱：90 种语言得 0.9 分、10 种语言得 0.2 分。微平均若按样本量加权、而高分语言样本又多，可能报出 0.88 的漂亮分数；宏平均（每语言一票）则是 (90*0.9 + 10*0.2)/100 = 0.83；而最差组只有 0.2。三个数字描述同一个模型，却讲了三个完全不同的故事。报哪个，就是在替哪些人说话。

直白说

平均分像一张全家福里只露出最高的几个人。要看见被挡住的人，得要么给每个人同样的位置（宏平均），要么专门盯着最矮的那个（最差组）。负责任评测的默认动作：永远把最差组和宏平均一起报，不要只给一个总平均。

严谨说

形式上，micro 给每个样本权重 1，macro 给每个组权重 1，worst-group 取 min。三者在组规模均衡时趋同，在组规模极不均衡（多语场景的常态：英语样本可能是某低资源语言的上千倍）时分歧最大。选择哪种聚合 = 选择把方差更多归给样本还是归给群体，这是无法回避的价值表态。

这是全模块最该记住的一条：一个总平均分几乎总会掩盖低资源语言的崩盘。当你看到 “模型支持 100+ 语言、平均准确率 0.85” 这样的宣传，第一反应应该是问：最差的那种语言是多少？覆盖到的语言占目标用户的多少？没有最差组与覆盖度，平均分是营销，不是评测。

7跨语言一致性

跨语言一致性：同一个问题，不同语言会变卦吗

能力差距之外还有一类微妙的危害：跨语言不一致。把语义完全相同的问题用不同语言问模型，它给出的答案应该一致——尤其是事实题（“水的沸点是多少？”）和安全相关的请求。但实践中模型常常用英语拒绝、却用某低资源语言照答，或对同一事实给出互相矛盾的回答。这既是校准的跨语漂移，也是安全护栏的跨语漏洞。

怎么量化？给定一组平行问题（同一问题的多语版本）与模型的多语回答，可以测：(i) 一致率——多少比例的问题，各语言答案彼此一致；(ii) 答案分布的方差/熵——跨语言答案越分散，一致性越差；(iii) 对安全题，测拒答率的跨语方差——理想情况下应在所有语言上同样拒答有害请求，方差大说明护栏在某些语言上失效。

平行问题：“{有害请求}” 的多语版本，模型的拒答行为 English → 拒答 ✓ 护栏在英语上训练充分 Spanish → 拒答 ✓ Swahili → 照答 ✗ ← 漏洞！低资源语言上护栏失效 Hindi → 照答 ✗ ← 漏洞！ 拒答率：高资源 100%，低资源 0% —— 安全性的跨语言鸿沟

这类评测对安全尤其要命：攻击者只需把有害请求翻译成一个护栏薄弱的低资源语言，就可能绕过对齐——这是已被反复验证的越狱手法。所以跨语言一致性不是锦上添花的公平指标，而是安全评测必须覆盖的攻击面。notebook 的练习会让你从一组多语答案算出一致率与方差，把 “模型在不同语言上是否言行一致” 变成一个可监控的数字。

把一致性度量做扎实，还要求一组真正语义对齐的平行问题——这又绕回了 FLORES 式的对齐难题。如果多语问题本身是机翻来的，翻译错误会被误记为 “模型不一致”，让评测高估问题。因此严谨的跨语一致性评测，往往需要人工校核的平行问句，或在分析时把 “翻译噪声” 与 “模型变卦” 显式分开。一致性低到底意味着什么，取决于你能不能排除这层污染——这再次体现本课的总纪律：一个数字的含义，永远依赖你对它来源的诚实审视。

跨语言一致性低有两种可能解释，评测时要分清：(i) 模型能力在低资源语言上确实不足（答错而非故意）；(ii) 模型护栏在低资源语言上没覆盖（该拒不拒）。前者是性能问题，后者是安全漏洞，缓解手段完全不同。只报一个 “一致率 70%” 而不拆开这两者，会误导后续决策。

8研究前沿与开放问题

研究前沿与开放问题

  • tokenizer 公平化：能否设计对所有语言 fertility 更均衡的 tokenizer（如按语言均衡采样训练语料、字节级模型 ByT5、或动态合并）？代价是英语效率下降——这又是一个公平/效率权衡，最优点取决于服务的人口。
  • 低资源评测的鸡生蛋：要测低资源语言就需要该语言的高质量评测集，但低资源语言恰恰缺评测集。用机翻造评测集会引入翻译伪影（translationese），污染结论；人工标注又昂贵。如何低成本造可信的多语基准是开放难题。
  • 跨语言安全对齐：如何让安全护栏可靠地迁移到训练中几乎没见过的语言？当前对齐高度偏向高资源语言，多语红队（multilingual red-teaming）的覆盖度远远不够，低资源语言越狱仍是现实威胁。
  • 聚合标准的缺失：多语评测该默认报宏平均、最差组还是分层报告？社区尚无公认规范，导致不同论文的 “多语性能” 不可比。把最差组 + 覆盖度 + 分语言明细定为多语模型卡的强制项，是评测社区可直接推动的事。
  • 效用 × 人口的影响评估：Blasi 2022 主张把性能与使用人口对照，但 “某语言差 0.2 分” 到底影响多少人、多严重，缺乏标准的社会影响度量。把评测数字接到真实人口与场景，是从 “基准分” 走向 “社会影响评测” 的关键一步。

必读：Ahia 2023（分词税的成本量化）、Petrov 2023（tokenizer 跨语不公与上下文）、Joshi 2020（语言资源分层）、Blasi 2022（效用的全球不均）、NLLB/FLORES-200（可比的多语基准）。完整清单见 references.md。
