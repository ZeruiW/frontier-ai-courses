1重复 prefill 的浪费

模块 01 我们用 copy-on-write 让两个共享前缀的序列零拷贝地共用 KV 块。本模块把这件事推到极致并系统化：当成千上万个请求反复带着相同的前缀涌来时，我们不仅要共享 KV 的存储，更要彻底跳过对这些前缀的重复计算。

先看清浪费有多普遍。现实里的 prompt 极少是彼此无关的随机串，它们大量共享前缀：

  • 公共 system prompt：同一个服务的所有请求往往带同一段几百到上千 token 的系统指令（角色设定、安全规则、工具说明）。
  • few-shot 示例：同一个任务的所有请求带同一组示例，动辄数千 token，每个请求都把它重算一遍。
  • 多轮对话历史：第 k 轮请求的前缀 = 前 k−1 轮的全部内容；同一会话里每一轮都把之前所有轮重新 prefill一次。

直白说

这些共享前缀的 K、V 是逐位相同的——同样的 token、同样的位置、同样的权重，算出来必然一样。为它们各算各的、各存各的，是在把昂贵的 prefill 算力和宝贵的显存大把大把地烧掉。

严谨说

形式化地说：注意力的 K、V 是输入前缀的确定性函数。若两个请求的前 L 个 token 完全相同，则它们前 L 个位置的 KV 完全相同。于是这部分 prefill 是可记忆化（memoizable）的纯计算——经典的「用缓存换重算」场景。

代价直接落在 TTFT 上。回忆模块 00：TTFT（首 token 延迟）主要由 prefill 决定。一个带 2000 token 公共前缀的请求，若每次都从头 prefill，用户就得为这 2000 token 的计算白等一次；而如果前缀已被缓存，prefill 只需处理那几十个新增的 token，TTFT 可以从几百毫秒掉到几十毫秒。

一句话抓住本模块前半：共享前缀的 KV 是确定性的、可缓存的；缓存它就能跳过重复 prefill，直接砍 TTFT。难点不在「能不能缓存」，而在「如何自动、跨请求、细粒度地发现并复用任意公共前缀」——这正是 RadixAttention 要解决的，也是本模块后半 PD 分离的伏笔：prefill 省下来了，decode 的瓶颈就更突出，于是想把两阶段拆开各自优化。

2Prefix Cache 与命中

Prefix Cache：缓存前缀的 KV，命中即跳过 prefill

prefix cache（前缀缓存）的机制朴素而有力：把已经算过的前缀连同它的 KV 存起来；新请求到达时，先查它的 prompt 有多长一段前缀命中了缓存，命中的部分直接复用 KV、跳过 prefill，只对未命中的剩余 token 做 prefill。

于是一次请求的 prefill 工作量从「处理整个 prompt」变成「只处理新增后缀」。定义prefix hit rate（前缀命中率）为命中 token 数 ÷ prompt 总 token 数，则：

\[\text{需要 prefill 的 token} = (1-\text{hit\_rate})\times L_{\text{prompt}},\qquad \text{省下的算力} \propto \text{hit\_rate}\times L_{\text{prompt}}\]

命中率越高，省下的 prefill 越多、TTFT 越低。在多轮对话里命中率尤其惊人：第 k 轮的前缀几乎全是前 k−1 轮，命中率随轮数趋近 1，意味着除了最新一轮的输入，几乎不用再 prefill 任何东西。

直白说

把它想成函数的记忆化：第一次算 f(前缀) 时把结果存进字典，以后凡是同样的前缀直接查字典返回。区别只在于这里的「键」是变长的 token 序列、且我们想匹配的是最长的那段公共前缀，而不仅仅是「整段完全相同」。

严谨说

正因为要匹配最长公共前缀（而非整串相等），朴素的「prompt 字符串 → KV」哈希表是不够的：它只能命中完全相同的 prompt，无法让「前 1900 token 相同、后 100 token 不同」的两个请求共享那 1900。我们需要一个能做最长前缀匹配的数据结构——前缀树。

前缀缓存不是免费的：缓存的 KV 也占显存，缓存越多、留给运行中请求的 KV 越少。所以前缀缓存必须配淘汰策略（哪些前缀该被踢出去腾地方）和引用计数（正在被某请求使用的前缀不能踢）。这把我们引向一个能同时支持「最长前缀匹配 + 共享 + 带引用计数的淘汰」的统一结构。

3RadixAttention 与前缀树

RadixAttention：用基数树自动复用前缀

RadixAttention（SGLang 提出）的核心洞察是：把所有请求的 KV 统一组织成一棵 radix tree（基数树 / 压缩前缀树），让公共前缀自然地对应树上共享的路径。这样前缀复用变成自动、跨请求、细粒度的——程序员什么都不用声明。

它的工作方式：每条从根到某节点的路径，就是一个被缓存的前缀；这条路径上挂着对应的 KV 块。新请求到达时，拿它的 token 序列从根开始沿树往下走，能走多远就复用多远（这就是最长前缀匹配）；走不动了，就从该节点长出一条新分支存放未命中部分的 KV。

radix 前缀树：公共前缀 = 共享路径（[..] 是一条边携带的 token 段） (root) │ [You are a helpful assistant.] <- 公共 system prompt，所有请求共享 (node A) ┌───┴─────────────┐ [Translate to French:] [Summarize:] <- 两类任务在此分叉 (node B) (node C) │ [Hello] │ [The cat...] (leaf B1) (leaf C1) 新请求 “You are a helpful assistant. Translate to French: Bye”: 从 root 走 A(命中 system) -> B(命中 Translate) -> 在 B 后命中 [Hello] 失败， 在 B 处长出新边 [Bye]。只需 prefill “Bye”，其余全部命中复用。

「radix（基数）压缩」指的是：树的一条边可以携带多个 token（一整段没有分叉的序列压成一条边），而不是每个 token 一个节点。这让树又浅又省内存。当一条边的中间出现分叉（新请求只匹配了这条边的前一半）时，就把这条边从中间裂开（split）成两段，在裂点处分叉——这是 radix 树插入的关键操作。

直白说

和模块 01 的 CoW 是什么关系？CoW 是微观机制：两个序列共享某几个物理块、写时分叉。RadixAttention 是宏观机制：用一棵树自动发现「哪些请求该共享哪段前缀」，再调用块级共享 + 引用计数去落实。前者是积木，后者是用积木自动搭楼的建筑师。

严谨说

淘汰用带reference count的 LRU eviction：每个被请求正在使用的前缀路径，其节点引用计数 > 0，不可淘汰；缓存满时，从引用计数为 0 的叶子里挑最久未访问的删除（删叶子才不会切断别人还在用的前缀）。这保证「正在服务的前缀绝不被踢」，同时回收无人使用的旧前缀。

RadixAttention 出自 Zheng et al. 2024（SGLang）。它把模块 01 的块级共享，升级成由前缀树驱动的、跨请求自动前缀复用，是结构化 LLM 程序（多轮、并行、分支）高效执行的基石。细节见 references.md 的 SGLang 条目。

4radix 树：插入与最长前缀匹配

radix 树：插入与最长前缀匹配

把 RadixAttention 的数据结构讲到能动手写。核心是两个操作：最长前缀匹配（查）与插入（增）。先定义最长前缀匹配——它必须等价于暴力前缀匹配，这是本模块 notebook 的核心不变量。

暴力版很简单：对缓存里每一个已存序列，逐位比较它与 query 的公共前缀长度，取最大值。这是 ground truth：

\[\text{match\_len}(q)=\max_{s\in\text{cache}}\ \big|\text{lcp}(q,\ s)\big|,\quad \text{lcp}= \text{最长公共前缀}\]

树版要在一棵 radix 树上得到同样的答案，但只需 O(匹配长度) 而非遍历整个缓存。匹配过程是：从根开始，看哪条出边的 token 段是 query 当前位置的前缀，命中就顺着走、累加匹配长度，并在一条边内做逐 token比较（边可能只匹配一部分）；走到无法继续就停，返回累计的匹配长度。

# radix 树最长前缀匹配（伪代码）——返回匹配长度，应等于暴力 lcp
def match_prefix(root, q):
    node, i = root, 0
    while i < len(q):
        child = node.children.get(q[i])      # 用首 token 索引出边
        if child is None:
            break                            # 没有以 q[i] 开头的边 -> 停
        edge = child.tokens                  # 这条边携带的 token 段
        j = 0
        while j < len(edge) and i < len(q) and edge[j] == q[i]:
            i += 1; j += 1                   # 在边内逐 token 比对
        if j < len(edge):
            break                            # 边只匹配了一部分 -> 停在边中间
        node = child                         # 整条边匹配 -> 进入下一节点
    return i                                 # 累计匹配的 token 数

插入则在匹配停下的位置接着做：若停在某条边的中间（只匹配了边的前 j 个 token），就把这条边裂成两段（前 j 个 token 一段、剩下的一段），在裂点建一个分叉节点，再把 query 的剩余后缀作为新边挂上去；若恰好停在某节点上，直接从该节点长出一条携带剩余后缀的新边。

为什么坚持「树版 == 暴力版」？因为 radix 树的全部价值是加速（把 O(缓存总量) 的匹配降到 O(匹配长度)），它绝不能改变匹配结果——否则就会复用错前缀、读到别人的 KV，悄悄改变输出。notebook 会对大量随机 query 断言两者逐字相等，这就是数据结构正确性的铁证。

5PD 分离的动机

PD 分离：prefill 与 decode 拆到不同 GPU

前缀复用把重复 prefill 砍掉后，我们换个视角看整座引擎。模块 00 讲过：prefill 算力受限、decode 带宽受限，两者性格迥异。把它们放在同一块 GPU 上混跑，会互相伤害。

直白说

一个长 prompt 的 prefill 占满了算力，正在逐 token 生成的请求就得排队等它算完——它们的 TPOT 被一次大 prefill 狠狠拖高，用户看到「打字机突然卡住一下」。反过来，为了照顾 decode 的延迟而限制 prefill 批量，又浪费了 prefill 的算力。一块 GPU 同时讨好两种负载，谁都讨好不好。

严谨说

这叫 prefill–decode interference（预填充-解码干扰）。模块 02 的 chunked prefill 是一种缓解（把长 prefill 切碎插空），但治标不治本——两阶段仍在抢同一份算力与带宽。更彻底的办法是物理隔离：让它们根本不在同一块 GPU 上。

PD disaggregation（prefill–decode 分离，DistServe 提出）就是这个彻底方案：把集群里的 GPU 分成两个池——prefill 实例专做 prefill（追求高算力利用、可大批量），decode 实例专做 decode（追求高带宽、大 batch、稳定低 TPOT）。请求先到 prefill 实例算出 prompt 的 KV，再把 KV传给 decode 实例继续逐 token 生成。

colocate（混跑） vs disaggregate（分离） colocate: [GPU] prefill 和 decode 抢同一块卡 -> 长 prefill 卡住 decode，TPOT 抖动 disaggregate: 请求 ─▶ [Prefill 池] 算出 prompt KV ──KV 传输(NVLink/RDMA)──▶ [Decode 池] 逐 token 生成 算力受限、可大批 带宽受限、大 batch、TPOT 稳 好处：两阶段各自独立优化、独立扩缩容；prefill 不再干扰 decode 的 TPOT

分离还带来一个常被忽视的好处：两阶段可以用不同的并行策略与硬件。prefill 算力受限，适合用更激进的张量并行把一次大矩阵乘摊到多卡、追求低延迟；decode 带宽受限，适合用更大的 batch 和更省带宽的并行方式。混跑时这两套策略只能二选一（同一组 GPU 上的模型切分是固定的），分离后则各取所需——这是「专池专用」在并行维度上的延伸。

分离的代价是多了一次 KV 传输（把 prefill 算出的 KV 从一个池搬到另一个池）。它划不划算，取决于传输开销是否远小于「混跑干扰带来的延迟损失」——在长 prompt、高并发场景下通常划算，这也是 DistServe 用 goodput（满足 SLO 的吞吐）而非裸吞吐来衡量收益的原因：分离的目标不是把某个数字单纯做大，而是让更多请求同时满足 TTFT 和 TPOT 的承诺。一个裸吞吐很高、却让一半请求 TPOT 超时的系统，goodput 可能还不如一个吞吐略低但人人达标的系统——这正是分离要纠正的偏差。

6KV 传输与资源配比

KV 传输与资源配比

PD 分离要回答两个量化问题：KV 传输的代价多大？prefill 与 decode 实例该按什么比例配？

先看KV 传输。prefill 实例算完一个请求，要把它整段 prompt 的 KV（大小 ≈ 模块 01 的公式：2 × L × H_kv × d_head × prompt_len × bytes）经 NVLink / RDMA 搬到 decode 实例。传输时间 ≈ KV 字节 ÷ 互连带宽。只要这个时间远小于 prefill 本身、且能与计算重叠（边算边传），它就被很好地隐藏。

这里有个关键的工程技巧：KV 是逐层算出来的，所以可以逐层流式传输——prefill 实例算完第 1 层的 KV 就立刻开始传它，同时继续算第 2 层，让传输与计算流水线重叠。这样 KV 传输几乎不增加端到端延迟，是 PD 分离在实践中可行的关键。反过来，若互连带宽太低（如跨节点走慢速网络），传输就盖不住、成为新瓶颈，分离反而变慢——所以 PD 分离通常要求 prefill 与 decode 实例之间有高速互连（同机 NVLink 或 RDMA）。

KV 传输 = 分离的生死线

把 KV 传输的账算到具体数字上就明白它为何是 PD 分离的生死线：一个 Llama-3-70B、prompt 长 4096 的请求，其 KV ≈ 2×80×8×128×4096×2 ≈ 1.3 GB。走同机 NVLink（数百 GB/s）传它只要几毫秒、轻松藏进 prefill；可一旦跨节点走普通以太网（几 GB/s），同一份 KV 要传上百毫秒——这比整个 decode 还久，分离非但不加速，反而凭空给每个请求加上一截致命延迟。所以 PD 分离的前提是高速互连，且 KV 与计算流水重叠；脱离这个前提谈分离，等于把瓶颈从「两阶段干扰」搬到了「跨机搬 KV」，得不偿失。

再看资源配比（PD ratio = prefill 实例数 ∶ decode 实例数）。配比的原则是让两个池的吞吐相匹配：单位时间里 prefill 池能处理的请求数，应约等于 decode 池能消化的请求数，否则一边堆积、一边空闲。用一个简单的平衡式刻画：

\[\frac{N_P}{N_D}=\frac{\lambda\cdot L_{\text{prompt}}/r_P}{\lambda\cdot L_{\text{gen}}/r_D}=\frac{L_{\text{prompt}}/r_P}{L_{\text{gen}}/r_D}\]

其中 N_P, N_D 是两池实例数、λ 是请求到达率、L_prompt / L_gen 是平均 prompt / 生成长度、r_P / r_D 是单实例的 prefill / decode 速率（token/s）。直觉：一个请求在 prefill 上要花的时间 ∝ prompt 长度 ÷ prefill 速率，在 decode 上要花的时间 ∝ 生成长度 ÷ decode 速率；两池实例数之比，就该等于这两个时间之比，才能让请求在两池间顺畅流动、谁都不成瓶颈。

直白说

打个比方：prefill 池是「备菜区」、decode 池是「炒菜区」。如果每道菜备菜要 2 分钟、炒菜要 6 分钟，那炒菜区就得是备菜区的 3 倍人手，否则备好的菜堆在传菜口、炒菜区却忙不过来。配比就是让两个工序的产能对齐。

严谨说

现实更复杂：prompt/生成长度是分布而非定值、到达率随时间波动、KV 传输也占带宽。所以生产系统会动态调配比（按实时负载在两池间迁移 GPU），而非用一个静态比例。但上面的平衡式是一切动态策略的出发点——先算出静态最优，再围绕它做反馈调节。

PD 分离不是万灵药：当 prompt 很短（prefill 本就便宜）、或互连带宽不足（KV 传输成了新瓶颈）、或请求量小不够填满两个池时，分离的额外传输与碎片化反而得不偿失。它是大 prompt、高并发、SLO 严苛场景下的利器，而非默认选择——是否分离本身就是一个要按负载权衡的决策。

7SLO 分解：TTFT/TPOT 映射资源

SLO 分解：把 TTFT/TPOT 映射到资源

把前后两半（前缀复用 + PD 分离）统一到一个框架下：服务的承诺是 SLO，通常拆成两个延迟指标，而它们恰好一一对应两个阶段：

SLO 指标由哪个阶段决定压低它的手段（本课）
TTFT 首 token 延迟prefill前缀复用（跳过重复 prefill）、chunked prefill、PD 分离的 prefill 池专门优化
TPOT 单 token 延迟decode大 batch 摊薄权重、投机解码（模块 03）、量化（模块 05）、PD 分离让 decode 不被 prefill 干扰

于是「满足 SLO」被分解成两个可分别下手的子问题：想压 TTFT，就在 prefill 这一侧做文章（缓存、切块、专池）；想压 TPOT，就在 decode 这一侧做文章（批量、投机、量化、隔离）。PD 分离的深层价值正在于此——它把两个本来纠缠在一起的 SLO 指标解耦，让你能独立地为各自配资源、各自达标，而不必在同一块 GPU 上做令人头疼的折中。

维度Colocate（混跑）Disaggregate（分离）
TPOT 稳定性差（被长 prefill 周期性打断）好（decode 池不受 prefill 干扰）
资源利用单池简单，但两负载互相迁就两池各自打满，但需 KV 传输
扩缩容只能整体扩两阶段独立扩缩容
适用中小规模、短 prompt、负载均衡大规模、长 prompt、SLO 严苛

notebook 会把这套 SLO 账算清：给定负载（到达率、prompt/生成长）与两池速率，算出满足 TTFT/TPOT 所需的配比；再对比 colocate 与 disaggregate 下 decode 的 TPOT 稳定性，亲眼看到分离如何把 prefill 对 decode 的干扰消掉。这呼应全课的账本方法论——把系统收益还原成可断言的数字。

8研究前沿与开放问题

研究前沿与开放问题

  • KV 池化与跨实例共享：把前缀 KV 从单实例的树提升为集群级的KV 池（如 Mooncake），让任意实例、任意会话、甚至跨节点共享同一份前缀 KV，并做分级存储（GPU/CPU/远端）与按热度迁移——这是把 RadixAttention 从单卡推广到数据中心。
  • 缓存淘汰与命中率的博弈：在显存有限下，如何在「多缓存前缀以提命中率」与「多留显存给运行请求以提 batch」之间动态权衡？带引用计数的 LRU 只是起点，按前缀复用频率、长度、计算成本的代价感知淘汰仍是开放问题。
  • PD 配比的动态自适应：真实负载的 prompt/生成长度分布与到达率时刻在变，静态配比必然次优。如何用实时反馈在 prefill/decode 两池间无缝迁移 GPU、并平滑处理迁移期的 KV，是分离式服务的核心难题。
  • 与投机/量化的叠加：前缀复用、PD 分离、投机解码（模块 03）、KV 量化（模块 05）是正交的加速维度，但叠加时彼此影响（如量化的 KV 还能否被前缀树精确匹配、投机解码在分离架构下如何放置 draft 模型），联合优化是活跃方向。
