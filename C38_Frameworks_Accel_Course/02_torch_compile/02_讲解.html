1eager 的天花板：为什么要编译

模块 01 你写出了 autograd——它工作在即时执行（eager）模式下：每写一个算子就立刻执行、立刻拿到结果。这是 PyTorch 多年的默认，灵活、好调试。但它有一个根本的性能天花板，理解这个天花板，就理解了 torch.compile 为什么存在。

eager 模式的问题在于它一次只看见一个算子。当你写 y = (a + b).relu() * c，框架依次启动三个内核：一个做加法、一个做 relu、一个做乘法。每个内核都要从主存读入输入、写回中间结果，下一个内核再读回。可这中间结果（a+b 和它的 relu）根本没必要落主存——它本可以一直待在寄存器里，被下一步直接消费。eager 看不到「下一步」，所以省不掉这些往返。

直白说

打个比方：eager 像一个只听一句、做一句的厨工——你说「切洋葱」他切完放下，你说「炒洋葱」他再拿起来。他从不提前知道整道菜的流程，所以没法把「切完直接下锅」连起来，白白多了无数次拿起放下。而编译器像看过整张菜谱的大厨，能把能连的步骤融合成一气呵成的动作。

严谨说

形式上：eager 模式下每个算子是一次独立的内核启动，中间张量在 HBM（主存）来回读写。回忆 C36/模块 00 的脊点——逐元素算子是访存受限的，时间几乎全花在这些读写上。把一串逐元素算子融合成一个内核，中间结果留在片上、不落 HBM，就能把 k 次往返压成 1 次。这是编译器最重要、最普适的优化。

一句话讲清 torch.compile 的价值：它把你的一段 Python 函数「整体看一遍」，捕获成一张计算图，再在图上做融合、常量折叠、死代码消除等优化，最后生成少数几个高效内核——用图模式的全局视野，补上 eager「只见树木不见森林」的损失。本模块就用 numpy 写一个玩具版：先 trace 出图，再在图上做这些优化 pass，并验证优化前后结果不变。

要强调的是：torch.compile（PyTorch 2.0 引入）的设计目标是既要图模式的性能、又尽量不丢 eager 的易用性。它不要求你重写代码，只在你的函数外包一层 torch.compile(fn)，第一次调用时自动捕获、编译，之后复用。这种「默认 eager、按需编译」的折中，正是它与早期纯静态图框架（TF 1.x）的关键区别，也是模块 03 JAX 函数式路线的对照。

给个量级感受 eager 浪费在哪。一个逐元素链 y=(a+b).relu()*c（设张量 N 个元素、fp32）：eager 下 add 读 2N 写 N、relu 读 N 写 N、mul 读 2N 写 N——总共约 8N 次主存读写、3 次内核启动。融合成一个内核后，只需读 a,b,c 共 3N、写 y 共 N——4N 次读写、1 次启动。对访存受限的逐元素算子，读写次数减半≈速度翻倍；内核启动从 3 降到 1，又省掉两次启动开销（对小张量，启动开销甚至能主导）。一个简单的融合，同时打了访存受限和开销受限两类瓶颈——这就是编译器最日常、最普适的收益。

2两种捕获：tracing vs scripting

两种捕获方式：tracing vs scripting

要在图上优化，第一步得先把「一段会执行算子的代码」变成「一张静态的图」。这一步叫图捕获，有两条根本不同的路线：

方式怎么捕获优点致命弱点
tracing 追踪用具体输入实际跑一遍，记录所经过的算子序列实现简单、只记真实走过的路、天然支持任意算子把数据相关的控制流烤死：if/循环只记录本次走的分支；看不到 Python 副作用
scripting 脚本化解析源代码（AST），把程序结构直接翻译成图保留 if/for 等控制流，覆盖更全只支持 Python 的一个子集；实现复杂、报错晦涩

用一个例子看清差别。设函数里有 if x.sum() > 0: return x*2 else: return x*3。tracing用某个具体 x 跑一遍：若这次 x.sum()>0，它只会记下 x*2这一条路，得到的图永远走 *2，即使下次传入负的 x 也错；它看不见那个 if，因为 Python 的 if 在 trace 时已经被求值掉了。而 scripting读源码，能把 if 本身翻译进图，保留分支语义。

直白说

记住一句话：tracing 记录的是「这一次具体执行」，scripting 翻译的是「代码本身」。tracing 像给一次烹饪过程拍延时摄影——拍到什么是什么，临场决定（控制流）就丢了；scripting 像把菜谱逐字翻译成另一种语言——结构都在，但只能翻译它认得的句式。

严谨说

现代实践的答案是两者结合 + 优雅回退。torch.compile 的前端 TorchDynamo 以 tracing 为主（在 CPython 字节码层拦截），但遇到无法 trace 的部分（数据相关分支、外部调用、打印）就graph break——把图在此切断、那一段退回 eager 执行、之后再开新图。这让它既能编译大部分热代码，又不会因为一句 print 就整个失败。JAX 则要求你用 lax.cond/lax.scan 显式写控制流（模块 03）。

本模块的玩具编译器走 tracing 路线（最能讲清「捕获成图」的本质，也是 Dynamo/JAX 的主路）。我们会重载算子，让它们在执行的同时把自己记录进一张图，而不是直接算出数值——这正是 tracing 的核心机制：用「记录」替换「执行」。理解了这一步，你就理解了为什么 tracing 看不见 Python 控制流——因为被记录的只有你的算子，不包括 Python 的 if。

3IR：图长什么样

IR：图到底长什么样

捕获出来的图，存成什么数据结构？这就是IR（中间表示）——介于你的源码与最终内核之间的、便于分析和变换的形式。深度学习编译器的 IR 通常是算子级的有向无环图：

  • PyTorch 的 torch.fx：把模块 trace 成一张 GraphModule，节点是 call_function/call_module/placeholder（输入）/output，可用 Python 直接遍历和改写。
  • JAX 的 jaxpr：把纯函数表示成一串带显式输入输出的 primitive 方程，可打印（jax.make_jaxpr(f)）——模块 03 会看它。
  • XLA 的 HLO：更靠近硬件的中层 IR，XLA 在其上做融合、布局、内存规划。

不管哪种，IR 的共同形态都是「一串带编号的指令，每条说明：用什么算子、吃哪些前序结果、产出什么」。这其实就是编译原理里的三地址码 / SSA在张量世界的版本。我们的玩具 IR 也长这样：

# 玩具 IR：每个 Node = (输出名, 算子, [输入名...], 可选常量)
# 源程序: y = relu(a + b) * 2.0
%0 = placeholder 'a'
%1 = placeholder 'b'
%2 = add        %0, %1
%3 = relu       %2
%4 = mul        %3, const(2.0)
%5 = output     %4

把程序变成这种显式的指令列表 + 依赖关系，是一切图优化的前提。因为现在「哪个值被谁用」「哪个子表达式是常量」「哪个节点没人要」都一目了然、可程序化判定了——而在原始的 Python 代码里，这些信息是隐式的、要靠分析才能得到。本模块 notebook 会从零定义这个 IR、写一个 tracer 生成它，然后在它上面跑三个经典优化 pass。

一个值得点明的设计选择：这种 IR 几乎都是 SSA（静态单赋值）形式——每个值只被赋值一次（%0,%1,%2… 各出现一次在等号左边）。为什么？因为 SSA 让「这个值是从哪来的」有唯一确定的答案（没有变量被反复覆盖的歧义），于是数据流分析（谁依赖谁、常量怎么传播、死代码是谁）变得极其干净——这是几十年编译器经验沉淀下来的形式，张量图直接继承了它。我们玩具 IR 的「每个节点一个新名字、永不复用」就是 SSA 的体现，正是它让后面三个 pass 能用十几行写清楚。

为什么编译器要先转成 IR 再优化，而不直接改源码？因为源码有太多与计算无关的噪音（变量名、临时表达式、语法糖），而 IR 是规范化的——同一个计算无论你怎么写，都归一成同样的节点序列。在规范形式上，「两个子图是否相同」「这个节点是否可删」这类问题才有干净的答案。IR = 把计算剥到只剩骨架，正好呼应本课「numpy 复刻只留骨架」的方法论。

4优化 pass 一：算子融合

优化 pass 之一：算子融合

有了图，第一个、也是最值钱的优化是operator fusion（算子融合）：把多个相邻算子合并成一个内核，中间结果不落主存。最经典的是逐元素链融合——一串逐元素算子（add、mul、relu、exp……）可以合并成一个「对每个元素依次做这串运算」的内核，全程只读一次输入、写一次输出。

融合前（eager）：3 个内核，中间结果两次落主存 [add]──写t1──>[relu]──写t2──>[mul]──>out 读写主存 ~ 6 次张量大小 融合后：1 个内核，中间结果留在寄存器 [add;relu;mul]──>out 读写主存 ~ 2 次张量大小 对每个元素: out[i] = relu(a[i]+b[i]) * c[i] 一次读入、一次写出

融合的收益直接来自模块 00 的瓶颈三分法：逐元素算子是访存受限的，其时间几乎全花在主存读写上。把 k 个逐元素算子融成 1 个，中间 k-1 个张量的读写就省了——理论上可接近 k 倍加速。这也是 FlashAttention（C36）的灵魂：它本质就是把注意力的一长串算子融成一个内核、避免 n×n 中间矩阵落主存。

直白说

融合能合并的，主要是逐元素和某些规约算子（它们的「单元素工作」能拼接）。两个大矩阵乘之间通常不能简单融合（各自是复杂的分块内核），但 matmul 之后紧跟的逐元素操作（加偏置、激活）几乎总能融进 matmul 的尾部（epilogue fusion）。

严谨说

融合的边界由数据依赖与算子类型决定。一个安全的融合规则：若节点 B 的唯一消费链都是逐元素、且 B 的输入形状相容，则可把 B 融入其生产者。真实编译器（Inductor）的融合规则复杂得多（要考虑内存复用、寄存器压力、规约的特殊性），但核心判据都是「中间结果能否不落主存」。

本模块 notebook 会实现一个最小的融合 pass：识别图中连续的逐元素算子链，把它们打包成一个fused_elementwise节点，并验证融合后求值与融合前逐位相同（融合只改执行方式，绝不改语义）。你会亲手看到「3 个节点变成 1 个、结果不变」——这正是 torch.compile 在 GPU 上自动做的事（生成一个 Triton 内核替代三次内核启动）。

那个被自动生成出来的内核长什么样？给个旁注：torch.compile 把 relu(a+b)*c 这条逐元素链编译成的 Triton 内核，骨架就是「每个线程取一组元素、在寄存器里把三步连着算完、只写一次」——和我们玩具 fused_elementwise 节点的语义一模一样，只是落到了 GPU 上：

# torch.compile 为逐元素链生成的 Triton 内核（简化示意）
@triton.jit
def fused_add_relu_mul(a_ptr, b_ptr, c_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid  = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)   # 本线程块负责的元素下标
    mask = offs < n
    a = tl.load(a_ptr + offs, mask=mask)        # 各读一次（进寄存器）
    b = tl.load(b_ptr + offs, mask=mask)
    c = tl.load(c_ptr + offs, mask=mask)
    t = tl.maximum(a + b, 0.0) * c              # 三步全在寄存器里连算，中间不落 HBM
    tl.store(out_ptr + offs, t, mask=mask)      # 只写一次

看 load/store 的次数就懂了收益从哪来：三次 load、一次 store（4N 访存），中间的 a+b 和它的 relu 从不离开寄存器。这正是把玩具图优化「中间结果不落主存」这条原则，落实到一段真实可跑的 GPU 代码上——你写的 numpy 融合 pass，工业级对应物就是这种自动生成的 Triton。

5优化 pass 二三：常量折叠与 DCE

优化 pass 之二、之三：常量折叠与死代码消除

融合之外，还有两个朴素但通用的图清理 pass，它们来自经典编译原理、在张量图上同样适用：

常量折叠 constant folding

如果一个子表达式只依赖常量，那它的值在编译期就能算出来，运行时不必重复计算。例如图里有 c = 2.0 * 3.0，折叠后直接把 c 替换成常量 6.0，删掉那个乘法节点。在深度学习里，缩放因子、形状推导、1/sqrt(d) 这类常量运算都能在编译期折掉。

死代码消除 dead code elimination (DCE)

如果一个节点的产出没有被任何输出依赖（直接或间接），它就是死代码——算了也没人用，可以删。死代码常在融合、折叠之后冒出来（某些中间节点被绕过后就成了孤儿），所以 DCE 通常作为优化的收尾 pass反复跑。判定方法很干净：从 output 节点反向标记所有可达节点，没被标记的全删。

# 三个 pass 串起来（本模块 notebook 实现）
graph = trace(fn, example_inputs)   # 1. 捕获成 IR
graph = constant_fold(graph)        # 2. 编译期算掉纯常量子图
graph = fuse_elementwise(graph)     # 3. 融合逐元素链
graph = dead_code_elim(graph)       # 4. 删没人用的节点
assert eval_graph(graph, inputs) == fn(inputs)   # 语义不变！
优化的铁律

所有图优化都必须遵守一条铁律：优化只能改「怎么算」，绝不能改「算出什么」。融合后的结果、折叠后的结果、删掉死代码后的结果，都必须与原图逐位一致（浮点误差内）。一个改变了语义的「优化」是 bug，不是优化。所以本模块每个 pass 之后都立刻assert eval_graph(优化后) == eval_graph(原图)对拍——这正是真实编译器测试的核心纪律（差分测试）。

这三个 pass（融合、折叠、DCE）加上公共子表达式消除（CSE，同一子表达式只算一次），构成了图编译器的基本工具箱。真实的 TorchInductor 在它们之上还做布局优化、内存规划、调度、自动生成 Triton/C++ 内核，但所有这些都建立在「图 + 一组保语义的变换 pass」这个骨架上——而这个骨架，你在本模块就会亲手写出来。

6真实流水：Dynamo 与 Inductor

把它跑起来：TorchDynamo 与 Inductor 的真实流水

把玩具放回真实语境。torch.compile(model) 背后是一条多级流水线：

阶段组件做什么
① 捕获TorchDynamo在 CPython 字节码层拦截 Python，把可 trace 的部分抓成 FX 图；遇阻则 graph break 退回 eager
② 微分AOTAutograd提前把反向也捕获成图（不再运行时动态建图），前向反向一起优化
③ 降低+优化TorchInductor在图上做融合、调度、内存规划等 pass（本模块玩具版的工业级对应）
④ 生成代码Triton / C++GPU 上生成 Triton 内核、CPU 上生成 C++/OpenMP；首次编译、之后缓存复用

几个与本模块直接呼应的工程概念：guard——编译产物记录了它依赖的前提（输入形状、dtype 等），下次调用先查 guard 是否成立，成立则复用、不成立则重编译。所以形状频繁变化会触发反复重编译、抵消收益，对策是 dynamic=True（按动态形状编译一次）或对输入做 padding。这也解释了为什么编译型框架偏爱固定形状。

直白说

你只需写 model = torch.compile(model)，剩下的捕获、融合、生成内核全自动。第一次调用慢（在编译），之后快（复用编译产物）。这就是「默认 eager、按需编译」的体验。

严谨说

graph break 越少，编译收益越大。实践中要尽量避免在热路径里写数据相关的 Python 控制流、.item()（强制同步取标量值）、打印等会打断 trace 的操作。用 torch._dynamo.explain 能看到一段代码产生了多少 graph break、卡在哪——这是调编译性能的入口。

一个值得建立的认知：torch.compile 把「以前要手写 CUDA/Triton 内核才能做的融合」自动化了。C36 里你手写 FlashAttention 的融合逻辑；而对很多逐元素/规约模式，torch.compile 已能自动生成接近手写水平的融合内核。这不意味着手写内核没用了——前沿/极致场景仍需手写（FlashAttention 这种结构性创新编译器还想不出来），但日常的「把一串小算子融起来」已被编译器接管。理解编译器在做什么，才知道何时该信它、何时该自己上。

7工程现实与陷阱

工程现实与陷阱

本模块的玩具编译器抓住了「捕获成图 + 保语义 pass」的骨架，但真实编译型执行有不少坑，了解它们能让你用好 torch.compile：

  • 控制流的代价：tracing 烤死控制流是根本限制。数据相关的 if/循环要么 graph break（退回 eager、丢失融合），要么用结构化控制流原语（JAX 的 lax.cond/scan）显式写——后者能进图但要改代码风格。
  • 动态形状：变长序列、变 batch 会触发重编译。dynamic=True 让编译器生成对形状泛化的代码（一次编译多形状复用），但有时比静态形状慢。padding 到固定桶（bucket）是常见折中。
  • 数值差异：融合、重排、用不同精度的中间累加，可能让编译后结果与 eager不逐位相同（但应在容差内）。这在做回归测试时要注意——别用 atol=0 比对 eager 与 compiled。
  • 调试变难：编译后栈帧、错误信息不再对应你的源码行。需要 TORCH_LOGS、torch._dynamo.explain 等工具看中间图与 graph break，这是编译型框架共同的调试税。
  • 首次编译开销：编译本身要时间（有时几十秒）。短任务/频繁变形状的场景，编译开销可能收不回来——这时 eager 反而更划算。编译不是免费午餐，要看摊销。

一个统一的判断：torch.compile（及一切图编译）的收益来自把多次执行的开销摊薄到一次编译上。所以它最适合形状稳定、反复执行、算子较碎的训练/推理热循环；对一次性、形状多变、本就是少数大内核（已经算力受限）的场景，收益有限甚至为负。知道收益从哪来，就知道何时该用、何时该关——这比记住 API 重要得多。

8研究前沿与开放问题

研究前沿与开放问题

  • 编译器 vs 手写内核的边界：编译器能自动融合逐元素/规约，但结构性创新（FlashAttention、稀疏、定制 attention）仍需手写。两者的边界在哪、能否让编译器「发明」出 FlashAttention 式的算法，是开放问题。
  • 动态形状的高效编译：变长是 LLM 推理的常态（不同序列长）。如何编译一次就对所有形状高效（而非每个形状重编译或退化到最坏），是 torch.compile/XLA 的活跃方向。
  • 捕获完整程序：graph break 损失收益。让 trace 覆盖更多 Python（含控制流、数据结构、自定义类）而不牺牲正确性，是 Dynamo 持续在做的；JAX 用纯函数约束换全覆盖，是另一条路。
  • 跨算子的全局优化：融合是局部的。更激进的优化（重写整个计算图、自动选并行策略、算子重排以改善内存峰值）需要全局视角与代价模型，与模块 04 的显存、C08 的并行交叉。
  • 可移植性与多后端：同一图要高效跑在 GPU/TPU/CPU/各种加速器上。MLIR、OpenXLA、Triton 都在试图建立可移植的编译栈，但「一次编译、处处高效」仍未解决。

必读：Ansel 等 2024《PyTorch 2》（torch.compile 的 Dynamo+Inductor 权威论文）、Tillet 等 2019《Triton》（Inductor 生成的内核语言）、torch.fx 论文（图捕获与变换）、Frostig 等 2018《Compiling ML programs via high-level tracing》（tracing 编译方法论）。清单见 references.md。
