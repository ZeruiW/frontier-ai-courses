1这门课讲什么：从单 agent 到 agent 系统

欢迎来到 多智能体编排与生产化（动手造 Agent 系列）。这门课只追求一件事：让你从「会写一个 agent」变成「会把多个 agent 编排成系统、并把它稳稳放进生产」。

如果你学过前一门课，你已经能从零写出一个单个 agent：一个 LLM 在 ReAct 回路里看观察、想、调工具、看结果，跨多步完成任务。那是一个零件。但真实世界里，单个 agent 很快会撞上四道墙：上下文窗口塞满了（一个超长研究任务，光把资料读进来就爆窗）、太慢了（十个互不依赖的子任务，串着做要等十倍时间）、什么都想自己干却样样不精（一个通用 agent 不如几个各管一摊的专精 agent）、放进生产就失控（没有权限边界、没有可观测、不能 7×24 自动跑）。

这四道墙，靠「把提示写得更聪明」是翻不过去的。翻过去要靠编排与生产化的工程：把一个大任务拆开、派给多个子 agent（各有隔离的上下文）、把它们并行起来、再把结果汇总；给它们装上权限边界让它们不能乱来；给整个系统装上可观测让你看得清每一步、算得出每一分钱；最后把它部署成一个能排队、能重试、能恢复、能被健康探测的服务。这门课就是把这套工程的五个核心零件——subagent、编排模式、权限沙箱、可观测与评测、部署——从零拆开、亲手重建。

学完你应当能回答这类问题（也是 agent / infra 岗位的高频面试题）：什么时候该上多 agent、什么时候单 agent 反而更好？subagent 的上下文为什么要隔离、结果该怎么回传？pipeline / fan-out / router / supervisor-worker 各适合什么任务？agent 的权限白名单和审批门该怎么设计、越权怎么挡？一次跨多个 subagent 的运行，你怎么追踪、怎么算成本、怎么评测它对不对？把一个 agent 部署成服务，队列 / worker / 重试 / 状态持久 / 健康检查这套骨架长什么样？——并且能在纯标准库 + MockLLM 里把这五样东西都从零跑通、用 assert 验证。

一句方法论上的话先说在前面：本课的价值不在「我们没有大模型 / API key 也能学」这个妥协，而在它逼你只关注真正难、真正不过时的部分——编排控制流、权限边界、可观测性与运维状态机。模型会换代、厂商接口会变、提示工程的奇技淫巧明年就过时；而「一个 orchestrator 如何分解任务并安全地汇总 subagent 的结果」「一个权限系统如何按白名单与可逆性放行 / 拦截」「一棵 span 树如何聚合出一次运行的成本」「一个任务队列如何在失败后退避重试又不重复副作用」这些结构性的东西，换到任何模型、任何厂商都立刻能用。把它们练扎实，就抓住了 agent 系统工程里真正稳定的那一层。

2世界观：orchestrator-worker 结构

贯穿全课的世界观，是把多 agent 系统理解成一个orchestrator-worker（编排者-工作者）结构，而非一群各自为政的 agent。一个 orchestrator（也叫 lead / supervisor）负责拆任务、派活、收结果、合成答案；多个 worker（subagent）各自专注一个子任务、跑完把结构化结果交回去。这正是 Anthropic 的 multi-agent research system 的骨架：

用户任务 (可能超出单个上下文窗口) │ ▼ ┌─────────────────────────┐ │ ORCHESTRATOR (lead) │ ① 分解任务 │ 分解 → 派活 → 汇总 │ └─────────────────────────┘ ② 扇出 fan-out ╱ │ ╲ ▼ ▼ ▼ ▼ ┌─────────┐ ┌─────────┐ ┌─────────┐ 每个 subagent: │subagent1│ │subagent2│ │subagent3│ · 隔离的上下文 │(ReAct) │ │(ReAct) │ │(ReAct) │ · 自己的工具子集 └─────────┘ └─────────┘ └─────────┘ · 回传结构化结果 ╲ │ ╱ ③ 扇入 gather ╲ │ ╱ + 合成 synthesis ▼ 最终答案

这张图就是整门课的总纲：每个模块都是在实现或加固这个结构的某一部分。模块 01（subagents）实现的是worker 这个零件——如何派生一个有隔离上下文的 subagent、如何把它的结果回传、如何并行扇出多个；模块 02（orchestration）实现的是orchestrator 那个大脑——用什么拓扑（pipeline / fan-out / router / supervisor-worker）把 worker 组织起来、怎么分解任务、怎么合成结果；模块 03（permissions）给这个结构装上权限边界——每个 agent 能调什么工具由白名单与审批门说了算，把越权与危险动作挡在执行之外；模块 04（observability）给整个结构装上透视镜——用 trace / span 树记录「orchestrator 分解 → 各 subagent 执行 → 合成」的全过程，聚合出成本与延迟，据此评测它对不对；模块 05（deploy）则把这个结构搬上生产——用任务队列 + worker + 状态机 + 重试退避 + 状态持久 + 健康检查，让它能长期、稳定、自动地接活干活。

把这张 orchestrator-worker 图记牢，你会发现五个看似分散的话题其实是同一个结构的五个面：worker 怎么造（01）、orchestrator 怎么编排（02）、整个结构怎么受控（03）、怎么被看清（04）、怎么稳稳上线（05）。这也是本课刻意的编排——不堆专题，而是绕着一个核心结构层层加深。

3先想清楚：到底要不要多 agent？

先想清楚：到底要不要多 agent？

在动手造之前，必须先建立一个工程判断，否则你会到处滥用多 agent。Anthropic《Building effective agents》反复强调的一条是：能用更简单的方案解决，就别上更复杂的 agent。多 agent 强大，但代价高昂——更多 token、更难调试、更难保证一致。

一个有用的决策顺序是：单次 LLM 调用 → 固定的 workflow（代码编排）→ 才是多 agent。

方案什么样子适合代价
单次 LLM 调用一问一答，无循环无工具分类、摘要、抽取、改写最低；但只能处理一步到位的事
workflow（代码编排）代码按固定路径串联 LLM 与工具（路径可预测）能清晰拆成固定步骤的任务（起草→校对→翻译）中；路径写死，不够灵活
单个 agent一个 LLM 在 ReAct 回路里自主决定下一步步骤难以预先固定、需动态决策的任务较高；不可控、可能跑偏
多 agent（编排）orchestrator 分解 + 多 subagent 并行 + 合成任务大到单上下文装不下、可并行、需专精分工最高；token 倍增、调试与一致性最难

什么时候多 agent 才真正划算？Anthropic 的经验是：当任务天然可并行、且信息量大到超出单个上下文窗口时——典型如「广度优先的研究 / 检索」：把一个大问题拆成许多互不依赖的子问题，每个 subagent 用自己的上下文窗口去深挖一个子问题，最后汇总。这种场景里，多 agent 用「多个上下文窗口」把一个单窗口装不下的任务分担开来，提速又扩容，收益压过代价。

反过来，什么时候多 agent反而更差？当子任务强耦合、需要频繁共享中间状态时（比如改一处代码要牵动好几处、各 subagent 必须时刻同步），多 agent 的隔离上下文反而成了障碍——它们看不到彼此的最新进展，协调成本爆炸，还不如一个 agent 顺着做。可并行、弱耦合 → 多 agent 赢；强耦合、需共享 → 单 agent 赢。本课教你把多 agent 造出来，但更要你记住何时不该用它。

一个真实的数字感：Anthropic 报告多 agent 系统的 token 消耗可达单 agent 的十几倍（每个 subagent 都有自己的上下文、还有 orchestrator 的协调开销）。所以多 agent 不是「默认更好」，而是「在对的任务上才更好」。先问『这任务可并行吗、信息量超窗口吗』，答案是否定就别上多 agent——这与模块 03 的最小权限、模块 05 的「能简单就别复杂」是同一种工程克制。

4方法论：用 MockLLM 模拟编排并对拍

方法论：没有大模型、没有 API key，怎么学编排与生产化？

本环境没有 GPU、不接任何真实大模型、不需要任何 API key。但编排与生产化的难点，从来不是「调用模型这一行 API」，而是包在模型外面的那一切：任务怎么分解与派发、subagent 上下文怎么隔离、结果怎么回传与合成、权限怎么放行 / 拦截、一次运行怎么追踪与算钱、任务队列怎么重试与持久与恢复。这些用纯标准库 + 一个假模型就能精确地表达和验证。

我们的核心工具叫 MockLLM：一个确定性的、规则驱动的假模型。它不学习、不联网、没有神经网络——只是对给定的上下文，按预设规则返回一个结构正确的输出（比如「subagent 收到子任务 X 就返回结论 Y」）。这听起来像作弊，恰恰相反：把模型换成确定性的桩，能力的不确定性就被剥离，剩下的全是编排与运维逻辑的对错。你写的 orchestrator、权限沙箱、span 树、任务队列状态机，在 MockLLM 下要么对、要么错，没有「模型今天状态不好」的借口——这正是把系统工程练成肌肉记忆的最干净环境。

直白说

打个比方：学指挥乐团不一定要先有一支世界级乐团。指挥的「真功夫」是怎么分谱、怎么让各声部各司其职、怎么让他们同时进来又整齐收尾、出错时怎么补救；这些在一个安全、可重复的「排练厅」（MockLLM）里能练得更扎实。等每个调度动作都做对了，换成真乐团（真实模型）只是把节拍器换成真人——逻辑一模一样。

严谨说

关键纪律是不变量 + assert：每个零件都和一个明确的不变量比对。subagent 的上下文必须真的隔离（改一个不影响另一个）；fan-out 的结果数必须等于派出的 subagent 数（部分失败也一个不少）；权限系统必须放行白名单内、拦截白名单外；span 树聚合出的总成本必须等于各叶 span 之和；任务队列重试用尽后必须进死信而非无限循环。逻辑正确 → assert 通过；assert 通过 → 这套编排 / 运维骨架可以原样搬到真实模型。

真实多 agent 系统里的东西本课的模拟对应真实接口 / 系统
大模型（每个 agent 的大脑）MockLLM：规则驱动的确定性桩Anthropic messages.create（claude-opus-4-8）
subagent（隔离上下文的 worker）一个带独立 messages 列表的对象真实里：另一个 agent 进程 / 一次独立的 API 会话
orchestrator 分解 + 合成Python 函数：split → dispatch → gather → synthlead agent（再过一遍 LLM 合成）
工具调用与权限dict 工具表 + 自写权限策略层tool_use / tool_result + 白名单 / 审批
一次运行的追踪span 字典 + parent_id 拼成的树OpenTelemetry trace / span
部署运行时内存队列 + worker 循环 + 状态机Celery / Temporal / 一个长期服务

务必清楚本课不教什么：不教提示工程的具体话术、不调真实模型的超参、不接真实危险工具、不追求 SOTA 分数、不实现真正的并发 / 多机。这些在你有了正确的编排与运维骨架之后，是第二步（references 里的官方文档、AutoGen、OpenTelemetry、Celery 接手）。本课负责把第一步——编排控制流、权限边界、可观测性、运维状态机的正确性夯死；这一步搞定，第二步才有意义。也正因如此，本课的代码刻意不调用任何需要密钥的服务，你随时能 `python` 跑通每一个 cell。

每个模块配一个 notebook，结构统一：先用标准库把机制从零实现并验证（5–6 个 worked 小节，每节都跑出可打印的输出与 assert 自测），再做 3–4 道带 assert 判分的 ✏️ 练习（先给骨架，自己填，再对照 📖 参考答案），最后一个真实数据胶囊（用真实编排配置 / 真实 trace 形状 / 真实部署语义，把纸面知识接到现实）。每个 notebook 都端到端可跑、不需要密钥；并在关键处旁附真实 Claude Messages API 接口的形状对照。

关于真实 Claude：本课特意在 05_deploy/agent_cli.py 里给了一个最小的真实适配器，体现本系列的承诺——有 key 用真实 Claude，无 key 自动回退到 MockLLM，绝不阻断：

# agent_cli.py 的适配思路（节选；本环境无 key 时走 MockLLM 分支）
import os
def make_llm():
    if os.environ.get('ANTHROPIC_API_KEY'):
        from anthropic import Anthropic
        client = Anthropic()                      # 读 ANTHROPIC_API_KEY
        def call(system, messages):
            r = client.messages.create(
                model='claude-opus-4-8', max_tokens=2048,
                system=system, messages=messages, tools=SCHEMAS)
            return r.stop_reason, [b.model_dump() for b in r.content]
        return call
    # —— 无 key 自动回退：用确定性 MockLLM，课程照常跑通 ——
    return mock_llm_call

这段适配器的形状贯穿全课：你在 MockLLM 上验证过的编排 / 权限 / 追踪 / 部署逻辑，把那一行 mock_llm_call 换成 messages.create(model='claude-opus-4-8', ...) 就能接上真实模型——其余的分解、扇出、权限、span、队列逻辑一行不改。这就是「scaffold 可迁移」的含义。
