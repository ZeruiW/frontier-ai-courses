1从『手动跑一次』到『部署成服务』

这是全课的收口。前四个模块，我们把 agent 系统的内核从零搭了起来：能编排多个 agent（01–02）、能控权限（03）、能可观测（04）。但这一切到现在都还停在「能在本地手动跑一次」的阶段——你打开终端、敲一行、看它跑完。本模块要回答最后一个、也是把它变成真实产品绕不过的问题：怎么把它部署成一个能长期、稳定、自动地接受并处理任务的服务？这就是 deployment（部署 / 生产化）。

「手动跑一次」和「部署成服务」之间，隔着一道工程鸿沟。手动跑：你在场、任务一个一个来、失败了你重跑、状态在你脑子里、跑完就退出。而生产要的是：任务源源不断地来（要排队、要削峰）、没人盯着（要自动重试、自动恢复）、可能崩溃重启（状态不能丢）、要被监控（要能被健康探测）、要能扩容（多个 worker 一起干）。把这些做到，才叫「部署」。

本模块从零搭一个最小但结构完整的部署骨架，五个零件：任务队列（缓冲 + 解耦接收与执行）、worker（从队列取任务执行）、状态机（精确管理每个任务的生命周期）、重试退避（失败了智能地再试）、状态持久化（崩溃重启不丢任务）、健康检查（让外部能探测服务死活）。这些是任何生产服务的通用骨架，不只对 agent——但 agent 有它特有的考量（长耗时、高成本、可能跑偏），我们会一并讲。

课程在 05_deploy/agent_cli.py 里还给了一个可运行的真实适配：把前面学的工具 + ReAct 回路 + 权限护栏 + 成本追踪拧成一个最小命令行 agent，体现本系列的承诺——有 ANTHROPIC_API_KEY 用真实 Claude（claude-opus-4-8），无 key 自动回退到离线骨架，绝不阻断。本模块讲的队列 / worker / 重试 / 持久，就是把这样一个 agent从『一次性 CLI』升级成『长期服务』所需的运行时。

一句话抓住本模块：部署 = 给 agent 装上一套能 7×24 自动运转的运行时。任务进队列排队，worker 不停地取出来跑，跑挂了状态机标记并退避重试，状态写进持久层防丢，健康探针随时报告系统死活。本模块教你把这套运行时从零造出来——它让一个『能手动跑一次』的 agent，变成一个没人盯着也能稳稳接活干活、崩了能恢复、坏了能被发现的服务。

2任务队列：解耦接收与执行

任务队列：解耦『接收』与『执行』

部署的第一块基石是task queue（任务队列）：一个缓冲区，提交的任务先入队，worker 再从队列取出执行。这个简单的间接层，解决了「手动跑」无法应对的几个生产问题。

队列的核心价值是解耦——把「接收任务的一方」（producer，如一个 HTTP 接口）和「执行任务的一方」（worker）分开。这个解耦带来三个关键能力：

  • 削峰：任务突然涌入时，队列把它们缓冲住，worker 按自己的节奏消化，而不是被瞬间打垮。
  • 横向扩容：执行慢了？多起几个 worker 一起从队列取任务消费——producer 一行不改。这是「能扩容」的根本机制。
  • 重试与容错：任务在队列里有明确身份，失败了可以重新入队、可以被另一个 worker 接手。没有队列，失败的任务就丢了。
producer(s) queue (缓冲) worker(s) ┌─────────┐ 入队 enqueue ┌──────────────┐ 取出 dequeue ┌────────┐ │ HTTP API│ ──────────────► │ [t3][t2][t1] │ ────────────► │worker-1│ │ 定时器 │ │ (FIFO/优先级)│ ────────────► │worker-2│ └─────────┘ └──────────────┘ └────────┘ 只管入队、不管执行 缓冲: 削峰/扩容/重试 只管取活、不管来源

直白说

队列像餐厅的「叫号取餐」：点单的人（producer）只管下单拿号、不用站在灶台前等；厨师（worker）按号顺序出餐、忙不过来就多开几个灶（扩容）；高峰期单子堆在叫号屏上（缓冲削峰），不会把厨房瞬间冲垮。下单和做菜被「号牌」解耦开了。

严谨说

形式上，最小队列是一个 FIFO（collections.deque）：enqueue(task) 加到尾、dequeue() 从头取。进阶是优先级队列（heapq，高优先级任务先出）。本课用内存队列模拟（真实里是 Redis / RabbitMQ / SQS）——但 enqueue / dequeue / 多 worker 消费的接口与语义和真实队列一字不差。这正是「在干净环境里把语义练对，再换成真队列只是替换实现」。

队列还引出一个生产中的核心语义：投递保证。at-least-once（至少一次）保证任务不丢、但可能被执行多次（worker 取了任务、跑到一半崩了、任务重回队列被再取）；at-most-once（至多一次）不重复但可能丢。多数队列默认「至少一次」（宁可重复别丢），这就逼出了下一个必修概念——幂等性（第 6 节）：既然任务可能跑多次，就得保证跑多次和跑一次效果相同，否则重复扣款、重复发信。队列的『至少一次』与执行的『幂等』是一对必须配套的设计。

3worker 与状态机：管理任务一生

worker 与状态机：精确管理每个任务的一生

有了队列，需要 worker（工作者）不停地从里面取任务执行。但「取出来跑」只是最粗的描述——生产需要精确地知道每个任务此刻在哪：还在排队？正在跑？跑成功了？失败了？在重试？这就需要 state machine（状态机）。

状态机把一个任务的生命周期建成「有限的状态 + 合法的转移」。一个 agent 任务的典型状态机：

enqueue worker 取出 跑成功 ──────► [queued] ───────────────► [running] ──────────► [succeeded] ▲ │ │ 还有重试次数 │ 跑失败 │ (退避后重新入队) ▼ └──────────────────── [failed] ──────────► [dead] (重试用尽) 合法转移: queued→running→succeeded/failed; failed→queued(重试)/dead

为什么要把它显式建成状态机，而不是用几个布尔标志（is_running、is_done）糊弄？因为状态机能拒绝非法转移——一个 succeeded 的任务不该再变成 running、一个 dead 的任务不该被重试。用一张合法转移表（{from_state: {允许去的 state}}）守住转移，任何非法转移都被拦下并报错。这把「任务此刻能不能做某事」从散落的 if 判断，收敛成一张可审计、可断言的表——和模块 03 的权限策略、模块 02 的 router 同构，都是「按规则查表决定」。

状态机还让可观测落地（接模块 04）：每个任务带 status，你随时能统计「队列里多少 queued、多少 running、多少 failed」——这正是健康检查（第 7 节）要报告的核心指标。状态转移本身也该记成结构化日志 / span（queued→running 是一个事件），出了事能回看每个任务的状态变迁史。状态机是把『任务一生』变得透明、可控、可审计的骨架。

直白说

状态机像快递的物流状态：揽收 → 运输中 → 派送中 → 已签收，或者「派送失败 → 重新派送」。每个包裹任何时刻都精确处在一个状态，且状态只能按合法路线流转（不会从「已签收」跳回「运输中」）。你查物流，看的就是这个状态。任务的状态机就是 agent 任务的「物流追踪」。

严谨说

形式上，状态机是 (states, transitions, transition(task, to_state))：transition 检查 to_state in transitions[task.state]，合法就改状态、记一条日志，非法就 raise。worker 的主循环就是驱动这个状态机：dequeue → transition(running) → 执行 → transition(succeeded/failed)。本课 notebook 从零实现状态机 + worker 主循环，并用 assert 验证「非法转移被拒绝」「任务状态正确流转」。

worker 主循环的一个关键纪律是一次只认领一个任务、跑完再认领下一个（或在并发模型里：每个 worker 协程串行处理它认领的任务）。这让「谁在跑哪个任务」清晰可追踪——任务被某个 worker 认领后标记 running，避免被另一个 worker 重复取走。在真实分布式队列里这靠「可见性超时 / 租约」实现（取走的任务暂时对其他 worker 不可见，跑完确认、或超时后重新可见）。本课用单进程顺序模拟，但「认领—执行—确认 / 失败」的状态流转逻辑与真实一致。

4重试与退避：智能地再试

重试与退避：失败了，智能地再试

生产中任务会失败：agent 调的外部工具超时、下游服务 5xx、限流、网络抖动。这些瞬时错误往往再试一次就好；而参数非法、任务本身无解这类确定性错误，重试一万次也没用。所以重试的第一要务是区分这两类错误——对瞬时错误重试、对确定性错误直接判死。

重试不能立刻、无限地试——那会在下游本就出问题时火上浇油（一堆 worker 同时疯狂重试，把刚要恢复的下游再次打垮，即「惊群」）。正确做法是 exponential backoff（指数退避）：每次重试前等待的时间指数增长，再叠加随机抖动打散重试时刻。

\[\text{wait}_k = \text{base}\times 2^{\,k}\times(1+\text{jitter}),\qquad k=0,1,2,\dots,\ \text{jitter}\in[0,1)\]

退避的两层用意：指数增长给下游越来越多的恢复时间（第一次等 1 秒、第二次 2 秒、第三次 4 秒……）；随机抖动避免所有失败的 worker 在同一时刻整齐地重试（否则退避也成了同步的惊群）。再配一个重试上限：试 N 次仍失败就放弃，把任务转入 dead 状态 / 死信队列（dead-letter queue），隔离出来供人工排查，而不是无限循环占着资源。

错误类型例子该重试吗处置
瞬时（可重试）超时、5xx、限流、网络抖动✅ 是指数退避后重新入队
确定性（不可重试）参数非法、任务无解、权限拒绝❌ 否立即判死 → dead
重试用尽瞬时错误试了 N 次仍失败—转 dead-letter，人工排查

agent 任务的重试还有一层特殊考量：成本。每次重试一个 agent 任务，可能是又一轮十几倍 token 的多 agent 编排（模块 01）。所以 agent 的重试上限要比普通任务更克制——重试 5 次一个烧钱的研究任务，可能比直接判死、转人工还贵。这呼应模块 04 的成本可观测：重试策略应该成本感知，对昂贵任务设更低的重试上限、或重试时降级到更便宜的模型。退避防的是惊群，上限防的是无底洞。

一个常见且危险的错误：对确定性错误也重试。一个任务因为参数非法失败，你的 worker 傻乎乎地退避后重试——参数还是非法，再失败、再重试……白白烧 N 次的钱和时间，最后还是死。重试前先问：这个错误重试有用吗？按错误类型（异常类 / HTTP 状态码）判定可重试性，是重试逻辑的第一道闸，比退避算法本身更重要。能重试的才重试，重试的才退避。

5状态持久化：崩溃不丢任务

状态持久化：崩溃重启不丢任务

生产服务一定会重启——发版、扩缩容、机器故障、OOM。如果任务和它们的状态只活在内存里，一重启就全没了：正在跑的任务凭空消失、队列里排着的任务蒸发、用户的请求石沉大海。所以部署的关键一环是 state persistence（状态持久化）：把任务与状态写进重启后仍存在的存储。

持久化要存什么？至少三样：队列里待处理的任务（重启后能接着取）、每个任务的状态（queued / running / failed / 重试次数，重启后能恢复到正确状态）、已完成任务的结果（让重复请求能直接返回、不必重跑）。本课用内存 dict + JSON 快照模拟（真实里是数据库 / Redis / 持久化队列）——把任务表 dump 成 JSON 存盘、重启时 load 回来。存储后端可换，但『写什么、何时写、怎么恢复』的语义是通用的。

持久化有一个微妙但关键的问题：running 状态的任务在崩溃时怎么办？一个任务被 worker 取走、标记 running、跑到一半进程崩了——重启后它在持久层里还是 running，但其实没人在跑它了（成了「孤儿任务」）。处理办法是：重启时把所有卡在 running 的任务视为「上次崩溃时中断的」，重新入队（回到 queued）让 worker 再取——这又依赖第 6 节的幂等性（这个任务可能上次已经跑了一部分，重跑必须安全）。这条「running → 重启 → 重新入队 → 重跑（幂等保证安全）」的链，是持久化与幂等配套工作的典型。

# 持久化的最小形态：任务表 dump/load(真实里换成 DB/Redis)
def snapshot(task_table, path):
    with open(path, "w") as f:
        json.dump(task_table, f)        # 把所有任务+状态写盘

def restore(path):
    with open(path) as f:
        table = json.load(f)
    # 关键: 把崩溃时卡在 running 的任务重新入队(它们的 worker 已经没了)
    for tid, t in table.items():
        if t["state"] == "running":
            t["state"] = "queued"        # 重新排队, 等幂等地重跑
    return table

持久化的频率也是个权衡：写得太勤（每个状态变化都落盘）保证最不丢、但慢；写得太疏（定期快照）快、但崩溃时会丢掉上次快照后的变化。真实里常用「关键状态变化即时写 + 周期性全量快照」的组合。本课为教学用即时写，但要记住这个权衡——它和模块 04 可观测的「记得全 vs 记得省」是同一种工程取舍。持久化让服务有了『记忆』——崩溃只是中断，而非失忆。

6幂等、健康检查与优雅停机

幂等、健康检查与优雅停机：生产的三道保险

最后三个零件，把部署骨架补成生产可用：幂等性（重复执行安全）、健康检查（让外部探测死活）、优雅停机（重启不丢任务）。它们都源于一个事实——生产系统会重复、会被探测、会被重启。

幂等性（idempotency）：前面反复提到——队列「至少一次」投递 + 崩溃重跑 running 任务，都意味着一个任务可能被执行多次。如果执行有副作用（扣款、发信、下单），重复执行就是重复扣款、重复发信。idempotency 要求同一个任务执行多次，效果与执行一次相同。实现办法是给每个任务一个幂等键（idempotency key），执行前先查「这个键是否已成功处理过」——处理过就直接返回上次结果、不再执行副作用。幂等是『至少一次』世界里避免重复副作用的唯一兜底，几乎是生产任务的必修。

健康检查（health check）：让外部（负载均衡 / 编排系统 / 监控）能探测「这个服务还活着吗、还能接活吗」。两种探针：liveness（存活——进程没死、没死锁）和 readiness（就绪——能接新流量了，如队列没爆、worker 在跑）。健康检查通常报告关键指标：队列深度、running / failed 任务数、错误率、worker 状态——这些正是模块 04 的可观测数据。健康检查是自动运维的眼睛：探针报告不健康，编排系统就重启它、不再给它发流量、或扩容更多实例。

优雅停机（graceful shutdown）：收到停机信号时，不立刻被杀死，而是：① 停止从队列取新任务；② 等正在跑的任务跑完（或安全中止、回退到 queued）；③ 把状态持久化；④ 再退出。粗暴地直接 kill 会丢任务——正在跑的任务半途而废、状态没存。优雅停机保证重启 / 扩缩容时不丢任务、不留半完成状态。它和持久化、幂等配套：优雅停机把 running 任务安全收尾或回队，持久化存下状态，重启后幂等地继续。

把这三道保险和前面的零件串起来，就是一个完整的生产闭环：任务入队（队列）→ worker 认领（状态机 running）→ 执行（幂等保证重复安全）→ 成功 / 失败（状态机）→ 失败则退避重试 / 转死信（重试）→ 全程状态落盘（持久化）→ 外部探测系统死活（健康检查）→ 重启时优雅收尾 + 恢复（优雅停机 + 持久化恢复 running 任务）。这个闭环就是把一个『能手动跑一次』的 agent，变成一个7×24 自动运转、崩了能恢复、坏了能被发现、重启不丢任务的服务所需的全部骨架。

生产三保险的统一心智：假设最坏情况一定发生——任务一定会被重复投递（→幂等）、服务一定会被探测和重启（→健康检查 + 优雅停机）、进程一定会崩（→持久化）。生产化工程的本质，就是不指望一切顺利，而是为每一种『一定会发生的坏情况』预先准备好安全的应对。这与模块 03 的「假设终将被攻破」、模块 04 的「假设需要回看」是同一种成熟心态——把对失败的预案做进系统骨架里。

7把全栈拧成一个 agent 服务

把全栈拧成一个 agent 服务

本节是全课的合流：把六个模块的零件拧成一个能部署的 agent 服务，看它们如何严丝合缝地拼起来。这也是 05_deploy/agent_cli.py 那个最小命令行 agent 想升级成的目标形态。

想象一个「研究 agent 服务」收到一个任务「调研三家公司并对比」，全栈是这样流转的：

  1. 入队（05）：任务进队列，状态 queued，立即返回一个任务 id（用户不必干等）。
  2. worker 认领（05）：worker 取出任务，状态机转 running。
  3. 编排（02）：orchestrator 分解成三个子任务，决定用 fan-out 拓扑。
  4. 派 subagent（01）：并行派三个 subagent，各有隔离上下文，回传结构化结果。
  5. 权限把关（03）：每个 subagent / orchestrator 的工具调用过沙箱，越权被拦、不可逆动作问人。
  6. 可观测（04）：整个过程织成一棵 span 树，挂载 token / cost，全程结构化日志。
  7. 收尾（05）：成功则状态机转 succeeded、结果持久化；失败则退避重试或转死信。健康探针随时报告队列深度与成功率。

这一条流转里，每个模块都不可或缺：没有 05 的队列 / worker，它接不了源源不断的任务；没有 02 的编排，它处理不了需要分解并行的复杂任务；没有 01 的 subagent，它扩展不了上下文；没有 03 的权限，它不敢碰真实工具；没有 04 的可观测，它错了 / 贵了 / 慢了你都不知道。六个模块拼成的不是六个孤立功能，而是一个有机的 agent 系统——这正是本课从一开始就用 orchestrator-worker 那张图统领全局的原因：每个模块都是这张图的一个面，最后它们合成完整的图。

回到 agent_cli.py：它是这个全栈的最小可运行切片——工具（03 的权限护栏裹着真实文件 / shell 工具）、ReAct 回路（单 agent 内核）、成本追踪（04 的雏形）、真实 Claude 适配（有 key 用 claude-opus-4-8、无 key 回退）。它本身是一个「一次性 CLI」；本模块讲的队列 / worker / 状态机 / 重试 / 持久 / 健康，就是把它升级成长期服务要套在外面的运行时。你可以把 agent_cli.py 的 run_agent 当作 worker 主循环里「执行一个任务」的那一步——队列负责喂任务给它、状态机管理它的一生、重试兜住它的失败、持久化记住它的进度。

最后一句收束全课：从『会写一个 agent』到这里『会把多个 agent 编排成系统并部署进生产』，你走完了 agent 工程从单体到系统、从 demo 到产品的全程。你练的每一样——subagent 隔离、编排拓扑、权限沙箱、span 树、队列状态机——都是不随模型与厂商过时的结构性功夫。把 MockLLM(...) 换成 messages.create(model='claude-opus-4-8', ...)（无 key 自动回退），你写的整套系统就能接上真实 Claude 跑进生产——这就是本课从头贯彻的「scaffold 可迁移」：你练的是 agent 系统工程，模型只是其中一个可替换的零件。

8研究前沿与开放问题

研究前沿与开放问题

  • 长耗时 agent 任务的部署模型：一个 agent 任务可能跑几分钟到几小时（多轮编排 + 多 subagent）。传统的「请求-响应」服务模型不适合——需要异步任务 + 进度流 + 可中断 / 可恢复。如何为「长耗时、有状态、可能需人介入」的 agent 任务设计运行时（如 Anthropic 的 Managed Agents、Temporal 式持久工作流），是活跃的工程方向。
  • 成本感知的调度与降级：agent 任务成本高且差异大。如何在部署层做成本感知调度——给昂贵任务设预算上限、负载高时自动降级到便宜模型、按成本优先级排队——是 agent 运维特有的难题（接模块 01 / 04 的成本意识）。
  • 有状态 agent 的扩缩容：无状态服务扩容简单（多起几个实例）；但 agent 任务有长上下文、有进行中的多 subagent 编排，扩缩容时如何迁移 / 恢复这些状态而不丢、不重复，比无状态服务难得多。
  • 人在回路的生产化：模块 03 的审批门在生产里怎么落地？一个跑了一半、卡在「等人确认转账」的 agent 任务，怎么持久化它的『暂停态』、怎么在人确认后唤醒它继续？把 human-in-the-loop 做成可靠的生产机制（而非阻塞一个进程干等）是开放问题。
  • 可靠性与级联故障：多 agent 系统的依赖链长（编排 → subagent → 工具 → 外部服务），一处故障易级联。如何用熔断器、舱壁隔离、降级把故障圈住（《Release It!》的稳定性模式之于 agent），让一个 subagent 依赖的外部服务挂掉不至于拖垮整个 agent 服务，是生产可靠性的核心。

必读：《Release It!》（Nygard，重试 / 退避 / 熔断 / 舱壁等稳定性模式，本模块的根）、Designing Data-Intensive Applications（Kleppmann，队列 / 投递语义 / 幂等 / 持久）、Google SRE Book（健康检查 / 优雅停机 / 负载管理）、Celery / Temporal（真实任务队列与持久工作流）、Anthropic Claude Agent SDK / Messages API（把骨架接到真实 claude-opus-4-8）。清单见 references.md。🎓 全课完结：你已经从零把多 agent 系统搭起（subagent 01 → 编排 02）、控住（权限 03）、看清（可观测 04）、并部署进生产（05）。把 MockLLM 换成真实 Claude，你写的整套系统就能上真实世界。
