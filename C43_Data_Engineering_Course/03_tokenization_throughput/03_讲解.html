1分词在万亿 token 下的三堵墙

分词（tokenization）听起来是个解决了的问题：拿现成的 BPE 分词器，对每篇文档调一次 encode() 就行。在小数据上确实如此。但当语料是万亿（1e12）token 时，这件「平凡」的事会突然撞上三堵墙：吞吐（单核分完要几个月）、内存（token 数组放不进内存）、和一个最隐蔽的浪费——padding（把短序列填齐造成的算力空烧）。

先和上游课程划清边界。C21（大规模预训练）讲的是分词的科学：词表多大、用 BPE 还是 unigram、分词粒度如何影响下游困惑度与压缩率——这些是「分词器应该长什么样」的问题。本课接手的是分词的工程：分词器已经定了，现在要把它高效地、正确地、可规模化地套到万亿 token 上。同一个 BPE 分词器，朴素地用和工程化地用，吞吐可以差几十倍、有效算力利用率可以差一倍。

直白说

分词在工程上有个得天独厚的好处：它是逐文档独立的——分 A 文档不需要看 B 文档。这种「embarrassingly parallel（易并行）」结构意味着理论上加机器就能线性提速。但「理论上」三个字藏着魔鬼：分词器的训练（合并规则的学习）是偏串行的，而分词产物的下游消费（packing、写盘）也可能成为新瓶颈。

严谨说

形式化本模块的三笔账。吞吐账：分完 N 个 token 的时间 ≈ N / (R · P · η)，其中 R 是单核每秒 token 数、P 是核数、η 是并行效率。浪费账：padding 浪费率 = 填充 token 数 ÷ 总 token 数，packing 的目标是把它压到接近 0。内存账：token 用几字节存（uint16 还是 uint32）由词表大小定，直接决定落盘体量与 mmap 是否必要。

本模块的一句话主线：分词的难点不在「怎么切词」，而在「万亿 token 下怎么把核跑满、把浪费压没、把内存放下」。这三件事分别由并行 + Amdahl 上限、序列 packing、token 数据类型 + 内存映射解决。学完你能为一条真实分词管线算出「要几台机器、跑几天、产出多大、浪费多少」。

2为什么能并行，又为什么不免费

分词为什么能并行，又为什么并行不是免费的

把分词拆成两个阶段看，能力差异立刻清楚。训练阶段（学 BPE 合并规则）：统计全语料的字节对频率、反复挑最高频的对合并——这一步本质串行（每次合并依赖上一次的结果），且要全局词频，难并行。好在它只做一次、且常在一个采样子集上做，不是吞吐瓶颈。编码阶段（把文本切成 token id）：拿训练好的合并规则套到每篇文档——这一步逐文档独立、完全可并行，也正是万亿 token 的吞吐主战场。

既然编码可并行，是不是加核就线性提速？不是。真实分词管线里总有串行或半串行的环节：从对象存储读原始文本（IO，可重叠但有上限）、把分词结果汇总写盘（多进程写同一批 shard 文件需协调）、以及BPE 编码里那点不可向量化的合并循环。这些串行占比，决定了加核的收益上限。

这里要澄清一个常见误解：「易并行」不等于「零通信」。逐文档独立确实意味着 worker 之间在计算阶段不需要互相通信，但它们仍然共享两个有限资源——输入带宽（所有 worker 都从同一批对象存储拉数据，总带宽是定值）和输出汇聚（所有 worker 的产物最终要落成有组织的 shard 文件）。当 worker 数少时，这两个共享资源绰绰有余、加核近线性提速；当 worker 数多到把输入带宽吃满、或把写盘出口堵住时，再加 worker 只是让它们排队等 IO。这就是为什么真实吞吐曲线总会从近线性逐渐压平——不是分词本身不可并行，而是它依赖的共享资源有上限。

直白说

打个比方：100 个工人切菜（分词），理论上比 1 个工人快 100 倍。但如果所有切好的菜都得经过一个出菜口打包（写盘汇总），出菜口就成了瓶颈——再多工人也快不过出菜口的速度。这个「出菜口」就是串行占比。

严谨说

这正是 Amdahl's law（阿姆达尔定律）说的：设串行占比为 s、并行核数为 P，加速比上限是

\[\text{Speedup}(P) = \frac{1}{s + \frac{1-s}{P}} \xrightarrow{P\to\infty} \frac{1}{s}\]

即便核数 P→∞，加速比也被 1/s 死死封住。s=5% 时，无论多少核，最多快 20 倍。所以分词调优的第一步不是加核，而是先量化并压低串行占比（如让每个 worker 各写各的 shard、避免汇总瓶颈）。

加核前先算 Amdahl

一个真实而昂贵的教训：很多人给分词管线疯狂加核，吞吐却卡在某个值上不去——瓶颈根本不在分词本身，而在串行的写盘/汇总，或在喂数据的 IO。Amdahl 定律告诉你：优化前必须先测出串行占比 s。如果 s 已经是 10%，那你的加速天花板就是 10 倍——这时该做的是把那 10% 的串行环节并行化（如分片写盘），而不是把核从 100 加到 1000（收益微乎其微）。

3吞吐账：万亿 token 要跑多久

吞吐账：万亿 token 到底要跑多久

把吞吐账算具体。一个现代 CPU 核心用优化过的分词库（如 SentencePiece / HuggingFace tokenizers 的 Rust 实现）每秒能分大约 1e5 ~ 1e6 个 token（取决于文本与词表）。取保守的 R=1e5 tok/s/核，分完 1e12 token：单核要 1e7 秒 ≈ 116 天。这就是为什么分词必须并行——单核根本等不起。

代入并行：P=1024 核、效率 η=0.8，有效吞吐 1e5·1024·0.8 ≈ 8.2e7 tok/s，分完 1e12 token 约 1.2e4 秒 ≈ 3.4 小时。从 116 天到 3.4 小时——这就是吞吐账的价值：它把「分词要不要并行、并行到什么程度」从拍脑袋变成可规划的工程决策。

11e5≈ 116 天纯计算，等不起
645.1e6≈ 2.3 天计算为主
10248.2e7≈ 3.4 小时开始触及 IO/汇总

注意最后一行的告诫：核数堆到上万，理论时间是 21 分钟，但实际几乎达不到——因为此时读数据的 IO 带宽和写产物的汇总早已成为瓶颈（回到上一节的 Amdahl）。真实的分词吞吐曲线不是一条无限上扬的直线，而是先近线性、再被 IO/串行压平。工程上的「够用就好」是：把核数加到吞吐曲线开始变平的拐点附近，再往上加核是浪费钱。notebook 会让你把这条曲线（含 Amdahl 上限）画/算出来。

吞吐账还有一个常被忽略的维度——它不是一次性的。语料每月随新的 CommonCrawl 快照增长，分词可能要反复跑（换了分词器、加了新数据）。所以分词工期不只影响「第一次训练前要等多久」，还影响迭代速度：如果每次调整数据配方都要重新分词三天，团队的实验节奏就被锁死在三天一轮。这就是为什么大团队会把分词产物缓存、做增量分词、甚至把它做成一个常驻服务——把「分词工期」从关键路径上挪走。一笔吞吐账，算的不只是机器成本，还有团队的时间成本。

吞吐账的可迁移智慧：任何大规模数据操作，先用「总量 ÷ 单位吞吐 ÷ 有效并行度」估个数量级，再决定要不要做、怎么做。这个数量级估算（back-of-envelope）哪怕只精确到 10 倍以内，也足以避免「上了集群才发现要跑三个月」的灾难。分词如此，去重（模块 01）、过滤（模块 04）皆如此。

4序列 packing：消灭 padding 浪费

序列 packing：消灭 padding 这个隐形浪费

现在讲最隐蔽、也最值钱的一笔账：padding 浪费。训练时模型吃的是定长序列（如长度 2048）。但真实文档长短不一——有的 50 token，有的 5000 token。朴素做法是把每篇文档单独成一条、短的用占位符填齐到 2048。问题来了：一篇 50 token 的文档，要填 1998 个 padding token，这些 token不产生任何有用梯度，却照样占显存、照样过一遍注意力计算——纯粹的算力空烧。

直白说

浪费有多大？如果文档平均长度只有序列长的零头，padding 浪费率可以高达 80%~90%——意味着你买的 GPU 算力，大部分花在了计算「无意义的填充符」上。在万亿 token、千卡集群的规模上，这是天文数字的浪费。

严谨说

解法是 sequence packing（序列打包）：把多条短文档拼接进同一条定长序列，用分隔符隔开，几乎不留空白。一条 2048 的序列可以塞下「50+300+1200+490」四篇文档，浪费率从 90% 砍到接近 0。浪费率定义：

\[\text{waste} = \frac{\#\text{padding tokens}}{\#\text{total tokens}} = 1 - \frac{\#\text{real tokens}}{B \cdot L}\]

其中 B 是序列条数、L 是序列长。packing 通过减少序列条数 B 来逼近「真实 token 占满每条序列」。

packing 本质是一个 bin packing（装箱）问题：把不同长度的文档（物品）塞进定长的序列（箱子），使箱子数最少（等价于浪费最少）。最优装箱是 NP 难的，但工程上用贪心近似就足够好：首次适配（first-fit）——来一篇文档，放进第一个还装得下的箱子，装不下就开新箱子；或更简单的贪心流式拼接——一直往当前序列拼，满了就封箱开新的。这些 O(n) 或 O(n log n) 的近似，打包率通常能到 95%+。

packing 的正确性前提

packing 有一个绝不能忘的正确性陷阱：一条序列里拼了多篇文档，必须用 document mask（文档掩码 / 块对角注意力掩码）阻止注意力跨越文档边界。否则第二篇文档会「看到」拼在它前面的第一篇——这叫跨文档污染（cross-contamination），会让模型学到本不该有的跨文档关联，悄悄损害质量。Krell et al. 2021 专门研究了这个问题。记住：packing 省算力的前提，是掩码挡住了跨文档泄漏。notebook 会从零实现这个块对角掩码并验证它正确隔离了各文档。

5内存账：token 用几个字节存

内存账：token 用几个字节存

分词的产物是海量的 token id 整数。一个常被忽略、却直接决定落盘体量与加载方式的决策是：每个 token id 用几个字节存？答案由词表大小决定。

token id 是 [0, vocab_size) 的整数。若 vocab_size < 65536 (2^16)，每个 id 用 uint16（2 字节）就够；若词表更大（如 12.8 万的多语种词表），就得用 uint32（4 字节）。这个看似微小的选择，在万亿 token 上是2 TB vs 4 TB的差别——直接关系到存储成本、IO 带宽、和能否 mmap。

直白说

为什么不无脑用 uint32 图省事？因为存储和 IO 都翻倍。万亿 token 用 uint16 是 2 TB，用 uint32 是 4 TB；训练时每个 epoch 都要把这些 token 从磁盘读一遍，IO 量也翻倍。在带宽受限的训练里，token 存得越紧，喂数据越快。

严谨说

真实框架（Megatron-LM、GPT-NeoX）把 tokenized 语料存成 .bin/.idx 两个文件：.bin 是所有 token 拼成的一个大数组（按词表选 uint16/uint32），.idx 记录每篇文档在大数组里的起止偏移。训练时用 memory-mapped (mmap) 把 .bin 当内存数组访问、由 OS 按需分页——于是能随机读取远大于内存的 token 文件，无需全部载入。

把内存账串起来：词表大小 → token 数据类型 → 落盘体量 → 是否必须 mmap → 训练时的 IO 带宽，这是一条环环相扣的工程链。一个 12.8 万词表的多语种模型，光是「uint16 装不下、被迫用 uint32」这一点，就让它的 tokenized 语料比同等 token 数的英文模型大一倍——这是做数据容量规划时必须算清的账，否则会低估存储与 IO 一倍。

为什么 mmap 在这里几乎是必选项，值得多说一句。训练要随机地从 token 数组里取序列（打乱顺序喂，见模块 02），而数组有 2~4 TB、远超单机内存。若不用 mmap，要么把整个数组读进内存（放不下），要么每次随机读都重新 seek + read 文件（系统调用开销大）。mmap 的妙处是把文件映射成一个虚拟内存数组，访问哪一页、OS 才从磁盘载入哪一页，并自动缓存热页——于是代码里 arr[i:i+L] 这种朴素切片，背后是 OS 高效的按需分页。这就是 Megatron/GPT-NeoX 的 .bin 必用 mmap 的原因：它让「随机访问一个比内存大千倍的 token 数组」变成一行普通的 numpy 切片。token 存得越紧（uint16），每页能放的 token 越多，分页与缓存也越高效——内存账与 IO 效率在 mmap 这里再次咬合。

内存账的可迁移智慧：在大规模下，「一个元素用几个字节」从来不是小事。token 用 uint16 还是 uint32、MinHash 签名用 int32 还是 int64（模块 01）、shard 元数据存多少——每个「× 总量」之后都是 TB 级的差别。养成「先问数据类型、再乘总量」的习惯，是大规模数据工程师的基本功。

6分词管线的吞吐全景

把流水串起来：分词管线的吞吐全景

现在把本模块的机制拼成一条完整的分词管线，并标出每一环的吞吐特性：

原始文本 shard (对象存储) │ ① 读 IO（可预取重叠，带宽有上限） ▼ 并行编码 encode() ← P 个 worker，逐文档独立（易并行，吞吐主体） │ ② 串行占比 s 在此之外（合并循环不可向量化的部分） ▼ 序列 packing（贪心装箱）+ 文档掩码 ← 消 padding 浪费，O(n) │ ③ 注意正确性：块对角掩码挡住跨文档泄漏 ▼ 按 uint16/uint32 写 .bin / .idx ← 汇总写盘（半串行，易成瓶颈） │ ④ 各 worker 各写各的 shard 可避免汇总瓶颈 ▼ tokenized 语料（mmap 供训练随机读）

读这张图的方式：吞吐由最慢的一环决定（流水线的木桶效应）。编码（②）虽是主体，但若读 IO（①）跟不上，worker 会饿着；若写盘汇总（④）是单点，再多 worker 也堵在出菜口。所以分词吞吐优化是个找瓶颈、消瓶颈的循环：先测出哪一环最慢（用吞吐账 + Amdahl 定位串行占比），再针对性地预取（治 IO）、加核（治计算）、或分片写盘（治汇总）。

把三笔账合起来，就是一次完整的分词管线规划：吞吐账告诉你要几台机器、跑几天；浪费账（packing）告诉你产出的 token 有多少是有效的、省了多少训练算力；内存账告诉你产物多大、要不要 mmap、IO 压力多大。这三笔账，正是把「分词」从一个 encode() 调用，升级成一个可规划、可预算、可扩展的工程系统所需的全部。

一个值得记住的全局视角：packing 省下的算力，最终是省在训练（C08）那一侧的。数据工程师在分词阶段多花一点心思做好 packing（浪费率从 50% 降到 5%），训练侧的有效 token 吞吐就能近乎翻倍——同样的 GPU 时间能多训近一倍的真实 token。数据工程与训练系统在这里紧密咬合：上游的工程质量，直接兑换成下游的算力效率。

7吞吐与正确性的权衡清单

吞吐与正确性的权衡清单

把本模块的工程取舍整理成一张决策表，作为做分词管线规划时的速查：

旋钮调大/开启的好处代价 / 风险经验起点
并行核数 P吞吐近线性提升受 Amdahl 串行占比与 IO 封顶加到吞吐曲线变平的拐点

预取深度藏住读 IO 延迟占额外内存（有界队列）够藏住一两个 batch 的读延迟

这张表的统一逻辑是本课反复出现的：先保正确（packing 必须配掩码），再追吞吐（并行 + 预取 + 紧凑存储），且每个旋钮都「够用即可」而非越大越好。并行核数有 Amdahl 上限，序列长要对齐训练配置，dtype 由词表硬约束——没有一个旋钮是「越大越好」的，每一个都有它的甜点区，靠前面三笔账把甜点区算出来。

最后强调一个容易被忽视的顺序问题：分词在整条数据管线里通常放在去重、过滤、去污染之后（先把该删的删掉，再对留下的干净文本分词，避免在垃圾数据上浪费分词算力）。这又是「先便宜后贵、先筛后算」的工程节奏在管线层面的体现——和模块 01 的「先精确去重再近重复」、模块 04 的「先启发式再分类器」同构。整门课的工程智慧，本质上是同一套「把昂贵操作留到数据最少时再做」的复用。

一个常见的新手陷阱：以为 packing 既然这么好，序列长就该开到极大以便装更满。序列长不是 packing 的自由旋钮，它由训练配置（模型的上下文长度）决定。你不能为了 packing 把 L 设成 100000——那会改变模型训练的语义。packing 是在给定的 L下尽量装满，而非反过来调 L 去迁就 packing。把这个因果搞反，是工程规划里的低级但致命的错误。

8研究前沿与开放问题

研究前沿与开放问题

  • 最优 packing 策略：first-fit / best-fit / 贪心流式各有打包率与计算开销的权衡，超长文档（超过 L）的截断 vs 切分也影响数据完整性。在变长、多模态序列上做最优装箱仍是活跃的工程研究（Krell 2021 是起点）。
  • 无 padding 训练（变长注意力）：与其 packing 后用掩码，不如让注意力内核原生支持变长序列（如 FlashAttention 的 varlen 接口、PyTorch 的 NestedTensor），彻底消除 padding。这把浪费问题从数据侧推到了内核侧，是 C36（GPU 内核）的延伸话题。
  • 流式 / 在线分词：边训练边分词（而非预先全量分词落盘），省掉 TB 级中间存储，但要求分词吞吐跟得上训练吞吐、且可复现。何时该预分词、何时该在线分词，是吞吐与存储的权衡。
  • 分词器本身的吞吐：BPE 编码的合并循环是分词吞吐的核心，Rust/C++ 实现（HF tokenizers、tiktoken）比纯 Python 快几十倍；如何进一步向量化/GPU 化 BPE 编码是工程前沿。
  • 分词与多语言/多模态：多语种大词表（12.8 万+）逼出 uint32 与更大存储；图像/音频 token、字节级模型（无显式分词）正在改变「token」的定义，分词工程也随之演化。

必读：Sennrich et al. 2016（BPE）、Kudo & Richardson 2018（SentencePiece）、Raffel et al. 2020（T5/C4，序列 packing 的早期大规模实践）、Krell et al. 2021（高效 packing 与跨文档污染）；工程对标 Megatron-LM / GPT-NeoX 的 .bin/.idx 数据格式。下游接 C08（训练系统）的有效 token 吞吐。完整清单见 references.md。
