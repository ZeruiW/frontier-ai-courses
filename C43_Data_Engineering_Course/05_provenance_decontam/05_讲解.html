1为什么溯源去污染：可信/可溯/可复现

我们来到这门课的终点站。前四个模块把数据做对、做快——去重（01）、流式加载（02）、分词（03）、质量过滤（04）。但还差最后一环，也是把这一切变成可信任系统的关键：当你训出一个模型、它在 MMLU 上拿了 85 分，你怎么证明这 85 分不是因为训练集里混进了考题？当半年后有人质疑某段数据的来源，你怎么回溯它是哪个快照、经哪些处理步骤来的？当你要让别人复现你的结果，你怎么保证他拿到的是逐字节相同的那份数据？

这三个问题——可信、可溯、可复现——就是本模块的全部。它们听起来像「软」的工程规范，但在 PB 规模下，它们是硬的技术问题：万亿 token 里要检测出与基准的泄漏，是一个大规模子串匹配问题；给一份 50 TB 数据集打不可变快照，靠的是内容哈希与清单（manifest）；记录每份数据的来龙去脉，是一张需要工程化维护的有向无环图（DAG）。

直白说

打个比方：一条没有溯源与去污染的数据管线，就像一家没有进货单、没有保质期、没有溯源码的食品厂——平时看不出问题，一旦出事（评测被质疑、版权诉讼、数据中毒），你完全无法回答「这批料哪来的、动过什么手脚、还有谁吃了同一批」。本模块就是给数据管线装上进货单（lineage）、防伪码（内容哈希）、质检报告（审计）。

严谨说

形式化三件事。去污染：给定训练集 T 与评测基准集 B，找出并删除 T 中与 B 有足够重叠（如共享 n≥13 的连续 n-gram）的文档；溯源：维护一张 (数据状态)→(处理步骤+代码版本+输入) 的 DAG，使任一产物可回溯到原始来源；快照：用内容哈希 h=SHA256(bytes) 给每个 shard 打不可变指纹，清单记录全部哈希，使「同一份数据」可被逐字节重建。

污染几乎必然发生

本模块的核心命题一句话讲清：评测可信的前提是训练集没见过考题，而在 PB 级爬取下，无意的污染几乎必然发生——维基百科里有 MMLU 题目的来源文章、GitHub 上有人贴了 GSM8K 的解答、论坛里转载了基准的样例。Brown et al.（GPT-3）做污染分析时发现各基准都有不同程度的训练集重叠；不去污染，你报的分数可能一半是模型能力、一半是背题。去污染不是锦上添花，是评测结论成立的地基。

2数据污染：泄漏从哪来，为何致命

数据污染：泄漏从哪来，为何致命

先说清楚data contamination（数据污染，又叫泄漏 leakage）到底是什么。它指评测基准的样本（或其改写）混进了训练数据，使模型在评测时实际上是在背诵见过的答案，而非展示泛化能力。结果是评测分数虚高，你以为模型很强，部署后却拉胯。

污染的来源比直觉的要多。直接来源：基准本身就是从网上选材的（MMLU 的题目来自考试题库、HellaSwag 来自 WikiHow），这些原始材料本就在 CommonCrawl 里。传播来源：基准发布后，被论文、博客、GitHub、论坛大量引用转载，连题带答案地散布到全网，下一次爬取就把它们收进来了。改写来源：有人把题目换个说法、翻译成别的语言重新发布，逐字匹配抓不到，但语义上仍是同一道题。

直白说

为什么 PB 规模让污染更难防？因为你爬得越多、越广，撞上基准材料的概率越大。小数据集可以人工核查来源，PB 级只能靠自动化检测。而且基准在不断增多（每年新出几十个），训练集也在不断更新（每月新快照），污染检测变成一个持续的、双向增长的工程任务，不是一次性体检。

严谨说

污染与模块 01 的记忆化是一对孪生问题。Carlini 等证明：一段文本在训练集里重复越多，被逐字背出的概率越高。污染正是「基准样本在训练集里重复了 ≥1 次」的特例——而且是最该防的那次重复，因为它直接破坏评测的有效性。去重（01）降低普遍记忆，去污染（05）专门狙击「记住了考题」这种最有害的记忆。

举个具体的链条感受一下污染是怎么悄悄发生的：MMLU 里有一道关于「法国首都」的题，它的素材来自某篇百科或考试题库——这篇素材本就在 CommonCrawl 的某次快照里（直接来源）；MMLU 发布后，有人在博客里贴出几道样例题讲解、有人把整个数据集镜像到 GitHub、有人在 Reddit 讨论某道题的答案（传播来源）；还有人把题目翻译成中文、或换个数字重新出了一道「同构题」发到论坛（改写来源）。下一次你爬全网做训练集，这三类内容全都会被收进来——你根本没主动去找基准，污染却自己找上门了。这正是为什么 PB 级爬取下无意污染几乎必然：你爬得越全，越躲不开这些已经渗透到全网的基准痕迹。

一个容易踩的认知误区：去污染不是「让分数变低」，而是「让分数变真」。去污染后某基准分数掉了，不代表你的模型变差了，而是揭穿了之前那部分虚高。真正危险的是不做去污染就发布分数——你和读者都被误导，等到实际部署或被第三方复现时才暴露，代价更大。可信评测宁可分数难看，也不要分数虚假。这也是为什么去污染必须在训练前做：训练后才发现污染，要么重训（极贵）、要么带着虚高分数发布（更糟），都没有好的退路。

3n-gram 重叠检测：去污染主力

n-gram 重叠检测：去污染的主力武器

去污染的核心技术是 n-gram overlap（n 元组重叠检测）。思路朴素而有效：如果一篇训练文档和某个基准样本共享了一段足够长的连续文字，就判定它被污染。「足够长」用 n-gram 的 n 来定——GPT-3 用 13-gram（连续 13 个词/token），共享任意一个 13-gram 即标记为污染。

\[\text{contaminated}(d, B) = \big[\, \exists\, g \in \mathrm{ngrams}_n(d):\ g \in \textstyle\bigcup_{b \in B}\mathrm{ngrams}_n(b)\,\big]\]

为什么是 n-gram 而不是整篇比对？因为污染往往是局部的——一篇长论坛帖里只嵌了一道基准题，整篇的相似度很低，但那一段是逐字泄漏。n-gram 能抓住这种「长文档里的短泄漏」。n 的选择是一场权衡：n 太小（如 3-gram），常见短语（the quick brown）会造成大量误报；n 太大（如 50-gram），改写一两个词就能绕过，漏报增多。13-gram 是社区经验下的甜点。

直白说

怎么做得快？把所有基准样本的 n-gram 预先建成一个哈希集合（或布隆过滤器），然后流式扫训练文档：对每篇文档滑动取 n-gram、查这个集合。查集合是 O(1)，所以检测一篇文档是 O(文档长度)，全部训练集是 O(总 token 数)——线性，可流式，易并行。

严谨说

复杂度账：设基准总 n-gram 数 m、训练总 token 数 N。建基准索引 O(m) 时间与空间；扫描训练集 O(N) 次集合查询。对比「每篇训练文档和每个基准样本两两比」的 O(N·|B|)，哈希集合把基准侧的 |B| 压成了 O(1) 查询——又是一次「用哈希分桶消掉一重循环」（呼应模块 01 的 LSH）。

基准索引用什么数据结构，也是个工程取舍。哈希集合（set）最直接、零误报，但要存下所有 n-gram 的完整哈希，内存随基准规模线性涨；当基准很多、n-gram 上亿时，常换成 Bloom filter（布隆过滤器）——它用几个位代表一个元素，内存省一个数量级，代价是有极小的假阳（查到「可能在」时偶尔误判，但绝不漏「不在」）。对去污染这个场景，布隆过滤器的极小假阳是可接受的（顶多多删几篇本来干净的文档，宁可错杀），换来的内存节省让「把所有基准塞进单机内存供流式查询」成为可能。这又是一个「为规模而做的数据结构选择」，呼应模块 01/02 反复出现的内存-精度权衡。

但 n-gram 检测有它的边界，必须诚实面对。它是词面（lexical）的：能抓逐字重叠，抓不住改写、翻译、语义同义的污染。对付改写，工程上会叠加：① 更短的 n-gram + 重叠比例阈值（容忍少量改动）；② 模块 01 的近重复检测（MinHash/SimHash）抓「整体很像」的；③ 嵌入相似度抓语义级。本模块 notebook 会从零实现 n-gram 检测，并用一个已知污染的真值集对拍它的召回率——把去污染当成一个严肃的检测问题来量化，而不是「跑个脚本就完事」。

4数据 lineage：可回溯的 DAG

数据 lineage：把管线变成可回溯的 DAG

去污染解决「有没有泄漏」，data lineage（数据谱系/溯源）解决「这份数据到底怎么来的」。它记录每份数据从原始来源经过哪些处理步骤、用哪个版本的代码与配置、由哪些输入产生——本质是一张有向无环图（DAG）。

一份训练 shard 的 lineage DAG（每个节点 = 一个数据状态 + 产生它的步骤）： [CC-2024-10 原始快照] (来源: commoncrawl.org, sha256=a1b2..) │ step: extract_text code: trafilatura@1.6 config: lang=en ▼ [抽取后文本] (sha256=c3d4..) │ step: quality_filter code: pipeline@v2.3 config: gopher_rules ▼ [过滤后文本] (sha256=e5f6..) │ step: dedup code: minhash_lsh@v1.1 config: tau=0.8 ▼ [去重后文本] (sha256=7890..) │ step: decontaminate code: ngram@v1.0 config: n=13, MMLU+GSM8K ▼ [训练就绪 shard] (sha256=ffff..) <- 每一步都可回溯到上游 + 用的代码/配置

为什么 lineage 在大规模下是硬需求而非可选项？因为 PB 级管线有几十个处理步骤、跑在几千台机器上、跨越几个月。当出问题时——某基准分数异常、发现一段不该有的数据、被质疑某来源的许可——你需要精确回答「这个产物是怎么来的」：哪个原始快照、哪个版本的过滤代码、哪次去重的阈值。没有 lineage，这些问题无法回答，调试与合规都无从下手。

直白说

lineage 的最小实现：每个数据节点记 (内容哈希, 产生它的步骤, 输入节点, 代码版本, 配置)。把这些节点连成图，就能从任一产物向上回溯到原始来源，或从某次代码 bug向下追踪所有受影响的产物。

严谨说

它和可复现性是一体两面：lineage 记录了「怎么做的」，加上每步的代码版本与配置被固定，你就能重新执行这张图、得到逐字节相同的结果。反过来，没有 lineage 的「可复现」是空话——你都不知道当初做了什么，谈何复现。

一个常被忽略的工程价值：lineage 让增量重算成为可能。当某一步的代码修了个 bug，你不必从头重跑整条管线——顺着 DAG 找出「依赖这一步的所有下游节点」，只重算它们即可。在动辄几十万核时的预处理任务里，这种「只重算受影响部分」能省下巨量算力。lineage 因此不只是「记账」，更是大规模管线高效运维的基础设施（这条线会接到 C37 MLOps）。

5内容哈希与可复现快照

内容哈希与可复现快照：让数据集不可变、可重建

可复现性的物理基础是 content hash（内容哈希）。给一份数据算 SHA-256，得到一个 64 位十六进制指纹：内容相同则哈希必然相同，内容差一个字节则哈希面目全非。这个简单性质支撑起三件大事：精确去重（模块 01）、完整性校验（下载的 shard 有没有损坏）、以及本节的主角——可复现快照。

一个 reproducible snapshot（可复现快照）= 一份不可变的数据集版本。做法是给数据集里每个 shard 算内容哈希，把「shard 路径 → 哈希、大小、来源」全部记进一个 manifest（清单）文件，再给清单本身算一个哈希作为整个快照的 ID。

直白说

有了快照，「用了哪份数据」就从一句含糊的话（「2024 年 10 月那版」）变成一个可验证的哈希。任何人拿到清单，逐个校验 shard 哈希，就能确认手里的数据和你训练时逐字节相同；差一个字节，校验就失败。这就是可复现的底线。

严谨说

不可变（immutable）是关键纪律：快照一旦发布，其内容永不修改——要改就发新版本、新快照 ID。这避免了「同一个名字指向不同内容」的灾难（你以为复现的是 v1，其实数据已被悄悄改成 v2）。Git 的 commit hash、Docker 的 image digest、Dolma 的数据版本，用的都是这套「内容寻址 + 不可变」的思想。

没有快照会怎样？想象一个真实的事故：你半年前训了个不错的模型，现在想复现、做消融。你打开数据目录，发现它早被别人「就地更新」过几次——加了新爬取、删了几个坏 shard、改了过滤参数重跑了一部分。现在这份数据既不是当初训练用的那份，你也无法知道差在哪。你的实验结论建立在一份已经消失的数据上，复现无从谈起，调试更是抓瞎。这不是假想——它是没有快照纪律的团队反复踩的坑。内容哈希快照就是把「当初那份数据」永久钉死、可验证地取回。

把快照、lineage、去污染三者串起来，就是一份可信数据集的完整画像：快照 ID 唯一标识这份数据（可复现），lineage 记录它怎么来的（可溯源），去污染报告证明它没混进考题（可信评测）。这三样加上下一节的审计报告，构成了「负责任地发布一个大规模数据集」的工程标准——FineWeb、Dolma 之所以受信任，正因为它们把这套东西都公开了：你不仅能下载它们的数据，还能看到每一步的代码、每个版本的哈希、去污染与审计的结果。可信不是承诺出来的，是证据堆出来的。

6数据审计：可信变可查的报告

数据审计：把可信变成可查的报告

最后一块是 data audit（数据审计）：系统性地检查并产出一份可查的报告，回答关于数据集的关键问题——多少文档、多少 token、来源构成、语言分布、PII 残留、与哪些基准有污染、许可情况。规模越大，越要靠自动化审计，而非人工抽查。

审计报告该包含什么？把它想成数据集的「体检表 + 成分表」：

审计维度查什么怎么查（工程手段）为何重要
规模文档数、token 数、各 shard 大小扫清单聚合统计成本/配比规划的基准
来源构成各来源（web/code/书）占比按 lineage 来源字段分组数据配比透明（接 C21）
污染与各基准的 n-gram 重叠数本模块的去污染检测评测可信的证据
PII 残留邮箱/电话/密钥的残留量正则抽样扫描（模块 04）合规与隐私
可复现快照 ID、清单哈希、种子记录内容哈希与配置他人能否重建

审计报告有两个读者，对应两种形态。机器读的是结构化的 JSON/表格，进监控系统、做回归检查（这次快照的污染率比上次高了？报警）；人读的是 datasheet（数据集卡片，Gebru et al.《Datasheets for Datasets》）——用自然语言记录构成、动机、已知偏差、适用范围与不适用场景，是数据透明与负责任发布的实践。二者缺一不可：JSON 给流水线把关，datasheet 给使用者知情。

审计在大规模下还有一层回归监控的意义。一条管线不是跑一次就完事，它会随新代码、新快照不断重跑——每次重跑都该自动产出审计报告，并和上一次对比：文档数是不是异常掉了一半（某步过滤出 bug）？污染率是不是突然升高（新爬取引入了基准）？PII 残留是不是回涨（脱敏规则失效）？把这些做成自动化的回归检查，管线就从「跑完祈祷没事」变成「出问题立刻报警」。这正是审计与 C37（MLOps）的接口——数据管线和模型一样，需要持续集成式的质量门禁，而审计报告就是那道门禁的检查项。

把本模块浓缩成一句可迁移的工程智慧：一条管线的产出是否可信，不取决于你「觉得」它干净，而取决于你能不能拿出证据——去污染报告证明没泄漏、lineage 证明来源清白、快照哈希证明可复现、审计报告把这些汇成可查的一页。这套「拿证据说话」的纪律，不只用于训练数据，在任何需要可信、可溯、可复现的数据系统（金融、医疗、科研）里都是同一套地基。学会它，你交付的就不只是数据，而是可被信任的数据。

7把账算到 PB 级：成本与权衡

把账算到 PB 级：可信管线的成本与权衡

溯源与去污染不是免费的，得算清它们在 PB 级的开销与权衡，才知道该做到什么程度：

读这张表：去污染、lineage、内容哈希都是线性或更小的开销，相对于训练本身（万亿 token 训几个 epoch）几乎可忽略——它们便宜到没有不做的理由。真正要权衡的是审计的深度（全量还是抽样）和要不要上语义级去污染（要跑嵌入模型，成本上一个台阶）。一个务实的配置：n-gram 去污染 + lineage + 内容哈希快照全做，审计抽样 + 关键维度全量，语义去污染仅对高价值基准。

最后回到本课的主线，把六个模块连起来看：去重（01）让数据不冗余，加载（02）让数据喂得动，分词（03）让数据高效，过滤（04）让数据高质，溯源去污染（05）让数据可信。五条主线背后是同一个命题——规模如何改变正确的做法：O(n²) 去重在 1e12 不可行（01）、全量打乱在 50 TB 不可行（02）、串行分词在万亿 token 不可行（03）、把贵的过滤放前面不可行（04）、靠人工核查污染与来源在 PB 级不可行（05）。每一条，答案都是用一种线性或近线性、可流式、可并行、可验证的工程，替换掉那个朴素但不可扩展的做法。这就是大规模数据工程的全部手艺。

8研究前沿与开放问题

研究前沿与开放问题

  • 语义去污染：n-gram 抓不住改写/翻译/同义的污染。用嵌入近邻或 LLM 判别做语义级去污染是方向，但「多相似才算污染」缺乏公认标准，且大规模跑嵌入成本高、阈值难定。
  • 去污染的军备竞赛：基准方为防污染开始用「私有测试集」「动态生成题」「加水印/canary 字符串」；训练方则要检测这些。检测与规避的拉锯（Carlini 等讨论的 evasion）是持续的开放问题。
  • 污染对分数的真实影响：发现污染后，到底该删样本、还是只在报告里标注、还是重训？污染率与分数虚高的定量关系（删 vs 不删差多少分）仍缺乏系统研究，各家做法不一。
  • lineage 的标准化：目前各机构的 lineage/provenance 格式各异，缺乏跨组织通用标准（类比软件供应链的 SBOM）。数据供应链的可追溯性正成为监管关注点，标准化是必然趋势。
  • 可复现的现实张力：PB 级数据集要长期保存所有快照成本高昂；外部来源（网页）会消失或变化，使「逐字节重建」事实上不可能。如何在「完全可复现」与「存储现实」间取舍，是工程与科学规范的拉锯。
  • 许可与版权溯源：训练数据的许可合规（哪些能用、署名要求、退出机制）越来越受法律关注。把许可信息纳入 lineage、做到「每段数据可追溯到其许可」，是合规驱动的新工程需求。
