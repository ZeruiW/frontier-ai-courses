1三种融合层次：感知的输出可以在三个地方进入 VLA

这是整门课的核心模块，也是 JD 里「设计感知输出接口以支持 VLA 模型」那条职责的字面对应。所以先把问题定义清楚：TSR 模块每帧产出一批结构化的检测结果（类别、位置、尺寸、置信度、跟踪 ID……），VLA 需要用到它们。接口设计要回答的第一个问题不是「传什么字段」，而是「在网络的哪个位置传」——这个选择决定了后面所有事情。

直白说

为什么量产系统最终会走向中间表示级？三个理由叠加：①token 成本与目标数解耦——城市路口 40 个交通元素时，符号级要 800–1200 个 token 光描述场景，而 BEV query 永远是那 100 个；②信息不经过「人写的 schema」这个瓶颈——你永远想不全该传哪些字段，而 BEV 特征里什么都有；③省掉一次序列化-反序列化，延迟与工程复杂度都低。代价是：感知和 VLA 变成一个不可分割的整体，出了问题很难说清是谁的错。

严谨说

但符号级远没有过时，而且在两个场景里不可替代。第一是调试与归因：当路测出现一次「该减速没减速」，符号级接口让你能直接打开那一帧的 prompt，看到「感知当时报的是 speed_limit_120, conf=0.31」——五秒钟定位。而 BEV query 是一堆浮点数，你只能重跑整条链路做消融。第二是安全相关的强语义：限速值、禁令类别这些直接决定合法性的东西，必须以可审计、可追溯、可写进日志的形式存在，因为事故调查要的是「系统当时认为限速是多少」这个明确答案，而不是一组特征。所以真实系统的形态几乎总是混合的：稠密几何走中间表示级，少量但关键的强语义（限速值、禁行、停车让行）额外走一条符号级通路，两条通路互为交叉校验。

一条可迁移的判据：「这个信息出了错，事后需要能说清楚吗？」需要 → 走符号级；不需要 → 走特征/中间表示级。可审计性是符号接口存在的根本理由，不是「信息量」或「性能」。面试里能把「为什么明知道有信息损失还要用文本接口」答成这一条，比背三种融合的定义强得多。

别把「符号级」等同于「让 LLM 读一段自然语言描述」。用自然语言描述场景是 token 成本最高、稳定性最差的做法（第 5 节会算：同样的信息，紧凑键值 schema 只要自然语言的 1/3 token，而且可以被严格解析与校验）。符号级接口应该是「结构化文本」，不是「文章」。

2TSR → VLA 的序列化 schema：每一个字段为什么必须有

假设我们走符号/混合路线。现在来设计那份 schema。下面这张表是本模块最实用的产出——它可以直接当成接口评审的检查单。设计原则只有一条：每加一个字段，都要能回答「下游拿它干什么，不传会导致什么具体故障」；答不上来的字段就是噪声，占 token 还让模板变脆。

字段类型 / 单位下游用它干什么不传会发生什么（具体故障）
schema_version字符串，如 tsr/1.3解析器选版本；模型卡记录训练时用的版本感知升级加了字段 → VLA 的解析器悄悄错位 → 全线误读。这是接口演进唯一可靠的抓手
t_capture / frame_id毫秒时间戳判断数据新鲜度；与自车状态对齐无法识别陈旧数据。感知卡了 300 ms，VLA 会拿 9 米前的世界做决策却毫不知情（模块 02 的 staleness 在这里落地）
track_id整数，跨帧稳定识别「这是同一块牌子」；做迟滞与状态机；关联历史一块牌子的 10 帧被当成 10 块牌子；无法做「连续 N 帧确认才生效」；无法解释「牌子消失了」是遮挡还是真的过去了
cls + cls_id枚举 + 整数语义分派无从谈起
value数值 + 单位（speed_kph=60）限速值、重量/高度限制的具体数字「限速牌」和「限速 60」是两回事。把数值编进类别名（speed_limit_60）会让类别数爆炸且无法表达罕见值
conf_det / conf_cls分开的两个 [0,1]检测置信 ≠ 分类置信，下游用法不同见第 4 节——这是最常见的接口设计错误
cls_top2第二候选类别 + 概率表达「60 还是 80 说不准」下游连「这里有两种可能」都不知道，只能被迫二选一（呼应模块 02 的多模态）
pos_ego$(x_{\text{fwd}}, y_{\text{left}})$ 米，自车坐标系算「还有多远到」「在哪条车道」见第 3 节：传图像像素等于让 LLM 做相机标定
sigma_dist米，距离的 1σ 不确定度远处小目标的距离本来就不准，下游要按不确定度决定提前量把 83 m 当成精确值，而它的真实误差是 ±7 m（第 3 节推导）
bbox_wh像素距离估计的输入；框太小本身就是不可靠信号丢掉一个几乎免费的可靠性代理
lane_assoc枚举：ego / left / right / opposite / service / unknown判断这块牌子管不管我把辅路限速 40 当成主路限速 40；把对向车道的禁令当成自己的。这是 TSR 下游最高频的实际事故
n_obs / age_ms整数 / 毫秒「跟了 20 帧的稳定目标」vs「刚冒出来的一帧」置信度本身不含这个信息——单帧 0.9 和连续 20 帧 0.9 的可信度差一个量级
state枚举：tentative / confirmed / lost生命周期；lost 后的宽限期牌子被树叶遮住一帧就「消失」→ 约束被误撤销
ttl_ms毫秒有效期看门狗：超期自动降级过期数据被当成当前数据
src相机 ID / 传感器多相机冲突时的仲裁；归因同一块牌子被前视与侧视各报一次，下游当成两块

直白说

表里最容易被漏掉、后果又最严重的两个字段是 track_id 和 lane_assoc。漏 track_id 的后果不是「少了个 ID」，而是下游彻底失去时间维度——它没法说「这块牌子我已经连续看到 15 帧了」，于是要么每帧都重新做决定（输出抖动），要么自己重新做一遍跟踪（把感知的活干第二遍，还干得更差，因为它只有框没有特征）。漏 lane_assoc 则是把一个感知有能力回答、下游没能力回答的问题甩给了下游：牌子挂在龙门架的哪一格、对应哪条车道，这需要标志与车道线的几何关联，感知模块有车道线、有 BEV，做起来是自然的；VLA 只拿到一个坐标，只能猜。

严谨说

更一般的原则是：接口的边界应该划在「谁有能力回答这个问题」的地方，而不是划在「谁的代码好改」的地方。感知能算的东西不要留给下游算——因为感知有原始像素、有多帧、有几何标定，下游只有一份摘要。反过来，感知不该做的也不要越界做：比如「这块限速牌该不该生效」涉及导航路径、当前车道、法规优先级，那是决策层的知识，感知强行判断只会在信息不全的情况下猜错，而且把错误锁死在一个下游无法纠正的字段里。一个好用的检验：把每个字段问一遍「如果这个判断错了，下游有没有信息把它纠正回来？」——没有的话，这个字段就不该由感知来定。

置信度 ≠ 时序一致性，别提前融合掉

面试里一个高频且很能区分人的追问：「你的 schema 里为什么要有 state 和 n_obs？置信度不是已经表达可靠性了吗？」标准答法：置信度是单帧证据强度，n_obs/state 是时间上的一致性，两者正交。一块牌子可以单帧 conf=0.95 但只出现过一帧（很可能是广告牌上的图案或一次瞬时误检），也可以单帧 conf=0.6 但连续 20 帧稳定跟踪（那几乎肯定是真的）。下游对这两种情况的处理完全不同：前者应该等，后者应该信。如果只传一个融合后的标量，你就永远无法在下游区分它们——而融合规则一旦写死在感知里，下游想改都改不了。这也是「置信度不要提前融合」这条更一般原则的一个实例。

还有一个务实的建议：把单位写进字段名（x_fwd_m 而不是 x，speed_kph 而不是 speed）。看起来啰嗦，但它把「单位错误」这一整类事故变成了不可能——而单位错误（米/厘米、m/s 与 km/h、度/弧度）在跨团队接口里是排第一的低级事故来源，且极难在代码评审里发现。这个约定对 LLM 尤其有价值：字段名本身就是给模型的提示，dist_m=82.4 比 dist=82.4 更不容易被误解成厘米。

3位置传什么：坐标系与距离的不确定度

schema 里最容易做错的一项是位置。三个候选，取舍很清楚：

坐标系内容优点致命问题何时用
图像像素 $(u,v,w,h)$检测框在图上的位置感知直接有，零成本下游要做反投影才能知道「多远」，而它没有内参外参；相机一换全部失效只在调试可视化时用
自车坐标 $(x_{\text{fwd}}, y_{\text{left}})$米，原点在后轴中心直接可用于「还有多远」「在哪条车道」；与相机无关需要距离估计，而距离估计有误差默认选择
BEV / 全局坐标地图坐标系下的位置可与高精地图先验融合、可跨帧累积依赖定位精度；定位漂移会污染感知输出有高精地图与高精定位时叠加提供

距离怎么来，误差有多大

单目相机估标志距离用针孔模型：焦距（像素）由分辨率与水平视场角决定，物理尺寸已知（中国的圆形限速牌直径通常 0.6 m 或 0.8 m），于是

\[f_{px} = \frac{W_{px}}{2\tan(\mathrm{FOV}_h/2)}, \qquad Z = \frac{f_{px}\cdot S}{w_{px}}, \qquad \frac{\mathrm{d}Z}{Z} = -\frac{\mathrm{d}w}{w}\]

最后那个式子是本节的关键：距离的相对误差等于框宽的相对误差。代入 1920×1080、$\mathrm{FOV}_h=60^\circ$ → $f_{px}=1662.8$，$S=0.6$ m：

框宽 $w$估计距离 $Z$1 px 误差 ⇒ 相对误差距离不确定度 $\sigma_Z$含义
60 px16.6 m1.67%±0.28 m近处，几乎精确
24 px41.6 m4.17%±1.73 m可用
12 px83.1 m8.33%±6.9 m远处，误差已达 7 米
8 px124.7 m12.5%±15.6 m只能当「那边有东西」用

直白说

所以「82.4 米」这个数字如果不带 $\sigma$，它就是在撒谎。下游看到 82.4 会以为精确到分米，实际上它可能是 75 也可能是 90。而这 15 米的差别在 30 m/s 下就是 0.5 秒的决策提前量——足以决定「现在开始平缓减速」还是「必须急刹」。更糟的是这个误差不是随机噪声，它是尺寸的确定性函数：越远越大、且是乘性的。下游只要拿到 bbox_wh_px 就能自己算出来——但前提是你把它传了。

严谨说

严谨地说，$Z = f S / w$ 在 $w$ 上做一阶传播得到 $\sigma_Z \approx (Z/w)\,\sigma_w = (Z^2/(fS))\,\sigma_w$——距离误差随距离的平方增长。$\sigma_w$ 的来源有三：检测框本身的定位误差（远处小框 ±1 px 是乐观估计）、标志物理尺寸 $S$ 的不确定（0.6 还是 0.8 m 的牌子？误判就是 33% 的系统性偏差）、以及相机标定误差。其中第二项常被忽略但影响最大：如果你不知道这块牌子的物理尺寸，单目就根本无法给出绝对距离——所以 schema 里的 cls 不只是语义，它同时是距离估计的先验。这也解释了为什么「先粗分类拿到尺寸先验，再精细分类」在 TSR 两级架构里是自然的（C55 模块 02）。

坐标系符号错误只在偏侧目标上暴露

一个真实且高频的接口事故：坐标系约定不一致。y 到底是「向左为正」还是「向右为正」？x 是「车头方向」还是「图像横轴」？角度是度还是弧度、逆时针还是顺时针？这类问题在同一个团队内靠口头约定还能撑住，跨团队（感知组 vs 规控组 vs 大模型组）必然出事——而且症状极其隐蔽：系统大部分时候是对的（因为多数标志在正前方，$y\approx 0$，符号错了看不出来），只在牌子明显偏一侧时才错，于是问题只在特定路段复现，查起来极痛苦。唯一可靠的做法是：把坐标系定义写进 schema_version 对应的文档，并在接口层加一个断言测试（放一个 $y_{\text{left}}=+5$ 的合成目标，检查下游认为它在左边）。这个测试写十行，能省掉一次线上事故。

4置信度必须传递：接口设计里最常见、代价最大的错误

这一节请当作整门课的重点。不传置信度，等于强迫下游把每一个检测都当成事实——而任何检测器的输出里都混着 10%–30% 的错误。接口一旦这样定，下游就永远没有办法把这部分错误挡住，因为信息在接口处就已经被丢掉了。

四个层次的错误，一层比一层隐蔽

  1. 不传：下游被迫全信。这是最粗暴、也最容易被发现的（一测就炸）。
  2. 传了，但只传一个融合后的标量：下游区分不了「单帧强证据」和「多帧弱证据」（见第 2 节），也区分不了「框准不准」和「类别对不对」。融合规则被锁死在感知里，下游想改也改不了。
  3. 传了，但没校准：0.9 实际只有 0.6 的正确率。下游用它做期望代价计算时，算出来的风险系统性偏低。
  4. 传了、校准了，但下游用固定阈值：阈值是拍脑袋定的（「0.7 听起来挺自信」），而不是从代价推出来的。这时候校准反而「显得没用」——因为调阈值能掩盖失准（见下面的 DUAL）。

校准是什么，以及它的度量

Calibration（校准）的定义很朴素：模型说 0.8 的那一批样本，实际正确率应该就是 80%。度量它的标准工具是 ECE（Expected Calibration Error，期望校准误差）——把样本按置信度分箱，算每个箱里「平均置信度」与「实际准确率」的差，再按箱内样本数加权平均：

\[\mathrm{ECE} = \sum_{m=1}^{M} \frac{|B_m|}{n}\;\Bigl|\;\underbrace{\mathrm{acc}(B_m)}_{\text{实际准确率}} \;-\; \underbrace{\mathrm{conf}(B_m)}_{\text{平均置信度}}\;\Bigr|\]

而下游要用它做的事，是一个期望代价最小化的决策。设采纳一个错误检测的代价是 $C_{\text{wrong}}$、拒绝并退到保守方案的代价是 $C_{\text{rej}}$，则「采纳」的贝叶斯最优条件是：

\[(1-p)\,C_{\text{wrong}} \;\le\; C_{\text{rej}} \quad\Longleftrightarrow\quad p \;\ge\; p^{\star} = 1 - \frac{C_{\text{rej}}}{C_{\text{wrong}}}\]

$C_{\text{wrong}}=10$、$C_{\text{rej}}=1.5$ 时 $p^\star = 0.85$。注意这个阈值是从代价算出来的，不是调出来的——而它成立的前提是 $p$ 真的是概率，也就是校准过的。notebook 会验证：在这个决策规则下，期望代价恰好在 ECE 最小（完全校准）时取到最小值，而「不传置信度」的基线代价比它高 97%。

直白说

这里有一个必须讲清楚、否则会被面试官问倒的微妙点：如果失准是单调的（比如温度缩放那种），而你又允许重新调阈值，那么决策完全不变。因为单调变换不改变排序，ROC 曲线一模一样，最优阈值只是平移了一下。这正是「我们调了调阈值就好了，所以校准没用」这个错误结论的来源——它在那个特定配置下确实「好了」。

严谨说

但这个补偿是脆弱且不可迁移的，三种情况下会立刻塌掉。①阈值是固定或共享的：下游按「0.7 = 挺可信」写死，或者多个消费者共用一个阈值；这时感知模型一升级、失准程度一变，所有下游行为同时漂移，而没人会想到去重调。②决策要用概率做算术：期望代价 $(1-p)C_{\text{wrong}}$、风险预算分配、代价不对称的门控——这些都直接用 $p$ 这个数值，而不只是它的排序，失准就是系统性的算错。③多源融合：把相机的 $p_1$ 和地图先验的 $p_2$ 相乘或做贝叶斯更新时，两个失准的概率相乘会把误差放大，而且方向不可预测。所以正确的说法是：校准不是为了让排序更好（它做不到），而是为了让「概率」这个数在下游可以被当作概率来算。

接口设计下游能做什么本例期望代价相对最优

接口一旦丢掉不确定性，下游永远补不回来

这是 JD 那条职责最核心的一句话，值得逐字记住：不传置信度不是「少传一个字段」，而是在接口层面永久删除了下游做风险决策的能力。下游收到 speed_limit_120 之后，如果没有伴随的概率，它只有两种选择：全信（于是感知的每一个误检都变成一次危险动作）或全不信（那要感知干什么）。而只要传了校准过的概率，下游立刻可以做「代价加权的采纳决策」，把 10 倍代价不对称的场景处理得完全不同——本模块 notebook 里的非对称门控把超速率降了 72%，用的就是这一个字段。面试里如果只有一句话的时间讲你对感知-决策接口的理解，就讲这一句。

不确定性不只是一个标量。一份完整的不确定性至少包含四样：①检测置信（这里有没有东西）；②分类分布（是什么，最好给 top-2 及其概率）；③几何不确定度（$\sigma_{\text{dist}}$，第 3 节）；④时序一致性（n_obs/state）。它们的下游用法完全不同：①决定要不要理会，②决定要不要表达「有两种可能」（呼应模块 02 的多模态），③决定提前量与安全裕度，④决定要不要再等几帧。把它们压成一个数，就是把四个正交的决策塌成一个。

5prompt 模板与稳定性：把接口当成协议来设计

符号级接口的物理形态是一段进入 prompt 的文本。而 LLM 对格式的敏感程度远超直觉：字段顺序、数值格式、分隔符、甚至空格数量的变化，都可能让同一份语义得到不同的输出。所以这段文本必须当成一个有版本、有校验、有兼容策略的协议来设计，而不是「拼个字符串给模型看看」。

三条铁律

铁律做法反例与它的具体后果
① 键值，不要位置track_id=4127|cls=speed_limit|value_kph=60|…位置式 4127|speed_limit|60|…：感知那边插入一个新字段，下游解析器会静默错位——把置信度读成距离，还不报错
② 字段顺序固定并写进版本顺序是 schema 的一部分，改顺序 = 升版本 = 重新评测「我只是把 conf 挪到前面，语义没变」：模型在训练时见到的是另一种顺序，注意力模式不同，输出会漂
③ 缺失值用显式 null，绝不用哨兵数值lane_assoc=null、dist_m=null用 -1 表示「距离未知」→ 下游的「忽略车后目标（dist<0）」规则把它静默丢掉。一个有效检测就这样消失了，且没有任何日志

还有四件必须定死的事

  • 数值格式：定点、固定小数位、单位在字段名里。60 / 60.0 / 6.0e+01 三种写法在 tokenizer 眼里是不同长度的不同 token 序列；训练时是 60.0、推理时变成 60，模型的行为就可能变。格式漂移属于训练-部署一致性问题（C60 的主题），只是发生在文本层。
  • 排序规则：目标按什么排？必须确定且稳定（如「先按 lane_assoc 分组，组内按距离升序」）。如果用哈希序或多线程完成序，同一帧跑两次会得到不同 prompt → 输出不可复现 → 任何 badcase 都无法稳定重放。
  • 截断策略：目标太多超 token 预算时丢谁？丢的规则必须与下游的安全逻辑一致——按距离截断会丢掉远处刚出现的限速牌（而那恰恰是需要提前决策的）；按置信度截断会丢掉低置信但高影响的目标。务实做法：按「安全相关性 × 距离」排序，并在 prompt 里显式写 truncated=true, n_dropped=7，让模型知道自己看到的不全。
  • 空场景的表示：一个标志都没有时传什么？传空字符串会让模型「看不到这个字段」从而依赖先验；传显式的 signs=[] (n=0) 才是「我确实看了，确实没有」。「没有证据」和「证据说没有」是两件事，接口必须能区分。

直白说

为什么这些看起来琐碎的约定值得写进课程？因为它们造成的故障有一个共同特征：静默。位置错位不报错、哨兵值被规则吃掉不报错、格式漂移不报错、排序不稳定不报错——它们全都表现为「模型有时候表现变差了」，而不是一个可以定位的异常。而排查这类问题的成本，通常是排查一个崩溃的几十倍。

严谨说

对应的工程手段也很清楚，而且都不贵：①渲染与解析必须成对实现并做 round-trip 测试（渲染出来再解析回去，字段必须逐一相等；这一个测试能挡住 80% 的模板事故）；②解析失败要 fail loud——宁可抛异常也不要「尽力猜」，因为猜错是静默的；③schema 版本进 prompt 的第一行，并在模型卡里记录训练时用的版本；④把一份「金标准 prompt」纳入回归测试，任何渲染改动都要 diff 它。这套做法与 C60 讲的训练-部署一致性是同一个方法论：把「约定」变成「可执行的检查」。

一句话概括本节：prompt 模板不是 UI，是 ABI。它是两个模块之间的二进制接口，只不过恰好长得像人话——而「长得像人话」正是它最危险的地方，因为它诱使人们随手改。

6错误传播与幻觉：VLA 会「合理化」一切喂给它的东西

现在假设接口设计得很好，但感知这一帧就是错了——报了一块根本不存在的「禁止驶入」。VLA 会怎么反应？答案是：它会生成一个完全自洽、有理有据、听起来无懈可击的绕行方案。

错误如何被「合理化」并放大 感知（错） VLA（忠实地条件生成） ┌────────────────────┐ ┌──────────────────────────────────────┐ │ cls = no_entry │──────►│ 「前方检测到禁止驶入标志，本车道不可 │ │ conf = 0.62 │ │ 通行。右侧车道空闲，建议提前变道并 │ │ lane_assoc = ego │ │ 减速至 40 km/h 后并线。」 │ │ **实际是广告牌** │ │ ↑ 语言流畅、逻辑自洽、**完全错误** │ └────────────────────┘ └──────────────────────────────────────┘ │ ▼ 高速上一次无理由变道 + 急减速 （后车追尾风险；用户信任崩塌） ★ 关键：**输出里没有任何一处表达「我不确定」**。 这是 silent failure ——比崩溃危险得多，因为没有任何信号触发兜底。

为什么会这样：条件生成没有「质疑输入」的机制

直白说

VLA 建模的是 $p(\text{动作} \mid \text{观测}, \text{感知输入}, \text{指令})$。它的训练目标里没有任何一项是「判断输入是否可信」——训练数据里的感知输入几乎总是对的（因为是离线标注或高质量回放），于是模型学到的是「感知说什么就是什么」。这不是模型的缺陷，是训练分布的必然结果：你没给它见过「感知错了，正确做法是保守」的样本，它就不会那么做。

严谨说

而语言模型的生成特性会把这个问题放大一层：它不仅接受错误输入，还会为它构造理由。因为流畅、自洽的解释在训练分布里是常态（人写的驾驶决策说明都是有理有据的），模型学到的是「给出决策就要配一段合理的解释」。于是错误被包装成了「有依据的判断」，反而更难被人工审核发现——一段写着「因为前方 60 米处有禁止驶入标志」的输出，比一段没有解释的输出看起来更可信。这是可解释性的一个反直觉的负面效应：解释的流畅度与决策的正确性无关，但人会把前者当作后者的证据。

两个方向的幻觉，要分开度量

类型定义怎么发生怎么度量与拦截
输入幻觉（被骗）感知报了不存在的东西，VLA 全盘接受并放大误检 + 下游无置信度门控度量：注入合成误检，统计下游动作错误率。拦截：置信度门控 + 非对称代价（第 7 节）
输出幻觉（编造）VLA 提到了感知输出里根本没有的实体语言先验太强（「路口通常有停车让行牌」）度量：解析输出中引用的实体，检查每个是否能对上一个 track_id。拦截：grounding 校验——引用不到就拒绝整条输出
沉默错误错了，且输出里没有任何不确定信号上面两者的共同后果度量：错误样本中「输出未表达不确定」的比例。这是最该被追踪的单一指标

输出幻觉的拦截手段值得展开，因为它便宜且有效：既然 schema 里每个目标都有 track_id，那就要求 VLA 的输出必须显式引用 track_id（「因为 track#4127 是限速 60，减速至 60」）。然后在输出侧做一次纯字符串校验：引用的每个 ID 是否都在本帧的输入里？不在就说明模型在编造，整条输出作废、走兜底。这个检查十几行代码、零延迟，却能把「模型凭空造出一块牌子」这类事故完全挡住——而且它同时给了你一个可日志、可统计的幻觉率指标。

级联的乘法

最后回到一个 C55 模块 02 讲过、这里必须重申的算术：端到端正确率是各环节正确率的乘积。

\[P_{\text{e2e}} = P_{\text{det}} \times P_{\text{cls}} \times P_{\text{assoc}} \times P_{\text{decide}}\]

每环 95% 的四环级联只有 81.5%。这意味着「把感知做到 99%」的边际价值，取决于其他环节现在是多少——如果车道关联只有 85%，把检测从 95% 提到 99% 带来的端到端提升不到 3.4 个点。而置信度传递之所以价值巨大，正是因为它打破了这个乘法：下游知道哪些环节这次不可靠时，可以选择不把错误往下传，而是退到一个已知安全的默认值。不传置信度 = 各环节的错误必然相乘；传了 = 下游有机会截断。

流畅的解释会制造它并不配得的信任

一个必须在设计阶段就想清楚的问题：VLA 的解释输出该不该给用户看？给看的好处是信任与可调试；坏处是「流畅的错误解释」会制造信任——用户看到「因为前方有施工标志」会倾向于相信系统真的看到了。务实的折中是：解释里必须带上它所依赖的感知证据与置信度（「依据：track#4127 限速牌，置信 0.62，距离 82±7 m」），让人看到的不只是结论，还有结论的脆弱程度。把不确定性一路透传到用户界面，是这条设计原则的终点。

7如何让 VLA 对低置信输入保持保守

知道了问题，来看手段。七种做法，按「在哪一层生效」排列——注意它们不是可选项列表，而是应该叠加使用的纵深防御。

层手段怎么做代价 / 边界
输入侧① 置信度门控低于阈值的检测不进 prompt，或进但标注为 uncertain=true阈值定低了漏、定高了噪；阈值必须从代价推导而不是拍脑袋

非对称门控：把代价不对称直接写进规则

第 ③ 条最值得展开，因为它是「置信度传递」的直接变现，也是最容易在面试里讲清楚的一个具体设计。核心观察：限速类约束的两个方向代价完全不同——

  • 把限速调低了（过度保守）：车开慢了。代价是效率与舒适，以及被追尾的间接风险。可恢复。
  • 把限速调高了（超速）：车开快了。代价是直接的安全与合规风险，且不可恢复（罚单已经开了，事故已经发生了）。

既然代价不对称，门槛就该不对称：「往安全方向走」用低门槛（$p \ge 0.30$ 就采纳），「往风险方向走」用高门槛（$p \ge 0.90$ 才采纳）。notebook 会把这个规则实现出来并量化：

对称阈值 0.70（校准）8.14%8.07%1.056−29%：光是「能拒绝」就有很大收益
非对称门控（校准）3.13%16.97%0.822−44%；超速率降 72%
非对称门控（过自信输入）6.99%11.02%1.030失准让收益打对折——门槛形同虚设
（参考）完全忽略感知，只用地图12.45%12.67%1.625比全采纳还差：感知确实有价值

直白说

这张表里最重要的是倒数第二行：同样的非对称门控规则，输入换成未校准的过自信置信度，加权风险从 0.822 涨到 1.030（+25%），超速率从 3.13% 涨到 6.99%（翻倍多）。因为「$p\ge0.90$ 才允许提速」这条规则的全部效力，都建立在「0.90 真的意味着 90%」上。过自信的模型把一堆实际只有 60% 正确率的检测标成了 0.92，门槛形同虚设。

严谨说

同时也要诚实地看到保守不是免费的：非对称门控把过度限速率从 11.4% 抬到了 17.0%。如果代价权重换一组（比如用户对「莫名其妙减速」极度反感，$C_{\text{under}}$ 权重加大），最优策略会不同。所以正确的做法不是「宁可错杀」，而是把 $C_{\text{over}}$ 与 $C_{\text{under}}$ 显式写下来，然后由代价推出门槛——这样当产品说「用户抱怨减速太频繁」时，你改的是一个有明确含义的代价参数，而不是去凭感觉挪一个阈值。把「拍脑袋的阈值」变成「可讨论的代价」，是这套方法论最实际的价值。

第 ④ 条（训练时注入带噪输入）是最容易被跳过、也最不能跳过的一条。前面三条都是外挂在模型之外的规则；如果模型本身从没见过「输入里带着 conf=0.4 的检测」这种情况，它就不知道该怎么用这个数字——你把置信度写进 prompt，它可能干脆忽略。正确做法是在训练数据构造阶段就注入合成感知误差（误检、漏检、错分、距离偏差），并把对应的专家动作标成保守的，让「低置信 → 保守」成为一个学到的行为而不是外加的规则。这也是评测时必须专门构造「感知错误」子集的原因——不然你根本不知道模型有没有学到。

把第 4 节与本节连起来的一句话：置信度传递创造了「拒绝」这个选项，而非对称门控决定了什么时候用它。没有前者，下游只有「全信」；有了前者但没有后者，下游只会对称地拒绝，白白丢掉大量安全方向上本可采纳的信息。

8面试标准答案骨架（JD 直接对应）

这一节直接对应 JD 里「设计感知输出接口以支持 VLA / 端到端模型」那条职责。五道题，覆盖了这条职责会被问到的全部角度。骨架的组织原则同前：先给判断，再给机制，然后给数字，最后给代价与边界。

Q1 · 你会怎么把 TSR 的输出接进 VLA？

项内容
面试官想听你知道有三个接入层次、各自的取舍，并且能给出一个混合方案而不是单选
40 秒骨架「三个层次。符号/文本级——把检测序列化成结构化文本进 prompt，可解释、可审计、与感知模块完全解耦，但有信息损失且 token 随目标数线性增长。特征级——ROI 特征投影成 token，信息全、成本低，但不可读。中间表示级——感知与 VLA 共享 BEV query，token 数固定、信息最全，是量产端到端的主流，代价是两边强耦合、误差无法归因。我会做混合：稠密几何走中间表示级，少量安全强语义（限速值、禁行、停车让行）额外走一条符号通路。判据是「这个信息出错以后需不需要事后说清楚」——需要就必须走符号级，因为事故调查要的是『系统当时认为限速是多少』这个明确答案，不是一组特征。」
加分点「符号级在调试与归因上的价值经常被低估：一次路测异常，打开那一帧的 prompt 五秒钟就能定位；BEV query 只能重跑消融。」
踩雷点只答「拼成文本塞进 prompt」；把「符号级」做成自然语言描述（token 贵 3 倍且无法严格解析）

Q2 · 你的 schema 里有哪些字段？为什么每一项都必须有？

项内容
面试官想听你能对每个字段说出「不传会发生什么具体故障」，而不是罗列字段名
40 秒骨架「除了类别和位置，有五项是最容易漏又最致命的。track_id——没有它，一块牌子的 10 帧会被当成 10 块牌子，也没法做「连续 N 帧确认才生效」。lane_assoc——判断这块牌子管不管我；不传就会把辅路限速 40 当成主路的，这是 TSR 下游最高频的实际事故，而且感知有车道线和 BEV，有能力回答；下游只有一个坐标，只能猜。value 独立成字段——「限速牌」和「限速 60」是两回事，把数值编进类别名会让类别数爆炸。sigma_dist——82 米这个数如果不带 ±7 米就是在撒谎。n_obs/state——置信度是单帧证据强度，时序一致性是另一个正交维度，单帧 0.95 出现一次 vs 连续 20 帧 0.6，下游处理完全不同。再加一个 schema_version，否则接口演进必然出静默错位。」
加分点「一条通用原则：接口边界应该划在『谁有能力回答这个问题』的地方——感知能算的不要留给下游；但『这块牌子该不该生效』涉及导航与法规优先级，感知不该越界猜。检验方法是问『如果这个判断错了，下游有没有信息纠正它』。」
踩雷点背字段清单但说不出故障场景；把单位省掉（dist 而不是 dist_m）

Q3 · 为什么置信度必须传？不传会怎样？

项内容
面试官想听这是这条 JD 最核心的一题。你要能说出「接口丢掉的信息永远补不回来」
40 秒骨架「不传置信度不是少传一个字段，是在接口层面永久删除了下游做风险决策的能力。任何检测器都有 10–30% 的错误率，下游拿不到概率就只有两种选择：全信（感知每个误检都变成一次危险动作）或全不信（那要感知干什么）。传了校准过的概率，下游立刻能做期望代价决策：采纳错误的代价 $C_w$、拒绝退保守的代价 $C_r$，最优阈值就是 $p^\star = 1-C_r/C_w$，这是算出来的不是调出来的。更进一步可以做非对称门控——降低限速低门槛、提高限速高门槛——我做过的实验里超速率降了 72%。而且要传的不止一个标量：检测置信、分类 top-2 分布、几何 σ、时序一致性，这四个是正交的，下游用法完全不同，压成一个数就是把四个决策塌成一个。」
加分点（很能加分）主动讲清楚那个微妙点：「单调失准 + 重调阈值 = 决策不变，这是『调调阈值就好了所以校准没用』的错觉来源。但三种情况会塌：①阈值固定或多消费者共享，模型一升级全线漂移；②决策要用概率做算术（期望代价、风险预算）；③多源融合把两个失准概率相乘。校准不是为了改善排序，是为了让概率这个数能被当作概率来算。」
踩雷点只说「置信度低就不要用」；说不出阈值该从代价推导；把校准说成能提升 AUC

Q4 · 感知错了，VLA 会怎样？怎么防？

项内容
面试官想听「合理化」与「沉默错误」两个词，以及可落地的拦截手段
40 秒骨架「VLA 会合理化错误输入——给它一块不存在的『禁止驶入』，它会输出一个完全自洽、有理有据的绕行方案，而且输出里没有任何一处表达不确定。这是 silent failure，比崩溃危险得多，因为没有信号触发兜底。根因是训练目标里没有『判断输入是否可信』这一项，训练数据里的感知输入几乎总是对的。要分开度量两种幻觉：输入幻觉（被骗）用注入合成误检来测下游动作错误率；输出幻觉（编造）用 grounding 校验——要求 VLA 输出必须显式引用 track_id，然后在输出侧检查每个引用是否存在于本帧输入，不存在就整条作废走兜底。这个检查十几行代码、零延迟。最该追踪的单一指标是『沉默错误率』：错了且输出未表达不确定的比例。」
加分点「还要防一个反直觉的效应：流畅的解释会制造它并不配得的信任。所以解释里必须带上依赖的证据与置信度（『依据 track#4127，置信 0.62，距离 82±7 m』），把不确定性一路透传到用户界面。」
踩雷点只说「加个安全兜底」；说不出输入幻觉与输出幻觉要用不同手段

Q5 · prompt 模板要注意什么？

项内容
面试官想听你把它当协议而不是字符串拼接；能说出静默故障的具体形态
40 秒骨架「三条铁律。①键值不要位置——位置式解析在感知插入新字段时会静默错位，把置信度读成距离还不报错。②字段顺序固定并写进 schema_version——改顺序等于改接口，要重新评测，因为模型训练时见到的注意力模式不同。③缺失值用显式 null，绝不用哨兵数值——用 -1 表示『距离未知』，下游『忽略车后目标』的规则会把它静默丢掉。再加四件事：数值格式定死（60.0 还是 60 是不同 token 序列，属于文本层的训练-部署一致性问题）、排序规则确定（否则同帧两次渲染出不同 prompt，badcase 无法重放）、截断策略与安全逻辑一致（并显式写 truncated=true, n_dropped=7）、空场景要能表达『我看了，确实没有』而不是什么都不写。工程上就一条：渲染与解析成对实现 + round-trip 测试，能挡掉八成模板事故。」
加分点「一句话总结：prompt 模板不是 UI，是 ABI——它恰好长得像人话，而这正是它最危险的地方，因为诱使人随手改。」
踩雷点答「多试几个 prompt 看哪个效果好」（那是调优，不是接口设计）

五题共用一组关键数字与短语，背下来即可：三个融合层次 · 「出错要不要说清楚」判据 · track_id/lane_assoc/sigma_dist · $p^\star = 1-C_r/C_w$ · 不传置信度 = 永久删除风险决策能力 · 非对称门控降超速 72% · 合理化与沉默错误 · grounding 校验 · prompt 是 ABI 不是 UI。

9研究前沿与开放问题

  • 符号接口与端到端的最终边界在哪？产业趋势明显在往中间表示级走（token 成本恒定、信息不过 schema 瓶颈），但可审计性与事故归因的需求不会消失。一个尚未解决的问题是：能否让端到端系统「事后生成」可审计的符号解释，且这个解释可证明地忠实于实际决策依据——目前的 post-hoc 解释都无法保证忠实性（模型可以给出一个与实际计算路径无关的合理解释）。这是可解释性研究里最硬的问题之一。
  • 不确定性的表示与传播。本模块讲的还是「每个目标一个标量 + 一个 σ」。真实的不确定性是联合的、结构化的：两块牌子是「二选一」还是「都在」？距离误差与类别误差相关吗？把完整的联合不确定性传给下游，token 成本会爆炸；只传边缘分布，下游就无法做正确的联合推理。这个取舍目前没有好的理论指导，工业界普遍只传边缘量。
  • LLM 到底会不会用置信度这个数字？把 conf=0.62 写进 prompt，模型是真的在做概率推理，还是只把它当成一个「弱化语气」的记号？已有证据表明 LLM 对 prompt 里的数值概率使用得相当粗糙，且对表述方式（数字 vs「可能」「大概」）高度敏感。「如何让模型正确使用输入的不确定性」目前主要靠在训练数据里构造对应样本，缺少更原理性的方法。这直接决定了第 7 节手段 ② 的天花板。
  • 感知与决策的联合优化 vs 接口稳定性。联合训练能让感知输出「决策真正需要的东西」而不是「人以为需要的东西」，收益明确；但它会让接口随训练一起漂移，模块化开发、独立评测、供应商分工全部失效。能否做到「训练时联合、部署时仍有稳定接口」，是量产组织形态与算法效率之间的真实矛盾，目前没有干净的答案。
  • 接口层面的对抗鲁棒性。如果感知输出是文本，那么一个被精心构造的场景（比如车身贴纸让检测器输出某个特定类别）就等价于一次 prompt injection。「物理世界的对抗样本 → 感知误检 → 文本注入 → VLA 行为被操纵」这条链路在学术上刚开始被研究，在工程上几乎没有防护。最低限度的防御是对序列化字段做严格的白名单与范围校验（不允许自由文本进入 prompt），但这只挡住了最粗糙的一类。
  • 校准在长尾与分布漂移下的维持。温度缩放这类后处理校准在同分布上很有效，但夜间、雨雾、新区域上校准会失效，而这些恰恰是最需要正确不确定性的场景。「分场景校准」（按天气/光照/距离分桶各校一个温度）是务实做法，但桶的划分本身又是一个开放问题，而且桶太细会导致每桶样本不足、校准本身过拟合。
