1为什么是 tile：两种朴素做法各自死在哪

目标：给定几十万个已投影成 2D 椭圆的高斯，算出 1920×1080 的图像。而 α 合成要求**每个像素上按深度有序**。有三种组织方式。

做法怎么做死在哪
逐像素对每个像素，找出覆盖它的高斯，排序，合成排序次数 = 像素数 = 207 万次。每次排序几十到几百个元素，而且相邻像素的排序结果高度重复——全是重复劳动
逐高斯按深度排一次全局序，然后从近到远把每个高斯「涂」上去不能提前终止（不知道哪个像素已经饱和了），而且写冲突严重——相邻高斯覆盖同一批像素，GPU 上是读-改-写竞争。更根本的是它无法做 $T$ 的串行累积
逐 tile（3DGS 的做法）把屏幕切成 16×16 的 tile；对每个 tile 收集覆盖它的高斯、排一次序；tile 内 256 个像素共享这一个顺序排序次数降到 8160 次，而代价是「tile 内共享顺序」这个近似（第 5 节）
1920x1080，16x16 的 tile： ceil(1920/16) = 120 列 ceil(1080/16) = 68 行 -> 8160 个 tile （1080/16 = 67.5，所以最后一行 tile 只用了 8 行像素） ┌────┬────┬────┬─ ... ─┬────┐ │ 0 │ 1 │ 2 │ │119 │ 每个 tile = 16x16 = 256 个像素 ├────┼────┼────┼─ ... ─┼────┤ GPU 上：一个 tile = 一个 block │120 │121 │ │ │ │ 一个像素 = 一个线程 ├────┼────┼────┼─ ... ─┼────┤ ... 256 个线程共享一份「排好序的高斯列表」 └────┴────┴────┴─ ... ─┴────┘ -> 从共享内存分批读，而不是各自去全局内存取

直白说

16×16 = 256 不是随便挑的：它正好是一个 CUDA block 的常用线程数，而 256 个线程刚好能协作把高斯数据分批载入共享内存。tile 太大 → 一个 tile 里的高斯列表太长、共享顺序的近似误差变大、而且提前终止的收益被摊薄（因为要等 tile 里最深的那个像素）；tile 太小 → 排序次数变多、每个高斯被重复登记到更多 tile 里。

严谨说

而「tile 内共享一个顺序」是 3DGS 的一个真实近似，不是实现细节。两个相互穿插的椭球，在 tile 的左半边 A 在前、右半边 B 在前，但它们在这个 tile 里只有一个顺序。相机转动时这个顺序会在某个角度突然翻转，画面「跳一下」——这就是 popping，StopThePop（2024）用分层/逐像素排序修它，代价是 2 倍左右的渲染时间。

2分箱与那个 64 位键

第一步：对每个高斯，算出它的 $3\sigma$ 包围盒覆盖哪些 tile，为每个 (高斯, tile) 组合生成一个条目。这个数字直接决定后面所有成本。

高斯数覆盖半径每个高斯覆盖的 tile 数(高斯,tile) 对总数每 tile 平均
100 k8 px4.000.40 M49.0
500 k4 px2.251.12 M137.9
500 k8 px4.002.00 M245.1
500 k20 px12.256.12 M750.6
1 M8 px4.004.00 M490.2

覆盖 tile 数 $\approx (2r/16 + 1)^2$。所以**半径从 8 涨到 20（2.5 倍），对数涨 3.06 倍**——而对数就是排序的输入规模。

这解释了模块 02 里 max_screen_size = 20 那个剪枝的第二重意义。它不只是为了控制仿射近似的误差（模块 02 第 4 节），更是为了控制排序成本——一个屏幕半径 100 px 的高斯要被登记到 $(200/16+1)^2 \approx 177$ 个 tile 里，抵得上 44 个正常大小的高斯。

键的设计：一次基数排序解决两件事

需要的顺序是「先按 tile 分组，组内按深度」。3DGS 的做法是把两者拼进一个 64 位整数：

uint64 key = (tile_id << 32) | depth_bits ┌──────────── 高 32 位 ────────────┬──────────── 低 32 位 ────────────┐ │ tile_id (0..8159) │ 深度（单调编码成 uint32） │ └───────────────────────────────────┴──────────────────────────────────┘ 对这个键做一次**基数排序**，结果自动就是「按 tile 分组、组内按深度升序」。 然后扫一遍找出每个 tile 的 [start, end) 区间即可。 官方实现：cub::DeviceRadixSort::SortPairs(...) —— 一次调用

直白说

为什么是基数排序而不是快排：基数排序是 $O(P)$，比较排序是 $O(P\log P)$。$P = 2\times10^6$ 时 $\log_2 P = 20.9$——比较排序要多做 21 倍的工作量级。而基数排序对 64 位键只需固定的几遍扫描（每遍处理 4–8 位），且完全没有分支——正好是 GPU 擅长的形状。

严谨说

而「深度用多少位」是一个有真实后果的选择，不是实现细节。位数不够时，不同深度的高斯会量化到同一个值，于是它们的相对顺序变成未定义（取决于排序是否稳定、以及输入顺序）。把深度范围 0.5–100 m 量化后，相邻键相等的比例：

深度位数相邻键相等（顺序未定义）的比例后果
16 位68.75%三分之二的相邻对顺序随机——而模块 01 量过，打乱顺序的中位偏差是 19.6%
20 位9.15%仍然明显
24 位0.585%大致可接受
32 位0.0025%官方的选择
官方实现的做法比「量化」更聪明：它直接把 float32 的深度按位重解释成 uint32。对正浮点数，IEEE 754 的位模式与数值是单调同序的——所以按 uint32 排序就等于按 float 排序，一位精度都不损失。而这个技巧只对正数成立，所以它依赖前一步的近平面剔除（$z > 0.2$）已经保证了深度为正——两个看起来无关的实现细节其实是耦合的。

3逐 tile 渲染：分批、共享内存、提前终止

每个 tile 的内层循环（256 个线程 = 256 个像素，同步推进）： T = 1.0; C = 0 for (batch of 256 gaussians in this tile's sorted range) { ─── 256 个线程协作，把这 256 个高斯的 (uv, Σ'⁻¹, α, color) 载入共享内存 ─── __syncthreads(); for (j = 0; j < 256; j++) { // 每个线程独立走这 256 个 alpha = α_j * exp(-0.5 * d^T Σ'⁻¹ d); if (alpha < 1/255) continue; // 太淡，跳过 if (T * (1-alpha) < 1e-4) { done = true; break; } // 提前终止 C += T * alpha * color_j; T *= (1 - alpha); } if (__syncthreads_count(done) == 256) break; // 整个 tile 都饱和了才退出外层 }

直白说

两个层次的提前终止要分清。① 线程级：某个像素饱和后它自己 break，不再累加——省的是算术；② block 级：只有当 tile 里全部 256 个像素都饱和了，才停止从全局内存载入下一批高斯——省的是访存。后者才是省时间的主项，而它要求整个 tile 一起饱和——所以一个 tile 里只要有一个像素看向天空（永不饱和），整个 tile 就要把列表走完。

严谨说

而收益的量级：模块 01 量过，$\alpha\in[0.1,0.7]$、$T_{\min}=10^{-4}$ 时，245 个高斯里只需处理 19 个——92.2% 的算术可以省掉，误差 $2.4\times10^{-5}$（远低于 8 bit 的 1/255）。但这是单个像素、且 $\alpha$ 都不小时的数字。notebook 在它自己那个含大片背景的场景上实测：省下 76.5% 的高斯-像素求值（均值从 34.4 降到 8.1）——低于 92.2%，因为该场景里 α 偏小、而且大片背景永远不饱和。而 block 级的收益还要更低，因为它取决于 tile 内最难饱和的那个像素。这是一个真实的、结构性的落差，不该含糊过去：92.2% 是理想上界，76.5% 是一个具体场景的实测，而访存的收益比两者都低。

$\alpha < 1/255$ 就跳过

这一行看着微不足道，但它与模块 02 的 $3\sigma$ 截断是同一件事的两面。$3\sigma$ 处的衰减因子是 $e^{-4.5} = 0.0111$，所以 $\alpha^{(g)} < 0.353$ 的高斯在 $3\sigma$ 处已低于 $1/255$——**对它们，包围盒的外圈本来就是白算的**。

4反向传播：重放、写冲突、以及必须存什么

模块 01 已经给出了 α 合成的梯度式。这里的问题是**怎么在 tile 结构上算它**。

需求为什么实现代价

写冲突的量级

高斯的屏幕半径覆盖的像素数反向时打到同一高斯的 atomicAdd 次数
4 px≈ 5050 × 59 个参数

直白说

这是 3DGS 训练比推理慢得多的主因之一，而它是结构性的。前向是「多个高斯 → 一个像素」（读多写少）；反向是「一个像素 → 多个高斯」（读少写多，且写地址高度重合）。官方内核的缓解手段是先在 block 内的共享内存里做归约，每个 tile 只对每个高斯发一次全局 atomicAdd——把 201 次降到「覆盖的 tile 数」次，即 4 次左右。

严谨说

而这又一次说明覆盖半径是主控变量：它同时决定了 ① (高斯,tile) 对数（第 2 节：半径 ×2.5 → 对数 ×3.06）、② 每 tile 的列表长度、③ 反向的 atomicAdd 次数。所以「剪掉屏幕半径过大的高斯」这一个操作同时改善了仿射近似的精度、排序成本、渲染成本与训练成本——在整套系统里很少见到这么划算的一个旋钮。

5整帧时延由最慢的那个 tile 决定

GPU 上一个 tile 对应一个 block。**block 之间没有同步，但整帧要等最后一个 block 结束。**所以有意义的量不是每 tile 的平均工作量，而是分布的尾部。

notebook 里量了两个场景。A 是一个平滑的、偏向画面下方的合成分布（20 万高斯、半径中位 6 px、1920×1080）；B 是 notebook 自己那个含「一面墙 + 一个近处物体」的场景。

均值136.134.4
中位11616

直白说

注意 B 比 A 差三倍多，而 B 才是真实场景的形状。A 的分布是平滑的，所以最大值只是均值的 2.67 倍；而 B 里有一个近处的物体压住十几个 tile，那几个 tile 的列表长是均值的 8.67 倍。所以「按均值估算帧时延」在平滑场景里低估 2.7 倍，在有近景的场景里低估近 9 倍——而任何有前景主体的场景都属于后者。空 tile（5–8%）的 block 几乎立刻退出，它们占的调度资源是浪费的，但代价很小，所以官方没做 tile 合并。

严谨说

而不均衡与提前终止有一个不太直观的互动。提前终止在「高斯多、$\alpha$ 大」的 tile 上收益最大（近处的实心物体，19/245 就停），而这些恰好是列表最长的 tile。所以提前终止不只是把平均值降下来，它同时把尾部压平了——这是两个收益，而后者对帧时延更重要。反过来，最糟的 tile 是「列表长、但 $\alpha$ 都很小」的那种：薄雾、半透明的植被、训练早期还没收敛的区域。

一个实际的性能坑：训练早期 FPS 极低，中后期突然变快。原因就是本节——初始化时所有高斯的 $\alpha$ 都被设成一个小值（官方用 0.1 的 inverse-sigmoid），于是没有任何 tile 能提前终止；等不透明度优化上来之后，92% 的工作才开始被省掉。所以拿训练早期的 iter/s 去外推总时长会严重高估。

6每帧的结构性账：钱花在哪，以及 tile 尺寸为什么是 16

下面是 500 k 高斯、覆盖半径 8 px、1920×1080 时每帧的操作计数。绝对毫秒数取决于硬件，所以这里只给计数与比值——而比值才是能迁移的那部分。

阶段规模每帧计数正比于
① 预处理（投影 + 协方差 + SH 求值）$O(N)$0.50 M 次高斯数
② 分箱（写 (高斯,tile) 条目）$O(P)$2.00 M 次写$P$
③ 基数排序（64 位键，8 位一遍）$O(P)$2.00 M × 8 遍 = 16.0 M 次扫描$P$
④ 载入（每 tile 的列表读一次）$O(P)$2.00 M 个条目 ≈ 72 MB 访存$P$
⑤ 渲染算术（不提前终止）$O(\text{像素}\times P/T)$508 M 次高斯-像素求值像素数 × 每 tile 列表长
⑤ 渲染算术（提前终止，每像素 19 个）同上39 M 次（省 92.2%）像素数 × 实际处理数

直白说

两个比值把整张账说清了。① $P/N = 4.0$——分箱与排序的规模是高斯数的 4 倍，所以「高斯数」不是成本的直接度量，$P$ 才是；② 渲染求值 / $P$ = 19.7（有终止）vs 254.1（无终止）。所以提前终止把「渲染」从压倒性的主项变成了与排序同一量级的一项——这也解释了为什么去掉它之后 3DGS 不只是慢一点，而是不再实时。

严谨说

而 tile 尺寸的取舍现在可以精确写出来。$P \propto (2r/T_s+1)^2$ 而 tile 数 $\propto 1/T_s^2$，所以每 tile 的列表长 $\propto (2r/T_s+1)^2 T_s^2$——两者往相反方向变，而 16×16 正好在拐点附近：

配置tile 数$P$每 tile 列表长
16×16（基准）81602.00 M（1.00×）245.1（1.00×）
8×8324004.50 M（2.25×）138.9（0.57×）
32×3220401.12 M（0.56×）551.5（2.25×）
高斯 ×2（16×16）81604.00 M（2.00×）490.2（2.00×）
半径 ×2.5（16×16）81606.12 M（3.06×）750.6（3.06×）
注意最后两行与前三行的性质完全不同。改 tile 尺寸是把成本在「排序」与「渲染」之间搬来搬去（一个 ×2.25、另一个 ×0.57，乘积几乎不变）；而改高斯数或覆盖半径是两项一起涨。所以 tile 尺寸只能调优，而剪枝（控制半径与数量）才能真正降成本——这就是模块 04 的题目。

7怎么验证一个光栅化器是对的

这一节讲方法，因为 notebook 里就是这么做的，而它对任何自己动手改内核的人都适用。

  1. 与逐像素暴力实现逐位比对——先把近似列全。tile 版一共有三个近似，而第三个最容易漏：① 提前终止；② tile 内共享顺序；③ $3\sigma$ 包围盒是 tile 对齐的——tile 版对该 tile 里的每个像素求值，哪怕那个像素在高斯的精确包围盒之外。所以暴力版必须用同一个判定集合才能逐位比对——notebook 里的做法是让暴力版独立地对每个像素判断「它所在的 tile 是否落在这个高斯的 tile 区间内」，完全不用分箱的输出，于是这才是一次真正的交叉验证。这样做之后两者严格相等到机器精度。而第三个近似本身的影响：把包围盒整体去掉，最大图像差是 $1.95\times10^{-3}$，即 0.50 个 8 bit 色阶——小但不为零，且与模块 02 算的「3σ 处 α 衰减 0.0111」量级完全对得上
  2. 关掉近似做消融。$T_{\min}=0$、tile 尺寸 = 1×1（退化成逐像素）、$3\sigma$ 截断改成 $\infty$。每关掉一个，差应当降到零
  3. 梯度用数值差分核对（模块 01 练习 3 的做法）。但要注意：提前终止让损失对参数不再光滑——在终止点附近，数值差分与解析梯度会不一致，而这不是 bug
  4. 顺序不变性的反向检查。把输入高斯的数组顺序打乱（不是深度顺序），渲染结果应当不变（因为会重新排序）。如果变了，说明排序键有相等项而排序不稳定——这正好抓住第 2 节那个深度位数问题
  5. 确定性检查。同一份输入跑两遍，输出必须逐位相同。如果不是，说明某处依赖了哈希顺序、未初始化内存，或（在 GPU 上）依赖了 atomicAdd 的完成次序——而最后一种在反向传播里几乎必然发生，所以「梯度不确定」是正常的，「前向不确定」不是
  6. 能量守恒检查。$\sum_i T_i\alpha_i + T_{\text{final}} = 1$ 必须逐像素成立到机器精度（模块 01 第 0 节）。提前终止会破坏它，而破坏的量正好是 $T_{\min}$ 的上界——所以它也是一个可验证的量
那为什么不干脆逐像素排序，把 popping 彻底解决？算一下就知道。1920×1080 有 207 万个像素，而 tile 只有 8160 个——排序次数差 254 倍。而每次排序的元素个数只从「每 tile 245 个」降到「每像素几十个」，降不了 254 倍——所以逐像素排序的总成本高一个数量级以上。StopThePop（2024）的折中是「分层」：在 tile 内按 2×2 或 4×4 的子块重排，只对顺序真正会翻转的那些高斯做局部修正，代价约 2 倍渲染时间，换来 popping 基本消失。
第 4 条值得单独记住，因为它把一个看不见的 bug 变成了一行测试。「打乱输入顺序，输出应不变」——如果深度用 16 位量化，68.75% 的相邻对会因为键相等而顺序未定义，于是这条测试立刻失败。而如果只看图像质量指标，这个 bug 会表现为「PSNR 差了 0.5 dB」，谁也不会想到是排序键的位数。
